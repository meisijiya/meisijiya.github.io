🎯 Aligo 商旅助手 — 项目浓缩版（STAR 法则）

生成日期：2026-09-10
来源：6 份知识卡片（docs/知识模型/）+ 30 道面试弹药 + 9 步流水线
用途：简历项目栏 + 面试 30-60-90 法则口述稿 + Agent 开发岗 / 传统开发岗 双版本
核心聚焦：AI 框架（Plan-and-Execute 多智能体）+ 业务设计（差旅规划 5 大子能力）

一、项目一句话介绍（30 秒结论）

Aligo 是基于 LLM 语义理解的多智能体差旅规划系统。采用 Plan-and-Execute 架构，通过 6 类意图识别 + 优先级并行调度（asyncio.gather），将端到端响应时间从 30s 优化到 15s。集成两层记忆（10 轮滑动窗口 + JSON 持久化 + LLM 异步总结）与 RAG 知识库（Milvus Lite + BGE Embedding），跨会话偏好准确率达 **95%**。配套 4 道韧性防线（熔断器三态 + 指数退避 jitter + 6 层 JSON 回退 + SkillLoader 双查找），LLM 服务异常时自动降级。

技术栈：Python 3.11 · AgentScope（多智能体框架）· 豆包/OpenAI 兼容 LLM · Milvus Lite · BGE-small-zh-v1.5 · asyncio · Rich · pytest

代码规模：核心代码 3000+ 行，6 大子系统，7 个测试文件，11 份知识卡片

二、STAR 法则项目描述（4 段式 · 简历直接用）

🌟 S - Situation（业务背景）

企业差旅规划场景的痛点：

维度 传统方案 Aligo 方案
交互方式 App 填表（10+ 字段） 自然语言一句话
个性化 每次重复填写偏好 跨会话记忆（95% 准确率）
知识查询 翻文档 / 问 HR RAG 知识库（准确率 95%）
行程规划 手动拼装（航班+酒店+行程） LLM 自动生成（端到端 15s）
稳定性 LLM 挂了全系统卡 30s+ 熔断 + 降级（用户立即收到提示）

目标用户：经常出差的白领 / 企业差旅管理员

项目定位：1 个杀手级项目 = 撑 Agent 开发岗 + 传统 Python 后端开发岗 双方向

🌟 T - Task（核心任务）

独立设计并实现基于 LLM 语义理解的多智能体差旅规划系统，覆盖：

  1. 5 大业务子能力：意图识别、行程规划、记忆管理、知识问答、联网搜索
  2. 6 大子系统：核心编排层 / Skill 插件系统 / 双层记忆 / 稳定性保障 / CLI 入口 / 测试与知识库
  3. 核心架构挑战：
    • LLM 输出格式不稳定 → 6 层 JSON 解析回退
    • 多 Agent 协同 → Plan-and-Execute + 优先级并行调度
    • 第三方服务不稳定 → 熔断 + 重试 + 健康检查三级保障

🌟 A - Action（关键行动 · 4 大亮点）

🎯 亮点 1：AI 框架 — Plan-and-Execute 多智能体编排

设计：单一 LLM 调用同时完成意图识别 + 调度决策，节省 latency

核心实现：

关键设计决策：

  • ✅ 单一 LLM 同时完成意图识别 + 调度（节省 1 次 LLM 调用 latency）

五、面试 30-60-90 法则演练稿（核心 10 题）

Q1：用 1 分钟介绍下这个项目

30 秒：

“Aligo 商旅助手是基于 LLM 语义理解的多智能体差旅规划系统，Plan-and-Execute 架构，6 类意图识别 + 优先级并行调度，响应时间 30s→15s，启动 3 秒。”

60 秒：

“技术栈是 Python + AgentScope + 豆包大模型 + Milvus + BGE。用户说一句’3月11日北京去杭州出差一周’，系统自动识别意图（行程规划 + 偏好管理 + 知识查询）、并行调度 6 个 Skill 智能体、整合记忆和知识库、生成完整行程。准确率 90%+。”

90 秒：

“重点说两个亮点：① 优先级并行调度——priority 1 的 4 个 Agent 并发跑，把 30s 优化到 15s（-50%）；② 4 道韧性防线——熔断器三态机（连续 5 次失败 OPEN）+ 指数退避 jitter（1s/2s/4s 退避 + 抖动）+ 6 层 JSON 回退解析 + SkillLoader 双查找，LLM 服务挂掉时用户立刻收到降级提示而不是卡 30 秒。”

Q4：什么是 Plan-and-Execute 架构？和 ReAct 有什么区别？

30 秒：

“Plan-and-Execute = 先规划后执行。LLM 先生成完整调度计划，再按计划调度子 Agent。ReAct = 思考-行动-观察循环，边想边做。”

60 秒：

“Plan-and-Execute 适合’步骤明确’的多 Agent 任务（比如 6 类意图分好优先级），ReAct 适合’边做边探索’的工具调用任务（比如数学推理 + 搜索）。Aligo 用 Plan-and-Execute，因为意图识别可以一次性给出完整 schedule（priority + skill name），不需要边执行边调整。”

90 秒：

“实现细节：IntentionAgent 一次 LLM 调用输出 JSON {"intents": [...], "agent_schedule": [{"name": "memory_query", "priority": 1}, ...]}，OrchestrationAgent 按 priority 排序、分批、每批 asyncio.gather 并发。return_exceptions=True 让一个 Skill 挂了不影响其他。挖出的潜规则：len(agent_schedule) == 1 时走非并行分支（gather 的小优化）；priority fallback 值不统一（0 vs 999 在不同分支用）。”

Q9：什么是意图识别？为什么用 LLM 而不是规则？

30 秒：

“识别用户想做什么。LLM 准确率 90%+，规则匹配 65%。”

60 秒：

“规则方案：关键词匹配，比如”想去”→ 行程规划，”我喜欢”→ 偏好管理。问题：长尾 query 覆盖不全（”我搬家到上海了” 隐含 home_location 变更）、歧义难处理（一句话多个意图）。LLM 方案：语义理解，能处理隐含意图，准确率 90%+。”

90 秒：

“实现细节：两段式 Prompt——先让 LLM 输出 reasoning（它怎么理解用户），再输出 JSON 决策（intents + agent_schedule）。6 类意图：itinerary_planning / memory_query / preference / rag_knowledge / information_query / event_collection。LLM 输出不稳定，用 6 层 JSON 回退解析（直接解析 → 去 fence → 去控制字符 → 单/双引号修复 → 去尾逗号 → json5 兜底）。”

Q13：怎么实现 Agent 的并行调度？

30 秒：

“asyncio.gather(*tasks, return_exceptions=True)，同 priority 并发。”

60 秒：

“所有 Skill 的 reply() 都是 async def，调用时返回协程对象。gather 统一调度，返回 list。return_exceptions=True 让一个 Skill 失败不中断其他，返回值是 list of 结果或异常。”

90 秒：

“实现细节：手写批次 flush 循环——按 priority 排序 → 分组（相同 priority 一起跑）→ 每批 gather → 收集结果 → 下一批。return_exceptions=True 后在 _execute_parallel_agents 里 isinstance(result, Exception) 检查，转成 {"status": "error"} 继续处理。挖出的坑：单 task 时 len(agent_schedule) == 1 走非并行分支（gather 的小优化）。”

Q14：什么是优先级调度？为什么需要？

30 秒：

“不同 Agent 有依赖关系——行程规划依赖信息收集。先并行 P1，再串行 P2。”

60 秒：

“P1（信息收集，互不依赖）→ P2（行程规划，依赖 P1）。实现：按 priority 排序，分组并行。好处：既快（并行）又对（串行）。”

90 秒：

“性能数据：4 个 P1 Agent 并发，从 3.2s 优化到 1.2s（max），整体 30s→15s。挖出的坑：priority fallback 值不统一——有的地方用 0 兜底，有的地方用 999 兜底，重构时易踩。”

Q17：为什么需要两层记忆？

30 秒：

“短期 = 当前会话上下文；长期 = 跨会话用户信息。单层不够。”

60 秒：

“纯短期 → 跨会话失忆（用户偏好记不住）；纯长期 → 单次会话上下文爆炸（每次调 LLM token 数爆）。两层组合：短期滑动窗口（10 轮 × 2 条 = 20 条 Msg）+ 长期 JSON 持久化（preferences + trip_history + chat_history）。”

90 秒：

“实现细节：短期用内存 List，超出 max_turns * 2 时切片 self.messages[-max_turns*2:]。长期用 JSON 文件，_migrate_data() 三道关卡（补字段 / dict→list / 解嵌套 bug）保证版本兼容。每次请求把长期 + 短期 5 轮 + 当前问题拼给 LLM。挖出的坑：JSON 无并发锁、多用户同 user_id 写会丢数据；token 无分块、超长对话超 LLM 上限。”

Q21：什么是 RAG？为什么需要？

30 秒：

“Retrieval-Augmented Generation，检索增强生成。让 LLM 用企业私域知识回答。”

60 秒：

“LLM 不知道企业差旅标准、报销政策。RAG：先检索相关文档 → 再让 LLM 基于文档生成。优点：① 不需要重新训练模型；② 答案可溯源（带文档引用）；③ 数据更新即时生效。”

90 秒：

“Aligo 用 Milvus Lite + BGE Embedding。BAAI/bge-small-zh-v1.5 是 512 维中文向量，本地 90MB 可跑。文档切分 600 字 + 100 overlap，Top-K=3 余弦相似度检索。Prompt 强约束：’如果【知识库信息】中没有包含回答用户问题所需的信息，请直接回答抱歉，知识库中没有找到相关信息，不要尝试根据你自己的知识编造答案’——这是企业级 RAG 的硬约束。”

Q24：什么是 Skill 插件化？有什么好处？

30 秒：

“每个子 Agent 是独立 Skill（目录 + SKILL.md + agent.py），4 个好处。”

60 秒：

“4 个好处：① 解耦（不重启主程序即可新增）；② 复用（不同项目共用 Skill）；③ 隔离（一个 Skill 错误不影响主程序）；④ 可测试（独立测每个 Skill）。”

90 秒：

“Aligo 6 个 Skill：ask-question（差旅知识库）/ event-collection（行程要素提取）/ memory-query（记忆查询）/ plan-trip（行程规划）/ preference（偏好管理）/ query-info（信息查询）。共性契约：继承 AgentBase + reply() 全 async + model=model 单例复用 + Progressive Disclosure 动态读 SKILL.md。挖出的坑：skill_mapping 把连字符映射到下划线，加新 Skill 时命名空间不统一。”

Q25：什么是懒加载？怎么实现的？

30 秒：

“用到才加载。LazyAgentRegistry 启动时扫元数据，用到时 importlib 加载。”

60 秒：

“实现：LazyAgentRegistry.__getitem__() 里检查 self.cache（dict），未命中则动态 importlib.util.spec_from_file_location() 加载，再 inspect.getmembers() 找 AgentBase 子类实例化。结果：启动时只加载 IntentionAgent 和 OrchestrationAgent，6 个 Skill 按需加载，启动 3 秒。”

90 秒：

“Progressive Disclosure 模式：每个 Agent 构造时实例化 SkillLoader，reply() 时调 skill_loader.get_skill_content(<skill_name>) 动态读 SKILL.md 中的’任务说明’段（不在 prompt 里硬编码）。优势：SKILL.md 修改不用重启主程序；按需加载节省内存。”

Q26：什么是熔断器？为什么需要？

30 秒：

“熔断器 = 防止雪崩的开关。连续失败 N 次后’打开’，直接拒绝调用（保护下游），过一段时间后’半开’试探，成功 N 次则’关闭’恢复。”

60 秒：

“需要它的原因：LLM 服务挂掉时如果不熔断，每个请求都会等超时（30s+），整个系统雪崩。三态机：CLOSED（正常）→ OPEN（拒绝，60s 后）→ HALF_OPEN（试探，2 次成功恢复）。”

90 秒：

“实现细节：CircuitBreaker.record_failure() 在 CLOSED 状态计数 +1，达到阈值（5 次）转 OPEN；HALF_OPEN 状态任何失败立刻回 OPEN（不消耗试探额度）。惰性恢复：仅在访问 state 时检查是否到恢复时间，零开销。配合 retry_with_backoff 用：重试全失败 → 熔断器计数 +1。”
