0. STAR 法则使用模板

每个亮点按下面四段结构组织,面试时照着讲 60~90 秒:

段落 时间占比 讲什么 关键词
Situation 10% 项目背景 + 这个亮点要解决的”痛点” 业务场景 / 已有方案的局限
Task 10% 我承担的目标 / 要达成的可观测指标 个人职责 / 量化目标
Action 60% 我做了哪些事,关键决策与取舍,踩过的坑 技术选型 / 代码细节 / 调参过程
Result 20% 结果数据 + 反思 + 可推广的经验 量化收益 / 后续优化方向

记忆口诀:S 是背景,T 是目标,A 讲干了啥,R 看效果。

一、业务设计(S 业务驱动 → T 设计目标 → A 架构决策 → R 工程结果)

1.1 启动类三层注解装配

S(背景):Spring Boot 项目启动类只一行 SpringApplication.run,但项目里有缓存、AI、MyBatis、限流四套 Bean 要装配。如果启动类只标 @SpringBootApplication,会出现 LangChain4j starter 自动装配 RedisEmbeddingStore 而本项目没有 EmbeddingModel Bean,导致 NoSuchBeanDefinitionException。

T(目标):用最少注解把缓存、AI、ORM 三个子系统装配起来,并消除自动装配冲突。验收标准:启动无报错、@Cacheable 生效、所有 Mapper 注入成功。

A(做了什么):

三个注解正交职责:缓存 / 装配 / ORM 扫描各管一摊。exclude 处理 LangChain4j 社区 Redis starter 的”多余 EmbeddingStore 自动装配”——本项目只用 ChatMemory,不需要 RAG。

R(结果与反思):

  • ✅ 启动无冲突,后续 @Cacheable("good_app_page") 在 AppController 直接生效。
  • ✅ @MapperScan 让 AppMapper / UserMapper / ChatHistoryMapper 自动注册,无 NoSuchBean。
  • 💡 反思:exclude 写错类名会导致 Bean 缺失或启动失败;@MapperScan 路径错会全 Mapper 注入失败——这是常见踩坑点。

面试话术(60 秒):启动类三个注解各管一摊,缓存/装配/ORM 解耦;exclude 处理 LangChain4j 自动装配冲突,体现”只引入项目真正用到的部分”的依赖边界意识。

1.2 AppController 三层权限模型

S(背景):AI 应用生成平台有三种角色——游客(看精选应用)、登录用户(生成自己的应用)、管理员(管理所有应用)。如果权限校验写在每个方法里,代码会重复且容易漏。

T(目标):用声明式注解 + 拦截器 + 业务内 equals 三种粒度,把权限校验和业务代码解耦。验收标准:游客看不到别人的应用,管理员能管理全部,本人能改自己的。

A(做了什么):

层级 实现 适用场景 代码位置
注解拦截 @AuthCheck(mustRole=ADMIN_ROLE) 管理员后台接口 aop/AuthInterceptor.java(@Around("@annotation(authCheck)"))
注解限流 @RateLimit(USER, 5, 60s, ...) AI 对话等高成本接口 ratelimter/aspect/RateLimitAspect.java
业务内 equals app.getUserId().equals(loginUser.getId()) 下载/修改本人应用 AppController.downloadAppCode

SSE 聊天端点完整代码(_recon/code-fact-L-app-controller.md 第 65-83 行):

统一校验范式:ThrowUtils.throwIf(条件, ErrorCode, msg) 一行替代 if-else,所有接口一致。

R(结果与反思):

  • ✅ 12 个端点统一鉴权,无任何”忘记校验”的灵异 bug。
  • ✅ SSE 结束帧 event("done") 让前端明确判定流是否结束,避免半包问题。
  • ⚠️ 易踩坑:downloadAppCode 用 String.valueOf(appId) 当文件名,若部署多个 app 会有同名冲突;chatToGenCode 自定义 {"d": chunk} 协议,前端必须按 data.d 取值。

面试话术(60 秒):权限分三层——注解(AOP)、拦截器、业务 equals,粒度由粗到细;SSE 用 event("done") 结束帧而非依赖连接关闭,更可控。

二、LangGraph 使用(S 痛点 → T 目标 → A 节点装配 + 三入口 → R 业务效果)

2.1 为什么用 LangGraph4j 取代函数链

S(背景):第一版 AI 代码生成是直接调 AiService.generateVueProjectCodeStream(appId, prompt),模型一次性写完。但出现三类问题:① 漏步骤(没收集图片直接生成);② 语法错(没人质检);③ 无法重试(失败只能让用户重发)。

T(目标):把 AI 代码生成拆成”可重入 + 可分支”的图,每个步骤可观测、可重试。验收标准:质检失败自动重生成,图片自动采集,Vue 项目自动打包。

A(做了什么):引入 org.bsc.langgraph4j,把流程拆成 6 个节点 + 1 个并发 reducer + 1 个 plan 节点。LangGraph4j 是 AI 场景专用,天然支持 MessagesState、流式节点输出、异步条件边——比 Spring State Machine 更适合。

R(结果与反思):

  • ✅ 质检失败自动回流 code_generator,无需用户重发。
  • ✅ 图模型比 if/else 嵌套可视化、易扩展、易测试。
  • 💡 反思:LangGraph4j 学习曲线比纯函数链陡,但换来”每步可观测、出问题能定位到具体节点”的运维价值。

面试话术(60 秒):直接调 LLM 一次性生成,缺步骤/无法重试/无可观测性。改用 LangGraph4j 状态机后,每步有日志、可重试、可条件分支——这是图模型比函数链的核心优势。

T(目标):把”图像收集 → 提示词增强 → 路由 → 生成 → 质检 → 构建”六个职责拆成六个节点,各司其职、可独立测试。

2.5 Java 21 虚拟线程

S(背景):SSE 长任务用传统 new Thread().start() 会占满平台线程(8MB/个)。LLM 调用本身就是阻塞的(等 HTTP 响应),如果用 Reactor 又要求全链路非阻塞,改造成本高。

T(目标):用同步写法实现”异步性能”,M 级并发不爆栈。验收标准:长任务不阻塞平台线程池,LLM 阻塞调用安全。

A(做了什么):全用 Thread.startVirtualThread(() -> { ... }) 启动虚拟线程:

  • 避免阻塞平台线程(虚拟线程是轻量级协程)。
  • 避免手写 ThreadPoolExecutor 的 core/max/queue 参数。
  • 兼容阻塞调用(LLM 调用本身就是阻塞)。

R(结果与反思):

  • ✅ 每个工作流实例独占一个虚拟线程,几毫秒启动,M 级并发不爆。
  • ✅ “同步写法 + 异步性能”——Java 对抗 Kotlin 协程 / Go goroutine 的官方答案。
  • ⚠️ Pinning 风险:synchronized 块会把虚拟线程 pin 到平台线程。本项目工作流里没大量 synchronized,所以安全。

面试话术(60 秒):虚拟线程 = “同步写法 + 异步性能”。Java 21 的虚拟线程让 LLM 阻塞调用不浪费线程池,这是 Java 生态对协程时代的回应。

三、LangChain4j 连接点(S 注解驱动 → T AI Service 装配 → A 工厂缓存 + 工具调用 → R 性能与稳定性)

3.1 “接口即服务”模式

S(背景):传统 AI 集成写法是”new ChatClient → 手动构造消息 → 手动处理流 → 手动管理 memory”。重复样板代码多,每个项目重写一遍。

T(目标):用接口 + 注解声明 AI 能力,框架运行时用动态代理生成实现。验收标准:开发者只定义接口,LangChain4j 自动装配。

A(做了什么):AiCodeGeneratorService 接口(/com/yupi/yuaicodemother/ai/AiCodeGeneratorService.java),5 个方法:

四个注解分工:

  • @SystemMessage(fromResource=...) —— 加载 classpath 资源作为系统提示词。
  • @UserMessage —— 把方法参数标为 user role。
  • @MemoryId —— 按 appId 隔离对话记忆。
  • 返回类型决定链路:HtmlCodeResult → 结构化非流式,Flux<String> → Reactor 流,TokenStream → 流式 + 工具回调。

R(结果与反思):

  • ✅ 接口无实现类,运行时 AiServices.builder().build() 动态代理生成——“类型驱动”的优雅。
  • ✅ Prompt 用 fromResource 加载外部 txt,便于版本管理、按租户覆盖、A/B 实验。
  • ⚠️ @MemoryId 漏写会导致多用户对话记忆串台;返回类型选错(TokenStream vs Flux<String>)会导致工具回调事件丢失。

面试话术(60 秒):LangChain4j 的”接口即服务”是 1.x 最优雅的设计。开发者定义接口,框架运行时用 JDK 动态代理生成实现,注解驱动对话记忆/工具调用/流式分发——改返回类型就改行为。

3.2 AiCodeGeneratorServiceFactory 双过期缓存

S(背景):AiServices.builder(...).build() 非常重——要装配 ChatModel、Memory Provider、Tool 列表、Guardrail 链。如果每次请求都重建,延迟会爆。

T(目标):按 (appId, codeGenType) 缓存装配好的 AI Service 实例。验收标准:第一次创建,后续命中缓存;写后 30 分钟硬过期,访问后 10 分钟滑动过期。

A(做了什么):Caffeine 本地缓存(AiCodeGeneratorServiceFactory.java 第 51-58 行):

双过期策略:expireAfterWrite 应对冷数据,expireAfterAccess 应对热数据,两者取先到——防雪崩模板。Key 是 appId + "_" + codeGenType.getValue()(如 "123_vue_project"),保证不同类型不撞车。

R(结果与反思):

  • ✅ 重对象(装配好的 AI Service)不再每次重建,首次创建后命中纳秒级延迟。
  • ✅ 不需要 Redis,本地缓存省网络 IO;AI Service 本身已 1-3 秒,本地缓存省 1ms 实际效果最大化。
  • ⚠️ 缓存键漏掉类型会导致不同 codeGenType appId 撞车;MessageWindowChatMemory.id(appId) 不传会导致所有用户共享同一记忆。

面试话术(60 秒):本地缓存有纳秒级延迟、无网络跳转优势,适合 AI Service 这种重对象 + 单机用场景。Caffeine 双过期策略是防雪崩的经典模式——expireAfterWrite 防冷数据堆积,expireAfterAccess 保热数据不被踢。

3.3 VUE_PROJECT 分支 + hallucinatedToolNameStrategy

S(背景):VUE_PROJECT 类型需要 AI 自主决定”什么时候调 readFile、什么时候调 fileModify”,这就是 Agent。同时 LLM 偶尔会”幻觉”出不存在的方法名,如果直接抛异常,整个生成就崩。

T(目标):VUE_PROJECT 分支注入工具链,加上”工具名幻觉”兜底。验收标准:AI 能自主调工具,工具名错能自我修正。

A(做了什么):VUE_PROJECT 分支装配(AiCodeGeneratorServiceFactory.java 第 60-74 行):

多例 Bean(Prototype):reasoningStreamingChatModelPrototype 用 @Scope(prototype) 而非单例,因为流式模型内部维护 SSE/Flux 通道状态,跨请求复用会串台。

R(结果与反思):

  • ✅ VUE_PROJECT 能自主调 6 个工具(读/写/删除/修改/列目录/退出)。
  • ✅ hallucinatedToolNameStrategy 把”工具名错误”作为工具结果回填,LLM 自我修正。
  • ✅ maxSequentialToolsInvocations(20) 防 LLM 死循环(如反复读同一文件)。
  • ⚠️ Prototype 模式 + SpringContextUtil.getBean 写法不如字段注入优雅,是历史包袱。

面试话术(60 秒):VUE_PROJECT 分支注入工具链 + hallucinatedToolNameStrategy 兜底,体现”给 LLM 反馈通道让它自我修正”的工程级 AI 系统核心策略。

3.4 BaseTool + @Tool + ToolManager

S(背景):LangChain4j 的 @Tool 注解方法要被 LLM 调用,但每个工具方法签名差异大、需要统一注册中心、且要把工具执行结果持久化到数据库。

T(目标):用抽象基类统一工具契约,Spring 自动发现所有 BaseTool 子类,ToolManager 一次性塞给 LangChain4j。验收标准:新增工具零配置,LLM 能调,执行结果可持久化。

A(做了什么):

BaseTool 抽象基类(ai/tools/BaseTool.java):

FileReadTool 实现(ai/tools/FileReadTool.java):

三个注解分工:

  • @Tool("读取指定路径的文件内容") —— description 是给 LLM 看的,决定 LLM 何时调它。
  • @P("文件的相对路径") —— 参数语义描述,LLM 据此填参数。
  • @ToolMemoryId Long appId —— 按 appId 隔离会话记忆。

ToolManager:List<BaseTool> 注入所有 @Component 子类,getAllTools() 返回 Object[]。

R(结果与反思):

  • ✅ 6 个工具(BaseTool + 4 个 File*Tool + ExitTool + 4 个 langgraph4j/tools/*Tool)Spring 自动发现,新增工具零配置。
  • ✅ “错误转字符串而非抛异常”——LLM 不怕出错,怕出错后流程崩。让 LLM 看到错误,就能自我修正(换路径重试)。
  • ✅ generateToolRequestResponse 不抽象,是通用模板;generateToolExecutedResult 抽象,是子类核心差异点——模板方法模式。
  • ⚠️ 路径穿越风险:绝对路径分支没做 .. 校验,恶意 ../../../etc/passwd 会被读到。
  • ⚠️ 大文件一次性 Files.readString 会爆内存。

面试话术(60 秒):BaseTool 是”3 抽象 + 1 具体”的骨架封装;@Tool description 是给 LLM 看的,决定调用准确率;”错误转字符串”是 Agent 设计的核心技巧——给 LLM 反馈通道让它自我修正。

四、观测层(S 黑盒 AI → T 三段式监控 → A Micrometer + Prometheus + Grafana → R 业务可观测)

4.1 整体链路:为什么需要观测层

S(背景):AI 系统上线后,运维痛点明显:① JVM 通用指标(HTTP 延迟、GC)够用,但不知道”AI 调用成功率、平均 token、生成耗时”;② 异步 SSE 链路长,从用户提问到模型响应跨多个线程,出问题难定位;③ LangChain4j 内部抛异常时,业务代码拿不到上下文。

T(目标):用 Micrometer + Prometheus + Grafana 三段式,采集 AI 业务指标并在 Grafana 大盘展示。验收标准:大盘能看到 QPS / P95 / token 消耗 / 成功率。

A(做了什么):三段式架构 + 预制 Grafana 大盘 JSON(grafana/ai_model_grafana_config.json,28KB)。

R(结果与反思):

  • ✅ Micrometer 是”指标门面”——与 SLF4J 同款设计,业务代码调 registry.counter(...),底层可换 Prometheus / InfluxDB / Datadog,不改业务。
  • ✅ 预制大盘 JSON 是工程最佳实践——新人 clone 项目后导入即看到生产视图,把运维经验沉淀为文件。
  • 💡 反思:Actuator + Prometheus 只解决”通用指标”,AI 业务指标必须项目自埋,JVM 不知道 token 消耗。

面试话术(60 秒):AI 系统的可观测性 = Micrometer(写入) + Prometheus(存储) + Grafana(展示)。Micrometer 是 SLF4J 同款指标门面,换底层不改业务代码。

4.2 Actuator 暴露的三个端点

S(背景):Spring Boot Actuator 是开箱即用的生产模块,需要决定”暴露哪些端点”——多了泄露信息,少了运维无数据。

T(目标):只暴露 health、info、prometheus 三个端点,够用且最小。

A(做了什么):application.yml 配置(main-app.md 第 102 行):

三个端点对应三类需求:

  • /actuator/health —— K8s liveness/readiness 探针,失败就重启/摘流量。
  • /actuator/info —— 版本号、构建时间等元数据。
  • /actuator/prometheus —— Prometheus 抓取的指标数据,文本格式。

R(结果与反思):

  • ✅ 一行依赖 + 一行配置,健康检查和指标暴露齐了——“零成本可观测性”。

面试话术(60 秒):Actuator 是”零成本可观测性”——暴露 health/info/prometheus 三个端点,K8s 探针接 health,Prometheus scrape 接 prometheus。

4.3 AI 业务指标埋点

S(背景):Actuator 暴露的是 JVM / HTTP 通用指标,不包含”AI 调用成功率、token 消耗、模型耗时”。这些指标 JVM 不知道,必须项目自埋。

T(目标):埋 3 个核心指标——ai.model.calls(调用次数)、ai.model.duration(耗时)、ai.model.tokens(token 消耗)。验收标准:Grafana 大盘能看到按 model 标签分类的所有指标。

A(做了什么):三件套协作:

三个 Micrometer 类型分工:

  • Counter —— 单调递增计数,适合 QPS / 错误次数。
  • Timer —— 自动算 P95/P99/P999 分位数,适合响应时间。
  • DistributionSummary —— 自定义分布统计,适合 token / 大小。

R(结果与反思):

五、限流与鉴权(S 双闸门必要 → T 双 AOP → A RateLimit + AuthCheck → R 工程安全)

5.1 限流 + 鉴权双闸门

S(背景):AI 项目有两个高成本操作——LLM 调用(按 token 计费)和工具调用(可能耗时长)。没有限流,恶意用户可能写脚本刷爆 API;没有鉴权,普通用户能调管理员接口。

T(目标):用两个独立 AOP 切面守住系统——限流挡高频,鉴权挡越权。

A(做了什么):两个 AOP 切面 + 注解声明式:

关注点 注解 切面 后端实现
限流 @RateLimit(USER, 5, 60s) RateLimitAspect Redisson 分布式令牌桶
鉴权 @AuthCheck(mustRole=ADMIN) AuthInterceptor session userId + 角色匹配

典型用法:

R(结果与反思):

  • ✅ 限流挡高频(防 token 预算烧光),鉴权挡越权(防数据泄露)。
  • ✅ 拦截顺序:限流 → 鉴权 → 业务——先挡高频(省鉴权开销),再校验权限。
  • ⚠️ 为什么不用 HandlerInterceptor:限流/鉴权粒度到方法级 + 参数感知,AOP 比 HandlerInterceptor 灵活。
  • ⚠️ HandlerInterceptor 优势是 URL 级别 + 直接方法调用无反射开销,本项目以方法注解为主故选 AOP。

面试话术(60 秒):限流 + 鉴权是后台标配双闸门,两道独立切面,任一失守都可能导致安全事故。限流先于鉴权——省资源、省开销、保护下游。

5.2 令牌桶 vs 漏桶

S(背景):限流算法选型直接影响用户体验。漏桶强制匀速,会让 AI 突发性请求排队;令牌桶允许桶里累积令牌,能扛突发。

T(目标):选型理由能讲清,不止是”大家都用令牌桶”。

A(做了什么):

  • 令牌桶:桶里持续生成令牌(按速率),请求消耗令牌,无令牌则拒绝。允许突发流量。
  • 漏桶:桶里请求必须排队,强制匀速流出。
  • 本项目用令牌桶,因 AI 生成是突发性的——用户可能连续问 5 个问题,然后沉默 10 分钟。

R(结果与反思):

  • ✅ 令牌桶允许短时高频,匹配 AI 用户的交互习惯。
  • ✅ Redisson 的 RRateLimiter 用 Redis Lua 实现,集群共享计数器。

面试话术(60 秒):令牌桶允许突发流量,漏桶强制匀速。AI 用户会连续问几个问题然后沉默,令牌桶匹配这种突发模式。

六、面试高频追问(STAR 速答)

Q1:为什么用 LangGraph4j 而不是 Spring State Machine?

S:Spring State Machine 是通用状态机库,LangGraph4j 是 AI 场景专用。
T:需要 AI 场景的 MessagesState、流式节点输出、异步条件边。
A:LangGraph4j 天然支持这些,Spring State Machine 都要自己包装——学习成本与维护成本都高。
R:用 LangGraph4j 后,AI 代码生成拆成 6 节点 + 条件边,可视化、易扩展、易测试。

Q2:三入口(同步/Flux/SSE)的差异和选型?

S:同一工作流,前端有不同调用场景。
T:业务层不变,传输层可换。
A:同步适合调试 + 批处理;Flux 适合 WebFlux 响应式网关;SSE 适合 MVC + 长任务(30 分钟超时)。
R:同一逻辑暴露三种 API,改传输协议不改业务,改业务不改协议。

Q3:Java 21 虚拟线程对工作流意味着什么?

S:SSE 长任务用传统线程占满 8MB 栈,LLM 调用又是阻塞的。
T:用同步写法实现”异步性能”。
A:全用 Thread.startVirtualThread 启动,几毫秒启动,M 级并发不爆栈。
R:工作流实例独占虚拟线程,Lighthouse 长任务性能稳定——Java 对抗 Kotlin 协程 / Go goroutine 的官方答案。

Q4:为什么用本地缓存(Caffeine)而不是 Redis 缓存 AI Service?

S:AiServices.builder().build() 非常重,装配耗时长。
T:缓存重对象,降低首次延迟。
A:本地缓存有纳秒级延迟 + 无网络 IO,适合 AI Service 这种重对象 + 单机用场景;Redis 多 1-5ms 网络 IO,而 AI Service 本身已 1-3 秒,本地缓存省 1ms 没意义。
R:首次创建后命中纳秒级,Caffeine 双过期策略防雪崩。

Q5:hallucinatedToolNameStrategy 为什么必要?

S:LLM 偶尔会幻觉出不存在的方法名,尤其 prompt 多变、工具多时。
T:不能让 LLM 错误导致整个生成崩。
A:hallucinatedToolNameStrategy(req -> "Error: there is no tool called " + req.name()) 把错误作为工具结果回填。
R:LLM 下一轮看到错误,自我修正为正确的 readFile——给 LLM 反馈通道是工程级 AI 系统的核心防御。

Q6:为什么用 Micrometer 而不是直接调 Prometheus 客户端?

S:指标需要灵活切换底层实现(开发用内存,生产用 Prometheus,云上换 Datadog)。
T:业务代码与底层解耦。
A:Micrometer 是 SLF4J 同款”指标门面”——业务调 registry.counter(...),底层可换 Prometheus / InfluxDB / Datadog,不改业务。
R:切换监控后端零业务代码改动。

Q7:限流为什么要先于鉴权?

S:恶意用户可能写脚本刷爆 AI API。
T:挡高频请求是第一道防线。
A:① 省资源(恶意高频请求不用鉴权);② 省鉴权开销(查 session/角色慢);③ 保护下游(限流后请求数可控)。
R:限流失败的请求直接 429,鉴权开销为零,下游负载可控。

Q8:令牌桶和漏桶的差异?

S:AI 用户会连续问几个问题然后沉默,请求分布不均匀。
T:选能扛突发的算法。
A:令牌桶允许桶里累积令牌,突发时一次消耗多个;漏桶强制匀速流出,会让突发请求排队。
R:令牌桶匹配 AI 用户的突发交互模式。

Q9:ThreadLocal 用过什么坑?

S:Tomcat 线程池复用线程,ThreadLocal 不清理会泄漏。
T:异步线程上下文传递 + 无内存泄漏。
A:MonitorContextHolder.set(ctx) + try-finally { clear() },必须成对出现。
R:无用户串号、无内存泄漏。进阶可改 InheritableThreadLocal 或阿里 TransmittableThreadLocal。

Q10:exclude 自动配置的三大场景?

S:starter 自动装配带来便利,但有时与项目冲突。
T:处理依赖冲突。
A:① 多个 starter 抢同一个 Bean(本项目 LangChain4j Redis starter 与自定义 RedisChatMemoryStore 冲突);② 自定义同名实现需覆盖默认;③ 单元测试不想加载重型组件。
R:显式声明依赖边界,只引入项目真正用到的部分。

七、关键洞察卡片(背诵清单,每条都可独立成 STAR)

  1. 启动类 = 装配图根:三个注解各管一摊——缓存、装配、ORM。
  2. LangGraph = 可重入 + 可分支的状态机:条件边是智能路由。
  3. 同一业务三种出口:分层 + 多协议适配经典设计。
  4. 接口即服务:LangChain4j 注解驱动 + 动态代理,类型决定行为。
  5. Caffeine 双过期策略:TTL + 空闲回收,防雪崩模板。
  6. Micrometer = 指标门面:与 SLF4J 同款设计。
  7. ThreadLocal + 线程池复用 = 串号高危:必须 finally clear。
  8. 限流先于鉴权:省资源、省开销、保护下游。
  9. AOP 拦截粒度 = 方法级 + 注解驱动:比 HandlerInterceptor 灵活。
  10. 预制 Grafana 大盘 JSON:把运维经验沉淀为文件。
