一、基础篇：什么是 Redis？

1.1 Redis 核心定位

维度 描述
全称 REmote DIctionary Service
本质 基于内存的 键值对数据结构服务器（不只是缓存）
核心优势 内存操作 → 亚毫秒级延迟；丰富数据结构 → 不止 KV
角色演变 从 “MySQL 前面的缓存” 到 “独立主数据库”

🎯 一句话：Redis 是一个用 C 语言写的、单线程（6.0+ 网络 IO 多线程）、基于内存的数据结构服务器，核心能力是 快 + 数据结构丰富。

1.2 Redis vs Memcached（高频面试对比）

对比维度 Redis Memcached
亚毫秒延迟 ✅ ✅
高级数据结构（List/Set/ZSet/Hash…） ✅ ❌（仅 String）
多线程架构 ❌（单线程事件驱动，6.0+仅网络IO多线程） ✅
持久化（快照/RDB） ✅ ❌
复制（Replication） ✅ ❌
事务 ✅ ❌
发布/订阅 ✅ ❌
Lua 脚本 ✅ ❌
地理空间支持 ✅ ❌

🎯 面试结论：Memcached 是纯缓存；Redis 更像一个 内存数据库，功能维度上碾压 Memcached。

1.3 Redis 四种部署架构

① 单机模式（Single Instance）

  • ✅ 优点：部署简单，延迟最低
  • ❌ 缺点：单点故障（SPOF），挂了全瘫
  • 🎯 适用：开发环境 / 对可用性无强要求的缓存场景

② 主从复制（Master-Slave / Replication）

关键概念：复制 ID（replication ID）+ 偏移量（offset）

  • 每个 Master 有一个 replication ID，每个写操作增加 offset
  • Slave 落后少量 offset → 部分同步（增量）
  • Slave 没有共同祖先 → 全量同步（RDB 快照 + 缓冲区增量）

面试考点：什么情况触发全量同步？

  • Slave 是新加入的，无共同祖先
  • Master 的 repl_backlog_buffer 太小，Slave 需要的 offset 已被覆盖

③ 哨兵模式（Sentinel）

Redis Sentinel 是一个分布式哨兵系统，不是单个进程！

Sentinel 四大职责：

  1. 监控（Monitoring）：持续检查 Master/Slave 是否存活
  2. 通知（Notification）：事件发生时通知管理员
  3. 故障转移（Failover）：Master 挂了，投票选举新 Master
  4. 配置管理（Config Provider）：告诉客户端当前 Master 是谁

Quorum（法定人数）配置表（面试常考）：

哨兵节点数 Quorum 可容忍故障数
1 1 0
3 2 1
5 3 2
7 4 3

🎯 一句话：Sentinel = 哨兵集群自动监控 + 自动故障转移，解决主从模式”主挂得手动切”的问题。

④ Cluster 集群模式（分布式分片）

核心机制：

  1. Hash Slot（哈希槽） — 集群的数据分布方式

    • 共 16384 个槽，每个 Master 负责一部分
    • 扩缩容时只需 移动槽，不需要移动所有 key — 这就是 Hash Slot 的巧妙之处！

  2. Gossip 协议 — 集群节点间通信方式

    • 所有节点不断互相通信（PING/PONG）
    • 用于发现新节点、检测故障、传播配置变更

  3. 故障转移 — Master 挂了的处理

    • Slave 发现 Master 不可达 → 发起投票
    • 多数 Master 同意 → Slave 提升为新 Master
    • 脑裂（Split-brain）：网络分区导致两边各有 Master，解决方法 → 奇数个 Master + 多数投票

🎯 一句话：Cluster = 数据自动分片 + 内置故障转移，解决大数据量下一台机器存不下的问题。

四种架构对比：

架构 数据分片 高可用 复杂度 适用场景
单机 ❌ ❌ 低 开发/测试
主从 ❌ ❌（手动切） 低 读写分离
Sentinel ❌ ✅（自动） 中 高可用不要求分片
Cluster ✅ ✅（自动） 高 大数据量 + 高可用

1.4 Redis 持久化模型

模式 原理 优点 缺点
无持久化 纯内存，不写盘 最快 重启数据全丢
RDB 定时快照（时间点内存镜像） 文件紧凑、恢复快 两次快照间的数据会丢
AOF 记录每条写命令（追加日志） 数据更完整（可配置 fsync 频率） 文件大、恢复慢
RDB + AOF 两者同时开启 取长补短 性能有一定损耗

🎯 一句话：重启时，如果 AOF 开启 → 优先用 AOF 恢复（因为最完整）；否则用 RDB。

1.5 Fork + 写时复制（Copy-on-Write）— 持久化的底层黑科技

这是 Redis 最巧妙的设计之一：

COW 详解：修改 key 时到底发生了什么？

完整流程图：

简化比喻

关键理解

问题 答案
COW 是什么 写时复制 = 要写的时候才复制物理内存页
COW 什么时候触发 父进程收到写请求并实际修改数据时（不是 fork 时）
COW 复制的是什么 物理内存页（不是整个数据库），最小化复制开销

为什么持久化开销小 fork 后父子共享只读内存，只有修改的页才复制，不修改就不复制

🎯 面试亮点：Redis 单线程如何高效做持久化？— 靠 fork() + 写时复制，子进程专职写盘，父进程继续服务请求。fork 时不复制、只共享；修改时才复制、最小开销。

二、面试篇：Redis 高频面试题 Top 20+

🎯 本章按面试频率和话题分类，每道题附带 核心回答 + 关键细节，适合突击复习。

2.1 基础认知类

Q1：Redis 是什么？为什么这么快？

Redis = Remote Dictionary Service，基于内存的 KV 数据结构服务器。

快的原因（4 点）：

  1. 内存操作：绝大部分操作在内存完成

  2. 高效数据结构：SDS、跳表、压缩列表等专为性能优化

    三者都是Redis 为兼顾内存、查询 / 操作性能，自研 / 改造的轻量结构，分别优化字符串、有序查找、列表场景

  3. 单线程模型：避免多线程竞争、上下文切换、死锁

  4. IO 多路复用：epoll 机制，一个线程处理大量客户端连接

💡 QPS：Redis 单机轻松 10w+，MySQL 难破 1w，差距约 10 倍。

Q2：Redis vs Memcached 怎么选？

维度 Redis Memcached
数据类型 丰富（String/List/Set/ZSet/Hash/Stream…） 仅 String
持久化 ✅ RDB + AOF ❌
集群 ✅ 原生 Cluster ❌ 需客户端实现
线程模型 单线程（6.0+ 网络 IO 多线程） 多线程
事务/Lua/发布订阅 ✅ ❌

🎯 结论：需要持久化、复杂数据结构 → Redis；仅做简单 KV 缓存且已用 Memcached → 可保留。

Q3：为什么用 Redis 做 MySQL 缓存？

两个核心原因：

  1. 高性能：内存读取远超磁盘 IO
  2. 高并发：Redis 单机 QPS 10w+，MySQL 单机不到 1w，Redis 能扛住大流量冲击

2.2 线程模型类（面试高频！）

Q4：Redis 是单线程的吗？

严格说：不是。

  • 命令执行：单线程（核心，我们常说的”Redis 是单线程”指这个）
  • 后台线程（BIO）：
    • bio_close_file：异步关闭文件
    • bio_aof_fsync：AOF 刷盘（everysec 模式下）
    • bio_lazy_free：异步释放内存（4.0+，unlink/flushdb async）
  • IO 多线程（6.0+）：io_thd_1/2/3，仅处理网络 IO 读写，命令执行仍是单线程

Q5：Redis 6.0 为什么引入 IO 多线程？

随着网络硬件性能提升，网络 IO 成为瓶颈，不再是 CPU。6.0 用多个 IO 线程并行处理网络读写，命令执行保持单线程。官方数据：性能提升至少 1 倍。

⚠️ 线程数建议 ≤ CPU 核数，不是越多越好。

2.3 数据类型类

Q7：Redis 有哪些数据类型？各自使用场景？

5 种基础类型：

类型 场景
String 缓存对象、计数、分布式锁、Session 共享
List 消息队列（简单场景）、最新消息列表
Hash 缓存对象（如用户信息）、购物车
Set 点赞、共同关注、抽奖（交集/并集/差集）
ZSet 排行榜、延迟队列、按时间排序

4 种扩展类型：

类型 版本 场景
BitMap 2.2 签到、用户在线状态（二值统计）
HyperLogLog 2.8 UV 统计（基数统计，误差 0.81%）
GEO 3.2 附近的人、滴滴叫车
Stream 5.0 消息队列（自动生成 ID、支持消费组）

Q8：五种数据类型底层是怎么实现的？

类型 小数据量时 大数据量时 7.0 变化
String SDS（简单动态字符串） SDS 不变
List quicklist（3.2+） quicklist 替代了 ziplist+linkedlist
Hash listpack 哈希表（dict） 7.0 用 listpack 替代 ziplist
Set 整数集合（intset） 哈希表（dict） 不变
ZSet listpack 跳表（skiplist）+ dict 7.0 用 listpack 替代 ziplist

🔑 String 的 SDS 亮点：O(1) 获取长度、二进制安全（可存图片）、自动扩容防溢出。

2.4 持久化类

Q9：Redis 如何实现数据不丢失？（持久化方式对比）

方式 原理 优点 缺点
RDB 定时内存快照 文件紧凑、恢复快 两次快照间数据丢失
AOF 记录每条写命令 数据更完整 文件大、恢复慢
混合 RDB + AOF 兼顾恢复速度与完整性 4.0+ 支持

🔑 重启恢复优先用 AOF（如果开启），因为最完整。

Q10：AOF 写回策略有哪几种？

策略 写回时机 优点 缺点
Always 每条命令同步写盘 不丢数据 性能最差
Everysec 每秒写盘一次 最多丢 1 秒数据 性能折中 ✅
No 由操作系统决定 性能最好 丢数据不可控

Q11：AOF 日志过大怎么办？— AOF 重写

当 AOF 文件过大，Redis 触发 AOF 重写（bgrewriteaof）：

  • 读取当前数据库状态，生成最精简的命令写入新 AOF 文件
  • 通过 fork 子进程 执行，不阻塞主线程
  • 重写期间新命令写入 AOF 重写缓冲区，完成后追加到新文件

Q12：RDB 快照会阻塞主线程吗？

  • save 命令：会阻塞（主线程执行）
  • bgsave 命令：不会阻塞（fork 子进程执行，利用写时复制）

🔑 写时复制（COW）：fork 后父子共享内存，只有父进程修改某页时才复制该页，保证子进程看到一致性快照。

2.5 过期 & 淘汰策略

Q13：Redis 的过期删除策略是什么？

惰性删除 + 定期删除 组合：

策略 机制 优缺点
惰性删除 访问 key 时才检查是否过期 对 CPU 友好，但内存不友好（过期 key 堆积）
定期删除 每隔一段时间随机抽一批 key 检查 折中方案

具体执行：每秒 10 次定期删除，每次随机抽 20 个 key，过期比例 > 25% 则继续循环。

Q14：Redis 内存满了怎么办？— 8 种淘汰策略

策略 范围 行为
noeviction — 不淘汰，直接报错（默认）
allkeys-lru 所有 key 淘汰最近最少使用的
volatile-lru 有过期时间的 key 淘汰最近最少使用的
allkeys-random 所有 key 随机淘汰
volatile-random 有过期时间的 key 随机淘汰
volatile-ttl 有过期时间的 key 淘汰最快过期的
allkeys-lfu 所有 key（4.0+） 淘汰最不常使用的
volatile-lfu 有过期时间的 key（4.0+） 淘汰最不常使用的

🎯 面试推荐回答：一般用 allkeys-lru 或 allkeys-lfu，前者按”最近少用”，后者按”频率低”。

Q15：LRU vs LFU 有什么区别？

维度 LRU（Least Recently Used） LFU（Least Frequently Used）
淘汰依据 最近访问时间 访问频率
问题 偶发访问会把热数据挤出 历史高频 key 难以淘汰
Redis 实现 近似 LRU，24bit 时钟值 对数计数器 + 衰减因子

🔑 Redis 不是精确 LRU，是近似 LRU：随机采样 N 个 key，淘汰其中 LRU 时钟值最小的。

2.6 缓存三大问题（面试必问！）

Q16：什么是缓存雪崩、击穿、穿透？

问题 原因 现象 解决方案
雪崩 大量 key 同时过期 / Redis 宕机 请求全打到 DB，DB 挂 过期时间加随机值、Redis 高可用、限流降级
击穿 热点 key 过期 大量请求同时查一个 key，打到 DB 互斥锁 / 永不过期 + 异步更新
穿透 查不存在的数据（缓存和 DB 都没有） 恶意攻击 / 业务误删 布隆过滤器、空值缓存、参数校验

🎯 一句话区分：雪崩 → 大面积同时失效；击穿 → 单点热点失效；穿透 → 数据本就不存在。

2.7 缓存一致性

Q17：如何保证数据库和缓存的一致性？

推荐方案：Cache Aside（旁路缓存）+ 先更新数据库，再删除缓存。

为什么不能先删缓存再更新数据库？（并发问题）

先更新 DB 再删缓存的理论并发窗口极小（缓存写入远快于 DB 更新），实际概率很低。

Q18：还有哪些缓存更新策略？

策略 描述 适用场景
Cache Aside 应用同时操作缓存和 DB ✅ 最常用
Read/Write Through 缓存代理 DB 操作 本地缓存（如 Guava、caffine）
Write Back 只写缓存，异步刷 DB CPU 缓存、文件系统 Page Cache

2.8 实战类

Q19：什么是 Redis 大 Key？有什么影响？如何处理？

定义：

  • String 类型 value > 10KB
  • 集合类型元素 > 5000 个

影响：

  1. 客户端超时阻塞（单线程处理耗时长）
  2. 网络阻塞（大 value 带宽占用高）
  3. del 阻塞工作线程
  4. 集群内存分布不均

处理方案：

  1. 查找：redis-cli --bigkeys（建议在从节点执行）
  2. 删除：
    • String → unlink（异步删除，4.0+）
    • Hash → hscan + hdel 分批删
    • Set → sscan + srem 分批删
    • ZSet → zremrangebyrank 分批删
  3. 配置 lazy free：lazyfree-lazy-eviction、lazyfree-lazy-expire 等

Q20：Pipeline 是什么？

Pipeline（管道）：客户端将多个命令打包一次发送，服务端处理后统一返回，减少 RTT（网络往返时间）。

⚠️ Pipeline 是客户端功能，不是服务端功能。注意不要一次发太多导致网络阻塞。

Q21：Redis 事务支持回滚吗？

不支持回滚！

  • MULTI 开启事务 → 命令入队 → EXEC 执行
  • DISCARD 只能主动放弃（清空队列），不能回滚已执行的操作
  • 即使事务中某条命令执行失败，其他命令仍正常执行 — 不保证原子性
  • 作者认为事务错误通常是开发阶段的编程错误，不需要回滚这种复杂功能

🎯 面试重点：Redis 事务 ≠ MySQL 事务，不支持回滚，不保证原子性！

Q22：如何用 Redis 实现分布式锁？

加锁：一条原子命令搞定

解锁：Lua 脚本保证原子性（先判断是否是自己的锁，再删除）

三个关键点：

  1. NX → 互斥性（key 不存在才设置）
  2. PX → 防死锁（客户端崩溃也能自动释放）
  3. unique_value → 防误删（只删自己加的锁）

优缺点：

  • ✅ 性能高、实现简单、天然避免单点故障（集群部署）

  • ❌ 超时时间不好设置（可加 WatchDog 续约）、主从异步复制可能导致锁丢失

    WatchDog 续约机制：

    一句话：自动延期锁的看门狗，防止业务还没跑完锁就过期了。

    适用于：Redisson 等基于 Redis 实现的分布式锁框架

    工作原理

    参数 默认值
    锁自动过期时间 30 秒
    续期检查间隔 10 秒（1/3 自动过期时间）
    续期时长 30 秒（重置回初始TTL）

Q23：Redlock（红锁）是什么？如何解决集群下分布式锁的可靠性？

Redlock：基于多个独立 Redis 主节点的分布式锁算法。

加锁过程（官方建议 ≥ 5 个节点）：

  1. 记录当前时间 T1
  2. 依次向 N 个节点加锁（SET NX PX），每个加锁操作设置超时（远小于锁过期时间）
  3. 成功后记录当前时间 T2
  4. 加锁成功条件：
    • 超过半数节点（≥ N/2+1）加锁成功
    • 总耗时（T2-T1）< 锁过期时间
  5. 锁实际有效时间 = 锁过期时间 - (T2-T1)

失败处理：向所有节点发起释放锁的 Lua 脚本。

🎯 一句话：Redlock = 多节点独立加锁 + 过半原则，解决主从复制锁丢失问题。

2.9 高可用类（详见第六篇）

方案 核心 面试要点
主从复制 读写分离、数据备份 全量同步 vs 增量同步
哨兵 自动故障转移 Quorum 投票、主观/客观下线
Cluster 数据分片（16384 槽） CRC16、Gossip 协议、MOVED/ASK 重定向

Gossip（八卦 / 流言）协议，核心是模拟人类闲聊传播信息，是分布式系统中节点间异步、最终一致性的信息扩散协议。

3.1 String — 最基础万能型

内部实现

编码类型 条件 说明
int 值为整数且能用 long 表示 直接存整数，省内存
embstr 字符串 ≤ 44 字节（3.0+） 一次内存分配，redisObject + SDS 连续存储
raw 字符串 > 44 字节 两次内存分配，分开存储

🔑 embstr 阈值版本变化：

  • 2.x：embstr ≤ 39 字节（旧 SDS 结构）
  • **3.2 ~ 6.2+**：embstr ≤ 44 字节（新 SDS 结构 sdshdr8，沿用至今）

为什么是 44 / 39 字节？

  • jemalloc 最小分配单元 = 64 字节（强制按 64 字节分配）
  • redisObject = 16 字节（始终不变）
  • \0 结束符 = 1 字节
版本 SDS 头部 计算 字符串空间
2.x（旧 SDS） sdshdr → 8 字节 64 - 16 - 8 - 1 39 字节
3.2+（新 SDS） sdshdr8 → 3 字节 64 - 16 - 3 - 1 44 字节

变化原因：3.2 版本重构 SDS，用 sdshdr8（1+1+1=3 字节）替代旧 sdshdr（4+4=8 字节），省了 5 字节，阈值从 39 升到 44。

⚡ embstr 陷阱：embstr 是只读的！一旦修改（如 APPEND），立即转为 raw 编码。

常用命令速查

应用场景

场景 实现 核心命令
点赞 SADD article:1 uid:1 — 自动去重，一人一赞 SADD/SREM/SCARD

⚠️ 注意：SINTER/SUNION/SDIFF 计算复杂度 O(N)（N = 最小集合基数），大数据量时会阻塞 Redis 主线程！

解决方案：

  • 从节点执行：主从架构下，在从节点执行集合运算，不影响主节点写操作
  • 客户端聚合：用 SCAN 分批获取元素到客户端本地，Python/Go 本地计算交集/并集/差集
  • 预计算：对实时性要求不高的场景，提前用定时任务计算结果并缓存

核心原则：把 O(N) 耗时操作移出 Redis 主线程，避免阻塞影响其他请求。

3.5 ZSet（Sorted Set）— 自带排名的有序集合

内部实现

条件 编码
元素 < 128 且 value < 64B listpack（7.0，替代旧版 ziplist）
不满足 → skiplist（跳表）+ hashtable（dict）

Skiplist 结构图

为什么用跳表而不是平衡树？

对比 跳表（skiplist） 平衡树（AVL/红黑树）
实现难度 简单（链表 + 随机层数） 复杂（旋转/重平衡）
范围查询 O(log n + m)（跳表天然支持区间） O(log n)（需要中序遍历）
插入删除 只改前后指针，不需整体重排 需要旋转维护平衡
序章 简单 复杂

Redis 为什么选跳表？

  1. 实现简单，不容易出 bug
  2. 范围查询天然支持（ZRANGEBYSCORE）
  3. 插入性能稳定（不需要旋转）
  4. 可以用 dict 辅助查询，O(1) 查 member

Skiplist + Dict 双重结构（Redis ZSet 实际实现）

🎯 一句话：ZSet 用 skiplist 做有序遍历 + dict 做 O(1) 查找，两者共享 member，各司其职。

在深入数据结构前，先看清全局架构：

redisObject 结构（每个键值对的核心元数据）：

3.X.1 SDS（Simple Dynamic String）— String 的底层

为什么不用 C 语言 char*？

C 字符串缺陷 SDS 解决方案
O(n) 获取长度（遍历到 \0） len 字段 → O(1)
以 \0 结尾，不能存二进制 用 len 判断结尾 → 二进制安全
拼接不检查空间 → 缓冲区溢出 alloc - len 检查剩余空间 → 自动扩容
内存重分配频繁 空间预分配 + 惰性释放

SDS 结构（Redis 5.0+，5 种类型）

SDS 类型 len/alloc 类型 最大容量
sdshdr5 5 bit 32 字节（已废弃不用）
sdshdr8 uint8_t 255
sdshdr16 uint16_t 65,535
sdshdr32 uint32_t 4,294,967,295
sdshdr64 uint64_t 超大

🔑 **__attribute__((packed))**：取消编译器字节对齐，按实际大小分配内存，节省空间。

String 的 3 种编码

3.X.2 双向链表 — List 的早期底层（已被替代）

优点：O(1) 取头尾/长度，泛型值指针
缺点：内存不连续（无法利用 CPU 缓存），每个节点有额外结构头开销

🎯 Redis 3.2 后用 quicklist 替代了纯链表。

3.X.3 压缩列表（Ziplist）— 紧凑内存布局（已被废弃）

设计理念

一块连续内存紧凑存储多个元素，省去节点指针开销。

致命缺陷：连锁更新（Cascade Update）

🔑 这就是为什么 ziplist 只适合少量小元素。最终催生了 quicklist 和 listpack。

3.X.4 哈希表（dict）— 全局键值存储 + Hash 类型的底层

结构层次

链式哈希（冲突解决）

渐进式 Rehash（面试高频！）

为什么需要？：一次性迁移大哈希表会长时间阻塞 Redis。

做法：分多次、逐步迁移。

Rehash 触发条件（负载因子）

3.X.5 整数集合（Intset）— Set 的小数据优化

升级操作（Upgrade）

插入一个更大类型的元素时：

  1. 扩展 contents 数组空间
  2. 将已有元素转换为新类型，保持有序
  3. 插入新元素

🔑 只升级不降级！删除大元素后，数组仍保持升级后的类型 — 以此换取”节省内存”策略：只要没出现大元素，就一直用最小类型。

3.X.6 跳表（Skiplist）— ZSet 的核心引擎

为什么不用红黑树？

跳表比红黑树更适合 Redis 的原因：

  1. 实现简单，代码量少
  2. 支持范围查询（ZRANGE）更自然
  3. 可以按层级遍历

结构

  • 查找时从最高层开始，逐层下降
  • 平均时间复杂度 **O(logN)**，最坏 O(N)
  • 每个节点随机生成层数

ZSet 的双重索引

🎯 一句话：dict 负责”查分数”，skiplist 负责”排顺序”，两者数据同步更新。

3.X.7 quicklist — List 的最终实现（3.2+）

设计思路

链表节点 + 压缩列表 = 取长补短

插入逻辑：先尝试塞入目标节点的 ziplist，塞不下才新建节点。

🎯 好处：控制每个 ziplist 大小，连锁更新的影响被限制在单个节点内。

3.X.8 listpack — 替代 ziplist 的新方案（5.0+，7.0 全面替代）

核心改进：去掉 prevlen！

  • 向 listpack 插入元素 → 不影响其他节点的长度字段
  • 彻底消灭连锁更新
  • 同时保留了紧凑内存布局和节省内存的优势

在 7.0 中：Hash、ZSet 的小数据场景底层已全部从 ziplist 切换为 listpack。

4.1 AOF（Append Only File）— 写命令日志

基本原理

每执行一条写命令（读命令不记录），就把该命令追加到 AOF 文件末尾。

先执行命令，再写日志（好处 + 风险）：

好处 风险
避免语法错误命令记录到 AOF 写完命令后、记录日志前宕机 → 数据丢失
不阻塞当前命令执行 写盘过程在主进程 → 可能阻塞下一个命令

三种写回策略

策略 触发 fsync 时机 数据安全 性能 适用场景
Always 每条命令同步写盘 ⭐⭐⭐ ⭐ 不差性能，要求不丢数据
Everysec 每秒一次异步写盘 ⭐⭐ ⭐⭐ ✅ 推荐：丢 1 秒数据可接受
No 永不 fsync，由 OS 决定 ⭐ ⭐⭐⭐ 纯缓存，不在意数据丢失

4.3 大 Key 对持久化的影响（面试高频！）

对 AOF 的影响

策略 大 Key 影响
Always 主线程执行 fsync() 写大 value → 长时间阻塞主线程
Everysec fsync 由 BIO 线程异步处理 → 不影响主线程
No 不执行 fsync → 不影响主线程

对 AOF 重写和 RDB 的影响（fork 阻塞）

fork 的两个阻塞阶段：

阶段 原因 如何监控
创建子进程时 复制父进程页表（页表越大越慢） INFO → latest_fork_usec
COW 时 主进程修改大 Key，复制物理内存 同上

优化建议

  1. 单实例内存控制在 10GB 以内（确保 fork 快速返回）
  2. 纯缓存场景 → 关闭持久化（不调 fork）
  3. 适当调大 repl-backlog-size → 避免频繁全量同步（全量同步会 fork）
  4. 用 unlink / 分批删除替代 del 删除大 Key
  5. 拆分大 Key → 用 Hash 分桶或 string 分片

对比维度 过期删除策略 内存淘汰策略
触发条件 key 到了过期时间 Redis 内存超过 maxmemory
操作对象 已过期的 key 任意 key（按策略选）
目的 清理过期数据 释放内存，保证 Redis 运行

过期删除策略（惰性删除 + 定期删除）

过期字典结构：

判断过期：查 expires 字典 → O(1)，比较时间戳。

Redis 采用「惰性删除 + 定期删除」组合：

① 惰性删除（Lazy）

② 定期删除（Periodic）

三种纯策略对比：

策略 对 CPU 对内存 适用场景
定时删除 ❌ 差 ✅ 好 内存极度紧张
惰性删除 ✅ 好 ❌ 差 CPU 紧张
定期删除（Redis 采用） ⭐ 折中 ⭐ 折中 通用

内存淘汰策略（8 种）

当 maxmemory 达到上限时触发。默认 maxmemory = 0（64位系统），即无限制。

策略 淘汰范围 淘汰依据 备注
noeviction — 不淘汰，报错 默认
allkeys-lru 所有 key 最近最少使用 ✅ 最常用
volatile-lru 有过期时间的 key 最近最少使用
allkeys-random 所有 key 随机
volatile-random 有过期时间的 key 随机
volatile-ttl 有过期时间的 key 最快过期的
allkeys-lfu 所有 key（4.0+） 最不常用（频率）
volatile-lfu 有过期时间的 key（4.0+） 最不常用（频率）

🎯 推荐：allkeys-lru（通用），热点数据场景换 allkeys-lfu。

Redis 的 LRU 实现（近似 LRU）：

  • 不是精确 LRU（维护链表开销大）
  • 随机采样 N 个 key（默认 5），淘汰其中 LRU 时钟值最小的
  • maxmemory-samples 可调采样数（越大越接近精确 LRU）

LRU vs LFU：

维度 LRU LFU
依据 最近使用时间 访问频率
Redis 实现 24bit 时钟值 对数计数器 + 衰减因子
问题 偶发批量扫描会挤出热数据 历史高频 key 难以淘汰

5.2 分布式锁 — Redis 版

单节点实现（面试必写！）

加锁：一条原子命令

解锁：Lua 脚本保证原子性

为什么需要这三个条件？

条件 作用 缺失的后果
NX 互斥 多个客户端同时拿到锁
PX 防死锁 客户端 crash 后锁永远不释放
unique_value 防误删 A 释放了 B 的锁

优缺点

✅ 优点：性能高、实现简单、集群天然避免单点
❌ 缺点：

  1. 超时时间难设 — 业务执行时间 > 锁过期时间 → 锁提前释放
    • 🔧 解决：WatchDog 续约机制（Redisson 自带）
  2. 主从异步复制 → Master 宕机后 Slave 没有锁数据 → 多个客户端同时拿到锁

Redlock（红锁）— 集群环境分布式锁

核心思路：向多个独立 Redis Master 节点分别加锁，过半成功才算加锁成功。

主观下线 vs 客观下线

选举新 Master / Leader Sentinel

7.1 缓存三大问题一图打尽

雪崩 — 大面积同时失效

应对：

  • 过期时间加随机值：expire_time = base + random(1, 300) 避免扎堆
  • 互斥锁：保证同一时间只有一个线程构建缓存
  • Redis 高可用集群（主从/哨兵/Cluster）
  • 熔断/限流：事发后保护 DB

击穿 — 单点热点失效

应对：

  • 互斥锁（setnx 实现）：拿不到锁的请求等待或返回默认值
  • “永不过期”：不设过期时间，后台异步更新
  • 逻辑过期：value 中存过期时间戳，发现过期后异步更新

穿透 — 数据本不存在

应对：

  • 布隆过滤器：先查布隆过滤器，不存在直接返回，不查 DB
  • 空值缓存：对不存在的 key 也设短过期缓存（如 5 分钟）
  • 参数校验：入口过滤非法请求

7.2 缓存更新策略

Cache Aside（旁路缓存）— ✅ 最常用

为什么先更新 DB 再删缓存，不能反过来？

三种策略对比

策略 原理 适用 使用情况
Cache Aside 应用控制缓存和 DB 读多写少 ✅ Redis 常用
Read/Write Through 缓存代理 DB 本地缓存 Guava Cache
Write Back 只写缓存，异步写 DB 写多 CPU Cache，Redis 不支持

保证最终一致性的补充方案

  1. 缓存设置较短过期时间：即使不一致也很快自动修复
  2. 延迟双删：写完 DB 后，延迟一段时间再删一次缓存
  3. MQ 异步重试：删缓存失败 → 发送 MQ 消息 → 重试删除
  4. Canal + MQ：监听 MySQL binlog → 异步更新/删除缓存
