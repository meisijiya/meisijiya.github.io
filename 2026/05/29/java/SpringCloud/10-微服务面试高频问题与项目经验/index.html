微服务基础概念面试题

Q1：什么是微服务架构？它与单体架构有什么区别？

答案：

微服务架构是一种将单一应用程序开发为一组小型服务的方法，每个服务运行在自己的进程中，通过轻量级通信机制交互。

主要区别：

维度 单体架构 微服务架构
部署 整体部署 独立部署
技术栈 统一 灵活选择
扩展 垂直扩展 水平扩展
可靠性 单点故障 故障隔离
复杂度 初期简单 运维复杂

Q2：微服务架构有哪些优缺点？

答案：

优点：

  1. 独立开发部署，快速迭代
  2. 技术栈灵活，可选择最适合的技术
  3. 按需扩展，节约成本
  4. 故障隔离，系统可用性高

缺点：

  1. 分布式系统复杂性高
  2. 运维复杂度高
  3. 测试复杂度高
  4. 数据管理困难
  5. 网络延迟影响性能

Q3：什么时候应该使用微服务架构？

答案：

适合使用微服务的场景：

  1. 大型复杂业务系统
  2. 需要快速迭代的业务
  3. 需要高可用、高扩展的系统
  4. 团队规模较大，需要独立开发
  5. 业务需要多语言多技术栈

不适合使用微服务的场景：

  1. 小型简单项目
  2. 快速验证的原型
  3. 团队规模小
  4. 对延迟要求极高

Q4：微服务架构的核心组件有哪些？

答案：

微服务架构的核心组件：

  1. 服务注册与发现：Eureka、Nacos、Consul
  2. 负载均衡：Ribbon、LoadBalancer
  3. 服务熔断：Hystrix、Sentinel、Resilience4j
  4. API网关：Gateway、Zuul
  5. 配置中心：Config、Nacos Config
  6. 链路追踪：Sleuth、Zipkin、SkyWalking
  7. 消息队列：RabbitMQ、Kafka、RocketMQ

Q5：如何设计微服务的边界？

答案：

微服务边界设计原则：

  1. 单一职责原则：每个服务只负责一个业务能力
  2. 服务自治原则：服务独立开发、测试、部署
  3. 接口隔离原则：通过定义良好的接口进行通信
  4. 业务边界拆分：按业务领域拆分（DDD领域驱动设计）

拆分步骤：

  1. 识别业务领域：用户、订单、商品、支付
  2. 定义服务边界：每个服务的职责范围
  3. 设计服务接口：REST API定义
  4. 数据库拆分：每个服务独立数据库
  5. 逐步迁移：从单体逐步拆分

Spring Cloud组件面试题

Q6：Spring Cloud是什么？它解决了什么问题？

答案：

Spring Cloud是基于Spring Boot的微服务工具集，提供了快速构建分布式系统的通用模式。

解决的核心问题：

  1. 服务治理：服务注册与发现（Eureka, Nacos）
  2. 负载均衡：客户端负载均衡（Ribbon, LoadBalancer）
  3. 服务容错：熔断、降级、限流（Hystrix, Sentinel）
  4. 配置管理：集中配置（Config, Nacos Config）
  5. API管理：统一入口（Gateway, Zuul）
  6. 链路追踪：分布式追踪（Sleuth, Zipkin）

Q7：Eureka的工作原理是什么？

答案：

Eureka工作原理：

  1. 服务注册：

    • 服务启动时，Eureka Client向Eureka Server发送注册请求
    • Eureka Server将服务信息保存到注册表
    • 服务信息包括：服务名、IP地址、端口、健康状态等

  2. 服务续约：

    • Eureka Client定期（默认30秒）发送心跳
    • Eureka Server接收心跳，更新服务状态
    • 如果90秒没有收到心跳，服务将被移除

  3. 服务发现：

    • Eureka Client启动时，从Eureka Server获取注册表
    • Eureka Client缓存注册表到本地
    • Eureka Client定期（默认30秒）更新注册表

  4. 自我保护机制：

    • 当Eureka Server在短时间内丢失过多客户端时
    • Eureka Server进入自我保护模式
    • 不再移除服务实例，防止网络分区导致的服务误删

Q8：Ribbon的负载均衡策略有哪些？

答案：

Ribbon内置负载均衡策略：

  1. RoundRobinRule（轮询策略）：按顺序轮流选择服务实例
  2. RandomRule（随机策略）：随机选择服务实例
  3. RetryRule（重试策略）：在一定时间内重试选择可用实例
  4. WeightedResponseTimeRule（加权响应时间策略）：根据响应时间分配权重
  5. BestAvailableRule（最少连接数策略）：选择并发请求最少的实例
  6. AvailabilityFilteringRule（可用性过滤策略）：过滤掉故障实例
  7. ZoneAvoidanceRule（区域感知策略）：避免选择不可用区域

Q9：Feign和RestTemplate有什么区别？

答案：

对比维度 Feign RestTemplate
调用方式 声明式，接口+注解 编程式，代码调用
可读性 高，接口定义清晰 低，代码冗余
维护性 高，接口统一管理 低，代码分散
负载均衡 自动集成Ribbon 需要手动配置
熔断降级 自动集成Hystrix 需要手动配置
代码量 少，只需定义接口 多，需要编写调用代码

Q10：Hystrix的熔断原理是什么？

答案：

Hystrix熔断原理：

  1. 熔断器状态：

    • 关闭状态：正常调用，统计失败率
    • 开启状态：快速失败，不调用服务
    • 半开状态：允许部分请求通过，测试服务是否恢复

  2. 熔断触发条件：

    • 请求量超过阈值（默认20个）
    • 错误率超过阈值（默认50%）
    • 统计时间窗口内（默认10秒）

  3. 熔断恢复机制：

    • 熔断器开启后，经过休眠时间窗口（默认5秒）
    • 进入半开状态，允许一个请求通过
    • 如果请求成功，关闭熔断器
    • 如果请求失败，保持熔断器开启

Q11：Spring Cloud Gateway和Zuul有什么区别？

答案：

对比维度 Spring Cloud Gateway Zuul
开发公司 Spring Cloud官方 Netflix
底层框架 WebFlux（Reactor） Servlet
性能 高，非阻塞IO 低，阻塞IO
长连接 支持WebSocket 不支持
限流 集成Sentinel/Redis 需要额外实现
过滤器 GatewayFilter ZuulFilter
维护状态 活跃维护 已停止维护

Q12：Nacos与Eureka有什么区别？

答案：

对比维度 Nacos Eureka
开发公司 阿里巴巴 Netflix
维护状态 活跃维护 已停止维护
一致性模型 支持CP和AP 仅AP
配置管理 支持 不支持
健康检查 TCP/HTTP/MySQL 仅客户端心跳
负载均衡 权重/元数据 仅客户端负载均衡
多数据中心 支持 不支持
管理界面 功能完善 功能简单

Q13：Sentinel与Hystrix有什么区别？

答案：

对比维度 Sentinel Hystrix

微服务架构设计面试题

Q14：如何保证微服务间的数据一致性？

答案：

分布式事务解决方案：

  1. 2PC/3PC：

    • 强一致性，性能差
    • 适合传统数据库事务

  2. TCC：

    • 最终一致性，性能好
    • 适合资金、库存等核心业务

  3. Saga：

    • 最终一致性，无锁
    • 适合长流程业务

  4. 本地消息表：

    • 最终一致性，可靠
    • 适合异步场景

  5. 事务消息：

    • 最终一致性，可靠
    • RocketMQ事务消息

  6. Seata：

    • 提供AT、TCC、Saga、XA四种模式
    • 根据业务场景选择合适模式

Q15：如何防止服务雪崩？

答案：

防止服务雪崩的方法：

  1. 熔断机制：

    • 快速失败，避免级联故障
    • 检测服务健康状态
    • 自动恢复服务调用

  2. 降级机制：

    • 提供降级响应
    • 返回默认值或缓存数据
    • 保证核心功能可用

  3. 限流机制：

    • 控制请求速率
    • 防止流量激增
    • 保护系统资源

  4. 隔离机制：

    • 线程池隔离
    • 信号量隔离
    • 避免资源竞争

Q16：如何设计高可用的微服务架构？

答案：

高可用设计原则：

  1. 冗余设计：

    • 服务多实例部署
    • 数据库主从复制
    • 缓存集群部署

  2. 故障隔离：

    • 线程池隔离
    • 信号量隔离
    • 进程隔离

  3. 快速失败：

    • 熔断机制
    • 超时控制
    • 限流保护

  4. 异步设计：

    • 消息队列
    • 异步调用
    • 事件驱动

  5. 监控告警：

    • 服务监控
    • 链路追踪
    • 告警通知

Q17：如何优化微服务间通信性能？

答案：

性能优化策略：

  1. 连接池优化：

    • 使用HTTP连接池
    • 配置合理的连接数
    • 设置合适的超时时间

  2. 序列化优化：

    • 使用高效的序列化框架
    • 避免序列化不必要的数据
    • 使用压缩减少传输数据量

  3. 缓存优化：

    • 使用本地缓存
    • 使用分布式缓存
    • 设置合理的缓存策略

  4. 异步调用：

    • 使用异步HTTP客户端
    • 使用CompletableFuture
    • 使用响应式编程

  5. 负载均衡优化：

    • 选择合适的负载均衡策略
    • 配置合理的重试机制
    • 使用服务预热

Q18：如何保证微服务间通信的可靠性？

答案：

可靠性保证策略：

  1. 超时控制：

    • 设置合理的超时时间
    • 区分连接超时和读取超时
    • 使用超时传递

  2. 重试机制：

    • 配置合理的重试次数
    • 使用指数退避策略
    • 避免重试风暴

  3. 熔断降级：

    • 使用熔断器防止服务雪崩
    • 配置降级策略
    • 提供降级响应

  4. 限流控制：

    • 使用限流器控制请求速率
    • 配置合理的限流策略
    • 提供限流响应

  5. 幂等性设计：

    • 接口幂等性设计
    • 使用唯一标识
    • 避免重复处理

项目经验描述技巧

19.1 项目经验描述框架 📝

STAR法则：

  • Situation（情境）：项目背景和挑战
  • Task（任务）：你的职责和目标
  • Action（行动）：你采取的行动
  • Result（结果）：取得的成果

示例：

情境：

  • 项目背景：电商平台，日订单量100万+
  • 技术挑战：系统响应慢，经常出现超时
  • 业务挑战：用户体验差，订单转化率低

任务：

  • 优化系统性能，提升用户体验
  • 设计微服务架构，支持业务快速迭代
  • 保证系统高可用，支持大促活动

行动：

  • 拆分单体应用为微服务架构
  • 引入Spring Cloud Alibaba全家桶
  • 实现服务熔断、降级、限流
  • 优化数据库查询，引入缓存机制
  • 实现分布式链路追踪

结果：

  • 系统响应时间从3秒降低到500毫秒
  • 系统可用性从99%提升到99.99%
  • 支持双11大促，订单量提升300%

19.2 技术深度展示 🎯

1. 原理理解：

  • 不仅会用，还要理解原理
  • 能够解释底层实现机制

  • 遇到的问题是什么

19.3 项目经验示例 💻

项目名称：电商平台微服务改造

项目背景：

  • 原有单体架构，代码耦合严重
  • 系统响应慢，经常出现超时
  • 无法支持业务快速迭代

技术架构：

  • Spring Cloud Alibaba全家桶
  • Nacos服务发现与配置中心
  • Sentinel流量控制与熔断降级
  • Seata分布式事务
  • Spring Cloud Gateway网关

  3. 分布式事务：使用Seata AT模式解决分布式事务问题，保证数据一致性
  4. 性能优化：使用缓存、异步、连接池等技术，提升系统性能

项目成果：

  • 系统响应时间从3秒降低到500毫秒
  • 系统可用性从99%提升到99.99%
  • 支持双11大促，订单量提升300%
  • 开发效率提升50%，发布周期从2周缩短到1天
