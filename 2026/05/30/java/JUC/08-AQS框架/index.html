1. AQS 概述

1.1 什么是 AQS

AQS（AbstractQueuedSynchronizer） 即抽象队列同步器，是 JUC 包下 java.util.concurrent.locks 中的一个抽象类。它是构建锁和其他同步器组件的基础框架。

🔑 一句话理解：AQS 是一个用 int 状态变量 + FIFO 等待队列 来实现线程同步的框架。

1.2 AQS 的存在意义

在 AQS 出现之前，Java 的同步主要依赖 synchronized 关键字。但 synchronized 存在局限性：

synchronized 的问题 AQS 的解决方案
不可中断的等待 支持可中断获取
不支持超时等待 支持超时获取锁
非公平模式固定 支持公平/非公平两种模式
单一条件队列 支持多个 Condition 条件队列
无法共享访问 支持独占 + 共享两种模式

1.3 模板方法设计模式

AQS 使用了经典的 模板方法模式（Template Method Pattern）：

设计精髓：AQS 把复杂的队列管理、线程挂起/唤醒逻辑全部封装好，开发者只需实现几个简单的”尝试获取/释放”方法，就能快速构建自己的同步器。

🏗️ 类比：AQS 像造车厂提供了底盘、发动机、变速箱（队列、状态管理、线程调度），你只需要设计车身外形（tryAcquire/tryRelease），就能造出不同的车（ReentrantLock、Semaphore 等）。

3. CLH 队列与 Node 节点详解

3.1 什么是 CLH 锁队列

CLH（Craig, Landin, and Hagersten）是一种基于链表的高性能、公平的自旋锁。AQS 对其做了变体实现：

  • 原版 CLH：每个节点自旋等待前驱节点释放锁
  • AQS 变体：每个节点阻塞等待（park），由前驱节点唤醒（unpark），而非自旋

5. 共享模式详解

共享模式（Shared Mode）下，多个线程可以同时获取锁（共享访问），例如 Semaphore 允许多个线程同时持有许可，ReadWriteLock 允许多个读线程同时读。

13. 面试常见问题

Q1：AQS 是什么？讲一下它的设计思想。

✅ 答题要点：AQS 是 JUC 包的基础框架，使用 volatile int state + CLH 变体 FIFO 队列实现线程同步。核心思想是模板方法模式：AQS 封装队列管理、线程挂起/唤醒等通用逻辑，子类只需实现 tryAcquire / tryRelease 等钩子方法。支持独占和共享两种模式。

Q2：AQS 如何实现线程的阻塞与唤醒？

✅ 答题要点：通过 LockSupport.park() 和 unpark()。park 底层调用操作系统原语（Linux 上用 futex），将线程变为 WAITING 状态，CPU 不再调度。unpark 给线程一个”许可”，如果线程已 park 则唤醒它，如果还没 park 则下次 park 直接通过。park/unpark 不需要 synchronized，且 unpark 可以先于 park 调用。

Q3：公平锁和非公平锁的区别？AQS 层面如何实现？

✅ 答题要点：

  • 非公平锁：lock() 时先 CAS 抢一次，tryAcquire 中 state=0 时直接 CAS 抢，不管队列里是否有等待线程
  • 公平锁：lock() 直接走 acquire，tryAcquire 中先检查 hasQueuedPredecessors()，队列中有等待者则排队
  • 非公平锁吞吐量更高（减少线程切换），但有饥饿风险

Q4：ReentrantLock 如何实现可重入？

✅ 答题要点：

  • tryAcquire 中检查 current == getExclusiveOwnerThread()，如果是当前线程，state += acquires（累加重入次数）
  • tryRelease 中 state -= releases，直到 state == 0 才完全释放
  • 重入次数存在 state 中，通过 exclusiveOwnerThread 记录持有者

Q5：ReentrantReadWriteLock 的读写互斥如何实现？

✅ 答题要点：

  • 读锁：共享模式，tryAcquireShared 检查是否有其他线程持有写锁，有则返回 -1 阻塞
  • 写锁：独占模式，tryAcquire 检查是否有读锁（exclusiveCount(c) == 0 && c != 0 说明有读锁）或写锁，有则返回 false
  • 锁降级：写锁持有者可以再获取读锁（tryAcquireShared 中允许 exclusiveOwnerThread == current）
  • 不支持锁升级（读锁→写锁），会导致死锁

Q6：CountDownLatch 和 CyclicBarrier 的区别？

✅ 答题要点：

CountDownLatch CyclicBarrier
基于 AQS 共享模式 基于 ReentrantLock + Condition
一个或多个线程等待其他线程完成任务 多个线程互相等待到达屏障点
不可重置 可循环使用
减计数 减计数（内部）
不支持回调 支持 Runnable 回调

Q7：Semaphore 的实现原理？

✅ 答题要点：基于 AQS 共享模式，state 表示可用许可数。acquire 调用 tryAcquireShared，CAS 减少 state，remaining < 0 则阻塞。release 调用 tryReleaseShared，CAS 增加 state，成功后调用 doReleaseShared 级联唤醒等待线程。

Q8：Condition 和 Object.wait/notify 的区别？

✅ 答题要点：

  • Condition 支持多个条件队列（一个 Lock 创建多个 Condition）
  • Condition 支持精确唤醒（signal 只唤醒一个 Condition 的等待线程）
  • Condition 配合 Lock 使用，Object 配合 synchronized 使用
  • Condition 内部通过双队列实现：条件队列（单向链表，nextWaiter）+ 同步队列（双向链表，prev/next）

Q9：AQS 中的 Node 有哪些状态？各代表什么含义？

✅ 答题要点：

  • CANCELLED (1)：线程已取消（超时或中断），将被清理
  • SIGNAL (-1)：后继节点需要被唤醒，前驱释放时会 unpark 后继
  • CONDITION (-2)：节点在条件队列中
  • PROPAGATE (-3)：共享模式下释放需要传播（头节点专用，解决竞态）
  • 0：初始状态

Q10：为什么共享模式需要 PROPAGATE 状态？

✅ 答题要点：解决 doReleaseShared 和 setHeadAndPropagate 之间的竞态条件。当头节点 waitStatus 被 doReleaseShared CAS 从 SIGNAL 改为 0 后，setHeadAndPropagate 读到的旧 head.waitStatus 可能是 0，即使还有资源也不会传播。PROPAGATE 确保在后续 setHeadAndPropagate 读取时判断 < 0 成立，从而继续传播。这是 JDK 6 修复的一个经典 bug（bug 6801020）。

Q11：AQS 为什么用双向链表？

✅ 答题要点：

  1. 向前查找：cancelAcquire 需要向前跳过已取消节点
  2. 向后唤醒：unparkSuccessor 需要从 tail 向前找到第一个有效节点（因为 next 可能未设置）
  3. 并发安全：prev 先于 CAS 设置，一定可靠；next 最后设置，可能滞后

Q12：AQS 如何保证线程安全？

✅ 答题要点：

  • volatile：state、Node 的 waitStatus、prev、next 都是 volatile，保证可见性
  • CAS：所有状态变更都通过 Unsafe.compareAndSwapXxx（原子指令）
  • 自旋：CAS 失败不自旋等待，而是自旋重试（enq、acquireQueued）
  • 无锁编程：队列操作全程无 synchronized，仅靠 CAS + volatile
