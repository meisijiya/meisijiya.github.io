1. CountDownLatch（倒计时器）

1.1 概念

CountDownLatch 是一个同步辅助工具，允许一个或多个线程等待其他线程完成操作后再继续执行。

核心思想：维护一个计数器（count），调用 countDown() 使计数器减一，调用 await() 的线程会阻塞直到计数器归零。

1.2 核心 API

方法 说明
CountDownLatch(int count) 构造方法，count 不能小于 0
await() 阻塞当前线程，直到计数器归零
await(long timeout, TimeUnit unit) 带超时的等待，超时后不再阻塞
countDown() 计数器减一（通常由工作线程调用）
getCount() 获取当前计数值

1.3 使用场景

  1. 主线程等待多个子任务完成：比如启动时需要加载多个配置源，全部加载完成后才对外服务
  2. 并行任务汇总：多个线程并行计算，主线程汇总结果
  3. 模拟并发测试：用 new CountDownLatch(1) 作为起跑枪，让所有线程同时开始
  4. 等待服务就绪：等待 N 个服务都注册完成后才开始消费

1.5 实现原理

CountDownLatch 内部使用 AQS（AbstractQueuedSynchronizer） 实现：

  • 状态（state）就是计数器的值
  • countDown() 调用 releaseShared(1)，通过 CAS 将 state 减 1
  • await() 调用 acquireSharedInterruptibly(1)，检查 state 是否为 0
    • state = 0：直接返回（计数已归零）
    • state != 0：将当前线程加入 CLH 队列阻塞等待
  • 当 countDown() 将 state 减到 0 时，唤醒所有等待的线程

1.6 注意事项

  • 一次性使用：计数器归零后无法重置，想重复使用请用 CyclicBarrier
  • countDown() 必须在 finally 中调用：防止异常导致计数器永远不归零
  • 计数器不能小于 0：构造时 count < 0 会抛 IllegalArgumentException
  • countDown() 不会阻塞：调用后立即返回，不会等待其他线程

2. CyclicBarrier（循环栅栏）

2.1 概念

CyclicBarrier 让一组线程到达一个屏障点时全部阻塞，直到最后一个线程到达后才一起继续执行。”Cyclic” 表示它可以重复使用（reset）。

2.2 核心 API

方法 说明
CyclicBarrier(int parties) 构造方法，parties 为参与线程数
CyclicBarrier(int parties, Runnable barrierAction) 所有线程到达后先执行 barrierAction
await() 到达屏障点并等待
await(long timeout, TimeUnit unit) 带超时的等待
getParties() 获取参与方数量
getNumberWaiting() 获取当前在屏障处等待的线程数
isBroken() 查询屏障是否处于损坏状态
reset() 重置屏障（会唤醒所有等待线程并抛出 BrokenBarrierException）

2.3 使用场景

  1. 多线程分阶段计算：所有线程完成当前阶段后统一开始下一阶段
  2. 多线程数据加载：分批加载数据，每批加载完成后统一开始解析
  3. 并行迭代算法：每轮迭代需要所有线程同步后再开始下一轮
  4. 模拟多玩家游戏：等待所有玩家准备好后同时开始

2.5 与 CountDownLatch 的区别

对比维度 CountDownLatch CyclicBarrier
可重用性 一次性，计数器归零后不可重置 可循环使用，自动重置
计数方向 递减（count → 0） 递增（等待数 → parties）
触发机制 countDown() 随时调用 所有线程必须到达屏障点
等待方 一般是主线程 await() 所有参与线程都在 await()
应用场景 主线程等子任务 / 发令枪 多线程同步屏障 / 分阶段执行
异常处理 不支持 barrier action 支持 barrier action
底层实现 AQS 共享模式 ReentrantLock + Condition
是否可重置 不可 可以（reset()）

2.6 实现原理

CyclicBarrier 基于 ReentrantLock + Condition 实现：

  1. 内部维护一个 count（初始值 = parties），每次 await() 将 count 减 1
  2. 如果 count > 0：线程在 Condition 上 await() 阻塞
  3. 如果 count == 0（最后一个线程到达）：
    • 如果有 barrierAction，先执行它
    • 然后调用 Condition.signalAll() 唤醒所有等待线程
    • 重置 count 为 parties，进入下一轮

3. Semaphore（信号量）

3.1 概念

Semaphore（信号量）用于控制同时访问某个资源的线程数量。可以把它理解为一个许可证管理器：总共发放 N 个许可证，线程获取许可证后才能访问资源，用完后归还。

3.2 核心 API

方法 说明
Semaphore(int permits) 构造方法，permits 为许可数量（非公平模式）
Semaphore(int permits, boolean fair) 可指定公平/非公平
acquire() 获取一个许可（可中断）
acquire(int permits) 获取指定数量的许可
tryAcquire() 尝试获取许可，立即返回 true/false
tryAcquire(long timeout, TimeUnit unit) 带超时的尝试获取
release() 释放一个许可
release(int permits) 释放指定数量的许可
availablePermits() 当前可用许可数
drainPermits() 获取所有可用许可
getQueueLength() 等待获取许可的线程数

3.3 使用场景

  1. 限流/资源池控制：限制同时访问数据库、连接池、文件的线程数
  2. 限速器：限制 API 调用频率
  3. 互斥锁：new Semaphore(1) 可以当互斥锁使用（类似 mutex）
  4. 有界容器控制：生产者-消费者模型中限制缓冲区访问

3.5 实现原理

Semaphore 内部同样使用 AQS 实现：

  • 公平模式：new Semaphore(n, true)，使用 FairSync，严格按 FIFO 顺序分配许可
  • 非公平模式：new Semaphore(n, false)（默认），使用 NonfairSync，允许插队
  • state 表示可用许可数
  • acquire()：CAS 将 state 减 1，如果 state < 0 则阻塞
  • release()：CAS 将 state 加 1，然后唤醒等待的线程

3.6 注意事项

  • **release() 前不一定先 acquire()**：Semaphore 不要求由获取许可的线程来释放，任何线程都可以调用 release()
  • 避免许可泄漏：确保在 finally 块中调用 release()
  • 许可数可以动态增加：release() 会使许可数超过初始值（如果调用多次）

4. Exchanger（交换器）

4.1 概念

Exchanger 用于两个线程之间交换数据。每个线程在 exchange() 方法处阻塞，直到另一个线程也到达该方法，双方交换各自持有的数据后继续执行。

4.2 核心 API

方法 说明
Exchanger() 构造方法
exchange(V x) 交换数据，阻塞直到对方线程也调用
exchange(V x, long timeout, TimeUnit unit) 带超时的交换

4.3 使用场景

  1. 生产者-消费者缓冲区交换：生产者填满缓冲区后与消费者的空缓冲区交换
  2. 校验码计算：一个线程计算数据，另一个线程计算校验码，交换后验证
  3. 遗传算法：两个线程各自进化种群，定期交换优秀个体

4.5 注意事项

  • 只能两个线程交换：不支持多个线程同时交换
  • exchange() 会阻塞：直到对方线程也调用 exchange()
  • 支持超时：可以设置超时时间避免永久阻塞
  • 泛型安全：建议使用泛型版本确保类型安全

5. Future 和 FutureTask

5.1 概念

Future 表示一个异步计算的结果。提交任务后立即返回一个 Future 对象，通过它可以：

  • 查询任务是否完成
  • 等待任务完成并获取结果
  • 取消任务

FutureTask 是 Future 和 Runnable 的实现类，既可以作为 Runnable 提交，又可以获取结果。

5.4 Future 的局限性

局限 说明
get() 会阻塞 只能轮询或阻塞等待，无法回调通知
无法链式组合 不支持任务之间的依赖关系（A 完成后再执行 B）
无法合并结果 不支持多个任务结果的合并（A + B）
异常处理弱 异常只能在 get() 时捕获，无法提前处理
不支持手动完成 无法从外部主动设置任务结果

这些局限性正是 CompletableFuture 要解决的问题。

6. CompletableFuture（异步编程利器）

6.1 概念

CompletableFuture 是 Java 8 引入的增强版 Future，支持：

  • 链式调用：thenApply() → thenAccept() → thenRun()
  • 组合操作：thenCompose()（串行）、thenCombine()（并行合并）
  • 多任务编排：allOf()（全部完成）、anyOf()（任一完成）
  • 异常处理：exceptionally()、handle()
  • 手动完成：complete() 从外部设置结果

8. 面试高频问题汇总

Q1: CountDownLatch 和 CyclicBarrier 的区别？

答：

维度 CountDownLatch CyclicBarrier
可重用性 一次性 可循环使用
等待方 一般是主线程 所有参与线程互相等待
计数方式 递减（count → 0） 屏障点汇聚（到达 parties）
应用场景 等待子任务完成 多线程分阶段同步

记忆口诀：CountDownLatch 是”主线程等大家”，CyclicBarrier 是”大家互相等”。

Q2: Semaphore 的作用是什么？和锁有什么区别？

答： Semaphore 用于控制并发访问资源的线程数量，本质是信号量。

  • Semaphore(1) 功能上等同于互斥锁，但语义不同
  • 锁（ReentrantLock）强调的是互斥，同一时刻只有一个线程能进入
  • Semaphore 强调的是并发数控制，可以允许多个线程同时访问（如连接池允许 10 个并发连接）
  • Semaphore 不要求 acquire 和 release 由同一线程执行

Q3: CompletableFuture 如何处理异常？

答： 三种方式：

  1. **exceptionally(Function)**：异常发生时提供默认值
  2. **handle(BiFunction)**：无论成功失败都执行，可以同时处理结果和异常
  3. **whenComplete(BiConsumer)**：无论成功失败都执行，但只观察不修改结果

Q4: CompletableFuture 的 thenApply 和 thenCompose 有什么区别？

答：

  • **thenApply(Function)**：转换结果，T → U，类似 Stream 的 map
  • **thenCompose(Function)**：串行组合，T → CompletableFuture<U>，类似 Stream 的 flatMap

关键区别：thenCompose 不会产生 CompletableFuture<CompletableFuture<T>> 的嵌套。

Q5: Future.get() 和 CompletableFuture.join() 有什么区别？

答：

方法 抛出异常 适用场景
Future.get() 检查型异常（InterruptedException, ExecutionException） 传统 Future
CompletableFuture.join() 未检查异常（CompletionException） Lambda 表达式中（无法抛检查型异常）

Q8: Semaphore 的公平模式和非公平模式有什么区别？

答：

  • 非公平模式（默认）：新来的线程可以插队，吞吐量高
  • 公平模式：严格按 FIFO 顺序分配许可，保证公平但性能较低

Q9: CountDownLatch 的计数器能重置吗？如果需要重置怎么办？

答： CountDownLatch 本身不能重置。如果需要重复使用，有两个方案：

  1. 使用 CyclicBarrier：天然支持循环使用
  2. 创建新的 CountDownLatch 实例：每轮使用新的实例

Q10: CompletableFuture.allOf() 和 anyOf() 的区别？

答：

  • **allOf(CompletableFuture<?>... cfs)**：等待所有任务完成，返回 CompletableFuture<Void>
  • **anyOf(CompletableFuture<?>... cfs)**：任意一个任务完成就返回，返回 CompletableFuture<Object>
