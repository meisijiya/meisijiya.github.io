1. 概念与背景

1.1 什么是虚拟线程？

虚拟线程（Virtual Thread）是 JDK 21 正式发布的一个轻量级线程实现，由 Project Loom 孵化多年后终于落地。

它的核心思想可以用一句话概括：

虚拟线程是一种由 JVM 管理、不绑定到单一 OS 线程的轻量级用户态线程。

与传统的 java.lang.Thread（称为平台线程 / Platform Thread）不同，虚拟线程的创建和销毁成本极低，可以在一个 Java 进程中同时存在百万量级的虚拟线程。

1.2 为什么需要虚拟线程？

问题一：OS 线程是昂贵的资源

传统的 Java 线程（new Thread()）本质上是操作系统线程（OS Thread）的 1:1 包装。OS 线程有两个核心瓶颈：

  1. 内存占用大：每个 OS 线程的栈空间默认约 1MB，10000 个线程就是 ~10GB 内存。
  2. 上下文切换开销大：频繁的线程切换需要内核态介入，CPU 时间被大量浪费。

问题二：同步阻塞模型的困境

大多数服务端应用（Tomcat、Spring Boot 等）采用的是一请求一线程的模型（Thread-Per-Request）。当线程执行阻塞操作（数据库查询、HTTP 调用）时，OS 线程被挂起无法服务其他请求。

解决方案的历史演进：

方案 代表技术 缺点
加大线程池 — OS 线程有上限，内存扛不住
异步编程 CompletableFuture、Callback 代码难读、调试困难、堆栈断裂
响应式编程 WebFlux、RxJava 学习曲线极陡，生态不完整
虚拟线程 Java 21 Virtual Threads ✅ 同步写法，异步性能

问题三：高并发场景的成本

一个聊天服务器同时维护 10 万个长连接，在传统模型下需要 10 万个平台线程，这基本不可行。但用虚拟线程，10 万个虚拟线程只对应几十个载体线程，资源消耗可忽略不计。

1.3 虚拟线程的设计目标

  1. 保留 Thread API：开发者不需要学习新的编程模型，Thread.start()、Thread.sleep()、synchronized 等全部可用。
  2. 低成本创建：创建百万虚拟线程就像创建百万字符串对象一样轻量。
  3. 透明的阻塞处理：当虚拟线程执行阻塞操作时，JVM 自动将其从载体线程上卸载（unmount），让载体线程去执行其他虚拟线程。

2. 虚拟线程 vs 平台线程

2.1 本质区别

维度 平台线程（Platform Thread） 虚拟线程（Virtual Thread）
映射关系 1:1 映射到 OS 线程 M:N 映射（多个虚拟线程共享少量载体线程）
栈内存 ~1MB（线程栈） 初始几百字节，按需增长存储在堆上
创建成本 高（~1ms，涉及系统调用） 极低（~1μs，纯 Java 对象）
调度者 OS 内核调度器 JVM 调度器（ForkJoinPool）
数量上限 ~几千到几万 百万级
上下文切换 内核态，~10μs 用户态，纳秒级
Thread 类型 Thread Thread 的子类（API 完全兼容）
getName() 有实际线程名 有虚拟线程名
daemon 可以是非守护线程 始终是守护线程

2.3 是否是守护线程（Daemon）

虚拟线程始终是守护线程。这意味着：

  • 当所有非守护平台线程结束时，JVM 会退出，虚拟线程即使还在运行也会被终止。
  • 你不能把虚拟线程设为非守护线程（setDaemon(false) 会抛异常）。

3. 实现原理

3.1 核心架构

虚拟线程的实现围绕三个关键概念：

3.2 Continuation（续延）

Java 虚拟线程的底层核心是 jdk.internal.vm.Continuation（一个内部 API，不推荐直接使用）。

Continuation 的核心能力是 yield / resume（挂起 / 恢复）：

  • yield：保存当前执行状态（程序计数器、局部变量表等），将栈帧冻结到堆上，让出 CPU。
  • resume：从堆上恢复之前保存的栈帧，继续执行。

3.3 Carrier Thread（载体线程）与 Mount / Unmount

  • 载体线程（Carrier Thread）：就是普通的平台线程，虚拟线程在上面”运行”。默认由 ForkJoinPool 提供。

  • Mount（挂载）：当一个虚拟线程需要执行时，JVM 调度器把它”挂载”到一个空闲的载体线程上。载体线程开始执行虚拟线程的 Runnable。

  • Unmount（卸载）：当虚拟线程遇到阻塞操作（如 Thread.sleep()、socket.read()、lock() 等），JVM 将其”卸载”，释放载体线程去执行其他虚拟线程。

3.4 虚拟线程的栈

重要区别：

平台线程栈 虚拟线程栈
存储位置 操作系统的栈区（预分配 ~1MB） Java 堆（Heap）上的 Continuation 对象
分配方式 调用 clone() 系统调用，OS 分配 JVM 分配 Java 对象
增长策略 固定大小 按需增长（类似 ArrayList）

3.5 阻塞操作的”魔法”

虚拟线程最核心的价值：当代码执行阻塞操作时，JVM 在 底层自动 unmount。

JVM 识别以下阻塞操作并自动 unmount/remount：

阻塞操作 是否自动 unmount
Thread.sleep() ✅ 是
Object.wait() ✅ 是
LockSupport.park() ✅ 是
socket.read() / NIO 操作 ✅ 是（JDK 内部替换为 NIO）
CompletableFuture.get() ✅ 是
synchronized 块内阻塞 ⚠️ 会导致 pinning（见第 6 章）
native 方法内阻塞 ❌ 通常不会
文件 I/O（FileInputStream.read()） ⚠️ 部分支持（旧式同步 I/O 会 pinning）

4. 创建与使用方式

4.1 方法总览

JDK 21 提供了四种主要方式创建虚拟线程：

方式 API 适用场景
直接创建并启动 Thread.startVirtualThread(Runnable) 快速启动
使用 Builder Thread.ofVirtual().name("xxx").start(Runnable) 需要自定义名称等属性
先创建后启动 Thread.ofVirtual().unstarted(Runnable).start() 需要在线程间传递线程对象
通过 ExecutorService Executors.newVirtualThreadPerTaskExecutor() 需要线程池模式管理

4.2 方式一：Thread.startVirtualThread()

最简单的方式，直接创建并启动一个虚拟线程。

4.3 方式二：Thread.ofVirtual() Builder 模式

Builder 模式提供更多控制：名称、未捕获异常处理器等。

4.4 方式三：Thread.ofVirtual().factory()

通过 ThreadFactory 批量创建同样配置的虚拟线程。

4.5 方式四：Executors.newVirtualThreadPerTaskExecutor()

返回一个 ExecutorService，每个任务创建一个新的虚拟线程。这是最推荐的模式。

JVM 使用 ForkJoinPool 作为默认调度器，采用 work-stealing 算法：

  • 载体线程数量：默认 = CPU 核心数（可通过 jdk.virtualThreadScheduler.parallelism 调整）。

  • 工作队列：每个载体线程有自己的工作队列，空了就从其他队列”偷”任务。

6. 限制与注意事项

6.1 Pinning（线程固定）— 最重要的问题

Pinning 指虚拟线程在某些情况下无法从载体线程上卸载，导致载体线程被”钉住”。

什么会导致 Pinning？

  1. 在 synchronized 块或方法内执行阻塞操作（最常见）
  2. 在 native 方法中执行阻塞操作
  3. 在持有对象监视器（Object.wait() 的重入）期间

Pinning 的后果

如何避免 Pinning？

做法 说明
✅ 用 ReentrantLock 替代 synchronized ReentrantLock 支持虚拟线程的 unmount
✅ 限制 synchronized 块范围 尽量只包裹 CPU 计算，不放阻塞操作在里面
✅ 使用 JFR 监控 启用 jdk.VirtualThreadPinned 事件检测 pinning
✅ 用 ConcurrentHashMap 替代 Hashtable / Collections.synchronizedMap

6.2 ThreadLocal 问题

虚拟线程的数量可能非常大（百万级），每个虚拟线程如果都使用 ThreadLocal，内存会爆炸。

替代方案

替代 说明

✅ 方法参数传递 最简单直接
✅ InheritableThreadLocal 慎用 虚拟线程不支持子线程概念

11. 面试常见问题

Q1: 什么是虚拟线程？它和传统的平台线程有什么区别？

答：虚拟线程是 JDK 21 引入的轻量级线程实现，由 JVM 管理而非 OS 调度。

平台线程 虚拟线程
1:1 映射到 OS 线程 M:N 映射（多个 VT 共享少量载体线程）
OS 内核调度 JVM 调度（ForkJoinPool）
栈在 OS 内存，~1MB 栈在堆上，按需增长
创建成本高（~1ms） 创建成本低（~1μs）
数量上限几千 数量可达百万

Q2: 虚拟线程的实现原理是什么？

答：三大核心机制：

  1. Continuation：保存/恢复执行状态，实现代码在任意点挂起和恢复。
  2. Carrier Thread + Mount/Unmount：虚拟线程运行时挂载到载体线程，阻塞时自动卸载，释放载体线程。
  3. ForkJoinPool + Work-Stealing：调度载体线程执行虚拟线程，空闲载体线程从忙碌线程”偷”任务。

Q3: 什么是 Pinning？如何避免？

答：当虚拟线程在 synchronized 代码块或 native 方法中执行阻塞操作时，JVM 无法将其从载体线程上卸载，导致载体线程被”钉住”。

避免方法：

  • 使用 ReentrantLock 替代 synchronized
  • 限制 synchronized 块范围，不放阻塞操作在里面
  • 使用 ConcurrentHashMap 替代 Hashtable
  • 开启 JFR 监控 jdk.VirtualThreadPinned 事件

Q4: 虚拟线程和线程池有什么区别？什么时候用哪个？

答：

  • 虚拟线程：每个任务创建一个虚拟线程，用完即弃。适合 IO 密集型、大量并发短任务。
  • 线程池：复用有限数量的 OS 线程，适合 CPU 密集、需要限流的场景。

虚拟线程不需要池化——创建成本极低，池化反而是反模式。

Q5: 虚拟线程是守护线程吗？有什么影响？

答：虚拟线程始终是守护线程。这意味着：

  • JVM 在所有非守护平台线程结束时退出，即使虚拟线程还在运行。
  • 不能调用 setDaemon(false)，否则抛出 IllegalArgumentException。

影响：需要确保有非守护的平台线程（如 main 线程等待）来保持 JVM 存活。

Q6: 虚拟线程如何影响 ThreadLocal？有什么替代方案？

答：虚拟线程数量可达百万级，每个都使用 ThreadLocal 会导致内存爆炸。

替代方案：

  • ScopedValue（JDK 22 正式特性）：不可变、虚拟线程友好、结构化传递。
  • 方法参数直接传递。
  • 如果必须用 ThreadLocal，确保任务完成后清理。

Q7: Spring Boot 如何启用虚拟线程？

答：

启用后，Tomcat 请求处理、@Async、@Scheduled 等自动使用虚拟线程。

Q8: 虚拟线程的上下文切换为什么快？

答：虚拟线程的上下文切换是用户态操作，不涉及内核：

  1. Unmount 时，JVM 将虚拟线程的栈帧保存到堆上（Java 对象操作）。
  2. Mount 时，从堆恢复栈帧。
  3. 整个过程没有系统调用，比 OS 线程上下文切换快几个数量级。

Q9: 虚拟线程能完全替代响应式编程吗？

答：不能完全替代，但大部分场景可以。

  • ✅ 替代场景：大部分后端 CRUD、API 网关、消息处理。
  • ❌ 仍需响应式的场景：极低延迟要求（微秒级）、背压（back-pressure）需求、流式数据处理的复杂组合操作。

结论：虚拟线程降低了异步编程的需求，但不是”杀死”响应式，而是让大部分开发者不需要学习响应式。

Q10: 100 万个虚拟线程同时 sleep 1 秒，总耗时是多少？

答：约 1 秒。因为所有虚拟线程几乎同时被挂载到载体线程上执行 sleep()，遇到阻塞后立即卸载，载体线程去执行下一个。载体线程数量（默认 = CPU 核心数）限制了并发度但不影响总耗时（只要任务是 IO 密集型）。
