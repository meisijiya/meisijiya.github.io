Pi-VibeCodingExtension — 把 Vibe Coding 从"野路子"变成"规范流程"

作者: 老江湖
日期: 五月 25, 2026  0:00:00
分类: AI开发

缘起：Vibe Coding 的两个核心矛盾

在长期使用 AI 辅助编程（Vibe Coding）的过程中，我逐渐感受到两个越来越明显的矛盾：

矛盾一：大模型会「范围膨胀」。 你跟它说”帮我实现登录页面”，它写着写着就开始改路由、改样式、甚至改 package.json。需求像滚雪球一样越来越大，最后你都不知道它改了什么。

矛盾二：上下文越用越长。 每次开新 session，你都得重新描述一遍项目状态——“我们在做这个项目，上次改了这些文件，现在要做这个任务…”。几轮下来，上下文就爆了，然后压缩（compaction），然后丢信息，然后你又得重新描述。死循环。

解法只有一个：最小化每一步，让 AI 始终知道「在做什么、做了什么、边界在哪」。

这就是 Pi-VibeCodingExtension 的起源——一套把上述理念工程化的 pi 扩展。

它是什么

一个面向 pi 的扩展，核心做三件事：

  1. 约束注入：读取 AGENTS.md（项目宪法），在每次对话中自动提醒 LLM「当前任务边界」
  2. 原子 Checkpoint：每个小任务完成后 → git commit → 自动生成 diff 摘要 → 更新 session 文档
  3. 无缝交接：Session 结束时生成完整交接文档，新 session 自动读取上下文，无需重新描述

快速上手

⚠️ /vibe-init 必须在 Git 仓库根目录运行（.git 所在目录），否则面板无法找到 plan 文件和 session 文档。

亮点：多模态无缝路由

主力模型（如 DeepSeek v4）是纯文本模型，不能直接”看”图。传统做法是手动切到多模态模型，分析完再切回来——割裂且容易忘记切。

本扩展的做法：

用户完全无感——就像主力模型「会看图」一样。同时保留了 /vibe-mimo 作为兜底方案，手动切换到原生多模态模型。

上下文自动适配：大上下文模型（≥300K）注入全量 vibe 上下文；小上下文模型（如 MiniMax 256K）自动降级为精简注入（~50 tokens），防止溢出。

Context7 文档 + Karpathy 行为准则

扩展内置两个提升代码质量的机制：

Context7 文档：LLM 写代码前自动查询最新官方文档，消除”编造 API”问题。需要注册免费 API Key。

Karpathy 行为准则：整合 Andrej Karpathy 的 LLM 编程观察（15 万 stars），在每次对话中注入：

  • Simplicity First：最小代码，不加投机功能
  • Surgical Changes：只改必须改的，不碰无关代码
  • Goal-Driven：先定义可验证成功标准，再动手

上下文注入策略（Token 最优 + 多模型感知）

注入仅在状态变化时触发（任务切换 / checkpoint 完成），避免每轮都重复注入。使用 message 注入而非 systemPrompt 注入，保证 Anthropic cache 命中率 97%。

总结

Vibe Coding 的最大问题不是「AI 不够聪明」，而是「AI 不知道边界在哪」。给 AI 一个清晰的宪法（AGENTS.md）、一套原子化的任务节奏（checkpoint）、一份完整的上下文（session docs），它就能在边界内高效工作，不膨胀、不跑偏、不丢失上下文。

最小化每一步，让 AI 始终知道「在做什么、做了什么、边界在哪」。

关于上下文压缩

一个常见的误解是「用了工作流就永远不需要压缩了」。更准确的说法是：

vibe 工作流大幅降低压缩频率，但不能完全替代压缩。

三层防护

层 机制 说明
1️⃣ 预防 短 session + 精简注入 + handoff 交接 从根源减少上下文堆积
2️⃣ 监控 /vibe-status 实时显示用量（🟢🟡🔴） 看得到，就不会意外溢出
3️⃣ 兜底 pi 自动压缩 + 压缩前自动 checkpoint git 永远有完整记录

handoff 交接的三种场景

/vibe-handoff 是「存档」→ 生成 docs/vibe/sessions/handoff-xxx.md。/vibe-enable 是「读档」→ LLM 自动读取。适用于：

  • /new 开新 session 前
  • 当前 session 快结束时
  • 多分支并行（分支 A 存档 → 分支 B 读档）
