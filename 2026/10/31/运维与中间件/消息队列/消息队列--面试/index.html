消息队列基础：是什么、解决什么问题

1. 什么是消息队列？

🎬 面试现场

面试官（口语化）：你先说说，什么是消息队列？它到底解决什么问题？

⚠️ 翻车点

最容易说成「就是一个队列存消息」，漏掉它真正解决的三个问题：解耦、削峰填谷、异步处理。另一个坑是以为用了消息队列消息就不会丢——其实丢可能发生在生产、broker、消费三端，得靠同步发送、刷盘/副本、手动提交 offset 层层保证，不是上了队列就自动可靠。

📝 回答重点

  • 一句话：生产者和消费者之间的异步中间件，Broker 在中间做缓冲和持久化。
  • 三大价值：解耦、削峰填谷、异步处理，顺带把高峰流量挡在后端前面。
  • 角色就三个：生产者发完就走，Broker 存并转发，消费者按自己速度拉。
  • 大促最典型，订单先落队列，接口几十毫秒就返回，后端按能力慢慢消费。

📈 拔高

存储上两家思路不同：Kafka 用顺序写日志文件，RocketMQ 用 CommitLog 加 ConsumeQueue 索引；消费进度用 offset 记，按消费者组分开存。

💡 主动加分的追问准备

面试官追问 你的答案
消息队列的推模式和拉模式有什么区别？实际生产一般用哪种？ 推模式是 broker 主动把消息推给消费者，实时性好但容易把消费者压垮；拉模式是消费者主动去 broker 拉，能控制消费速度但可能有延迟。实际主流都是拉模式，Kafka 和 RocketMQ 都是拉模式（定时轮询或长轮询），RabbitMQ 两种都支持但推模式用得多。
消息丢失一般发生在哪些环节？怎么保证消息不丢？ 三个环节：生产端消息发出去 broker 没收到，开同步发送等 broker 确认；broker 端存了没刷盘就宕机，配同步刷盘或多副本同步复制；消费端拉下来没处理完就挂了，处理完再手动提交 offset。

❌ 千万别说的话

  • “消息队列就是个 FIFO 队列” ：它远不止存消息，重点是解耦、削峰、异步，还涉及 broker 持久化、offset、分区这些机制。
  • “用了消息队列消息就不会丢” ：丢可能发生在生产、broker、消费三端，得靠同步发送、刷盘/副本、手动提交 offset 层层保证。

2. 为什么需要消息队列？

🎬 面试现场

面试官（口语化）：你说现在系统都爱用消息队列，它到底解决什么痛点？没有它会怎样？

⚠️ 翻车点

只答「解耦」一个点就太窄，消息队列真正解决三件事：异步处理、服务解耦、流量控制。另一坑是只讲好处不提代价——多一个中间件，可用性下降、复杂度升高、还要面对一致性挑战，不是一上来就该引入的。

📝 回答重点

  • 架构从单体拆成微服务后，同步 HTTP 调用会把链路串一起，一个慢全链慢。
  • 三件事：异步处理砍掉调用方等待，服务解耦让下游随便加，流量控制把峰值拖平。
  • 典型四类场景：订单异步、日志投递、任务分发、数据同步。
  • 代价也得讲：多一层故障面，还要处理重复、顺序和最终一致。

📈 拔高

引入前先算两笔账：MQ 挂了链路能不能兜底，消费端幂等怎么做；这两条定不下来就别急着上。

💡 主动加分的追问准备

面试官追问 你的答案
异步处理和服务解耦看着很像，区别在哪？ 异步关注时间维度，让调用方不等、快速返回；解耦关注依赖维度，让上游不关心下游是谁、有几个。一个场景可能两者兼具，侧重点不同。
削峰时消息积压太多怎么办？ 先看原因。流量真大就临时扩容消费者到分区数上限；消费者有 bug 就先修 bug，期间把消息转存别处，修好再回放。

❌ 千万别说的话

  • “消息队列就是用来解耦的，还百利无一害” ：它还解决异步处理和削峰填谷，但多一个中间件就多一层不稳定：可用性、复杂度、丢失重复顺序这些一致性问题都得额外处理。

3. 说一下消息队列的模型有哪些？

🎬 面试现场

面试官（口语化）：消息队列有哪几种消息模型？分别适合什么场景，说清楚。

⚠️ 翻车点

只背「队列和发布订阅两种」不够，得说清它们能不能一对多、消费者关系。另一坑是以为两种模型互斥——发布订阅其实能兼容队列（订阅者只有一个就等同于队列），而且 RabbitMQ 用队列模型靠 Exchange 多队列冗余也能实现多消费者。

📝 回答重点

  • 两种模型：点对点队列和发布订阅，区别在一条消息能被几个消费者拿走。
  • 队列模型里多个消费者是竞争关系，消费即删，适合任务分发。
  • 发布订阅每条消息广播给所有订阅者，适合通知和日志分发。
  • RabbitMQ 靠 Exchange 把消息冗余到多个队列，用队列模型模拟广播。
  • Kafka 和 RocketMQ 用消费者组：组内分摊，跨组各收一份。

📈 拔高

Kafka 里分区和组内消费者是一对一绑定，消费者数超过分区数，多出来那些就一直空转，扩容时最容易踩这个坑。

💡 主动加分的追问准备

面试官追问 你的答案
Kafka 一个消费者组的消费者能超过分区数吗？ 能，但多出来的消费者分不到分区一直空闲。分区组内只能一人消费，所以消费者数最多等于分区数才能充分利用。
RabbitMQ 是队列模型，怎么实现发布订阅？ 靠 Exchange，生产者发到 Exchange 按绑定规则路由到多个队列，fanout 类型就广播到所有绑定队列，每个队列挂一个消费者收到同样消息。

❌ 千万别说的话

  • “队列模型每条消息只能被一个消费者消费，所以没法一对多” ：RabbitMQ 通过 Exchange 把消息冗余到多个队列，就实现了多消费者收到。
  • “消费者组只是个分组名” ：它决定分区怎么分摊：组内每条消息只一人处理，不同组各收全量副本，是负载均衡的核心。

4. 简述下消息队列核心的一些术语？

🎬 面试现场

面试官（口语化）：消息队列里那些 Producer、Broker、Topic 都是啥？你给我捋一遍核心术语。

⚠️ 翻车点

最容易把所有术语混着背，不区分不同 MQ 的模型差异。另一坑是以为 Consumer Group 是标配——RabbitMQ 基于 AMQP 压根没有消费组概念，靠多消费者绑定同一队列轮询。

📝 回答重点

  • 四个通用词先讲清：Producer、Consumer、Broker、Message。
  • 三家模型不同：RabbitMQ 是 Exchange-Queue，Kafka 是 Topic-Partition，RocketMQ 是 Topic-MessageQueue。
  • RabbitMQ 特有 Exchange、Queue、Binding、Routing Key，还有 vhost 做租户隔离。
  • Kafka 特有 Partition、Offset、Consumer Group、ISR，2.8 起 KRaft 不再依赖 ZooKeeper。
  • RocketMQ 特有 Tag、Producer Group、NameServer，MessageQueue 靠 ConsumeQueue 做索引。

📈 拔高

可靠性靠 ACK、重试和死信三件套：RabbitMQ 走 DLX，RocketMQ 自动进 %DLQ%，Kafka 没有原生死信队列，得自己在消费端实现。

💡 主动加分的追问准备

面试官追问 你的答案
Kafka 的 Partition 和 RocketMQ 的 MessageQueue 本质区别？ 功能一样都拆 Topic 提并发。差异在实现：Kafka 物理隔离独立日志目录，RocketMQ 是逻辑概念共用 CommitLog 靠 ConsumeQueue 索引区分。
消费者数超过分区数会怎样？ 多出的消费者空闲分不到分区。比如 4 分区塞 6 消费者，有 2 个一直没活干，所以消费者数一般别超分区数。

❌ 千万别说的话

  • “消费组是消息队列的标配” ：RabbitMQ 基于 AMQP 没有消费组，靠多消费者绑定同一队列自动轮询分发。
  • “Partition 和 MessageQueue 是两种完全不同的东西” ：功能等价都是为了提高并发度，只是底层存储实现不同。

5. 消息队列设计成推消息还是拉消息？推拉模式的优缺点？

🎬 面试现场

面试官（口语化）：消费端这块，你更倾向推模式还是拉模式？各自有啥优缺点，你咋选的？

⚠️ 翻车点

很多人一说推模式就”实时”、拉模式就”可控”就完了。最容易漏三点：第一，推模式痛点是 Broker 要去适配每个消费者的速率，消费者快慢不一，Broker 维护这些状态把自己搞复杂了；第二，拉模式不是纯拉，RocketMQ、Kafka 底层都用长轮询补实时性，纯轮询会有大量空请求浪费；第三，RocketMQ 的 PushConsumer 看着是推，底层还是拉，只是框架封装了自动拉取，别被名字骗了。

📝 回答重点

  • 推模式实时性好，但 Broker 要按每个消费者的速度推，快慢不一就爆仓。
  • 拉模式主动权在消费者，消费不过来就降频，代价是延迟和一堆空请求。
  • 主流是拉加长轮询：有消息立刻返回，没有就挂住连接等。
  • Kafka 的 fetch.max.wait.ms 默认 500ms，RocketMQ Broker 侧挂起默认 20 秒。
  • RocketMQ 的 PushConsumer 名字叫推，底层还是拉，只是把拉取封装好了。

📈 拔高

判断推拉别看客户端 API 名字，看谁发起请求：消费者主动发就是拉，Broker 主动发才是推。

💡 主动加分的追问准备

面试官追问 你的答案
拉模式下消费者挂了一段时间重启会丢消息吗？ 不会。消息都存在 Broker，消费者维护自己的消费位移，重启后从上次位移继续拉，只要消息没过期删除就能拉到，消费者状态和 Broker 解耦。
为什么 Kafka、RocketMQ 都选拉模式？ 消息队列本身有持久化需求，使命就是收消息、存消息。消费者各种各样有快有慢，Broker 不该依赖消费者状态，存好你来自取。推模式让 Broker 去维护每个消费者速率，吃力不讨好。

❌ 千万别说的话

  • “Kafka、RocketMQ 是推模式” ：它们是拉模式，RocketMQ 的 PushConsumer 只是把自动拉取封装成推的样子给业务看，底层还是拉。
  • “长轮询就是频繁轮询” ：长轮询是 hold 住请求等有消息再返回，避免了频繁空请求，和短轮询不断问是两码事。

可靠性四问：不丢、不重、有序、积压

6. 消息队列如何保证消息不丢失？

🎬 面试现场

面试官（口语化）：消息队列怎么做到消息不丢？从发到收整个链路都说说。

⚠️ 翻车点

最容易只盯一端，生产、存储、消费三段都得配。另一大坑是 RabbitMQ 消费端，有的便捷 API 帮你自动 ack，处理到一半宕机消息就真丢了。先看清所用方法的 autoAck 参数，稳妥就手动 basicAck。

📝 回答重点

  • 三段都得盯：生产等 Broker 确认，存储落盘再加多副本，消费处理完才 ACK。
  • RabbitMQ 生产开 Publisher Confirm，配 mandatory，路由失败走 ReturnCallback 兜底。
  • 存储别只标 durable，Quorum Queue 靠 Raft 多副本，同步到多数派才返回成功。
  • 消费确认看清楚：便捷 API 可能自动 ack，稳妥就手动 basicAck，业务跑完再确认。
  • RocketMQ 同步发送盯 SendStatus，存储同步 SYNC_FLUSH，重试 16 次进 %DLQ%。
  • Kafka 生产 acks=all 配 min.insync.replicas 至少 2，消费关自动提交，手动 commitSync。

📈 拔高

订单支付这种核心链路全开最高可靠，行为日志偶尔丢几条就用异步刷盘加 acks=1 换吞吐。超时重发天然带来重复，所以消费端幂等兜底也是这条链的一环。

💡 主动加分的追问准备

面试官追问 你的答案
生产者重试会不会导致消息重复？ 会，超时重试但首次可能已收到。Kafka 0.11+ 用幂等/事务在 Broker 去重。RocketMQ 和 RabbitMQ 靠消费端幂等，比如唯一 ID 去重表。
进死信队列的消息怎么处理？ 人工介入，写专门消费者捞出来分析失败原因，修复后重投或补偿。RabbitMQ 走 DLX，RocketMQ 自动 %DLQ%，Kafka 自写 topic 模拟。

❌ 千万别说的话

  • “消息发出去就安全了” ：存储没刷盘或消费没处理完都可能丢，必须生产、存储、消费三段一起保障。
  • “Kafka 和 RabbitMQ 一样自带死信队列” ：Kafka 没有原生死信队列，得自己写代码发到专门 topic 来实现。

7. 消息队列如何处理重复消息（保证消息的幂等性）？

🎬 面试现场

面试官（口语化）：消息队列里怎么保证同一条消息被消费多次，结果还是对的？这块你平时是怎么做的？

⚠️ 翻车点

很多人张口就说「用 Redis 去重就完事」。但 Redis 和业务库是两个存储，写 Redis 成功、业务处理失败时不删 key，就会留下一致性漏洞。还有人以为开了 Kafka 的幂等生产者就彻底解决了——其实它只防生产端单会话内的重复，消费端的重复它根本兜不住。

📝 回答重点

  • 消息重复没法从源头消除，生产超时重发、消费完没提交位点都会再来，只能消费端幂等兜底。
  • 方案一唯一标识去重：全局唯一 ID 消费前先查，查到就直接返回，没查到才执行业务。
  • Redis 存 msg:ID 用 setIfAbsent 设 7 天过期，快，但业务失败要记得删 key。
  • 方案二建去重表：msg_id 唯一索引，插入报 DuplicateKeyException 就跳过，和业务同事务。
  • 方案三业务自身幂等：版本号 CAS 更新或状态机校验，第二次进来影响 0 行直接返回。
  • 高并发下去重表每条多一次库写会成瓶颈，量大就分表，清理按时间批量删。

📈 拔高

Kafka 幂等生产者只在生产端、单会话内去重，重启换 PID 就防不住，别当万能药。去重数据定好清理策略，7 天或 30 天后基本不会再重复，按时间批量删或分表 drop。

💡 主动加分的追问准备

面试官追问 你的答案
Kafka 的幂等生产者能彻底解决重复吗？ 不能。Kafka 0.11 后靠 PID + 序列号在 Broker 端去重，但只保证单个生产者会话内不重复，重启后 PID 变了跨会话防不住，而且只解决生产端，消费端重复还得自己做幂等。
去重表数据量太大怎么清理？ 设计时就要定清理策略。按时间（7 天或 30 天基本不再重复投递）用定时任务批量删；量特别大就按天或按月分表，直接 drop 过期表比逐条删高效得多。

❌ 千万别说的话

  • “开了 Kafka 幂等生产者就不用担心重复了” ：它只解决单生产者会话内、且只在生产端的重复，跨会话重发和消费端重复消费都防不住，消费端幂等还得自己写。

8. 消息队列如何保证消息的有序性（顺序性）？

🎬 面试现场

面试官（口语化）：你项目里消息队列怎么保证顺序的？比如同一个订单的创建、支付、发货不能乱。

⚠️ 翻车点

最容易答偏的是把「有序」说成全局有序。其实绝大多数业务只要部分有序就够了——按业务 Key 把同类消息路由到同一个分区/队列，每个队列配单线程消费。张口就要全局有序（单生产者单队列单消费者）会把并发优势全丢掉。还有人忽略生产者重试会把顺序打乱。

📝 回答重点

  • 队列只保证分区内部有序，跨分区不管，让需要保序的消息都落到同一个分区。
  • Kafka、RocketMQ 用 Partition Key：订单号当 Key 哈希到同一分区，分区内有序。
  • RocketMQ 还能用 MessageQueueSelector 按 Key 选队列，本质一回事。
  • RabbitMQ 走顺序队列，单队列配单消费者。要并发就按订单号哈希拆多个队列，一队列一消费者。
  • 全局有序只剩单队列单线程一条路，除同步 Binlog 这种场景基本没人选，并发全丢。
  • 生产者重试会乱序，max.in.flight 设 1 能保序但压吞吐，更好是开幂等生产者。

📈 拔高

顺序消费时一个分区同一时刻只被组里一个消费者占住，Key 落对分区，组内多消费者也不会互抢。想提并发就扩分区，保序范围收得越窄越好扩。

💡 主动加分的追问准备

面试官追问 你的答案
生产者发送失败重试会导致乱序吗？ 会。A 发送失败在重试，B 已成功，A 重试完就跑到 B 后面了。可把 max.in.flight.requests.per.connection 设为 1，但吞吐下降。更好是开幂等生产者配合 acks=all 和 retries，由 Broker 端排序去重。
消费端多线程怎么保证顺序？ 分区是消费的最小并行单位，一个分区同一时间只被一个消费者消费。只要 Key 相同的消息落同一分区，组内多消费者也不会冲突。想提并发就加分区数，让更多消费者并行处理不同分区。

❌ 千万别说的话

  • “消息队列天然保证全局有序” ：队列只保证分区/队列内有序，跨分区无序；全局有序得牺牲并发，绝大多数场景做的是部分有序。

9. 消息队列如何处理消息堆积？

🎬 面试现场

面试官（口语化）：线上消息队列突然堆积了几百万条，你第一反应是什么？怎么处理？

⚠️ 翻车点

一上来就「加消费者」是大坑：Topic 的分区/队列数必须大于等于消费实例数，不然新加的消费者分不到分区，干瞪眼。还有人堆机器不看根因——如果是代码 bug 导致消费慢，扩容只是掩盖问题，得先定位修 bug，再临时扩容止血。

📝 回答重点

  • 堆积就是产远大于销，第一反应不是加机器，先看消费是不是被 bug 卡住。
  • 扩容前先核对分区数 ≥ 实例数，一个分区只分给一个实例，不够就先扩分区。
  • Kafka 扩分区只能加不能减，RocketMQ 加队列老客户端可能要重启，RabbitMQ 拆队列分流。
  • 消费提速三招：批量消费一次拉百条，异步消费扔线程池配手动提交，DB 走批量 SQL。
  • 限流得自己建，比如 Guava RateLimiter。别把 linger.ms、batch.size 当限流，那俩只管攒批。
  • 止血之后回来找根因，消费慢是 bug 就修 bug，扩容只是争取时间。

📈 拔高

顺序消费时加消费者没用，一个分区只被一个消费者消费，得先提速单个消费者或连分区一起扩。治完堆积值得把保序范围缩小，按订单 ID 路由，分区内保序、分区间并行。

💡 主动加分的追问准备

面试官追问 你的答案
消费者崩溃了，堆积的消息会丢吗？ 不会。Kafka 消息持久化在磁盘、消费位点也持久化，重启从上次 offset 继续。RocketMQ 消息在 CommitLog、进度在 ConsumerOffset，Broker 没挂就没丢。
顺序消费场景下堆积了怎么办？ 不能随便加消费者，一个分区只能被一个消费者消费，加了也没用。先提单消费者处理速度，或加分区同时加消费者。也可把严格顺序范围缩小，按订单 ID 路由到不同分区，分区内顺序、分区间并行。

❌ 千万别说的话

  • “堆积了就直接加机器加消费者” ：分区数没大于等于实例数，新消费者分不到分区白加；而且要先定位是不是 bug，否则扩容只是掩盖问题。

事务消息：RocketMQ、Kafka、RabbitMQ 三家的做法

10. 说一下 RocketMQ 中关于事务消息的实现？

🎬 面试现场

面试官（口语化）：RocketMQ 的事务消息到底是怎么实现的？它跟本地事务怎么保证一致？

⚠️ 翻车点

只甩一句「两阶段提交」就完事最容易翻车——追问「半消息是什么、什么时候回查」就接不住了。还有个更隐蔽的坑：以为事务消息能保证消费端一定成功。其实它只保证发送端本地事务和消息投递的一致性，消费失败还得靠消费端自己的重试。

📝 回答重点

  • RocketMQ 事务消息是两阶段提交：先发半消息，消费者看不到，再执行本地事务。
  • 本地事务成功就发 Commit，半消息转正式消息。失败发 Rollback，Broker 直接丢弃半消息。
  • 没及时 Commit 或 Rollback 就触发事务回查，Broker 扫半消息队列，回调生产者的 checkLocalTransaction。
  • 回查三态 COMMIT_MESSAGE、ROLLBACK_MESSAGE、UNKNOW，UNKNOW 比如查库超时，过会再查。
  • 半消息放 RMQ_SYS_TRANS_HALF_TOPIC，已处理记录写 RMQ_SYS_TRANS_OP_HALF_TOPIC，扫描靠它过滤。
  • 回查上限 transactionCheckMax 默认 15 次，超了当 Rollback 扔掉。间隔 4.x 默认 60 秒，5.x 源码默认 30 秒。

📈 拔高

op 队列不直接删半消息，因为 CommitLog 只顺序追加，顺序写机械盘能到几百兆每秒，随机写只有几十 KB。事务消息只保发送端一致，消费失败仍靠消费端重试 16 次，再失败进死信。

💡 主动加分的追问准备

面试官追问 你的答案
半消息为什么不直接删除，而是要搞一个 op 队列来标记？ RocketMQ 的 CommitLog 顺序追加写入，写进去的消息不会再改也不会删，这是为了保证写入性能（机械盘顺序写约 600MB/s，随机写可能只有几十 KB/s）。所以只能用 op 队列标记哪些半消息已处理，扫描时做个过滤。
如果生产者一直返回 UNKNOW，Broker 会无限回查吗？ 不会，有上限。默认最多回查 15 次，transactionCheckMax 可配。超过还是 UNKNOW 就当 Rollback 扔掉。回查间隔 4.x 默认 60 秒，5.x 源码默认 30 秒。

❌ 千万别说的话

  • “事务消息能保证消费者一定消费成功” ：它只保证发送端本地事务和消息投递一致，消费端失败还得靠消费端重试（默认 16 次，再失败进死信队列）。
  • “事务消息就是普通消息加个标记” ：它要发半消息、等本地事务、发 Commit/Rollback，Broker 还得把消息写两遍，触发回查开销更大，吞吐比普通消息低不少。

11. RocketMQ 的事务消息有什么缺点？你还了解过别的事务消息实现吗？

🎬 面试现场

面试官（口语化）：你说用过 RocketMQ 事务消息，它有哪些坑？除了它，你还知道别的事务消息方案吗？

⚠️ 翻车点

只答”半消息加回查”流程、不提缺点会被追问。RocketMQ 事务消息三个真痛点：改造成本大、不支持批量、MQ 挂了整个事务瘫。最容易被忽略的是第三点——它先发半消息再执行本地事务，等于”先写 MQ 再写数据库”，MQ 一挂，MySQL 好好的业务也跑不了。对比方案别只说 RocketMQ，去哪儿 QMQ 的本地消息表正好解决”MQ 挂了业务动不了”的问题。

📝 回答重点

  • 先说三个痛点：改造成本大、不支持批量发送、MQ 挂了业务跟着瘫。
  • 改造成本大，得自己实现 TransactionListener，回查逻辑也得写，跟平时加个注解差远了。
  • 批量官方不支持，一个事务只装一条消息，多条类型只能逐条发。
  • 最要命的是先发半消息再跑本地事务，MQ 一挂，MySQL 正常业务也停了。
  • 换方案我提去哪儿 QMQ 的本地消息表，消息和业务进同一个事务，提交后再异步发 MQ。

📈 拔高

半消息这条链上 MySQL 是被动的，业务能不能跑全看 MQ 脸色，这是它和本地消息表的根本分野。补偿任务把发送兜住之后，MQ 挂了顶多消息晚到，业务照常跑。

💡 主动加分的追问准备

面试官追问 你的答案
RocketMQ 的回查机制什么时候触发？ 两种：本地事务超时被 Broker 主动问，或者确认丢了 Broker 定时查。4.x 默认 60 秒一次、transactionCheckMax 15 次超了回滚，5.0 改超 4 小时强制回滚。
本地消息表方案有啥缺点？ 多一张消息表要维护，DBA 得配合。业务和消息写同一事务，量大可能拖慢业务。补偿扫描间隔不好定，太频繁浪费、太稀疏延迟高，一般 5-10 秒。

❌ 千万别说的话

  • “RocketMQ 事务消息先写数据库再发消息” ：正好反了，它是先发半消息（先写 MQ）再执行本地事务，所以 MQ 挂了业务才动不了。
  • “本地消息表删记录失败没事” ：删失败会重复发，消费端必须做幂等，用消息 ID 或业务唯一键去重。

12. 说一下 Kafka 中关于事务消息的实现？

🎬 面试现场

面试官（口语化）：讲讲 Kafka 的事务消息是怎么实现的？和你了解的 RocketMQ 事务消息有啥不一样？

⚠️ 翻车点

最容易栽的是把 Kafka 事务当成”分布式事务”那种——其实它不是。Kafka 的事务是实现 Exactly Once 语义，而且这个”恰好一次”只在”从 Kafka 消费、处理后再写回 Kafka”这种特定场景才成立，不是”发一条消息只被消费一次”。另一个坑：Kafka 没有回查机制，事务超时就直接回滚（默认 60 秒），想重试得新开事务重发全部消息。

📝 回答重点

  • Kafka 事务三件套：事务协调器管启停，幂等生产者用 PID 加序号去重，消费端设 read_committed 只看已提交的。
  • 流程是开事务、写消息、发 commit，协调器先预写事务日志，再往分区写结束标记。
  • 消费端看到事务标记才放行，标记之前的半成品消息一律跳过。
  • 幂等和事务分工要分清：PID 加序号只管去重，跨实例的事务唯一性靠 transactional.id。
  • 事务消息混在普通消息里，Broker 侧不做半消息隔离，全靠消费端按标记过滤。

📈 拔高

transactional.id 被新实例接管时，老实例没提交的事务直接 abort，所以多实例部署一人一个 ID。事务越长 LSO 卡得越久，我把批攒够再开事务，提交窗口压到最短。

💡 主动加分的追问准备

面试官追问 你的答案
Kafka 事务消息影响消费延迟吗？ 会。read_committed 下只能消费 LSO 之前的消息，事务没提交后面全得等。写入还要过协调器确认，所以事务要尽量短。
transactional.id 能随便设吗？ 不能。同一时刻同一 transactional.id 只能有一个活跃生产者实例，新实例启动会踢掉老的。多个实例并行发事务必须每个 ID 不同，通常业务标识加实例编号。
Kafka 有回查机制吗？ 没有。事务超时就回滚，默认 60 秒可配 transaction.timeout.ms，协调器主动回滚并写 Abort Marker。想重试得新开事务重发全部消息。

❌ 千万别说的话

  • “Kafka 事务消息就是分布式事务，保证发一条只被消费一次” ：错，它实现的是”消费-处理-写回 Kafka”场景下的 Exactly Once，不是任意发送消费的恰好一次，别被名字唬住。
  • “Kafka 事务和 RocketMQ 一样靠回查” ：不一样，Kafka 没有回查，超时直接回滚，且事务消息由消费端过滤。

13. 说一下 RabbitMQ 的事务机制？

🎬 面试现场

面试官（口语化）：RabbitMQ 也有事务？它跟数据库事务是一回事吗，怎么用？

⚠️ 翻车点

第一句就要划清界限：RabbitMQ 事务只管消息发送这一环节的原子性，不涉及消费端，更不是分布式事务，和数据库 ACID 不是一回事。致命问题是太慢——官方口径是开事务吞吐降 250 倍，所以生产几乎不用，都用 Publisher Confirm。还有：事务和 Confirm 互斥，同一 Channel 两个都开就报错。

📝 回答重点

  • 三个命令：txSelect 开、txCommit 提交、txRollback 回滚，一批消息要么全部进队列，要么全部回滚。
  • 原子性只到单队列，跨队列提交可能只在部分队列可见，别答成全 broker 事务。
  • 官方口径开事务吞吐降 250 倍，慢在 txCommit 同步等 Broker 回确认，生产基本不用它。
  • 要异步确认走 Publisher Confirm，单条 waitForConfirms、批量、ConfirmListener 三种用法。
  • 回滚后未 commit 的发布不入队，也不会走死信，要保留只能生产者自己重发。

📈 拔高

事务期间 Channel 被锁，同一条连接上的其他操作全在干等，这比吞吐数字更伤。Confirm 走异步回调，哪条失败能精确知道，高频链路我一律用它。

💡 主动加分的追问准备

面试官追问 你的答案
事务能保证消费端也成功吗？ 保证不了。事务只管生产端到 Broker，消息进队列后消费者拉取、处理、ack 都不在范围内，端到端可靠得靠手动 ack、幂等消费、失败重试。
事务和 Confirm 能同时开吗？ 不行，互斥。同一 Channel 要么事务要么 Confirm，调了 txSelect 再 confirmSelect 会报错，两套同步/异步逻辑无法兼容。

❌ 千万别说的话

  • “用了 RabbitMQ 事务就能和数据库混在一起保证 ACID” ：两回事，数据库回滚了消息可能已发出。这种一致性得靠本地消息表或 RocketMQ 的事务消息。

Kafka 深挖：时间轮、索引、控制器与请求链路

14. 你了解 Kafka 中的时间轮实现吗?

🎬 面试现场

面试官（口语化）：Kafka 里那些延迟任务——消息过期、连接超时、心跳检测——它是怎么高效管理的？时间轮你了解吗？

⚠️ 翻车点

最容易答偏的是把时间轮说成「就是一个定时器」，然后讲不清它比普通优先队列强在哪。关键是插入和删除都是 O(1)，而传统优先队列每次操作都要 O(logN)。还有人忽略 Kafka 是多层时间轮，单层根本管不了从毫秒到小时跨度的任务。另外 Kafka 用 DelayQueue 驱动推进这个巧妙设计得点出来，不然说不清「空推进」问题。

📝 回答重点

  • Kafka 用时间轮管延迟任务，消息过期、连接超时、心跳检测都走它。
  • 结构是环形数组，每个槽代表固定间隔，任务算好下标扔进槽里，指针扫到就取出来执行。
  • 插入删除都是 O(1)，传统优先队列每次 O(logN)，任务几十万时堆先扛不住。
  • 单层跨度不够就叠多层时间轮，1ms、20ms、400ms 往上，很少的槽管毫秒到小时。
  • 推进不靠定时器轮询，靠 DelayQueue 装槽，时间没到就阻塞，没有空推进浪费。

📈 拔高

槽做成双向链表是因为任务会被取消，删节点要 O(1)。350ms 这种任务第一层装不下先放高层，时间推进再降回第一层触发，精度不丢。

💡 主动加分的追问准备

面试官追问 你的答案
时间轮精度是不是越高越好？ 不是。精度越高槽越多、内存越大，推进频率也得跟上。Kafka 默认第一层 1ms 够用，一般取任务最小延迟的十分之一到五分之一就行。
时间轮能处理执行时间很长的任务吗？ 时间轮只负责触发，不负责执行。任务触发后丢线程池异步跑，不阻塞推进。Kafka 里触发的任务都是异步提交的。

❌ 千万别说的话

  • “时间轮就是个定时器，到点执行任务” ：定时器每毫秒推进会有空推进浪费 CPU；Kafka 用 DelayQueue 阻塞驱动才避免这点，这点才是亮点。
  • “单层时间轮就够了” ：单层跨度有限，跨毫秒到小时得靠多层 + 降级机制，否则 1 小时的任务根本放不下。

15. Kafka的索引设计有什么亮点？

🎬 面试现场

面试官（口语化）：Kafka 一天处理那么多消息，查一条指定 Offset 的消息怎么做到那么快？它的索引设计有什么讲究？

⚠️ 翻车点

最容易漏的是稀疏索引这个点——Kafka 隔一段才记一次索引，错把这说成「每条消息都建索引」就全错了。另一个盲区是改进版二分查找（冷热分区）：标准二分跳着访问，对 page cache 不友好会触发缺页中断，这点几乎没人答得出来，答出来就是高分。三大类索引（位移/时间戳/已中止事务）也得拎清楚。

📝 回答重点

  • 核心是稀疏索引加段文件，每隔 4KB 记一条 Offset 和物理位置，索引小才装得进内存。
  • 日志切成多个 Segment，每个配 .log 和 .index，先二分定段再进段内找。
  • 拿 Offset 二分找小于等于它的索引项，取物理位置顺扫几条就到，一次磁盘 IO 搞定。
  • 三类索引分文件：位移 .index、时间戳 .timeindex、中止事务 .txnindex。
  • 位移索引用相对位移存，每项 8 字节，项越短内存装得越多、命中率越高。
  • 写入全是顺序追加，随机写变顺序写，改进版二分还分热冷区，热查询不碰冷页。

📈 拔高

这类设计的账要算清：稀疏换内存、顺序换吞吐，Kafka 没在索引上花每条消息的代价。放在 MySQL 里对比就是 InnoDB 主键不宜过长，一个道理。

💡 主动加分的追问准备

面试官追问 你的答案
稀疏索引间隔怎么控制？设太大太小会怎样？ 由 log.index.interval.bytes 控制，默认 4KB。太小索引膨胀、内存变大。太大则定位后顺序扫描的消息变多、查询变慢。一般保持默认。
想按时间查某个时刻之后的消息怎么定位？ 先在时间戳索引里二分找小于等于目标时间戳的最近项，拿到 Offset，再用这个 Offset 去位移索引查物理位置，两次索引查询加一次顺序扫描。

❌ 千万别说的话

  • “Kafka 每条消息都建索引” ：是稀疏索引，默认每 4KB 才建一条，靠内存装得多才快。
  • “直接标准二分查索引就行” ：标准二分跳访问会触发缺页中断，Kafka 用的是冷热分区改进版二分才保证热查询不读盘。

16. 看过源码？那说说 Kafka 控制器事件处理全流程？

🎬 面试现场

面试官（口语化）：你说看过 Kafka 源码？那把控制器处理事件的全流程给我走一遍。

⚠️ 翻车点

很多人把 Controller 说成「管分区的组件」，但说不清 ZK 模式下怎么靠临时节点选主、KRaft 下怎么靠 Raft 投票，更说不清事件模型为什么从多线程加锁改成了单线程队列。还有人把三种通知请求（LeaderAndIsrRequest、StopReplicaRequest、UpdateMetadataRequest）张冠李戴。

📝 回答重点

  • Controller 管整个集群的协调：主题增删、分区重分配、Leader 选举、监听 Broker 上下线、下发元数据。
  • 选主得分模式讲：ZK 模式下大家抢建 /controller 临时节点，先建成的就是它，宕机会话一断节点就消失，再抢一次。
  • 事件模型是单线程事件队列：0.11.0.0 起把共享元数据操作封成事件塞进阻塞队列，一个专属线程串行跑，KAFKA-5028 就是这个改动。
  • 流程一串到底：变更通知进 ControllerEventManager，ControllerEventThread 取出来，KafkaController#process 按事件类型分发到 processXXXX。
  • 通知 Broker 只用三种请求：LeaderAndIsrRequest 发 Leader 和 ISR，StopReplicaRequest 停副本，UpdateMetadataRequest 刷元数据。

📈 拔高

ZK 模式下只有 Controller 自己在 ZK 上挂集群元数据 Watcher，非 Controller 的 Broker 只建 /brokers/ids 临时节点。KRaft 下这套全换成 Raft 投票和日志复制，候选节点看 controller.quorum.voters。

面试官追问 你的答案
为什么要用单线程事件队列而不是加锁？ 多线程抢共享元数据要到处加锁，性能差还容易出 bug。0.11 后把共享数据操作抽象成事件入队，单线程串行处理，省掉锁还提升可维护性。

❌ 千万别说的话

17. 看过源码？那说说 Kafka 处理请求的全流程？

🎬 面试现场

面试官（口语化）：Kafka Broker 收到一个请求到返回响应，中间都经历了什么？

⚠️ 翻车点

把 Acceptor、Processor、KafkaRequestHandlerPool 三层顺序和各自职责说反。还有人不知道网络线程和 I/O 线程之间是生产者-消费者模式、两者解耦，以及为什么控制类请求要单独走一套 Listener。

📝 回答重点

  • Kafka Broker 走 Reactor 模式，和 Netty、Redis 一个套路，三层各管一段。
  • 第一层 Acceptor 每个 listener 只有一个，只管建连，轮询挑一个 Processor 把连接交出去。
  • 第二层 Processor 是网络线程，默认 3 个由 num.network.threads 控制，读数据封装成 Request 扔进共享队列，处理完再把 Response 送回客户端。
  • 第三层 I/O 线程池 KafkaRequestHandlerPool 默认 8 个由 num.io.threads 控制，从队列取 Request，在 KafkaApis 按 apiKey 分发，完事塞回对应 Processor 的响应队列。
  • 网络线程和 I/O 线程是生产者-消费者，解耦后各自扩：消费不过来加 io.threads，网络堵了加 network.threads。
  • 控制类请求单独走一套 listener，一个 Processor、队列写死 20，得配 control.plane.listener.name 才生效，免得被数据请求堵到超时。

📈 拔高

两套 listener 是变相的优先级：删 topic 时 producer 还在写，Preferred Leader 选举时老 leader 还在等 follower，控制请求排在数据后面就超时。KRaft 下 Controller 和 Broker 之间走 controller listener，不占 data listener。

💡 主动加分的追问准备

面试官追问 你的答案
请求队列满了新请求怎么办？ Processor 会阻塞在往队列放请求那一步，等空位才能继续，它管理的其它连接事件也处理不了，整体吞吐下降；这时该加 I/O 线程数提高消费速度。
num.network.threads 和 num.io.threads 怎么调？ network.threads 瓶颈在网络 I/O，连接多、带宽打满时加；io.threads 瓶颈在磁盘和业务处理，一般设成跟 CPU 核心数相当（默认就是 8）。看 RequestQueueSize 和 ResponseQueueSize 指标：请求队列堆就加 io.threads，响应队列堆就加 network.threads。

❌ 千万别说的话

  • “Processor 既读请求又处理业务逻辑” ：读和封装 Request 是 Processor（网络线程）干的，真正的业务处理在 KafkaRequestHandlerPool 的 I/O 线程里，两者通过共享队列解耦，别混为一谈。

面试官（口语化）：Kafka 里 ZooKeeper 到底是干嘛的？老版本没它为啥压根起不来？

⚠️ 翻车点

只说「存元数据」太笼统，答不出具体存哪、怎么存。还有人把消费者的 Offset 还停在 ZooKeeper 上——0.9 之后早就挪到 __consumer_offsets 主题了，只有老版本才存在 ZooKeeper。

  • 先说清版本：这套是 4.0 之前的 ZK 模式，4.0 已把 ZooKeeper 整个移除，新集群全跑 KRaft。

ZooKeeper 整个挂了 Kafka 还能跑吗？ 已在运行的 Broker 还能处理读写，因为元数据缓存都在内存里；但凡是涉及元数据变更的操作（建主题、Leader 切换、新 Broker 加入）都做不了，这时候有 Broker 宕机就选不出新 Leader，对应分区不可用。

❌ 千万别说的话

  • “消费者 Offset 一直在 ZooKeeper 上” ：0.9 之后已经挪到 __consumer_offsets 主题了，只有老版本才存 ZooKeeper；另外别把 /controller 和 /brokers/ids 的作用搞混。

19. Kafka为什么要抛弃 Zookeeper？

🎬 面试现场

面试官（口语化）：Kafka 现在都 KRaft 了，当初为什么要扔掉 ZooKeeper？

⚠️ 翻车点

只说「为了性能」太单薄。三个维度（架构、扩展性、运维）都得点到，尤其要讲清 ZooKeeper 强一致写入慢、自己选举时还不提供服务，以及单 Controller 故障转移要全量重加载元数据这两点。

📝 回答重点

  • 一句话：KRaft 用 Kafka 自己的 Raft 共识接管元数据，ZooKeeper 这个外部依赖直接去掉。
  • 架构上，上个中间件就得陪一套 ZK，部署、监控、排障全是两套系统，去掉后只维护 Kafka 自己。
  • 扩展性上，ZK 是强一致写，要等超半数节点确认，它自己选举期间还不提供服务，集群大了元数据就是瓶颈。
  • 故障转移也快了：老方案新 Controller 要全量重载元数据再同步给所有 Broker，KRaft 的 Controller Quorum 早同步好，切换只补增量。
  • 迁移工具 kafka-metadata.sh 3.4 就有早期版，3.6 和 3.7 的官方文档还标不推荐上生产，3.8 起才撤警告。
  • 回退卡在 finalize：finalize 之前各阶段能按官方回退表撤，一旦 finalize 就回不去了，先在测试环境跑一遍。

📈 拔高

KRaft 不光省掉一套系统，元数据日志本来就在 Quorum 里复制，Controller 换人只补增量，分区数才敢往上堆。ZK 那边写入要等超半数确认，它自己选主那阵还不服务，两边的差距主要在这。

💡 主动加分的追问准备

面试官追问 你的答案
KRaft 模式下 Controller 怎么选出来的？ 用 Raft 选举：候选节点向其它节点发起投票，拿到超半数票就成为 Leader，每次选举带任期号 epoch，任期号大的说话算数；不依赖外部协调服务，通常几百毫秒完成，比 ZooKeeper 快得多。
老集群怎么从 ZooKeeper 迁到 KRaft？ 3.4 提供早期迁移工具，3.6 和 3.7 的官方文档仍写不推荐上生产，3.8 起才撤掉这条警告。先起 KRaft Controller，用 kafka-metadata.sh 把快照迁过去，再滚动重启 Broker 连新 Quorum。finalize 之前可按官方回退表撤销，finalize 之后回不去。

❌ 千万别说的话

  • “ZooKeeper 读写很快” ：它是强一致协调服务，写入要等超半数节点确认，性能差且只适合小量元数据；而且它自己选举期间还不提供服务，正是这些瓶颈逼出了 KRaft。

20. 说一下 Kafka 为什么性能高？

🎬 面试现场

面试官（口语化）：Kafka 名气大，大家都说它快，那你具体讲讲它性能高到底是靠什么撑起来的？

⚠️ 翻车点

最容易泛泛说一句「因为用了零拷贝」就完了，其实 Kafka 的快是五点合力，只提一点显得没体系。另一个坑是把零拷贝说成「一次都不拷贝」——它省的是用户态和内核态之间的拷贝，磁盘到内核缓冲那次还在。

📝 回答重点

  • Kafka 的快靠五件事一起使劲：顺序写磁盘、Page Cache、零拷贝、批量处理、分区并行。
  • 顺序写：消息只往日志尾部追加，机械盘顺序写能到 100-200MB/s，这是单盘经验值，官方 RAID-5 案例里线性写 600MB/s 对随机写 100k/s，差 6000 倍以上。
  • Page Cache：写先进页缓存，内存返回就算成功，后台线程批量刷盘，单条延迟是内存级微秒级。
  • 零拷贝：拉消息走 sendfile，数据从磁盘到网卡不过用户态，省两次 CPU 拷贝和两次上下文切换。
  • 批量处理：生产者攒够 16KB 或等 linger.ms（默认 0）哪个先到发哪个，一次往返带几百上千条。
  • 分区并行：一个 Topic 几十个分区各写各的，消费者也能并行拉，加机器就加吞吐。

📈 拔高

零拷贝省的是用户态和内核态那两次，磁盘到内核缓冲那次还在，网卡带 scatter-gather DMA 才连内核到 Socket 那次也省掉。快不快还得看 acks，acks=1 落 Page Cache 就返回，Leader 断电会丢，要强可靠得配 acks=all。

💡 主动加分的追问准备

面试官追问 你的答案
零拷贝是真的一次都不拷吗？省掉哪几次？ 不是完全不拷，是省掉用户态和内核态之间的拷贝。传统 4 次拷贝，用 sendfile 后数据不过用户空间；网卡支持 scatter-gather DMA 时连内核到 Socket 的拷贝也省了，CPU 几乎不参与。
顺序写为啥比随机写快？ 机械硬盘瓶颈是磁头寻道（约 10ms），随机写每秒最多百次；顺序写不寻道能跑满带宽。SSD 没寻道问题，但随机写会触发 GC 和写放大。

❌ 千万别说的话

  • “Kafka 零拷贝就是数据一次都不拷贝” ：省的是用户态和内核态之间的拷贝，磁盘到内核缓冲那次仍在；网卡支持 scatter-gather 时才能把内核到 Socket 那次也省掉。
  • “Kafka 靠顺序写所以从不丢消息” ：默认 acks=1，落 Page Cache 就返回，Leader 断电会丢；要强可靠得配 acks=all。

21. 为什么 RocketMQ 不使用 Zookeeper 作为注册中心呢？而选择自己实现 NameServer？

🎬 面试现场

面试官（口语化）：RocketMQ 为啥不用 Zookeeper 当注册中心，非自己搞个 NameServer？

⚠️ 翻车点

真正的理由是消息队列的注册中心不需要强一致性，ZK 那套选主+强一致的代价用不上——这点答不出就偏了。还有人把 NameServer 说成有状态要选主，其实它无状态、互不通信、无选主，依据设计文档和源码。也别漏掉兜底手段是客户端重试加本地缓存，而不是靠 NameServer 保证实时一致。

📝 回答重点

  • 注册中心压根不需要强一致性，Zookeeper 那套 ZAB 选主对路由是大材小用。
  • NameServer 只存 Broker 地址和路由，无状态、节点间互不通信，谁挂了客户端就切别的节点。
  • 心跳这套数字要背熟，Broker 每 30 秒上报一次，NameServer 每 10 秒扫描一次，超 120 秒没心跳就剔除。
  • 路由全放内存，一次查询就是几次 HashMap get。客户端带本地缓存，所有 NameServer 挂了也能撑一阵。
  • ZK 写入只能走 Leader，规模大了成瓶颈。NameServer 每个节点都能独立收注册，天然水平扩展。

📈 拔高

源码里注册周期被钳制在 10~60 秒，120 秒对应 BROKER_CHANNEL_EXPIRED_TIME 这个常量。客户端重试是避开上次失败的 Broker 重选队列，单 Broker 集群绕一圈还是会回原 Broker。

💡 主动加分的追问准备

面试官追问 你的答案
NameServer 挂了重启路由会丢吗？ 会，但 Broker 每 30 秒发心跳带完整路由信息，NameServer 重启后最多 30 秒重建，客户端靠本地缓存基本无感知。
为啥不用 Nacos 或 Consul 这些成熟注册中心？ 技术上可以但没必要，NameServer 代码量就几千行、核心是维护几张 HashMap，阿里自己能搞定。RocketMQ 诞生时 Nacos 也还没出来。

❌ 千万别说的话

  • “NameServer 和 Zookeeper 一样保证强一致” ：NameServer 是最终一致，靠客户端重试（同步发送默认 2 次，避开上次失败的 Broker 重选队列，单 Broker 集群仍会回原 Broker）和本地缓存兜底，不保证路由实时完全一致。

22. RocketMQ 的延迟消息是怎么实现的？

🎬 面试现场

面试官（口语化）：RocketMQ 能发延迟消息，比如下单 30 分钟未支付自动关单，它底层到底是怎么把消息「按住」一会儿再投递的？

⚠️ 翻车点

别一上来就说「用定时任务扫」，要讲清核心机制是偷梁换柱：先把消息藏进内部 Topic，到点再还原。另一个坑是以为支持任意精度延迟，早期开源版只支持固定的延迟等级 1s~2h，按指定延时时间投递是 5.0 才有的。

📝 回答重点

  • 延迟消息的机关在偷梁换柱：先把消息藏进内部 Topic，到点再还原。
  • Broker 收到带 DelayLevel > 0 的消息，不投原 Topic，先把 Topic 换成 SCHEDULE_TOPIC_XXXX。
  • 原始 Topic 和队列 ID 会备份进消息 Properties，还原时靠它找回身份，防止消息丢了户口。
  • ScheduleMessageService 给每个延迟级别起定时任务，默认每 100ms 扫对应队列，队头到期就还原重写 CommitLog。
  • 开源 4.x 只给 18 个固定等级，从 Level 1=1s 到 Level 18=2h，任意精度得等 5.0。

📈 拔高

源码里 delayLevel2QueueId = delayLevel - 1，Level 3 落在 Queue 2。定时任务首次延迟 1 秒、异常退避 10 秒，早期不给任意精度是拿队列换排序，每级一个队列只查队头 O(1)，全局 PriorityQueue 要 O(logN)。

💡 主动加分的追问准备

面试官追问 你的答案
为什么早期不支持任意精度延迟（比如 13 秒）？ 任意精度要对海量消息按到期时间排序，全局 PriorityQueue 插入删除是 O(logN)，吃 CPU。固定级别把排序问题转成队列问题，每级一个队列，只需查队头，复杂度 O(1)。
RocketMQ 5.0 怎么支持任意精度？ 5.0 走 DELAY 类型 Topic，按消息里的时间戳投递，默认精度 1000ms、上限 24h。社区解读称内部用多级时间轮（Hashed Wheel Timer），任务放对应格子，插入取出接近 O(1)。

❌ 千万别说的话

  • “RocketMQ 延迟消息支持任意精度，13 秒也行” ：开源 4.x 只支持 18 个固定延迟等级（1s~2h），按任意延时时间投递是 5.0 才加的，内部实现社区解读为时间轮。
  • “延迟消息丢了就丢了，重启也没了” ：延迟消息已持久化到 CommitLog 和 ConsumeQueue（在 SCHEDULE_TOPIC_XXXX 下），重启后 ScheduleMessageService 会从消费进度继续扫描恢复。

23. RocketMQ 的开发参考了 Kafka，那两者在架构和功能上有什么区别？

🎬 面试现场

面试官（口语化）：都说 RocketMQ 是参考 Kafka 写的，那它俩到底差在哪？别光说都快，讲讲架构和功能上的区别。

⚠️ 翻车点

别只说「RocketMQ 借鉴了 Kafka 然后加了功能」这种空话。要落到具体四点架构差异（协调节点、分区、存储、备份）和四点功能差异（过滤、事务、延迟、死信），否则一追问就露怯。

📝 回答重点

  • 协调这块 Kafka 早期靠 ZooKeeper，2.8 起能切 KRaft，4.0 起 ZK 直接移除。RocketMQ 从头用 NameServer，无状态不用选主。
  • 分区设计不同：Kafka 每个 Partition 存完整消息，RocketMQ 的 Queue 只存索引，消息全进 CommitLog。
  • 存储上 Kafka 每个 Partition 下是多段 Segment 文件，Topic 一多页缓存被摊薄。RocketMQ 所有 Topic 共写一个 CommitLog，写更集中。
  • 主从粒度也不同：Kafka 是 Partition 级主从，RocketMQ 以 Broker 为单位同步 CommitLog，开 DLedger 多副本时例外。
  • 功能上 RocketMQ 多出三样：Tag 同 Topic 内再细分过滤、事务消息绑本地业务、延迟消息原生就有。
  • 重试多次失败自动进死信队列，Kafka 原生没有。Kafka 事务只保一批消息同成败。

📈 拔高

RocketMQ 多读一次 ConsumeQueue 不亏：单条记录 20 字节，一个文件约 6MB，基本全在 PageCache，真贵的是两边都躲不掉的 CommitLog 消息体读取。Kafka 新部署现在只剩 KRaft 一条路，3.9 是最后一个带 ZK bridge 的版本。

💡 主动加分的追问准备

面试官追问 你的答案
RocketMQ 消费多读一次 IO，影响大吗？ ConsumeQueue 单条记录仅 20 字节（offset、size、tag hashcode），一个文件约 6MB，热点基本在 PageCache 里。真耗时的是从 CommitLog 读消息体，这步两边都躲不掉，开销可忽略。
Kafka 用 KRaft 后还需要 ZK 吗？ 2.8 起可上 KRaft，3.3 后生产可用，4.0 起彻底移除 ZK。老集群迁移有成本，新部署只有 KRaft 一条路。

❌ 千万别说的话

  • “RocketMQ 和 Kafka 存储一样，都是每个分区一个文件” ：不一样。Kafka 每 Partition 独立 Segment 文件，Topic 多了页缓存被摊薄，写不如 RocketMQ 集中；RocketMQ 所有 Topic 写同一个 CommitLog，靠 ConsumeQueue 做索引。
  • “Kafka 也支持事务消息和延迟消息” ：Kafka 事务只能保一批同成败，且原生不支持延迟消息；这两项是 RocketMQ 在功能上做加法的典型体现。

24. RabbitMQ 中无法路由的消息会去到哪里？

🎬 面试现场

面试官（口语化）：消息发到交换机上，结果没找到匹配的队列，这种没法路由的消息最后去哪了？

⚠️ 翻车点

默认答案”直接丢”只对一半。RabbitMQ 默认确实会静默丢弃无法路由的消息，连提示都没有，生产环境这么搞消息就悄悄没了。很多人把死信队列和”无法路由”混为一谈——其实死信队列管的是消息进队列之后被拒绝、过期、溢出的事，跟”在交换机层面就路由不掉”是两个阶段，别张冠李戴。

📝 回答重点

  • 默认行为是消息在交换机上找不到匹配队列就直接丢弃，mandatory 默认 false，连个通知都没有。
  • 生产环境我一般配备份交换机：声明主交换机时加 alternate-exchange 参数，转发不过去的自动送到它，再绑个 fanout 兜底队列。
  • 没配备份交换机才轮到消息回退：mandatory=true 时消息走 Basic.Return 退回生产者，Return Listener 自己决定重发还是报警。
  • 死信队列管的是消息进队列之后被拒绝、过期、溢出，跟交换机层路由不掉是两码事，别混。

📈 拔高

配了备份交换机，消息经它转发就算已路由，mandatory 不会再退回，Return Listener 也不会触发。备份交换机自己也匹配不上时消息同样被丢弃，所以它最好绑 fanout 加一个始终收得到的兜底队列。

💡 主动加分的追问准备

面试官追问 你的答案
备份交换机和 Return Listener 都配了，消息走哪个？ 备份交换机优先。配了它，无法路由的消息直接转发过去，不会触发 Return Listener。AE 链走尽后消息被丢弃，只有没配备份交换机才退回生产者。
死信队列和备份交换机会冲突吗？ 不会，作用在不同阶段。备份交换机处理交换机层面无法路由，消息压根没进队列。死信处理进队列后被拒绝/过期/溢出，一条消息不可能同时触发两者。

❌ 千万别说的话

  • “无法路由的消息会进死信队列” ：死信管的是进队列后被拒绝/过期/溢出，无法路由发生在交换机层面消息压根没进队列，两者阶段不同，死信只能算兜底补充。

25. RabbitMQ 中消息什么时候会进入死信交换机？

🎬 面试现场

面试官（口语化）：说说什么情况下，一条消息会从小队列被扔到死信交换机去？

⚠️ 翻车点

三种条件要记全，最容易漏掉”队列满了挤掉老消息”这条。还有个经典坑：单条消息设 TTL 时，RabbitMQ 只检查队头消息是否过期。队头是 1 小时、后面有 1 分钟的消息，这条 1 分钟的也得等前面的处理完才进死信，队列级 TTL 没这问题。另外 reject 时 requeue 必须设 false 才进死信，设 true 只是重新入队。

📝 回答重点

  • 经典队列三种情况进死信：消费者拒绝、消息过期、队列溢出，最容易漏的是溢出这条。
  • 拒绝要配 requeue=false，设成 true 只是重新入队，消息根本到不了死信。
  • 过期看 TTL：消息或队列设了 TTL，到点没被消费就变死信转走。
  • 溢出是队头背锅：队列设 x-max-length 或 x-max-length-bytes，超容量时最老的队头被挤进死信。
  • 配置就两句：声明队列时加 x-dead-letter-exchange 和 x-dead-letter-routing-key，header 还会带 x-death 标死信原因。

📈 拔高

Quorum 队列还有第四种：消费被反复拒绝超过 delivery-limit，消息直接转死信，经典队列没这条。单条 TTL 只查队头，1 小时的队头会挡着后面 1 分钟的消息，做延迟队列得用队列级 TTL 或上延迟插件。

💡 主动加分的追问准备

面试官追问 你的答案
用死信队列做延迟队列有什么坑？ 靠 TTL 过期，消息必须按顺序过期，后进的短 TTL 也得等前面处理完。延迟插件按到期时间调度，不依赖队头顺序，精确投递没这问题，但要额外装。
死信队列的消费者挂了，消息会丢吗？ 不会丢，死信队列也是普通队列，消息持久化断电重启还在，只是会积压，积压太多可能撑爆磁盘，一般配监控告警人工介入。

❌ 千万别说的话

  • “死信队列的死信交换机指回原队列就行” ：会无限循环耗尽资源。正确做法是死信队列要么不设死信交换机，要么指向专门的终极死信队列兜底。

26. 说一下 AMQP 协议？

🎬 面试现场

面试官（口语化）：你一直在用 RabbitMQ，那 AMQP 协议到底是个啥，底层模型怎么设计的？

⚠️ 翻车点

核心模型五个名词别漏：Connection、Channel、Exchange、Queue、Binding。最容易答偏的是 Channel 存在的意义——它是为了复用一条 TCP 连接省成本，一个应用几十个线程各开 Connection 太浪费。还有版本坑：面试默认说 AMQP 0-9-1（RabbitMQ 用的），和 1.0 不兼容，1.0 协议层不定义 exchange 和 binding、改地址寻址，RabbitMQ 仍把地址解析成 exchange 加 routing key 的 0-9-1 模型。

📝 回答重点

  • AMQP 是应用层消息协议，管消息怎么发、怎么路由、怎么存，RabbitMQ 和 Qpid 直接实现它，ActiveMQ 走插件支持 AMQP 协议族。
  • Connection 是一条 TCP 长连接，Channel 是它上面的轻量逻辑连接，几十个线程各开连接太浪费，一个线程配一个 Channel 才隔离。
  • Exchange 收消息按规则分发，Queue 才是真正存消息的地方，Binding 把两者连起来，带上 routing key 决定送哪。
  • 四种交换机：Direct 精确匹配 key，Fanout 广播给绑定的队列，Topic 用 * 配一词 # 配多词，Headers 按消息头，平时最少用。
  • 版本认准 AMQP 0-9-1，RabbitMQ 用的就是这版。1.0 协议层不定义 exchange 和 binding，改成地址寻址，RabbitMQ 自己仍把地址解析回 exchange 加 routing key。

📈 拔高

信封层面 AMQP 只规定帧格式和方法名，五件套属于上层模型。性能分水岭在 Channel 复用和 Publisher Confirm，事务一开吞吐掉一个量级。

💡 主动加分的追问准备

面试官追问 你的答案
ack 和 nack 有啥区别？ ack 消费成功可删消息。nack 消费失败，带 requeue 决定重入队还是进死信，reject 只能拒单条，nack 可批量，实际多用 nack。
Channel 和 Connection 啥关系，为何不直接用 Connection？ Connection 是 TCP 长连接，三次握手加 TLS 成本高。Channel 是其上轻量虚拟连接，几十线程各开 Connection 太浪费，开 Channel 复用即可，且线程间隔离，官方建议一线程一 Channel。

❌ 千万别说的话

  • “AMQP 事务和 Confirm 选事务” ：事务同步阻塞，吞吐量掉到 1/10 以下，生产环境优先用 Publisher Confirm 异步确认替代。

27. RabbitMQ 中主要有哪几个角色或者说概念？

🎬 面试现场

面试官（口语化）：你先说说 RabbitMQ 里都有哪几个角色，消息从生产到消费都经过了谁？

⚠️ 翻车点

最容易答成「生产者发消息、消费者收消息、中间一个队列」就完了——只说出三个最基本的，把交换机、绑定、路由键、VHost 全漏了。RabbitMQ 的核心在于生产者不直接把消息丢进队列，而是先给交换机，由交换机按绑定规则路由到队列，这套链路才算完整。

📝 回答重点

  • 生产者把消息连同路由键交给交换机，不直接塞队列，这是最容易讲漏的一步。
  • 交换机按类型和绑定规则分流，Direct、Fanout、Topic、Headers 四种，各管一套匹配逻辑。
  • 绑定把交换机和队列连起来，路由键决定消息走哪条路，两个一起才是完整路由。
  • 队列是真正存消息的地方，消费者从这里取，取走之前消息都归它管。
  • VHost 是虚拟主机，一套独立的交换机、队列和权限，多环境靠它隔离。

📈 拔高

角色只是名词，消息真跑起来靠生产者到交换机再到队列这条链，链落在哪套 VHost 决定隔离边界。排查跨环境问题先确认连的是哪个 VHost，再顺链路往下看。

💡 主动加分的追问准备

面试官追问 你的答案
消费者处理太慢队列堆满了怎么办？ 短期加消费者实例，RabbitMQ 支持多个消费者竞争消费同一队列。长期分析慢的原因，再开 prefetch 限制每个消费者手里未确认消息数，别让一个慢消费者拖垮整队列。
队列有长度限制吗，堆太多会怎样？ 队列本身没硬限制，但可用 x-max-length 设最大消息数、x-max-length-bytes 设总字节数。不限的话堆太多撑爆内存会触发流控，把生产者阻塞。

❌ 千万别说的话

  • “RabbitMQ 就是生产者和消费者中间放个队列” ：漏了交换机、绑定和路由键，消息根本进不了队列，这不是完整的 RabbitMQ 模型。

28. RabbitMQ 的 routing key 和 binding key 的最大长度是多少字节？

🎬 面试现场

面试官（口语化）：routing key 和 binding key 最长能写多少字节？这个限制是哪来的？

⚠️ 翻车点

别张嘴就说「255 字符」——是字节不是字符。key 里用了中文，一个 UTF-8 汉字占 3 字节，照样会超限被 broker 拒绝。还有人不知道这两个 key 都是 AMQP 0-9-1 里的 short string 类型，上限是协议帧里 1 个长度字节定死的 255。

📝 回答重点

  • 两个 key 上限都是 255 字节，AMQP 0-9-1 把它定成 shortstr，1 字节长度加 255 字节载荷，超了 broker 抛 channel 异常。
  • routing key 是发消息时带的，binding key 是建绑定时定的，一个告诉交换机往哪走，一个定义怎么匹配进队列。
  • 匹配看交换机类型：Direct 要求一字不差，Topic 才吃通配符，Headers 改看消息头键值对。
  • 命名按 {业务域}.{模块}.{事件} 来，比如 order.payment.success，几十字符就够，中文一个汉字 3 字节最容易踩线。

📈 拔高

真要塞长路由信息，别指望 Headers 交换机绕开限制，它的键也是 shortstr，同样 255 字节封顶。只有键对应的值能更长，详情还是放消息体。

💡 主动加分的追问准备

面试官追问 你的答案
消息发出去了消费者却收不到怎么排查？ 先确认交换机、队列、绑定建好没，再看 routing key 和 binding key 是否匹配，Topic 通配符易写错。队列消息数为 0 说明路由环节就出了问题。
真需要超过 255 字节的路由信息怎么办？ routing key 塞太多信息就是设计问题，超长部分放消息体，key 只留核心标识。想在消息头放路由就用 Headers 交换机，注意它的键同样是 shortstr、255 字节封顶，只有值能更长。

❌ 千万别说的话

  • “上限是 255 字符，中文随便写” ：是字节不是字符，中文 UTF-8 一字 3 字节，很容易超限被拒；命名建议只用英文、数字、点号和下划线。

29. 说说 RabbitMQ 的工作模式？

🎬 面试现场

面试官（口语化）：RabbitMQ 有哪几种工作模式？分别适用什么场景？

⚠️ 翻车点

别只背「5 种模式」——官方文档列的是 7 种。最容易漏的是 RPC 和发布确认（Publisher Confirms）。还有人把发布确认当成独立业务模式，其实它严格说是生产者端的可靠性保障机制，不是和前几种并列的「消息流转模式」。

📝 回答重点

  • 官方教程列下来是 7 种，最容易漏 RPC 和发布确认，张嘴就说 5 种会露怯。
  • 最基础是简单模式，一个生产者对一个队列一个消费者。工作队列一个队列多消费者抢活，设 prefetch=1 才能能者多劳。
  • 发布订阅发到 Fanout 全量广播，路由模式发到 Direct 按 key 精确分流，主题模式发到 Topic 走通配。
  • RPC 用 correlation_id 和 reply_to 串起请求和响应，跨语言或复用已有服务时用它。
  • 发布确认是生产者端的可靠性机制，broker 异步回告成败，可靠性要求高的场景必开。

📈 拔高

prefetch=1 只是最保守的起点，压测后按消费速度提上去，照抄会把吞吐压死。发布确认属于可靠性机制，和事务、mandatory 是一类问题，数模式时别把它和流转模式并列。

💡 主动加分的追问准备

面试官追问 你的答案
Work Queue 消费者处理一半挂了消息会丢吗？ 看 ack：自动 ack 推走就删会丢。手动 ack 时连接断开 RabbitMQ 会把消息放回队列分给其他消费者，业务侧做好幂等就行。
Fanout 和 Topic 都能广播，什么时候用哪个？ 所有消费者都要全量用 Fanout 更简高效。不同消费者收不同类型消息用 Topic 靠通配符选择性订阅更灵活。

❌ 千万别说的话

  • “RabbitMQ 就 5 种模式” ：官方是 7 种，漏了 RPC 和发布确认；后者是可靠性机制不是独立流转模式，别和前面并列讲成一类。

30. 说说 RabbitMQ 的集群模式？

🎬 面试现场

面试官（口语化）：聊聊 RabbitMQ 的集群，你都知道哪几种模式？各自有啥坑？

⚠️ 翻车点

最容易把三种模式混着讲，尤其分不清标准集群和镜像集群的数据到底复不复制。标准集群消息只在单节点、不自动复制，节点挂了那上面的消息就没法消费；只有镜像/仲裁队列才保高可用。还有人觉得三种都得配——其实标准集群最常用，镜像队列已经在 RabbitMQ 4.0 里移除（3.9 起就标了弃用），新项目应该直接上仲裁队列（Quorum Queue）。

📝 回答重点

  • 集群三种玩法：标准集群、镜像集群、联邦集群，高可用再配仲裁队列。
  • 标准集群全节点共享元数据，消息只存单节点不复制，连任意节点能做负载均衡，节点挂了上面的消息就没法消费。
  • 镜像集群给队列配 master 加 mirror，消息同步到全部镜像，master 挂了自动提升，3.x 及以前用 set_policy 按前缀配，别全量镜像拖性能。
  • 联邦集群靠 federation 插件做跨地域多活，把下游集群配成 upstream，消息自动同步过去。
  • 高可用直接上仲裁队列，3.8 引入、底层 Raft，不脑裂不丢消息，镜像队列 4.0 已移除。

📈 拔高

仲裁队列把每条消息都按持久化处理，队列本身也不允许非持久，拿它存临时消息纯浪费磁盘 IO。Raft 的故障恢复没有官方秒级承诺，报数字反而露怯。

💡 主动加分的追问准备

面试官追问 你的答案
集群节点之间怎么发现对方？ 靠 Erlang Cookie，所有节点 .erlang.cookie 文件内容必须一致，不一致握手直接失败，部署常见坑就是忘了同步。
镜像队列和仲裁队列生产环境怎么选？ 直接选仲裁队列，镜像队列 4.0 已移除。仲裁队列用 Raft 保证一致性，所有消息一律按持久化处理，队列也不允许非持久，要放允许丢失的临时消息才退回标准队列。

❌ 千万别说的话

  • “RabbitMQ 集群所有消息会自动复制” ：只有镜像/仲裁队列才同步，标准集群消息只存单节点，节点挂了上面的消息就丢了。

31. RabbitMQ 怎么实现延迟队列？

🎬 面试现场

面试官（口语化）：RabbitMQ 怎么搞延迟队列？你说两个方案，再讲讲里面的坑。

⚠️ 翻车点

最经典也最坑的是 TTL + DLX 的时序问题：队列先进先出，队头消息没过期，后面的全卡着——你先后发 10 秒、5 秒、2 秒三条，2 秒那条也得等 10 秒那条先出去，这坑只在 per-message TTL 上出。另一个坑是把延迟插件当现役方案：它已停止维护，依赖的 Mnesia 在 4.3 被移除，堆到十万级以上官方明说不合适。

📝 回答重点

  • 先分版本：3.x、4.0 没有原生延迟，4.4 起 quorum 队列原生支持，发消息带 x-opt-delivery-time 指定未来投递时间。
  • 老方案 TTL + DLX：队列不配消费者，消息待到 TTL 过期自动转到死信交换器，消费者从死信队列取消息。
  • DLX 触发官方认四类：被拒、消息过期、队列超长、quorum 投递超限，整队列过期的消息不进 DLX。
  • 延迟插件 rabbitmq_delayed_message_exchange 已停维护，它靠 Mnesia 存消息，单磁盘副本节点一丢消息就丢，官方说十万级以上规模不合适。
  • 插件用法记一下：x-delayed-message 交换器声明时带 x-delayed-type，发消息带 x-delay，到期才投递，不走队列排队所以没时序问题。

📈 拔高

4.3 起 quorum 队列自带 delayed retry，重试退避不用自己拿 DLX 搭。延迟插件停维护后没有后继插件，新项目要延迟投递直接上 4.4 的 x-opt-delivery-time。

💡 主动加分的追问准备

面试官追问 你的答案
TTL + DLX 里死信队列量大了会成瓶颈吗？ 会，它本质还是普通队列。可按业务分多个死信队列、消费者开多 channel 并行，新项目直接换 quorum 队列原生延迟。
还有哪些 MQ 原生支持延迟消息？ RocketMQ 从 4.x 起支持（早期仅 18 个固定延迟级别，5.0 后支持任意时间），Pulsar 也原生支持，Kafka 原生不支持需外部调度器配合。

❌ 千万别说的话

  • “TTL + DLX 会按延迟时间先后消费” ：队列 FIFO，短延迟消息被长延迟的队头卡住，必须按延迟档分队列或上延迟插件才能解决。
