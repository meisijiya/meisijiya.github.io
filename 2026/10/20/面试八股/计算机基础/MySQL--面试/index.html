为什么 MySQL 值得单独背

后端面试里，MySQL 是唯一一块「原理层和数据层都能聊」的科目。

Redis 你可以只背数据结构，JVM 你可以只背 GC 参数，但 MySQL 不行——面试官问「为什么用 B+ 树不用红黑树」，你答不出树的高度计算方式，前面讲的隔离级别全白讲；他问「MVCC 是怎么实现的」，你说不清 ReadView 的四个字段，那句「MySQL 默认 RR」就是背来的。

更关键的是 MySQL 的追问链特别长。你说「走索引了」，他立刻接「Using index 和 Using index condition 有什么区别」；你说「加索引就快了」，他立刻接「什么情况下索引反而更慢」。能不能接住第二问，才是区分背过和理解的分水岭。

所以这篇不给你第四十份知识点罗列，而是把 69 道高频题还原成真实的面试现场：每道题都是「面试官怎么问 → 你第一反应会怎么翻车 → 正确答法 → 追问怎么接」。

怎么用这篇：不要背「要点」，要背「现场反应」。左边那栏是面试官的问题，右边是你脑子里应该立刻蹦出来的东西。考前一小时扫「⚠️ 翻车点」那一行，性价比最高。

一、索引与存储引擎：为什么是 B+ 树，以及索引到底怎么用

1. MySQL InnoDB 引擎中的聚簇索引和非聚簇索引有什么区别？

🎬 面试现场

面试官（口语化）：InnoDB 的聚簇索引和二级索引到底差在哪儿？为什么二级索引查数据还要回表？

⚠️ 翻车点

把「非聚簇索引」说成「MyISAM 那种存物理地址的索引」就错了。InnoDB 的二级索引叶子节点存的是索引列的值 + 主键值，存物理地址的是 MyISAM。答错这一点，后面的回表代价、主键为何有序全都接不上。

📝 回答重点

  • InnoDB 的数据都挂在聚簇索引上，叶子节点直接存完整数据行，一张表只有一个聚簇索引，默认就是主键。
  • 二级索引叶子存索引列和主键值，拿完整行要再回表一次，存物理地址的是 MyISAM。
  • 两边都是 B+ 树：非叶子节点存主键和页号，叶子之间有双向链表做范围查询，页内还有页目录，先二分到组再顺着链表走。
  • B+ 树定位到的是页，不是具体记录，页大小默认 16KB。
  • 主键要有序：无序插入往页中间塞，页满了触发页分裂，写入明显变慢，所以我一般推荐自增主键。
  • 回表贵在两棵独立的 B+ 树要各走一遍，数据量大就是大量随机 I/O，这也是不推荐 select * 的原因。

📈 拔高

自增主键让新行永远追加在最后一页，页几乎不用分裂，UUID 随机插入则把写入放大成一堆随机 I/O。回表次数能不能压下来，本质看二级索引的覆盖度设计，高频查询的列组合值得单独建联合索引。

💡 主动加分的追问准备

面试官追问 你的答案
一张表没有主键时 InnoDB 怎么建聚簇索引？ 会挑第一个所有键列都是 NOT NULL 的唯一索引当聚簇索引。没有就自动生成 6 字节隐藏列 row_id（GEN_CLUST_INDEX），它业务不可见、查询也用不上，所以建表最好显式指定主键。
为什么二级索引存主键而不是物理地址？ 聚簇索引的数据物理位置会变，页分裂、页合并、数据更新都会挪位置，存地址就要在每次挪动时更新所有二级索引，成本太高。主键值稳定，数据怎么挪都不影响二级索引。
什么时候二级索引查询不用回表？ 当查询的列都在索引里时就是覆盖索引。比如索引 (name, age) 查 select name, age from t where name = 'xx'，叶子节点已有 name、age、主键，EXPLAIN 的 Extra 会显示 Using index。

❌ 千万别说的话

  • “InnoDB 的非聚簇索引叶子节点存的是数据行的物理地址。” ：那是 MyISAM，InnoDB 存的是主键值。
  • “聚簇索引一张表可以有多个。” ：一张表只有一个聚簇索引。
  • “用 UUID 做主键没关系，反正都是唯一的。” ：无序主键频繁触发页分裂，写入性能显著变慢。

2. MySQL 索引的最左前缀匹配原则是什么？

🎬 面试现场

面试官（口语化）：联合索引的最左前缀匹配到底是怎么回事？范围查询一出现后面的列是不是就废了？

⚠️ 翻车点

把「>=、BETWEEN 这类还能接着往后匹配」说出口就错了。官方口径是等值条件才轮得到下一级键，>、<、>=、<=、!=、BETWEEN、LIKE 一出现，后面的列就不再参与区间构造。只记「> < 才停」，追问一句 where a >= 1 and b = 2 里 b 怎么用就露馅。

📝 回答重点

  • 最左前缀指联合索引按最左列排，最左列相同再按次左列排，所以查询条件得从最左列开始用。
  • 对 (a, b, c)：a = 1、a = 1 and b = 2、a = 1 and b = 2 and c = 3 都符合。只写 b = 2、c = 3、b = 2 and c = 3 就直接用不上。
  • 等值条件能一级一级用下去。一旦出现非等值条件，后面的列就不再参与区间构造，> < >= <= !=、BETWEEN、LIKE 全算，我一般记「等值过了才有下一级」。
  • where a >= 1 and b = 2 里 b 拿不到区间构造。where a = 1 and b = 2 and c > 3 能完整用上，因为等值把 a、b 钉死，c 那一段区间是连续的。
  • 用不上的列还有救：索引里存了它的值就能走索引下推，引擎层先滤掉再回表，a = 1 and c = 3 就是典型。
  • 8.0.13 有 Skip Scan，把最左列的值枚举成常量条件逐个查，type 变 range，Extra 显示 Using index for skip scan。限制也不少：单表、只引用索引列、无 GROUP BY 或 DISTINCT、条件是常量（含 IN()），最左列基数一大就退化成全扫（经验值）。

📈 拔高

range 访问和继续定位是两码事：a >= 1 依然给 a 框出一段连续区间，后面的列只是退出定位，还能在引擎层当过滤条件用。所以我看执行计划先量 key_len，等值前缀用了几段一眼就清楚。

💡 主动加分的追问准备

面试官追问 你的答案
联合索引 (a, b, c) 执行 where b = 1 and a = 2 能用上索引吗？ 能用上。MySQL 优化器会自动调整条件顺序，把 a = 2 放到前面，写成 where b = 1 and a = 2 和 where a = 2 and b = 1 效果一样，不用纠结条件书写顺序。
a >= 1 这种非等值条件为什么还能走 range？ range 要的是能框出一段连续区间，a >= 1 就给 a 框出来了，定位照常走。但 b 退出区间构造，官方例 key_part2 >= 10 之后 key_part3 就不再参与，b 只能靠索引下推过滤。
建联合索引时列的顺序怎么定？ 高频查询条件放左边，区分度高的列放左边。范围查询的列放最右边，因为后面的列不再参与区间构造。有排序需求就把排序字段放进索引，避免 filesort。

❌ 千万别说的话

  • “只要 SQL 里出现了范围查询，后面的索引列就全用不上了。” ：后面的列不参与区间构造了，但索引里存了值还能走下推过滤。
  • “写 SQL 时必须严格按索引列的顺序写条件。” ：优化器会自动调整条件顺序。
  • “MySQL 8 的 Skip Scan 彻底打破了最左匹配原则。” ：它只是把最左列的值逐个枚举出来再查，官方限制也不少。

3. MySQL 的覆盖索引是什么？

🎬 面试现场

面试官（口语化）：覆盖索引是个什么概念？怎么判断一条 SQL 走没走覆盖索引？

⚠️ 翻车点

把 Using index 和 Using index condition 混为一谈。前者是覆盖索引（不需要回表），后者是索引下推（要回表但回表次数变少），两个不会同时出现，说成「都是不查表」就错得很彻底。

📝 回答重点

  • 覆盖索引就是查询列索引里全有，直接从二级索引拿数据，不用回表取完整行。
  • 好处三连：结果集大时省掉几万次回表，索引更紧凑内存命中率高，只把索引页加载进 Buffer Pool。
  • 判断看 EXPLAIN 的 Extra：Using index 是完全靠索引没回表，Using index condition 是索引下推，还要回表但次数变少。
  • 例：索引 (last_name, first_name, hire_date) 查 SELECT last_name, first_name, hire_date FROM employees WHERE last_name = '鸭' AND first_name = '面试' 正好覆盖，多取一个 department_id 就得回表。
  • 设计先照顾高频查询，select a, b from t where c = 1 就建 (c, a, b)。主键天然存在二级索引里，select 带主键不用额外塞。
  • 别贪多：列越多索引越大、写入维护越贵，select * 是天敌，写多读少的表别狂加覆盖索引。

📈 拔高

覆盖和下推别混着答：一个彻底不回表，一个必须回表但少回几次，Extra 也只会亮其中一个。真正要权衡的是值不值得为一条慢查询把列全塞进索引，写入变慢的账迟早要还。

💡 主动加分的追问准备

面试官追问 你的答案
覆盖索引和索引下推有什么区别？ 覆盖索引是完全不回表，索引里就有查询要的全部数据。索引下推是把过滤条件推到引擎层提前滤掉，最终还是要回表拿完整行。一个不回表，一个少回几次。
一个查询既用覆盖索引又用索引下推，可能吗？ 不可能。走了覆盖索引就不回表，索引下推没有用武之地。EXPLAIN 的 Extra 要么 Using index，要么 Using index condition，不会同时出现。
不改业务代码怎么让查询走覆盖索引？ 加联合索引。分析慢查询日志找出频繁执行的查询，把 where 条件列和 select 列组合成联合索引，比如 select a, b from t where c = 1 就加 (c, a, b) 或 (c, b, a)，只加索引对业务代码零侵入。

❌ 千万别说的话

  • “Using index 和 Using index condition 是一回事，都代表不用回表。” ：后者仍然要回表。
  • “覆盖索引就是把表所有列都加进索引。” ：索引列过多会显著增加写入维护成本，得不偿失。
  • “用了 select * 也可能是覆盖索引。” ：除非索引里包含表的全部列，否则必然回表。

4. MySQL 的索引下推是什么？

🎬 面试现场

面试官（口语化）：索引下推是干什么的？为什么 MySQL 5.6 要加这个优化？

⚠️ 翻车点

把下推说成「在 Server 层过滤」或「把条件推到索引上定位」都不对。下推是把不能用于索引查找、但索引里存了该列值的条件交给引擎层提前过滤，目的是减少回表次数，而不是减少 I/O 页数或提升定位能力。

📝 回答重点

  • 索引下推是 5.6 加的优化：把没法参与定位、但索引里存了值的条件下推到引擎层，回表前先滤一遍。
  • 没下推时引擎层只管定位，把主键丢回 Server 层，回表拿到完整行才用剩余条件过滤，回表次数就是这么高的。
  • 官方例子 (zipcode, lastname, firstname) 配 zipcode='95054' AND lastname LIKE '%etrunia%'，lastname 左模糊定位用不上，可索引里有它的值。
  • 没下推要回表上万次，有下推在引擎层先滤掉，只剩百来条回表，差距就是这么拉开的。
  • Extra 显示 Using index condition 就是走了下推，InnoDB 和 MyISAM 都支持，想对比性能可 SET optimizer_switch = 'index_condition_pushdown=off'。
  • 官方排除项要背准：存储函数、子查询、触发条件不走下推。覆盖索引和主键查询用不上，因为压根不回表。

📈 拔高

下推省的是回表次数不是页数，定位能力一点没变，别和覆盖索引混答。聚簇索引读取时完整行已经进了缓冲区，主键查询走下推省不了 I/O，官方排除它就是这个原因。

💡 主动加分的追问准备

面试官追问 你的答案
索引下推只能用在联合索引上吗，单列索引能用吗？ 理论上单列索引也能用，但意义不大。下推的价值在用索引里的额外列过滤，单列索引没有多余列可用。联合索引才能第一列定位、后面的列下推过滤。
索引下推和最左前缀匹配是什么关系？ 下推是对最左前缀的补充。联合索引 (a, b, c) 查 where a = 1 and c = 3，按最左匹配只能用 a 定位。c 退出了区间构造，但索引里存了 c 的值，引擎层直接过滤，回表次数大幅减少。
为什么主键查询不需要索引下推？ 因为主键索引叶子节点直接存完整数据行，查到就拿到全部数据，压根没有回表这个环节，而下推解决的就是「减少回表次数」。

❌ 千万别说的话

  • “索引下推能让条件在索引上直接定位，少读很多页。” ：下推不提升定位能力，只是少回表。
  • “覆盖索引和索引下推经常一起出现。” ：走了覆盖索引就没有回表，下推失去意义。
  • “任何条件都能下推。” ：官方排除存储函数、子查询和触发条件，实际用没用上看 EXPLAIN 的 Using index condition。

5. MySQL 中使用索引一定有效吗？如何排查索引效果？

🎬 面试现场

面试官（口语化）：建了索引就一定用得上吗？怎么排查一条 SQL 到底走没走索引？

⚠️ 翻车点

把 type=index 直接等同于「没走索引」就错了。type=index 是全索引扫描，扫的是整棵索引树，key 也可能是 PRIMARY，和 type=ALL 的全表扫描不是一回事。

📝 回答重点

  • 索引不一定有效：建了不代表用，用了不代表快。走不走全看优化器算账，表只有几百行时全表扫确实更便宜。
  • 排查先上 EXPLAIN，盯三个字段：type 看访问方式，key 看实际走的索引（NULL 就是没走），rows 看预估扫描行数。
  • 访问方式大致 const 最快，ref 等值定位，range 扫一段区间，index 全索引扫描，ALL 最慢的全表扫描。
  • 例：表 t1 查 where f3 = 11 用不上最左列，优化器改全扫 idx_f2_f3，key 就是它、type 是 index。换成 where f2 = 11 同一个索引，type 变 ref。
  • 失效根因两类：查找能力用不上（最左前缀不匹配、列上套函数运算、LIKE 左带通配符、OR 连非索引列、隐式类型转换），或优化器觉得不划算。
  • 生效还慢多半是选错索引：FORCE INDEX 强制指定跑一遍对比时间，ANALYZE TABLE 刷统计信息，8.0 还能 EXPLAIN ANALYZE 看实际和预估差多少。

📈 拔高

key_len 是看最左前缀用了几段的硬指标，等值一段占多少字节算得出来，比盯着 Extra 猜靠谱。统计信息是采样的，数据分布一偏优化器就会选错，所以线上慢查先怀疑它。

💡 主动加分的追问准备

面试官追问 你的答案
EXPLAIN 里 type 的 ref 和 range 有什么区别？ ref 是等值匹配，像 WHERE name = 'cong'，直接定位到一个值。range 是范围扫描，像 WHERE id > 100 AND id < 200，要沿叶子链表扫一段区间。等值定位更精准，ref 通常优于 range。
怎么知道优化器是不是选错了索引？ 用 FORCE INDEX 强制指定某个索引跑一遍对比时间，强制后反而快很多就说明选错了。再用 ANALYZE TABLE 刷统计信息，MySQL 8.0 用 EXPLAIN ANALYZE 看实际行数和预估行数差多少，差太大就是统计信息不准。
隐式类型转换为什么导致索引失效？ 索引树里存的是原始类型的值，转换相当于对索引列套了一层函数。varchar 字段存的是 ‘123’，转成数字 123 后没法直接在索引树上定位，只能逐行取出转换再比较，变成全表扫描。

❌ 千万别说的话

  • “EXPLAIN 里 type=index 就是没走索引。” ：它扫的是索引树，主键索引也算，仍算用上了索引。
  • “建了索引查询就一定会走索引。” ：优化器按成本选，表小或统计信息不准时可能直接全表扫。
  • “只要有索引，优化器就不会选错。” ：统计信息是采样的，数据分布不均时估算会明显偏离。

6. 请详细描述 MySQL 的 B+ 树中查询数据的全过程

🎬 面试现场

面试官（口语化）：从根节点到拿到一行数据，B+ 树里的查询到底经历了哪几步？

⚠️ 翻车点

只讲「从根节点往下找」是不够的，B+ 树只能定位到页。真正的第二阶段——16KB 叶子页内部靠页目录二分 + 组内单链表遍历定位到具体记录——才是这题的区分点，也是最容易漏答的部分。

📝 回答重点

  • 查询分两段：先从 根节点 定位到 叶子节点，再在页里定位到具体记录。
  • 树上查找拿查询键跟索引键比大小，二分定出区间，顺指针往下走到下一层。
  • 3 层树理论最多 3 次磁盘 I/O，页先查 Buffer Pool，命中就不用读磁盘。
  • 叶子页 16KB，记录按主键顺序排，页间用 双向链表 串着，范围查询顺着链表扫。

📈 拔高

页内这步我先讲清出处：官方手册只说记录按页组织，页目录那套细节来自源码分析。按源码的说法，页里建 页目录，每组最多 8 条记录，先在目录里二分找到组，再沿组内单链表遍历，最多看 8 条。三层存 2000 万是 1170×1170×16 的估算，行越宽存越少。

面试官追问 你的答案
为什么 B+ 树比 B 树更适合做数据库索引？ 两个核心原因：B+ 树非叶子节点不存数据、只存索引键和指针，一个页能放更多条目，树更矮、I/O 更少。B+ 树叶子节点之间有双向链表，范围查询顺着链表扫，而 B 树要做中序遍历整棵树，I/O 随机且慢。

  • “B+ 树查一次就能直接定位到那一行。” ：B+ 树只能定位到页，页内还得靠页目录二分加组内链表。
  • “B+ 树查询固定就是 3 次磁盘 I/O。” ：那是理论上限，Buffer Pool 命中时实际远少于 3 次。
  • “叶子节点里的记录是散乱存放的。” ：按主键顺序排列，组内用单向链表串联，页之间用双向链表串联。

7. 在什么情况下，不推荐为数据库建立索引？

🎬 面试现场

面试官（口语化）：索引是不是越多越好？哪些情况下建索引反而是负担？

⚠️ 翻车点

把「区分度低就不该建索引」说成绝对规则就翻车了。语料里明确给了例外：数据分布严重倾斜时（比如 status 有 90% 是「已完成」），针对那 10% 的高频查询建索引反而能过滤掉 90% 的数据，是有意义的。

  • 只答「索引多了写会变慢」同样不够，漏掉了空间占用和优化器负担这两条；更要命的是给不出量级——面试官想听的是「同一张表建 1 个索引和建 10 个索引，批量插 100 万条能差 3-5 倍」这种可对比的结论。
  • 回答「索引多了就删一删」却说不出怎么判断哪个该删，等于没答；删除前要确认它不是为唯一性约束建的。

📝 回答重点

  • 五类场景不建索引：小表、写多读少、区分度低、查询用不到、长文本字段。
  • 区分度看 Cardinality/总行数，小于 0.1 效果差，但 status 九成是已完成、常查那一成时照样值得建。
  • 索引 3 个加到 8 个，写入吞吐差约 40%，主键一改所有二级索引都得跟着动。
  • 长文本建 前缀索引 或哈希列，只存前缀值没法覆盖全列，复杂搜索上 FULLTEXT 或 ES。
  • 清理先看 sys.schema_unused_indexes，它统计自启动以来没用过的索引，跑得够久才有意义。

📈 拔高

返回数据占比大时，优化器按成本估算可能放弃索引走全表扫，官方没有固定百分比。Online DDL 加索引期间读写可并发，只有头尾短暂元数据锁，超大表仍放低峰期做。

8. MySQL 的查询优化器如何选择执行计划？

🎬 面试现场

面试官（口语化）：优化器凭什么判断该走索引还是全表扫描？它的成本是怎么算的？

⚠️ 翻车点

把成本模型简化成「看数据量比例」而不给 I/O 成本和 CPU 成本的具体口径，答不出 读一页记为 1、处理一行记为 0.2 这个量纲，就答不出「为什么全表扫描反而更便宜」。

📝 回答重点

  • 优化器按成本选方案：解析 SQL、预处理校验、生成多个执行计划挑最便宜的。
  • 成本就是 I/O 成本 加 CPU 成本，默认读一页记 1，处理一行记 0.2。
  • 算账靠 统计信息：行数、索引不同值个数、分布均匀度，走索引读 3-4 个页。
  • 100 万行的表查单条走主键成本约 4，全表扫要读几千页加遍历 100 万行。

📈 拔高

1 和 0.2 是默认常数，能通过 server_cost、engine_cost 表调整。多表 JOIN 时优化器枚举连接顺序，optimizer_search_depth 默认 62，超出就改贪心。EXPLAIN ANALYZE 能看真实执行行数，比只看估算准。

9. 为什么 MySQL 索引用的是 B+ 树而不是红黑树？

🎬 面试现场

面试官（口语化）：索引为什么选 B+ 树？红黑树不是也能存数据吗？

⚠️ 翻车点

只答「B+ 树矮、I/O 少」是不够的，漏掉「叶子节点双向链表做范围查询」和「非叶子节点不存数据所以扇出大」这两条加分点；更要命的是把 B 树和 B+ 树搞混——B 树的非叶子节点也存数据。

  • 说「哈希表比 B+ 树慢」同样是错的：哈希等值查询是 O(1)，比 B+ 树的 O(log n) 更快，它的问题是不支持范围查询和不支持排序；另外别把 InnoDB 里那个自动创建的自适应哈希索引忘了。
  • 只报「三层 B+ 树能存两千万条」这个结论不说推导过程，面试官要的是算法；推导的关键是「16KB 页 ÷ 14 字节 ≈ 1170 个索引项」这个换算。

📝 回答重点

  • 差距在 IO 次数：红黑树每层一次随机 IO，2000 万条要 24-25 层，B+ 树扇出上千，3 层搞定。
  • 磁盘随机 IO 一次约 10 毫秒，内存只要纳秒级，所以磁盘结构树高就是生死线，树越矮越好。
  • 16KB 页放 14 字节索引项约 1170 个扇出，三层 1170×1170×16 估算约 2000 万条，行越宽存越少。
  • 双向链表 让范围查询顺链表顺序扫，红黑树得中序遍历，磁盘上全是随机跳读。
  • 非叶子节点不存数据能塞更多 key，树矮 I/O 少，索引页缓存命中率也更高。
  • 哈希等值查询 O(1) 比 B+ 树还快，短板是不支持范围查询和排序，所以替代不了索引。

📈 拔高

红黑树没被彻底淘汰，Buffer Pool 的脏页列表、空闲列表这些内存结构就在用。InnoDB 还有个自适应哈希索引，盯上高频索引值自动建哈希加速点查。不用 B 树是因为它非叶子节点也存数据，扇出小且查询深度不稳定。

💡 主动加分的追问准备

面试官追问 你的答案
B+ 树的节点大小为什么是 16KB？能改吗？ 16KB 是 InnoDB 默认页大小，和系统页对齐，一次 IO 正好读整页。可改，innodb_page_size 支持 4KB-64KB，但只能初始化时设。页小树变高，页大刷脏开销大，一般保持默认。
红黑树插删比 B+ 树简单在哪？ 红黑树插删只做几次旋转和变色，最多碰 3-4 个节点。B+ 树插入可能分裂递归到根、删除可能合并递归到上层，节点在磁盘上，改一次就是一次 IO。
为什么说 B+ 树查询性能稳定？ 数据全在叶子，每个查询都走完根到叶的路径，树有几层就是几次 IO。B 树数据分布各层，运气好第二层查到、运气差到底层，响应时间没法预测。
三层 B+ 树能存多少数据，是怎么算的？ 主键 8 字节加指针 6 字节，非叶子节点存 16KB/14B≈1170 个 key。一行按 1KB 算，一个叶子存 16 条。三层 1170×1170×16，约 2000 多万条。行越小存越多。
为什么 MongoDB 早期用 B 树，后来换成 B+ 树了？ 早期以单文档查询为主，B 树非叶子节点带数据、命中即返看着更快。后来范围和排序需求变多，WiredTiger 换成了 B+ 树变种，叶子串起来后范围查询快得多。
自适应哈希索引是怎么工作的？什么时候该关掉它？ InnoDB 盯索引页访问，某值被反复查就自动建哈希，下次直接定位跳过树查找。高并发写时它的锁竞争会成瓶颈，监控到锁等待高就可以关掉。
为什么 InnoDB 要求主键尽量短？ 主键越短非叶子节点塞的 key 越多，树越矮 IO 越少。二级索引叶子都冗余存主键，主键越长索引越占空间，int 换 36 字节 UUID 体积能翻几倍。
主键用 uuid 字符串代替 bigint，对存储量有什么影响？ uuid 36 字节，索引项从 14 涨到 42 字节，扇出 1170 降到 390，三层只剩 390×390×16≈240 万条，少一个数量级，树还可能变四层。
二级索引的三层 B+ 树能存多少数据？ 二级索引叶子存主键值。主键索引列都按 8 字节算，叶子一条 16 字节能放约 1000 条，三层 1170×1170×1000≈13.5 亿条，但查数据要回表。
表数据量超过 2000 万就要分库分表吗？ 不一定，2000 万只是参考值。索引设计得好几千万单表也没问题。要分的信号是慢查询变多、写入 QPS 顶不住、磁盘告警，能不分就不分。

  • “红黑树和 B+ 树性能差不多，只是实现风格不同。” ：磁盘场景下 IO 次数差一个数量级。
  • “B 树和 B+ 树是一回事，只是叫法不同。” ：B 树非叶子节点也存数据。
  • “MySQL 里凡是排序结构都用 B+ 树，红黑树完全用不到。” ：Buffer Pool 的脏页列表、空闲列表等内存结构就会用到红黑树。
  • “B+ 树比哈希表查询快。” ：哈希等值查询是 O(1)，比 B+ 树还快；B+ 树赢在范围查询和排序。

10. MySQL 的存储引擎有哪些？它们之间有什么区别？

🎬 面试现场

面试官（口语化）：MySQL 的存储引擎你能列几个吗？最常用的 InnoDB 和老牌的 MyISAM 到底差在哪、差在什么原理上？

⚠️ 翻车点

  • 只背引擎清单不答「区别」，面试官要的是 InnoDB 与 MyISAM 的差异原理：存储结构、锁机制、事务开销。
  • 说 InnoDB 的行锁是「锁住物理行」，准确说法是锁索引记录；更严重的是不知道查询没走索引时行锁会退化为锁住全部扫描记录。
  • 把 MyISAM 的读性能好归因为「B+ 树更快」，真实原因是它没有事务开销、不用维护 undo log、不用做 MVCC 版本链查找。
  • 认为 MEMORY 引擎可以替代 Redis，前者只能通过 SQL 访问且重启即丢，后者是独立服务且有持久化。

📝 回答重点

  • 95% 场景用 InnoDB：支持事务、行锁、MVCC、外键，数据按聚簇索引组织，主键查询快。
  • MyISAM 不支持事务只有表锁，索引 .MYI 数据 .MYD 分开存，读快但并发写差。
  • MEMORY 全在内存、重启即丢，做临时表。Archive 只支持 INSERT/SELECT，压缩率高。
  • 差别的根子是设计目标：MyISAM 为读多写少的静态页，InnoDB 为事务 ACID 而生。
  • InnoDB 行锁锁的是索引记录，查询没走索引时行锁退化为锁住全部扫描记录。
  • 引擎清单以 SHOW ENGINES 输出为准，选型基本无脑 InnoDB，5.5 起它就是默认。

📈 拔高

版本线索：5.5 InnoDB 成默认，5.6 补全文索引，8.0 系统表全迁 InnoDB，MyISAM 只留兼容。MyISAM 读快是因为没事务开销、不维护 undo log 也不做 MVCC 版本链查找。

💡 主动加分的追问准备

面试官追问 你的答案
InnoDB 的行锁是怎么实现的？是锁住整行数据吗？ 行锁锁的是索引记录。走主键就锁主键索引那条，走二级索引先锁二级记录再锁对应主键记录。没走索引时行锁退化为锁住全部扫描记录，等同表锁，所以建索引也是在收窄锁粒度。
MyISAM 既然只有表锁，为什么还说它读性能好？ 没有事务开销，不用维护 undo log，也不做 MVCC 版本链查找，直接顺序读。但这优势只在无并发写时成立，一有写操作，表锁会把所有读都挡住。
MEMORY 引擎数据放内存里，和 Redis 比有什么区别？ MEMORY 是 MySQL 进程内存储，只能 SQL 访问、重启即丢。Redis 是独立 KV 服务，数据结构多、有持久化、跨进程。临时表计算用 MEMORY，分布式缓存和会话用 Redis。
生产环境怎么查看当前表用的是什么存储引擎？ SHOW TABLE STATUS LIKE '表名' 的 Engine 列直接可见，SHOW CREATE TABLE 末尾也有 ENGINE 参数。批量查用 information_schema.TABLES 的 ENGINE 列。

  • “InnoDB 的行锁是锁住一整行物理数据。” ：行锁锁的是索引记录，没走索引会锁住全部扫描记录。
  • “MyISAM 读性能好是因为它的 B+ 树索引更高效。” ：真正原因是没有事务开销、不用维护 undo log、不用做 MVCC 版本链查找。
  • “MEMORY 引擎比 Redis 快，可以拿来替代 Redis 做分布式缓存。” ：它在 MySQL 进程内、只能 SQL 访问、重启即丢，做不了分布式缓存。
  • “MyISAM 现在还是很好的选择，只是有点过时。” ：MySQL 8.0 已经把系统表迁到 InnoDB，官方只把它留作兼容用途。

11. MySQL 的索引类型有哪些？

🎬 面试现场

面试官（口语化）：MySQL 的索引类型你给我捋一遍呗，别光说 B+ 树，我从哪几个维度分类、每种索引分别用在什么场景？

⚠️ 翻车点

  • 只答「B+ 树索引」一种，把「按数据结构分」这一个维度当成了全部，面试官问「按存储方式怎么分」「按索引性质怎么分」就答不上来。
  • 把聚簇索引和主键索引当成两个并列概念说，实际上在 InnoDB 里主键索引就是聚簇索引。
  • 说唯一索引「不允许有 NULL」或者「完全不能有 NULL」，实际是允许多个 NULL。
  • 把哈希索引说成 MySQL 默认索引，或者不知道 InnoDB 里有个自适应哈希索引是自动建的。

📝 回答重点

  • 先按三个维度拆：数据结构、存储方式、索引性质，别只盯着 B+ 树一种。
  • 数据结构四种：B+ 树当主力，哈希只做等值，全文索引走倒排，空间索引走 R 树。
  • 存储方式两种：聚簇索引叶子存整行、一张表只能有一个；二级索引只存索引列加主键，查别的列要回表。
  • 性质上常见六种：主键、唯一、普通、联合、全文、空间。
  • 联合索引按列顺序排，用不到最左那列就整条用不上。

📈 拔高

InnoDB 的自适应哈希索引是自动建的，不用手管；三层 B+ 树大概能放两千万行，查一行最多三次磁盘 IO。

💡 主动加分的追问准备

面试官追问 你的答案
InnoDB 里如果没显式定义主键，聚簇索引怎么建？ InnoDB 会找第一个非空的唯一索引当聚簇索引；如果连唯一索引都没有，就自己生成一个 6 字节的隐藏列 row_id 作为聚簇索引的键，这个 row_id 是全局递增的而不是表级别的。所以建表时最好显式指定主键，否则隐藏主键既浪费空间，排查问题时也看不到。
哈希索引既然等值查询这么快，为什么不是默认索引？ 三个原因：第一不支持范围查询，WHERE id > 100 没法用；第二不支持排序，ORDER BY 用不上；第三哈希冲突多的时候性能会退化。数据库查询大量场景是范围查询、排序、分页，哈希索引应付不了，B+ 树更适合当默认。
联合索引 (a, b) 和分别建 a、b 两个单列索引有什么区别？ 联合索引是一棵 B+ 树，先按 a 排序再按 b 排序，WHERE a = 1 AND b = 2 一次索引扫描就搞定；分别建两个单列索引是两棵树，MySQL 可能会用索引合并，但效率不如联合索引。联合索引还能做覆盖索引，比如 SELECT b FROM t WHERE a = 1 不用回表。代价是占用空间更大、更新维护成本更高。
全文索引和 LIKE '%keyword%' 有什么区别？ LIKE '%keyword%' 是前后模糊匹配，没法用 B+ 树索引，只能全表扫描。全文索引是分词后建倒排索引，能快速定位包含某个词的记录，还支持自然语言搜索、布尔模式搜索和按相关性排序。但全文索引对中文支持不好，需要配合 ngram 分词器；正经的全文搜索需求一般用 Elasticsearch 更靠谱。

❌ 千万别说的话

  • “MySQL 的索引类型就是 B+ 树索引和哈希索引两种。” ：还有全文索引、空间索引，而且分类本身有三个维度。
  • “聚簇索引和主键索引是两种不同的索引。” ：InnoDB 里主键索引就是聚簇索引。
  • “唯一索引的字段不能是 NULL。” ：唯一索引允许 NULL，而且可以有多个 NULL。
  • “联合索引 (a, b, c) 上 WHERE a = 1 AND c = 3 能用上 a、b、c 三个字段。” ：跳过 b 之后 c 在 B+ 树里无序，只能用上 a。

12. MySQL 中的回表是什么？

🎬 面试现场

面试官（口语化）：回表这个词你解释一下？二级索引查完为什么还要再查一次表，那个代价到底有多大？

⚠️ 翻车点

  • 只说「回表就是再查一次」，不讲随机 I/O 这个真正的代价来源，面试官追问「性能影响在哪」就答浅了。
  • 把 Using index 说成「走了索引」，它表示的其实是覆盖索引、不用回表；判断有没有回表要看 Extra 里有没有这一项。
  • 说主键查询也要回表。主键索引就是聚簇索引，叶子节点直接存完整数据行，一次查找就拿到所有字段。
  • 把回表的代价说成「多一次查询」，本质问题是一次查询变成大量分散的随机 I/O。

📝 回答重点

  • 回表就是二级索引拿不到整行，得拿主键再查一次聚簇索引。
  • 代价不在多查一次，而在主键散落导致的随机 I/O，返回几万行时性能断崖。
  • 消除靠覆盖索引，EXPLAIN 的 Extra 显示 Using index 就是没回表。
  • 减少靠索引下推，引擎层先用索引里的列过滤，再拿剩下的主键回表。
  • 少写 select *，只查索引里的列也能把这层开销躲掉。

📈 拔高

优化器是算账的，估到回表行数占比太高时可能直接改走全表扫描，所以「建了索引没用上」多半是代价估算的结果，不是索引坏了。

💡 主动加分的追问准备

面试官追问 你的答案
一个查询走了索引但还是很慢，可能是什么原因？ 大概率是回表次数太多。比如查询返回几十万行，每行都要回表拿数据，产生大量随机 I/O。可以看 EXPLAIN 的 rows 估算值，如果很大说明回表代价高。解决办法是用覆盖索引减少回表，或者优化查询条件缩小结果集。
怎么判断一个查询有没有回表？ 看 EXPLAIN 的 Extra 列。如果显示 Using index，说明走了覆盖索引，没有回表。如果没有这个提示，或者显示 Using index condition，说明有回表。另外如果 type 是 index，表示全索引扫描，也可能有回表。
主键查询需要回表吗？ 不需要。主键索引就是聚簇索引，叶子节点直接存完整数据行，一次查找就能拿到所有数据。回表只发生在二级索引查询时。
覆盖索引和索引下推的区别是什么？ 覆盖索引是「压根不需要回表」，查询要的所有列索引里都有，Extra 显示 Using index；索引下推是「还是要回表，但回表次数变少了」，Extra 显示 Using index condition，是引擎层先按索引里的列过滤掉不匹配的记录，再回表。一个是不回表，一个是少回表。

❌ 千万别说的话

  • “回表就是多查一次表，性能影响不大。” ：真正的代价是大量随机 I/O，返回几万行时性能会急剧下降。
  • “EXPLAIN 里显示 Using index 说明走了索引。” ：它表示的是覆盖索引，本来就不需要回表。
  • “主键查询也要回表，因为要拿完整行数据。” ：主键索引就是聚簇索引，叶子节点直接存完整行，不用回表。
  • “只要建了索引就一定会用上。” ：返回行数超过表的 15%-30% 时，优化器可能主动放弃二级索引改走全表扫描。

13. MySQL 中 InnoDB 存储引擎与 MyISAM 存储引擎的区别是什么？

🎬 面试现场

面试官（口语化）：InnoDB 和 MyISAM 你给我说下最核心的区别，再讲讲为什么现在基本都换 InnoDB 了。

⚠️ 翻车点

  • 只答”一个支持事务一个不支持” —— 这只是最核心那一条，面试官接着会问索引结构、锁粒度、崩溃恢复，必须成体系地答。
  • 说 MyISAM 是”表级锁所以完全不能并发读” —— 它有读锁并发读锁、并发插入的特性，只是写并发是灾难。
  • 说 InnoDB 的索引和数据是分开的 —— 正好相反，InnoDB 的主键索引就是聚簇索引，数据和索引放在一起。
  • 说 MyISAM 崩溃后用 myisamchk 修复”不会丢数据” —— 修复过程可能丢数据。
  • 说 InnoDB 支持外键所以推荐用外键 —— 支持不等于该用，互联网项目一般靠业务代码保证约束，因为外键性能差。

📝 回答重点

  • 最核心一条：InnoDB 有事务和行级锁，MyISAM 两样都没有。
  • InnoDB 主键索引就是聚簇索引，数据跟索引放一起；MyISAM 索引和数据分开，叶子存物理地址。
  • InnoDB 靠 redo log 做崩溃恢复；MyISAM 崩了只能用 myisamchk 修，还可能再丢数据。
  • MyISAM 的表锁支持并发读，还有个并发插入特性，但写并发就是排队。
  • 5.5 起 InnoDB 是默认引擎，现在选型基本无脑它。

📈 拔高

InnoDB 的行锁加在索引上，UPDATE 没走索引会退化成扫全表加锁；MyISAM 的 concurrent_insert 只缓解写阻塞，改不了表锁本质。

💡 主动加分的追问准备

面试官追问 你的答案
InnoDB 为什么一定要有主键？没指定主键会怎样？ 因为 InnoDB 的数据组织方式就是聚簇索引，必须有主键来组织数据。如果没显式指定主键，InnoDB 会找第一个非空的唯一索引作为主键；如果连唯一索引都没有，会自动生成一个 6 字节的隐藏 row_id 作为主键，但 row_id 对用户不可见，查询时也用不上，所以建表时最好显式指定主键。
MyISAM 的表锁有没有办法优化并发性能？ 有个 concurrent_insert 参数。设成 1 时只要表中间没有空洞，INSERT 操作可以和 SELECT 并发执行；设成 2 时不管有没有空洞都允许并发插入，MySQL 会把新数据插到表末尾。不过这只是缓解，本质上表锁限制还在，高并发写入场景还是建议换 InnoDB。
InnoDB 的行锁是锁在哪里的？是锁记录本身吗？ 行锁实际上是锁在索引上的，不是锁数据行本身。走主键索引就锁主键索引上的记录，走辅助索引会先锁辅助索引上的记录，再锁对应的主键索引记录。所以一条 UPDATE 如果没走索引就会退化成表锁，因为它要扫全表，相当于锁了所有行。
现在还有什么场景会用 MyISAM 吗？ 现在生产环境基本见不到了。早年可能有些只读报表库会用，但现在 InnoDB 性能也很好，没必要为那点性能差异放弃事务和崩溃恢复能力。MySQL 8.0 之后连系统表都从 MyISAM 换成 InnoDB 了。面试时能说清两者区别就行，实际工作中无脑选 InnoDB。

❌ 千万别说的话

  • “MyISAM 也支持事务，只是用得少。” ：MyISAM 完全不支持事务。
  • “InnoDB 的数据和索引分开存储，辅助索引也存完整行。” ：InnoDB 主键索引是聚簇索引，数据和索引在一起；辅助索引才只存索引值和主键。
  • “MyISAM 表级锁意味着读也不能并发。” ：读锁之间可以并发，还有并发插入特性。
  • “MyISAM 崩溃后用 myisamchk 修复，数据不会丢。” ：修复过程本身可能丢数据。

14. MySQL 是如何实现事务的？

🎬 面试现场

面试官（口语化）：你给我讲讲 MySQL 的事务到底是怎么落地的？靠哪几个东西支撑的？

⚠️ 翻车点

只答「靠 redo log 和 undo log」会被立刻追打：一致性不是单独实现的组件，锁和 MVCC 才是隔离性的真正承载者，四个组件各对应 ACID 的不同侧面。

📝 回答重点

  • 四个组件分工：redo log 保持久性、undo log 保原子性、锁和 MVCC 保隔离性，一致性是它们合起来的结果。
  • redo log 走 WAL、循环写，innodb_flush_log_at_trx_commit 决定提交时刷不刷盘。
  • undo log 存修改前的旧值，回滚靠它反向恢复。
  • 行锁三种：记录锁、间隙锁、临键锁，可重复读默认用临键锁防幻读。
  • redo 和 binlog 靠两阶段提交对齐，恢复时按 XID 判断提交还是回滚。

📈 拔高

刷盘策略里 1 最安全、0 最多丢 1 秒、2 只防进程崩溃不防断电，这就是「双 1 配置」的由来；行锁加在索引上，没索引的更新会退化成全表加锁。

💡 主动加分的追问准备

面试官追问 你的答案
innodb_flush_log_at_trx_commit 设成 2 和 0 有什么区别？ 0 是每秒把 redo log 从 log buffer 刷到磁盘，MySQL 进程挂了就丢 1 秒数据；2 是每次提交写到 OS 的 page cache，MySQL 挂了数据还在 page cache，但机器断电就丢。2 比 0 安全一点，性能差不多。
MVCC 能解决幻读吗？ 能解决快照读的幻读，解决不了当前读的幻读。快照读走版本链，ReadView 定死可见范围；当前读（如 select … for update）读最新数据，要靠间隙锁防幻读。
undo log 什么时候会被清理？ 不是事务提交就能删，要等没有事务需要用到这些旧版本。purge 线程扫描活跃事务，找到最老的 ReadView，比它还老的 undo log 才能删除，所以长事务会导致 undo log 堆积。
为什么 redo log 循环写而 binlog 一直追加？ redo log 用于崩溃恢复，checkpoint 之前的日志对应数据页已刷盘，可以覆盖复用空间，否则磁盘会被撑爆；binlog 用于主从复制和数据恢复，历史记录不能丢。

❌ 千万别说的话

  • “MySQL 事务就是靠 redo log 和 undo log 实现的”（漏掉锁和 MVCC，一致性也不是独立实现的）
  • “MVCC 能彻底解决幻读”（当前读的幻读要靠间隙锁，不是 MVCC）

15. MySQL 中的 MVCC 是什么？

🎬 面试现场

面试官（口语化）：MVCC 到底是个什么机制？InnoDB 是怎么做到读写不互相阻塞的？

⚠️ 翻车点

把 MVCC 说成「存了好几份数据」是错的：InnoDB 数据页上只存最新版本，历史版本全在 undo log 里，靠 roll_pointer 串成版本链。

  • 只答「没有 MVCC 就锁更多、并发更低」也不够，要点破根源：没有历史版本时，读要么读到脏数据、要么读不到旧值，只能等写事务结束，这就是纯加锁的 LBCC 方案。
  • 以为二级索引里也存了 trx_id 和 roll_ptr 所以能直接判断版本 —— 二级索引条目只有索引列值和主键值，版本判断必须回表到聚簇索引。

📝 回答重点

  • 一句话：写不覆盖旧值而是造新版本，读按自己的 ReadView 在版本链上找。
  • 每行两个隐藏列：trx_id 记最后改它的事务，roll_pointer 指向上一版。
  • ReadView 四个字段：creator_trx_id、m_ids、min_trx_id、max_trx_id。
  • RC 每次 SELECT 重建 ReadView，RR 第一条建完用到事务结束，差别就在这。
  • 快照读走 MVCC 不加锁，当前读要读最新版本并加临键锁。
  • 二级索引不存版本信息，可见性判断必须回表到聚簇索引。

📈 拔高

二级索引页头有个 page_max_trx_id，整页记录对当前事务都可见时覆盖索引才成立；长事务会让它一直偏大，覆盖索引全失效、undo log 也清不掉。

💡 主动加分的追问准备

面试官追问 你的答案
MVCC 能不能解决写写冲突？ 不能。MVCC 解决的是读写冲突，让普通读不阻塞写、写不阻塞普通读；写写冲突靠锁，两个事务同时 UPDATE 同一行，后一个要等前一个提交或回滚。
为什么 ReadView 里要记 max_trx_id，只用 m_ids 不行吗？ 不行。m_ids 只记录生成 ReadView 那一刻的活跃事务，之后新启动的事务 ID 肯定更大，只用 m_ids 会把新事务的修改当成已提交看到。max_trx_id 就是用来挡住这些后来者的，trx_id >= max_trx_id 一律不可见。
只读事务 creator_trx_id 是 0，那自己改的数据怎么算可见？ 只读事务不会有修改操作，不存在这个场景；一旦有写操作，InnoDB 会分配真正的事务 ID，creator_trx_id 就不再是 0。
undo log 什么时候清理？ INSERT 产生的 undo log 提交后立刻可清；UPDATE 和 DELETE 产生的要等到没有事务需要该版本。后台 purge 线程根据活跃事务的 ReadView 判断哪些可安全删除，长事务会导致 undo log 堆积。
既然二级索引没有版本信息，RR 级别下二级索引怎么保证可重复读？ 靠的是聚簇索引的 MVCC。二级索引只负责定位主键，真正的版本判断在回表时做。RR 级别下事务启动会创建一个 ReadView，回表到聚簇索引后用 ReadView 和记录的 trx_id 判断能看到哪个版本，当前版本不可见就沿 undo log 版本链往前找，直到找到对当前事务可见的版本。
page_max_trx_id 存在哪儿？每条记录都有吗？ 它存在索引页的 Page Header 里，整个页只有一个，不是每条记录都有。它记录的是最后修改这个页的事务中最大的那个 trx_id。所以只要这个页上有任何一条记录被新事务改过，整个页的 page_max_trx_id 都会变大，可能导致这个页上其他没被修改的记录覆盖索引也一起失效、都得回表。
如果一个事务长期不提交，对二级索引查询有什么影响？ 影响很大。长事务不提交，它改过的二级索引页 page_max_trx_id 会一直很大，后续查这些页时覆盖索引全用不上、都得回表；同时 undo log 也清不掉，版本链越来越长，回表后的版本查找也越来越慢。所以生产环境要监控长事务，发现即处理。
长事务导致 undo log 膨胀，具体是什么原理？ InnoDB 用 MVCC 实现事务隔离，每次更新数据会把旧版本存到 undo log 里形成版本链。purge 线程会定期清理不再需要的旧版本，但前提是没有活跃事务需要读这些旧版本。长事务的 ReadView 一直不释放，它开始时刻之后产生的所有版本都不能清理，这些 undo log 就一直堆积，事务跑得越久堆积越多。
LBCC 就没有优点吗？ 实现简单是它最大的优点。MVCC 要维护版本链和 ReadView，逻辑复杂不少；并发不高的场景 LBCC 足够用，还好维护，早期不少嵌入式数据库就是纯 LBCC。
binlog、redo log、undo log 三个日志分别负责什么？为什么 redo log 循环写而 binlog 只能追加写？ binlog 是 Server 层逻辑日志，管主从复制和按时间点恢复，必须长期保留只能追加；redo log 是 InnoDB 物理日志，只管崩溃恢复，脏页刷盘后就没用所以循环覆盖；undo log 存旧值，管回滚和 MVCC 版本链。

❌ 千万别说的话

  • “MVCC 就是给数据存多个版本”（数据页只有最新版本，历史版本在 undo log）
  • “ReadView 的 max_trx_id 是当前最大已分配事务 ID”（是下一个将被分配的事务 ID）
  • “没有 MVCC 就是完全串行执行”（是读写互斥、锁粒度的问题，不是全局排队）

16. MySQL 中的事务隔离级别有哪些？

🎬 面试现场

面试官（口语化）：MySQL 有哪几个事务隔离级别？分别对应什么问题？默认是哪个？

⚠️ 翻车点

最容易错的是把 InnoDB 的可重复读说成「彻底消除了幻读」——它只是大幅缓解，快照读和当前读混用仍会出现幻读。

  • 把不可重复读和幻读混为一谈：前者变的是同一行的内容（UPDATE/DELETE 引起），后者变的是符合条件的行数（INSERT 引起），根因和解法都不一样；三个问题按严重程度是 脏读 > 不可重复读 > 幻读。
  • 认为 MVCC 能解决所有幻读 —— MVCC 只管得住快照读，当前读还得靠间隙锁。

📝 回答重点

  • 四个级别从低到高：读未提交、读已提交、可重复读、串行化，MySQL 默认选可重复读。
  • 脏读读到的是别人没提交的数据，不可重复读是同一行内容变，幻读是范围查询行数变。
  • 可重复读走 MVCC 快照，标准 SQL 不排除幻读，InnoDB 靠 next-key 锁缓解。
  • 串行化下关闭 autocommit，普通 SELECT 会隐式转成 FOR SHARE，读写全排队。
  • MVCC 只管快照读，当前读要防幻读还得靠间隙锁。
  • 读已提交每次 SELECT 开新快照，可重复读复用首次快照，这是两者最大的差别。

📈 拔高

InnoDB 缓解幻读靠两层：快照读走 MVCC 看不到新插入的行，当前读用 next-key 锁把范围锁死。坑在先快照读后当前读，两次结果可能对不上。

17. MySQL 中有哪些锁类型？

🎬 面试现场

面试官（口语化）：MySQL 有哪些锁？从粒度和模式两个维度说说，再讲讲间隙锁和临键锁。

⚠️ 翻车点

最容易翻车的是「记录锁是加在行上的」——记录锁实际作用在索引记录上；没走索引时会把扫到的所有行都锁住，效果等于表锁。

📝 回答重点

  • 粒度分表锁和行锁，模式分共享锁和排他锁，S 锁之间不冲突、X 锁独占。
  • SELECT ... FOR UPDATE 取 X 锁，LOCK IN SHARE MODE 取 S 锁，LOCK TABLES t READ 是表级 S 锁。
  • 记录锁加在索引记录上，没走索引就锁住扫过的所有行，效果等于表锁。
  • 间隙锁只阻止往间隙里插数据，锁与锁之间互不冲突，RC 级别下直接禁用。
  • 临键锁是记录锁加间隙锁，前开后闭区间像 (3,5]。插入意向锁之间也不互相阻塞。
  • 自增插入走 Auto-Inc Lock，8.0.3 起 innodb_autoinc_lock_mode 默认 2，只用互斥量。

📈 拔高

意向锁是表级标记，加行锁前先在表上放 IS 或 IX，表锁请求只看标记，不用扫遍记录。空间索引用谓词锁，按查询的最小边界矩形加锁，挡住别的事务插入或修改。

面试官追问 你的答案
什么情况会触发表锁而不是行锁？ 三种：查询没走索引只能全表扫描，锁加到所有扫到的记录上，效果等于表锁。显式用 LOCK TABLES。DDL 如 ALTER TABLE 会加 MDL 写锁。
两个事务都用间隙锁锁住同一个间隙会死锁吗？ 单纯持有间隙锁不会，间隙锁之间不冲突。但如果各自持有间隙锁又想往对方锁住的间隙插数据就会死锁：A 持有 (3,5) 想插 (5,10)，B 持有 (5,10) 想插 (3,5)，互等触发。
为什么说间隙锁是可重复读级别特有的？ 可重复读要防幻读，间隙锁正是干这个的。读已提交不需要防幻读，关闭间隙锁只保留记录锁，锁范围小、死锁概率低，这也是很多互联网公司选 RC 的原因之一。
线上加字段导致查询全部超时怎么回事？ ALTER TABLE 需要 MDL 写锁，若有长事务持有 MDL 读锁不放，ALTER TABLE 就一直等。更糟的是写锁请求优先级更高，后面的查询全堵在 ALTER TABLE 后面。办法是先干掉长事务，或用 pt-online-schema-change 做无锁 DDL。

❌ 千万别说的话

  • “记录锁是锁在数据行上的”（锁的是索引记录，没索引会锁全表）
  • “间隙锁之间会冲突”（间隙锁之间不冲突，插入意向锁之间也不冲突）

18. 你们生产环境的 MySQL 中使用了什么事务隔离级别？为什么？

🎬 面试现场

面试官（口语化）：你们线上用的什么隔离级别？为什么这么选？跟默认值不一样的话，代价是什么？

⚠️ 翻车点

只说「RC 并发高」会漏掉半一致性读这个关键机制，也说不出 RC 下 binlog 必须用 ROW 格式的原因。

  • 把「MySQL 默认是读已提交」当成官方默认值更离谱：官方默认仍然是可重复读，读已提交是很多团队自己改的；而且选 RR 是 statement 格式 binlog 的历史包袱，不是「性能更好所以默认」。

📝 回答重点

  • 线上很多互联网公司用 READ COMMITTED，RR 的间隙锁范围大，锁等待和死锁都更多。
  • 官方例子里 RR 会把 5 行全锁住，RC 只保留真正更新的 2 行，其余加完就放。
  • 半一致性读只在 RC 生效：UPDATE 撞上锁就读最新已提交版本，不满足条件直接跳过。
  • RC 下 binlog 必须用 ROW 格式，否则主从复制可能对不上。
  • 改级别用 SET GLOBAL transaction_isolation = 'READ-COMMITTED'，新连接生效，改前先确认 binlog 是 ROW。
  • 银行、证券这类强一致场景仍用 RR 甚至串行化，多数业务在 RC 加业务层兜底。

📈 拔高

默认停在 RR，通常认为和早期 statement 格式 binlog 有关，RR 的间隙锁保证提交顺序和 binlog 顺序一致，从库重放不会错。现在有 ROW 格式，这个限制没了，但默认值一直没改。

RR 级别配 row 格式的 binlog，还会有主从不一致吗？ 不会。row 格式记录的是每一行的变更，不是 SQL 语句。不管事务的提交顺序怎样，每一行的最终状态是确定的，从库重放的结果肯定和主库一样。
为什么 MySQL 不干脆把默认值改成读已提交？ 向前兼容。很多老系统依赖可重复读的行为，贸然改默认值会让这些系统的行为突然变化而出问题。官方的态度是让用户自己按场景选，不替用户做决定。
什么情况下 RC 会退化成表锁？ UPDATE 或 DELETE 的 WHERE 条件没走索引时。行锁加在索引上，没走索引就得扫全表、每扫一行锁一行，扫描期间整表基本处于锁定状态。所以即使用 RC 也要保证 UPDATE、DELETE 走索引，否则并发优势就没了。
间隙锁具体怎么加的，举个例子？ 锁的是索引记录之间的间隙。比如 id = 1, 5, 10 三条记录，RR 下执行 SELECT * FROM t WHERE id > 3 FOR UPDATE 会锁住 (3,5]、(5,10]、(10,+∞)，别的事务想插 id = 4 就会被阻塞，即使该行还不存在。

19. MySQL 事务的二阶段提交是什么？

🎬 面试现场

面试官（口语化）：MySQL 为什么要搞二阶段提交？redo log 和 binlog 怎么保证一致？

⚠️ 翻车点

把二阶段提交说成「先写 redo 再写 binlog」就等于没答——那正是没有二阶段时会出问题的顺序；关键在于 prepare 状态 + XID 匹配。

📝 回答重点

  • redo log 是 InnoDB 的物理日志，环形写满从头覆盖，管崩溃恢复。binlog 是 Server 层逻辑日志，追加写，管主从复制。
  • 提交时先写 redo log 标成 prepare，再写 binlog，落盘后把 redo 改成 commit。
  • 宕机恢复看 XID：prepare 但 binlog 没写就回滚，两边 XID 对得上才提交。
  • 少了二阶段，先写 redo 宕机会主库有从库没有，先写 binlog 则从库有主库没有。
  • 组提交把多个事务的 fsync 攒一起做，innodb_flush_log_at_trx_commit 生产一般设 1。

📈 拔高

两阶段提交就是分布式事务那套思路，两边都点头才落锤。崩溃恢复只记一条：prepare 且没 binlog 回滚，写了 binlog 就比对 XID，匹配才提交。

💡 主动加分的追问准备

面试官追问 你的答案
为什么不直接把 redo log 和 binlog 合成一个日志？ 它们服务于不同场景：redo log 是 InnoDB 引擎私有的物理修改日志、循环写、保证崩溃恢复。binlog 是 Server 层的逻辑操作日志、追加写、做主从复制和归档。Server 层与存储引擎层分层独立，强行合并会破坏分层设计。
binlog 写成功但通知 InnoDB commit 失败会怎样？ redo log 还是 prepare 状态。重启恢复时 MySQL 拿 redo log 里的 XID 去 binlog 查，能查到说明 binlog 完整，就把事务提交掉，不会丢数据也不会不一致。
组提交攒太久会不会有问题？ 会。攒久了事务响应时间变长，用户感知是「提交卡了一下」。这段时间宕机还可能整批事务丢失。所以生产不会把 delay 设太大，几百微秒到几毫秒即可。
从库复制时也有二阶段提交吗？ 从库执行 relay log 里的事务时也会写 redo log 和 binlog，所以也走二阶段提交。不过从库的 binlog 是可选的，不需要级联复制可以关掉，关掉后只写 redo log，不需要二阶段。

❌ 千万别说的话

  • “二阶段提交就是先写 redo log 再写 binlog”（这只是顺序，真正的关键是 prepare 状态与 XID 匹配）
  • “redo log 和 binlog 是一回事，合并就行”（一个物理一个逻辑，层级与用途都不同）

20. MySQL 中长事务可能会导致哪些问题？

🎬 面试现场

面试官（口语化）：线上跑了个长事务，会带来哪些麻烦？该怎么发现、怎么收拾？

⚠️ 翻车点

  • 只答「锁变多、别人被阻塞」，漏掉 undo log 膨胀、主从延迟、回滚代价这三条——这四条才是完整的伤害面。
  • 不知道长事务的杀伤力有多具体。「会拖慢数据库」是废话，「一个跑了 30 秒没提交的定时任务把连接池打爆，整个服务挂了 5 分钟」才有说服力。
  • 只会说「拆成小批次」却没说清没索引时怎么拆。删大表时 create_date 没索引，按日期拆依然全表扫描，必须用主键分段。
  • 漏掉「删除转插入」的思路：大表要删掉 4.8 亿条、只留 2000 万条时，正确解法是建新表只灌要留的数据再改名，而不是硬删。
  • 回答「kill 掉就行」。长事务 kill 掉时回滚本身也要时间，可能要等，这一层很多人没意识到。

📝 回答重点

  • 锁持有时间变长，后面的事务排队等，连接池被占满，上游超时可能引发雪崩。
  • undo log 膨胀：长事务不提交版本链清不掉，几百 MB 能涨到几十 GB。
  • 主库跑 10 分钟的大事务，从库也要重放 10 分钟，主从延迟期间读从库拿到旧数据。
  • 回滚本身也要时间，kill 掉不等于立刻恢复，之前跑的活还全白干。
  • 删大表先查主键 min/max 再主键分段删，日期列没索引时按日期拆照样全表扫。
  • 用 information_schema.innodb_trx 捞出跑超 60 秒的事务，事务里别塞 RPC 和外部 IO。

📈 拔高

大表要删掉绝大部分数据时，建新表灌要留的行再改名，比硬删快得多，pt-online-schema-change 和 gh-ost 这类工具还能顺手同步增量。预防长事务就四条：事务里别放 RPC，能异步的挪出去，大批量分批提交，@Transactional 别包住整个方法。

长事务导致 undo log 膨胀，具体是什么原理？ InnoDB 用 MVCC 实现事务隔离，更新数据会把旧版本存进 undo log 形成版本链。purge 线程定期清理不再需要的旧版本，但前提是没有活跃事务要读。长事务的 ReadView 不释放，它开始之后产生的版本都清不掉，undo log 就一直堆积。

21. MySQL 的 Change Buffer 是什么？它有什么作用？

🎬 面试现场

面试官（口语化）：Change Buffer 你听说过吗？它是干什么的，为什么 IO 密集的库都靠它扛写入压力？

⚠️ 翻车点

  • 把 Change Buffer 说成独立于 Buffer Pool 之外的另一块内存区域，它其实是 Buffer Pool 的一部分，占用 Buffer Pool 的空间。
  • 说 Change Buffer 适用于所有索引。主键索引、唯一索引、全文索引、空间索引都用不了它。
  • 担心「变更先放内存，数据库挂了数据不就丢了」，答成不安全。实际上每次写 Change Buffer 都会写 redo log，内容也会定期刷到系统表空间持久化。
  • 把 Change Buffer 和 redo log 混为一谈。redo log 解决的是「写数据页」的随机写问题，Change Buffer 解决的是「读索引页」的随机读问题。

📝 回答重点

  • Change Buffer 是 InnoDB 缓存二级索引变更的内存区域，占 Buffer Pool 空间，默认上限 25%，innodb_change_buffer_max_size 最高能调到 50。
  • 索引页不在 Buffer Pool 时，先把「删旧值、插新值」记下来直接返回，等页被读进来或后台刷盘时一次性 merge，省掉大量随机读。
  • 只有普通二级索引能用：主键索引是聚簇索引，唯一索引必须读页查重，全文和空间索引结构特殊，都用不了。
  • 版本口径分清：8.0 默认 all，8.4 起手册默认 none，innodb_change_buffering=none 可以关。
  • 每次写它都同步写 redo log，内容也定期持久化到系统表空间，崩溃恢复靠 redo log 重放，不会丢。

📈 拔高

写多读少、二级索引多、机械盘的场景收益最大，SSD 加内存够大的库收益有限。8.4 之后 change buffering 默认关，新库先看业务写入模式再决定开不开。

面试官追问 你的答案
Change Buffer 和 redo log 有什么关系？它们不是都能提升写入性能吗？ 解决的层面不同。redo log 把随机写变顺序写，主键索引和二级索引都会写，管写数据页。Change Buffer 让二级索引变更先不读页、攒着批量 merge，管读索引页。写 Change Buffer 时也写 redo log 保持久。
为什么唯一索引不能用 Change Buffer？ 唯一索引插入或更新时必须读索引页查重，页反正要读进来，缓存变更没意义。InnoDB 干脆规定唯一索引不走 Change Buffer。
线上数据库要不要调大 Change Buffer 的比例？ 看场景。写密集、二级索引多，可以调大到 30%-40% 攒更多变更。代价是留给数据页的空间变少，缓存命中率可能降，最终靠压测找写入吞吐和查询延迟的平衡点。

❌ 千万别说的话

  • “Change Buffer 是 InnoDB 之外单独的一块内存区域。” ：它占用的是 Buffer Pool 的内存空间，默认上限是 Buffer Pool 的 25%。
  • “Change Buffer 对主键索引和唯一索引同样生效。” ：唯一索引必须读页校验重复，主键索引就是聚簇索引，两者都用不了。
  • “变更先放在内存里，数据库宕机会丢数据。” ：每次写 Change Buffer 都写 redo log，内容也定期持久化到系统表空间，崩溃恢复能还原。
  • “Change Buffer 和 redo log 是一回事，都能提升写性能。” ：一个解决读索引页的随机 I/O，一个把随机写变成顺序写。

22. MySQL 的乐观锁和悲观锁是什么？

🎬 面试现场

面试官（口语化）：乐观锁和悲观锁你说说呗，具体到 MySQL 里怎么实现？什么场景用哪个？

⚠️ 翻车点

  • 只背定义不说实现 —— 面试官要的是 SELECT ... FOR UPDATE、SELECT ... LOCK IN SHARE MODE 和 version 字段这几个具体手段。
  • 说乐观锁就是”用一条 SQL 判断有没有被别人改” —— 没说清它是读时记版本号、更新时把版本号带进 WHERE，靠影响行数为 0 判断冲突。
  • 说 FOR UPDATE 锁的一定是”那一行” —— 没走索引时 InnoDB 会锁全表的所有行，并发直接退化成串行。
  • 说乐观锁”性能一定比悲观锁好” —— 秒杀这种写冲突极高的场景，乐观锁大量失败重试反而更慢。
  • 忘了乐观锁用原值做 CAS 有 ABA 问题 —— 值从 100 改成 50 又改回 100，CAS 会认为没变过。

📝 回答重点

  • 悲观锁是操作前先拿锁：SELECT ... FOR UPDATE 拿排他锁，SELECT ... FOR SHARE 拿共享锁，别的事务读写都得等它提交或回滚。
  • 典型写法是扣库存：BEGIN → FOR UPDATE 锁行 → 业务判断库存够 → UPDATE 扣减 → COMMIT，秒杀常用。
  • 乐观锁不加锁，读的时候带上 version，更新时把它塞进 WHERE，影响 0 行说明被人改过，重试还是报错业务定。
  • 也能拿原值做 CAS：UPDATE ... WHERE stock = 100，值改回原样会被误判没变过，version 只增不减没这问题。
  • 选型看冲突概率：读多写少冲突低，乐观锁省开销吞吐高。写多冲突高，悲观锁排队更稳。
  • 8.0 加了 FOR UPDATE NOWAIT 立刻报错不等锁，SKIP LOCKED 跳过被锁的行，任务队列多 worker 抢活很好用。

📈 拔高

面试常追 CAS 的 ABA 和重试风暴，落点是 version 只增不减、重试要封顶。悲观锁没走索引会锁全表并发串行，这比选型本身更容易被追问。

面试官追问 你的答案
乐观锁更新失败率很高怎么办？ 先确认是不是真要并发写同一行。秒杀场景可以拆库存桶随机打散冲突，或用队列合并批量处理。最差做法是无限重试，会把库压垮。
FOR UPDATE 是锁行还是锁表？ 走索引时锁满足条件的行，没走索引会锁全表所有行，并发直接串行。RR 级别下还会加间隙锁，锁范围比预期大。
乐观锁的 version 字段用什么类型？ 我一般用 INT 或 BIGINT。INT 上限约 21 亿，每秒更新 1000 次只够约 25 天，每秒 1 次才够 60 年，怕不够直接上 BIGINT。timestamp 毫秒精度在高并发下会同毫秒撞车，UUID 比数字慢。
分布式系统里怎么实现乐观锁？ 表里的 version 字段照样能用。跨服务就得上分布式锁，Redis 的 WATCH 加 MULTI 或 Redisson 的 RLock 都行，ZooKeeper 临时顺序节点更可靠但性能差些。

  • “FOR UPDATE 永远只锁住匹配的那几行。” ：没走索引时会锁全表所有行，并发直接串行。
  • “乐观锁在任何场景下都比悲观锁性能好。” ：高冲突写场景下乐观锁的大量失败重试反而更慢。
  • “用 WHERE stock = 100 做 CAS 就不会有并发问题。” ：这是 ABA 问题，值改回原样就绕过去了，要用只增不减的 version 字段。

23. MySQL 中如果发生死锁应该如何解决？

🎬 面试现场

面试官（口语化）：线上突然报死锁了，你会怎么排查和解决？先说自动机制，再说怎么手工把它捞出来。

⚠️ 翻车点

  • 只说”MySQL 会自动检测并回滚”，面试官想听的是自动机制 + 手动干预两条路，以及具体怎么查、怎么杀。
  • 说自动检测会回滚”最后那个事务” —— InnoDB 选的是代价最小（持锁更少、回滚更便宜）的事务，不是最后提交的。
  • 不知道 8.0 之后 INFORMATION_SCHEMA.INNODB_LOCKS / INNODB_LOCK_WAITS 已经被移除，查旧表会直接报表不存在。
  • 说死锁只能靠超时解决 —— 默认是有死锁检测的，innodb_deadlock_detect 默认开着。
  • 把”避免死锁”和”处理死锁”混着讲 —— 一套是事后救火（检测、杀线程），一套是事前预防（拆事务、固定加锁顺序、降隔离级别）。

📝 回答重点

  • InnoDB 默认开死锁检测（innodb_deadlock_detect），发现死锁就挑代价最小的事务回滚，把锁让给另一个。
  • 兜底是锁等待超时，innodb_lock_wait_timeout 默认 50 秒，超时只回滚当前语句，整事务回滚得开 innodb_rollback_on_timeout。
  • 排查第一步 SHOW ENGINE INNODB STATUS，看 LATEST DETECTED DEADLOCK 段，两边持什么锁、等什么锁、回滚了谁都写得清楚。
  • 8.0 之后锁信息查 performance_schema.data_locks 和 data_lock_waits，旧的 INNODB_LOCKS 已移除，查了报表不存在。
  • 手动救火三步：查锁表定位阻塞线程，在 INNODB_TRX 里拿 trx_mysql_thread_id，然后 KILL 掉它。
  • 预防靠拆小事务、固定加锁顺序、建好索引防锁全表，官方明确说死锁跟隔离级别无关，降级别不算防死锁手段。

📈 拔高

死锁检测本身烧 CPU，压测发现检测占比高可以关掉，把锁等待超时压到 1 到 2 秒，靠快速超时加应用重试。回滚选小事务是因为 undo 少、锁放得快，日志里 WE ROLL BACK TRANSACTION 会写明回滚了谁。

24. MySQL 中的 Log Buffer 是什么？它有什么作用？

🎬 面试现场

面试官（口语化）：InnoDB 写数据是遵循 WAL 的对吧？那你给我讲讲 Log Buffer 是个什么东东，它到底解决了什么问题？

⚠️ 翻车点

  • 把 Log Buffer 说成「缓存数据页的地方」，和 Buffer Pool 的职责搞混。
  • 只说「它用来缓存 redo log」，讲不出它真正要解决的是每次提交都 fsync 一次的系统调用开销。
  • 不会说 Log Buffer 和 Buffer Pool 是并列的两块独立内存区域，以及脏页刷盘和 redo log 刷盘是两条独立链路。
  • 答不出 innodb_flush_log_at_trx_commit 三个取值的差别，尤其是 0 和 2 丢数据的边界在哪。
  • 忽略掉「Log Buffer 和 binlog cache 有什么区别」这个高频追问。

📝 回答重点

  • Log Buffer 是 InnoDB 缓存 redo log 的内存区域，默认 16MB（8.4 起 64MB），innodb_log_buffer_size 控制。
  • 作用是攒小写入：事务的 redo log 先进缓冲，避免每条都 fsync，提交时一次刷盘省下系统调用。
  • 刷盘时机两个口径：提交时按 innodb_flush_log_at_trx_commit 走，后台周期刷由 innodb_flush_log_at_timeout 控制，默认 1 秒一次。
  • innodb_flush_log_at_trx_commit=1 是提交即 write 加 fsync 最稳，设 0 和 2 都可能在崩溃时丢最多 1 秒，2 只是多写一层 OS 缓存。
  • 够不够用看 SHOW GLOBAL STATUS LIKE 'Innodb_log_waits'，持续增长就把缓冲调到 32MB 或 64MB。
  • binlog cache 和它是两条链路：redo log 是引擎层物理日志管崩溃恢复，binlog 是 Server 层管复制，靠两阶段提交对齐。

📈 拔高

「用量过半就刷」是源码行为，手册只写了提交刷和周期刷，按手册答更稳。redo log 和 binlog 靠两阶段提交对齐，写 redo 标 prepare、写 binlog、再标 commit，恢复时凭它决定事务回滚还是提交。

💡 主动加分的追问准备

面试官追问 你的答案
innodb_flush_log_at_trx_commit 设成 2 和设成 0 有什么区别？都是可能丢数据，为啥要分两个值？ 分层不一样。0 只写在 Log Buffer，2 会 write 到 OS 缓存。手册口径是两者在崩溃时都可能丢最多 1 秒。生产想稳用 1，想换性能一般选 2 不选 0。
Log Buffer 和 Buffer Pool 有什么关系？ 两块独立内存，干的活不同。Buffer Pool 缓存数据页，写数据先把它改脏。Log Buffer 缓存 redo log，记的是改了什么。脏页刷盘和 redo log 刷盘是两条独立链路。
有了 redo log 还要 binlog，两个日志不是重复了吗？ 定位不同。redo log 是引擎层物理日志，记数据页改动，循环写空间固定，管崩溃恢复。binlog 是 Server 层逻辑日志，记执行的 SQL，追加写，管主从复制和按时间点恢复。

❌ 千万别说的话

  • “Log Buffer 就是 Buffer Pool 的一部分，专门存 redo log。” ：Log Buffer 和 Buffer Pool 是内存层里并列的两块独立区域，不是同一个东西。
  • “每次事务提交都会把 redo log 逐条 fsync 到磁盘，Log Buffer 只是缓存一下。” ：恰恰相反，Log Buffer 存在的意义就是把多次小写入攒起来合并成一次大写入，降低 fsync 次数。
  • “innodb_flush_log_at_trx_commit 设成 0 和设成 1 安全性一样，只是性能差一点。” ：一个是宕机丢 1 秒数据，一个是绝对不丢，金融、订单这类场景必须用 1。
  • “redo log 和 binlog 是一回事，写一份就够了。” ：一个是引擎层的物理日志用于崩溃恢复，一个是 Server 层的逻辑日志用于主从复制，写法和用途都不一样。

25. 什么是 Write-Ahead Logging (WAL) 技术？它的优点是什么？MySQL 中是否用到了 WAL？

🎬 面试现场

面试官（口语化）：WAL 这个词你肯定听过，它到底是个什么思想？为什么数据库要这么设计，MySQL 用了吗？

⚠️ 翻车点

  • 只答「先写日志再写数据」这一句就停，答不出 WAL 相对「直接写数据」到底赢在哪。
  • 讲不清「日志落盘就算提交成功，数据文件还是旧的」这个关键点，把它说成「数据也一起落盘了」。
  • 说不清 redo log 的环形结构，讲不出 write pos 和 checkpoint 两个指针分别代表什么。
  • 把 redo log 说成「追加写、文件会越来越大」，和它循环写、空间固定的事实说反。
  • 答不出 redo log 写满时的表现，更答不出 checkpoint 抖动是什么。

  • WAL 就是先写日志再写数据：改动先落日志，崩溃后靠日志重放恢复，日志落盘就算事务持久化完成。
  • InnoDB 分三步：事务改 Buffer Pool 的页变脏，同时写 redo log buffer，提交时把 redo log 刷到盘，后台空闲再异步刷脏页。
  • redo log 体积小、顺序追加，数据页 16KB 随机写又大又慢，先写日志把随机写变顺序写，写到一半崩溃也不废数据页。
  • 8.0.30 起容量由 innodb_redo_log_capacity 管，默认 100MB，文件是约 32 个 #ib_redoN，老的 ib_logfile0/1 两文件说法已过时。
  • 它循环复用：write pos 追着写，checkpoint 标记刷到哪，写满就得停下推 checkpoint，更新全阻塞，这叫 checkpoint 抖动。
  • 其它数据库也在用这套思想：PostgreSQL 就叫 WAL，Oracle 叫 redo log，Redis 的 AOF 本质也是先写日志。

📈 拔高

write pos 和 checkpoint 是教学类比，官方手册只有 checkpoint 概念，说出来没毛病但别当官方术语。redo log 与 binlog 靠两阶段提交对齐：写 redo 标 prepare、写 binlog、再标 commit，恢复时凭它决定回滚还是提交。

💡 主动加分的追问准备

面试官追问 你的答案
redo log 和 binlog 都是日志，它们有什么区别？ redo log 是引擎层物理日志，记数据页改动，循环写空间固定，管崩溃恢复。binlog 是 Server 层逻辑日志，记 SQL 语句，追加写越写越大，管复制和按时间点恢复，两者靠两阶段提交对齐。
什么是两阶段提交？为什么需要它？ 为了 redo log 和 binlog 一致。先写 redo log 标 prepare，再写 binlog，最后把 redo log 标 commit。恢复时只有 prepare 没有 binlog 就回滚，有对应 binlog 就提交。
redo log 写满了会发生什么？ 被迫停下来推 checkpoint，就得刷一批脏页，刷脏期间所有更新被阻塞，这叫 checkpoint 抖动。解法是调大 innodb_redo_log_capacity，或提高 innodb_io_capacity 让刷脏更积极。
redo log 能不能保证不丢数据？ 取决于 innodb_flush_log_at_trx_commit 的设置。设成 1 才能保证不丢，每次提交都 fsync 到磁盘。设成 0 或 2 的话，如果 MySQL 进程或者操作系统崩溃，最多可能丢 1 秒的数据。还要注意，redo log 只能保证已提交事务的数据不丢，未提交的事务本来就会被回滚。

❌ 千万别说的话

  • “WAL 的意思是写日志，写数据之前先把日志写了就行，细节不重要。” ：面试官真正想听的是它相对直接写数据页的两个优势：顺序追加代替随机写、日志半截不废页。
  • “redo log 是追加写的，文件会一直涨，得定期清理。” ：InnoDB 的 redo log 是固定大小的环形文件，靠 write pos 和 checkpoint 两个指针复用空间，不是追加写。
  • “事务提交的时候数据和日志都一起落盘了。” ：WAL 下只要日志落盘就算提交成功，数据页是脏页，之后才由后台线程异步刷盘。
  • “redo log 满了不会有问题，MySQL 会自动扩容。” ：redo log 满了会触发 checkpoint 抖动，更新全部阻塞，只能靠调大日志文件或提高 innodb_io_capacity 缓解。

26. MySQL 插入一条 SQL 语句，redo log 记录的是什么？

🎬 面试现场

面试官（口语化）：插入一条数据，redo log 到底记了什么？是记的这条 SQL 吗？

⚠️ 翻车点

  • 答”redo log 记的是 SQL 语句” —— redo log 是物理日志，记的是数据页某个偏移位置被改成了什么值，跟 binlog 那种逻辑日志不是一回事。
  • 把它和 binlog 混为一谈 —— 两者一个在存储引擎层、一个在 Server 层，一个物理一个逻辑，用途也完全不同。
  • 说 redo log 只记数据变更、不记元数据 —— 页目录、页头等元数据的变更同样要记，否则恢复出来的页是坏的。
  • 说”redo log 满了就报错” —— 手册的说法是强制推进 checkpoint、拼命刷脏页，写入被拖住、TPS 断崖是常见经验表现。
  • 答不出 WAL 的顺序 —— 是日志先落盘、数据页后落盘，不是反过来。

📝 回答重点

  • redo log 是物理日志，记「哪个页哪个偏移改成了什么值」，不记 SQL 语句。
  • 拿到插入先走 WAL：先改 Buffer Pool 里的页，redo 写进 Log Buffer，提交时 redo 先落盘，数据页后台慢慢刷。
  • 生产要双 1：innodb_flush_log_at_trx_commit=1 每次提交刷 redo，sync_binlog=1 每次提交刷 binlog。
  • 两阶段提交里 redo 先标 prepare，写完 binlog 再标 commit，恢复时查 binlog，有就提交没就回滚。
  • redo 满了就强制推进 checkpoint 刷脏页腾空间，写入拖慢属经验表现，8.0.30 起改用 innodb_redo_log_capacity 调总容量。

📈 拔高

redo 是 InnoDB 私货，binlog 是 Server 层公共日志，一个管崩溃恢复一个管主从复制。循环写有 write pos 和 checkpoint 两个指针，8.0.30 前是 ib_logfile0/1 两个文件，之后搬到 #innodb_redo 目录自动管文件数。

💡 主动加分的追问准备

面试官追问 你的答案
redo log 和 undo log 有什么区别？ redo log 记”改完之后是什么”，崩溃恢复把没刷盘的数据页改回来。undo log 记”改之前是什么”，回滚时把数据改回去，它还撑起 MVCC 版本链，读操作靠它找可见版本。
如果 redo log 满了会发生什么？ MySQL 会强制推进 checkpoint、拼命刷脏页腾空间，写入被拖住、TPS 大跌是常见经验表现。大小要按写入量配，8.0.30 前用 innodb_log_file_size，之后用 innodb_redo_log_capacity 撑住 1 小时写入量。
redo log 的 LSN 是什么？ LSN 是 Log Sequence Number，redo log 的全局自增序号，每写一条日志加对应字节数。它用来判断页要不要恢复、比 checkpoint 和 write pos，页头也存 LSN，比出来小的才重做。
MySQL 8.0 对 redo log 有什么优化？ 8.0.30 引入 innodb_redo_log_capacity 直接设 redo log 总容量，MySQL 自动管日志文件数量，容量支持在线动态调整。这之前用 innodb_log_file_size 得停机改。另有并行写 redo log 优化，高并发写入更快。

❌ 千万别说的话

  • “redo log 里记的就是那条 INSERT 语句。” ：redo log 是物理日志，记数据页偏移与新值。
  • “redo log 和 binlog 差不多，区别就是放的位置不同。” ：一个物理一个逻辑，一个引擎层一个 Server 层，用途完全不同。
  • “redo log 满了会直接报错拒绝服务。” ：手册只说强制推进 checkpoint 刷脏页，写入被拖住、TPS 大跌是经验表现。
  • “undo log 和 redo log 是一回事。” ：redo 记”改后”用于恢复，undo 记”改前”用于回滚，还支撑 MVCC 版本链。

27. MySQL 的 Doublewrite Buffer 是什么？它有什么作用？

🎬 面试现场

面试官（口语化）：MySQL 有 redo log 了，为什么还要 Doublewrite Buffer？它俩管的是一回事吗？

⚠️ 翻车点

把 Doublewrite 说成「数据丢不了的保险」——它防的是页损坏（torn page），redo log 防的是数据丢失，两者解决的是不同问题。

📝 回答重点

  • Doublewrite 防的是页损坏，脏页刷盘前先在内存备份，再顺序写到 doublewrite 文件，最后才写数据文件。
  • 页 16KB、系统 IO 常是 4KB，断电写一半就是 torn page，redo log 往坏页重放还是坏页。
  • 恢复时发现数据文件页坏了，先从 doublewrite 文件取完整页盖回去，再照常走 redo log 恢复。
  • 8.0.20 起搬出 ibdata1，落到 #ib_16384_0.dblwr 独立文件，可以单独放更快的盘。
  • 开销主要是多一次顺序写，攒批摊薄，别怕开；只有存储能原子写 16KB 时才考虑 innodb_doublewrite=OFF。

📈 拔高

redo log 管数据丢失，Doublewrite 管数据损坏，一个保持久性一个保页完整，这题答出层次就赢了。真想关它，手册只背书 Fusion-io 这类原子写设备自动禁用，ZFS、带电容 SSD 属社区说法。

💡 主动加分的追问准备

面试官追问 你的答案
Doublewrite Buffer 和 redo log 都能保证数据不丢，有什么区别？ redo log 保事务持久性，提交时日志落盘就返回成功。Doublewrite 保页完整性，防刷脏页断电弄坏页。redo log 解决数据丢失，Doublewrite 解决数据损坏，页坏了 redo log 也救不了，得靠 Doublewrite 备份。
为什么不直接把 redo log 的页面粒度改成 16KB，这样不就不需要 Doublewrite 了？ redo log 记增量修改不是整页，一个事务可能只改几个字节，每次记整页日志量会暴增。redo log 要尽可能小、尽可能快，而 Doublewrite 只在刷脏页时触发，频率低得多，多写一份开销可以接受。
MySQL 8.0 把 Doublewrite 移到独立文件有什么好处？ 能把 Doublewrite 文件单独放更快的盘。以前它在 ibdata1 里跟数据抢 I/O，现在分开，用便宜 SSD 专放它、主存储放正常数据，I/O 互不影响，也方便单独监控调优。

❌ 千万别说的话

  • “有 redo log 就不需要 Doublewrite 了”：redo log 往损坏的页上重放，结果还是坏页。
  • “Doublewrite Buffer 是把数据写两遍，性能砍半”：实际只有 5%-10% 的损失，顺序写摊薄了成本。
  • “Doublewrite 可以随意关闭省性能”：只有存储层能保证原子写 16KB 时才可以关。

三、SQL 执行与调优：从一条 SQL 到慢查询治理

28. 详细描述一条 SQL 语句在 MySQL 中的执行过程。

🎬 面试现场

面试官（口语化）：你给我从头讲一遍，一条 SELECT 语句丢进 MySQL 之后，到底经历了哪些环节才把结果返回给我？

⚠️ 翻车点

最常翻车的是把「分析器」和「优化器」讲成一回事。分析器只负责 SQL 写得对不对（词法分析、语法分析、生成 AST），优化器才负责怎么执行最快（选索引、决定 JOIN 顺序、是否改写子查询）。另外 MySQL 8.0 已经砍掉了查询缓存，别再把「查查询缓存」当成流程必答项。讲到执行计划里的排序时也别只说「有索引就排序了」，答不出 filesort 的 sort_buffer、单路与双路排序的区别，追问 Using filesort 到底在排什么就接不住。

📝 回答重点

  • 分两层：Server 层管连接、解析、优化，存储引擎层管真实读写。
  • 流程是连接器鉴权 → 分析器拆 token 查语法生成 AST → 优化器选索引定 JOIN 顺序出计划 → 执行器调 Handler API 读行。
  • 8.0 已砍查询缓存，一写全失效命中率太低，别把它当流程必答项。
  • 执行计划里 ORDER BY 对不上索引就走 filesort，数据在 sort_buffer 里排，默认 256KB，塞不下溢出磁盘做外部排序。
  • 字段少用单路排序，字段多走双路，看 max_length_for_sort_data 阈值，字段多时单路溢盘反而更慢。
  • 更新语句在执行阶段写 redo、undo、binlog，靠两阶段提交对齐，行锁经 MVCC 读写不阻塞。

📈 拔高

优化器拿 AST 按成本挑执行计划，统计信息过期就会选错，FORCE INDEX 能兜底但根子在 ANALYZE TABLE。排序想免 filesort，要么索引方向对齐，要么覆盖索引省回表，8.0 降序索引让 a ASC b DESC 混排也直接走索引。

💡 主动加分的追问准备

面试官追问 你的答案
分析器和优化器有什么区别？ 分析器只管 SQL 写得对不对：拆 token、查语法、生成语法树。优化器拿这棵树决定怎么执行：选哪个索引、JOIN 顺序、子查询要不要改写。语法树固定，执行计划有很多种，优化器挑成本最低的。
为什么 MySQL 8.0 砍掉查询缓存？ 查询缓存失效策略太激进，表上有任何写操作，这张表相关缓存全部失效，高并发写场景几乎命中不了，反而增加维护开销。读多写少用 Redis 这类专业缓存更合适。
执行器调用的存储引擎接口长什么样？ 是统一的 Handler API：ha_open 打开表、ha_rnd_next 全表扫描读下一行、ha_index_read 索引定位读取、ha_write_row 写入一行、ha_delete_row 删除一行。不同存储引擎各自实现，Server 层不关心底层是 InnoDB 还是 MyISAM。
EXPLAIN 看到走了索引但查询还是很慢，可能是什么原因？ ①回表太多，二级索引命中几十万行，每行都回表，随机 IO 拉垮。②索引选择性太差，比如性别字段。③返回字段多不是覆盖索引，传输耗时。④索引树太大装不下内存，频繁读磁盘。重点看 rows 估算值和 Extra。
强行用单路排序一定比双路排序快吗？ 不一定。单路省掉按行 ID 再读字段那次 IO，但所有字段都进 sort_buffer，占内存大。SELECT 字段多时装不下就溢出磁盘做外部排序，可能反而比双路慢。字段少用单路，字段多双路更合适。
怎么判断一条 SQL 的排序是不是在内存里完成的？ 看状态变量 sort_merge_passes。执行 SQL 前后各 SHOW STATUS LIKE 'sort_merge_passes' 一次，数值增加就说明发生了磁盘外部排序，因为归并排序才会累加这个计数。也可以开启 optimizer_trace，能看到排序用了多少内存、有没有溢出。
ORDER BY 和 GROUP BY 的排序有什么区别？ MySQL 5.7 及之前 GROUP BY 默认对分组字段排序，相当于隐式 ORDER BY，不需要可加 ORDER BY NULL 去掉。8.0 改了这个行为，不再隐式排序，要排序得显式写 ORDER BY。GROUP BY 还可能用到临时表，Extra 显示 Using temporary。
MySQL 8.0 的降序索引解决了什么问题？ 以前索引只能升序存储，ORDER BY a ASC, b DESC 这种混合排序没法完全利用索引，b 这列得 filesort。8.0 支持建索引时指定排序方向，比如 CREATE INDEX idx ON t(a ASC, b DESC)，混合排序也能直接走索引，对「按时间降序取最新数据」这类分页场景尤其有用。

❌ 千万别说的话

  • “MySQL 会先查查询缓存。”：MySQL 8.0 已经砍掉这个功能，别把它当成标准流程讲。
  • “分析器和优化器是一回事，都是解析 SQL 的。”：职责完全不同，语法树由分析器生成、执行计划由优化器决定。
  • “sort_buffer_size 调得越大排序越快，调到 1G 没问题。”：每个连接各有一份 sort_buffer，调太大内存吃紧还会影响并发。

29. MySQL 中如何进行 SQL 调优？

🎬 面试现场

面试官（口语化）：线上有一条 SQL 跑得特别慢，落到你头上，你这套 SQL 调优的方法论是什么？

⚠️ 翻车点

别只答「加索引」。调优是三步闭环：先用慢查询日志定位慢 SQL，再用 EXPLAIN 分析执行计划，最后针对性优化。只说「加索引」会被追问「那你的索引为什么没生效」，然后就翻车了。另外别把优化顺序答反：优先优化 SQL，硬件升级是最后手段——SQL 优化是指数级提升，硬件是线性提升，一条烂 SQL 全表扫描 1000 万行，换 SSD 也只是从 10 秒变 3 秒，改成走索引可能只要 10 毫秒。

📝 回答重点

  • 拿到慢 SQL 先走三步：慢查询日志定位，EXPLAIN 看计划，再动手改。
  • 索引最常翻车在函数运算、隐式转换、OR 带非索引列、左侧 % 通配，还有不满足最左匹配。
  • EXPLAIN 看 type、rows、Extra：ALL 是全表扫，Using filesort 说明排序没吃到索引。
  • SQL 写法先自查：禁 SELECT *，分页改游标 WHERE id > 代替 LIMIT 大偏移，热点查询上缓存。
  • 优化顺序别答反：先 SQL 再索引再配置，硬件升级放最后，SQL 是指数级收益。
  • 索引有写入代价，建之前问三件事：查询频率、区分度、能不能并成联合索引。

📈 拔高

调优还有两个维度：锁竞争和无效计算，SHOW ENGINE INNODB STATUS 看锁等待，PROCESSLIST 看在跑的事务。索引不是越多越好，每个二级索引都是一棵要维护的 B+ 树，建索引前先看区分度。

💡 主动加分的追问准备

面试官追问 你的答案
联合索引 (a, b, c)，条件是 WHERE a = 1 AND c = 3，能用索引吗？ 能用到，但只能用到 a 这一列。联合索引按 a、b、c 顺序排列，跳过 b 就无法利用 c 的有序性，MySQL 用 a = 1 快速定位后在该范围内逐行判断 c = 3。想让三列都生效，条件必须包含 a 和 b。
线上突然出现大量慢查询，排查思路是什么？ 先看是不是某时间点突然出现，查那时有没有发布、有没有跑批。再看慢查询日志找出最频繁的 SQL，EXPLAIN 看执行计划、查索引有没有失效。同时看 CPU、磁盘 I/O、连接数有没有打满，锁等待用 PROCESSLIST 和 INNODB STATUS 查。
什么情况下优化器会放弃使用索引？ 优化器按成本估算，认为全表扫更快就不走索引。典型是结果集占比太高，100 万条能匹配 60 万条，走索引反而多一次回表不如全表扫。统计信息不准也会误判，可 ANALYZE TABLE 更新。
联合索引不满足最左匹配时，索引就完全不能用了么？ 不是完全不能用，是用不到后面的列。索引 (a, b, c) 上写 WHERE a = 1 AND c = 3 时，MySQL 仍会用 a 定位，只是 c 无法利用有序性，表现为只能用上第一列。
线上数据库 CPU 飙到 100%，怎么排查？ 先用 SHOW PROCESSLIST 找执行时间长的语句，EXPLAIN 看是不是全表扫或锁等待。紧急情况先 KILL 掉对应线程再优化。连接数打满就查连接泄漏或连接池配太小。
表里有 1 亿条数据，加一个索引要多久？会不会锁表？ MySQL 5.6 起有 Online DDL，加索引不锁全表，只在开始结束瞬间有短暂元数据锁。1 亿条数据建索引可能跑几十分钟到几小时，有额外 I/O 和 CPU 开销。建议低峰期执行，或用 pt-online-schema-change 做无锁变更。
innodb_buffer_pool_size 设成内存的 100% 会怎样？ 会把操作系统和其他进程挤死。MySQL 进程本身要占内存，操作系统也需要内存做文件缓存和运行其他服务，设太大可能触发 OOM Killer 把 MySQL 直接杀掉，一般留 20%~30% 给操作系统比较稳妥。
读写分离之后怎么解决主从延迟导致的数据不一致？ ①写完立刻要读的强制走主库，比如刚下单就查订单。②能容忍短暂延迟的在应用层等一会，或用半同步复制保证至少一个从库收到 binlog。③用 GTID 判断从库同步到哪，没到就等或切主库。

❌ 千万别说的话

  • “建了索引就一定能用上。”：函数运算、隐式类型转换、OR 带非索引字段、左侧通配符、联合索引不满足最左匹配，都会让索引失效。
  • “ORDER BY 和 GROUP BY 哪个先？”：执行顺序里 GROUP BY 在 ORDER BY 之前，这是固定顺序，不要说反。
  • “性能不行就加内存、换 SSD。”：硬件升级是最后手段，SQL 优化才是收益最高的一步。

面试官（口语化）：我们线上要监控慢 SQL，方案你设计一下，怎么发现、怎么分析、怎么持续跟进？

⚠️ 翻车点

31. SQL 中 select、from、join、where、group by、having、order by、limit 的执行顺序是什么？

🎬 面试现场

面试官（口语化）：SELECT、FROM、JOIN、WHERE、GROUP BY、HAVING、ORDER BY、LIMIT 这几个子句，实际执行的时候是按什么顺序来的？

⚠️ 翻车点

两个高频坑：一是把书写顺序当成执行顺序（WHERE 在 SELECT 之前，所以不能用 SELECT 里定义的别名）；二是把 WHERE 和 HAVING 讲反——WHERE 在分组前过滤、不能用聚合函数，HAVING 在分组后过滤、可以用聚合函数。

📝 回答重点

  • 逻辑顺序是 FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT，跟书写顺序不一样。
  • 因为 WHERE 在 SELECT 之前跑，SELECT 里定义的别名不能拿去 WHERE 里用。
  • WHERE 在分组前过滤原始行、不能用聚合函数；HAVING 在分组后过滤组、可以用。
  • ORDER BY 能用别名，因为它在 SELECT 之后执行。
  • LIMIT 最后跑，取前 N 条必须先 ORDER BY；排序列有重复值时要加主键做第二排序，否则结果不稳定。

📈 拔高

逻辑顺序只帮你理解语义，实际执行看 EXPLAIN：有 (user_id, create_time) 这种复合索引时，优化器可以顺着索引倒序取够 10 条就停，连排序都省了。

💡 主动加分的追问准备

面试官追问 你的答案
DISTINCT 在执行顺序里排第几？ DISTINCT 和 SELECT 一起执行，在 GROUP BY、HAVING 之后、ORDER BY 之前，作用是对 SELECT 出来的结果去重。如果同时有 GROUP BY 和 DISTINCT，DISTINCT 一般没实际效果，因为 GROUP BY 已经让每组只剩一行。
子查询的执行顺序是怎样的？ 看类型。FROM 子句里的子查询会先执行生成临时表，外层查询在这个临时表上执行；WHERE 里的相关子查询每处理外层一行就要执行一次内层查询，性能很差；非相关子查询可能被优化器改写成 JOIN，效率好很多。
UNION 的执行顺序是怎样的？ 先分别执行每个 SELECT，再合并结果集。UNION 会去重，要额外做排序去重操作；UNION ALL 不去重直接拼接，性能更好。要对 UNION 的最终结果排序，ORDER BY 要写在最后一个 SELECT 后面，或把整个 UNION 包成子查询再排序。
GROUP BY 后面能写表达式吗？ 可以，MySQL 支持在 GROUP BY 里写表达式。但 GROUP BY YEAR(create_time) 这种写法用不上 create_time 上的索引，因为要对每一行计算 YEAR()。数据量大时要么加冗余的 year 字段做索引，要么用虚拟列 + 索引。

❌ 千万别说的话

  • “执行顺序和书写顺序一样，SELECT 在最前。”：这正好反了，WHERE 在 SELECT 之前。
  • “WHERE 和 HAVING 都能用聚合函数。”：WHERE 在分组前执行，此时聚合函数还没法算，COUNT(*) > 10 写在 WHERE 里会直接报错。

32. 如何使用 MySQL 的 EXPLAIN 语句进行查询分析？

🎬 面试现场

面试官（口语化）：EXPLAIN 你平时怎么用？重点看哪几个字段？看到什么就该警觉了？

⚠️ 翻车点

  • 把 possible_keys 当成”实际用了哪个索引” —— 它只是候选清单，key 才是优化器最终选的。
  • 只看 key 不看 rows —— 走了索引但预估要扫几十万行，照样慢得离谱。
  • 忽略 Extra 里的 Using filesort 和 Using temporary —— 这两个几乎是明确的优化信号。
  • 说 type = index 和 type = ALL 差不多、都能接受 —— index 是扫整棵索引树，ALL 是全表扫描，差着数量级。
  • 把 Using index 和 Using index condition 混为一谈 —— 前者是覆盖索引完全不回表，后者是 ICP 少回表。

📝 回答重点

  • 先看 type，从好到坏是 const > eq_ref > ref > range > index > ALL，看到 ALL 就是全表扫。
  • 再看 key，possible_keys 只是候选清单，key 才是优化器真正用上的索引。
  • rows 是预估扫描行数，几百行和几十万行就是毫秒和几秒的差别。
  • Extra 里 Using index 是覆盖索引不回表，Using filesort、Using temporary 基本都该优化。
  • 要真实执行数据就用 EXPLAIN ANALYZE（8.0.18+），它会把查询真跑一遍。

📈 拔高

Using index condition 是索引下推，少回表但没消除；DERIVED 在 derived_merge 打开时会被合并进外层，不是所有子查询都物化成临时表。

💡 主动加分的追问准备

面试官追问 你的答案
一个慢查询，EXPLAIN 看到走了索引但还是慢，可能是什么原因？ 先看 rows 估算值和 Extra 里有没有 filesort、temporary。常见几种：回表行数太多随机 I/O 扛不住，索引选择性差比如 status 只有几个值，索引树太大内存装不下，返回数据量大网络耗时，另外 EXPLAIN 只是估算，要真实数据用 EXPLAIN ANALYZE。
possible_keys 有值但 key 是 NULL，是什么情况？ 说明优化器认为全表扫描比走索引更划算。常见场景是表数据量很小，或者查询条件覆盖了大部分数据，走索引反而多一次回表的开销。另外索引字段类型不匹配也会导致索引失效，比如 varchar 字段拿 int 去比较。
Using index 和 Using index condition 有什么区别？ Using index 是覆盖索引，查询需要的字段全在索引里，直接从索引拿数据不用回表。Using index condition 是索引条件下推 ICP，MySQL 5.6 引入的优化，把部分 WHERE 条件下推到存储引擎层，在索引遍历时就过滤掉，减少回表次数。前者完全不回表，后者是少回表。
怎么判断一个索引的选择性好不好？ 用 SELECT COUNT(DISTINCT column) / COUNT(*) 算一下区分度。比如订单表的 order_id 区分度接近 1，状态字段可能只有 0.001，那给状态字段单独建索引基本没意义。一般区分度低于 0.1 的字段不适合单独建索引，但可以作为复合索引的一部分。

❌ 千万别说的话

  • “possible_keys 显示了索引，说明这条 SQL 走了索引。” ：真正走没走要看 key，它为 NULL 就是没走。
  • “type = index 和 type = ALL 差不多，都是慢查询。” ：index 是扫整棵索引树，ALL 是全表扫描，差着数量级。
  • “Using index 就是用上索引了。” ：它的准确含义是覆盖索引、不用回表；真正靠索引过滤减少回表的是 Using index condition。
  • “EXPLAIN 看到的行数就是实际扫描行数。” ：EXPLAIN 是优化器的估算值，要看真实执行情况得用 EXPLAIN ANALYZE。

33. MySQL 中 count(*)、count(1) 和 count(字段名) 有什么区别？

🎬 面试现场

面试官（口语化）：count()、count(1)、count(字段名) 这仨都是数行数的，它们到底差在哪儿？写 count() 和写 count(1) 性能上有区别吗？

⚠️ 翻车点

  • 只答「性能一样」，漏掉最要命的区别：count(字段名) 不统计 NULL 行，三个函数返回的数字可能压根不一样。
  • 说 count(1) 比 count() 快、或者 count() 比 count(1) 快，官方文档里明明白白写着没有任何性能差异。
  • 说 count(字段名) 一定比 count(*) 慢，其实字段是主键或有索引时差距很小。
  • 一上来就喊「大表 count 得靠缓存」，却不知道 MyISAM 本身有行数计数器、InnoDB 在 8.0.17 之后还支持并行扫描。

📝 回答重点

  • 最大区别在 NULL：count() 和 count(1) 数所有行，*count(字段) 只数该字段非 NULL 的行。
  • count(*) 和 count(1) 性能完全一样，官方原话是没有性能差异。
  • count(字段) 在字段没索引时要全表扫还要判 NULL，一般略慢；是主键或有索引时差距不大。
  • MyISAM 维护精确行数计数器，不带 WHERE 的 count(*) 直接返回。
  • InnoDB 有 MVCC 撑不了全局计数器，只能扫索引，而且优先挑最小索引来扫。

📈 拔高

8.0.17 起 InnoDB 支持并行扫描，大表 count 会快一截；再快就得上缓存或计数表，代价是维护缓存和库的一致性。

💡 主动加分的追问准备

面试官追问 你的答案
要统计一张 5000 万行的订单表，直接 count(*) 太慢，你怎么优化？ 先看业务对精确度的要求。允许一定误差就直接用 SHOW TABLE STATUS 拿估算值，毫秒级返回；要精确值又要快，就用缓存方案，在 Redis 里维护计数器，订单增删时同步更新、查询时直接读 Redis，同时处理好缓存和数据库的一致性，比如用事务消息或定期校对兜底。
count(1) 里的 1 能换成别的数字或字符串吗？比如 count(2)、count(‘abc’)？ 可以换，效果完全一样。count(1)、count(2)、count(‘abc’) 都等价于 count(*)，因为这个常量只是占位符，告诉 MySQL 对每一行都计数，实际不会真去读它的值，优化器会把它们统一处理成同一份执行计划。
count(*) 走的是主键索引还是二级索引？ InnoDB 会选占用空间最小的索引。如果表上有二级索引，优化器通常选二级索引而不是主键索引，因为二级索引叶子只存主键值，数据量比聚簇索引小很多，扫的数据页更少、I/O 开销更低。可以直接用 EXPLAIN 看 key 列用的是哪个索引。
为什么有的表 count(*) 瞬间返回，有的表要扫半天？ 差别在存储引擎。MyISAM 能维护精确的行数计数器，不带 WHERE 的 count(*) 直接查计数器，O(1)；InnoDB 因为 MVCC 下不同事务可见行数不同，维护不了全局计数器，只能扫索引，所以大表上会慢，8.0.17 之后靠并行扫描改善。

❌ 千万别说的话

  • “count(1) 比 count(*) 更快。” ：官方文档明确写着两者没有任何性能差异，常量只是占位符。
  • “count(字段名) 统计的是总行数。” ：它只统计字段非 NULL 的行，字段有 NULL 时结果会少。
  • “count(*) 在 MySQL 上就是 O(1)，跟表多大无关。” ：只有 MyISAM 在不带 WHERE 时近似成立，InnoDB 要扫索引。
  • “大表做 count 只能靠 Redis 缓存扛。” ：先看 MySQL 8.0.17 之后的并行扫描，再考虑缓存方案和一致性成本。

34. 从 MySQL 获取数据，是从磁盘读取的吗？（buffer pool）

🎬 面试现场

面试官（口语化）：我们查一条数据的时候，是每次都去磁盘读吗？buffer pool 到底是怎么工作的？为什么全表扫描不会把缓存冲垮？

⚠️ 翻车点

  • 说「每次查数据都要读磁盘」，完全没提 Buffer Pool 这一层缓存。
  • 把 Buffer Pool 说成缓存查询结果的，等于把 Query Cache 和 Buffer Pool 混为一谈，而前者 8.0 已经被删了。
  • 只说 InnoDB 用 LRU 淘汰，不知道它是改良版：链表分新生代/老年代两段，新页先进老年代，还得在老年代待够时间才准进新生代。
  • 解释不清「为什么跑个全表扫描不会把热点数据挤掉」，这正是改良版 LRU 存在的全部理由。

📝 回答重点

  • 不一定读磁盘：Buffer Pool 命中就直接从内存返回，没命中才把整页加载进来。
  • 最小单位是数据页，默认 16KB，查一行也会整页带入，靠的是空间局部性。
  • 改数据先改内存，改过的页叫脏页，等后台线程找时机刷盘。
  • 淘汰用改良版 LRU：分新生代和老年代，新页先进老年代，待够 1 秒再被访问才升上去。
  • 这么设计是为了扛住预读失效和全表扫描污染，一次性访问的页挤不掉热点。

📈 拔高

老年代默认占整个链表的 3/8，innodb_buffer_pool_size 一般按物理内存的 50%~80% 给，5.7 起可以在线调；Query Cache 缓的是结果集，8.0 已经删掉了。

💡 主动加分的追问准备

面试官追问 你的答案
怎么看 Buffer Pool 的命中率？多少算正常？ 可以用 SHOW ENGINE INNODB STATUS，里面有个 Buffer pool hit rate，显示最近一段时间的命中率；也可以查 information_schema.INNODB_BUFFER_POOL_STATS 自己算。正常业务场景下命中率应该在 99% 以上，低于 95% 就要考虑是不是 Buffer Pool 太小，或者有大量全表扫描在跑。
脏页什么时候刷到磁盘？刷盘期间还能读写吗？ 刷盘有几个时机：redo log 写满了必须刷、Buffer Pool 空间不够需要淘汰脏页时会先刷、后台线程定期刷、数据库正常关闭时会刷完所有脏页。刷盘期间正常读写不受影响，因为刷的是 Buffer Pool 里的页副本，读写走的还是内存；但如果刷盘压力太大，会影响整体 I/O 性能。
Buffer Pool 里除了数据页和索引页，还有什么？ 还有几块：一是 Change Buffer，用来缓存对二级索引的变更；二是自适应哈希索引，InnoDB 自己建的哈希索引来加速热点数据访问；还有锁信息、数据字典这些。不过数据页和索引页占大头，其他部分占比很小。
线上跑了个 mysqldump，缓存命中率掉了一大截，为什么？ mysqldump 是全表扫描，会把整张表的页都过一遍。传统 LRU 下这些页插链表头会把热点数据挤出去，InnoDB 的改良 LRU 让它们先进老年代，而且必须在老年代待够 1 秒再次访问才提升，所以一次性扫描的页不会挤掉真正的热点，扫描完慢慢淘汰就恢复了。

❌ 千万别说的话

  • “查一条数据就会去磁盘把那一行读上来。” ：实际是整页 16KB 一起加载进 Buffer Pool。
  • “MySQL 有 Query Cache，同样的 SQL 第二次直接返回结果。” ：Query Cache 在 8.0 已经被删除，现在只有 Buffer Pool。
  • “InnoDB 的 Buffer Pool 就是标准的 LRU。” ：它是改良版，分新生代和老年代，新页先到老年代、待够时间才进新生代。
  • “innodb_buffer_pool_size 调得越大越好，内存全给它。” ：太大可能挤占操作系统文件缓存甚至引发 swap，得结合命中率和其他内存开销来定。

35. MySQL 中 varchar 和 char 有什么区别？

🎬 面试现场

面试官（口语化）：说下 CHAR 和 VARCHAR 的区别呗，你平时建表怎么选的？

⚠️ 翻车点

把「定长 vs 变长」讲成唯一区别就答完了，面试官一追问「VARCHAR(50) 和 VARCHAR(200) 占用空间一样吗」「InnoDB 存 CHAR 一定定长吗」就直接翻车——这两点才是区分候选人的地方。

📝 回答重点

  • CHAR 是定长、不足补空格；VARCHAR 按实际长度存，额外花 1~2 字节记长度。
  • 选型惯例：定长短串用 CHAR，比如 MD5、国家代码，其余一律 VARCHAR。
  • VARCHAR(N) 的 N 是字符数不是字节数，受单行 65535 字节限制，utf8mb4 下大约到 16383。
  • N 会影响排序：sort_buffer 按最大长度估算行数，放不下就走双路排序多一次回表。
  • CHAR 读取会自动去掉尾部空格，要保留空格只能用 VARCHAR。

📈 拔高

变长字符集下 InnoDB 会把 CHAR 按实际字节数变长存，只有 latin1 这类单字节字符集才真正定长；频繁更新的短字段用 CHAR 反而少页分裂。

💡 主动加分的追问准备

面试官追问 你的答案
VARCHAR(50) 和 VARCHAR(200) 存同样的字符串，占用空间一样吗？ 磁盘占用一样（实际字符数 + 1~2 字节长度信息）。但定义长度影响内存分配，排序、JOIN 等操作按最大长度预分配，所以 VARCHAR(200) 比 VARCHAR(50) 多占内存，影响 sort_buffer 能放的行数，间接影响排序性能。
InnoDB 存 CHAR 一定是固定大小吗？ 不一定。变长字符集（utf8）下 InnoDB 会把 CHAR 按实际字节数变长存储，避免按最大字节数固定存储浪费空间；只有 latin1 这种单字节字符集 CHAR 才真正定长。
VARCHAR 长度超过多少会存到行外？ 看行格式。旧的 Compact/Redundant 格式下单字段超过 768 字节就把超出部分存到溢出页，行内保留 768 字节前缀加指针；现代默认的 Dynamic/Compressed 格式遵循「最长字段优先」原则，为保证一页至少容纳两行（整行不超过约 8000 字节），最长字段整块移出行外，行内只留 20 字节指针。

❌ 千万别说的话

  • “VARCHAR(50) 和 VARCHAR(200) 存储空间不一样，所以要用小的。” ：磁盘占用是按实际长度算的，差别在内存预分配和排序上。
  • “CHAR 完全没有用，直接全用 VARCHAR 就好。” ：MD5、固定国家代码、频繁更新的短字段用 CHAR 更合适。
  • “InnoDB 里 CHAR 永远定长，占满 N 个字符的空间。” ：变长字符集下 InnoDB 会优化成按实际字节数存储。

36. MySQL 中 DELETE、DROP 和 TRUNCATE 的区别是什么？

🎬 面试现场

面试官（口语化）：DELETE、DROP、TRUNCATE 这仨有啥区别？说下底层实现和什么时候用哪个。

⚠️ 翻车点

只答「DELETE 删行、DROP 删表、TRUNCATE 清空」就停，最容易被追问翻车的是「TRUNCATE 是 DDL 还是 DML、能不能回滚」和「DELETE 后表空间为什么不释放」。

📝 回答重点

  • DELETE 是 DML，逐行删、记 undo/redo/binlog，可 WHERE、可回滚。DROP 和 TRUNCATE 是 DDL，隐式提交、回滚无效。
  • DELETE 底层只打删除标记，空间留作复用、.ibd 不变小。要回收得 OPTIMIZE TABLE 或 ALTER TABLE … ENGINE=InnoDB 重建表。
  • TRUNCATE 等价 DROP + CREATE，不逐行处理也不记 undo，快得多，还会把 AUTO_INCREMENT 重置回起始值。
  • 速度 DROP > TRUNCATE > DELETE。删几百万行就分批 DELETE，每次 LIMIT 一万再 sleep 几秒，别拖长事务。
  • 误删恢复：DELETE 靠 binlog 或 flashback 工具能救回来，TRUNCATE 和 DROP 只能等备份。

📈 拔高

DROP 快是因为 file-per-table 开着时就是删 .ibd 文件，8.0 起表结构进数据字典、不再有 .frm。共享表空间 ibdata1 只增不减，关掉 innodb_file_per_table 后 DROP 也收不回空间。

💡 主动加分的追问准备

面试官追问 你的答案
为什么 DELETE 大表很慢，有什么办法加速？ 逐行处理，每行记 undo log、redo log 并维护 binlog。加速手段：分批删除每次 1 万行加 LIMIT、删完 sleep 几秒。清空表直接 TRUNCATE，保留少量数据就导出来、TRUNCATE 原表再导回去，或新建表 INSERT INTO SELECT 过去再 RENAME。
TRUNCATE 是 DDL 还是 DML？为什么？ DDL。底层实现是 DROP + CREATE，属于表结构操作，DDL 隐式提交事务、不记 undo log，所以不能回滚。MySQL 官方文档也明确 TRUNCATE 是 DDL，这与 Oracle 一致——有人以为它是 DML 能回滚，生产环境就翻车了。
DELETE 后表空间为什么不释放？怎么回收？ InnoDB 删除后只把数据页标记为可复用，不归还给文件系统，.ibd 文件大小不变。回收要重建表：ALTER TABLE xxx ENGINE=InnoDB 或 OPTIMIZE TABLE xxx，本质是数据导出重建再导回，会锁表或产生大量 IO。5.6 之后有 Online DDL 可在线重建减少影响，但仍建议低峰期做。

❌ 千万别说的话

  • “TRUNCATE 和 DELETE 一样，都能 ROLLBACK 回来。” ：TRUNCATE 是 DDL，会隐式提交，ROLLBACK 无效。
  • “DELETE 删完数据磁盘空间就释放了。” ：只是变成可复用空间，.ibd 文件大小不变。
  • “DROP TABLE 会连 binlog 一起记一条完整数据删除记录。” ：binlog 记的是逻辑操作，drop 记录的是 DDL 事件而不是逐行删除。

37. MySQL 中 DATETIME 和 TIMESTAMP 类型的区别是什么？

🎬 面试现场

面试官（口语化）：DATETIME 和 TIMESTAMP 选哪个？区别说清楚，尤其时区那块。

⚠️ 翻车点

只会说「TIMESTAMP 范围小、占用小，DATETIME 范围大」不够，最容易被追问的是「TIMESTAMP 跨时区主从同步会不会出问题」和「2038 年问题怎么迁移」。

📝 回答重点

  • TIMESTAMP 存的是 UTC 时间戳，写入按会话时区转、读出再转回。DATETIME 存字面值，写什么取什么，跟时区无关。
  • 范围 TIMESTAMP 到 2038 年就没了，DATETIME 能到 9999 年，长期数据我直接选 DATETIME。
  • 存储 TIMESTAMP 不带小数秒 4 字节、带 6 位小数秒 7 字节，DATETIME 对应 5 字节和 8 字节。
  • 跨时区主从同步最怕时区配置不一致，连接串里显式指定 serverTimezone，DATETIME 没这问题。
  • 2038 年之后的订单合同类数据用 DATETIME 或 BIGINT 存毫秒时间戳。

📈 拔高

主从两边会话时区不一致时，statement 格式 binlog 会让同一条 INSERT 落成不同的值，切 ROW 格式才稳。TIMESTAMP 真到 2038 想迁移，官方给的方向是改成 64 位存储，目前还没落地，所以新表该换就换。

💡 主动加分的追问准备

面试官追问 你的答案
线上表用了 TIMESTAMP 存创建时间，担心 2038 年问题想改成 DATETIME，怎么迁移风险最小？ 加一个新的 DATETIME 列，用 UPDATE 把老列值复制过去（注意时区转换，最好在同一时区下操作），改应用读写切到新列，验证没问题后删旧列或保留观察。表特别大时全表 UPDATE 锁很久，可分批更新，用 WHERE id BETWEEN 控制范围。
两个不同时区的数据库做主从同步，TIMESTAMP 的值会出问题吗？ 基于语句的复制可能有问题：TIMESTAMP 依赖会话时区，主从时区不同则同一条 INSERT 在两边执行结果不同。用基于行的复制就没事，因为复制的是实际 UTC 时间戳值。跨时区主从建议用 ROW 格式 binlog。
应用层用 BIGINT 存毫秒时间戳和用 DATETIME 比，哪个好？ BIGINT 跨语言跨平台最通用（Java、JavaScript、Python 都能直接处理），没有时区心智负担，但查库不直观。DATETIME 直观、SQL 里做时间范围查询方便（如 WHERE created_at > ‘2026-01-01’）。个人倾向 DATETIME，除非系统对跨平台互操作性要求特别高。

❌ 千万别说的话

  • “TIMESTAMP 存的是当前时间，DATETIME 存的是本地时间。” ：TIMESTAMP 存的是 UTC 时间戳，DATETIME 才是字面值。
  • “DATETIME 也会自动按会话时区转换。” ：DATETIME 与时区无关，存什么取什么。
  • “TIMESTAMP 和 DATETIME 存储空间一样，都是 8 字节。” ：分别是 4/7 与 5/8 字节（不含/含 6 位小数秒）。

38. MySQL 中 TEXT 类型最大可以存储多长的文本？

🎬 面试现场

面试官（口语化）：TEXT 能存多大？和 VARCHAR 怎么选，索引能不能加？

⚠️ 翻车点

答「TEXT 最大 65535 字节」只答了一半就收，容易漏掉：这是字节数不是字符数；TEXT 行内只存 20 字节指针、多一次 IO；以及不能建完整索引只能建前缀索引。
📝 回答重点

  • 上限是字节数不是字符数，UTF-8 一个汉字 3 字节，TEXT 约存 2 万个汉字。
  • 家族按容量排：TINYTEXT 255 字节、TEXT 64 KB、MEDIUMTEXT 16 MB、LONGTEXT 4 GB。
  • 选型先看长度可控吗，可控就 VARCHAR(1000) 读取快，正文富文本这种不可控的才上 TEXT。
  • 存储上 DYNAMIC 行格式下行内只放 20 字节指针、内容进溢出页，COMPACT 还在行内留前 768 字节。
  • DEFAULT 值 8.0.13 起只支持表达式写法 **DEFAULT (‘’)**，写 DEFAULT ‘’ 照样报错。
  • 加索引只能建前缀索引，中间匹配的 LIKE 走不了，全文检索上 FULLTEXT 或 Elasticsearch。

📈 拔高

只查 id 和 title 时别写 SELECT *，把溢出页上的 content 捞出来就是白挨一次 IO。VARCHAR 的 65535 字节是整行所有 VARCHAR 的总和上限，utf8mb4 下单列实际最多 16383 字符。

💡 主动加分的追问准备

面试官追问 你的答案
VARCHAR 最大能存多少？和 TEXT 怎么选？ VARCHAR 最大 65535 字节，这是整行所有 VARCHAR 字段的总和限制，单字段还要扣其他字段空间。原则是长度可控且不太长用 VARCHAR，长度不可控或可能很大用 TEXT。VARCHAR 存行内读取快，TEXT 存溢出页多一次 IO。
为什么 TEXT 不能做索引字段？ 不是完全不能，是不能建完整索引，只能建前缀索引。InnoDB 索引页默认 16KB，一个索引条目最大只能 767 字节（MySQL 5.6）或 3072 字节（5.7+ 开启 innodb_large_prefix），TEXT 可能几十 KB 甚至几 MB，塞不进索引条目，只能截取前缀。
线上大表的 TEXT 字段要加索引做模糊搜索，怎么处理？ 前缀索引对 LIKE ‘%xxx%’ 帮不上忙。两个方案：一是上 FULLTEXT 全文索引（MySQL 5.6+ 的 InnoDB 支持，但中文分词效果一般，需配合 ngram 分词器）。二是把搜索需求抽离到 Elasticsearch，MySQL 只负责存储、ES 负责搜索，这也是业界主流做法。

❌ 千万别说的话

  • “TEXT 最大能存 65535 个字。” ：是 65535 字节，UTF-8 中文下大约 2 万字。
  • “TEXT 和 VARCHAR 差不多，字段大一点用 TEXT 就行。” ：TEXT 行内只有 20 字节指针，读取多一次 IO，字段几百字以内用 VARCHAR 更优。
  • “TEXT 可以直接建普通索引。” ：必须指定前缀长度，否则直接报错。

39. MySQL 中 AUTO_INCREMENT 列达到最大值时会发生什么？

🎬 面试现场

面试官（口语化）：自增 ID 涨到上限会怎样？主键该怎么选型？

⚠️ 翻车点

两个坑：一是以为自增到上限会回绕或报错就没事——没定义主键时的 row_id 回绕是静默覆盖数据，比主键冲突严重得多；二是把「AUTO_INCREMENT 计数器会回收」说成常态。

📝 回答重点

  • 自增到上限后 INSERT 直接报 Duplicate entry，不会回绕到 0 或 1，就是卡着不动。
  • 上限按类型算，BIGINT UNSIGNED 约 1.8×10^19，int 主键日均百万插入 6 年就撑爆。
  • AUTO_INCREMENT 锁竞争靠 innodb_autoinc_lock_mode 缓解，8.0 默认 2，因为默认复制改成 ROW 了。
  • 没定义主键时 InnoDB 用 6 字节隐藏列 row_id，回绕静默覆盖这条只有社区经验、官方文档没写，所以生产必须显式主键。
  • 预防就三招：BIGINT UNSIGNED、监控 AUTO_INCREMENT 用率、快满时迁新表或换号段类分布式 ID。

📈 拔高

8.0 起自增计数器持久化到 redo log，但崩溃恢复时新值没刷盘仍可能复用，别把「不回收」说死。UUID 随机插入导致 B+ 树频繁页分裂，写入能差 10 倍以上，非要用就 UUID_TO_BIN 转成有序二进制。

💡 主动加分的追问准备

面试官追问 你的答案
删除数据后自增 ID 会回收吗？ 正常运行不会。删掉 id=100 下次插入还是 101。8.0 之前重启会从表里找最大 ID 再 +1，可能「回收」一些 ID。8.0 起计数器持久化到 redo log，不会回收。MyISAM 直接读表定义文件，也不回收。
自增 ID 在高并发下有什么问题？ 主要是性能瓶颈：自增 ID 必须串行分配，高并发插入时竞争 AUTO_INCREMENT 锁。MySQL 5.1.22 之后引入 innodb_autoinc_lock_mode，默认 1 连续模式（8.0 改为 2），批量插入预分配 ID 减少锁等待。设成 2 交错模式性能最好但 ID 不连续，binlog 用 statement 格式时主从可能不一致。
为什么不建议用 UUID 做主键？ 36 字符字符串存储空间大，更要命的是随机。InnoDB 用 B+ 树组织数据，主键有序插入都追加到末尾很快。UUID 随机插入导致频繁页分裂，写入性能可能差 10 倍以上。非要用可用有序 UUID，MySQL 8.0 提供 UUID_TO_BIN 转成有序二进制格式。

❌ 千万别说的话

  • “自增 ID 到上限会自动从 1 重新开始。” ：会卡在最大值并因主键冲突报 Duplicate entry，不会自动回绕。
  • “row_id 到上限最多报个错，影响不大。” ：它是静默覆盖老数据，数据丢了都没有报错。
  • “UUID 做主键只是占空间大一点。” ：随机插入导致的页分裂对写入性能影响更致命。

40. 在 MySQL 中存储金额数据，应该使用什么数据类型？

🎬 面试现场

面试官（口语化）：金额字段用啥类型存？Java 那边怎么配合？

⚠️ 翻车点

用 FLOAT/DOUBLE 存钱是硬伤；另一个常见翻车点是 Java 侧用 new BigDecimal(0.1) 或用 equals 比较 BigDecimal，直接把精度问题又带了回来。

📝 回答重点

  • 存金额只用 DECIMAL 或 BIGINT 存分，FLOAT/DOUBLE 有精度丢失，0.1+0.2 出来是 0.30000000000000004。
  • 普通金额 DECIMAL(18,2) 就够，Java 侧对应 BigDecimal，天然高精度，MyBatis 自动映射不用配。
  • BIGINT 存分把金额乘 100 变整数，long 运算快、固定 8 字节，但精确不到厘，费率换算场景不能用。
  • DECIMAL(M,D) 里 M 是总位数、D 是小数位，费率计算留足位数用 DECIMAL(18,4)，M 别乱设大。
  • Java 侧三个坑：new BigDecimal(0.1) 丢精度要写字符串构造器，除法必须指定精度和舍入模式，比较用 compareTo。

📈 拔高

DECIMAL 按需分配空间，每 9 位十进制数字占 4 字节，M 设大了纯浪费。BigDecimal 比 long 慢 5 到 10 倍，但除非每秒几十万笔的高频交易，这点差距在业务侧可以忽略。

💡 主动加分的追问准备

面试官追问 你的答案
为什么 0.1 + 0.2 不等于 0.3？ 计算机用二进制存浮点数，0.1 和 0.2 在二进制里是无限循环小数，存储时被截断（IEEE 754 规定截断方式），所以结果是 0.30000000000000004。DECIMAL 像字符串一样逐位存数字，没有这个问题。
BigDecimal 性能比 long 差多少？ 差 5 到 10 倍。long 是原始类型直接走 CPU 寄存器运算。BigDecimal 是对象，每次运算要创建新对象、做数组运算。但对大多数业务可忽略，除非是每秒几十万笔的高频交易。真到那个量级一般用 BIGINT 存分再加内存计算引擎优化。
数据库里存分，前端展示怎么处理？ 接口返回时除以 100 转成元，在 DTO 转换层统一处理，或用 Jackson 自定义序列化器。不要在数据库查询时做除法，一是可能有精度问题，二是走不了索引。也有团队直接返回分让前端处理，但要约定好字段语义。

❌ 千万别说的话

  • “用 FLOAT/DOUBLE 存金额，差一点点不影响业务。” ：交易量一大就是系统性财务偏差。
  • “BigDecimal 可以直接 new BigDecimal(0.1)。” ：精度在构造时就已经丢了，必须用字符串构造器。
  • “比较金额用 equals 就行。” ：equals 会比较精度，1.0 与 1.00 不相等，要用 compareTo。

41. MySQL 中 VARCHAR(100) 和 VARCHAR(10) 的区别是什么？

🎬 面试现场

面试官（口语化）：VARCHAR 括号里的数字到底影响什么？平时该定多长？

⚠️ 翻车点

答「存的字符数上限不同」就停会被追死——磁盘占用其实一样，真正的影响面是内存预分配、长度标识字节数、索引长度限制和DDL 锁表。

📝 回答重点

  • N 只是字符数上限，VARCHAR 变长，存 5 个字符就占 5 个字符，磁盘占用一样。
  • 存储 = 长度标识 + 数据，最大长度 ≤255 字节用 1 字节，超过用 2 字节，按字节不按字符。
  • 排序、分组、临时表在 MEMORY 引擎下按定义长度预分配内存，字段定太大容易被高估。
  • 8.0 默认 TempTable 对 VARCHAR 变长存储更省，排序会不会落盘得看配置。
  • 索引 key 上限 3072 字节，只适用 DYNAMIC/COMPRESSED 行格式，COMPACT/REDUNDANT 是 767。
  • 单行 65535 字节硬顶，utf8mb4 下 VARCHAR(16383) 到头，够用就行别全写 255。

📈 拔高

改长度先看会不会跨 255 字节档：同档内 5.6 起就能走 INPLACE 在线改，跨档或缩小要 COPY 重建表。老版本 MEMORY 排序按定义长度吃内存，8.0 的 TempTable 已经把变长这块补上了。

💡 主动加分的追问准备

面试官追问 你的答案
VARCHAR(255) 和 VARCHAR(256) 有什么实质区别？ 长度标识字节数不一样。单字节字符集下 VARCHAR(255) 最大 255 字节，1 字节标识够用，VARCHAR(256) 得用 2 字节，每行多占 1 字节。
为什么不建议直接把 VARCHAR 定义成最大值？ 主要影响内存：排序、分组、临时表按定义长度预分配，VARCHAR(65535) 只存几个字符太浪费。索引 key 限制在 3072 字节，可能只能建前缀索引。可读性上 VARCHAR(20) 才看得出是用户名。
修改 VARCHAR 长度会锁表吗？ 分情况。5.6 起，只扩大长度且长度标识字节数不变可走 INPLACE 不锁表，如 VARCHAR(50) 改 VARCHAR(100)。标识从 1 字节变 2 字节或缩小长度，就要 COPY 重建表。

❌ 千万别说的话

  • “VARCHAR(100) 比 VARCHAR(10) 占空间大。” ：磁盘占用按实际数据算，两者一样。
  • “VARCHAR 的长度只影响能存多少字符。” ：还会影响内存预分配、排序方式、长度标识字节数和索引是否超限。
  • “定长一点用 CHAR(255) 更省事。” ：定长存储会浪费空间，且 CHAR 读取时尾部空格会被自动去掉。

42. MySQL 在设计表（建表）时需要注意什么？

🎬 面试现场

面试官（口语化）：建表你会注意哪些点？说说你的建表规范。

⚠️ 翻车点

只答「选好类型、加索引」这种泛泛之谈不够；本题最容易被追问的是「为什么要用自增 ID 而不是业务 ID」「NULL 怎么处理」「大表加字段风险」这几个具体决策点。

📝 回答重点

  • 类型往小了选：int 够就别上 bigint，金额用 DECIMAL 别用 FLOAT，时间用 DATETIME。
  • 主键用自增 BIGINT 顺序追加不页分裂，UUID 随机插写放大明显，业务 ID 另建唯一索引。
  • 索引建在 where、join、order by 的常用字段，组合查询走复合索引和最左前缀。
  • NULL 能不用就不用，建表写 NOT NULL DEFAULT，x = null 查不到要用 is null。
  • 别用物理外键，一致性放应用层，冗余昵称省 join，维护策略提前定好。
  • 大表加字段上 pt-online-schema-change 或 gh-ost，字段和表都必须写注释。

💡 主动加分的追问准备

面试官追问 你的答案
为什么推荐用自增 ID 而不是业务 ID 做主键？ 自增 ID 顺序递增，每次 insert 都在 B+ 树最右边追加，不会页分裂，写入性能最好。业务 ID（手机号、身份证号）一是可能变更，二是没有顺序性，随机插入导致大量页分裂。业务 ID 可以单独建唯一索引，但主键仍用自增的好。
大表加字段有什么风险？怎么处理？ 5.6 之前 alter table 锁全表，几百万数据可能锁几小时，线上直接挂。5.6 之后有 Online DDL，但加字段仍有 metadata lock 阻塞查询。做法用 pt-online-schema-change 或 gh-ost：建新表、后台迁移、原子切换。
字段要不要加注释？有什么规范？ 必须加，没注释的表就是技术债。字段注释写清业务含义，枚举值列出每个值代表什么，表注释写清表干什么。看着不重要，等接手没注释的老系统就懂多痛苦。

❌ 千万别说的话

  • “严格遵循三范式，字段一个都不能冗余。” ：互联网业务普遍适度冗余以减少 join。
  • “字段可以随便加，ALTER TABLE 在高版本很快。” ：大表加字段仍有 metadata lock，5.6 之前更是锁全表。
  • “有业务含义的唯一 ID 就直接拿来做主键。” ：业务 ID 可能变更且无序，随机插入页分裂严重，应单独建唯一索引。

43. MySQL一张表最多可以有多少列？

🎬 面试现场

面试官（口语化）：一张表最多能建多少列？超了会怎样？

⚠️ 翻车点

只答「4096 列」会翻车：实际 InnoDB 只有 1017 列，且函数索引会创建隐藏虚拟列偷走配额——这一点最容易漏。

📝 回答重点

  • Server 层理论上限 4096 列，InnoDB 硬限 1017 列，是内部记录结构的限制，别按 4096 设计。
  • 行大小 65535 字节硬顶，变长字段行内仍占长度标记，几百个 VARCHAR 会撑爆。
  • 函数索引会建 VIRTUAL 隐藏列，占用用户列配额，SHOW CREATE TABLE 里看不到。
  • 三个隐藏列 DB_ROW_ID 6 字节、DB_TRX_ID 6 字节、DB_ROLL_PTR 7 字节不占配额。
  • 大字段 DYNAMIC 只存 20 字节指针，COMPACT 占 768 字节，行格式决定塞得下多少 TEXT。
  • 单表超 100 列就该拆表，低频属性收进一个 JSON 列。

📈 拔高

接近 1000 列时报 Row size too large，多半是新加的 VARCHAR 累积超 65535，跟列数本身关系不大。分区表列多了元数据膨胀，查 information_schema 会明显变慢。

💡 主动加分的追问准备

面试官追问 你的答案
如果我非要建一张接近 1000 列的表，有什么优化建议？ 先把行格式改 DYNAMIC，大字段存溢出页腾行内空间。用 TINYINT、SMALLINT 代替 INT 省字节，低频字段收进一个 JSON 列，最后考虑垂直拆成主表加扩展表。
函数索引会创建隐藏列，那普通索引呢？ 普通索引不创建隐藏列，直接引用原表的列。函数索引特殊在于索引的是表达式的计算结果，结果必须有地方存，所以 MySQL 会自动创建一个 VIRTUAL 类型的生成列，它确实存在并占用列配额。
65535 字节的行大小限制是针对磁盘存储还是内存？ 是 MySQL Server 层定义的逻辑限制，与磁盘还是内存无关，限制的是一行记录里所有列的「声明长度」之和。

❌ 千万别说的话

  • “MySQL 一张表最多 4096 列，照着这个上限设计就行。” ：InnoDB 实际只有 1017 列。
  • “函数索引不占列数，它只是个索引。” ：会创建隐藏虚拟列，真实占用用户列配额。
  • “TEXT 字段内容存到溢出页，所以完全不影响行大小限制。” ：行内仍要为每个字段留长度标记/指针位置，几百个字段仍会撑爆 65535。

44. MySQL 中 int(11) 的 11 表示什么？

🎬 面试现场

面试官（口语化）：我们表里到处写着 int(11)，这个 11 到底是啥意思？是不是只能存 11 位数？跟存储空间有关系吗？

⚠️ 翻车点

  • 把显示宽度当成长度限制，说 int(11) 只能存 11 位数字、超过就报错，这是最经典的误解。

  • 不知道 MySQL 8.0.17 起显示宽度和 ZEROFILL 都已标记废弃，还在给新项目写 int(11)。

📝 回答重点

  • int(11) 的 11 是显示宽度，只管输出补零，跟存储空间、数值范围没关系。

  • 选型看字节：TINYINT 1 字节、INT 4 字节、BIGINT 8 字节，够用就行。

📈 拔高

显示宽度当年给终端输出对齐用，客户端工具自己会格式化后就成了没人用的包袱。UNSIGNED 正数范围翻倍，但减法会溢出，开 NO_UNSIGNED_SUBTRACTION 才返回负数。

面试官追问 你的答案
主键用 INT 还是 BIGINT？什么时候必须上 BIGINT？ 大多数业务 INT UNSIGNED 的 42 亿够用。高频流水表、日志表每天几百万条，几年就撑爆，得用 BIGINT。Snowflake 这类 64 位分布式 ID 也必须 BIGINT。先算增长预期，主键溢出再改迁移成本极高。

45. 数据库的三大范式是什么？

🎬 面试现场

面试官（口语化）：建表的时候大家都说要符合三大范式，你能给我讲讲这三大范式分别是什么吗？实际项目里又为什么经常不严格遵守它？

⚠️ 翻车点

  • 只背「1NF 原子性、2NF 消除部分依赖、3NF 消除传递依赖」这十二个字，举不出每一条对应的具体反例。
  • 讲 2NF 时说不出它主要针对的是联合主键的场景，这是最容易被追问的地方。
  • 讲 3NF 时举的例子不成立：把「部门名称依赖部门ID」说成部分依赖，或者干脆不说清依赖箭头。
  • 只答范式定义，答不出「那实际项目为什么不严格遵守」——面试官真正想问的是范式与性能的取舍。
  • 忽略「JSON 字段算不算违反 1NF」这种看起来刁钻、实际高频的追问。

📝 回答重点

  • 1NF 字段原子不可拆，「北京市朝阳区xx路」要拆成省、市、区、详细地址。
  • 2NF 非主键字段完全依赖主键，主要针对联合主键，订单时间只依赖订单 ID 就别进明细表。
  • 3NF 非主键字段之间不能互相依赖，部门名称依赖部门 ID 就该拆去部门表。
  • 实际项目普遍反范式，订单表冗余 user_name 省掉 JOIN，代价是靠维护策略兜底。
  • 读多写少、要快照、分库分表、报表宽表这四类场景最适合冗余。

📈 拔高

再往上还有 BCNF，要求每个决定因素都是候选键，4NF 要消除多值依赖，实际开发很少走到那一层。冗余上线前得把维护策略定死，同步更新、异步同步还是当快照，选错了线上就对不上账。

💡 主动加分的追问准备

面试官追问 你的答案
什么情况下你会选择反范式设计？ 读多写少的场景会反范式，订单查询页每次 JOIN 用户名太慢，直接冗余一份。分库分表后跨库 JOIN 搞不定也得冗余。冗余字段要想清楚维护：同步更新、异步同步还是当快照不更新。
你们项目里有没有遇到过数据冗余导致不一致的问题？ 遇到过。商品表改名，订单里的商品名没同步，客服查单对不上。后来分两种：商品信息当下单快照就不同步，要最新数据的走 Canal 订阅 binlog 异步更新。关键是团队对哪些字段当快照、哪些要同步有共识。
1NF 说字段要原子不可分，那 JSON 字段算不算违反 1NF？ 严格来说算，JSON 里还能嵌套字段。但 5.7 起原生支持 JSON，还能对内部字段建虚拟列和索引，实用上已算可查询的原子单元。范式是指导原则不是死规矩，看业务要不要独立查询 JSON 内部。

❌ 千万别说的话

  • “2NF 就是要求所有字段都不能为空、不能重复。” ：2NF 说的是在 1NF 基础上非主键字段必须完全依赖主键、不能只依赖主键的一部分，比如订单明细表用「订单ID + 商品ID」做联合主键时，把只依赖订单ID 的「订单时间」放进来就违反了 2NF。
  • “3NF 只要求非主键字段依赖主键就行，字段之间有依赖没关系。” ：3NF 还要求非主键字段之间不能有依赖。员工表里存了部门ID 和部门名称，部门名称依赖的是部门ID 而不是员工ID，这就是传递依赖，应该把部门名称拆到部门表里。
  • “实际项目里千万别用反范式，一定要严格遵守范式。” ：读多写少、要快照、分库分表这些场景反范式是主流做法，关键是配套的维护策略。
  • “字段冗余了数据肯定不一致，所以冗余是绝对不能接受的。” ：冗余可以靠同步更新、异步同步或快照策略管控住，用不用要看业务收益。

46. 在 MySQL 中，你使用过哪些函数？

🎬 面试现场

面试官（口语化）：平时写 SQL，你常用哪些 MySQL 的函数？随便说几个你印象深的，再讲讲它们一般用在什么场景。

⚠️ 翻车点

  • 只背函数名列表，说不出每个函数对应的典型业务场景（比如 DATEDIFF 用来算留存率、GROUP_CONCAT 用来拼报表），面试官一问「用在哪儿」就卡住。
  • 把「对字段使用函数会导致索引失效」说成「函数不能写在 WHERE 里」。真正的原因是 DATE(create_time) 对每一行都要调用函数计算，优化器没法利用 B+ 树的有序性定位数据——改成范围条件就能走索引。

窗口函数是 8.0 那批演进的一员，同批还有 CTE 和降序索引，5.7 上这些语法都不存在。时间函数还有会话时区的坑，NOW() 给的是会话时区本地时间，跨区服务我用 UTC_TIMESTAMP() 对齐。

面试官追问 你的答案
COUNT(*)、COUNT(1) 和 COUNT(字段) 有什么区别？ COUNT(*) 和 COUNT(1) 在 InnoDB 里性能一样，优化器会自动选最小的索引来扫。COUNT(字段) 会跳过 NULL 值，只统计非空行数。如果字段上有索引且允许 NULL，COUNT(字段) 可能比 COUNT(*) 更快，因为实际扫描的数据量更小。
WHERE 和 HAVING 有什么区别？ WHERE 在分组前过滤原始行，HAVING 在分组后过滤聚合结果。比如查订单金额超过 1000 的用户，要写 GROUP BY user_id HAVING SUM(amount) > 1000。WHERE 里不能写聚合函数，HAVING 可以。执行顺序是 WHERE → GROUP BY → HAVING。
怎么实现 Oracle 的 NVL 函数功能？ 用 IFNULL 或 COALESCE。IFNULL(a, b) 只能两个参数，a 为 NULL 就返回 b。COALESCE(a, b, c, ...) 支持多个参数，返回第一个非 NULL 的值。Oracle 迁移到 MySQL 时 NVL 要统一换成 IFNULL。
GROUP_CONCAT 拼出来的结果不完整，怎么排查？ 先看是不是撞上了默认 1024 字节的长度限制，超长会被截断。确认后调大会话变量 group_concat_max_len。另外拼的字段里如果有分隔符，还要用 SEPARATOR 指定一个业务上不会出现的分隔符，避免和内容混在一起。

❌ 千万别说的话

  • “WHERE 里不能用函数，函数只能写在 SELECT 里。” ：可以写在 WHERE 里，但对字段用函数会让索引失效。DATE(create_time) = '...' 会全表扫描，改成时间范围条件就能走索引。
  • “GROUP_CONCAT 没有长度限制，随便拼。” ：默认有 1024 字节上限，超长会被截断，需要用 group_concat_max_len 调整。
  • “窗口函数是 MySQL 5.7 就有的特性。” ：窗口函数是 8.0 才引入的，5.7 上写不出 ROW_NUMBER() OVER (...)。
  • “MySQL 加了 JSON 类型就可以替代 MongoDB 了。” ：JSON 函数让 MySQL 能处理半结构化数据，但复杂查询性能不如 MongoDB，定位是存扩展字段这类场景。
  • “count 字段名和 count(*) 一样快。” ：COUNT(字段) 会跳过 NULL，只统计非空行数；COUNT(*) 和 COUNT(1) 在 InnoDB 里性能一样，区别不在这里。

48. 如何处理 MySQL 的主从同步延迟？

🎬 面试现场

面试官（口语化）：我们从库经常比主库慢好几秒，偶尔用户写完立刻查就查不到旧数据，这个延迟你怎么治？

⚠️ 翻车点

最容易被翻车的是拿 Seconds_Behind_Master 当真相来源——它算的是 relay log 最后一条事件时间戳和当前时间的差值，主库长时间没写入时它会是 0，但实际网络可能已经断了。

📝 回答重点

  • 延迟消不掉，只能缩短或在业务层绕开，写后读这类关键查询直接锁主库。
  • 治本靠链路：大事务拆小、从库开并行重放、硬件和慢查询跟上，哪环慢修哪环。
  • Seconds_Behind_Master 不可信，主库停写或断网它照样报 0，真实延迟用 pt-heartbeat 对时间戳。
  • 半同步能压住延迟上限，主库等从库确认才返回。8.0.26 起新插件名 rpl_semi_sync_source，旧名已弃用。
  • 监控看 SHOW REPLICA STATUS，8.0.26 前叫 SHOW SLAVE STATUS，两个名字都要认得。

📈 拔高

并行重放分三代：5.6 分库并发、5.7 LOGICAL_CLOCK、8.0 WriteSet，replica_parallel_workers 的线程数按压测定。半同步的 wait point 由 rpl_semi_sync_source_wait_point 控制，默认 AFTER_SYNC。

💡 主动加分的追问准备

面试官追问 你的答案
Seconds_Behind_Master 为 0 就说明没延迟吗？ 不一定。它为 0 只说明从库已把 relay log 里的事件都执行完，不代表主从完全同步。网络断了收不到新 binlog 时这个值也是 0。主库长时间没写入时也是 0。要准确监控得用 pt-heartbeat，主动写入时间戳算真实延迟。
大事务为什么会导致主从延迟？ binlog 提交后才写入。大事务主库跑 10 分钟，从库也得重放 10 分钟，这期间就落后了。后面的小事务还得排队，延迟被放大。所以批量更新拆成多次小提交。
级联复制是什么意思？ 就是从库再挂从库。主库只发给一级从库，一级再发二级，dump 线程压力小了。适合从库特别多的场景，比如每个机房一个一级、机房内再挂二级。延迟还会叠加，二级延迟 = 一级延迟 + 自身重放时间。

❌ 千万别说的话

  • “延迟是 MySQL 的 bug，把 Seconds_Behind_Master 调大一点就行了。”
  • “主从延迟只要不写大事务就完全不会发生。”

49. 如何实现数据库的不停服迁移？

🎬 面试现场

面试官（口语化）：我们要把自建库迁到云上，量不小，业务还不能停，你给我一个不停服的迁移方案。

⚠️ 翻车点

只说「用同步工具搬过去」会被追问穿——不停服迁移的核心难点是在线数据的插入和修改如何保持一致，以及出问题怎么回滚，这两点必须主动讲出来。

📝 回答重点

  • 数据量小直接代码搬，几十万条核对完就收。上量了才值得上双写加灰度的方案。
  • 六步走：新库先挂成旧库从库同步，业务双写带开关，低峰关同步开双写，抽样核对，1% 起灰度切读，稳定后再关双写。
  • 双写顺序是先写旧库再写新库，新库写失败靠同步补，两边不在一个事务，最终一致就够。
  • 每次写都要幂等，同一条数据可能被同步链路和双写各来一次，拿唯一键做 UPSERT 兜住。
  • 核对靠抽样：按 id % 100 抽主键、按最近时间窗抽增量，关键字段算 MD5 或 CRC32 对比，回滚开关随时能切回旧库。

📈 拔高

全量切换后旧库就落后了，所以双写要再跑一周才下线，回滚预案按双写、灰度、全量三阶段各留一手。异构迁移我用 flink-cdc，先全量历史再无缝接增量，MySQL 到 PG、ES 都能走。

💡 主动加分的追问准备

面试官追问 你的答案
双写的时候两边数据不一致怎么办？ 先定位哪个环节不一致。双写逻辑有 bug 就修掉，再用同步链路全量覆盖一遍。两边冲突就查幂等，用 UPSERT 或加唯一键。实在不行跑修复脚本，以旧库为准把差异补到新库。
几十亿条数据的大表怎么迁移？ 分批迁移，按时间或主键范围切批次、每批几百万条，用 pt-archiver 限速同步，避免压到线上业务。全量完再开增量，后面和小表流程一样。大表迁移周期长，可能跑几天甚至几周。

50. 什么是批量数据入库？相比单条插入有什么优势？

🎬 面试现场

面试官（口语化）：我们每天要往数仓塞几十万条记录，现在是一条条 insert 的，太慢了，批量入库到底快在哪？

⚠️ 翻车点

最容易被翻车的点是不提 rewriteBatchedStatements——用 JDBC 或 MyBatis 的 Batch 不加这个参数，性能可能比手动拼接 SQL 差一个量级（实测 1000 条 55663ms vs 2275ms）。

📝 回答重点

  • 批量入库就是多条攒一起一次交互插进去，快在两处：网络往返少了，SQL 解析、写日志这些固定开销也摊薄了。
  • JDBC 或 MyBatis 的 Batch 要开 rewriteBatchedStatements，驱动才把一批 insert 重写成多值语句。
  • 实测同一条链路，saveBatch 不加参数 59927ms，加上 rewrite 2589ms，差二十多倍。
  • 一批 500 到 5000 条比较稳，一次十万条会撞 max_allowed_packet，8.0 默认 64MB 直接报错，事务太大回滚也慢。
  • 拼接 SQL 也别贪大，单条语句太长同样撞包限制，拆成小批多次提交最稳。

📈 拔高

rewriteBatchedStatements 默认关着，官方理由是整批失败不好定位，5.7 及以前还牵扯查询缓存，实际项目我直接打开。批量自增主键用 getGeneratedKeys() 一次取回，拼接 SQL 用 LAST_INSERT_ID() 只拿得到第一条。

💡 主动加分的追问准备

面试官追问 你的答案
批量插入时怎么获取自增主键？ JDBC 的 getGeneratedKeys() 可以批量拿回来。MyBatis-Plus 的 saveBatch 默认不返回，需要配置 useGeneratedKeys=true，而且实体类的 ID 字段会被自动填充。注意拼接 SQL 那种方式用 SELECT LAST_INSERT_ID() 只能拿到第一条的 ID，后面的要自己算。
批量插入遇到主键冲突怎么处理？ 三种策略：INSERT IGNORE 遇到冲突直接跳过不报错。REPLACE INTO 遇到冲突先删后插相当于覆盖。ON DUPLICATE KEY UPDATE 遇到冲突执行更新逻辑。幂等重试场景用 IGNORE，全量同步用 REPLACE，增量更新用 ON DUPLICATE KEY。
rewriteBatchedStatements 对 UPDATE 和 DELETE 也有效吗？ 对 UPDATE 有效但效果不如 INSERT 明显：UPDATE 的 rewrite 不是拼成一条 SQL，而是把多条 UPDATE 打包成一个网络包发送以减少 RTT，DELETE 同理。不过批量 UPDATE 的优化空间本来就有限，真要大批量更新建议直接写一条带条件的 UPDATE 语句，比如 UPDATE table SET status=1 WHERE id IN (1,2,3,...)。

❌ 千万别说的话

  • “用 MyBatis-Plus 的 saveBatch 就行了，比手动拼 SQL 还快。”
  • “批量插入一次插得越多越省事，一次十万条没问题。”

51. 多线程并发同步数据时（数据库的数据同步到数仓中）需要注意什么问题？

🎬 面试现场

面试官（口语化）：我们要用多线程把 MySQL 的数据同步到数仓去，多个线程并发消费同一批 binlog 变更，你说说这中间会踩什么坑？

⚠️ 翻车点

最容易漏掉「同一行数据的变更必须有序」这一点——binlog 本身有严格顺序，多线程并发一打乱，同一行先 UPDATE A 再 UPDATE B 变成 B 先 A 后，最终数据就是错的。

📝 回答重点

  • 拿到这种题我先盯顺序：同一行的变更必须按 binlog 顺序走，乱了最终数据就是错的。
  • 分发按主键哈希路由到固定 Kafka 分区，一个分区只给一个消费线程，分片内天然有序。
  • 位点和数据写进同一个事务，先 INSERT ... ON DUPLICATE KEY UPDATE 批量 UPSERT，再更位点表，一起 COMMIT。
  • 写入端容易成瓶颈，我用 UPSERT 兜住重试幂等，再攒批提交，每 100 条或每秒一次。
  • 丢消息分三处查：生产端 acks=all、Broker 同步刷盘、消费端先处理再提交 offset。

📈 拔高

分片粒度按表或按主键选，单表量大才值得按主键拆。并发度别瞎加，Kafka 分区数就是上限，线程数超过它没意义。数仓侧 ClickHouse 有 ReplacingMergeTree 能兜底去重。

同步过程中源库做了 DDL（比如加字段）会怎样？ Canal 默认把 DDL 当特殊事件发出来，消费端自己处理：暂停消费、改数仓表结构、再恢复。Debezium 有 schema registry 能自动感知结构变化，但下游适配是另一回事。生产建议 DDL 走单独发布流程，和同步任务错开执行。

52. 什么是数据全量同步和增量同步？它们各有什么优缺点？

🎬 面试现场

面试官（口语化）：我们要把业务库的数据同步到数仓，全量同步和增量同步这两个方案各自的优缺点是什么？你会怎么选？

⚠️ 翻车点

  • 只答「增量效率高」，不说全量「逻辑简单、一致性有保障」这一面，面试官会觉得你只看了速度没看可靠性。
  • 说增量同步就是「按 update_time 拉」，却不说清它的两个坑：捕获不到物理删除、时间精度不够会漏数据。
  • 把「全量 + 增量组合」当成一个方案讲，却漏掉最关键的一步——全量完成后要记录 binlog 位点，否则增量接不上。
  • 说增量同步天然不会丢数据、不会重复。恰恰相反：实现复杂、变更追踪可能漏数据，而网络抖动和消费者重启又会导致重复消费，幂等性必须自己解决。

📝 回答重点

  • 全量同步是整张表重新复制一遍，逻辑简单、一致性有保障，代价是量大时慢、压源库。
  • 增量同步只搬上次之后变了的行，效率高，但实现复杂，漏数据和重复消费都得自己兜。
  • 我的套路是先全量打底再增量保鲜，全量开跑前先记 binlog 位点，全量完了从这个位点续。
  • 增量怎么发现变化有三条路：时间戳法会漏 DELETE，触发器法压源库，解析 binlog 是主流。
  • Canal 两个坑：位点默认存内存，重启就丢，binlog 格式必须 ROW，否则解析不出字段变更。

📈 拔高

时间戳法还有秒级精度的坑，同一秒内多次修改可能漏掉，认真做还得上 binlog 方案。生产常见 T+1 全量加准实时增量的混合模式，白天靠增量保时效，凌晨全量覆盖保一致。增量消息带上唯一 ID，目标端建去重表，重复消费也伤不到数据。

面试官追问 你的答案
如果增量同步过程中 Canal 挂了几个小时，重启后怎么保证数据不丢？ Canal 会记录消费到的 binlog 位点，重启后从上次位点续，前提是 binlog 没被清理，MySQL 默认保留 30 天（binlog_expire_logs_seconds=2592000）。挂太久位点被 purge，就先补一次全量再从最新位点续增量。生产建议把保留期调更长，并配 Canal 告警。
时间戳法增量同步怎么处理删除操作？ 时间戳法捕获不到物理删除。解法一是逻辑删除，加 is_deleted 字段，删除时置 1，update_time 也更新，增量就能捕获。解法二是换 binlog 方案，DELETE 同样写进去。非用时间戳法又必须物理删除，只能定期全量对比，删掉多出来的记录。
大表全量同步怎么避免对源库造成太大压力？ 几个手段组合用。分批次导出，每次 LIMIT 10 万条，中间 sleep 几秒摊开压力。用从库导出不走主库。选凌晨这种业务低峰期。pt-archiver 内置限流，能控制每秒扫描行数。MySQL 8.0 还能用 CLONE 插件物理拷贝数据文件，比逻辑导出快很多。

❌ 千万别说的话

  • “增量同步就是定时按 update_time 拉数据，没什么复杂度。” ：捕获不到删除、时间精度不够会漏数据，是两个硬伤。
  • “增量同步不会有重复数据，因为消息队列只投递一次。” ：网络抖动和消费者重启都会导致重复消费，幂等性必须自己在目标端解决。
  • “全量完成后直接开增量就行，不需要记位点。” ：不记 binlog 位点，全量期间产生的变更就接不上，数据会缺一段。
  • “增量同步实时性高，所以可以彻底替代全量。” ：全量在初始化、容灾恢复和定期校验时不可替代，实际项目里两者是配合关系。

53. 如何在 MySQL 中实现读写分离？

🎬 面试现场

面试官（口语化）：我们主库扛不住了，想做读写分离。你说说有哪几种实现方式？主从延迟这个坑怎么填？

⚠️ 翻车点

  • 只说「上个代理就行了」，漏掉代码层封装也是一条主流路线，两种方案的适用场景完全不同。
  • 只讲配置不讲主从延迟，刚写完主库立马读从库可能读到旧数据，这是读写分离必须点出来的大坑。
  • 忽略事务边界，把一个事务里的读操作路由到从库、写操作路由到主库，直接破坏事务一致性。
  • 方案讲完了却没提中间件本身的单点问题，生产上一个代理实例挂掉等于全站读写全断。

📝 回答重点

  • 两条实现路线：代码层封装自己写路由，中间件代理对应用透明，按团队情况挑。
  • 代码层常用 AbstractRoutingDataSource 配 AOP，按注解切数据源，灵活但多语言各写一套。
  • 中间件有 ProxySQL、ShardingSphere-Proxy、MySQL Router，切换不用改应用，代价是多一跳要运维。
  • 事务里的读写必须绑同一个连接全走主库，拆到主从两边一致性就破了。
  • 最大的坑是主从延迟：关键读加 hint 强制走主，写后短时间内的读也先走主库。

📈 拔高

半同步复制能缩小延迟窗口，但 ACK 只代表事件写进从库 relay log 并落盘，不代表已经回放，读旧数据它兜不死。中间件本身是单点，生产要么多实例加故障切换，要么用 ShardingSphere-JDBC 这种嵌在应用里的方案。

面试官追问 你的答案

54. 什么是 CDC（Change Data Capture）？常见的 CDC 工具有哪些？

🎬 面试现场

面试官（口语化）：CDC 是什么？常见有哪些工具，我们项目该选哪个？

⚠️ 翻车点

  • 把它解释成”定时轮询比对数据” —— 那只是三种实现里最差的一种，CDC 的主流做法是解析数据库日志。
  • 漏掉 binlog 格式必须是 ROW 这个硬前提 —— binlog_format 不是 ROW、binlog_row_image 不是 FULL，就拿不到变更前的数据。
  • 说工具时只报名词不特点，面试官要的是选型理由：多数据源选谁、国内 MySQL 场景选谁、流批一体选谁。
  • 说 CDC 能做到强一致，它本质是异步链路，有秒级延迟，关键链路决策不能依赖它。
  • 忽略位点（offset）管理 —— 工具重启要能从断点恢复，位点丢失等于数据丢失。

📝 回答重点

  • CDC 实时捕获增删改，主流做法是解析 binlog，不扫表也不侵入业务 SQL。
  • 工具选型：国内 MySQL 场景用 Canal，多数据源或深度绑 Kafka 选 Debezium，流批一体用 Flink CDC。
  • 三种实现要分清：解析数据库日志是主流，时间戳比对会漏 DELETE，触发器侵入大基本没人用。
  • 硬前提是 binlog_format=ROW，binlog_row_image 也要 FULL 才拿得到变更前的值。
  • 位点必须持久化，工具重启靠它从断点续，DDL 事件下游要能接得住。

📈 拔高

CDC 是异步链路，秒级延迟摆在那里，库存扣减、金额计算这类关键决策还得走源库。老版本 Debezium 全量快照会锁表，1.6 之后的增量快照分批读不锁，初始化大表要认准这个版本。

💡 主动加分的追问准备

面试官追问 你的答案
MySQL binlog 有几种格式？为什么 CDC 必须用 ROW 格式？ 三种：STATEMENT 记录原始 SQL 语句，MIXED 混合模式自动选择，ROW 记录每行数据的变化。CDC 必须用 ROW，因为只有 ROW 才能拿到变更前后的完整数据。STATEMENT 只记 SQL，下游没法精确还原数据状态，比如 UPDATE users SET balance = balance - 10 这种语句，不知道具体哪些行变了、变成什么值。
CDC 同步有延迟，怎么保证业务上的数据一致性？ 技术层面盯消费 lag，超阈值告警，写入端做幂等避免重复消费。业务层面关键决策别依赖 CDC 数据，库存扣减、金额计算必须走源库，数据分析、索引更新、缓存刷新这类容忍延迟的场景才适合它。
Canal 和 Kafka 怎么配合使用？ Canal Server 负责解析 binlog，Canal Client 或 Canal Adapter 负责把变更事件推到 Kafka。典型架构是 Canal Server 连 MySQL 解析 binlog，再通过 Canal Adapter 直接写 Kafka，下游消费者从 Kafka 拉消息处理。也可以直接输出到 RocketMQ、RabbitMQ，配置 destination 的 mq 参数即可。
源库数据量很大，CDC 初始化全量数据会不会锁表影响业务？ 老版本 Debezium 全量快照会对表加锁，影响业务写入。1.6 之后的增量快照分批读不锁表，读到哪记一个位点，期间的 binlog 变更也能正确处理。Flink CDC 2.0 也做了无锁快照，Canal 只做增量，全量得自己用 DataX 或 Sqoop 导。

  • “CDC 就是定时扫表比对 update_time。” ：那是延迟大、漏 DELETE、还压主库的落后做法，主流是解析数据库日志。
  • “binlog 用 STATEMENT 格式也能做 CDC。” ：只有 ROW 格式能拿到变更前后完整数据。
  • “CDC 是同步的，下游能立刻看到强一致的结果。” ：它是异步链路，有秒级延迟，关键链路要走源库。
  • “工具挂了直接重新从头跑就行。” ：必须靠位点从断点恢复，否则会丢数据或重复消费。

55. 什么是 MySQL 的主从同步机制？它是如何实现的？

🎬 面试现场

面试官（口语化）：MySQL 主从同步到底怎么跑起来的？主库挂了怎么办？

⚠️ 翻车点

只说「binlog 复制」不够，一定要能讲出三个线程的分工和半同步的两种模式；主从延迟的应急手段也常被追问。

📝 回答重点

  • 核心是 binlog 复制：主库把写操作记进二进制日志，从库拉过来重放一遍。
  • 三个线程分工：主库 dump 线程推送，从库 I/O 线程 拉进 relay log，从库 SQL 线程 回放。
  • MySQL 默认异步复制，写完 binlog 就返回，半同步至少等一个从库 ACK，是折中。
  • 并行回放一路演进：5.6 按库并行，5.7 用 LOGICAL_CLOCK 分组，8.0 用 WriteSet 按行哈希判冲突。
  • 查延迟看 Seconds_Behind_Master，它只是时间戳差、瞬时值会跳变，8.0.22 之后叫 Seconds_Behind_Source，更准靠 pt-heartbeat。

📈 拔高

半同步里 AFTER_COMMIT 是主库先提交再等 ACK，客户端响应也要等这个 ACK，真实风险是已提交的事务可能不在任何从库上，主库一挂切换就丢。AFTER_SYNC 把等待点挪到引擎提交前，更稳。完全同步复制在 MySQL 文档里只是概念对比，没有内建实现。

💡 主动加分的追问准备

面试官追问 你的答案
binlog 有哪几种格式，区别是什么？ statement 记 SQL 原文，日志小但可能因函数结果不同导致主从不一致（如 NOW()）。row 记每行变更前后值，日志大但绝对一致。mixed 由 MySQL 自己判断，一般用 statement，遇到不安全语句自动切 row，生产推荐 row。
主从延迟太大怎么办，有应急手段吗？ 先定位原因：从库配置差、大事务还是并行度不够。应急手段：强制读主库，用 sql_slave_skip_counter 跳过出错 SQL，调大 slave_parallel_workers，8.0 换 WriteSet 模式。长期升级从库配置、拆分大事务、做好读写分离负载均衡。
半同步为什么比全同步更实用？ 3 个从库配置等 1 个确认，只要有一个从库说收到了主库就返回，只有最快的那个从库和主库同时挂掉才会丢数据，兼顾了性能和可靠性。

❌ 千万别说的话

  • “主从延迟看 Seconds_Behind_Master 就行”（它受网络抖动影响，pt-heartbeat 更准）
  • “半同步就是等所有从库确认”（那是同步复制，半同步只要至少 N 个）

56. 什么是分库分表？分库分表有哪些类型（或策略）？

🎬 面试现场

面试官（口语化）：单库单表撑不住我们的业务了，你说说分库分表到底是分什么，有哪几种分法？

⚠️ 翻车点

只答「水平分片、垂直分片」这种两级分类，而分不清「分表」和「分库」是两件事；或者讲不出分片键选型差异——哈希取模扩容要全量迁移，范围分片会有热点，一致性哈希才能只迁相邻节点。

📝 回答重点

  • 分库分表就是单机扛不住加机器、单表太大拆小表，分表解决查询慢，分库摊薄单机资源瓶颈。
  • 水平分表按行切，用户 ID 取模分成 user_0 到 user_2，结构相同数据不同；垂直分表拆冷热列，宽表瘦身。
  • 水平分库把数据按规则铺到多个实例，垂直分库按业务拆 user_db、order_db、product_db，微服务基本都这么干。
  • 拆不拆有硬指标：MySQL 默认最大连接数才 151，阿里手册建议单表 500 万行或 2GB 就分库分表，2000 万行只是经验推算。
  • 分片键三策略：哈希取模分布均匀但扩容要全量重分，范围分片扩容方便但最新库易热点，一致性哈希只迁约 1/N 数据，ShardingSphere 没内置得自己实现。
  • 代价有跨库 JOIN、分布式事务和主键冲突，中间件自带 XA/BASE 事务和 Snowflake 生成器，Seata 只是 BASE 的一种实现。

📈 拔高

ShardingSphere 走 CLASS_BASED 自定义分片算法能补一致性哈希的缺口，但要自己写实现类并处理虚拟节点。跨库 JOIN 现在有 Federation 引擎做实验性支持，生产还是冗余字段加应用层组装更稳。

💡 主动加分的追问准备

面试官追问 你的答案
分片键选得不好会出什么问题？怎么补救？ 最常见是数据倾斜，某些分片成了热点。补救：加二级分片，大商家数据再按订单 ID 取模分一次，或引入虚拟节点摊平分布。直接改分片键成本最高，要全量迁移。
不停机扩容怎么做？ 双写加灰度切换：搭好新分片→新老库双写→用 Canal 监听 binlog 增量同步老数据→数据校验→灰度切读流量→观察后全切写流量→下掉双写逻辑。整个过程可能好几周，期间要盯数据一致性。
分库分表后怎么做跨分片分页查询？ 最笨的是每个分片都查 limit 再内存合并，16 个分片能拉 16 万条排序。优化：产品上限制只看前 1000 条，或用游标记住上一页最后一条值做 keyset 分页，或走 ES 分页后回数据库主键回查。

❌ 千万别说的话

  • “分库分表就是分库或者分表，二选一”：水平/垂直两个维度都可以同时作用在库和表上。
  • “哈希取模扩容也很方便，加个库就行”：扩容要重新分配大量数据，这是它最大的坑。
  • “分库分表之后 SQL 不用改，中间件会透明处理一切”：跨库 JOIN、跨分片聚合、分布式事务都得业务侧或中间件显式处理。

57. 为什么在 MySQL 中不推荐使用多表 JOIN？

🎬 面试现场

面试官（口语化）：我们代码里好多 SQL 都是三个表以上 JOIN，为什么你们不让这么写？

⚠️ 翻车点

被追着问「那 JOIN 到底是不是一定慢」时容易露怯——2 个表、索引合理、数据量可控的 JOIN 没问题，不推荐的是超过 3 个表的大 JOIN。

📝 回答重点

  • 数据库是系统瓶颈，把复杂关联交给它会吃满 CPU 内存，阿里手册直接写「超过三个表禁止 JOIN」。
  • 大表 JOIN 慢在执行计划一旦选错就全表扫描，几百万行的表两两组合，一个慢查询就能把库打挂。
  • 我一般拆成多次单表查询在应用层关联：单表好加索引、执行计划稳定，应用服务器加机器就能扛。
  • 执行原理是选驱动表逐行拿关联字段去被驱动表查，被驱动表没索引时 10 万乘 100 万次比较直接爆炸。
  • 所以死守两条：小表驱动大表，被驱动表关联字段必须有索引，优化器选错用 STRAIGHT_JOIN 强制。
  • 分库分表后跨库 JOIN 中间件只有 Federation 实验性支持，生产还是冗余字段、全局表、应用层组装。

📈 拔高

被驱动表没索引时走 Block Nested-Loop Join，驱动表塞进 256KB 的 join_buffer 再批量比，8.0.18 之后的 Hash Join 对无索引等值 JOIN 有提升。真要压榨 JOIN 上限，先 WHERE 过滤缩小范围，报表类 SQL 挪到业务低峰期跑。

💡 主动加分的追问准备

面试官追问 你的答案
如果业务上必须用多表 JOIN，有什么优化手段？ 检查关联字段都有索引用 EXPLAIN 看有无全表扫描，用 STRAIGHT_JOIN 强制小表驱动大表，用 WHERE 先过滤再 JOIN 缩小范围。定期报表放业务低峰期，实在不行做宽表提前算好结果用空间换时间。
应用层关联会不会增加网络开销？查 3 次肯定比查 1 次慢吧？ 网络开销确实增加，但总耗时不一定更长：3 次走索引的单表查询每次几毫秒，加起来十几毫秒，一次执行计划不好的大 JOIN 可能几百毫秒甚至几秒。单表结果还能缓存，JOIN 很难缓存，整体吞吐反而更高。
分库分表之后跨库 JOIN 怎么处理？ 中间件 Federation 引擎只有实验性支持，生产别指望。主流方案是把常关联字段冗余到主表，或在每个分库放一份全局字典表，或分别查库后在内存 merge，或同步到 ES、数仓做聚合。

❌ 千万别说的话

  • “JOIN 一定比多次单表查询慢”：索引合理、数据量可控时 2 表 JOIN 完全没问题。
  • “不用管驱动表，MySQL 自己会选最优的”：优化器确实会尝试选小表驱动大表，但会选错，STRAIGHT_JOIN 就是为此准备的。
  • “分库分表后 JOIN 中间件能帮我跨库做”：跨库 JOIN 基本做不了，要么冗余要么应用层组装。

58. MySQL 中 INNER JOIN、LEFT JOIN 和 RIGHT JOIN 的区别是什么？

🎬 面试现场

面试官（口语化）：INNER、LEFT、RIGHT 这几个 JOIN 到底差在哪儿，LEFT JOIN 的过滤条件放 ON 和放 WHERE 有区别吗？

⚠️ 翻车点

LEFT JOIN 时把右表过滤条件写进 WHERE，会把左表没匹配的行全部过滤掉——这是最常被追问翻车的点。

📝 回答重点

  • 核心看不匹配的行怎么处理：INNER JOIN 只留两边都匹配的，LEFT JOIN 留左表全部、右表补 NULL，RIGHT JOIN 反过来很少用。
  • RIGHT JOIN 能用的场合，换表位置写 LEFT JOIN 都能做到，主表放左边读着顺，阿里手册也建议统一用 LEFT JOIN。
  • LEFT JOIN 的右表过滤条件放 ON 还是 WHERE 是关键：放 ON 丢不了左表行，放 WHERE 会把补 NULL 的行一起过滤掉。
  • 找「左有右无」用 LEFT JOIN 加 WHERE 右表主键 IS NULL，反向用 IS NOT NULL，INNER JOIN 下 ON 和 WHERE 等价。
  • JOIN 顺序优化器可能选错，拿不准就用 STRAIGHT_JOIN 强制小表驱动大表。
  • FULL OUTER JOIN MySQL 不支持，LEFT JOIN 加 RIGHT JOIN 再 UNION 模拟，要保重复换 UNION ALL。

📈 拔高

CROSS JOIN 笛卡尔积不需要 ON，100 行乘 200 行直接两万行，生成 SKU 组合这类场景才用。ON 是关联规则、WHERE 是结果过滤，这个语义差吃透了，OLTP 里一堆隐性丢行的坑都能自己排查。

💡 主动加分的追问准备

面试官追问 你的答案
LEFT JOIN 和 LEFT OUTER JOIN 有什么区别？ 没区别，OUTER 可省略。LEFT JOIN 是 LEFT OUTER JOIN 的简写，INNER JOIN 是 JOIN 的简写，SQL 标准里 OUTER 是可选的，MySQL、PostgreSQL、Oracle 都支持省略。
怎么用 LEFT JOIN 实现 INNER JOIN 的效果？ 在 WHERE 里加右表字段 IS NOT NULL 的条件，比如 WHERE o.id IS NOT NULL，把填 NULL 的行过滤掉，效果等同 INNER JOIN。反过来想找左表有右表没有的，就用 WHERE o.id IS NULL。
MySQL 支持 FULL OUTER JOIN 吗？怎么实现？ 不直接支持，要用 UNION 模拟：先 LEFT JOIN 拿左表全部，再 RIGHT JOIN 拿右表全部，UNION 合并去重。想保留重复就用 UNION ALL 再自己加去重逻辑。

❌ 千万别说的话

  • “LEFT JOIN 就是在 WHERE 里加个条件过滤一下”：放错位置会把左表数据整个丢掉。
  • “RIGHT JOIN 和 LEFT JOIN 结果不一样”：只是写法方向不同，换个表位置就能互相转换。
  • “MySQL 支持 FULL OUTER JOIN”：要用 UNION 模拟。

59. 什么是数据库的视图？

🎬 面试现场

面试官（口语化）：视图到底是个什么东西？用视图查数据会不会变慢，能建索引吗？

⚠️ 翻车点

以为视图能「让查询变快」或「能像表一样建索引」——视图不存数据，MySQL 的视图也不能直接建索引。

📝 回答重点

  • 视图是虚拟表，不存数据，本质是起了名字的 SELECT，查它就是现场跑定义里的 SQL。
  • 最大用途三个：封装复杂查询，只暴露部分字段控权限，底层表重构时改视图定义上层不动。
  • 优化器默认做视图合并，把外层条件合进定义里一条 SQL 跑，执行计划跟手写一样。
  • 聚合、DISTINCT、GROUP BY、UNION 这类合并不了，先物化成临时表再查，慢一个量级。
  • MySQL 视图不能建索引，不存数据索引没地方放，底层表的索引查视图时照样能用。
  • 可更新视图限单表、无聚合无子查询，实际项目里当只读用，要存结果用物化视图。

📈 拔高

视图嵌套别超两层，套多了展开的 SQL 又长又难优化。要真正提速得上物化视图，Oracle 和 PostgreSQL 原生支持，MySQL 只能触发器或定时任务自己同步。

💡 主动加分的追问准备

面试官追问 你的答案
视图能建索引吗？ MySQL 的视图不能直接建索引，视图不存数据，索引没地方放。底层表的索引查视图时能用上。Oracle 的物化视图真存数据可以建索引，MySQL 要类似效果得自己维护汇总表。
用视图会影响查询性能吗？ 视图本身不快不慢，看底层 SQL 的效率。能合并时和手写一样，有聚合、DISTINCT 没法合并就先物化成临时表，可能更慢。多层嵌套展开后的 SQL 又长又难优化。
什么情况下你会用视图？ 三种：复杂报表查询，把 JOIN 和子查询封装成视图直接 SELECT。权限控制，视图只暴露允许的列再授权。兼容老接口，底层表重构时建同名视图过渡。

❌ 千万别说的话

  • “用视图可以提升查询性能”：视图每次现算，只会更慢或持平。
  • “MySQL 的视图可以像表一样建索引”：不存数据就没地方放索引。
  • “视图和表一样，可以随便增删改”：多表 JOIN、含聚合或 DISTINCT 的视图不能更新。

60. 为什么不推荐在 MySQL 中直接存储图片、音频、视频等大容量内容？

🎬 面试现场

面试官（口语化）：为什么大家都说图片别往 MySQL 里塞？放进去到底会出什么事？

⚠️ 翻车点

只说「占空间、影响性能」这种泛泛的话，讲不出 Buffer Pool 污染、binlog 膨胀、备份膨胀这三条具体的因果链。

📝 回答重点

  • 图片视频放对象存储，数据库只存 URL 或文件路径，几十个字节搞定。
  • Buffer Pool 默认才 128MB，生产上按物理内存 50%-70% 调优，几 MB 的 BLOB 一读就把热点页全挤出去。
  • ROW 模式下图片原样进 binlog，10 万条 200KB 头像一天灌出 20GB，主从延迟持续累积。
  • mysqldump 把 BLOB 转成十六进制字符串，体积翻倍，10GB 图片变 20GB，跑一整晚都跑不完。
  • DYNAMIC 行格式大 BLOB 只在页内留 20 字节指针，数据全在溢出页，读一张 3MB 图要跨近 200 个页。
  • 对象存储自带 CDN 加速、签名 URL 防盗链，按 GB 计费，带宽不和业务查询抢连接。

📈 拔高

老系统迁移分三步：新数据写 URL、批量回填并清空历史 BLOB、最后用 pt-online-schema-change 删列，全程不停服。图片和业务数据的事务一致用本地消息表做最终一致就够，上 TCC 代价太大。

💡 主动加分的追问准备

面试官追问 你的答案
业务上确实需要保证图片和业务数据的事务一致性，怎么办？ 用本地消息表做最终一致：先传对象存储拿 URL，再在一个事务里同时写业务表和文件记录表。回滚留下的孤儿文件让定时任务扫掉。强一致可用 TCC，代价大，一般没必要。
老系统已经把图片存在 MySQL 里了，怎么平滑迁出去？ 三步走：新数据直接写对象存储，老代码兼容，读时判断是 URL 还是 BLOB。后台批量迁历史数据，每批迁完更新 URL 字段并清空 BLOB。全清完后用 pt-online-schema-change 删列。迁移控速，别把 IO 打满。
对象存储挂了怎么办，URL 全 404 业务不也崩了？ 选大厂对象存储，阿里云 OSS 承诺 99.995% 可用性，比自建 MySQL 高可用还靠谱。兜底开跨区域复制，主备 bucket 异地部署，DNS 健康检查自动切换。自建用 MinIO 多节点加纠删码，单节点挂了数据不丢。

❌ 千万别说的话

  • “数据库存图片只是慢一点而已”：会撑爆 Buffer Pool、撑爆 binlog、拖垮备份恢复。
  • “存 BLOB 还能省一次网络请求”：真按 URL 存时读文件走的是对象存储/CDN，数据库只回几十字节。
  • “MySQL 存大文件性能也可以优化”：BLOB 溢出页机制决定的，随机 IO 成倍增加是结构性问题。

61. 相比于 Oracle，MySQL 的优势有哪些？

🎬 面试现场

面试官（口语化）：Oracle 和 MySQL 你怎么选？MySQL 凭什么能打得过 Oracle？

⚠️ 翻车点

一味吹 MySQL 而说不出 Oracle 的强项（PL/SQL、物化视图、闪回查询、位图索引、RAC），会被追问「那 Oracle 强在哪、什么场景必须用 Oracle」。

📝 回答重点

  • 最直接两条优势：免费开源、轻量易搭，解压加几行命令就能跑起来。

面试官追问 你的答案

62. MySQL 中 EXISTS 和 IN 的区别是什么？

🎬 面试现场

面试官（口语化）：EXISTS 和 IN 到底有什么区别，写哪个更好？NOT IN 我用出过一次诡异结果，是什么坑？

⚠️ 翻车点

NOT IN 遇到子查询里有 NULL 会直接返回空结果——这是隐藏的 NULL 陷阱，也是这一题最容易翻车的地方。

📝 回答重点

  • EXISTS 是逐行去子查询探测，找到一条就停；IN 是先物化子查询结果，再拿外层去匹配。
  • 外表小子表大用 EXISTS，外表大子表小用 IN，量级接近时交给优化器。
  • 5.6 之后优化器会把 IN 改写成半连接，很多场景两种写法执行计划一样。
  • NOT IN 撞上子查询里的 NULL 会直接返回空结果，这是三值逻辑的坑。
  • 子查询可能有 NULL 就换 NOT EXISTS，或者在子查询里加 IS NOT NULL 过滤。

📈 拔高

看执行计划认关键词：SUBQUERY 是独立子查询被物化，DEPENDENT SUBQUERY 是关联子查询，MATERIALIZED 表示结果落进了临时表。

💡 主动加分的追问准备

面试官追问 你的答案
线上有个慢查询用了 IN 子查询，子查询返回 50 万条数据，怎么优化？ 核心问题是结果集太大。方向：改成 EXISTS 让外表驱动、每次只探测一条用子表索引；业务允许时把子查询结果按时间范围拆成多次小查询；改成 JOIN，很多场景 JOIN 比 IN 子查询性能更好、优化器处理 JOIN 更成熟；子查询结果相对固定时可提前算好放临时表或 Redis。
EXISTS 里面写 SELECT 1 和 SELECT * 有区别吗？ 执行层面没区别，EXISTS 只关心子查询有没有返回行，压根不看返回什么内容，写什么都一样，优化器都会忽略。但可读性上写 SELECT 1 更能表达「我只是探测存在性」的意图。
什么场景下 IN 比 EXISTS 快？ 子查询结果集很小的时候。比如只返回 10 个 ID，IN 放进内存哈希表，外层 100 万行每行做一次 O(1) 哈希查找；换成 EXISTS 就是 100 万次索引探测，单次虽快但累加起来开销大。另外静态列表场景如 WHERE status IN (1,2,3) 直接用 IN 就好。

❌ 千万别说的话

  • “NOT IN 和 NOT EXISTS 随便选”：子查询里有 NULL 时 NOT IN 直接返回空结果。
  • “EXISTS 一定比 IN 快”：子查询结果集很小时 IN 反而更快。
  • “写 EXISTS 就要写 SELECT * 才有意义”：EXISTS 只看有没有返回行，写什么都一样。

63. 什么是数据库的逻辑删除？数据库的物理删除和逻辑删除有什么区别？

🎬 面试现场

面试官（口语化）：你们删数据是直接 DELETE 还是打个标记？如果打了标记，用户反复报名同一活动，唯一索引会不会炸？

⚠️ 翻车点

逻辑删除撞唯一索引这个问题答不上来——只加 is_deleted 到唯一索引里，用户反复横跳第三次操作照样冲突。

📝 回答重点

  • 逻辑删除是打标记（is_deleted），物理删除是 DELETE 真删，数据彻底没了。
  • 互联网业务多用逻辑删除，数据能恢复也能做审计，代价是表变大、查询要多带条件。
  • 唯一索引会炸：把 is_deleted 塞进唯一键只有 0 和 1 两个值，反复横跳第三次照样冲突。
  • 解法一：换成 deleted_at 时间戳，删除时写当前时间，每次都不重复。
  • 解法二：用主键值当删除标记，删除时写入本行 ID，天然唯一。
  • 解法三：复用同一条记录来回改状态，另建流水表留痕。

📈 拔高

别忘了把 is_deleted 放进联合索引最前面，否则每个查询都要多过滤一轮；MyBatis-Plus 的 @TableLogic 能自动补条件，但自己写的原生 SQL 还是得手写。

💡 主动加分的追问准备

面试官追问 你的答案
逻辑删除的数据越来越多，查询变慢了怎么办？ 几个方向：is_deleted 字段要加进联合索引里，让走索引的查询直接过滤掉已删除数据；定期归档，把删除时间超过一定天数的数据迁到历史表，主表只保留活跃数据；用分区表，按时间或状态分区，查询时直接跳过历史分区。
用 ORM 框架怎么保证每个查询都自动带上 is_deleted 条件？ 主流框架都有全局过滤器：MyBatis-Plus 有 @TableLogic 注解，配置后框架自动在查询时加 AND is_deleted = 0，删除操作也会自动变成 UPDATE；JPA 可以用 @Where 注解或 Hibernate Filter。要注意原生 SQL 不会自动加，写原生 SQL 得自己记着。
逻辑删除的数据还要不要建索引？ 要，但要建得聪明：最好把 is_deleted 放在联合索引前面，比如 (is_deleted, create_time)，查未删除数据时能快速跳过已删除的。如果表里 90% 都是已删除数据，可以考虑条件索引只给 is_deleted = 0 建；PostgreSQL 原生支持条件索引，MySQL 可以用虚拟列变通实现。
deleted_at 方案同一秒内删除又恢复又删除怎么办？ 时间戳精度要够高，用毫秒或微秒级别的 bigint 而不是秒级 datetime。另外同一秒内反复操作这种极端场景，业务层也应该做防抖，不让用户疯狂点击。实在不放心可以在 deleted_at 里存「时间戳 + 随机数」或直接用 UUID，但一般没必要搞这么复杂。

❌ 千万别说的话

  • “逻辑删除就是加个 is_deleted 字段完事了”：唯一索引冲突、查询漏过滤都是真坑。
  • “把 is_deleted 加进唯一索引就解决了”：反复横跳时它只有 0 和 1 两个值，照样冲突。
  • “逻辑删除不占空间”：数据还在，表只会越来越大。

64. 什么是数据库的逻辑外键？数据库的物理外键和逻辑外键各有什么优缺点？

🎬 面试现场

面试官（口语化）：你们建外键约束吗？为什么大厂都说不许用外键？

⚠️ 翻车点

只答「外键慢」而说不出具体慢在哪（级联更新爆炸、每次写都多一次检查、锁范围变大、死锁概率上升、分库分表建不了），也答不出逻辑外键怎么在应用层做校验。

📝 回答重点

  • 逻辑外键就是库里不建 FOREIGN KEY，靠应用代码校验关联数据存在性。
  • 物理外键由数据库强制检查，一致性有保障但慢：每次写多一次检查，级联更新能把库拖死。
  • 锁范围也会变大，关联表越多死锁概率越高；分库分表之后根本建不了。
  • 逻辑外键灵活，除了存在性还能校验「没被冻结、没注销」这类业务条件。
  • 阿里 Java 开发手册明确写了不得使用外键与级联。

📈 拔高

代价是一致性靠代码质量兜底，常见做法是统一封装校验入口、定期扫孤儿数据；数据量小、并发低的内部系统，用物理外键反而省事。

💡 主动加分的追问准备

面试官追问 你的答案
用逻辑外键怎么保证数据一致性？万一代码有 bug 漏检查了怎么办？ 几道防线：统一封装数据访问层，所有涉及外键关系的操作走同一套校验逻辑，不散落在各处；定期跑数据校验脚本扫描出孤儿数据及时处理；code review 重点关注关联数据的校验逻辑；核心数据实在不放心可以用数据库触发器兜底，性能损失可接受即可。
级联删除用逻辑外键怎么实现？ 手动写代码递归删：删用户时先把用户的订单都逻辑删除，再把订单对应的订单项都逻辑删除。可以封装成一个 Service 方法统一处理，或者用事件机制，删除用户时发事件、订单模块监听后自己处理关联数据。比物理外键麻烦，但可控性强，想跳过某些关联数据的删除也方便。
有没有折中方案？既要一致性保障又要性能？ 应用层做强校验、数据库层做弱约束：用触发器在插入时检查关联数据但不用 FOREIGN KEY，避免级联更新问题；或异步校验，写入时不检查，后台定时任务扫描不一致数据报警处理；或读多写少场景用物理外键但关掉级联更新，只做插入检查。
分库分表后跨库数据一致性怎么保证？ 这是分布式事务问题：轻量方案用最终一致性，先插主表再异步同步到关联表，失败重试或补偿；重量级方案用 TCC 或 Saga 模式，每个操作有对应回滚逻辑。实际业务大部分场景最终一致性就够，强一致代价太大，关键是业务设计上容忍短暂的不一致窗口。

❌ 千万别说的话

  • “用了外键数据一定是最干净的”：分库分表和逻辑删除场景下物理外键根本用不了。
  • “逻辑外键就是不做校验”：校验责任只是从数据库挪到了应用代码，必须自己写并做定期巡检。
  • “外键慢是因为多一次 join”：瓶颈主要在级联更新、每次写入的额外检查和锁竞争。

65. 什么是游标 Cursor 分页？相比传统 LIMIT OFFSET 分页有什么优势？

🎬 面试现场

面试官（口语化）：列表页翻到后面特别慢，用 LIMIT OFFSET 和用游标分页差在哪？游标字段怎么选？

⚠️ 翻车点

以为游标分页是银弹——它没法随机跳页、没法高效统计总数、向前翻页很别扭，这些局限要主动说出来。另外只把游标分页当唯一解法也不行，答不出子查询延迟关联、搜索引擎 search_after 和业务层限制最大页数这几层手段，追问「除了游标还有别的办法吗」就接不住。

📝 回答重点

  • 游标分页拿上一页最后一条的标识当起点，WHERE id > 10000 直接定位，不用数前面。
  • 传统 LIMIT OFFSET 是扫描再丢弃，EXPLAIN 的 rows 会把 offset 算进去，越翻越慢。
  • 深分页最贵的是回表：跳过一亿条如果还要回表，代价直接不可接受。
  • 游标字段要唯一且有序，一般用主键；按时间排序就上 (create_time, id) 复合游标。
  • 局限也明显：不能跳页、拿不到总页数、向前翻要反向排序，数据被删还会错位。

📈 拔高

还有几层手段可以叠加：延迟关联的子查询先在索引里定位起始 id、ES 的 search_after 配 PIT、以及业务层限制最大页数；到十亿级得上分库分表加 ES。

💡 主动加分的追问准备

面试官追问 你的答案
游标分页能不能实现向前翻页？ 可以，但要改变排序方向和比较符号：往后翻是 WHERE id > cursor ORDER BY id ASC，往前翻就变成 WHERE id < cursor ORDER BY id DESC，取出来后在应用层反转一下顺序。实现比较别扭，如果确实需要双向翻页，可以用两个游标 prev_cursor 和 next_cursor，分别记录当前页第一条和最后一条的位置。
如果游标字段被删除了会怎样？ 用已删除记录的 ID 当游标，WHERE id > 删除的ID 条件仍能正常工作，只是从下一个存在的 ID 开始取，不报错也不漏数据。但时间戳 + ID 复合游标且 ID 被删时，WHERE 里的 id < last_id 部分可能命中不到预期数据，这种场景建议游标里只用时间戳、放弃 ID 的精确定位。
游标分页和 Elasticsearch 的 scroll API 是一回事吗？ 不是。scroll API 是 ES 早期的深度分页方案，会创建快照保持数据一致性，但占用大量资源，官方已不推荐用于实时场景。ES 7.0 之后推荐 search_after，这才是真正的游标分页思路，传入上一页最后一条的 sort 值定位下一页，不占用额外资源，适合实时翻页；scroll 现在主要用于批量导出全量数据。
游标分页如果按创建时间排序，时间相同的记录怎么处理？ 时间相同的记录没法用单字段游标区分，需要用联合游标，比如 WHERE (create_time, id) > (上一页最后一条的 create_time, id) ORDER BY create_time, id LIMIT 10。MySQL 8.0 支持 Row Constructor 比较，写起来简洁；如果是低版本，就得拆成 WHERE create_time > x OR (create_time = x AND id > y) 这种写法。
ES 的 search_after 和 MySQL 的游标分页有什么区别？ 原理一样，都是拿上一页的排序值当起点。区别有两处：ES 要配 PIT 才能保证翻页期间数据不变，MySQL 没有这个机制；两者都不能跳页，只能往后翻。
子查询优化为什么比直接写 LIMIT 快？ 关键在延迟关联：子查询只在二级索引上找起始 id，索引里只有 name 和 id，比扫主键索引便宜得多；拿到 id 后 id >= xxx LIMIT 10 在主键索引上是一次范围查询，B+ 树定位完顺序读 10 条就结束。
线上要同时支持跳页和性能，你怎么办？ 业务层三个办法：限制最大翻页数、把列表改成无限滚动、引导用户加筛选条件缩小范围。列表页用游标分页，跳页需求就限制页数上限。
你说子查询走覆盖索引会快，但如果 WHERE 条件里有其他字段筛选，还能走覆盖索引吗？ 得看条件字段是不是在索引里。如果有联合索引 (status, id)，那 WHERE status = 1 ORDER BY id 就能走覆盖索引。但如果条件字段没有索引，或者索引不包含所有需要的字段，还是得回表，优化效果就打折扣。实际项目里，可以专门为分页查询建一个包含筛选条件和排序字段的联合索引。
游标分页的方案，如果用户想跳到任意页怎么办？ 游标分页确实没法直接跳页。如果业务必须支持跳页，可以折中处理：前 100 页用传统 offset 查询，offset 还不算太大，性能可以接受；超过 100 页就只允许用上一页下一页的方式翻，或者引导用户用筛选条件缩小范围。很多电商网站就是这么做的，你翻到几十页之后会发现没法继续往后跳了。
如果表数据量特别大，比如 10 亿条，这些优化方案还够用吗？ 十亿级得从架构解决：分库分表把数据拆散，查询路由到具体分片；列表类需求交给 ES，MySQL 只存明细。
延迟关联和子查询优化是一回事吗？ 原理一样，都是先在索引上把 id 捞出来再回表，区别只是写法不同：子查询把 id 作为外层的过滤条件，延迟关联用 JOIN 关联 id 集合。两者都要建立在「筛选条件 + 排序字段能进覆盖索引」这个前提上，否则优化效果会打折扣。

❌ 千万别说的话

  • “游标分页可以完全替代 LIMIT OFFSET”：跳页场景和总数统计还得靠传统分页。
  • “游标字段随便选一个有序字段就行”：必须唯一且有序，否则会漏数据或重复。
  • “OFFSET 大只是慢一点”：页码越深越慢，而且还会回表放大开销。
  • “深度分页只能靠分库分表才能解决。”：延迟关联、游标分页、限制最大页数这些手段在单表上就能解决大部分问题。

66. 如果组长要求你主导项目中的分库分表，大致的实施流程是？

🎬 面试现场

面试官（口语化）：组长让你主导一次分库分表改造，从评估到上线，整个流程你打算怎么走？

⚠️ 翻车点

  • 直接跳过分片键的选择就开始设计表结构，而分片键恰恰是后面所有成本的总开关，选错了改起来代价极大。
  • 数据迁移环节讲得含糊，说一句「用工具同步一下」就带过，迁移后的校验才是最容易出事的地方。
  • 灰度切换没有回滚预案，切换期间双写怎么保证主键不冲突、出问题怎么退回去，这些必须提前设计。
  • 分片数量拍脑袋定，既没算业务增长预期，也没想到分片过多带来的路由开销和运维复杂度。

📝 回答重点

  • 拿到这种题先评估该不该拆：手册口径是单表超 500 万行或 2GB 才推荐拆，业内说的 2000 万行、单库 QPS 5000 是经验值，没瓶颈就先优化索引和 SQL。
  • 分片方案先定分片键，选查询频率高、分布均匀的字段，电商一般 user_id 或 order_id，选错后面改代价极大。
  • 策略上哈希取模分布最均匀，范围分片扩容最方便，分片数量一步到位，16 或 32 个避免频繁扩容。
  • 中间件小团队选 ShardingSphere-JDBC，嵌入应用官方定位 Low loss，接近原生 JDBC，但连接数占用更多。
  • 迁移最容易出事：Canal 监听老库 binlog 做增量，批量脚本搬存量，迁完必须校验行数和关键字段，对不上就补偿修复。
  • 灰度切换先切读流量观察一阵再切写，双写期间主键换成 Snowflake 这类分布式 ID，新库出问题能立刻回滚。

📈 拔高

订单表和明细表按同一个 order_id 分片做成绑定表，不然一个订单的数据散在不同分片，JOIN 直接废掉。真不想折腾这套，TiDB、PolarDB-X 这类分布式数据库自带分片，对应用透明，代价是运维门槛和云费用。

分片数量怎么定？定少了扩容麻烦，定多了是不是也有问题？ 按未来 3 到 5 年体量一步到位，预估 5 年后 10 亿条、单表控制在 2000 万以内就得配够 50 个。分片多了路由开销和运维复杂度也涨，实践中 16、32、64 这种 2 的幂次常见，方便扩容时做分裂，具体视体量而定。

  • “按创建时间分片最自然。” ：创建时间往往是低频查询字段，真按它分片，每次查询都得扫全部分片。
  • “数据迁完直接切流量。” ：不做行数和关键字段校验就切，等于把脏数据推到线上。
  • “双写期间主键用数据库自增就行。” ：各库自增必然撞号，双写阶段必须先换成全局唯一的分布式 ID。

67. 对数据库进行分库分表可能会引发哪些问题？

🎬 面试现场

面试官（口语化）：分库分表能扛住单机瓶颈，但也会带来一堆分布式的问题。你觉得主要会引发哪些问题？分别怎么解？

⚠️ 翻车点

  • 只想到「分布式事务难搞」这一条，漏掉跨库 JOIN 失效、全局 ID 冲突、排序分页变复杂、聚合统计麻烦这四个同样高频的坑。
  • 把 2PC 当成标准答案照搬，不评价它的协调者单点和锁持有时间长的问题。
  • 只会说分页要「把所有分片数据拉回来归并」，想不出游标翻页和二次查询这两种减少无效传输的办法。
  • 讲全局 ID 方案时只说「用 UUID」，不展开雪花算法、Leaf 号段、UUID 在有序性和索引效率上的差别。

📝 回答重点

  • 分库分表后冒出来的分布式问题主要是五个：事务一致性、跨库 JOIN 失效、全局 ID 冲突、排序分页变复杂、聚合统计麻烦。
  • 单机事务没了，MySQL 的 XA 事务实现了 X/Open XA 规范，就是标准两阶段提交的接口，问题是协调者单点、锁持有时间长。
  • 一致性要求高的核心链路用 TCC，Try、Confirm、Cancel 三个方法都得幂等。实时性要求不高就上本地消息表或 RocketMQ 事务消息保最终一致。
  • 跨库 JOIN 只能在应用层拆两次查再拼，高频字段冗余进主表，或者拼成宽表同步到 ES 走检索。
  • 全局 ID 换掉自增：雪花算法本地生成快但怕时钟回拨，Leaf-snowflake 的 ZK 是弱依赖，回拨 5ms 内等待重试，更大偏移直接报错。
  • 分页别深翻，改游标翻页只许上一页下一页，或者先用 offset 估算边界再缩小各分片范围，聚合统计推给 ES 或 ClickHouse。

📈 拔高

TCC 的 Cancel 失败靠框架事务日志反复重试，多次失败就告警人工介入，幂等是设计前提。中间件选型上 SQL 解析和路由在应用进程内完成的是客户端分片，独立代理部署的是 Proxy 模式，看团队有没有 DBA 运维能力。

面试官追问 你的答案
分库分表后数据倾斜怎么办？比如某个分片数据量特别大？ 分片键选得不好才会倾斜，大客户数据全堆一个分片。解法是换「用户 ID + 时间」组合分片键，或者给大客户单独一套分片逻辑，已经倾斜就迁移数据拆热点。
分库分表中间件你用过哪些？原理上有什么区别？ 原理分两类。客户端分片像 ShardingSphere-JDBC，jar 包嵌入应用，解析和路由都在进程内，性能好但有代码侵入。代理层分片像 MyCat、Proxy，独立部署，应用无感但多一跳网络。
分布式事务用 TCC 的话，Cancel 阶段失败了怎么办？ TCC 框架都有事务日志，Cancel 失败会一直重试，多次失败就告警人工介入。三个方法必须幂等，Cancel 被重复调用结果要一样。
不用中间件，自己实现分库分表路由可行吗？ 可行但没必要。解析 SQL 拿到分片键的值，算出目标库表改写执行，难点在子查询、聚合、跨分片 JOIN 这些复杂 SQL，还有连接池、事务边界、结果归并，自己写容易漏边界，生产用成熟中间件。

❌ 千万别说的话

  • “分库分表之后还能继续用本地事务。” ：跨库写就跨不了本地事务了，必须上 2PC、TCC 或事务消息。
  • “跨库 JOIN 交给数据库自己搞定就行。” ：数据分散在不同分片，只能在应用层拆成多次查询再拼装，或者字段冗余、宽表进 ES。
  • “分库之后用数据库自增 ID 还能保证全局唯一。” ：自增 ID 在分库之后必定重复，得换成雪花算法、Leaf、UUID 这类分布式 ID 方案。
  • “分库分表后分页还能照常用 limit 100000, 10。” ：必须把各分片数据归并排序，数据量大时只能靠游标翻页或二次查询。

68. 为什么阿里巴巴的 Java 手册不推荐使用存储过程？

🎬 面试现场

面试官（口语化）：存储过程不是也能提性能吗，为什么大厂的开发规范里明确不让用？

⚠️ 翻车点

  • 只答”性能差” —— 存储过程在特定场景下性能并不差，真正的理由是它把业务逻辑焊死在数据库里，带来的工程化问题远大于性能收益。
  • 把它说成”落后的老技术” —— 它在 2000 年前后的企业级开发里有合理存在价值，问题出在今天的架构体系不兼容。
  • 只会说”不好调试”就说不出为什么不好调试 —— 要能落到打不了断点、写不了单测、CI/CD 覆盖不了这几点上。
  • 忽略了版本管理问题 —— 应用代码有 Git，存储过程改完直接执行，谁改了什么全靠人肉记，这是多人协作里最容易出事的地方。
  • 答成”存储过程不能用了” —— 它在数据迁移批处理、遗留系统维护等场景仍然合理，只是不能作为常规业务逻辑的载体。

📝 回答重点

  • 阿里手册给的是【强制】禁止，SQL 规约原文理由就一句：难以调试和扩展，更没有移植性。
  • 根子是把业务逻辑焊死在数据库里，换库时 SQL 方言 全要重写，把核心逻辑锁死在一家数据库上风险太大。
  • 调试测试都难：应用代码能打断点写单测，存储过程这些全干不了，CI/CD 也覆盖不到，排查只能靠日志。
  • 版本管理是多人协作的雷区，存储过程改完直接在库里执行，谁改了什么全靠人肉记录，回滚也没抓手。
  • 它也别一棍子打死，数据迁移批处理、遗留系统维护还能用，新功能别再往上堆。抠性能优先考虑缓存、读写分离、分库分表。

📈 拔高

69. 什么是数据库的游标？

🎬 面试现场

面试官（口语化）：游标这个东西你用过吗？说说它是什么，MySQL 里的游标怎么用，以及它到底值不值得用？

⚠️ 翻车点

  • 把游标说成「结果集的一个指针」，答不出它只能在存储程序里使用这个硬限制。
  • 只会说 DECLARE/OPEN/FETCH/CLOSE 四步，讲不出 NOT FOUND 处理器和 done 标志是怎么配合来结束循环的。
  • 说游标是「客户端游标」，实际 MySQL 游标是服务端游标，结果集在 OPEN 时物化成内部临时表，超限转磁盘。
  • 只会讲「游标性能差」，说不出差在哪：FETCH 的函数调用开销、逐行 UPDATE 各自走一遍解析优化、事务日志被撑大。
  • 答不出「游标开着的时候另一个事务改了数据会怎样」，这题直接考隔离级别和 MVCC 快照。

📝 回答重点

  • 游标让程序逐行遍历结果集，类似编程里的迭代器，结果集太大或每行要做复杂判断时才用。
  • MySQL 游标只能在存储程序里用，过程、函数、触发器都算，基本四步：DECLARE、OPEN、FETCH、CLOSE。
  • 它是服务端游标，OPEN 一执行结果集就物化成内部临时表，先放 MEMORY，超了 max_heap_table_size 或 tmp_table_size 就转磁盘 MyISAM 表。
  • 性能把集合操作降成逐行：每次 FETCH 一次函数调用，循环体里 UPDATE 逐条走解析优化，日志也多写，跟一条集合 UPDATE 差百倍。
  • Java 侧逐行处理大结果集走 JDBC 流式读取：先用 TYPE_FORWARD_ONLY 和 CONCUR_READ_ONLY 建 Statement，再设 fetchSize 为 Integer.MIN_VALUE。
  • 忘了 CLOSE 不会泄漏，声明所在的 BEGIN…END 块结束时自动关，但存储过程拖成长事务会一直持有旧读视图。

📈 拔高

服务端游标在 OPEN 时物化，隔离级别决定的是那一刻的快照，FETCH 之后别的事务提交了新数据也看不到。MySQL 不支持 REF CURSOR，游标没法当参数传出去，批处理逻辑想复用就得挪到应用层写。

游标打开期间如果另一个事务改了数据，游标读到的是改之前还是改之后的？ 服务端游标在 OPEN 时就把结果集物化成内部临时表，快照那一刻定死，后面 FETCH 读的都是物化结果，别的事务再改也看不到。

面试前 10 分钟速查

索引与存储引擎

  • B+ 树：非叶子节点只存键、叶子节点串成链表，范围查询友好；红黑树树高更大、磁盘 I/O 次数更多
  • B+ 树三层能存多少：16KB 页 ÷ 14 字节 ≈ 1170 个 key，三层约 2000 万行（行越小存越多）
  • B+ 树查询全过程：先从根节点二分定位区间、垂直走到叶子节点（三层最多 3 次磁盘 I/O），再到 16KB 叶子页里用页目录二分定位分组、沿组内链表找到目标记录
  • 聚簇索引：数据本身，叶子节点存整行；二级索引叶子存主键值，回表才有数据
  • 回表：二级索引定位到主键后再去聚簇索引取整行；查得越宽回表代价越大，覆盖索引可免回表
  • 无主键的聚簇索引：优先取第一个非空唯一索引，都没有就用 6 字节隐藏列 row_id；它对业务不可见、查询用不上，建表最好显式指定主键
  • 覆盖索引：查询字段全在二级索引里，不回表；EXPLAIN 的 Extra 显示 Using index
  • 索引下推（ICP）：把条件下推到存储引擎层过滤，减少回表
  • 最左前缀：联合索引按列顺序命中，范围列之后的列无法再用于等值匹配
  • 最左前缀的例外：>=、<=、BETWEEN、like 'xx%' 含等值定位，不会中断匹配，只有 >、< 才会中断；MySQL 8.0.13 的 Skip Scan 只是隐式补上最左列，仍要求最左列基数极低
  • 索引类型：Hash（等值快、不支持范围/排序）、B+ 树（默认，范围友好）、全文（分词检索）、空间（GIS）
  • 存储引擎：InnoDB（默认，事务/行锁/MVCC/聚簇索引）、MyISAM（表锁、无事务）、MEMORY（全内存、重启即丢）、Archive（只支持增查、压缩率高）、NDB（Cluster 分布式引擎）
  • 建索引注意事项：区分度低的列（性别/状态）别单独建、别给超长字段建、联合索引把等值列放前面
  • 索引不是越多越好：每个索引都要维护，占用 Buffer Pool，写入成本随索引数线性上升
  • 索引不一定有效：优化器按成本估算走索引还是全表扫，几百行的小表全表扫更便宜、统计信息不准也会算错账；用 EXPLAIN 看 type/key/rows，FORCE INDEX 对比、ANALYZE TABLE 更新统计信息，sys.schema_unused_indexes 找从未用过的索引
  • 索引失效常见：类型隐式转换、函数包裹列、LIKE '%x'、联合索引不满足最左前缀
  • 查询优化器：解析 → 预处理 → 优化三阶段，成本 ≈ 读页数 × 1 + 扫描行数 × 0.2；多表 JOIN 要小表驱动大表，优化器选错时用 STRAIGHT_JOIN 强制顺序
  • InnoDB vs MyISAM：行锁 vs 表锁、MyISAM 有精确行数计数器 vs InnoDB 的 COUNT(*) 只能扫索引、崩溃恢复 InnoDB 有 redo log、事务只有 InnoDB 支持
  • Change Buffer：非唯一二级索引的页变更先攒在内存，攒够再批量写回；唯一索引用不了（要判重）

事务与锁

  • 四级隔离：RU < RC < RR < SERIALIZABLE；MySQL 默认 RR
  • RR 靠 MVCC + 间隙锁：解决幻读靠这两样；RC 无间隙锁
  • 隔离级别三类问题：脏读（读到别人没提交的数据）、不可重复读（同一行内容变了）、幻读（符合条件的行数变了），严重程度依次递减
  • 生产为什么常用 RC：RR 的间隙锁锁范围大、并发低、死锁多，RC 只用行锁；前提是 binlog_format=ROW，改级别用 SET GLOBAL transaction_isolation
  • 半一致性读：RC 下 UPDATE 扫到被锁的行，先读最新已提交版本判断是否满足 WHERE，不满足就不等锁，这是 RC 并发更高的关键
  • ReadView 四个字段：trx_ids、up_limit_id、low_limit_id、creator_trx_id
  • MVCC 隐藏字段：每行有 trx_id（最后修改它的事务 ID）和 roll_pointer（指向 undo log 的上一版本），多次修改串成版本链；没有 MVCC 就只能靠加锁（LBCC）保证一致，读写互斥、吞吐腰斩
  • 快照读 vs 当前读：普通 SELECT 走 MVCC 读历史快照不加锁；FOR UPDATE、LOCK IN SHARE MODE、UPDATE、DELETE 必须读最新版本并加锁
  • 二级索引没有 MVCC：二级索引条目不存 trx_id/roll_ptr，版本可见性只能回表时靠聚簇索引判断；页头 page_max_trx_id 判断整页都可见时才免回表
  • RR 挡不住所有幻读：先快照读再当前读，两次结果行数可能不同；要防幻读得从头就用 FOR UPDATE
  • 锁：行锁（记录锁、间隙锁、临键锁）、表级锁（MDL、意向锁、插入意向锁）、Auto-Inc Lock
  • 间隙锁细节：锁的是索引记录之间的间隙，SELECT ... WHERE id > 3 FOR UPDATE 会锁住后面的区间；间隙锁之间不冲突，但互相往对方锁住的间隙插入就会死锁
  • 乐观锁 vs 悲观锁：乐观锁用版本号/时间戳 UPDATE ... WHERE version = ? 靠应用重试；悲观锁用 SELECT ... FOR UPDATE 或 LOCK IN SHARE MODE 靠数据库阻塞
  • 死锁：两个事务各持一把锁互等；检测看 SHOW ENGINE INNODB STATUS 的死锁段，事后处理是回滚代价小的事务并重试，业务上要固定加锁顺序
  • 长事务危害：undo log 堆积版本链不释放、锁长期不释放、主从延迟被拉大；线上要设 innodb_lock_wait_timeout 并监控长事务
  • 长事务排查：information_schema.innodb_trx 按 trx_started 揪出超时会话；大表删除按主键分段、每批十万条，别让一条 SQL 删几亿行
  • 崩溃恢复：innodb_flush_log_at_trx_commit=1 最安全（提交即刷盘）
  • 事务实现四组件：Redo Log 保持久性、Undo Log 保原子性、锁与 MVCC 保隔离性，一致性是三者共同作用的结果

日志

  • 三种日志分工：redo log 物理日志（记页的改动，崩溃恢复用）、undo log 事务回滚与 MVCC 版本链、binlog 逻辑日志（主从复制与增量订阅用）
  • redo log 记的是：「某个数据页做了什么修改」，不是 SQL 原文；写的是物理页偏移
  • redo log vs binlog：引擎层物理日志、循环写空间固定、用于崩溃恢复；Server 层逻辑日志、追加写、用于主从复制与按时间点恢复
  • WAL（Write-Ahead Logging）：写前日志，先写日志再改数据页，保证「提交前数据落盘」的顺序；InnoDB 的 redo log 就是 WAL 的实现
  • redo log 的环形结构：write pos 是当前写到哪里、checkpoint 是脏页刷盘刷到哪里；write pos 追上 checkpoint 说明 redo log 满了，会触发 checkpoint 抖动、阻塞所有写入
  • Log Buffer：redo log 先写内存缓冲区再刷盘；innodb_flush_log_at_trx_commit=1 提交即刷，=2 写 OS 缓存每秒刷，=0 交给 OS（最不安全）
  • Log Buffer 的刷盘时机：事务提交时按 innodb_flush_log_at_trx_commit 刷、用量过半后台线程刷、后台线程每秒兜底刷；Innodb_log_waits 持续增长说明写入在等刷盘腾空间
  • binlog 写入时机：事务提交时写（sync_binlog=1 表示每次提交都 fsync）
  • 二阶段提交：prepare 阶段写 redo log 并标记 prepare，commit 阶段写 binlog 落盘后再把 redo log 改成 commit；恢复时 redo 是 prepare 而 binlog 没有对应 XID 就回滚，有则提交
  • Doublewrite Buffer：脏页刷盘前先备份到 Doublewrite 文件，防止部分写（torn page）造成页损坏；redo log 只解决数据丢失、解决不了数据损坏
  • Change Buffer 的边界：只对普通二级索引生效，主键索引、唯一索引（必须先读页判重）、全文与空间索引用不了；默认最多占 Buffer Pool 的 25%

SQL 与调优

  • SQL 执行过程：连接器 → 分析器（词法/语法分析、生成语法树）→ 优化器（选索引、定连接顺序、SQL 改写）→ 执行器（调存储引擎逐行读取）；MySQL 8.0 已移除查询缓存；更新语句还要先写 redo log、再写 undo log、Server 层写 binlog，用两阶段提交保持一致；ORDER BY 走不上索引时用 filesort，sort_buffer（默认 256KB）放不下就落盘做外部排序
  • 执行顺序：FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
  • **EXPLAIN 看 type**：ALL 全表扫、ref/range 走索引；key 是实际索引（NULL 表示没用上）；rows 是预估扫描行数；Extra 里 Using index 是覆盖索引、Using filesort 是需额外排序
  • EXPLAIN 的增强：EXPLAIN FORMAT=JSON 能看到每一步的成本估算，EXPLAIN ANALYZE（8.0.18+）真正执行并给出实际行数
  • Buffer Pool：读数据先看内存缓冲池，命中直接返回；未命中才从磁盘读页并载入
  • Buffer Pool 的数据页粒度：页默认 16KB，查一行也整页载入；改良 LRU 分 young/old 两代，新页先进 old、待够 1 秒再次访问才升为热点，避免全表扫描把热点挤掉
  • Buffer Pool 命中率公式：1 - (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests)，生产应接近 100%
  • 慢查询：slow_query_log + long_query_time；mysqldumpslow / pt-query-digest 聚合
  • 慢查询的补充：log_queries_not_using_indexes 能抓出跑得很快却没走索引的 SQL；pt-query-digest 按 SQL 指纹聚合次数、平均耗时、扫描行数，生产更推荐它
  • 游标分页与深度分页：LIMIT 100000, 10 要先扫十万行再丢弃，EXPLAIN 的 rows 是 100010 而不是 10；解法是游标分页（WHERE id > last_id）、延迟关联（先在二级索引取 id 再回表）、或交给搜索引擎
  • SQL 调优三步：定位慢 SQL → EXPLAIN 分析执行计划 → 针对性优化；目标是既减少磁盘 I/O，也降低锁竞争
  • SQL 调优三板斧：索引（联合索引 + 覆盖索引）、写法（禁 SELECT *、禁 %LIKE、注意两表字符集一致）、架构（Redis 缓存、读写分离、冷热分离）
  • 运维侧调优：innodb_buffer_pool_size 设物理内存的 70%~80%，定期 ANALYZE TABLE 更新统计信息、OPTIMIZE TABLE 整理碎片（会锁表，大表放低峰期）
  • count 家族：count(*) 统计行数最快（MyISAM 有精确行数计数器）、count(1) 与之几乎等价、count(字段) 只统计非 NULL 且要取值，大表上更慢
  • count 的实现差异：InnoDB 因 MVCC 维护不了全局计数，只能扫索引，且优先扫占用空间最小的二级索引；8.0.17 起支持并行扫描
  • EXISTS vs IN：外表小、子查询表大用 EXISTS（逐行探测、命中即停），外表大、子查询表小用 IN（先物化再匹配）；NOT IN 遇到 NULL 会返回空集，优先用 NOT EXISTS
  • 三种 JOIN：INNER 只返回两边都匹配的行，LEFT 返回左表全部（右侧补 NULL），RIGHT 与 LEFT 交换主表位置等价；LEFT JOIN 的过滤条件放 ON 不丢左表行，放 WHERE 会把补 NULL 的行滤掉
  • 多表 JOIN 慎用：超过 3 个表建议拆到应用层关联；驱动表小、被驱动表的关联字段必须有索引，否则是 A × B 次比较量级

表结构

  • 金额类型：用 DECIMAL，绝不用 FLOAT/DOUBLE
  • **VARCHAR vs CHAR**：VARCHAR 变长、CHAR 定长；长度声明影响实际存储与排序行为
  • VARCHAR(100) vs VARCHAR(10)：磁盘占用按实际长度，但排序、分组、临时表按声明的最大长度预分配内存，VARCHAR(2000) 会把 sort_buffer 撑爆
  • int(11) 的 11：是显示宽度（含符号位），不限制能存多大数；int 实际固定 4 字节
  • **DATETIME vs TIMESTAMP**：DATETIME 存 1000~9999 年且不受时区影响，TIMESTAMP 存 UTC 且受时区与 2038 问题影响
  • TEXT 家族：TINYTEXT 255 字节、TEXT 64KB、MEDIUMTEXT 16MB、LONGTEXT 4GB；上限是字节数，UTF-8 下一个汉字 3 字节
  • TEXT 的存储与索引：行内只留 20 字节指针、内容在溢出页，读一次多一次磁盘 I/O；只能建前缀索引，5.7 及之前还不支持 DEFAULT
  • **DELETE / TRUNCATE / DROP**：DELETE 可回滚有日志、TRUNCATE 不可回滚重置自增、DROP 删表结构
  • DELETE 不释放空间：只把数据页标记为可复用，.ibd 文件大小不变，要靠 OPTIMIZE TABLE 或 ALTER TABLE ... ENGINE=InnoDB 重建才回收
  • AUTO_INCREMENT 溢出：到上限后卡在最大值并报 Duplicate entry，不会自动回绕；int 主键日均百万条 6 年就撑爆，新表直接上 BIGINT UNSIGNED
  • 无主键时 row_id 会回绕：6 字节隐藏列是全局共享的，到 2^48-1 后回绕并静默覆盖同 ID 的老数据，所以生产必须显式指定主键
  • 逻辑删除：加 deleted 标记，物理删除：真删行
  • 逻辑删除的唯一索引坑：反复删除再插入会撞唯一索引；把 is_deleted 换成 deleted_at 时间戳（默认 NULL）或直接写被删记录的主键 ID
  • 逻辑外键 vs 物理外键：逻辑外键靠应用保证，物理外键有性能与并发代价
  • 三大范式：1NF 列不可分、2NF 非主属性完全依赖主键、3NF 非主属性不传递依赖主键；反范式用冗余换查询性能（要接受一致性问题）
  • 建表注意事项：类型够用就好、主键用自增 BIGINT、区分度低的字段别建索引、不用物理外键、尽量 NOT NULL DEFAULT、预留扩展字段和 JSON 字段；where column = null 查不到数据要用 is null
  • 一张表最多多少列：Server 层理论上限 4096 列，InnoDB 实际硬限制 1017 列，还受 65535 字节行大小约束；超过 100 列就该考虑拆表
  • 大表 DDL：5.6 之前 ALTER TABLE 锁全表，之后有 Online DDL 但仍有元数据锁阻塞查询，大表用 pt-online-schema-change 或 gh-ost
  • 存储过程/触发器：难以调试、无法移植、占用数据库 CPU、业务逻辑应放应用层

视图与 SQL 对象

  • 视图：虚拟表不存数据、查询时现场执行；MySQL 默认做视图合并，含聚合、GROUP BY、UNION 时会先物化成临时表，性能反而更差
  • 可更新视图与物化视图：视图要可更新必须基于单表且不含聚合、DISTINCT、GROUP BY、UNION、子查询；MySQL 不支持物化视图，只能自己用定时任务维护汇总表
  • 数据库游标：只能在存储过程/函数里用，四步 DECLARE/OPEN/FETCH/CLOSE；它是服务端游标，忘记关会占住服务端资源，还会让 undo log 无法清理
  • 游标 vs 集合操作：游标把集合操作变成逐行操作，10 万行就是 10 万次内部调用加 10 万条独立 UPDATE，差距是百倍级别；MySQL 游标只读、只进，不支持 REF CURSOR；Java 侧可以用 JDBC 流式读取（fetchSize = Integer.MIN_VALUE）替代，内存只留当前行

高可用

  • 主从：binlog → relay log → SQL 线程重放；Seconds_Behind_Master 监控延迟
  • 主从三线程：主库 dump 线程推 binlog、从库 I/O 线程写 relay log、SQL 线程重放；三种模式是异步、同步、半同步，默认异步；半同步要等至少 N 个从库确认，AFTER_SYNC 比 AFTER_COMMIT 安全
  • 延迟治理：并行复制、pt-heartbeat、避免大事务
  • 读写分离：代理层（ProxySQL）/ 中间件 / 应用层多数据源三种实现；代价是读旧数据（写后立刻读可能读到从库旧值），强一致读走主库或半同步；一个事务的读写必须走同一个库
  • 全量 vs 增量同步：全量简单但慢、增量快但依赖 binlog 位点；CDC 是从 binlog 解析变更事件的通用方案（Canal、Debezium 等）
  • CDC 工具：Debezium、Canal、Maxwell、Flink CDC；前提是 binlog_format=ROW 且 binlog_row_image=FULL
  • CDC 位点与幂等：Canal 位点要持久化到 ZooKeeper 或文件（否则重启丢进度），Debezium 存 Kafka；下游用 UPSERT 保证重复消费不出脏数据
  • 防单点：MGR 多主 / ProxySQL 中间件 / 云托管
  • 防单点方案：主从 + 读写分离、主备（备机只同步）、MGR 官方多主、MHA/Orchestrator 自动故障转移；MGR 要求所有表都有主键且对网络延迟敏感
  • 不停服迁移：双写 → 数据校验 → 切读 → 停旧写 → 切写
  • 迁移双写三个坑：先写旧库、成功后再写新库；两边不在同一事务里、只求最终一致；必须幂等，用唯一键 + UPSERT 兜住重复写
  • 迁移数据校验：主键抽样（id % 100 = 0）、时间范围抽样、关键字段 crc32 校验和比对
  • 批量数据入库：一次 INSERT 多值或 JDBC addBatch()/executeBatch()；连接串加 rewriteBatchedStatements=true，1000 条实测能从 12 万毫秒降到几百毫秒
  • 批量入库的坑：单批别超 max_allowed_packet（默认 4MB），建议 500~5000 条一批、分批提交，别把一次导入变成大事务
  • 数仓并发同步：同一行的变更必须由同一线程按顺序处理（按主键哈希路由到固定分区），位点与数据写入要在同一事务里提交，写入端用 UPSERT 保证幂等

分库分表

  • 垂直 / 水平拆分：垂直拆分治大表，水平拆分治单表容量
  • 四种拆分方式：水平分表（按行拆）、垂直分表（按列拆、冷热分离）、水平分库（表结构复制到多实例）、垂直分库（按业务模块拆库）
  • 分片键：必须选查询最高频的维度；分片后失去全局唯一性与跨片 JOIN 能力
  • 分片键避坑：别选低频字段（如 create_time）、别选分布不均的字段（一个大商家占 60% 订单）；关联表要用同一分片键做成绑定表
  • 什么时候该拆：单表超 2000 万行、单库 QPS 超 5000、磁盘或连接数告警；没瓶颈就别拆，先把索引和 SQL 优化到位
  • 扩容方式：用一致性哈希或预分片，避免二次迁移
  • 分布式 ID：分库后自增 ID 必冲突，换雪花算法 / Leaf 号段 / UidGenerator / TinyID
  • 分布式事务：2PC 协调者单点、锁持有久；TCC 灵活但要写 Try/Confirm/Cancel 三套；本地消息表适合最终一致
  • 跨片查询兜底：广播表、绑定表、异步汇总
  • 中间件选型：ShardingSphere-JDBC 嵌入应用性能最好、ShardingSphere-Proxy 对应用透明但多一跳、MyCat 社区不活跃、Vitess 云原生、PolarDB-X/TDSQL 对上层透明
  • 实施流程：定分片键 → 容量与分片数规划 → 改造访问层（分片中间件/ORM 插件）→ 建新库双写 → 数据校验 → 切读 → 切写 → 旧库只读观察 → 下线
  • 会引发的问题：跨片 JOIN 与聚合、分布式事务、跨片分页与排序、热点分片、扩容迁移、运维与监控成本上升

存储与选型

  • MySQL vs Oracle：MySQL 开源免费、上手门槛低、资源占用小、生态繁荣；Oracle 强在 RAC 共享存储、PL/SQL、并行查询、Data Guard 零数据丢失复制
  • MySQL 的短板：存储过程能力弱、没有原生物化视图、没有位图索引、不支持闪回查询和 RAC；传统企业的核心账务系统仍会留着 Oracle
  • 大文件不存 MySQL：图片、音视频放对象存储、库里只存 URL，否则会撑爆 Buffer Pool、放大 binlog、拖垮备份恢复
