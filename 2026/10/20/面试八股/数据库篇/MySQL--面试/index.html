为什么 MySQL 值得单独背

后端面试里，MySQL 是唯一一块「原理层和数据层都能聊」的科目。

Redis 你可以只背数据结构，JVM 你可以只背 GC 参数，但 MySQL 不行——面试官问「为什么用 B+ 树不用红黑树」，你答不出树的高度计算方式，前面讲的隔离级别全白讲；他问「MVCC 是怎么实现的」，你说不清 ReadView 的四个字段，那句「MySQL 默认 RR」就是背来的。

更关键的是 MySQL 的追问链特别长。你说「走索引了」，他立刻接「Using index 和 Using index condition 有什么区别」；你说「加索引就快了」，他立刻接「什么情况下索引反而更慢」。能不能接住第二问，才是区分背过和理解的分水岭。

所以这篇不给你第四十份知识点罗列，而是把 47 道高频题还原成真实的面试现场：每道题都是「面试官怎么问 → 你第一反应会怎么翻车 → 正确答法 → 追问怎么接」。

怎么用这篇：不要背「要点」，要背「现场反应」。左边那栏是面试官的问题，右边是你脑子里应该立刻蹦出来的东西。考前一小时扫「⚠️ 翻车点」那一行，性价比最高。

一、索引与存储引擎：为什么是 B+ 树，以及索引到底怎么用

1. MySQL InnoDB 引擎中的聚簇索引和非聚簇索引有什么区别？

🎬 面试现场

面试官（口语化）：InnoDB 的聚簇索引和二级索引到底差在哪儿？为什么二级索引查数据还要回表？

⚠️ 翻车点

把「非聚簇索引」说成「MyISAM 那种存物理地址的索引」就错了。InnoDB 的二级索引叶子节点存的是索引列的值 + 主键值，存物理地址的是 MyISAM。答错这一点，后面的回表代价、主键为何有序全都接不上。

📝 现场作答

  • 聚簇索引的叶子节点直接存完整数据行，一张表只能有一个聚簇索引，默认就是主键索引；非聚簇索引叶子节点只存索引列的值和主键值，拿到完整数据要再回表一次。
  • 两者底层都是 B+ 树：非叶子节点存主键和页号用于定位叶子节点，叶子节点之间有双向链表便于范围查询，页内还有页目录，查找时先二分定位到组再沿单链表遍历。
  • B+ 树只能帮我们定位到页而不是具体记录，页大小默认 16KB。
  • 主键最好有序且最好是自增的：数据按主键顺序排列，无序插入会往页中间塞，页满就触发页分裂，性能很差；用 UUID 做主键写入性能能差 3-5 倍。
  • 回表代价高是因为聚簇索引和非聚簇索引是两棵独立的 B+ 树，回表要额外走一遍树查找，数据量大时会产生大量随机 I/O，这也是不推荐 select * 的原因。
  • 与 MyISAM 对比：MyISAM 没有聚簇索引，主键索引和普通索引叶子节点都只存数据行的物理地址，数据文件与索引文件分离，主键查询是「B+ 树查找 + 磁盘寻址」，范围查询可能产生大量随机 I/O。

💡 主动加分的追问准备

面试官追问 你的答案
一张表没有主键时 InnoDB 怎么建聚簇索引？ 会找第一个非空的唯一索引作为聚簇索引；连唯一索引都没有，就自动生成一个 6 字节的隐藏列 row_id 作为聚簇索引，但它对业务不可见、查询用不上，所以建表时最好显式指定主键。
为什么二级索引存主键而不是物理地址？ 聚簇索引的数据物理位置不固定，页分裂、页合并、数据更新都会让物理地址变化，存地址就意味着每次数据移动都要更新所有二级索引，维护成本太高；主键值稳定，数据怎么移动都不影响二级索引。
什么时候二级索引查询不用回表？ 当查询的列都在索引里时就是覆盖索引。比如索引 (name, age) 查 select name, age from t where name = 'xx'，叶子节点已有 name、age、主键，EXPLAIN 的 Extra 会显示 Using index。

❌ 千万别说的话

  • “InnoDB 的非聚簇索引叶子节点存的是数据行的物理地址。” —— 那是 MyISAM，InnoDB 存的是主键值。
  • “聚簇索引一张表可以有多个。” —— 一张表只有一个聚簇索引。
  • “用 UUID 做主键没关系，反正都是唯一的。” —— 无序主键会频繁触发页分裂，写入性能能差 3-5 倍。

2. MySQL 索引的最左前缀匹配原则是什么？

🎬 面试现场

面试官（口语化）：联合索引的最左前缀匹配到底是怎么回事？范围查询一出现后面的列是不是就废了？

⚠️ 翻车点

「出现范围查询后面全用不上」是错的。>=、<=、BETWEEN、like 'xx%' 这类包含等值定位的不会停止匹配，只有 >、< 才会。答成「一律中断」，追问一句 where a >= 1 and b = 2 就露馅。

📝 现场作答

  • 最左前缀匹配指使用联合索引时，查询条件必须从索引最左列开始匹配：联合索引 (first_name, last_name, age) 先按 first_name 排序，相同再按 last_name，相同再按 age。
  • 跳过最左侧字段后，后面的列在 B+ 树中是无序的，压根没法利用索引快速定位。
  • 对 (a, b, c)：where a = 1、where a = 1 and b = 2、where a = 1 and b = 2 and c = 3 符合最左匹配；where b = 2、where c = 3、where b = 2 and c = 3 不符合。
  • where a = 1 and c = 3 能用上 (a, b, c)，但 MySQL 5.6 之前只能用 a = 1 过滤；5.6 引入索引下推后，可在引擎层查到 a = 1 的数据后直接用 c 过滤，减少回表次数。
  • 遇到 >、< 会停止匹配：a 范围筛选后，不同 a 值之间的 b、c 是无序的（如 a=2 与 a=3 的 b 值无排序关系），后面用不上索引。
  • 遇到 >=、<=、BETWEEN、like 'xx%' 不停止匹配，因为包含等值判断，可直接定位到某条数据再往后扫描；where a = 1 and b = 2 and c > 3 能完整用上联合索引，因为 a、b 等值前提下 c 仍有序。
  • MySQL 8.0.13 引入 Skip Scan Range Access Method，可绕过最左匹配：它统计最左列基数（示例中 f2 只有 1、2 两个值，基数为 2），把最左列的值拼进条件构造出 where f2=1 and f3=1、where f2=2 and f3=1 逐个查询，所以 type 变成 range，Extra 显示 Using index for skip scan——本质仍是没逃出最左匹配。
  • Skip Scan 局限很大：要求最左列基数很低（否则列举不如全表扫），且需要联合索引、不能跨表、不能用 GROUP BY 或 DISTINCT、只能用一个索引不能回表、查询条件必须是常量（含 IN()）。基数一大就会退化成全扫描二级索引。

💡 主动加分的追问准备

面试官追问 你的答案
联合索引 (a, b, c) 执行 where b = 1 and a = 2 能用上索引吗？ 能用上。MySQL 优化器会自动调整条件顺序，把 a = 2 放到前面，写成 where b = 1 and a = 2 和 where a = 2 and b = 1 效果一样，不用纠结条件书写顺序。
为什么 >= 不停止匹配但 > 会停止？ 关键在能不能精确定位到一条记录。a >= 1 能精确定位到 a = 1 的第一条数据，a = 1 内部的 b、c 有序可继续匹配；a > 1 定位到的是 a = 2 的第一条，已经跨过 a = 1 的整个范围，不同 a 值之间 b、c 无序。
建联合索引时列的顺序怎么定？ 高频查询条件放左边；区分度高的列放左边；范围查询的列放最右边，避免阻断后面列的匹配；经常有排序需求就把排序字段放进索引，避免 filesort。

❌ 千万别说的话

  • “只要 SQL 里出现了范围查询，后面的索引列就全用不上了。” —— >=、<=、BETWEEN、like 'xx%' 不停止匹配。
  • “写 SQL 时必须严格按索引列的顺序写条件。” —— 优化器会自动调整条件顺序。
  • “MySQL 8 的 Skip Scan 彻底打破了最左匹配原则。” —— 它只是隐式补上最左列的条件，且要求最左列基数极低。

3. MySQL 的覆盖索引是什么？

🎬 面试现场

面试官（口语化）：覆盖索引是个什么概念？怎么判断一条 SQL 走没走覆盖索引？

⚠️ 翻车点

把 Using index 和 Using index condition 混为一谈。前者是覆盖索引（不需要回表），后者是索引下推（要回表但回表次数变少），两个不会同时出现，说成「都是不查表」就错得很彻底。

📝 现场作答

  • 覆盖索引指二级索引中已经包含查询需要的所有字段，查询时直接从索引拿数据，不用再回表去主键索引取完整数据行，本质是「索引里有的数据就不去表里取」。
  • 好处有三个：减少 I/O（结果集大时省掉的回表次数可能是几万几十万次）、查询更快（索引比表数据更紧凑、在内存里命中率更高）、减少内存占用（只加载索引页到 Buffer Pool）。
  • 例子：CREATE TABLE employees (emp_id INT PRIMARY KEY, first_name VARCHAR(50), last_name VARCHAR(50), hire_date DATE, department_id INT, INDEX idx_name_hiredate (last_name, first_name, hire_date))。
  • 查 SELECT last_name, first_name, hire_date FROM employees WHERE last_name = '鸭' AND first_name = '面试' 时 idx_name_hiredate 就是覆盖索引，不用回表；一旦多取一个 department_id，索引里没有，就必须回表。
  • 判断方式：看 EXPLAIN 的 Extra 列，显示 Using index 就说明完全靠索引完成、没有回表；Using index condition 是索引下推，需要回表但次数减少。
  • 设计技巧：高频查询优先，先分析执行频率最高的查询来设计；别贪多，索引列越多索引越大写入维护成本越高，要权衡读写比例；利用联合索引，比如常见 select a, b from t where c = 1 就建 (c, a, b)；主键天然在二级索引里（叶子节点自动存主键），select 列含主键就不用额外把主键塞进索引。
  • 局限：select 的列很多时全塞进索引反而得不偿失；select * 是覆盖索引的天敌，除非索引包含表所有列否则必然回表；写多读少的场景加太多覆盖索引会拖慢写入。

💡 主动加分的追问准备

面试官追问 你的答案
覆盖索引和索引下推有什么区别？ 覆盖索引是完全不回表，索引里有查询需要的全部数据；索引下推是减少回表次数，把过滤条件下推到引擎层提前过滤，最终还是要回表拿完整数据。前者是「能不回表就不回表」，后者是「必须回表但少回几次」。
一个查询既用覆盖索引又用索引下推，可能吗？ 不可能。走了覆盖索引就不回表，索引下推没有用武之地。EXPLAIN 的 Extra 要么 Using index，要么 Using index condition，不会同时出现。
不改业务代码怎么让查询走覆盖索引？ 加联合索引。分析慢查询日志找出频繁执行的查询，把 where 条件列和 select 列组合成联合索引，比如 select a, b from t where c = 1 就加 (c, a, b) 或 (c, b, a)，只加索引对业务代码零侵入。

❌ 千万别说的话

  • “Using index 和 Using index condition 是一回事，都代表不用回表。” —— 后者仍然要回表。
  • “覆盖索引就是把表所有列都加进索引。” —— 索引列过多会显著增加写入维护成本，得不偿失。
  • “用了 select * 也可能是覆盖索引。” —— 除非索引里包含表的全部列，否则必然回表。

4. MySQL 的索引下推是什么？

🎬 面试现场

面试官（口语化）：索引下推是干什么的？为什么 MySQL 5.6 要加这个优化？

⚠️ 翻车点

把下推说成「在 Server 层过滤」或「把条件推到索引上定位」都不对。下推是把不能用于索引查找、但索引里存了该列值的条件交给引擎层提前过滤，目的是减少回表次数，而不是减少 I/O 页数或提升定位能力。

📝 现场作答

  • 索引下推是 MySQL 5.6 引入的优化，把部分查询条件从 Server 层下推到存储引擎层，在引擎层就过滤掉不符合条件的数据，不用再回表查完整数据。
  • 以前流程：引擎层用索引定位数据、返回主键给 Server 层，Server 层回表拿完整数据再用剩余条件过滤；有下推后引擎层直接用索引里的列过滤，不符合条件的压根不回表。
  • 主要用在联合索引上。官方例子：people 表有 INDEX (zipcode, lastname, firstname)，查 zipcode='95054' AND lastname LIKE '%etrunia%' AND address LIKE '%Main Street%'。
  • 没有下推时只能用上 zipcode='95054'，lastname LIKE '%etrunia%' 是左模糊匹配走不了索引查找，只能在 Server 层过滤，所有记录都要回表。
  • 有下推时引擎层定位到 zipcode 的数据后，直接用索引里的 lastname 值过滤，不合格的跳过不回表，只有合格的才回表再由 Server 层用 address 过滤。
  • 数量级：假设 zipcode=’95054’ 有 10000 条、符合 lastname 条件的只有 100 条，没有下推要回表 10000 次，有了下推只回表 100 次。
  • 判断方式：EXPLAIN 的 Extra 显示 Using index condition。
  • 限制：MySQL 5.6 及以后才支持，InnoDB 和 MyISAM 都能用；子查询可能让下推失效，要看 EXPLAIN；条件里用函数或表达式则不生效（如 WHERE YEAR(create_time) = 2024）；主键查询不需要下推（叶子节点直接存完整数据，没有回表环节）；覆盖索引也不需要下推。
  • 与覆盖索引对比：下推解决「减少回表次数」（Using index condition，仍回表），覆盖索引解决「完全避免回表」（Using index，不回表）；两者不能同时存在。
  • 需要对比性能时可手动开关：SET optimizer_switch = 'index_condition_pushdown=off'; / 'index_condition_pushdown=on'。实际场景没必要关闭，这个优化没有副作用。

💡 主动加分的追问准备

面试官追问 你的答案
索引下推只能用在联合索引上吗，单列索引能用吗？ 理论上单列索引也能用，但意义不大。下推的价值在于用索引里的额外列过滤，单列索引只有一列，要么走索引查找直接用上要么用不上，不存在「定位完了再用索引列过滤」的场景。联合索引才能第一列定位、后面的列下推过滤。
索引下推和最左前缀匹配是什么关系？ 下推是对最左前缀的补充。联合索引 (a, b, c) 查 where a = 1 and c = 3 时按最左匹配只能用 a 定位，c 用不上索引查找；但索引里存了 c 的值，引擎层可以直接过滤，减少回表。
为什么主键查询不需要索引下推？ 因为主键索引叶子节点直接存完整数据行，查到就拿到全部数据，压根没有回表这个环节，而下推解决的就是「减少回表次数」。

❌ 千万别说的话

  • “索引下推能让条件在索引上直接定位，少读很多页。” —— 下推不提升定位能力，只是少回表。
  • “覆盖索引和索引下推经常一起出现。” —— 走了覆盖索引就没有回表，下推失去意义。
  • “函数索引也能享受索引下推。” —— 条件里用函数或表达式时下推不生效。

5. MySQL 中使用索引一定有效吗？如何排查索引效果？

🎬 面试现场

面试官（口语化）：建了索引就一定用得上吗？怎么排查一条 SQL 到底走没走索引？

⚠️ 翻车点

把 type=index 直接等同于「没走索引」就错了。type=index 是全索引扫描，扫的是二级索引而不是主键索引，确实算「用上了索引」，和 type=ALL 的全表扫描不是一回事。

📝 现场作答

  • 索引不一定有效：建了索引不代表会用，用了也不代表快。最终走不走索引靠优化器的成本计算，比较走索引和全表扫描各自的 I/O 成本与 CPU 成本；表只有几百行时全表扫描确实更便宜，统计信息不准也会让优化器算错账。
  • 最直接的排查手段是 EXPLAIN，重点看三个字段：type（ALL 全表扫描、index 全索引扫描、range 范围扫描、ref 等值匹配）、key（实际使用的索引名，NULL 就是没走）、rows（预估扫描行数，越大代价越高）。
  • 「什么叫用上了索引」：利用主键索引快速查找、利用二级索引快速查找、全扫描二级索引，这三种都算用上了索引；全扫描主键索引就是常说的全表扫描（等价于没用索引）。
  • 因为 InnoDB 基于聚簇索引构建数据，没有二级索引时查数据必须且只能用聚簇索引。示例：表 t1 有主键 f1 和联合索引 idx_f2_f3(f2,f3)，查 SELECT * FROM t1 where f3 = 11 时 EXPLAIN 的 key 是 idx_f2_f3、type 是 index，即全扫描二级索引——因为二级索引已包含 f1、f2、f3 所需数据，直接全扫二级索引开销更小。
  • 换成 where f2 = 11 同样用 idx_f2_f3，但 type 变成 ref，表示与常量等值匹配快速定位。
  • 如果表再加一个 f4 字段，索引就覆盖不了返回值，要拿 f4 必须回表，EXPLAIN 就退回全表扫描。
  • 索引失效的常见场景（根因就两类：索引树快速查找能力用不上，或优化器算账不划算）：联合索引不符合最左前缀；索引列上做运算（WHERE id + 3 = 8）；索引列上用函数（WHERE LOWER(name) = 'cong'，MySQL 8.0 可用函数索引解决）；LIKE 左侧带通配符（'%cong%'，而 'cong%' 可以走索引）；OR 连接了非索引字段；隐式类型转换（varchar 列 = 1 等价于 CAST(name AS signed int) = 1，联表时两边字段编码不一致同样有问题）；优化器认为全表扫描更划算（热点数据走索引反而要回表几十万次）；ORDER BY 字段既不是主键也不是覆盖索引时可能全表扫再排序。
  • 索引生效反而变慢，通常是优化器估计值不准选错了索引，可用 FORCE INDEX 对比执行时间，或用 ANALYZE TABLE 更新统计信息，MySQL 8.0 还可用 EXPLAIN ANALYZE 对比实际行数与预估行数。

面试官追问 你的答案
EXPLAIN 里 type 的 ref 和 range 有什么区别？ ref 是等值匹配（如 WHERE name = 'cong'），直接定位到某个值；range 是范围扫描（如 WHERE id > 100 AND id < 200），要扫一段连续索引区间。性能上 ref 通常优于 range，等值定位更精准，range 还得沿叶子链表扫一段。
怎么知道优化器是不是选错了索引？ 用 FORCE INDEX 强制指定某个索引跑一遍对比执行时间，强制走某索引反而快很多说明确实选错了；也可用 ANALYZE TABLE 更新统计信息，MySQL 8.0 用 EXPLAIN ANALYZE 看实际行数与预估行数差多少，差太大说明统计信息不准。
隐式类型转换为什么导致索引失效？ 索引树里存的是原始类型的值，转换相当于对索引列套了一层函数。varchar 字段存的是 ‘123’，转成数字 123 后没法直接在索引树上定位，只能逐行取出转换再比较，变成全表扫描。

  • “EXPLAIN 里 type=index 就是没走索引。” —— 它是全索引扫描，扫的是二级索引，仍算用上了索引。
  • “建了索引查询就一定会走索引。” —— 优化器按成本选，表小或统计信息不准时可能直接全表扫。
  • “只要有索引，优化器就不会选错。” —— 统计信息是采样收集的，数据分布不均时估算会明显偏离。

6. 请详细描述 MySQL 的 B+ 树中查询数据的全过程

🎬 面试现场

面试官（口语化）：从根节点到拿到一行数据，B+ 树里的查询到底经历了哪几步？

⚠️ 翻车点

只讲「从根节点往下找」是不够的，B+ 树只能定位到页。真正的第二阶段——16KB 叶子页内部靠页目录二分 + 组内单链表遍历定位到具体记录——才是这题的区分点，也是最容易漏答的部分。

📝 现场作答

  • 查询分两个阶段：先从根节点垂直定位到叶子节点，再在叶子节点内部定位到具体数据行。
  • 第一阶段是树的垂直查找：把查询键值与节点中的索引键值比较，用二分法确定落在哪个区间，顺指针走向子节点，重复直到叶子节点。一棵 3 层的 B+ 树最多 3 次磁盘 I/O 就能定位到叶子节点。
  • 第二阶段是页内查找：叶子节点是一个 16KB 数据页，InnoDB 用页目录加速查找——记录被分成若干组，每个槽指向一组的最大记录，先用二分在页目录里定位到记录所在组，再沿组内单向链表遍历找到目标记录。
  • 完整路径：根节点 → 中间节点 → 叶子节点 → 页目录二分 → 组内链表遍历。
  • 16KB 叶子页的四段结构：文件头和页头（页号、页类型、上一页下一页指针，叶子节点靠双向链表串联，范围查询可沿链表后扫）；用户记录区（按主键顺序排列，记录间用单向链表串联）；页目录（每组 4-8 条记录，槽指向对应组最大记录）；文件尾（存 checksum 校验页完整性）。
  • 页目录二分的例子：查主键 3，5 个槽时先二分得 low=0、high=4，中位 2 槽指向主键 4，4 大于 3 故 high=2；再二分 (0+2)/2=1，槽 1 中主键 2 小于 3，low=1、high=2；此时 high-low=1 落在槽 2，槽间挨着可由槽 2 反推槽 1 位置，从主键 2 沿链表往下即定位到主键 3。
  • 分组大小有明确规定：第一个分组只有一条记录，中间分组 4-8 条，最后一个分组 1-8 条，所以不用担心遍历长链表。
  • 实际查询还要过 Buffer Pool：先在 Buffer Pool 找目标页，命中直接用；没命中从磁盘读页进 Buffer Pool 再返回。根节点和热点中间节点基本常驻 Buffer Pool，大部分查询只需 1 次磁盘 I/O 读叶子节点，所以「3 次 I/O」是理论上限，实际平均更低。

💡 主动加分的追问准备

面试官追问 你的答案
为什么 B+ 树比 B 树更适合做数据库索引？ 两个核心原因：B+ 树非叶子节点不存数据、只存索引键和指针，一个页能放更多条目，树更矮、I/O 更少；B+ 树叶子节点之间有双向链表，范围查询顺着链表扫即可，而 B 树要做中序遍历整棵树，I/O 随机且慢。
3 层 B+ 树大概能存多少数据？ 主键 bigint 8 字节、指针 6 字节时一个非叶子节点约存 1170 个条目；叶子每行 1KB、一页存 16 条。第一层 1 个根节点，第二层 1170 个中间节点，第三层约 137 万个叶子节点，总共约能存 2000 万条记录。
页目录为什么不把每条记录都建一个槽？ 空间成本太高。每个槽 2 字节，一页 1000 条记录就要 2KB 页目录，占整页 12.5%。分组后每组 4-8 条，只需 125-250 个槽，页目录只占几百字节；用组内链表遍历换空间，最多遍历 8 条，代价可接受。

❌ 千万别说的话

  • “B+ 树查一次就能直接定位到那一行。” —— B+ 树只能定位到页，页内还得靠页目录二分加组内链表。
  • “B+ 树查询固定就是 3 次磁盘 I/O。” —— 那是理论上限，Buffer Pool 命中时实际远少于 3 次。
  • “叶子节点里的记录是散乱存放的。” —— 按主键顺序排列，组内用单向链表串联，页之间用双向链表串联。

7. 在什么情况下，不推荐为数据库建立索引？

🎬 面试现场

面试官（口语化）：索引是不是越多越好？哪些情况下建索引反而是负担？

⚠️ 翻车点

把「区分度低就不该建索引」说成绝对规则就翻车了。语料里明确给了例外：数据分布严重倾斜时（比如 status 有 90% 是「已完成」），针对那 10% 的高频查询建索引反而能过滤掉 90% 的数据，是有意义的。

📝 现场作答

  • 不适合建索引的五类场景：数据量小的表（几百上千条，全表扫描更快，B+ 树查找和回表开销不划算）；写多读少的表（每次 INSERT/UPDATE/DELETE 都要同步维护索引）；区分度低的字段（如性别只有男女两个值，过滤不掉多少数据，优化器大概率直接全表扫）；查询根本不走的字段（从不出现在 WHERE、ORDER BY、JOIN 里，纯占磁盘）；长文本字段（TEXT、BLOB 索引 key 长度受限只能建前缀索引，查询效果差，大字段本身存储分散、随机 I/O 开销大，有搜索需求应该放 Elasticsearch）。
  • 维护成本：INSERT 要把新数据插到索引树正确位置，页满就触发页分裂，一张表 5 个索引就更新 5 棵 B+ 树；UPDATE 相当于先删旧索引记录再插新的，更新主键时所有二级索引都存着主键值，全得跟着改；DELETE 标记删除后索引树会变稀疏，浪费空间。
  • 经验数据：一张表索引从 3 个增加到 8 个，写入吞吐量下降约 40%，所以订单表这类高频写入的索引能省则省。
  • 区分度公式是 Cardinality / 总行数，Cardinality 是不重复值数量；用 SHOW INDEX FROM users; 看 Cardinality 列，或 SELECT COUNT(DISTINCT status) / COUNT(*) AS selectivity FROM orders;，结果小于 0.1 的字段索引效果很差，但分布倾斜的字段是例外。
  • 长文本字段的处理方案：前缀索引 CREATE INDEX idx_content ON articles(content(100));（缺点是没法用于 ORDER BY，也没法做覆盖索引）；哈希字段加一列存 MD5 或 CRC32 后对哈希列建索引，查询时用 content_hash = MD5('要查的内容') AND content = '要查的内容'；MySQL 5.6 起 InnoDB 支持 FULLTEXT 索引；数据量大、搜索需求复杂的场景同步到 Elasticsearch。
  • 索引失效的常见坑：对索引列做运算（WHERE YEAR(create_time) = 2024）；隐式类型转换（phone 是 VARCHAR 却传数字）；OR 条件包含非索引字段（name 有索引、age 没有，整体走全表扫描）；最左匹配不满足（联合索引 (a,b,c) 查 b=1 AND c=2，跳过 a 用不上索引）。

面试官追问 你的答案
区分度低的字段一定不能建索引吗？有例外吗？ 不是绝对的。数据分布倾斜的场景可以考虑，比如任务表 status 90% 是「已完成」、10% 是「待执行」，业务上频繁查「待执行」时建索引有意义，能快速过滤掉 90% 的数据，要结合实际业务判断。
怎么判断一个索引有没有被使用过？ MySQL 5.6 之后可以看 sys.schema_unused_indexes 视图，列出来的都是从未被用过的索引，可以考虑删掉；performance_schema.table_io_waits_summary_by_index_usage 能看每个索引的使用次数；也可以用 EXPLAIN 分析实际查询，看 key 列是否命中预期索引。

8. MySQL 的查询优化器如何选择执行计划？

🎬 面试现场

面试官（口语化）：优化器凭什么判断该走索引还是全表扫描？它的成本是怎么算的？

⚠️ 翻车点

把成本模型简化成「看数据量比例」而不给 I/O 成本和 CPU 成本的具体口径，答不出 读一页记为 1、处理一行记为 0.2 这个量纲，就答不出「为什么全表扫描反而更便宜」。

📝 现场作答

  • 优化器基于成本估算选方案，核心是哪个方案成本低选哪个，过程分三步：解析阶段（把 SQL 文本解析成语法树、检查语法）、预处理阶段（验证表和字段是否存在、检查权限、做一些简单查询重写）、优化阶段（生成多个候选执行计划、计算各自动成本、选成本最低的）。
  • 成本由 I/O 成本和 CPU 成本组成：读一页成本记为 1，处理一行记为 0.2，成本大致是 读取的页数 * 1 + 扫描的行数 * 0.2。
  • 举例：100 万行的订单表走主键查单条只需读 3~4 个页，成本约 4；全表扫描要读几千页并遍历 100 万行，成本高得多。
  • 依赖表的统计信息估算成本，包括表有多少行、索引有多少个不同值、数据分布是否均匀。I/O 成本直观是因为 MySQL 按页读，一页 16KB，即使只查一条也要整页加载进内存，这是空间局部性原理；走索引查单条 B+ 树一般 34 层定位到叶子节点，读 34 个页，而 10GB 数据全表扫约 65 万个页。CPU 成本主要看扫描行数，扫 100 万行就是 100 万次比较。
  • 优化器可能选错索引，根因是统计信息不准：MySQL 用采样而非精确统计收集，数据分布不均时估算会偏，比如订单表 99% 是「已完成」、1% 是「待支付」，统计信息告诉优化器区分度还行，实际查「已完成」时走索引反而更慢，因为要回表 99% 的数据。
  • 处理办法：ANALYZE TABLE orders; 更新统计信息，SHOW INDEX FROM orders; 查看统计信息；确定选错时可用 SELECT * FROM orders FORCE INDEX(idx_status) WHERE status = 'pending'; 强制指定索引，但这是下策，治标不治本，更好的做法是优化表结构或索引设计。
  • 查询重写：常量折叠，WHERE age > 10 + 8 重写为 WHERE age > 18；子查询展开，WHERE user_id IN (SELECT id FROM users WHERE vip = 1) 可能被重写成 SELECT orders.* FROM orders JOIN users ON orders.user_id = users.id WHERE users.vip = 1，展开后优化器能更好评估整体成本、选择合适的连接顺序和连接算法。
  • 多表 JOIN 的连接顺序影响巨大：A 表 1000 万行、B 表 100 行，B 驱动 A 只需循环 100 次，反过来要循环 1000 万次，差 10 万倍。优化器会枚举所有可能的连接顺序算成本选最低，但排列组合是阶乘级别，10 张表就 360 万种组合，所以有 optimizer_search_depth 控制搜索深度，超出就用贪心算法凑合。

9. 为什么 MySQL 索引用的是 B+ 树而不是红黑树？

🎬 面试现场

面试官（口语化）：索引为什么选 B+ 树？红黑树不是也能存数据吗？

⚠️ 翻车点

只答「B+ 树矮、I/O 少」是不够的，漏掉「叶子节点双向链表做范围查询」和「非叶子节点不存数据所以扇出大」这两条加分点；更要命的是把 B 树和 B+ 树搞混——B 树的非叶子节点也存数据。

📝 现场作答

  • 核心原因就一个：磁盘 IO 次数。红黑树是二叉树，每个节点最多两个子节点，存 2000 万条数据树高约 24-25 层，每访问一个节点就是一次磁盘随机 IO（一次约 10ms），24 层就是 240ms；B+ 树是多叉树，每个节点能存上千个索引项，2000 万条数据树高只要 3 层，3 次 IO 约 30ms，快一个数量级。
  • 内存访问一次约 100 纳秒、磁盘随机 IO 一次约 10 毫秒，差了 10 万倍。内存里红黑树 24 层只是 2400 纳秒，微秒级搞定；磁盘上就是 240ms。内存数据结构追求操作简单、平衡性好（红黑树插删都是 O(log n)，Java 的 TreeMap、HashMap 冲突链表转红黑树就是这个逻辑）；磁盘数据结构追求 IO 次数少，B+ 树加大扇出把树压扁，3-4 层撑千万级数据。
  • B+ 树「矮胖」的算法：节点大小通常设成磁盘页大小，InnoDB 默认 16KB；主键 bigint 8 字节 + 指针 6 字节 = 14 字节一个索引项，16KB 能存 16 × 1024 ÷ 14 ≈ 1170 个索引项，也就是一个非叶子节点有 1170 个子节点。1170 扇出意味着两层约 137 万条、三层约 16 亿条；红黑树扇出固定是 2，log₂(20000000) ≈ 24.25，要 24-25 层。
  • 范围查询：B+ 树所有数据都在叶子节点、叶子之间双向链表连接，先找到范围起点再顺链表后扫，是顺序 IO；红黑树要找起点后做中序遍历，每访问一个节点都可能跳到不相邻位置，磁盘上就是大量随机 IO。
  • 不用 B 树的原因：B 树非叶子节点也存数据。B+ 树这样设计有两个好处——非叶子节点不存数据能塞更多索引项、扇出更大树更矮；所有查询都要走到叶子节点，性能稳定，不会出现有时第二层查到、有时第四层才查到。
  • MongoDB 用的是 B 树，因为其场景更多是单条查询、范围查询相对少；MySQL 范围查询多，B+ 树的链表结构更合适。
  • 红黑树在数据库并非完全无用：Buffer Pool 管理脏页列表、空闲列表等内存结构就可以用红黑树，因为都在内存里、数据量不大、实现简单性能也够。

B+ 树的节点大小为什么是 16KB？能改吗？ 16KB 是 InnoDB 默认页大小，与操作系统页对齐，一次磁盘 IO 正好读一整页效率最高。可以改，innodb_page_size 支持 4KB、8KB、16KB、32KB、64KB，但只能在数据库初始化时设置，之后改不了。页太小扇出变小树变高，页太大内存利用率低、刷脏页开销大，一般保持默认即可。
红黑树插删比 B+ 树简单在哪？ 红黑树每次插删只需几次旋转和变色，最多涉及 3-4 个节点；B+ 树插入可能触发节点分裂（一个节点变两个）并向上递归到根，删除可能触发节点合并并递归到上层，涉及节点多、操作复杂，而且每个节点都在磁盘上，改一次就是一次 IO。
为什么说 B+ 树查询性能稳定？ 因为数据全在叶子节点，所有查询都要走完从根到叶子的完整路径，树有几层就是几次 IO，非常稳定；B 树数据分布在各层，运气好在第二层就查到、运气差要到最底层，性能波动大。数据库需要可预测的响应时间，稳定性很重要。

  • “B 树和 B+ 树是一回事，只是叫法不同。” —— B 树非叶子节点也存数据。
  • “MySQL 里凡是排序结构都用 B+ 树，红黑树完全用不到。” —— Buffer Pool 的脏页列表、空闲列表等内存结构就会用到红黑树。

10. MySQL 是如何实现事务的？

🎬 面试现场

面试官（口语化）：你给我讲讲 MySQL 的事务到底是怎么落地的？靠哪几个东西支撑的？

⚠️ 翻车点

只答「靠 redo log 和 undo log」会被立刻追打：一致性不是单独实现的组件，锁和 MVCC 才是隔离性的真正承载者，四个组件各对应 ACID 的不同侧面。

📝 现场作答

  • 四个核心组件：Redo Log、Undo Log、锁、MVCC，分别对应 ACID 的不同方面。Redo Log 保证持久性，Undo Log 保证原子性，锁机制和 MVCC 保证隔离性，一致性是三者共同作用的结果。
  • Redo Log 走 WAL 机制：先把修改顺序写到 redo log，再找机会把数据页刷盘，顺序写比随机写快几个数量级。
  • redo log 采用循环写，有两个指针：write pos 表示当前写到哪，checkpoint 表示已经刷盘的位置，两者之间是待刷盘的脏数据，checkpoint 之前可以覆盖复用空间。
  • 事务提交时 redo log 必须落盘，由 innodb_flush_log_at_trx_commit 控制：设成 1 每次提交都刷盘（最安全最慢），设成 0 每秒刷一次（宕机可能丢 1 秒数据），设成 2 写到操作系统 page cache（MySQL 挂了数据还在，机器挂了才丢）。
  • Undo Log 在每次修改前把原值存进去，回滚时按 undo log 反向操作恢复，保证要么全做完要么全撤销。
  • 每条记录有两个隐藏字段：trx_id 记录最后修改该数据的事务 ID，roll_pointer 指向 undo log 里的上一个版本，多次修改串成版本链。
  • InnoDB 三种行锁：Record Lock 锁单条记录，Gap Lock 锁区间不包含记录本身，Next-Key Lock 是 Record Lock + Gap Lock，可重复读级别下默认用 Next-Key Lock 防幻读。
  • 行锁是加在索引上的，不是加在数据行上；SQL 没走索引就会锁全表，这是常见踩坑点。
  • 两阶段提交保证 redo log 与 binlog 一致：prepare 阶段 redo log 写盘并标记 prepare，commit 阶段 binlog 写盘后把 redo log 状态改成 commit；恢复时按 XID 是否匹配来决定提交还是回滚。

innodb_flush_log_at_trx_commit 设成 2 和 0 有什么区别？ 0 是每秒把 redo log 从 log buffer 刷到磁盘，MySQL 进程挂了就丢 1 秒数据；2 是每次提交写到 OS 的 page cache，MySQL 挂了数据还在 page cache，但机器断电就丢。2 比 0 安全一点，性能差不多。
MVCC 能解决幻读吗？ 能解决快照读的幻读，解决不了当前读的幻读。快照读走版本链，ReadView 定死可见范围；当前读（如 select … for update）读最新数据，要靠间隙锁防幻读。
undo log 什么时候会被清理？ 不是事务提交就能删，要等没有事务需要用到这些旧版本。purge 线程扫描活跃事务，找到最老的 ReadView，比它还老的 undo log 才能删除，所以长事务会导致 undo log 堆积。
为什么 redo log 循环写而 binlog 一直追加？ redo log 用于崩溃恢复，checkpoint 之前的日志对应数据页已刷盘，可以覆盖复用空间，否则磁盘会被撑爆；binlog 用于主从复制和数据恢复，历史记录不能丢。

  • “MySQL 事务就是靠 redo log 和 undo log 实现的”（漏掉锁和 MVCC，一致性也不是独立实现的）
  • “MVCC 能彻底解决幻读”（当前读的幻读要靠间隙锁，不是 MVCC）

11. MySQL 中的 MVCC 是什么？

🎬 面试现场

面试官（口语化）：MVCC 到底是个什么机制？InnoDB 是怎么做到读写不互相阻塞的？

⚠️ 翻车点

把 MVCC 说成「存了好几份数据」是错的：InnoDB 数据页上只存最新版本，历史版本全在 undo log 里，靠 roll_pointer 串成版本链。

📝 现场作答

  • MVCC 全称 Multi-Version Concurrency Control，核心思想是让读写操作互不阻塞：写操作不覆盖原数据而是生成新版本，读操作根据事务启动时间在版本链上找到属于自己的版本。
  • 每条记录有两个隐藏字段：trx_id 记录最后修改该数据的事务 ID，roll_pointer 指向 undo log 指针；每次 UPDATE 把旧值写进 undo log、新值写进数据页，roll_pointer 指向旧版本。
  • undo log 类型上，INSERT 产生的是 TRX_UNDO_INSERT_REC（里存主键信息，回滚时按主键找到记录删掉），事务提交后就回收；UPDATE 产生的是 TRX_UNDO_UPD_EXIST_REC，不会马上删，因为可能有别的事务要读历史版本。
  • ReadView 有四个关键字段：creator_trx_id（当前事务 ID，只读事务为 0）、m_ids（生成 ReadView 时所有活跃事务的 ID 列表）、min_trx_id（m_ids 中的最小值）、max_trx_id（下一个将被分配的事务 ID）。
  • 可见性判断规则：trx_id == creator_trx_id 可见；trx_id < min_trx_id 可见；trx_id >= max_trx_id 不可见；min_trx_id <= trx_id < max_trx_id 时看是否在 m_ids 里，不在则可见。
  • 读已提交和可重复读的判断逻辑完全一样，差别只在 ReadView 生成时机：RC 每次 SELECT 重新生成，RR 第一次 SELECT 生成后一直复用，所以一个事务里看到的是同一个 ReadView。
  • 快照读是普通 SELECT，走 MVCC 不加锁读历史快照；当前读是 SELECT … FOR UPDATE、SELECT … LOCK IN SHARE MODE、UPDATE、DELETE，必须读最新版本并加锁，会加 Next-Key Lock 锁住记录和间隙。
  • 可重复读并不能完全避免幻读：先快照读再当前读，事务 2 插入的新数据在当前读里能看到，两次结果行数就不一样了；解决办法是从头就用 SELECT … FOR UPDATE。

💡 主动加分的追问准备

面试官追问 你的答案
MVCC 能不能解决写写冲突？ 不能。MVCC 解决的是读写冲突，让普通读不阻塞写、写不阻塞普通读；写写冲突靠锁，两个事务同时 UPDATE 同一行，后一个要等前一个提交或回滚。
为什么 ReadView 里要记 max_trx_id，只用 m_ids 不行吗？ 不行。m_ids 只记录生成 ReadView 那一刻的活跃事务，之后新启动的事务 ID 肯定更大，只用 m_ids 会把新事务的修改当成已提交看到。max_trx_id 就是用来挡住这些后来者的，trx_id >= max_trx_id 一律不可见。
只读事务 creator_trx_id 是 0，那自己改的数据怎么算可见？ 只读事务不会有修改操作，不存在这个场景；一旦有写操作，InnoDB 会分配真正的事务 ID，creator_trx_id 就不再是 0。
undo log 什么时候清理？ INSERT 产生的 undo log 提交后立刻可清；UPDATE 和 DELETE 产生的要等到没有事务需要该版本。后台 purge 线程根据活跃事务的 ReadView 判断哪些可安全删除，长事务会导致 undo log 堆积。

❌ 千万别说的话

  • “MVCC 就是给数据存多个版本”（数据页只有最新版本，历史版本在 undo log）
  • “ReadView 的 max_trx_id 是当前最大已分配事务 ID”（是下一个将被分配的事务 ID）

12. 如果 MySQL 中没有 MVCC，会有什么影响？

🎬 面试现场

面试官（口语化）：假如 MySQL 没有 MVCC，会变成什么样？为什么大厂都想要 MVCC？

⚠️ 翻车点

只答「锁变多、并发变低」不够。要说清读写互斥的根源：没有历史版本时，读要么读脏数据要么读不到旧值，只能等写事务结束，也就是 LBCC。

📝 现场作答

  • 没有 MVCC 就得靠加锁保证一致性，这套方案叫 LBCC（Lock-Based Concurrency Control）：读要等写完，写要等读完，系统吞吐量直接腰斩。
  • 具体场景：事务 2 把记录 A 从 100 改成 200 还没提交，事务 1 想读——读 200 是脏读，读 100 旧值已经找不到（数据已被改成 200），纯 LBCC 下唯一办法就是让事务 1 阻塞等事务 2 提交或回滚。
  • MVCC 的价值：写操作产生新版本，读操作沿版本链找属于自己的版本，读写各走各的互不干扰，普通 SELECT 压根不加锁。
  • PostgreSQL 也用 MVCC，但旧版本真的存在数据页里，靠后台 VACUUM 进程定期清理过期版本；优点是回滚快，缺点是存储空间消耗大，VACUUM 不及时表会膨胀。
  • Oracle 的 MVCC 与 MySQL 类似，也用 undo 段存历史版本，但 undo 段是共享的，空间不够时旧版本会被覆盖，查询可能报 “ORA-01555: snapshot too old”；MySQL 的 undo log 在事务需要时不会被清理，不会出这个问题。
  • MySQL 里不是所有存储引擎都有 MVCC：MyISAM 没有，只支持表锁，读时整张表都锁住，写要等所有读完成，所以高并发写场景性能很差。
  • InnoDB 在 MySQL 5.1 之后成为默认引擎，很大一部分原因就是 MVCC 带来的高并发能力。

面试官追问 你的答案
MVCC 是万能的吗？有没有 MVCC 也搞不定的场景？ MVCC 只解决读写冲突，写写冲突还是靠锁，两个事务同时 UPDATE 同一行，后来的必须等先来的提交或回滚。另外当前读（SELECT … FOR UPDATE）不走 MVCC，直接读最新版本加锁。
长事务一直不提交，MVCC 会有什么问题？ undo log 堆积。长事务的 ReadView 很早，它需要的历史版本就一直不能清理，极端情况下 undo log 占用几个 G 甚至几十个 G，所以阿里规范要求单个事务不超过 5 秒。
LBCC 就没有优点吗？ 实现简单是它最大的优点。MVCC 要维护版本链和 ReadView，逻辑复杂不少；并发不高的场景 LBCC 足够用，还好维护，早期不少嵌入式数据库就是纯 LBCC。

❌ 千万别说的话

  • “没有 MVCC 就是完全串行执行”（是读写互斥，锁粒度问题，不是全局排队）
  • “MySQL 的 MVCC 和 PostgreSQL 一样把多版本存在数据页里”（PG 才这么做，MySQL 存在 undo log）

13. MySQL 中的事务隔离级别有哪些？

🎬 面试现场

面试官（口语化）：MySQL 有哪几个事务隔离级别？分别对应什么问题？默认是哪个？

⚠️ 翻车点

最容易错的是把 InnoDB 的可重复读说成「彻底消除了幻读」——它只是大幅缓解，快照读和当前读混用仍会出现幻读。

📝 现场作答

  • 四种隔离级别，按隔离性从低到高：读未提交 READ UNCOMMITTED、读已提交 READ COMMITTED、可重复读 REPEATABLE READ、串行化 SERIALIZABLE。
  • 读未提交：能看到别的事务未提交的数据，等于毫无隔离，典型问题是脏读，读到的数据可能人家一会儿就回滚了。
  • 读已提交：只能看到已提交的数据，脏读消失，但同一事务两次查同一条数据结果可能不同，即不可重复读；Oracle、PostgreSQL、SQL Server 默认是这个级别。
  • 可重复读：事务开始后看到的永远是开始那一刻的快照，MySQL InnoDB 默认级别，用 MVCC 实现；但标准 SQL 定义下这个级别仍会有幻读（两次范围查询返回行数不同）。
  • 串行化：最严格，事务排队执行，相当于把并发关了；InnoDB 在这个级别下会把普通 SELECT 自动加上共享锁，能杜绝所有并发问题，但性能基本废了。
  • MySQL 默认 RR 是历史原因：早期主从复制用 Statement 格式 binlog，读已提交下同一事务两次读可能不同，导致主从执行同一条 SQL 结果对不上；可重复读天然保证事务内数据一致，配合 binlog 复制更稳。现在有 Row 格式 binlog 后 RC 也能用，但默认值一直没改。
  • 互联网公司基本都调成 RC：RR 下要维护更多 undo log 版本链、长事务内存消耗大；RR 的间隙锁范围更大，容易锁等待甚至死锁；业务上多数场景不需要「同一事务内数据不变」。
  • InnoDB 缓解幻读的两招：快照读走 MVCC 看不到别人新插入的行；当前读加间隙锁锁住索引记录之间的间隙，别人往这个范围插数据直接被阻塞。坑是先快照读再当前读，两次结果可能不一样。
  • 串行化级别下如果关闭 autocommit，普通 SELECT 会被隐式转成 SELECT … FOR SHARE，即加共享锁，读写都排队。

从可重复读调成读已提交，业务代码要注意什么？ 两点：一是同一事务多次查同一数据可能拿到不同结果，若业务依赖「读到的事务内不变」这个假设要重新审视；二是间隙锁没了，UPDATE、DELETE 锁范围变小，并发插入的幻读要靠业务层或唯一索引兜底。

14. MySQL 中有哪些锁类型？

🎬 面试现场

面试官（口语化）：MySQL 有哪些锁？从粒度和模式两个维度说说，再讲讲间隙锁和临键锁。

⚠️ 翻车点

最容易翻车的是「记录锁是加在行上的」——记录锁实际作用在索引记录上；没走索引时会把扫到的所有行都锁住，效果等于表锁。

📝 现场作答

  • 两个维度分类：粒度上分表锁和行锁，粒度越细并发越高；模式上分共享锁 S 锁和排他锁 X 锁，S 锁之间互不冲突，X 锁独占且与 S 锁冲突。
  • SELECT ... LOCK IN SHARE MODE 取 S 锁，SELECT ... FOR UPDATE 取 X 锁；MyISAM 只支持表锁，InnoDB 两者都支持；LOCK TABLES yes READ 是表级 S 锁，LOCK TABLES yes WRITE 是表级 X 锁。
  • 元数据锁 MDL 分读锁（MDL_SHARED，SELECT 时获取，多个事务可同时持有）和写锁（MDL_EXCLUSIVE，ALTER TABLE 时获取，阻塞其他一切读写锁）；作用是防止并发 DDL 与 DML 冲突，并保护元数据一致性。
  • 意向锁 IS / IX 是表级锁：给表中某行加 S 锁前先在表上加 IS 锁，加 X 锁前先加 IX 锁，这样后续加表级锁只需看表上有没有 IS/IX，不必遍历所有记录。IS 与 IX 互相不冲突。
  • 行锁三种：记录锁（锁当前记录，作用在索引上，即使没主键也会有隐藏的聚簇索引）、间隙锁（锁记录之间的间隙，阻止插入）、临键锁（记录锁 + 间隙锁，前开后闭区间如 (3,5]，能防止查询 id=5 的幻读）。
  • 数据页里除真实记录外还有 Infimum 和 Supremum 两条虚拟记录，记录之间都存在间隙。
  • 间隙锁之间不冲突，唯一目的就是防止别的事务往间隙里插数据；可重复读级别生效，改成 READ COMMITTED 后对搜索和索引扫描禁用间隙锁，仅保留用于外键约束检查和重复键检查。
  • 插入意向锁 Insert Intention Locks 不锁间隙，而是等待某个间隙：被间隙锁阻塞的插入事务会生成插入意向锁，插入意向锁之间不阻塞，这样持有间隙锁的事务释放时能找到等待者并唤醒。
  • Auto-Inc Lock 是自增列插入时的特殊表级锁，插入语句结束才释放；MySQL 5.1.22 之后引入互斥量，取得递增值即可释放锁，性能更好。
  • innodb_autoinc_lock_mode 三个取值：0 只用 Auto-Inc Lock；1（默认）已知插入行数用互斥量、未知用 Auto-Inc Lock，这样基于 statement-based binlog 复制也安全；2 只用互斥量。
  • 谓词锁 Predicate Locks 用于空间索引：多维数据没有绝对排序，next-key locking 不好使，于是基于查询的最小边界矩形 MBR 设置谓词锁，其他事务无法插入或修改匹配的行。

什么情况会触发表锁而不是行锁？ 三种：查询没走索引只能全表扫描，锁加到所有扫到的记录上，效果等于表锁；显式用 LOCK TABLES；DDL 如 ALTER TABLE 会加 MDL 写锁。

15. 你们生产环境的 MySQL 中使用了什么事务隔离级别？为什么？

🎬 面试现场

面试官（口语化）：你们线上用的什么隔离级别？为什么这么选？跟默认值不一样的话，代价是什么？

⚠️ 翻车点

只说「RC 并发高」会漏掉半一致性读这个关键机制，也说不出 RC 下 binlog 必须用 ROW 格式的原因。

📝 现场作答

  • MySQL 默认 RR，但很多互联网公司生产用 RC，核心目的是提高并发、降低死锁概率：RR 为防幻读引入间隙锁和临键锁，锁范围更大；RC 只用行锁，锁定范围小、并发能力更强。
  • 官方例子对比：表 t 有 5 行 (1,2),(2,3),(3,2),(4,3),(5,2)，执行 UPDATE t SET b = 5 WHERE b = 3 不提交——RR 下 5 行全部加 x-lock 并保留，后续 UPDATE t SET b = 4 WHERE b = 2 直接被阻塞。
  • 换成 RC，SQL-A 只保留真正更新的 2 行的锁，其余行加锁后立即释放；此时 SQL-B 能顺利执行并锁住 b=2 的 3 行，完美避开 SQL-A 加的锁。
  • 半一致性读：RC 下 UPDATE 扫描到某行发现被锁，InnoDB 不会傻等，而是读该行最新已提交版本判断是否满足 WHERE 条件，不满足就跳过不等锁。例中 (2,3) 已被改成 (2,5)，而 SQL-B 要更新 b=2 的行，读最新版本发现 b=5 不满足条件，所以不用等这把锁。
  • 半一致性读只在 RC 级别生效，RR 下不会触发，这是 RC 并发更高的重要原因。
  • RC 没有间隙锁确实可能幻读，处理方式：多数业务场景影响不大可忽略；有影响的用乐观锁（加 version 字段，更新时带版本号校验）；极少数强一致场景手动加锁 SELECT … FOR UPDATE 或临时改成 RR。
  • 大厂选 RC 的四个理由：并发量大、RC 锁粒度小能扛更多 QPS；死锁风险低运维成本小（RR 间隙锁很容易死锁）；binlog 用 ROW 格式做主从复制，不依赖 RR 保证复制一致性；幻读问题在业务层面好解决。银行、证券这类金融系统一致性要求极高，仍会用 RR 甚至 SERIALIZABLE。
  • 改隔离级别不需要重启：SET GLOBAL transaction_isolation = 'READ-COMMITTED'，新连接生效、已有连接需断开重连；也可写进 my.cnf 供下次重启生效，改之前最好确认 binlog 是 ROW 格式。

面试官追问 你的答案
RC 级别下 binlog 必须用什么格式，为什么？ 必须 ROW。STATEMENT 记 SQL 原文，RC 下没有间隙锁，主从执行顺序可能不同导致不一致，比如并发插入时自增 ID 对不上；ROW 记录具体改了哪些行、值是什么，不论顺序如何最终结果一致。
生产环境怎么改隔离级别，需要重启吗？ 不需要重启。在线改全局参数 SET GLOBAL transaction_isolation = 'READ-COMMITTED'，新连接用新级别，已有连接断开重连才生效；也可写 my.cnf 下次重启生效。改之前确认 binlog 是 ROW 格式。
什么情况下 RC 会退化成表锁？ UPDATE 或 DELETE 的 WHERE 条件没走索引时。行锁加在索引上，没走索引就得扫全表、每扫一行锁一行，扫描期间整表基本处于锁定状态；所以即使用 RC 也要保证 UPDATE、DELETE 走索引，否则并发优势就没了。
间隙锁具体怎么加的，举个例子？ 锁的是索引记录之间的间隙。比如 id = 1, 5, 10 三条记录，RR 下执行 SELECT * FROM t WHERE id > 3 FOR UPDATE 会锁住 (3,5]、(5,10]、(10,+∞)，别的事务想插 id = 4 就会被阻塞，即使该行还不存在。

16. MySQL 事务的二阶段提交是什么？

🎬 面试现场

面试官（口语化）：MySQL 为什么要搞二阶段提交？redo log 和 binlog 怎么保证一致？

⚠️ 翻车点

把二阶段提交说成「先写 redo 再写 binlog」就等于没答——那正是没有二阶段时会出问题的顺序；关键在于 prepare 状态 + XID 匹配。

📝 现场作答

  • 二阶段提交是保证 redo log（InnoDB 引擎层）和 binlog（Server 层）数据一致性的机制，两层日志各自独立，写入过程宕机就可能两边对不上。
  • Prepare 阶段：事务提交时 InnoDB 先把修改写到 redo log，状态标记为 prepare，表示准备好了但还没真正提交。
  • Commit 阶段：redo log 写完后 Server 层把操作写到 binlog，binlog 落盘成功再通知 InnoDB 把 redo log 状态改成 commit，事务才算提交完成。
  • redo log 记的是数据页的物理修改（如「第 5 号数据页偏移量 100 处写入 xxx」），是固定大小的环形日志，写满从头覆盖，用于崩溃恢复；binlog 记的是逻辑操作（如 UPDATE user SET age=18 WHERE id=1），追加写入不覆盖，用于主从复制、数据恢复和备份归档。
  • 不用二阶段的两种顺序都会主从不一致：先 redo 后 binlog，redo 写完宕机则 InnoDB 恢复出这条数据而从库拿不到 binlog；先 binlog 后 redo，binlog 写完宕机则从库有、主库恢复后没有。
  • 二阶段下的崩溃恢复判断：redo log 是 prepare 且 binlog 没写 → 回滚；redo log 是 prepare 且 binlog 已写 → 检查两边 XID 是否匹配，匹配就提交。
  • 两阶段提交本质是经典分布式事务方案——大家都点头 ok 了才提交，避免后续回滚或补数据的麻烦。
  • 组提交优化：多个事务同时提交时先写进日志缓冲区，攒够一定大小或等一定时间再一把 fsync；binlog 侧由 binlog_group_commit_sync_delay（延迟多少微秒再 fsync）和 binlog_group_commit_sync_no_delay_count（攒够多少次再 fsync）控制。
  • innodb_flush_log_at_trx_commit：1 每次提交都刷盘（安全性最高、性能最低），2 写到 OS 缓存每秒刷盘（中等、较高），0 写到 log buffer 每秒刷盘（最低、最高）；生产一般设 1，压测或能接受丢 1 秒数据的场景可设 2。

💡 主动加分的追问准备

面试官追问 你的答案
为什么不直接把 redo log 和 binlog 合成一个日志？ 它们服务于不同场景：redo log 是 InnoDB 引擎私有的物理修改日志、循环写、保证崩溃恢复；binlog 是 Server 层的逻辑操作日志、追加写、做主从复制和归档。Server 层与存储引擎层分层独立，强行合并会破坏分层设计，且 binlog 格式要兼容各种存储引擎。
binlog 写成功但通知 InnoDB commit 失败会怎样？ redo log 还是 prepare 状态。重启恢复时 MySQL 拿 redo log 里的 XID 去 binlog 查，能查到说明 binlog 完整，就把事务提交掉，不会丢数据也不会不一致。
组提交攒太久会不会有问题？ 会。攒久了事务响应时间变长，用户感知是「提交卡了一下」；这段时间宕机还可能整批事务丢失。所以生产不会把 delay 设太大，几百微秒到几毫秒即可。
从库复制时也有二阶段提交吗？ 从库执行 relay log 里的事务时也会写 redo log 和 binlog，所以也走二阶段提交。不过从库的 binlog 是可选的，不需要级联复制可以关掉，关掉后只写 redo log，不需要二阶段。

  • “二阶段提交就是先写 redo log 再写 binlog”（这只是顺序，真正的关键是 prepare 状态与 XID 匹配）
  • “redo log 和 binlog 是一回事，合并就行”（一个物理一个逻辑，层级与用途都不同）

17. MySQL 的 Doublewrite Buffer 是什么？它有什么作用？

🎬 面试现场

面试官（口语化）：MySQL 有 redo log 了，为什么还要 Doublewrite Buffer？它俩管的是一回事吗？

⚠️ 翻车点

把 Doublewrite 说成「数据丢不了的保险」——它防的是页损坏（torn page），redo log 防的是数据丢失，两者解决的是不同问题。

📝 现场作答

  • Doublewrite Buffer 是 InnoDB 用来解决部分页写入问题（torn page）的安全机制。InnoDB 一页 16KB，而操作系统的 I/O 单位通常是 4KB，写一个 InnoDB 页需要 4 次系统 I/O；如果写到一半断电，只写了 1 个 4KB，这页既不是旧数据也不是新数据，处于半死不活的状态。
  • 做法是：在把脏页刷到数据文件之前，先把数据写到一个专门的区域做备份；万一刷盘过程中断电，恢复时可以从备份区域把完整的页拿出来重新写一遍，保证数据不会损坏。
  • redo log 救不了部分写问题：redo log 记录的是物理逻辑日志，是在页的基础上做修改（比如「第 5 页偏移量 100 处改成 xxx」），如果页本身已经损坏，redo log 往坏页上重放结果还是坏页。redo log 的前提是页本身得完整，它解决「数据丢失」，不解决「数据损坏」。
  • 完整写入流程：①脏页要刷盘时先把这批页拷贝到内存中的 Doublewrite Buffer；②Doublewrite Buffer 写满或触发刷新条件后，先把数据顺序写到磁盘上的 Doublewrite 文件（顺序写，性能不差）；③Doublewrite 文件写完后，再把数据页写到它真正该去的数据文件位置（随机写）；④如果第 3 步写到一半挂了，恢复时 InnoDB 会检查数据文件中的页是否完整，发现损坏就从 Doublewrite 文件里把备份拿出来覆盖坏页，然后正常走 redo log 恢复流程。
  • 存储位置：MySQL 8.0.20 之前 Doublewrite Buffer 存在系统表空间 ibdata1 里，占用 2MB，分成两个 1MB 区域，每个区域能存 64 个 16KB 的页；8.0.20 开始被移到独立文件，默认是 #ib_16384_0.dblwr 和 #ib_16384_1.dblwr，好处是可以放到更快的存储设备上。
  • 性能影响不大：写 Doublewrite Buffer 是内存拷贝非常快；刷到 Doublewrite 文件是顺序写，机械盘顺序写性能也能到 100MB/s 以上；这批页攒够了再一起刷，摊薄了每个页的开销。实测开启 Doublewrite 大概带来 5%-10% 的性能损失。
  • 什么时候可以关掉：存储本身能保证原子写 16KB 时就不需要，比如支持原子写的文件系统（ZFS、某些配置下的 XFS）、带电容保护的企业级 SSD 或存储阵列、能保证原子写的 Fusion-io 之类设备。关闭方式是 innodb_doublewrite=OFF，但除非确认存储层能兜底否则别关。

面试官追问 你的答案
Doublewrite Buffer 和 redo log 都能保证数据不丢，有什么区别？ redo log 保证事务持久性，写顺序日志比写数据页快，事务提交时只要 redo log 落盘就能返回成功；Doublewrite 保证页完整性，防止刷脏页时断电导致页损坏。redo log 解决「数据丢失」，Doublewrite 解决「数据损坏」；而且 redo log 恢复的前提是页本身完整，页都坏了 redo log 也无能为力，这时得靠 Doublewrite 里的备份。
为什么不直接把 redo log 的页面粒度改成 16KB，这样不就不需要 Doublewrite 了？ redo log 记录的是增量修改不是整页内容，一个事务可能只改了页里几个字节，每次都记整页会导致日志量暴增、写入性能大幅下降。redo log 的设计目标就是尽可能小、尽可能快，让事务能快速提交；而 Doublewrite 只在刷脏页时才触发，频率比 redo log 低得多，多写一份备份的开销可以接受。
MySQL 8.0 把 Doublewrite 移到独立文件有什么好处？ 最大好处是可以把 Doublewrite 文件放到单独磁盘或更快的存储设备上。以前它在 ibdata1 里和数据一起抢 I/O 带宽，现在分开了可以用一块便宜的 SSD 专门放 Doublewrite 文件、主存储放正常数据，I/O 隔离互不影响；独立文件也方便监控和调优，能单独看这部分 I/O 情况。

  • “Doublewrite Buffer 是把数据写两遍，性能砍半”——实际只有 5%-10% 的损失，顺序写摊薄了成本。
  • “Doublewrite 可以随意关闭省性能”——只有存储层能保证原子写 16KB 时才可以关。

三、SQL 执行与调优：从一条 SQL 到慢查询治理

18. 详细描述一条 SQL 语句在 MySQL 中的执行过程。

🎬 面试现场

面试官（口语化）：你给我从头讲一遍，一条 SELECT 语句丢进 MySQL 之后，到底经历了哪些环节才把结果返回给我？

⚠️ 翻车点

最常翻车的是把「分析器」和「优化器」讲成一回事。分析器只负责 SQL 写得对不对（词法分析、语法分析、生成 AST），优化器才负责怎么执行最快（选索引、决定 JOIN 顺序、是否改写子查询）。另外 MySQL 8.0 已经砍掉了查询缓存，别再把「查查询缓存」当成流程必答项。

📝 现场作答

  • MySQL 架构分两层：Server 层负责连接管理、SQL 解析、查询优化等逻辑处理，存储引擎层负责数据的实际存取。
  • 连接器：客户端先与 MySQL 建立连接（TCP 三次握手），连接器验证账号密码和权限；权限在连接建立时从权限表读取，连接中途用 GRANT 改权限也要重新连接才生效。空闲连接默认 8 小时后断开，由 wait_timeout 控制；长连接会导致执行过程的临时内存不释放，可用定期断开重连或 MySQL 5.7 之后的 mysql_reset_connection 重置连接状态。
  • 查询缓存：老版本会先查查询缓存，MySQL 8.0 已砍掉该功能——表一更新缓存就全部失效，命中率太低。
  • 分析器：先做词法分析，把 SQL 拆成一个个 token（SELECT 是关键字、* 表示所有列、user 是表名、id 是列名、1 是常量）；再做语法分析按 MySQL 语法规则检查，语法有问题报 You have an error in your SQL syntax；最后生成一棵描述 SQL 结构的抽象语法树 AST。
  • 优化器：拿到 AST 后决定用哪个索引、怎么扫描表；多表 JOIN 决定连接顺序，一般原则是小表驱动大表；有多个索引可选时根据统计信息估算各方案成本、选代价最小的；还会做 SQL 改写，如把子查询转成 JOIN、常量折叠、条件下推，最终生成执行计划，可用 EXPLAIN 查看。
  • 执行器：按执行计划先再检查一次对这张表的查询权限，然后调用存储引擎的 Handler API 一行一行读数据并做条件过滤，最后返回结果集。InnoDB 通过主键索引在 B+ 树上找到叶子节点拿到完整行；若条件是 WHERE name = 'Yes' 这类非主键，则走二级索引先拿到主键值再回表。
  • 更新语句（INSERT/UPDATE/DELETE）前面的连接、解析、优化流程相同，区别在执行阶段：先写 redo log 记录物理变化，再写 undo log 记录修改前数据用于回滚，Server 层写 binlog 用于主从复制；redo log 与 binlog 用两阶段提交保证一致——redo log 先标 prepare，再写 binlog，最后把 redo log 标 commit。锁方面 InnoDB 默认行锁，通过 MVCC 实现读写不阻塞，UPDATE 先读行加排他锁，事务提交时释放。
  • 优化器不是万能的：统计信息过期（未及时 ANALYZE TABLE）、数据分布不均匀按平均值估算、多个索引可选时选错，都会导致执行计划不对；可用 FORCE INDEX 强制索引或 STRAIGHT_JOIN 强制连接顺序，但根本办法是保证统计信息准确、索引设计合理。

面试官追问 你的答案
分析器和优化器有什么区别？ 分析器只管 SQL 写得对不对：拆 token、检查语法、生成描述结构的语法树。优化器拿这棵树决定怎么执行：选哪个索引、JOIN 的连接顺序、子查询要不要改写。同一 SQL 语法树是固定的，但执行计划可以有很多种，优化器负责挑成本最低的。
为什么 MySQL 8.0 砍掉查询缓存？ 查询缓存失效策略太激进，表上有任何写操作，这张表相关缓存全部失效，高并发写场景几乎命中不了，反而增加维护开销。读多写少用 Redis 这类专业缓存更合适。
执行器调用的存储引擎接口长什么样？ 是统一的 Handler API：ha_open 打开表、ha_rnd_next 全表扫描读下一行、ha_index_read 索引定位读取、ha_write_row 写入一行、ha_delete_row 删除一行。不同存储引擎各自实现，Server 层不关心底层是 InnoDB 还是 MyISAM。
EXPLAIN 看到走了索引但查询还是很慢，可能是什么原因？ ①回表次数太多，二级索引命中几十万行每行都要回表，随机 IO 拉垮；②索引选择性太差，比如性别字段；③返回字段太多不是覆盖索引，传输耗时；④索引树太大内存装不下频繁读磁盘。重点看 rows 估算值和 Extra 里有没有 Using filesort、Using temporary。

❌ 千万别说的话

  • “MySQL 会先查查询缓存。”——MySQL 8.0 已经砍掉这个功能，别把它当成标准流程讲。
  • “分析器和优化器是一回事，都是解析 SQL 的。”——职责完全不同，语法树由分析器生成、执行计划由优化器决定。

19. MySQL 中如何进行 SQL 调优？

🎬 面试现场

面试官（口语化）：线上有一条 SQL 跑得特别慢，落到你头上，你这套 SQL 调优的方法论是什么？

⚠️ 翻车点

别只答「加索引」。调优是三步闭环：先用慢查询日志定位慢 SQL，再用 EXPLAIN 分析执行计划，最后针对性优化。只说「加索引」会被追问「那你的索引为什么没生效」，然后就翻车了。

📝 现场作答

  • 核心思路是减少磁盘 I/O 和避免无效计算，分三步：定位慢 SQL → 分析执行计划 → 针对性优化。
  • 索引层面：合理设计联合索引并利用覆盖索引避免回表（如只需要 name 和 age，索引建成 (name, age)）；遵守最左匹配原则，WHERE b = 1 吃不到 (a, b, c)；避免在索引列上做函数运算，WHERE YEAR(create_time) = 2024 会让索引失效，应改成 WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01'。
  • SQL 写法层面：禁止 SELECT *，只查必要字段；避免 %LIKE 前缀模糊查询（LIKE '%关键词' 必然全表扫描）；连表查询要检查字段字符集是否一致，utf8 和 utf8mb4 的字段 JOIN 会导致隐式转换，索引直接废掉。
  • 架构层面：热点数据上 Redis 缓存，访问频率高但变化少的数据没必要每次都查库；大表考虑分库分表，单表超过 2000 万行查询性能会明显下降；读写分离把查询压力分摊到从库。也可以从业务侧优化：少展示不必要字段、减少多表查询、把列表查询换成分页分批查询。
  • EXPLAIN 重点看三个指标：type 访问类型从好到差是 system > const > eq_ref > ref > range > index > ALL，看到 ALL 基本就是全表扫描，ref 以上算健康；rows 是预估扫描行数，越小越好，显示 100 万就有问题；Extra 中 Using index 表示覆盖索引不用回表，Using where 表示存储引擎返回后还要在 Server 层过滤，Using filesort 说明排序没用上索引，Using temporary 说明用了临时表（常见于 GROUP BY、DISTINCT）。
  • 索引失效的常见场景：对索引列做运算或函数调用（如 WHERE YEAR(birthday) = 1990）；隐式类型转换（phone 是 varchar 却传数字 13800138000，改成带引号即可走索引）；OR 条件中有非索引字段（name = '张三' OR age = 25 变全表扫描）；联合索引不满足最左匹配（索引 (a, b, c) 时 WHERE b = 1 失效、WHERE a = 1 AND c = 3 只能用 a）；LIKE 左侧通配符；以及优化器基于成本的自主选择。
  • 慢查询日志配置：SET GLOBAL slow_query_log = ON;、SET GLOBAL long_query_time = 1;（记录超过 1 秒的 SQL）、SET GLOBAL log_queries_not_using_indexes = ON;（记录没走索引的查询），用 SHOW VARIABLES LIKE '%slow_query%' 和 SHOW VARIABLES LIKE 'long_query_time' 查看配置；日志文件路径一般在 /var/lib/mysql/xxx-slow.log，用 mysqldumpslow -s t -t 10 按查询时间排序取前 10 条，或 mysqldumpslow -s r -t 10 按扫描行数排序。
  • 大表优化：单表数据太多时即使走索引，B+ 树层级也会变深、查询性能下降。深分页 LIMIT 1000000, 10 会扫描前 100 万条再丢弃，改用游标分页 WHERE id > 1000000 ORDER BY id LIMIT 10；冷热数据分离，把 3 个月前的订单挪到历史表。

💡 主动加分的追问准备

面试官追问 你的答案
联合索引 (a, b, c)，条件是 WHERE a = 1 AND c = 3，能用索引吗？ 能用到，但只能用到 a 这一列。联合索引按 a、b、c 顺序排列，跳过 b 就无法利用 c 的有序性，MySQL 用 a = 1 快速定位后在该范围内逐行判断 c = 3。想让三列都生效，条件必须包含 a 和 b。
线上突然出现大量慢查询，排查思路是什么？ 先看是不是某个时间点突然出现，查那个时间有没有发布、有没有跑批任务；再看慢查询日志找出最频繁的几条 SQL，用 EXPLAIN 分析执行计划、检查索引是否失效；同时看服务器指标（CPU、磁盘 I/O、连接数）是否打满；如果是锁等待，用 SHOW PROCESSLIST 和 SHOW ENGINE INNODB STATUS 排查。
什么情况下优化器会放弃使用索引？ 优化器基于成本估算，认为全表扫描更快就不走索引。典型场景是结果集占总数据量比例太高，比如 100 万条数据里能匹配 60 万条，走索引反而多一次回表不如直接全表扫。另外统计信息不准也会误判，可以用 ANALYZE TABLE 更新统计信息。
联合索引不满足最左匹配时，索引就完全不能用了么？ 不是完全不能用，是用不到后面的列。索引 (a, b, c) 上写 WHERE a = 1 AND c = 3 时，MySQL 仍会用 a 定位，只是 c 无法利用有序性，表现为只能用上第一列。

❌ 千万别说的话

  • “建了索引就一定能用上。”——函数运算、隐式类型转换、OR 带非索引字段、左侧通配符、联合索引不满足最左匹配，都会让索引失效。
  • “ORDER BY 和 GROUP BY 哪个先？”——执行顺序里 GROUP BY 在 ORDER BY 之前，这是固定顺序，不要说反。

20. 如何在 MySQL 中监控和优化慢 SQL？

🎬 面试现场

面试官（口语化）：我们线上要监控慢 SQL，方案你设计一下，怎么发现、怎么分析、怎么持续跟进？

⚠️ 翻车点

只答「开慢查询日志」是不够的，面试官要听的是完整闭环：开启日志 → 工具汇总统计 → EXPLAIN 分析 → 落地优化 → 定期巡检跟踪效果。另外别把慢查询日志说成同步写，它不会阻塞 SQL 执行，开销主要在磁盘 IO。

📝 现场作答

  • 核心手段是开启 MySQL 慢查询日志，把执行时间超过阈值的 SQL 自动记录下来；拿到慢 SQL 后用 EXPLAIN 分析执行计划找出问题，再针对性优化。
  • 三步流程：①开启慢查询日志并设置合理阈值，线上一般 1~2 秒；②定期用 mysqldumpslow 或 pt-query-digest 汇总统计；③对高频慢 SQL 用 EXPLAIN 分析，看是否走了索引、扫描了多少行、有没有文件排序，再针对性优化。
  • 查看当前配置：SHOW VARIABLES LIKE 'slow_query_log';、SHOW VARIABLES LIKE 'long_query_time';、SHOW VARIABLES LIKE 'slow_query_log_file';。
  • 配置文件 my.cnf 中 [mysqld] 段可设：slow_query_log = 1、slow_query_log_file = /var/log/mysql/mysql-slow.log、long_query_time = 2.0、log_queries_not_using_indexes = 1；也可在线动态开启用 SET GLOBAL 改同样的参数，不必重启。
  • log_queries_not_using_indexes 很实用，即使执行很快，没走索引的 SQL 也会被记录；数据量小看不出来，数据量涨上去就变成慢查询。
  • 分析工具：mysqldumpslow 是 MySQL 自带的，-s t -t 10 按执行时间排序取前 10 条、-s c -t 10 按执行次数排序；pt-query-digest 属于 Percona Toolkit（yum install percona-toolkit），按 SQL 指纹聚合，统计每类 SQL 的执行次数、平均耗时、最大耗时、扫描行数并给出优化建议，生产环境推荐用它。
  • 常见优化方向：①缺索引或索引失效——type 为 ALL 说明全表扫描、key 为 NULL 说明没走索引，检查 WHERE、JOIN、ORDER BY 用到的字段；②回表太多——SELECT 的字段不在索引里每行都要回主键索引取数据，用覆盖索引把需要的字段都放进索引；③排序和临时表——Extra 出现 Using filesort 说明有排序、Using temporary 说明用了临时表，尽量通过索引避免；④返回数据量太大——禁止 SELECT *，只查需要的字段并配合 LIMIT；⑤复杂 JOIN 容易让优化器选错计划，可拆成多个单表查询在应用层关联。
  • 其他监控手段：APM 工具（SkyWalking、Pinpoint、CAT）能自动采集 SQL 执行时间并串进调用链；数据库中间件（MyCat、ShardingSphere）提供 SQL 统计功能；云数据库审计（阿里云 RDS、腾讯云 MySQL）在控制台直接看慢 SQL 并给优化建议。
  • 定期巡检机制：建议每周做一次慢 SQL 巡检——用 pt-query-digest 生成报告、按总耗时排序找出 Top 10、逐条分析并把能优化的提工单排期、跟踪优化效果并对比优化前后的执行时间。

面试官追问 你的答案
long_query_time 设成多少合适？ 一般线上 1~2 秒。太短会记录太多 SQL 淹没真正的问题，太长会漏掉值得优化的。交易系统对延迟敏感可以设 500 毫秒（MySQL 5.1 之后支持毫秒级精度，0.5 即 500 毫秒）。刚上线不确定时可先设宽松点，比如 3 秒，跑一段时间看日志量再调。
慢查询日志会不会影响 MySQL 性能？ 影响很小。慢查询日志是异步写的，不阻塞 SQL 执行，主要开销是磁盘 IO；慢 SQL 多时日志文件增长快，可能占满磁盘，所以日志要做好轮转、定期清理历史日志。生产环境开慢查询日志利远大于弊。

  • “慢查询日志只记录慢的。”——log_queries_not_using_indexes 开启后，跑得再快但没走索引的 SQL 也会被记录。

21. MySQL 数据库的性能优化方法有哪些？

🎬 面试现场

面试官（口语化）：MySQL 性能优化整体上有哪几招？你们线上是从哪些层面做的？

⚠️ 翻车点

容易把顺序答反：优先优化 SQL，硬件升级是最后手段。SQL 优化是指数级提升，硬件是线性提升——一条烂 SQL 全表扫描 1000 万行，换 SSD 也只是从 10 秒变 3 秒，改成走索引可能只要 10 毫秒。另外 innodb_buffer_pool_size 不能设成内存的 100%，会把操作系统挤死、触发 OOM Killer。

📝 现场作答

  • 核心目标是减少磁盘 I/O 和降低锁竞争，手段分开发侧和运维侧两大块。
  • 开发侧 SQL 优化：禁止 SELECT *，字段越少扫描的数据页越少、网络传输也更快；避免在索引列上做函数运算（WHERE YEAR(create_time) = 2026 直接让索引失效）；避免 %LIKE 前缀模糊查询；联合索引遵守最左匹配原则（WHERE b = 1 吃不到 (a, b, c)）；连表查询检查字符集一致，utf8 和 utf8mb4 混用触发隐式转换导致索引失效。
  • 开发侧表结构优化：选合适的数据类型，能用 int 别用 bigint，能用 char(50) 别用 char(500)；适当冗余字段减少 JOIN，比如订单表冗余商品名称避免每次关联商品表；根据查询频率建索引但别滥建，每个索引都有写入和存储成本；单表超过 2000 万行考虑分库分表。
  • 运维侧配置调优：innodb_buffer_pool_size 设成物理内存的 70%~80%，让热数据尽量待在内存里；max_connections 根据业务并发量调整但别设太大，每个连接都要吃内存；thread_cache_size 调大一点，减少线程频繁创建销毁的开销。
  • 运维侧架构升级：热点数据上 Redis 缓存，访问频率高但变化少的数据没必要每次都查库；读写分离把查询压力分摊到从库；SSD 替换机械硬盘，随机 I/O 性能提升一个数量级。
  • Buffer Pool：InnoDB 读数据不是每次都走磁盘，热数据常驻内存的 Buffer Pool。设太小会频繁换入换出、磁盘 I/O 飙升。64G 内存的服务器 Buffer Pool 可给到 48G~50G 左右。命中率用 SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%'; 查看，算法是 (1 - Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests) * 100%，健康值应在 99% 以上，低于 95% 就该考虑加内存或优化查询。
  • 索引维护成本：每个二级索引都占磁盘空间，且每次 INSERT、UPDATE、DELETE 都要同步维护——一张表建了 10 个索引，插一条数据就要更新 11 棵 B+ 树。某张表 20 多个字段建了 15 个索引，单条插入要 200ms，删掉 10 个不常用索引后插入性能提升了 5 倍。建索引前要问：字段查询频率高不高、区分度够不够（gender 这种只有两个值的字段建索引没意义）、能不能合并成联合索引（(a) 和 (a, b) 存在时前者可删掉）。
  • 日常维护：定期 ANALYZE TABLE orders; 更新统计信息，数据量变化大的表建议每周一次；定期 OPTIMIZE TABLE orders; 整理碎片（频繁删除会产生碎片、降低数据页利用率），注意该操作会锁表，大表要在业务低峰期执行；冷热数据分离，3 个月前的订单可按月分表或迁移到历史库。
  • 缓存策略：真正扛不住的场景要上缓存，常见是 Cache Aside——读时先查 Redis 未命中再查库并写回缓存，写时先更新数据库再删除缓存；注意高并发下删除缓存的时机很关键，可用延迟双删或订阅 binlog 的方式保证最终一致性。

面试官追问 你的答案
线上数据库 CPU 飙到 100%，怎么排查？ 先用 SHOW PROCESSLIST 看当前有哪些 SQL 在跑，找出执行时间长的语句；用 EXPLAIN 分析执行计划，看是不是全表扫描或锁等待；慢 SQL 导致的紧急情况可先 KILL 掉对应线程再针对性优化；如果连接数打满，检查应用是不是有连接泄漏或连接池配置太小。
表里有 1 亿条数据，加一个索引要多久？会不会锁表？ MySQL 5.6 之后有 Online DDL，加索引不会锁全表，只在开始和结束瞬间有短暂元数据锁。但 1 亿条数据建索引可能要跑几十分钟甚至几小时，期间有额外 I/O 和 CPU 开销。建议在业务低峰期执行，或用 pt-online-schema-change 这类通过触发器同步的方式做无锁变更。
innodb_buffer_pool_size 设成内存的 100% 会怎样？ 会把操作系统和其他进程挤死。MySQL 进程本身要占内存，操作系统也需要内存做文件缓存和运行其他服务，设太大可能触发 OOM Killer 把 MySQL 直接杀掉，一般留 20%~30% 给操作系统比较稳妥。
读写分离之后怎么解决主从延迟导致的数据不一致？ ①写完立刻要读的场景强制走主库，比如用户刚下完单就查订单详情；②能容忍短暂延迟的场景在应用层加短暂等待，或用半同步复制保证至少一个从库收到了 binlog；③用 GTID 判断从库是否已同步到指定位置，没同步就等一会儿或切到主库。

  • “性能不行就加内存、换 SSD。”——硬件升级是最后手段，SQL 优化才是收益最高的一步。
  • “索引越多查询越快。”——每个索引都要占空间并在每次写入时维护，10 个索引意味着插一条数据要更新 11 棵 B+ 树。

22. SQL 中 select、from、join、where、group by、having、order by、limit 的执行顺序是什么？

🎬 面试现场

面试官（口语化）：SELECT、FROM、JOIN、WHERE、GROUP BY、HAVING、ORDER BY、LIMIT 这几个子句，实际执行的时候是按什么顺序来的？

⚠️ 翻车点

两个高频坑：一是把书写顺序当成执行顺序（WHERE 在 SELECT 之前，所以不能用 SELECT 里定义的别名）；二是把 WHERE 和 HAVING 讲反——WHERE 在分组前过滤、不能用聚合函数，HAVING 在分组后过滤、可以用聚合函数。

📝 现场作答

  • 逻辑执行顺序是：FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT，和书写顺序完全不同。
  • 各子句作用：FROM 确定数据源并加载表数据；JOIN 执行表连接、合并多表数据；WHERE 行级过滤，筛掉不符合条件的行；GROUP BY 按指定列分组；HAVING 组级过滤，筛掉不符合条件的组；SELECT 选择要返回的列、计算表达式；ORDER BY 对结果排序；LIMIT 限制返回行数。
  • SELECT 里的别名不能在 WHERE 里用：SELECT price * quantity AS total FROM orders WHERE total > 1000; 会报 total 列不存在，因为 WHERE 执行在 SELECT 之前，别名还没被定义。两种改法——在 WHERE 里重复写表达式 WHERE price * quantity > 1000；或用子查询/派生表 SELECT * FROM (SELECT price * quantity AS total FROM orders) AS t WHERE total > 1000。
  • WHERE 与 HAVING 的区别：WHERE 在分组前过滤、作用于原始行数据、不能用聚合函数；HAVING 在分组后过滤、作用于分组结果、可以用聚合函数。例：WHERE status = 'paid' 先过滤已支付订单，GROUP BY user_id 分组，HAVING COUNT(*) > 10 再过滤订单数大于 10 的用户。把 COUNT(*) > 10 写在 WHERE 里会报错，因为此时还没分组。性能上能用 WHERE 过滤的尽量用 WHERE，它执行得早，能减少后续处理的数据量。
  • ORDER BY 能用 SELECT 的别名，因为它执行在 SELECT 之后，别名此时已定义好；ORDER BY 也可以用 SELECT 里没出现的列，只要那列在 FROM 的表里存在。但如果有 GROUP BY，ORDER BY 就只能用 SELECT 里出现的列或聚合函数，不能用原始表的其他列，因为分组后原始行数据已经没了。
  • LIMIT 最后执行，要取「最大的前 10 条」必须先 ORDER BY 再 LIMIT；没有 ORDER BY 直接 LIMIT 10 取到的是随机的 10 条，因为关系型数据库不保证物理存储顺序。另一个坑：ORDER BY 的列有重复值时 LIMIT 结果可能不稳定，比如 ORDER BY create_time LIMIT 10，多条数据 create_time 相同时每次查结果可能不同，解法是加主键做第二排序：ORDER BY create_time DESC, id DESC LIMIT 10。
  • 优化器可能调整物理执行顺序：逻辑顺序帮你理解语义，实际执行要看 EXPLAIN。例如 WHERE user_id = 100 ORDER BY create_time DESC LIMIT 10，若 user_id 有索引，优化器先索引定位再排序取前 10；若 (user_id, create_time) 有复合索引，优化器可能直接在索引上按 create_time 倒序扫描，找到 10 条就停，连排序都省了。

面试官追问 你的答案
DISTINCT 在执行顺序里排第几？ DISTINCT 和 SELECT 一起执行，在 GROUP BY、HAVING 之后、ORDER BY 之前，作用是对 SELECT 出来的结果去重。如果同时有 GROUP BY 和 DISTINCT，DISTINCT 一般没实际效果，因为 GROUP BY 已经让每组只剩一行。
子查询的执行顺序是怎样的？ 看类型。FROM 子句里的子查询会先执行生成临时表，外层查询在这个临时表上执行；WHERE 里的相关子查询每处理外层一行就要执行一次内层查询，性能很差；非相关子查询可能被优化器改写成 JOIN，效率好很多。
UNION 的执行顺序是怎样的？ 先分别执行每个 SELECT，再合并结果集。UNION 会去重，要额外做排序去重操作；UNION ALL 不去重直接拼接，性能更好。要对 UNION 的最终结果排序，ORDER BY 要写在最后一个 SELECT 后面，或把整个 UNION 包成子查询再排序。
GROUP BY 后面能写表达式吗？ 可以，MySQL 支持在 GROUP BY 里写表达式。但 GROUP BY YEAR(create_time) 这种写法用不上 create_time 上的索引，因为要对每一行计算 YEAR()。数据量大时要么加冗余的 year 字段做索引，要么用虚拟列 + 索引。

  • “执行顺序和书写顺序一样，SELECT 在最前。”——这正好反了，WHERE 在 SELECT 之前。

23. MySQL 中 varchar 和 char 有什么区别？

🎬 面试现场

面试官（口语化）：说下 CHAR 和 VARCHAR 的区别呗，你平时建表怎么选的？

⚠️ 翻车点

把「定长 vs 变长」讲成唯一区别就答完了，面试官一追问「VARCHAR(50) 和 VARCHAR(200) 占用空间一样吗」「InnoDB 存 CHAR 一定定长吗」就直接翻车——这两点才是区分候选人的地方。

📝 现场作答

  • CHAR 是定长，VARCHAR 是变长。CHAR(10) 固定占 10 个字符空间，不足用空格填充；VARCHAR(10) 存多少占多少，额外花 1~2 字节记录实际长度。
  • 性能上 CHAR 理论上快一点点（定长不需要额外计算长度），但实际业务中可以忽略；选型原则是固定长度的短字符串用 CHAR（如 MD5 摘要、ISO 国家代码），其余一律 VARCHAR。
  • VARCHAR(N) 的 N 会影响排序性能：MySQL 用 sort_buffer 计算能放多少行时，用的是定义的最大长度 N 而不是实际长度；放不下就走双路排序（先排排序字段+主键，再回表取完整数据），多一次回表。
  • VARCHAR(N) 的 N 是字符数不是字节数，理论上限受单行 65535 字节约束：扣掉 2 字节长度信息（超过 255 字节时需 2 字节）和允许 NULL 时的 1 字节标记，NOT NULL 最大 65533 字节、允许 NULL 最大 65532 字节；utf8mb4 下 VARCHAR(16383) 就是上限。
  • CHAR 读取时会自动去掉尾部空格：CHAR(5) 存 ‘abc ‘ 用 CONCAT 包出来是 [abc]，需要保留尾部空格只能用 VARCHAR。
  • CHAR 仍有适用场景：ISO 国家代码 CHAR(2)、MD5 摘要 CHAR(32)、去横杠 UUID CHAR(32)、性别标记 CHAR(1) 存 M/F；频繁更新的短字段用 CHAR 不会产生碎片，VARCHAR 长度变化可能导致页分裂。
  • 注意 utf8 这类变长字符集下 InnoDB 会把 CHAR 当变长存储（CHAR(10) 按实际字节数存），只有 latin1 这种单字节字符集才真正定长。

💡 主动加分的追问准备

面试官追问 你的答案
VARCHAR(50) 和 VARCHAR(200) 存同样的字符串，占用空间一样吗？ 磁盘占用一样（实际字符数 + 1~2 字节长度信息）。但定义长度影响内存分配，排序、JOIN 等操作按最大长度预分配，所以 VARCHAR(200) 比 VARCHAR(50) 多占内存，影响 sort_buffer 能放的行数，间接影响排序性能。
InnoDB 存 CHAR 一定是固定大小吗？ 不一定。变长字符集（utf8）下 InnoDB 会把 CHAR 按实际字节数变长存储，避免按最大字节数固定存储浪费空间；只有 latin1 这种单字节字符集 CHAR 才真正定长。
VARCHAR 长度超过多少会存到行外？ 看行格式。旧的 Compact/Redundant 格式下单字段超过 768 字节就把超出部分存到溢出页，行内保留 768 字节前缀加指针；现代默认的 Dynamic/Compressed 格式遵循「最长字段优先」原则，为保证一页至少容纳两行（整行不超过约 8000 字节），最长字段整块移出行外，行内只留 20 字节指针。

❌ 千万别说的话

  • “VARCHAR(50) 和 VARCHAR(200) 存储空间不一样，所以要用小的。” —— 磁盘占用是按实际长度算的，差别在内存预分配和排序上。
  • “CHAR 完全没有用，直接全用 VARCHAR 就好。” —— MD5、固定国家代码、频繁更新的短字段用 CHAR 更合适。
  • “InnoDB 里 CHAR 永远定长，占满 N 个字符的空间。” —— 变长字符集下 InnoDB 会优化成按实际字节数存储。

24. MySQL 中 DELETE、DROP 和 TRUNCATE 的区别是什么？

🎬 面试现场

面试官（口语化）：DELETE、DROP、TRUNCATE 这仨有啥区别？说下底层实现和什么时候用哪个。

⚠️ 翻车点

只答「DELETE 删行、DROP 删表、TRUNCATE 清空」就停，最容易被追问翻车的是「TRUNCATE 是 DDL 还是 DML、能不能回滚」和「DELETE 后表空间为什么不释放」。

📝 现场作答

  • 作用不同：DELETE 删除行数据保留表结构，支持 WHERE 过滤、可部分删除、可回滚；DROP 直接干掉整张表，数据/结构/索引全没、不可回滚；TRUNCATE 清空数据保留结构，等价于 DROP + CREATE、不可回滚。
  • 速度：DROP > TRUNCATE > DELETE。DELETE 最慢是因为逐行处理并记录日志。
  • DELETE 底层不是真擦除磁盘，而是给数据行打删除标记，空间留作「可复用空间」等后续插入，所以 .ibd 文件大小不变；要真正回收得 OPTIMIZE TABLE 或 ALTER TABLE xxx ENGINE=InnoDB 重建表。
  • DELETE 会生成三类日志：redo log（物理修改，崩溃恢复）、undo log（旧数据，事务回滚和 MVCC）、binlog（逻辑操作，主从复制）。删 1000 万行可能要跑几十分钟。
  • DROP 的实现：开启独立表空间时，每张表的数据和索引在 .ibd 文件、表结构在 .frm 文件，DROP TABLE 就是文件系统层面删文件，所以非常快；可用 SHOW VARIABLES LIKE ‘innodb_file_per_table’ 查看，默认 ON。若设为 OFF，表数据都在共享表空间 ibdata1 中，DROP 不会回收空间，因为 ibdata1 只增不减。MySQL 8.0 之后取消了 .frm，表结构存进数据字典。
  • TRUNCATE 实现等价 DROP + CREATE，不逐行处理、不记 undo log，因此快得多；并且会重置自增 ID（主键 AUTO_INCREMENT 表 TRUNCATE 后下一条 ID 从 1 开始，DELETE 清空全表则接着上次值继续）。
  • DDL/DML 区别：DELETE 是 DML，在事务内可回滚；TRUNCATE 和 DROP 是 DDL，会隐式提交当前事务，ROLLBACK 无效。
  • 场景选择：删部分数据用 DELETE + WHERE；清空后重新导入用 TRUNCATE；表不要了用 DROP；大批量删除分批 DELETE（如每次 LIMIT 10000），避免长事务。
  • 误操作恢复：DELETE 可用 binlog 或 flashback 工具恢复；TRUNCATE 和 DROP 只能靠备份。

💡 主动加分的追问准备

面试官追问 你的答案
为什么 DELETE 大表很慢，有什么办法加速？ 逐行处理，每行记 undo log、redo log 并维护 binlog。加速手段：分批删除每次 1 万行加 LIMIT、删完 sleep 几秒；清空表直接 TRUNCATE；保留少量数据就导出来、TRUNCATE 原表再导回去；或新建表 INSERT INTO SELECT 过去再 RENAME。
TRUNCATE 是 DDL 还是 DML？为什么？ DDL。底层实现是 DROP + CREATE，属于表结构操作，DDL 隐式提交事务、不记 undo log，所以不能回滚。MySQL 官方文档也明确 TRUNCATE 是 DDL，这与 Oracle 一致——有人以为它是 DML 能回滚，生产环境就翻车了。
DELETE 后表空间为什么不释放？怎么回收？ InnoDB 删除后只把数据页标记为可复用，不归还给文件系统，.ibd 文件大小不变。回收要重建表：ALTER TABLE xxx ENGINE=InnoDB 或 OPTIMIZE TABLE xxx，本质是数据导出重建再导回，会锁表或产生大量 IO；5.6 之后有 Online DDL 可在线重建减少影响，但仍建议低峰期做。

❌ 千万别说的话

  • “TRUNCATE 和 DELETE 一样，都能 ROLLBACK 回来。” —— TRUNCATE 是 DDL，会隐式提交，ROLLBACK 无效。
  • “DELETE 删完数据磁盘空间就释放了。” —— 只是变成可复用空间，.ibd 文件大小不变。
  • “DROP TABLE 会连 binlog 一起记一条完整数据删除记录。” —— binlog 记的是逻辑操作，drop 记录的是 DDL 事件而不是逐行删除。

25. MySQL 中 DATETIME 和 TIMESTAMP 类型的区别是什么？

🎬 面试现场

面试官（口语化）：DATETIME 和 TIMESTAMP 选哪个？区别说清楚，尤其时区那块。

⚠️ 翻车点

只会说「TIMESTAMP 范围小、占用小，DATETIME 范围大」不够，最容易被追问的是「TIMESTAMP 跨时区主从同步会不会出问题」和「2038 年问题怎么迁移」。

📝 现场作答

  • 时区机制：TIMESTAMP 存的是 Unix 时间戳，插入时把当前时区时间转成 UTC 存储，读取时再按连接会话时区转回来；同一条数据在北京时区和纽约时区读出的本地时间不同。DATETIME 存字面日期时间，写什么存什么、跟时区无关。
  • 范围：TIMESTAMP 用 4 字节存 Unix 秒数，32 位有符号整数最大 2147483647，对应 2038-01-19 03:14:07 UTC，只能表示 19702038 年；DATETIME 范围 10009999 年。
  • 存储空间：MySQL 5.6.4 之后两者都支持微秒精度。TIMESTAMP 不带小数秒 4 字节、带 6 位小数秒 7 字节；DATETIME 不带小数秒 5 字节、带 6 位小数秒 8 字节。
  • 时区配置要一致：用 TIMESTAMP 的表要保证服务器与应用连接的时区统一，可在连接串里显式指定，如 SET time_zone = ‘+08:00’，或 JDBC URL 用 serverTimezone=Asia/Shanghai。DATETIME 没这个问题，但业务真要跨时区就得在应用层自己换算。
  • 2038 年之后的数据（如长期保存的订单、合同）建议用 DATETIME 或 BIGINT 存毫秒级时间戳；MySQL 官方方案是把 TIMESTAMP 改成 64 位存储，目前尚未实现。
  • 默认值与自动更新：TIMESTAMP 可写 DEFAULT CURRENT_TIMESTAMP 和 ON UPDATE CURRENT_TIMESTAMP 记录创建/修改时间，这两个特性 MySQL 5.6.5 之后 DATETIME 也支持；但 5.6.4 之前一张表只能有一个 TIMESTAMP 列带 DEFAULT CURRENT_TIMESTAMP。
  • 索引：TIMESTAMP 更紧凑，大量按时间范围查询时（日志表、订单表）索引效率略高，1 亿条数据索引大小可能差出 100MB，但通常可以忽略，选型优先看业务需求。
  • 其他时间类型：DATE 3 字节（10009999 年）、TIME 3 字节（-838:59:59838:59:59）、YEAR 1 字节（1901~2155 年）。实际开发中大部分场景用 DATETIME 就够了。

💡 主动加分的追问准备

面试官追问 你的答案
线上表用了 TIMESTAMP 存创建时间，担心 2038 年问题想改成 DATETIME，怎么迁移风险最小？ 加一个新的 DATETIME 列，用 UPDATE 把老列值复制过去（注意时区转换，最好在同一时区下操作），改应用读写切到新列，验证没问题后删旧列或保留观察。表特别大时全表 UPDATE 锁很久，可分批更新，用 WHERE id BETWEEN 控制范围。
两个不同时区的数据库做主从同步，TIMESTAMP 的值会出问题吗？ 基于语句的复制可能有问题：TIMESTAMP 依赖会话时区，主从时区不同则同一条 INSERT 在两边执行结果不同。用基于行的复制就没事，因为复制的是实际 UTC 时间戳值。跨时区主从建议用 ROW 格式 binlog。
应用层用 BIGINT 存毫秒时间戳和用 DATETIME 比，哪个好？ BIGINT 跨语言跨平台最通用（Java、JavaScript、Python 都能直接处理），没有时区心智负担，但查库不直观；DATETIME 直观、SQL 里做时间范围查询方便（如 WHERE created_at > ‘2026-01-01’）。个人倾向 DATETIME，除非系统对跨平台互操作性要求特别高。

❌ 千万别说的话

  • “TIMESTAMP 存的是当前时间，DATETIME 存的是本地时间。” —— TIMESTAMP 存的是 UTC 时间戳，DATETIME 才是字面值。
  • “DATETIME 也会自动按会话时区转换。” —— DATETIME 与时区无关，存什么取什么。
  • “TIMESTAMP 和 DATETIME 存储空间一样，都是 8 字节。” —— 分别是 4/7 与 5/8 字节（不含/含 6 位小数秒）。

26. MySQL 中 TEXT 类型最大可以存储多长的文本？

🎬 面试现场

面试官（口语化）：TEXT 能存多大？和 VARCHAR 怎么选，索引能不能加？

⚠️ 翻车点

答「TEXT 最大 65535 字节」只答了一半就收，容易漏掉：这是字节数不是字符数；TEXT 行内只存 20 字节指针、多一次 IO；以及不能建完整索引只能建前缀索引。

📝 现场作答

  • TEXT 家族四种类型按容量递增：TINYTEXT 最大 255 字节（短标签、备注）、TEXT 最大 65535 字节（约 64 KB，普通文章）、MEDIUMTEXT 最大 16777215 字节（约 16 MB，富文本/长博客）、LONGTEXT 最大 4294967295 字节（约 4 GB）。
  • 这些上限是字节数不是字符数：UTF-8 存中文一个汉字 3 字节，所以 TEXT 实际约能存 2 万个汉字。
  • 存储机制与 VARCHAR 有本质区别：VARCHAR 数据直接存行内，TEXT 行内只存 20 字节指针、内容放独立溢出页。读 TEXT 字段要多一次磁盘 IO，所以只查 id 和 title 时不要写 SELECT * 把 content 也捞出来。
  • TEXT 在 MySQL 5.7 及之前不支持 DEFAULT 值，建表写 content TEXT DEFAULT ‘’ 会直接报错；MySQL 8.0 放开了，但很多生产环境还跑 5.7，容易踩坑。
  • 索引：TEXT 不能建完整索引，必须指定前缀长度，如 CREATE INDEX idx_content ON article(content(100))；前缀索引只能用于前缀匹配，LIKE ‘%关键词%’ 这种中间匹配走不了索引，要全文检索得上 FULLTEXT 索引或用 Elasticsearch。
  • 选型：确定内容不超过几百字用 VARCHAR(1000) 更合适、性能也更好。TEXT 真正适合的是文章正文/富文本（长度不可控）、日志详情和错误堆栈、以及 MySQL 5.7 之前没有 JSON 类型时的 JSON 扩展字段替代。
  • VARCHAR 最大 65535 字节，但那是整行所有 VARCHAR 字段的总和限制，单字段还要扣掉其他字段占用的空间。

面试官追问 你的答案
VARCHAR 最大能存多少？和 TEXT 怎么选？ VARCHAR 最大 65535 字节，这是整行所有 VARCHAR 字段的总和限制，单字段还要扣其他字段空间。原则是长度可控且不太长用 VARCHAR，长度不可控或可能很大用 TEXT。VARCHAR 存行内读取快，TEXT 存溢出页多一次 IO。
为什么 TEXT 不能做索引字段？ 不是完全不能，是不能建完整索引，只能建前缀索引。InnoDB 索引页默认 16KB，一个索引条目最大只能 767 字节（MySQL 5.6）或 3072 字节（5.7+ 开启 innodb_large_prefix），TEXT 可能几十 KB 甚至几 MB，塞不进索引条目，只能截取前缀。
线上大表的 TEXT 字段要加索引做模糊搜索，怎么处理？ 前缀索引对 LIKE ‘%xxx%’ 帮不上忙。两个方案：一是上 FULLTEXT 全文索引（MySQL 5.6+ 的 InnoDB 支持，但中文分词效果一般，需配合 ngram 分词器）；二是把搜索需求抽离到 Elasticsearch，MySQL 只负责存储、ES 负责搜索，这也是业界主流做法。

  • “TEXT 最大能存 65535 个字。” —— 是 65535 字节，UTF-8 中文下大约 2 万字。
  • “TEXT 和 VARCHAR 差不多，字段大一点用 TEXT 就行。” —— TEXT 行内只有 20 字节指针，读取多一次 IO，字段几百字以内用 VARCHAR 更优。

27. MySQL 中 AUTO_INCREMENT 列达到最大值时会发生什么？

🎬 面试现场

面试官（口语化）：自增 ID 涨到上限会怎样？主键该怎么选型？

⚠️ 翻车点

两个坑：一是以为自增到上限会回绕或报错就没事——没定义主键时的 row_id 回绕是静默覆盖数据，比主键冲突严重得多；二是把「AUTO_INCREMENT 计数器会回收」说成常态。

📝 现场作答

  • 自增 ID 达到上限后，再插入仍返回那个最大值，随后因主键冲突直接报 Duplicate entry；MySQL 不会自动回绕到 0 或 1，而是卡在最大值不动。
  • 不同类型上限：TINYINT 1 字节（127/255）、SMALLINT 2 字节（32,767/65,535）、MEDIUMINT 3 字节（8,388,607/16,777,215）、INT 4 字节（2,147,483,647/4,294,967,295）、BIGINT 8 字节（9.2×10^18/1.8×10^19）。很多团队用 int 做主键，日均 100 万条插入的话 6 年就撑爆，新表建议直接上 BIGINT UNSIGNED。
  • 没指定主键时 InnoDB 会用 6 字节隐藏列 row_id 做聚簇索引，它是全局共享的：所有用到 row_id 的表每次插入都取该值再 +1，范围 0 到 2^48-1（约 281 万亿）。到上限后会回绕到 0 重新开始，新插入的数据直接覆盖 row_id 相同的老数据且没有任何报错——比主键冲突报错更可怕。所以生产环境必须显式指定主键。
  • 预防与应对：建表用 BIGINT UNSIGNED；定期查 information_schema.TABLES 监控 AUTO_INCREMENT 使用率；快到上限时迁移到新表用 BIGINT，或改用分布式 ID 方案（Snowflake、Leaf、UidGenerator、数据库号段模式）。
  • 分布式 ID 方案：Snowflake 雪花算法 64 位（时间戳 + 机器码 + 序列号），单机每秒能生成 400 多万个 ID；美团 Leaf、百度 UidGenerator 在其基础上优化；号段模式每次从数据库批量取一段 ID 缓存在内存里用。
  • 高并发下自增 ID 必须串行分配，会竞争 AUTO_INCREMENT 锁。MySQL 5.1.22 之后有 innodb_autoinc_lock_mode 参数，默认 1 是连续模式（8.0 改成 2），批量插入时预分配 ID 减少锁等待；设成 2 是交错模式，性能最好但 ID 可能不连续，binlog 用 statement 格式时主从可能不一致。
  • 不建议用 UUID 做主键：36 字符字符串占空间，且随机写入导致 B+ 树频繁页分裂，写入性能可能差 10 倍以上；非要用可用有序 UUID，MySQL 8.0 提供 UUID_TO_BIN 转成有序二进制。

28. 在 MySQL 中存储金额数据，应该使用什么数据类型？

🎬 面试现场

面试官（口语化）：金额字段用啥类型存？Java 那边怎么配合？

⚠️ 翻车点

用 FLOAT/DOUBLE 存钱是硬伤；另一个常见翻车点是 Java 侧用 new BigDecimal(0.1) 或用 equals 比较 BigDecimal，直接把精度问题又带了回来。

📝 现场作答

  • 业界主流两种方案：DECIMAL 或 BIGINT 存分。绝对不能用 FLOAT/DOUBLE，浮点数有精度丢失。
  • DECIMAL 是定点数、精度可控，DECIMAL(18,2) 表示最多 18 位数字、其中 2 位小数，Java 侧对应 BigDecimal，天然支持高精度运算。
  • BIGINT 存分是把金额乘以 100 变整数，99.99 元存成 9999 分，Java 侧用 long，性能比 BigDecimal 好，但只能精确到分。
  • 浮点数误差实例：SELECT 0.1 + 0.2 结果是 0.30000000000000004 而不是 0.3，因为二进制无法精确表示十进制小数，IEEE 754 规定了截断方式；每笔订单少算 0.01 元、日均 100 万笔，一年就是 365 万。
  • BIGINT 存分的三个好处：整数运算比 DECIMAL 快（CPU 直接处理）、存储固定 8 字节比 DECIMAL 省、Java 侧用 long 没有 BigDecimal 的对象开销。但涉及汇率换算、费率计算这类需要精确到厘的场景就不行了，比如千分之三手续费 123 元收费 0.369 元，存分只能存 37 或 36，要么多收要么少收。
  • DECIMAL(M,D) 中 M 是总位数、D 是小数位数：普通金额 DECIMAL(18,2)（18 位能存到千万亿级别）；费率计算用 DECIMAL(18,4) 或 DECIMAL(18,6)，中间多留几位小数最后再截断；别把 M 设太大，DECIMAL 按需分配空间，M 越大占用越多。
  • Java 侧要点：禁止用 double 构造 BigDecimal（new BigDecimal("0.1") 才是精确的）；除法必须指定精度和舍入模式 a.divide(b, 2, RoundingMode.HALF_UP)；比较用 compareTo 而不是 equals，因为 equals 会比较精度，1.0 与 1.00 不相等。MyBatis 里 DECIMAL 字段会自动映射成 BigDecimal，不用额外配置。
  • 场景建议：普通电商订单金额用 BIGINT 存分；支付手续费计算用 DECIMAL(18,4)；汇率换算用 DECIMAL(18,6)；金融交易系统用 DECIMAL(18,8)。绝大多数业务 DECIMAL(18,2) 就够，性能差距在现代硬件上可忽略。

29. MySQL 中 VARCHAR(100) 和 VARCHAR(10) 的区别是什么？

🎬 面试现场

面试官（口语化）：VARCHAR 括号里的数字到底影响什么？平时该定多长？

⚠️ 翻车点

答「存的字符数上限不同」就停会被追死——磁盘占用其实一样，真正的影响面是内存预分配、长度标识字节数、索引长度限制和DDL 锁表。

📝 现场作答

  • N 表示最大字符数上限，VARCHAR(100) 能存 100 字符、VARCHAR(10) 能存 10 字符；存相同内容磁盘占用一样，因为 VARCHAR 变长，存 5 个字符就只占 5 个字符空间，不会填充到 100。
  • 真正区别在内存：MySQL 执行 ORDER BY、GROUP BY、DISTINCT、UNION 等操作时需要创建临时表或排序缓冲区，按字段定义的最大长度分配内存。VARCHAR(100) 在 utf8mb4 下每行预留约 400 字节，VARCHAR(20) 只预留约 80 字节。
  • 典型坑：一张 100 万行的表，remark 定义成 VARCHAR(2000) 但实际数据只有几十个字符，排序时 MySQL 按 2000×4=8000 字节预估每行内存，合计 8GB，很容易撑爆 sort_buffer_size 落盘排序，性能断崖式下跌。
  • 存储结构 = 长度标识 + 实际数据，长度标识占 1 或 2 字节：最大长度 ≤ 255 字节用 1 字节，> 255 字节用 2 字节（按字节算不是字符）。utf8mb4 下 VARCHAR(50) 最大 200 字节用 1 字节标识，VARCHAR(100) 最大 400 字节用 2 字节标识。
  • 长度受三个约束：行大小限制（单行最大 65535 字节，一表所有字段加起来不能超）、字符集影响（utf8mb4 每字符最多 4 字节，VARCHAR(16383) 是上限）、索引长度限制（InnoDB 索引 key 最大 3072 字节，utf8mb4 下 VARCHAR(1000) 是 4000 字节超限，只能建前缀索引如 content(200)）。
  • 与 CHAR 对比：CHAR 定长，CHAR(10) 存 ‘abc’ 也占 10 字节且读取时自动去尾部空格；VARCHAR 变长，实际长度 + 长度标识，存 ‘abc’ 占 4 字节，尾部空格保留。CHAR(32) 存 MD5 比 VARCHAR(32) 少 1 字节长度标识且不用动态算长度。
  • 原则是够用就行：用户名最长 20 字符就定义 VARCHAR(20)，不要图省事全写 VARCHAR(255)。

VARCHAR(255) 和 VARCHAR(256) 有什么实质区别？ 长度标识字节数不一样。VARCHAR(255) 在单字节字符集下最大 255 字节，1 字节长度标识就够；VARCHAR(256) 超过 255，得用 2 字节记录长度，每行多占 1 字节，数据量大时累加也不少。

30. MySQL 在设计表（建表）时需要注意什么？

🎬 面试现场

面试官（口语化）：建表你会注意哪些点？说说你的建表规范。

⚠️ 翻车点

只答「选好类型、加索引」这种泛泛之谈不够；本题最容易被追问的是「为什么要用自增 ID 而不是业务 ID」「NULL 怎么处理」「大表加字段风险」这几个具体决策点。

📝 现场作答

  • 核心原则是够用就好，在满足业务需求前提下让表结构尽量精简、高效、易维护。
  • 字段类型选最合适的：能用 int 就别用 bigint，能用 varchar(64) 就别用 varchar(256)；日期用 DATETIME 或 TIMESTAMP 别拿 VARCHAR 存；金额用 DECIMAL 别用 FLOAT/DOUBLE。类型选小了后期改很麻烦，选太大浪费空间也影响性能。整型看量级选（tinyint 127、smallint 3 万多、int 21 亿、bigint 基本无上限）；字符串按是否定长选（身份证号 char(18)、昵称 varchar）；时间看是否跨时区（跨时区用 TIMESTAMP，否则 DATETIME 更通用）。
  • 必须有主键，推荐自增 BIGINT。UUID 做主键导致索引分裂严重、写入性能差一截（随机插入 B+ 树页分裂，写入性能能差 3-5 倍）；有唯一业务 ID 可另建唯一索引，主键仍用自增。复合主键尽量别用（如 (user_id, create_time)），给后续扩展埋坑。
  • 索引建在刀刃上：where、join、order by 常用字段建索引，多字段组合查询用复合索引并注意最左前缀原则；区分度低的字段（性别、状态）别建索引；每加一个索引，insert 和 update 都要多维护一棵 B+ 树。
  • 合理冗余减少 join：互联网业务一般不追求严格三范式，订单表冗余用户昵称可以省掉每次 join。
  • 别用物理外键：会拖慢写入性能，还给分库分表埋坑，一致性在应用层保证或用消息队列做最终一致性。
  • NULL 的影响：索引对 NULL 处理特殊，where column = null 查不到数据，要用 is null；NULL 参与运算结果还是 NULL（1 + NULL = NULL）。最佳实践是能不用就不用，数值给默认 0、字符串给空串、时间给当前时间或 1970-01-01，建表写 NOT NULL DEFAULT xxx；但要区分「没填」和「填了但是 0」的场景 NULL 仍有意义。
  • 预留扩展字段：预留 ext1、ext2、ext3 三个 varchar 字段放临时需求；预留一个 JSON 字段 extra_info（MySQL 5.7 之后 JSON 字段能建虚拟列和索引）；状态字段用 int 而不是 tinyint 留足状态位。代价是查询和存储效率略低，但省了频繁 alter table 的运维成本。
  • 大表 alter table 风险：5.6 之前会锁全表，几百万数据可能锁十几分钟甚至几小时；5.6 之后有 Online DDL，但加字段仍有 metadata lock 期间查询被阻塞；大表加字段用 pt-online-schema-change 或 gh-ost，原理是建新表、后台慢慢迁移数据、最后原子切换。
  • 字段必须加注释，写清业务含义，枚举值要列出每个值代表什么；表注释写清这张表干什么、存什么数据。

31. MySQL一张表最多可以有多少列？

🎬 面试现场

面试官（口语化）：一张表最多能建多少列？超了会怎样？

⚠️ 翻车点

只答「4096 列」会翻车：实际 InnoDB 只有 1017 列，且函数索引会创建隐藏虚拟列偷走配额——这一点最容易漏。

📝 现场作答

  • 理论最大列数 4096（MySQL Server 层写死的常量，为兼容各种存储引擎和内部数据结构而设的上限），但实际能建多少受两个硬约束限制。
  • 约束一：行大小限制。一行数据最多 65535 字节，所有列的存储开销加起来不能超。VARCHAR、TEXT 这类变长字段虽可把数据存到页外，但每字段至少占 1-2 字节长度标记和可能的 NULL 标记，几百个 VARCHAR 加起来就可能撑爆 65535。
  • 约束二：存储引擎限制。InnoDB 硬限制是 1017 列，比理论值低很多，因为 InnoDB 要为每一列维护元数据，列数太多会导致内部结构膨胀。
  • InnoDB 的 1017 限制来自行格式里的 “field start offsets” 数组，该数组记录每个字段的起始位置，设计上最多支持 1017 个用户可见列。
  • 隐藏列会偷配额：InnoDB 表实际有 3 个隐藏列——DB_ROW_ID（无主键时自动生成的 6 字节行 ID）、DB_TRX_ID（6 字节事务 ID）、DB_ROLL_PTR（7 字节回滚指针，指向 undo log），它们不占 1017 配额；但 MySQL 8.0 引入的函数索引会创建真正的 VIRTUAL 隐藏列（如对 UPPER(name) 建索引），这个隐藏列占用用户列配额——建 10 个函数索引可用列数就少 10 个，SHOW CREATE TABLE 里看不到它。
  • 行格式差异：REDUNDANT 老格式前 768 字节存行内超出部分存溢出页；COMPACT 是 5.0+ 默认、元数据更紧凑、大字段处理同上；DYNAMIC 是 5.7+ 默认，大字段只存 20 字节指针、数据全在溢出页；COMPRESSED 类似 DYNAMIC 且额外压缩。DYNAMIC 下塞几十个 TEXT 也不易超 65535（每字段只占 20 字节指针），COMPACT 下每个 TEXT 要占 768+ 字节，几十个就爆。
  • 实际踩过的坑：ALTER TABLE 加列到接近 1000 列时可能突然报 “Row size too large”（之前都是小字段，新加的 VARCHAR(500) 累积超 65535）；分区表每个分区独立维护列信息，列数多后元数据膨胀导致 information_schema 查询变慢；列数超过 200 后 mysqldump 导出的 INSERT 语句特别长，某些客户端工具会解析超时。
  • 经验值：单表超过 100 列就要考虑拆表，或用 JSON 字段收纳低频访问的属性。

32. 如何在 MySQL 中避免单点故障？

🎬 面试现场

面试官（口语化）：我们线上 MySQL 现在就一台机器挂着，它挂了整个业务就瘫了，你说说你怎么把这个单点去掉？

⚠️ 翻车点

只说「加个从库做主从复制」会被直接追问穿：主从默认是异步复制，主库提交后不等从库确认，切主库那一刻是可能丢数据的，必须主动把半同步复制这条说清楚。

📝 现场作答

  • 避免单点故障的核心是冗余：不能让一台机器挂了整个服务就瘫痪。方案有四类：主从复制 + 读写分离（主库写、从库读，主库挂了把从库提升为主库，最基础，大部分公司在用）、主备架构（备库不对外服务只默默同步，切换更简单但资源浪费）、MGR 集群（MySQL Group Replication，官方多主集群，支持自动故障转移、数据强一致，MySQL 5.7.17 开始支持）、MHA/Orchestrator（第三方高可用管理工具，MHA 能在主库宕机后 30 秒内完成故障转移，并尽量保证数据不丢失）。
  • 主备架构的切换分人工和自动两种：人工切换靠运维收到告警手动把备机切成主机，可能得几分钟；自动切换用 keepalived 或自研脚本监控心跳，几十秒内完成。缺点是备机平时不干活，资源浪费。
  • 主从复制原理：主库把变更写到 binlog，从库的 IO 线程拉取 binlog 写到 relay log，SQL 线程再重放 relay log 完成同步。配置上主库要设 server-id、log-bin、binlog-format = ROW，从库要设 server-id、relay-log、read-only = 1。要注意复制延迟，监控 Seconds_Behind_Master，超过阈值就告警。
  • 主主架构两台机器互为主从都能写，生产环境一般不推荐：两台同时写同一张表自增 ID 会冲突，虽然可以用不同的 auto_increment_offset（1 和 2）配合 auto_increment_increment = 2 规避，但仍会出现两边同时更新同一行、最终谁生效取决于时间顺序的冲突。真要用得在业务层隔离，比如按用户 ID 路由到固定主库。
  • MHA 由 Manager 节点和 Node 节点组成，Manager 监控主库状态，主库挂了就自动选一个从库提升为主库。牛逼之处是会尽量补全丢失的 binlog——主库宕机时最新 binlog 可能还没同步到从库，MHA 会 SSH 登录到挂掉的主库把 binlog 拷出来应用到新主库，最大限度减少数据丢失。常用命令 masterha_check_repl --conf=/etc/mha/app1.cnf 检查状态、masterha_master_switch --conf=/etc/mha/app1.cnf --master_state=alive 手动切换。缺点是要额外部署 Manager 节点，而 Manager 本身也是单点。
  • MGR 优势是官方原生、不依赖第三方工具、强一致，不存在主从延迟读到旧数据的问题；缺点是对网络延迟敏感，节点间网络抖动影响性能，而且要求所有表都有主键，没主键的表不支持。可用 performance_schema.replication_group_members 查状态，用 MEMBER_ROLE = 'PRIMARY' 找当前主节点。
  • 除架构层面还要做监控告警和定期备份：监控主从延迟、连接数、磁盘空间，备份存到不同物理位置防机房级灾难。备份分全量（mysqldump 或 xtrabackup，每天或每周一次）、增量（基于 binlog，可恢复到任意时间点）、异地（存不同机房甚至不同城市）。恢复时先恢复最近全量，再按顺序应用增量备份和 binlog。

主从复制延迟太大怎么办？ 先定位原因。大事务导致（比如批量更新几十万条跑半小时，从库也得重放半小时）就拆分大事务分小批次；从库机器性能差就提升配置或加从库分担；MySQL 5.7 之后可开并行复制，用 slave_parallel_workers 让多线程并行重放 relay log。

怎么做到跨机房 MySQL 高可用？ 主要挑战是网络延迟。同城双活可用 MGR 或主从 + 半同步，几毫秒延迟问题不大；异地容灾一般用异步复制，延迟大但至少数据有副本。真要做异地多活得在应用层分片，不同用户数据写到不同机房主库避免跨机房写，单纯靠数据库层面很难做到异地多活。

33. 如何处理 MySQL 的主从同步延迟？

🎬 面试现场

面试官（口语化）：我们从库经常比主库慢好几秒，偶尔用户写完立刻查就查不到旧数据，这个延迟你怎么治？

⚠️ 翻车点

最容易被翻车的是拿 Seconds_Behind_Master 当真相来源——它算的是 relay log 最后一条事件时间戳和当前时间的差值，主库长时间没写入时它会是 0，但实际网络可能已经断了。

📝 现场作答

  • 先摆结论：主从延迟是必然存在的，不可能完全消除，只能尽量缩短延迟或在业务层规避。
  • 延迟的根本原因在复制链路：主库写 binlog → dump 线程推送变更事件 → 从库拉取 → I/O 线程写 relay log → SQL 线程重放。链路上任何一环慢了延迟就上来。
  • 业务层面四种处理：①关键业务强制走主库，比如用户注册完立马登录这种写后读场景，虽然牺牲读写分离意义但频次不高；②延迟感知，写操作后记录时间戳，短时间内的读请求强制走主库，过了延迟窗口再走从库，可用 ThreadLocal 或 Redis 记录写操作时间；③二次查询兜底，从库查不到就再查一次主库，问题是有人恶意查不存在的数据会每次都打到主库、变相攻击；④缓存前置，写主库同时写缓存、读先查缓存，但引入了缓存一致性问题，等于拿一个问题换另一个问题。
  • 常见原因与优化：从库单线程重放导致 Seconds_Behind_Master 持续增长 → 开启并行复制；大事务单个事务跑几分钟 → 拆分大事务；从库配置低 CPU/IO 打满 → 升级硬件；从库查询压力大 SQL 线程抢不到资源 → 增加从库数量并优化慢查询；网络延迟（跨机房）→ 缩短物理距离用专线；从库太多主库 dump 线程压力大 → 用级联复制。
  • 并行复制演进：MySQL 5.6 开始引入并行复制，不同库的事务可并发；5.7 引入 LOGICAL_CLOCK，同一 group commit 的事务可并发；8.0 引入 WriteSet，只要更新的行不冲突就能并发。开启方式是 SET GLOBAL slave_parallel_type = 'LOGICAL_CLOCK' 和 SET GLOBAL slave_parallel_workers = 8，slave_parallel_workers 设成 CPU 核心数的 2 倍左右，太少并行度不够、太多线程切换开销大。
  • 延迟监控：SHOW SLAVE STATUS 里的 Seconds_Behind_Master 最常用但不一定准；更靠谱的是 pt-heartbeat，主库定时写入时间戳、从库查出来和当前时间比较算真实延迟，主库侧 pt-heartbeat --database=test --table=heartbeat --update --daemonize，从库侧 pt-heartbeat --database=test --table=heartbeat --monitor。
  • 半同步复制：对一致性要求高时开启，主库等至少一个从库确认收到 binlog 再返回客户端，这样从库延迟最多是一个事务的执行时间，不会无限累积；代价是写性能下降、每次写多一次网络往返。配置是 INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so'、SET GLOBAL rpl_semi_sync_master_enabled = 1、SET GLOBAL rpl_semi_sync_master_timeout = 1000（毫秒），从库在 timeout 内没响应主库会自动降级成异步复制，不会一直阻塞。

面试官追问 你的答案
Seconds_Behind_Master 为 0 就说明没延迟吗？ 不一定。它为 0 只说明从库已把 relay log 里的事件都执行完，不代表主从完全同步。网络断了收不到新 binlog 时这个值也是 0；主库长时间没写入时也是 0。要准确监控得用 pt-heartbeat，主动写入时间戳算真实延迟。
大事务为什么会导致主从延迟？ binlog 是事务提交后才写入的，一个大事务在主库执行 10 分钟，提交后 binlog 一次性发给从库，从库也要执行 10 分钟，这 10 分钟从库就落后了。而且大事务期间主库可能还有其他小事务提交，这些小事务得排在大事务后面重放，延迟进一步放大。所以生产环境要避免大事务，批量更新拆成多次小批量。
级联复制是什么意思？ 就是从库再挂从库。主库只同步给一级从库，一级从库再同步给二级从库，主库 dump 线程压力小了、不用给每个从库都发 binlog。适合从库数量特别多的场景，比如多机房容灾每个机房一个一级从库、机房内再挂多个二级从库。缺点是延迟会叠加，二级从库的延迟是一级从库延迟加上自身重放时间。

34. 如何实现数据库的不停服迁移？

🎬 面试现场

面试官（口语化）：我们要把自建库迁到云上，量不小，业务还不能停，你给我一个不停服的迁移方案。

⚠️ 翻车点

只说「用同步工具搬过去」会被追问穿——不停服迁移的核心难点是在线数据的插入和修改如何保持一致，以及出问题怎么回滚，这两点必须主动讲出来。

📝 现场作答

  • 先关注量级：几十万数据直接用代码迁移、简单核对就结束；数据量大才需要好好设计方案。
  • 不停服迁移要解决三件事：保证在线数据的插入和修改不丢（数据一致性）、必须准备回滚（出问题时及时切回老库）、以及整体过程的节奏控制。
  • 业界主流方案是双写 + 灰度切流，六步流程：①把云上新库作为自建旧库的从库做数据同步（也可以用阿里云 DTS 这类云上能力）；②改造业务代码同时写旧库和新库（双写必须带开关，能通过改配置实时打开/关闭）；③在业务低峰期确认主从完全无延迟时，关闭同步同时打开双写开关，此时读的仍是旧库；④数据核对，量大只能抽样，用定时任务写代码抽样比对，一旦不一致就告警记录；⑤确认一致后灰度切流，比如 1% 用户切到读新库（按访问顺序、用户 ID 或其他业务字段），没问题就 5% → 20% → 50% → 100%；⑥继续保留双写跑几天甚至更久，确认新库确实没问题后关闭双写只写新库，迁移完成。
  • 双写有三个坑：①先写旧库，旧库成功后再写新库；先写新库但旧库失败就要回滚新库、逻辑复杂，而先写旧库的话新库写失败可以靠同步链路补上。②两个库的写不在同一事务里，做不到强一致，不停服迁移本来就不追求强一致、最终一致就够，新库写失败就记录下来事后补偿或靠同步链路兜底。③必须幂等，因为同一条数据可能被同步链路同步一次又被双写写一次，常见做法是用唯一键做 UPSERT。
  • 同步延迟处理：从库同步主库正常是几十到几百毫秒，网络抖动或大事务可能到秒级甚至分钟级。切流前必须确认延迟足够小，建议在业务低峰期延迟稳定在 1 秒以内再开始切流；延迟降不下来要排查是不是有大事务、从库配置太低或网络有问题。
  • 数据校验策略（全量校验几亿条不现实，抽样是标准做法）：①基于主键抽样，如 id % 100 = 0 的数据拿出来对比；②基于时间范围抽样，比如对比最近 1 小时新增或修改的数据；③关键字段校验，不用对比每个字段，挑几个关键字段做 MD5 或 CRC32 校验。示例 SQL 是 SELECT id, crc32(concat(user_id, amount, status, update_time)) as checksum FROM orders WHERE id % 100 = 0，两边跑同样 SQL 对比结果，不一致的记录下来人工排查。
  • 回滚预案三阶段：双写阶段回滚 = 关掉双写开关只写旧库；灰度切读阶段回滚 = 把读流量全部切回旧库；全量切换后回滚最棘手，因为已经关闭双写和同步链路后旧库数据就落后了，所以建议全量切换后再跑一周双写，确认稳定再彻底下线旧库。
  • 除主从同步 + 代码双写外，还可用第三方工具如 flink-cdc，方便且支持异构（MySQL 同步到 PG、ES 等），支持先同步全量历史数据再无缝切到增量：新增的插入数据会追加到实时一致性快照中，更新的数据则会在已有历史数据里做更新。

双写的时候两边数据不一致怎么办？ 先定位是哪个环节导致的不一致。双写逻辑有 bug 就修复后用同步链路做一次全量覆盖同步；同步链路和双写冲突就检查写入是否幂等，用 UPSERT 或加唯一键约束；实在不行就跑数据修复脚本，以旧库为准把差异数据补到新库。
几十亿条数据的大表怎么迁移？ 分批迁移，按时间或主键范围切成多个批次、每批几百万条，可以用 pt-archiver 这类工具限速同步，避免对线上业务造成压力。全量同步完再开增量同步，后面流程和小表一样。大表迁移周期长，可能要跑几天甚至几周。
迁移到新库后性能反而变差怎么排查？ 先看索引是不是没建全，新库索引结构要和旧库保持一致；再检查新库配置参数如 buffer_pool_size、连接数是否合理；再看硬件规格，云数据库不同规格性能差很多；最后用 EXPLAIN 分析慢 SQL 看执行计划有没有变化，可能是统计信息不准导致优化器选错执行计划。

❌ 千万别说的话

  • “停机一小时做全量迁移最稳妥，数据量再大也就多等一会儿。”
  • “双写直接把两边都写上就行了，不用管先后顺序，也不用做幂等。”

35. 什么是批量数据入库？相比单条插入有什么优势？

🎬 面试现场

面试官（口语化）：我们每天要往数仓塞几十万条记录，现在是一条条 insert 的，太慢了，批量入库到底快在哪？

⚠️ 翻车点

最容易被翻车的点是不提 rewriteBatchedStatements——用 JDBC 或 MyBatis 的 Batch 不加这个参数，性能可能比手动拼接 SQL 差一个量级（实测 1000 条 55663ms vs 2275ms）。

📝 现场作答

  • 批量数据入库就是把多条数据攒一起，用一条 SQL 或一次数据库交互一口气插进去，不是一条一条慢慢 insert。
  • 优势集中在两点：①减少网络往返，单条插入每条数据都要客户端和数据库握一次手，10 万条就是 10 万次 RTT，批量插入一次发过去，网络开销直接降到原来的几百分之一；②摊薄数据库开销，每条 SQL 执行都要走解析、编译、写日志这套流程，批量操作把这些固定成本分摊到几千上万条数据上，单条成本可忽略。写法上单条是 10 万条 INSERT 语句，批量则是一条 INSERT INTO user(name, age) VALUES ('yes', 18), ('yupi', 19), ...。
  • 三种常见实现方式：①JDBC 原生方式，用 PreparedStatement 的 addBatch() 和 executeBatch()；②SQL 拼接，直接写 INSERT INTO table VALUES (v1), (v2), (v3), ... 多值语句；③ORM 框架封装，如 MyBatis-Plus 的 saveBatch()、MyBatis 的 insertBatch()。
  • 用 JDBC 或 MyBatis 的 Batch 方式，一定要在连接串加 rewriteBatchedStatements=true，不加性能可能差 25 倍左右。原理是 MySQL 驱动会把一批 insert 重写成 insert into xxx values (a),(b),(c)... 一条语句，和手动拼接效果一样。该参数默认是 false，因为批量语句中某条失败会导致整批失败不好定位问题，且参数不同的批量语句可能导致查询缓存失效；但实际项目中这两点影响不大，建议直接开启。
  • 实测对比（1000 条数据）：单条循环插入 121011ms；MyBatis-Plus saveBatch 59927ms，它比单条快一倍但底层是 for 循环一条条执行 sqlSession.insert，攒够一定数量才 flush 一次；saveBatch + rewrite 2589ms；手动拼接 SQL 2275ms；JDBC executeBatch 55663ms（底层逻辑和 saveBatch 差不多）；JDBC executeBatch + rewrite 324ms。结论：用 JDBC 或 ORM 的 Batch 功能务必加 rewriteBatchedStatements=true；手动拼接 SQL 要注意单次拼接数量别太大，分批处理。
  • 批量大小建议：一般 500 到 5000 条一批。一次插 10 万条有三个风险——SQL 过长超过 max_allowed_packet 限制会直接报错（MySQL 默认 4MB）、单条事务太大导致 undo log 和 redo log 暴涨失败回滚时间很长、长时间持有锁影响其他业务。所以大批量要拆成小批次、每批几千条、分多次提交。

批量插入时怎么获取自增主键？ JDBC 的 getGeneratedKeys() 可以批量拿回来。MyBatis-Plus 的 saveBatch 默认不返回，需要配置 useGeneratedKeys=true，而且实体类的 ID 字段会被自动填充。注意拼接 SQL 那种方式用 SELECT LAST_INSERT_ID() 只能拿到第一条的 ID，后面的要自己算。
批量插入遇到主键冲突怎么处理？ 三种策略：INSERT IGNORE 遇到冲突直接跳过不报错；REPLACE INTO 遇到冲突先删后插相当于覆盖；ON DUPLICATE KEY UPDATE 遇到冲突执行更新逻辑。幂等重试场景用 IGNORE，全量同步用 REPLACE，增量更新用 ON DUPLICATE KEY。
rewriteBatchedStatements 对 UPDATE 和 DELETE 也有效吗？ 对 UPDATE 有效但效果不如 INSERT 明显：UPDATE 的 rewrite 不是拼成一条 SQL，而是把多条 UPDATE 打包成一个网络包发送以减少 RTT，DELETE 同理。不过批量 UPDATE 的优化空间本来就有限，真要大批量更新建议直接写一条带条件的 UPDATE 语句，比如 UPDATE table SET status=1 WHERE id IN (1,2,3,...)。

36. 多线程并发同步数据时（数据库的数据同步到数仓中）需要注意什么问题？

🎬 面试现场

面试官（口语化）：我们要用多线程把 MySQL 的数据同步到数仓去，多个线程并发消费同一批 binlog 变更，你说说这中间会踩什么坑？

⚠️ 翻车点

最容易漏掉「同一行数据的变更必须有序」这一点——binlog 本身有严格顺序，多线程并发一打乱，同一行先 UPDATE A 再 UPDATE B 变成 B 先 A 后，最终数据就是错的。

📝 现场作答

  • 核心目标是数据一致性和正确性，同时把性能拉满。三个关键问题必须解决。
  • ①数据顺序错乱：binlog 本身有严格顺序，多线程并发就乱了，同一行数据先 UPDATE A 再 UPDATE B，调度一乱变成 B 先执行 A 后执行，最终数据就是错的。解决思路是同一行数据的变更必须由同一个线程按顺序处理——按主键哈希路由到固定的 Kafka 分区，每个分区只有一个消费线程，分片内天然有序，分片粒度按主键或按表都行。
  • ②数据丢失或重复：同步任务用 checkpoint 记录消费位点，但线程处理完数据挂了位点没提交，重启后重复消费；位点提交了但写入失败，数据就丢了。解决办法是把位点和数据写入绑定成原子操作——同一事务里先 INSERT INTO dw_table (...) VALUES (...), (...) ON CONFLICT (pk) DO UPDATE SET ... 批量 UPSERT，再 UPDATE sync_offsets SET binlog_pos = 'new_position' WHERE shard_id = 'current_shard' 更新位点，最后 COMMIT。
  • ③写入性能瓶颈：读是并行的，写入端容易成瓶颈，尤其数仓侧锁竞争严重。两个优化方向：一是用 UPSERT 实现幂等写入，重试不会报错（UPSERT 是 UPDATE 和 INSERT 的合体，数据不存在就插入、存在就更新，没有 UPSERT 重复写入就会主键冲突报错）；二是攒批处理，每 100 条或每秒提交一次，减少网络往返和事务开销。
  • Kafka 层面的可靠性：链路一般是源库 → Binlog 采集 → Kafka → 消费者 → 数仓。消息丢失三个场景——生产端丢失（acks 配置为 0 或 1，Leader 没同步给 Follower 就挂了，解决是 acks=all 等所有 ISR 副本确认）、Broker 端丢失（消息写入 PageCache 还没刷盘机器宕机，解决是调小刷盘间隔或开启同步刷盘但性能下降）、消费端丢失（拿到消息就提交 offset，处理失败数据就没了，解决是先处理再提交、失败重试）。消息重复要靠幂等处理：数据库唯一约束 + UPSERT、消费端维护已处理 ID 集合（可用 Redis 的 Set）、业务逻辑本身幂等（直接覆盖而不是累加）。
  • 分片策略：按表分片简单且有表级顺序保证但大表成瓶颈；按主键哈希负载均衡但跨行事务顺序难保证，适合单表数据量大；按库分片隔离性好但库少时并发度低。Canal、Debezium 这些 CDC 工具都支持配置分片策略。
  • 性能调优：批量大小一般 100-1000 条或 1-5 秒攒一批，太小频繁提交开销大、太大内存占用高且失败重试代价大；并发度和分片数匹配，Kafka 分区数决定最大并发度、线程数超过分区数没意义；数仓侧 ClickHouse 用 ReplacingMergeTree 天然支持去重，Hive/Spark 可以分区覆盖写入；监控消费延迟 lag、写入耗时、失败率，超阈值告警。

同步过程中源库做了 DDL（比如加字段）会怎样？ 大多数 CDC 工具对 DDL 处理比较粗暴。Canal 默认把 DDL 当成一条特殊事件发出来，消费端要自己处理，比如暂停消费、修改数仓表结构、再恢复。Debezium 支持 schema registry，能自动感知结构变化，但下游系统能不能适配是另一回事。生产环境建议 DDL 走单独的发布流程，同步任务和 DDL 操作错开执行。
数据同步延迟太大怎么排查？ 从三个环节查：一看 Binlog 采集端，是不是源库写入太猛、采集跟不上，监控 Binlog 位点增长和采集延迟；二看 Kafka，看消费者 lag 有多大、分区是否均衡；三看写入端，是不是数仓侧写入太慢、锁等待严重。定位瓶颈后要么加并发、要么加大批量、要么优化目标端写入性能。
同步任务宕机重启后怎么保证不丢数据？ 靠 checkpoint 机制：每次成功写入一批数据后把当前消费位点持久化下来，可以存 Kafka 自带 offset，也可以存数仓的位点表里，重启后从最近一次 checkpoint 恢复消费。为避免位点提交成功但数据没写入，位点和数据必须在同一个事务里提交，或者写入逻辑要幂等，重复消费不产生脏数据。
全量同步和增量同步怎么配合？ 先全量后增量，关键是切换时机。全量同步开始前先记录当前 Binlog 位点，全量导完后从这个位点开始增量消费。如果全量同步时间长、期间源库还在写入，Binlog 可能被清理掉，这时候要么调大 Binlog 保留时间，要么全量增量并行跑一段时间再切换。

37. 什么是 MySQL 的主从同步机制？它是如何实现的？

🎬 面试现场

面试官（口语化）：MySQL 主从同步到底怎么跑起来的？主库挂了怎么办？

⚠️ 翻车点

只说「binlog 复制」不够，一定要能讲出三个线程的分工和半同步的两种模式；主从延迟的应急手段也常被追问。

📝 现场作答

  • 核心是 binlog 复制：主库把写操作记到二进制日志里，从库拉过来重放一遍。
  • 三个线程：主库的 dump 线程监听 binlog 变更并推送事件给从库；从库的 I/O 线程拉取主库数据写进本地 relay log；从库的 SQL 线程读 relay log 逐条执行 SQL。
  • 三种复制模式按主库返回时机区分：异步复制写完 binlog 立即返回（性能最高，主库挂了可能丢数据）、同步复制等所有从库确认（性能最差、可靠性最高）、半同步复制等至少 N 个从库确认（折中）。
  • MySQL 默认异步复制；5.5 引入半同步复制插件，5.7 做了增强，核心是不用等所有从库，有一个确认即可。
  • 5.7 区分两种半同步模式：AFTER_COMMIT 是主库先提交事务再等从库确认，主库提交后确认前挂掉会导致新主库没这条数据但客户端已收到成功响应；AFTER_SYNC 是主库先等从库确认再提交，更安全。
  • 并行复制演进：5.6 只能按库并行；5.7 引入 LOGICAL_CLOCK，主库同时处于 prepare 阶段的事务肯定不冲突，打上相同 last_committed 标记，从库看到相同标记即可并行执行；配套参数 binlog_group_commit_sync_delay 和 binlog_group_commit_sync_no_delay_count 控制组提交等待。
  • 8.0 引入 WriteSet，通过主键或唯一索引算哈希判断两个事务是否更新同一行，没冲突就能并行回放，摆脱对主库并行度的依赖。
  • 主从延迟常见原因：从库配置比主库差、从库承担大量读请求或报表被抢占资源、大事务（改几百万行）、主库并发高从库并行复制跟不上。
  • 监控延迟可用 SHOW SLAVE STATUS 里的 Seconds_Behind_Master，但它是 relay log 最后一个事件时间戳与当前时间的差值，网络抖动会影响，更靠谱的是用 pt-heartbeat 往主库定时写时间戳，从库读出算差值。
  • 提升从库为新主库：确认 relay log 已全部回放完，STOP SLAVE 停复制，RESET SLAVE ALL 清主库信息，改应用配置指向新主库，其他从库 CHANGE MASTER TO 指向新主库；用 MHA 或 Orchestrator 可自动完成切换并对齐 binlog 位点。

38. 什么是分库分表？分库分表有哪些类型（或策略）？

🎬 面试现场

面试官（口语化）：单库单表撑不住我们的业务了，你说说分库分表到底是分什么，有哪几种分法？

⚠️ 翻车点

只答「水平分片、垂直分片」这种两级分类，而分不清「分表」和「分库」是两件事；或者讲不出分片键选型差异——哈希取模扩容要全量迁移，范围分片会有热点，一致性哈希才能只迁相邻节点。

📝 现场作答

  • 分库分表就是把原本存在一个数据库或一张表里的数据，拆散到多个数据库或多张表里去：单机扛不住了就加机器，单表太大了就拆小表。
  • 水平分表：同一张表的数据按行拆分，比如按用户 ID 取模分成 user_0、user_1、user_2，每张表结构一模一样，只是数据不同。
  • 垂直分表：把宽表的列拆开，冷热分离。比如用户表拆成 user_base 存用户名、手机号，user_detail 存个人简介、头像这些占空间的字段。
  • 水平分库：表结构复制到多个数据库实例，数据按规则分散存储，比如订单按用户 ID 哈希到 order_db_0、order_db_1、order_db_2。
  • 垂直分库：按业务模块拆库，用户放 user_db、订单放 order_db、商品放 product_db，微服务架构下基本都这么干。
  • 为什么上分库分表：MySQL 默认最大连接数 151，调到 2000 也扛不住几万 QPS；InnoDB 的 B+ 树数据越多树越高，树高每加一层就多一次磁盘 I/O，单表超过 2000 万到 5000 万行就得考虑拆，字段多的可能 1000 万就撑不住。
  • 分表解决的是单表数据量过大导致查询慢，分库解决的是单机资源瓶颈，把压力分摊到多台服务器。
  • 水平拆分的核心是选分片键，三种常见策略：哈希取模（分布均匀但扩容要重新分配大量数据）、范围分片（扩容方便但最新库压力最大、容易热点）、一致性哈希（扩容只迁移相邻节点部分数据，ShardingSphere 支持）。
  • 代价：跨库 JOIN 要拆成多次查询在应用层组装或做数据冗余；分布式事务得上 Seata 这类框架用 AT 或 TCC 模式；自增主键会冲突，得换 Snowflake、Leaf 这类分布式 ID；count、order by、group by 这类跨分片聚合要各分片拉数据回来合并；运维从盯一个库变成盯几十个。
  • 常用中间件：ShardingSphere（Apache 顶级项目，分 JDBC 和 Proxy 两种模式）、MyCat（基于 Cobar 改进，代理模式，社区不太活跃）、Vitess（YouTube 出品，云原生，专为 MySQL 设计，适合 Kubernetes）、TDSQL 与 PolarDB-X（腾讯云和阿里云的分布式数据库，对上层透明）。

分片键选得不好会出什么问题？怎么补救？ 最常见是数据倾斜，某些分片数据量特别大成了热点。补救：一是加二级分片，大商家数据再按订单 ID 取模分一次；二是引入虚拟节点，把物理分片映射成更多虚拟分片；三是直接改分片键，但成本最高，得全量迁移数据。
不停机扩容怎么做？ 双写加灰度切换：搭好新分片→新老库双写→用 Canal 监听 binlog 增量同步老数据→数据校验→灰度切读流量→观察后全切写流量→下掉双写逻辑。整个过程可能好几周，期间要盯数据一致性。
分库分表后怎么做跨分片分页查询？ 最笨的办法是每个分片都查 limit offset + size 再在内存合并排序，limit 10000,10 配 16 个分片就是 16 万条在内存排序。优化方向：禁止深分页（产品上限制只看前 1000 条）；用游标分页记住上一页最后一条的排序字段值；或用 ES 做分页、数据库只做主键回查。

❌ 千万别说的话

  • “分库分表就是分库或者分表，二选一”——水平/垂直两个维度都可以同时作用在库和表上。
  • “哈希取模扩容也很方便，加个库就行”——扩容要重新分配大量数据，这是它最大的坑。
  • “分库分表之后 SQL 不用改，中间件会透明处理一切”——跨库 JOIN、跨分片聚合、分布式事务都得业务侧或中间件显式处理。

39. 为什么在 MySQL 中不推荐使用多表 JOIN？

🎬 面试现场

面试官（口语化）：我们代码里好多 SQL 都是三个表以上 JOIN，为什么你们不让这么写？

⚠️ 翻车点

被追着问「那 JOIN 到底是不是一定慢」时容易露怯——2 个表、索引合理、数据量可控的 JOIN 没问题，不推荐的是超过 3 个表的大 JOIN。

📝 现场作答

  • 核心原因是数据库往往是系统瓶颈，把复杂关联交给数据库会占用大量 CPU 和内存，影响其他查询；这里说的多表一般指超过 3 个表的 JOIN，阿里 Java 开发手册明确写了「超过三个表禁止 JOIN」。
  • 数据量小时差别不明显，但每张表几百万、几千万行时问题被放大：JOIN 要对每个表扫描、匹配、组合，执行计划一旦选错就可能全表扫描，一个慢查询就能把数据库 CPU 打满。
  • 更好的做法是把 JOIN 拆成多次单表查询，在应用层做关联：应用服务器可水平扩展，加机器就能扛流量，而数据库扩展成本高得多。
  • 执行原理：MySQL 会选一张表作驱动表、另一张作被驱动表，遍历驱动表每一行拿关联字段去被驱动表查匹配记录。
  • 假设驱动表 10 万行、被驱动表 100 万行：被驱动表关联字段有索引时每次是 B+ 树查找 O(logN)；没索引就是 10 万 × 100 万 = 1000 亿次比较，直接爆炸。所以 JOIN 时必须保证被驱动表关联字段有索引。
  • 小表驱动大表原则：驱动表行数 A、被驱动表行数 B 且被驱动表关联字段有索引时，复杂度约 A × 2log₂B。A=1000、B=100 万约 4 万次操作；反过来 A=100 万、B=1000 约 2000 万次操作，差 500 倍。
  • 优化器有时会选错驱动表，可以用 STRAIGHT_JOIN 强制指定顺序，例如 SELECT * FROM small_table STRAIGHT_JOIN big_table ON small_table.id = big_table.ref_id;。
  • 应用层关联的好处：单表查询更容易命中索引、执行计划稳定；结果可直接缓存到 Redis，而 JOIN 查询涉及多表、任何一张表更新都要失效缓存；分库分表后跨库 JOIN 基本没法做，提前把关联放到应用层后面扩展改动小；应用服务器便宜好扩展。
  • 什么时候可以用 JOIN：表数量不超过 3 个、每张表百万级以内、关联字段都有索引、用 EXPLAIN 确认没有全表扫描、查询频率不高。报表查询和后台管理系统没问题，面向用户的高频接口要拆。
  • 被驱动表没索引时 MySQL 会用 Block Nested-Loop Join，把驱动表批量装进 join_buffer 再批量比较，join_buffer 默认 256KB，只是优化不是救命稻草；MySQL 8.0.18 之后引入 Hash Join，对无索引等值 JOIN 有提升，但最佳实践仍是建好索引。

💡 主动加分的追问准备

面试官追问 你的答案
如果业务上必须用多表 JOIN，有什么优化手段？ 检查关联字段是否都有索引并用 EXPLAIN 看有没有全表扫描；用 STRAIGHT_JOIN 强制小表驱动大表；用 WHERE 条件先过滤再 JOIN 缩小范围；定期报表 SQL 放业务低峰期执行；实在不行做一张宽表把关联结果提前算好用空间换时间。
应用层关联会不会增加网络开销？查 3 次肯定比查 1 次慢吧？ 网络开销确实增加，但整体耗时不必然更长：3 次走索引的单表查询每次可能几毫秒，加起来十几毫秒；一次执行计划不好的复杂 JOIN 可能几百毫秒甚至几秒。而且单表查询结果可缓存，第二次请求直接命中，JOIN 很难缓存，整体吞吐量反而更高。
分库分表之后跨库 JOIN 怎么处理？ 数据库层面基本没法做。方案有：冗余字段，把常关联字段冗余到主表；全局表，字典表、配置表这种小表在每个分库放一份；应用层关联，分别查两个库再在内存 merge；或用数据中台把分散数据同步到 ES 或数仓做聚合查询。没有银弹，按业务场景选。

❌ 千万别说的话

  • “JOIN 一定比多次单表查询慢”——索引合理、数据量可控时 2 表 JOIN 完全没问题。
  • “不用管驱动表，MySQL 自己会选最优的”——优化器确实会尝试选小表驱动大表，但会选错，STRAIGHT_JOIN 就是为此准备的。
  • “分库分表后 JOIN 中间件能帮我跨库做”——跨库 JOIN 基本做不了，要么冗余要么应用层组装。

40. MySQL 中 INNER JOIN、LEFT JOIN 和 RIGHT JOIN 的区别是什么？

🎬 面试现场

面试官（口语化）：INNER、LEFT、RIGHT 这几个 JOIN 到底差在哪儿，LEFT JOIN 的过滤条件放 ON 和放 WHERE 有区别吗？

⚠️ 翻车点

LEFT JOIN 时把右表过滤条件写进 WHERE，会把左表没匹配的行全部过滤掉——这是最常被追问翻车的点。

📝 现场作答

  • 核心区别在于如何处理不匹配的行：INNER JOIN 只返回两表都能匹配上的行，相当于取交集；LEFT JOIN 返回左表所有行，右表没有匹配则填 NULL；RIGHT JOIN 返回右表所有行，左表没有匹配则填 NULL。
  • 举例：users 的 id=1,2,3，orders 的 user_id=1,1,2。INNER JOIN 返回用户 1（2 条）和用户 2（1 条），用户 3 不返回；LEFT JOIN 返回所有用户，用户 3 的 order 字段为 NULL；FROM orders o RIGHT JOIN users u ON o.user_id = u.id 和 FROM users u LEFT JOIN orders o ON u.id = o.user_id 结果一样。
  • 业务场景：INNER JOIN 用于「下过单的用户列表」这类只关心两边都有数据的情况；LEFT JOIN 用于报表，如「所有用户及其订单数量，没订单的显示 0」，配合 COUNT(o.id) 分组；LEFT JOIN + WHERE o.id IS NULL 可以找出「左表有但右表没有」的记录，比如没下过单的用户。
  • RIGHT JOIN 实际很少用，能用 LEFT JOIN 换表位置做的一律用 LEFT JOIN，主表放左边更符合阅读习惯，阿里 Java 开发手册也建议统一用 LEFT JOIN。
  • ON 与 WHERE 的区别：LEFT JOIN 时条件放 ON 是先关联再过滤，左表数据不会丢，ON u.id = o.user_id AND o.amount > 100 下用户 3 仍会返回、order 字段为 NULL；条件放 WHERE 是关联完再过滤，WHERE o.amount > 100 下 NULL > 100 为 false，用户 3 被过滤掉。INNER JOIN 时两者效果一样，因为不匹配的行本来就会被丢弃。
  • JOIN 的执行顺序由优化器选择，一般遵循小表驱动大表，但会判断错；可以用 STRAIGHT_JOIN 强制指定顺序，不过除非确定优化器选错，一般不建议。
  • CROSS JOIN 是笛卡尔积，不需要 ON 条件，左表 100 行、右表 200 行结果就是 20000 行，业务中少用，但生成 SKU 之类的组合数据时有用。
  • MySQL 不直接支持 FULL OUTER JOIN，需要用 UNION 模拟：SELECT * FROM a LEFT JOIN b ... UNION SELECT * FROM a RIGHT JOIN b ...，两边都有的数据想只出现一次用 UNION，想保留重复用 UNION ALL 加去重逻辑。

💡 主动加分的追问准备

面试官追问 你的答案
LEFT JOIN 和 LEFT OUTER JOIN 有什么区别？ 没区别，OUTER 可省略。LEFT JOIN 是 LEFT OUTER JOIN 的简写，INNER JOIN 是 JOIN 的简写，SQL 标准里 OUTER 是可选的，MySQL、PostgreSQL、Oracle 都支持省略。
怎么用 LEFT JOIN 实现 INNER JOIN 的效果？ 在 WHERE 里加右表字段 IS NOT NULL 的条件，比如 WHERE o.id IS NOT NULL，把填 NULL 的行过滤掉，效果等同 INNER JOIN；反过来想找左表有右表没有的，就用 WHERE o.id IS NULL。
MySQL 支持 FULL OUTER JOIN 吗？怎么实现？ 不直接支持，要用 UNION 模拟：先 LEFT JOIN 拿左表全部，再 RIGHT JOIN 拿右表全部，UNION 合并去重；想保留重复就用 UNION ALL 再自己加去重逻辑。

❌ 千万别说的话

  • “LEFT JOIN 就是在 WHERE 里加个条件过滤一下”——放错位置会把左表数据整个丢掉。
  • “RIGHT JOIN 和 LEFT JOIN 结果不一样”——只是写法方向不同，换个表位置就能互相转换。
  • “MySQL 支持 FULL OUTER JOIN”——要用 UNION 模拟。

41. 什么是数据库的视图？

🎬 面试现场

面试官（口语化）：视图到底是个什么东西？用视图查数据会不会变慢，能建索引吗？

⚠️ 翻车点

以为视图能「让查询变快」或「能像表一样建索引」——视图不存数据，MySQL 的视图也不能直接建索引。

📝 现场作答

  • 视图是一张虚拟表，本身不存数据，每次查询时现场执行定义好的 SQL 去底层表取数据，可以理解成一条起了名字的 SELECT 语句，查视图等于执行那条 SQL。
  • 三个最常见用途：封装复杂查询，把多表 JOIN、子查询藏起来对外暴露一张简单的「表」；控制数据访问权限，只让用户看到部分字段（比如员工表只暴露姓名和部门，薪资不给看）；提供稳定接口，底层表结构改了只调整视图定义，上层应用不用动。
  • 视图查询时 MySQL 会把视图定义里的 SQL 和查询条件合并成一条 SQL 执行，比如视图定义是 SELECT * FROM orders WHERE status = 1，查 SELECT * FROM v_orders WHERE amount > 100，实际执行的是 SELECT * FROM orders WHERE status = 1 AND amount > 100，这个过程叫视图合并，是 MySQL 优化器的默认处理方式。
  • 不能合并的情况：视图里有聚合函数、DISTINCT、GROUP BY、UNION 等，这时 MySQL 会先把视图结果物化成临时表再执行外层查询，性能差很多。
  • 可更新视图的条件：只能基于单表不能有 JOIN；没有聚合函数、GROUP BY、DISTINCT、UNION；没有子查询；SELECT 列表里都是表的真实列，没有表达式或计算列。比如 CREATE VIEW v_active_users AS SELECT id, name, email FROM users WHERE status = 1; 之后可以直接 UPDATE v_active_users SET name = '张三' WHERE id = 1;，但实际项目里很少对视图做写操作，还是当只读用稳妥。
  • 性能问题：视图不存数据、每次现算，不会让查询变快，底层 SQL 慢则封装成视图一样慢；视图嵌套更要小心，一般建议嵌套不超过 2 层。
  • 需要「存结果提升性能」应该用物化视图，但 MySQL 原生不支持，得自己用触发器或定时任务把数据同步到一张真实表；Oracle 和 PostgreSQL 原生支持物化视图。
  • 视图与临时表区别：视图不存数据、永久存在、每次现算，用于封装复杂 SQL 和权限控制；临时表真实存数据、会话结束自动删除、查询时直接读数据，用于中间结果暂存。
  • 常用命令是 CREATE VIEW、ALTER VIEW、DROP VIEW，使用方式和查普通表一样，比如 SELECT * FROM v_employee_dept WHERE dept_name = '研发部';。

💡 主动加分的追问准备

面试官追问 你的答案
视图能建索引吗？ MySQL 的视图不能直接建索引，因为视图不存数据，索引没地方放；但视图底层的表可以建索引，查视图时会用到底层表的索引。Oracle 的物化视图因为真存数据可以建索引，MySQL 要实现类似效果得自己维护一张汇总表。
用视图会影响查询性能吗？ 视图本身不会让查询变快或变慢，关键是底层 SQL 的执行效率：能合并时执行计划和直接写 SQL 一样；视图里有聚合、DISTINCT 等没法合并的操作，MySQL 会先物化成临时表再查，可能反而更慢；视图套视图多层嵌套时展开后的 SQL 又长又难优化。
什么情况下你会用视图？ 三种：复杂报表查询，把一堆 JOIN 和子查询封装成视图，业务代码直接 SELECT 视图；权限控制，建个视图只暴露允许的列再给这个视图授权；兼容老接口，底层表要重构但上层不想动，建个同名视图做过渡。

❌ 千万别说的话

  • “用视图可以提升查询性能”——视图每次现算，只会更慢或持平。
  • “MySQL 的视图可以像表一样建索引”——不存数据就没地方放索引。
  • “视图和表一样，可以随便增删改”——多表 JOIN、含聚合或 DISTINCT 的视图不能更新。

42. 为什么不推荐在 MySQL 中直接存储图片、音频、视频等大容量内容？

🎬 面试现场

面试官（口语化）：为什么大家都说图片别往 MySQL 里塞？放进去到底会出什么事？

⚠️ 翻车点

只说「占空间、影响性能」这种泛泛的话，讲不出 Buffer Pool 污染、binlog 膨胀、备份膨胀这三条具体的因果链。

📝 现场作答

  • MySQL 是关系型数据库，核心职责是高效处理结构化数据和维护数据之间的关系，存大文件本就不擅长。
  • Buffer Pool 会被撑爆：单次查询拿几 MB 到几十 MB 的 BLOB，本来能缓存几万条热点数据，存图片后只能放几百张。
  • binlog 与主从同步被拖垮：一张 5MB 图片在 binlog 里也要写 5MB，主从同步带宽瞬间被吃满、延迟飙升；ROW 模式下每天 10 万条、平均 200KB 的头像就是一天 20GB binlog，千兆网卡跑满 100MB/s 出头，20GB 至少跑 3 分钟以上，主从延迟持续累积。
  • 备份恢复成本成倍增长：mysqldump 是逻辑备份，BLOB 会被转成十六进制字符串、体积膨胀一倍，10GB 变 500GB、mysqldump 跑一晚上都跑不完；Percona XtraBackup 稍好，但全量备份动辄上 TB、每天增量也要几百 GB。
  • BLOB 存储机制：MySQL 有 TINYBLOB（255B）、BLOB（64KB）、MEDIUMBLOB（16MB）、LONGBLOB（4GB）四种类型；InnoDB 对超过 768 字节的 BLOB 值只在数据页内存前 768 字节，其余放溢出页，读一条含大 BLOB 的记录要跨多个溢出页，随机 IO 成倍增加——一张 3MB 图片在默认 16KB 页下要读接近 200 个页。
  • Buffer Pool 污染：Buffer Pool 是 LRU 缓存，默认大小一般是物理内存的 50%-70%，16GB 内存机器配 8GB；一次全表扫描就能把热点数据全挤出去，后续查询全部 cache miss，响应从毫秒级掉到秒级。MySQL 5.6 之后引入 young/old 分区缓解，但大 BLOB 量大仍扛不住。
  • 正确做法：大文件放对象存储（阿里云 OSS、AWS S3、腾讯云 COS、MinIO）或文件系统，数据库里只存一个 URL 或文件路径，几十个字节搞定。
  • 对象存储的独有能力：水平扩展无上限（MySQL 分库分表很痛苦）、原生支持 CDN 加速、签名 URL 与时效控制可防盗链、存储成本几分钱/GB/月远低于高性能 SSD、独立带宽不和业务查询抢连接。

💡 主动加分的追问准备

面试官追问 你的答案
业务上确实需要保证图片和业务数据的事务一致性，怎么办？ 用本地消息表做最终一致性：先上传对象存储拿 URL，再在一个事务里同时写业务表和文件记录表；如果上传成功但事务回滚，后台起定时任务扫描孤儿文件删掉。追求强一致可以用 Seata 的 TCC 模式，但代价大，一般最终一致性就够。
老系统已经把图片存在 MySQL 里了，怎么平滑迁出去？ 三步走：第一步新数据直接写对象存储、老代码兼容，读时判断是 URL 还是 BLOB；第二步后台批量迁移历史数据，每批迁移完更新对应记录的 URL 字段并清空 BLOB；第三步所有 BLOB 清空后用 pt-online-schema-change 把 BLOB 列删掉。全程不停服，但批量迁移要控制速度，别把数据库 IO 打满。
对象存储挂了怎么办，URL 全 404 业务不也崩了？ 选大厂的对象存储服务，阿里云 OSS 承诺 99.995% 可用性，比自建 MySQL 高可用还靠谱；真要兜底就开启跨区域复制，主 bucket 在杭州、备 bucket 在上海，DNS 解析做健康检查自动切换。自建的话 MinIO 支持多节点部署和纠删码，单节点挂了数据不丢。总之比把所有鸡蛋放在数据库一个篮子里强。

❌ 千万别说的话

  • “数据库存图片只是慢一点而已”——会撑爆 Buffer Pool、撑爆 binlog、拖垮备份恢复。
  • “存 BLOB 还能省一次网络请求”——真按 URL 存时读文件走的是对象存储/CDN，数据库只回几十字节。
  • “MySQL 存大文件性能也可以优化”——BLOB 溢出页机制决定的，随机 IO 成倍增加是结构性问题。

43. 相比于 Oracle，MySQL 的优势有哪些？

  • MySQL 最大的优势是免费开源和轻量易用，对互联网公司这两点几乎是决定性的。

  • 上手门槛低：MySQL 安装就是解压加几行命令，Oracle 要配置监听、实例、表空间，新手折腾一天都不一定跑起来。
  • 资源占用少：MySQL 空跑内存占用几十 MB，Oracle 启动就要吃掉几百 MB 到几 GB。
  • 生态繁荣：GitHub 上跟 MySQL 相关的开源项目有几十万个，中间件、ORM 框架、分库分表工具应有尽有，Stack Overflow 上基本都有答案。
  • 架构差异：MySQL 是单进程多线程，一个 mysqld 处理所有连接、每连接一个线程，灵活但一个线程崩了可能影响整个进程；存储引擎可插拔（InnoDB、MyISAM、Memory 各有用途）。Oracle 是多进程架构，有 PMON、SMON、DBWR、LGWR 等后台进程各司其职，还有 SGA 共享内存区协调各进程，复杂但健壮，适合 7×24 关键业务。
  • 功能对比：存储过程 MySQL 支持但功能有限、Oracle 的 PL/SQL 功能强大；物化视图 MySQL 8.0 开始支持但功能弱、Oracle 完善且自动刷新；分区表 MySQL 只支持基本分区、Oracle 支持复合分区和间隔分区；位图索引 MySQL 不支持、Oracle 支持且适合低基数列；并行查询 MySQL 8.0 开始支持、Oracle 成熟可指定并行度；闪回查询 MySQL 不支持、Oracle 支持；RAC 集群 MySQL 不支持；TDE 加密 MySQL 只有企业版支持。
  • 高可用：MySQL 靠主从复制加第三方工具（MHA、Orchestrator、MySQL Group Replication），故障切换可能有几秒到几十秒不可用还可能丢数据；Oracle 的 Data Guard 可做零数据丢失同步复制，RAC 是多节点共享存储，节点挂了其他立刻接管、应用感知不到，代价是一套 RAC 加共享存储硬件加软件上千万很正常。
  • 互联网公司选 MySQL 的原因：业务大多读多写少，主从复制加读写分离能扛几十万 QPS；分库分表是互联网应对数据量的标准做法，ShardingSphere、MyCat 都围绕 MySQL 设计；学习曲线平缓，新人几天上手而 Oracle DBA 培养周期按年算；云厂商的托管 MySQL（阿里云 RDS、AWS Aurora、腾讯云 TDSQL）成熟、运维成本几乎为零。淘宝、美团、字节的核心业务全是 MySQL。
  • 传统企业选 Oracle：Data Guard 能做到 RPO=0、RTO<30 秒；复杂 OLAP 查询的优化器和并行执行引擎远强于 MySQL；大量使用存储过程和触发器，PL/SQL 是完整的编程语言；合规要求认证；出了问题有厂商工程师远程支援。

44. MySQL 中 EXISTS 和 IN 的区别是什么？

🎬 面试现场

面试官（口语化）：EXISTS 和 IN 到底有什么区别，写哪个更好？NOT IN 我用出过一次诡异结果，是什么坑？

⚠️ 翻车点

NOT IN 遇到子查询里有 NULL 会直接返回空结果——这是隐藏的 NULL 陷阱，也是这一题最容易翻车的地方。

📝 现场作答

  • 两者都能实现子查询过滤，但执行机制完全不同：EXISTS 是逐行去子查询里探测有没有匹配，找到一条就停；IN 是先把子查询结果全算出来（物化），再拿外层数据去匹配。
  • 选哪个核心看两张表数据量对比：外表小、子查询表大用 EXISTS（外表 1000 行、子查询表 100 万行，EXISTS 最多执行 1000 次索引探测）；外表大、子查询表小用 IN（子查询只返回 100 条，缓存起来后外表 100 万行逐行匹配）；两边差不多都行，优化器现在挺聪明。
  • EXISTS 的执行是驱动表 + 被驱动表探测：外层每取出一行就拿关联字段去子查询探测，找到一条即返回 true 并停止当前探测。性能取决于「外表行数 × 单次探测成本」，子查询表再大只要有索引，单次探测就是 O(logN)。
  • IN 是先物化后匹配：先执行子查询把结果集全部算出来存到内存或临时表，外层再逐行去匹配。子查询返回 100 万条时光物化这一步就很重；如果外表也没有合适索引，MySQL 不得不对外表全表扫描，每行还要去物化表里做一次索引查询，性能瓶颈极其明显。
  • MySQL 5.6 之后优化器会根据情况把 IN 子查询转换成 EXISTS 或半连接，所以很多场景写 IN 和 EXISTS 实际执行计划一样；但复杂场景转换不了，保险起见还是按数据量特征手动选。
  • 用 EXPLAIN 看执行计划时关注 select_type 和 Extra：SUBQUERY 表示独立子查询、IN 被物化了；DEPENDENT SUBQUERY 表示关联子查询，是 EXISTS 的特征；MATERIALIZED 表示子查询结果被物化成临时表。
  • NOT IN 遇到 NULL 会出问题：SQL 三值逻辑下任何值与 NULL 比较都是 UNKNOWN，NOT IN 需要所有比较都为 false 才返回 true，出现一个 UNKNOWN 就返回空结果。
  • NOT EXISTS 没这个问题，能正常返回不匹配的行。所以子查询可能有 NULL 值时优先用 NOT EXISTS，或者在 IN 子查询里加 WHERE user_id IS NOT NULL。

面试官追问 你的答案
线上有个慢查询用了 IN 子查询，子查询返回 50 万条数据，怎么优化？ 核心问题是结果集太大。方向：改成 EXISTS 让外表驱动、每次只探测一条用子表索引；业务允许时把子查询结果按时间范围拆成多次小查询；改成 JOIN，很多场景 JOIN 比 IN 子查询性能更好、优化器处理 JOIN 更成熟；子查询结果相对固定时可提前算好放临时表或 Redis。
EXISTS 里面写 SELECT 1 和 SELECT * 有区别吗？ 执行层面没区别，EXISTS 只关心子查询有没有返回行，压根不看返回什么内容，写什么都一样，优化器都会忽略。但可读性上写 SELECT 1 更能表达「我只是探测存在性」的意图。
什么场景下 IN 比 EXISTS 快？ 子查询结果集很小的时候。比如只返回 10 个 ID，IN 放进内存哈希表，外层 100 万行每行做一次 O(1) 哈希查找；换成 EXISTS 就是 100 万次索引探测，单次虽快但累加起来开销大。另外静态列表场景如 WHERE status IN (1,2,3) 直接用 IN 就好。

  • “NOT IN 和 NOT EXISTS 随便选”——子查询里有 NULL 时 NOT IN 直接返回空结果。
  • “EXISTS 一定比 IN 快”——子查询结果集很小时 IN 反而更快。
  • “写 EXISTS 就要写 SELECT * 才有意义”——EXISTS 只看有没有返回行，写什么都一样。

45. 什么是数据库的逻辑删除？数据库的物理删除和逻辑删除有什么区别？

🎬 面试现场

面试官（口语化）：你们删数据是直接 DELETE 还是打个标记？如果打了标记，用户反复报名同一活动，唯一索引会不会炸？

⚠️ 翻车点

逻辑删除撞唯一索引这个问题答不上来——只加 is_deleted 到唯一索引里，用户反复横跳第三次操作照样冲突。

📝 现场作答

  • 逻辑删除是不真删数据，而是给记录打「已删除」标记，一般加 is_deleted 字段，0 正常、1 已删除，查询时自动带 WHERE is_deleted = 0 把已删除的过滤掉。
  • 物理删除就是直接 DELETE FROM user WHERE id = 1;，数据从表里彻底消失；逻辑删除是 UPDATE user SET is_deleted = 1 WHERE id = 1;。
  • 现在互联网业务基本都用逻辑删除，因为数据就是资产，删了想恢复、想做分析、想追溯都没门了。
  • 取舍：物理删除省空间、查询快，不用额外加 WHERE 条件，但数据没了就是没了；逻辑删除数据还在随时能恢复、能做审计分析，代价是表越来越大、查询要多带条件，而且开发时容易忘加过滤条件把已删除的数据也查出来。
  • 维度对比：存储空间上物理删除会释放、逻辑删除持续占用；数据恢复上物理删除不可能、逻辑删除改标记即可；查询性能上物理删除无额外开销、逻辑删除需要过滤条件；审计追溯上物理删除不支持、逻辑删除完整保留；开发复杂度上物理删除简单、逻辑删除每个查询都要带条件。
  • 唯一索引冲突的坑：活动报名表用 user_id + shop_id 做唯一索引，用户逻辑删除后再报名，新记录与那条已删除记录冲突；把 is_deleted 加进唯一索引也不行，用户反复横跳时 is_deleted 只有 0 和 1 两个值，第三次操作还是会冲突。
  • 解法一：把 is_deleted 换成 deleted_at，类型是 datetime 或 bigint 时间戳、默认 NULL，唯一索引改成 user_id + shop_id + deleted_at。删除时写入当前时间，每次删除的时间戳都不一样就不会冲突，判断逻辑变成 WHERE deleted_at IS NULL。
  • 解法二：用主键 ID 当删除标记，is_deleted 改成 bigint 默认 0，删除时把当前记录的主键 ID 写进去（如 2222），唯一索引用 user_id + shop_id + is_deleted，因为每条记录 ID 都不同不会冲突。判断未删除用 WHERE is_deleted = 0，已删除用 WHERE is_deleted > 0。
  • 解法三：复用记录 + 流水表。活动报名表只存当前状态，唯一索引用 user_id + shop_id，报名改 0、退出改 1、再报名再改 0，始终就这一条记录来回改；审计追溯交给流水表，每次操作插一条、只增不删不改。

逻辑删除的数据越来越多，查询变慢了怎么办？ 几个方向：is_deleted 字段要加进联合索引里，让走索引的查询直接过滤掉已删除数据；定期归档，把删除时间超过一定天数的数据迁到历史表，主表只保留活跃数据；用分区表，按时间或状态分区，查询时直接跳过历史分区。

46. 什么是数据库的逻辑外键？数据库的物理外键和逻辑外键各有什么优缺点？

🎬 面试现场

面试官（口语化）：你们建外键约束吗？为什么大厂都说不许用外键？

⚠️ 翻车点

只答「外键慢」而说不出具体慢在哪（级联更新爆炸、每次写都多一次检查、锁范围变大、死锁概率上升、分库分表建不了），也答不出逻辑外键怎么在应用层做校验。

📝 现场作答

  • 逻辑外键是不在数据库层面建外键约束，靠应用代码维护表间关联：数据库只存一个普通字段，比如订单表存 user_id，但检查由业务代码做。
  • 物理外键是真正建 FOREIGN KEY 约束，数据库自动检查关联数据是否存在，不存在就报错不让插入。
  • 现在互联网公司基本都用逻辑外键，阿里巴巴 Java 开发手册明确写了「不得使用外键与级联」，核心原因就一个字：慢——高并发下数据库忙着检查约束、处理级联更新，很容易成为瓶颈。
  • 物理外键的具体问题：一是级联更新拖垮数据库，学生表 ID 一改，成绩表所有关联学生 ID 都得跟着改，一次 UPDATE 可能触发几十万行级联更新，其他请求全部阻塞；二是每次写操作都要检查，插入成绩记录要先查学生表确认存在，删学生要先查成绩表确认无关联记录，INSERT/UPDATE/DELETE 都带额外查询，TPS 上不去；三是锁竞争加剧，改任一表关联记录，另一表相关记录也得锁住，关联表越多锁范围越大、死锁概率越高；四是分库分表不支持，跨物理库建不了外键。
  • 逻辑外键的好处是灵活：业务上不只要求用户存在，还要求用户没被冻结、没注销，改一下 customerExists 方法就行，物理外键做不到。
  • 逻辑外键写法就是插入前手动检查，例如插入订单前 if (!customerExists(order.getCustomerId())) throw new IllegalArgumentException("用户不存在"); 再保存。
  • 物理外键的业务局限：一是逻辑删除搞不定，物理外键只管数据存不存在，不管 is_deleted 是 0 还是 1，「被逻辑删除的用户不能下单」这种需求无能为力；二是分库分表搞不定，用户表在 A 库、订单表在 B 库外键根本建不起来，所以分布式系统里逻辑外键是唯一选择。
  • 什么时候可以用物理外键：数据量小、并发低、对一致性要求极高的场景，比如内部管理系统、配置中心，一天几百次写操作，那点检查开销不算事，反而省掉应用层一堆校验代码。
  • 维度对比：数据一致性上物理外键由数据库强制保证、逻辑外键依赖代码质量；性能上物理外键有开销、逻辑外键可控；灵活性上物理外键只能检查存在性、逻辑外键可承载任意业务逻辑；分布式支持上物理外键不支持、逻辑外键支持；开发成本上物理外键建表时配置、逻辑外键需要写校验代码；维护成本物理外键低、逻辑外键高。

分库分表后跨库数据一致性怎么保证？ 这是分布式事务问题：轻量方案用最终一致性，先插主表再异步同步到关联表，失败重试或补偿；重量级方案用 TCC 或 Saga 模式，每个操作有对应回滚逻辑。实际业务大部分场景最终一致性就够，强一致代价太大，关键是业务设计上容忍短暂的不一致窗口。

❌ 千万别说的话

  • “用了外键数据一定是最干净的”——分库分表和逻辑删除场景下物理外键根本用不了。
  • “逻辑外键就是不做校验”——校验责任只是从数据库挪到了应用代码，必须自己写并做定期巡检。
  • “外键慢是因为多一次 join”——瓶颈主要在级联更新、每次写入的额外检查和锁竞争。

47. 什么是游标 Cursor 分页？相比传统 LIMIT OFFSET 分页有什么优势？

🎬 面试现场

面试官（口语化）：列表页翻到后面特别慢，用 LIMIT OFFSET 和用游标分页差在哪？游标字段怎么选？

⚠️ 翻车点

以为游标分页是银弹——它没法随机跳页、没法高效统计总数、向前翻页很别扭，这些局限要主动说出来。

📝 现场作答

  • 游标分页是基于位置标记的分页方式，每次请求带上上一页最后一条数据的标识作为游标，直接定位到下一页起点；传统 LIMIT OFFSET 是从头开始数，跳过前 N 条再取 M 条。
  • 对比：SELECT * FROM user ORDER BY id LIMIT 10 OFFSET 10000;（第 1001 页，每页 10 条）对比 SELECT * FROM user WHERE id > 10000 ORDER BY id LIMIT 10;（上一页最后一条 id 是 10000）。
  • 核心优势两点：一是性能稳定，OFFSET 10000 要先扫描前 10000 条再丢弃，页码越深越慢，游标分页直接用 WHERE 跳到起点，第几页速度都差不多；二是数据一致性好，翻页过程中有新数据插入时传统分页可能重复或漏数据，游标分页基于固定位置往后取不受新增影响。
  • 深度分页根因：MySQL 处理 LIMIT offset, count 时实际上先取出 offset + count 条数据，再把前 offset 条丢掉。LIMIT 100000, 10 即使走索引也要在索引树上遍历 10 万个节点，如果查询字段不在索引里还要回表 10 万次，最后只返回 10 条；EXPLAIN 看这个语句的 rows 估算值是 100010 而不是 10。
  • 游标字段必须同时满足唯一且有序。
  • 方案一：自增主键做游标，首页 ORDER BY id LIMIT 10，下一页 WHERE id > 100 ORDER BY id LIMIT 10；实现简单，但只能按 ID 排序，业务要按创建时间倒序就不行。
  • 方案二：时间戳 + ID 复合游标，适用于消息列表、动态 Feed 流。首页 ORDER BY create_time DESC, id DESC LIMIT 10，下一页 WHERE (create_time < '2024-01-01 12:00:00') OR (create_time = '2024-01-01 12:00:00' AND id < 100) ORDER BY create_time DESC, id DESC LIMIT 10；带上 ID 是因为同一秒可能有多条数据，只用 create_time 会漏数据。要走索引需建联合索引 CREATE INDEX idx_create_time_id ON post(create_time, id);。
  • 方案三：编码游标，把 create_time 和 id 用 Base64 编码成字符串传给前端，前端原样传回；用 Base64.decode(cursor).split(",") 解码出时间和 ID，对前端更友好也避免暴露内部字段名。
  • 局限：只能上一页下一页没法直接跳到第 100 页，后台管理系统的跳页场景还得用传统分页；排序字段不唯一且没有合适辅助字段时很难构造有效游标；向前翻页要反向排序实现麻烦；天然不知道总共有多少页，需要额外 COUNT 查询。
  • 业界实践：推特（x）、Facebook、Instagram 的 Feed 流全是游标分页，API 一般返回 {"data": [...], "paging": {"next_cursor": "abc123", "has_more": true}}，前端下拉加载把 next_cursor 传回来即可，has_more 为 false 说明到底。Elasticsearch 的 search_after 也是游标分页思路。

💡 主动加分的追问准备

面试官追问 你的答案
游标分页能不能实现向前翻页？ 可以，但要改变排序方向和比较符号：往后翻是 WHERE id > cursor ORDER BY id ASC，往前翻就变成 WHERE id < cursor ORDER BY id DESC，取出来后在应用层反转一下顺序。实现比较别扭，如果确实需要双向翻页，可以用两个游标 prev_cursor 和 next_cursor，分别记录当前页第一条和最后一条的位置。
如果游标字段被删除了会怎样？ 用已删除记录的 ID 当游标，WHERE id > 删除的ID 条件仍能正常工作，只是从下一个存在的 ID 开始取，不报错也不漏数据。但时间戳 + ID 复合游标且 ID 被删时，WHERE 里的 id < last_id 部分可能命中不到预期数据，这种场景建议游标里只用时间戳、放弃 ID 的精确定位。
游标分页和 Elasticsearch 的 scroll API 是一回事吗？ 不是。scroll API 是 ES 早期的深度分页方案，会创建快照保持数据一致性，但占用大量资源，官方已不推荐用于实时场景。ES 7.0 之后推荐 search_after，这才是真正的游标分页思路，传入上一页最后一条的 sort 值定位下一页，不占用额外资源，适合实时翻页；scroll 现在主要用于批量导出全量数据。

❌ 千万别说的话

  • “游标分页可以完全替代 LIMIT OFFSET”——跳页场景和总数统计还得靠传统分页。
  • “游标字段随便选一个有序字段就行”——必须唯一且有序，否则会漏数据或重复。
  • “OFFSET 大只是慢一点”——页码越深越慢，而且还会回表放大开销。

面试前 10 分钟速查

索引

  • B+ 树：非叶子节点只存键、叶子节点串成链表，范围查询友好；红黑树树高更大、磁盘 I/O 次数更多
  • 聚簇索引 = 数据本身，叶子节点存整行；二级索引叶子存主键值，回表才有数据
  • 覆盖索引：查询字段全在二级索引里，不回表
  • 索引下推（ICP）：把条件下推到存储引擎层过滤，减少回表
  • 最左前缀：联合索引按列顺序命中，范围列之后的列无法再用于等值匹配
  • EXPLAIN 看 type（ALL 全表扫、ref/range 走索引）、key（实际索引，NULL 表示没用上）、rows（预估扫描行数）
  • 索引失效常见：类型隐式转换、函数包裹列、LIKE '%x'、联合索引不满足最左前缀

事务与锁

  • 四级隔离：RU < RC < RR < SERIALIZABLE；MySQL 默认 RR
  • RR 靠 MVCC + 间隙锁 解决幻读；RC 无间隙锁
  • ReadView 四个字段：trx_ids、up_limit_id、low_limit_id、creator_trx_id
  • 锁：行锁（记录锁、间隙锁、临键锁）、表级锁（MDL、意向锁、插入意向锁）、Auto-Inc Lock
  • 崩溃恢复：innodb_flush_log_at_trx_commit=1 最安全（提交即刷盘）

SQL 与调优

  • 执行顺序：FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT
  • Buffer Pool 命中率公式：1 - (Innodb_buffer_pool_reads / Innodb_buffer_pool_read_requests)，生产应接近 100%
  • 慢查询：slow_query_log + long_query_time；mysqldumpslow / pt-query-digest 聚合
  • 禁止 SELECT *；分页深翻用游标分页（WHERE id > last_id）而非大 OFFSET

表结构

  • 金额用 DECIMAL，绝不用 FLOAT/DOUBLE
  • VARCHAR 变长、CHAR 定长；长度声明影响实际存储与排序行为
  • DATETIME 存 1000~9999 年且不受时区影响，TIMESTAMP 存 UTC 且受时区与 2038 问题影响
  • DELETE 可回滚有日志、TRUNCATE 不可回滚重置自增、DROP 删表结构
  • 逻辑删除：加 deleted 标记，物理删除：真删行
  • 逻辑外键靠应用保证，物理外键有性能与并发代价

高可用

  • 主从：binlog → relay log → SQL 线程重放；Seconds_Behind_Master 监控延迟
  • 延迟治理：并行复制、pt-heartbeat、避免大事务
  • 防单点：MGR 多主 / ProxySQL 中间件 / 云托管
  • 不停服迁移：双写 → 数据校验 → 切读 → 停旧写 → 切写

分库分表

  • 垂直拆分治大表，水平拆分治单表容量
  • 分片键必须选查询最高频的维度；分片后失去全局唯一性与跨片 JOIN 能力
  • 扩容用一致性哈希或预分片，避免二次迁移
  • 跨片查询兜底：广播表、绑定表、异步汇总
