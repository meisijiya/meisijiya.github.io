1. 如何使用 JMeter 测试文件上传接口？

🎬 面试现场

面试官（口语化）：文件上传接口用 JMeter 怎么测？

⚠️ 翻车点

最容易翻车的是漏掉 “Use multipart/form-data for POST” 这个复选框——不勾它，文件根本传不上去，报错时很难第一时间想到是这个开关。第二个坑是只做单次上传就收工：文件路径、文件名在项目里是会变的，不做参数化脚本就没有复用性。第三个坑是不加断言：响应返回了不等于上传成功，不加断言就无从判断。第三个常见疏漏是没加监听器，跑完根本看不到响应结果。

📝 现场作答

  • 可以使用 JMeter 中的 HTTP Request 采样器来测试文件上传接口，具体步骤如下：
    1. 启动 JMeter，并创建一个新的 Test Plan。
    2. 在 Test Plan 下添加一个 Thread Group 以模拟用户行为。
    3. 在 Thread Group 下添加一个 HTTP Request 采样器。
    4. 在 HTTP Request 采样器中，设置所需的上传接口的 URL 和请求方法（通常是 POST 请求）。
    5. 在 HTTP Request 采样器的 “Body Data” 部分，选择 “Use multipart/form-data for POST” 复选框。
    6. 点击 “Body Data” 部分的 “Add” 按钮，添加一个文件类型的元件，并选择要上传的文件。
    7. 为了查看响应结果，可以添加一个监听器，例如 “View Results Tree”。
    8. 点击运行按钮，开始测试文件上传接口。
  • 扩展的六点：
    1. 参数化测试：实际项目中，文件的路径、文件名等可能会有所不同，可以在 JMeter 中使用 CSV Data Set Config 来进行参数化测试，从而提高脚本的复用性和灵活性。
    2. 压力测试：除了单次上传测试，还可以设置多个线程以及不同的调度策略，对文件上传接口进行压力测试，观察在高并发情况下接口的性能表现。
    3. 断言：为了确保文件上传接口的正确性，可以添加断言组件；例如使用响应断言来验证接口返回的状态码和响应内容，确保文件上传操作成功。
    4. 后处理器：如果接口返回的数据需要进一步处理和验证，可以使用后处理器，例如 JSON Extractor 或 Regular Expression Extractor 提取返回的数据，并进行相应的验证。
    5. 命令行运行：JMeter 测试脚本可以通过命令行运行，这对于持续集成和自动化测试非常有用；可以将 JMeter 脚本集成到 Jenkins 等 CI/CD 平台中，以实现自动化的接口测试。
    6. 插件：JMeter 社区有许多有用的插件，可以扩展 JMeter 的功能，比如额外的数据处理组件、报告生成工具等，这些插件可以增强你的测试能力。

2. 对于 POST 请求需要传递 JSON 格式数据，如何在 JMeter 中实现？

🎬 面试现场

面试官（口语化）：用 JMeter 发 POST 带 JSON，具体怎么配？

⚠️ 翻车点

最容易翻车的是只贴了 JSON 却不设 Content-Type——服务端按表单解析，字段全丢，现象是”参数没传过去”。第二个坑是找不到”发送参数处”这个勾选项：JSON 是在 HTTP 请求取样器里往下滚到”发送参数处”、勾选”HTTP 请求主体数据”之后才有的入口，不是随便往文本框粘。第三个坑是不做断言：请求发出去了不代表业务成功，要用响应断言校验返回数据。

📝 现场作答

  • 在 JMeter 中发送需要传递 JSON 格式数据的 POST 请求，可以按照以下步骤进行：
    1. **添加”线程组”**：打开 JMeter，右键点击”测试计划”，选择”添加” -> “线程（用户）” -> “线程组”。
    2. **添加”HTTP 请求”**：在线程组上右键，选择”添加” -> “取样器” -> “HTTP 请求”。
    3. 配置 HTTP 请求：在”HTTP 请求”取样器中，设置好服务器名称或 IP、端口号（如果有的话）、HTTP 请求方法选择”POST”、并填写具体的路径。
    4. 添加 JSON 数据：在同一个”HTTP 请求”取样器中，往下滚动到”发送参数处“，勾选”HTTP 请求主体数据“。然后，把要发送的 JSON 数据粘贴到文本框内。
    5. 设置请求头：还需要告诉服务器你发送的是 JSON 数据。在”HTTP 请求”取样器上右键，选择”添加” -> “配置元件” -> “HTTP Header 管理器“。在”HTTP Header 管理器”中，添加一个新条目，名称为 “Content-Type“，值为 “application/json“。
  • 做完这些配置后，就能够成功在 JMeter 中使用 POST 请求发送 JSON 数据了。扩展的四点：
    1. 校验响应：为了确保 POST 请求的结果是符合预期的，一般需要添加一个”断言”。可以在”HTTP 请求”取样器上右键，选择”添加” -> “断言” -> “响应断言“，来检查响应数据是否包含或等于某些预期的值。
    2. 使用变量：实际测试中，如果发送的数据中有一些动态值或者从之前的请求中获取的值，可以使用 JMeter 的变量功能；可以用 JMeter 的内置函数，比如正则表达式提取器或者 JSON 提取器，来提取前一请求的响应中的值，并在后续请求的数据中使用该变量。
    3. 结果查看器：为了查看请求和响应的细节，可以在取样器上右键，选择”添加” -> “监听器” -> “查看结果树“；这个工具可以帮助调试并详细查看 HTTP 请求和响应。
    4. 参数化与数据驱动测试：如果需要多次发送不同的数据，可以使用 CSV 数据文件来参数化；添加一个 CSV 数据文件集配置元件，然后在 HTTP 请求中的数据部分使用变量来引用 CSV 文件中的数据。

3. 如何在 JMeter 中测试 GET 请求接口？

🎬 面试现场

面试官（口语化）：拿 JMeter 测一个 GET 接口，整个流程你走一遍给我看看。

⚠️ 翻车点

最容易漏掉的是监听器和参数化：只把请求发出去、不挂 “View Results Tree” 看结果，等于没测；只测一组固定路径，也不叫覆盖。另外线程组的三个参数（线程数、Ramp-Up Period 秒、循环次数）不是可选项，不填就等于压测参数没定义。

📝 现场作答

  • 在 JMeter 中测试 GET 请求接口的大致步骤如下：
    1）打开 JMeter，新建一个测试计划（Test Plan）；
    2）在测试计划下添加线程组（Thread Group），定义用户数、循环次数等参数；
    3）在线程组下添加 HTTP 请求（HTTP Request）；
    4）在 HTTP 请求配置中设置 GET 请求的 URL、协议、服务器名称或 IP 地址、端口号等参数；
    5）执行测试，并查看结果。
  • 具体操作：
    1）打开 JMeter，点击左上角的”文件(File)”菜单，选择”新建(New)”来创建一个新的测试计划；
    2）右键点击测试计划，选择”添加(Add)” -> “Threads(Users)” -> “Thread Group”；
    3）设置线程属性，比如线程数(Number of Threads)、Ramp-Up Period (秒)和循环次数(Loop Count)；
    4）右键点击新建的线程组，选择”添加(Add)” -> “Sampler” -> “HTTP Request”；
    5）在 HTTP 请求的配置窗口中，设置协议（通常为 http 或 https），服务器名称或 IP 地址，端口号（如存在），路径（即 GET 请求的具体路径）；
    6）为了查看结果，可以为线程组添加一个监听器，比如右键点击线程组，选择”添加(Add)” -> “Listener” -> “View Results Tree”；
    7）保存并运行测试计划，查看结果树中的响应数据。
  • 实际项目中常见的增强手段：
    1）用户定义变量：可以在测试计划中添加”Config Element” -> “User Defined Variables”，这样可以在 HTTP 请求中的路径、参数等位置使用这些变量；
    2）参数化与数据驱动：需要测试多组数据时，可以使用 JMeter 中的 CSV Data Set Config 配置元素，它可以从外部 CSV 文件中读取参数，提高测试灵活性；
    3）断言：JMeter 提供不同类型的断言（如响应断言、JSON 断言等）来确保接口返回的响应符合预期，可以添加一个响应断言（Response Assertion）来检查响应的数据是否包含特定的文本或 JSON 路径等；
    4）聚合报告（Aggregate Report）：为了更专业地查看测试结果，可以使用”Aggregate Report”来查看线程组的累计结果，这对分析性能测试的数据非常有用；
    5）分布式测试：如果需要大规模的性能测试，JMeter 支持分布式测试，可以使用主从模式分布式运行多个 JMeter 实例来模拟大量的并发用户；
    6）插件支持：JMeter 有丰富的插件支持，可以通过安装不同的插件来扩展其功能，比如有些插件可以生成图表、支持更复杂的协议或提供附加的监听器类型；
    7）命令行执行：除了在 GUI 界面上运行测试计划，JMeter 还支持命令行模式（非 GUI 模式），这对于 CI/CD 流水线中的自动化测试非常有帮助。

4. 如何在 JMeter 中测试 JSON 数据格式的接口？

🎬 面试现场

面试官（口语化）：要测一个 JSON 接口，JMeter 里从建计划到校验结果，你怎么配？

⚠️ 翻车点

最容易错的两步：一是忘了设 Content-Type 为 application/json，服务端可能按表单解析而报参数缺失；二是没配 HTTP Header Manager 就直接往 Body Data 里填 JSON，请求头里没有正确的类型声明，接口往往返回 415 或者解析成空对象。另外 POST 的 JSON 要写在 “Body Data” 里，选错选项卡同样白测。

📝 现场作答

  • 在 JMeter 中测试 JSON 数据格式的接口可以通过以下步骤完成：
    1）创建一个测试计划；
    2）添加一个线程组；
    3）添加 HTTP 请求采样器；
    4）配置 HTTP 请求采样器，设置 URL、请求方法（如 GET 或 POST）以及请求体中的 JSON 数据；
    5）配置 HTTP Header Manager，设定 Content-Type 为 application/json；
    6）添加响应断言（如 JSON 断言）来验证响应的内容；
    7）运行测试并查看结果。
  • 具体配置细节：
    1）打开 JMeter，默认已经创建了一个新的测试计划，如果没有可以手动创建一个新的测试计划；
    2）右键点击测试计划，选择 “Add” -> “Threads (Users)” -> “Thread Group”；
    3）右键点击线程组，选择 “Add” -> “Sampler” -> “HTTP Request”，在采样器中配置相应的 URL 和 HTTP 方法，如 GET 或者 POST；如果是 POST 请求，需要在 “Body Data” 中输入请求的 JSON 数据，例如：

4）在 HTTP 请求中发送 JSON 数据时需要设定 Content-Type 为 application/json：右键点击线程组，选择 “Add” -> “Config Element” -> “HTTP Header Manager”，添加新的 HTTP Header，名称为 Content-Type，值为 application/json；
5）为了确保接口返回了正确的 JSON，可以添加响应断言：右键点击 HTTP 请求采样器，选择 “Add” -> “Assertions” -> “JSON Assertion”，在 JSON 断言中配置想验证的 JSON 路径和值；
6）点击工具栏上的绿色箭头按钮运行测试；
7）右键点击线程组，选择 “Add” -> “Listener” -> “View Results Tree”，添加查看结果树以便更直观地查看和分析测试结果。

  • 这些步骤可以帮助你在 JMeter 中高效地测试接口的 JSON 数据格式。还可以考虑：JMeter 插件中的 JSON Path PostProcessor 可以帮助更加细粒度地解析和验证 JSON 响应；使用 CSV Data Set Config 进行参数化测试，用不同的 JSON 输入数据测试 API 的稳定性和处理能力；JMeter 支持分布式测试，允许将测试负载分布到多个机器上，以提高测试效能；还可以将 JMeter 测试脚本整合到 CI/CD 流水线中，如 Jenkins 等，进行持续集成和自动化测试。

6. 如何在 JMeter 中进行参数化？参数化类型有哪些？

🎬 面试现场

⚠️ 翻车点

    1）CSV Data Set Config：这是最常用的方式，通过将参数存储在一个 CSV 文件中，然后在 JMeter 中调用；
    2）User Defined Variables：定义全局或者局部的参数变量；
    3）Configuration Elements：例如 “HTTP Request Defaults”，可以设置一些默认参数；

  • 如何验证参数化是否成功：首先，可以在 CSV Data Set Config 中设置一个迭代数，看是否按预期读取参数；其次，可通过 Debug Sampler 来检查变量是否正确读取和替换。
  • 复杂场景下维护的技巧：如果参数文件较大，可以分模块管理，例如不同的 CSV 文件存储不同类型的参数；利用配置管理工具（如 Git）来管理参数文件的版本。

10. 如果下一个接口需要使用上一个接口返回的加密数据，如何在 JMeter 中提取？

🎬 面试现场

面试官（口语化）：第二个接口要用第一个接口返回的那串加密数据，在 JMeter 里怎么把它取出来传下去？

⚠️ 翻车点

坑点在于只提取了值、没留下名，或者名取对了却在下一个接口里引用错。JMeter 的提取器不是”自动传参”的，它只是把匹配到的内容存进一个变量，下一个请求必须显式用 ${变量名} 去引用。另外一个常见错误是照抄正则时把转义写丢，导致正则匹配不到却以为”提取器失效”。

📝 现场作答

  • 在 JMeter 中，如果需要使用上一个接口返回的加密数据作为下一个接口的输入参数，可以通过”正则表达式提取器”来实现，步骤如下：
    1）首先，在上一个接口的 HTTP 请求后添加一个”正则表达式提取器”（Regular Expression Extractor）；
    2）在”正则表达式提取器”中配置提取规则，包括”引用名”（Reference Name）、”正则表达式”（Regular Expression）、”模板”（Template）、”匹配数字”（Match No.）和”默认值”（Default Value）；
    3）配置”引用名”，它是变量名，通过这个变量名我们可以在后续的请求中引用提取到的数据；
    4）在下一个接口的 HTTP 请求中，通过使用 ${引用名} 来调用提取到的数据。
  • 例如，上一个接口返回的数据是：{“encryptedData”: “abc123xyz”}，需要提取 encryptedData 的值，可以这样配置：引用名 encryptedData；正则表达式 "encryptedData":\s*"([^"]+)"；模板 Template；匹配数字 1；默认值 Default Value。然后在下一个 HTTP 请求中使用 ${encryptedData} 引用提取到的数据。
  • 除了正则表达式提取器，JMeter 还支持其他数据提取器：
    1）JSON 提取器（JSON Extractor）：如果接口返回的是标准的 JSON 格式数据，使用 JSON 提取器会更加方便和直接，可以配置 JSON 路径 $..encryptedData 来提取加密数据；
    2）XPath 提取器（XPath Extractor）：如果接口返回的是 XML 数据，可以使用 XPath 表达式来提取需要的部分，例如 XPath 表达式 //encryptedData/text() 可以提取到 abc123xyz 中的内容。
  • 有些时候接口返回的数据比较复杂或者嵌套很多，可以结合使用多个提取器进行数据的逐层提取。
  • 为了保证测试的稳定性和可维护性，建议在编写提取规则时做好注释和解释，方便日后的维护和排查问题；同时可以利用 JMeter 的 Debug Sampler 和 View Results Tree 等组件来调试和验证提取的正确性。

12. 如果接口的请求参数需要加密处理，你们使用的是什么加密方式？你是如何处理加密的？

🎬 面试现场

面试官（口语化）：接口参数要加密，你们用的什么算法，加密这块怎么处理的？

⚠️ 翻车点

最容易被追问倒的是密钥怎么安全地送到服务端：对称加密速度快但密钥必须保密，常见做法是用 RSA 加密 AES 密钥，再把加密后的密钥和密文一起发。另一个坑是把密钥硬编码在代码里或者把摘要、密文混在一起不区分——那样既没有完整性保护，也埋了安全隐患。

📝 现场作答

  • 在处理接口请求参数的加密时，通常使用对称加密和非对称加密两种主要方式。对称加密主要包括 AES（高级加密标准），非对称加密主要包括 RSA（公钥加密），具体选择哪种加密方式要根据实际需求。
  • 选择 AES 进行数据加密，是因为 AES 相对而言速度较快，且安全性也很高。处理加密的具体步骤如下：
    1）生成密钥：首先生成一个随机的 AES 密钥，这个密钥将用于加密和解密数据；
    2）加密数据：使用生成的 AES 密钥对请求参数进行加密，这里会选择一种适合的填充方式（如 PKCS7Padding），以确保数据块大小符合加密算法的要求；
    3）传输密钥：由于使用了对称加密，密钥的保护至关重要，在传输 AES 密钥时使用 RSA 加密这个 AES 密钥，并将加密后的密钥与加密数据一起发送；
    4）解密数据：在服务器端，首先使用私钥解密 AES 密钥，然后使用这个 AES 密钥解密请求参数，得到原始的请求数据。
  • AES（高级加密标准）：AES 是一种对称加密算法，意味着加密和解密使用的是同一个密钥。AES 支持 128 位、192 位和 256 位密钥。它的优点有：
    1）高效性：由于 AES 使用对称密钥算法，对数据块进行逐块加密，因此在处理大量数据时速度很快；
    2）高安全性：AES 通过多轮的置换和代换操作，能提供非常高的安全性，至今为止没有实用的攻击破解 AES。
  • RSA（公钥加密算法）：RSA 是一种非对称加密算法，使用一对密钥，即公钥和私钥。公钥用于加密，私钥用于解密；公钥可以公开给任何人，而私钥必须保密。它的优点有：
    1）公钥基础设施（PKI）：由于公钥可以公开，可以在不安全的网络上方便地分发和验证身份；
    2）数字签名：RSA 不仅用于加密数据，还可以用于生成和验证数字签名，确保数据的完整性和来源的真实性。
  • 实际应用中还需要考虑以下几点：
    1）数据的完整性：除了加密外，通常会对请求参数进行哈希运算（如使用 SHA-256），生成数据摘要，并将这个摘要与加密数据一起发送，来确保数据未被篡改；
    2）性能优化：由于加密和解密操作会增加计算资源的消耗，需要在性能和安全性之间找到一个平衡点，比如对于敏感信息加密，而非所有数据都加密；
    3）安全通信：尽管对请求参数做了加密，整个通信过程也最好使用 HTTPS 协议来增加一层安全保障，HTTPS 能够加密传输层的数据，进一步避免数据在传输过程中被窃取或篡改。

    1）了解加密方法：首先了解密文的加密算法和密钥管理方法，这是关键的一步，因为只有明白数据是如何加密和解密的，才能进行有效的测试；

16. 如何在 JMeter 中进行断言？

🎬 面试现场

面试官（口语化）：接口返回的结果怎么判断对不对，JMeter 里的断言是怎么加的？

⚠️ 翻车点

两个常见误区：一是只加一种断言，JSON 接口用响应断言去匹配关键字，XML 接口不用 XPath 断言，定位能力很弱；二是忽略断言之间的关系——同一个请求节点下添加多个断言时，它们之间是 AND 关系，所有断言都必须通过，该请求才会被认为是成功的，漏配一个就可能让失败请求被放过。

📝 现场作答

  • 在 JMeter 中进行断言的步骤如下：
    1）打开 JMeter 并加载你的测试计划；
    2）在测试计划中找到需要断言的请求节点；
    3）右键点击该请求节点，选择”添加（Add）” -> “断言（Assertions）”；
    4）在出现的菜单中选择你需要的断言类型，例如”响应断言（Response Assertion）”、”响应时间断言（Duration Assertion）”等；
    5）配置断言参数，比如匹配内容、模式、响应时间等。
  • 常见断言类型：
    1）响应断言：这是最常用的断言类型之一，主要用来验证响应的内容是否包含特定的字符串、正则表达式或响应码，例如检查接口返回的 JSON 格式数据中是否包含某个关键字；
    2）JSON 断言：如果接口返回的是 JSON 数据，可以使用 JSON 断言来验证响应数据中的特定字段和值，从而精确地校验返回的数据结构和内容；
    3）XPath 断言：用来验证 XML 格式的响应数据，使用 XPath 表达式来定位和检查文本内容，对于处理 web 服务返回的 XML 数据尤其有用；
    4）响应时间断言：用于确保服务器在规定的时间内返回响应，适用于那些对性能有较高要求的测试场景；
    5）自定义断言（BeanShell Assertion 或者 JSR223 Assertion）：对于复杂的验证逻辑，可以使用自定义断言，通过脚本（如 Groovy、BeanShell、JavaScript 等）来进行复杂的校验；
    6）组合断言：在实际工作中可能需要同时验证多个方面，可以在同一个请求节点下添加多个断言，它们之间的关系是 AND，也就是说所有断言都必须通过，该请求才会被认为是成功的。

18. 如何在 JMeter 中处理 HTTPS 证书？

🎬 面试现场

📝 现场作答

  • 在 JMeter 中处理 HTTPS 证书实际上是为了使测试能够顺利进行并得到准确的数据，JMeter 提供了一个内置的证书管理机制，可以轻松地配置和管理 HTTPS 证书，关键步骤如下：
    1）生成 JMeter CA 证书：启动 JMeter 的 HTTP(S) 测试脚本记录器，JMeter 会自动生成一个用于捕获 HTTPS 流量的 CA 证书；
    2）将 CA 证书导入浏览器：将生成的证书（通常位于 $JMETER_HOME/bin 目录下，文件名为 ApacheJMeterTemporaryRootCA.crt）导入到你用来执行测试的浏览器的受信任的根证书颁发机构存储区；
    3）配置 JMeter HTTP 请求：对于 HTTPS 请求，确保你在测试计划的 HTTP 请求采样器中正确地设置了”协议”为 https，并准确设置目标服务器和端口。
  • 以上步骤能确保 JMeter 能顺利处理 HTTPS 流量。
  • 测试环境里用自签名证书很常见：为了使用自签名证书，可以在 JMeter 中配置系统属性 javax.net.ssl.trustStore 和 javax.net.ssl.trustStorePassword 指向自签名证书的可信存储。
  • 证书别名与信任链：在复杂的场景中，可能需要处理多个证书链，使用不同别名和信任链管理证书显得尤为重要；熟悉 keytool 命令行工具，可以帮助你批量导入证书和管理密钥库。
  • TLS Version & Protocols：JMeter 允许你指定使用的 TLS 版本和不同的加密算法，如果对安全性有更高的要求或需求，可以调节 JMeter 的 https.default.protocol 和 https.socket.protocols 参数，确保使用合适的协议。

26. 如何在 Requests 中处理 HTTPS 证书？

面试官（口语化）：用 Requests 发 HTTPS 请求的时候，证书这块你打算怎么处理？自签名证书的项目能不能直接跑通？

⚠️ 翻车点

最容易踩的是把 verify=False 当成”万能解法”直接抛上去。它确实能让自签名证书的请求跑通，但也跳过了证书验证，中间人攻击的风险就全摊开了——Requests 默认是要验证服务器提供的 HTTPS 证书的，为的就是防止中间人攻击和确保服务器身份的原始性。所以 verify=False 只能用在可信的开发或测试环境，不要拿到生产环境用。第二个坑是只会 verify=False，不会用 verify 指定 CA 证书文件，也不会用 cert 提供客户端证书。

📝 现场作答

  • 在使用 Requests 库进行网络请求时，处理 HTTPS 证书主要有以下几种常见的方法：
    1. 忽略证书验证：在某些测试环境中，可能会有自签名证书或无效证书，可以通过设置参数 verify=False 来忽略证书验证。
    2. 指定证书文件：如果有一个 CA 证书文件，可以通过 verify 参数来指定该证书文件，这确保了请求只会信任该证书或该证书链上的证书。
    3. 提供客户端证书：有时候服务器可能需要客户端提供证书，这时可以使用 cert 参数来提供客户端证书文件，它可以是一个包含两个文件路径的元组（证书文件和私钥文件），或者一个配置了这两个文件的单个文件。

    • 证书验证：为了确保与服务器之间的通信是安全的，请求库默认会验证服务器提供的 HTTPS 证书，这是为了防止中间人攻击和确保服务器身份的原始性。
    • 自签名证书：在开发或测试环境中，使用自签名证书还是比较普遍的。虽然自签名证书并不安全（因为它们没有经过公认的 CA 验证），但是在内部网络中进行测试时通常是可以接受的。
    • 证书链：实际应用中，证书通常不只是一个单一的文件，而是一系列证书组成链条。根证书（CA）信任中间证书，中间证书信任最终的服务器证书，可以使用 verify 参数提供一个包含完整证书链的文件。
    • SSL 上下文：对于一些高级应用，可能需要对 SSL 上下文进行更多的配置。虽然 Requests 库没有直接暴露这个功能，但可以通过创建一个 requests.Session 然后设置自定义的 SSLContext 来实现更多自定义控制，例如需要启用和禁用特定的 TLS 版本或密码套件时，就用这个方式。
    • 安全考量：虽然可以通过设置 verify=False 来绕过证书验证，但这会带来明显的安全风险，只应该在可信的开发或测试环境中使用，而不要在生产环境中使用。

⚠️ 翻车点

最容易答偏的是只说”把 Token 放到 header 里”就完事，漏掉签名的生成过程。签名不是随便拼一个字符串，一般是根据特定的算法（如 HMAC、MD5）对请求数据及密钥进行哈希；Token 也通常是从授权服务器通过用户名密码认证获取，获取后可能需要缓存。另一个坑是签名和 Token 混为一谈——它们是两件事，一个是自己算出来的，一个是服务端发的。

    1. 首先导入 Requests 库和其他所需库（如 hashlib、hmac）。

    • 哈希和加密算法：除了 HMAC-SHA256，还需要熟悉其他常见的签名算法，如 MD5、RSA 等。在实际项目中选择合适的算法非常重要，尤其是在对安全要求较高的项目中。
    • Token 的管理：Token 的有效期和刷新机制也是需要考虑的。如果 Token 有效期较短，需要设计合理的刷新机制，确保在 Token 失效时及时获取新的 Token。
    • 安全性：在生成签名和 Token 的过程中，需要严格保护密钥和秘密信息。此外，在传输过程中使用 HTTPS 加密通信，防止中间人攻击。
    • 错误处理：在实际应用中，接口可能会遇到各种错误情况，比如网络问题、权限不足等，需要设计合理的错误处理机制，确保系统的可靠性和健壮性。

JMeter 请求配置

  • POST 参数位置：POST 参数写在 HTTP 请求采样器的 “Body Data” 选项卡，键值对格式，例如 username=admin&password=123456；写成 Parameters 里拼在 URL 上虽能通，但与真实调用形态不一致。
  • POST 发 JSON：HTTP 请求采样器里往下滚到”发送参数处”，勾选”HTTP 请求主体数据”后粘贴 JSON；再用 “HTTP Header Manager” 加一条 Content-Type 值为 application/json，否则服务端按表单解析、字段全丢。
  • JSON 请求体与请求头分离：请求体中的 JSON 写在 “Body Data” 里（不是 Parameters），Content-Type 必须通过 “Config Element” -> “HTTP Header Manager” 显式设为 application/json，漏配常表现为接口返回 415 或解析成空对象。
  • 文件上传接口：在 “Body Data” 部分勾选 “Use multipart/form-data for POST”，再点 “Add” 添加文件类型的元件选择要上传的文件；路径与文件名会变，用 CSV Data Set Config 参数化，并加响应断言校验状态码与响应内容、挂 “View Results Tree” 看结果。
  • GET 接口测试：测试计划下加 Thread Group，设定线程数、Ramp-Up Period (秒)、循环次数 (Loop Count)，再加 HTTP Request 配置协议、服务器名称或 IP、端口号与路径；路径里的固定参数放到 “Config Element” -> “User Defined Variables” 里用 ${VAR_NAME} 引用。
  • SOAP 请求：用专门的 “SOAP/XML-RPC 请求” 采样器而不是普通 HTTP Request，XML 粘在它的数据输入框；再用 “HTTP Header Manager” 配 Content-Type: text/xml;charset=UTF-8。
  • 参数化的四类：CSV Data Set Config 面向大量数据（文件路径、变量名称、分隔符），User Defined Variables 面向全局常量（定义后作用域内不变、不能运行时动态改），Configuration Elements（如 “HTTP Request Defaults”）面向通用请求参数，函数和变量用于动态生成或引用（如 __Random()）。

JMeter 数据处理

  • JMeter 没有加密元件：加密靠 “JSR223 PreProcessor”（语言选 Groovy）或 “JSR223 Sampler” 写脚本，脚本里必须 vars.put 把密文回写成 JMeter 变量，再在 HTTP Request 里用 ${encodedParameter} 引用，否则请求带出去的仍是原始参数。
  • Base64 与 AES 脚本写法：Base64 用 import org.apache.commons.codec.binary.Base64 调 encodeBase64String；AES 用 javax.crypto.Cipher 与 javax.crypto.spec.SecretKeySpec，密钥需 16 字节。
  • 密文响应的断言方式：不能拿明文关键字去匹配密文，先用 “JSR223 PostProcessor” 或 “BeanShell PostProcessor” 调 prev.getResponseDataAsString 解密并存进变量（如 ${decryptedResponse}），再用 “Response Assertion” 把 “Apply to” 选成 “JMeter Variable” 并填该变量名。
  • 提取上一步的加密数据：用”正则表达式提取器”配置引用名、正则表达式、模板 $1$、匹配数字 1、默认值 NOT_FOUND，下一个请求用 ${引用名} 显式引用；标准 JSON 用 JSON 提取器配 JSON 路径 $..encryptedData，XML 用 XPath 提取器配 //encryptedData/text()。
  • 跨线程组传参：普通 JMeter 变量作用域仅限当前线程组，要动态跨组用全局属性对象 props——一组里 props.put(“variableName”, “value”)，另一组里 props.get(“variableName”)；用户定义的变量虽全组可访问但运行中不可动态变化，CSV Data Set Config 适合大量参数不适合单参数。
  • 加密方案选型：用 AES 加密业务数据（AES 支持 128 位、192 位和 256 位密钥），用 RSA 加密 AES 密钥后与密文一起发送，密文接口还要用 SHA-256 摘要校验完整性、密钥不得明文存放在代码或日志中。
  • 密文接口的测试维度：解密后与期望数据比对、特殊字符与长字符串边界、密文泄露与重放风险、AES256 通常比 AES128 更安全、加密模式 GCM 自带完整性检验、性能上加解密开销。

JMeter 校验与通知

  • Cookie 管理：HTTP 样本下右键 Add -> Config Element -> HTTP Cookie Manager，点 Add 填名称、值、域、路径；它默认自动处理服务器下发的 Set-Cookie 并带到后续请求，可用 Clear Cookies each iteration 选项在每次迭代时清掉，Policy 默认是标准浏览器行为。
  • Header 的两种加法：多个请求共享同一 Header 用 “HTTP Header Manager”（默认 Header 只在请求未显式指定时才生效），单个请求的定制需求直接写在 HTTP 请求的”头部信息”部分；动态值可用 User Defined Variables、CSV Data Set Config 或 BeanShell PreProcessor、JSR223 PreProcessor 动态设置。
  • 断言类型：响应断言（字符串、正则、响应码）、JSON 断言（按 JSON 路径和值精确校验）、XPath 断言（XML 响应）、响应时间断言（限定响应时长）、自定义断言（BeanShell Assertion 或 JSR223 Assertion，写 Groovy、BeanShell、JavaScript）。
  • 多断言是 AND 关系：同一请求节点下添加的多个断言必须全部通过，该请求才算成功；只配一种断言会让定位能力偏弱。
  • 自动发结果邮件：用内置的 SMTP Sampler，填 SMTP 服务器地址、用户名、密码、发件人与收件人，并在目标监听器上设条件（如测试执行完毕时发送）；能否发出取决于网络访问权限与服务器配置，Gmail 的 SMTP 服务需要开启”双因素认证”以及”低安全应用访问权限”。
  • 报告与 CI/CD：用”聚合报告”或”图形结果”收集统计信息，配合 “Beanshell Sampler” 或 “JSR223 Sampler” 生成报告内容；也可把 JMeter 集成到 Jenkins，用 Jenkins 自带的邮件插件在每次代码更新后自动触发并反馈结果。

JMeter 安全与代理

  • HTTPS 证书三步：启动 HTTP(S) 测试脚本记录器生成 JMeter CA 证书，把 $JMETER_HOME/bin 目录下的 ApacheJMeterTemporaryRootCA.crt 导入浏览器的受信任的根证书颁发机构存储区，再把 HTTP 请求采样器的协议设为 https 并配准服务器与端口。
  • 自签名证书：配置系统属性 javax.net.ssl.trustStore 与 javax.net.ssl.trustStorePassword 指向自签名证书的可信存储；JMeter 内置机制并不会自动信任任意 HTTPS 站点。
  • 证书链与 TLS 版本：多证书链场景用不同别名管理并用 keytool 批量导入、管理密钥库；通过 https.default.protocol 与 https.socket.protocols 指定 TLS 版本与加密算法；证书过期会影响测试结果，需用系统参数或在执行前检查并更新。
  • 代理录制流程：选 Fiddler、Charles Proxy 或 Burp Suite，配置监听端口（Fiddler 通常监听 8888，改端口前确认未被占用），把浏览器/移动端 WiFi/代码请求指向该端口（Fiddler 通常监听 8888；Python 里用 requests 库的 proxies 参数），录完导出（Charles Proxy 可导出 HAR 文件）重放成脚本。
  • HTTPS 流量解密：要解密必须安装代理工具提供的证书，例如在浏览器的信任证书管理中安装 Fiddler 根证书，只配端口不解密只会录到握手失败。
  • HTTPS 接口的验证范围：确认 URL 以 https 开头、请求方法与请求头按接口文档配置；自签名证书在工具内加信任配置，更推荐把证书加载到客户机信任存储，而不是长期用 verify=False；除功能外还要做安全性测试，可用 OWASP ZAP 或 Burp Suite 做漏洞扫描和渗透测试。

Requests 基础

  • 七种请求方法：requests.get、requests.post、requests.put、requests.delete、requests.head、requests.patch、requests.options；head 与 GET 类似但不返回响应体、仅返回响应头，options 用于获取服务器支持的 HTTP 方法。
  • 常用参数：超时要显式设置（如 requests.get(url, timeout=3)）避免程序卡死；认证用 HTTPBasicAuth；文件上传用 POST 的 files 参数（如 files = {‘file’: open(‘report.xls’, ‘rb’)}）；大文件用流式请求 requests.get(url, stream=True) 配合 response.iter_content(chunk_size=1024) 逐块处理以改善内存使用。
  • JSON 接口四步：requests.post(url, headers=headers, data=json.dumps(data))，headers 里 Content-Type 设为 application/json，响应判 status_code == 200 并调 response.json()，异常分别捕获 HTTPError、ConnectionError、Timeout、RequestException 并配 logging 记录请求与响应。
  • 请求头：headers 必须以字典形式传，一个头名对应一个值；常用 Content-Type、Accept、Authorization、Cookie；想确认实际发出的头可用 response.request.headers 回读。
  • 带 Cookie 的三种写法：构造字典作为 cookies 参数传、或在 headers 里手工拼 ‘Cookie’ 字符串、或用 requests.cookies.RequestsCookieJar 以 jar.set 设置 domain 与 path 处理复杂场景；已知一批 Cookie 也可用 requests.utils.cookiejar_from_dict() 构造后赋给 session.cookies。
  • Session 与 Cookie 持久化：用 requests.Session() 贯穿全流程，登录请求返回的 Cookie 自动保存、后续请求自动携带；长时间跑的测试可把 session.cookies 用 pickle 序列化存文件再载入；requests 不受浏览器 Same-Origin Policy 限制，跨域靠设定合适头部解决；账号密码等敏感数据走环境变量或密钥管理服务。
  • HTTPS 证书三种处理：verify=False 忽略验证（只在可信的开发/测试环境用）、verify='/path/to/ca-bundle.crt' 指定 CA 证书文件或完整证书链、cert=('/path/client.crt', '/path/client.key') 提供客户端证书；更精细的 TLS 版本与密码套件控制靠 requests.Session 设置自定义 SSLContext。

接口自动化工程化

  • 用例间参数传递：在 conftest.py 里用 @pytest.fixture 定义返回共享参数的 fixture，测试函数按参数名声明即可拿到（不要用全局变量硬传）；作用域可选 function、class、module、session，作用域越大创建和销毁次数越少；fixture 之间还能互相依赖构建数据依赖链。
  • 用例数据管理：数据与脚本分离，存放在 Excel、JSON、CSV 文件或数据库表中，按功能或模块分成测试套件，用 Git 做版本控制；设计要覆盖正常情况、异常情况（传非法参数看错误信息）与边界情况（空值、最大最小值）。
  • 签名与 Token：签名是按特定算法（如 HMAC、MD5）对请求数据与密钥做哈希，用 hmac.new(secret_key.encode(), message.encode(), hashlib.sha256).hexdigest() 得到十六进制串，参数按 key 排序拼成 key=value&key=value 作为 message；Token 由授权服务器用用户名密码认证获取，要考虑有效期与刷新机制；请求头分别放 Signature 与 Authorization: Bearer {token}。
  • 数据驱动的落地方式：Java 用 JUnit 的 Parameterized 配 Apache Commons CSV 遍历 CSV；Python 用 unittest 配 pandas 读 Excel（pd.read_excel 后 iterrows 逐行断言）；Web 用 Selenium 配 TestNG 的 DataProvider 从 Excel 取数。
  • 参数化类型与实现方法：类型分值参数化、文件参数化、数据库参数化、环境变量参数化、API 参数化；实现上可在代码里硬编码（不推荐）、读测试数据文件（Excel 用 Apache POI、CSV 用 OpenCSV）、用配置文件或环境变量、用框架自带的数据驱动功能（TestNG 的 DataProvider、JUnit 的 Parameterized）、或直接用 JDBC 查库并缓存结果。
  • 随机数据生成：random.randint 生成整数、random.uniform(1.5, 6.5) 生成范围内浮点数，random.seed(42) 固定种子保证可重复（调试与回归必须），随机字符串用 string.ascii_letters 配 random.choice 拼出指定长度（如 8 位），需要更复杂的随机能力时改用 numpy（np.random.randint、np.random.uniform）。
  • 流水线接入：用例框架如 RestAssured、Postman、JMeter、Robot Framework 结合 Jenkins、CircleCI 做定时执行与结果报告，代码提交后立即跑测试以快速反馈。
