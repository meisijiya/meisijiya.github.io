1. 常用自动化测试工具及其运行原理是什么？写出一段元素查找的代码。

🎬 面试现场

面试官（口语化）：自动化测试常用哪些工具？它们大概是什么原理？顺手写一段元素查找的代码看看。

⚠️ 翻车点

最容易答成「工具就那几个，说一下名字」——面试官真正想听的是运行原理。另一类翻车是原理说成「模拟用户操作」这一句就带过，那等于没答；Selenium WebDriver 的运行原理是有固定顺序的：启动浏览器 → 定位元素 → 模拟操作 → 验证结果 → 关闭浏览器。写代码时也有坑：只写 findElement 不写 quit()，脚本跑完浏览器还挂着；驱动路径不设 webdriver.chrome.driver，换台机器就跑不起来。

📝 现场作答

  • 常用的自动化测试工具有 Selenium、Appium、Junit、TestNG、Postman、Cypress 等。这些工具主要通过自动化脚本模拟用户操作，实现程序功能的自动化测试。
  • 各工具的定位：
    1. Selenium：一个开源的 Web 测试工具，可支持多种浏览器和编程语言，常被用于 Web 应用的功能测试。
    2. Appium：一个用于移动应用测试的开源框架，可支持 iOS 和 Android 设备，使用 WebDriver 协议。
    3. Junit：Java 语言的单元测试框架，广泛应用于测试驱动开发（TDD）中。
    4. TestNG：类似 Junit，但更为强大的测试框架，提供了多线程测试执行的功能。
    5. Postman：用于 API 测试的工具，可以用于测试 Web 服务和服务器端的接口。
    6. Cypress：一个现代 Web 测试工具，特别是在前端开发以及 CI/CD 流水线中很受欢迎。

  • Selenium WebDriver 运行的基本原理大致如下：
    1. 启动浏览器：通过创建一个 WebDriver 实例来启动浏览器，例如 ChromeDriver、FirefoxDriver 等。
    2. 定位元素：利用各种定位策略（如 By.id、By.name、By.xpath、By.cssSelector 等）来查找指定的 Web 页面元素。
    3. 模拟用户操作：对找到的元素进行各种操作，例如点击（click）、输入（sendKeys）、获取文本（getText）等。
    4. 验证结果：通过断言（assertions）验证操作结果是否符合预期。
    5. 关闭浏览器：最后，通过调用 quit() 或者 close() 方法关闭浏览器。
  • 进一步的能力：Selenium 支持 Chrome、Firefox、Safari、Edge 等多种浏览器，支持 Java、C#、Python、Ruby、JavaScript 等多种语言；提供丰富的 API 接口处理拖放、处理 JavaScript alerts/popup、文件上传下载等复杂交互；能很好地与 CI/CD 工具（如 Jenkins）集成，也可以与 TestNG、Junit 等测试框架结合使用，或者引入 Allure 等测试报告工具。

❌ 千万别说的话

  • “自动化测试工具就是模拟用户点鼠标而已。” —— 原理是模拟用户操作没错，但完整链路还包括定位元素、验证结果、关闭浏览器这些环节。
  • “用 Selenium 找元素就是按 ID 找。” —— 定位策略有 By.id、By.name、By.xpath、By.cssSelector 等多种。
  • “脚本跑完不用管，浏览器会自己关。” —— WebDriver 提供了启动、停止和操作浏览器的方法，最后应通过调用 quit() 或者 close() 方法关闭浏览器。

2. Selenium WebDriver 支持哪些编程语言编写测试用例？

🎬 面试现场

面试官（口语化）：Selenium 支持哪些语言写用例？各自优缺点你了解吗？

⚠️ 翻车点

最容易只报一串语言名字就停——面试官真正想听的是各语言的优缺点。比如 Java 是 Selenium 原生开发的语言，强类型、适合大规模项目，但语法冗长；Python 语法简洁、社区资源丰富，但大规模并发时性能稍逊。还有人忽略选择依据：很多团队选语言时还会考虑生态环境、团队已有技术栈、开发者的熟悉程度和社区支持，不只是看语言本身。

📝 现场作答

  • Selenium WebDriver 支持多种编程语言编写测试用例，包括但不限于以下几种：Java、Python、C#、JavaScript（特别是 Node.js）、Ruby、PHP。
  • 各语言的优缺点：
    1. Java：优点是 Selenium 原生开发的语言，同时它拥有丰富的工具和库，强类型语言，适合大规模项目开发；缺点是语法相对冗长，初学者有时会觉得繁复。
    2. Python：优点是语法简洁明了，非常适合自动化脚本编写，有丰富的库支持和社区资源；缺点是有时性能较 Java 稍逊一筹，特别是在大规模并发的情况下。
    3. **C#**：优点是与 Microsoft 技术栈整合完美，特别是在 Windows 环境中，语法现代，支持诸如 LINQ 等强大的功能；缺点是对于跨平台支持相对来说没有那么灵活，尽管已经有了 .NET Core。
    4. JavaScript（Node.js）：优点是非常适合与前端开发紧密结合，异步编程模型支持高效的 I/O 操作，广受前端开发者欢迎；缺点是异步编程需要一定的学习曲线，错误处理可能较为复杂。
    5. Ruby：优点是语法优美，逻辑清晰，非常适合快速开发和原型设计，被 Cucumber 和 Watir 等测试框架青睐；缺点是性能不如 Java 和 C#，社区资源相对其他语言少一些。
    6. PHP：优点是 Web 开发者广泛使用，较容易上手；缺点是主要适用于 Web 开发，对于复杂的自动化测试场景，选择其他语言可能更加合适。
  • 更深层次的考虑：很多团队在选择语言时还会考虑生态环境、团队已有技术栈、开发者的熟悉程度和社区支持等因素。选择使用哪种语言编写 Selenium WebDriver 测试用例时，不仅要看语言本身的优缺点，还要评估整个项目的需求，包含团队成员的技能、系统的复杂度以及未来维护和扩展的需求。

3. Selenium 中提供几种类型的 WebDriver API？

🎬 面试现场

面试官（口语化）：Selenium 有几种 WebDriver API？分别管什么？

⚠️ 翻车点

最容易只说「每个浏览器一个」——漏掉 RemoteWebDriver 这一类，它是用于分布式测试、可以远程控制不同浏览器的。第二个坑是只数浏览器不记名字：ChromeDriver、FirefoxDriver、EdgeDriver、InternetExplorerDriver、SafariDriver、OperaDriver 各对应一个浏览器。第三个坑是忽略版本匹配：驱动版本不兼容、元素查找不到、浏览器窗口未响应这些问题新手常遇到，要靠驱动版本匹配和 WebDriver 的日志系统来排查。

4. 什么是 Selenium IDE？

🎬 面试现场

面试官（口语化）：Selenium 听说有好几个组件，那个 IDE 是干什么的？跟 WebDriver 有什么区别？

⚠️ 翻车点

最容易答错的是把 Selenium IDE 说成「要写代码的集成开发环境」——它不需要编写代码，是以插件形式运行在浏览器里的录制回放工具。另一个坑是只说优点不说缺点：它的灵活性有限、对复杂场景和条件控制支持有限，而且录制的脚本对 Web 页面布局变化比较敏感，后期维护比较麻烦。

📝 现场作答

  • Selenium IDE（Integrated Development Environment）是 Selenium 系列工具中的一部分，是一种用于 Web 应用自动化测试的工具。它以插件的形式运行在浏览器中（如 Firefox 和 Chrome），允许用户通过录制和回放的方式来创建自动化测试脚本。
  • Selenium IDE 的一个显著特点是它不需要编写代码——用户可以通过 GUI 界面中的录制按钮捕获一系列用户操作，并生成相应的测试脚本。对刚接触自动化测试的新手而言，它是一个友好的入门工具。
  • Selenium 家族：Selenium 系列工具不仅包括 Selenium IDE，还有 Selenium WebDriver 和 Selenium Grid。Selenium WebDriver 提供灵活的编程语言支持（如 Java、Python 等），适合更复杂的测试场景；Selenium Grid 则帮助分布式执行测试，提升测试效率。
  • 录制和回放机制：
    • 录制：用户在浏览器中进行操作，如输入数据、点击按钮等，Selenium IDE 会记录这些操作并生成相应的测试脚本。
    • 回放：用户可以随时回放之前录制的操作，用于验证功能测试是否通过。
  • 优缺点：
    • 优点：1）简单易用：不需要编写代码，直接录制操作；2）快速入门：适合初学者和小型项目的快速测试。
    • 缺点：1）有限的灵活性：对复杂的测试场景和条件控制支持有限；2）维护困难：录制的脚本对 Web 页面布局的变化比较敏感，后期维护可能比较麻烦。
  • 扩展功能：
    • 测试用例管理：用户可以在 Selenium IDE 中创建和管理多个测试用例。
    • 插件支持：Selenium IDE 支持各种插件扩展，如数据驱动测试、集成各种 CI/CD 工具等。
  • 实际案例：有一家电商网站需要测试用户在网站上注册账号、浏览商品、添加商品到购物车并最终结算，这一系列操作可以通过 Selenium IDE 进行录制，并在不同的浏览器上进行回放，确保功能正常。

7. Selenium 的工作原理是什么？

🎬 面试现场

面试官（口语化）：你敲一行 click，Selenium 到底怎么让浏览器真的点下去的？

⚠️ 翻车点

最容易漏掉的是「解析指令」这一环：脚本并不是直接指挥浏览器，而是 Selenium 客户端先与浏览器驱动程序（WebDriver）通信，把指令转换成浏览器能理解的命令。另一个坑是把 ChromeDriver、GeckoDriver 说成「Selenium 的浏览器」——它们是中间人，负责把脚本指令传给浏览器并拿回执行结果。

📝 现场作答

  • Selenium 是一个广泛使用的开源工具，用于 Web 应用程序测试。它能够模拟用户在浏览器中的操作，并自动执行这些操作。Selenium 的工作原理可以简单总结为以下几个步骤：
    1. 发送指令：测试脚本发出浏览器指令，例如点击按钮、输入文本。
    2. 解析指令：Selenium 客户端与浏览器驱动程序（WebDriver）通信，将这些指令转换成浏览器能够理解的命令。
    3. 执行操作：浏览器执行这些命令，模拟用户的实际操作。
    4. 反馈结果：浏览器驱动程序返回操作结果给 Selenium 客户端，并且最终测试脚本获取这些结果进行验证。
  • Selenium 组件：Selenium 由几个组件构成，它们各自有不同的功能：
    • Selenium WebDriver：主要用于现代浏览器的跨浏览器测试，提供了与浏览器的接口。
    • Selenium IDE：用于录制和回放，适合回归测试和初学者。
    • Selenium Grid：用于并行测试，帮助将测试分布在多台机器上执行。
  • 驱动程序（WebDriver）的作用：每个浏览器有一个对应的驱动程序，例如 ChromeDriver 对应谷歌浏览器，GeckoDriver 对应火狐浏览器。驱动程序主要充当中间人角色，把测试脚本的指令传递给浏览器并获取执行结果。
  • 编写测试脚本：可以用多种编程语言编写 Selenium 测试脚本，例如 Java、Python、C#、Ruby 等，步骤通常包括：初始化 WebDriver；导航到被测网页；查找和操作网页元素；验证操作结果；关闭和清理资源。
  • 定位元素：Selenium 提供多种方式来定位页面元素，包括 ID、Name、Class Name、Tag Name、CSS Selector、XPath 等。定位准确的元素是编写测试用例成功的关键。
  • 并行测试与持续集成：Selenium Grid 允许在多个浏览器和操作系统组合上并行运行测试用例，这在大型项目中非常重要。而持续集成工具（如 Jenkins、GitHub Actions）与 Selenium 集成，即可实现代码提交后自动运行测试，提高效率和代码质量。
  • 错误处理与调试：测试脚本在执行过程中可能遇到各种错误，如元素无法找到、时间超时等。学会处理这些异常是成为一个合格自动化测试工程师的重要技能。明智地使用等待机制（显式等待、隐式等待）可以减少这些错误。

8. Selenium 2 和 Selenium 1 的区别是什么？

🎬 面试现场

面试官（口语化）：Selenium 1 和 Selenium 2 到底差在哪？架构上有什么不一样？

⚠️ 翻车点

📝 现场作答

  • Selenium 2（也叫 Selenium WebDriver）和 Selenium 1（也叫 Selenium RC）在架构和功能上有几个关键区别：
    1. 架构变化：Selenium 2 引入了 WebDriver API，替代了 Selenium 1 的 JavaScript 封装的 Remote Control（RC）服务器。WebDriver API 直接通过浏览器本地的兼容性接口与浏览器沟通，从而提升了执行速度和稳定性。

  • 功能增强：Selenium 2 不仅仅是改进了架构，还增加了许多新功能。比如它支持更复杂的用户交互操作，包括拖放、键盘事件等，提升了自动化测试的能力和灵活性。

多标签页怎么切？ window_handles 获取所有打开的窗口句柄，switch_to.window(handle) 切换到指定窗口。

❌ 千万别说的话

  • “close() 和 quit() 是一回事。” —— close() 关闭当前标签页，quit() 关闭所有关联的窗口并退出浏览器实例。
  • “隐式等待是等到条件成立为止。” —— 隐式等待是等待指定时间后抛出 NoSuchElementException，等条件成立的是显式等待。

容易答成”测试多的项目都适合”，漏掉最核心的判断维度——页面结构和功能相对稳定。自动化脚本依赖于页面的 DOM 结构，如果页面变化频繁，维护和更新脚本的成本会非常高，所以早期研发阶段或需求还不确定的项目不太适合一开始就做 UI 自动化。另一个坑是只讲成本不讲收益，把”投入与回报比较高”这个维度漏掉。

    2. 重复性高的测试需求。如果某些测试需要频繁执行，比如回归测试、跨浏览器测试，那么自动化测试能极大地提高效率。

  • 相关技术点的延伸：
    • 选择合适的自动化测试框架和工具：Selenium 是非常流行的 Web UI 自动化测试工具之一，但还不止这些，像 Cypress、Puppeteer 都是值得考虑的选择。不同的框架和工具有不同的优缺点，选择时需要结合具体项目的需求、团队的技术栈和熟悉程度进行判断。

    • 持续集成与持续交付（CI/CD）：自动化测试与 CI/CD 的结合，可以自动触发脚本运行并生成报告，实现测试自动化的闭环。工具如 Jenkins、GitLab CI 都是常见的 CI 工具，可以与自动化测试框架无缝集成。
    • 数据驱动测试：数据驱动测试是一种自动化测试策略，通过抽离测试数据与测试逻辑，使得同一脚本可以针对不同的数据集进行运行。这样不仅提高了脚本的覆盖面，还增强了测试的灵活性。

📝 现场作答

  • UI 自动化测试主要是通过编写代码来模拟用户操作，以此来验证软件的用户界面是否按照预期工作。具体的步骤如下：
    1. 选择合适的自动化测试工具：常见的工具有 Selenium、Cypress、Katalon Studio 等。
    2. 设置测试环境：包括安装相关的浏览器驱动、测试框架以及配置工具。

    4. 运行测试脚本：执行编写好的测试脚本，捕获和记录测试结果。
    5. 分析测试结果：对测试结果进行分析，修复发现的缺陷并重测。

17. UI 自动化测试的流程是什么？

🎬 面试现场

面试官（口语化）：完整的 UI 自动化测试流程有哪几步？从需求分析到回归，你给我排一遍。

⚠️ 翻车点

容易漏的是最后两步——缺陷管理（记录并报告缺陷，跟踪修复直到解决所有问题）和回归测试（修复后重新执行脚本，确认新代码没引入新问题）。另一个坑是环境准备只说「装个浏览器」：环境要贴近生产环境，操作系统、浏览器、应用程序、数据库、网络环境等配套资源都要一致。

📝 现场作答

  • UI 自动化测试的流程通常包括以下几个步骤：
    1. 需求分析：充分理解项目的需求和预期用户行为，明确测试目标和范围。
    2. 测试环境准备：搭建与生产环境相似的测试环境，包括操作系统、浏览器、应用程序等。
    3. 工具选择：选择适合的自动化测试工具，如 Selenium、Appium 或其他专用工具。
    4. 编写测试脚本：根据测试用例编写相应的自动化脚本，确保覆盖所有关键功能和业务场景。
    5. 执行测试：运行测试脚本，记录执行结果，捕捉异常和错误。
    6. 结果分析：分析测试结果，判断是否存在缺陷，同时生成详细的测试报告。
    7. 缺陷管理：记录并报告缺陷，跟踪修复过程直到解决所有问题。
    8. 回归测试：在问题修复后，重新执行测试脚本以确保新代码没有引入新的问题，确保功能正常。
  • 需求分析：理解业务需求对于正确设计测试用例和选择适宜的测试工具至关重要。常见的需求文档有 PRD（产品需求文档）和 FRD（功能需求文档）。
  • 测试环境准备：确信测试环境尽量贴近实际的生产环境，这样才能保证测试结果的可靠性；还需保证数据库、网络环境等配套资源的一致性。
  • 工具选择：要考虑工具的兼容性、开源程度、社区支持和学习曲线。Selenium 经常用于 Web 应用测试，而 Appium 则用于移动应用测试。
  • 编写测试脚本：应结构清晰、代码可维护，还需尽量避免硬编码。常用的脚本语言有 Python、Java 等。
  • 执行测试：可以使用持续集成工具（如 Jenkins）来自动化执行测试脚本并将结果反馈给开发团队，这样可以集成到 DevOps 流水线中。
  • 结果分析：测试结果中不仅要包含通过与失败的简单统计，还应具体描述每一个失败项，便于定位问题。可以使用 Allure、ExtentReports 等工具生成详细的报告。
  • 缺陷管理：使用缺陷跟踪工具（如 JIRA、Bugzilla）记录和管理缺陷，可以跟踪每个缺陷的状态，确保所有问题都得到及时解决。
  • 回归测试：回归测试尤其重要，用来确保修复后的系统没有引入新的错误。推荐使用版本控制和测试用例管理工具，确保回归测试的有效性。

18. 如何验证 UI 自动化测试的覆盖率？

🎬 面试现场

Selenium 基础

  • 定义与组成：Selenium 是开源的自动化测试工具，用于自动化 Web 应用程序测试，由 Selenium WebDriver、Selenium IDE、Selenium Grid、Selenium RC 四部分组成，其中 RC 是旧版本、现已被 WebDriver 取代。
  • 工作原理四步：测试脚本发出指令 → Selenium 客户端与浏览器驱动程序通信、把指令转换成浏览器能理解的命令 → 浏览器执行命令模拟用户操作 → 驱动程序把执行结果返回给客户端供脚本断言验证。
  • 驱动是中间人：每个浏览器有对应驱动，ChromeDriver 对应谷歌浏览器、GeckoDriver 对应火狐浏览器，驱动只负责把脚本指令传给浏览器并取回执行结果，脚本指令并不直发浏览器。
  • WebDriver 五步链路：启动浏览器（创建 ChromeDriver、FirefoxDriver 实例）→ 用 By.id、By.name、By.xpath、By.cssSelector 定位元素 → 模拟 click、sendKeys、getText 操作 → 用断言验证结果 → 调用 quit() 或 close() 关闭浏览器，漏掉关闭步骤浏览器会一直挂着。
  • 定位策略：可用 By.id、By.name、By.xpath、By.cssSelector，旧版写法还有 find_element_by_id(id)、find_elements_by_class_name(class_name)、find_element_by_xpath(xpath)，两版 API 都要照抄题块原写法。
  • WebDriver API 类型：ChromeDriver（Google Chrome）、FirefoxDriver（Mozilla Firefox）、EdgeDriver（Microsoft Edge）、InternetExplorerDriver（Internet Explorer）、SafariDriver（Safari）、OperaDriver（Opera），另有用于分布式测试、可远程控制不同浏览器的 RemoteWebDriver。
  • 分布式执行：RemoteWebDriver 可与 Selenium Grid 协作实现跨节点浏览器管理，写法为 webdriver.Remote(command_executor=’http://localhost:4444/wd/hub‘, desired_capabilities=DesiredCapabilities.CHROME)，可在多台机器并行执行以节省测试时间。
  • 版本匹配与排查：驱动版本不兼容、元素查找不到、浏览器窗口未响应是新手高频问题，需保证驱动与浏览器版本匹配，并开启 selenium.webdriver.remote.remote_connection 的 DEBUG 日志定位根源。
  • 支持语言：Java、Python、C#、JavaScript（特别是 Node.js）、Ruby、PHP；Java 是 Selenium 原生开发语言、强类型适合大规模项目但语法冗长，Python 简洁但大规模并发性能稍逊，Ruby 性能不如 Java 和 C#。
  • Selenium IDE：以插件形式运行在浏览器中（Firefox 和 Chrome），不需要编写代码，靠 GUI 录制按钮捕获用户操作生成脚本再回放；缺点是灵活性有限、对复杂场景和条件控制支持有限，且录制的脚本对 Web 页面布局变化敏感、后期维护麻烦。
  • 支持测试类型：功能测试、回归测试、UI 测试、跨浏览器测试、数据驱动测试五类；数据驱动用 CSV 或 Excel 等数据文件驱动测试，配合 TestNG、JUnit 可实现并行与套件管理。
  • 优缺点：优点是开源免费、社区资源丰富、支持多浏览器多语言、扩展性强；缺点是对动态 Web 页面和 AJAX 请求支持较弱、没有内置报告功能（需配合 TestNG、JUnit）、依赖浏览器与 WebDriver 版本兼容。
  • 版本演进：Selenium 2 引入 WebDriver API 取代 Selenium 1 基于 JavaScript 封装的 RC 服务器，直接通过浏览器本地兼容性接口通信以提升速度和稳定性；Selenium 1 是异步执行需要大量等待，Selenium 2 是同步执行。
  • 常用函数：click()、send_keys(keys)、get(url) 分别是模拟点击、输入文本、打开 URL；close() 只关闭当前标签页，quit() 关闭所有关联窗口并退出浏览器实例。
  • 等待机制：显式等待 WebDriverWait(driver, timeout).until(condition) 等条件成立（如元素可见），隐式等待 implicitly_wait(time) 等待指定时间后抛出 NoSuchElementException。
  • 弹窗与窗口：switch_to.alert 处理 alert、confirm、prompt，配合 accept()、dismiss()、send_keys()；多标签用 window_handles 取全部句柄、switch_to.window(handle) 切换，窗口控制还有 maximize_window()、minimize_window()、refresh()。
  • 其他常用函数：get_screenshot_as_file(filename) 截图保存，get_cookies()、add_cookie(cookie_dict)、delete_cookie(name) 操作 cookie，懒加载滚动用 driver.execute_script(“window.scrollTo(0, document.body.scrollHeight);”)。

UI 自动化基础

  • 定义：UI 自动化测试本质是用编程方式模拟用户操作，自动化测试并验证用户界面（User Interface）是否按预期工作，检查按钮、输入框、菜单等元素在不同浏览器或平台上的表现一致。
  • 五大分类：功能测试、回归测试、烟雾测试、兼容性测试、性能测试；烟雾测试是浅测试，目标是在很短的时间内提供早期反馈，而不是跑全量用例。
  • 优势：可重复执行相同用例，回归测试收益最高，能减少手工测试工作量与人为错误，并保证应用在不同设备与浏览器上表现一致。
  • 局限：编写与维护脚本需要投入开发资源，UI 测试通常较为缓慢、不适合覆盖所有测试场景，复杂的用户交互难以处理，实际项目中通常与单元测试、API 测试结合使用。
  • 最佳实践：分层测试（UI 测试专注用户交互，业务逻辑和后台交给其他层次）、数据驱动测试（不改代码只改数据以提高测试覆盖率）、保持独立性（用例不依赖其他用例的执行结果）。
  • 适合做的项目：页面结构和功能相对稳定、重复性高的测试需求多、投入与回报比较高、项目规模较大且复杂；需求未确定的早期研发阶段不适合一开始就做，因为脚本依赖 DOM 结构、页面频繁变动会让维护成本非常高。
  • 工具选择：Selenium（开源、多语言、多浏览器）、Cypress（现代前端测试工具，适合单页应用）、Appium（移动端，同时支持 Android 和 iOS）、TestCafe（Web 框架，可直接在浏览器中运行测试代码）。
  • 优缺点：优点是提高效率与准确性、提高覆盖率、可集成 CI/CD；缺点是开发维护成本高、不适合很复杂的 UI 交互、需要编程与框架知识、无法完全替代手工测试（体验性、感知性测试仍需人工）。
  • 来源与维护成本：手动测试在功能复杂后变得费时费力、易出错、难覆盖全部场景，自动化测试由此出现；脚本初次编写耗时耗力，但建立后只需在需求变化或 UI 变动时少量维护，UI 异常变动导致脚本失效时通常要结合手工测试。

UI 自动化落地

  • 八步流程：需求分析 → 测试环境准备 → 工具选择 → 编写测试脚本 → 执行测试 → 结果分析 → 缺陷管理 → 回归测试；缺陷管理要跟踪修复直到解决所有问题，回归测试要在修复后重跑脚本确认没有引入新问题。
  • 环境准备：搭建与生产环境相似的测试环境，包含操作系统、浏览器、应用程序等，并保证数据库、网络环境等配套资源一致性，否则结果不可靠。
  • 需求与工具：常见需求文档是 PRD（产品需求文档）和 FRD（功能需求文档）；工具选型看兼容性、开源程度、社区支持和学习曲线，Selenium 用于 Web 应用测试、Appium 用于移动应用测试。
  • 报告与缺陷工具：报告用 Allure、ExtentReports 生成并逐条描述失败项，缺陷用 JIRA、Bugzilla 记录和跟踪状态，CI 执行可用 Jenkins 接入 DevOps 流水线。
  • 环境搭建七步：选框架（Selenium、Appium、Cypress）→ 装编辑器（Visual Studio Code、PyCharm）→ 配运行环境（Python 环境、Node.js）→ 搭浏览器驱动（Chrome 对应 chromedriver、Firefox 对应 geckodriver、Internet Explorer 对应 IEDriverServer）→ 接 Git → 设 Jenkins 等 CI/CD → 配 Allure 或 ExtentReports 报告。
  • 依赖安装：Selenium 用 pip 安装（pip install selenium），Cypress 用 npm 安装（npm install cypress –save-dev），代码提交用 git clone、git commit、git push。
  • 覆盖率验证六步：收集需求和功能点 → 列出覆盖所有功能点的测试用例 → 把人工用例转成自动化脚本 → 执行 → 生成覆盖率报告（JUnit、TestNG 结合 Jacoco 等代码覆盖率工具）→ 分析未覆盖部分并补充用例和脚本。
  • 用例多样性：除主路径和正常场景外还要覆盖边界条件、异常处理和负面测试，例如表单提交除了正常输入，还要测空输入、非法字符；需求溯源可用 Jira、Trello 跟踪需求变化与版本管理。
  • 报告与工具集成：报告不只看覆盖率，还要关注失败用例并分析是脚本问题还是应用问题；Jenkins 可定时持续运行并生成报告，配合 Docker 容器保证环境一致性和隔离性。

框架设计

  • 建框架五步：选工具框架 → 设计测试架构 → 编写高质量脚本 → 接入 CI/CD → 建立报告与反馈；工具按场景选，Selenium 适合 Web 测试、Appium 适合移动应用、TestNG 或 JUnit 适合 Java 单元测试。
  • 架构模块：测试架构至少包含测试用例模块、测试数据模块、报告生成模块、日志模块，保证脚本的维护性和可扩展性；只装好 Selenium 写一批脚本只是用例，不是框架。
  • 设计模式：采用 Page Object Model (POM) 模式，把页面元素和行为封装在类中，UI 更改只需在一个地方更新，提高脚本复用性与可维护性，可配合 SOLID 等面向对象原则增强健壮性。
  • 避免硬编码：用数据驱动和关键字驱动编写脚本，测试数据放 JSON、Excel 等数据文件并配配置文件，同时用注释、文档和定期代码审查提升可读性。
  • 用例设计十步：明确测试目标 → 理解被测系统 → 选工具 → 设计用例（覆盖常见用户场景和边缘情况）→ 数据准备（输入数据与预期输出数据）→ 编写脚本 → 设置与生产一致的环境 → 执行并与预期结果对比 → 分析结果并生成报告 → 定期自动化维护。
  • 配套能力：用 POM 提高用例可读性与可维护性，用 Jenkins、GitHub Actions、Travis CI 等把测试接入 CI/CD 流水线，用 Git 管理测试脚本并与开发代码同步，按项目场景组合白盒测试、黑盒测试、回归测试等策略。
