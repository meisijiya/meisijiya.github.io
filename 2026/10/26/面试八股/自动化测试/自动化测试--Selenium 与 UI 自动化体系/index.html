1. 常用自动化测试工具及其运行原理是什么？写出一段元素查找的代码。

🎬 面试现场

面试官（口语化）：自动化测试常用哪些工具？它们大概是什么原理？顺手写一段元素查找的代码看看。

⚠️ 翻车点

最容易答成「工具就那几个，说一下名字」——面试官真正想听的是运行原理。另一类翻车是原理说成「模拟用户操作」这一句就带过，那等于没答；Selenium WebDriver 的运行原理是有固定顺序的：启动浏览器 → 定位元素 → 模拟操作 → 验证结果 → 关闭浏览器。写代码时也有坑：只写 findElement 不写 quit()，脚本跑完浏览器还挂着；驱动路径不设 webdriver.chrome.driver，换台机器就跑不起来。

📝 回答重点

  • 常用工具我先报一串：Selenium、Appium、Junit、TestNG、Postman、Cypress，都是靠脚本模拟用户操作来做测试。
  • 各自管哪块：Selenium 跑 Web 功能测试、多浏览器多语言；Appium 跑 iOS 和 Android、走 WebDriver 协议；Junit 是 Java 单元测试、常用于 TDD；TestNG 类似 Junit 但更强、能多线程执行；Postman 测接口；Cypress 是现代前端测试工具、CI/CD 里很受欢迎。
  • 我一般用 Selenium Java 版写元素查找，照着这个写：
  • WebDriver 的链路就是五步：启动浏览器（建 ChromeDriver、FirefoxDriver 实例）→ 定位元素（By.id、By.name、By.xpath、By.cssSelector）→ 模拟操作（click、sendKeys、getText）→ 验证结果（断言）→ 关闭浏览器（quit() 或 close()）。最后那步别省，不然浏览器一直挂着。

📈 拔高

  • 选型别只看名字，要看被测对象：Web 用 Selenium、移动用 Appium、接口用 Postman。跨语言、多浏览器这套组合在 CI/CD（比如 Jenkins）里集成很顺，配合 TestNG/JUnit 和 Allure 报告基本能跑通全流程。
  • 代码里两个坑我踩过：驱动路径不设 webdriver.chrome.driver 换台机器就起不来；只写 findElement 不写 quit()，进程和浏览器都残留。这俩是新手高频翻车点。

💡 主动加分的追问准备

面试官追问 你的答案
Selenium WebDriver 的运行原理分几步？ 五步：启动浏览器建 WebDriver 实例、用 By.id、By.xpath 等定位元素、click 和 sendKeys 模拟操作、断言验证结果、最后 quit() 关闭浏览器。
Selenium 之外还有哪些常用自动化测试工具？ Appium 管移动（iOS 和 Android、走 WebDriver 协议）、Junit 做 Java 单元测试和 TDD、TestNG 类似 Junit 但支持多线程、Postman 测 API、Cypress 是现代前端和 CI/CD 里流行的 Web 测试工具。
Selenium 的定位策略有哪些？ By.id、By.name、By.xpath、By.cssSelector 等，用这些策略查找指定的 Web 页面元素。

❌ 千万别说的话

  • “自动化测试工具就是模拟用户点鼠标而已。” 原理是模拟用户操作没错，但完整链路还包括定位元素、验证结果、关闭浏览器这些环节。
  • “用 Selenium 找元素就是按 ID 找。” 定位策略有 By.id、By.name、By.xpath、By.cssSelector 等多种。
  • “脚本跑完不用管，浏览器会自己关。” WebDriver 提供了启动、停止和操作浏览器的方法，最后应通过调用 quit() 或者 close() 方法关闭浏览器。

2. Selenium WebDriver 支持哪些编程语言编写测试用例？

🎬 面试现场

面试官（口语化）：Selenium 支持哪些语言写用例？各自优缺点你了解吗？

⚠️ 翻车点

最容易只报一串语言名字就停——面试官真正想听的是各语言的优缺点。比如 Java 是 Selenium 原生开发的语言，强类型、适合大规模项目，但语法冗长；Python 语法简洁、社区资源丰富，但大规模并发时性能稍逊。还有人忽略选择依据：很多团队选语言时还会考虑生态环境、团队已有技术栈、开发者的熟悉程度和社区支持，不只是看语言本身。

📝 回答重点

  • Selenium WebDriver 支持的语言我先报出来：Java、Python、C#、JavaScript（特别是 Node.js）、Ruby、PHP。
  • Java 和 Python：Java 是 Selenium 原生语言、工具库最全、强类型适合大项目，就是语法啰嗦；Python 写脚本最舒服、社区大，但大规模并发时性能比 Java 差一截。
  • C# 和 JavaScript：C# 和微软技术栈贴得紧、Windows 下顺、支持 LINQ，跨平台差些（有 .NET Core）；Node.js 和前端贴得近、异步 I/O 高效，但异步和错误处理有学习曲线。
  • Ruby 和 PHP：Ruby 语法漂亮、适合快速原型，被 Cucumber、Watir 喜欢，性能和社区弱；PHP Web 开发者熟、上手快，复杂场景不太合适。
  • 选型我一般不止看语言本身，还得看生态环境、团队已有技术栈、开发者熟不熟、社区支持，再掂一下项目复杂度和维护需求。

📈 拔高

  • 语言选择本质是团队成本问题。Java 在大型项目里撑得住，Python 在中小项目和快速验证里最划算，别为了「先进」硬上冷门语言。
  • 一个容易忽略的点：JavaScript/Node.js 适合前端团队直接上手，Ruby 适合配 Cucumber 做 BDD。前端团队用 Node.js 能少一层语言切换成本，Ruby 配 Cucumber 做行为驱动测试也顺手。

💡 主动加分的追问准备

面试官追问 你的答案
Selenium WebDriver 支持哪些语言？ 包括但不限于 Java、Python、C#、JavaScript（特别是 Node.js）、Ruby、PHP。
Java 和 Python 各有什么特点？ Java 是 Selenium 原生语言、工具库全、强类型适合大项目，但语法冗长。Python 语法简洁、库和社区强，大规模并发时性能稍逊 Java。
Ruby 写自动化有什么优缺点？ 优点是语法优美、逻辑清晰，非常适合快速开发和原型设计，被 Cucumber 和 Watir 等测试框架青睐。缺点是性能不如 Java 和 C#，社区资源相对其他语言少一些。
C# 适合什么场景？ 它与 Microsoft 技术栈整合完美，特别是在 Windows 环境中，语法现代，支持诸如 LINQ 等强大的功能。缺点是跨平台支持没那么灵活，尽管已经有了 .NET Core。
团队实际选语言看什么？ 还要看生态、团队现有技术栈、大家对这门语言的熟悉度和社区支持，再加上系统复杂度和后续维护需求。

❌ 千万别说的话

  • “Selenium 只支持 Java 和 Python。” 它支持 Java、Python、C#、JavaScript（特别是 Node.js）、Ruby、PHP 等多种语言。
  • “Python 因为是脚本语言所以性能一定不如 Java。” 差距主要体现在大规模并发的情况下，日常脚本化场景差别不大。
  • “选语言只看语言本身的优劣。” 还要评估整个项目的需求，包括团队成员的技能、系统的复杂度以及未来维护和扩展的需求。

⚠️ 翻车点

最容易只说「每个浏览器一个」——漏掉 RemoteWebDriver 这一类，它是用于分布式测试、可以远程控制不同浏览器的。第二个坑是只数浏览器不记名字：ChromeDriver、FirefoxDriver、EdgeDriver、InternetExplorerDriver、SafariDriver、OperaDriver 各对应一个浏览器。第三个坑是忽略版本匹配：驱动版本不兼容、元素查找不到、浏览器窗口未响应这些问题新手常遇到，要靠驱动版本匹配和 WebDriver 的日志系统来排查。

面试官追问 你的答案
Selenium 有哪些类型的 WebDriver API？ ChromeDriver（Google Chrome）、FirefoxDriver（Mozilla Firefox）、EdgeDriver（Microsoft Edge）、InternetExplorerDriver（Internet Explorer）、SafariDriver（Safari）、OperaDriver（Opera），以及用于分布式测试、可远程控制不同浏览器的 RemoteWebDriver。
这些 API 能做什么？ 每种 WebDriver 都能启动、停止、操作浏览器，脚本靠它模拟交互，比如开 URL、找元素、点按钮、填表单。
分布式测试用哪个？ RemoteWebDriver 适合跨平台、跨浏览器的分布式测试，配合 Selenium Grid 能在多台机器上并行跑，省时间。
用 WebDriver 要注意什么？ 需要下载与浏览器版本匹配的驱动程序并配置系统路径。不同浏览器 WebDriver 所需运行环境不同，比如 SafariDriver 在 Windows 上并不常见，更多是在 macOS 上运行 Safari。
遇到元素查不到、窗口无响应怎么排查？ 这类问题常由驱动版本不兼容等引起，可以借助 WebDriver 的日志系统来查找问题的根源，比如开启 selenium.webdriver.remote.remote_connection 的 DEBUG 日志。

❌ 千万别说的话

  • “WebDriver 就等于浏览器驱动，一种浏览器一个类。” 除了各浏览器的专用驱动，还有 RemoteWebDriver，用于分布式测试并可远程控制不同的浏览器。
  • “装个驱动包就能跑，不用管版本。” 驱动要和浏览器版本匹配，还要考虑不同浏览器 WebDriver 所需的运行环境，比如 SafariDriver 更多在 macOS 上使用。
  • “分布式测试就在本机多开几个浏览器。” RemoteWebDriver 可以与 Selenium Grid 协作实现跨节点的浏览器管理，在多个机器上并行执行测试。

4. 什么是 Selenium IDE？

🎬 面试现场

面试官（口语化）：Selenium 听说有好几个组件，那个 IDE 是干什么的？跟 WebDriver 有什么区别？

⚠️ 翻车点

最容易答错的是把 Selenium IDE 说成「要写代码的集成开发环境」——它不需要编写代码，是以插件形式运行在浏览器里的录制回放工具。另一个坑是只说优点不说缺点：它的灵活性有限、对复杂场景和条件控制支持有限，而且录制的脚本对 Web 页面布局变化比较敏感，后期维护比较麻烦。

📝 回答重点

  • Selenium IDE 是 Selenium 家族里的一员，做 Web 应用自动化测试。它以插件形式跑在浏览器里（Firefox 和 Chrome），靠录制回放建脚本，不用写代码。
  • 对新手挺友好，点 GUI 里的录制按钮就能捕获操作、生成脚本，录完随时回放验证功能过没过。
  • Selenium 家族还有 WebDriver 和 Grid：WebDriver 支持 Java、Python 多语言、跑复杂场景；Grid 做分布式执行、提效。
  • 优缺点：优点是简单易用、不用写代码、快速入门，适合初学者和小项目；缺点是灵活性有限、复杂场景和条件控制支持弱，而且录出来的脚本对页面布局变化很敏感、后期维护麻烦。
  • 扩展上能管多个测试用例，支持数据驱动测试、接 CI/CD 之类的插件。

📈 拔高

  • 录制回放最大的坑是脚本脆：页面一改版，录好的脚本大面积红。所以 IDE 适合做原型验证和快速冒烟，复杂回归还是得靠 WebDriver 写脚本。
  • 我一般把 IDE 当「用例速写工具」，先把流程跑通、确认页面稳了，再让 WebDriver 接正式用例。这样比一上来就写脚本省时间。

💡 主动加分的追问准备

面试官追问 你的答案
Selenium IDE 的录制和回放分别是什么？ 录制就是你点按钮、填数据时它把操作记下来生成脚本，回放就是把这套操作再跑一遍看功能过不过。
Selenium IDE 的优缺点是什么？ 好处是不用写代码，录一遍就能跑，适合入门和小项目。缺点是复杂场景撑不住，页面一改脚本就得跟着改。
Selenium 家族里还有哪些成员？ 除了 Selenium IDE，还有 Selenium WebDriver 和 Selenium Grid：WebDriver 提供灵活的编程语言支持（如 Java、Python 等），适合更复杂的测试场景。Grid 帮助分布式执行测试，提升测试效率。

❌ 千万别说的话

  • “Selenium IDE 是一套需要自己写代码的集成开发环境。” 它以插件形式运行在浏览器中，显著特点是不需要编写代码，靠 GUI 录制按钮捕获操作生成脚本。
  • “Selenium IDE 能覆盖所有复杂测试场景。” 它对复杂的测试场景和条件控制支持有限，录制的脚本对页面布局变化敏感，维护起来比较麻烦。

5. 列出 Selenium 支持的一些测试类型？

🎬 面试现场

面试官（口语化）：Selenium 到底能干哪些活？功能、回归、数据驱动这些它都能做吗？

⚠️ 翻车点

只答「功能测试、回归测试」两句就停，容易被判成只会用 Selenium 跑冒烟。UI 测试、跨浏览器测试、数据驱动测试这三条同样属于 Selenium 支持的测试类型，别漏。另一个坑是把 Selenium IDE 当成执行引擎——它是浏览器插件，用途是快速录制和回放测试脚本、给测试用例做原型设计。

📝 回答重点

  • Selenium 支持的测试类型我先报五类：功能测试（按需求文档验证功能）、回归测试（代码改完确认没破坏旧功能）、UI 测试（查界面元素显示和工作是否正常）。
  • 跨浏览器测试（不同浏览器下一致性和兼容性）、数据驱动测试（用 CSV、Excel 这类数据文件驱动，验证不同输入下的表现）也都算。
  • 配套组件：Selenium WebDriver 直接跟浏览器交互、点按钮输文本、支持 Chrome、Firefox、Safari；Selenium Grid 多浏览器多系统并行跑、提效，大项目跨环境回归常用；Selenium IDE 是浏览器插件、快速录制回放、做原型。
  • Page Object Model（POM） 是维护性设计模式，把每个页面当对象、封装元素和操作方法，降耦合、好维护。
  • TestNG/JUnit 配合 Selenium 能做套件管理、并行、数据驱动；CI/CD 接 Jenkins、GitHub Actions 跑流水线。

📈 拔高

  • 五类测试不是平铺的，功能测试和回归测试是基本盘，数据驱动测试是提覆盖率的手段，跨浏览器测试才真正用到 Grid 的价值。
  • POM 配合数据驱动，一套脚本能喂不同数据，维护成本降一大截，比堆脚本划算。

💡 主动加分的追问准备

面试官追问 你的答案
数据驱动测试在 Selenium 里怎么做？ 使用数据文件（如 CSV 或 Excel）驱动测试，以验证应用程序在不同输入数据下的表现。Selenium 结合 TestNG/JUnit 这类测试框架可以实现数据驱动测试等更高级的功能。
Selenium Grid 解决什么问题？ 它允许在多个浏览器和操作系统上并行运行测试，极大提高测试效率，特别适合大型项目中需要在不同环境下进行回归测试的场景。
POM 在 Selenium 项目里为什么重要？ Page Object Model 是把每个页面封成一个对象，元素和操作都放进去，降低耦合、好维护。

❌ 千万别说的话

  • “Selenium 支持的测试类型就是功能测试和回归测试。” 它还支持 UI 测试、跨浏览器测试，以及用数据文件（如 CSV 或 Excel）驱动的数据驱动测试，一共五类。
  • “Selenium IDE 是个执行引擎。” 它是一种浏览器插件，用于快速录制和回放测试脚本，适合快速生成测试脚本或者做测试用例的原型设计；真正直接与浏览器交互的是 Selenium WebDriver。

6. 什么是 Selenium？

7. Selenium 的工作原理是什么？

🎬 面试现场

面试官（口语化）：你敲一行 click，Selenium 到底怎么让浏览器真的点下去的？

⚠️ 翻车点

最容易漏掉的是「解析指令」这一环：脚本并不是直接指挥浏览器，而是 Selenium 客户端先与浏览器驱动程序（WebDriver）通信，把指令转换成浏览器能理解的命令。另一个坑是把 ChromeDriver、GeckoDriver 说成「Selenium 的浏览器」——它们是中间人，负责把脚本指令传给浏览器并拿回执行结果。

📝 回答重点

  • 工作原理我按四步说：发送指令（脚本发出点按钮、输文本这类命令）→ 解析指令（Selenium 客户端跟浏览器驱动程序通信、把指令翻译成浏览器能懂的命令）→ 执行操作（浏览器真执行）。
  • 反馈结果（驱动把结果传回客户端、脚本拿去验证）。关键在解析指令这环：脚本不是直接指挥浏览器，得先跟驱动过一遍，这是 WebDriver 的中间人角色。ChromeDriver 管 Chrome、GeckoDriver 管火狐，都是中间人。
  • 组件分工：WebDriver 跑现代浏览器跨浏览器测试、给浏览器接口；IDE 录制回放、适合回归和新手；Grid 并行、把测试摊到多台机器。
  • 大项目里 Grid 多浏览器多系统并行很重要，接 Jenkins、GitHub Actions 能提交后自动跑。元素找不到、超时这类异常要靠等待机制（显式等待、隐式等待）来减少。

📈 拔高

  • 面试最容易被追问的就是指令到底发给谁：不是直接发给浏览器，是先发给驱动、翻译成浏览器命令再执行。这条答错整个原理就塌了。
  • 等待机制选型是高频追问：显式等待等条件（如元素可见）更精准，隐式等待是傻等固定时间容易慢，能用显式等待就别用隐式。

8. Selenium 2 和 Selenium 1 的区别是什么？

  • 版本演进得讲全：Selenium 2 = RC + WebDriver 合并；Selenium 3 起推动 W3C WebDriver 标准化；Selenium 4 完全移除 JSON Wire Protocol、全面转 W3C，还加了 relative locators（相对定位器）和 Chrome DevTools Protocol（CDP） 原生支持。

10. 什么是 UI 自动化测试？

🎬 面试现场

面试官（口语化）：UI 自动化测试到底是什么？它和接口测试、单元测试是什么关系？

⚠️ 翻车点

容易答窄的是只说”用脚本点按钮”，漏掉它的定位——UI 自动化测试本质上是使用编程的方式来模拟用户操作，自动化地测试和验证用户界面（User Interface）是否按照预期工作，并且它适用于检查各种 UI 元素，如按钮、输入框、菜单等，确保这些元素在不同浏览器或平台上的表现一致。另一个坑是把 UI 自动化当成万能的，忘了它较为缓慢、不适合覆盖所有测试场景，实际项目中通常与单元测试、API 测试结合使用。

📝 回答重点

  • 用编程的方式模拟用户操作，自动测和验证界面（User Interface）是不是按预期工作，查按钮、输入框、菜单这些元素在不同浏览器或平台上表现是否一致、合不合要求。
  • 优势是效率高、省手工、少人为错误，尤其频繁回归的场景，脚本写一次能反复跑，省时间人力，还保证不同设备浏览器一致。
  • 常用工具：Selenium（开源、多语言、多浏览器）、Cypress（现代前端、快、稳、体验友好）、Appium（移动端、Android 和 iOS 都行）、TestCafe（好上手、直接在浏览器里跑测试代码）。
  • 最佳实践：分层测试（UI 只管交互，业务逻辑和后台交给别的层）、数据驱动（不改代码、改数据覆盖更多用例、提覆盖率）、保持独立（每个用例不依赖别的用例执行结果，脚本才稳、可重用）。
  • 局限也得说：写和维护脚本要投开发资源、复杂交互难搞定、UI 测试偏慢、不适合覆盖所有场景，实际项目里跟单元测试、API 测试搭配用。

📈 拔高

  • 别把 UI 自动化当万能。它最值钱的是回归，最贵的是维护。页面一改版，脚本成片红。
  • 一个项目该不该上，看它稳不稳、变不变。早期需求天天改就别急着堆 UI 脚本，等页面稳了再动手更划算。

11. UI 自动化测试有哪些分类？

🎬 面试现场

面试官（口语化）：UI 自动化测试一般分哪几类？每类关注的点分别是什么？

⚠️ 翻车点

容易只报出五个名字却不讲各自侧重点。功能测试查功能模块是否按需求文档执行，回归测试验证代码变更后旧功能是否还正常，烟雾测试是快速验证基本功能的浅测试，兼容性测试确保在不同浏览器、操作系统和设备上运行一致，性能测试关注高负载下的表现与稳定性。另一个坑是把烟雾测试说成”跑全量用例”，它的定位恰恰是很短时间内提供早期反馈。

📝 回答重点

  • UI 自动化一般分五类：功能测试、回归测试、烟雾测试、兼容性测试、性能测试，各有侧重。
  • 功能测试最基础，查每个功能模块是不是按需求文档跑，脚本模拟用户操作找功能缺陷。
  • 回归测试是代码有改动或加了新功能时，确认老功能还正常、没引入新 bug，脚本能快速重复跑同一批用例、又快又准。
  • 烟雾测试是浅测，快速验基本功能能不能跑起来，短时间给早期反馈、逮重大问题。兼容性测试是保证在不同浏览器、操作系统、设备上一致运行，脚本在不同环境重复跑同一套用例。
  • 性能测试盯高负载下的反应和表现，UI 自动化里通常模拟大量用户操作，评估稳定性和性能。

📈 拔高

  • 五类不是并列关系：功能测试和回归测试是基本盘，烟雾测试是发版前快速体检，兼容性测试才用得上 Grid 跨环境，性能测试严格说不是 UI 自动化的强项。
  • 烟雾测试和回归测试别混。烟雾是「浅而快、看基本盘能不能起来」，回归是「改动后确认没坏旧功能」，深度和触发时机都不一样。

兼容性测试在 UI 自动化里怎么落地？ 就是在不同浏览器、系统、设备上把同一套用例重复跑，跑出来一致才算兼容。

面试前 10 分钟速查

Selenium 基础

  • 定义与组成：Selenium 是开源的自动化测试工具，用于自动化 Web 应用程序测试，由 Selenium WebDriver、Selenium IDE、Selenium Grid、Selenium RC 四部分组成，其中 RC 是旧版本、现已被 WebDriver 取代。
  • 工作原理四步：测试脚本发出指令 → Selenium 客户端与浏览器驱动程序通信、把指令转换成浏览器能理解的命令 → 浏览器执行命令模拟用户操作 → 驱动程序把执行结果返回给客户端供脚本断言验证。
  • 驱动是中间人：每个浏览器有对应驱动，ChromeDriver 对应谷歌浏览器、GeckoDriver 对应火狐浏览器，驱动只负责把脚本指令传给浏览器并取回执行结果，脚本指令并不直发浏览器。
  • WebDriver 五步链路：启动浏览器（创建 ChromeDriver、FirefoxDriver 实例）→ 用 By.id、By.name、By.xpath、By.cssSelector 定位元素 → 模拟 click、sendKeys、getText 操作 → 用断言验证结果 → 调用 quit() 或 close() 关闭浏览器，漏掉关闭步骤浏览器会一直挂着。
  • 定位策略：可用 By.id、By.name、By.xpath、By.cssSelector，旧版写法还有 find_element(By.ID, id)、find_elements(By.CLASS_NAME, class_name)、find_element(By.XPATH, xpath)，两版 API 都要照抄题块原写法。
  • WebDriver API 类型：ChromeDriver（Google Chrome）、FirefoxDriver（Mozilla Firefox）、EdgeDriver（Microsoft Edge）、InternetExplorerDriver（Internet Explorer）、SafariDriver（Safari）、OperaDriver（Opera），另有用于分布式测试、可远程控制不同浏览器的 RemoteWebDriver。
  • 分布式执行：RemoteWebDriver 可与 Selenium Grid 协作实现跨节点浏览器管理，写法为 webdriver.Remote(command_executor=’http://localhost:4444/wd/hub‘, desired_capabilities=DesiredCapabilities.CHROME)，可在多台机器并行执行以节省测试时间。
  • 版本匹配与排查：驱动版本不兼容、元素查找不到、浏览器窗口未响应是新手高频问题，需保证驱动与浏览器版本匹配，并开启 selenium.webdriver.remote.remote_connection 的 DEBUG 日志定位根源。
  • 支持语言：Java、Python、C#、JavaScript（特别是 Node.js）、Ruby、PHP；Java 是 Selenium 原生开发语言、强类型适合大规模项目但语法冗长，Python 简洁但大规模并发性能稍逊，Ruby 性能不如 Java 和 C#。
  • Selenium IDE：以插件形式运行在浏览器中（Firefox 和 Chrome），不需要编写代码，靠 GUI 录制按钮捕获用户操作生成脚本再回放；缺点是灵活性有限、对复杂场景和条件控制支持有限，且录制的脚本对 Web 页面布局变化敏感、后期维护麻烦。
  • 支持测试类型：功能测试、回归测试、UI 测试、跨浏览器测试、数据驱动测试五类；数据驱动用 CSV 或 Excel 等数据文件驱动测试，配合 TestNG、JUnit 可实现并行与套件管理。
  • 优缺点：优点是开源免费、社区资源丰富、支持多浏览器多语言、扩展性强；缺点是对动态 Web 页面和 AJAX 请求支持较弱、没有内置报告功能（需配合 TestNG、JUnit）、依赖浏览器与 WebDriver 版本兼容。
  • 版本演进：Selenium 2 引入 WebDriver API 取代 Selenium 1 基于 JavaScript 封装的 RC 服务器，直接通过浏览器本地兼容性接口通信以提升速度和稳定性；Selenium 1 是异步执行需要大量等待，Selenium 2 是同步执行。
  • 常用函数：click()、send_keys(keys)、get(url) 分别是模拟点击、输入文本、打开 URL；close() 只关闭当前标签页，quit() 关闭所有关联窗口并退出浏览器实例。
  • 等待机制：显式等待 WebDriverWait(driver, timeout).until(condition) 等条件成立（如元素可见），隐式等待 implicitly_wait(time) 等待指定时间后抛出 NoSuchElementException。
  • 弹窗与窗口：switch_to.alert 处理 alert、confirm、prompt，配合 accept()、dismiss()、send_keys()；多标签用 window_handles 取全部句柄、switch_to.window(handle) 切换，窗口控制还有 maximize_window()、minimize_window()、refresh()。
  • 其他常用函数：get_screenshot_as_file(filename) 截图保存，get_cookies()、add_cookie(cookie_dict)、delete_cookie(name) 操作 cookie，懒加载滚动用 driver.execute_script(“window.scrollTo(0, document.body.scrollHeight);”)。

UI 自动化基础

  • 定义：UI 自动化测试本质是用编程方式模拟用户操作，自动化测试并验证用户界面（User Interface）是否按预期工作，检查按钮、输入框、菜单等元素在不同浏览器或平台上的表现一致。
  • 五大分类：功能测试、回归测试、烟雾测试、兼容性测试、性能测试；烟雾测试是浅测试，目标是在很短的时间内提供早期反馈，而不是跑全量用例。
  • 优势：可重复执行相同用例，回归测试收益最高，能减少手工测试工作量与人为错误，并保证应用在不同设备与浏览器上表现一致。
  • 局限：编写与维护脚本需要投入开发资源，UI 测试通常较为缓慢、不适合覆盖所有测试场景，复杂的用户交互难以处理，实际项目中通常与单元测试、API 测试结合使用。
  • 最佳实践：分层测试（UI 测试专注用户交互，业务逻辑和后台交给其他层次）、数据驱动测试（不改代码只改数据以提高测试覆盖率）、保持独立性（用例不依赖其他用例的执行结果）。
  • 适合做的项目：页面结构和功能相对稳定、重复性高的测试需求多、投入与回报比较高、项目规模较大且复杂；需求未确定的早期研发阶段不适合一开始就做，因为脚本依赖 DOM 结构、页面频繁变动会让维护成本非常高。
  • 工具选择：Selenium（开源、多语言、多浏览器）、Cypress（现代前端测试工具，适合单页应用）、Appium（移动端，同时支持 Android 和 iOS）、TestCafe（Web 框架，可直接在浏览器中运行测试代码）。
  • 优缺点：优点是提高效率与准确性、提高覆盖率、可集成 CI/CD；缺点是开发维护成本高、不适合很复杂的 UI 交互、需要编程与框架知识、无法完全替代手工测试（体验性、感知性测试仍需人工）。
  • 来源与维护成本：手动测试在功能复杂后变得费时费力、易出错、难覆盖全部场景，自动化测试由此出现；脚本初次编写耗时耗力，但建立后只需在需求变化或 UI 变动时少量维护，UI 异常变动导致脚本失效时通常要结合手工测试。

UI 自动化落地

  • 八步流程：需求分析 → 测试环境准备 → 工具选择 → 编写测试脚本 → 执行测试 → 结果分析 → 缺陷管理 → 回归测试；缺陷管理要跟踪修复直到解决所有问题，回归测试要在修复后重跑脚本确认没有引入新问题。
  • 环境准备：搭建与生产环境相似的测试环境，包含操作系统、浏览器、应用程序等，并保证数据库、网络环境等配套资源一致性，否则结果不可靠。
  • 需求与工具：常见需求文档是 PRD（产品需求文档）和 FRD（功能需求文档）；工具选型看兼容性、开源程度、社区支持和学习曲线，Selenium 用于 Web 应用测试、Appium 用于移动应用测试。
  • 报告与缺陷工具：报告用 Allure、ExtentReports 生成并逐条描述失败项，缺陷用 JIRA、Bugzilla 记录和跟踪状态，CI 执行可用 Jenkins 接入 DevOps 流水线。
  • 环境搭建七步：选框架（Selenium、Appium、Cypress）→ 装编辑器（Visual Studio Code、PyCharm）→ 配运行环境（Python 环境、Node.js）→ 搭浏览器驱动（Chrome 对应 chromedriver、Firefox 对应 geckodriver、Internet Explorer 对应 IEDriverServer）→ 接 Git → 设 Jenkins 等 CI/CD → 配 Allure 或 ExtentReports 报告。
  • 依赖安装：Selenium 用 pip 安装（pip install selenium），Cypress 用 npm 安装（npm install cypress –save-dev），代码提交用 git clone、git commit、git push。
  • 覆盖率验证六步：收集需求和功能点 → 列出覆盖所有功能点的测试用例 → 把人工用例转成自动化脚本 → 执行 → 生成覆盖率报告（JUnit、TestNG 结合 Jacoco 等代码覆盖率工具）→ 分析未覆盖部分并补充用例和脚本。
  • 用例多样性：除主路径和正常场景外还要覆盖边界条件、异常处理和负面测试，例如表单提交除了正常输入，还要测空输入、非法字符；需求溯源可用 Jira、Trello 跟踪需求变化与版本管理。
  • 报告与工具集成：报告不只看覆盖率，还要关注失败用例并分析是脚本问题还是应用问题；Jenkins 可定时持续运行并生成报告，配合 Docker 容器保证环境一致性和隔离性。

框架设计

  • 建框架五步：选工具框架 → 设计测试架构 → 编写高质量脚本 → 接入 CI/CD → 建立报告与反馈；工具按场景选，Selenium 适合 Web 测试、Appium 适合移动应用、TestNG 或 JUnit 适合 Java 单元测试。
  • 架构模块：测试架构至少包含测试用例模块、测试数据模块、报告生成模块、日志模块，保证脚本的维护性和可扩展性；只装好 Selenium 写一批脚本只是用例，不是框架。
  • 设计模式：采用 Page Object Model (POM) 模式，把页面元素和行为封装在类中，UI 更改只需在一个地方更新，提高脚本复用性与可维护性，可配合 SOLID 等面向对象原则增强健壮性。
  • 避免硬编码：用数据驱动和关键字驱动编写脚本，测试数据放 JSON、Excel 等数据文件并配配置文件，同时用注释、文档和定期代码审查提升可读性。
  • 用例设计十步：明确测试目标 → 理解被测系统 → 选工具 → 设计用例（覆盖常见用户场景和边缘情况）→ 数据准备（输入数据与预期输出数据）→ 编写脚本 → 设置与生产一致的环境 → 执行并与预期结果对比 → 分析结果并生成报告 → 定期自动化维护。
  • 配套能力：用 POM 提高用例可读性与可维护性，用 Jenkins、GitHub Actions、Travis CI 等把测试接入 CI/CD 流水线，用 Git 管理测试脚本并与开发代码同步，按项目场景组合白盒测试、黑盒测试、回归测试等策略。
