1. 常用的移动应用自动化测试工具有哪些？

🎬 面试现场

面试官（口语化）：移动端自动化测试常用哪些工具？挑一个说说它的特点。

⚠️ 翻车点

四个名字必须记准：Appium、Espresso、Robotium、XCUITest，并说清归属——Espresso 是 Google 提供的 Android UI 测试工具，XCUITest 是 Apple 提供的 iOS 测试框架且集成在 Xcode 中，Robotium 是早期的 Android 测试框架，Appium 是开源跨平台工具。别把 Espresso 和 Robotium 的定位说反：Espresso 快、适合频繁执行单元测试、集成 Android Studio；Robotium 偏用户体验的自动化测试，跨平台跨版本兼容性不如其他工具。

📝 现场作答

  • 常用的移动应用自动化测试工具包括：Appium、Espresso、Robotium、XCUITest。
  • Appium：Appium 是一个开源自动化工具，支持在 Android 和 iOS 平台上对原生、混合和移动网页应用进行自动化测试。它使用 WebDriver 协议，与 Selenium 类似，可以用多种编程语言进行编写，如 Java、Python、JavaScript 等。它的一个优势在于无需修改应用的源代码。Appium 支持多语言客户端库和多平台，具有丰富的社区支持；如果有基于 Selenium 的自动化测试背景，转向 Appium 会相对轻松。此外，它的理念是“不重新发明轮子”，只需一次编写代码便能在不同平台上运行。
  • Espresso：这是 Google 提供的 Android UI 测试工具。Espresso 简单易用，速度快，特别适合需要频繁执行单元测试的开发场景。它与 Android Studio 集成度高，可以直接在开发环境中进行调试和执行，使得测试过程更顺畅。Espresso 利用同步机制极大减少了 flaky 测试，即测试中的不确定性问题，提供了稳定和可重复的测试环境；同时，结合 Android Test Orchestrator 使用，可以并行执行测试，提高测试效率。
  • Robotium：这是一个早期的 Android 测试框架，它允许对 Android 的原生和混合应用程序进行自动化黑盒测试。Robotium 更偏向于用户体验的自动化测试，简化了复杂的测试用例的编写。它的缺陷之一是在跨平台和跨版本的兼容性不如其他工具；虽然不像 Espresso 那样得到 Google 的官方支持，但它的轻量级特性使得它在某些特定场景下依旧实用，适用于简单的 UI 测试。
  • XCUITest：这是 Apple 提供的 iOS 测试框架，集成在 Xcode 中，专为 iOS 应用开发环境设计。其优点在于速度快，特别适合 CI/CD 环境，可以方便地在设备和模拟器上运行测试。得益于 Apple 官方的支持，XCUITest 对 iOS 更新和新特性具有较好的支持和兼容性；如果应用只针对 iOS 平台，XCUITest 是首选。此外，它与 Swift 和 Objective-C 有很好的适配性，测试代码可以直接集成到项目中。

面试官追问 你的答案
Appium 相比 Selenium 的优势是什么？ Appium 支持在 Android 和 iOS 平台上对原生、混合和移动网页应用进行自动化测试，使用 WebDriver 协议，与 Selenium 类似，可以用 Java、Python、JavaScript 等多种编程语言编写；它的理念是“不重新发明轮子”，只需一次编写代码便能在不同平台上运行，且无需修改应用的源代码。

  • “Robotium 现在是 Google 官方首推的 Android UI 框架。” —— Robotium 不像 Espresso 那样得到 Google 的官方支持。

2. 简述 Appium 的原理？

🎬 面试现场

面试官（口语化）：Appium 到底是怎么跨平台控制手机的？说一下原理。

⚠️ 翻车点

讲不清中间那层转译。Appium Server 不是把命令直接丢给设备：它先把测试请求转译为对应移动设备的原生自动化命令，再通过平台指定的自动化引擎（如 UIAutomator2 for Android 或 XCUITest for iOS）发送到实际设备上执行，设备执行完把结果返回 Appium Server，Server 再把结果传回客户端。另外 Android 侧有两个引擎名别混：主流程里用的是 UIAutomator2 for Android，而在「无须修改应用」那一条里提到的是 UIAutomator for Android。

📝 现场作答

  • Appium 是一个开源的自动化测试工具，主要用于移动应用程序的测试。它的核心原理是通过 WebDriver 协议，以跨平台的方式实现对 Android 和 iOS 应用程序的自动化测试。具体步骤如下：
    1）Appium Server 启动并接收客户端发送的测试请求。
    2）Appium Server 将测试请求转译为对应移动设备的原生自动化命令。
    3）通过平台指定的自动化引擎（如 UIAutomator2 for Android 或 XCUITest for iOS），发送命令到实际的移动设备上执行。
    4）移动设备执行这些自动化命令后，将执行结果返回给 Appium Server。
    5）最后，Appium Server 再将这些结果传回给客户端。
  • 跨平台兼容性：Appium 支持编写一次测试代码，然后在不同的平台（iOS 和 Android）上运行，不需要为每个平台单独编写自动化测试脚本，只需一次编写，测试脚本即可在多种设备和操作系统上执行。
  • 支持多种应用类型：Appium 不仅支持原生应用（Native App），还支持混合应用（Hybrid App）和移动浏览器应用（Mobile Web App）。原生应用是指那些使用 iOS 或 Android SDK 开发的应用，混合应用则使用了 WebView 组件在内嵌网页中显示内容，移动浏览器应用指的是在移动设备浏览器上运行的网页应用。
  • 无须修改应用：与一些其他测试工具不同，Appium 不需要重新编译或修改移动应用，它通过使用官方自动化框架（如 UIAutomator for Android 和 XCUITest for iOS）来直接与应用程序交互。
  • 多语言支持：Appium 支持多种编程语言，如 Java、Python、JavaScript、Ruby、C# 等。这主要是因为 Appium 使用 WebDriver API，而 WebDriver 又有许多现成的客户端绑定，可以用不同的语言编写测试脚本。
  • 开源与社区支持：由于 Appium 是开源的，因此它有很强的社区支持，丰富的插件和扩展可以帮助你更好地实现自动化测试，可以很方便地找到相关资料、教程以及解决方案。
  • 并行测试：使用 Appium，可以在多个设备上并行运行测试，从而提高测试效率和覆盖范围，这对大规模的回归测试尤其有帮助。

3. 使用 Appium 可能遇到的错误有哪些？

🎬 面试现场

面试官（口语化）：用 Appium 跑测试，最常碰到哪些报错？怎么排查？

⚠️ 翻车点

要能说清五类错误各自的根因，而不是笼统说「环境问题」。最典型的是元素定位失败：定位策略不正确（如 ID、XPath 等），排查时可以用 Appium 自带的 Inspector 工具查看 UI 元素的属性，并尽量避免使用 XPath 这种较为复杂的定位方法，优先使用 ID 或 CSS 选择器等性能更好的方法。还有人爱用 Thread.sleep()，更合适的做法是用显式等待（例如 WebDriverWait）来等待特定元素出现。

📝 现场作答

  • 使用 Appium 进行移动端自动化测试时，可能遇到以下一些常见错误：
    1）环境配置错误：这是最常见的问题，包括 Appium Server、Android SDK 或 Xcode 的路径未正确配置。
    2）设备连接问题：设备未正确连接或未被识别，通常是由驱动程序问题或设备授权引起的。
    3）元素定位失败：无法找到或互动特定的 UI 元素，可能是因为定位策略不正确（如 ID、XPath 等）。
    4）超时错误：测试脚本等待某个元素或操作过久而超时，可能是网络延迟或设备性能问题导致的。
    5）Appium 版本不兼容：Appium 的不同版本或者与特定的移动操作系统版本不兼容，可能导致脚本无法运行。
  • 环境配置错误：确保所有路径的环境变量都已正确设置，例如在命令行中运行 adb devices 来确认 Android 设备是否被识别。
  • 设备连接问题：使用 adb devices 确认设备连接状态；检查设备的调试模式是否已开启；确保驱动程序已经安装并且是最新的。
  • 元素定位失败：使用 Appium 自带的 Inspector 工具来查看 UI 元素的属性；尽量避免使用 XPath 这种较为复杂的定位方法，优先使用 ID 或 CSS 选择器等性能更好的方法；考虑添加延迟或者等待机制，比如显式等待或隐式等待。
  • 超时错误：使用显式等待（例如 WebDriverWait）来等待特定元素出现，而不是使用 Thread.sleep()；优化你的应用加载时间和减小网络延迟的影响。
  • Appium 版本不兼容：定期检查和更新 Appium 以及相关依赖库的版本；检查 Appium 官方文档获取关于版本兼容性的最新信息；在项目中使用版本控制，确保每个人使用一致的环境和依赖项。

4. 需要一台服务器来运行 Appium 上的测试吗？

🎬 面试现场

面试官（口语化）：跑 Appium 测试是不是必须自己搞一台服务器？

⚠️ 翻车点

这题不能答成「必须」。Appium 不一定需要一台独立的服务器来运行测试，本地环境也可以搭建 Appium Server 并进行测试。真正的取舍在并发规模与多设备多平台大规模测试上：这时候用一台专用服务器更具优势。答“必须”会被直接否掉；答“完全不用”也忽略了大规模回归场景。另外要注意区分三个层次：本地环境搭建、使用专用服务器、远程执行（Selenium Grid 或配合云服务如 AWS Device Farm、BrowserStack）。

📝 现场作答

  • Appium 不一定需要一台独立的服务器来运行测试。本地环境也可以搭建 Appium Server 并进行测试。然而在某些情况下使用一台专用服务器可能更具优势，特别是当需要并发运行多个测试或者希望在多设备、多平台上进行大规模测试时。换句话说，Appium Server 可以在本地机器上运行，但为了优化性能和管理复杂的测试任务，使用一台独立的服务器会更加理想。
  • 本地环境搭建：
    • 优点：方便开发者在本地调试和运行测试；不需要额外的硬件投资；简单的设置过程即可启动测试。
    • 缺点：受到本地计算资源的限制，不能大规模并发运行测试；配置稍有变化本地环境可能会受到影响。
  • 使用专用服务器：
    • 优点：更强大的计算资源，可以支持并行和大规模测试；集中管理测试环境，配置一致且易于维护；更好的稳定性和可扩展性。
    • 缺点：需要额外的硬件资源和维护成本；需要配置网络和安全设置，可能增加复杂性。
  • 远程执行：配置一台专门的服务器，通过远程连接来运行和管理测试。例如，通过 Selenium Grid 或者 Appium Server 配合云服务（如 AWS Device Farm、BrowserStack 等），可以实现跨多个设备和平台的并发测试。
  • CI/CD 集成：在 DevOps 流程中，自动化测试至关重要。将 Appium Server 部署在专门的测试服务器上，可以与持续集成和持续交付（CI/CD）系统（如 Jenkins、GitLab CI）无缝集成，实现自动化测试和构建。
  • 实例：假如一支开发团队需要每天运行数千个移动端测试用例，并且这些用例需要在多种设备、不同操作系统版本上执行，显然本地机器无法满足需求，此时就非常有必要在专用的服务器集群上部署 Appium Server，并通过合适的调度和管理工具（例如 Kubernetes）来协调这些测试任务。

5. 有哪些 Android UI 自动化测试工具？

🎬 面试现场

面试官（口语化）：Android UI 自动化有哪些工具？各自什么定位？

⚠️ 翻车点

五个名字和定位要分清：Espresso（谷歌官方，集成在 Android Testing Support Library 内部，支持同步测试）、UI Automator（谷歌推出，支持跨应用测试）、Appium（开源跨平台）、Robotium（开源黑盒 UI 框架）、MonkeyRunner（Android SDK 自带，适用于功能测试和回归测试）。最容易搞混的是 MonkeyRunner 与前两者：不同于 UI Automator 和 Espresso，MonkeyRunner 是在设备（或模拟器）上操作整个应用的。

📝 现场作答

最容易只答「断言失败就停，验证失败继续」——方向对，但答得太浅。关键差别是失败后的行为：断言用于检查程序某个特定点的状态是否符合预期，一旦失败测试立即中止并报告错误；验证则是在测试过程中持续检查程序状态，即使某个验证失败测试也会尽可能继续执行，并在最后汇总所有的错误——一次运行里能发现更多错误。第二个坑是不会按场景选：断言通常用于关键操作和前置条件检查，验证一般用于后置检查和非关键操作。第三个坑是分不清测试层级：单元测试中断言更常见，集成测试和系统测试中验证更有用。

  • 优势有三条：
    1. 可维护性：页面变了只改对应的页面类，不用动所有测试用例；

    3. 复用性：页面类和操作方法能在不同测试用例间复用，减少重复代码。

    1. 前期投入大：要在前期投入时间做页面类设计和元素定位；

16. 有哪些生成自动化测试报告的方式？

只答一句「用 Allure」是最容易翻车的说法——面试官接下来会问「那框架自带的报告呢」「CI 上怎么自动发出来」，答不上来就露怯。另一个坑是把「工具自带报告」和「第三方报告工具」混为一谈：前者是框架内建的、后者是外挂集成的，层次不同。另外很多人知道怎么生成报告，却答不出报告里该有哪些东西。

📝 现场作答

  • 生成自动化测试报告主要有四种方式：
    1. 使用测试框架自带的报告功能：很多常见测试框架如 JUnit、TestNG 提供了内置的报告生成功能，能在测试运行后生成基本的测试报告；
    2. 第三方报告生成工具：一些专业工具可以跟测试框架集成，生成更美观、更详细的报告，例如 Allure、ExtentReports；
    3. 结合 CI/CD 工具：将测试与持续集成/持续部署工具结合，通过这些工具自动化生成并发布测试报告，常见的有 Jenkins、Bamboo，通常都有丰富的插件支持；
    4. 自定义脚本：针对特定需求编写自己的脚本，通过解析测试日志文件生成定制化报告，常见日志格式有 XML、JSON 等，这些格式易于解析和处理。
  • 各类工具的具体形态：
    • JUnit & TestNG：JUnit 是广泛使用的 Java 测试框架，它的 mvn surefire-report:report 命令可以生成简单的 HTML 格式报告；TestNG 比 JUnit 功能更丰富、自带的报告功能更强大，通过 test-output 目录中的 index.html 文件可以查看报告。
    • Allure：全称 Allure Framework，是一个灵活轻量级的多语言测试报告工具，适用于 JUnit、TestNG、JUnit5 等多种测试框架，通过解析测试结果文件生成可视化、交互式报告；优势是报告布局清晰、交互性强，能展示详细的测试执行信息。
    • ExtentReports：适用于 Selenium、Appium 等测试框架的报告生成工具，能创建详细的、可定制的 HTML 报告，包括截图、步骤详情、系统信息等；优势是容易集成到不同测试框架，报告视觉效果好，能满足高级展示需求。
    • CI/CD 工具：Jenkins 是最流行的 CI/CD 工具之一，通过插件（如 JUnit Plugin、Allure Plugin 等）可以自动生成并发布测试报告；Bamboo 是 Atlassian 推出的 CI/CD 工具，也支持自动生成测试报告，并与 JIRA 等工具集成。
    • 自定义报告工具：基于日志或结果文件（如 XML、JSON）编写脚本，把测试执行结果解析后生成报告。例如用 Python 的 xml.etree.ElementTree 模块解析 JUnit 格式的 XML 文件再生成 HTML 报告，或者用报告生成库如 ReportLab 生成 PDF 格式报告。

📝 现场作答

  • POM（Page Object Model）是一种用于自动化测试的设计模式，主要是将页面中的元素及其操作封装成对象，以提高代码的可维护性和可重用性。在 POM 模型中，通常将项目划分为以下几个模块：

    2）测试用例模块（Test Cases）：把所有测试用例放在这个模块里，每个测试用例都会调用页面模块中的方法来进行特定的操作及验证结果。
    3）配置模块（Configuration）：存放所有的配置文件，比如浏览器配置、测试环境的 URL 等。
    4）数据驱动模块（Data Provider）：包含测试数据，数据驱动的测试可以从这里读取不同的数据集。
    5）辅助模块（Helpers/Utilities）：存放一些公共的辅助类和方法，比如等待元素出现的方法、截图的方法等。
  • 实际工作中常常还会涉及一些额外但非常有用的实践和工具：
    1）使用工厂模式（Factory Pattern）：有些项目会结合工厂模式来动态生成页面对象实例，这样当页面变化时，只需要更改工厂类，而不是每个测试用例。
    2）借助框架（Frameworks）：通常会配合一些自动化测试框架，比如 Selenium，和测试框架，如 TestNG 或者 JUnit，来更好地组织和运行测试用例。
    3）持续集成（CI）：将自动化测试集成到 CI/CD 流程中，像 Jenkins，可以保障测试的及时执行和反馈，提升敏捷开发的效率。
    4）日志和报告（Logging & Reporting）：采用日志机制和自动化测试报告工具，如 Allure Report，可以帮助快速定位错误，提高测试的有效性和透明度。

24. 如何在自动化测试中破解验证码？

🎬 面试现场

面试官（口语化）：我们登录流程有图形验证码，自动化跑不过去，你打算怎么解决？

⚠️ 翻车点

最容易被扣分的是上来就写 OCR 图像识别——实际上大多数情况下禁用验证码和使用测试账户才是最简单且安全的选择，因为不涉及复杂的图像处理过程，并且可以确保自动化测试的稳定性。把打码平台和 OCR 当首选方案，等于绕开了正解。另外打码平台是要花钱的，还有响应时间问题，别只讲好处。

📝 现场作答

  • 在自动化测试中，验证码往往是一个难点，因为验证码的设计目的是防止自动化，因此需要找到一些巧妙的方式来绕过它。破解验证码有几种常见的方式：
    1）禁用验证码：在测试环境中，通过配置后端或者获取特殊权限，使验证码在测试环境中失效。
    2）使用测试账户：创建专门的测试账户，这些账户在应用中被标记为不需要输入验证码。
    3）打码平台：使用第三方打码平台或服务，将验证码图片发送到该平台，由人工或机器进行识别并返回结果。
    4）图像处理：使用图像处理和 OCR（Optical Character Recognition）技术自动识别验证码。
  • 大多数情况下，使用第一和第二种方法会是最简单且安全的选择，因为它们不会涉及到复杂的图像处理过程，并且可以确保自动化测试的稳定性。
  • 禁用验证码：如果有对代码或测试环境的控制权，可以在开发或测试配置中禁用验证码，例如某些框架或应用允许在开发环境下跳过验证码验证；也可以修改后台逻辑，在测试阶段在后端代码中加一个判断，如果是测试环境就跳过验证码的验证步骤。
  • 使用测试账户：专门创建几个无验证码的测试账户，并在测试脚本中使用这些账户进行测试；创建时可以和开发团队沟通，确保这些账户始终不会需要验证码。
  • 打码平台：有些打码平台如 2Captcha 或 DeathByCaptcha，可以通过 API 提供验证码识别服务。这些平台通常支持图片验证码和部分复杂的验证码识别，但会存在一些费用和响应时间的考虑。编写脚本时可以使用这些平台的 API，将验证码图片上传并获取识别结果，从而在脚本中自动填写验证码。
  • 图像处理与 OCR：对于一些相对简单的验证码，可以使用 Python 的 pytesseract 库结合 OpenCV 进行图像预处理和文本识别。图像预处理包括去除噪点、二值化处理、形态学操作等，增加识别的准确率。

25. Web 自动化测试中，有哪些常用的库？

🎬 面试现场

面试官（口语化）：Web 自动化这块你都用什么工具？能说说这几个库各自什么脾气、什么场景用哪个吗？

⚠️ 翻车点

最容易翻车的是「报菜名」：一口气念五个库名就停住，面试官追问「Puppeteer 和 Playwright 到底差在哪」「Cypress 适合什么项目」就答不上来。第二个坑是把工具名和适用场景对错——把 Playwright 说成只支持 Chrome（那是 Puppeteer 的短板），把 Cypress 说成需要额外装 WebDriver。第三个坑是只讲优点不讲边界：TestCafe 不依赖 WebDriver 等第三方工具、Playwright 支持所有主流浏览器，这些优势要连着各自的适用场景一起说，才是真懂。

📝 现场作答

常用的 Web 自动化测试库，主要是下面这五个：

  1. Selenium：这是目前最流行的 Web 自动化测试框架之一，支持多种编程语言，包括 Java、Python、C# 等。它可以模拟用户行为进行浏览器操作。
  2. Cypress：这是一个现代的 Web 测试框架，它集成了许多便捷的功能，特别适用于前端开发中的 E2E 测试，基于 JavaScript 构建。
  3. Puppeteer：这是 Google 为 Chrome 开发的无头浏览器工具，基于 Node.js，主要用于 Web 端自动化测试和数据爬取。
  4. TestCafe：这也是一个基于 JavaScript 的自动化测试工具，不需要其他的 Web 驱动程序或者服务，可以直接运行在所有主流的浏览器中。
  5. Playwright：这是由微软开发的类似于 Puppeteer 的工具，但它支持多种浏览器，包括 Chromium、Firefox 和 WebKit。

每个库的特点和应用场景：

  • Selenium：特点是具有强大的浏览器兼容性，支持多种编程语言，且生态系统十分成熟；它可以与 TestNG、JUnit 等测试框架整合，用于开发复杂的测试流程。应用场景是适用于需要跨浏览器测试、多语言支持、要求高度定制化的复杂项目。
  • Cypress：特点是快速、稳定、高性能，而且调试非常方便；它采用了基于 DOM 的模型，操作直观且错误信息丰富，非常适合前端开发者使用。应用场景是前端项目的 E2E 测试的理想选择，尤其是使用 JavaScript/TypeScript 开发的项目。
  • Puppeteer：特点是专注于 Chrome 和 Chromium 的无头浏览器操作，具有高度的稳定性和性能，非常适合页面内容抓取、生成 PDF 截屏等操作。应用场景是单一浏览器环境的任务，如数据抓取、网页操作模拟、自动化截图、生成网页 PDF 等。
  • TestCafe：特点是不依赖 WebDriver 等第三方工具，易于上手且免去了许多兼容性问题，能够在多种浏览器中运行，并且它自动管理测试缓存，确保独立测试环境。应用场景是特别适合快速开发和运行 Web 端集成测试，尤其在需要同时兼容多浏览器的情况下。
  • Playwright：特点是弥补了 Puppeteer 仅支持 Chrome 的不足，它支持所有主流浏览器，还提供了丰富的 API，测试性能和稳定性极佳。应用场景是适用于需要跨浏览器测试，但又希望保持高性能和高度可控的项目。

面试前 10 分钟速查

Appium

  • 移动端自动化四大工具：Appium（开源跨平台）、Espresso（Google 提供的 Android UI 测试工具）、Robotium（早期的 Android 测试框架）、XCUITest（Apple 提供的 iOS 测试框架，集成在 Xcode 中）。
  • 只有 Appium 是跨平台开源工具：Espresso 快、适合频繁执行单元测试、与 Android Studio 集成度高；Robotium 偏用户体验的自动化测试，跨平台跨版本兼容性不如其他工具；只针对 iOS 时 XCUITest 是首选。
  • Appium 的能力边界：用 WebDriver 协议控制原生应用、混合应用和移动浏览器应用，无需修改应用源代码，可用 Java、Python、JavaScript、Ruby、C# 等多语言编写。
  • Appium 的五步链路：Server 启动并接收请求 → 把请求转译为对应移动设备的原生自动化命令 → 经 UIAutomator2 for Android 或 XCUITest for iOS 下发到设备 → 设备执行后把结果返回 Server → Server 再把结果传回客户端。
  • Appium 不必配专用服务器：本地环境同样可以搭建 Appium Server 并测试；但并发跑多个测试、或要在多设备多平台上做大规模测试时，专用服务器在算力、集中管理和稳定性上更有优势。
  • 远程与集群执行：通过 Selenium Grid，或 Appium Server 配合 AWS Device Farm、BrowserStack 等云服务做跨设备并发；CI/CD 场景把 Appium Server 部署在专门的测试服务器上，接 Jenkins、GitLab CI。
  • 五类常见错误：环境配置错误（Appium Server、Android SDK 或 Xcode 的路径未正确配置）、设备连接问题、元素定位失败、超时错误、Appium 版本不兼容。
  • 元素定位失败的排查：用 Appium 自带的 Inspector 工具查看 UI 元素的属性；尽量避免使用 XPath 这种较复杂的定位方法，优先使用 ID 或 CSS 选择器等性能更好的方法。
  • **等待策略别用 Thread.sleep()**：用显式等待（例如 WebDriverWait）等待特定元素出现来避免超时错误，同时优化应用加载时间、减小网络延迟的影响。
  • 设备连不上怎么查：用 adb devices 确认设备连接状态，检查设备的调试模式是否已开启，确保驱动程序已安装且是最新版本。
  • Android UI 工具定位：Espresso 集成在 Android Testing Support Library 内部、支持同步测试；UI Automator 支持跨应用测试；Robotium 是开源黑盒 UI 框架；MonkeyRunner 是 Android SDK 自带工具，不同于 UI Automator 和 Espresso，它是在设备（或模拟器）上操作整个应用的。
  • 其他 Android 工具：Selendroid 面向未修改的本地和混合应用、写法类似 Selenium；Calabash 跨平台、用 Cucumber 风格的自然语言脚本；TestComplete 是商业化但跨平台、支持桌面 Web 和移动应用。

  • 登录场景六项覆盖：验证输入有效性（长度、字符类型）、错误提示、登录成功并跳转到相应界面、网络状态、多种设备与操作系统版本的兼容性、SQL 注入与暴力破解等安全性。
  • 网络状态要分四种：无网络、弱网络、Wi-Fi 和移动数据下都要跑一遍登录。
  • 登录侧的性能与体验：评估登录操作的响应时间、CPU、内存使用情况，可用 Firebase Performance、Android Profiler、Xcode Instruments；错误提示要清晰明确，用户能快速看懂并修正。
  • 登录的安全检查：检查登录数据传输是否使用了加密的通信方式，比如 HTTPS；并做 SQL 注入、暴力破解等常见安全测试。
  • Monkey 属于自动化测试：它是专门用于 Android 应用的自动化测试工具，模拟用户的点击、滑动、触摸、文本输入等操作，特别适合 App 的稳定性和耐久性测试。
  • Monkey 命令：adb shell monkey -p your.package.name -v 1000，其中 -p your.package.name 指定应用包名，-v 指定详细日志级别，1000 为要生成的事件数量。
  • Monkey 的三大局限：事件随机生成、无法复现某个特定 Bug；缺乏精确定位和操作顺序，不适合细致业务流程的自动测试；不进行具体逻辑验证，捕不到所有类型的 Bug，尤其是功能性缺陷。
  • Monkey 优势：命令行方式简单易用、覆盖面广、速度快，一般每秒可生成数个到数十个事件。
  • 稳定性测试四步：安装并准备好需要测试的 APK → 连接设备或启动模拟器并确保处于调试模式 → 输入 Monkey 命令启动测试（如 adb shell monkey -p your.package.name -v 5000，5000 为事件数量）→ 分析输出日志寻找异常和崩溃点。
  • Monkey 高级参数：–throttle 500 在每个事件之间添加 500ms 的延时、–ignore-crashes 忽略应用崩溃继续发送事件、–monitor-native-crashes 监控并报告本地层次的崩溃、–pct-touch 50 设置 50% 的触摸事件比例；-v 可以指定多个 v 来增加详细程度。
  • Monkey 日志分析：重点关注日志中的异常信息，如 ANR（应用无响应）和崩溃（Force Close）；用 adb logcat > monkey_log.txt 把日志保存到文件里便于后续分析。
  • Monkey 不能替代手工稳定性测试：它的事件是随机的、覆盖率不可控，做完基本 Monkey 测试后还要手工做极限操作、用专门的测试脚本；应用有权限需求时需手动授予权限或配置 Monkey 处理。
  • 性能测试六步：需求分析 → 设计测试方案（确定环境、工具、数据、用例）→ 在接近真实的条件下建立测试环境 → 执行测试 → 监控并收集数据 → 分析数据并写报告、提优化建议。
  • 性能指标五类：响应时间、处理能力、吞吐量、资源使用情况（如 CPU、内存、电池等）、稳定性（如崩溃率、错误率等）。
  • 三款工具定位：JMeter 主要用于负载测试和性能测试、开源免费、支持 HTTP、FTP、JDBC 等协议；LoadRunner 用于检测系统在高负荷下的表现、是商业化软件且成本较高；Appium 主要用于移动端应用的功能和性能自动化测试、基于 WebDriver 协议可集成进 CI/CD 流程。
  • 性能测试最佳实践：在实际网络条件、多种设备型号和操作系统中模拟真实环境；测试期间甚至生产环境都持续监控；按「发现问题—解决问题—再次测试—再次优化」持续迭代；除常规负载测试外还要做极高负载下的极限测试。

断言与持续集成

  • 断言与验证的核心差别：断言检查某个特定点的状态是否符合预期，一旦失败测试立即中止并报告错误；验证持续检查程序状态，即使某个验证失败也尽可能继续执行、最后汇总所有错误，一次运行能发现更多错误。
  • 按场景选：断言用于关键操作和前置条件检查（如登入页面是否正确加载），验证用于后置检查和非关键操作；单元测试多用断言，集成测试和系统测试多用验证。
  • Selenium 本身不提供断言：断言由测试框架处理，如 JUnit、TestNG（针对 Java）、PyTest、Unittest（针对 Python）；Selenium 更侧重浏览器自动化操作。
  • 常见断言方法：assertTrue(condition) 断言条件为真、assertFalse(condition) 断言条件为假、assertEqual(a, b) 断言两者相等、assertNotEqual(a, b) 断言两者不相等、assertIn(a, b) 断言 a 是否在 b 中，Java 侧还有 assertNull、assertNotNull。
  • Web 断言两种写法：用 assert 关键字做简单断言（如 assert “Welcome” in driver.title），或用 unittest 模块中的断言方法（如 self.assertIn(“Welcome”, driver.title)）。
  • 动态内容先等再断言：元素尚未加载完就断言会莫名其妙失败，用显式等待（Explicit Waits）确保元素加载后再断言，例如 WebDriverWait(driver, 10).until(EC.presence_of_element_located((By.ID, ‘myDynamicElement’)))。
  • 断言实践：单个测试用例里不要放过多断言；尽量避免一个断言里包含多个不同条件，让单条断言失败后更容易定位；失败时带上自定义错误消息（如 self.assertEqual(a, b, msg=”a 和 b 应该相等”)）。
  • 断言的价值：能检测代码中的潜在问题，使代码在不同开发阶段都符合预期行为，对持续集成和持续部署环境尤其关键。
  • 持续测试工具链六件套：Jenkins（流水线，靠 Selenium Plugin、Parameterized Trigger Plugin 等插件集成）、TestNG（并行测试、测试配置，注解机制设依赖关系）、Allure（报告，需配置适配器 Adapter 才能生成 HTML 报告）、Maven/Gradle（依赖管理与构建自动化）、Docker（容器化，官方提供 Selenium Grid 镜像）、BrowserStack（跨浏览器真实环境，通过 REST API 集成）。
  • 报告要配合断言看：JUnit、TestNG 都提供丰富的断言功能，再结合日志和报告工具如 Allure Report，才能全面展示测试结果。

PO 模型与测试报告

  • PO 模式是什么：PO 全称 Page Object 模式（Page Object Model，简称 POM），是自动化测试里的一个设计模式，把页面元素和对元素的操作抽象成对象，让测试代码更清晰、可维护、可重用。
  • PO 的三件套：页面类（Page Class）、页面元素（Web Elements）、操作方法（Actions）三者配套，缺一个就退化成单纯的定位器集中管理，不是真正的 PO。
  • POM 的完整形态：每个页面对应一个对象，把该页面的 UI 元素和操作方法一起封装，通过定义页面类的方法来模拟用户的操作，而不只是把定位器集中到一个类里。
  • POM 落地示例：为登录页建 LoginPage 类，用 By.id(“username”)、By.id(“password”)、By.id(“loginButton”) 定位元素，并封装 enterUsername、enterPassword、clickLoginButton 这类方法，任何需要登录的用例都能复用。
  • POM 的四条优势：提高代码可维护性（改页面只改对应类文件）、代码复用性高、易于理解和管理、减少代码冗余（操作封装成方法，减少硬编码）；通常配合 TestNG 或 JUnit 使用，还能与 Cucumber 等 BDD 工具结合。
  • PageFactory 能省事：Selenium WebDriver 提供了 PageFactory 类，能更简洁地实现 POM，甚至可以自动初始化页面上的元素。
  • PO 的代价：前期投入大（页面类设计和元素定位要提前做），且需要良好的面向对象设计能力，保证页面类结构合理、便于扩展。
  • PO 不限于 Web：移动应用自动化测试框架如 Appium 同样可以采用 PO 模式；PO 通常结合 Selenium、pytest 这类测试框架一起用。
  • POM 的五个模块：页面模块（Page Objects）、测试用例模块（Test Cases）、配置模块（Configuration，放浏览器配置和测试环境 URL）、数据驱动模块（Data Provider）、辅助模块（Helpers/Utilities，放等待元素出现、截图等公共方法）。
  • 工厂模式解耦页面变化：用工厂模式（Factory Pattern）动态生成页面对象实例，页面变化时只需更改工厂类，而不是每个测试用例；再用 Selenium 加 TestNG 或 JUnit 组织运行，用 Jenkins 做持续集成，用 Allure Report 做日志与报告。
  • 四类模块封装：测试用例模块、测试数据模块、测试工具模块、测试报告模块；封装目的是实现功能复用、降低代码耦合度、便于团队协作和管理。
  • 测试数据要独立成模块：通过数据驱动测试把测试数据放到外部文件（如 Excel、CSV、JSON）中，实现测试数据与测试脚本分离，改动数据更方便，还能用不同数据做批量测试。
  • 测试工具与报告模块：数据库连接模块、HTTP 请求模块、文件处理模块等通用功能写成工具模块直接调用；把测试结果统计和报告生成逻辑封装成模块，统一报告格式和内容。
  • 封装目的五点：提高代码重用性、提高代码可维护性、减少代码耦合度、便于团队协作开发、增强代码可读性和可理解性。
  • Web 自动化闭环六环节：测试需求分析、测试用例设计、测试脚本编写、测试执行、结果分析和报告、问题跟踪和回归测试（发现问题后跟踪，修复后回归）。
  • 闭环的目的：确保测试过程全面、细致、不遗漏任何细节，确保系统的稳定性和可靠性，并通过闭环持续改进测试流程，提高自动化测试的效率和精准度。
  • 闭环之外还要补：工具选择（Selenium、Cypress、Puppeteer）、测试环境与生产环境保持一致（用 Docker 等容器技术管理）、CI/CD 流水线集成（Jenkins、GitLab CI）、随机测试和探索性测试，以及 JMeter、LoadRunner 做性能测试等非功能性测试。
  • 生成报告有四条路：测试框架自带报告、第三方报告工具、结合 CI/CD 工具自动生成发布、基于日志或结果文件写自定义脚本。
  • 框架自带报告：JUnit 可用 mvn surefire-report:report 生成简单的 HTML 报告；TestNG 自带报告更丰富，通过 test-output 目录中的 index.html 查看。
  • 第三方报告工具：Allure（Allure Framework）是灵活轻量级的多语言报告工具，适用于 JUnit、TestNG、JUnit5，优势是布局清晰、交互性强；ExtentReports 适用于 Selenium、Appium，能生成含截图、步骤详情、系统信息的可定制 HTML 报告。
  • CI 上自动发报告：用 Jenkins、Bamboo 这类 CI/CD 工具配合插件（如 JUnit Plugin、Allure Plugin）自动生成并发布报告，Bamboo 还能与 JIRA 集成。
  • 自定义报告脚本：解析结构化的日志或结果文件（如 XML、JSON）再生成报告，例如用 Python 的 xml.etree.ElementTree 模块解析 JUnit 格式的 XML 生成 HTML，或用 ReportLab 生成 PDF。
  • 选工具的八个点：易用性、兼容性和支持的技术、社区与支持、可扩展性、成本、集成能力、性能与稳定性、报告与分析能力。
  • 选工具要结合团队现状：编程能力强的团队适合 Selenium、Appium 这类要写代码的工具，新手适合 TestProject、Katalon Studio 这类无代码或低代码工具；规模大、逻辑复杂的项目需要 Robot Framework 这类能处理复杂场景的工具，小项目选轻量工具。
  • 还要算落地成本：优先复用团队已熟悉的工具以减少学习成本，并考虑未来发展——可扩展性、维护性，以及能否跟上测试管理、CI/CD、DevOps 的趋势。
  • 分析报告的六个动作：看用例执行情况、分析失败用例、确认测试覆盖率、看性能指标、查日志和截图、做历史趋势对比。
  • 失败根因分三类：环境问题（环境不稳、资源竞争）、数据问题（数据不完整或被污染）、代码变更，先排这三类再下代码有问题的结论。
  • 通过的用例也要复盘：要确认通过用例是否完全覆盖预期功能，哪怕通过也可能遗漏边缘场景，不能只看通过率。
  • 性能报告看的是 KPI：响应时间、并发用户数、资源消耗，以及吞吐量、延迟时间、错误率、CPU/内存使用情况，而不是单纯的通过或失败。
  • CI/CD 里报告更重要：要详细检查构建版本、部署环境、依赖更新这些可能的诱因，报告与流水线紧密集成能更快反馈和修复问题。
  • 自动发邮件的七项内容：发件人地址、收件人地址、邮件主题、邮件正文、附件、抄送地址（CC）、密送地址（BCC，BCC 不会显示其他收件人的地址）。
  • 自动发信的三条路径：用 Python 的 smtplib 配合 email 库走 SMTP 服务；配置 Gmail SMTP、Outlook SMTP 等邮件服务器地址、端口与认证信息；或用 SendGrid、Mailgun 等第三方服务提供的 API 接口。
  • 发信注意事项：准确填写地址避免发错人；确保正文和附件编码正确避免乱码；邮箱密码用配置文件或环境变量管理，不要在代码里直接暴露；注意各服务商的附件大小限制；不要频繁发送大量相似邮件，避免被当成垃圾邮件。
  • 邮件模板：用 HTML + CSS 设计模板提升效率和一致性，模板中用占位符和变量由程序动态替换，生成个性化邮件。

工具与杂项

  • 验证码在自动化里是难点：验证码的设计目的就是防止自动化，所以要靠”巧妙的方式”绕过，常见做法有四种：禁用验证码、使用测试账户、打码平台、图像处理加 OCR 识别。
  • 首选是禁用验证码或测试账户：在测试环境配置后端、获取特殊权限让验证码失效，或创建被标记为不需要输入验证码的专门测试账户；这两种最简单也最安全，不涉及复杂的图像处理过程，还能确保自动化测试的稳定性。
  • 打码平台是第三选择：把验证码图片发送到第三方打码平台或服务，由人工或机器识别并返回结果；常见平台如 2Captcha、DeathByCaptcha 通过 API 提供识别服务，但要考虑费用和响应时间。
  • OCR 路线的关键是图像预处理：用 Python 的 pytesseract 库结合 OpenCV，先做去除噪点、二值化处理、形态学操作再识别，以增加识别的准确率。
  • Web 自动化的常用库有五个：Selenium（最流行的框架之一，支持 Java、Python、C# 等多种语言）、Cypress（现代 Web 测试框架，基于 JavaScript 构建，适合前端 E2E）、Puppeteer（Google 为 Chrome 开发的无头浏览器工具，基于 Node.js）、TestCafe（基于 JavaScript，不需要额外的 Web 驱动或服务）、Playwright（微软开发，支持 Chromium、Firefox 和 WebKit）。
  • Selenium 的适用场景：浏览器兼容性强大、多语言支持、生态成熟，可与 TestNG、JUnit 等测试框架整合开发复杂测试流程，适合需要跨浏览器测试、多语言支持、要求高度定制化的复杂项目。
  • Cypress 的适用场景：快速、稳定、高性能、调试方便，基于 DOM 的模型操作直观、错误信息丰富，是前端项目 E2E 测试的理想选择，尤其是 JavaScript/TypeScript 项目。
  • Puppeteer 的适用场景：专注 Chrome 和 Chromium 的无头浏览器操作，稳定性和性能高，适合页面内容抓取、生成 PDF 截屏，以及数据抓取、网页操作模拟、自动化截图等单一浏览器环境的任务。
  • TestCafe 的适用场景：不依赖 WebDriver 等第三方工具，免去许多兼容性问题，能在多种浏览器中运行并自动管理测试缓存，适合快速开发和运行 Web 端集成测试。
  • Playwright 的适用场景：弥补了 Puppeteer 仅支持 Chrome 的不足，支持所有主流浏览器，API 丰富、性能和稳定性极佳，适合既要跨浏览器又要高性能和高度可控的项目。
