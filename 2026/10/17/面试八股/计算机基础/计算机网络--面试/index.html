为什么网络题值得单独背

后端面试里，网络是唯一一块「不背就一定答不上、背了就一定答得上」的科目。

操作系统那类题需要你真跑过、踩过坑；网络不一样——它的答案是确定的、公开的、面试官会一条一条往下抠。TCP 三次握手为什么是三次、滑动窗口两个值取哪个、0-RTT 有什么风险，这些问题没有模糊空间，答错就是错。

更关键的是网络题的追问链特别长。你说”HTTP/2 解决了队头阻塞”，面试官立刻接”哪一层的？”；你说”用 JWT 无状态”，他立刻接”怎么撤销？”——能不能接住第二问，才是区分背过和理解的分水岭。

所以这篇不给你第四十份知识点罗列，而是把 37 道高频题还原成真实的面试现场：每道题都是「面试官怎么问 → 你第一反应会怎么翻车 → 正确答法 → 追问怎么接」。

怎么用这篇：不要背「现场作答」，要背「翻车点」。面试时最容易失分的从来不是不知道，而是知道自己不知道却硬答。考前扫翻车点，性价比最高。

一、HTTP 与协议演进

[1] HTTP 1.0 和 2.0 有什么区别？

🎬 面试现场

面试官：HTTP 从 1.0 演进到 2.0，中间到底解决了哪些问题？你给我捋一遍演进主线。

⚠️ 翻车点

  • 把版本差异说成”新版本功能更多”，讲不出每一步分别在解决什么痛点。
  • 认为 HTTP/1.1 的 Pipeline 已经解决了队头阻塞（实际上响应仍要按序回来，等于没解决）。
  • 说 HTTP/2 靠多路复用就完全没有队头阻塞了（TCP 层的队头阻塞依然存在）。

📝 回答重点

  • 拿到这题分两段答：1.0 到 1.1 治连接成本，1.1 到 2.0 治传输效率，每一步都要能说出治的是什么病。
  • 1.1 的杀手锏是 Keep-Alive 长连接默认开，多个请求复用同一条 TCP，另外加了 Host 头，虚拟主机才成为可能。
  • HTTP/2 升级四件套：多路复用、二进制分帧、HPACK 压缩、服务端推送，Chrome 106 起默认关掉推送，主力就剩前三样。
  • HPACK 两端各维护索引表，重复 Header 只发索引号，Huffman 单独省三成上下，总收益看请求里重复头部多少。
  • HTTP/2 只拆掉了应用层的队头阻塞，TCP 丢一包所有流都得等，这层要到 HTTP/3 换 QUIC 才真正拆掉。

📈 拔高

现在按 2026 年 11 月 W3Techs 口径：HTTP/3 站点占 41.2% 已反超 HTTP/2 的 35.1%，HTTP/1.1 退到剩余份额，旧的 40%、60% 说法过时了。

💡 主动加分的追问准备

追问 答案
HTTP/2 的多路复用解决了 HTTP 层的队头阻塞，为什么还会有 TCP 层的队头阻塞？ 多路复用是在应用层把请求打散成帧乱序发送，但底下跑的还是一条 TCP 连接。TCP 有序传输，帧 2 丢了会卡住等它重传，后面先到的帧 3 也得排队。这是 TCP 协议本身的特性，应用层搞不定。
能简单讲讲 HTTP 的历史演进吗？ 1989 年伯纳斯-李提出 URI/HTML/HTTP 三个概念（即 HTTP/0.9，只有 GET、无请求头）。1996 年正式发布 HTTP/1.0，加入 HEAD/POST、状态码、头部和 Content-Type。1997 年 HTTP/1.1 首次记录于 RFC 2068，1999 年发布 RFC 2616，2014 年拆成 RFC7230–RFC7235 六份文档。2015 年发布 HTTP/2。2018 年 IETF 把 HTTP over QUIC 更名为 HTTP/3。
HTTP 为什么一开始设计成文本协议、只有 GET？ 1989 年互联网初期算力和网速都很弱，Tim Berners-Lee 的想法是文档存在服务器里，只需要从服务器获取文档，所以只有 GET、不需要请求头、拿完就断。

❌ 千万别说的话

  • “HTTP/1.1 的 Pipeline 已经实现了并行请求，所以队头阻塞解决了。” ：Pipeline 兼容性极差几乎没人用，响应仍按序返回。
  • “HTTP/2 完全没有队头阻塞问题。” ：TCP 层的问题被掩盖，不是被消灭。

[2] HTTP 2.0 和 3.0 有什么区别？

🎬 面试现场

面试官：HTTP/2 和 HTTP/3 最核心的差别在哪？为什么现在有人开始上 HTTP/3 了？

⚠️ 翻车点

  • 只答”HTTP/3 更快”，说不出底层从 TCP 换成了 UDP + QUIC。
  • 以为 HTTP/2 的队头阻塞被彻底解决了（TCP 层还在）。
  • 把 0-RTT 说成”任何时候建连都是 0 RTT”（首次建连做不到）。

📝 回答重点

  • 核心差别在传输层：HTTP/2 跑 TCP，HTTP/3 跑 UDP 上的 QUIC，丢包从卡住全部流变成只卡丢的那条流。
  • 建连要两三个 RTT，QUIC 把传输握手和 TLS 1.3 握手合成一次，老用户 resumption 可以 0-RTT，首次建连做不到。
  • 连接迁移靠 Connection ID，换了 IP 只要 ID 没变连接就不掉，TCP 靠四元组识别，Wi-Fi 切 4G 必断。
  • 头部压缩从 HPACK 换 QPACK，静态表从 61 项扩到 99 项，动态表更新走独立单向流，包乱序也不卡解析。
  • QUIC 的 Packet Number 单调递增，重传也发新号，接收端能分清新包和重传，RTT 估算更准。
  • 铺得慢是因为 UDP 常被运营商限速、防火墙不开 443 UDP，而且加解密都在用户态，服务端 CPU 开销更高。

📈 拔高

QUIC 把 TCP 的可靠传输在应用层重写了一遍，拥塞控制想换就换，发个新版本 App 就行，TCP 改一行要全球几十亿设备配合，这是它敢做连接迁移和加密包号的底气。

💡 主动加分的追问准备

追问 答案
UDP 明明不可靠，为什么能做 HTTP/3 的基础？ QUIC 并不依赖 UDP 的任何特性，它在应用层重新实现了一遍 TCP 的核心功能：序列号 + ACK 保证不丢，滑动窗口 + 拥塞控制保证不堵。区别在于 TCP 在内核里改动极难，而 QUIC 在应用层，想怎么改就怎么改。
QUIC 的重传机制和 TCP 有什么不同？ TCP 重传用相同的序列号，接收端无法区分新包还是重传包，RTT 估算容易出错。QUIC 每个包都用单调递增的 Packet Number，哪怕是重传数据 Packet Number 也是新的，接收端能精确判断，RTT 计算更准、拥塞控制反馈更及时。
0-RTT 有什么安全风险？ 0-RTT 数据没有前向保密性，用的是上次会话的密钥，攻击者录下包、日后拿到服务器私钥就能解密历史数据。它还有重放问题，服务端分不清真请求还是重放。所以 0-RTT 只放幂等请求，POST 有副作用的不能进。
HPACK 具体怎么工作？ 维护两张表：静态表（协议写死，如 Index 2 代表 method: GET）和动态表（通话过程中运行时建立，新 Header 加入表，后续只发索引号，如”我叫张三，是程序员”记为 Index 62，下次只说”我是 62”）。
为什么 QPACK 要单独开一条单向流传动态表？ HPACK 极度依赖顺序，包 1（定义 Index 62）丢了而包 2（引用 Index 62）到了，应用层解析就失败阻塞。QPACK 用 Encoder/Decoder Streams 单独传更新指令，用 Known Received Count 判断索引是否已确认，未确认就直接发字面量、不查表。
HTTP/3 普及率为什么还不如 HTTP/2？ UDP 常被运营商限速甚至丢弃，企业防火墙默认不开 UDP 443。QUIC 协议复杂，服务端实现难度和 CPU 开销更高（加解密与拥塞控制在用户态），老负载均衡、WAF、CDN 支持不足。但 Cloudflare、Google、Facebook 已全面铺开。
QUIC 能连接迁移，TCP 为什么加不了？ TCP 是内核协议，改动要兼容全球几十亿设备，四元组识别连接定死了三四十年。加 Connection ID 字段要求所有中间设备、操作系统升级，根本推不动。QUIC 在应用层跑，服务端和客户端统一升级就行。

❌ 千万别说的话

  • “HTTP/3 只是把 HTTP/2 的版本号改了一下，协议基本没变。” ：底层传输层整个换了。
  • “HTTP/3 首次建连也是 0 RTT。” ：只有之前已经握过手（Connection ID 已生成）才有 0-RTT。

[3] 常见的 HTTP 状态码有哪些？

🎬 面试现场

面试官：HTTP 状态码分几类？200、301、304、403、502 你分别什么时候用？说说你的选择逻辑。

⚠️ 翻车点

  • 把状态码叫”错误码”，只想到 4xx、5xx，忽略 2xx、3xx 也在表达处理状态。
  • 分不清 301 和 302 的语义差别，只会答”都能跳转”。
  • 用 400 一把梭，出错时全部返回 400 / 500。

📝 回答重点

  • 先说结构：状态码是三位数，首位 1 到 5 分五类，IANA 到 2025 年 9 月共注册 64 个，可用范围 100 到 599。
  • 2xx 是成功：200 带 body，204 成功但没有 body，206 配合 Range 断点续传，响应里带着 Content-Range。
  • 3xx 管跳转和缓存：301 永久、302 临时，都用 Location 指新地址，307 允许跳但不许把 POST 改成 GET。
  • 304 专管缓存，配合 If-Modified-Since 用，意思是缓存还是新的，服务器不用重发 body。
  • 4xx 是请求侧的问题：403 是服务器明确禁止，404 是没找到，409 像并发冲突，429 限流，400 含糊尽量少用。
  • 5xx 是服务端的锅：500 通用错误别把堆栈甩出去，502 是网关正常但后端出错，503 过载维护可以带 Retry-After。

📈 拔高

状态码是开放集合，Nginx 和自研系统都扩过私有码，面试里把 301、302、307、304 的语义边界讲清，比背全几十个码更能拿分。

💡 主动加分的追问准备

追问 答案
301 和 302 到底差在哪？ 都用 Location 字段跳转、浏览器都会重定向，区别在语义：一个”永久”，一个”临时”。网站升级到 HTTPS、原 HTTP 不再使用，配 301。夜间维护、服务暂时不可用，配 302，浏览器知道是暂时情况、不做缓存优化，第二天还会访问原地址。
403 和 404 有什么区别？ 403 不是客户端请求出错，是服务器明确禁止访问，body 里说明原因更好。404 原意是资源在本服务器上未找到，但现在被用滥了，服务器不高兴也给 404，客户端无从判断真未找到还是别的原因。
304 Not Modified 是重定向吗？ 它没有通常的跳转含义，用于 If-Modified-Since 等条件请求表示资源未修改，主要用于缓存控制，可以理解成”重定向到已缓存的文件”。
状态码是谁的责任？ 是双方共同责任。客户端据状态码判断是否重发请求、错因是什么。服务端应选择最恰当的状态码，出错时尽量不要简单地返回 400、500 这种意思含糊的码。

❌ 千万别说的话

  • “4xx 除了 404 剩下的都是 500。” 或者”后端随便报什么都返回 400/500。” ：语义含糊会浪费排障时间。
  • “状态码就是错误码，只有 4xx、5xx 才是状态码。” ：2xx、3xx 同样在表达处理状态。

[4] HTTP 请求包含哪些内容，请求头和请求体有哪些类型？

🎬 面试现场

面试官：一笔 HTTP 请求报文由哪几部分组成？首部字段分几类？

⚠️ 翻车点

  • 把请求报文和响应报文的组成混着说（请求行 vs 状态行）。
  • 只会说”有请求头有请求体”，说不出首部字段的四大分类。
  • 说不清 Cookie 和 Session 的配合流程，只说”Session 存在服务端”。

📝 回答重点

  • 请求报文四段：请求行放方法、路径、版本，接着请求头、空行、请求体，GET 基本没有请求体，POST 的数据都在最后那段。
  • 方法记九个：GET、HEAD、POST、PUT、PATCH、DELETE、OPTIONS、CONNECT、TRACE，HEAD 只回头部，PUT 整体替换，PATCH 部分修改。
  • 首部字段分四类：通用、请求、响应、实体，Host 算请求首部，Content-Length 和 Content-Type 归实体首部。
  • Cookie 和 Session 配合：登录成功服务端把用户数据存起来，用 Set-Cookie 把 Session ID 发给浏览器，之后每个请求带着这个 ID 来认人。
  • 缓存控制看 Cache-Control：no-store 一点不许存，no-cache 是先回源验证再用，max-age 定存活秒数，Expires 是绝对时间的旧方案。
  • 压缩靠 Accept-Encoding 协商，浏览器列出支持的算法，服务端挑一种压完，用 Content-Encoding 回告选了哪种。

📈 拔高

追问一般落在细节区分：no-cache 先回源验证再用，PUT 负责整体替换，PATCH 只动一部分，把这两组对比讲清基本就稳了。

💡 主动加分的追问准备

追问 答案
Cookie 到底解决了什么问题？ HTTP 是无状态协议，HTTP/1.1 用 Cookie 保存状态：服务器发到浏览器，后续请求携带，告知服务端是否来自同一浏览器。常见用途是会话管理（登录状态、购物车、游戏分数）、个性化设置、行为跟踪。
缓存怎么做、优势是什么？ 两条路：让代理服务器缓存，或让浏览器缓存。优势是缓解服务器压力、降低客户端获取资源的延迟，通过 Cache-Control 和 Expires 控制。
PUT 和 PATCH 到底差在哪？ PUT 只能完全替代原始资源，PATCH 允许部分修改。
Cache-Control 的 no-cache 和 no-store 有区别吗？ no-store 是禁止缓存。no-cache 不是不缓存，而是强制确认：缓存服务器要先向源服务器验证资源有效性，有效才拿来响应客户端。

❌ 千万别说的话

  • “HTTP/1.0 也能用 Keep-Alive 长连接，所以两者没区别。” ：1.0 需显式声明且默认短连接，1.1 才默认长连接。
  • “Session 就是存在 Cookie 里的。” ：Session ID 在 Cookie 里，用户数据在服务端。

[5] HTTP 和 HTTPS 有什么区别？

🎬 面试现场

面试官：HTTPS 到底解决了 HTTP 的哪几个风险？TLS 握手四次都发了什么？为什么证书要搞一层层的链？

⚠️ 翻车点

  • 只答”HTTP 明文、HTTPS 加密”，说不出窃听、篡改、冒充三类风险。
  • 把 TLS 握手说成”三次”，实际是四次通信。
  • 说”HTTPS 也不安全，有中间人攻击”——把用户点”继续访问”和协议漏洞混为一谈。

📝 回答重点

  • HTTPS 就是 HTTP 外面套一层 TLS，端口 80 变 443，它治三种风险：窃听、篡改、冒充，对应加密、校验、证书三套手段。
  • 加密用混合方案：握手阶段用非对称加密交换会话密钥，之后通信用对称加密，因为对称快，非对称只负责把密钥安全递过去。
  • 证书治冒充：CA 用自己私钥给网站公钥签名，客户端拿内置 CA 公钥解开、比对哈希，对得上才可信，对不上浏览器就弹警告。
  • 以 TLS 1.2 为例握手四次通信：ClientHello、ServerHello 带证书、客户端验证后送 pre-master key、服务器回结束通知，三个随机数共同生成会话密钥。
  • 根证书离线保管不直接签网站，由中间 CA 逐级往下签，客户端从叶证书验到根，根一失守整条链都不可信。
  • HTTPS 挡不住用户强点浏览器警告，也挡不住电脑被植入根证书，那是客户端沦陷，不能拿它否认协议。

📈 拔高

TLS 1.3 把握手压到 1-RTT，配合会话恢复还能 0-RTT，QUIC 干脆把这层搬进传输层，讲 HTTPS 时带上这条演进线。

💡 主动加分的追问准备

追问 答案
HTTPS 一定能保证安全吗？ 不能绝对保证。前提是用户在证书警告页点了浏览，接受伪造证书，或电脑中毒被导入中间人根证书。这都是客户端沦陷，不是协议漏洞。中间人与两端各握手一次拿两把密钥，在中间解密再转发。
HTTPS 的应用数据怎么保证完整性？ 靠 TLS 记录协议：压缩片段后附加 MAC（哈希生成）用于完整性校验和数据认证，计算 MAC 时加入片段编码防重放，再加密、加报头。
为什么根证书不直接签发网站证书，非要搞中间层？ 为了确保根证书的绝对安全性，把根证书隔离得越严格越好。根证书一旦失守，整条信任链都会出问题。
客户端具体怎么校验证书？ 用同样的 Hash 算法算出 H1，用内置 CA 公钥解密 Certificate Signature 得到 H2，两者相等则证书可信。若签发者是中间 CA，就按签发者字段找到它、要来中间证书，逐级验到预载的根证书为止。

❌ 千万别说的话

  • “HTTPS 有中间人攻击，所以 HTTPS 并不安全。” ：前提是用户接受伪造证书或本机被植入根证书，是客户端问题。
  • “HTTPS 是三次握手。” ：TCP 三次握手之后还有 TLS 四次通信，别把两者混成三次。

[6] HTTP 中 GET 和 POST 的区别是什么？

🎬 面试现场

面试官：GET 和 POST 到底差在哪？别跟我说”参数位置不同”就完了，说说本质和实际开发里怎么选。

⚠️ 翻车点

  • 只答”GET 参数在 URL、POST 参数在请求体”，把表面差异当本质。
  • 说”POST 比 GET 安全，因为参数在 body 里”。
  • 说”GET 不能带请求体”（协议上其实允许）。
  • 说”GET 天然带缓存”（准确说是 GET 响应默认可缓存）。

📝 回答重点

  • 本质区别就一句：GET 是读，协议上安全、幂等，服务器状态不动。POST 是写，非幂等，会改状态。
  • 长度限制别赖协议：Chrome 约 2MB，Nginx 默认请求行 8KB，Tomcat 的 maxPostSize 默认 2MiB 还只管表单。
  • GET 带请求体协议不禁止，但浏览器忽略、服务器直接拒，真要传复杂数据用 POST。
  • 安全差别不在方法：明文下 GET 的 URL 和 POST 的 body 都抓得到，靠 HTTPS 才行。
  • 简单请求有条件：GET 不带自定义头、或只带白名单头才免预检，带 Authorization 照样先发 OPTIONS。
  • “查用 GET、写用 POST”是工程习惯，REST 正统用 PUT/PATCH/DELETE 表达修改，别当规范背。

📈 拔高

方法语义写在 RFC 9110 里，长度上限却是浏览器和服务器各自的产品决定，换个配置就变。缓存行为也归这层管：GET 响应默认进浏览器缓存，POST 想缓存得自己配缓存头。

💡 主动加分的追问准备

追问 答案
为什么说 GET 安全、POST 非安全？ 安全性指请求不会改服务器端资源。GET 只拉数据没有副作用，POST 提交数据会产生副作用，比如新增用户、扣减库存。这是 HTTP 协议的官方定义。
GET 的长度限制到底是多少？ 协议没规定长度，限制来自浏览器和服务器：Chrome 约 2MB，Nginx 默认请求行 8KB，Tomcat 的 maxPostSize 默认 2MiB 且只管表单参数。
规范的 RESTful API 怎么划分方法？ GET 查询资源，POST 新增资源，PUT 全量更新资源，DELETE 删除资源，PATCH 局部更新资源。
为什么密码这类敏感数据即使加密也不该用 GET？ 即使加了 HTTPS，敏感数据拼在 URL 里仍会被记进服务器访问日志、浏览器历史和 Referer，而且浏览器默认缓存 GET 响应，容易落到磁盘缓存。

❌ 千万别说的话

  • “POST 因为参数在请求体里所以比 GET 安全。” ：明文传输下抓包同样可见，安全靠 HTTPS。
  • “GET 的长度限制是 HTTP 协议规定的。” ：协议从没这么规定，限制来自浏览器/服务器配置。

大量 WebSocket 连接怎么做负载均衡？ 长连接不能每跳换机器，一般在握手阶段用 Nginx 或 HAProxy 做一次负载均衡，建连后就粘在那台后端。Nginx 要配 ip_hash 或 sticky session，更大规模换 Kong、APISIX 这类网关。
长轮询和 SSE 比 WebSocket 差在哪？ 都是单向的：长轮询每条消息仍要一次 HTTP 往返，SSE 只能服务器推、客户端发消息还得走普通 HTTP，且 IE 不支持。WebSocket 是双向的，实时性和服务器压力都更好。

❌ 千万别说的话

  • “WebSocket 就是把 HTTP 的长连接拿来用。” ：它是协议升级（101 Switching Protocols）后在同一条 TCP 连接上换了应用层协议。
  • “WebSocket 断线会自动重连，浏览器已经处理了。” ：协议没有内置重连，必须自己实现。

Content-Length 和实际请求体长度不一致会怎样？ 比实际小会截断后面的数据，甚至污染下一个请求。比实际大则一直等到超时。两边解析不一致还能被做成 HTTP 走私，攻击者往里夹带请求。

HTTP/1.1 的 Keep-Alive 怎么工作？ HTTP/1.0 每个请求都新建连接，请求完就断。1.1 默认开 Keep-Alive，一连接发多个请求省掉握手。但 1.1 串行，前一个没收完后一个发不出，这就是队头阻塞。连接能保持多久看 Connection 和 Keep-Alive: timeout 头。
HTTP/2 的帧头 9 字节都是什么？ 帧头固定 9 字节，标明帧类型、长度和流 ID。HEADERS 帧放请求头，DATA 帧放请求体，多个请求可在同一连接上交错传输。

二、TCP 连接与可靠性

[9] 到底什么是 TCP 连接？

🎬 面试现场

面试官：很多人说 TCP 连接就是”两端拉了根线”，你给我讲讲，一条 TCP 连接到底是什么？

⚠️ 翻车点

  • 以为 TCP 连接是一根真实的物理线路、虚拟通道，或者一条独立的内核 socket 结构。
  • 把 Socket 直接等同于 TCP 连接，答不出”一个连接需要两个 Socket”的区别。

📝 回答重点

  • TCP 连接就是双方内存里维护的一套状态，叫 TCB：两端 Socket、状态机、收发缓冲区、重传队列、计时器都在里面。
  • Socket 只是通信端点，好比门牌号，一条连接要客户端和服务端两个 Socket 共同构成。
  • 唯一标识一条连接的是四元组：源 IP、源端口、目的 IP、目的端口，同机成千上万条连接全靠它区分。
  • 三次握手就是初始化这套状态：同步双方初始序列号 ISN，确认双向收发能力正常。
  • 序列号按字节编号，不按报文段。窗口大小写在首部，接收缓冲满了可通告 0 窗口关闭。
  • 发送窗口取 min(rwnd, cwnd)，也就是接收方通告窗口和自身拥塞窗口的较小值。

📈 拔高

Linux 下一条 ESTABLISHED 连接的 TCB 就是 tcp_sock 结构体，序列号空间、拥塞参数、重传定时器全挂在上面。它的内存占用跟着收发缓冲配置走，长连接数一多这块先吃紧。

💡 主动加分的追问准备

追问 答案
网线拔了连接还在吗？ 在。TCP 靠状态维护，拔线后只要双方不发数据，两边 TCB 仍是 ESTABLISHED。发数据超时或 Keep-Alive 探测失败后才销毁连接、释放 TCB。
服务器怎么发现客户端已挂？ 三种。服务端重传多次失败就判定断开。开 TCP Keep-Alive 默认 2 小时探一次太慢，生产上多在应用层做心跳，如 30 秒 ping 一次、3 次不响应断开。操作系统也会通知，如 Linux epoll 下网卡挂掉内核报 socket 出错。
三元组和四元组怎么区分？ 三元组 = IP + 端口 + 协议类型，如 192.168.1.1:8080 (TCP)，标识一个服务。四元组 = 源 IP + 源端口 + 目的 IP + 目的端口，唯一标识一条连接，如 192.168.1.100:50000 -> 192.168.1.1:80。
拔线后怎么让状态尽快收敛？ 应用层心跳比内核 Keep-Alive 更实用：内核默认 2 小时间隔太长，一个死连接要白占两小时 TCB 和文件描述符。

❌ 千万别说的话

  • ❌「TCP 连接就是客户端和服务器之间建立的一条物理链路 / 一根虚拟线路。」：它只是双方内存里的状态。
  • ❌「一个 Socket 就是一条 TCP 连接。」：一个 Socket 是一个端点，一条连接要两个 Socket。

[10] TCP 是用来解决什么问题？

🎬 面试现场

面试官：IP 层已经把包送到目的主机了，TCP 到底在上面多做了什么？你给我把机制说全。

⚠️ 翻车点

  • 把”可靠传输”只答成”有确认机制”，说不出超时重传、序号去重、缓冲区的配合关系。
  • 答不出确认号的两层含义（既表示已收到，也表示下次从哪发）。

📝 回答重点

  • IP 只管尽力送，TCP 把易丢易乱的包变成有序不重复的字节流，靠下面这套机制。
  • 确认应答按字节编号，确认号两层意思：这些我都收到了，下次请从这儿发。
  • 丢了就重传：超时间隔随次数变长，连续收到相同 ACK 还会快速重传，不用干等。
  • 滑动窗口定一次连发多少，流量控制按接收方缓冲压速率，拥塞控制按丢包猜容量，冲突取小。
  • 延迟应答先攒再回：RFC 1122 上限 500ms，常见收满 2 段或几十毫秒就回 ACK。
  • 重复数据不慌：ACK 丢了后续确认号会捎带进度，接收缓冲按序号去重，应用层读不到两份。

📈 拔高

超时丢包后窗口不会归零：RFC 5681 把 ssthresh 砍半、cwnd 重置为 1 SMSS 重新慢开始，下一轮再探带宽。延迟应答常和捎带应答凑一起，ACK 蹭着数据报走，四次挥手有时能并成三次。

💡 主动加分的追问准备

追问 答案
滑动窗口丢的是 ACK 包有影响吗？ 没有影响。后续应答报文里的确认号会告诉发送方”该序号之前的数据都已收到”，被丢的旧 ACK 是冗余的。
丢 TCP 数据报呢？ 有影响。缺 501–1000 时接收方反复要求从 501 开始，发送端连收相同 ACK 就快速重传。缺的段到达后先存进接收缓冲区，再按序正常应答。
滑动窗口的意义是什么？ TCP 为可靠牺牲了效率，滑动窗口补回一部分，即使用了它，效率依然不如 UDP。
拥塞控制的窗口变化规律？ 窗口小就指数涨，到 ssthresh 改成线性涨。超时丢包后 cwnd 回到 1 SMSS 重新慢开始，快速恢复则砍一半再线性涨。

❌ 千万别说的话

  • ❌「超时重传的时间间隔是固定的。」：它随重传次数变长，重传多次无果就放弃这条连接。
  • ❌「TCP 重复接收数据是允许的，应用层也会收到两份。」：重复在 TCP 层无妨，但缓冲区和序号去重保证应用层读不到重复数据。

[11] 一台服务器，最多能建立多少 TCP 连接？

🎬 面试现场

面试官：给你一台 8G 内存的服务器，你告诉我最多能撑多少条 TCP 连接？推导给我听。

⚠️ 翻车点

  • 直接答”65535，因为端口号只有 16 位”，这是最经典的误区。
  • 只背”四元组理论上限 2^48”，说不出实际被文件描述符和内存卡死，最终结论不落地。

📝 回答重点

  • 没有固定答案，理论上限看四元组，实际被内存、文件描述符、端口范围卡死，瓶颈基本是内存。
  • 服务端固定监听一个端口，能变的只有客户端 IP 和端口，单进程上限 2^48，约 281 万亿条。
  • 端口只约束单端，一个客户端 IP 对一个服务端端口最多 65535 条，条数靠客户端 IP 数撑起来。
  • 内存按 200KB 一条估，8G 内存拿七成做连接，8GB × 0.7 ÷ 200KB ≈ 2.9 万条。
  • fd 三层卡着：系统 file-max、用户 limits.conf、进程 ulimit -n（默认 1024），超限报 Too many open files。
  • 要撑百万连接：ulimit -n 和 file-max 调大，ip_local_port_range 扩到 1024–65535，再开 tcp_tw_reuse。

📈 拔高

C10K 到 C10M 的分水岭是 epoll 这类事件驱动，再往上要 DPDK 绕内核、多队列网卡和 NUMA 亲和。短连接的坑在 TIME_WAIT 堆积，高并发一律走长连接加连接池。

💡 主动加分的追问准备

追问 答案
客户端连不上报 address already in use？ 客户端临时端口用完，或旧连接还卡在 TIME_WAIT 没释放。Linux 默认可用端口范围 32768–60999 约 2.8 万个，频繁对同一 IP:Port 发短连接很快被 TIME_WAIT 占满。解法：扩大 ip_local_port_range、开 tcp_tw_reuse、改长连接。
多网卡多 IP 对上限有影响吗？ 有影响。服务端 IP 也是四元组的一部分，两个 IP 各监听 8080，对同一客户端来说就是两个不同目的四元组，理论上连接数翻倍。但实际瓶颈还是内存和 CPU，多 IP 只是抬高理论天花板。
百万连接下每秒能处理多少请求？ 百万连接 ≠ 百万 QPS。纯推送/广播场景瓶颈在带宽，每秒几万条没问题。若每个请求都要查库、调外部接口，CPU 和 IO 很快见底，QPS 可能只有几千。前者考验连接维护能力，后者考验请求处理能力。
TIME_WAIT 怎么解决？ 三招：改长连接减少频繁关闭，开 tcp_tw_reuse 让新连接复用 TIME_WAIT 端口。tcp_fin_timeout 可以调短，但它只影响 FIN_WAIT_2，对 TIME_WAIT 无效。

❌ 千万别说的话

  • ❌「一台服务器最多 65535 条连接，因为端口号就 16 位。」：端口只约束单端，客户端 IP 一变条数就翻几亿倍。
  • ❌「调小 tcp_fin_timeout 就能解决 TIME_WAIT 堆积。」：它管的是 FIN_WAIT_2，不是 TIME_WAIT。

[12] TCP 和 UDP 有什么区别？

🎬 面试现场

面试官：TCP 和 UDP 你肯定背过表格，那我问你：为什么 DNS 用 UDP 不用 TCP？HTTP/3 又为什么反过来上了 UDP？

⚠️ 翻车点

  • 只背”TCP 可靠 UDP 不可靠”，说不出面向连接 vs 面向数据报的本质差异。
  • 误以为 UDP 一定比 TCP 快所以”能不用就不用”，说不出各自的适用边界。

📝 回答重点

  • TCP 面向连接，给的是可靠字节流；UDP 面向数据报，无连接不保序，可靠性让上层自己做。
  • 头部差距大：UDP 首部只有 8 字节，最大 64K 超了要应用分包；TCP 最小 20 字节，带选项到 60 字节。
  • TCP 校验和不止首部和数据，还要算上 IP 伪首部，源目的 IP、协议号都在里面。
  • 粘包只发生在 TCP：UDP 首部带长度字段，消息边界清楚，读完首部就是一整个数据报。
  • UDP 发送通常立即下传、不排队等 ACK，套接字的发送缓冲额度满了会报错，接收队列满了直接丢包。
  • UDP 没有连接级全双工语义，双方随时互发数据报，connect 只是绑定默认对端，不握手。

📈 拔高

DNS 报文几十字节，丢一次重发就行，所以走 UDP，HTTP/3 用 QUIC 把可靠传输挪到用户态，绕开内核 TCP。选型看要不要消息边界和可靠传输，别拿谁更快糊弄过去。

[13] 为什么要 TCP，IP 层实现控制不行么？

🎬 面试现场

面试官：既然链路层加 IP 就能通信了，为什么非要再叠一层 TCP？把可靠性做在 IP 层不行吗？

⚠️ 翻车点

  • 只答”因为分层设计更灵活”，说不出 IP 层做不了、也不该做，理由是设备数量与无状态转发。
  • 把端到端原则误解成”网络完全不能有功能”，忘了 NAT/防火墙/CDN 的现实妥协。

📝 回答重点

  • IP 层只管路由转发，按尽力而为投递，可靠性做成可选服务放端点，要快用 UDP，要可靠上 TCP。
  • 一条路要过海量设备，IP 要做控制，每台都得管序列号、确认、重传，转发效率直接崩。
  • 快递中转站同理：每站拆包重传，不如只管转发，最后由收件人自己校验。
  • 端到端原则说的就是每跳都成功不等于端到端收到，中间重传救不了最终结果。
  • 核心路由器每秒转发几十亿包，靠无状态转发，只看目的 IP，不维护任何连接状态。

📈 拔高

NAT、防火墙、CDN 都是端到端原则的现实妥协，NAT 让 P2P 变复杂，防火墙会误杀正常流量。QUIC 把可靠性从内核 TCP 挪到用户态，IP 层依然只管转发，其实是分层思想的延续。

追问 答案
UDP 也是传输层，和 TCP 分工差在哪？ UDP 基本就是给 IP 加了个端口号，别的什么都不管。TCP 是重型选手，连接管理、可靠传输、流量控制、拥塞控制一应俱全。选哪个看场景：DNS 丢一次重发即可 → UDP。视频直播丢几帧没事但不能卡 → UDP。转账一个字节都不能错 → TCP。
端到端原则这么好，为什么现在还在中间加 NAT、防火墙、CDN？ 现实妥协。NAT 因 IPv4 地址不够用，防火墙因安全需求必须在边界过滤，CDN 因性能要把内容推到用户近处。这些都违背端到端原则但解决了实际问题，代价是 NAT 让 P2P 变复杂、防火墙常误杀流量、CDN 有缓存一致性问题。
QUIC 把可靠传输挪到应用层，不是和分层矛盾吗？ 不矛盾，反而是分层思想的延续。动机是 TCP 在内核里改不动、历史包袱重，搬到应用层后迭代速度快得多。IP 层依然只管转发，可靠性仍在端点实现，只是从内核 TCP 挪到了用户态 QUIC。
链路层和 IP 层各起什么作用？ 链路层不可或缺，设备终归是逐跳链路连接的。IP 充当地址功能，靠 IP 找到对方后链路层到 IP 就能完成通信。也正因为”理论上不需要传输层”，TCP 的存在才必须用端到端原则论证。

❌ 千万别说的话

  • ❌「IP 层也能做可靠性，只是实现起来比较麻烦而已。」：不是麻烦，是会让海量无状态设备被迫维护连接状态，网络无法 scale。
  • ❌「有了 TCP 就不需要 IP 了。」：IP 负责寻址与转发，是 TCP 能工作的前提。

[14] TCP 的粘包和拆包能说说吗？

🎬 面试现场

面试官：你用 Socket 连续 write 了 10 次，接收端却一次读出来一堆，粘包拆包到底怎么回事？怎么破？

⚠️ 翻车点

  • 说成”TCP 有 bug””粘包是操作系统 bug”，其实它是字节流的固有特性，不是 bug。
  • 只说”用固定长度”就收尾，没意识到定长会靠填充浪费带宽，也没给出生产上真正可用的方案。

📝 回答重点

  • TCP 是字节流，没有起止边界，消息边界得应用自己划，粘的是应用层数据报。
  • 粘包两个成因：发送端把多次写入合并，接收端没及时读，几个包被一次读走。
  • 拆包就是单次写入超过发送缓冲剩余空间，或者数据大于 MSS 被切开。
  • 生产最常用消息头加消息体，头部记 body 长度，读够长度才算一条完整消息。
  • 分隔符方案写起来快，正文里出现结束符会截断，复杂内容得额外编解码。
  • HTTP 把两招合起来：请求头用 \r\n 分隔，body 长度看 Content-Length，长度未知就用 chunked。

📈 拔高

Java 里 BufferedWriter 换行配 BufferedReader.readLine()，Netty 直接用 LengthFieldBasedFrameDecoder 这类现成解码器。定长方案能用但小包要补空格，带宽白花，只适合包大小本来就固定的场景。

💡 主动加分的追问准备

追问 答案
粘包拆包只发生在传输层吗？ 数据链路层、网络层、传输层都可能出现。日常网络应用开发多在传输层，且因 UDP 特性，该问题仅在 TCP 协议中发生（UDP 有明确消息边界）。
能不能只靠定长解决？ 能，但不理想：小包要补空格到指定长度，额外增加网络传输负担。定长适合包大小固定、且可控填充开销可接受的场景。
分隔符方案的硬伤是什么？ 消息正文中若出现结束符会被提前截断，产生半包。处理复杂字符串需要对内容做编解码以保证结束符语义正确。
Netty 之类框架怎么解决？ 内部编解码器（Codec）做长度字段/分隔符的边界识别，报文解码器把字节流切成完整业务消息。Netty 的 LengthFieldBasedFrameDecoder、DelimiterBasedFrameDecoder 就是这两种思路的现成实现。

❌ 千万别说的话

  • ❌「粘包是 TCP 协议的设计缺陷或内核 bug。」：它是字节流的固有特性，靠应用层定边界解决。
  • ❌「只要服务端 read 一次就能拿到一个完整包。」：read 的返回长度完全由内核缓冲区当前有多少数据决定，与包边界无关。

[15] 说说 TCP 的三次握手？

🎬 面试现场

面试官：三次握手那三个包分别长什么样？为什么非得三次，两次不行、四次行不行？

⚠️ 翻车点

  • 答”三次握手是为了确认双方的收发能力”就收尾，RFC 793 指出的首要原因是防止历史连接建立。
  • 答不出第二次握手把 ACK 和 SYN 合并的技术原因（SYN 和 ACK 都由内核控制，而 FIN 由应用程序触发）。

📝 回答重点

  • 三次握手干两件事：同步初始序列号，顺带确认双方收发都通。
  • 第一次客户端发 SYN 带随机 ISN，进 SYN_SENT；第二次服务端回 SYN+ACK，进 SYN_RCVD。
  • 第三次客户端补 ACK，两边进 ESTABLISHED，连接就算建好。
  • 首要原因是防历史连接：只有两次，迟到的旧 SYN 会让服务端先建连再被 RST 白折腾。
  • 中间两步能合并：确认收到 x 和告诉对方自己的 seq 都由内核一次做完，所以是三次不是四次。
  • 握手包通常不带数据，TFO 这类扩展允许在 SYN 里带，实际用得少，一般等建连再发。

📈 拔高

ISN 必须随机，一是躲上个连接的残留包，二是防会话劫持和 RST 攻击。ACK 丢了服务端会在 SYN_RCVD 重传 SYN+ACK，重试耗尽就放弃，客户端再发数据会收到 RST。

💡 主动加分的追问准备

追问 答案
第三次握手的 ACK 丢了会怎样？ 客户端发完 ACK 就进 ESTABLISHED，以为建好了。服务端没收到还卡在 SYN_RCVD，会超时重传 SYN+ACK，客户端收到后再补一次 ACK。重传若干次仍失败，服务端放弃这个半连接。此时客户端若发数据，服务端发现连接没建好，直接回 RST 终止。
什么是 SYN Flood，怎么防御？ 攻击者伪造大量不存在的 IP 发 SYN，服务器回 SYN+ACK 后等不到应答，队列被半连接堆满。防御靠 SYN Cookie，不维护半连接状态，把状态编码进序列号，收到第三次握手再验证。再配合调大队列和防火墙前置过滤。
初始序列号为什么要随机？ 一是躲历史连接残留包：上个连接刚关，残留包还在网络里飘，四元组相同、序列号相近就会被误收。二是防会话劫持：ISN 可预测的话，攻击者能伪造 TCP 包接管会话。
服务端看到大量 CLOSE_WAIT 是什么原因？ 对端已发 FIN，本端却还没调 close()：要么业务代码没调 close，要么调得不及时。CLOSE_WAIT 堆积基本等于应用侧有 fd 或线程泄漏。
完整的 TCP 11 个状态？ LISTEN、SYN-SENT、SYN-RECEIVED、ESTABLISHED、FIN-WAIT-1、FIN-WAIT-2、CLOSE-WAIT、CLOSING、LAST-ACK、TIME-WAIT、CLOSED。

❌ 千万别说的话

  • ❌「三次握手的目的就是确认双方的收发能力。」：收发能力验证是效果，RFC 793 明确的首要原因是防止历史连接的建立、减少不必要的资源消耗。
  • ❌「第三次握手也可以带大量数据，没区别。」：前两次带数据有安全风险，而且服务端重传 SYN+ACK 时客户端已进 ESTABLISHED，连接不一定对得上号。

[16] TCP 初始序列号 ISN 怎么取值的？

🎬 面试现场

面试官：三次握手里那个初始序列号到底怎么算出来的？为什么不能写死？

⚠️ 翻车点

  • 答”随机生成一个数”——漏掉时间递增这一半，说不清为什么 4 微秒加 1。
  • 把 RFC 793 的假时钟和 RFC 6528 的安全改进混为一谈。

📝 回答重点

  • ISN 不是拍脑袋随机，公式是时钟 M 加伪随机函数 F，时间递增和随机混着来。
  • 时钟 M 每 4 微秒加 1，到 2^32 回绕，约四个半小时转一圈，短时间重连必然比旧连接大。
  • 写死成 0 会出事：断线重连后服务端还记着旧状态，新连接的包会被认成旧连接的，数据全乱。
  • RFC 6528 把 F 定为 MD5 哈希，拿四元组加一个密钥算，攻击者没密钥算不出下一个 ISN。
  • ISN 能预测就能伪造报文插进连接做会话劫持，老系统抓几个包就能摸出规律。

📈 拔高

时间递增管冲突，MD5 加密钥管防预测，RFC 793 和 RFC 6528 是两层改进。带宽极大时序列号消耗快，RFC 7323 的 PAWS 靠 TCP 时间戳选项判报文新旧。

💡 主动加分的追问准备

追问 答案
四个半小时回绕一次会不会出问题？ 正常不会。TCP 有 MSL 概念，报文在网络里最多存活 2 分钟，四个半小时远大于 MSL，绕回来时旧报文早没了。但带宽极大、序列号消耗极快时可能不到四个半小时就绕完，这时开 TCP 时间戳选项判新旧。
序列号和确认号什么关系？ 序列号说”我这段数据从第几个字节开始”，确认号说”我已经收到哪之前所有数据，下一个要第几个”。例：客户端 seq=1000 发 100 字节，服务端回 ACK=1100，意思是 1100 之前的都收到了，下次从 1100 开始发。
序列号是按字节还是按包编号？ 按字节。TCP 给发送的每个字节编序号，报文段首部里的 Seq 字段存的是本段第一个字节的序号。

❌ 千万别说的话

  • ❌「ISN 就是个随机数。」——它是时间递增（每 4 微秒 +1）+ 随机的组合，只说随机就答不完整。
  • ❌「RFC 793 规定的 ISN 用 MD5 加密钥。」——MD5 + 四元组 + 密钥是 RFC 6528 的安全改进，RFC 793 只规定与假时钟绑定递增。

[17] TCP 三次握手时，发送 SYN 之后就宕机了会怎么样？

🎬 面试现场

面试官：客户端发完 SYN 就崩了，对面服务器会一直挂着吗？它怎么发现这个人已经没了？

⚠️ 翻车点

  • 以为服务端会”永远等”或者”立刻释放”，其实是有重试次数和超时机制的。
  • 把重试间隔说成固定的，实际是指数退避。

📝 回答重点

  • 服务端回 SYN+ACK 后进 SYN_RCVD，连接放进半连接队列，等第三次握手的 ACK。
  • 等不到 ACK 就指数退避重传：1、2、4、8、16 秒，tcp_synack_retries 默认 5 次。
  • 第 5 次重发后再等 32 秒仍无响应才判死释放，前后共 1+2+4+8+16+32 = 63 秒。
  • 队列大小归 tcp_max_syn_backlog 管，常见 1024 或 2048，满了新 SYN 直接被丢弃。
  • 反过来服务端发完 SYN+ACK 就宕机，客户端按 tcp_syn_retries 重试，新内核约 131 秒后报连接超时。
  • 半连接状态存不下来时上 SYN Cookie，代价是窗口缩放、SACK 这些扩展选项用不了。

📈 拔高

tcp_synack_retries 设 0 只发一次 SYN+ACK，公网丢包一多正常握手就大批失败，生产一般留 2 次以上。全连接队列溢出时默认静默丢 ACK 让客户端重传，tcp_abort_on_overflow 设 1 才直接回 RST。

💡 主动加分的追问准备

追问 答案
SYN Cookie 怎么做到不存半连接状态？ 把客户端 IP、端口、时间戳、MSS 等经单向散列编码成 32 位序列号放进 SYN+ACK 的 ISN，ACK 带回该值加一，收到 ACK 后用同样算法反算验证，通过才真正建连，服务端全程零状态存储。
SYN Cookie 的缺点？ 不存状态导致 Window Scale、SACK 等握手阶段选项失效，还有 CPU 开销。所以 Linux 默认半连接队列将满时才启用（tcp_syncookies）。
tcp_synack_retries 设成 0 会怎样？ 只发一次 SYN+ACK，收不到就失败。公网丢包常见，设 0 会导致大量正常握手失败，一般至少 2~3 次。
全连接队列满了会怎样？ 看 tcp_abort_on_overflow：默认 0 时静默丢弃 ACK 让客户端重传，队列腾出来还有机会建连。设 1 则直接回 RST，生产建议保持默认并监控溢出。

❌ 千万别说的话

  • “服务端收到 SYN 就直接建立连接了”：要经过 SYN_RCVD 和半连接队列。
  • “重传间隔是固定的 1 秒”：是指数退避 1/2/4/8/16。

[18] 什么是 SYN Flood 攻击？

🎬 面试现场

面试官：SYN Flood 到底打的是什么资源？你们线上怎么防？

⚠️ 翻车点

  • 只答”半连接队列被占满”，说不出分层的防御手段。
  • 把 SYN Cookie 说成”降低系统开销”，其实是”不占队列状态”。

📝 回答重点

  • 打的是半连接队列：攻击者伪造一堆源 IP 发 SYN，服务端逐个回 SYN+ACK 记账等 ACK，ACK 永远不来。
  • 系统层首选 SYN Cookie，队列满时不分配资源，把客户端信息哈希进 ISN，验证 ACK 通过才建连。
  • 调参也算系统层：缩短半连接超时、加大 backlog，但攻击者照样能填满，只算治标。
  • 网络层用速率限制和 SYN 代理，清洗设备代客户端完成握手，收到有效 ACK 才给后端转发新 SYN。
  • 架构层上云清洗和四层负载均衡，边缘过滤加 LB 自己握手里外配合，边界再用 ACL 挡伪造源。

📈 拔高

首包丢弃专打伪造源：攻击者不会重传 SYN，正常客户端超时自动重传，设备见到重传包才放行。单机参数挡不住分布式洪泛，大流量还得靠边缘清洗把半连接队列从后端剥走。

[19] TCP 协议是如何保证可靠传输的？

🎬 面试现场

面试官：IP 明明是不可靠的，TCP 凭什么能保证可靠？都靠哪些机制？

⚠️ 翻车点

  • 答成”TCP 有三次握手所以可靠”，把可靠性来源答偏了。
  • 混淆流量控制（rwnd）和拥塞控制（cwnd）。

📝 回答重点

  • 我按四件事讲：给数据编号、收到要确认、丢了就重传、发太快就管住窗口。
  • 序列号加确认号按字节编号，ACK 一到就知道哪段丢了，校验和不对的包直接丢弃。
  • 超时重传的 RTO 按 RTT 均值加约 4 倍偏差算，超时没 ACK 就重发，重传后指数退避。
  • 滑动窗口做流量控制，接收方在 ACK 里通告 rwnd，别把它的缓冲区撑爆。
  • 拥塞控制用 cwnd 保护网络：慢启动每轮翻倍，拥塞避免每 RTT 加 1 MSS，三个重复 ACK 快速重传。
  • SACK 扩展让接收方精确回报收到哪几段，避免重发已到达的数据。

📈 拔高

丢包触发快速恢复时 ssthresh 减半，cwnd 在 ssthresh 基础上再加 3 个 MSS，靠手上没确认的包继续探。发送窗口实际取 min(rwnd, cwnd)，SYN 和 FIN 也各占一个序号。

追问 答案
TCP 能保证数据 100% 不丢吗？ 不能，只能”尽最大努力可靠交付”。网络彻底断开、对方宕机、重传达上限时连接会被强制断开，应用层收到错误，关键业务仍需应用层确认机制。

  • “拥塞窗口是接收方通知的”：cwnd 由发送方自己维护，接收方只给 rwnd。

[20] 说说 TCP 的四次挥手？

🎬 面试现场

面试官：断开连接为什么要四次？能不能合并成三次？顺便把状态变迁讲一遍。

⚠️ 翻车点

  • 状态名说错、顺序说错（尤其把 FIN_WAIT_1/FIN_WAIT_2 和 CLOSE_WAIT/LAST_ACK 混）。
  • 认为 TIME_WAIT 只出现在客户端。

📝 回答重点

  • 第一次挥手：主动方发 FIN 进 FIN_WAIT_1，被动方立即回 ACK 进 CLOSE_WAIT。
  • 被动方应用把剩余数据发完再补自己的 FIN 进 LAST_ACK，主动方回最后一个 ACK 后进 TIME_WAIT。
  • TIME_WAIT 等满 2MSL 才 CLOSED，Linux 内核直接硬编码 60 秒，MSL=30 秒只是等效说法。
  • 合并不成三次是因为全双工：收到 FIN 只说明对方不再发，本端可能还有数据，ACK 和 FIN 就分开了。
  • TIME_WAIT 在主动关闭方，服务端主动关连接时一样会在它身上堆一大串。
  • 留 2MSL 一是丢了 ACK 能补发，二是让两个方向的旧报文都死在网络里，不被新连接误收。

📈 拔高

TIME_WAIT 堆太多一般两个原因：HTTP 没开长连接，或者长连接请求数上限太小，nginx 的 keepalive_requests 老版本默认 100，1.15.3 起改 1000。CLOSE_WAIT 堆住就是应用没调 close，属于代码 bug 要去查。

💡 主动加分的追问准备

追问 答案
MSL 和 TTL 有什么区别？ MSL 是时间（报文最大生存时间），TTL 是 IP 头的跳数，每过一跳减 1，到 0 丢弃并回 ICMP。MSL 需不小于 TTL 耗尽所需的时间。Linux TTL 一般 64，MSL 取 30s。
为什么是 2MSL 而不是 4、8MSL？ 一来一回（我的 ACK 最长跑 1 MSL，对方重发的 FIN 最长再跑 1 MSL）已覆盖最坏情况，1% 丢包率下连续丢两次的概率仅万分之一，忽略它比处理它更划算。
服务端 TIME_WAIT 过多是什么原因？ ①HTTP 未开长连接，短连接响应完服务端主动关闭。②长连接请求数上限太小，如 nginx keepalive_requests 默认 1000（1.15.3 起），老版本才是 100，QPS 高时频繁关连接，开 Keep-Alive 并调大它就行。
服务端大量 CLOSE_WAIT 说明什么？ 被动关闭方收到 FIN 后没调用 close，状态卡在 CLOSE_WAIT 无法转 LAST_ACK，属于应用代码 bug 或处理逻辑阻塞，需要排查为什么没执行到 close。

❌ 千万别说的话

  • “服务端收到 FIN 马上发 FIN，所以要四次是因为丢包”：四次的原因是全双工、ACK 与 FIN 通常不能合并。
  • “TIME_WAIT 是客户端特有的状态”：它属于主动关闭方，两端都可能出现。

[21] 为什么 TCP 挥手需要有 TIME_WAIT 状态？

🎬 面试现场

面试官：主动关闭方都断开完了，为什么还要在 TIME_WAIT 里赖两分钟不走？

⚠️ 翻车点

  • 只答”防止旧报文干扰新连接”，漏掉”保证最后一个 ACK 可达”这一半。
  • 把 tcp_tw_recycle 当成推荐方案推荐出去。

📝 回答重点

  • 主动关闭方发完最后一个 ACK 进入 TIME_WAIT，内核直接写死 TCP_TIMEWAIT_LEN 为 60 秒，没有「MSL=30 秒」这种说法。
  • 最后一个 ACK 若丢，被动方会重发 FIN。留在 TIME_WAIT 就能立刻补 ACK，不然后端收到 RST 会报关闭错误。
  • 关闭后网络里还有迟到的旧报文，等 MSL 让它们消亡，同四元组立刻重建才不会串数据。
  • 代价在客户端：主动关一次占一个临时端口，端口耗尽就报 Cannot assign requested address。
  • 缓解靠 tcp_tw_reuse，要配合 timestamps，默认值 2 只对回环生效。tcp_tw_recycle 破坏 NAT，4.12 已移除。

📈 拔高

Linux 里 tcp_fin_timeout 管的是 FIN_WAIT_2 停多久，跟 TIME_WAIT 的 60 秒是两码事。2MSL「一来一回」是教学拆解，RFC 9293（原 793）只规定 TIME-WAIT 要停留 2×MSL，MSL 本身仍是 2 分钟。

💡 主动加分的追问准备

追问 答案
TIME_WAIT 占的资源大吗？ 每条约 23KB，随内核版本变化，10 万条约 2030MB，对现代服务器不算大。真正的问题是端口耗尽，客户端可用端口约 2.8 万个，短连接频繁建销容易占光。
怎么查当前 TIME_WAIT 数量？ ss -tan state time-wait | wc -l 直接计数，netstat -an | grep TIME_WAIT 看明细。数量过多要排查短连接是否过多、该用连接池的地方有没有用。
长连接还是短连接产生更多 TIME_WAIT？ 短连接。HTTP/1.0 默认短连接，每请求一次关一次连接就产生一个 TIME_WAIT。HTTP/1.1 默认 keep-alive 可复用，Nginx 默认 keepalive_timeout 75 秒。
TIME_WAIT 为什么固定 60 秒？ 内核直接写死 TCP_TIMEWAIT_LEN = 60*HZ，RFC 9293 的 MSL 是 2 分钟，Linux 没有把 MSL 改成 30 秒这回事。
服务端主动关闭大量连接有什么好办法？ 没有完美方案。建议服务端不主动关闭，把主动关闭权交给客户端（应用层发一条消息让客户端断开），或用 SO_REUSEADDR 支持快速重启。

❌ 千万别说的话

  • “开启 tcp_tw_recycle 就能秒回收 TIME_WAIT”：它会破坏 NAT 场景（同一 NAT 出口的机器时间戳不递增会被误判为过期包丢弃），且已被内核移除。
  • “把 tcp_tw_reuse 和 SO_REUSEADDR 是一回事”：前者是内核选项、用于连接复用；后者是用户态套接字选项、用于端口绑定。

[22] 除了四次挥手，还有什么方法断开连接？

🎬 面试现场

面试官：正常四次挥手之外，TCP 还有哪些方式能把连接断掉？各自的适用场景是什么？

⚠️ 翻车点

  • 只说”RST 一种”，漏掉超时自动断开（keepalive / 应用层超时）。
  • 认为 RST 是”更好的关闭方式”。

📝 回答重点

  • 四次挥手之外就两条路：RST 强制关闭和超时自动断开。
  • RST 收到立刻断，不走挥手不等确认，缓冲区没处理的数据直接丢。
  • 超时断开靠内核 keepalive 探测：默认空闲 7200 秒起、75 秒一次、共 9 次，判死要两小时开外。
  • 应用层也有自己的超时：HTTP 空闲超时、连接池回收、WebSocket 心跳。
  • 正常业务走四次挥手把数据发完，RST 只留给异常场景，比如检测到攻击立刻掐断。
  • linger=0 让 close 直接发 RST 能快速回收，客户端会收到 connection reset，慎用。

📈 拔高

默认 keepalive 要两小时十一分钟才判死，生产上一般把空闲探测调到 60 秒级。RST 和四次挥手互补，前者清异常连接，后者保数据完整。

追问 答案
收到 RST 后应用层感知到什么？ read 返回 -1 且 errno 为 ECONNRESET。write 第一次可能成功但数据发不出去，第二次会收到 SIGPIPE 或返回 EPIPE。Java 侧表现为 Connection reset / Broken pipe 异常。
怎么在代码里控制发 RST 还是四次挥手？ 设置 socket 选项 SO_LINGER：l_onoff=0 或未设置时 close 走正常四次挥手。l_onoff≠0 且 l_linger=0 时直接发 RST。l_onoff≠0 且 l_linger>0 时 close 阻塞等待发完，超时则发 RST。
服务端大量 TIME_WAIT 和大量 CLOSE_WAIT 分别什么原因？ TIME_WAIT 多说明服务端主动关闭，属正常现象，可调 tcp_tw_reuse。CLOSE_WAIT 多说明服务端收到 FIN 却没调用 close，是代码 bug 或逻辑阻塞。
HTTP 长连接和短连接哪个更省？ 长连接。HTTP/1.0 默认短连接每请求关一次连接，每次都产生 TIME_WAIT。HTTP/1.1 默认 keep-alive 复用连接，关闭频率大幅降低。

  • “TCP 有 keepalive 就不会产生僵尸连接”：默认 2 小时起步，太长，生产必须调短。

[23] TCP 超时重传机制是为了解决什么问题？

🎬 面试现场

面试官：数据发出去石沉大海怎么办？超时重传的 RTO 到底是怎么算出来的？

⚠️ 翻车点

  • 把 RTO 说成固定值或简单取 RTT 的两倍。
  • 认为收到 ACK 就一定是回复第一次发送的，不提 Karn 算法。

📝 回答重点

  • 解决的是丢包后怎么办：包石沉大海时 TCP 得有兜底，不然谈不上可靠传输。
  • 发完就开计时，RTO 内没等到 ACK 就重发。RTO 由平滑 RTT 加若干倍均差算出来。
  • 确认号按字节累计，只认最大连续收到的位置，ACK 不能越过缺口乱报。
  • Karn 算法对重传的包不采样 RTT，分不清 ACK 回的是哪一次，这时直接把 RTO 翻倍。
  • 超时代价大：等待期间吞吐归零，cwnd 掉回 1 个 MSS 重新慢启动，所以才有快速重传补位。
  • 内核参数记三个：tcp_retries1=3，tcp_retries2=15，tcp_syn_retries=6 约 131 秒。

📈 拔高

RFC 793 那套 RTO 公式现在只当教学参考，现行算法以 RFC 6298 为准，Linux 实际把 RTO 下限压到 200 毫秒。tcp_retries2=15 的 924.6 秒约 15.4 分钟是下界，链路半通不闭时实际还能拖更久。

💡 主动加分的追问准备

追问 答案
RTO 设置不合理有什么后果？ 太小则正常包还没回来就重传，浪费带宽甚至加剧拥塞。太大则真丢包要等很久才恢复，体验差。早期固定值或简单平均效果很差，现在都用 Jacobson 算法把 RTT 波动算进去。
超时重传和快速重传的区别？ 超时重传是兜底，RTO 到期没收到 ACK 触发。快速重传是优化，收到 3 个重复 ACK 说明后面的包到了、中间某个丢了，立即重传。窗口末尾的包丢了或整段链路断了，只能靠超时重传。
为什么 3 个重复 ACK 才触发快速重传，2 个不行？ 网络本身会乱序，1~2 个重复 ACK 很可能只是乱序不是丢包。连续 3 个说明后面至少 3 个包都到了，中间那个大概率真丢，误判概率足够低。
RTO 翻倍是哪种机制？ 指数退避。避免网络已拥堵还疯狂重传火上浇油。超时重传后 ssthresh 减半、cwnd 退回 1 个 MSS 重新慢启动。

❌ 千万别说的话

  • “RTO 就是 RTT 的两倍/固定 1 秒”：它是动态计算的，且是 RTT 均值加若干倍均差。
  • “ACK 号可以乱报，只要大于某个数就行”：累计确认只能报最大连续收到的位置。

[24] TCP 中何时会出现 RST（reset）报文？

🎬 面试现场

面试官：线上老是报 Connection reset，RST 到底什么时候会出现？你怎么定位是谁发的？

⚠️ 翻车点

  • 只答”对方端口没开”，说不出连接已不存在性丢失、非法序列号、SO_LINGER、队列溢出这几类。
  • 把 RST 和 FIN 的差别讲反（说 RST 更优雅）。

📝 回答重点

  • RST 是强制终止信号，收到立刻断开，收发缓冲区数据全丢，不走四次挥手。
  • 对方回 RST 最常见的三类：端口没人监听、连接已被重启清掉、序列号非法。
  • 主动发 RST 有两条路：close 时 SO_LINGER 置 0，或全连接队列溢出且 tcp_abort_on_overflow 开着。
  • 和 FIN 的区别一句话：FIN 先发完缓冲区数据再关，对端 read 不报错。RST 直接丢数据，对端报 Connection reset by peer。
  • 定位先抓包看 RST 源 IP，再 ss -tlnp 查监听，然后排查防火墙切断和 LB 超时配置。
  • 队列溢出别图省事开 tcp_abort_on_overflow，打满会出 RST 风暴，线上一般保持 0。

📈 拔高

RST 攻击能得手，是因为 TCP 头明文带着序列号，TLS 也盖不住，防御靠随机化 ISN 和 TCP MD5 签名。抓包时看 RST 前面那个包，前面是 SYN 就是端口没监听，前面是正常数据就是连接中途出了问题。

💡 主动加分的追问准备

追问 答案
抓包看到大量 RST 怎么定位责任方？ 看 RST 包的源 IP：服务端发的大概率是服务挂了、端口没监听或客户端数据有问题，客户端发的则是超时或主动断开。
服务重启后老客户端为什么会收到 RST？ TCP 连接靠四元组识别，重启后内核 socket 表被清空，老四元组找不到对应 socket，内核按协议回 RST，客户端 read 报 Connection reset by peer。所以要优雅重启：先停收新连接、等老连接处理完再退出，或用 SO_REUSEADDR 加热重启。
什么情况下该主动发 RST 而不是 FIN？ ①检测到对方行为异常（协议解析失败、认证不通过、恶意请求），没必要走 FIN 流程。②服务过载需要快速释放资源，比如全连接队列将满时对新请求直接 RST 好过排队等超时。正常业务流量仍应走 FIN。
为什么 RST 攻击在 HTTPS 下依然有效？ TLS 只加密应用层数据，TCP 头部明文，含序列号。攻击者嗅探到 TCP 流量能拿到四元组和序列号范围并伪造 RST。实际难度在于要在同一网络嗅探，且伪造序列号必须刚好落在接收窗口内。

❌ 千万别说的话

  • “收到 RST 后对端还能把缓冲区数据读完”：RST 直接丢弃收发缓冲区数据。
  • “服务重启后老连接会自动恢复”：socket 表丢失就是回 RST，必须靠优雅重启或 SO_REUSEADDR 规避。

三、TCP 拥塞控制与窗口

[25] TCP 有超时重传为什么还需要快速重传机制？

🎬 面试现场

面试官：TCP 不是已经有超时重传了吗，为什么还要搞一个快速重传？两者什么时候各管用？

⚠️ 翻车点

  • 答”快速重传可以缩短 RTO，所以更快”——把两者的触发依据（时间驱动 vs 数据驱动）混为一谈。
  • 以为快速重传能覆盖所有丢包场景，忽略它对窗口末尾丢包、连续丢包、网络断开完全无能为力。

📝 回答重点

  • 超时重传是时间驱动，RTO 到点没 ACK 才动，几百毫秒起步。快速重传是数据驱动，收到 3 个重复 ACK 立刻补包。
  • 阈值定 3 是因为网络会乱序，1~2 个重复 ACK 很可能是迟到包，3 个才敢断定中间那个丢了。
  • 恢复时间从几百毫秒压到几个 RTT，吞吐差别就在这。
  • 它盖不住三种情况：窗口末尾丢包、一次连丢多个、网络整个断了，这些只能等超时。
  • 快速恢复里 ssthresh 初值取 max(cwnd/2, 2*MSS)，cwnd 设成 ssthresh + 3*MSS，收新 ACK 后直接进拥塞避免。
  • 两者互斥：快速重传触发会重置超时计时器，只有它没机会的场景才轮到超时。

📈 拔高

有 SACK 时一次能把丢的段全补上，没有 SACK 只知道触发点那一个包丢了，恢复效率差一截。tcp_reordering 默认 3，内核检测到经常乱序会自动调大这个阈值。

💡 主动加分的追问准备

追问 答案
快速重传和超时重传可能同时触发吗？ 不会，两者互斥。快速重传触发时会重置超时计时器，抢先处理了丢包。只有窗口末尾丢包、网络完全断开等场景才等到超时。
网络乱序很严重时，快速重传会不会频繁误触发？ 会，这是已知问题。极端乱序下很容易凑出 3 个重复 ACK。有些 TCP 变种引入额外乱序检测（结合 SACK 信息判断乱序还是真丢包，或动态调整阈值），Linux 内核的 tcp_reordering 就是干这个的，默认值 3，检测到经常乱序会自动调大。
快速恢复里 cwnd 为什么要设成 ssthresh + 3×MSS，而不是直接回到 ssthresh？ 那 3 个重复 ACK 说明已有 3 个包离开网络到达接收方，网络里实际数据少了 3 个包。加这 3 个 MSS 相当于补偿回来，让发送方能继续发数据填满管道，既保守控制又不让链路空跑。
没有 SACK 时代怎么解决丢包重传？ RFC 2018 定义 SACK 是 1996 年的事。此前主要靠 Go-Back-N（从丢失点往后全部重传，浪费带宽）和快速重传（能早动手，但仍不知道哪些包其实已到）。

❌ 千万别说的话

  • 不要说”超时重传太慢所以要快速重传”就收尾——必须补上”两者互补、覆盖场景不同”才完整。
  • 不要把”3 个重复 ACK”说成 TCP 拥塞控制里的阈值，它是快速重传的触发条件，两者别混。

[26] TCP 的 SACK 的引入是为了解决什么问题？

🎬 面试现场

面试官：SACK 是干什么的？没有它的时候 TCP 丢包重传是怎么做的？

⚠️ 翻车点

  • 只说”SACK 能告诉发送方哪些数据收到了”，说不出它解决的具体痛点：传统累计确认下发送方不知道该重传哪些。
  • 忽略实现约束，SACK 靠 TCP 选项字段携带，选项最多 40 字节，所以块数有限。

📝 回答重点

  • 传统累计确认只能说到哪之前都收到，中间丢一个包，发送方不知道具体丢了哪些，只能超时后大面积重传。
  • SACK 让接收方在 ACK 外补一句”Y-Z 这段我也收到了”，发送方只重传真正丢的那一段。
  • 例：ACK 说接下来要 5500，SACK 一路更新 6000-6500 到 6000-7500，发送方就确定 5500-5999 丢了，只补它。
  • 走 TCP 选项字段，三次握手时协商。一个 SACK 块 8 字节，选项总长 40 字节，最多带 3-4 个块。
  • D-SACK 报告重复接收：SACK 第一段描述重复区间，被 ACK 覆盖就是重复。参数 tcp_dsack，现代 Linux 默认开启。

📈 拔高

SACK 只管重传范围，触发时机还靠快速重传，两个配合才完整。接收端维护乱序队列，攻击者能用大量乱序包耗尽内存，Linux 4.x 前的 SACK Panic 就是构造 SACK 序列打崩内核。

💡 主动加分的追问准备

追问 答案
SACK 和快速重传什么关系，能同时用吗？ 完全可以，而且效果更好。快速重传解决什么时候动手，SACK 解决重传哪些数据。没有 SACK 时快速重传只能修触发点那一个包，后面再丢得等新 ACK 或超时。
中间设备不支持 SACK，但两端都支持，会怎样？ 透传的没问题，老防火墙会删掉不认识的 TCP 选项。两端以为协商成功，实际 SACK 信息到不了对端。不会出错，只是优化消失，退化成传统模式。
D-SACK 具体帮发送方优化了什么？ 让发送方知道自己是否重传过头了（原包只是迟到，收到两份相同数据）。这可用于判断是否 RTO 太短需要调大、网络是否乱序需调整拥塞控制策略，长期看让重传决策更准。
SACK 有什么风险？ 接收方要维护乱序队列，攻击者能用大量乱序包耗尽内存，Linux 4.x 前的 SACK Panic 就是构造 SACK 序列打崩内核。老设备还可能剥掉 SACK 选项，极端时会触发重传风暴。

❌ 千万别说的话

  • “SACK 让 TCP 变可靠了。”：可靠性一直是 TCP 的目标，SACK 优化的是丢包恢复效率，不是可靠性本身。
  • “SACK 块可以随便加。”：TCP 选项总长 40 字节摆在那，实际最多 3-4 块。

[27] TCP 滑动窗口的作用是什么？

🎬 面试现场

面试官：滑动窗口到底是干什么的？它和拥塞控制是什么关系？

⚠️ 翻车点

  • 只答”提高效率”，漏掉更重要的流量控制——防止接收方缓冲区被撑爆导致丢包。
  • 分不清 cwnd 和 rwnd，说不清实际发送窗口是两者取小。

📝 回答重点

  • 滑动窗口干两件事：流量控制加流水线效率。防的是把接收方缓冲区撑爆，不只为了发得快。
  • 接收方在 ACK 里带 rwnd，发送方只在窗口内发。它把可收量从 1000 降到 500，发送就按 500 走。
  • 发送方自己按网络拥塞算一个 cwnd，实际发送窗口取 **min(cwnd, rwnd)**，谁小听谁的。
  • 对比停止等待：窗口 3 时连发 1 2 3，收到 ACK1 窗口右移再发 4，等 ACK 的空隙不闲着。
  • 窗口左边界随已确认数据右移，大小不变，右边进新数据。接收方收缩窗口的场景另说。

📈 拔高

零窗口时发送方靠持续计时器发探测报文，不会死锁。cwnd 管网络拥塞，rwnd 管接收能力，拥塞控制算法决定的就是 cwnd 怎么涨落。

💡 主动加分的追问准备

追问 答案
接收方缓冲区满了怎么办，发送方该怎么知道？ 接收方通过 ACK 报头里的窗口字段把 rwnd 收缩到 0，发送方必须停止发送。
cwnd 和 rwnd 谁说了算，两者冲突时取谁？ 取 min(cwnd, rwnd)。cwnd 反映网络是否拥塞，rwnd 反映接收方处理能力，任一方成为瓶颈都会限制发送速率。
接收方把窗口通告为 0，双方会不会死锁？ 不会。发送方有持续计时器，定期发零窗口探测报文，接收方缓冲区腾出来后重新通告窗口。就算更新报文丢了，探测计时器还在兜底，连接不会卡死。
滑动窗口和拥塞控制是一回事吗？ 不是。滑动窗口提供流量控制与流水线效率的框架，拥塞控制（慢启动、拥塞避免等）决定 cwnd 的取值，两者取小后才是实际发送窗口。

❌ 千万别说的话

  • 不要把滑动窗口说成”只是提高效率的工具”，漏掉流量控制这一半。
  • 不要说”发送窗口 = cwnd”或”= rwnd”，正确答案是 min(cwnd, rwnd)。

[28] 说说 TCP 拥塞控制的步骤？

🎬 面试现场

面试官：讲一下 TCP 拥塞控制的完整流程，慢启动、拥塞避免、快重传快恢复分别在什么条件下发生、窗口怎么变？

⚠️ 翻车点

  • 把”收到 3 个重复 ACK”和”超时”混用同一套 cwnd 调整逻辑，两者完全不同：超时后 cwnd 退到 1 个满段重新慢启动，3 重复 ACK 只砍半进快恢复。
  • 背不出阈值和公式：ssthresh = max(FlightSize/2, 2×MSS)、cwnd = ssthresh + 3×MSS、每收一个重复 ACK 加 1 个 MSS、收到新 ACK 后 cwnd 设回 ssthresh。
  • 忽略 cwnd 初始值的真实取值，教材里常说 1，Linux 实际是 10 个 MSS（可用 ss -nli 查看）。

📝 回答重点

  • 拥塞控制就五个动作：慢启动、拥塞避免、超时重传、快速重传、快速恢复，全在调 cwnd。
  • 慢启动：每收到一个 ACK，cwnd 加 1，一个 RTT 翻一倍，一直涨到 ssthresh。
  • ssthresh 初始值设得尽可能大，比如最大可通告窗口。cwnd 小于它走慢启动，碰到后切拥塞避免。
  • 拥塞避免：每个 ACK 加 1/cwnd，凑满一个 RTT 正好加 1 个 MSS，指数变线性。
  • 超时最狠：ssthresh = max(FlightSize/2, 2×MSS)，cwnd 退到 1 个满段，重新从头慢启动。
  • 快速恢复由 3 个重复 ACK 触发：ssthresh 先砍半，cwnd 抬到 ssthresh + 3×MSS，重传后每收重复 ACK 加 1，收到新 ACK 就回拥塞避免。

📈 拔高

Linux 实际初始 cwnd 是 10 个 MSS，不是教材的 1，用 ss -nli 能看到。超时重传比快速恢复狠得多，前者退回起点重新爬，后者减半后继续线性涨。

💡 主动加分的追问准备

追问 答案
快速恢复过程中，为什么收到新数据 ACK 后 cwnd 要设回 ssthresh？ 快速恢复的首要目的是把 cwnd 压下来减缓拥塞，所以先由大到小。过程中每收一个重复 ACK 加 1，是为了尽快把丢失包补出去。收到新 ACK 说明恢复结束，cwnd 设回 ssthresh 重新线性增长。
Linux 里 cwnd 的初始值到底是多少？ 10 个 MSS，可用 ss -nli 观察连接初始拥塞窗口。教材说初始化为 1 是为讲清算法做的简化。
为什么慢启动要指数增长，拥塞避免要线性？ 连接刚建立时网络状况未知，线性起步太慢浪费带宽，猛冲又可能打爆网络。指数增长能快速逼近链路上限，碰到 ssthresh 后放缓，用线性小心试探。
超时重传为什么必须把 cwnd 打到 1？ 超时意味着连 ACK 都收不到，无法判断是单包丢失还是网络严重拥塞/断裂，只能保守地认为网络已不可用，退回最小窗口重新慢启动探测，避免持续压垮网络。
拥塞避免阶段”每个 ACK 加 1/cwnd”怎么理解？ 等价于”每收到一个完整窗口的 ACK，cwnd 加 1 个 MSS”，即每 RTT 加 1，把指数增长降为线性。

❌ 千万别说的话

  • 不要把超时重传和快速重传的窗口调整说成同一套，前者 cwnd 退到 1 个满段重新慢启动、后者减半进快速恢复。
  • 不要说”慢启动从 cwnd=1 开始”却不说这是简化假设，Linux 实际初始值是 10 个 MSS。
  • 不要漏掉超时后 ssthresh = max(FlightSize/2, 2×MSS) 这个核心公式。

四、网络分层与寻址

[29] ARP 和 RARP 分别是什么？有什么区别？

🎬 面试现场

面试官：ARP 解决什么问题？和 RARP 有什么区别？为什么 ARP 只在局域网内工作？

⚠️ 翻车点

  • 忽略 ARP 的存在必要性：IP 是逻辑地址，局域网内投递最终必须靠 MAC，IP 协议本身不提供二层寻址。
  • 说 ARP 跨网段也能用，ARP 广播过不了路由器。
  • 漏掉 ARP 无认证带来的 ARP 欺骗/中间人风险。

📝 回答重点

  • ARP 干的是 IP 转 MAC：局域网投递最终靠 MAC 地址，只知道对方 IP 发不出帧。
  • 先查本地 ARP 缓存，没有就广播问”谁是 192.168.1.100”，对方单播回，写进缓存下次直接用。
  • 请求广播是因为还不知道目标 MAC，响应单播是因为已经知道，再广播纯浪费。
  • RARP 方向相反，MAC 转 IP，无盘工作站启动时问服务器该用什么 IP，早被 DHCP 取代。
  • ARP 没有认证，谁都能伪造响应，这是 ARP 欺骗的根源。防御靠静态 ARP 绑定、DAI、VLAN 隔离。
  • 广播过不了路由器，跨网段只问默认网关的 MAC，每跳 MAC 变、IP 不变。

📈 拔高

免费 ARP 自问自答，用来查 IP 冲突、通知换网卡。代理 ARP 是路由器替人应答，能通但破坏隔离，现在不推荐。

💡 主动加分的追问准备

追问 答案
ARP 缓存表满了会怎样？ 老条目按 LRU 策略被淘汰。Linux 下由 gc_thresh 系列参数控制，默认软限制 512 条、硬限制 1024 条。局域网设备特别多时需调大，否则会频繁触发 ARP 查询影响性能。
什么是免费 ARP（Gratuitous ARP）？ 主机自问自答的 ARP 请求，源和目标 IP 都填自己。作用：一是检测 IP 冲突，二是通知其他设备更新 ARP 缓存，换网卡或 VRRP 主备切换时让新 MAC 被认识。
代理 ARP 在什么场景用？ 路由器替别人回答 ARP 请求。典型场景是主机分属不同子网但物理上同一网段又没配网关，互相问不到响应，路由器就用自己的 MAC 应答并代转发。现在不推荐，破坏网络隔离。
ARP 有没有认证机制？ 没有，协议设计上就是无认证的，这是 ARP 欺骗的根源。防御靠静态绑定、DAI、VLAN 等旁路手段，而不是协议自身。

❌ 千万别说的话

  • “ARP 协议工作在网络层。”：它是链路层/网络接口层的寻址协议。
  • “IP 包直接带 MAC 跨网段传输。”：跨网段每跳 MAC 都变，只有 IP 不变。

[30] TCP/IP 四层模型是什么？

🎬 面试现场

面试官：TCP/IP 四层模型每层干什么？各层的数据单位和包头字段分别是什么？

⚠️ 翻车点

  • 层次名称说错，第四层是网络接口层（链路物理层），是数据链路层与物理层的合体，不是”物理层”单层。
  • 数据单位张冠李戴：应用层是数据、传输层是报文段、网络层是数据包、链路层是帧。

📝 回答重点

  • 四层从上到下：应用层、传输层、网络层、网络接口层。第四层是链路层加物理层的合体，别答成纯物理层。
  • 数据单位背清楚：应用层数据、传输层报文段、网络层数据包、链路层帧。
  • 应用层合并了 OSI 的应用、表示、会话三层。端口要熟：DNS 53、HTTP 80、FTP 20/21。
  • 传输层管进程到进程，TCP 面向连接，靠四元组：源 IP、源端口、目的 IP、目的端口，对应到 Socket。
  • 网络层封装成 IP 数据报负责选路，IGMP 管多播组，ICMP 报错误，ping 就靠它。
  • 发送自上而下层层加头，接收自下而上层层去头。网卡 DMA 进出队列，硬中断转软中断再进协议栈。

📈 拔高

端口最常被追问，DNS 走 UDP 53，报文超 512 字节才转 TCP，FTP 是 20/21 两条连接。收发路径里硬中断转软中断再进协议栈，内核网络题爱接着考这段。

💡 主动加分的追问准备

追问 答案
为什么 TCP/IP 只分四层而 OSI 分七层？ TCP/IP 是实用演进的结果，会话层、表示层并进应用层，数据链路层加物理层合成网络接口层，去掉纯概念层次。OSI 反过来，先有理论模型再落地协议。
TCP/IP 和 OSI 的对应关系是什么？ OSI 的应用层、表示层、会话层对应 TCP/IP 应用层，传输层对传输层，网络层对网络层，数据链路层加物理层对应网络接口层。
传输层报文字段和五层模型怎么对齐？ 传输层是 Segment（报文段），网络层是 Packet，链路层是 Frame，五层模型再多拆出物理层的比特流。
一次 TCP 连接的四元组是什么？ 源 IP、源端口、目的 IP、目的端口。传输层就是靠它把报文交给唯一的 Socket。

❌ 千万别说的话

  • “TCP/IP 四层模型第四层就是物理层。”：网络接口层是链路层与物理层的合体。
  • 不要把 TCP 说成”在网络层”，传输层是它的正式归属。

[31] RPC 与 OSI 七层的关系（RMI / gRPC 实战）

🎬 面试现场

面试官：OSI 七层模型怎么分的？另外你项目里的 RPC 框架（RMI/gRPC）跑在哪一层？

⚠️ 翻车点

  • 只背七层名字，答不出每层职责、数据单位和典型协议。
  • 把 RPC 说成”传输层协议”——它是应用层的通信框架，底下仍然是 TCP 在跑。
  • 只会说 gRPC 比 RMI 好，说不出两者在序列化、跨语言、流式能力上的具体差异。

📝 回答重点

  • RPC 属于应用层，像调本地方法一样调远端，网络细节交给 gRPC、Thrift、Dubbo 封装。
  • 分层落点：应用层做序列化编解码，传输层 TCP，网络层 IP，底下四层一步都不少。
  • Java RMI 四步：远程接口继承 java.rmi.Remote → 实现继承 UnicastRemoteObject → registry.rebind 绑定（默认 1099 端口）→ 客户端 lookup 后调用。
  • 启动顺序 rmiregistry → Server → Client，注册表不先起，客户端 lookup 直接失败。
  • RMI 与 gRPC：RMI 靠 Java 序列化，JDK 17 移除的是 RMI Activation，序列化没被弃用。gRPC 基于 Protobuf 和 HTTP/2，跨语言好、支持四种调用模式。

📈 拔高

gRPC 官方传输只走 HTTP/2，HTTP/3/QUIC 还在社区实验，别说成正式支持。RMI 只能同步阻塞也过时了，JDK 16 起支持 CompletableFuture 异步远程调用。

追问 答案
RPC 框架在网络模型里属于哪一层？ 应用层。RPC 让远程调用对调用方透明，但底下仍要落到应用层的 RPC 协议 + 传输层的 TCP + 网络层的 IP 来完成真正传输。
Java RMI 的调用链大概经过哪些层？ 应用层走 RMI 协议序列化与注册表查找，传输层走 TCP，网络层走 IP，网络接口层走 MAC 与帧。客户端只需通过注册表拿到远程对象代理即可像本地调用一样使用。
RMI 和 gRPC 的区别？ RMI 是 JDK 原生方案，依赖 Java 序列化，跨语言差。gRPC 基于 Protobuf，跨语言支持好、有强类型契约、流式 RPC 能力强，是现在的主流选择。
序列化方式为什么会影响框架选型？ Java 原生序列化与业务类强耦合、跨语言无法解析、体积大且有反序列化漏洞风险。Protobuf 按字段编号编码、语言无关、体积小，是 gRPC 的默认选择。

❌ 千万别说的话

  • ❌「RPC 是传输层协议」：传输层只有 TCP/UDP，RPC 属于应用层
  • ❌「RPC 绕过了 TCP/IP 四层，直接调用远端内存」：它只是隐藏细节，底层链路一步不少
  • ❌「OSI 分七层、TCP/IP 分四层，所以两者不通用」：映射关系明确，前四层一一对应，后三层被合并

[32] Cookie、Session、Token 之间有什么区别？

🎬 面试现场

面试官：Cookie、Session、Token 三者有什么区别？各自的存储位置、安全性、生命周期？分布式和跨域场景你怎么选型？

⚠️ 翻车点

  • 把”HTTP 无状态”和”Cookie 存了状态”说成矛盾——Cookie 是无状态协议下的状态补充机制。
  • 认为 Token 一定比 Session 安全——JWT 存 localStorage 防 CSRF，但一旦泄漏即等同于凭证；Payload 明文可解码，所谓”加密”要分清是签名还是加密。
  • 忽略分布式 Session 的真实问题：粘滞会话换机器要重新 Hash 绑定、Session 复制同步流量随节点数急剧放大（近似平方级）。

📝 回答重点

  • Cookie 由服务器下发、存在客户端，容量约 4KB，易被篡改，每次请求都携带。
  • Session 数据存服务端、客户端只留 Session ID，更安全，高并发下每次请求都要查。
  • Token 服务端不存、只验签，短过期配 Refresh Token 续期，适合分布式和跨域。
  • JWT 三段是 Header、Payload、Signature，Payload 只是 Base64 不是加密，隐私别放。
  • JWT 放 localStorage 配 Authorization 头防 CSRF，必须设 exp 且别太长。
  • 选型看场景：轻量状态用 Cookie，服务端身份认证用 Session，分布式跨域认证用 Token。

📈 拔高

分布式 Session 最常用 SpringSession 把数据统一放 Redis，粘滞和复制两个老方案在扩容时都有硬伤。Token 和 Session 也能叠加：JWT 做无状态校验，Refresh Token 落 Redis 保留可撤销性。

💡 主动加分的追问准备

追问 答案
HTTP 明明无状态，为什么 Cookie 能携带状态？ HTTP 每个请求独立、自身不记状态。Cookie 是 HTTP 协议簇的一部分，作为客户端侧的状态载体随请求携带，才让服务器”间接有状态”。
为什么把 JWT 放 localStorage 而不是 Cookie？ Cookie 会随请求自动发送，容易被 CSRF 利用。localStorage 不会被自动携带，配合 Authorization 头由前端显式附加，可规避 CSRF。
JWT 是加密的吗？ 准确说是签名：Header 与 Payload 是 Base64 编码可被任何人解码查看，安全性来自 Signature 的密钥校验，能防篡改但不能防偷看，因此 Payload 不能放隐私信息。
Session 和 Token 能并存吗？ 可以。常见做法是 Access Token 用 JWT 做无状态校验，同时把 Refresh Token 或会话数据落 Redis，两者结合兼顾性能与可撤销性。
秒杀场景下负载均衡到不同 Tomcat 为什么会重复购买？ 第一次请求到 TomcatA 记录 Session，第二次到 TomcatB，TomcatB 认为该用户是首次访问从而放行，造成重复购买。本质是 Session 不共享，需粘滞、复制或集中存储解决。
Cookie 的安全属性有哪些要配？ HttpOnly 防止 JS 读取降低 XSS 窃取风险，Secure 只走 HTTPS，SameSite 限制跨站携带缓解 CSRF。

❌ 千万别说的话

  • 不要说”JWT 是加密的、内容看不到”：Payload 是 Base64 明文，签名只保证不被篡改。
  • 不要说”Token 一定比 Session 安全”：Token 泄漏即等同凭证，Session 可即时服务端失效，安全性取决于整体设计。
  • 不要把 Cookie、Session、Token 说成互斥的三选一，实际可以叠加使用。

[33] JWT Token 能说说吗？

🎬 面试现场

面试官：我们系统用的是 JWT，你跟我讲讲它到底是怎么工作的，为什么大家现在都喜欢用它？

⚠️ 翻车点

  • 以为 JWT 的 Payload 是加密的，直接把手机号、身份证塞进去
  • 说”JWT 无状态所以不能撤销”，其实这是有解的，只是要付出有状态的代价

📝 回答重点

  • 结构三段用点号连接：Header 声明算法，Payload 放声明，Signature 防篡改。
  • 流程：登录后服务端签发，客户端每次放进 Authorization 头，验签通过就认。
  • 卖点是自包含加无状态：服务端不存 Token，任意节点都能验签，天然适合微服务。
  • 声明字段背几个：iss 签发者、exp 过期、iat 签发时间、jti 唯一标识。
  • 算法两类：HS256 对称一把钥匙签了验，RS256 非对称私钥签公钥验，适合第三方验签。
  • Payload 是 Base64URL 编码不是加密，隐私别放。真要加密上 JWE，五段结构重得多。

📈 拔高

要强制下线有解：jti 黑名单、用户版本号、短 Access 配长 Refresh，代价是丢掉一部分无状态。Payload 只能防篡改防不了偷看，密钥长度和轮换也要跟上，HS256 至少 32 字节。

💡 主动加分的追问准备

追问 答案
JWT 未过期但要强制下线怎么办？ 三种方案：① Redis 黑名单存 jti，验签后再查，违背无状态且规模大了有性能问题。② 用户版本号，写进 Payload，验签比对，改密码/登出时递增，一刀切掉所有设备。③ 短 Access + 长 Refresh，Refresh Token 存服务端可主动撤销。
Payload 能加密吗？怎么加？ 用 JWE：五部分结构，先用接收方公钥加密一个对称密钥，再用该对称密钥加密 Payload。只有持私钥的接收方能解密，但比 JWS 重得多，一般场景用签名就够。
alg: none 有什么安全问题？ 经典漏洞：把正常 Token 的 alg 改成 none 并删掉签名，若服务端盲信 Token 声明的算法，篡改后的 Payload 直接验签通过。服务端必须强制指定算法，忽略 Token 里的 alg 字段。
多设备登录怎么只踢掉某一台设备？ 每个 Token 带唯一 jti，服务端维护 Token 列表，要踢就把该 jti 加黑名单。或每个设备一个存服务端的 Refresh Token，删掉它，该设备的 Access 过期后续不了期。
为什么 JWT 不适合存 Session 数据？ JWT 签发后不可变，Session 数据（如购物车）频繁变动，每次变动都要重新签发，开销大且客户端要配合更新。加上 JWT 体积比 Session ID 大，频繁变动数据放进去浪费带宽。动态数据走服务端存储。

❌ 千万别说的话

  • ❌「JWT 是加密的，里面的内容别人看不到」：Payload 是 Base64 编码，任何人都能解开看
  • ❌「JWT 无状态，所以没法注销、没法失效」：黑名单 / 版本号 / Refresh Token 都能解决，只是牺牲一部分无状态性

[34] 简单谈谈你对 DNS 的理解？

🎬 面试现场

面试官：你给我讲讲浏览器输入一个域名之后，DNS 是怎么把域名变成 IP 的？

⚠️ 翻车点

  • 把「递归查询」和「迭代查询」的对象说反——是本地 DNS 递归地替客户端问，根/TLD/权威只指路
  • 认为一个域名可以同时配 A 记录和 CNAME 记录

📝 回答重点

  • DNS 把域名翻成 IP，还顺带做负载均衡，一个域名配多个 IP 分散流量。
  • 解析顺序：浏览器缓存 → hosts 和系统缓存 → 本地 DNS → 根 → TLD → 权威。
  • 分工记清楚：客户端问本地 DNS 用递归，本地 DNS 问根/TLD/权威用迭代。
  • 记录类型：A、AAAA、CNAME、MX、NS、TXT，CNAME 常用来指 CDN 调度域名。
  • TTL 管缓存寿命，短则生效快查询多，长则相反，故障切换前先调短 TTL。
  • 被劫持或污染就上 DoH 或 DoT，加密查询换公共 DNS 服务器。

📈 拔高

hosts 优先只是主流 OS 的默认行为，次序由系统配置决定，RFC 没有强制。UDP 响应没超上限就不切 TCP：无 EDNS0 是 512 字节，带 EDNS0 通常到 4096，区域传送固定走 TCP。

💡 主动加分的追问准备

追问 答案
为什么 DNS 用 UDP 而不是 TCP？ 查询报文很短，一个 UDP 包就够，UDP 还更快。响应超上限才回退 TCP：无 EDNS0 是 512 字节，有 EDNS0 通常到 4096，区域传送固定走 TCP。丢包靠应用层超时重传补。
hosts 文件和 DNS 是什么关系？ 主流 OS 默认先查 hosts 再查 DNS，次序由系统配置决定，RFC 没有强制。开发时改 hosts 把域名指向 127.0.0.1 做本地调试就是这个原理。
DNS 查询慢怎么优化？ 四招：① 换靠谱的 DNS 服务器，运营商不行就用公共 DNS。② 用 dns-prefetch 预解析可能访问的域名。③ 接入 HTTPDNS 绕过本地 DNS，规避运营商劫持和解析慢。④ 适当延长 TTL 减少查询次数。
一个域名能同时有 A 记录和 CNAME 记录吗？ 不能，同一域名 A 与 CNAME 互斥。CNAME 表示「这个名字是另一个名字的别名」，同时存在其他记录会产生解析歧义。但子域名可以：主域名用 A 记录，www 子域用 CNAME 指向 CDN。

❌ 千万别说的话

  • ❌「DNS 服务器是递归帮我把每一级都问一遍根服务器」：根/TLD/权威只做指路（迭代），递归由本地 DNS 承担
  • ❌「DNS 就是个查 IP 的翻译工具」：它还承担负载均衡分发流量的职责

[35] 简单谈谈你对 CDN 的理解？

🎬 面试现场

面试官：CDN 到底是解决了什么问题？它的原理你讲得清楚吗？

⚠️ 翻车点

  • 只说「CDN 就是缓存」，讲不出回源机制、GSLB 调度和缓存策略的选型
  • 把 CDN 说成单纯的静态资源加速，忽略它还能做动态加速、WAF、DDoS 防护

📝 回答重点

  • CDN 就是把内容缓存到就近边缘节点，命中直接回，未命中才回源。
  • 流程：智能 DNS 把用户调度到最近节点，节点查缓存，命中即返回。
  • GSLB 综合地理位置、延迟、节点负载、运营商线路挑最优节点。
  • 缓存三类：强缓存放图片和静态文件，协商缓存看 ETag，API 用短缓存。
  • 更新三招：主动刷新 URL、预热推送热点、文件名带版本号强制更新。
  • 好处是降延迟、省带宽、抗 DDoS，WAF 和边缘计算也能挂在节点上。

📈 拔高

命中率、TTFB 这些数字是常见目标值，因业务而异，别背成硬指标。回源也分策略：按需、预热、分层回源，边缘节点先找区域节点再找源站。

💡 主动加分的追问准备

追问 答案
缓存规则怎么配？ 按文件类型区分：图片和图标配长缓存 30 天，css/js 配 7 天，html 配 1 小时。动态资源用短时间或不缓存，用户私有数据明确设置不缓存。
除了静态资源，CDN 还能干什么？ 动态加速做路由优化、连接复用和智能压缩。直播点播做 HLS/DASH 分片和自适应码率。API 加速做响应缓存、请求合并、智能路由。
怎么解决跨域？ 在 CDN 节点上配置响应头 Access-Control-Allow-Origin 和 Access-Control-Allow-Methods，配 OPTIONS 预检的放行规则。
哪些资源适合上 CDN？ 静态资源长时间缓存，动态资源短时间或不缓存，用户私有数据不缓存。配合版本号或哈希值做更新，启用 Gzip/Brotli，图片用 WebP/AVIF。

❌ 千万别说的话

  • ❌「CDN 就是把网站都镜像一份到各个节点」：准确说法是按需缓存 + GSLB 调度，不是全量镜像
  • ❌「CDN 只能加速静态资源」：动态加速、边缘计算、WAF 防护都在 CDN 节点上做

[36] 从网络角度来看，用户从输入网址到网页显示，期间发生了什么？

🎬 面试现场

面试官：你在浏览器地址栏敲下域名、按回车，到页面渲染出来，中间到底发生了什么？你按协议顺序给我捋一遍。

⚠️ 翻车点

  • 把顺序背成「ARP → TCP → IP → DNS」，实际是 URL 解析 → DNS → TCP → TLS → HTTP，ARP 属于建链时的链路层环节
  • 把端口号说反（源端口是客户端随机生成，目标端口才是 80/443）
  • 把协议栈顺序倒过来说（IP → TCP → HTTP）

📝 回答重点

  • 先看步骤：URL 解析、DNS 拿 IP、TCP 三次握手，HTTPS 站点再加 TLS 握手，之后才发 HTTP 报文。
  • DNS 我一般这么答：先查浏览器缓存，再查系统缓存和 hosts，都没有才问本地 DNS；本地 DNS 也没有，就做根 → 顶级域 → 权威三级查询，回来每层都缓存一份。
  • 三次握手时端口就定好：源端口内核从临时端口池随机分配，目标端口 HTTP 80、HTTPS 443。
  • 封装往下发：网络层加 IP 头，链路层用 ARP 解析下一跳网关的 MAC、加帧头，物理层交给路由器逐跳转发。
  • HTTPS 站点别漏 TLS 握手：1.2 全握手 2 个往返，1.3 只要 1 个往返，握手完才轮到 HTTP 报文。
  • 服务端回 HTTP 响应，浏览器解析渲染就出页面；想强制 HTTPS 就让服务端回 301。

📈 拔高

浏览器可能内置异步 DNS 解析器，实现顺序有差异；做递归解析的是本地 DNS，根、顶级域、权威服务器只做迭代。301 会被浏览器长期缓存，HSTS 能省掉第一次明文跳转。

💡 主动加分的追问准备

追问 答案
DNS 属于哪一层？完整流程是什么？ 应用层协议。浏览器缓存 → OS 缓存和 hosts → 本地 DNS → 根 DNS 返回 TLD 服务器地址 → TLD 返回权威服务器地址 → 权威返回目标 IP → 本地 DNS 缓存并回给客户端。
服务端怎么知道数据该交给哪个应用？ 靠传输层端口号。每个协议（TCP/UDP）用端口号标识不同应用或服务，服务端监听特定端口接收数据。所以三次握手阶段双方就需要在 SYN 里协商好目标端口。
服务器 ping 不通但 HTTP 能请求成功，为什么？ 会。ping 用的是网络层 ICMP，HTTP 用传输层 TCP。服务器防火墙只禁止了 ICMP 而没禁 TCP，就会出现 ping 不通但 HTTP 正常。
连一个不存在的 IP 会怎样？ 分情况。局域网内不存在的 IP，ARP 请求无人应答，帧发不出去，connect 一直阻塞到内核超时报错。非局域网的不存在 IP，路由器转发后 SYN 收不到确认，触发超时重传，重传次数用尽后连接被释放。
连一个 IP 存在但端口不存在的服务呢？ 服务端没监听该端口，收到 SYN 后回 RST 报文，客户端收到 RST 直接断开连接。UDP 则没有 RST，会在网络层由 ICMP 协议回报「端口不可达」。
页面一直转圈不出图，怎么排查？ 逐层抓包排查。先看本机能否访问别的站点，能就查 DNS 有没有解析出 IP，再看三次握手是否完成，没完成就上服务端用 ps 看进程、netstat 看端口。握手正常就看响应码，404 查 URL，500 查服务端日志，200 就开 F12 看前端渲染。
内核是怎么收到网络包的？ 网卡以 DMA 把帧直接写进内存并发硬中断，中断处理只做最少的事，然后发起 NET_RX_SOFTIRQ 软中断。ksoftirqd 内核线程每个 CPU 一个，通过 poll 轮询收包交给协议栈，TCP 包最终进用户 socket 的接收队列。代码位置：网卡驱动在 driver/net/ethernet/intel，协议栈在 net 目录。

❌ 千万别说的话

  • ❌「先 ARP 拿到 MAC 地址再解析域名」——ARP 是拿到 IP 之后、建链时才在链路层用到
  • ❌「HTTPS 就是 HTTP 加个加密」——中间多了独立的 TLS 握手，1.2 全握手 4 段通信 2 个往返，1.3 只要 1 个往返，握手完才发 HTTP 报文

[37] 常见的登录鉴权方式有哪些？各自的优缺点是？

🎬 面试现场

面试官：登录鉴权这块你们是怎么做的？现在主流有哪几种方案，各自适合什么场景？

⚠️ 翻车点

  • 把 Cookie、Session、Token 当成同一层面的东西比较
  • 说 Token 认证「安全性高、无懈可击」，不说它签发后难以撤销的短板

📝 回答重点

  • 主流四种：Session-Cookie、Token、OAuth2.0、API Key，答之前先点破区别在状态放服务端还是客户端。
  • Session-Cookie 把状态放服务端，Cookie 只负责运 Session ID；分布式场景要 Session 复制、粘性会话或外置 Redis。
  • Token 自带签名和用户信息，服务端不存状态、天然适合分布式；短板是签出去收不回，靠短有效期加 Refresh Token 兜底。
  • OAuth2.0 是授权协议，第三方登录只是它最常见的用法；互联网产品做登录认证，用的是基于它的 OIDC。
  • API Key 实现最简单，适合内部微服务互调；一旦泄露等于门户大开，要配 IP 白名单和签名验签。

📈 拔高

授权码模式第一步重定向要带 client_id、redirect_uri、scope、state 四个参数，state 回调时原样带回校验，防的是 CSRF。授权码走浏览器地址栏、access_token 由后端直连换取，所以 client_secret 和 token 都不暴露给第三方页面。

💡 主动加分的追问准备

追问 答案
Session 分布式怎么解决？ 三选一：Session 复制（性能差）、粘性会话（Nginx 固定转发，机器挂了会丢）、Session 外置到 Redis（主流，Spring Session 就是这个思路）。
access_token 和 refresh_token 有什么区别？ access_token 有效期短（一般几小时），频繁传输出去容易泄露，只用来实际请求资源。refresh_token 有效期长（几天甚至几个月），只在 access_token 过期时换新的，传输次数少，泄露风险低。
API Key 泄露了怎么办？怎么防？ 应急是立刻轮换、作废旧 Key。预防靠四招：Key 只在后端用，绝不出现在前端代码里。配 IP 白名单只认特定来源。用签名验签，参数加时间戳一起签名，Key 本身不传输。定期轮换，降低泄露风险。
Token 认证怎么做细粒度权限？ access_token 本身短时效，泄露影响窗口有限。服务端每次请求都校验权限，配合 refresh_token 续期设计，细粒度控制靠的就是这两层。

❌ 千万别说的话

  • ❌「Session 和 Token 就是两种不同的存储方式」——它们不在同一层，核心区别是状态存在服务端还是客户端
  • ❌「OAuth2.0 就是第三方登录」——它本质是授权协议，第三方登录只是它最常见的应用场景

六、面试前 10 分钟速查

如果只剩十分钟，扫这一页。

必须张口就来的定义

  • 发送窗口 = **min(cwnd, rwnd)**，cwnd 是拥塞控制算的，rwnd 是接收方通告的
  • TCP 可靠性四件套：编号、确认、重传、窗口
  • 三次握手的首要目的是防止历史连接建立，不是确认收发能力
  • ISN = 时间递增（每 4 微秒 +1）+ 随机，只说随机就答不完整
  • DNS：客户端到本地 DNS 用递归，本地 DNS 到根/TLD/权威用迭代
  • JWT 的 Payload 是 Base64 编码，签名只防篡改不防偷看

最该记住的易错点

  1. HTTP/2 的多路复用解决的是 HTTP 层队头阻塞，TCP 层的还在
  2. HTTPS = TCP 三次握手 + TLS 四次通信，别混成三次
  3. TIME_WAIT 属于主动关闭方，客户端和服务端都可能出现，不是客户端特有
  4. 快速重传是数据驱动（3 个重复 ACK），超时重传是时间驱动（RTO）
  5. tcp_fin_timeout 管的是 FIN_WAIT_2，不是 TIME_WAIT
  6. ARP 只在同一广播域工作，跨网段每跳 MAC 都变、IP 不变
  7. JWT 放 localStorage 是为了规避 CSRF，代价是 XSS 可窃取

数字 含义
