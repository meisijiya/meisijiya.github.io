一、开场三连：进程与线程

面试开场永远从最”基础”的地方切，因为这里最能看出你是不是只会背。

1. 操作系统中的进程有哪几种状态？

🎬 面试现场

面试官（推了推眼镜）：进程有哪几种状态？

⚠️ 翻车点：张口就答”就绪、运行、阻塞”。这答案不算错，但会让面试官觉得你在背书——因为他要问的一定是这个。

📝 现场作答

先给完整的五状态模型，再补两个扩展态：

  • 基础五态：新建 → 就绪 → 运行 → 阻塞 → 终止

    • 就绪：已具备运行条件，在就绪队列排队等 CPU
    • 运行：正在 CPU 上执行
    • 阻塞：等待某个事件（如磁盘 I/O），主动让出 CPU
    • 内存紧张时派生：就绪挂起（数据已换出磁盘，具备换入条件）和阻塞挂起（连换入条件都不具备）

  • Linux ps aux 的 STAT 列就是这套模型的实战映射：

    状态 含义
    R Running，运行中或就绪
    S 可中断睡眠，等的是”能被信号打断”的事件
    D 不可中断睡眠，等的是磁盘 I/O 这类打不断的事件
    Z 僵尸，子进程已死、父进程未 wait
    T 停止，被信号挂起

  • Linux 调度由 CFS 完成，按虚拟运行时间 vruntime 排序，规则只有一句：谁欠的时间多谁先跑

💡 主动加分的追问准备

面试官追问 你的答案
为什么僵尸进程不吃 CPU 还要处理？ 它不占 CPU 不占内存，但 PID 和 PCB 还在。PID 有上限，几千个僵尸就能让系统 fork 失败。父进程正确处理 SIGCHLD 即可回收
什么是孤儿进程？ 父进程先退出，内核把它托管给 PID 为 1 的 init 自动清理，本身无害
阻塞态能直接跳回运行态吗？ 不能，必须先回就绪态排队。状态机里没有这条边

❌ 千万别说的话

  • “阻塞态被唤醒后直接变成运行态”——必须过就绪态
  • “kill -9 能杀掉 D 状态进程”——它是不可中断睡眠，信号 pend 着，等 I/O 完成才会处理
  • “孤儿进程是异常”——内核会自动收尸

2. 线程和进程有什么区别？

🎬 面试现场

面试官：进程和进程的区别？

⚠️ 翻车点：背出”进程是资源分配单位、线程是调度单位”就停下了。这是 20 年前的标准答案，现在只值一半分——因为它没回答 Linux 上到底怎么实现的。

📝 现场作答

先给经典定义，然后立刻下沉到内核实现，这是分水岭：

  • 经典定义：进程是资源分配的基本单位，线程是调度执行的基本单位

  • Linux 的真相：内核对线程没有任何特殊处理

    • 二者统一由 task_struct（include/linux/sched.h）描述
    • pid 是线程 ID，tgid 是所属进程 ID；getpid() 返回的是 tgid
    • 创建进程 fork 只传 SIGCHLD，地址空间 mm_struct、文件系统信息 fs_struct、文件表 files_struct 全部独立申请
    • 创建线程 pthread_create → glibc create_thread → clone，传入 CLONE_VM | CLONE_FS | CLONE_FILES 三件套，与父进程共享这三者，内核就不再单独申请了
    • 底层殊途同归：kernel_clone → copy_process → wake_up_new_task

  • 判断一个 task 到底是进程还是线程，只看一件事：有没有独立地址空间

  • 优先级字段：static_prio 100139（nice 调它）、rt_priority 099、prio/normal_prio 由调度策略推导

  • 内核线程的 mm_struct 为 NULL，所以准确叫法是”内核线程”而非”内核进程”

💡 主动加分的追问准备

面试官：那 coroutine 呢？

Go 的 goroutine 更轻，是因为它连内核都进不去——切换只是换栈指针和寄存器，栈初始才 2KB。快的原因有三：栈小、无系统调用、调度器用 work stealing + 本地队列免锁。只答”用户态不用系统调用”是不完整的。

❌ 千万别说的话

  • “Linux 为线程设计了一套轻量级进程机制”——没有，就是共享资源的 task_struct
  • “进程和线程是完全不同的东西”——Linux 上相同点远大于不同点
  • CLONE_VM/CLONE_FS/CLONE_FILES 三个 flag 的含义记反

3. 什么是用户态和内核态？

🎬 面试现场

面试官：用户态和内核态的区别？为什么需要区分？

⚠️ 翻车点：”用户态不能访问硬件”——这句话一说出口就减分，因为存在一堆合法例外。

📝 现场作答

  • 本质是 CPU 的特权级划分：x86 通过 CS 寄存器低两位的 CPL 判断，内核态 CPL=0，用户态 CPL=3

  • 触发态切换的三种情况：

    类型 例子 同步性
    系统调用 read/write/fork/open 同步
    异常 除零、缺页、非法指令 同步
    硬件中断 时钟、键盘、网卡 异步

  • x86-64 系统调用流程：调用号放 rax、参数放 rdi/rsi/rdx → 执行 syscall → 内核查系统调用表 → 结果回 rax → sysret 切回

  • 为什么要分：宏内核（Linux、FreeBSD）性能高但驱动 bug 可能搞崩全系统；微内核（Minix、QNX、seL4）内核态代码量小、稳定性高，代价是 IPC 切换开销大

  • 一次系统调用几百到几千个 CPU 周期，慢在三处：上下文切换、权限检查、缓存与 TLB 失效（有时后者代价更大）

💡 主动加分的追问准备

面试官：用户态就真的碰不到硬件？

有三条合法路径：

  1. iopl() / ioperm() 开放特定 IO 端口
  2. mmap() 直接映射设备内存，如显卡的 DRI
  3. DPDK 直接映射网卡内存，绕过内核协议栈

还有个细节能显水平：**System.currentTimeMillis() 在现代 Linux 上走 vDSO，在用户态直接读时钟，通常根本不产生系统调用**。

另外，内核态出 bug 不一定蓝屏——轻微 Oops 只杀当前进程，只有数据结构破坏、死锁、栈溢出才是 Kernel Panic。

❌ 千万别说的话

  • “用户态绝对无法访问硬件”——有 iopl、mmap 设备内存、DPDK
  • “系统调用就是函数调用”——它涉及特权级切换和寄存器上下文保存

4. 进程之间的通信方式有哪些？

🎬 面试现场

面试官：进程间通信有哪几种？

⚠️ 翻车点：报菜名式列一遍就停。面试官要的是每种方式的适用边界。

📝 现场作答

给一张选型表，比口头罗列有效得多：

方式 边界/消息语义 数据量 关键特性
管道 字节流，无边界 内核环形缓冲默认 64KB 匿名管道仅限亲缘进程；mkfifo 命名管道可跨无关进程
消息队列 有边界，支持按类型取 单条默认上限 8KB System V msgget/msgsnd/msgrcv，现代推荐 POSIX
共享内存 无语义 零拷贝，几 MB 可比管道快 10 倍以上 shm_open → ftruncate → mmap；内核不提供任何同步
信号量 无 无数据 本质是计数器，P 减一/V 加一，减到 0 阻塞
信号 无 不能带数据 纯异步通知，只传信号编号
Unix 域套接字 有边界 大 不走网络协议栈，且能传递文件描述符
  • 共享内存是唯一零拷贝的：多进程页表指向同一块物理内存
  • 共享内存也是最危险的：必须自己配信号量/互斥锁，否则并发写直接乱套
  • Unix 域套接字的实战：/var/run/mysqld/mysqld.sock、/var/run/docker.sock

💡 主动加分的追问准备

面试官：管道和消息队列的核心区别？

管道是字节流，一次 write 100 字节可能被对方分 3 次读完，需要应用自己定义分隔符；消息队列有消息边界，要么整条读完要么不读。

❌ 千万别说的话

  • 把”信号”和”信号量”混为一谈——一个是异步通知，一个是同步计数原语
  • 说共享内存”又快又安全”——它同时最快也最危险

5. 什么是 CPU 缓存一致性协议 MESI？

🎬 面试现场

面试官（Java 背景，通常从这里切进 JMM）：MESI 讲讲？为什么需要它？

⚠️ 翻车点：把 MESI 讲成”硬件层的东西，和 Java 无关”。这句话直接断掉你和后面 volatile 的联系。

📝 现场作答

核心就一句话：多核各自缓存一份数据，靠给缓存行打标签来协商谁是正版。

  • 四种状态：

    状态 含义 记忆法
    M Modified 独占且已改，是脏数据，未写回主存 改过的，脏
    E Exclusive 独占未改，与主存一致 我一个人有，没人改
    S Shared 多核共享且一致 大家都有，都没改
    I Invalid 本地失效，需重新拉取 作废了

  • E 状态存在的意义是省一次总线广播：只有自己持有时，E → M 无需通知其他核

  • 协作靠嗅探：Core A 发 Invalidate，Core B 嗅探到后把自己置 I 并回确认，A 收到确认才真正修改。核数多了总线带宽不够，服务器 CPU 改用目录协议避免广播风暴

  • Store Buffer 是关键：让 A 不必等确认就能继续执行，于是产生了”本核认为改了、别的核还没变”的可见性问题——这正是 Java volatile 和内存屏障要解决的硬件根源

  • 变种：MOESI（AMD，加 Owner 态支持脏数据直共享）、MESIF（Intel，加 Forward 态只让一个 S 核响应读请求）

💡 主动加分的追问准备

伪共享是这块的高频深挖题：

  • 缓存行通常 64 字节，两个毫不相关的变量落进同一行，会互相触发失效
  • Java 8 用 @Contended 解决（需加 -XX:-RestrictContended），JDK 内部的 LongAdder、Striped64 都用了

面试官：volatile 能保证原子性吗？

不能。它只保证可见性 + 禁止重排，i++ 这种读改写依然不原子。

❌ 千万别说的话

  • “volatile 保证原子性”——M/V 级别的经典错误
  • 把伪共享说成”两个线程竞争同一变量”——伪共享是不相关的变量互相拖累

二、调度、中断与 CPU 指标

进程状态讲完，面试官通常顺势切到”那谁决定哪个进程跑”，然后一路问到你答不出来为止。

6. 进程的调度算法你知道吗？

🎬 面试现场

面试官：进程调度算法有哪些？

⚠️ 翻车点：只背 FCFS/SJF/RR 三个。真正拉开差距的是 MLFQ、HRRN，以及 Linux 实际用的 CFS。

📝 现场作答

按”调度思想演进”来讲，逻辑会非常顺：

  • FCFS 先来先服务：简单，但队头一个大任务能让后面一堆 10ms 小任务全干等
  • SJF 最短作业优先：平均等待时间最优，但需要预知执行时间（现实中不可得），抢占版是 SRTF
  • 优先级调度：坑在饥饿——低优先级任务永远排不上队
  • RR 时间片轮转：固定时间片（如 10ms）保证响应性
  • MLFQ 多级反馈队列：3~5 个队列，典型配置 Q0/8ms（交互式、新进程）、Q1/16ms（普通计算）、Q2/32ms（CPU 密集后台）。新进程进 Q0，用完时间片没跑完降一级，并定期提回 Q0 防饿死
  • HRRN 高响应比优先：响应比 R =（等待时间 + 服务时间）/ 服务时间，等待越久响应比越高，短任务先跑、长任务最终也会被调度，适合批处理
  • CFS（Linux 2.6.23 至今）：不用固定时间片，按最小 vruntime 选取，红黑树组织，取出 O(1)、插入 O(log n)；nice 值 -20~19，差 5 时 CPU 时间比例约差 3 倍
  • 实时调度：SCHED_FIFO 和 SCHED_RR，实时进程不参与 CFS，只要实时队列非空就一直跑，设多了会把普通进程饿死
  • 新内核默认调度周期延迟 24ms、最小调度粒度 3ms，可运行进程超 8 个时周期变 3ms × 进程数；交互式系统 10~20ms 较合适

💡 主动加分的追问准备

优先级反转几乎必问：

低优先级进程持有锁，高优先级进程等锁时，被中等优先级进程抢占了，高优先级进程就间接被中等优先级卡住。

火星探路者号就是因为没做优先级继承出过事故。解决方案是优先级继承：让持锁的低优先级进程临时提升到等锁的高优先级进程同级别。

MLFQ 防 gaming 的细节也常追问：不能只看单次时间片有没有用完，现代实现（BSD、Solaris）按各队列累计运行时间超阈值才降级。

❌ 千万别说的话

  • “Linux 用时间片轮转”——Linux 用的是 CFS 的 vruntime 抢占，没有固定时间片
  • “SJF 最好所以都用 SJF”——需要预知执行时间，现实中不可用

7. 操作系统在进行线程切换时需要进行哪些动作？

🎬 面试现场

面试官：线程切换要做哪些动作？开销大吗？

📝 现场作答

四步，标准答案：

  1. 保存当前线程上下文到 TCB
  2. 修改线程状态（Running → Ready，Ready → Running）
  3. 调度器选出下一个线程
  4. 恢复目标线程上下文

线程上下文包含三块：

  • CPU 寄存器状态：PC、SP、x86-64 下 16 个通用寄存器 + 浮点/向量寄存器
  • 程序状态字 PSW：中断开关、特权级、条件码
  • 线程栈：用户栈 + 内核栈（两个都要保存，否则调用链断裂）

TCB 即 struct task_struct，关键字段：线程状态、PC、寄存器内容、SP、优先级、Thread ID、调度信息（策略 + 时间片）。

开销的答案要说到根因上：线程切换比进程切换快的根本原因是内存映射不动。

  • 进程切换要改 CR3 换页表，TLB 全部失效，一次 TLB miss 代价是几十到几百个 CPU 周期
  • 线程切换共享地址空间，TLB 映射可继续用
  • 实测同进程线程切换比跨进程快 5~10 倍，Linux 上典型耗时 1~10 微秒
  • goroutine 更轻：约几百纳秒

💡 主动加分的追问准备

追问 答案
跨进程的线程切换也快吗？ 不快，本质就是进程切换，地址空间变了页表和 TLB 都得换
怎么排查切换开销？ vmstat 看 cs 列，pidstat -w 看单进程；每秒几万次正常，几十万次通常意味着锁竞争激烈或线程过多
怎么优化？ 短临界区用自旋锁避免切换、CPU 亲和性绑定（DPDK）减少跨核缓存失效、批量处理（Netty EventLoop）降低切换频率

❌ 千万别说的话

  • “自旋锁是万能优化”——临界区长会白烧 CPU，单核上持锁线程根本没机会跑

8. 什么是软中断、什么是硬中断？

🎬 面试现场

面试官：软中断和硬中断有什么区别？

⚠️ 翻车点：答成”硬中断是硬件触发的，软中断是软件触发的”。这是最常见的错答——触发方和实现方是两回事。

📝 现场作答

先讲中断的价值：化主动为被动。没有中断，CPU 只能轮询判断条件是否成立；有了中断，CPU 可以先干别的，条件成立再来唤醒。

然后纠正那个常见误解：

  • 按触发方式分类：中断（外部设备，异步）、异常（CPU 执行指令时检测到的反常条件，同步）、INT 指令（软件主动指定中断号，如 INT 0x80 就是 Linux 系统调用入口）
  • 按实现机制分类：上面三者全是硬中断——硬/软看的是谁来检测和分发，不是谁触发

所以正确定义是：

硬中断 软中断
检测方 CPU 硬件 Linux 软件（ksoftirqd 守护进程）
发现时机 每个指令周期最后一个周期采样中断向量表 轮询软中断标记位数组，某位为 1 就取对应处理函数
top 中 hi 列 si 列

软中断存在的意义是硬中断处理程序不能做太久：它可能临时关中断，不及时返回会导致其他中断（鼠标键盘）响应延迟甚至丢失。

网卡收包因此拆成上下半部：

  • 上半部：硬中断处理程序快速跑完，置软中断标记位（注意是置标志位，不是给 CPU 发中断信号）
  • 下半部：软中断处理程序按协议栈逐层解析后交给应用

面试官：异常为什么也是硬中断？

因为异常是 CPU 自己给自己中断号，不存在外部设备参与，但检测和分发仍然由硬件完成。容易被误归到软件侧。

❌ 千万别说的话

  • “软中断是软件触发的中断”——那是 INT 指令；软中断的触发源仍是硬件事件，只是处理环节被软件化延迟执行

11. CPU 使用率和 CPU 负载指的是什么？

🎬 面试现场

面试官（可能结合运维场景）：CPU 使用率和 CPU 负载有什么区别？

⚠️ 翻车点：把 load average 当成”排队任务数”直接背。它是指数衰减平滑的结果，不是瞬时快照。

📝 现场作答

先给定义，再给数据来源：

  • CPU 使用率：某时间窗口内 CPU 真正干活的时间占比

    • 原始数据在 /proc/stat，字段从左到右：user、nice、system、idle、iowait、irq、softirq、steal、guest、guest_nice
    • 计算方式：采样两个时间点做差，cpuUsage = 100.0 * (totalDiff - idleDiff) / totalDiff
    • top/htop 只是每隔几秒采样一次算差值

  • CPU 负载：等待 CPU 的任务数量（含运行中 + 排队中），分 1/5/15 分钟三个指数滑动平均

    • load = load * exp(-5/60) + active_tasks * (1 - exp(-5/60))
    • 三个时间窗口对应 exp(-5/60)、exp(-5/300)、exp(-5/900)，作用是平滑掉瞬时尖峰、反映趋势

四种组合要给面试官一张判定表：

使用率 负载 结论
高 高 计算能力瓶颈
低 高 大量 I/O 密集任务或锁竞争
高 低 调度良好，无积压
低 低 资源未充分利用

💡 主动加分的追问准备

两个细节最能显水平：

  1. 负载统计包含 I/O 等待的任务——这就是”低使用率 + 高负载”的成因
  2. 多核要除以核心数解读：8 核机器负载 8.0 表示每核刚好一个任务，16.0 表示每核还排着一个

完整排查链路：

  1. 告警负载高但 CPU 才 30% → vmstat 1 5 看 b 列（等待 I/O 的进程数）和 wa 列（I/O 等待占 CPU 百分比）
  2. b=15、wa=65% 就是典型磁盘瓶颈
  3. 再用 iostat -x 1 看 await（正常个位数毫秒）和 %util（接近 100% 说明磁盘打满）
  4. iotop 定位具体进程

❌ 千万别说的话

  • “使用率高就是负载高”——线上 4 核机器使用率 20%、平均负载 8 的情况大量存在，此时系统已经出现瓶颈
  • 把 15 分钟负载当瞬时值——趋势比绝对值重要：15 分钟高于 1 分钟说明系统正在恶化

22. 听说过 CFS 吗？

🎬 面试现场

面试官（顺着调度深挖）：CFS 讲讲？

📝 现场作答

  • 定义：CFS（Completely Fair Scheduler，Linux 2.6.23 起替代 O(1)）用 vruntime 虚拟运行时间衡量”欠多少 CPU”，把可运行进程放进按 vruntime 排序的红黑树，每次取最左节点运行

  • 调度循环：取最左 → 运行使 vruntime 增长 → 时间片用完或主动让出 → 更新 vruntime 重插入 → 再次取最左；插入/删除均 O(log N)

  • 计算公式：vruntime 增量 = 实际运行时间 × (NICE_0_WEIGHT / 进程权重)，其中 NICE_0_WEIGHT = 1024

    nice 权重 相对 CPU
    -20 88761 ≈ 87 倍
    0 1024 基准
    19 15 ≈ 1/68

  • 为什么替代 O(1) 调度器：O(1) 把进程分进 140 个优先级队列，交互式进程识别粗糙，常把”正在等输入”的进程误判为 CPU 密集型而降优先级，桌面用起来卡顿。CFS 不猜类型——睡眠期间 vruntime 不增长，醒来天然靠左

  • 长睡进程的特殊处理：睡很久醒来时 vruntime 会被重置为”当前队列最小 vruntime − sched_latency“，避免一觉醒来霸占 CPU

  • 多核：每 CPU 一棵红黑树，由 load_balance 评估负载差异，超阈值才迁移，避免频繁迁移丢失缓存

💡 主动加分的追问准备

面试官：CFS 的最新进展？

Linux 6.6（2023-10）引入 EEVDF（最早虚拟截止时间优先）替代 CFS，为请求时间片小的任务算 deadline，改善延迟敏感场景的体验。容器大规模场景下红黑树变深、O(log N) 开销明显，这正是 EEVDF 要解决的问题之一。

❌ 千万别说的话

  • “CFS 保证低延迟”——它目标是公平而非低延迟，硬实时得用 SCHED_FIFO/SCHED_RR
  • “死循环进程会卡死全系统”——时间片有上限，多核下还能分散到其他核

三、内存管理与地址空间

调度讲完，面试官通常会问一句”那进程是怎么拿到内存的”，顺势进入这块。这部分最能区分”看过源码”和”只背过书”。

9. 为什么要有虚拟内存？

🎬 面试现场

面试官：为什么要引入虚拟内存？

⚠️ 翻车点：答”为了隔离进程和扩大可用内存”。太表面，答不到 VMA 这一层。

📝 现场作答

从数据结构讲起，这是加分点：

  • 每个进程的 task_struct 挂一个 mm_struct，表示虚拟地址空间
  • 已分配的每段地址范围由 vm_area_struct（VMA）表示，vm_start/vm_end 界定区间，多个 VMA 互不交叉，加起来就是占用情况
  • 物理页是按需分配的：进程加载时只拿地址空间范围，物理页等实际访问触发缺页中断时才向伙伴系统申请

VMA 管理器的演进值得主动讲，说明你真读过内核：

  • 6.1 之前：红黑树 + 双向链表。红黑树（mm_rb）保证查询/插入/删除 O(log n)，双向链表（mmap）加速遍历。缺点是红黑树平衡操作牵连多节点且修改要同步链表，必须加锁（mmap_sem），多线程下锁争抢严重
  • 6.1 起：替换为 maple tree（mm_mt，ma_root 为 __rcu *），从设计上就基于 RCU 无锁读，减少锁开销

缺页处理链路（面试官爱顺着代码问）：

  1. do_user_addr_fault（arch/x86/mm/fault.c）先 find_vma(mm, address) 找到所属 VMA
    • 6.1 前遍历双向链表并配合缓存；6.1 后用 MA_STATE 宏构造查找状态 + mas_walk 在 maple tree 中查询
  2. handle_mm_fault → __handle_mm_fault，把 vma、address 及各级页表项统一收进参数对象 struct vm_fault（长参数列表整合成参数对象是 6.1 内核常见重构手法）
  3. Linux 用四级页表 pgd / pud / pmd / pte，逐级检查或申请
  4. 落到 handle_pte_fault 分流：文件映射缺页、swap 缺页、写时复制缺页、匿名映射缺页……普通变量走 do_anonymous_page → alloc_zeroed_user_highpage_movable → 伙伴系统 alloc_pages

💡 主动加分的追问准备

面试官：堆和栈的物理内存什么时候分配？

进程加载时只分配地址空间范围（VMA），物理页等实际访问触发缺页中断时才申请。所以申请了大数组但没写入，不会立刻占物理内存。

❌ 千万别说的话

  • 以为 malloc/申请内存时就分配了物理内存——实际只拿到一个 VMA 地址区间
  • 忽略 find_vma 这一步——缺了它就无法判断地址是否合法、是否属于当前进程

10. 什么是分段、什么是分页？

🎬 面试现场

面试官：分段和分页有什么区别？

📝 现场作答

先给本质差异，再讲历史演进：

分段 分页
划分依据 程序的逻辑结构（代码/数据/堆栈） 固定大小物理单位
段/页大小 不固定 固定 4KB
碎片类型 外部碎片 内部碎片
用户可见性 对程序员可见（需指定段） 透明

历史脉络讲出来会显得很扎实：

  • 分段来自 8086：16 位寄存器 + 20 位地址总线，用「段基址左移 4 位（即乘 16）+ 段内偏移」访问 20 位空间。因一段仅 64KB，必须不断换段基址才能访问全空间
  • 80286 引入保护模式与 GDT：段寄存器改存”选择子”（段描述符索引 + TI + RPL），通过 RPL 与目标 DPL 比较判断访问权限，实现进程间地址隔离；实模式无权限校验
  • 80386 起通用寄存器和地址总线都是 32 位，分段失去意义，但为向前兼容保留，段基址全设 0 即平坦模式——这是 Linux 的做法

分页的动机就是碎片：200MB 内存跑 LOL/Chrome/微信后剩 30MB 连续空闲都装不下新程序，只能把 Chrome 换出到磁盘再重新装入。按 4KB 分页后只需换入用到的页。

多级页表解决页表自身浪费：32 位 4GB 空间按 4KB 分页超百万页，每页表项 4 字节，单进程页表就要 4MB，100 个进程即 400MB。改用多级页表后只有用到的页表项才分配内存——32 位一般两级，64 位四级甚至五级。

TLB 缓存最近使用的页表项，命中率一般 99% 以上；未命中才走内存页表。进程切换必须刷新 TLB，因为各进程页表不同——这正是频繁切换进程开销大的原因。

页面置换：FIFO 最简单但会把热点页换出；LRU 效果好但记录访问时间开销大；Linux 用近似 LRU，维护 active/inactive 两条链表，inactive 链表末尾优先换出。

💡 主动加分的追问准备

  • 缺页中断与普通中断不同：普通中断处理完返回下一条指令，缺页中断处理完要重新执行触发它的那条指令
  • 大页（Linux 支持 2MB/1GB）减少页表项、降低 TLB miss，但内部碎片变大——只需 5KB 数据也占满一个大页。数据库、虚拟机才用

❌ 千万别说的话

  • “Linux 是段页式系统”——分段在 Linux 上是兼容遗留，实际按平坦模式运行，真正干活的是分页

21. 什么是物理地址，什么是逻辑地址？

🎬 面试现场

面试官：物理地址和逻辑地址的区别？地址转换是怎么做的？

📝 现场作答

  • 物理地址是内存芯片上的真实位置；逻辑地址是程序看到的地址
  • MMU 依据页表翻译，对程序透明，因此进程间天然隔离

转换流程要给具体例子：

进程切换时，OS 把新进程的页表基址写入 CPU 的 CR3 寄存器。

逻辑地址的三大好处：

  1. 位置无关加载——同一个二进制可以加载到不同物理位置
  2. 进程隔离——野指针最多触发一次缺页异常，不会读到别的进程
  3. 虚拟内存——32 位程序可以”看到” 4GB 空间

TLB 是 CPU 内部的页表项缓存，命中直接出物理地址，命中率可达 99%+；否则一次逻辑访问变成两次内存访问。多级页表在 32 位下能让页表占用节省 90%+，64 位用四级页表。

❌ 千万别说的话

  • “用户态程序可以访问物理地址”——Linux 的 /dev/mem 需要 root，生产环境一般禁用
  • 把”分段”当成 x86-64 的实际内存管理机制——分段已被架空

23. 负数的二进制如何表示？

🎬 面试现场

面试官（可能从 Java 类型转换切入）：负数的二进制怎么表示？

📝 现场作答

  • 用补码：正数按位取反再加 1；正数的补码就是它本身，最高位即符号位（0 正 1 负）
  • 8 位示例：5 = 00000101 → 取反 11111010 → 加 1 得 11111011 = -5
    • 验证：11111011 + 00000101 = 100000000，丢弃溢出位正好为 0
  • 补码让减法变加法：5 - 3 实际算 5 + 11111101(-3) = 100000010，丢掉最高位得 00000010 = 2，硬件只需一个加法器
  • 数学本质是模运算：8 位相当于模 256，-3 ≡ 253 ≡ 11111101

表示范围不对称是 Java 高频细节：

  • 8 位有符号：-128 ~ 127；int：-2147483648 ~ 2147483647
  • byte b = -128; (byte)(-b) 仍输出 -128，Integer.MIN_VALUE 取负还是自己

符号扩展：byte→int 正数补 0、负数补 1。byte b = -1; int i = b; 仍是 -1；想要无符号值用 b & 0xFF 得 255。

位运算：

  • >> 算术右移保留符号位：-8 >> 2 = -2
  • >>> 逻辑右移补 0：-8 >>> 2 = 1073741822
  • C 没有 >>>，有符号右移行为依编译器

❌ 千万别说的话

  • 认为浮点数用补码——浮点走 IEEE 754，负数只是把符号位置 1，其余位不变
  • 解释负数为什么比正数多一个是因为”补码更聪明”——实际是 0 合并省下的编码落到了最小值上

13. I/O 是什么？

🎬 面试现场

面试官：讲讲你对 I/O 的理解？

📝 现场作答

  • I/O 是数据在计算机与外部世界之间的搬运：Input 进来、Output 出去
  • 路径：外设产生数据 → I/O 控制器搬到内存 → CPU 从内存取；输出反向
  • 按设备特性分两类：
类型 设备 访问方式
块设备 硬盘、SSD 按固定块读写（512B 或 4KB），支持随机访问
字符设备 键盘、串口 只能顺序字节流，读完即逝

速度鸿沟是理解一切性能问题的起点，这组数字务必背下来：

介质 延迟
CPU 时钟周期 ~0.3 ns
L1 缓存 ~1 ns
内存 ~100 ns
SSD 随机读 ~150 µs
机械盘随机读 ~10 ms

相当于 CPU 跑一秒 = 等机械硬盘一年。 所以一切 I/O 优化都在削这段鸿沟。

四种缓冲策略：

  • 缓冲 I/O：走 Page Cache——读命中直接返回，写批量刷盘
  • 直接 I/O（O_DIRECT）：绕过 Page Cache。MySQL InnoDB 默认开启，因为它要自己掌控刷盘时机。代价是内存地址和长度必须按块对齐
  • I/O 调度器：重排请求减少寻道。CFQ（公平）、Deadline（防饿死）、Noop（适合 SSD）；现代默认 mq-deadline / bfq，SSD/NVMe 常用 none 或 mq-deadline
    • 查看修改：cat /sys/block/sda/queue/scheduler、echo mq-deadline > /sys/block/sda/queue/scheduler
  • 零拷贝三件套：mmap（映射免一次拷贝）、sendfile（内核缓冲区直发 socket）、splice（fd 间直搬）

❌ 千万别说的话

  • 误以为”非阻塞 = 异步”——非阻塞只解决”数据没准备好”，拷贝阶段仍要用户线程等
  • 以为所有 I/O 都必须经 Page Cache——数据库恰恰要绕开它

14. 为什么网络 I/O 会被阻塞？

🎬 面试现场

面试官：为什么网络 I/O 会阻塞？

📝 现场作答

本质是等待——等数据到、等缓冲区腾位置、等连接建立。OS 把进程挂起让出 CPU，条件满足后再唤醒，因此一次阻塞+唤醒要付两次上下文切换。

三类阻塞：

类型 触发条件
读阻塞 接收缓冲区为空
写阻塞 发送缓冲区已满
连接阻塞 connect 等三次握手、accept 等已完成队列

服务端流程 socket → bind → listen → accept：

  • socket 返回 fd
  • listen 的 backlog 在 Linux 只指已完成连接队列大小（BSD 派生系统是单队列，Linux 是双队列）
  • accept 取出三次握手完成的连接，返回新的 fd

客户端不需要 bind（默认选源 IP + 随机端口），connect 后进入 SYN_SEND，收到 SYN+ACK 后转 ESTABLISHED。

write 为什么会阻塞：TCP 有发送缓冲区和对端的流量控制，发太快对端会通过窗口告知”别发了”，缓冲区满就只能等。

解除阻塞靠 fcntl(fd, F_SETFL, flags | O_NONBLOCK) 设为非阻塞，读写不满足条件立刻返回 EAGAIN/EWOULDBLOCK。

队列溢出后果不同，这点能区分深度：

  • 半连接队列满 → 新 SYN 被丢弃、客户端超时重传（SYN Flood 的攻击面）
  • 已完成队列满 → 服务端回 RST 迫使客户端重连
  • 用 netstat -s 看 overflow 统计

❌ 千万别说的话

  • 把 backlog 说成”等待建立连接的请求总数”——Linux 下它仅算已完成队列

15. I/O 模型有哪些？

🎬 面试现场

面试官：I/O 模型有哪几种？区别在哪？

⚠️ 翻车点：报出五种名字就停。核心差异是「等数据」和「拷贝数据」这两个阶段分别由谁完成——这句话是本题的得分锚点。

📝 现场作答

模型 阶段① 等数据 阶段② 拷贝数据 代表
阻塞 I/O 用户线程等 用户线程等 最基础
非阻塞 I/O 立刻返回 EWOULDBLOCK 用户线程等 轮询
I/O 多路复用 select/epoll 统一等 用户线程等 Nginx、Redis、Netty
信号驱动 内核发 SIGIO 用户线程等（处理函数里 recvfrom 仍阻塞） 较少用
异步 I/O 内核等 内核拷贝，完成后通知 Windows IOCP

逐个补要点：

  • 阻塞：recvfrom 一直挂起到数据准备好且内核→用户拷贝完成。实现简单，适合单线程串行
  • 非阻塞：数据没准备好立即返回，进程反复轮询 recvfrom；accept 同理返回 -1 并置 errno。纯轮询浪费 CPU，必须配合多路复用
  • 多路复用：select/poll/epoll 一次监控多个 fd，任一就绪即返回，再由程序发起真实读写；一个线程管上千连接，省掉海量线程
  • 信号驱动：sigaction 注册 SIGIO 处理函数。信号可能丢失、处理耗时长，不适合高速 I/O
  • 异步：aio_read 立即返回，内核后台完成内核→用户拷贝，完成后按调用指定的方式发信号通知

注意一个细节：多路复用与信号驱动都在 recvfrom 处仍会阻塞，只有阻塞 I/O 和异步 I/O 是两端。

❌ 千万别说的话

  • 把”非阻塞 I/O”和”异步 I/O”混为一谈——前者需要两次系统调用（问状态 + 读数据），后者一次请求内核全包
  • 以为信号驱动 I/O 全程无阻塞——处理函数里的 recvfrom 照样阻塞

16. 同步和异步的区别？

🎬 面试现场

面试官：同步和异步有什么区别？

📝 现场作答

一句话定义：**同步/异步描述的是”谁等结果”**。同步必须等当前步骤做完才能继续；异步提交后立即返回，由回调/事件通知结果。

Java 落地（这才是面试官想听的）：

  • 经典写法是把任务与回调绑定：Callable<String>（有返回值任务）+ Consumer<String>（回调），异步线程执行 task.call() 后再 callback.accept(result)
  • Spring 事件中心就是观察者/发布订阅模式：事件中心是 ApplicationContext（实现 ApplicationEventPublisher），发布用 publisher.publishEvent(new MyCustomEvent(data))，监听只需在 Bean 方法上加 @EventListener

CompletableFuture 的线程流转是高频误区：

  • supplyAsync 把任务 1 扔进 ForkJoinPool 并返回空壳 future
  • thenApply 发现任务未完成，只把回调注册到 future 内部链表，主线程立刻往下走，不会被叫回来
  • 任务 1 完成后，由刚做完它的同一个工作线程 A 直接接着执行 thenApply（”送佛送到西”）
  • 用 thenApplyAsync 则第二步作为新任务重新入池，由另一个工作线程 B 执行。两种写法主线程都不参与

💡 主动加分的追问准备

@EventListener 默认是异步的吗？

不是，默认是同步的——发布线程会阻塞到所有监听器执行完。要真正异步必须再加 @Async。

❌ 千万别说的话

  • 以为 thenApply 会等主线程回来执行——它由完成上游任务的工作线程顺带执行
  • 认为 @EventListener 默认异步——发布方会被监听方拖住

17. 阻塞和非阻塞的区别？

🎬 面试现场

面试官：阻塞和非阻塞的区别？

📝 现场作答

  • 阻塞时：OS 把线程从运行态切到等待态并移出就绪队列，不消耗时间片但内存（含栈）仍占着；数据到达后重新入队。一次阻塞+唤醒共两次上下文切换
  • 非阻塞时：立刻返回状态码（EAGAIN），线程可先去干别的

维度对比：

阻塞 非阻塞
编程复杂度 低 高（要处理返回状态）
线程与连接关系 1 线程 : 1 连接 少量线程 : 海量连接
CPU 利用率 低 高

纯非阻塞的代价是轮询：间隔太短 CPU 空转，太长响应延迟高，所以极少单独使用，基本都配 I/O 多路复用。

Java 落地：

  • 传统 InputStream.read() 是阻塞
  • NIO 用 serverChannel.configureBlocking(false) 设非阻塞，accept() 无连接时返回 null 而非阻塞
  • 配 Selector 即 I/O 多路复用——这是 Netty 的底层原理
  • 模型对应：BIO = 同步阻塞；NIO = 同步非阻塞（底层 epoll）；AIO = 异步 I/O（立即返回 + 回调）

💡 主动加分的追问准备

阻塞 ≠ 挂起，这个区分很能显水平：

  • 阻塞：线程主动发起、自愿等待
  • 挂起：OS 强制，如内存不足把进程换出到磁盘，进程自己都不知情

高并发下阻塞为什么致命：10 万连接 = 10 万线程，按默认 1MB 栈就要 100GB 内存，直接 OOM；上下文切换也会压垮 CPU。而 1~2 个线程 + epoll 就能监控 10 万连接。

❌ 千万别说的话

  • 把阻塞和挂起混为一谈
  • 认为 NIO 是异步的——它是”非阻塞 + 同步”

18. 同步、异步、阻塞、非阻塞的 I/O 的区别？

🎬 面试现场

面试官：把这四个词的关系理清楚。

⚠️ 翻车点：逐个解释四个词定义。这是最没效率的答法——面试官要的是它们分组后的关系图。

📝 现场作答

先给分组，这句话是本题的核心：

阻塞/非阻塞讲第一阶段（等数据准备）用户线程的状态；
同步/异步讲第二阶段（内核→用户空间拷贝）由谁来等。

一次完整 I/O 分两阶段：

四种组合：

组合 模型 典型代表
同步 + 阻塞 BIO 1000 连接开 1000 线程
同步 + 非阻塞 轮询 实际很少单独用
同步 + 多路复用 本质仍是同步 I/O select/poll/epoll，Java NIO、Netty、Nginx、Redis
异步 AIO Linux AIO、Windows IOCP

多路复用最主流的原因：Linux 原生 AIO 较鸡肋——只支持 Direct I/O（绕开 Page Cache）、对普通文件不友好、编程模型复杂回调满天飞；而 epoll 一个线程能撑几十万连接。

Netty 的封装：Boss 线程负责 accept 连接，Worker 线程组负责读写。由此引出两个模式：

  • Reactor = 事件就绪通知你、读写自己做（同步）
  • Proactor = 内核做完读写再通知（异步）

Windows IOCP 天然是 Proactor，Linux 下 Boost.Asio 的 Proactor 也是 Reactor 模拟的。

记忆比喻：非阻塞 = 自己反复去驿站取快递，到了也得自己扛回家；异步 = 快递员送到门口敲门。

❌ 千万别说的话

  • 认为 Java NIO 是异步 I/O——它是”非阻塞 + 同步”的组合：select() 本身阻塞直到事件就绪，Channel.read 的拷贝阶段仍是同步等待
  • 以为 Linux 上 glibc 的 POSIX AIO 是真异步——它用线程池模拟，本质仍是同步阻塞。真要用异步得上 io_uring 或换 Windows IOCP

19. 到底什么是 Reactor？

🎬 面试现场

面试官：讲讲 Reactor 模式。

📝 现场作答

定义：一个 Reactor 线程用多路复用器同时盯住大量连接，某个连接有事件就唤醒它，再按事件类型分发给对应 Handler 执行——本质是”少量线程服务海量连接”。

三个特点：事件驱动（非阻塞 I/O）、少量线程处理大量 I/O、分发与处理解耦。基础事件只有连接、读、写三种。

关键区分：Reactor 是同步非阻塞——只通知”数据来了”，读取写入由应用自己完成；Proactor 是异步非阻塞——OS/IO 库读好后回调应用，如 Windows IOCP。

三种模型：

模型 结构 案例
单 Reactor 单线程 一个线程全干 Redis 6.0 前，单线程 10 万+ QPS
单 Reactor 多线程 主线程监听 + 工作线程池 —
多 Reactor 多线程 Boss Group 接连接 + Worker Group 读写 Netty 默认

Netty 常用配置是 1 个 Boss + CPU 核数 × 2 个 Worker。

EventLoop 就是 Reactor 线程的实现：一个 EventLoop 绑一个线程，内部跑一个 Selector 循环，监听注册其上的所有 Channel。

实战要点：耗时业务必须丢到独立业务线程池，否则阻塞整个事件循环——Netty 中可给 Handler 指定 EventExecutorGroup 换线程执行。

Nginx 用 epoll 单机扛 10 万+ 并发连接，Node.js 事件循环同理。Demux/Dispatcher/Handler 这套名词只是流程产物，不是定义的一部分。

❌ 千万别说的话

  • 把 Reactor 和 Proactor 说反——Reactor 同步非阻塞，Proactor 异步非阻塞
  • 把耗时业务写在 Reactor 线程里
  • Boss 线程堆到很多个——一般只需 1 个，调优重点在 Worker 数

20. Select、Poll、Epoll 之间有什么区别？

🎬 面试现场

面试官：select、poll、epoll 有什么区别？

📝 现场作答

核心差异一句话：select 位图限 1024、poll 动态数组无数量限制，但都要每次拷贝并线性扫描；epoll 用红黑树 + 就绪链表，只注册一次、只返回就绪 fd。

select poll epoll
数据结构 fd_set 位图 struct pollfd 数组 红黑树 + 就绪链表
数量限制 FD_SETSIZE = 1024 无（受内存限制） 无
每次调用 全量拷贝 + 全量扫描 全量拷贝 + 全量扫描 只遍历就绪链表，空则挂起
注册时机 每次调用都要重传 每次调用都要重传 只注册一次
复杂度 O(总数) O(总数) O(就绪数)

细节：

  • select：readfds/writefds/exceptfds 三个集合，nfds 是最大值 +1，timeout 为 NULL 无限等、0 立即返回
  • poll：events 填 POLLIN/POLLOUT/POLLERR/POLLHUP/POLLPRI，revents 由内核回填；timeout 以毫秒计，-1 无限等、0 非阻塞
  • epoll：epoll_create 建实例 → epoll_ctl 用 EPOLL_CTL_ADD/MOD/DEL 管红黑树（O(log N)）→ epoll_wait 只遍历就绪双向链表。性能与就绪数相关而非注册总数，还支持 mmap 减少拷贝

两种触发模式：

  • LT 水平触发（默认）：未读完每次都返回
  • ET 边缘触发：只在状态变化时通知一次

量化对比：10 万连接仅 100 活跃时，select 是 O(10 万) 且每次拷贝，epoll 是 O(100) 且只注册一次，实测快 10 倍以上。

💡 主动加分的追问准备

追问 答案
ET 怎么用？ 必须配非阻塞 I/O，循环 read 直到返回 EAGAIN；用阻塞 I/O 会在最后一次 read 卡死整个线程
epoll 一定比 select 快吗？ 对短连接反而没优势——每连接都要注册+删除，红黑树开销大
Nginx 怎么处理惊群？ 用 accept_mutex，避免多个线程同时 accept 到同一个连接

❌ 千万别说的话

  • “select 只能监控 1024 个 fd”——准确说是 FD_SETSIZE 限制，可调系统参数但有上限
  • 说 epoll 在所有场景都碾压 select——短连接场景反而退化

24. 死锁是什么？如何预防和避免死锁？

🎬 面试现场

面试官：说下死锁，以及怎么处理。

📝 现场作答

定义：两个及以上进程因争夺资源互相等待、无外力则都无法推进。

四个必要条件必须同时成立——这个”必须”和后面的”破坏任一即可”是本题的关键：

条件 含义
互斥 资源同一时刻只能被一个进程占用
请求与保持 持有 A 的同时等 B，且不放 A
不剥夺 资源用完前不能被强行抢走
循环等待 A 等 B、B 等 C、C 等 A

经典例子：双锁交叉获取；银行场景下 A→B 与 B→A 同时转账。

四种应对手法，按破坏的条件分类：

破坏的条件 方法 代价
互斥 只读文件共享、打印机虚拟化成打印队列、数据库用 MVCC 适用面窄
请求与保持 一次性申请所有资源，全拿或全不拿（acquire_all_locks） 资源利用率低、易饥饿
不剥夺 带超时获取 lock.acquire(timeout=1) 可能误杀正常业务
循环等待 全局锁顺序表（account=1、order=2、inventory=3、payment=4）按序加锁、逆序释放 需要人工维护约定

银行家算法（避免死锁的经典代表）：

  • 维护 Available / Max / Allocation 三个矩阵，need = Max − Allocation
  • 请求前先判断是否超过 need、是否超过 available
  • 试分配后检测是否存在安全序列，不安全就回滚

检测与恢复：构建等待图用 DFS 判断环；恢复手段是终止进程或剥夺资源。

数据库侧可用 SHOW ENGINE INNODB STATUS、information_schema.INNODB_LOCK_WAITS、innodb_lock_wait_timeout=50。
