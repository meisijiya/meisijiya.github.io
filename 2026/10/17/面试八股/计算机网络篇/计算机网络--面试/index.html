为什么网络题值得单独背

后端面试里，网络是唯一一块「不背就一定答不上、背了就一定答得上」的科目。

操作系统那类题需要你真跑过、踩过坑；网络不一样——它的答案是确定的、公开的、面试官会一条一条往下抠。TCP 三次握手为什么是三次、滑动窗口两个值取哪个、0-RTT 有什么风险，这些问题没有模糊空间，答错就是错。

更关键的是网络题的追问链特别长。你说”HTTP/2 解决了队头阻塞”，面试官立刻接”哪一层的？”；你说”用 JWT 无状态”，他立刻接”怎么撤销？”——能不能接住第二问，才是区分背过和理解的分水岭。

所以这篇不给你第四十份知识点罗列，而是把 37 道高频题还原成真实的面试现场：每道题都是「面试官怎么问 → 你第一反应会怎么翻车 → 正确答法 → 追问怎么接」。

怎么用这篇：不要背「现场作答」，要背「翻车点」。面试时最容易失分的从来不是不知道，而是知道自己不知道却硬答。考前扫翻车点，性价比最高。

一、HTTP 与协议演进

[1] HTTP 1.0 和 2.0 有什么区别？

🎬 面试现场

面试官：HTTP 从 1.0 演进到 2.0，中间到底解决了哪些问题？你给我捋一遍演进主线。

⚠️ 翻车点

  • 把版本差异说成”新版本功能更多”，讲不出每一步分别在解决什么痛点。
  • 认为 HTTP/1.1 的 Pipeline 已经解决了队头阻塞（实际上响应仍要按序回来，等于没解决）。
  • 说 HTTP/2 靠多路复用就完全没有队头阻塞了（TCP 层的队头阻塞依然存在）。

📝 现场作答

  • 演进围绕两个核心痛点：连接成本（TCP 连接多、慢），以及头部冗余 + 队头阻塞导致的传输效率低。
  • 1.0 → 1.1 的核心是长连接（Keep-Alive）：1.0 是短连接，每次请求都要三次握手、四次挥手；1.1 默认长连接，复用同一个 TCP。同时引入 Host 头，1.0 时代一台服务器只能部署一个网站，1.1 之后虚拟主机（多域名共用一个 IP）成为可能。
  • 1.1 → 2.0 四大升级：多路复用（把一个 TCP 连接拆成无数逻辑流，请求打散成二进制帧乱序发送）、二进制分帧（1.x 是纯文本协议）、头部压缩（HPACK，客户端与服务端各维护索引表，重复 Header 只发索引 ID，省 70%+ 流量）、服务端推送（预判客户端还会要 style.css 就主动推，不过不好控制，Chrome 等主流浏览器已废弃支持）。
  • 关键对比数据：HPACK 的动态表依赖 TCP 的可靠有序；2.0 一个 TCP 承载无数并行流，而 1.1 支持 Pipeline 但响应仍需按序回来。
  • 现状数据：HTTP/1.1 还占 40%+ 网站，HTTP/2 超 60% 网站（2025 年数据）。
  • 演进背景值得提：Google 先推 SPDY，凭全球占有率超 60% 的底气推动标准化，2015 年发布 HTTP/2，后来 Google 放弃 SPDY 拥抱标准。

💡 主动加分的追问准备

追问 答案
HTTP/2 的多路复用解决了 HTTP 层的队头阻塞，为什么还会有 TCP 层的队头阻塞？ 多路复用是在应用层把请求打散成帧乱序发送，但底下跑的还是一条 TCP 连接。TCP 是有序传输，假设帧 1、2、3 发过去，帧 2 丢了，TCP 会卡在那等帧 2 重传成功才把帧 3 交给上层，哪怕帧 3 早就到了。这是 TCP 协议本身的特性，应用层搞不定。
能简单讲讲 HTTP 的历史演进吗？ 1989 年伯纳斯-李提出 URI/HTML/HTTP 三个概念（即 HTTP/0.9，只有 GET、无请求头、响应后即断）；1996 年正式发布 HTTP/1.0（HEAD/POST 方法、状态码、头部、版本号、Content-Type），Dave Raggett 在 1995 年领导 HTTP 工作组；1997 年 HTTP/1.1 首次记录于 RFC 2068，1999 年废弃并发布 RFC 2616，2014 年因过于庞大拆分为 RFC7230–RFC7235 六份文档；2015 年发布 HTTP/2；2018 年 IETF 批准把 HTTP over QUIC 更命名为 HTTP/3。
HTTP 为什么一开始设计成文本协议、只有 GET？ 1989 年互联网初期算力和网速都很弱，Tim Berners-Lee 的想法是文档存在服务器里，只需要从服务器获取文档，所以只有 GET、不需要请求头、拿完就断。

❌ 千万别说的话

  • “HTTP/1.1 的 Pipeline 已经实现了并行请求，所以队头阻塞解决了。” —— Pipeline 兼容性极差几乎没人用，响应仍按序返回。
  • “HTTP/2 完全没有队头阻塞问题。” —— TCP 层的问题被掩盖，不是被消灭。

[2] HTTP 2.0 和 3.0 有什么区别？

🎬 面试现场

面试官：HTTP/2 和 HTTP/3 最核心的差别在哪？为什么现在有人开始上 HTTP/3 了？

⚠️ 翻车点

  • 只答”HTTP/3 更快”，说不出底层从 TCP 换成了 UDP + QUIC。
  • 以为 HTTP/2 的队头阻塞被彻底解决了（TCP 层还在）。
  • 把 0-RTT 说成”任何时候建连都是 0 RTT”（首次建连做不到）。

📝 现场作答

  • 最核心的区别不在 HTTP 本身，而在传输层：HTTP/2 跑在 TCP 上，HTTP/3 跑在 UDP 上，之上是 Google 的 QUIC。比喻：HTTP/2 是把 100 个人塞进一辆公交车还得排队上车；HTTP/3 是每人发一辆车，谁丢包只重发自己的车。
  • 队头阻塞：HTTP/2 的流 TCP 并不认识，一旦丢包就暂停所有流；QUIC 的 Stream A 丢包只阻塞 Stream A，Stream B、C 照跑，弱网环境提升巨大。
  • 建连速度：HTTP/2 需 TCP 三次握手 + TLS 握手，最快 2–3 个 RTT 才能发数据；QUIC 把传输层握手与加密握手合并（QUIC 握手过程包含 TLS 1.3），老用户（Resumption）可直接 0-RTT 发数据。
  • 连接迁移：HTTP/2 靠四元组（IP:Port）识别连接，Wi-Fi 切 4G 就断；HTTP/3 靠 Connection ID，IP 变了只要 ID 没变连接就一直在线。
  • 头部压缩：HTTP/2 用 HPACK，依赖 TCP 的有序传输，包乱序会让动态字典错乱；HTTP/3 换 QPACK，允许头部帧乱序到达。QPACK 把静态表从 61 项扩展到 98 项，并把动态表更新放在独立单向 Stream 上传输（Known Received Count / Section Acknowledgement 机制），避免阻塞。
  • QUIC 还做到：加密 Packet Number 和大部分 Header（强制 TLS 1.3，防止中间设备”协议僵化”）、连接级 + 流级双层流量控制、用户态拥塞控制（升级算法只需更新客户端 App，不用动操作系统）。

💡 主动加分的追问准备

追问 答案
UDP 明明不可靠，为什么能做 HTTP/3 的基础？ QUIC 并不依赖 UDP 的任何特性（除了端口和校验和），它是在应用层重新实现了一遍 TCP 的核心功能：序列号 + ACK 保证不丢，滑动窗口 + 拥塞控制保证不堵。区别在于 TCP 在操作系统内核里改动极难，而 QUIC 在应用层，Google 想怎么改就怎么改。
QUIC 的重传机制和 TCP 有什么不同？ TCP 重传用相同的序列号，接收端无法区分新包还是重传包，RTT 估算容易出错。QUIC 每个包都用单调递增的 Packet Number，哪怕是重传数据 Packet Number 也是新的，接收端能精确判断，RTT 计算更准、拥塞控制反馈更及时。
0-RTT 有什么安全风险？ 0-RTT 数据没有前向保密性，因为用的是上次会话的密钥；攻击者若录下 0-RTT 的包，日后拿到服务器私钥就能解密历史数据。另外存在重放攻击，服务端无法区分是客户端发的还是重放。所以 0-RTT 只适合幂等请求（如 GET），POST 这类有副作用的操作不能放进去。
HPACK 具体怎么工作？ 维护两张表：静态表（协议写死，如 Index 2 代表 method: GET）和动态表（通话过程中运行时建立，新 Header 加入表，后续只发索引号，如”我叫张三，是程序员”记为 Index 62，下次只说”我是 62”）。
为什么 QPACK 要单独开一条单向流传动态表？ HPACK 极度依赖顺序，默认”收到第 N 个包时一定已收到第 N-1 个包”。若包 1（更新动态表定义 Index 62）丢了而包 2（引用 Index 62）到了，应用层解析失败仍会阻塞。QPACK 用 Encoder/Decoder Streams 单独传更新指令，并用 Known Received Count 判断索引是否已确认，未确认就直接发字面量、不查表。
HTTP/3 普及率为什么还不如 HTTP/2？ UDP 常被运营商限速甚至丢弃，企业防火墙默认不开 UDP 443；QUIC 协议复杂、服务端实现难度和 CPU 开销更高（加解密与拥塞控制在用户态）；老负载均衡、WAF、CDN 支持不足。但 Cloudflare、Google、Facebook 已全面铺开。
QUIC 能连接迁移，TCP 为什么加不了？ TCP 是内核协议，改动要兼容全球几十亿设备，四元组识别连接定死了三四十年；加 Connection ID 字段要求所有中间设备、操作系统升级，根本推不动。QUIC 在应用层跑，服务端和客户端统一升级即可。

❌ 千万别说的话

  • “HTTP/3 只是把 HTTP/2 的版本号改了一下，协议基本没变。” —— 底层传输层整个换了。
  • “HTTP/3 首次建连也是 0 RTT。” —— 只有之前已经握过手（Connection ID 已生成）才有 0-RTT。

[3] 常见的 HTTP 状态码有哪些？

🎬 面试现场

面试官：HTTP 状态码分几类？200、301、304、403、502 你分别什么时候用？说说你的选择逻辑。

⚠️ 翻车点

  • 把状态码叫”错误码”，只想到 4xx、5xx，忽略 2xx、3xx 也在表达处理状态。
  • 分不清 301 和 302 的语义差别，只会答”都能跳转”。
  • 用 400 一把梭，出错时全部返回 400 / 500。

📝 现场作答

  • 状态行由三部分组成：Version（通常是 HTTP/1.1，用处不大）、Reason（原因短语，如 “OK”、”Not Found”，只为兼容早期文本客户端，多数客户端会忽略）、Status Code（十进制数字）。它叫”状态码”不是”错误码”，客户端据此决定继续发请求、切协议还是重定向。
  • 三位数，理论取值 000–999，但 RFC 用第一位分五类且 099 不用，实际可用范围是 100–599：1×× 提示信息（协议处理中间态）、2×× 成功（报文已收到并正确处理）、3×× 重定向（资源位置变动）、4×× 客户端错误（请求报文有误）、5×× 服务器错误（服务器内部出错）。
  • 2×× 常用：200 OK（非 HEAD 请求通常带 body）、204 No Content（成功但无 body，服务器要正确区分 200 和 204）、206 Partial Content（范围请求/断点续传，通常伴随 Content-Range，如 Content-Range: bytes 0-99/2000）。另有 201 Created、202 Accepted。
  • 3×× 常用：301 Moved Permanently（永久重定向，如全站 HTTP 切 HTTPS）、302 Found（临时重定向，资源还在只是暂用另一个 URI，如夜间维护跳静态页，浏览器不做缓存优化）、304 Not Modified（配合 If-Modified-Since 条件请求做缓存控制，可理解为”缓存重定向”）。301/302 都用 Location 字段指明新 URI；307 与 302 类似但不允许把 POST 改成 GET。
  • 4×× 常用：400 Bad Request（通用、含糊，开发时应尽量避免）、403 Forbidden（服务器禁止访问，如信息敏感、法律禁止）、404 Not Found（资源未找到）、405 Method Not Allowed、406 Not Acceptable、408 Request Timeout、409 Conflict（可理解为并发竞态）、413 Payload Too Large、414 URI Too Long、429 Too Many Requests（限连策略）、431 Request Header Fields Too Large。另有 401 Unauthorized（需要认证）、410 Gone、412 Precondition Failed。
  • 5×× 常用：500 Internal Server Error（通用错误，不应把内部函数调用栈暴露给外界）、501 Not Implemented、502 Bad Gateway（网关/代理自身正常但访问后端出错）、503 Service Unavailable（临时过载或维护，通常带 Retry-After）、504 Gateway Timeout、505 HTTP Version Not Supported。
  • 数量与开放性：RFC 标准目前共 41 个状态码，但定义是开放的，Apache、Nginx 都定义了自己的专有状态码，自研应用也可在不冲突前提下扩展。

💡 主动加分的追问准备

追问 答案
301 和 302 到底差在哪？ 两者都用 Location 字段跳转、浏览器都会重定向，区别在语义：一个是”永久”，一个是”临时”。网站升级到 HTTPS、原来的 HTTP 不再使用，属于永久，配 301；夜间系统维护、服务暂时不可用，属于临时，配 302，浏览器知道只是暂时情况、不做缓存优化，第二天还会访问原地址。
403 和 404 有什么区别？ 403 不是客户端请求出错，而是服务器明确禁止访问（信息敏感、法律禁止等），服务器友好时可在 body 里说明原因；404 原意是资源在本服务器上未找到，但现在被”用滥了”，服务器”不高兴”就给 404，客户端无从判断是真未找到还是别的原因。
304 Not Modified 是重定向吗？ 它没有通常的跳转含义，用于 If-Modified-Since 等条件请求表示资源未修改，主要用于缓存控制，可以理解成”重定向到已缓存的文件”。
状态码是谁的责任？ 是双方共同责任。客户端据状态码判断是否重发请求、错因是什么；服务端应选择最恰当的状态码，出错时尽量不要简单地返回 400、500 这种意思含糊的码。

❌ 千万别说的话

  • “4xx 除了 404 剩下的都是 500。” 或者”后端随便报什么都返回 400/500。” —— 语义含糊会浪费排障时间。
  • “状态码就是错误码，只有 4xx、5xx 才是状态码。” —— 2xx、3xx 同样在表达处理状态。

[4] HTTP 请求包含哪些内容，请求头和请求体有哪些类型？

🎬 面试现场

面试官：一笔 HTTP 请求报文由哪几部分组成？首部字段分几类？

⚠️ 翻车点

  • 把请求报文和响应报文的组成混着说（请求行 vs 状态行）。
  • 只会说”有请求头有请求体”，说不出首部字段的四大分类。
  • 说不清 Cookie 和 Session 的配合流程，只说”Session 存在服务端”。

📝 现场作答

  • 请求报文四段：请求行（请求方法如 GET/POST、请求资源路径如 /test.html、HTTP 版本如 HTTP/1.1）→ 请求头（各种键值对，传递客户端环境、请求内容和认证信息）→ 空行（分隔请求头与请求体）→ 请求体（仅 POST、PUT 等方法存在）。
  • 响应报文：状态行（版本 + 状态码 + 状态描述）→ 响应头 → 空行 → 响应体。常见响应头：Date（服务器时间戳）、Server（如 Apache/1.3.29）、Last-Modified、ETag（缓存验证）、Content-Type（如 text/html）、Content-Length、Connection（close / keep-alive）、Accept-Ranges（如 bytes）。
  • URI 家族三个：URI（Uniform Resource Identifier，统一资源标识符）、URL（Uniform Resource Locator，统一资源定位符）、URN（Uniform Resource Name，统一资源名称）。
  • 九种方法：GET（获取资源）、HEAD（只获取报文首部、不返回实体主体，用于确认 URL 有效性及资源更新日期）、POST（传输实体主体）、PUT（上传文件，自身不带验证机制）、PATCH（部分修改，PUT 只能完全替换）、DELETE（与 PUT 相反，同样不带验证机制）、OPTIONS（查询支持的方法，会返回 Allow: GET, POST, HEAD, OPTIONS）、CONNECT（与代理建立隧道，如 CONNECT www.example.com:443 HTTP/1.1）、TRACE（服务器返回通信路径）。
  • 首部字段分四类：通用首部（Cache-Control、Connection、Date、Pragma、Transfer-Encoding、Upgrade、Warning）、请求首部（Accept、Accept-Charset、Accept-Encoding、Accept-Language、Authorization、Host、If-Match、If-Modified-Since、If-None-Match、Max-Forwards、Proxy-Authorization、Range、User-Agent）、响应首部（Accept-Ranges、Age、ETag、Location、Proxy-Authenticate、Retry-After、Server、WWW-Authenticate）、实体首部（Allow、Content-Encoding、Content-Language、Content-Length、Content-Location、Content-Range、Content-Type、Expires、Last-Modified）。
  • Cookie 与 Session 配合：Cookie 是服务器发至浏览器并保存在本地的数据块，后续向同一服务器请求时携带，告知服务端是否来自同一浏览器；Session 存服务端（文件、数据库、内存，也可用 Redis 这类内存型数据库，效率更高）。流程是：用户登录提交表单 → 服务器验证后将用户信息存 Redis（Key 为 Session ID）→ 响应报文 Set-Cookie 首部含该 ID → 浏览器存下 Cookie → 后续请求携带该 Cookie 值 → 服务器取出 Session ID 去 Redis 取用户信息。
  • Cache-Control 指令：no-store 禁止缓存；no-cache 强制确认（缓存服务器须先向源服务器验证资源有效性）；private 私有缓存存于用户浏览器仅供单用户使用；public 公共缓存存于代理服务器供多用户使用；max-age=1000000 指定缓存保存时间。Expires 首部字段也可告知过期时间。
  • 连接方式：HTTP/1.1 开始默认长连接，要断开用 Connection: close；HTTP/1.1 之前默认短连接，要用长连接则发 Connection: Keep-Alive。
  • 内容编码：常用的有 gzip、compress、deflate、identity。浏览器发 Accept-Encoding 列出支持的压缩算法及优先级，服务器选一种压缩响应主体并回 Content-Encoding 告知所选算法。

追问 答案

[5] HTTP 和 HTTPS 有什么区别？

🎬 面试现场

面试官：HTTPS 到底解决了 HTTP 的哪几个风险？TLS 握手四次都发了什么？为什么证书要搞一层层的链？

⚠️ 翻车点

  • 只答”HTTP 明文、HTTPS 加密”，说不出窃听、篡改、冒充三类风险。
  • 把 TLS 握手说成”三次”，实际是四次通信。
  • 说”HTTPS 也不安全，有中间人攻击”——把用户点”继续访问”和协议漏洞混为一谈。

📝 现场作答

  • 核心差别：HTTPS 在 TCP 与 HTTP 之间加入 SSL/TLS 协议；HTTP 三次握手后即可传报文，HTTPS 还要再做 SSL/TLS 握手；默认端口 HTTP 80、HTTPS 443；HTTPS 需向 CA 申请数字证书保证服务器身份可信。
  • HTTP 明文传输的三个风险：窃听风险（链路可获取通信内容）、篡改风险（强制植入垃圾广告）、冒充风险（冒充天猫、京东）。HTTPS 分别用：信息加密（解决窃听）、校验机制（解决篡改）、身份证书（解决冒充）。
  • 混合加密：通信建立前用非对称加密交换会话秘钥，通信过程中全部用对称加密的会话密钥加密明文。原因是对称加密只用一个密钥、速度快但无法安全交换；非对称加密公钥可任意分发、私钥保密，能解决密钥交换但速度慢。
  • 数字签名：摘要算法（哈希函数）保证内容完整性——双方各算一次”指纹”比对。但”内容 + 哈希值”整体仍可能被中间人替换，所以要引入非对称加密：公钥加密/私钥解密保证传输安全，私钥加密/公钥解密证明消息来源于持有私钥的一方。
  • 数字证书：CA 把持有者公钥、用途、颁发者、有效时间等打成包，做 Hash 得到 Hash 值，用 CA 自己的私钥加密生成 Certificate Signature，再加到证书上。客户端校验时用同样 Hash 算法算出 H1，用内置的 CA 公钥解密 Certificate Signature 得到 H2，比较 H1 == H2 则证书可信。
  • TLS 握手四次：① ClientHello 发 TLS 版本（如 TLS 1.2）、Client Random、密码套件列表（如 RSA）；② SeverHello 回确认的 TLS 版本、Server Random、确认的密码套件、服务器数字证书；③ 客户端回应——用浏览器/操作系统内置的 CA 公钥验证证书真实性，取出服务器公钥，发送 pre-master key（被服务器公钥加密）、加密通信算法改变通知、客户端握手结束通知（附带之前所有内容的摘要供服务端校验）；④ 服务器最后回应——用协商算法算出会话密钥，发出加密通信算法改变通知和服务器握手结束通知（带摘要供客户端校验）。三个随机数（Client Random、Server Random、pre-master key）共同生成”会话秘钥”。
  • 现行密钥交换算法有两种：RSA 和 ECDHE，RSA 流程更好理解因此常拿来做示例。
  • 证书信任链：客户端只信任根证书（如 GlobalSign Root CA），逐级验签中间证书，再验证 baidu.com 证书，这样一层层构成信任链路。之所以要中间层，是为了确保根证书的绝对安全性。
  • TLS 分两层：握手协议（协商加密算法、生成对称密钥，保护后续应用数据）和记录协议（保护应用数据、验证完整性与来源）。记录协议流程：消息分割成短片段 → 逐片段压缩 → 加消息认证码 MAC（防篡改并做数据认证，计算时还加上片段编码以防重放攻击）→ 用对称密码加密 → 加上由数据类型、版本号、压缩后长度组成的报头 → 交给 TCP 层传输。

HTTPS 一定能保证安全吗？ 不能绝对保证。中间人攻击的前提是用户点击接受了中间人服务器的证书——浏览器会弹出证书存在问题提示，用户执意点”继续浏览此网站”就等于接受了伪造证书；或者电脑中毒被恶意导入中间人根证书，操作系统信任它后浏览器不会告警。这两种情况利用的都是客户端漏洞（用户行为、系统被污染），不是 HTTPS 协议本身有漏洞。中间人的完整流程是：与客户端握手拿到对称密钥 A、与服务端握手拿到对称密钥 B，之后用 A 解密客户端数据、用 B 加密后转发给服务端，再反向操作，全程”偷看”双方数据。
HTTPS 的应用数据怎么保证完整性？ 靠 TLS 记录协议：压缩片段后附加 MAC（哈希生成）用于完整性校验和数据认证，计算 MAC 时加入片段编码防重放，再加密、加报头。
为什么根证书不直接签发网站证书，非要搞中间层？ 为了确保根证书的绝对安全性，把根证书隔离得越严格越好。根证书一旦失守，整条信任链都会出问题。
客户端具体怎么校验证书？ 用同样的 Hash 算法算证书 Hash 值 H1；用内置 CA 公钥解密 Certificate Signature 得到 H2；H1 == H2 则证书可信。若签发者不是根证书，则根据证书里的签发者字段找到中间 CA 并向其请求中间证书，逐级验证到预载在根证书清单里的根证书为止。

❌ 千万别说的话

  • “HTTPS 有中间人攻击，所以 HTTPS 并不安全。” —— 前提是用户接受伪造证书或本机被植入根证书，是客户端问题。
  • “HTTPS 是三次握手。” —— TCP 三次握手之后还有 TLS 四次通信，别把两者混成三次。

[6] HTTP 中 GET 和 POST 的区别是什么？

🎬 面试现场

面试官：GET 和 POST 到底差在哪？别跟我说”参数位置不同”就完了，说说本质和实际开发里怎么选。

⚠️ 翻车点

  • 只答”GET 参数在 URL、POST 参数在请求体”，把表面差异当本质。
  • 说”POST 比 GET 安全，因为参数在 body 里”。
  • 说”GET 不能带请求体”（协议上其实允许）。
  • 说”GET 天然带缓存”（准确说是 GET 响应默认可缓存）。

📝 现场作答

  • 本质区别：GET 是获取资源、只读操作，协议设计为幂等、安全，不改变服务器端资源状态；POST 是提交资源、写操作，协议设计为非幂等、非安全，会改变服务器端资源状态。
  • 12 个维度的核心对比：参数位置（GET 拼在 URL 查询串 ? 后 / POST 放请求体）、请求体（GET 协议规定无 / POST 有）、幂等性（GET 幂等 / POST 非幂等）、安全性（GET 安全 / POST 非安全）、数据长度限制（GET 受浏览器/服务器 URL 长度限制，如 Chrome 约 2KB、Nginx 默认 4KB；POST 协议层面无长度限制，仅受服务器配置限制，如 Tomcat 默认 8MB）、缓存支持（GET 响应浏览器默认缓存，可用 Cache-Control 禁用；POST 默认不缓存，需手动配置缓存头）、历史记录（GET 参数进地址栏和历史记录；POST 不进）、编码方式（GET 仅 URL 编码，空格转 %20；POST 支持 URL 编码、JSON、表单、二进制，依 Content-Type）、跨域预检（GET 属简单请求，无 OPTIONS 预检；POST 若带自定义头或非 form-urlencoded 格式则属非简单请求，需 OPTIONS 预检）、书签收藏、数据类型（GET 仅支持 ASCII，非 ASCII 需编码；POST 支持任意类型如二进制文件、中文、特殊字符）、日志记录（服务器日志记录 GET 的完整 URL 含参数，POST 只记请求路径不记请求体）。
  • 幂等性定义：多次发送相同请求，服务器端资源状态始终一致。多次查询同一用户信息结果一致是 GET 幂等；多次提交同一订单可能创建多个订单是 POST 非幂等。注意 PUT/DELETE 协议规定为幂等，PATCH 为非幂等。
  • 三个必须纠正的误区：① “GET 只能传少量数据、POST 能传大量”是错的，HTTP 协议从未限制两者参数长度，限制来自浏览器/服务器配置；② “POST 更安全”是片面的，未加密的 POST body 和 GET 的 URL 参数一样明文，抓包可见，真正的安全靠 HTTPS 对整个请求（URL + 头 + 体）加密；③ “GET 不能传复杂数据”不准确，部分框架支持把复杂数据拼进查询串，但会导致 URL 过长、编码繁琐、易被缓存和日志记录，复杂数据优先用 POST。
  • 使用原则”查用 GET，改增删用 POST”，这是 RESTful API 设计规范：GET 用于数据查询、静态资源请求、筛选排序；POST 用于新增资源（注册、下单）、传输敏感数据（密码、身份证号）、传输复杂/大数据（JSON 嵌套、文件上传、二进制流）、无幂等性要求的操作。
  • 两个特殊情况：协议上 GET 允许有请求体，但所有浏览器/服务器都不支持（Chrome 忽略 GET 的请求体，Nginx 直接拒绝），所以实际开发中 GET 绝对不能带请求体；POST 可以做查询但不推荐，POST 默认不缓存，多次查询会重复请求服务器，性能低于能利用浏览器缓存的 GET，且违背协议设计初衷。

为什么说 GET 安全、POST 非安全？ 安全性指请求不会对服务器端资源造成任何修改/新增/删除。GET 仅拉取数据，无副作用；POST 提交数据会产生副作用（新增用户、扣减库存）。这是 HTTP 协议的官方定义。
GET 的长度限制到底是多少？ 协议层面没有限制，限制来自浏览器和服务器对 URL 长度上限：Chrome 约 2KB，Nginx 默认 4KB；POST 则只受服务器配置限制，如 Tomcat 默认 8MB。

[7] WebSocket 与 HTTP 有什么区别？

🎬 面试现场

面试官：WebSocket 和 HTTP 到底差在哪？握手过程你给我说一遍？连接断了怎么办？

⚠️ 翻车点

  • 只答”WebSocket 是长连接，HTTP 是短连接”，说不出最本质的通信方向差异。
  • 说不清 Sec-WebSocket-Key 到 Sec-WebSocket-Accept 的计算过程。
  • 以为 WebSocket 协议自带自动重连。

📝 现场作答

  • 最本质的区别是通信方向：HTTP 是单向的，客户端问一句、服务器答一句；WebSocket 是双向的，建立连接后双方都能主动发消息，不用等对方先开口。
  • HTTP 做实时性太差：在线聊天室、实时行情只能靠客户端不停轮询，每隔 1 秒问”有新消息没”，10 万用户同时在线就是每秒 10 万个请求，服务器扛不住、延迟还高。
  • WebSocket 复用 HTTP 的握手流程：第一次请求仍走 HTTP，带上 Upgrade: websocket 告诉服务器要升级协议，服务器同意后返回 101 状态码，之后整个 TCP 连接切到 WebSocket 协议，连接一直保持。请求示例： 服务器同意则返回：
  • Sec-WebSocket-Accept 的算法：客户端随机生成的 Base64 字符串（Key）与一个固定 GUID 拼接，做 SHA-1 哈希再 Base64 编码。目的是防止不支持 WebSocket 的代理服务器误把普通 HTTP 请求当成 WebSocket 连接。
  • 帧格式四个关键字段：① FIN 位表示是不是消息最后一帧（支持大消息拆多帧）；② Opcode 标识帧类型，0x1 文本帧、0x2 二进制帧、0x8 关闭帧、0x9 Ping、0xA Pong；③ Mask 位和 Masking-Key 做数据掩码，规范要求客户端发服务器必须掩码、服务器发客户端不用；④ Payload Length 表示数据长度，小于 126 字节直接用 7 位表示，126–65535 用后续 2 字节，更大用 8 字节。
  • 心跳保活：连接长时间无数据传输会被 NAT 设备或防火墙干掉。协议内置 Ping/Pong 帧，客户端或服务器定期发 Ping，对方必须回 Pong。很多框架自动处理，如 Spring WebSocket 默认 25 秒发一次心跳；业务层也可自己实现，比如每 30 秒发 {"type":"ping"}，收到 {"type":"pong"} 认为正常，更灵活还能顺带传业务状态。
  • 四种方案横向对比（通信方向 / 实时性 / 服务器压力 / 浏览器兼容 / 断线重连）：HTTP 轮询——单向、差、高、全支持、需自己实现；HTTP 长轮询——单向、中等、中等、全支持、需自己实现；SSE——单向、好、低、IE 不支持、自动重连；WebSocket——双向、好、低、IE 10+、需自己实现。SSE 用 EventSource 建立连接，服务器可持续推送，但客户端想发消息还得走普通 HTTP。
  • 典型场景：即时通讯（微信网页版、Slack、Discord）、实时行情（股票、加密货币交易所）、协同编辑（Google Docs、飞书文档）、游戏（H5 玩家位置与战斗状态同步）、监控大屏。

追问 答案
WebSocket 连接断了怎么办？有自动重连吗？ WebSocket 协议本身没有自动重连，断了就是断了，得自己实现：监听 onclose 和 onerror 触发后启动重连。重连策略通常用指数退避，第一次 1 秒后重连，失败 2 秒，再失败 4 秒，最大退到 30 秒或 1 分钟封顶，避免服务器刚挂就被重连请求打爆。用 Socket.IO 这类库则重连机制内置。
WebSocket 可以跨域吗？ 可以，不受浏览器同源策略限制，客户端能连任意域名的 WebSocket 服务。但服务端通常会校验 Origin 头，防止被恶意网站滥用。Nginx 代理 WebSocket 时必须配置 proxy_set_header Upgrade 和 proxy_set_header Connection，否则握手会失败。
为什么客户端发的数据要掩码，服务端发的不用？ 防止缓存投毒攻击。早年有些 HTTP 代理不认识 WebSocket，会把 WebSocket 帧当成普通 HTTP 数据缓存；恶意客户端构造特定字节序列，能让代理误以为这是一个 HTTP 响应从而污染缓存。客户端数据掩码后每次发送的字节都不一样，无法构造这种攻击。
大量 WebSocket 连接怎么做负载均衡？ WebSocket 是长连接，不能像 HTTP 那样每次请求负载均衡到不同机器。一般用 Nginx 或 HAProxy 在握手阶段做一次负载均衡，连接建立后就绑定到那台后端机器；Nginx 要配 ip_hash 或 sticky session。更大规模会用专门的网关（Kong、APISIX）。
长轮询和 SSE 比 WebSocket 差在哪？ 都是单向的：长轮询每条消息仍要一次 HTTP 往返，SSE 只能服务器推、客户端发消息还得走普通 HTTP，且 IE 不支持。WebSocket 是双向的，实时性和服务器压力都更好。

❌ 千万别说的话

  • “WebSocket 就是把 HTTP 的长连接拿来用。” —— 它是协议升级（101 Switching Protocols）后在同一条 TCP 连接上换了应用层协议。
  • “WebSocket 断线会自动重连，浏览器已经处理了。” —— 协议没有内置重连，必须自己实现。

  • 解析五步：① 读第一行请求行，按空格切分出请求方法 POST、URI /api/login、协议版本 HTTP/1.1；② 逐行读请求头，每行 key: value，遇到空行停止（Host 告诉服务器是哪个域名，Content-Type 告诉请求体格式，Content-Length 告诉请求体多少字节）；③ 空行之后是请求体，根据 Content-Length 读指定长度，再按 Content-Type 决定怎么解析；④ 根据 URI 路由到对应处理逻辑执行业务代码；⑤ 生成响应，格式同样是状态行 + 响应头 + 空行 + 响应体。
  • 请求行三要素：请求方法（只是语义约定，服务端爱怎么实现怎么实现）、URI（可能带查询参数如 /search?keyword=java&page=1，要解析出 keyword 和 page）、HTTP 版本（影响解析方式——HTTP/1.1 是文本协议一行一行读；HTTP/2 是二进制帧格式，完全不同的解析逻辑）。
  • Content-Type 三种常见格式：application/x-www-form-urlencoded（表单默认，key=value&key2=value2）、multipart/form-data（上传文件用，每个字段用分隔符隔开）、application/json（前后端分离主流格式）。
  • 没有 Content-Length 时，若有 Transfer-Encoding: chunked 就是分块传输，每块前标明长度，最后一块长度为 0 表示结束，适合数据量不确定的场景。
  • 框架层：Tomcat、Nginx 在底层完成 HTTP 解析，上层直接拿到封装好的 Request 对象。以 Spring MVC 为例，DispatcherServlet 收到的 HttpServletRequest 已解析好：getMethod() 拿方法、getRequestURI() 拿路径、getHeader() 拿请求头、getInputStream() 拿请求体；参数绑定也由框架完成，@RequestParam 从查询参数取值、@RequestBody 把请求体反序列化成对象、@PathVariable 从 URI 取占位符。
  • HTTP/1.1 vs HTTP/2 解析差异：HTTP/1.1 报文是可读字符串，用 \r\n 分隔行、空行分隔头和体，解析简单但每行都要扫描找换行符、效率不高；HTTP/2 是二进制协议，报文被切成一个个帧，每个帧有固定的 9 字节头，标明类型、长度、流 ID，HEADERS 帧放请求头、DATA 帧放请求体，多个请求可在同一连接上交错传输。

💡 主动加分的追问准备

追问 答案
Content-Length 和实际请求体长度不一致会怎样？ 两种情况。Content-Length 比实际小，服务端只读声明长度，后面的数据被截断或留在缓冲区污染下一个请求；比实际大，服务端会一直等，直到超时或连接断开。这还可被利用做 HTTP 走私攻击——前端代理和后端服务器对同一请求解析不一致，攻击者可以夹带恶意请求。
怎么判断请求体读完了？ 两种方式：一是看 Content-Length，读够指定字节数就完；二是 Transfer-Encoding: chunked，读到长度为 0 的块就结束。如果两个头都没有，对请求一般认为没有请求体；对响应只能靠服务端关闭连接标识结束。
multipart/form-data 具体怎么解析？ 用一个随机生成的 boundary 字符串做分隔符，Content-Type 里声明 boundary 是什么。请求体里每个字段用 --boundary 开头，字段有自己的 Content-Disposition 标明字段名和文件名，还可能有 Content-Type 标明文件类型，最后用 --boundary-- 结束。服务端按 boundary 切分，逐个解析。上传大文件时常用流式解析，避免整个文件读进内存。
HTTP/1.1 的 Keep-Alive 怎么工作？ HTTP/1.0 默认每个请求都新建 TCP 连接，请求完就断；HTTP/1.1 默认开启 Keep-Alive，一个连接可发多个请求，省掉重复握手开销。但 HTTP/1.1 是串行的，前一个请求响应没收完，后一个请求发不出去，这就是队头阻塞。服务端通过 Connection: keep-alive 和 Keep-Alive: timeout=60 告诉客户端这个连接能保持多久。
HTTP/2 的帧头 9 字节都是什么？ 帧头固定 9 字节，标明帧类型、长度、流 ID；HEADERS 帧放请求头、DATA 帧放请求体，多个请求可在同一连接上交错传输。

  • “HTTP/1.1 和 HTTP/2 都是一行行读文本。” —— HTTP/2 是二进制帧，每个帧有固定 9 字节头。

二、TCP 连接与可靠性

[9] 到底什么是 TCP 连接？

🎬 面试现场

面试官：很多人说 TCP 连接就是”两端拉了根线”，你给我讲讲，一条 TCP 连接到底是什么？

⚠️ 翻车点

  • 以为 TCP 连接是一根真实的物理线路、虚拟通道，或者一条独立的内核 socket 结构。
  • 把 Socket 直接等同于 TCP 连接，答不出”一个连接需要两个 Socket”的区别。

📝 现场作答

  • TCP 是传输层协议，提供可靠的、面向连接的、字节流服务；连接本质是通信双方在内存里维护的一堆状态信息，即 TCB（传输控制块）。
  • TCB 最关键的三项：Socket（本地 IP + 本地端口）、序列号 Seq（防乱序丢包）、窗口 Window（对端还能接多少）。
  • 唯一标识一条 TCP 连接的是四元组：源 IP、源端口、目的 IP、目的端口；同一台机器上成千上万条连接就靠四元组区分。
  • 三次握手的作用就是初始化这些状态 + 同步双方初始序列号 ISN + 确认双向收发能力正常；只要两边 TCB 状态对得上，连接就”存在”。
  • 一个 Socket 是一个通信端点（相当于门牌号），一条完整 TCP 连接需要客户端、服务器两个 Socket 共同构成。
  • 序列号是给每个字节编号（不是每个报文段）；窗口大小写在首部 Window 字段，是动态的，缓冲区满可通告 0（窗口关闭）。
  • 发送窗口取 min(rwnd, cwnd)：接收方通告窗口与自身拥塞窗口的较小值。
  • TCB 还包含 11 个连接状态、收发缓冲区、重传队列、各类计时器、RTT 估计、cwnd/ssthresh，一条连接约占几百字节到几 KB。

💡 主动加分的追问准备

追问 答案
网线拔了连接还在吗？ 在。TCP 是状态维护，拔线但双方都不发数据，两边 TCB 依然是 ESTABLISHED；只有一方发数据超时、或 Keep-Alive 探测失败后才会销毁连接、释放 TCB。
服务器怎么发现客户端已挂？ 三种：① 服务端发数据发不出去触发超时重传，重传多次失败即判定断开；② 开 TCP Keep-Alive（默认 2 小时无数据发探测包，几次无响应关闭），但生产环境一般自己在应用层做心跳（如 30 秒 ping 一次、3 次不响应断开）；③ 操作系统通知，如 Linux epoll 下网卡挂掉内核通知 socket 出错。
三元组和四元组怎么区分？ 三元组 = IP + 端口 + 协议类型（如 192.168.1.1:8080 (TCP)），在一台机器上唯一标识一个服务/应用；四元组 = 源 IP + 源端口 + 目的 IP + 目的端口，唯一标识一条 TCP 连接，如 192.168.1.100:50000 -> 192.168.1.1:80。
拔线后怎么让状态尽快收敛？ 应用层心跳比内核 Keep-Alive 更实用：内核默认 2 小时间隔太长，一个死连接要白占两小时 TCB 和文件描述符。

❌ 千万别说的话

  • ❌「TCP 连接就是客户端和服务器之间建立的一条物理链路 / 一根虚拟线路。」——它只是双方内存里的状态。
  • ❌「一个 Socket 就是一条 TCP 连接。」——一个 Socket 是一个端点，一条连接要两个 Socket。

[10] TCP 是用来解决什么问题？

🎬 面试现场

面试官：IP 层已经把包送到目的主机了，TCP 到底在上面多做了什么？你给我把机制说全。

⚠️ 翻车点

  • 把”可靠传输”只答成”有确认机制”，说不出超时重传、序号去重、缓冲区的配合关系。
  • 答不出确认号的两层含义（既表示已收到，也表示下次从哪发）。

📝 现场作答

  • TCP 十个核心机制：确认应答、超时重传、滑动窗口、流量控制、拥塞控制、延迟应答、捎带应答、粘包问题、异常情况、连接管理（三次握手/四次挥手），核心是可靠传输。
  • 确认应答：发送端给每个字节编序号，接收方按序号处理后返回 确认序号 = 序号 + 1 并置 ACK = 1。确认号两层含义：① 该序号之前的数据我全收到了；② 下次请从这个序号开始发。
  • 超时重传：一段时间没收到 ACK 就认为丢包重发。重传间隔随重传次数指数变长，达到阈值后置 RST = 1 尝试重置连接，双端清除彼此信息；若网络严重故障 RST 也发不出去，就只能断开连接。
  • 重复数据的处理：发送方分不清”数据丢了”还是”ACK 丢了”，所以重复在 TCP 层无所谓，靠接收缓冲区按序列号去重，保证应用层读不到重复数据。
  • 滑动窗口：窗口大小 = 无需等 ACK 就能连续发送的最大值（如 2500 字节 / 5 个段），某段收到 ACK 后窗口前移；内核发送缓冲区记录未应答数据，应答后删除。
  • 快速重传：窗口 501–2001 中 501–1000 丢失，接收方反复回同一个 ACK 要求从 501 开始，发送端连续收到相同 ACK 即重传该段，不必等超时。
  • 流量控制是滑动窗口的补充，按接收方处理能力限制发送速率；拥塞控制按”小窗口起步→不丢包就增大→丢包就缩小”寻找阈值；两者冲突时取较小的窗口（rwnd 与 cwnd）。
  • 延迟应答：收到数据不立即回 ACK，一般延迟 200ms 或收到 2 个包再回；期间可用于处理数据、扩大缓冲区以提升吞吐，特殊情况下能把四次挥手并成三次。
  • 捎带应答：把 ACK 和 SYN（乃至待发数据）合并成一个报文发送，减少封装与分用开销。
  • 异常场景：进程崩溃会释放 fd、可发 FIN，与正常关闭无区别；主机正常关机/断电/断网则 FIN 或后续 ACK 收不到，触发重传多次无果后删除对方信息。

💡 主动加分的追问准备

追问 答案
滑动窗口丢的是 ACK 包有影响吗？ 没有影响。后续应答报文里的确认号会告诉发送方”该序号之前的数据都已收到”，被丢的旧 ACK 是冗余的。
丢 TCP 数据报呢？ 有影响。接收方因缺 501–1000 会持续返回要求从 501 开始的 ACK，发送端连续收到相同 ACK 触发快速重传；收到后因内核有接收缓冲区可先存着，再按缓冲区数据正常应答。
滑动窗口的意义是什么？ TCP 为可靠牺牲了效率，滑动窗口是弥补这种牺牲的手段——但即使用了它，效率依然不如 UDP。
拥塞控制的窗口变化规律？ 慢开始：小窗口试探链路是否通畅；扩大窗口①：指数增长；扩大窗口②：到 ssthresh 阈值后线性增长；缩小窗口①：直接缩到 0 再重来；缩小窗口②：砍一半后线性增长。

❌ 千万别说的话

  • ❌「超时重传的时间间隔是固定的。」——它随重传次数变长，到阈值后触发 RST。
  • ❌「TCP 重复接收数据是允许的，应用层也会收到两份。」——重复在 TCP 层无妨，但缓冲区和序号去重保证应用层读不到重复数据。

[11] 一台服务器，最多能建立多少 TCP 连接？

🎬 面试现场

面试官：给你一台 8G 内存的服务器，你告诉我最多能撑多少条 TCP 连接？推导给我听。

⚠️ 翻车点

  • 直接答”65535，因为端口号只有 16 位”——这是最经典的误区。
  • 只背”四元组理论上限 2^48”，说不出实际被文件描述符和内存卡死，最终结论不落地。

📝 现场作答

  • 没有固定答案：理论上限由四元组决定，实际上被文件描述符、内存、端口范围、CPU 四件事卡死，最终瓶颈基本落在内存。
  • 四元组推导：单个服务端进程通常固定监听一个端口（如 8080）和 0.0.0.0，所以变的只有客户端 IP + 客户端端口——客户端 IP 最多 2^32（约 42 亿），客户端端口最多 2^16（65536，端口 0 不可用，此处忽略），故单进程理论上限 = 2^32 × 2^16 = 2^48 ≈ 281 万亿。
  • 若允许多个服务端进程监听不同端口（最多 2^16 个），理论上限 = 2^32 × 2^16 × 2^16 = 2^64，可视为无穷大——所以端口号从来不是真瓶颈。
  • **端口号只限制”单端”**：单个客户端 IP 对单个服务器端口最多发起 65535 条连接；但服务器可服务多个客户端，客户端 IP 不同就能各开 65535 条，因此是”客户端 IP 数 × 客户端端口数”，而非单端口 65535。
  • 内存才是真瓶颈：每个连接静态约 3KB（含 sock、tcp_sock 等数据结构），收发缓冲区还会随数据流动态调整到几 MB；工程上按 100KB～300KB/连接 估算较合理（结构体 + 收发缓冲区 + 协议栈开销 + 内核管理数据结构），折中取 200KB。
  • 8G 内存、70% 用于 TCP 连接时：连接数 ≈ 8GB × 0.7 ÷ 200KB ≈ 2.9 万条。
  • 文件描述符三层限制：系统级 /proc/sys/fs/file-max、用户级 /etc/security/limits.conf 的 nofile、进程级 ulimit -n（默认通常 1024）。Linux 里一切皆文件，每个 TCP 连接就是一个 socket、一个 fd，超限直接报 Too many open files。
  • C10K → C10M：早期瓶颈在 select/poll 的 O(n) 遍历和线程上下文切换；epoll/kqueue + 事件驱动让 Nginx、Redis 单机轻松十万级；再往千万走要上 DPDK 绕过内核、用户态协议栈、多队列网卡、NUMA 亲和。
  • 长短连接的瓶颈不同：短连接瓶颈在 TIME_WAIT（主动关闭方等 2MSL ≈ 60 秒），高并发下堆积几万个 socket 吃端口和内存；长连接瓶颈在内存和 fd，但没有反复握手的开销，同等资源能撑更多有效连接——所以高并发基本都是长连接 + 连接池。
  • 实际调优参数：ulimit -n 调到百万并同步调高 file-max；net.ipv4.ip_local_port_range（默认 32768–60999，可扩到 1024–65535）；net.ipv4.tcp_tw_reuse=1；net.ipv4.tcp_mem / tcp_rmem / tcp_wmem；net.core.somaxconn 与 net.ipv4.tcp_max_syn_backlog（半连接与全连接队列长度）。

追问 答案
客户端连不上报 address already in use？ 客户端临时端口用完，或旧连接还卡在 TIME_WAIT 没释放。Linux 默认可用端口范围 32768–60999 约 2.8 万个，频繁对同一 IP:Port 发短连接很快被 TIME_WAIT 占满。解法：扩大 ip_local_port_range、开 tcp_tw_reuse、改长连接。
多网卡多 IP 对上限有影响吗？ 有影响。服务端 IP 也是四元组的一部分，两个 IP 各监听 8080，对同一客户端来说就是两个不同目的四元组，理论上连接数翻倍。但实际瓶颈还是内存和 CPU，多 IP 只是抬高理论天花板。
百万连接下每秒能处理多少请求？ 百万连接 ≠ 百万 QPS。纯推送/广播场景瓶颈在带宽，每秒几万条没问题；若每个请求都要查库、调外部接口，CPU 和 IO 很快见底，QPS 可能只有几千。前者考验连接维护能力，后者考验请求处理能力。
TIME_WAIT 怎么解决？ 三招：改长连接减少频繁关闭；开 tcp_tw_reuse 让新连接复用 TIME_WAIT 端口；tcp_fin_timeout 可以调短，但它只影响 FIN_WAIT_2，对 TIME_WAIT 无效。

❌ 千万别说的话

  • ❌「一台服务器最多 65535 条连接，因为端口号就 16 位。」——端口只约束单端，客户端 IP 一变条数就翻几亿倍。
  • ❌「调小 tcp_fin_timeout 就能解决 TIME_WAIT 堆积。」——它管的是 FIN_WAIT_2，不是 TIME_WAIT。

[12] TCP 和 UDP 有什么区别？

🎬 面试现场

面试官：TCP 和 UDP 你肯定背过表格，那我问你——为什么 DNS 用 UDP 不用 TCP？HTTP/3 又为什么反过来上了 UDP？

⚠️ 翻车点

  • 只背”TCP 可靠 UDP 不可靠”，说不出面向连接 vs 面向数据报的本质差异。
  • 误以为 UDP 一定比 TCP 快所以”能不用就不用”，说不出各自的适用边界。

📝 现场作答

  • 核心差异：TCP 面向连接、可靠、字节流；UDP 面向数据报、无连接、不保证可靠性，细微处理交给上层应用。
  • 头部：UDP 首部只有 4 个 16 位字段、共 8 字节，读完前 8 字节剩下的全是载荷；TCP 首部最小 20 字节，4 位数据偏移以 4 字节为单位，最大 60 字节（选项最多 40 字节）。UDP 首部长度字段本身也是 16 位，故 UDP 最大传输 64K（含首部），超过需应用层手动分包与拼装。
  • TCP 首部关键字段：16 位源/目的端口、32 位序号、32 位确认号、6 个标志位（URG/ACK/PSH/RST/SYN/FIN）、16 位校验和（包含首部和数据两部分）、16 位紧急指针。
  • 确认号的含义：ACK = 1 表示确认号有效；PSH 提示应用立刻从缓冲区取数据；RST 为复位报文段；SYN 为同步报文段；FIN 为结束报文段。
  • 基于 TCP 的协议：HTTP/HTTPS、FTP、SMTP（发信）/POP3（收信）；基于 UDP 的协议：QUIC（HTTP/3）、DHCP、DNS。
  • UDP 无粘包：UDP 有明确的报文长度字段，保护消息边界，读完首部剩下的就是本数据报；粘包拆包问题只在 TCP 这一类流式协议上出现。
  • UDP 无发送缓冲区：调用 sendto 直接交给内核传给网络层，不像 TCP 在发送缓冲区排队等 ACK；不拥塞控制、无重传，发送通常立即返回。
  • UDP 接收缓冲区：内核中暂存数据报，排队的条数受缓冲区大小限制；缓冲区满则新到达的数据直接丢弃，且不保证接收顺序与发送顺序一致（受网络延迟、路由差异影响）。
  • UDP 服务器能同时收多个客户端数据：因为无连接，服务器无需为每个客户端维持单独连接，同一个套接字用 recvfrom() 就能接收不同客户端的数据报（recvfrom 每次调用处理一个数据报，多个同时到达在内核队列排队）；同时 UDP 支持多播和广播。
  • UDP 不是全双工的：UDP 设计目标就是简单低开销，全双工需要更多控制信息、状态维护和流量控制，与设计意图相悖；但可以实现全双工效果。UDP 里的 connect 只改变套接字绑定的目的地址和端口，不与对端握手、不建立连接。

[13] 为什么要 TCP，IP 层实现控制不行么？

🎬 面试现场

面试官：既然链路层加 IP 就能通信了，为什么非要再叠一层 TCP？把可靠性做在 IP 层不行吗？

⚠️ 翻车点

  • 只答”因为分层设计更灵活”，说不出核心——IP 层做不了、也不该做，理由是设备数量与无状态转发。
  • 把端到端原则误解成”网络完全不能有功能”，忘了 NAT/防火墙/CDN 的现实妥协。

📝 现场作答

  • 答案核心是分层架构的灵活性和可扩展性：IP 层只负责路由和传输，可靠性作为可选服务由上层自选——要可靠性用 TCP，不要、要实时性、允许少量丢包用 UDP。
  • 不在 IP 层实现的根本原因：一条数据要经过海量设备，每台设备都靠 IP 寻址；若 IP 层做控制，所有设备都要关心序列号、确认、重传，整体传输效率会大打折扣。
  • 快递中转站模型：A 发给 F 要经过 B、C、D、E。若每个中转站都拆开检查包裹再封装（各自重传），远不如”只管转发、最终由 F 自己校验”高效。
  • 端到端原则：功能若能在端点（收发双方）完整实现，就不要放进网络中间。重传若放 IP 层，A→B 丢了 B 重传 C，C 丢了重传 D，但 D 最终收没收到 A 其实还是不知道——中间每跳都成功，端到端可靠性依然没保证。
  • IP 的”尽力而为”是故意的：不保证送达、不保证顺序、不保证不重复。互联网几十亿设备，核心路由器每秒转发几十亿包，能跑这么快正是因为只看目的 IP 转发、不维护任何连接状态（无状态转发）；每个路由器都维护序列号、窗口、超时计时器的话内存和 CPU 直接扛不住。
  • 因此分工明确：中间网络只负责尽力投递，丢了就丢了；可靠性由端点的 TCP 负责——这就是 TCP 的设计出发点。

追问 答案
UDP 也是传输层，和 TCP 分工差在哪？ UDP 基本就是给 IP 加了个端口号，别的什么都不管；TCP 是重型选手，连接管理、可靠传输、流量控制、拥塞控制一应俱全。选哪个看场景：DNS 丢一次重发即可 → UDP；视频直播丢几帧没事但不能卡 → UDP；转账一个字节都不能错 → TCP。
端到端原则这么好，为什么现在还在中间加 NAT、防火墙、CDN？ 现实妥协。NAT 因 IPv4 地址不够用，防火墙因安全需求必须在边界过滤，CDN 因性能要把内容推到离用户近处。这些都违背端到端原则但解决了实际问题，代价是 NAT 让 P2P 变复杂、防火墙常误杀正常流量、CDN 带来缓存一致性问题。
QUIC 把可靠传输挪到应用层，不是和分层矛盾吗？ 不矛盾，反而是分层思想的延续。动机是 TCP 在内核里改不动、历史包袱重，搬到应用层后迭代速度快得多。IP 层依然只管转发，可靠性仍在端点实现，只是从内核 TCP 挪到了用户态 QUIC。
链路层和 IP 层各起什么作用？ 链路层不可或缺——设备终归是逐跳链路连接的；IP 充当地址功能，靠 IP 找到对方后链路层到 IP 其实就能完成通信了。也正因为”理论上不需要传输层”，TCP 的存在才必须用端到端原则论证。

❌ 千万别说的话

  • ❌「IP 层也能做可靠性，只是实现起来比较麻烦而已。」——不是麻烦，是会让海量无状态设备被迫维护连接状态，网络无法 scale。
  • ❌「有了 TCP 就不需要 IP 了。」——IP 负责寻址与转发，是 TCP 能工作的前提。

[14] TCP 的粘包和拆包能说说吗？

🎬 面试现场

面试官：你用 Socket 连续 write 了 10 次，接收端却一次读出来一堆——粘包拆包到底怎么回事？怎么破？

⚠️ 翻车点

  • 说成”TCP 有 bug””粘包是操作系统 bug”——它其实是字节流的固有特性，不是 bug。
  • 只说”用固定长度”就收尾，没意识到定长会靠填充浪费带宽，也没给出生产上真正可用的方案。

📝 现场作答

  • 本质：TCP 是面向连接的流式传输协议，数据以无明确起止边界的字节流形式传输，必须由应用自己划分边界；粘的是应用层的数据报。
  • 为什么 TCP 首部无法像 UDP 那样分割：UDP 首部带报文长度字段，TCP 首部没有长度属性字段，因此传输层无法确定数据报边界。
  • 粘包成因：① 单次写入数据小于发送缓冲区，TCP 把多次写入合并成一次发出；② 接收端应用层没及时读取接收缓冲区，多个包堆在一起被一次读走。
  • 拆包成因：① 单次写入数据大于发送缓冲区剩余空间；② 待发数据大于 MSS（最大报文长度），TCP 在传输前就被拆开。
  • 四种通用解法：① 固定包长（统一 1024 字节，不足补空格）——能解决但数据量小时要靠填充字符补齐，白白增加网络负担，不是理想方案；② 添加分隔符（末尾加 \r\n）——实现简单，但正文若出现结束符仍会半包，复杂内容要额外编解码；③ 消息头 + 消息体（头部记录 body 长度，读够长度才算完整消息）——设计、实现复杂度较高但最通用；④ 自定义协议统一封装。
  • 分隔符的典型写法：Java 用 BufferedWriter 以 \n 结尾写入（并记得 flush()），服务端用 BufferedReader.readLine() 按行读取确定流边界。
  • 长度字段的典型写法：定义固定字节数的消息头（如 8 字节）存 body 长度，封装成 head + body；接收端先 read 满消息头取出 body 长度，再循环 read 直到读够 body 长度。
  • HTTP 是分隔符 + 长度字段的组合：请求行以 \r\n 结束、请求头以 \r\n 结束、\r\n\r\n 表示头结束；body 用 Content-Length 标识长度（接收端先按它申请 buffer，发送端按实际字节数填入）；长度未知时用 Transfer-Encoding: chunked。
  • chunked 的构成：chunk（大小 + 数据，大小用 16 进制表示，chunk 间以 CRLF 分隔）+ last-chunk（大小为 0 表示结束）+ trailer（附加 header，一般为空，用 CRLF 标识整体结束）。
  • chunked 的取舍：优点是 10K 的 body 只需申请 1K buffer 循环用 10 次而非申请 10K 连续内存，内容长度未知时也能发，还能边压缩边发；缺点是解析复杂，且在 Nginx 这类转发场景下难以处理分块数据的转发。

追问 答案
粘包拆包只发生在传输层吗？ 数据链路层、网络层、传输层都可能出现；日常网络应用开发多在传输层，且因 UDP 特性，该问题仅在 TCP 协议中发生（UDP 有明确消息边界）。
能不能只靠定长解决？ 能，但不理想：小包要补空格到指定长度，额外增加网络传输负担。定长适合包大小固定、且可控填充开销可接受的场景。
分隔符方案的硬伤是什么？ 消息正文中若出现结束符会被提前截断，产生半包；处理复杂字符串需要对内容做编解码以保证结束符语义正确。

[15] 说说 TCP 的三次握手？

🎬 面试现场

面试官：三次握手那三个包分别长什么样？为什么非得三次，两次不行、四次行不行？

⚠️ 翻车点

  • 答”三次握手是为了确认双方的收发能力”就收尾——RFC 793 指出的首要原因是防止历史连接建立。
  • 答不出第二次握手把 ACK 和 SYN 合并的技术原因（SYN 和 ACK 都由内核控制，而 FIN 由应用程序触发）。

📝 现场作答

  • 定义：通过三个包保证双向收发能力正常、同步初始序列号，建立可靠连接。
  • 第一次：客户端发 SYN（SYN=1）并带随机 ISN seq=x，客户端进入 SYN_SENT。
  • 第二次：服务端回 SYN+ACK（SYN=1, ACK=1），ack = x + 1，同时带自己的 ISN seq = y，服务端进入 SYN_RCVD。
  • 第三次：客户端发 ACK（ACK=1），ack = y + 1，客户端进入 ESTABLISHED；服务端收到后同样进入 ESTABLISHED，连接建立。
  • 为什么必须三次 —— 首要原因是防止历史连接：若只有两次握手，一个滞留的旧 SYN 可能后到，服务端无法分辨新旧，直接回 SYN+ACK 并进入 ESTABLISHED，甚至开始发数据；客户端发现 ack 不对会回 RST 终止，白白浪费双方资源。三次握手让客户端有”开口解释”的机会——接的是老连接就 RST，是新连接就回 ACK。
  • 第二个作用是同步初始序列号：要完成”Client 告诉 Server 我的 seq=x → Server 确认 → Server 告诉 Client 我的 seq=y → Client 确认”这四步；但第二步”Server 确认收到 x”与第三步”Server 告诉 Client 我的 seq=y”都由内核在同一时刻完成，可以合并成一个 SYN+ACK，所以是三次而不是四次。
  • 序列号为什么必须同步：网络可能丢包、重复、乱序，TCP 要靠序列号去重、排序、重传；序列号有序且连续，初始化不同步，后面所有数据都对不上号。
  • 为什么不是四次：逻辑上确实是 SYN → ACK → SYN → ACK 四次，只是中间两条由内核合并；理论上 3 次以上都能工作，但 3 次已经够，没必要更多。
  • 三次握手能带数据吗：第一次和第二次不能带（连接尚未建立，允许带数据会带来安全风险，攻击者可在 SYN 里塞大量数据）；第三次可以带，此时客户端已确认服务端接收能力正常。不过实际很少这么用，一来需要应用层配合，二来大多数场景等连接建立后再发数据。

💡 主动加分的追问准备

追问 答案
第三次握手的 ACK 丢了会怎样？ 客户端发完 ACK 就进 ESTABLISHED，以为建好了；服务端没收到还卡在 SYN_RCVD，会超时重传 SYN+ACK，客户端收到后再补一次 ACK；重传若干次仍失败，服务端放弃这个半连接。此时客户端若发数据，服务端发现连接没建好，直接回 RST 终止。
什么是 SYN Flood，怎么防御？ 攻击者伪造大量不存在的 IP 发 SYN，服务器回 SYN+ACK 后这些 IP 不会应答，只能等超时，半连接堆积占满 SYN 队列，正常用户就连不上。防御有三招：① 调大 SYN 队列、缩短半连接超时时间（治标不治本）；② SYN Cookie——不维护半连接状态，把状态编码进 SYN+ACK 的序列号，收到第三次握手时再验证；③ 防火墙/代理前置过滤，只有完成三次握手的连接才放行。
初始序列号为什么要随机？ ① 防止历史连接残留包干扰新连接：上个连接刚关闭、网络里还有残留包在飘，新连接若用相同四元组和相近序列号，残留包会被误认为新连接的数据；② 安全考虑：ISN 固定或可预测的话，攻击者可伪造 TCP 包做会话劫持或 TCP 重置攻击。
服务端看到大量 CLOSE_WAIT 是什么原因？ 对端已发 FIN，本端却还没调 close()：要么业务代码没调 close，要么调得不及时。CLOSE_WAIT 堆积基本等于应用侧有 fd 或线程泄漏。
完整的 TCP 11 个状态？ LISTEN、SYN-SENT、SYN-RECEIVED、ESTABLISHED、FIN-WAIT-1、FIN-WAIT-2、CLOSE-WAIT、CLOSING、LAST-ACK、TIME-WAIT、CLOSED。

❌ 千万别说的话

  • ❌「三次握手的目的就是确认双方的收发能力。」——收发能力验证是效果，RFC 793 明确的首要原因是防止历史连接的建立、减少不必要的资源消耗。
  • ❌「第三次握手也可以带大量数据，没区别。」——前两次带数据有安全风险；且服务端重传 SYN+ACK 时客户端已进 ESTABLISHED，连接不一定对得上号。

[16] TCP 初始序列号 ISN 怎么取值的？

🎬 面试现场

面试官：三次握手里那个初始序列号到底怎么算出来的？为什么不能写死？

⚠️ 翻车点

  • 答”随机生成一个数”——漏掉时间递增这一半，说不清为什么 4 微秒加 1。
  • 把 RFC 793 的假时钟和 RFC 6528 的安全改进混为一谈。

📝 现场作答

  • 本质：ISN = 以时间戳为基础 + 随机值，两者缺一不可。
  • RFC 793 的规定：ISN 与一个假时钟绑定，每 4 微秒加 1，超过 2^32 后从 0 重新开始——即大约四个半小时回绕一次。所以 ISN 本质是个递增值。
  • 为什么不能写死成 0：连接已经发到第 20 个包、序列号到 20000 时网络突然断了，客户端用同样的端口重连、序列号又从 0 开始，服务端还记着旧连接状态并返回第 20 个包的 ACK，客户端完全对不上号。基于时间递增则短时间重连的 ISN 必然比之前大，不会撞车。
  • 两个设计收益：① 避免序列号冲突——两个连接短时间用相同 ISN 会让数据包被误认为属于前一次连接，引发数据错乱；② 提高安全性——动态 ISN 让预测或篡改序列号变困难，能抵御序列号预测攻击。
  • RFC 6528 的安全改进：ISN 公式里的 M 就是那个每 4 微秒加 1 的计时器，F 是伪随机函数——可基于 MD5 把源 IP、源端口、目的 IP、目的端口 + 一个密钥做哈希。即使攻击者知道四元组，没有密钥也算不出 ISN。
  • 序列号预测攻击：攻击者若能预测下一个 ISN，就能伪造报文注入连接。经典场景是TCP 会话劫持——伪装成客户端向服务端发送序列号正确的包，服务端以为是正常客户端就接受了。早期部分操作系统 ISN 算法太弱，抓几个包就能摸出规律，Morris 蠕虫利用过这个漏洞；现代系统用 RFC 6528 后，预测难度从”做几道数学题”变成”破解 MD5”。

追问 答案
四个半小时回绕一次会不会出问题？ 正常不会。TCP 有 MSL 概念，一个报文在网络中最多存活 2 分钟，四个半小时远大于 MSL，绕回来时旧报文早被丢弃。但若带宽极大、序列号消耗极快，可能不到四小时半就绕完，这时需要开启 TCP 时间戳选项辅助判断报文新旧。
序列号和确认号什么关系？ 序列号标识”我发的这段数据从第几个字节开始”，确认号标识”我已经收到第几个字节之前的所有数据，下一个期望收到第几个”。例：客户端 seq=1000 发 100 字节，服务端回 ACK=1100，含义是”1100 之前的都收到了，下次从 1100 开始发”。两者配合实现了可靠传输和流量控制。
序列号是按字节还是按包编号？ 按字节。TCP 给发送的每个字节编序号，报文段首部里的 Seq 字段存的是本段第一个字节的序号。

❌ 千万别说的话

  • ❌「ISN 就是个随机数。」——它是时间递增（每 4 微秒 +1）+ 随机的组合，只说随机就答不完整。
  • ❌「RFC 793 规定的 ISN 用 MD5 加密钥。」——MD5 + 四元组 + 密钥是 RFC 6528 的安全改进，RFC 793 只规定与假时钟绑定递增。

[17] TCP 三次握手时，发送 SYN 之后就宕机了会怎么样？

🎬 面试现场

面试官：客户端发完 SYN 就崩了，对面服务器会一直挂着吗？它怎么发现这个人已经没了？

⚠️ 翻车点

  • 以为服务端会”永远等”或者”立刻释放”，其实是有重试次数和超时机制的。
  • 把重试间隔说成固定的，实际是指数退避。

📝 现场作答

  • 服务端收到 SYN 后回复 SYN+ACK，并把连接放进半连接队列（SYN Queue），自己进入 SYN_RCVD 状态。
  • 收不到第三次握手的 ACK，服务端按指数退避重传 SYN+ACK：1s、2s、4s、8s、16s……Linux 默认重试 5 次，由 /proc/sys/net/ipv4/tcp_synack_retries 控制。
  • 第 5 次重发后还会再等 32s，仍无响应才判定连接失败、移出半连接队列释放资源，总耗时约 1+2+4+8+16+32 = 63 秒。
  • 半连接队列大小由 net.ipv4.tcp_max_syn_backlog 控制（Linux 默认常见 1024/2048），满了新 SYN 直接被丢弃；只有收到第三次握手 ACK 才移入全连接队列等 accept()。
  • 反过来服务端发完 SYN+ACK 宕机，客户端按 tcp_syn_retries（默认 6 次、约 127 秒）重试，对客户端来说就是”连接超时”。

💡 主动加分的追问准备

追问 答案
SYN Cookie 怎么做到不存半连接状态？ 把客户端 IP、端口、时间戳、MSS 等经单向散列编码成 32 位序列号放进 SYN+ACK 的 ISN，ACK 带回该值加一，收到 ACK 后用同样算法反算验证，通过才真正建连，服务端全程零状态存储。
SYN Cookie 的缺点？ 不存状态导致 Window Scale、SACK 等握手阶段选项可能失效；且有 CPU 开销。所以 Linux 默认半连接队列将满时才启用（tcp_syncookies）。
tcp_synack_retries 设成 0 会怎样？ 只发一次 SYN+ACK，收不到就失败。公网丢包常见，设 0 会导致大量正常握手失败，一般至少 2~3 次。
全连接队列满了会怎样？ 看 tcp_abort_on_overflow：默认 0 时静默丢弃 ACK 让客户端重传，有机会在队列腾出后建连；设 1 则直接回 RST。生产建议保持默认并监控溢出。

❌ 千万别说的话

  • “服务端收到 SYN 就直接建立连接了”——要经过 SYN_RCVD 和半连接队列。
  • “重传间隔是固定的 1 秒”——是指数退避 1/2/4/8/16。

[18] 什么是 SYN Flood 攻击？

🎬 面试现场

面试官：SYN Flood 到底打的是什么资源？你们线上怎么防？

⚠️ 翻车点

  • 只答”半连接队列被占满”，说不出分层的防御手段。
  • 把 SYN Cookie 说成”降低系统开销”，其实是”不占队列状态”。

📝 现场作答

  • 原理是打满服务器的半开连接队列：攻击者伪造大量不同源 IP 发 SYN，服务端逐个回 SYN+ACK 并记账等 ACK，ACK 永远不会来，正常用户的连接被挤出。
  • 系统层——SYN Cookie：队列满时不再分配资源，把 ISN 设成由客户端 IP、端口、时间戳和服务器密钥算出的哈希值；合法客户端回 ACK 携带 Cookie+1，服务端重算验证通过才建连。
  • 系统层——缩短半连接超时 / 扩大 backlog：更快释放半开连接、加大缓冲，但治标不治本，攻击者能填满更大的队列。
  • 网络层——速率限制与 SYN 代理/源认证：防火墙或清洗设备代客户端完成握手，收到有效 ACK 后才向后端转发新 SYN；首包丢弃利用”攻击者不重传、正常客户端会重传”的差异来识别伪造源。
  • 架构层——云清洗服务与负载均衡：Cloudflare、Akamai、AWS Shield 等在互联网边缘过滤；L4 LB 自己完成握手，把半连接队列管理从后端剥离；边界设备用 ACL 过滤。

💡 主动加分的追问准备

追问 答案
首包丢弃为什么有效？ 伪造源 IP 的攻击者不会重传 SYN；正常客户端超时后会自动重传 SYN，设备收到重传包才视为合法并放行或启动源认证。
SYN Cookie 为什么不能一直开？ 它使 Window Scale、SACK 等需握手协商的选项失效，且有 CPU 开销；且靠状态编码无法覆盖全部信息。
为什么要多层防御？ 单机 SYN Cookie/参数挡不住大规模分布式洪泛；速率限制对伪造源 IP 和 DDoS 效果有限，必须配合边缘清洗与架构层卸载。

❌ 千万别说的话

  • “SYN Flood 靠的是带宽打满”——它是打连接状态资源，不是打带宽。
  • “开了 SYN Cookie 就彻底免疫 SYN Flood”——它只保护半连接队列，其他资源仍可能被拖垮。

[19] TCP 协议是如何保证可靠传输的？

🎬 面试现场

面试官：IP 明明是不可靠的，TCP 凭什么能保证可靠？都靠哪些机制？

⚠️ 翻车点

  • 答成”TCP 有三次握手所以可靠”，把可靠性来源答偏了。
  • 混淆流量控制（rwnd）和拥塞控制（cwnd）。

📝 现场作答

  • 核心思路四句：给数据编号、收到要确认、丢了就重传、发太快要控制。
  • 序列号 + 确认号：TCP 按字节编号，接收方 ACK 说明”第 N 字节之前的数据都收到了”，发送方据此判断哪些丢失。
  • 超时重传：发完数据启动计时器，超时未收到 ACK 就重发；RTO 由 Jacobson 算法按 RTT 均值加约 4 倍均值偏差动态算出，重传后 RTO 翻倍指数退避。
  • 流量控制（滑动窗口）：接收方在 ACK 里通告 rwnd，发送方不能超过它，避免撑爆对方缓冲区；rwnd=0 时停发并定期发探测报文。
  • 拥塞控制（cwnd）：慢启动（每轮 RTT 翻倍）、拥塞避免（每 RTT 加 1 个 MSS）、快速重传（3 个重复 ACK）、快速恢复（ssthresh 减半，cwnd=ssthresh+3）。
  • 校验和：报文校验和不对直接丢弃，等发送方超时重传；再加上 SACK 扩展，接收方能精确告知”1002-1500、1600-2000 已收到”，避免重传已到达数据。
  • 实际发送窗口取 min(rwnd, cwnd)；SYN/FIN 也各占一个序号。

💡 主动加分的追问准备

追问 答案
TCP 能保证数据 100% 不丢吗？ 不能，只能”尽最大努力可靠交付”。网络彻底断开、对方宕机、重传达上限时连接会被强制断开，应用层收到错误；关键业务仍需应用层确认机制。
序列号为什么不从 0 开始？ 安全考虑。固定序列号易被猜测，攻击者可伪造报文插入连接实施 TCP 劫持；随机化还能避免上次连接残留旧报文被新连接误收。
流量控制和拥塞控制的区别？ 流量控制是端到端、由接收方 rwnd 控制，保护接收方；拥塞控制是端到网络、由发送方 cwnd 控制，保护网络；发送窗口取两者较小值。
快速重传为什么快？ 不等 RTO，收到 3 个重复 ACK（如连续 ACK=1001）就判定 1001 丢失立即重传，把恢复时间从几百毫秒降到几十毫秒。

❌ 千万别说的话

  • “TCP 因为三次握手才可靠”——握手是双向确认与参数协商，可靠性靠编号、确认、重传、窗口。
  • “拥塞窗口是接收方通知的”——cwnd 由发送方自己维护，接收方只给 rwnd。

[20] 说说 TCP 的四次挥手？

🎬 面试现场

面试官：断开连接为什么要四次？能不能合并成三次？顺便把状态变迁讲一遍。

⚠️ 翻车点

  • 状态名说错、顺序说错（尤其把 FIN_WAIT_1/FIN_WAIT_2 和 CLOSE_WAIT/LAST_ACK 混）。
  • 认为 TIME_WAIT 只出现在客户端。

📝 现场作答

  • 客户端先发 FIN，进入 FIN_WAIT_1（seq=u）。
  • 服务端收 FIN 立即回 ACK（seq=v, ack=u+1），进入 CLOSE_WAIT；客户端收到该 ACK 后进入 FIN_WAIT_2。
  • 服务端应用把剩余数据发完后发 FIN（seq=u+1, ack=v），进入 LAST_ACK。
  • 客户端回最后一个 ACK（seq=u+1, ack=v+1），进入 TIME_WAIT；服务端收 ACK 后进入 CLOSED。
  • 客户端 TIME_WAIT 持续 2MSL（Linux 固定 60s，MSL=30s）后自动进入 CLOSED。
  • 不能合并成三次的原因：TCP 全双工，收到 FIN 只说明”对方不会再发数据”，本端可能还有数据要发，所以被动关闭方的 ACK 与 FIN 通常不同时发。
  • TIME_WAIT 发生在主动关闭方，客户端和服务端都可能；2MSL 保证 ①最后的 ACK 丢失时能对重发的 FIN 补发 ACK，②两个方向的旧报文都在网络中消亡，不被新连接误收。

💡 主动加分的追问准备

追问 答案
MSL 和 TTL 有什么区别？ MSL 是时间（报文最大生存时间），TTL 是 IP 头的跳数，每过一跳减 1，到 0 丢弃并回 ICMP。MSL 需不小于 TTL 耗尽所需的时间。Linux TTL 一般 64，MSL 取 30s。
为什么是 2MSL 而不是 4、8MSL？ 一来一回（我的 ACK 最长跑 1 MSL，对方重发的 FIN 最长再跑 1 MSL）已覆盖最坏情况；1% 丢包率下连续丢两次的概率仅万分之一，忽略它比处理它更划算。
服务端 TIME_WAIT 过多是什么原因？ ①HTTP 未开长连接，短连接响应完服务端主动关闭；②长连接请求数上限太小，如 nginx keepalive_requests 默认 100，QPS 高时频繁关连接。分别用 Keep-Alive 和调大 keepalive_requests 解决。
服务端大量 CLOSE_WAIT 说明什么？ 被动关闭方收到 FIN 后没调用 close，状态卡在 CLOSE_WAIT 无法转 LAST_ACK，属于应用代码 bug 或处理逻辑阻塞，需要排查为什么没执行到 close。

❌ 千万别说的话

  • “服务端收到 FIN 马上发 FIN，所以要四次是因为丢包”——四次的原因是全双工、ACK 与 FIN 通常不能合并。
  • “TIME_WAIT 是客户端特有的状态”——它属于主动关闭方，两端都可能出现。

[21] 为什么 TCP 挥手需要有 TIME_WAIT 状态？

🎬 面试现场

面试官：主动关闭方都断开完了，为什么还要在 TIME_WAIT 里赖两分钟不走？

⚠️ 翻车点

  • 只答”防止旧报文干扰新连接”，漏掉”保证最后一个 ACK 可达”这一半。
  • 把 tcp_tw_recycle 当成推荐方案推荐出去。

📝 现场作答

  • 主动关闭方发完最后一个 ACK 后进入 TIME_WAIT，持续 2MSL（RFC 793 的 MSL 是 2 分钟，Linux 实现为 30s，故 2MSL=60s）。
  • 作用一：最后一个 ACK 若丢失，被动关闭方没收到会重发 FIN；若主动方已进 CLOSED 就会回 RST 导致关闭报错。留在 TIME_WAIT 就能对重发的 FIN 立刻补发 ACK。
  • 作用二：旧连接关闭后网络中仍有”迟到”的旧报文，若立刻用同样的四元组建新连接，旧报文会被新连接当成自己的数据接收，造成数据错乱；等 2MSL 让两个方向的报文自然消亡。
  • 2MSL 的来历是”一来一回”的最坏时间：我发的 ACK 最长跑 1 个 MSL，对方重发的 FIN 最长再跑 1 个 MSL。
  • 代价：服务端主动关大量连接会堆积资源占用；客户端主动关则 2MSL 内端口被占（临时端口通常 32768–60999），端口耗尽会报 Cannot assign requested address。
  • 参数：tcp_tw_reuse（连接发起方复用超过 1s 的 TIME_WAIT 连接，需配合 tcp_timestamps）；SO_REUSEADDR（用户态套接字选项，允许在 TIME_WAIT 端口上重新 bind，用于重启）；tcp_tw_recycle 会破坏 NAT 环境、Linux 4.12 后已移除，不推荐。

💡 主动加分的追问准备

追问 答案
TIME_WAIT 占的资源大吗？ 每条约 3.3KB，10 万条约 330MB，对现代服务器不算大；真正的问题是端口耗尽——客户端可用端口约 2.8 万个，短连接频繁建销容易占光。
怎么查当前 TIME_WAIT 数量？ ss -tan state time-wait | wc -l 直接计数，netstat -an | grep TIME_WAIT 看明细；数量过多要排查短连接是否过多、该用连接池的地方有没有用。
长连接还是短连接产生更多 TIME_WAIT？ 短连接。HTTP/1.0 默认短连接，每请求一次关一次连接就产生一个 TIME_WAIT；HTTP/1.1 默认 keep-alive 可复用，Nginx 默认 keepalive_timeout 75 秒。
为什么 Linux 把 MSL 从 2 分钟改成 30 秒？ 2 分钟是 RFC 793 在 1981 年定的，当时网络延迟高。现代网络报文很难存活那么久，30 秒已覆盖绝大多数情况，缩短 MSL 能更快回收 TIME_WAIT 资源。
服务端主动关闭大量连接有什么好办法？ 没有完美方案。建议服务端不主动关闭，把主动关闭权交给客户端（应用层发一条消息让客户端断开），或用 SO_REUSEADDR 支持快速重启。

❌ 千万别说的话

  • “开启 tcp_tw_recycle 就能秒回收 TIME_WAIT”——它会破坏 NAT 场景（同一 NAT 出口的机器时间戳不递增会被误判为过期包丢弃），且已被内核移除。
  • “把 tcp_tw_reuse 和 SO_REUSEADDR 是一回事”——前者是内核选项、用于连接复用；后者是用户态套接字选项、用于端口绑定。

[22] 除了四次挥手，还有什么方法断开连接？

🎬 面试现场

面试官：正常四次挥手之外，TCP 还有哪些方式能把连接断掉？各自的适用场景是什么？

⚠️ 翻车点

  • 只说”RST 一种”，漏掉超时自动断开（keepalive / 应用层超时）。
  • 认为 RST 是”更好的关闭方式”。

📝 现场作答

  • 除四次挥手外主要有两种：RST 强制关闭和超时自动断开。
  • RST：带 RST 标志的报文，对端收到立刻释放连接，不走四次挥手，不等对方确认；代价是收发缓冲区里未处理的数据直接丢。
  • 超时断开：连接长时间无数据往来时由内核 keepalive 探测；应用层也可设自己的超时（HTTP Keep-Alive timeout、数据库连接池空闲超时、WebSocket 心跳）。
  • Linux keepalive 三参数：tcp_keepalive_time 默认 7200 秒开始探测、tcp_keepalive_intvl 默认 75 秒间隔、tcp_keepalive_probes 默认 9 次；默认要 2 小时 + 11 分钟才判死，生产一般大幅调短（如空闲 60 秒开始探测）。
  • 正常业务用四次挥手保证数据发完；RST 用于异常场景，如检测到攻击要立刻掐断、程序出 bug 需要快速释放资源。
  • 高性能服务器有时故意设 linger=0 让 close 直接发 RST 快速回收，但客户端可能收到 connection reset，体验变差，需权衡。

💡 主动加分的追问准备

追问 答案
收到 RST 后应用层感知到什么？ read 返回 -1 且 errno 为 ECONNRESET；write 第一次可能成功但数据发不出去，第二次会收到 SIGPIPE 或返回 EPIPE。Java 侧表现为 Connection reset / Broken pipe 异常。
怎么在代码里控制发 RST 还是四次挥手？ 设置 socket 选项 SO_LINGER：l_onoff=0 或未设置时 close 走正常四次挥手；l_onoff≠0 且 l_linger=0 时直接发 RST；l_onoff≠0 且 l_linger>0 时 close 阻塞等待发完，超时则发 RST。
服务端大量 TIME_WAIT 和大量 CLOSE_WAIT 分别什么原因？ TIME_WAIT 多说明服务端主动关闭，属正常现象，可调 tcp_tw_reuse；CLOSE_WAIT 多说明服务端收到 FIN 却没调用 close，是代码 bug 或逻辑阻塞。
HTTP 长连接和短连接哪个更省？ 长连接。HTTP/1.0 默认短连接每请求关一次连接，每次都产生 TIME_WAIT；HTTP/1.1 默认 keep-alive 复用连接，关闭频率大幅降低。

❌ 千万别说的话

  • “RST 更安全、关闭更快所以都用 RST”——RST 会丢数据，正常业务必须走 FIN。
  • “TCP 有 keepalive 就不会产生僵尸连接”——默认 2 小时起步，太长，生产必须调短。

[23] TCP 超时重传机制是为了解决什么问题？

🎬 面试现场

面试官：数据发出去石沉大海怎么办？超时重传的 RTO 到底是怎么算出来的？

⚠️ 翻车点

  • 把 RTO 说成固定值或简单取 RTT 的两倍。
  • 认为收到 ACK 就一定是回复第一次发送的，不提 Karn 算法。

📝 现场作答

  • 解决的核心问题是丢包后怎么办：路由器过载、链路故障都会丢包，TCP 作为可靠传输必须有兜底机制。
  • 逻辑：发出数据后启动计时器，规定时间（RTO）内没收到 ACK 就认为包丢了，重发一遍。
  • ACK 确认号是字节为单位且只能确认最大连续收到的包：发 1、2、3、4 收到 1、2、4 时只能 ACK 3，绝不能 ACK 5，否则发送方误以为 5 之前都收到了。
  • RTO 由 RTT 推导。RFC 793 公式：SRTT = ALPHA*SRTT + (1-ALPHA)*RTT，RTO = min[UBOUND, max[LBOUND, BETA*SRTT]]；ALPHA 取 0.80.9，BETA 取 1.32.0，上界 UBOUND 约 1 分钟，下界 LBOUND 约 1 秒。
  • Karn / Partridge 算法：发生重传的往返不采样 RTT（分不清 ACK 是回复谁），代价是网络突然变差时 RTO 偏短，所以重传时直接把 RTO 翻倍。
  • Jacobson / Karels 算法：把最新 RTT 与平滑后的 SRTT 做波动计算，得到更合适的 RTO，兼顾抖动。
  • 超时重传代价大：等待期间吞吐降到 0；一旦超时就把 cwnd 砍到 1 个 MSS 重新慢启动；有时数据没丢只是 ACK 晚到，重传纯属浪费带宽——所以才有快速重传作为补充。
  • Linux 参数：tcp_retries1 默认 3（达此次数尝试更新路由）、tcp_retries2 默认 15（直接放弃连接，指数退避下约 13~30 分钟）、tcp_syn_retries 默认 6（约 127 秒后放弃 SYN 重试）。

💡 主动加分的追问准备

追问 答案
RTO 设置不合理有什么后果？ 太小则正常包还没回来就重传，浪费带宽甚至加剧拥塞；太大则真丢包要等很久才恢复，体验差。早期固定值或简单平均效果很差，现在都用 Jacobson 算法把 RTT 波动算进去。
超时重传和快速重传的区别？ 超时重传是兜底，RTO 到期没收到 ACK 触发；快速重传是优化，收到 3 个重复 ACK 说明后面的包到了、中间某个丢了，立即重传。快速重传更快但依赖后续包持续到达，窗口末尾的包丢了或整段链路断了只能靠超时重传。
为什么 3 个重复 ACK 才触发快速重传，2 个不行？ 网络本身会乱序，1~2 个重复 ACK 很可能只是乱序不是丢包；连续 3 个说明后面至少 3 个包都到了，中间那个大概率真丢，误判概率足够低。
RTO 翻倍是哪种机制？ 指数退避。避免网络已拥堵还疯狂重传火上浇油；超时重传后 ssthresh 减半、cwnd 退回 1 个 MSS 重新慢启动。

❌ 千万别说的话

  • “RTO 就是 RTT 的两倍/固定 1 秒”——它是动态计算的，且是 RTT 均值加若干倍均差。
  • “ACK 号可以乱报，只要大于某个数就行”——累计确认只能报最大连续收到的位置。

[24] TCP 中何时会出现 RST（reset）报文？

🎬 面试现场

面试官：线上老是报 Connection reset，RST 到底什么时候会出现？你怎么定位是谁发的？

⚠️ 翻车点

  • 只答”对方端口没开”，说不出连接已不存在性丢失、非法序列号、SO_LINGER、队列溢出这几类。
  • 把 RST 和 FIN 的差别讲反（说 RST 更优雅）。

📝 现场作答

  • RST 是 TCP 的强制终止信号，收到后连接立刻断开，发送与接收缓冲区的数据直接丢弃，不走四次挥手。
  • 常见触发场景：①端口没人监听——SYN 到达但无进程 listen，内核直接回 RST；②连接已不存在——服务端重启或进程崩溃后 socket 表被清空，客户端用老四元组发数据，内核回 RST；③收到非法数据——序列号不在接收窗口内或属于不存在的连接。
  • 另外两类主动触发：④close 时设置 SO_LINGER 且 linger=0，内核发 RST 而不是 FIN；⑤全连接队列溢出，当 tcp_abort_on_overflow=1 时内核回 RST 拒绝新连接。
  • 与 FIN 的区别：FIN 是有序优雅关闭（先发完缓冲区数据再 FIN，对端 read 不报错）；RST 是暴力关闭（缓冲区数据全丢），对端 read 返回错误，recv 抛 Connection reset by peer。
  • 排查顺序：tcpdump/wireshark 看 RST 包的源 IP 判断是谁发的 → 确认进程存活与端口监听（ss -tlnp）→ 查安全组/iptables/firewalld 中途切连接 → 查 Nginx/HAProxy/LB 的连接超时配置 → 查 TIME_WAIT 是否占满端口。
  • RST 攻击：知道双方 IP、端口和序列号范围即可伪造 RST 劫持连接；防御靠 TLS 加密隐藏序列号、TCP MD5 签名（RFC 2385，BGP 常用）、随机化 ISN。
  • 相关内核参数：tcp_max_syn_backlog、net.core.somaxconn、tcp_abort_on_overflow（线上一般保持 0，避免打满时出现 RST 风暴）。

💡 主动加分的追问准备

追问 答案
抓包看到大量 RST 怎么定位责任方？ 看 RST 包的源 IP：服务端发的大概率是服务挂了、端口没监听或认为客户端数据有问题；客户端发的是客户端超时或主动断开。还要看前一个包：前面是 SYN 说明端口没监听，前面是正常数据包说明连接中途出问题。
服务重启后老客户端为什么会收到 RST？ TCP 连接靠四元组识别，重启后内核 socket 表被清空，老四元组找不到对应 socket，内核按协议回 RST，客户端 read 报 Connection reset by peer。所以要优雅重启：先停收新连接、等老连接处理完再退出，或用 SO_REUSEADDR 加热重启。
什么情况下该主动发 RST 而不是 FIN？ ①检测到对方行为异常（协议解析失败、认证不通过、恶意请求），没必要走 FIN 流程；②服务过载需要快速释放资源，比如全连接队列将满时对新请求直接 RST 好过排队等超时。正常业务流量仍应走 FIN。
为什么 RST 攻击在 HTTPS 下依然有效？ TLS 只加密应用层数据，TCP 头部明文，含序列号。攻击者嗅探到 TCP 流量即可拿到四元组和序列号范围并伪造 RST；实际难度在于要在同一网络嗅探，且伪造序列号必须刚好落在接收窗口内。

❌ 千万别说的话

  • “收到 RST 后对端还能把缓冲区数据读完”——RST 直接丢弃收发缓冲区数据。
  • “服务重启后老连接会自动恢复”——socket 表丢失就是回 RST，必须靠优雅重启或 SO_REUSEADDR 规避。

[25] TCP 有超时重传为什么还需要快速重传机制？

🎬 面试现场

面试官：TCP 不是已经有超时重传了吗，为什么还要搞一个快速重传？两者什么时候各管用？

⚠️ 翻车点

  • 答”快速重传可以缩短 RTO，所以更快”——把两者的触发依据（时间驱动 vs 数据驱动）混为一谈。
  • 以为快速重传能覆盖所有丢包场景，忽略它对窗口末尾丢包、连续丢包、网络断开完全无能为力。

📝 现场作答

  • 超时重传是时间驱动的，RTO 通常是 RTT 的好几倍，几百毫秒甚至秒级；很多场景网络本身没问题，只是某个包丢了，等超时纯属浪费。
  • 快速重传是数据驱动的：连续收到 3 个重复 ACK，说明后续包都正常到达、中间某个包丢了，网络畅通就立刻重传。
  • 效果：丢包恢复时间从几百毫秒压到几个 RTT，吞吐提升明显。
  • 为什么阈值是 3：网络本身存在乱序，1-2 个重复 ACK 容易误判迟到包；3 个意味着后续至少 3 个包已到达，平衡”快速响应”与”避免误判”，默认 3 次是 RFC 定义的标准行为。
  • 覆盖不到的三个场景：窗口末尾的包丢了（没有后续包触发重复 ACK）、连续丢多个包（一次只修一个）、网络完全断开（连重复 ACK 都没有）——只能等超时。
  • 二者互斥而非叠加：快速重传触发后会重置超时计时器，属于”抢先”处理；只有它没机会触发的场景才会等到超时。
  • 快速恢复（RFC 5681）配套使用：ssthresh = cwnd/2；cwnd = ssthresh + 3*MSS；每收到一个重复 ACK，cwnd 加 1 个 MSS；收到新 ACK 后 cwnd 设为 ssthresh，直接进入拥塞避免，不走慢启动。
  • 与 SACK 配合：没有 SACK 时快速重传只知道触发点那一个包丢了；有 SACK 可一次性重传全部丢失段，恢复效率大幅提升。

💡 主动加分的追问准备

追问 答案
快速重传和超时重传可能同时触发吗？ 不会，两者互斥。快速重传触发时会重置超时计时器，抢先处理了丢包；只有窗口末尾丢包、网络完全断开等场景才等到超时。
网络乱序很严重时，快速重传会不会频繁误触发？ 会，这是已知问题。极端乱序下很容易凑出 3 个重复 ACK。有些 TCP 变种引入额外乱序检测（结合 SACK 信息判断乱序还是真丢包，或动态调整阈值），Linux 内核的 tcp_reordering 就是干这个的，默认值 3，检测到经常乱序会自动调大。
快速恢复里 cwnd 为什么要设成 ssthresh + 3×MSS，而不是直接回到 ssthresh？ 那 3 个重复 ACK 说明已有 3 个包离开网络到达接收方，网络里实际数据少了 3 个包。加这 3 个 MSS 相当于补偿回来，让发送方能继续发数据填满管道，既保守控制又不让链路空跑。
没有 SACK 时代怎么解决丢包重传？ RFC 2018 定义 SACK 是 1996 年的事；此前主要靠 Go-Back-N（从丢失点往后全部重传，浪费带宽）和快速重传（能早动手，但仍不知道哪些包其实已到）。

❌ 千万别说的话

  • 不要说”超时重传太慢所以要快速重传”就收尾——必须补上”两者互补、覆盖场景不同”才完整。
  • 不要把”3 个重复 ACK”说成 TCP 拥塞控制里的阈值，它是快速重传的触发条件，两者别混。

[26] TCP 的 SACK 的引入是为了解决什么问题？

🎬 面试现场

面试官：SACK 是干什么的？没有它的时候 TCP 丢包重传是怎么做的？

⚠️ 翻车点

  • 只说”SACK 能告诉发送方哪些数据收到了”，说不出它解决的具体痛点：传统累计确认下发送方不知道该重传哪些。
  • 忽略实现约束——SACK 靠 TCP 选项字段携带，选项最多 40 字节，所以块数有限。

📝 现场作答

  • 传统 TCP 用累计确认，接收方只能表达”序号 X 之前的数据都收到了”；中间丢一个包，发送方只知道 X 后面有问题，具体哪些丢了、哪些其实已经到了，完全不知道——要么超时后一股脑全重传，要么靠重复 ACK 猜，效率都低。
  • SACK 让接收方精确表达”连续数据只到 X，但 Y-Z 区间我也收到了”，发送方只重传真正丢失的那一段。
  • 典型场景：ACK 告知接下来要 5500，同时 SACK 不断更新为 6000-6500、6000-7000、6000-7500，发送方据此明确知道 5500-5999 丢了，于是只重传这一段。
  • 多段不连续也能表达，例如 SACK 0-500, 1000-1500, 2000-2500 表示这三段已收。
  • 实现细节：通过 TCP 选项字段携带，三次握手时协商；一个 SACK 块占 8 字节记录左右边界，因选项总长上限 40 字节，通常最多带 3-4 个块。Linux 下默认开启，参数 net.ipv4.tcp_sack。
  • D-SACK：SACK 的扩展，用于告知发送方”你可能错误重传了我已经收到的段”。利用 SACK 第一段描述重复序号区间，若该段被 ACK 覆盖即说明重复（例：ACK 都到 6000 了还回 SACK 5000-5500）。参数 tcp_dsack，Linux 2.4 之后默认开启。
  • 知道重复有什么用：说明刚才那个包其实收到了、丢的是回程 ACK 包；或判断是否存在乱序（先发的后到）；或 RTO 是不是设得太小；或是网络数据复制抢先一步。
  • 历史背景：SACK 由 RFC 2018 定义于 1996 年；之前主要靠 Go-Back-N 和快速重传。SACK 配合快速恢复后，在高延迟、高丢包网络下吞吐提升明显。

💡 主动加分的追问准备

追问 答案
SACK 和快速重传什么关系，能同时用吗？ 完全可以，而且效果更好。快速重传解决”什么时候触发重传”（3 个重复 ACK 就动手），SACK 解决”重传哪些数据”（精确定位丢失段）。没有 SACK 时快速重传只能修触发点那一个包，后面还丢的得再等 3 个重复 ACK 或超时。
中间设备不支持 SACK，但两端都支持，会怎样？ 如果只是透传不认识的选项没问题；但老防火墙会直接删掉不认识的 TCP 选项，两端握手协商成功以为支持，实际数据传输时 SACK 信息到不了对端。不会出错，但优化效果消失，丢包恢复退化成传统模式。
D-SACK 具体帮发送方优化了什么？ 让发送方知道自己是否重传过头了（原包只是迟到，收到两份相同数据）。这可用于判断是否 RTO 太短需要调大、网络是否乱序需调整拥塞控制策略，长期看让重传决策更准。
SACK 有什么风险？ 三点：① 接收方要维护乱序队列，内存开销增加，攻击者可用大量乱序包耗尽资源，Linux 4.x 之前的 SACK Panic 漏洞就是精心构造的 SACK 序列让内核崩溃；② 部分老防火墙/中间设备会剥掉 SACK 选项；③ 极端情况下接收方一次性确认大量乱序数据，可能触发重传风暴打满链路。

❌ 千万别说的话

  • 不要说”SACK 让 TCP 变可靠了”——可靠性一直是 TCP 的目标，SACK 优化的是丢包恢复效率，不是可靠性本身。
  • 不要说 SACK 块可以随便加——TCP 选项总长 40 字节摆在那，实际最多 3-4 块。

[27] TCP 滑动窗口的作用是什么？

🎬 面试现场

面试官：滑动窗口到底是干什么的？它和拥塞控制是什么关系？

⚠️ 翻车点

  • 只答”提高效率”，漏掉更重要的流量控制——防止接收方缓冲区被撑爆导致丢包。
  • 分不清 cwnd 和 rwnd，说不清实际发送窗口是两者取小。

📝 现场作答

  • 两件事：流量控制（接收方告诉发送方自己还能收多少，防止缓冲区满而丢包）+ 效率（窗口内可连续发多个包，不必发一个等一个 ACK）。
  • 流量控制机制：接收方在 ACK 里带上还能收多少数据（窗口大小 rwnd），发送方只能在窗口内发；接收方处理一部分后把可收量从 1000 降到 500，发送方就按 500 继续，永远不会撑爆接收方。
  • 效率对比：停止等待是”发 1 → 等 ACK → 发 2 → 发 3”，网络大部分时间闲置；窗口大小 = 3 时是”发 1 2 3 → 收到 ACK1 → 窗口滑动 → 发 4”，在等待 ACK 的间隙继续发后续包。
  • 三个核心量：cwnd（发送方按网络拥塞程度自算）、rwnd（接收方告知的接收窗口）、**实际发送窗口 = min(cwnd, rwnd)**。
  • 滑动过程（窗口大小 = 3，序号从 1 开始）：初始为「已确认 1 | 已发送待确认 2,3,4 | 可发送 5,6,7 | 不能发送 8…」；收到 ACK2 后变为「已确认 1,2 | 待确认 3,4,5 | 可发送 6,7,8 | 不能发送 9…」——2 从待确认移出、5 发出、8 解禁。
  • 每收到一个 ACK 窗口右移一格，窗口大小不变、整体右移。
  • 一句话定义：滑动的本质是收到 ACK 后已确认数据移出窗口，右边界向右扩展纳入新数据。

💡 主动加分的追问准备

追问 答案
接收方缓冲区满了怎么办，发送方该怎么知道？ 接收方通过 ACK 报头里的窗口字段把 rwnd 收缩到 0，发送方必须停止发送。
cwnd 和 rwnd 谁说了算，两者冲突时取谁？ 取 min(cwnd, rwnd)。cwnd 反映网络是否拥塞，rwnd 反映接收方处理能力，任一方成为瓶颈都会限制发送速率。
接收方把窗口通告为 0，双方会不会死锁？ 不会。发送方有持续计时器，会定期发零窗口探测报文；接收方缓冲区有空间后重新通告窗口。窗口更新报文必须持久化，不能只放在缓冲区里，否则接收方崩溃重启后会一直等不到更新。
滑动窗口和拥塞控制是一回事吗？ 不是。滑动窗口提供流量控制与流水线效率的框架，拥塞控制（慢启动、拥塞避免等）决定 cwnd 的取值，两者取小后才是实际发送窗口。

❌ 千万别说的话

  • 不要把滑动窗口说成”只是提高效率的工具”，漏掉流量控制这一半。
  • 不要说”发送窗口 = cwnd”或”= rwnd”，正确答案是 min(cwnd, rwnd)。

[28] 说说 TCP 拥塞控制的步骤？

🎬 面试现场

面试官：讲一下 TCP 拥塞控制的完整流程，慢启动、拥塞避免、快重传快恢复分别在什么条件下发生、窗口怎么变？

⚠️ 翻车点

  • 把”收到 3 个重复 ACK”和”超时”混用同一套 cwnd 调整逻辑——两者完全不同：超时后 cwnd 归 1 重新慢启动，3 重复 ACK 只砍半并快恢复。
  • 背不出阈值和公式：ssthresh = cwnd/2、cwnd = ssthresh + 3×MSS、每收到一个重复 ACK 加 1 个 MSS、收到新 ACK 后 cwnd = ssthresh。
  • 忽略 cwnd 初始值的真实取值——教材里常说 1，但 Linux 实际是 10 个 MSS（可用 ss -nli 查看）。

📝 现场作答

  • 拥塞控制由五个算法实现：慢启动、拥塞避免、超时重传、快速重传、快速恢复，根据不同拥塞情况采取不同操作，动态调整发送速率。
  • 两条经典状态转移路径：慢启动 → 拥塞避免 → 超时重传 → 慢启动；慢启动 → 拥塞避免 → 快速重传 → 快速恢复 → 拥塞避免。
  • 慢启动：cwnd 从较小值起步，每收到一个 ACK 就 +1，因此每收到”一个窗口大小”的数据后 cwnd 翻倍，指数增长直到 ssthresh。示例：cwnd=1 → 收 1 个 ACK 变 2 → 收 2 个 ACK 变 4 → 收 4 个 ACK 变 8。
  • 慢启动门限 ssthresh：cwnd < ssthresh 用慢启动；cwnd ≥ ssthresh 用拥塞避免。ssthresh 一般为 65535 字节。
  • 拥塞避免：每收到一个 ACK，cwnd 增加 1/cwnd；因此一个 RTT 内所有 ACK 加起来正好让 cwnd 增加 1 MSS，由指数增长变为线性增长。示例（ssthresh=8）：8 个 ACK 各加 1/8，累计 +1，cwnd 从 8 变 9。
  • 超时重传（激进）：ssthresh = cwnd/2；cwnd 重置为 1，重新慢启动，速率骤降、会造成卡顿。
  • 快速重传：连续收到 3 个重复 ACK 即认定丢包，此时认为只是少量丢失、网络不严重：cwnd = cwnd/2；ssthresh = cwnd（即减半后的值）；进入快速恢复。
  • 快速恢复四步：cwnd = ssthresh + 3（3 表示已确认有 3 个包离开网络，用于补偿填满管道）；重传丢失包；再收到重复 ACK 则 cwnd += 1；收到新数据 ACK 后把 cwnd 设为第一步的 ssthresh，直接回到拥塞避免。
  • 效果对比：超时重传是”一夜回到解放前”，快恢复不回到起点、仍保持较高水位并继续线性增长。
  • 初始值细节：Linux 每条 TCP 连接的 cwnd 初始值是 10（个 MSS），不是 1，可用 ss -nli 查看。

💡 主动加分的追问准备

追问 答案
快速恢复过程中，为什么收到新数据 ACK 后 cwnd 要设回 ssthresh？ 快速恢复是拥塞发生后的优化，首要目的仍是降低 cwnd 减缓拥塞，所以必然出现由大到小；而过程中”每收一个重复 ACK 加 1”是为了尽快把丢失包发出去、尽快消除丢包这个根本问题，所以这一阶段 cwnd 反而在逐步增大。收到新 ACK 说明该 ACK 确认了新数据，恢复过程结束，回到恢复前的 ssthresh 水平重新线性增长。
Linux 里 cwnd 的初始值到底是多少？ 10 个 MSS，可用 ss -nli 观察连接初始拥塞窗口；教材里”初始化为 1”的假设是为讲清算法而简化。
为什么慢启动要指数增长，拥塞避免要线性？ 连接刚建立、网络状况未知，若线性起步则要么太慢浪费带宽、要么一次性猛冲把网络打爆；指数增长能在探测阶段快速逼近链路上限，触到 ssthresh 后必须放缓，用线性方式小心试探。
超时重传为什么必须把 cwnd 打到 1？ 超时意味着连 ACK 都收不到，无法判断是单包丢失还是网络严重拥塞/断裂，只能保守地认为网络已不可用，退回最小窗口重新慢启动探测，避免持续压垮网络。
拥塞避免阶段”每个 ACK 加 1/cwnd”怎么理解？ 等价于”每收到一个完整窗口的 ACK，cwnd 加 1 个 MSS”，即每 RTT 加 1，把指数增长降为线性。

❌ 千万别说的话

  • 不要把超时重传和快速重传的窗口调整说成同一套，前者 cwnd=1、后者 cwnd 只减半。
  • 不要说”慢启动从 cwnd=1 开始”却不说这是简化假设，Linux 实际初始值是 10 个 MSS。
  • 不要漏掉 ssthresh = cwnd/2 这个核心阈值公式。

四、网络分层与寻址

[29] ARP 和 RARP 分别是什么？有什么区别？

🎬 面试现场

面试官：ARP 解决什么问题？和 RARP 有什么区别？为什么 ARP 只在局域网内工作？

⚠️ 翻车点

  • 忽略 ARP 的存在必要性——IP 是逻辑地址，局域网内投递最终必须靠 MAC，IP 协议本身不提供二层寻址。
  • 说 ARP 跨网段也能用——ARP 广播不能过路由器。
  • 漏掉 ARP 无认证带来的 ARP 欺骗/中间人风险。

📝 现场作答

  • ARP 把 IP 转 MAC。因为 IP 只是逻辑地址，数据包在局域网里最终靠 MAC 送到具体网卡；只知道对方 IP 没用，必须知道对方 MAC 才能把帧发出去。
  • RARP 把 MAC 转 IP。典型场景是无盘工作站启动：机器只知道自己网卡的 MAC，不知道该用什么 IP，就通过 RARP 问服务器。
  • 对比：转换方向相反（IP→MAC vs MAC→IP）、使用场景不同（发数据前查目标 MAC vs 设备启动时获取自己的 IP）；工作方式相同（都是广播请求、单播响应）；现状不同——ARP 仍在广泛使用，RARP 基本被 DHCP 取代。
  • ARP 流程：A 先查本地 ARP 缓存 → 没有则广播 ARP 请求（”谁是 192.168.1.100？把你的 MAC 告诉我”）→ B 单播响应自己的 IP-MAC → A 把映射写入 ARP 缓存，下次直接用。缓存有过期时间，Linux 下一般 60 秒到几分钟。
  • 为什么请求广播、响应单播：请求时根本不知道目标 MAC，只能广播；响应时已知请求方 MAC，再广播只是浪费带宽。
  • RARP 流程：设备广播”My MAC 是 xx，谁能告诉我该用什么 IP？”→ RARP 服务器查配置表 → 单播回 IP → 设备完成网络配置。RARP 已被 BOOTP 和 DHCP 取代，DHCP 不只分配 IP，还能给网关、DNS、子网掩码，且支持动态分配。
  • ARP 缓存可用 arp -a 查看，能减少广播；但 ARP 没有任何认证机制，谁都能伪造响应，把别人的 IP 指向自己的 MAC 即为 ARP 欺骗，中间人攻击和局域网嗅探大量基于此。防御手段：静态 ARP 绑定、DAI 动态 ARP检测、VLAN 隔离。
  • 跨网段：ARP 只在同一广播域内工作，广播包过不了路由器。A 要给另一网段的 C 发数据时，A 不直接 ARP 问 C 的 MAC，而是把包发给默认网关、只需知道网关 MAC；路由器再在 C 所在网段查 C 的 MAC 并转发。每跳 MAC 都在变，IP 全程不变。

💡 主动加分的追问准备

追问 答案
ARP 缓存表满了会怎样？ 老条目按 LRU 策略被淘汰。Linux 下由 gc_thresh 系列参数控制，默认软限制 512 条、硬限制 1024 条。局域网设备特别多时需调大，否则会频繁触发 ARP 查询影响性能。
什么是免费 ARP（Gratuitous ARP）？ 主机自问自答的 ARP 请求，源 IP 和目标 IP 都填自己的 IP。作用：① 检测 IP 冲突；② 通知网络内其他设备更新 ARP 缓存，如换网卡、VRRP 主备切换时让新 MAC 被大家认识。
代理 ARP 在什么场景用？ 路由器替别人回答 ARP 请求。典型场景是两台主机在不同子网但物理上在同一网段且未配网关，互相 ARP 收不到响应，此时路由器开代理 ARP、用自己的 MAC 应答并代为转发。现在一般不推荐，因为它破坏网络隔离、增加安全风险。
ARP 有没有认证机制？ 没有，协议设计上就是无认证的，这是 ARP 欺骗的根源。防御靠静态绑定、DAI、VLAN 等旁路手段，而不是协议自身。

❌ 千万别说的话

  • 不要说”ARP 协议工作在网络层”——它是链路层/网络接口层的寻址协议。
  • 不要说”IP 包直接带 MAC 跨网段传输”——跨网段每跳 MAC 都变，只有 IP 不变。

[30] TCP/IP 四层模型是什么？

🎬 面试现场

面试官：TCP/IP 四层模型每层干什么？各层的数据单位和包头字段分别是什么？

⚠️ 翻车点

  • 层次名称说错——第四层是网络接口层（链路物理层），是数据链路层与物理层的合体，不是”物理层”单层。
  • 数据单位张冠李戴：应用层是数据、传输层是报文段、网络层是数据包、链路层是帧。

📝 现场作答

  • TCP/IP 是协议簇的代名词，含 TCP、IP、MAC、UDP、HTTP、FTP 等，是四层模型（应用层、传输层、网络层、网络接口层），可视为 OSI 七层的简化版，另有一种五层说法。
  • 应用层：整合了 OSI 的应用层、表示层、会话层，直接为应用程序服务，定义信息交换格式并把消息交给传输层；数据单位是数据。协议与端口：DNS 53（UDP/TCP，长度超 512 字节用 TCP）、DHCP 67/68（UDP）、SNMP 161/162（UDP）、FTP 20/21（控制连接 21、数据连接 20）、TELNET 23、HTTP 80、SMTP 25、POP3 110、IMAP 143。
  • 传输层：负责两个终端设备上进程之间通信，提供通用数据传输服务（通用=不针对某个特定应用）；数据单位是报文段。TCP 面向连接、可靠；UDP 无连接、尽最大努力。字段：TCP 的 Source Port / Destination Port / Sequence Number / Acknowledgment Number / Flags；UDP 的 Source Port / Destination Port / Length / Checksum。
  • 网络层：把传输层报文段或用户数据报封装成 IP 数据报，负责选路，把分组送到目的主机；数据单位是数据包。协议：IP（核心，逻辑地址寻址、无连接不可靠）、IGMP（多播组成员管理）、ICMP（传递控制消息、报告异常、ping 的基础）。字段：Source IP Address / Destination IP Address / TTL / Protocol。别混淆传输层 UDP「用户数据报」与网络层「IP 数据报」。
  • 网络接口层：数据链路层把 IP 数据报组装成帧在相邻节点间传送，物理层实现相邻节点间比特流透明传送并屏蔽介质与设备差异；数据单位是帧。要素：CSMA/CD、MAC、差错检测（奇偶校验、CRC 等）、多路访问、以太网。字段：Source MAC Address / Destination MAC Address / Type。
  • 发送路径：应用层把数据放入 Socket 发送缓冲区 → 协议栈自上而下 → 传输层加 TCP 头 → 网络层加 IP 头、路由查找、按 MTU 分片 → 链路层做物理寻址、加帧头帧尾入发包队列 → 驱动通过 DMA 从队列取帧交网卡发送。
  • 接收路径：网卡 DMA 把帧放入收包队列并以硬中断通知 → 中断处理程序分配 sk_buff 并拷贝、通过软中断通知内核 → 协议栈自下而上：链路层校验合法性、去帧头帧尾交网络层 → 网络层取 IP 头判断走向，确认发往本机则去头交传输层 → 传输层按四元组找 Socket 并拷贝到接收缓存 → 应用层用 Socket 接口读取。
  • 分层的意义：简化设计与实现、模块化独立演进、保证跨厂商互操作性、故障隔离便于定位。

💡 主动加分的追问准备

追问 答案
为什么 TCP/IP 只分四层而 OSI 分七层？ TCP/IP 是实用演进的结果，把 OSI 的会话层、表示层合并进应用层，把数据链路层与物理层合并为网络接口层，去掉了纯概念性的层次；OSI 是先有理论模型再落地协议。
TCP/IP 和 OSI 的对应关系是什么？ OSI 应用层/表示层/会话层 → TCP/IP 应用层；OSI 传输层 → TCP/IP 传输层；OSI 网络层 → TCP/IP 网络层；OSI 数据链路层 + 物理层 → TCP/IP 网络接口层。
传输层报文字段和五层模型怎么对齐？ 传输层数据单位是 Segment（报文段）；网络层是 Packet；链路层是 Frame；五层模型中还多拆出一个物理层的比特流。
一次 TCP 连接的四元组是什么？ 源 IP、源端口、目的 IP、目的端口。传输层就是靠它把报文交给唯一的 Socket。

❌ 千万别说的话

  • 不要说”TCP/IP 四层模型第四层就是物理层”——网络接口层是链路层与物理层的合体。
  • 不要把 TCP 说成”在网络层”，传输层是它的正式归属。

[31] RPC 与 OSI 七层的关系（RMI / gRPC 实战）

🎬 面试现场

面试官：OSI 七层模型怎么分的？另外你项目里的 RPC 框架（RMI/gRPC）跑在哪一层？

⚠️ 翻车点

  • 只背七层名字，答不出每层职责、数据单位和典型协议。
  • 把 RPC 说成”传输层协议”——它是应用层的通信框架，底下仍然是 TCP 在跑。
  • 只会说 gRPC 比 RMI 好，说不出两者在序列化、跨语言、流式能力上的具体差异。

📝 现场作答

  • OSI 七层自下而上：物理层 → 数据链路层 → 网络层 → 传输层 → 会话层 → 表示层 → 应用层。前四层与 TCP/IP 四层的对应见第 30 题，后三层（会话、表示、应用）被 TCP/IP 合并进应用层。
  • RPC 属于应用层。它的核心思想是让客户端像调用本地方法一样调用远程方法，把底层网络通信细节交给框架（gRPC、Apache Thrift、Dubbo）封装。
  • 一次 RPC 调用的分层落点：应用层走 RPC 协议做序列化与编解码，传输层走 TCP（gRPC 也支持 QUIC），网络层走 IP，网络接口层走 MAC 与帧。RPC 只是把”应用层怎么调远端”这件事标准化了，底下四层一步都没少。
  • Java RMI 四步：定义继承 java.rmi.Remote 的远程接口 → 实现类继承 UnicastRemoteObject → 服务端注册并绑定到 RMI 注册表（默认端口 1099，registry.rebind）→ 客户端 LocateRegistry.getRegistry + lookup 后调用。
  • 启动顺序：rmiregistry → 运行 Server → 运行 Client。注册表先起，否则客户端 lookup 会失败。
  • RMI 与 gRPC 的差异：RMI 是 JDK 原生方案，依赖 Java 序列化（JDK 17 起已被弃用）、跨语言差、只能同步阻塞；gRPC 基于 Protobuf，跨语言支持好、有强类型契约、支持四种调用模式（一元、流式、客户端流、服务端流），且基于 HTTP/2 天生擅长长连接。

💡 主动加分的追问准备

追问 答案
RPC 框架在网络模型里属于哪一层？ 应用层。RPC 让远程调用对调用方透明，但底下仍要落到应用层的 RPC 协议 + 传输层的 TCP + 网络层的 IP 来完成真正传输。
Java RMI 的调用链大概经过哪些层？ 应用层走 RMI 协议序列化与注册表查找，传输层走 TCP，网络层走 IP，网络接口层走 MAC 与帧；客户端只需通过注册表拿到远程对象代理即可像本地调用一样使用。
RMI 和 gRPC 的区别？ RMI 是 JDK 原生方案，依赖 Java 序列化，跨语言差；gRPC 基于 Protobuf，跨语言支持好、有强类型契约、流式 RPC 能力强，是现在的主流选择。
序列化方式为什么会影响框架选型？ Java 原生序列化与业务类强耦合、跨语言无法解析、体积大且有反序列化漏洞风险；Protobuf 按字段编号编码、语言无关、体积小，是 gRPC 的默认选择。

❌ 千万别说的话

  • ❌「RPC 是传输层协议」——传输层只有 TCP/UDP，RPC 属于应用层
  • ❌「RPC 绕过了 TCP/IP 四层，直接调用远端内存」——它只是隐藏细节，底层链路一步不少
  • ❌「OSI 分七层、TCP/IP 分四层，所以两者不通用」——映射关系明确，前四层一一对应，后三层被合并

五、鉴权、DNS 与 CDN

[32] Cookie、Session、Token 之间有什么区别？

🎬 面试现场

面试官：Cookie、Session、Token 三者有什么区别？各自的存储位置、安全性、生命周期？分布式和跨域场景你怎么选型？

⚠️ 翻车点

  • 把”HTTP 无状态”和”Cookie 存了状态”说成矛盾——Cookie 是无状态协议下的状态补充机制。
  • 认为 Token 一定比 Session 安全——JWT 存 localStorage 防 CSRF，但一旦泄漏即等同于凭证；Payload 明文可解码，所谓”加密”要分清是签名还是加密。
  • 忽略分布式 Session 的真实问题：粘滞会话换机器要重新 Hash 绑定、Session 复制性能随节点数指数级下降。

📝 现场作答

  • 会话定义：用户开一个浏览器、点击多个超链接访问多个 web 资源、再关闭浏览器，整个过程称为一个会话。
  • Cookie：由服务器生成、存在客户端的一小段数据，是无状态 HTTP 的补充机制。存储在客户端；容量一般限 4KB；易被篡改伪装；生命周期由过期时间控制（也可用会话 Cookie）；每次请求都携带，有额外网络开销。传输靠响应头 Set-Cookie 下发、请求头 Cookie 回传。用途：会话管理、个性化设置、跟踪与分析。
  • Session：服务器端状态管理机制，每个会话生成唯一 Session ID，数据存服务器（实践中常存 Redis），客户端只存 Session ID。容量理论上不受限、受服务器内存约束；比 Cookie 更安全，因为数据在服务端；默认浏览器关闭即结束。性能上每次请求都要查服务器，高并发时增加负载。
  • Token：用于无状态身份认证，通常用 JWT，靠签名保证安全；服务器不存 Token，只验证其有效性。自包含、跨平台、生命周期短（如 15 分钟）并配 Refresh Token 续期。适合分布式认证、跨域跨服务、移动端与 SPA、第三方授权。
  • JWT 结构：Header（typ: JWT、alg: HS256）+ Payload + Signature，用 . 分隔。注册声明有 iss 签发方、iat 签发时间、aud 接收方、exp 过期时间、nbf 生效时间、jti 唯一标识。
  • JWT 使用建议：一般放 localStorage（放 Cookie 有 CSRF 风险）；请求通过 Authorization 头携带；Payload 不放隐私信息；必须设 exp 且不宜过长。
  • 对比结论：是否需要服务器存储——Cookie ❌、Session ✔、Token ❌；是否支持分布式——Cookie ❌、Session ❌（需扩展）、Token ✔；跨域支持——Cookie 受限较多（需配 SameSite）、Session ❌、Token ✔；设计复杂度——Cookie 低、Session 中、Token 高；性能开销——Cookie 低、Session 高、Token 低。
  • 选型结论：Cookie 用于轻量级非敏感状态（用户偏好、主题）；Session 用于需要高安全性、依赖服务器存储的身份认证；Token 用于分布式、跨域、跨平台认证。
  • 分布式 Session 五个方案：① Session 绑定/粘滞——扩容会重新 Hash 绑定导致重新登录、单节点宕机则全丢；② Session 复制——无需改代码但同步占带宽、多节点同步性能指数级下降；③ 前端存储——不占服务端内存但有安全风险、受 cookie 大小限制；④ 后端集中存储——安全且易水平扩展但要改代码；⑤ SpringSession（常用）——Session 统一存 Redis。

追问 答案
HTTP 明明无状态，为什么 Cookie 能携带状态？ HTTP 每个请求独立、自身不记状态；Cookie 是 HTTP 协议簇的一部分，作为客户端侧的状态载体随请求携带，才让服务器”间接有状态”。
为什么把 JWT 放 localStorage 而不是 Cookie？ Cookie 会随请求自动发送，容易被 CSRF 利用；localStorage 不会被自动携带，配合 Authorization 头由前端显式附加，可规避 CSRF。
JWT 是加密的吗？ 准确说是签名：Header 与 Payload 是 Base64 编码可被任何人解码查看，安全性来自 Signature 的密钥校验，能防篡改但不能防偷看，因此 Payload 不能放隐私信息。
Session 和 Token 能并存吗？ 可以。常见做法是 Access Token 用 JWT 做无状态校验，同时把 Refresh Token 或会话数据落 Redis，两者结合兼顾性能与可撤销性。
秒杀场景下负载均衡到不同 Tomcat 为什么会重复购买？ 第一次请求到 TomcatA 记录 Session，第二次到 TomcatB，TomcatB 认为该用户是首次访问从而放行，造成重复购买；本质是 Session 不共享，需粘滞、复制或集中存储解决。
Cookie 的安全属性有哪些要配？ HttpOnly 防止 JS 读取降低 XSS 窃取风险，Secure 只走 HTTPS，SameSite 限制跨站携带缓解 CSRF。

❌ 千万别说的话

  • 不要说”JWT 是加密的、内容看不到”——Payload 是 Base64 明文，签名只保证不被篡改。
  • 不要说”Token 一定比 Session 安全”——Token 泄漏即等同凭证，Session 可即时服务端失效，安全性取决于整体设计。
  • 不要把 Cookie、Session、Token 说成互斥的三选一，实际可以叠加使用。

[33] JWT Token 能说说吗？

🎬 面试现场

面试官：我们系统用的是 JWT，你跟我讲讲它到底是怎么工作的，为什么大家现在都喜欢用它？

⚠️ 翻车点

  • 以为 JWT 的 Payload 是加密的，直接把手机号、身份证塞进去
  • 说”JWT 无状态所以不能撤销”，其实这是有解的，只是要付出有状态的代价

📝 现场作答

  • JWT 全称 JSON Web Token，是一种身份认证令牌格式，结构是 xxxxx.yyyyy.zzzzz 三段用点号连接：Header（元数据 + 签名算法）、Payload（声明信息）、Signature（Header+Payload 的签名，防篡改）。
  • 流程：登录成功后服务端签发 JWT → 客户端保存 → 每次请求放进 Authorization 头 → 服务端验签，通过就信任 Payload 里的用户信息。
  • 核心优势是自包含 + 无状态：服务端不存 Token，任意节点都能验签，天然适合分布式和微服务，不用解决 Session 共享问题。
  • 标准声明字段要能背：iss（签发者）、sub（主题，一般放用户 ID）、aud（接收方）、exp（过期时间，Unix 时间戳）、nbf（生效时间）、iat（签发时间）、jti（唯一标识）。
  • 签名算法分两类：对称的 HMAC 系列（HS256/384/512，同一密钥签名验签，适合单体或内部服务）；非对称的 RSA/ECDSA 系列（RS256/ES256，私钥签公钥验，适合需要第三方验签的场景）。
  • Payload 只是 Base64 编码、不是加密，敏感信息不能放；需要加密用 JWE 标准（五部分：Header、Encrypted Key、IV、Ciphertext、Authentication Tag），但复杂度和性能都差很多。
  • 安全四要点：密钥要足够长（HS256 至少 32 字节）并定期轮换、防 XSS 窃取（Token 放 localStorage 有风险，改 HttpOnly Cookie 但要处理 CSRF）、过期时间合理（Access 15 分钟几小时，Refresh 730 天）。

💡 主动加分的追问准备

追问 答案
JWT 未过期但要强制下线怎么办？ 三种方案：① Redis 黑名单存 jti，验签后再查，违背无状态且规模大了有性能问题；② 用户版本号，写进 Payload，验签比对，改密码/登出时递增，一刀切掉所有设备；③ 短 Access + 长 Refresh，Refresh Token 存服务端可主动撤销。
Payload 能加密吗？怎么加？ 用 JWE：五部分结构，先用接收方公钥加密一个对称密钥，再用该对称密钥加密 Payload。只有持私钥的接收方能解密，但比 JWS 重得多，一般场景用签名就够。
alg: none 有什么安全问题？ 经典漏洞：把正常 Token 的 alg 改成 none 并删掉签名，若服务端盲信 Token 声明的算法，篡改后的 Payload 直接验签通过。服务端必须强制指定算法，忽略 Token 里的 alg 字段。
多设备登录怎么只踢掉某一台设备？ 每个 Token 带唯一 jti，服务端维护 Token 列表，要踢就把该 jti 加黑名单；或每个设备一个存服务端的 Refresh Token，删掉它，该设备的 Access 过期后续不了期。
为什么 JWT 不适合存 Session 数据？ JWT 签发后不可变，Session 数据（如购物车）频繁变动，每次变动都要重新签发，开销大且客户端要配合更新；加上 JWT 体积比 Session ID 大，频繁变动数据放进去浪费带宽。动态数据走服务端存储。

❌ 千万别说的话

  • ❌「JWT 是加密的，里面的内容别人看不到」——Payload 是 Base64 编码，任何人都能解开看
  • ❌「JWT 无状态，所以没法注销、没法失效」——黑名单 / 版本号 / Refresh Token 都能解决，只是牺牲一部分无状态性

[34] 简单谈谈你对 DNS 的理解？

🎬 面试现场

面试官：你给我讲讲浏览器输入一个域名之后，DNS 是怎么把域名变成 IP 的？

⚠️ 翻车点

  • 把「递归查询」和「迭代查询」的对象说反——是本地 DNS 递归地替客户端问，根/TLD/权威只指路
  • 认为一个域名可以同时配 A 记录和 CNAME 记录

📝 现场作答

  • DNS（Domain Name System）的核心作用就是把域名翻译成 IP 地址；人脑记不住 IP 但记得住 www.baidu.com，翻译完成后浏览器才能发起真正的网络请求。
  • DNS 不只是翻译工具，还具备负载均衡能力：一个域名可配多个 IP，返回时轮询或按策略选择，把流量分散到不同服务器。
  • 域名分级结构从右往左依次降低：根域（不写出来）→ 顶级域 TLD（.com、.cn、.org）→ 二级域（baidu）→ 子域（www）。这个结构直接决定了「先问根、再问 TLD、最后问权威」的一级级往下找的方式。
  • 完整解析流程：浏览器缓存 → 操作系统 hosts 文件和 DNS 缓存 → 本地 DNS 服务器（运营商 DNS 或 8.8.8.8、114.114.114.114）→ 根 DNS 拿到 TLD 服务器地址 → TLD DNS 拿到权威服务器地址 → 权威 DNS 返回完整记录 → 本地 DNS 缓存结果并返回浏览器，浏览器也缓存一份。绝大多数请求在前几步就命中缓存了。
  • 查询模式：客户端到本地 DNS 用递归（问一次，对方问到答案才回你）；本地 DNS 到根/TLD/权威用迭代（对方说「我不知道，你去问这个地址」）。这么设计是因为让客户端自己迭代太麻烦，让根服务器做递归又扛不住全球请求量。
  • 常见记录类型：A（IPv4）、AAAA（IPv6）、CNAME（别名，常用于指向 CDN 调度域名）、MX（邮件服务器）、NS（权威服务器）、TXT（域名所有权验证、SPF 反垃圾）。
  • 每条记录都有 TTL 控制缓存寿命：TTL 短则变更生效快但查询量大，TTL 长则减少查询但生效慢；故障切换场景必须把 TTL 设得很短，否则流量会一直打到故障机器上。静态站点可设 1 天，经常换 IP 的服务设几分钟。
  • 安全风险三类：DNS 劫持（篡改响应导到别处，早年间运营商跳转广告页）、DNS 污染（故意返回错误 IP）、隐私泄露（明文传输，中间人知道你访问了哪些站点）。解法是 DNS over HTTPS 和 DNS over TLS，配合 1.1.1.1、8.8.8.8 这类支持 DoH 的服务器。

追问 答案
为什么 DNS 用 UDP 而不是 TCP？ DNS 查询和响应都很短，一个 UDP 包就够，没必要付三次握手的开销；DNS 对实时性敏感，UDP 更快。但不是完全不用 TCP——响应超过 512 字节时切到 TCP，区域传送（zone transfer）也用 TCP。UDP 的不可靠问题可以在应用层用超时重传来补。
hosts 文件和 DNS 是什么关系？ hosts 优先级高于 DNS。操作系统发起 DNS 查询前先查 hosts，命中就直接用、完全不问 DNS。开发时改 hosts 把域名指向 127.0.0.1 做本地调试就是这个原理。
DNS 查询慢怎么优化？ 四招：① 换靠谱的 DNS 服务器（运营商 DNS 不行就用公共 DNS）；② 用 dns-prefetch 预解析可能访问的域名；③ 接入 HTTPDNS 绕过本地 DNS，规避运营商劫持和解析慢；④ 适当延长 TTL 减少查询次数。
一个域名能同时有 A 记录和 CNAME 记录吗？ 不能，同一域名 A 与 CNAME 互斥。CNAME 表示「这个名字是另一个名字的别名」，同时存在其他记录会产生解析歧义。但子域名可以：主域名用 A 记录，www 子域用 CNAME 指向 CDN。

❌ 千万别说的话

  • ❌「DNS 服务器是递归帮我把每一级都问一遍根服务器」——根/TLD/权威只做指路（迭代），递归由本地 DNS 承担
  • ❌「DNS 就是个查 IP 的翻译工具」——它还承担负载均衡分发流量的职责

[35] 简单谈谈你对 CDN 的理解？

🎬 面试现场

面试官：CDN 到底是解决了什么问题？它的原理你讲得清楚吗？

⚠️ 翻车点

  • 只说「CDN 就是缓存」，讲不出回源机制、GSLB 调度和缓存策略的选型
  • 把 CDN 说成单纯的静态资源加速，忽略它还能做动态加速、WAF、DDoS 防护

📝 现场作答

  • CDN 像互联网的「快递网络」：把静态资源、视频、图片等缓存到全球各边缘节点，让用户从最近的服务器取内容。传统模式是「用户 → 源站（可能很远）」，CDN 是「用户 → 就近边缘节点 → 缓存命中直接返回」，未命中才回源站取，取完缓存再返回。
  • 完整流程：用户请求域名 → 智能 DNS（GSLB）解析到最近的 CDN 节点 → 边缘节点检查本地缓存 → 命中直接返回；未命中则回源站获取、缓存后返回用户。
  • 全局负载均衡（GSLB）综合地理位置、网络延迟、节点负载、运营商线路等维度选出最优节点。
  • 三类缓存策略：强缓存（固定时间不过期，适合图片/CSS/JS）、协商缓存（用 ETag/Last-Modified 验证是否变化，适合频繁更新的资源）、动态缓存（短时间缓存，适合 API 响应）。
  • 三类回源策略：按需回源（未命中才回）、预热回源（主动把热点内容推送到节点）、分层回源（边缘节点 → 区域节点 → 源站）。
  • 缓存刷新三件套：主动刷新（手动清指定 URL）、预热（主动推送）、URL 版本号强制更新（style.v1.css、app.a1b2c3d4.js）。
  • 指标要背：命中率 > 90%、回源率 < 10%、TTFB < 100ms、下载速度 > 5MB/s；节点可用性 > 99.9%、服务可用性 > 99.99%、故障恢复 < 5 分钟。
  • 核心优势：性能（就近访问降延迟、多节点并行提吞吐、智能路由）、成本（CDN 承担大部分带宽、源站减压、按需付费）、高可用（分布式架构单点故障不影响整体、节点故障自动切换、流量清洗抗 DDoS）、安全（WAF 防护、DDoS 防护、HTTPS 的 SSL/TLS 卸载加速）。
  • 生态结合：CDN + 智能 DNS（选最优节点）、CDN + 负载均衡（节点后端再挂源站集群）、CDN + WAF（请求先过 CDN 节点检测）、CDN + 边缘计算（节点上跑函数，如 Cloudflare Workers、阿里云边缘函数）。

追问 答案
缓存规则怎么配？ 按文件类型区分：jpg/png/gif/ico 配 expires 30d；css/js 配 expires 7d；html 配 expires 1h。动态资源用短时间或不缓存，用户私有数据（个人数据）明确设置不缓存。
除了静态资源，CDN 还能干什么？ 动态内容加速（路由优化、HTTP/2 与 HTTP/3 协议优化、连接复用、智能压缩）；直播点播（HLS/DASH 分片、自适应码率、实时转码）；API 加速（响应缓存、请求合并、智能路由、限流熔断）。
怎么解决跨域？ 在 CDN 节点上配置响应头 Access-Control-Allow-Origin 和 Access-Control-Allow-Methods，配 OPTIONS 预检的放行规则。
哪些资源适合上 CDN？ 静态资源（HTML/CSS/JS、图片、字体、图标、音视频）长时间缓存；动态资源（HTML、API）短时间或不缓存；用户私有数据不缓存。配合版本号/哈希值做更新，启用 Gzip/Brotli，图片用 WebP/AVIF。

  • ❌「CDN 就是把网站都镜像一份到各个节点」——准确说法是按需缓存 + GSLB 调度，不是全量镜像
  • ❌「CDN 只能加速静态资源」——动态加速、边缘计算、WAF 防护都在 CDN 节点上做

[36] 从网络角度来看，用户从输入网址到网页显示，期间发生了什么？

🎬 面试现场

面试官：你在浏览器地址栏敲下域名、按回车，到页面渲染出来，中间到底发生了什么？你按协议顺序给我捋一遍。

⚠️ 翻车点

  • 把顺序背成「ARP → TCP → IP → DNS」，实际是 URL 解析 → DNS → TCP → TLS → HTTP，ARP 属于建链时的链路层环节
  • 把端口号说反（源端口是客户端随机生成，目标端口才是 80/443）
  • 把协议栈顺序倒过来说（IP → TCP → HTTP）

📝 现场作答

  • 核心一句话概括：HTTP/HTTPS → DNS → TCP → IP → ARP，每个协议各司其职。
  • 第一步 URL 解析：浏览器从地址里拆出协议、域名、端口、资源路径，构造 HTTP 请求报文。
  • 第二步 DNS 解析域名：先查浏览器缓存 → 再查操作系统缓存和 hosts 文件 → 都没有才问本地 DNS 服务器；本地 DNS 也没有缓存时，走根 DNS → 顶级域 DNS → 权威 DNS 三级迭代查询，权威返回 IP，本地 DNS 缓存后回给浏览器，浏览器再缓存一份。
  • 第三步 TCP 三次握手：客户端发第一个 SYN 时，TCP 头部填 SYN 标记位，并带上源端口和目标端口。源端口由浏览器随机生成，目标端口看协议：HTTP 默认 80，HTTPS 默认 443。
  • 第四步逐层封装：网络层加 IP 头，填源 IP 和目标 IP；数据链路层通过 ARP 协议获取路由器的 MAC 地址，加上 MAC 头填源/目标 MAC；物理层把帧转发给路由器，路由器按下一跳逐级转发直到目标服务器。
  • 第五步服务端回 SYN-ACK，客户端再回 ACK，三次握手完成。若是 HTTP，客户端直接发 HTTP 请求；若是 HTTPS，还要先完成 TLS 四次握手，之后才发送 HTTP 报文。
  • 第六步服务端返回 HTTP 响应，浏览器解析渲染呈现给用户。
  • 延伸：HTTP 跳 HTTPS 由服务端配置重定向实现，nginx 里在 80 端口的 server 块 return 301 https://$host$request_uri;，浏览器收到 301 后自动发起新的 HTTPS 请求（默认 443）。

💡 主动加分的追问准备

追问 答案
DNS 属于哪一层？完整流程是什么？ 应用层协议。浏览器缓存 → OS 缓存和 hosts → 本地 DNS → 根 DNS 返回 TLD 服务器地址 → TLD 返回权威服务器地址 → 权威返回目标 IP → 本地 DNS 缓存并回给客户端。
服务端怎么知道数据该交给哪个应用？ 靠传输层端口号。每个协议（TCP/UDP）用端口号标识不同应用或服务，服务端监听特定端口接收数据。所以三次握手阶段双方就需要在 SYN 里协商好目标端口。
服务器 ping 不通但 HTTP 能请求成功，为什么？ 会。ping 用的是网络层 ICMP，HTTP 用传输层 TCP。服务器防火墙只禁止了 ICMP 而没禁 TCP，就会出现 ping 不通但 HTTP 正常。
连一个不存在的 IP 会怎样？ 分情况：局域网内不存在的 IP，内核广播 ARP 无人应答，SYN 根本发不出去，卡在 ARP；非局域网的不存在 IP，路由器转发后 SYN 在网络中消亡，收不到确认，触发超时重传 SYN，直到重传次数用尽后连接被释放。
连一个 IP 存在但端口不存在的服务呢？ 服务端没监听该端口，收到 SYN 后回 RST 报文，客户端收到 RST 直接断开连接。UDP 则没有 RST，会在网络层由 ICMP 协议回报「端口不可达」。
页面一直转圈不出图，怎么排查？ 抓包逐层排除：① 客户端能否访问其他站点，判断本机网络；② 能访问则看 DNS 有没有解析出 IP；③ 解析出了就看有没有完成三次握手，没有就去服务端用 ps 确认进程启动、netstat 确认端口监听；④ 发了 HTTP 请求就看响应码——404 查 URL，500 查服务端日志，200 就在浏览器 F12 控制台看前端渲染问题。
内核是怎么收到网络包的？ 网卡以 DMA 方式把帧直接写入内存并向 CPU 触发硬中断；中断处理函数只做最少工作并发出软中断请求（NET_RX_SOFTIRQ）后尽快释放 CPU；ksoftirqd 内核线程（每 CPU 一个，数量等于核数）通过 poll 轮询收包，交给协议栈逐层处理，TCP 包最终进入用户 socket 的接收队列。网卡驱动在 driver/net/ethernet/intel，协议栈代码在 net 目录。

❌ 千万别说的话

  • ❌「先 ARP 拿到 MAC 地址再解析域名」——ARP 是拿到 IP 之后、建链时才在链路层用到
  • ❌「HTTPS 就是 HTTP 加个加密」——中间多了独立的 TLS 握手（标准流程为四次通信），握手完成后才发 HTTP 报文

[37] 常见的登录鉴权方式有哪些？各自的优缺点是？

🎬 面试现场

面试官：登录鉴权这块你们是怎么做的？现在主流有哪几种方案，各自适合什么场景？

⚠️ 翻车点

  • 把 Cookie、Session、Token 当成同一层面的东西比较
  • 说 Token 认证「安全性高、无懈可击」，不说它签发后难以撤销的短板

📝 现场作答

  • 鉴权的本质是「证明你是你」，主流四种方案：Session-Cookie、Token、OAuth2.0、API Key。
  • Session-Cookie：登录后服务端创建 Session（内存或 Redis），把 Session ID 塞进 Cookie 返回；后续请求浏览器自动带 Cookie，服务端查 Session 得到用户。优点是状态在服务端、对单体应用友好；缺点是分布式场景麻烦——请求打到不同机器就认不出，得靠 Session 共享或粘性会话，架构复杂度上升。
  • Token：登录后服务端签发 Token，客户端每次在 Header 里带上，服务端验签+验有效期后放行。最常见的是 JWT，Token 自带用户信息和服务端签名，服务端不存状态、天然适合分布式。缺点是签出去就收不回来，想提前失效必须维护黑名单，或用「短有效期 + Refresh Token」。
  • OAuth2.0：本质是授权协议，解决「让第三方应用访问我在其他平台的资源」。例如微信登录某 App，App 拿不到你的密码，只需微信授权的令牌去换头像昵称。优点是用户体验好、不用到处注册；缺点是依赖第三方平台，对方接口挂了你就登不了。适合 C 端产品的第三方登录，不适合内部系统。
  • API Key：给每个调用方分配唯一 Key，请求时带上，服务端校验 Key 合法性与接口权限。实现最简单，适合内部微服务调用和开放平台的轻量鉴权；但泄露即失效、无法做细粒度权限控制，一般要配合 IP 白名单和签名验签。
  • Cookie / Session / Token 三者不在同一层：Cookie 是浏览器存储机制，Session 是服务端会话管理，Token 是认证凭证。Session-Cookie 模式下 Session 是状态、Cookie 只是运输 Session ID 的载体；Token 模式下 Token 本身就是凭证，放 Cookie 或 Header 都行、服务端不存状态。关键区别在于状态存在哪。
  • 分布式 Session 的三种解法：① Session 复制（机器间同步，Tomcat 支持但性能差）；② 粘性会话（Nginx 按用户固定打到同一台机器，机器挂了 Session 就丢）；③ Session 外置（存 Redis 集中共享，主流方案，Spring Session 就是干这个的）。
  • OAuth2.0 授权码模式六步：客户端重定向到授权服务器（带 client_id、redirect_uri、scope）→ 用户登录并同意授权 → 授权服务器回调 redirect_uri 带上 code → 客户端用 code + client_secret 换 token → 返回 access_token 和 refresh_token → 客户端用 access_token 访问资源服务器。先换码再换 Token 的原因：授权码走浏览器重定向、暴露在 URL 里，而 access_token 由后端请求获取、不经过浏览器，client_secret 也不暴露。
  • 延展两个高频考点：SSO 用统一认证中心，所有系统跳过去登录一次，企业内 CAS 用得多、互联网产品 OAuth2.0 用得多；MFA 要求两类以上认证因素——「你知道的」（密码、PIN）、「你拥有的」（手机验证码、硬件令牌、Authenticator App）、「你本身的」（指纹、人脸、虹膜）。

💡 主动加分的追问准备

追问 答案
Session 分布式怎么解决？ 三选一：Session 复制（性能差）、粘性会话（Nginx 固定转发，机器挂了会丢）、Session 外置到 Redis（主流，Spring Session 就是这个思路）。
access_token 和 refresh_token 有什么区别？ access_token 有效期短（一般几小时），用于实际请求资源；refresh_token 有效期长（几天甚至几个月），只在 access_token 过期时换新的。这么设计是因为 access_token 频繁在网络上传输容易泄露，短有效期降低风险，而 refresh_token 传输次数少。
API Key 泄露了怎么办？怎么防？ 应急是立刻轮换、作废旧 Key。预防四招：① Key 只在后端用，绝不出现在前端代码里；② 配 IP 白名单，只认特定来源；③ 用签名验签——请求参数 + 时间戳 + Key 一起签名，Key 本身不传输，服务端用同样方式签名比对；④ 定期轮换 Key，降低长期泄露风险。
Token 认证怎么做细粒度权限？ access_token 本身短时效 + 服务端校验权限；配合 refresh_token 和短有效期设计——access_token 泄露影响窗口有限，refresh_token 只用于续期。

❌ 千万别说的话

  • ❌「Session 和 Token 就是两种不同的存储方式」——它们不在同一层，核心区别是状态存在服务端还是客户端
  • ❌「OAuth2.0 就是第三方登录」——它本质是授权协议，第三方登录只是它最常见的应用场景

必须张口就来的定义

  • 发送窗口 = **min(cwnd, rwnd)**，cwnd 是拥塞控制算的，rwnd 是接收方通告的
  • TCP 可靠性四件套：编号、确认、重传、窗口
  • 三次握手的首要目的是防止历史连接建立，不是确认收发能力
  • ISN = 时间递增（每 4 微秒 +1）+ 随机，只说随机就答不完整
  • DNS：客户端到本地 DNS 用递归，本地 DNS 到根/TLD/权威用迭代
  • JWT 的 Payload 是 Base64 编码，签名只防篡改不防偷看

最该记住的易错点

  1. HTTP/2 的多路复用解决的是 HTTP 层队头阻塞，TCP 层的还在
  2. HTTPS = TCP 三次握手 + TLS 四次通信，别混成三次
  3. TIME_WAIT 属于主动关闭方，客户端和服务端都可能出现，不是客户端特有
  4. 快速重传是数据驱动（3 个重复 ACK），超时重传是时间驱动（RTO）
  5. tcp_fin_timeout 管的是 FIN_WAIT_2，不是 TIME_WAIT
  6. ARP 只在同一广播域工作，跨网段每跳 MAC 都变、IP 不变
  7. JWT 放 localStorage 是为了规避 CSRF，代价是 XSS 可窃取
