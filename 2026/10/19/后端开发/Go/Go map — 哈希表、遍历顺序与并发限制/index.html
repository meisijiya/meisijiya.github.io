09 Go map

map 是 Go 最常用的容器，但引用语义、随机遍历顺序、「并发写直接崩进程」这三条，是从 Java/Python 迁过来最容易踩的坑。

9.2 map 是引用类型

map 的值在运行时就是指向哈希表的指针，赋值复制的是指针不是表：

Java 的 HashMap b = a;、Python 的 b = a 语义完全一致。

维度 Go map[K]V Java HashMap<K,V> Python dict
空值状态 var m map[K]V → nil，只能读 null 引用 → NPE None → AttributeError
读取不存在 返回类型零值 返回 null d[k] 抛 KeyError

两个 map 能否 == ❌ 编译错误 ✅ 比引用 ✅ 比内容

Python 3.7+ 的 dict 语言规范保证插入序，Java 的 HashMap 从来不保证，Go 的 map 是故意不给顺序，三者不能互相套用直觉。Python 的 d.get(k) 返回 None，用 if not d.get(k): 判断会把「值为 None」和「key 不存在」混为一谈；Go 的 ok 给了明确出口。

struct 里装 map：混合语义

struct 是值类型，但里面的 map 字段仍然共享：把 c1 复制成 c2 后改 c2.Items，c1.Items 一样会变。「struct 复制了 = 数据隔离」只对值类型字段成立。

9.3 遍历顺序为什么是随机的

这不是 bug，是刻意设计。 语言规范写着：map 的迭代顺序未指定，不保证两次迭代相同。

老版本实现里同桶的键按插入顺序追加，程序一旦依赖上这个顺序，底层换实现后就会静默出错。Go 的选择是每次 range 随机选一个起始桶和桶内偏移，让依赖顺序的隐式假设立刻暴露成可见的 bug。

9.4 delete 与 len

delete 没有返回值，key 不存在时连 panic 都不会有。Java 的 remove(k) 返回旧值或 null，Python 的 del d[k] 抛 KeyError——Go 的 delete 等价于 d.pop(k, None)。对 nil map 的 delete 也是 no-op，len(nilMap) 返回 0。

一个自坑：v := m["bob"] 之后 delete(m, "bob")，v 仍是 85——**v 是拷贝**。

9.5 map 不可比较

map 属于不可比较类型，影响是链式的：

两个 map 之间不能用 ==（唯一允许的是 m == nil）；map 不能做另一个 map 的键，也不能放进数组；含 map 字段的 struct 也不可比较——e1 == e2 会报 struct containing map[string]string is not comparable。需要支持相等比较的 struct，别在它里面放 map。

interface 类型本身可比较，但比较时会看动态类型：

因为 interface 相等的前提是「动态类型相同 且 动态类型可比较」，而 map[string]int 不可比较。Go 只能自己遍历比对，或者用 reflect.DeepEqual（走反射、慢，只适合测试调试）。

9.6 传参副作用

Go 的参数传递永远是按值传递，但 map 的「值」本身是指针，副本仍指向同一张表。Go 特有的地方在于它和「Go 一律按值传递」并存——很多人因此以为传 map 是值传递，实测就翻车。

对照其他类型：传 []T 改元素调用方能看到，但 append 扩容时看不到；传 struct 改字段看不到（值拷贝）；传 *struct 才能改到原数据。

要隔离，两种做法：返回新 map（不碰入参），或者用 struct 封装 + 指针接收者——指针接收者能改到原数据，值接收者只能改副本。

9.7 并发限制：写 map 直接崩进程

然后整个进程退出。 三条性质必须记住：

  1. 这是 fatal error，不是 panic。运行时 throw 出来，recover() 拦不住。
  2. 不只写会崩：遍历时写是 concurrent map iteration and map write，读写同时发生是 concurrent map read and map write。
  3. 不需要 -race 就触发。go run -race 只是更早报出「数据竞争」，是诊断工具。

为什么这么狠：map 的桶数组、元素计数、溢出桶链表都没有一致性保护，并发写可能把链表接成环（遍历死循环）、可能写坏计数导致越界，这种损坏是静默的内存错误。Go 的取舍是宁可现在崩。Java 的 HashMap 同样非线程安全，但失败模式是抛 ConcurrentModificationException——一个能 catch 的普通异常。

三条解决路线

路线一：sync.RWMutex + 普通 map（默认选它）

锁必须和 map 放在同一个 struct 里并配指针接收者，别忘了先 make 初始化 users。锁写成独立全局变量、或 UserStore 按值传递，锁就失效了。

路线二：sync.Map（场景很窄，不是万能替代）

sync.Map 只为两种场景优化：某个 key 的值只写一次、之后被反复读（只增不减的缓存）；多个 goroutine 操作互不相交的 key 集合。这时它能显著降低锁竞争。代价是 key 和 value 都是 any，类型安全没了，取出要做类型断言（失败会 panic）；它还是 struct，首次使用后不能再拷贝。用之前先问：我的场景真落在这两条里吗？

路线三：自己分片（sharding）

把一张大 map 拆成 N 个小 map，每片一把锁，按 key 的哈希值决定落到哪片（示意：shards [16]struct{ sync.RWMutex; counts map[string]int }，写入时用 hash(key)%16 选片）。它能把写并发极高、冲突率低场景下的锁竞争摊薄；代价是跨分片操作（比如统计总数）变麻烦，标准库不提供分片 map。

怎么选

方案 适用场景 类型安全 主要坑
sync.RWMutex + 普通 map 绝大多数业务场景 ✅ 保留 锁要和 map 同生命周期
sync.Map key 只写一次后只读；操作不相交 key ❌ 变 any 不是通用替代
自己分片 写并发极高、冲突率低 ✅ 保留 跨分片操作麻烦

日常业务九成场景用第一种就够。**sync.Map 是优化手段，不是替代品。**

9.8 nil map：能读，不能写

读 OK、len OK、delete OK，写 panic。 而且这个 panic 是普通的 runtime panic，能被 recover 兜住，跟 9.7 那种进程级崩溃不是一个量级。

nil map 不是 bug，它代表「一个只读的空集合」，在函数签名里很有用：func total(scores map[string]int) int 可以接收 nil 入参并返回 0。如果 Go 像 Java 那样 nil 直接 NPE，所有「可能没数据」的入参都得先判空。

最常见的两个踩坑点：struct 的零值字段（cfg := Config{} 之后 cfg.Labels["env"] = "prod" 直接 panic）和函数返回未初始化的 map。修法一样：**该写的时候先 make**，允许调用方继续写入的函数必须返回初始化过的空 map。

9.9 动手练

  1. 基础读写：写 scoreOf(scores map[string]int, name string) (int, bool)，分别传入存在的 key、不存在的 key、nil map，观察 ok 的取值。
  2. 验证引用语义：b := a 后写 b["y"] = 2 并打印 a；再把 b 重新赋值为新 map 再打印一次 a，注释说明两次输出为何不同。
  3. 遍历顺序：写一个按 key 升序打印 map 的函数，去掉排序跑 3 次看输出是否变化，再加回排序验证 3 次一致。
  4. 复现并发写崩溃：先用 9.7 的双 goroutine 代码跑一次（它会直接终结进程），再改用 sync.RWMutex 封装成 SafeMap，加上 go run -race 确认没有 race 报告。

9.10 常见错误清单

错误 现象 正确做法
往 nil map 写入 panic: assignment to entry in nil map 先 make；struct 字段用构造函数初始化
并发写 map fatal error: concurrent map writes，recover 救不了 加锁 / sync.Map / 分片，加 go test -race 验证
interface 里装 map 再比较 运行时 panic: comparing uncomparable type 取出具体类型再比较，别用 any 装 map
锁没和 map 放一起 加了锁但仍有竞态 锁和 map 放同一个 struct，方法用指针接收者
到处用 sync.Map 失去类型安全，断言会 panic 优先普通 map + 锁；只用于「只写一次」或「不相交 key」
