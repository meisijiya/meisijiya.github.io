08 Go 切片

切片是 Go 里用得最多、也最容易用错的类型：这一次把它的底层数组、扩容代价和别名陷阱彻底讲透。

8.1 数组 vs 切片：一个是值，一个是「视图」

数组 [N]T 是定长、值类型。 长度写在类型里，[5]int 和 [10]int 是两个互不相同的类型。数组赋值就是逐元素复制，传参也是复制：

切片 []T 是一个「视图」：本身只是个小描述符（切片头），指向某个底层数组的某个位置，加上自己的长度和容量。复制切片复制的是描述符，指向的数据还是同一份。

两个容易忽略的推论：Java 的 int[] 对应的是 Go 的切片，不是 Go 的数组（Java 数组是引用类型，Go 数组是值类型、长度写死在类型里）；Python 的切片会复制，Go 的切片不会——lst[1:3] 造出全新 list，s[1:3] 只是换个起点看同一块内存。

8.2 切片三要素：ptr、len、cap

一个切片值由三部分组成：ptr 指向底层数组中第一个元素（切片起点）；len 是长度，决定 s[0] 到 s[len-1] 能访问多少个元素；cap 是容量，表示从切片起点到底层数组末尾最多能放下多少个元素。

字面量的 len 和 cap 相等。需要预留空间时用 make：make([]int, 0, 100) 得到 len=0、cap=100，这是「先占坑再填」的典型写法。容量决定了 append 何时需要重新分配底层数组。

8.3 切片表达式：越界与「三索引切片」

切片表达式的形式是 s[low:high]，左闭右开，结果是共享同一块底层数组的新描述符。s[1:] 表示「从下标 1 到末尾」，s[:3] 表示「从头到下标 2」，s[:] 表示全部。

越界会 panic，而且上界看的是 cap 不是 len

和 Python 的两处差异：Go 不支持负数下标（s[-1:] 编译不过），Go 的切片没有步长（s[::2] 不存在）。

还有一个更隐蔽的规则：**对切片做 s[low:high] 时，high 的上界是 cap(s) 而不是 len(s)**：

这意味着你能看到并写入 len 之外的槽位（初始是零值）。如果 a 是数组而不是切片，同样的写法是编译错误——数组长度是类型的一部分，编译器判得出来。

三索引切片 s[low:high:max]

第三个索引把新切片的 cap 钉死为 max - low。最大的用途是：防止 append 悄悄写坏共享同一数组的邻居。

Go 1.21 之后写法更清楚：slices.Clip(buf[:4]) 等价于 buf[:4:4]。打算 append 又担心和别的切片共享底层数组时，就用三索引切片把 cap 钉死。

8.4 append 的扩容机制

append 的签名是 func append(s []T, elems ...T) []T，行为分两种情况：

  • 容量够（len(s) + 追加数量 <= cap(s)）：直接在底层数组末尾写入，新切片只是 len 加一，cap 不变，和原切片共享数据。
  • 容量不够：分配一块新的底层数组，把原来的 len 个元素拷进去再追加，返回指向新数组的切片。原切片仍指向旧数组，两者互不影响。

扩容倍数是实现细节，不是语言契约

常见的说法是「append 会翻倍」，这个说法只在一定范围内成立：容量 小于 256 时新容量大致是原来的 2 倍；达到 256 及以上 时增长率降到 1.25 倍左右（实现里还带一个固定偏移，小容量阶段看起来会略高）；最终的新容量还会向上取整到内存分配器的尺寸类（size class）。

这些数字属于运行时实现细节，Go 升级版本就可能变。业务代码不要依赖具体倍数，唯一可靠的假设只有一条：**append 之后必须使用它的返回值**。

扩容带来的「不共享」错觉

把 make([]int, 3, 10) 换成 make([]int, 3)，结果就变成 a 保持 [0 0 0]——因为扩容了，新旧彻底分离。这类「有时共享有时不共享」的行为是 Go 里最难排查的 bug 温床之一。

8.5 别名陷阱：两个切片，一块内存

共享是特性，不是 bug

Java 里 int[] b = a; 是引用共享，Go 切片只是更精确的描述。真正的问题在于 Go 的切片还能被重新切、重新分配，「共享」会在你意料之外的时间点被打破。

copy 的语义

copy(dst, src) 把 src 的元素拷进 dst，实际拷贝个数是 min(len(dst), len(src))，返回值就是拷贝了多少个。**源和目标重叠时行为类似 memmove**，不会把数据搅乱。

for 循环里 append 的经典错误

range 表达式只在进入循环时求值一次，所以循环次数是最初的 len(s) == 3，不会死循环；但循环体里的 s 已经是扩容后的新切片了，结果往往是「看起来对但完全不是想要的」。

8.6 nil 切片 vs 空切片

这两种「长度都是 0」的切片，在 Go 里是两种不同的值：

写法 s == nil len(s) cap(s) JSON 序列化 Java 对照
var s []int true 0 0 null null
s := []int{} false 0 0 [] new ArrayList<>()
make([]int, 0, 8) false 0 8 [] new ArrayList<>(8)

实践建议：对外输出 JSON 的结构体，字段用 []T{} 而不是零值 nil，否则客户端收到 null 而不是 []，Java 端反序列化时更容易出问题。接收方要记得：nil 切片可以 append、可以 range、可以安全读下标；另外 Go 里 if s {} 是语法错误，只能写 s != nil 或 len(s) > 0。

8.7 二维切片的坑：行是切片

[][]int 看上去像 Java 的 int[][]，但每一行本身就是一个切片（有自己的 ptr / len / cap），所以多出一堆 Java 那边不存在的坑。

坑一：只分配外层，行还是 nil

make([][]int, 3) 只创建了 3 个空的行描述符，每行指向的还是 nil。必须逐行初始化：

对比 Python：[[0] * 3] * 3 会让三行指向同一个列表对象，改一行三行全变——这是 Python 新手第一大坑。Go 的 make 每次都给你新内存，但它换了个坑给你，就是上面这个。

坑二：行与行之间共享底层数组

只要两行的区间有重叠，写任何一行都会影响另一行。多行共享底层数组时，请用三索引切片把每行的 cap 钉死，把「共享」限制在你明确想要的范围内。

顺带提醒：返回 [][]int 之前，务必确认每一行都已经 make 过——只 make 外层就返回，调用方拿到的还是一堆 nil 行。

8.8 动手练

  1. 扩容观察器：每轮 append 一个元素，打印 len、cap 和底层数组首地址（&s[0]），把前 300 次的结果贴进表格，找出 cap 翻倍的确切位置。
  2. 别名侦探：构造两个共享底层数组的切片（b := a[:2]），用「直接 append」「三索引切片」「提前 make 足容量」三种方式修复，验证哪一种能保证 a 不被改写。
  3. 二维切片初始化器：实现 buildGrid(rows, cols int) [][]int，故意写出错误版本并跑一次，把 panic 信息抄下来，解释它到底在哪一步炸了。
  4. nil 与空：写一个返回 JSON 的小接口，让某个字段先是 nil 切片、再改成空切片，用 curl 观察两次响应的差异。

8.9 常见错误清单

# 错误写法 后果 正确写法
1 append(s, v) 不接返回值 元素凭空消失 s = append(s, v)
2 b := a[:2] 后 b = append(b, x) 悄悄改写 a 的后续元素 b := a[:2:2] 或先 slices.Clone
3 把 s[1:3] 当成复制 修改结果会影响原切片 slices.Clone(s[1:3])
4 grid := make([][]int, n) 直接写 grid[i][j] panic: index out of range 逐行 grid[i] = make([]int, m)
5 for i := range s { s = append(s, ...) } 循环次数按旧 len 先把结果写到新切片
6 长期持有 &s[i] 扩容后指针指向过期数据 append 后重新取地址

收束成一句：切片是「指针 + 长度 + 容量」的三元组视图，**append 可能在原地写、也可能换一块新内存，你无法从类型上判断。所以 Go 的纪律是——永远使用 append 的返回值，永远不假设两个切片互不相干**。
