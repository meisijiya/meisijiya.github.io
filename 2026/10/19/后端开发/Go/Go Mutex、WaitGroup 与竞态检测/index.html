13 Go Mutex、WaitGroup 与竞态检测

数据竞争到底长什么样？这一篇把 Go 的同步三件套——互斥锁、等待组、竞态检测器——连同 context 取消机制一起讲透。

13.1 数据竞争：不是「偶尔出错」，而是「无法推理」

Go 对数据竞争（data race）的定义很干脆：两个 goroutine 并发访问同一块内存，其中至少一个是写，而且没有任何同步手段。它强调的是「并发访问」而不是「结果错了」——没有同步时，谁先写谁后写完全由调度器决定。

Java 里写过类似代码的人第一反应是 counter++ 不是原子的，要换 AtomicInteger。Go 的问题更彻底：普通变量的并发读写一律是竞争，哪怕你只写不读。

维度 Go Java
普通变量并发写 静默出错，编译期与运行期都不报（除非开 -race） 同样静默出错
内置容器并发写 运行时直接崩：fatal error: concurrent map writes HashMap 迭代才抛 ConcurrentModificationException
并发写的正解 自己加锁，或用 sync.Map ConcurrentHashMap

Go 的取向是宁可当场崩，也不悄悄给你错数据。注意 map 并发写触发的是 fatal error 而不是 panic，recover() 救不回来，进程直接退出。

13.2 sync.Mutex：Go 版的 synchronized

三个必须记住的特性：

  1. 零值可用。var mu sync.Mutex 直接就能用，Java 里得记得 new ReentrantLock()。
  2. 不可重入。同一 goroutine 里连续 Lock() 两次，第二次永久阻塞——Go 的锁不记录持有者，直接死锁。Java 的两种锁都可重入，这点极易踩。
  3. 不会自动释放。Java 的 synchronized 块退出时自动解锁，Go 必须自己 Unlock()，所以永远用 defer c.mu.Unlock()。

Unlock 配错锁类型会直接 fatal：sync: unlock of unlocked mutex。

Go vs Java：锁原语对照

维度 Go Java
互斥锁 sync.Mutex，零值可用 synchronized / ReentrantLock，需 new
是否可重入 ❌ 重入即死锁 ✅ 两者都可重入
异常时释放 ❌ 手动 Unlock（务必 defer） ✅ 退出代码块自动释放
读写锁 sync.RWMutex，写者优先 ReentrantReadWriteLock，可选公平/非公平
条件变量 sync.Cond，需自己配一把锁 wait() / notify()，与对象锁绑定
原子类 sync/atomic，atomic.Int64 等 AtomicLong 等
计数等待 sync.WaitGroup CountDownLatch / CompletableFuture
取消与超时 context.Context 无统一内置方案

13.3 sync.RWMutex：读多写少才划算

RWMutex 把「读」和「写」拆开：多个读者可同时持锁，写者独占。

三条容易忽略的规则：

  • **RLock 必须配 RUnlock，Lock 必须配 Unlock**。配错会 fatal，比如对一把只加了写锁的锁调用 RUnlock，报 sync: RUnlock of unlocked RWMutex。
  • 读锁不能升级成写锁。持有 RLock 时再调 Lock()，等于自己等自己，死锁。
  • 递归读锁也可能死锁。若 A 持有读锁、B 正在等写锁，A 再来一次 RLock 就会被挂住——Go 的 RWMutex 是写者优先的，一旦有写者在等，新读者一律排队。

写多的时候用 RWMutex 反而更慢——每次 RLock/RUnlock 都要额外维护读者计数，只有读远多于写时才有正收益。

13.4 sync.WaitGroup：别再用 sleep 等 goroutine

WaitGroup 是一个计数信号量：加一、减一、等归零。

每个 goroutine 只写自己那个下标，虽然底层是同一个数组，但不同内存位置不构成数据竞争。

规则是：当计数器为 0 时，增加计数的调用必须发生在 Wait 之前，也就是 Add(1) 必须在 go 之前。写错位置就会这样：

永远不要用 time.Sleep 代替等待：sleep 是「猜时间」，机器一忙就出错。Go 1.25 起新增 wg.Go(func(){...})，把 Add + go + Done 三步合成一步。

13.5 sync.Once 与 atomic：一次初始化与轻量计数

sync.Once 保证某段初始化代码只执行一次，哪怕被多个 goroutine 同时触发。

它和 Java static 块有个明显差别：如果 Do 里的函数 panic 了，Once 仍认为这件事「已经做过了」，后续再调 Do 不会重试。所以 Once 适合「加载配置、建立连接」这类场景。

13.6 竞态检测器：让 Go 自己喊出 bug

Go 的杀手锏是竞态检测器：编译时给内存访问插桩，运行时记录每次访问的 goroutine 身份，一旦发现两个 goroutine 对同一地址发生冲突访问且没有同步，立刻打印报告。

前提是需要 CGO 和 C 编译器：Windows 上要装 MinGW 的 gcc，CGO_ENABLED=0 会直接报 -race requires cgo。检测器大致慢 220 倍、内存涨 510 倍，别拿它压测。

Write at ... by goroutine 8 是冲突的写方，Previous read at ... by goroutine 7 是另一方，两段栈告诉你在哪里出的事；最后那段 created at 告诉你这个 goroutine 从哪儿来，定位并发问题第三段往往最关键。

它能发现未同步的变量读写、map 并发写、缺失的原子操作；发现不了业务层面的逻辑竞态、死锁、goroutine 泄漏。而且它是动态检测：只有真正跑到的、真正冲突的访问才会被报出来，覆盖不足它就一声不吭。所以并发相关的测试统一带上 -race 并放进 CI。

13.7 context：给后台任务一个取消开关

Go 的 context 是一等公民：标准库里凡是可能长时间阻塞的 API（net/http、database/sql、os/exec）都提供了 ...Context 版本，让「取消」和「超时」成为可以层层传递的显式参数。

几条核心约定：

  • 用 context.WithCancel(parent) 派生，用 ctx.Done() 感知取消，ctx.Err() 区分 context.Canceled（主动取消）和 context.DeadlineExceeded（超时）。
  • ctx 一律作为函数的第一个参数，名字就叫 ctx——它几乎出现在每个函数签名里，位置必须统一。
  • 不要把 ctx 存进结构体字段。结构体一旦持有 ctx，生命周期就被外部的取消信号绑死了，测试时也难以替换。
  • 派生出来的 ctx 必须调用 cancel，go vet 的 lostcancel 检查专盯这个。而且取消是协作式的：ctx 不会强杀 goroutine，被取消方要自己检查 ctx.Done() 并退出。

Java 那边没有对等的统一方案，通常靠 Future.cancel(true)。Go 的优势是标准库全链路支持：把 ctx 往下传，HTTP 请求、数据库查询会自己响应取消。

13.8 锁的粒度、复制陷阱与性能取舍

最常见的性能问题不是「锁太慢」，而是临界区太大。锁只该包住真正共享内存的那几行，网络调用绝不能放在锁里，否则锁被长时间占用，并发直接塌陷。

更彻底的解法是用 channel 传递数据所有权：每个 goroutine 独占一份数据，别的 goroutine 通过 channel 发请求、收结果，共享可变状态被消灭了，连锁都不需要——这是 Go 处理并发的首选姿势。

复制一把锁：go vet 的 copylocks

sync.Mutex 使用后不可复制。结构体一旦用值接收者，调用方法时会隐式复制整个结构体，锁也就被复制了——复制出来的锁和原锁是两份互不相干的状态，加锁等于没加。

go vet ./... 的 copylocks 检查会直接报出来，形如 Get passes lock by value: Cache contains sync.Mutex。凡是结构体里放了 Mutex、RWMutex、WaitGroup、Once，接收者一律用指针。

13.10 动手练

  1. 修 bug + 验证：把 13.1 那段 counter++ 改对，写个 counter_test.go 用 go test -race ./... 跑通；再故意把 Add 挪进 goroutine 内部，看报告长什么样。
  2. 读写锁对比：同一缓存分别写 Mutex 版与 RWMutex 版，用 go test -bench 在「100 个读、1 个写」和「写占一半」两种负载下各跑一次，用数据解释 13.3。
  3. 给后台任务加取消：写一个带 context.WithTimeout 的定时任务，用 runtime.NumGoroutine() 观察超时后 goroutine 是否真的退出。
  4. 让 vet 说话：写一个用值接收者持有 sync.Mutex 的方法，跑 go vet ./... 读懂报错并改对。

13.11 常见错误清单

# 错误写法 后果 正确做法
1 wg.Add(1) 写在 goroutine 内部 Wait 提前返回，任务还在跑 Add 必须在 go 之前
2 defer wg.Done() 写在父函数里 计数器提前归零 Done 写在 goroutine 内部
3 忘记解锁或锁类型配错 死锁 / fatal error 永远用 defer 配对释放
4 同一 goroutine 连续 Lock 死锁（Go 锁不可重入） 拆成两个函数，别递归加锁
5 值接收者持有 Mutex 锁被复制，保护失效 接收者一律用指针
6 持有 RLock 时再 Lock 死锁（读锁不能升级） 先释放读锁再取写锁
7 用 time.Sleep 等 goroutine 机器一忙就错 用 WaitGroup 或 channel 信号
8 共享 map 不加锁 fatal error: concurrent map writes 加锁，或换 sync.Map
9 网络调用放在临界区内 锁被长时间占用，并发塌陷 临界区只留内存操作
10 派生 ctx 后不调 cancel 定时器与 goroutine 泄漏 defer cancel() 写上

整篇的核心是：Go 的并发哲学是「用最少的共享换最大的并行」。锁、WaitGroup、atomic、context 都只是补丁，真正的解法是让数据只有一个主人。
