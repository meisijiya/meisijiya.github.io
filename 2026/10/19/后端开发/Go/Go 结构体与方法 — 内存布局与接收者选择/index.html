Go 结构体与方法 — 内存布局与接收者选择

04 Go 结构体与方法

struct 怎么定义、方法怎么挂、接收者选值还是指针、字段顺序为什么影响性能——把 Go 这套”没有类”的面向对象一次讲透。

4.1 先把结构体当成一张”数据表”

Go 里没有 class，承载数据的是 struct：

字段名的首字母大小写决定是否导出：Name 对包外可见，name 只在包内可见。这条规则对结构体字段、函数、类型一视同仁，和 Java 的 public / private 目的相同但机制不同——没有关键字，靠命名约定。

反引号里的是结构体 tag，它是 encoding/json 的字段契约，omitempty 表示字段为零值时不输出该 key。

零值：Go 最被低估的设计

var u User 之后，u.Name == ""、u.Age == 0，它已经是一个可用的对象，不需要构造函数。Go 的设计原则叫**”让零值可用”（make the zero value useful）：零值能正常工作，连 NewXxx 都可以省掉。反例是塞一个 map[string]string 字段：零值是 nil map，读可以、写会 panic**。

三种初始化方式

字段名式和位置式编译结果完全一样，可维护性天差地别：位置式要求字段顺序一字不差，对方一加字段你就编译不过。go vet 的 composites 检查会专门点名跨包的位置式字面量。new(User) 是内置函数，分配清零内存并返回 *User，它不是构造函数——不能接参数。Java 里 new User("x") 那种写法，在 Go 里对应 NewUser("x") 这个普通函数。

4.2 方法：挂在类型上的函数

方法就是带接收者（receiver）的函数，接收者写在函数名前面：

u.Greet() 本质等价于 Greet(u)——接收者就是第一个参数，编译器替你塞进去。

几条硬规则：接收者必须是当前包内定义的具名类型，不能给 string、int 加方法；接收者可以是指针；方法不写在 type 块里而是独立声明；接收者名要短且统一，官方风格是类型首字母缩写（u 对 User、c 对 Client），**不要叫 this 或 self**。

方法也不只属于结构体：给 type Celsius float64 挂一个 String() string，就实现了 fmt.Stringer，fmt.Println 会自动调用——正是 Java toString() 的位置。

4.3 值接收者 vs 指针接收者

关键只有一句：值接收者调用时会复制一份副本，指针接收者传的是原对象的地址。

所以给上面那个 User 写一个 func (u User) Birthday() { u.Age++ }，调用后 u.Age 一点没变——而且不会编译报错，静默失效是这类 bug 最麻烦的。

什么时候必须用指针接收者

  1. 方法要修改接收者——不用指针，改的就是副本。
  2. 结构体比较大——值接收者每次调用都拷贝整个结构体。含 int64 或多个 string 字段就该按大结构体对待。
  3. 结构体里有 sync.Mutex 等锁——值接收者会复制锁的状态，go vet 的 copylocks 会报。
  4. 结构体里有 slice 或 map——值接收者复制的是 slice header，底层数组却是共享的。于是方法里写 t.Items[0] = "x" 调用方看得见，而 t.Items = append(t.Items, item) 调用方看不见。同一个字段两种行为，含 slice / map 必用指针。

方法集：接口实现上的隐藏规则

Go 判断”某类型是否实现了某接口”时，看的是方法集（method set）：类型 T 的方法集 = 所有值接收者的方法；*T 的方法集 = 值接收者方法 + 指针接收者方法。于是：

所以只要一个类型里有任何一个指针接收者方法，这个类型的”值”就不再满足需要它的接口。从 Java 转过来的人常在这里栽：方法明明写得好好的，塞进 []Describer 就编译不过。

同一份规则还解释了另一个坑：调用指针接收者方法时，编译器会对可寻址的值自动取地址，(&u).Rename(...) 的 & 可以省。但 map 元素不可寻址，users["a"].Rename("x") 会报错。

对比表

维度 值接收者 func (u User) 指针接收者 func (u *User)

复制开销 与结构体大小成正比 无
方法集 T 和 *T 都包含 只有 *T 包含

一致性这行值得展开：Effective Go 建议”一个类型的所有方法用同一种接收者”。一旦混用，T 和 *T 的方法集就不一样，接口赋值会在某个遥远的地方突然编译失败。口诀：有没有要改状态的方法？有就用指针，没有就用值。

4.4 内存布局：字段顺序真的影响性能

Go 的结构体没有对象头。它是一块连续内存，字段按声明顺序排布，各自对齐到自身类型要求的位置，空隙用填充字节（padding）补上，**整体大小向上取整到”最大字段对齐倍数”**。

64 位平台上：bool 占 1 字节，int32 占 4 字节，int / int64 / 指针占 8 字节，string 占 16 字节。

用 unsafe 包能直接量：

把同样三个字段按 Count int64 → Flag bool → Tail bool 重排（记作 Ordered），unsafe.Sizeof(Mixed{}) 是 24，unsafe.Sizeof(Ordered{}) 是 16，省了三分之一——Mixed 把 bool 放在 int64 前面，逼出 7 字节 padding；而末尾的 padding 反正要补齐到 8 的倍数，把小字段放最后不吃亏。差距在数组里会被放大：[]Mixed 一万个元素就多占 8 万字节。golangci-lint 的 fieldalignment 能揪出这类结构体。

对照 Java：User{Name string; Age int} 在 Go 里是 24 字节，[]User 是一整块连续内存；Java 的 User[] 只是引用数组，每个 User 还要额外背上对象头。**”值语义 + 无对象头”是 Go 省内存的关键。**

4.5 匿名字段与嵌入：用组合代替继承

Go 没有 extends。想复用公共字段，办法是嵌入——写一个匿名字段：

Base 的字段被提升到外层可直接访问，Base 上的方法也提升成 User 的方法。这是 Go 唯一的复用手段，而它是组合不是继承。

三个必须知道的限制：

一、提升出来的字段不能在字面量里直接写。 复合字面量只认结构体自己声明的字段名，必须写成 User{Base: Base{ID: 1}, Name: "meisijiya"}，写 User{ID: 1} 编译报错 unknown field ID。

二、同层同名会歧义，外层同名会遮蔽。 若 Base 和另一个嵌入类型都有 Name，u.Name 报 ambiguous selector，必须写全 u.Base.Name；外层声明的 Name 会遮蔽提升上来的同名字段。

三、嵌值就是拷贝，嵌指针就是共享。 写成 type User struct { *Base } 就是与外部共享同一个 Base。

4.6 构造函数惯例：NewXxx

Go 没有构造函数关键字，约定写一个 NewXxx 函数，一般返回指针：

几个要点：返回指针是主流写法，因为调用方几乎总要把对象存下来继续改；可以返回 error，Java 构造函数抛不了受检异常，Go 里构造失败就返回 error；**NewUser 不是关键字**，就是普通函数。

那什么时候返回值而不是指针？看大小和语义：小结构体、创建后基本只读，返回 User 值，逃逸分析常让它待在栈上；大结构体或创建后还要改，返回 *User，避免每次拷贝。

4.7 动手练

  1. 定义并初始化。写一个 Feed 结构体：ID string、Title string、URL string、Tags []string、FetchedAt time.Time。用字段名字面量初始化并打印所有字段，再用位置式字面量初始化一次，对比可维护性差异。

  2. 接收者对比实验。给 User 写 Greet() string（值接收者）和 Rename(name string)（指针接收者），调用后打印原对象的 Name，亲眼看到值接收者改不动原对象。

  3. 量一量内存布局。用 unsafe.Sizeof 量 struct{ Flag bool; N int64 } 和 struct{ N int64; Flag bool }，先预测再运行验证；再把 int64 换成 int32 重算一次，解释两次结果为什么不同（提示：总大小要向上取整到对齐倍数）。

  4. 嵌入 + 装饰器。定义 Logger 接口和 consoleLogger 实现，定义 Server 嵌入 Logger，再写一个 countingLogger 装饰器包住它。分别构造”正常赋值”和”忘记赋值”两种 Server，观察后者调用方法时的 panic。

4.8 常见错误清单

按踩坑频率排序，前三条最容易出现在面试题里：

  1. 值接收者里改字段，改的是副本。u.Age++ 编译照过、运行照跑，就是不生效。要改状态就用指针接收者。
  2. 同一类型混用值 / 指针接收者，T 满足不了接口，编译失败。一个类型一套接收者风格。
  3. 含 sync.Mutex 的结构体用值接收者，复制锁状态。含锁必用指针。
  4. 含 slice / map 的结构体用值接收者。改元素看得见、append 看不见。含引用类型字段必用指针。
  5. 嵌入接口没初始化，srv.Log(...) 直接 nil 解引用 panic。构造函数里必须赋上实现。
  6. 提升字段写进字面量，User{ID: 1} 编译不过，要写成 User{Base: Base{ID: 1}}。
  7. 跨包用位置式字面量，User{"a", 1} 对方一改字段就编译失败。跨包一律用字段名。
  8. 大结构体按值返回，签名写 User 而非 *User，每次调用都在拷贝。超过几个机器字就换指针。
  9. 含 slice / map 的结构体用 == 比较，编译报错。逐字段比或用 reflect.DeepEqual。
  10. 字段顺序没排过，bool 塞在 int64 前面凭空多出 7 字节 padding。用 fieldalignment 检查。

Go 的”面向对象”只有三块积木：结构体装数据、方法挂行为、接口描述能力。这一篇把前两块讲完了，接收者选择和内存布局是贯穿始终的底层约束。下一篇接着看第三块——interface 与隐式实现：为什么 Go 敢不要 implements 关键字，一个类型怎么在不加声明的情况下”变成”一个接口。
