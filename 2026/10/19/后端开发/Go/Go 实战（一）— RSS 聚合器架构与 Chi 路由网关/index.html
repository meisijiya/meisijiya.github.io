15 Go 实战（一）— RSS 聚合器架构与 Chi 路由网关

从零搭一个 RSS 聚合器的 HTTP 网关：先把目录结构、路由、中间件和统一响应的边界划清楚，再谈数据库与并发抓取。

15.1 这个项目到底要解决什么问题

15.1.1 先把业务闭环拆开

RSS 聚合器的用户故事很短，但每一环都对应一类工程问题：

阶段 用户在干什么 服务端必须做到的事
注册 填昵称创建账号 生成用户记录和一枚 API Key，密钥只在创建时明文返回一次
订阅 拿 API Key 提交 RSS 地址 校验地址、落库、建立「用户 ↔ 订阅源」的关联
抓取 什么都不做，后台自动跑 并发拉取订阅源，解析标题 / 链接 / 发布时间并入库
查询 查订阅列表和文章列表 联表分页返回

四条线里只有注册和查询是同步 HTTP 接口，抓取是纯后台任务。所以第一个工程决定就出来了：先把 HTTP 网关立稳，再往里塞业务——网关的路由、错误格式、关停行为一旦不稳定，后面所有工作都会被它反噬。

15.1.2 架构图

三个刻意为之的设计：handler 不碰数据库，只把 HTTP 世界翻译成 Go 世界；service 不碰 HTTP，参数和返回值都是普通 Go 值；store 是接口，实现可互换。

15.1.3 分层靠目录强制，不靠自觉

Go 没有注解驱动的依赖注入，它给你的工具是目录结构 + 接口：

层 目录 允许依赖 能出现 HTTP 相关的东西吗
接入层 internal/httpapi service 能，这是它的本职工作
领域层 internal/service store、models 不能
存储层 internal/store models 不能

「service 层不能出现 HTTP 相关的东西」是这套分层最值钱的一条：它意味着同一个 service 既能被 HTTP handler 调用，也能被后台抓取 goroutine 调用。Go 里 internal/ 目录能挡掉九成架构事故。

15.2 工程初始化：目录、模块与配置

15.2.1 目录结构逐个解释

路径 职责 关键约束
cmd/rssagg/main.go 进程入口 只做装配和启停，不写业务逻辑
internal/config 读 .env / 环境变量 不依赖项目内其它包，是依赖树的叶子
internal/httpapi 路由、handler、中间件 只能依赖 service，不能直接依赖 store
internal/service 业务规则与流程编排 感知不到 HTTP，也不知道数据存在哪
internal/store 存储接口 + 实现 只依赖 models

入口之所以叫 cmd/rssagg：Go 的约定是一个仓库可以编译出多个二进制，每个可执行程序一个 cmd/<名字>/ 子目录且必须是 package main；以后想再拆一个 cmd/migrate 做迁移，位置就留好了。

15.3 路由层：为什么选 chi

15.3.1 为什么选 chi

选 chi 的三个理由：轻量（只依赖标准库）、组合式中间件（func(http.Handler) http.Handler 可以随便套）、可嵌套（r.Route("/v1", ...) 做版本前缀，r.Mount 挂子应用）。和 Java 特别值得说：Spring 的拦截器靠 addInterceptors 注册，没法给单个 handler 单独挂一层；chi 的 r.With(mw).Get("/users", h) 就是给单个接口加一层。

15.3.2 chi.NewRouter 与注册路由

chi.NewRouter() 返回 *chi.Mux，实现了 http.Handler，能直接塞进 http.Server.Handler。{id} 是路径参数，取值用 chi.URLParam(r, "id")；查询参数是 r.URL.Query().Get("page")。r.NotFound 和 r.MethodNotAllowed 必须显式覆写：chi 默认返回纯文本，客户端按 JSON 解析会直接崩。

15.3.3 http.Server 的字段

Addr 是监听地址（:8080 表示所有网卡），Handler 是路由树（传 nil 会用默认的 DefaultServeMux）。四个超时字段是重点：ReadHeaderTimeout 缺失就没有 Slowloris 防护，恶意连接能占住 goroutine 不放；ReadTimeout 防慢速上传；WriteTimeout 防客户端不读响应；IdleTimeout 防连接堆积。Go 的 http.Server 默认一个超时都不设，这是最容易漏的安全项。

15.3.4 优雅关闭

两个必须记住的点：**ListenAndServe 在正常关闭时返回的是 http.ErrServerClosed 而不是 nil，不判断的话每次正常关停都会打一条 error 日志；Shutdown 只停止接受新连接，再等在途请求跑完**，必须配 context.WithTimeout，超时后用 Close() 强制断开。

15.4 统一响应与错误处理

15.4.1 一个 respondWithJSON 打天下

w.Header().Set 必须在 w.WriteHeader 之前——这是 Go 最常见的低级 bug。WriteHeader 一旦调用，响应头就已经写进 socket 了，之后再 Set 毫无效果：症状是状态码对了，但 Content-Type 变成 Go 默认猜测的 text/plain; charset=utf-8，前端 JSON.parse 报错。同理，**一个请求只能调用一次 WriteHeader**。

15.4.2 错误响应约定

场景 状态码 响应体示例
请求体不是合法 JSON 400 {"error":"请求体不是合法 JSON: ..."}
参数校验不通过 422 {"error":"name 不能为空"}
缺 API Key / Key 无效 401 {"error":"缺少 API Key"}
服务端内部错误 500 {"error":"internal server error"}

三条纪律：4xx 给可读的中文提示；5xx 只给一句通用话，真实细节只写日志不进响应体；格式全站统一成 {"error": "..."} 一种形状。

15.4.3 http.Error 和自定义 JSON 怎么选

http.Error(w, "something went wrong", 500) 是标准库自带的错误输出：写纯文本、Content-Type 设为 text/plain; charset=utf-8、自动加 X-Content-Type-Options: nosniff。它适合返回给人看的页面，用在 API 接口上客户端按 JSON 解析会炸。

Spring 靠 @RestControllerAdvice 自动完成这件事，FastAPI 靠注册 exception_handler。Go 没有注解，只能靠约定 + 一个辅助函数——所以 respondWithError 必须在项目里只有一份，放在 internal/httpapi 包里共用。

15.5 第一个业务接口：创建用户

15.5.1 入参结构体与 json tag

Go 的 encoding/json 在没有 tag 时会做大小写不敏感匹配（Name、name 都能对上），但客户端多传的字段会被静默忽略。显式写 tag 表达两件事：字段名以 wire 格式为准，以及「这个字段我认得」。Java 的 Jackson 需要 @JsonProperty，Python 的 pydantic v2 要 Field(alias=...)：三门语言都要显式声明映射关系，只是 Go 默认宽松。

15.5.2 为什么用 Decoder 而不是 Unmarshal

维度 json.Unmarshal json.NewDecoder
内存占用 整个 body 进内存 边读边解析
未知字段 默认忽略 DisallowUnknownFields() 直接报错
大整数 目标为 any 时按 float64 解，丢精度 UseNumber() 保留原始数字

省一次内存拷贝。 Unmarshal 要求你先 io.ReadAll(r.Body) 拿到完整字节切片，等于把请求体在内存里存了两份；Decoder 直接从 r.Body 读，边读边解析。Java 侧的 Jackson readValue(InputStream, Class) 本身就是流式的。

把「前端字段名拼错」变成一次明确的 400。 DisallowUnknownFields() 开启后，前端把 userName 写成 username，服务端直接报 400；不开启的话服务端静默忽略，name 保持零值，返回一个 name 为空的用户——这种 bug 能潜伏好几个月，因为接口返回 201，客户端也不报错。

解决大整数精度丢失。 Go 把数字解到 any 时用 float64 承载，超过 2^53 的整数会被悄悄改掉：9007199254740993 反序列化进 any 打印出来是 9.007199254740992e+15，末尾的 3 没了。Python 的 int 是任意精度，Java 的 long 是定长 64 位，都不会「悄悄变形」；Go 最容易在这上面翻车，解法是 dec.UseNumber()。

15.6 中间件：Go 的装饰器

15.6.1 签名与本质

http.Handler 只有一个方法 ServeHTTP(ResponseWriter, *Request)，所以「中间件」就是一个吃 handler、吐 handler的函数：

Go 的中间件就是装饰器——和第 10 篇讲的闭包、高阶函数是一回事。Java 的对应物是 HandlerInterceptor 或 Servlet 的 Filter；Go 的写法最直白：中间件是一个返回函数的函数。

15.6.2 执行顺序：注册顺序 = 由外到内

规则只有一条，但必须记牢：注册顺序 = 请求进入顺序 = 响应返回顺序的逆序。 排顺序的原则：RequestID 必须最外层，否则后面的日志里就拿不到 ID；Recoverer 要在 Logger 里面，这样 panic 被兜住之后 Logger 依然能记录状态码和耗时；Auth 放在最内层。

15.6.3 panic 恢复中间件

Go 的 panic 沿 goroutine 栈向上冒泡，如果一路没人 recover，整个进程立刻退出——比 Java 更硬朗，所以 Recoverer 是必须有的一层。注意三点：**recover() 必须写在 defer func(){...}() 这种直接调用的匿名函数里，defer recover() 是无效的；debug.Stack() 拿的是当前 goroutine 的调用栈，一定要打进日志；出错后不要再写响应**。

15.6.4 请求 ID 与结构化日志

四个点：context key 用自定义类型（用 string 做 key 时 go vet 会报警告）；请求 ID 优先用客户端带来的；状态码靠包装 ResponseWriter 拿到；包装会丢可选接口（http.Flusher、http.Hijacker 失效）。

15.6.5 路由与中间件对照表

注册位置 写法 生效范围 典型用途
全局 r.Use(mw) 整棵路由树 RequestID、Logger、Recoverer
版本分组 r.Route("/v1", func(r chi.Router){...}) 子树 版本前缀、给整组加中间件
单个路由 r.With(mw).Get("/x", h) 仅这一个 handler 鉴权、限流
兜底 r.NotFound(...) / r.MethodNotAllowed(...) 全局 统一 404 / 405 格式

15.8 动手练

四个任务都基于本文代码，按顺序做，每步都能用 curl 验证：

  1. 补一个查询接口。实现 GET /v1/users/{id}，用 chi.URLParam(r, "id") 取路径参数；查到返回 200，查不到返回 404。提示：store 接口要加 FindByID(ctx, id)。
  2. 加一条字段校验。给 createUserRequest 加一个 Email 字段（非必填），填了就必须包含 @，否则返回 422。
  3. 把未知字段的错误改友好。定义一个自己的错误类型，用 errors.As 识别后返回「请求包含未知字段：userName」，这一步是为了理解第 6 篇讲的 errors.As。
  4. 加一个慢请求中间件。在 Logger 之外加一个 SlowRequest，超过 200ms 的请求打一条 Warn 日志。

15.9 常见错误清单

坑 现象 正确做法
WriteHeader 之后再 Header().Set 状态码对但 Content-Type 不对，客户端解析 JSON 失败 所有 Header().Set 必须在 WriteHeader 之前
忽略 Decode 的错误 请求体是坏的，结构体全是零值，接口却返回 201 每次 Decode 都要判 err
忘了 DisallowUnknownFields 前端字段名拼错，服务端静默忽略，返回一个字段为空的对象 开启它，把拼错变成 400
len(s) 当字符数 中文字段的长度限制比预期严 3 倍 len([]rune(s))
http.Server 不设超时 慢连接能占住 goroutine，服务被拖垮 至少设 ReadHeaderTimeout / ReadTimeout / WriteTimeout
