Go 泛型与类型约束 — 从 any 到类型安全

14 Go 泛型与类型约束

没有泛型时只能拿 any 加类型断言硬扛，泛型把这笔账挪到了编译期。

14.1 泛型解决什么问题：any 的代价

Go 1.18 之前，「对任意元素做同一件事」只有 any 这条路：

能跑，但有四笔账要付：

  1. 类型安全塌到运行时。混进一个 string，编译器一声不吭，要等线上跑到那行才炸。
  2. 装箱开销。int 存进 any 是一次装箱（接口槽指针 + 可能一次堆分配），读时还得拆。
  3. 样板代码爆炸。多支持一种类型就复制一遍函数体，第三个就「改一个忘一个」。
  4. 签名信息量被抹掉。func sumInts(values []any) 看不出要什么，func sumInts[T ~int](values []T) 一眼懂。

和 Java 对比：Java 的 List<T> 也能编译期查错，但 T 可以任意指定，代价是运行时被擦除成 Object，取元素要强转。Go 的泛型则强制你写一份约束，说清 T 能干什么。

Go 磨到 1.18 才肯加泛型，源于一贯立场：宁可少特性，不要复杂度爆炸。落地时也极其克制——不支持运算符重载、约束必须显式写、方法一度不能带自己的类型参数（这条到 Go 1.27 才放开）。

用起来（T 和 U 都能推断出来）：

编译器从 s []T 推出 T = User，从 f func(T) U 推出 U = string，这叫类型推断。Go 1.18 推断很弱，1.21 起宽松不少；推不出来就显式实例化，如 Map[int, string](ints, strconv.Itoa)。

类型参数的名字纯粹是惯例：社区惯例是 T 表示泛型类型、U 表示第二个类型参数、K / V 表示 map 的 key / value、E 表示元素。典型签名如 func Zero[T any]() T、func Keys[K comparable, V any](m map[K]V)。写 MyAnyType 也能编译，只是签名会长。

14.3 约束基础：any、comparable 与「约束就是接口」

约束（constraint）本质就是接口，只多一条限制：只能用作类型参数的约束，不能当普通接口值使用。

any 是 interface{} 的别名，最宽松；comparable 表示「可以用 == 和 != 比较」：

用 any 约束时不能写 item == target（any 不保证底层类型可比较）。Go 1.20 起 comparable 放宽，普通接口类型也能满足；但两个接口值用 == 时，若动态类型不可比较（如装着 slice），运行时会 panic。

约束写法速查表：

需求 写法 能做什么
任意类型 any 只能存、传、返回，不能 ==
可比较 comparable == / !=、可作 map key
有序 cmp.Ordered < <= > >=、可加减
某个方法 interface{ String() string } 调用 String()
一组类型 interface{ ~int | ~float64 } 数值运算
数值 + 有方法 interface{ ~int | ~float64; String() string } 两者都行

cmp.Ordered 由 Go 1.21 的 cmp 包提供，不用自己抄一遍。

「约束接口不能当值用」极易踩坑：

原因：约束接口可能含 int | string 这种类型联合，运行时不存在能表示「既是 int 又是 string」的具体值——它只描述类型集合，不是可实例化的类型。

14.4 联合类型约束与 ~ 运算符

类型联合（union）把一组类型打包成约束：

~ 是 Go 1.18 引入的近似（tilde）运算符，意思是「底层类型是它即可」。Go 有具名类型，如 type Celsius float64、type UserID int64：写成 interface{ int64 | float64 } 时它们都不满足——底层类型虽同，类型本身不同；加上 ~ 后都满足。

即：类型集合必须两两不相交（int 本身就在 ~int 里）、不能放带方法的接口类型、不能用类型参数。也因此，泛型容器通常靠 ~[]E 这种类型集表达，而不是靠联合——标准库 slices.Contains 的真实签名 func Contains[S ~[]E, E comparable](s S, v E) bool 就是例子：S ~[]E 意思是「S 的底层类型是某个 []E」，所以 []int 或 type Ints []int 都能用。

Go 1.27 起这条限制被放开了：方法可以声明自己的类型参数，上面那行直接可用，s.Map(f) 就能调用。但有两个边界必须记住：

  • 接口方法依然不能有类型参数（interface method cannot have type parameters）；
  • 泛型方法不进方法集，所以它不能用来实现接口方法——别指望拿一个泛型方法去满足某个接口。

如果你要立刻用上这个语法，注意新语法同样由 go.mod 里的 go 指令决定：go 1.24 的老模块即使拿 Go 1.27 的工具链编译，泛型方法也用不了，得先升 go 指令。

14.6 何时用泛型、何时用接口

三者的区别不在「强不强」，而在描述的东西不同：

维度 any + 类型断言 泛型 接口
类型安全 运行时检查 编译期检查 编译期检查（实现方）
表达的意思 「我接受任何值」 「同一份算法，任意 T」 「一组行为」
典型场景 JSON 反序列化、任意 map 容器、算法、API 包装 依赖注入、插件、多实现
装箱 有 无（调用点类型确定） 取决于实现与接收者
主要缺点 断言样板、易 panic 约束难设计、API 难改 值接收者有装箱开销

一句话判据：

  • 「同一段算法，处理不同类型」→ 泛型。
  • 「同一件事，不同实现」→ 接口。
  • **「具体类型要到运行时才知道」→ any**。

举例：「按年龄排序用户取前 N 个」的排序算法对 int、float64、string 实现一样，差别在数据本身，用泛型；「存储后端」可能 MySQL 也可能 Redis，差别在行为，用接口。

标准库的例子更能说明问题：Go 1.21 起 slices 和 maps 基本就是泛型的集大成。

slices.Sort 要 cmp.Ordered、slices.Contains 要 comparable——约束直接写在标准库签名上，能不能过编译取决于元素类型满不满足。这就是「约束是 API 的一部分」。

maps 在 Go 1.23 之后，maps.Keys 返回可迭代序列而非切片，可直接 for k := range maps.Keys(m) 遍历。

14.7 泛型的限制与代价

限制清单（面试常问）：

  1. 方法能不能有类型参数看版本：Go 1.26 及以前不行，只能写自由函数；Go 1.27 起允许，但泛型方法不进方法集，不能用它实现接口方法。
  2. 不能重载运算符。想在泛型上做 a + b，只能让约束限定在数值联合里。
  3. 约束接口不能当值用。
  4. 类型联合必须两两不相交，且不能含带方法的接口类型、不能含类型参数。
  5. 类型参数没有默认值，也没有 Java 那种 T... 可变长类型参数——用 []T 表达。

代价分两头看：

  • 运行期：编译器对泛型做形状共享——GC 形状相同的类型共用一份代码，类型相关的方法表通过字典在调用时传入。调用点类型确定，不像 any 那样要装箱，也没有反射开销，所以泛型在热路径上通常比 any + 断言更快。
  • 编译期：多一份代码生成和字典，编译略慢、二进制略大，但可接受。
  • API 复杂度：最容易被忽略的一条。约束是公开 API 的一部分——一旦发布 func Foo[T Ordered](...)，调用方可能已按推断用到它；以后改约束，调用方代码可能集体编译不过。所以约束要一次设计好。

14.8 动手练

  1. 实现 Reduce[E, A any](s []E, init A, f func(A, E) A) A：用累加器把 []User 折成总年龄，再写一版非泛型的对比代码量。
  2. 实现 Filter[T any](s []T, keep func(T) bool) []T，想清楚空输入和全被过滤掉时返回 make([]T, 0) 还是 nil。
  3. 定义 type Number interface{ ~int | ~float64 } 并实现 Sum[T Number](s []T) T；再把 Celsius（底层 float64）传进去——去掉 ~ 会报什么错？
  4. 挑战题：给 14.5 的 Stack[T] 加一个 Map[U any](f func(T) U) Stack[U] 方法，分别在 go 1.24 和 go 1.27 两个 go.mod 下编译一次——看报错随版本变化，再改写成自由函数对比调用体验。
  5. 抄下 slices.Contains 与 slices.Sort 的真实签名，说清为什么分别要 comparable / cmp.Ordered。

14.9 常见错误清单

现象 原因 修法
cannot use type Ordered outside a type constraint 把约束接口当普通接口用了 只能用在类型参数位置
overlapping terms: int and ~int 联合里类型集合重叠 二选一，别同时写
cannot use error in union (contains methods) 联合里放了带方法的接口类型 拆成普通接口约束
cannot use type parameter T as operand in type set 联合里用了类型参数 改用 ~[]E 这类类型集
method must have no type parameters 给方法加了类型参数 改成自由函数
cannot use generic type Stack[T] without instantiation 忘了写 Stack[string] 补上实例化
invalid operation: ... (mismatched types) 在 any 约束下写了 == 换成 comparable 约束

最后一个提醒：别为了用泛型而用泛型。处理三种类型以内、逻辑又不复杂的场景，any + 类型断言或写三个小函数往往更好读。泛型真正划算的地方是——同一份算法服务于很多类型且值得复用。库和工具包是主战场，业务代码里少，这和 Java 生态的直觉一致。
