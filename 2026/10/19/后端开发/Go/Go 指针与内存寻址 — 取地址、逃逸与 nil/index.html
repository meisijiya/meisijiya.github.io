11 Go 指针与内存寻址

Go 把指针保留了下来，却给它套了三层安全网：不能算地址、不用手动释放、空指针会明确崩溃。

11.1 取地址与解引用

跟指针有关的运算符只有两个：&x 是取地址，*p 是解引用。

注意 p 的**类型是 *int**，不是 int。它是一个「装着地址的盒子」，盒子本身也有类型：把 *int 赋给 *string 编译期就报类型不匹配。

跟 Java 最大的区别在这儿：Java 里你拿不到一个变量的地址，引用本身就是地址，你没法通过它改写「这个引用指向谁」。另外只有可寻址的表达式才能取地址：变量、数组元素、结构体字段可以，字面量、函数返回值不行。

Go / C / Java 三方对比

维度 C Java Go
声明指针 int *p; Integer p;（对象引用） var p *int
取地址 &x 拿不到，引用本身就是地址 &x
解引用 *p p.intValue() *p
指针运算 允许：p + 1 不允许 不允许（编译期报错）
空指针 NULL null nil
解引用空指针 未定义行为 抛 NullPointerException panic，进程终止
悬垂指针 允许（free 后仍可访问） GC 保证不出现 GC 保证不出现
手动释放 free(p) 无 无

一句话概括：Go 的指针 = C 的指针语法 + 编译期禁掉指针运算 + GC 兜底 + 类型约束。

11.2 Go 的指针为什么说它「安全」

安全不是说它不会崩，而是指它把 C 里最危险的几条路堵死了。

11.2.1 不能做指针运算

C 的指针本质就是个整数，p + 1 能跳到下一个元素，p + 8 能硬跳到任意位置——这是 C 越界漏洞的源头。Go 直接禁：

唯一的绕法是标准库自带的 unsafe 包，比如 unsafe.Add(unsafe.Pointer(p), 8)。业务代码里看到 unsafe 基本可判定为「有 bug，或有极致的性能需求」。

11.2.2 不能把整数强转成指针

C 里可以 (int*)0xdeadbeef 凭空造一个野指针，Go 不给这条路。绕法是 unsafe.Pointer(uintptr(0xdeadbeef))，但 go vet 会报 possible misuse of unsafe.Pointer——等于官方在骂你。

11.2.3 解引用未初始化指针：编译期不管，运行期 panic

go vet 查不出这个，staticcheck 也未必能查（它可能在别处被赋过值）。**唯一的防线是你自己写 if p != nil**。这也是它跟 Java NullPointerException 最大的区别：Java 是「运行到那儿才发现」，Go 是「忘了判就崩」。

C 里 free(p) 之后 p 仍指向已释放内存，成为悬垂指针；Go 没有 free，堆对象由 GC 回收。唯一的优化手段是让指针别逃逸（见 11.5）。

11.3 nil 指针：Go 为什么不用 NULL

Go 的零值哲学决定了指针的零值只能是 nil：NULL 在 C 里是宏，就是整数 0 的替身，能塞进任何整型变量。Go 需要 nil 能参与类型检查——只有指针、切片、map、channel、func、interface 这六类可以是 nil，var x int = nil 报错。

nil 对不同类型意味着完全不同的东西

类型 读 nil 写 nil 说明
指针 *T panic — 解引用空指针必崩
切片 []T 合法 append 合法 len 为 0，range 不进循环
映射 map[K]V 合法（返回零值） panic 必须先 make 或用字面量
通道 chan T 永久阻塞 永久阻塞 close nil 通道会 panic
函数 func() 调用即 panic — 空函数不可调用
接口 any 不为 nil（见下） — 装的是「非空类型 + nil 值」

经典陷阱：typed nil

接口值在运行时是「动态类型 + 动态值」两元组。i 的动态类型是 *User，动态值是 nil，所以 i != nil。这是 Go 的 typed nil 陷阱，Java 里没有对应物。规避办法：接口别装 nil 指针。

11.4 指针与结构体

结构体是 Go 里最常配合指针使用的类型。规则很简单：用指针改的是原对象，用值改的是副本。

11.4.1 &User{...} 是取地址的简写

&User{Name: "老江湖", Age: 24} 编译器视角下等价于「先造一个临时变量再取地址」，差别只在能不能在表达式里把字段填好。new(User) 则是「先分配一块零值内存再给指针」：

两者在内存行为上完全等价，都可能栈分配也可能堆分配，取决于是否逃逸。要填字段用 &User{...}，要「先拿指针再填」用 new(User)。

11.4.2 接收者：值接收者 vs 指针接收者

调用时不用显式写 &——Go 会对可寻址的变量自动取地址（c.AddPtr(1) 等价于 (&c).AddPtr(1)）。但前提是变量可寻址：map 的元素不可寻址，m["a"].AddPtr(1) 编译不过。

11.4.3 方法集的不对称：面试常考点

类型 方法集包含
T（值类型） 只有值接收者的方法
*T（指针类型） 值接收者的方法 + 指针接收者的方法

推论：只要你的类型里有指针接收者的方法，它就不能直接当接口实现传给别人。假设 User.Rename 是指针接收者方法，那么 var w Writer = &User{} 通过，var w Writer = User{} 失败。所以有条共识：方法集里出现指针接收者，就统一用它。

11.5 逃逸分析：栈还是堆

11.5.1 变量什么时候上堆

Go 编译器会做逃逸分析（escape analysis）：判断变量的生命周期会不会超出所在函数的栈帧。逃出去了就分配到堆上交给 GC 管；没逃出去就留在栈上，函数返回即回收，零 GC 压力。典型逃逸有三种：返回局部变量地址、被闭包捕获、地址存进会逃逸的容器。

最反直觉的一点：Go 里返回局部变量地址是安全的。 C 里返回 &local 是未定义行为（栈帧一销毁指针就悬垂），Go 编译器会自动把 local 从栈「搬到」堆上（输出里写 moved to heap）。这正是 Go 比 C 少一类内存 bug 的原因。

11.5.3 逃逸的代价

GC 的触发条件是堆内存相对上次 GC 增长了阈值（默认 GOGC=100，即堆翻倍触发一次）。所以逃逸对象多，堆就增长快，GC 就触发频繁，CPU 占用上升、stop-the-world 时间变长；反过来栈上的对象根本不进 GC 统计，分配几乎零成本。

优化手法就是别让指针乱跑：能用值传递就别用指针传。反过来，大结构体用值接收者每次调用都要整份拷贝，那才是该换指针接收者时。

11.6 new 与 make：一个分配内存，一个初始化容器

这俩是 Go 新手最常混的一对 builtin。一句话：new 管「给一块零值内存」，make 管「把容器准备好用」。

维度 new(T) make(T, len, cap)
适用类型 任意类型 T 仅 slice、map、channel
返回值 *T（指针） T（值，不是指针）
分配的内存 一块 T 大小的零值内存 容器本身 + 运行时附属结构
初始化 全部字段为零值 额外做完「能用」的初始化
典型用法 结构体、指针类型 make([]int, 0, 10)

new(int) 几乎没意义——x := 0 就够了。**new 的合理场景基本只有「我需要一个指向某结构体的指针」**。

最经典的长度陷阱

make 的第二个参数是长度，第三个才是容量。make([]int, 100) 是想要 100 个元素；make([]int, 0, 100) 才是「预留 100 容量，稍后 append」。

至于 nil map：它可以读（返回零值），但不能写——m["a"] = 1 会 panic: assignment to entry in nil map。要写先 make。

11.7 常见坑

11.7.1 指针塞进 slice / map，仍然指向原变量

如果你想要「三个独立副本」，应该存值：users := []User{{Name: "A"}}。

顺带一个高频面试点，range 出来的变量是拷贝：[]*User 里 u 是指针的拷贝，改 u.Name 等于改同一对象；[]User 里 u 是结构体副本，改完原切片不变。

11.7.2 map 元素不可寻址

想改 map 里的结构体，得改成 map[string]*User。

11.8 动手练

练习一：地址与解引用
声明 x := 42，用 &x 拿到指针，打印指针本身和 *p；再通过 *p = 100 修改 x，打印 x 验证确实被改了。

练习二：nil 边界
写三个小函数：一个接收 *User 并在解引用前检查 nil，一个接收 []int 并在 nil 切片上安全地 append，一个接收 map[string]int 并在 nil map 上安全地读。观察三者对 nil 的待遇差异。

练习三：逃逸分析实战
写 func byValue() User 和 func byPointer() *User 两个函数，跑 go build -gcflags="-m" main.go，对比输出里 moved to heap / escapes to heap 的位置，把结论写进注释里。

练习四：切片里的指针
准备 []User 和 []*User 各一份，在 for range 里改名字，观察哪一个改动了原始数据，并解释原因。
