12 Go goroutine 与 channel

goroutine 怎么起、channel 怎么传、什么时候该关、什么时候会漏——Go 并发里最容易翻车的四个点，一次讲透。

12.1 goroutine：比线程轻，也比线程便宜

Go 里启动并发只有一个入口：go f()。

Go 没有任何隐式等待，等待得自己写：

和 Java 线程 / Python 线程差在哪

维度 Go goroutine Java 线程 Python 线程
创建成本 几 KB 栈，纳秒级 约 1 MB 栈 + 内核对象 不算贵，但受 GIL 限制
可用数量 几万到几十万 几千条就明显吃内存 纯 CPU 任务无法真并行
栈大小 初始约 2 KB，按需增长 固定，深递归易溢出 沿用主线程栈
调度 运行时自调度，多核并行 OS 抢占式 GIL 同一时刻只跑一个
通信方式 channel 传值（首选） 共享内存 + 锁 共享内存 + 锁

goroutine 背后是 GMP 调度模型：G 是 goroutine，M 是 OS 线程，P 是逻辑处理器（数量等于 GOMAXPROCS）。Go 运行时自己实现了用户态调度器，把海量 goroutine 复用到少量 OS 线程上，多个 P 各自绑定一个 M，从而实现真正的多核并行。

这也是 Go 和 Java 最根本的路线差异。Java 默认把你丢进共享内存 + 锁的世界（synchronized、ConcurrentHashMap），写对之前得先做竞态分析；Go 希望你把”共享数据”改写成”传递数据”。

⚠️ 别理解成”Go 里不用锁”。多个 goroutine 改同一份内存当然要 sync.Mutex（下一篇 13 专讲），但能用消息传递解决的，就别去共享内存。

12.2 channel：一条有类型的管道

Java 里你熟悉 BlockingQueue；Go 的 channel 更像一条没有缓冲的传送带。

无缓冲 channel：必须同时就绪

无缓冲 channel 的语义是 rendezvous（同步交接）：发送方和接收方必须同时准备好，通信才真正完成。

两个直接后果：其一，channel 同时是同步原语，一次收发完成一次 happens-before 同步，不用额外加锁；其二，无缓冲 channel 把并发度压到 1——多个 worker 共用一条无缓冲 channel 读任务时，实际永远只有一个 worker 在交接，想提高并发度就得用有缓冲 channel。注意 make(chan int) 默认无缓冲，而 Java 的 ArrayBlockingQueue 要指定容量、满了才阻塞，这是两个库默认值上的经典差异。

channel 操作速查表

操作 代码 语义
创建（无缓冲） ch := make(chan int) 收发必须同时就绪
创建（有缓冲） ch := make(chan int, 10) 容量 10，满了发送才阻塞
发送 ch <- v 无接收方或缓冲满时阻塞
接收 v := <-ch 通道空时阻塞
接收并判关闭 v, ok := <-ch ok == false 表示已关闭且排空
遍历 for v := range ch 通道关闭后循环自动结束
关闭 close(ch) 只应由发送方调用，重复 close 会 panic
只发 / 只收 chan<- int / <-chan int 编译期限制方向
元素数 / 容量 len(ch) / cap(ch) 当前几个 / 总共能装几个

12.3 关闭 channel：谁发送，谁负责关

三条必须背下来的规则：

规则一：关闭后接收立刻返回，不再阻塞。

ok 和 map 取值的 v, ok := m[k] 一模一样，用来区分”收到一个恰好是零值的元素”和”通道已关闭”。关闭后每次接收都立即返回零值，不看 ok 就会陷入无限循环。

规则二：重复 close 会 panic（panic: close of closed channel）；规则三：向已关闭 channel 发送会 panic（panic: send on closed channel）；close(nil) 同样 panic。

这三条 panic 有个很坑的共同点：发生在非 main goroutine 里，整个进程会挂掉——Go 里任何未被 recover 的 panic 都会终止程序。谁负责 close 必须在设计时定死。关闭 channel 也不是强制义务，只有当你需要明确告诉接收方”不会再有新数据了”时才 close。

12.4 select：同时等多个 channel

行为规则：没有 case 就绪时 select 阻塞；多个 case 同时就绪时选一个是随机的（伪随机，不是源码顺序）；ok 的含义和普通接收一致，用来识别”这个 channel 已被关闭”。

default：把 select 变成非阻塞

这是 Go 里实现”轮询 / 非阻塞尝试“的标准写法，比 Java 的 queue.poll() 多一层含义：Java 的 poll() 是”取一个元素”，Go 的 default 是”这一轮什么都没等到“。

陷阱：select 里的 channel 表达式每次进入都重新求值

select 每次进入语句时，会按源码顺序把 case 里的 channel 表达式各求值一次。所以 case v := <-nextChan(): 写在 for 循环里，每轮都会重新调用一次 nextChan()——你可以在循环里安全地”换一条通道”，但也别在 case 里写有副作用的函数，它的执行次数比你以为的多。

顺带一提，time.After 每次调用都会新建一个定时器且不会提前释放，循环里要用 time.NewTimer + Stop/Reset 复用。

12.6 有缓冲 channel：削峰与任务队列

make(chan int, 10) 表示能装 10 个元素。此时发送缓冲没满就立即返回、满了才阻塞；接收有货就立即返回、空了才阻塞。所以有缓冲 channel 是天然的生产者—消费者队列，用来削平突发流量。

对比无缓冲：有缓冲时生产者可以一口气塞 100 个任务然后继续干活，解耦程度更高，代价是失去了”必须有人接”的同步语义。

三个细节：缓冲大小 = 任务总数，生产者一次塞完不会阻塞；**close(jobs) 必须在所有任务发完之后；close(results) 放在 wg.Wait() 之后**，因为只有所有 worker 退出后才不会再有写入。

12.7 方向化 channel：把 API 设计成最小权限

好处很直接：在编译期就挡住误用。只想收数据的函数拿到 chan<- int 是编译错误，根本没法偷偷往里写。

方向化 channel 还能表达”这个函数会关闭它“：接收方向的 <-chan int 不能被 close()，编译期就报”cannot close receive-only channel”。所以”只收”这个类型本身就说明了”关闭权不在你手上”。配合 context 是 Go 服务端的标准形态：

12.8 传结构体，还是传切片 + 完成信号

最容易搞错的一点：通过 channel 发送一个 slice，只复制了 slice 头（指针 + 长度 + 容量），底层数组还是同一块。

所以传切片时，要么接收方只读不改，要么发送前显式复制一份。选结构体还是选切片，标准很朴素：这个数据在下游会被改吗？ 会改且上游还要用就传值复制，不会被改就传切片省内存。

12.9 goroutine 泄漏：看不见的线程杀手

goroutine 泄漏指的是：goroutine 永远等不到结果而卡住，栈和内存一直不释放。可怕之处在于——进程不报错、不崩溃，只是内存一路涨，最后 OOM。

四类典型写法：向无缓冲 channel 发送但对方可能不读了（发送方永久阻塞，加缓冲或 select + ctx.Done()）；**for v := range ch 但发送方忘了 close（接收方永久阻塞，补上 defer close(ch)）；消费者提前 return 而生产者还在发（生产者永久阻塞，需要 quit channel / context 取消）；defer close(ch) 写在 if 之后**（提前 return 的路径没注册 defer）。

defer 写错位置是最高频的一种——defer 只在它所在那行被执行时才注册：

✅ 正确做法是把 defer close(ch) 紧跟在 make 后面，也就是一进函数就注册。

Go 没有 kill goroutine 的办法（不能像 Java 那样 interrupt 线程），取消的唯一标准姿势是协作式取消：传一个 context.Context 或 quit channel，goroutine 在阻塞点用 select 同时监听”数据”和”取消”两个信号。排查泄漏也有现成手段：给进程发 SIGQUIT（或按 Ctrl+\），Go 运行时会把所有 goroutine 的栈打到日志里，栈顶停在哪个 channel 操作上一目了然。

12.10 动手练

  1. 手写 rendezvous：两个 goroutine 用无缓冲 channel 完成 5 次交接；再改成容量 1 的有缓冲，用 time.Sleep 制造不同时序，观察输出顺序变化并解释原因。
  2. 实现带超时的取数：用 select + time.NewTimer 实现 fetchWithTimeout(ch, d)，超时返回 error。**不要用 time.After**，再故意把 timer 放进循环跑 1000 次，用 runtime.NumGoroutine() 观察差异。
  3. 复现并修掉泄漏：producer 往无缓冲 channel 发送 10 条，consumer 只收 3 条就返回，观察 producer 卡在哪；再用 quit channel 修好它。
  4. 把共享内存改成 channel：先用 sync.Mutex 保护 map[string]int 实现计数，再用 channel + 单个 goroutine 持有 map 重写一遍，对比两者的代码行数。

12.11 常见错误清单

❌ 错误写法 后果 ✅ 正确做法
close(ch) 写了两次 panic，进程退出 只由发送方 close 一次
向已关闭 channel 发送 panic，进程退出 用 select + quit channel 协调生命周期
v := <-ch 后不看 ok 关闭后死循环拿零值 用 v, ok := <-ch 或 for range
defer close(ch) 写在错误分支之后 提前 return 时漏关 defer 紧跟创建语句
以为 ch <- v 发送的是深拷贝 切片底层数组共享 发送前 copy 一份
循环里用 time.After 定时器堆积，隐性泄漏 复用 time.NewTimer + Reset

最后再强调 Go 并发的三条底层原则，面试被追问时按这个顺序答：一，不要用共享内存 + 锁去实现本可以用 channel 表达的数据流；二，每个 channel 都要有明确的关闭者，通常就是发送方；三，每个 goroutine 都要有明确的退出路径，靠 channel 关闭、context 取消或 quit channel。把这三条落实到代码里，goroutine 泄漏和”偶发卡死”这类问题基本就消失了大半。下一篇我们会把共享内存那条路补完：sync.Mutex、sync.WaitGroup 和 go test -race 怎么用。
