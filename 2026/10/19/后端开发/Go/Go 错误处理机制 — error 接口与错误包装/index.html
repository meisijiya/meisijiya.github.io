06 Go 错误处理机制

Go 为什么没有异常？error 到底是个什么东西？一次讲清 error 接口、错误包装链、errors.Is/As 以及 panic 的边界。

6.1 error 接口：把错误当成一个普通值

于是 var err error = &MyError{Code: 1001} 就合法了。error 是值，不是”异常”：可以比较、可以当普通字段塞进结构体、可以放进 map 当值。Go 的错误处理哲学就是一句：错误是数据，不是控制流。

strconv.Atoi("42b") 返回的错误打印出来是 strconv.Atoi: parsing "42b": invalid syntax，天然分三层：函数名 → 动作 → 底层原因。分层信息是 Go 错误信息的典型形态，6.5 节的包装链会看到它的威力。

6.2 错误永远是最后一个返回值

惯例签名

三原则：error 放最后一个返回值；成功返回 nil；失败时结果值返回零值。命名返回值也合法，但一个团队里要么全用要么全不用。

为什么 Go 没有异常

不是能力缺失，是明确的设计取舍：

  • 控制流：异常抛出即中断栈帧；Go 的错误只是一个返回值，控制流不中断
  • 处理权：栈上任意一层的 catch 都能截获；Go 里只有直接调用方能决定
  • 漏处理：Java 受检异常编译期报错；Go 漏写 if err != nil 编译器不拦，但一眼能看出来

代价是啰嗦，收益是失败路径永远可见。Java 用受检异常做补偿，但那只在 Java 世界里成立——跨语言调用、函数式接口、goroutine 里统统失效。

if err != nil 的几种写法

第 3 种只适用于”确实没有补救手段”的调用，比如 Close——绝不要用 _ = err 吞掉真正的错误。

6.3 创建错误：errors.New 与 fmt.Errorf

只能传字面字符串，没有格式化能力，内部类型是 *errors.errorString。用在错误信息固定不变时。

可以带格式动词，关键能力是能用 %w 包装下层错误，把链条续上。

怎么选：信息固定用 errors.New，含动态数据用 fmt.Errorf，要保留底层错误必须用 %w，要给上层一个可比较的”哨兵”就定义包级 var ErrXxx = errors.New("...")。

哨兵错误就定义在包级，比如 var ErrNotFound = errors.New("record not found")；在 Get 里用 errors.Is(err, sql.ErrNoRows) 判断底层错误，命中就 return nil, ErrNotFound，把底层错误转成本包自己的语义。标准库里到处是这个模式：io.EOF、os.ErrNotExist、sql.ErrNoRows。它们都是包级变量，**用 errors.Is 比较，不要用 ==**。

哨兵错误的软肋：调用方只知道”是这一类”，拿不到”到底为什么”——哪个用户、哪个字段出错。需要携带数据就得用自定义错误类型。

一个高频坑：typed nil

沿用 6.1 的 MyError：

e 的类型是 *MyError、值是 nil。赋给 error 接口后，接口的动态类型是 *MyError、动态值是 nil——接口本身 不等于 nil。于是 if err != nil 判成”有错”，调 err.Error() 还会空指针解引用。**修法是 nil 时显式 return nil**。

面试高频题。记住：返回 error 时，绝不要返回一个”nil 的具体错误类型的指针”。

三个标准库函数

errors.Is / errors.As 沿着整条链往下找，中间包了几层都不影响——所以 errors.Is(err, io.EOF) 能认出任意层包装出来的文件末尾。两个坑：errors.As 的第二个参数必须是指针，且指向的类型要实现 error，否则 errors.As 自己会 panic——传 &ve 而不是 ve；errors.Is 的 target 不可比较时不会 panic。

避免错误信息重复

包装最常见的翻车是信息重复：底层说了 db: connection refused，上层又包一层 query users failed，就成了 query users failed: db: connection refused。

规则：每一层只补自己这一层独有的信息。 底层错误通常是技术细节，上层包装该补的是业务语义：

6.7 panic 与 recover 的边界

panic 会中断当前 goroutine 的正常执行，沿调用栈向上展开，触发栈上所有 defer 里的 recover；没人 recover 就打印堆栈并以非零状态退出。

什么时候可以用

  1. 程序初始化阶段的致命失败：配置文件读不到、数据库连不上——log.Fatal 或 panic 都合理。
  2. 不可恢复的内部状态被破坏，或者干脆是编程错误（bug）：给一个明确不允许 nil 的参数传了 nil，继续执行只会让错误更大。

什么时候不该用

任何”外部输入可能不合法”的情况都不该用 panic。 用户输入是正常业务的一部分，用 panic 处理它等于把用户的错误请求升级成服务崩溃。库代码更不要用 panic 做常规错误处理，调用方可能压根没写 recover。

recover 只在 defer 里有效

recover() 必须在被 panic 的那个 goroutine 的 defer 函数里直接调用才有效，包一层函数再调无效；它也只能救当前 goroutine，别的 goroutine 里的 panic 抓不到。Go 1.21 起 panic(nil) 会被转成 *runtime.PanicNilError，别拿它传信息。

HTTP 中间件里 recover 是合理的（别让一个请求打挂整个服务），但必须记录日志并带上堆栈、返回 500 而不是假装成功。

捕获方式 if err != nil try/catch/finally try/except/finally
中断控制流 否 是 是
错误链 %w + errors.Is/As initCause / getCause raise ... from ...

同一段”查用户、查不到就报业务错、查崩了补上下文”的逻辑，Java 用 try/catch + orElseThrow，Python 用 try/except + raise ... from e，Go 用返回值 + %w。逻辑完全一样，差别只在表达方式。
