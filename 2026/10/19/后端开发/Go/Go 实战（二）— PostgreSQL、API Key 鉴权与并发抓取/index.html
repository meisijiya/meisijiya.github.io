16 Go 实战（二）— PostgreSQL、API Key 鉴权与并发抓取

前一篇把路由和中间件的骨架搭了起来，这一篇把它接到真实的 PostgreSQL 上：迁移、代码生成、API Key 鉴权、并发抓取入库，一次串通。

16.1 数据模型：四张表撑起整个聚合器

用户注册后拿到一把 API Key，用 Key 订阅若干 RSS 源，后台定时并发抓取，文章存进库。四张表的关系，决定了后面所有代码的形状。

16.1.1 先看关系图

两条从 USERS 出发的线语义不同：USERS → FEEDS 是谁登记了它，USERS → FEED_FOLLOWS → FEEDS 是谁订阅了它。

16.1.2 四张表的 DDL

数据库用 PostgreSQL，迁移文件由 goose 管理：数字前缀决定执行顺序。

16.1.3 表结构速查

表 作用 关键约束 设计理由
users 用户主体 api_key_hash 唯一 一人一把 Key，摘要唯一即可
feeds 被登记的订阅源 (user_id, url) 唯一 同一人不能重复登记同一地址
feed_follows 订阅关系中间表 (user_id, feed_id) 唯一 多对多的标准落地方式，天然防重复订阅
posts 抓取到的文章 (feed_id, link) 唯一 反复抓取时重复文章被唯一约束挡住

16.1.4 为什么订阅关系必须单独一张表

把订阅关系塞进 users 表、加一个 feeds UUID[] 数组列也能跑，但一旦要回答「谁订阅了源 X？」，数组列就没法建反向索引。多对多中间表是标准答案：把「关系」当成一行来存，于是它有了主键、创建时间、可以被索引、被唯一约束保护。Java 对应 @ManyToMany。

16.2 迁移与代码生成：goose 管版本，sqlc 管类型

手写 database/sql 的查询，Scan 的目标类型和 SQL 里的列类型之间没有任何编译期检查。sqlc 的答案是——你写 SQL，它反推出类型安全的代码。

16.2.1 goose：把 schema 变成有版本的历史

命令形态是固定的四段：goose -dir <迁移目录> <驱动> <连接串> <子命令>。三个必须知道的细节：数字前缀决定顺序（要补齐位数）；已执行过的文件不要改，goose 只记版本号；up 是幂等的。

16.2.2 sqlc：从 SQL 反推出类型安全的 Go 代码

sqlc 的输入是 schema（表结构）和 queries（查询语句），输出是 Go 代码。查询语句要用 -- name: 注释声明名字和返回类型：:one 一行，:many 多行，:exec 无结果集。比如 -- name: GetUserByAPIKeyHash :one 后面跟一条 SELECT id, name, created_at FROM users WHERE api_key_hash = $1; 就行。

最关键的是 overrides：PostgreSQL 的 uuid 默认映射成 pgtype.UUID，不写 override 就会到处是这种噪音。sqlc compile 只校验 SQL，放进 CI 能报出「引用了不存在的列」。

16.2.3 为什么要 sqlc，而不是手写 SQL 或上 ORM

核心理由只有一条：Go 里没有一个像 JPA 那样被广泛接受的一等公民 ORM。GORM 是最接近的，但反射和魔法方法太多。sqlc 反过来走：你写 SQL，工具补类型。

16.2.4 目录约定：生成物锁进 internal

sql/schema 是表结构的唯一真相源，goose 执行它、sqlc 读它推导类型；生成物放在 internal/ 下，只能被本模块内代码导入；不要手改。

16.3 API Key 鉴权：把一把密钥变成用户身份

接口分两类：创建用户是公开的，其余都要证明「你是谁」。这里不用 JWT：这是服务端给自己客户端用的场景，一把可随时吊销的随机密钥就够了。

16.3.1 请求头格式与解析

约定请求头是标准的两段式：Authorization: ApiKey <key>。解析函数放在 internal/auth，不依赖任何 HTTP 框架，只吃 http.Header：

strings.Cut 一次切出两段；strings.EqualFold 做大小写不敏感比较——HTTP 的认证方案名按规范就不区分大小写。

语言 表达「可能失败」的方式 典型写法 调用方怎么接
Go 返回值 error func GetAPIKey(h http.Header) (string, error) key, err := ...; if err != nil { ... }
Java 抛异常 throw new IllegalArgumentException("...") try { ... } catch (IllegalArgumentException e) { ... }
Python 抛异常 raise ValueError("...") try: ... except ValueError: ...

16.3.2 数据库里只存摘要

明文存 API Key 绝对不能做：库被拖走、备份泄露、日志被打出来，密钥就等于公开了。所以库里存 SHA-256 摘要。

密钥本身用 crypto/rand 读 32 字节随机数，再用 base64.RawURLEncoding 编码（放进 HTTP 头里不用转义）。为什么用 SHA-256 而不是 bcrypt/Argon2？ 用户密码熵很低、可以被离线爆破，必须用慢哈希；API Key 是随机数，穷举空间是 $2^{256}$。用慢哈希保护高熵随机密钥，是把慢哈希用错了地方。

16.3.3 中间件与 context 传递

中间件是「装饰器」在 Go 里的样子：func(http.Handler) http.Handler，收到请求时先干活，再决定要不要往下传。context.Context 和 Java 的 ThreadLocal 是一家人，但有两条硬性约定——不要存进结构体字段，只放请求范围的元数据。取用户用 r.Context().Value(ctxKeyUser) 断言即可。

16.3.4 401 响应的约定

错误响应统一一个结构：状态码 + {"error":{"message":"..."}}。鉴权失败一律返回 401 Unauthorized，并且不透露具体原因：没带头、头格式不对、Key 不存在、数据库故障，全是同一个响应体。

16.4 订阅关系接口：多对多的写入与读取

有了鉴权，接口就能按用户维度工作了。先把 API 清单列出来，写代码时对着它实现。

16.4.1 API 清单

方法 路径 需要鉴权 请求体 成功状态 说明
POST /v1/users 否 {"name":"..."} 201 创建用户，响应里一次性返回明文 API Key
POST /v1/feeds/follows 是 {"feed_id":"..."} 201 订阅一个已登记的源
GET /v1/feeds/follows 是 - 200 列出我订阅的源（分页）
POST /v1/scrape 是 - 202 手动触发一次抓取
GET /v1/posts 是 ?limit=&offset= 200 列出我订阅源上的文章

订阅关系的写入用一条带 RETURNING 的 INSERT 就够了：INSERT INTO feed_follows (id, user_id, feed_id) VALUES ($1, $2, $3) RETURNING id, user_id, feed_id, created_at;，在 sqlc 里标成 -- name: CreateFeedFollow :one。

16.4.2 创建订阅：把唯一约束冲突翻译成人话

判断唯一约束冲突，用 PostgreSQL 驱动返回的错误码：

errors.As 是 Go 1.13 之后的标准做法：沿着错误链往上找，找到第一个能装进目标类型的错误就停下。pgErr 是指针类型，&pgErr 是 **pq.Error。

别写「先查一遍再插」。两个请求同时查到「不存在」然后同时插入，就出现了重复。正确姿势是让唯一约束裁决，冲突了翻译成 409。

16.4.3 查询我的订阅与模型转换

查询逻辑和创建对称：从 context 取用户 → 调 sqlc 生成的 ListFeedFollows（一条 feed_follows JOIN feeds 的查询）→ 逐行转成业务结构体 → 返回。

转换层要单独一层，因为 sqlc 生成的 database.FeedFollow 是贴着数据库表的：列名变了它就变，直接当响应体返回，等于把数据库结构公开成了 API 契约。所以另定义业务结构体 FeedFollow 带 json tag。

另外 make([]FeedFollow, 0, len(rows)) 更稳：序列化成 [] 而不是 nil。业务模型（models.go）决定对外吐什么字段。

16.5 RSS 解析与并发抓取

接口能读能写了，接下来是聚合器的核心：把订阅源里的文章抓回来存进库。

16.5.1 gofeed 解析

RSS/Atom 的解析用 github.com/mmcdole/gofeed：parser.ParseURL(url) 返回 *gofeed.Feed，失败用 fmt.Errorf 包装一层错误。

两个必踩的坑：Feed.Items 才是正规入口，老的 Feed.Channel 是历史遗留字段；PublishedParsed 可能为 nil，用 time.Now().UTC() 兜底。Description 带 HTML，直接塞进前端会出 XSS。

16.5.2 用 WaitGroup 编排抓取任务

抓取是典型的 IO 密集型任务：大部分时间在等网络。Go 的 goroutine 就是为这种场景准备的。

四个必须讲清楚的点：**wg.Add(1) 必须在 go 之前——写在 goroutine 内部的话，主协程可能在 Add 执行前就跑到 wg.Wait()，任务全丢，这是 Go 并发里最经典的竞态；Go 1.22 起 for range 的循环变量每轮新建，把 feed 作为参数传给 goroutine 已经不是必需；信号量用带缓冲的 channel** 实现。

语言 并发单元 等待全部完成 限制并发数
Go go 关键字 sync.WaitGroup 带缓冲 channel 当信号量
Java ExecutorService invokeAll 固定大小的线程池
Python ThreadPoolExecutor as_completed 池大小参数

goroutine 比线程轻量得多（初始栈只有几 KB），Java 的线程是 OS 线程，开多了是几 GB 栈。

16.5.3 抓到的文章要入库

只 log.Printf 打印出来是最常见的「看起来做完了」——数据没落库，接口查出来还是空的。入库要用 Upsert，因为同一个源会被反复抓取：

ON CONFLICT (feed_id, link) DO UPDATE 依赖 posts 表上的唯一索引。冲突时更新标题和摘要，但**保留原来的 id 和 published_at**。

错误处理是分层的：单篇文章失败 → 跳过继续；单个源失败 → 记日志返回；整体不因任何一个源失败而中断。定时调度用 time.Ticker 加 select，进程退出时 context 一取消就返回。

16.6 分页查询：offset 的坑与游标解法

「列出我的文章」这个接口必然要分页。分页怎么做，差别比看上去大得多。

16.6.1 limit/offset 到底慢在哪

这段 SQL 语法没问题，但有两个隐蔽的坑。第一，深分页会越来越慢：OFFSET 100000 是「先产出 100000 行再扔掉」，数据库仍要扫过并排序。第二，翻页期间数据在变会重复或漏看：第一页查完、第二页还没点时来了 10 篇新文章，OFFSET 20 就会把原来第 21 条挤到第 31 条。

16.6.2 游标（keyset）分页

游标分页的思路是：不告诉服务器「跳过前 N 条」，而是告诉它「从这一条之后开始」。

(p.published_at, p.id) < ($2, $3) 是 PostgreSQL 的行值比较，等价于 p.published_at < $2 OR (p.published_at = $2 AND p.id < $3)，但只写一遍，索引也能用。为什么要带 id 这个第二排序键？因为排序必须唯一——两篇文章 published_at 相同时，只按它排，边界就会漏掉或重复某条。

游标一般是把 published_at 和 id 拼起来做 base64 编码，客户端原样回传。为了让查询走索引，还要追加一个迁移文件建 (published_at DESC, id DESC) 的索引。数据量小、页数少时用 offset 最省事；数据量上来后，尤其是无限滚动的信息流，游标才是稳妥选择。

16.6.3 参数化查询：注入问题从根上消失

回头看 16.6.1 那条 SQL，参数是 $1 $2 $3，值从来不和 SQL 文本拼在一起，这是防注入的唯一可靠办法。用 sqlc 之后更省心：生成的代码里不存在拼字符串的机会，参数是传值，注入在物理上不可能发生——而手写 fmt.Sprintf 拼 SQL，塞个单引号就能被注入。Java 用 PreparedStatement 的 ? 占位符，Python 用 DB-API 的参数元组；区别在于 Go 手写拼 SQL 是合法语法，编译器不会拦你。

16.7 从零跑通全流程

前面讲的都是片段，这一节把它们串成一条能跑的完整命令序列。

16.7.1 环境与依赖

.env 放配置和密钥，**一定要加进 .gitignore**：PORT=8080 和 DATABASE_URL=postgres://postgres:postgres@localhost:5432/rssagg?sslmode=disable。

16.7.2 建库、迁移、生成代码

第 3 步之后 internal/database 下就会多出 db.go、models.go 和几个 *.sql.go。第一次生成时你大概率会看到编译错误 cannot use "xxx" (untyped string constant) as uuid.UUID value，这不是 bug，是 overrides 没配。

路由装配和上一篇一致：公开的 POST /v1/users 挂在根路由上，受保护的放进 r.Group(func(r chi.Router) { r.Use(app.authMiddleware); ... })。

16.7.3 灌数据

这里的 url 只是示意，实际填一个完整的、带协议头的 RSS 地址（http 或 https 开头），只给域名 ParseURL 解析不了。再订阅一次会返回 409 和 already following this feed，这就是唯一约束在起作用。

16.8 上线前的检查清单

能跑通和能上线之间隔着一堆「不出事看不出来」的配置，下面这四项最容易漏。

16.8.1 连接池

database/sql 自带连接池，但默认值对生产环境往往不合适：

MaxOpenConns 不设的话默认无限，突发流量直接打爆数据库连接，报 too many connections。先算 PostgreSQL 那边 max_connections 的总数，再按实例数分摊。ConnMaxLifetime 用来应对中间件掐掉长连接，取 5 分钟左右即可。

16.8.2 超时

没有超时的 http.Client 是最常见的资源泄漏源。 一个卡住的对端能让 goroutine 一直挂着，几千个之后内存和文件描述符就都满了：

数据库查询也要带超时，否则一条慢 SQL 能把连接池占满：拿到 r.Context() 之后套一层 context.WithTimeout(ctx, 3*time.Second) 再传给 sqlc 的查询方法即可。

16.8.3 优雅关闭

进程收到 SIGTERM 时应该做三件事：停止接收新请求、等待在途请求做完、关掉数据库连接。http.Server.Shutdown 就是干这个的：

Shutdown 会关闭监听器、等待所有活跃连接空闲。如果超过 10 秒还没结束，context 超时，进程被强制退出——优雅关闭是「尽力而为」，不是「保证完成」。

16.8.4 限流

限流有两层含义。对内是保护自己的服务不被单个客户端打爆，按 API Key 维度做令牌桶限速（golang.org/x/time/rate），超限返回 429。对外是抓取别人的 RSS 源时要「礼貌」：加 User-Agent、限并发、失败退避重试。

16.9 动手练

练习一：加一个「重置 API Key」接口。 新增 POST /v1/users/me/api-key，生成新密钥、更新 api_key_hash、返回新的明文 Key。验收：旧 Key 立刻失效，新 Key 可用。

练习二：给抓取加重试与退避。 单个源抓取失败时最多重试 3 次，间隔依次为 1s、2s、4s；三次都失败就标记该源为失败状态（给 feeds 加 last_error 列）。验收：把某个源的地址写错，日志里能看到 3 次重试，其它源照常入库。

16.10 常见错误清单

下面是实际写这类项目时最容易踩的坑，按「症状 → 原因 → 修法」整理。

症状 真正的原因 修法
goose up 报版本已执行，但表还是老的 改了已执行过的迁移文件内容，goose 只记版本号不记内容 已执行的迁移永不改，追加新文件；开发期用 reset 推倒重来
sqlc generate 后编译报类型不匹配 overrides 没配，数据库的 uuid 被映射成了驱动类型 在 sqlc.yaml 里加 uuid → uuid.UUID 的 override
明明带了正确的 Key 却一直 401 入库时存了明文，查询时按摘要查 统一走 auth.HashAPIKey，库里只存摘要
重复订阅时插入了两条 没加 UNIQUE(user_id, feed_id)，或者只靠「先查再插」 加唯一索引，靠数据库裁决，冲突转 409
抓取一次后文章越来越多 posts 没有 (feed_id, link) 唯一约束 加唯一约束 + ON CONFLICT DO UPDATE
抓取任务「偶尔」丢一两个源 wg.Add(1) 写在了 go 语句里面 wg.Add(1) 必须在 go 之前
整个进程被一个源的异常带崩 goroutine 里的 panic 不会被主协程的 recover 捕获 每个 goroutine 内部自己 defer recover()
翻到第 50 页要等好几秒 OFFSET 让数据库扫过并丢弃前 50 页的数据 换游标分页，并建 (published_at, id) 索引
数据库报 too many connections 没设 SetMaxOpenConns，或者进程起了太多副本 按 max_connections 反推每个实例的池大小
接口返回 null 而不是 [] 切片是 nil make([]T, 0, len(rows)) 初始化
抓取时个别文章没有发布时间 源本身没写时间，PublishedParsed 是 nil 用抓取时间兜底

最后一条单独强调一下：**published_at 是 NOT NULL 列**，不做 nil 判断就 INSERT，会得到一个「插入失败但错误信息很奇怪」的现象。
