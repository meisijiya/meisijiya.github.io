1. APP 弱网测试是怎么做的？

🎬 面试现场

面试官（口语化）：APP 弱网测试一般怎么开展？

⚠️ 翻车点

最容易答偏的是只答”用 Charles 模拟”却答不出三种测试方法的分工：工具模拟（Network Link Conditioner/Charles/Fiddler）、真实网络测试（地铁/地下停车场等）、自建弱网实验室。另一个坑是答不出弱网下关注的核心指标（响应时间、请求超时次数、丢包率、断网重连时间等），只说”看能不能用”。

📝 现场作答

APP弱网测试主要是为了验证应用在各种网络环境下的稳定性和性能。实现这一目的通用的方法有以下几种：

1）使用网络模拟工具：例如Network Link Conditioner（iOS）、Charles、Fiddler等工具，可以模拟不同类型的弱网络环境，比如高延迟、低带宽、丢包等。

2）实际网络测试：将测试设备连接到现实中不同的网络环境进行测试，如地铁、地下停车场、电梯等信号不稳定的地方。

3）自建测试环境：搭建专业化的网络测试环境，利用路由器、网络调制器等硬件设备模拟各种复杂的网络状况。

通过这些方法，可以考查APP在弱网环境下的响应速度、数据传输的可靠性、用户体验等方面的问题，帮助优化APP的网络性能。

扩展知识

1）网络模拟工具的优劣

Network Link Conditioner：这是iOS设备提供的一个功能，能模拟多种网络状况，例如3G网络、高丢包率环境等。适用于开发过程中专门针对iOS设备的测试。
Charles和Fiddler：这两个都是跨平台的网络调试工具，不仅能模拟网络状况，还能监控并修改HTTP请求，非常适合调试和排查问题。

2）实际网络测试的重要性

虽然模拟工具非常方便，但现实中的网络环境更加复杂多变。实际网络测试可以捕捉到模拟工具难以再现的问题，例如瞬间断网、邻频干扰等。地铁、地下停车场等地方的测试不仅验证了APP在弱网环境中的稳定性，也能发现用户在真实使用过程中容易遇到的问题。

3）自建测试环境与自动化

对于大型企业或专业测试机构，可以考虑建设专门的弱网实验室，引入高端设备模拟各种复杂网络场景。
自动化测试脚本也是一个重要方面，可以写脚本定期运行，在不同的网络环境下测试核心功能，及时捕捉到新版本可能引入的问题。

4）相关性能指标

在弱网测试过程中，主要关注以下几个指标：响应时间、请求超时次数、数据包丢失率、断网重连时间、页面加载速度、用户操作流畅度等。这些指标有助于全面评价APP的网络性能。

5）优化建议

根据测试结果，可以采用一些性能优化方法，比如数据压缩、请求合并、缓存策略优化、使用更高效的传输协议如HTTP/2等。这些优化措施能有效提升APP在弱网环境下的表现。

2. APP 的性能测试是怎么做的？

🎬 面试现场

面试官（口语化）：你们 APP 上线前是怎么做性能测试的？能说说整套流程吗？

⚠️ 翻车点

最容易答成「装个工具跑一下就完了」。APP 性能测试是有固定流程的：先需求分析、再设计方案、搭建环境、执行测试、监控收集、分析报告，少一步都算没答全。另外把 JMeter、LoadRunner、Appium 混为一谈也容易被追问——JMeter 主要负载/性能测试，Appium 主要移动端自动化，不是一回事。

📝 现场作答

  • APP 性能测试是对移动端应用使用过程中各项性能指标进行测量和评估的过程，指标包括响应时间、处理能力、吞吐量、资源使用情况（CPU、内存、电池等）和稳定性（崩溃率、错误率等）。
  • 主要步骤：
    1. 需求分析：明确目标（提高响应速度、优化内存使用等），写出具体性能测试需求。
    2. 设计测试方案：确定测试环境、测试工具、测试数据和测试用例。
    3. 建立测试环境：在接近真实条件下搭建，包括多种设备、操作系统和网络条件。
    4. 执行测试：使用自动化测试工具如 JMeter、LoadRunner、Appium 等执行测试。
    5. 监控和收集数据：实时监控系统性能，记录 CPU、内存、电池等资源使用、响应时间等关键指标。
    6. 分析和报告：对数据进行分析，编写详细报告，提出优化建议和改进措施。
  • 工具：
    • JMeter：开源免费，主要负载测试和性能测试，模拟多用户对 web 应用、数据库等的请求，支持 HTTP、FTP、JDBC 等多种协议，扩展性强，可编写自定义插件。
    • LoadRunner：商业化软件，负载测试和性能测试，功能强大但成本较高，支持多种应用协议，提供详细的性能监测和分析。
    • Appium：开源，主要移动端自动化测试（功能和性能），支持 Android 和 iOS，基于 WebDriver 协议，可集成到 CI/CD 流程。
  • 最佳实践：
    1. 模拟真实环境：在实际网络条件、多种设备型号和操作系统中测试。
    2. 持续监控：测试期间及生产环境中持续监控，及时发现和解决性能问题。
    3. 优化迭代：测试发现问题-解决问题-再次测试-再次优化，持续重复。
    4. 负载极限测试：除常规负载测试外，进行极高负载下的极限测试，对稳定性很重要。

💡 主动加分的追问准备

面试官追问 你的答案
JMeter 和 LoadRunner 选哪个？ JMeter 开源免费、扩展性强；LoadRunner 商业化、功能强大但成本高，支持多种应用协议并提供详细监测分析。选型看预算与协议需求。
为什么要做负载极限测试？ 除了常规负载测试，还在极高负载下看系统表现，这对稳定性非常重要。

❌ 千万别说的话

  • “APP 性能测试就是装个工具跑一下。” —— 实际有需求分析、设计方案、环境搭建、执行、监控收集、分析报告六步。

3. 如何测试 APP 的内存使用情况？

🎬 面试现场

面试官（口语化）：你们怎么测 APP 的内存占用和泄漏？有几种路子？

⚠️ 翻车点

答成「看一眼任务管理器」会被追问细节。内存测试有三条路：开发者工具、第三方工具、手动查看。Android 和 iOS 的工具名别混：Android Studio 用 Profiler，Xcode 用 Instruments；泄漏检测 Android 用 LeakCanary，iOS 用 MemoryGraph。

📝 现场作答

  • 测试 APP 内存使用情况的三种方式：
    1. 使用开发者工具：大多数移动端开发平台内置性能分析工具，包括内存使用分析工具。Android Studio 使用 Profiler，Xcode 使用 Instruments。
    2. 第三方工具：LeakCanary（Android）或 MemoryGraph（iOS）。
    3. 手动测试：某些情况下用设备自带系统功能手动查看内存使用情况，如 Android 设备开发者模式中的「内存」选项。
  • Android Studio Profiler：
    • 在 Android Studio 主界面底部选择「Profiler」选项卡。
    • 确保测试设备通过 USB 连接开发机器，并在设备上启用开发者选项和 USB 调试模式。
    • 启动 APP 后，在 Profiler 中选择「Memory」选项卡，实时查看内存使用情况，并可创建多次快照查看不同时间点的内存状态。
  • Xcode Instruments：
    • 在 Xcode 中选择菜单「Product」->「Profile」。
    • 在弹出的 Instruments 选择窗口中选择「Allocations」（分配）或「Leaks」（内存泄漏）工具。
    • 启动 APP，在 Instruments 的实时图表上观察内存使用情况，查找泄漏或异常内存占用。
  • 第三方工具：
    • LeakCanary（Android）：开源的检测内存泄漏的库，集成后 APP 发生内存泄漏时会通知并提供详细的泄漏路径。
    • MemoryGraph（iOS）：实时内存使用分析工具，可生成内存使用图表，帮助定位内存泄漏。

💡 主动加分的追问准备

面试官追问 你的答案
Profiler 和 Instruments 的具体操作步骤？ Android：底部 Profiler -> Memory，连接设备并启用 USB 调试，启动 APP 后实时查看并创建快照。iOS：Product -> Profile，选 Allocations 或 Leaks，启动 APP 观察图表。
LeakCanary 和 MemoryGraph 分别用在哪个平台？ LeakCanary 用在 Android，MemoryGraph 用在 iOS。

❌ 千万别说的话

  • “内存泄漏就看任务管理器。” —— 实际要用 Profiler/Instruments 或 LeakCanary/MemoryGraph 等工具定位。

4. 如何测试 APP 的流量使用情况？

🎬 面试现场

面试官（口语化）：APP 流量怎么测？用什么工具抓包？

⚠️ 翻车点

答成「装个代理看一眼」不完整。标准流程是：安装 APP -> 启动网络监测工具 -> 抓包并操作产生流量 -> 分析流量日志 -> 总结记录。还要注意过滤掉广告、Push Notification 等非核心业务流量，聚焦业务场景。

📝 现场作答

  • 测试 APP 流量使用情况的步骤：
    1. 使用模拟器或真实设备安装 APP。
    2. 安装并启动网络监测工具，常见工具有 Charles Proxy、Wireshark 或 Fiddler。
    3. 在工具中启动抓包功能，并进行所需操作以便产生流量，如浏览页面、下载数据等。
    4. 观察并分析工具中的流量日志，过滤掉不相关的数据，重点检查特定时间段内数据使用的具体情况。
    5. 总结并记录结果，确定使用流量的高峰时段和实际流量大小，检测是否符合预期。
  • 扩展知识：
    1. 平台特定工具：Android 设备可用 Android Studio 中的 Network Profiler；iOS 设备可用 Xcode 中的 Network Link Conditioner。
    2. 自动化测试：编写自动化测试脚本，结合 JMeter 等自动化测试工具，模拟真实用户使用情境并捕获详细流量数据。
    3. 云测试服务：BrowserStack、Firebase Test Lab 等云测试服务，提供分布广泛的设备农场，帮助在不同设备、网络条件下进行流量使用测试。
    4. 流量分析技巧：过滤广告、Push Notification 等非核心业务流量，聚焦应用实际业务场景下的流量使用，同时监控后台数据同步、缓存机制等对流量的影响。
    5. 数据加密和隐私：检查 API 请求和数据传输过程中的安全性，确保数据传输是加密的，避免敏感信息暴露，这也是流量分析的一部分。

💡 主动加分的追问准备

面试官追问 你的答案
流量分析时要注意什么？ 过滤广告、Push Notification 等非核心业务流量，聚焦业务场景；监控后台数据同步、缓存机制对流量的影响；检查 API 请求和数据传输的安全性与加密。
有哪些平台特定工具？ Android 用 Android Studio 的 Network Profiler，iOS 用 Xcode 的 Network Link Conditioner。

❌ 千万别说的话

  • “流量测试就是装个代理看一眼。” —— 实际还要抓包操作、分析日志、总结记录，并注意过滤与安全检查。

5. 如何测试 APP 的 CPU 消耗情况？

🎬 面试现场

面试官（口语化）：你们怎么测 APP 的 CPU 占用？步骤和工具说一下。

⚠️ 翻车点

答成「看一眼 CPU 占用率」不完整。流程是：开发者工具/监控软件 -> 连接设备 -> 启动监控 -> 执行测试用例 -> 分析 CPU 使用率 -> 生成报告。Android 与 iOS 工具别混：Android 用 Android Studio Profiler 或 ADB，iOS 用 Xcode Instruments。

📝 现场作答

  • 测试 APP CPU 消耗情况的步骤：
    1. 使用开发者工具或监控软件：Android 用 Android Studio Profiler 或 ADB 工具；iOS 用 Xcode 的 Instruments 工具。
    2. 连接设备：将测试设备（手机或模拟器）连接到开发环境。
    3. 启动监控工具：启动对应开发工具的性能分析功能，选择需要监控的 APP。
    4. 执行测试用例：利用预先设计的测试用例，覆盖 APP 的各个功能模块和操作场景。
    5. 分析 CPU 使用率：通过监控工具查看并记录 CPU 使用率的数据，注意观察高峰值和平均值。
    6. 生成报告：导出监控数据，生成包括 CPU 使用情况的性能测试报告。
  • 扩展知识：
    1. 开发者工具和监控软件：Android 用户 ADB 比较常用，可通过 command line 进行细粒度性能分析，如 adb shell top 查看实时 CPU 消耗；Android Studio Profiler 是图形化工具，提供详细的 CPU、内存、网络等使用情况。iOS 用户 Instruments 提供 Time Profiler 工具，可精准分析方法调用和 CPU 使用情况。
    2. 模拟实际使用环境：尽量在接近用户实际使用场景中进行测试，如连接真实设备而非模拟器、使用具有实际数据的账户进行操作。
    3. 自动化测试：借助 Appium 或 Espresso 等自动化测试框架，更高效执行大规模、重复性测试用例，确保测试覆盖面的完整性和数据的可信度。
    4. 性能优化建议：减少主线程负担，把耗时操作（网络请求、文件读写）放到子线程；优化算法和数据结构；避免频繁的布局重绘，使用缓存机制减少不必要的重绘操作。

6. 如何测试 APP 的 FPS（帧率）？

🎬 面试现场

面试官（口语化）：APP 的帧率你们怎么测？有哪几种方法？

⚠️ 翻车点

答成「装个 FPS 显示器」不完整。三种方法：内置调试工具、第三方工具、代码嵌入。Android 和 iOS 的内置工具名别混：Android Studio Profiler 的 Graphics 选项、Xcode Instruments 的 Core Animation FPS。

📝 现场作答

  • 测试 APP FPS 的三种方法：
    1. 内置调试工具：一些开发平台（如 Android Studio、Xcode）提供了内置工具显示 APP 的 FPS。
    2. 第三方工具：Android 的 Systrace、GPU Profiler，iOS 的 Instruments 等。
    3. 代码嵌入：在 APP 中嵌入 FPS 监控代码，通过在特定时间内计算绘制帧的数量得到 FPS。
  • 内置调试工具：
    • Android Studio Profiler：Android Studio 提供性能分析工具，可实时显示当前 APP 的 FPS，打开「Profiler」窗口，选择「Graphics」选项，可以看到帧率等细节。
    • Xcode Instruments：在 Xcode 中使用 Instruments 工具中的「Core Animation FPS」选项监控 iOS APP 的帧率。
  • 第三方工具：
    • Systrace：针对 Android，分析包括 FPS 在内的许多性能参数，是深度性能分析工具，帮助查找性能瓶颈。
    • GPU Profiler：Android Studio 中的 GPU Profiler 可更详细分析图形性能，适用于复杂的图形应用程序。
    • PerfDog：支持多平台（Android/iOS）的工具，可详细展示 FPS 变化图，具有强大的分析能力。

7. 如何使用 JMeter 进行性能测试？

🎬 面试现场

面试官（口语化）：用 JMeter 做一次性能测试，完整流程怎么走？

⚠️ 翻车点

答成「打开 JMeter 点运行」不完整。标准七步：下载安装 -> 创建测试计划 -> 添加线程组 -> 添加采样器 -> 设置采样器 -> 添加监听器 -> 执行测试。另外 JMeter 不只 HTTP，还支持 JDBC、LDAP、SOAP、FTP、SMTP 等。

📝 现场作答

  • 使用 JMeter 进行性能测试的步骤：

9. 常见的性能测试指标有哪些？

🎬 面试现场

面试官（口语化）：性能测试你最关注哪些指标？能系统说一下吗？

⚠️ 翻车点

📝 现场作答

  • 常见的性能测试指标：
    1. 响应时间：系统从收到请求到完成响应所需的时间，越短说明系统对用户的响应能力越强。
    2. 吞吐量：一定时间内系统能够处理的请求数量或数据量，高说明能处理高并发请求或大量数据传输。
    3. 并发用户数：系统同时处理的用户数，帮助理解系统在高压力下的表现。
    4. 错误率：测试过程中出现的错误请求占总请求的比例，高错误率通常表明系统在高负载下稳定性有问题。
    5. 资源利用率：包括 CPU 使用率、内存使用率、磁盘 I/O 等，反映系统在不同负载条件下的资源消耗情况。
  • 扩展知识：
    1. 延迟（Latency）：和响应时间相似，但通常指网络传输延迟，尤其在分布式系统中网络延迟可能对整体性能有重大影响。
    2. 事务成功率：在负载测试中不仅要查看处理的请求总数，还要关注实际完成的事务数量，如完成一笔交易或一次完整数据处理所需的步骤。
    3. 连接时间：客户端与服务器之间建立连接所需的时间，在高并发场景下过长的连接时间可能形成性能瓶颈。
    4. Jitter：指延时的变动，稳定的延时比起变动不定的延时更容易让系统表现得一致。
    5. 数据库性能指标：包括查询执行时间、缓存命中率、锁定和争用等，对数据密集型应用尤为重要。

  • 扩展知识：
    1. 系统瓶颈：QPS 能帮助找出系统中的瓶颈；如果在高负载情况下 QPS 遇到明显下降，需要考虑是否是因为 CPU、内存、磁盘 I/O 或网络等资源不足，进而采取优化措施。

📝 现场作答

  • 性能测试的执行环境可以通过以下方式确定：
    1. 机房/云服务提供商：确定测试是否在自有机房、第三方机房，还是使用了云服务平台，如 AWS、Azure、Google Cloud。
    2. 硬件配置：包括 CPU、内存、磁盘类型（SSD/HDD）、网络带宽等。
    3. 软件配置：操作系统版本、数据库版本、应用服务器及其相关组件的版本和配置。
    4. 网络环境：是否有负载均衡器、防火墙、路由器等，以及它们的配置。
    5. 测试工具：确定使用的性能测试工具，如 JMeter、LoadRunner，并记录其版本及重要配置。
  • 扩展知识：
    1. 机房/云服务提供商：在不同的物理环境下，硬件和网络资源的稳定性和可预测性会有很大差异；自有机房中的物理服务器一般具备较小的网络延迟，而云环境则有更高的灵活性和扩展性。
    2. 硬件配置：硬件配置直接影响计算能力和存储速度；通常详细记录所使用的 CPU 核数和主频、内存大小和类型、磁盘 I/O 性能等，某些关键应用场景可能更依赖于高速 SSD 的随机读写能力。
    3. 软件配置：软件环境包括操作系统（如 Windows、Linux）、应用服务器（如 Apache Tomcat、Nginx）、中间件（如 Kafka、RabbitMQ）以及数据库（如 MySQL、PostgreSQL）的具体版本；不同版本的软件在性能上可能有很大的差异，因此需要精确记录。
    4. 网络环境：负载均衡器配置、防火墙规则、带宽瓶颈和延迟问题等都会影响性能测试的结果；有时为了模拟真实用户的访问行为，会在网络路径上引入人工延迟。
    5. 测试工具：不同的测试工具有各自的优缺点；JMeter 是开源工具，易于扩展，但可能在高并发场景下性能有限；LoadRunner 功能强大，但可能更昂贵。除了选择工具，还要详细记录工具的版本和配置，因为不同版本的工具可能在性能测试策略及结果上有差异。

14. 如何分析性能测试结果？

🎬 面试现场

面试官（口语化）：性能测试跑完后，你们怎么分析结果？流程是什么？

⚠️ 翻车点

答成「看一眼报告」不完整。分析性能测试结果有六步：收集数据 -> 数据处理 -> 建立基线 -> 可视化 -> 瓶颈分析 -> 优化建议。还要注意去除异常值、建立基线、可视化识别趋势，不能只看单一指标。

📝 现场作答

  • 分析性能测试结果的步骤：
    1. 收集数据：从性能测试工具（如 JMeter、LoadRunner 等）中提取关键的测试数据，包括响应时间、吞吐量、错误率等。
    2. 数据处理：对数据进行整理和清洗，去除异常值以确保数据的准确性。
    3. 建立基线：基线是对比的参考点，可以是先前版本的性能测试结果，也可以是同类型系统的性能数据。
    4. 可视化：通过图表（如折线图、柱状图等），更直观地展现结果的变化趋势和瓶颈。
    5. 瓶颈分析：找出系统性能瓶颈，通常可能出现在 CPU、内存、磁盘 I/O 或网络等方面。
    6. 优化建议：根据瓶颈分析结果，提出具体优化方案。
  • 扩展知识：
    1. 收集数据：通常收集多个维度的数据全面评估系统性能，如响应时间（Response Time）、每秒请求率（Requests per Second）、吞吐量（Throughput）、资源利用率（CPU、内存）、错误率等；这些数据通常记录到日志文件或直接展示在性能测试工具界面上，需要定期导出并保存，确保导出的数据完整且无误。
    2. 数据处理：数据清洗的主要目的是去除异常值和不合实际的错误数据，这些数据可能是由于网络抖动、测试环境偶发故障等原因产生；不去除这些异常数据，分析结果可能会不准确；使用 Excel、R 语言、Python 的 pandas 库等统计工具筛选和清洗数据。
    3. 建立基线：基线是一个相对标尺，有了基线能清楚地知道性能是变好了还是变差了；通常选择一个已经被验证过的、能稳定运行的版本的性能数据作为基线，或者是理想状态下的性能数据；每次进行性能测试后都更新基线，保证能随时进行对比分析。
    4. 可视化：数据可视化能够方便地识别趋势和异常点；通过时间序列图可以看到响应时间在测试中的变化，识别出哪些时间段性能较差；常用可视化工具包括 Grafana、Excel、Tableau 等，选择工具时应考虑数据量和所需展示的图形复杂度。
    5. 瓶颈分析：瓶颈通常出现在资源消耗较高的地方；如果 CPU 使用率经常接近 100%，那么 CPU 可能是瓶颈；同理，磁盘 I/O、内存占用率、网络带宽等方面都可能存在瓶颈；借助监控工具（如 Prometheus、Nagios 等）实时监控系统各项资源的使用情况，结合性能测试数据进行分析。
    6. 优化建议：优化建议通常基于性能瓶颈的具体表现；如果发现数据库响应时间太长，可能需要优化 SQL 查询、添加索引、分库分表等；通过代码优化、硬件升级（如增加服务器）、调整系统架构（如采用分布式系统）等手段，可以有效改善性能瓶颈。

15. 软件测试中，Think Time 的作用是什么？

🎬 面试现场

面试官（口语化）：软件测试里 Think Time 是干什么的？

⚠️ 翻车点

最容易答偏的是把 Think Time 当成”随便停一下”，答不出它模拟真实用户操作节奏的价值，以及防止过度加载导致结果失真。另一个坑是分不清高负载场景（减小 Think Time）和正常负载场景（增加 Think Time）的配置差异。

📝 现场作答

Think Time 在软件测试中，尤其是在性能测试中，扮演着非常重要的角色。它模拟真实用户在操作过程中的思考时间，确保测试场景更加贴近用户的实际使用情况，而不仅仅是对系统连续、无间断地进行压力测试。这种思考时间帮助我们生成更准确、更可靠的性能测试结果。

扩展知识

1）真实性模拟：在实际使用软件时，用户并不会每次操作之间毫无停顿。有些操作会需要用户思考、决策或等待加载等，而 Think Time 的设置正是为了模仿这些真实使用场景，使测试结果能够更准确地反映实际情况。

2）防止过度加载：如果性能测试中没有加入 Think Time，那么模拟用户就会不断地发送请求，造成非正常的高负载，这种情况既不真实也不具备参考价值。而有了 Think Time，测试系统更能反映在合理用户负载下的表现。

3）调节负载：通过调整 Think Time，可以方便地控制测试负载。例如，想要测试系统在高负载下的表现，可以减少 Think Time；相反，想测试在正常负载下的表现，可以增加 Think Time。

4）不同场景的 Think Time 设定：不同应用场景的 Think Time 设定也是不同的。例如，在电子商务网站中，用户的 Think Time 可能较长，因为他们在选购商品时需要时间比较和思考；而在在线游戏中，Think Time 可能较短，因为用户的反应速度会比较快。

5）基于用户行为的分析：设置 Think Time 有赖于对用户行为的分析。这通常是通过日志分析、用户调研等方式获得，理解用户在不同操作环节的平均思考时间，从而设定合理的 Think Time 参数。

16. 软件测试中，接口的响应时间不达标时怎么办？

🎬 面试现场

面试官（口语化）：压测的时候发现某个接口响应时间超标了，你接手后会怎么一步步处理？

⚠️ 翻车点

最容易翻车的回答是直接跳到「加缓存」「升配置」这种手段，而没有先定位原因。面试官想听到的是一条有顺序的处理链路：先确定是哪个接口不达标、分析瓶颈在哪，再看日志和监控，最后才谈优化手段。只报工具名不讲定位过程，会被追问「你怎么知道瓶颈在那」然后接不住。

📝 现场作答

  • 我会按一个有序的思路来处理：
    1. 分析原因：先确定是哪个接口的响应时间不达标，并详细分析性能瓶颈在哪里。
    2. 日志和监控分析：通过查看服务器日志、应用日志，配合监控工具（如 New Relic、Prometheus）确认问题的根本原因。
    3. 优化代码与算法：检查代码效率，看是否有可优化的算法或多余的计算。
    4. 数据库优化：查看是否有数据库查询瓶颈，考虑索引的使用、查询的有效性、数据库配置等。
    5. 缓存机制：对不会频繁变化的数据，可考虑引入 Redis、Memcached 等缓存，减轻数据库压力。
    6. 系统架构调整：根据需求，适当引入异步处理、多线程、多进程来提高响应速度。
    7. 硬件和网络：检查服务器硬件性能、网络带宽是否满足需求，可适度升级硬件或优化网络连接。
  • 高并发场景下，负载均衡是提升响应时间的重要手段，可以通过 Nginx、HAProxy 把流量分散到多台服务器，减少单机压力。
  • 对需要长时间处理的任务，可用异步处理和消息队列（如 RabbitMQ、Kafka），避免阻塞主线程。
  • 响应时间长也可能与上下游依赖有关，比如外部 API 调用过慢，可以考虑服务降级或更换更快的 API。
  • 静态资源或大文件传输可以走 CDN 加速，间接提高接口响应速度。
  • 可以用 JMeter、LoadRunner、Gatling 等工具模拟实际高并发场景做全面性能测试；特别庞大的表可以做分库分表提高查询速度；数据库连接池和线程池的配置优化也能减少等待时间。

17. 你认为 APP 性能测试需要重点关注哪些方面？

🎬 面试现场

面试官（口语化）：让你负责一款 APP 的性能测试，你会重点关注哪些方面？

⚠️ 翻车点

很多人只答「看 CPU 和内存」，覆盖面太窄。这道题的关键是六个维度都要点到：启动时间、响应时间、资源使用率、流畅度、稳定性、网络性能。还有一个隐蔽的翻车点是细节记错——比如响应时间的阈值，原文口径是超过 300ms 用户体验会受影响，流畅度的目标帧率是 60fps，这些数字说错或含糊会被追问打回。

📝 现场作答

  • 我会从六个方面重点关注：
    1. 启动时间：APP 启动是否迅速，特别是首次启动的时间。首次启动要加载资源和初始化数据，通常比应用已在后台的冷启动需要更多时间；优化上可以用懒加载技术，按需加载组件和资源。
    2. 响应时间：APP 对用户操作的响应速度。点击按钮、页面跳转等操作如果超过一定阈值（通常是 300ms），用户体验会受影响；优化上可以前后台数据处理分离，异步操作放后台线程，并配合合理的用户提示降低感知等待时间。
    3. 资源使用率：关注 CPU、内存、电池的消耗。长期高占用会导致设备发热和电池消耗加剧，需要用 Profile 工具（如 Android 的性能分析工具、iOS 的 Instruments）监控运行时资源使用，并定期清理不必要的内存、减少不必要的计算、优化图片和多媒体资源。
    4. 流畅度：关注卡顿和掉帧，通常通过监控帧率来衡量（如 Android 的 Choreographer 和 iOS 的 CADisplayLink），目标帧率应保持在 60fps；优化上减少主线程任务量，用 GPU 处理复杂动画和图形。
    5. 稳定性：APP 在高负荷或长时间使用下是否会崩溃。要收集和分析崩溃日志（可用 Firebase Crashlytics 等第三方崩溃统计工具），做好异常处理，尤其是网络请求、文件操作等易出错模块，并保持第三方 SDK 的更新和兼容性测试。
    6. 网络性能：APP 在不同网络条件下的表现，包括加载时间、数据传输速率，特别是弱网或高延迟场景（如 2G/3G 网络、Wi-Fi 切换）；可通过数据压缩、缓存策略和合理的请求重试机制来提升。

18. 有哪些常见的 APP 性能测试的关注点？

🎬 面试现场

面试官（口语化）：说说你平时做 APP 性能测试，都会关注哪些点？用什么工具和方法？

⚠️ 翻车点

这道题最常见的问题是答完「响应时间、CPU、内存」就停了，把流量消耗和电量消耗漏掉——移动端特有的这两个指标恰恰是考察点。另一个翻车点是混淆工具定位：JMeter、LoadRunner 是后端接口性能工具，移动端应用本身的资源分析要用 Android Profiler / iOS Instruments，说反了会显得没实际做过。

📝 现场作答

  • 常见关注点可以总结为七个方面：
    1. 响应时间：用户体验最直接的体现，包括启动时间、页面切换时间、按钮点击后的反应时间等。
    2. 流量消耗：APP 在不同操作下的数据流量消耗，特别是在移动网络环境下。
    3. CPU 和内存使用率：关注各种操作下的占用情况，防止资源耗尽导致设备卡顿甚至崩溃。
    4. 电量消耗：特别是长时间使用时，APP 对设备电池的消耗是重要衡量标准。
    5. 稳定性：测试长时间运行和高负载下的稳定性，检查是否有崩溃、闪退等现象。
    6. 兼容性：在不同设备、不同操作系统版本下的表现，确保各种环境下正常运行。
    7. 网络状况：模拟弱网、断网、切换网络等情况，确保网络波动下仍有良好体验。
  • 工具选择：JMeter 针对后端接口性能测试，可模拟多用户同时访问；LoadRunner 是综合性测试工具，支持大量协议；Android Profiler / iOS Instruments 适用于移动端应用，可详细查看 CPU、内存、网络等资源使用情况。
  • 测试方法：压力测试模拟大量用户同时操作，观察最大承受能力；负载测试观察不同负载下的响应时间和稳定性；峰值测试测瞬间剧增的请求应对能力；耐久测试长时间持续运行，观察是否出现性能衰退或资源耗尽。
  • 性能优化：代码优化减少不必要的计算和资源消耗；图片优化用合适的格式和尺寸；网络请求优化减少不必要的请求、使用缓存；资源管理避免内存泄漏和频繁垃圾回收。

20. 常见的性能测试方法有哪些？

🎬 面试现场

面试官（口语化）：性能测试的方法有好几种，你都能说出来吗？它们各自的目的和适用场景是什么？

⚠️ 翻车点

最典型的翻车是把负载测试和压力测试混为一谈，或者只报名词不解释目的。原文口径很清楚：负载测试是「一定负载下的性能表现」，压力测试是「超过设计负载测稳定性和极限」——一个是预期内，一个是超预期，这条界线说反了整道题就崩了。另一个坑是漏掉容量测试「侧重找最大处理能力」这个侧重点。

📝 现场作答

  • 常见的性能测试方法主要有六种：
    1. 负载测试：通过增加系统的负载来测试系统在一定负载下的性能表现。主要目的是找出系统的吞吐量、响应时间、会话处理量等指标，一般用于确定网站或应用在正常工作负荷下的性能表现。
    2. 压力测试：通过施加超过系统设计负载的压力来测试系统的稳定性及性能极限，从而识别出可能导致系统在高负载下崩溃的瓶颈，常用于确保系统在意外高负载时保持稳定运行。
    3. 容量测试：测试系统能够处理的最大负载，确保系统在接近或达到容量时依然性能稳定。它与负载测试类似，但更侧重于找到系统的最大处理能力，广泛应用于资源规划、系统扩展规划等场景。
    4. 基准测试：通过标准测试工具和方法，得出系统在特定条件下的性能数据，进行横向和纵向对比。通常使用行业标准工具如 LoadRunner、JMeter，用统一的测试脚本和负载条件，对不同系统或不同版本进行性能对比。
    5. 并发测试：测试系统在多个用户同时操作时的性能表现，重点关注并发量对系统的影响和资源竞争，常用于实时系统、多用户系统、大型 Web 应用等场景。
    6. 稳定性测试：长时间运行系统，检测其在稳定运行情况下的性能表现及潜在问题，也被称为「疲劳测试」，用于检测内存泄露、资源耗尽等长时间运行问题，通常在系统上线前进行。

21. 性能测试的目的是什么？

🎬 面试现场

面试官（口语化）：先从最基础的问起——做性能测试，到底是为了达到什么目的？

⚠️ 翻车点

一句话「评估系统性能」谁都会说，但面试官想听到的是落到具体指标上：响应时间、吞吐量、资源利用率、高负载下的稳定性。能再往深处讲一层——性能测试还能支撑容量规划、给出优化建议、通过基准测试跟踪性能退化趋势——就能明显拉开差距。

📝 现场作答

  • 性能测试的主要目的是评估软件系统在特定负载和环境下的性能表现：确定系统的响应时间、吞吐量、资源利用率以及在高负载下的稳定性等关键指标，确保软件能在实际使用场景中满足用户需求，保持良好的用户体验。
  • 围绕这个目的，有几个关键维度：
    1. 响应时间：系统从接收请求到将响应返回给客户端所需的时间，直接影响用户体验，响应时间越短用户等待越少。
    2. 吞吐量：系统在给定时间内能够处理的事务数量，高吞吐量意味着能同时处理更多用户请求，对大规模应用至关重要。
    3. 资源利用率：包括 CPU、内存、磁盘和网络带宽等的使用情况，通过监控可以发现高负载下的资源瓶颈并优化。
    4. 稳定性：关注长时间运行及高负载下的可靠性，通过长时间压力测试发现潜在的内存泄漏、资源耗尽和其他导致崩溃的问题。
  • 性能测试还有几个延伸目的：
    • 容量规划：预测系统在不同负载下的表现，提前做好硬件资源准备，避免实际使用中出现性能瓶颈。
    • 优化建议：发现性能瓶颈后提供优化方向，例如优化数据库查询、改进代码效率、增加缓存等。
    • 基准测试：确定系统在理想环境下的基本性能指标，通过定期基准测试跟踪性能趋势，识别性能退化问题。

23. 服务端性能测试可以从哪些角度进行？

🎬 面试现场

面试官（口语化）：服务端的性能测试，你一般会从哪几个角度切入？每个角度具体怎么做？

⚠️ 翻车点

这道题的陷阱是只背出「负载、压力、容量」几个名词就收尾。面试官往往会往下追：「可扩展性测试是什么？配置测试测什么？」——这两个角度最容易被漏掉。另外每个角度都要能说出具体手段，比如负载测试用 JMeter、LoadRunner 模拟多用户并监测响应时间、CPU 使用率、内存占用，说不出执行细节就露馅。

📝 现场作答

  • 服务端性能测试可以从七个主要角度进行：
    1. 负载测试：确定服务在特定负载下的表现，指标通常包括并发用户数、请求数等。这是评估系统正常工作条件下表现的主要手段，用负载测试工具（如 JMeter、LoadRunner）模拟多个用户同时发请求，通过监测响应时间、CPU 使用率、内存占用等指标，确认系统能否在预期负载下正常运行。
    2. 压力测试：评估系统在极限负载下的行为，找到服务的最大承受能力以及高负载下的稳定性。做法是逐步增加负载，直到系统崩溃或性能显著下降，找到瓶颈，比如请求量超过某个阈值时出现大量响应超时或错误。
    3. 容量测试：了解系统能处理的最大用户数和数据量，帮助规划未来扩展需求。侧重点是找到最大处理能力——不断增加用户数或数据量，直到服务无法接受新请求或性能不可接受。
    4. 性能基准测试：通过相对固定的测试条件记录系统多个时间节点的表现，生成性能基线，对评估软件更新、硬件更换等情形下的性能变化非常有帮助。
    5. 稳定性测试：观察系统长时间运行中的表现，检测是否有内存泄漏或性能逐步下降的问题。做法是让系统在持续高负载下运行数小时或数天，检查内存泄漏、文件句柄泄漏等问题。
    6. 可扩展性测试：评估系统增加硬件资源后性能是否有线性或接近线性的提升。如果增加资源后性能没有明显提升，可能需要重新评估架构设计或找新的性能瓶颈。

    4. 编写关联：每次 HTTP 请求中可能有会话 ID、令牌等动态值，使用 VuGen 提供的关联功能自动或手动提取这些动态值，确保每次回放生成的 HTTP 请求有效，避免因固定值导致请求失败。
    5. 回放脚本：在 VuGen 中回放脚本，验证参数化和关联处理正常，检查响应内容，确保输入的汉字能解析到正确的域名。
    6. 设置负载测试：打开 LoadRunner 的 Controller，创建新的负载测试场景，从脚本库导入验证通过的脚本，设置虚拟用户数量、测试持续时间（如 30 分钟、一小时等）和负载模式（如渐进加载、达到即稳定等）。
    7. 监控和分析：启动负载测试后用 LoadRunner 内置监控工具查看响应时间、吞吐量、错误率等实时性能指标；测试结束后用 Analysis 工具详细分析数据、生成报告，找出系统瓶颈和并发性能问题。

29. 性能测试怎么进行？性能测试的流程是什么？

🎬 面试现场

面试官（口语化）：从接到任务到出报告，一个完整的性能测试流程是怎么走的？

⚠️ 翻车点

最常见的问题是背了七步流程却讲不出每步的细节动作。追问「需求分析阶段具体做什么」，要能答出确定基线和用户模拟；追问「执行阶段看什么」，要能答出数据监控和日志记录。还有一个坑：流程的最后一步是优化和再测试的迭代闭环，不是交完报告就结束——漏掉这个循环就答得不完整。

📝 现场作答

  • 性能测试的流程一般包括七个步骤：
    1. 需求分析：明确性能测试的目标和范围，确定关键性能指标（如响应时间、吞吐量、资源利用率等）。细节上要确定基线——了解当前系统的性能表现作为对比基准；并做用户模拟——决定如何模拟用户行为，常见的有并发用户数、事务类型和频率等。
    2. 测试环境搭建：配置硬件和软件环境，使其尽可能贴近生产环境。包括服务器、数据库、网络设备等硬件资源准备；工具上，JMeter 适合开源免费的小型项目，LoadRunner 适用于大型复杂系统。
    3. 设计测试用例：基于需求分析设计具体测试用例，考虑不同的用户负载和场景。选取最有代表性的用户操作场景，设计负载模型——定义平稳负载、渐增负载和尖峰负载等条件。
    4. 执行测试：运行设计好的测试用例，利用监控工具实时监控 CPU、内存、磁盘 I/O 等资源使用情况，并记录系统日志帮助故障排查。
    5. 分析结果：收集和分析测试数据，与基线进行对比判断性能提升或下降，通过分析确定性能瓶颈是在代码、数据库还是硬件资源上。
    6. 报告反馈：撰写性能测试报告并提出优化建议。报告应包含测试环境、测试过程、测试结果和优化建议，用图表展示关键性能指标使结果更直观。
    7. 优化和再测试：系统优化后重复上述测试过程，直到达到预期性能指标。一般需要多次性能测试和优化的迭代才能达到最佳效果。

30. 什么是性能测试的环境配置？

🎬 面试现场

面试官（口语化）：搭建性能测试环境的时候，环境配置指的是什么？都要配置哪些东西？

⚠️ 翻车点

很多人把环境配置狭隘地理解成「装个工具、起个服务」。原文口径是为性能测试特意设置的硬件、软件、网络、安全等配置，目标是模拟真实用户场景。容易漏掉的三块：一是数据库要准备与生产数据量相当的数据集；二是网络环境要模拟带宽、延迟、抖动、丢包率；三是环境隔离——测试环境要和开发、生产环境相互隔离，这点很少有人主动提。

📝 现场作答

  • 性能测试的环境配置是指为进行性能测试而特意设置的硬件、软件、网络、安全等配置，目标是模拟真实用户场景，确保响应时间、吞吐量等性能指标能真实体现生产环境下的表现。
  • 核心内容包括：
    1. 服务器配置：尽可能模拟生产环境的服务器配置，包括硬件配置（CPU、内存、磁盘等）、操作系统版本，以及 Web 服务器、应用服务器等中间件的版本。
    2. 数据库配置：数据库往往是性能瓶颈，其硬件配置、数据量、索引、并发连接数等要尽量与生产一致，还需预先准备一份与生产数据量相当的数据集。
    3. 网络环境：模拟实际网络环境，包括带宽、延迟、抖动、丢包率等；企业内部系统还要考虑内外网连接状况。
    4. 测试工具选择及配置：常用 JMeter、LoadRunner 等，它们支持多样化的监控指标和自定义脚本模拟复杂用户行为；配置时根据测试需求设置虚拟用户数、请求频率、数据参数化等。
    5. 安全配置：性能测试涉及大量数据和高并发请求，要确保敏感数据保护，防止测试过程中数据泄漏。
    6. 性能监控工具：配置 Grafana、Prometheus、Nagios 等监控工具，实时观察 CPU 消耗、内存使用、磁盘 I/O、网络流量等指标，有效发现性能瓶颈。
    7. 环境隔离：性能测试环境应与开发环境、生产环境相互隔离，避免其他环境的负载和配置变更影响测试结果，保障测试数据独立性和测试过程稳定性。
    8. 测试脚本的维护和优化：经常维护和优化测试脚本，确保准确模拟生产环境真实用户行为，包括处理动态数据、模拟多种用户行为流转、处理不同业务场景。

这题最容易只答「测试目标、测试场景」两三项就完了，覆盖不全。原文口径有十项：目标、环境、数据、工具、场景、监控与度量、测试步骤、风险评估与缓解策略、资源分配、报告和分析。其中风险评估与缓解策略和资源分配是最高频被漏的两项。另外面试里常会接着问「你实际怎么做」，可以带出先做基准测试、渐进式负载这些实践经验。

📝 现场作答

  • 性能测试计划主要包括十项内容：
    1. 测试目标：明确测试目的和预期结果，定义要验证的性能指标，如响应时间、事务吞吐量、资源利用率等。
    2. 测试环境：描述所需的硬件、软件环境和配置，确保环境尽可能模拟生产环境。
    3. 测试数据：定义测试所需的数据集，确保覆盖可能的生产情景。
    4. 测试工具：列出将使用的工具（如 JMeter、LoadRunner）及其用途。
    5. 测试场景：设计具体场景，包括用户行为、并发用户数量、负载模式等。
    6. 监控与度量：列出要监控的关键性能指标和度量参数，说明如何收集和分析数据。
    7. 测试步骤：详细列出测试执行的步骤、顺序和具体操作。
    8. 风险评估与缓解策略：识别可能影响测试结果的风险并制定缓解策略。
    9. 资源分配：确定测试执行所需的人力、时间和其他资源。
    10. 测试报告和分析：规定测试结果的汇报方式和分析方法。

    • 先做基准测试：正式测试前先跑一次基准测试，记录无负载或最小负载下的性能表现，作为参考指标。

    • 性能瓶颈分析：发现性能明显下降时，用日志、监控工具分析瓶颈，找出 CPU 瓶颈、内存不足、数据库锁竞争等具体影响因素。
    • 并发用户模拟：通过定义具体的用户操作脚本，逼真还原实际使用情况。
    • 长期性能测试（Soak Testing）：通过长时间运行测试发现内存泄漏、资源耗尽等问题。
    • 自动化与持续集成：把性能测试纳入持续集成体系，定期自动跑性能测试脚本，及时发现性能退化。

36. 软件测试中，当服务器满载时，吞吐量和响应时间是如何变化的？

⚠️ 翻车点

这题最容易答成「负载越高吞吐越高、响应时间线性变长」——前半句对、后半句错。原文口径是分阶段的：负载在开始阶段增加时吞吐量会逐步提高，但一旦达到服务器处理能力的峰值（满载状态），吞吐量不再增加，甚至可能下降；而响应时间在低负载时较短，到满载状态会显著增加，满载情况下往往呈指数级增加。只答「压不垮就行」也丢分——服务器资源已被完全利用时，新请求会被排队或拒绝，这就是吞吐量的来源。

    2. 响应时间：在负载较低时，响应时间通常较短。但是，随着负载增加到满载状态，响应时间会显著增加。这是因为服务器忙于处理大量请求，每一个新的请求都需要等待更长的时间才能被处理。因此，满载情况下，响应时间往往会呈指数级增加。

40. 软件性能测试中，QPS 如何从 200 慢慢加载到 300 和 400？

🎬 面试现场

面试官（口语化）：性能测试里 QPS 从 200 慢慢加到 300、400，怎么操作？

⚠️ 翻车点

最容易答偏的是只说”调并发数”却答不出渐进式负载测试的完整步骤：定义初始负载 → 设置增量步骤 → 设置稳定时间 → 监控性能指标 → 记录和分析数据。另一个坑是答不出稳定时间的作用（每次增加 QPS 后保持一定时间观察系统表现），只顾着往上加压而没给系统稳定窗口。

📝 现场作答

在软件性能测试中，QPS（Queries Per Second，查询每秒）是一个重要的指标，用来评估服务在高并发情况下的表现。如果你想从每秒200的请求负载慢慢增加到300和400，你可以采用渐进式负载测试的方式。具体步骤如下：

定义初始负载：
开始以每秒200个请求（即QPS=200）的负载进行测试。

设置增量步骤：
定义每次增加的QPS，比如每次增加50，这样200 -> 250 -> 300 -> 350 -> 400。

设置稳定时间：
每次增加QPS后，保持一定的时间，如5分钟，以便观察和记录系统表现。这个时间可以根据具体应用场景进行调整。

监控性能指标：
在测试过程中，实时监控重要性能指标，如CPU、内存、响应时间、错误率等。

记录和分析数据：
收集各种性能数据，并在每个负载水平上进行分析，以确认系统是否能够稳定处理相应的QPS。

扩展知识

在实际操作中，负载测试工具和方法选择也至关重要。以下是一些扩展知识：

工具选择：
常见的负载测试工具有Apache JMeter、Gatling、Locust等。根据具体的测试需求和实际应用场景选择合适的工具。

自动化测试脚本：
利用脚本自动执行上述步骤，如在JMeter中可以通过创建测试计划并配置线程组与调度器来实现渐进式负载测试。

性能瓶颈排查：
通过监控工具如Grafana与Prometheus或者应用性能管理（APM）工具如New Relic、Datadog等来实时监控和排查性能瓶颈。

模拟真实用户行为：
不仅要关注QPS，还要模拟更加真实的用户行为，如考虑用户的请求频率、访问模式等，让测试更贴近实际使用场景。

系统扩展性测试：
在逐步增加负载的过程中，关注系统的可扩展性，即当负载增加时，系统能否通过增加资源（如CPU、内存）来维持或提升性能。

🎬 面试现场

⚠️ 翻车点

最容易翻车的回答是「看日志啊」一句话就完了。面试官要的是完整定位链路和每步的具体手段：日志分三类（系统日志、应用日志、数据库日志）；复现要用一致性环境加 JMeter、Gatling 模拟相同并发；分析返回数据可以用 Wireshark 抓包确认传输中数据是否丢失或变化；资源检查要用 Prometheus、Grafana、Zabbix 持续监控。跳步或者只会说「重启试试」都过不了关。

📝 现场作答

  • 我会按这六步定位：
    1. 查看日志：这是最直观有效的方法，检查三类日志——系统日志（syslog）看系统级别的问题，应用日志看运行状态、错误信息和业务逻辑相关信息，数据库日志（包括查询日志、慢查询日志）帮助发现数据库瓶颈和死锁问题。
    2. 复现问题：在相同环境、相同负载下复现，确保问题不是偶然发生。具体做法是用一致性测试环境——相同的硬件、操作系统和配置下运行相同测试用例，用 JMeter 或 Gatling 模拟相同的并发请求。
    3. 分析返回数据：对比预期数据和实际返回数据，明确差异之处。可以用 Wireshark 抓包查看网络传输的数据，确认数据在传输中是否有丢失或变化。
    4. 检查系统资源：压力测试会消耗大量系统资源，用 Prometheus、Grafana、Zabbix 等监控工具持续监控内存、CPU、网络带宽等指标，关注内存泄漏、CPU 过载、网络带宽过高等问题，确保资源没有成为瓶颈。
    5. 验证配置：确认测试环境配置与生产环境一致，包括操作系统参数、数据库连接池大小、线程数等——错误的配置可能导致性能问题和数据报错。
    6. 监控依赖服务：错误可能源于依赖的外部服务或第三方 API，用心跳检测、定期调用 API 等方式监控外部服务可用性；微服务架构中要检查各个服务的健康状况，确保它们能承受压测带来的请求。

怀疑是依赖服务挂了怎么确认？ 用心跳检测、定期调用 API 等方式监控外部服务的可用性；微服务架构中检查各个服务的健康状况，确认它们能否承受压力测试带来的请求。

❌ 千万别说的话

  • “报错了先重启服务再压一遍。” —— 这跳过了定位环节。正确顺序是先查日志、复现问题、分析返回数据，确认问题源头后再处理；配置不一致、依赖服务异常这类问题重启根本解决不了。
  • “返回数据不对肯定是接口 bug。” —— 压测场景下原因可能是多方面的：资源瓶颈（内存泄漏、CPU 过载、带宽过高）、环境配置与生产不一致、依赖的外部服务或第三方 API 异常，都要逐一排查。

⚠️ 翻车点

这题的坑是答成「调优就是改代码」。原文口径是先测试拿基准数据，再分析瓶颈，再针对性调优，再迭代的闭环流程——核心在于识别并消除瓶颈。另一个失分点是漏掉调优的层次：硬件、系统配置、应用、数据库四个层面都要覆盖。还有「避免过度优化」这个注意事项很少人主动提，说出来能明显加分。

📝 现场作答

  • 性能调优是指通过一系列手段优化软件系统的性能，以达到预期的运行速度、响应时间和资源使用效率，核心在于识别并消除瓶颈，把系统潜在效率充分发挥出来。
  • 一般流程：
    1. 性能测试：先用性能测试工具（如 JMeter、LoadRunner）对系统做压力测试，获取性能基准数据。
    2. 瓶颈分析：根据测试结果定位瓶颈，可能出现在 CPU、内存、I/O 操作、数据库查询等多个地方。
    3. 调优策略：针对具体瓶颈制定策略，比如数据库查询慢就优化 SQL 语句、增加索引或改进表结构。
    4. 迭代优化：不断测试、分析和调整，直到达到性能目标。
  • 常见调优手段（四个层面）：
    • 硬件层面：增加服务器数量或升级硬件配置，如增加内存、使用更快速的硬盘。
    • 系统配置：调优操作系统和中间件配置参数，如调整线程池大小、优化内存管理。
    • 应用层面：优化代码逻辑、减少不必要的计算、利用缓存机制、分布式部署。
    • 数据库优化：分表分库、索引优化、查询优化、使用缓存等。
  • 注意事项：
    • 需求明确：调优前明确性能目标，例如响应时间不超过 2 秒、支持的并发用户数等。
    • 避免过度优化：集中精力在主要瓶颈处，不必要的微优化会导致代码可读性下降、维护难度增加。
    • 监控工具：合理使用监控工具实时监控系统性能，调优后继续监控，确保优化效果。

    • 分布式协调：考虑各测试节点间的协调，主控制节点和从节点的同步以及结果数据的汇总都需要详细配置。

⚠️ 翻车点

这题考的是渐进加压策略，最容易答得含糊。原文口径有具体的数字节奏：先启动较少的用户数（例如 10 或 20 个），然后每分钟增加 10 到 20 个用户直到预期最高并发，达到后保持一段时间观察稳定性，最后逐步降低观察恢复情况——四个阶段一个都不能少，数字要能说出来。很多人只答「慢慢加」，加压节奏和收尾观察都说不上来。

  • 这种场景通常设置一个逐渐增加的负载策略，逐步测量系统在不同负载下的性能表现和稳定性，找出极限和瓶颈。具体分四步：
    1. 启动较少的用户数并发请求，例如 10 或 20 个用户。
    2. 逐渐增加并发用户数，例如每分钟增加 10 到 20 个用户，直到达到预期的最高并发用户数。
    3. 达到最高并发后保持一段时间，观察系统的稳定性和性能。
    4. 最后逐步降低并发用户数，观察系统的恢复情况。
  • 这样能确保系统在不同并发负载下被全面测试，了解系统在负载增长和下降过程中的响应情况。
  • 配套的几个关键点：
    • 工具选择：JMeter、LoadRunner、Gatling 等工具提供了便捷的方式模拟并发用户，并能生成详细的性能报告。
    • 性能监控：对系统实时监控 CPU、内存、磁盘、网络等资源使用率，可用 Prometheus、Grafana 等工具实现监控和可视化，更好地分析性能瓶颈。
    • 场景模拟：尽可能模拟真实用户行为，如随机的页面访问、数据提交、文件上传等，更真实地反映系统性能。
    • 数据准备：提前准备测试数据——数据库读取要有足够测试数据，文件操作要准备足够文件样本，数据的选择和准备直接影响测试结果准确性。
    • 基线测试：在逐步加压之前先做基线测试，了解系统初始状态下的性能，有助于后续分析对比、发现潜在问题。

45. 软件测试中，并发用户数与响应时间、吞吐量之间的关系是什么？

🎬 面试现场

面试官（口语化）：并发用户数往上加的时候，响应时间和吞吐量会怎么变？能描述一下这条曲线吗？

⚠️ 翻车点

这题的坑是只答「并发越高越慢」，说不出吞吐量的先增后降。原文口径是：并发用户数增加时，响应时间逐渐变长，吞吐量到达一个顶点后开始下降——原因是 CPU、内存、I/O 等资源逐渐耗尽形成瓶颈。还要能讲清线性增长与非线性增长的分界：低并发时近似线性，接近系统容量后响应时间急剧上升、吞吐量见顶甚至下降。

📝 现场作答

  • 先把三个概念说清：
    1. 并发用户数：同一时间内有多少用户同时在使用该系统。
    2. 响应时间：系统响应用户请求的时间，从用户发送请求到接收到返回结果之间的时间。
    3. 吞吐量：系统在单位时间内处理的请求数量。
  • 三者的关系：随着并发用户数增加，响应时间逐渐变长，而吞吐量在到达一个顶点后可能开始下降——原因是系统的 CPU、内存、I/O 等资源逐渐被耗尽，形成性能瓶颈。总结：并发用户数增加时，响应时间一般变长，吞吐量先增加然后可能减少。
  • 深入几个层面：
    1. 系统容量与瓶颈：每个系统都有能处理的最大并发用户数即系统容量，超过后资源达到极限，响应时间急剧上升，性能显著下降。
    2. 线性增长与非线性增长：并发用户数较低时，响应时间增加不明显、吞吐量稳步提升，呈比较线性的增长；一旦接近系统容量，响应时间增加变得很明显（非线性增长），吞吐量到达瓶颈甚至下降。
    3. 性能优化应用：了解三者关系可以指导优化——通过负载均衡、优化算法、增加硬件资源等措施提高处理能力；通过监测这些指标提前发现并解决瓶颈，避免高峰期崩溃。
    4. 实际案例：用负载测试工具（如 JMeter、LoadRunner）模拟并发用户，测量响应时间和吞吐量了解系统表现，再根据结果调整代码和配置，比如使用异步处理、减少数据库查询次数来优化。

    • 监控工具与技术：用 JMeter、LoadRunner、Grafana、Prometheus 等工具模拟大量用户访问、监控系统资源使用情况、定位性能瓶颈。
    • 持续测试与持续优化：性能测试不应是上线前的最后一步，而应贯穿整个开发过程，通过持续集成和持续测试保证每次代码修改不引入新的性能问题。
    • 性能调优策略：问题发现后用代码优化、数据库优化、缓存机制、提高硬件资源、架构调整等手段优化。

47. 你们的性能测试是做前端还是后端？

🎬 面试现场

面试官（口语化）：你们团队的性能测试是压前端还是压后端？两边分别怎么做？

⚠️ 翻车点

直接答「只做后端压测」或者「只做前端」都是坑。原文口径是前后端都覆盖：前端关注用户体验和页面加载速度，后端关注服务器响应时间、吞吐量和资源利用率。前端这块容易答空，要能说出具体指标和工具——页面加载时间用 Lighthouse、PageSpeed Insights，交互响应时间，静态资源优化，不同网络类型（如 3G、4G）下的表现。最后能补上端到端综合测试更完整。

📝 现场作答

  • 我们的性能测试覆盖前端和后端两部分：前端性能主要涉及用户体验和页面加载速度，后端性能重点关注服务器的响应时间、吞吐量和资源利用率，通过综合测试确保应用整体性能最佳。
  • 前端性能测试：
    • 页面加载时间：衡量从用户请求页面到页面完全显示所需的时间，使用 Lighthouse、PageSpeed Insights 等工具。
    • 交互响应时间：监测点击按钮、输入内容等操作后的响应速度，确保用户体验流畅。
    • 资源优化：分析和优化静态资源（HTML、CSS、JavaScript）的加载，包括文件大小和加载顺序。
    • 网络性能：评估不同网络类型（如 3G、4G）下的加载速度，确保在不同网络环境中表现良好。
  • 后端性能测试：
    • 响应时间：服务器处理请求并返回响应的平均时间，通常通过 JMeter 等工具实现。
    • 吞吐量：测量特定时间内服务器可处理的请求数量，评估系统的扩展性。
    • 并发性：评估同时处理多个请求时的性能表现，确定并发处理能力和瓶颈。
    • 资源利用率：监测服务器的 CPU、内存、磁盘 I/O 等使用情况，发现潜在的资源限制问题。
  • 前后端结合的综合测试：
    • 端到端测试：模拟真实用户的操作路径，全面评估从前端到后端的整体性能表现。
    • Stress Testing（压力测试）：超负荷运行系统，确定最大承载能力和极限性能。
    • Soak Testing（耐久测试）：长时间运行测试，观察是否存在内存泄漏或其他资源耗尽问题。

面试官追问 你的答案
前端性能用什么工具测？ 页面加载时间用 Lighthouse、PageSpeed Insights 衡量；交互响应时间通过监测用户操作（如点击按钮或输入内容）后的响应速度来评估。
后端性能主要看哪几个指标？ 响应时间（通常通过 JMeter 等工具测）、吞吐量（特定时间内可处理的请求数量）、并发性（同时处理多个请求的表现）、资源利用率（CPU、内存、磁盘 I/O 使用情况）。
前后端怎么结合起来测？ 做端到端测试——模拟真实用户的操作路径，全面评估从前端到后端的整体性能表现；再配合压力测试确定极限性能、耐久测试观察内存泄漏等长期问题。

  • “前端后端分开测完各出各的报告就行。” —— 原文口径强调综合测试：通过端到端测试模拟真实用户操作路径，全面评估从前端到后端的整体性能表现，确保整个系统的可靠性和高效性。

48. 性能测试中，1000 人抢购中只有 10 人能成功，你会如何设置并发数？

🎬 面试现场

面试官（口语化）：一个秒杀场景，1000 人抢购只有 10 人能成功，并发数你设成 10 还是 1000？

⚠️ 翻车点

这题最大的陷阱就是答「设成 10」——按成功人数设置并发。原文口径非常明确：并发数应设置为 1000，一开始就模拟出所有参与抢购的用户数，重点是测试系统在高并发下的行为，而不是让并发数根据成功人数来设置，因为抢购逻辑应该由后台系统决定。同时要能补充：并发 1000 之外还要监测实际成功请求数和响应时间。

📝 现场作答

  • 并发数设置为 1000——一开始就模拟出所有参与抢购的用户数，这样才能真实反映系统在实际场景下的承载能力以及用户抢购接口的处理能力。重点是测试系统在高并发下的行为，而不是让并发数根据成功人数来设置，因为抢购逻辑应该是由后台系统来决定的。
  • 围绕这个场景还要关注：
    1. 并发用户数与吞吐量：并发数是同时发起请求的用户数，吞吐量是系统在一定时间内处理完成的请求数量，二者紧密相关但概念不同；高并发测试有助于测量系统短时间内处理大量请求的能力。
    2. 瓶颈分析：通过设置高并发数检测系统瓶颈，比如是否出现数据库锁定、网络拥堵甚至系统崩溃，这些信息能帮助开发人员优化，如提升数据库读写速度、增加负载均衡。
    3. 负载测试与压力测试的搭配：负载测试检查系统在正常工作负载下的表现，压力测试施加更高负载直到出现故障；对抢购场景，压力测试能帮助了解系统的极限和潜在崩溃点。
    4. 成功率和响应时间：并发数设为 1000 的同时，还要监测实际的成功请求数以及响应时间——抢购场景下保持一定的成功率并尽可能减少响应时间至关重要。
    5. 分布式压力测试：为更真实模拟大量用户并发请求，通常采用分布式压力测试工具，例如 Apache JMeter 和 Locust，通过多台机器模拟上千用户同时访问，获取更接近真实环境的数据。

49. 测试一个项目接口的性能时，你会如何设置并发？

🎬 面试现场

面试官（口语化）：给你一个项目接口做性能测试，并发数你会怎么定？说说你的依据和做法。

⚠️ 翻车点

这题的坑是答「拍脑袋设个 100」。原文口径的起点是确定目标用户量——通过市场预估、历史数据分析得到有多少用户会同时访问，再据此分阶段设置并发（50、100、500 用户等）。另一个失分点是不提渐进式加载和重复测试：从较小并发逐步增加才能精确找到瓶颈，单次结果可能是巧合需要多次重复排除偶然因素。

📝 现场作答

  • 我会按四步来设置：
    1. 确定目标用户量：先清楚了解系统的目标用户量，即有多少用户会同时访问该接口，这个数据可以通过市场预估、历史数据分析得到。
    2. 设置并发用户数：根据目标用户量来设置，分阶段模拟，比如 50 用户并发、100 用户并发、500 用户并发等，观察系统在不同负载下的性能。
    3. 定义测试场景：确保模拟的用户行为与真实用户行为一致，比如登录、查询数据库、提交表单等操作。
    4. 监控系统性能：并发测试时实时监控 CPU、内存、磁盘 I/O、网络带宽等关键指标，及时发现并分析系统瓶颈。
  • 配套的实践要点：
    • 工具选择：用 JMeter、LoadRunner、Gatling 等性能测试工具，可以方便地设置各种并发场景，并有丰富的报告功能帮助分析数据。
    • 渐进式加载：除了直接设置高并发用户数，我会选择从较小的并发量逐步增加，这样能更精确地找到系统的性能瓶颈在哪。
    • 测试环境选择：确保性能测试环境尽可能与生产环境一致，包括软件配置、硬件配置——环境有显著差异会导致测试结果不准确。
    • 重复测试：性能测试需要多次重复进行，以确保数据稳定可靠——偶然一次的高性能或低性能可能只是巧合，需要多次测试排除偶然因素。
    • 分析与优化：通过测试数据详细分析找出性能瓶颈，针对性优化，例如代码优化、数据库优化、硬件升级。

50. 在性能测试时，你们一般的 CPU 和内存配置是多少？

🎬 面试现场

面试官（口语化）：你们压测的时候，压力机或服务器的 CPU、内存一般给多大配置？

⚠️ 翻车点

这题的陷阱是报一个具体的数字。原文口径明确：配置取决于待测系统的实际应用场景和性能需求，性能测试的目标是模拟生产环境的工作负载，所以一般会使用与生产环境相近的硬件配置——生产用多核 CPU 和大内存服务器，测试也选类似配置，以保证测试结果准确可参考。答不出原则、只编数字，或者不知道按应用类型区分（CPU 密集型 vs IO 密集型），都会露馅。

📝 现场作答

  • CPU 和内存配置取决于待测系统的实际应用场景和性能需求，没有统一数字。性能测试的目标是模拟生产环境下的工作负载，所以我们一般使用与生产环境相近的硬件配置——比如生产环境用多核 CPU 和大内存服务器，测试时也选类似配置，确保测试结果的准确性和可参考性。
  • 几个展开的要点：
    1. 测试环境 vs 生产环境：尽量模拟生产环境的硬件配置；有时出于成本考虑两者会不同，这时可以用虚拟机或容器技术（如 Docker）创建多实例并行测试，用测试工具和方法模拟更高的负载。
    2. CPU 和内存的重要性：高性能 CPU 能处理更多并发请求，足够的内存能减少内存交换频率、提高响应速度。按应用类型调整：CPU 密集型应用（如大量计算任务）需要更高频率和更多核数的 CPU；IO 密集型应用（如数据库服务器）需要优化内存和存储配置，减少磁盘 IO。
    3. 综合资源配置：除 CPU 和内存外，还要关注存储 IO、网络带宽等资源——性能瓶颈往往不是单一硬件问题，而是多个因素的综合结果，需要全面考虑。
    4. 测试工具和指标：用 benchmark 工具和性能监控工具评估，指标包括 CPU 使用率、内存占用、输入输出操作次数（IOPS）等；常用性能测试工具有 Apache JMeter、LoadRunner、Gatling，还可利用系统自带监控工具（如 Linux 的 top、htop、vmstat）实时监控资源使用情况，动态调整和优化配置。
