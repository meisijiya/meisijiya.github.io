性能测试--面试

作者: 老江湖
日期: 十月 28, 2026  20:00:00
分类: 面试八股 性能测试

Hi，我是 meisijiya ，也是 老江湖 ，感谢你的阅读，我们一起进步。

1. APP 弱网测试是怎么做的？

🗣️ 回答重点

  • 弱网测试主要看 App 在慢网和丢包条件下的表现，会不会白屏、会不会卡死，断网之后能不能自己恢复。
  • 常用的路子有三条。第一条是工具模拟，macOS 上用 Network Link Conditioner 配模拟器，或者用 Charles 做限速和延迟注入。第二条是真实场景，去地铁、地下车库、电梯里真机跑。第三条是自建环境，拿路由器和网络模拟设备搭一套可控的弱网。
  • 我盯的指标是响应时间、超时次数和丢包率，还有断网重连时间与页面加载速度。
  • 工具造不出来的场景一定要去真实网络里补一遍，比如瞬间断网、基站切换和邻频干扰。

📈 拔高

  • Network Link Conditioner 现在不是 iOS 设备内置的功能。它的主流形态是 Xcode Additional Tools 里的偏好设置面板，能选 3G、EDGE、LTE 预设，也能自定义带宽、延迟和丢包率，通常配合模拟器使用。
  • Charles 支持带宽限速和延迟，不支持丢包。Fiddler Classic 只有 Windows 版本，Fiddler Everywhere 能做延迟和丢请求，也不做带宽限速。所以「三款工具都能模拟丢包」这个说法不成立。
  • 真实网络测试的价值在于模拟工具造不出的东西：瞬间断网、邻频干扰和地下停车场的信号衰减。模拟工具的可控性好，但还原不了这种复杂性，两者是互补关系。
  • 自动化这块我会写脚本定期在几档网络下跑核心链路，比如浏览、下单和支付。手工跑一轮只能证明当时能用，抓不到版本回归。
  • 优化方向一般从数据压缩、请求合并和缓存策略入手，也可以换成 HTTP/2。改完要回到同一档弱网复测，不然不知道有没有真效果。

2. APP 的性能测试是怎么做的？

🗣️ 回答重点

  • 我们有一套固定流程：需求分析、设计测试方案、搭环境、执行、监控收集数据、分析出报告。这六步少一步都会被追问。
  • 需求分析阶段要写清楚测哪些指标：响应时间、吞吐量和资源占用，还有耗电和崩溃率。
  • 环境尽量贴近真实，覆盖多种机型、多个系统版本和不同网络条件。
  • 执行阶段用工具跑。压后端接口用 JMeter 或 LoadRunner，移动端自动化用 Appium，这两类不是一回事，混着说会被追问。

📈 拔高

  • 指标要能对上业务场景。首页启动 2 秒和商品详情 2 秒，用户容忍度完全不同，脱离场景谈阈值没有意义。
  • 除了常规负载，我们会做一轮极高负载的极限测试，确认崩溃点在哪。出了问题才知道该降级还是该扩容。
  • 测试结束不等于交付。问题修完要用同一套用例、同一套环境复测，否则前后数据不可比。
  • 生产环境也要留监控。压测只能证明某个时间点扛得住，线上流量结构一变照样出问题。
  • 工具选型看场景：JMeter 开源免费、扩展性强，适合中小团队。LoadRunner 协议覆盖广、报告详细，成本也高，适合大型复杂系统。

3. 如何测试 APP 的内存使用情况？

🗣️ 回答重点

  • 三条路。IDE 自带工具：Android Studio 的 Profiler 抓堆转储看对象，Xcode 的 Instruments 用 Allocations 看分配、用 Leaks 看泄漏。第三方库：Android 上集成 LeakCanary。系统功能：开发者选项里手动看内存占用。
  • Android 现在的路径是先进 Profiler 选目标进程，再开实时内存或者 Heap Dump。抓堆转储要求应用是 debuggable 的包。
  • iOS 除了 Instruments，还可以直接用 Xcode 自带的 Memory Graph 调试器。

📈 拔高

  • 网上流传的「MemoryGraph 是 iOS 的第三方内存工具」是错的。并不存在这个第三方工具，指的是 Xcode 内置的 Memory Graph Debugger，调试区一个按钮就能导出内存图，查循环引用最快。
  • LeakCanary 是 Square 维护的库，检测到泄漏会给出完整引用链，比堆转储好读，适合常驻在开发包里。
  • 看内存不要只看总量。稳定在某个水位是正常的，持续线性上涨才是泄漏。抓两次快照做差集，增长的对象就是嫌疑。
  • 手动查内存适合快速判断，真要定位问题还是要靠工具。开发者选项只能告诉你「占了多少」，告诉不了「谁占的」。

4. 如何测试 APP 的流量使用情况？

🗣️ 回答重点

  • 装好 App 之后挂代理抓包，Charles、Proxyman、Fiddler 都行，按会话看每个请求收发多少字节。
  • Android 也可以用 Android Studio 的 Network Inspector 看实时收发和单个请求的大小。iOS 用 Instruments 的 Network 模板。
  • 抓的时候过滤掉广告 SDK 和推送通道，只看业务请求，不然数字全是噪音。
  • 最后按场景汇总：浏览一屏多少流量、看一个视频多少流量，跟预期对一下。

📈 拔高

  • Network Link Conditioner 只模拟网络条件，不统计流量。把它当流量测量工具是错的，iOS 测流量要用 Instruments 的 Network 或者代理工具。
  • Wireshark 能统计全量字节，但按请求归因很难，一般用来查协议层面的问题，不适合做业务流量统计。
  • 后台数据同步和缓存策略会显著改变流量。同一版 App，缓存命中和不命中能差一倍。
  • 云设备农场能解决机型覆盖问题，BrowserStack 和 Firebase Test Lab 都提供多设备多网络条件的测试。
  • 流量分析顺手还能查安全：请求是不是全走 HTTPS，有没有把敏感字段明文发出去。

5. 如何测试 APP 的 CPU 消耗情况？

🗣️ 回答重点

  • Android 我用 Android Studio 的 CPU Profiler 做采样，或者命令行 adb shell top 看实时占用。
  • iOS 用 Instruments 的 Time Profiler，它能给出调用树，直接定位到方法级的热点。
  • 流程是连设备、开采样，跑预先设计好的用例，看峰值和平均值，最后导出数据写报告。
  • 用例要覆盖主要功能模块，只测一个页面得出的结论没有代表性。

📈 拔高

  • adb shell top 由 toybox 提供，个别定制 ROM 可能裁掉了这个命令，设备上跑不了就换 Profiler。dumpsys cpuinfo 给的是快照不是实时值，替代不了 top。
  • 定位到方法级热点更推荐 CPU Profiler，底层是 Simpleperf，采样精度比 top 高。
  • 测试尽量用真机而不是模拟器，模拟器的 CPU 模型和真机差别很大。
  • 自动化可以用 Appium 或 Espresso 批量跑用例，覆盖面和数据可信度都比手工强。
  • 优化从三处下手：主线程别做网络和文件读写，算法和数据结构别写 O(n²)，减少不必要的布局重绘并给重复计算加缓存。

6. 如何测试 APP 的 FPS（帧率）？

🗣️ 回答重点

  • 三种方法。IDE 工具：Android Studio 的 CPU Profiler 里看 Frame Timeline，Xcode 的 Instruments 用 Animation Hitches 模板。第三方：PerfDog 支持双端，Android 还有 GPU Inspector。代码埋点：在渲染回调里数帧。
  • 埋点要按固定窗口统计，一秒算一次最直观。Android 用 Choreographer，iOS 用 CADisplayLink。

📈 拔高

  • 几个工具名已经变了。Android Studio 没有独立的「Graphics」选项卡，帧相关信息在 CPU Profiler 的 Frame Timeline 里。Xcode 的 Core Animation 模板改名叫 Animation Hitches，看的是卡顿次数而不是单纯帧率。Systrace 已被 Perfetto 接替，现在用基于 Perfetto 的 System Trace。
  • 埋点代码最容易错在首帧。第一帧时间戳是 0，直接拿来减会算出一个巨大的间隔。窗口起点要单独记，不能拿上一帧时间当起点。
  • 60fps 是官方流畅目标，对应每帧 16.7ms。掉到 30fps 用户能明显感到卡。
  • PerfDog 的价值在于跨端对比，同一段操作在 Android 和 iOS 上的帧率曲线能放在一起看。

7. 如何使用 JMeter 进行性能测试？

🗣️ 回答重点

  • 七步走：建测试计划、加线程组、加采样器、配采样器、加监听器、跑、看结果。
  • 线程组里线程数就是并发用户数，Ramp-Up 是爬坡时间，循环次数决定每个用户跑几轮。
  • 采样器一般选 HTTP Request，配 URL、方法、参数。监听器用 View Results Tree 调试，用 Summary Report 看汇总。
  • 跑之前先小并发试一次，确认请求真的发出去了、断言也过了。

📈 拔高

  • 正式压测用非 GUI 模式：jmeter -n -t plan.jmx -l result.jtl。GUI 在高并发下自己就会成为瓶颈，把压测机的资源吃掉。
  • 参数化用 CSV Data Set Config，复杂逻辑用 Groovy 或 Beanshell。插件生态在 JMeter Plugins 站点，采样器、监听器、报告生成工具都有。
  • 分布式压测配一台 master 多台 slave，走 RMI 通信。slave 的数量决定你能压到多高。
  • 非 HTTP 场景也覆盖：JDBC 测数据库，LDAP 测目录服务，SOAP/XML-RPC 有专用采样器，FTP 和 SMTP 有原生支持。
  • 接进 CI 之后每次提交都能跑一遍，性能退化在合并前就能发现。

8. JMeter 为性能测试提供了哪些好处？

🗣️ 回答重点

  • 开源免费，成本几乎为零，团队里谁都能装。
  • 协议覆盖广，HTTP 和 HTTPS 之外还有 JDBC、LDAP、SOAP、FTP、SMTP。
  • GUI 上手快，写完脚本能直接在界面里看结果。
  • 插件机制能扩展采样器和报告，分布式模式能压到很高的并发。

📈 拔高

  • 脚本能复用，同一份 jmx 可以在不同环境跑，配合 CI 还能每次提交自动回归。
  • 命令行执行加生成 HTML 报告，适合接进 Jenkins 或 GitLab CI，非 UI 环境下也能跑。
  • 社区活跃，遇到问题基本都能搜到现成答案。云平台上也能直接跑大规模测试，不用自建压测集群。
  • 但要知道它的边界。JMeter 是 Java 应用，单机并发受线程模型限制，压到一定量级就该上分布式。
  • 优势是相对的。它的易用性和免费是最大卖点，深度分析和复杂协议支持不如商业工具。

9. 常见的性能测试指标有哪些？

🗣️ 回答重点

  • 五个基础的：响应时间、吞吐量和并发用户数，还有错误率与资源利用率。
  • 响应时间看用户等多久，吞吐量看单位时间处理多少，并发用户数看同时在线多少。
  • 错误率反映高负载下稳不稳，资源利用率看 CPU、内存、磁盘 IO 的消耗。
  • 这五个要一起看。只看其中一个基本都会得出错误结论。

📈 拔高

  • 扩展指标里延迟和响应时间容易混。延迟一般指网络传输耗时，分布式系统里这一块占比可能很高。
  • 事务成功率比请求成功率更贴近业务。一笔下单可能对应五六个请求，请求都成功不代表业务成功。
  • 连接时间指客户端和服务器建立连接的时间。高并发下这一项过长，会先把连接池打满。
  • Jitter 指延迟的波动。平均延迟一样，波动大的系统体感更差。
  • 数据密集型应用还要看查询执行时间、缓存命中率和锁等待。这几项直接决定数据库能不能扛住。

10. 什么是 TPS（Transactions Per Second）？

🗣️ 回答重点

  • TPS 是每秒处理的事务数，用来衡量数据库、应用服务器或者整个系统的处理能力，高负载场景下最常看这个。
  • 测法是用 JMeter 或 LoadRunner 模拟并发，记录每秒完成的事务数，同时看响应时间和 CPU 占用。
  • TPS 不会随着并发无限上涨。到顶之后继续加并发，TPS 反而会掉。

📈 拔高

  • 事务要先定义清楚。一个事务是一笔业务还是一次请求，团队之间必须先对齐，否则数字没法横向比较。
  • TPS 与响应时间、吞吐量和 CPU 利用率是一条链上的东西。TPS 掉的时候，CPU 打满说明算力不够，CPU 不高说明卡在锁、IO 或者下游。
  • 真实场景里 TPS 的绝对值不重要，重要的是同版本之间的对比。改完代码 TPS 涨了多少，这个才有决策价值。
  • 电商大促和银行转账看 TPS 的方式一样，但对绝对值的预期差好几个数量级，目标要按业务定。

11. 什么是 QPS（Queries Per Second）？

🗣️ 回答重点

  • QPS 是每秒处理的查询数，Web 服务、数据库和搜索引擎都用它衡量处理能力。
  • 算法很简单：总查询次数除以总时间，单位是秒。
  • QPS 掉了先看资源。CPU 打满、内存不足和磁盘 IO 打满，还有网络带宽吃紧，这四样依次排查。
  • 光有定义不够，还要能说出它跟响应时间、并发用户数的关系。

📈 拔高

  • QPS 不高但响应时间也很短，说明系统没饱和，只是压力还没上来。这种情况不能判断性能差。
  • 负载测试时逐步加请求量，画出 QPS 曲线，顶点就是系统的实际处理上限。
  • 提升 QPS 的常见手段：加机器、加缓存减少穿透到数据库、把耗时操作异步化、优化算法和索引。
  • 搜索引擎和 Web 服务的 QPS 含义略有差别。前者数查询词，后者数 HTTP 请求，跨系统比较要先对齐口径。

12. 软件测试中，如何确定系统中的并发用户数？

🗣️ 回答重点

  • 五个依据。看业务需求里的用户规模和关键流程，翻历史日志算高峰期并发，跟业务和市场要增长预测，假设几种负载场景做估算，最后用工具实测验证。
  • 已经上线的系统，历史数据最可信。没上线的只能靠估算，估完一定要用工具跑一遍校准。

📈 拔高

  • 并发用户数不等于总用户数，也不等于同时在线的用户数。真正压到服务端的是同一时刻发请求的那批人。
  • 光看最大并发没意义，要看负载分布：这些用户是集中在同一个接口，还是散在不同模块，结果完全不同。
  • 除了并发数还要同时看响应时间、吞吐量、错误率和资源利用率。只看并发数达标不算通过。
  • 并发数是会变的。每次大版本发布都应该复测，最好接进 CI 自动跑。
  • 分析瓶颈可以借助 New Relic 或 AppDynamics 这类 APM，能直接看到哪个服务在拖后腿。

13. 如何确定性能测试是在什么环境执行的？

🗣️ 回答重点

  • 五个维度都要记下来：机房还是云、硬件配置、软件版本、网络环境、测试工具及其版本。
  • 硬件看 CPU 核数和主频、内存大小、磁盘是 SSD 还是 HDD、网络带宽。
  • 软件看操作系统版本、数据库版本、应用服务器和中间件版本。
  • 网络看有没有负载均衡、防火墙，它们的配置是什么。
  • 工具版本同样要记，不同版本的压测工具结果会有差异。

📈 拔高

  • 自有机房的物理机网络延迟小且稳定，云环境弹性好但抖动大，同一套参数结果可能不同。
  • 版本差异是最容易被忽略的变量。数据库小版本升级可能让一条查询快一倍，报告里不写版本，别人没法复现。
  • JMeter 在高并发下自身会吃掉压测机的 CPU 和网络。压测机配置不够，测出来的瓶颈可能是压测机自己，所以压测机也要记录。
  • 磁盘类型的差异比很多人想的大。HDD 的随机读写能力远低于 SSD，数据库场景换盘就能差好几倍。
  • 为了模拟真实用户，有时会故意在网络路径上注入延迟。这种人为因素必须写进环境描述。

14. 如何分析性能测试结果？

🗣️ 回答重点

  • 六步：收集数据、清洗数据、建立基线、做可视化、找瓶颈、给优化建议。
  • 清洗就是去掉异常值，比如网络抖动或者环境偶发故障造成的尖刺。
  • 基线可以选上个版本的结果，也可以选同类系统的数据。没有基线就没有「好还是坏」的判断。
  • 可视化用时间序列图，响应时间随时间怎么走，一眼就能看出哪个时间段有问题。

📈 拔高

  • 瓶颈的判定要看资源饱和点。CPU 长期接近 100% 就是 CPU 瓶颈，磁盘 await 高就是 IO 瓶颈，连接池打满就是配置瓶颈。
  • 清洗工具不限于脚本，Excel、R、pandas 都能做。关键是清洗规则要写进报告，别人才能复核。
  • 基线要跟着版本更新。一直用一年前的基线比，数据早就不可比了。
  • 可视化工具按数据量选：小规模用 Excel 或 Grafana，需要复杂图表再上 Tableau。
  • 分析工具别只用一个。JMeter 出原始数据，Prometheus 加 Grafana 看资源趋势，APM 看链路耗时分布，三者对不上就说明有一环没测准。
  • 优化建议要具体到可执行：哪条 SQL 加索引，哪个接口加缓存，哪个服务拆出去。写「性能有待优化」等于没写。

15. 软件测试中，Think Time 的作用是什么？

🗣️ 回答重点

  • Think Time 模拟真实用户在操作之间的思考和阅读停顿，不是随便加个固定延时。
  • 它的作用是让虚拟用户的节奏接近真人，测试结果才有参考价值。
  • 测极限压力时把它调小甚至去掉，让请求密集打过去。测真实业务负载时按真实间隔设置。

📈 拔高

  • 去掉 Think Time 会让请求几乎无间隔连发，服务器被瞬间淹没，RPS 虚高、响应时间失真。这种数据不能用来评估真实用户体感。
  • 真实间隔从日志里算：同一用户两次请求的时间差就是天然的 Think Time，取中位数比拍脑袋准。
  • 场景不同间隔差别很大。电商选购要反复比较，间隔长。在线游戏点击频繁，间隔短。
  • LoadRunner 提供固定和随机两种模式。随机模式更接近真人，因为没人会精确停 5 秒。
  • Think Time 会影响虚拟用户的分布，进而影响实际并发。改了这个参数，前后数据就不能直接比。

16. 软件测试中，接口的响应时间不达标时怎么办？

🗣️ 回答重点

  • 先定位再优化，顺序不能反。
  • 第一步确认是哪个接口超标，超了多少，是稳定超标还是偶发。
  • 第二步看日志和监控：应用日志找慢方法，慢查询日志找慢 SQL，APM 看链路里哪一段耗时最长。
  • 第三步才谈手段：改代码和算法、加索引、加缓存、上负载均衡、异步化。

📈 拔高

  • 「你怎么知道瓶颈在那」是这题真正的考点。答不出定位过程，只报工具名，会被继续追问到答不上来。
  • 常见瓶颈位置：数据库慢查询和锁等待、外部 API 调用、序列化开销、连接池或线程池配置过小。
  • 高并发场景下负载均衡是关键手段。用 Nginx 或 HAProxy 把流量分到多台机器，单机压力立刻降下来。
  • 耗时长的任务可以改成异步加消息队列（RabbitMQ、Kafka），避免阻塞主线程。
  • 上下游依赖也会拖慢响应。外部接口慢就做服务降级，或者换一个更快的供应商。
  • 静态资源和大文件走 CDN，能间接降低接口压力。
  • 优化完必须复测，用同一套用例同一套环境。不复测等于没优化。

17. 你认为 APP 性能测试需要重点关注哪些方面？

🗣️ 回答重点

  • 六个方面：启动时间、响应时间、资源使用率、流畅度、稳定性、网络性能。
  • 启动时间重点看首次启动。冷启动要加载资源、初始化数据，比热启动慢很多，优化上用懒加载。
  • 响应时间看点击和跳转，优化方向是前后台处理分离，把耗时操作放子线程，同时给用户合理的等待提示。
  • 流畅度用帧率衡量，Android 看 Choreographer，iOS 看 CADisplayLink。
  • 稳定性看崩溃和长时间运行表现，用 Crashlytics 这类工具收集崩溃日志。

📈 拔高

  • 300ms 这个阈值在业内流传很广，但它不是权威标准。Nielsen 的经典三档是 0.1 秒、1 秒、10 秒：0.1 秒内用户觉得即时，1 秒内思路不断，超过 1 秒明显影响流畅感。面试时说「业内经验值在几百毫秒量级」比说死 300ms 更稳。
  • 60fps 有官方依据，对应每帧 16.7ms，这是 Android 和 iOS 都在用的流畅目标。
  • 资源使用率里耗电最容易被漏。长期高占用会让设备发热，发热又会降频，最后表现成卡顿。
  • 网络性能要覆盖弱网和高延迟，还要覆盖 Wi-Fi 和蜂窝切换这种真实场景。
  • 稳定性问题要提前做异常处理，网络请求和文件操作是最容易出错的模块。第三方 SDK 也要跟版本并做兼容测试。

18. 有哪些常见的 APP 性能测试的关注点？

🗣️ 回答重点

  • 七个：响应时间、流量消耗、CPU 和内存占用、耗电、稳定性、兼容性、网络状况。
  • 流量和耗电是移动端特有的，Web 性能测试里没有，面试时主动提这两点很加分。
  • 工具别用错：JMeter 和 LoadRunner 压的是后端接口，App 本身的资源要看 Android Profiler 和 iOS Instruments。
  • 方法上分四类：压力测试看极限，负载测试看不同负载下的表现，峰值测试看瞬间流量，耐久测试看长时间运行。

📈 拔高

  • 把 JMeter 说成移动端性能工具是典型失分点。它能压接口，但看不到 App 的 CPU、内存、耗电。
  • 兼容性算不算性能测试，看团队口径。多数团队把它单列，但它确实影响性能表现，机型差异会让同一版 App 在中低端机上卡顿。
  • 优化手段要能落地：代码层面减少不必要的计算，图片用合适的格式和尺寸，网络请求合并并用缓存，资源管理避免泄漏和频繁 GC。
  • 监控和预警要提前做。等到用户投诉卡顿再查，成本高得多。

19. 常见的 APP 性能测试工具有哪些？

🗣️ 回答重点

  • 先说清楚分类，再报名字。压测类：JMeter、LoadRunner。移动端自动化：Appium、Robotium。云真机：Firebase Test Lab。分发和崩溃收集：TestFlight。
  • Appium 是开源的跨平台自动化框架，基于 W3C WebDriver 协议，支持 Android 和 iOS，客户端语言有 Java、Python、Ruby、JavaScript、C#。
  • JMeter 压接口，支持多种协议，插件生态好。
  • LoadRunner 是企业级压测工具，协议覆盖广，报告详细。

📈 拔高

  • Appium 不是性能测试工具。它做功能自动化，做不了并发压测。把它说成性能工具，追问并发场景就答不上来。
  • Robotium 只支持 Android，且多年不更新，新项目基本不用了。
  • TestFlight 是分发和内测渠道，顺带收集崩溃，不是压测工具。
  • Firebase Test Lab 的价值在真机矩阵，能覆盖大量机型和系统版本，跑兼容性和启动耗时很合适。
  • 面试时能说清「每个工具在什么场景用」，比背一长串名字更有说服力。

20. 常见的性能测试方法有哪些？

🗣️ 回答重点

  • 六种：负载测试、压力测试、容量测试、基准测试、并发测试、稳定性测试。
  • 负载测试看预期负载下的表现，压力测试把负载加到超过设计值，看什么时候崩。
  • 容量测试找最大处理能力，用来做资源规划。
  • 基准测试用固定条件测出数据，做横向和纵向对比。
  • 稳定性测试长时间跑，又叫疲劳测试，专门查内存泄漏和资源耗尽。

📈 拔高

  • 负载测试和压力测试的界线要能一句话说清：一个在预期负载内看表现，一个超出预期看极限和崩溃点。说反了这题基本就废了。
  • 容量测试和负载测试很像，区别在侧重点。容量测试关心最大能扛多少，负载测试关心给定负载下稳不稳。
  • 基准测试的关键是条件固定。脚本、数据、环境都固定，数据才有可比性，否则每次跑出来的数都不一样。
  • 并发测试关注资源竞争，比如同一行库存被多个请求同时扣减，这类问题在常规负载测试里看不出来。

21. 性能测试的目的是什么？

🗣️ 回答重点

  • 评估系统在特定负载和环境下的表现，落到具体指标上：响应时间、吞吐量、资源利用率、高负载下的稳定性。
  • 回答不能停在「评估性能」四个字，要说出拿哪些指标评估。
  • 往上一层，性能测试还支撑容量规划、给优化建议、用基准测试跟踪性能退化。

📈 拔高

  • 容量规划的价值在于提前买机器，而不是等线上崩了再扩容。压测出来的曲线就是采购依据。
  • 基准测试要定期跑。同一套用例每月跑一次，性能曲线往下走就说明有代码在拖后腿。
  • 性能测试不是压力测试的同义词。压力测试只是其中一种方法，目的是找崩溃点。
  • 稳定性这一项要单独说。长时间运行才能暴露内存泄漏和资源耗尽，短时间的压测看不出来。

22. 做好性能测试工作的关键是什么？

🗣️ 回答重点

  • 五个要素：明确指标、设计合理场景、保证环境一致、持续监控分析、反复测试优化。
  • 明确指标是前提。没有目标数字，测完也不知道算不算通过。
  • 场景要覆盖真实用户行为，包括正常压力和极端压力。
  • 环境一致性最容易被忽视。测试环境和生产差太多，结果只能参考，不能作为上线依据。

📈 拔高

  • 环境不一致的具体影响：数据量差一个数量级，慢查询根本不会出现。机器少一半，压出来的瓶颈全在 CPU 上，看不到真实的 IO 问题。
  • 监控不是测完再看，是压测过程中实时看。曲线突然掉头的那一秒，往往就是瓶颈出现的位置。
  • 优化是迭代的。一轮测试只能发现一层瓶颈，修完下一轮才会露出第二层。
  • 反复优化的具体手段包括改代码、优化数据库查询、调整架构。每次都回到测试环节验证，不验证就不知道有没有效果。

23. 服务端性能测试可以从哪些角度进行？

🗣️ 回答重点

  • 七个角度：负载、压力、容量、基准、稳定性、可扩展性、配置。
  • 负载和压力前面说过。容量测最大处理能力，基准测固定条件下的表现。
  • 稳定性让系统长时间跑，查内存泄漏和句柄泄漏。
  • 可扩展性看加机器之后性能涨不涨，配置测试看不同参数组合哪个最优。

📈 拔高

  • 可扩展性和配置测试是两个最容易被漏的角度，也最容易被追问。
  • 加了一倍机器，TPS 只涨 30%，说明架构里有单点或者共享资源在卡，这时候该重构而不是继续加机器。
  • 配置测试能省真金白银。连接池从 20 调到 50、JVM 堆从 4G 调到 6G，可能比加一台机器更有效。
  • 稳定性测试的做法是持续高负载跑数小时到数天，重点看内存曲线和句柄数量有没有单调上涨。
  • 每个角度都要能说出具体手段，只会报名词会被一句「具体怎么做」问穿。

24. 什么是压力测试、负载测试以及性能测试？

🗣️ 回答重点

  • 性能测试是总称，压力测试和负载测试都是它的子集。
  • 负载测试在预期负载内看表现，确认系统在预期用户量下还能保持可接受的响应时间。
  • 压力测试把负载加到超出设计值，一直压到崩溃，找出瓶颈和崩溃点。
  • 实际项目里三种会一起做，组合成完整方案。

📈 拔高

  • 负载水平说反是这题最常见的错。负载测试是正常工作负载，压力测试是超负荷。
  • 压力测试的重点在关键业务系统上：金融、电商、在线游戏，崩一次损失很大。
  • 负载测试常设多个档位，从低到高逐步加，直到出现明显拐点，这个拐点就是系统容量。
  • 工具上 LoadRunner、JMeter、Gatling 都能做，选型看协议覆盖和团队熟悉度。

25. LoadRunner 的工作原理是什么？

🗣️ 回答重点

  • 四个部分。VuGen 录制并生成脚本，Controller 编排场景并分配负载生成器，Load Generator 实际发请求造负载，Analysis 分析结果出报告。
  • 数据流是单向的：脚本从 VuGen 出来，进 Controller 调度，由 Load Generator 执行，结果汇到 Analysis。

📈 拔高

  • 官方名是 Analysis，不是 Analyzer。现在的产品名是 LoadRunner Professional，云压测能力由独立产品 LoadRunner Cloud 提供，不是套件内置。
  • 它的价值在于模拟并发加找瓶颈，不是「支持的协议多」。协议多是手段，不是卖点。
  • 协议覆盖确实广：Web、数据库、消息队列、SAP、Citrix 都有支持，复杂系统里这一项很关键。
  • 负载生成器可以部署在不同机器和不同地域，模拟跨网络访问，比单机造出来的负载真实。
  • 面试时能把四个组件的分工和数据流讲清楚，比罗列优势更有说服力。

26. LoadRunner 如何录制和编写脚本？

🗣️ 回答重点

  • 录制：VuGen 新建脚本选协议，点录制，输入 URL，操作页面，停止录制生成脚本。
  • 增强：参数化把用户名密码这类硬编码数据换成参数，加检查点验证响应对不对，把一串操作定义成事务来测响应时间，写错误处理让脚本出错不至于中断。
  • 调试：在 VuGen 里回放，确认参数和检查点都正常。
  • 然后进 Controller 配场景，跑完用 Analysis 看报告。

📈 拔高

  • 录制完不能直接跑。没参数化，所有虚拟用户都是同一个账号。没事务，测不出响应时间。没检查点，出错也看不出来。
  • 动态值（会话 ID、令牌）要靠关联处理，VuGen 提供自动和手动两种方式。不做关联，回放必然失败。
  • 脚本层用的是 C 语言，循环、条件判断都能写，复杂逻辑靠它实现。
  • 协议选择要匹配被测系统。Web 应用选 HTTP/HTML，Web Service 选对应协议，选错协议脚本根本录不出来。
  • Controller 里能配多个虚拟用户并行，也能配不同行为策略，接近真实用户分布。

27. LoadRunner 中的 Think Time 有什么作用？

🗣️ 回答重点

  • 模拟虚拟用户在操作之间的停顿，让行为接近真人。
  • 峰值负载测试里通常会减小甚至去掉，让请求更密集，逼近系统极限。
  • 常规性能测试里按真实用户节奏设置，测出来的才是真实业务表现。

📈 拔高

  • 去掉 Think Time 会让服务器被连发请求淹没，得到的是失真数据，测不出真实瓶颈。
  • LoadRunner 提供固定和随机两种模式。固定适合做对比实验，随机更贴近真人。
  • Think Time 会影响虚拟用户的分布，进而影响实际并发。改了这个参数，前后数据就不能直接比。
  • 设置依据是日志和用户行为数据，不是经验数字。不同环节的间隔应该分别统计。

28. 在搜索引擎中输入汉字可以解析到对应的域名，请问如何用 LoadRunner 进行测试？

🗣️ 回答重点

  • 建脚本时选 Web (HTTP/HTML) 协议，因为测的是浏览器访问行为。
  • 录制：输入要测的地址，输入汉字，观察解析过程，LoadRunner 会记录下这些 HTTP 请求。
  • 参数化：建参数文件装不同的汉字，让每个虚拟用户输入不同的内容。
  • 关联：把会话 ID 和令牌这类动态值提取出来，否则回放必然失败。
  • 回放验证通过后进 Controller 配场景，设虚拟用户数、持续时间和负载模式，跑完用 Analysis 分析。

📈 拔高

  • 这题真正考的是完整链路：录制、参数化、关联、回放验证、场景编排、结果分析。漏掉关联和参数化是最常见的失分点。
  • 参数文件的内容要覆盖真实输入分布。全是生僻字或者全是热门词，测出来的压力不一样。
  • 负载模式选渐进加载，一次打满会跳过中间负载下的瓶颈。
  • 场景里要监控响应时间、吞吐量和错误率，只看测试有没有跑完没有意义。

29. 性能测试怎么进行？性能测试的流程是什么？

🗣️ 回答重点

  • 七步：需求分析、搭环境、设计用例、执行、分析结果、出报告、优化后再测。
  • 需求分析要定两件事：基线是什么，用户行为怎么模拟。
  • 执行阶段要实时监控资源并记录日志，出了问题才有据可查。
  • 最后一步是闭环。优化完必须再测，直到达到预期指标。

📈 拔高

  • 交完报告不等于结束。绝大多数性能问题要改几轮才能收敛，流程图画成直线会被追问。
  • 需求分析阶段最容易被跳过，但后面所有结论都以它为参照。基线没定，数据好坏无从判断。
  • 设计用例时要选最有代表性的用户操作路径，再定义负载模型：平稳负载、渐增负载、尖峰负载。
  • 工具按规模选：小项目 JMeter 够用，大型复杂系统才考虑 LoadRunner。
  • 报告要包含环境、过程、结果和优化建议，用图表展示关键指标，否则没人愿意看。

30. 什么是性能测试的环境配置？

🗣️ 回答重点

  • 为性能测试专门准备的硬件、软件、网络和安全配置，目标是尽量还原生产环境。
  • 服务器配置对齐生产：CPU、内存、磁盘类型、操作系统版本、中间件版本。
  • 数据库要造一份和生产同量级的数据集，数据量差太多，慢查询根本跑不出来。
  • 网络要模拟带宽、延迟、抖动和丢包，企业内部系统还要考虑内外网连接。
  • 环境要和开发、生产隔离，避免互相影响。

📈 拔高

  • 环境隔离不只是为了干净，也是为了数据安全。压测会产生大量脏数据，打到生产库是事故。
  • 监控工具（Grafana、Prometheus、Nagios）也要提前配好，压测过程中才看得到资源曲线。
  • 测试脚本要持续维护。接口改一个字段脚本就失效，不维护的脚本半年后基本跑不起来。
  • 安全配置别漏。压测涉及大量真实数据，脱敏和访问控制要在准备阶段做掉。
  • 数据库索引和并发连接数也要对齐生产，这两项对结果的影响比硬件还大。

31. 性能测试计划包括哪些内容？

🗣️ 回答重点

  • 十项：测试目标、测试环境、测试数据、测试工具、测试场景、监控与度量、测试步骤、风险评估与缓解、资源分配、报告与分析。
  • 目标要写成可验证的数字，比如响应时间不超过 2 秒、并发 500 时错误率低于 1%。
  • 场景要写清楚用户行为、并发数量和负载模式。
  • 风险与缓解、资源分配这两项最常被漏，但它们决定计划能不能落地。

📈 拔高

  • 风险项要具体：生产数据拿不到怎么办，压测窗口和业务高峰撞了怎么办，压测机不够怎么办。写「注意风险」没有意义。
  • 计划之外还要配套动作：正式测试前先跑基准，负载用渐进方式加，长时间跑一轮 Soak 查泄漏，最后接进 CI 定期回归。
  • 并发用户模拟靠具体的操作脚本，脚本越接近真实用户，结果越可信。
  • 计划是给评审用的。评审时没人问的项，往往就是漏掉的项。

32. 性能测试报告包括哪些内容？

🗣️ 回答重点

  • 七部分：范围和目标、环境描述、工具及版本、用例设计、结果分析、瓶颈及措施、结论与建议。
  • 环境描述要能让人复现：服务器配置、系统版本、网络带宽都写清楚。
  • 工具版本必须写。同一份脚本，JMeter 5.4 和 5.6 跑出来的数可能不一样。
  • 结论与建议是给决策者看的，要能直接支撑「能不能上线」这个判断。

📈 拔高

  • 报告里最有价值的是结论和建议，不是数据表。数据谁都能贴，判断才体现专业度。
  • 结果分析要带对比：和基线比、和上一版比、和预期指标比。孤立的一组数字没有意义。
  • 瓶颈那部分要写清楚定位过程和证据，写「性能有待优化」等于没分析。
  • 用例设计也要写进去。并发数、事务类型、请求频率这些参数不写，别人没法复现你的测试。

33. 软件测试中，什么是内存泄露？什么是内存溢出？

🗣️ 回答重点

  • 内存泄露是分配出去的内存没释放或者丢了引用，回收不回来。它会累积，长期跑下去才表现为内存不足。
  • 内存溢出（OutOfMemory，OOM）是申请的内存超过可用上限，分配直接失败，表现为异常或者崩溃。
  • 一句话区分：泄露是该还的没还，溢出是想要的太多。

📈 拔高

  • 术语上更准确的说法是「内存不足」，不是「内存溢出」。缓冲区溢出是越界写入，和内存耗尽完全是两回事，别混着说。
  • 泄露的后果不必然是耗尽内存。泄漏速度很慢的系统可能几年都不出问题，但一旦叠加流量高峰就会爆。
  • 有 GC 的语言也会泄漏：静态集合只加不删、监听器注册了没注销、ThreadLocal 用完不清，这些 GC 都回收不了。
  • 溢出的成因多半是数据结构设计不合理，或者处理超大数据量时没估算内存上限。
  • 检测工具：C 和 C++ 用 Valgrind，Android 用 Memory Profiler 和 LeakCanary，Java 用 VisualVM 或 MAT 分析堆转储。

34. 软件测试中，什么是吞吐量和吞吐率？

🗣️ 回答重点

  • 吞吐量是单位时间内系统处理的事务量，时间单位可以是秒、分钟、小时。
  • TPS 是每秒处理的事务数，是吞吐量按「每秒」计量时的数值。
  • 换算要会：一分钟处理 600 个订单，吞吐量是 600 单每分钟，TPS 是 10。

📈 拔高

  • 「吞吐率就是 TPS」这个说法不严谨。吞吐率是带时间单位的处理速率，TPS 只是它的一种单位表达。面试时把口径说清楚，比背一个定义更稳。
  • 两个指标都要和响应时间一起看。吞吐高但响应慢，说明系统在硬扛，用户体感很差。
  • 测量靠压测工具，趋势观察靠 Prometheus 加 Grafana。
  • 提升手段无非三条：改硬件配置、优化代码、改架构。先定位再动手，别一上来就加机器。

35. 软件测试中，吞吐量、吞吐率和负载之间有什么关系？

🗣️ 回答重点

  • 负载上去，吞吐量先上升，到某个点之后趋于平稳，再往上加就开始下降。
  • 响应时间随负载增加而变长，接近容量时上升速度明显加快。
  • 负载不只是并发用户数，还包括 CPU 负载、内存占用、磁盘 IO 压力。

📈 拔高

  • 曲线的拐点是这题的考点。拐点之前加负载有收益，拐点之后加负载只会拖垮响应时间。
  • 很多资料说吞吐量和吞吐率是同义词，严格讲口径不同，吞吐率可以带任意时间单位。
  • 实际用法上，拐点位置决定了扩容阈值。容量规划就是围绕这个点做的。
  • 负载的定义比很多人想得宽。只把并发用户数当负载，会漏掉批处理任务和后台同步这类非用户流量。

36. 软件测试中，服务器满载时吞吐量和响应时间是如何变化的？

🗣️ 回答重点

  • 满载之后吞吐量不再增长，甚至下降。资源用尽，新请求只能排队或者被拒绝。
  • 响应时间在低负载时比较平稳，接近满载时急剧上升。
  • 这两条要一起说，只说吞吐或者只说响应时间都不完整。

📈 拔高

  • 「指数级增长」这个说法不严谨。排队论里 M/M/1 的响应时间是双曲线式的，利用率趋近 1 时垂直发散，形状像指数但机制不同。说「接近饱和点时急剧上升」更准确。
  • 曲线上有两个点值得记：拐点是性能开始劣化的位置，崩溃点是系统完全撑不住的位置。两者之间还有一段缓冲。
  • 瓶颈效应：任何一项资源成为短板，整个系统都会被拖住。磁盘 IO 打满时，CPU 再空闲也没用。
  • 救场手段按成本排：先加缓存和优化查询，再考虑负载均衡，最后才是加机器。

37. 软件测试中，如何估算接口的 TPS 指标？

🗣️ 回答重点

  • 七步：明确测试目标、准备测试环境、选择测试工具、设计测试用例、逐步加压执行、收集数据算 TPS、结果验证。
  • 环境越接近生产，结果越可信。网络延迟和数据库性能尤其要对齐。
  • 加压要逐步加，一步打满会让系统直接崩，测不出中间过程。
  • 算出来的 TPS 要和响应时间、成功率一起报，单独一个数说明不了问题。

📈 拔高

  • 这题真正被追问的是「你这个数怎么来的」。能说清链路，比报一个漂亮的数字更有说服力。
  • 不同业务场景的 TPS 要求完全不同。秒杀和日常浏览不是一个量级，目标要先定清楚。
  • 用例设计要覆盖典型场景：普通操作、高并发操作、异常情况。用例不合理，测出来的 TPS 没有代表性。
  • 验证环节别省。测出来的 TPS 和预期对不上，要么环境有问题，要么瓶颈没找到，都得回头查。
  • 结果不达标就进调优：对比基线找差距，定位瓶颈，改完再测一轮。

38. 什么是稳定性测试？如何进行稳定性测试？

🗣️ 回答重点

  • 让系统长时间连续运行，看会不会崩溃、有没有内存泄漏、性能有没有逐步下滑。
  • 步骤：定目标和范围、选工具、定计划（环境、负载模式、时长）、执行、监控收集、分析出报告。
  • 负载模式通常选恒定负载，模拟线上稳定期的持续压力。
  • 时长一般按业务周期定，至少覆盖一个完整的高峰到低谷。

📈 拔高

  • 稳定性测试不是独立的一类，它和压力测试、负载测试、容量测试一起构成完整的评估方案。
  • 判断标准不能只看崩没崩。内存曲线持续上涨、GC 频率变高、响应时间缓慢变长，都是失败信号。
  • 工具组合：压测用 JMeter 或 LoadRunner，监控用 Prometheus 加 Grafana，日志分析用 ELK。
  • 这类测试最怕环境不稳定。测试机自己抖动一次，前面跑的几个小时就白跑了，所以环境隔离要做好。

39. 软件性能测试中，如何实现 20 并发 40 次循环？

🗣️ 回答重点

  • JMeter 里线程组的线程数填 20，代表 20 个并发用户。循环次数填 40，代表每个用户跑 40 轮。
  • 总请求量是 20 乘 40，等于 800 次。
  • 在线程组下加 HTTP 请求采样器，配上监听器，跑完看汇总报告。

📈 拔高

  • 线程数和循环次数的归属别说反。说反了，压出来的量级差 20 倍。
  • 设置只是起点。压测过程中要盯 CPU、内存、磁盘 IO，否则资源瓶颈会污染结果。
  • 单机扛不住就上分布式，用多台压测机分片。
  • 加一点 Think Time 更接近真实用户。纯连发测出来的是接口上限，不是业务表现。
  • 这个需求换个工具也能做：LoadRunner 用虚拟用户数和迭代次数，Gatling 用注入模型，思路一样。

40. 软件性能测试中，QPS 如何从 200 慢慢加载到 300 和 400？

🗣️ 回答重点

  • 用渐进式加压。起点 QPS 200，每次加 50，按 200、250、300、350、400 这样走。
  • 每一档保持 5 分钟左右的稳定期，观察系统在这档负载下的表现。
  • 全程监控 CPU、内存、响应时间、错误率。
  • 每一档的数据单独记录，最后对比哪一档开始出现劣化。

📈 拔高

  • 稳定期的作用是让系统进入稳态。刚加压的那几十秒里缓存还没热、连接池还在扩，数据不代表这一档的真实水平。
  • 工具都能实现：JMeter 用线程组加调度器，Gatling 用注入模型，Locust 用自定义负载形状。
  • 一次拉到 400 会跳过中间档，也就看不到拐点出现在哪一档。
  • 加压过程中顺便观察可扩展性：资源加上去了，QPS 能不能同比例涨。
  • 用户行为也要模拟，全是同一接口的请求会把缓存命中率拉到虚高，测出来偏乐观。

41. 压力测试返回数据报错时如何定位问题？

🗣️ 回答重点

  • 六步：查日志、复现问题、分析返回数据、检查系统资源、核对配置、监控依赖服务。
  • 日志分三类：系统日志看内核和进程级问题，应用日志看异常栈和业务逻辑，数据库日志看慢查询和死锁。
  • 复现要在同环境同负载下做，用 JMeter 或 Gatling 打同样的并发，确认不是偶发。
  • 返回数据对比预期和实际，必要时用 Wireshark 抓包，看传输过程中数据有没有丢失或变形。
  • 资源用 Prometheus、Grafana、Zabbix 持续盯，确认不是内存泄漏或带宽打满导致的报错。

📈 拔高

  • 「看日志啊」是最差的回答，因为它没有顺序也没有手段。面试官要的是链路。
  • 配置不一致导致的报错最隐蔽。压测环境的连接池比生产小一半，跑到一定并发必然报超时，这种问题重启一万次也没用。
  • 微服务架构下要查依赖链。上游服务超时会让下游返回一堆 5xx，真正的根因可能在链路末端。
  • 重启能解决的报错，说明是状态问题而不是容量问题，两类问题的处理方式完全不同。
  • 报错也可能是测试脚本自己的问题，比如参数化数据重复导致主键冲突。先排除这一层，再怀疑系统。

42. 软件测试中，说说你对性能调优的理解？

🗣️ 回答重点

  • 调优是闭环：先压测拿基准数据，再分析瓶颈，再针对性改，改完再测。
  • 核心是识别并消除瓶颈，不是把每个参数都调一遍。
  • 四个层面都要覆盖：硬件、系统配置、应用代码、数据库。
  • 调优前先定目标。响应时间不超过 2 秒、能扛住多少并发，这些数字定下来，才知道什么时候停。

📈 拔高

  • 避免过度优化。把精力放在主要瓶颈上，为了 1% 的提升把代码改得没人看得懂，是负收益。
  • 常见手段对照瓶颈：CPU 高就优化算法或加机器，内存涨就查泄漏，慢 SQL 就加索引或改查询，锁等待就拆事务或换隔离级别。
  • 调优之后要继续监控。有些优化在压测环境有效，上线后流量结构变了就失效。
  • 数据库层面的手段要单独记：分库分表、索引优化、查询改写、加缓存，这几项通常是收益最大的。
  • 应用层面还有分布式部署和缓存，能分担单机压力。

43. 如果要实现万级别的并发测试，你会怎么做？

🗣️ 回答重点

  • 单机达不到万级并发，必须上分布式。用多台压测机，一台做主控，其余做执行节点。
  • 主控负责分发脚本和收集结果，执行节点负责发请求，节点之间的同步和结果汇总要提前配好。
  • 环境要和生产隔离，绝对不能直接压生产库。
  • 数据要提前准备，避免多个虚拟用户抢同一条记录造成锁冲突。

📈 拔高

  • 分布式压测最容易出问题的地方是主从协调：时间不同步、结果汇总丢失、某个节点挂了没被发现。
  • 压测机本身也会成为瓶颈。网络带宽、文件句柄数、端口耗尽，这些先排查一遍。
  • 定位瓶颈用 JProfiler 或 VisualVM 看应用内部，用监控看资源，两边对得上才能确认。
  • 虚拟用户的行为要贴近真实，全是同一接口同一参数，压出来的是缓存命中率，不是真实负载。
  • 数据量也要跟得上。并发到万级，数据库里只有几千条数据，测出来全是命中缓存的结果。

44. 软件测试中，如果用户并发需要慢慢加载，你如何设置？

🗣️ 回答重点

  • 分四段。起步用 10 到 20 个用户，之后每分钟加 10 到 20 个，到峰值后保持一段时间观察稳定性，最后逐步降下来看恢复情况。
  • 起步量要小，让系统有热身时间。
  • 保持阶段是重点，只有在这个阶段才能看出系统在目标负载下能不能长期稳住。
  • 降载阶段容易被忽略，但它能暴露资源释放问题，比如连接没回收、线程没退出。

📈 拔高

  • 加压节奏要有依据。每分钟加多少，取决于系统的预热速度和业务增长曲线，不是随便定的。
  • 加压前先做一轮基线测试，记录空载或低载时的表现，后面才有对比参照。
  • 监控要覆盖 CPU、内存、磁盘、网络，配合 Prometheus 和 Grafana 看趋势，而不是只看压测工具的报告。
  • 数据要提前准备够。压到高并发时数据不够用，虚拟用户会重复读同一条记录，测出来的数偏乐观。
  • 场景要贴近真实：随机页面访问、提交数据、上传文件混着来，比只压一个接口更能暴露问题。

45. 软件测试中，并发用户数与响应时间、吞吐量之间的关系是什么？

🗣️ 回答重点

  • 并发上去，响应时间变长，吞吐量先升后降。
  • 原因是资源被逐步耗尽：CPU 排队、内存吃紧、IO 打满，最后形成瓶颈。
  • 低并发时两者接近线性关系，接近容量后变成非线性，响应时间急剧上升。

📈 拔高

  • 系统容量就是这条曲线的拐点位置。超过它，加负载只会让体验更差。
  • 这条曲线指导两件事：什么时候扩容，什么时候优化代码。拐点靠前说明单机效率低，拐点靠后说明架构还有空间。
  • 实测用 JMeter 或 LoadRunner 分档加压，画出曲线，比背结论有说服力。
  • 优化手段跟着瓶颈走：负载均衡分摊压力，异步处理削峰，加缓存减少穿透。

46. 你们的性能测试需求从哪里来？

🗣️ 回答重点

  • 六个来源：业务需求、历史数据、竞争分析、用户反馈、行业标准、开发团队。
  • 业务需求最直接，产品会给出并发和响应时间的目标。
  • 历史数据最可靠，日志里能算出真实的高峰并发。
  • 开发团队会针对新功能主动提需求，比如新加了一个批量接口。

📈 拔高

  • 需求拿到之后要转成可测的指标。业务说「要快」，得追问快到什么程度，多少并发下快到什么程度。
  • 性能测试不该只在上线前做。接进 CI 之后，每次提交都能发现性能退化，修复成本低得多。
  • 竞争分析能给指标找个外部锚点，避免内部拍脑袋定一个没有依据的目标。
  • 需求落地要配套四件事：选测试类型、搭环境、上监控、定调优策略。缺一样都会卡在半路。

47. 你们的性能测试是做前端还是后端？

🗣️ 回答重点

  • 两边都做。前端看用户体验，后端看服务能力。
  • 前端关注页面加载、交互响应、静态资源大小、不同网络下的表现。工具用 Lighthouse 做实验室测量，PageSpeed Insights 结合真实用户数据。
  • 后端关注响应时间、吞吐量、并发能力、资源利用率，工具用 JMeter 或 LoadRunner。
  • 最后做端到端，模拟完整用户路径，看整体表现。

📈 拔高

  • PageSpeed Insights 的数据分两块：实验室数据由 Lighthouse 跑出来，实地数据来自 Chrome UX Report 的真实用户。两者结论不一致时，以实地数据为准。
  • 前端指标要落到具体项上，比如首屏时间、最大内容绘制和交互延迟，这些比笼统的「页面加载时间」有用。
  • 端到端测试能发现前后端各自达标但组合起来不达标的情况，比如接口快但首屏渲染慢。
  • 后端压测之外还要配压力测试找极限，配耐久测试查长期运行的泄漏。

48. 性能测试中，1000 人抢购中只有 10 人能成功，你会如何设置并发数？

🗣️ 回答重点

  • 按参与抢购的人数设并发，不按成功人数设。1000 人抢 10 件，并发就要模拟 1000 个用户同时打进来。
  • 重点是测系统在高并发下的行为：会不会锁死、会不会雪崩、错误率多少、响应时间多少。
  • 成功人数由业务规则决定，那是后台限流和库存扣减的结果，不是测试参数。

📈 拔高

  • 「并发数应设置为 1000」这个说法没有权威出处，它只是某些教材里的示例值。真正的并发数要按预估峰值和容量规划来定。
  • 真实打到后端的通常只是削峰、排队和限流之后剩下的那部分。压测时可以两种都测：原始峰值测极限，削峰后测业务实际压力。
  • 抢购场景要同时看成功率和响应时间。只有 10 个人成功，但如果另外 990 个人等了三秒才被告知失败，体验一样是灾难。
  • 高并发下重点查数据库锁和网络拥堵，这两处最先出问题。
  • 单机模拟不了上千并发时，用 JMeter 或 Locust 做分布式压测。

49. 测试一个项目接口的性能时，你会如何设置并发？

🗣️ 回答重点

  • 先定目标用户量。通过市场预估和历史数据，算出有多少人会同时访问这个接口。
  • 再分档设并发：50、100、500 这样往上走，看系统在每一档的表现。
  • 同时用渐进加载，从低并发慢慢加，比直接跳档更容易找到瓶颈。
  • 结果要重复跑几轮，单次数据可能是巧合。

📈 拔高

  • 环境一致性决定了数据能不能用。测试环境和生产差太多，压出来的瓶颈和线上不是同一个。
  • 分档测试的价值在于画出曲线。只测一档，你只知道「这档行不行」，不知道「还能扛多少」。
  • 监控要覆盖 CPU、内存、磁盘 IO、网络带宽，任何一个先饱和，结论就变了。
  • 场景定义要贴近真实：登录、查询、提交混着来，不要只压一个读接口。
  • 工具用 JMeter、LoadRunner 或 Gatling，三者都能配复杂场景并出报告。

50. 在性能测试时，你们一般的 CPU 和内存配置是多少？

🗣️ 回答重点

  • 没有统一数字，取决于业务场景和性能目标。原则是和生产的硬件配置对齐。
  • 生产用多核大内存，测试也用相近配置，这样测出来的结果才能作为上线依据。
  • 按应用类型调整：CPU 密集型看重核数和主频，IO 密集型（比如数据库）看重内存和磁盘性能。

📈 拔高

  • 成本受限时可以用虚拟化或容器起多实例并行压，用测试方法补硬件差距。但要在报告里写明配置差异，说明结论的适用边界。
  • 除了 CPU 和内存，还要看存储 IOPS 和网络带宽。这两项经常才是真正的短板。
  • 观察手段：Linux 下 top、htop、vmstat 看资源，配合 APM 看应用内部耗时，两边对上才敢下结论。
  • 配置不是拍脑袋定的，是拿基准测试跑出来的。换一套配置就该重测一轮，不能直接沿用旧结论。
