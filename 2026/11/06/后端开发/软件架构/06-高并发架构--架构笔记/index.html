06 高并发架构

📌 本篇速览

  • 并发数、QPS、RT 三角关系与单机容量
  • 缓存五层与 Cache Aside 读写姿势
  • 限流、熔断、降级保命机制
  • 消息队列削峰与解耦
  • 索引、防超卖与分库分表
  • 秒杀三层漏斗与阶梯压测

高并发不是加机器，是让流量在到达数据库之前被一层层挡掉。本文讲清缓存、限流、异步与分库分表这几张标准牌。

6.1 重新认识高并发：指标与单机容量

🔹 高并发先翻成数字。三个指标要分清：并发数是同一时刻正在处理的请求数；

📌 考点：并发数 ≈ QPS × RT；RT 上涨会线性放大并发数，线程池瞬间拉满。
QPS 是每秒处理的请求数，衡量吞吐量；RT 是响应时间，办一单要多久。三者关系是并发数约等于 QPS 乘 RT。

🔹 QPS 2000、RT 50 毫秒时，系统同时处理 100 个连接。RT 因一条慢 SQL 涨到 500 毫秒，并发数立刻变成 1000，资源占用翻十倍，线程池瞬间拉满。

Tomcat 默认 200 个工作线程，一个请求占一个线程到处理完才还。单机 QPS 约等于线程数除以 RT。接口快时 RT 50 毫秒能扛 4000 QPS，里面藏着一条没走索引的 SQL，RT 变成 500 毫秒就只剩 400 QPS。线程在等数据库的那 500 毫秒什么也没干，坑位却不让给别人，这就是纯浪费。

6.2 缓存：最便宜的并发

🔹 缓存是性价比最高的一招。一个几百 QPS 的接口加层缓存能扛到几千。但它意味着一份数据存两处，改了价格页面没变这类问题，根子都在缓存。

🔹 缓存分五层，越早挡越便宜：浏览器与 CDN 挡静态资源，请求连机房都不用进；网关缓存合并热点；本地缓存在 JVM 内存里是纳秒级；Redis 跨实例共享是主力；数据库是最终数据源。选型口诀是先问数据允许多旧再放哪层，命中率到 90% 时数据库只会看到十分之一流量。

6.2.1 读写标准姿势

🔹 标准姿势是 Cache Aside。读先查缓存，命中直接返，未命中查库并回写缓存，必须设 TTL。写先更新数据库再删缓存，删而非改，避免并发写乱序把旧值写回。### 6.2.2 三大经典异常

三大经典异常成因不同。穿透是查不存在的数据，缓存永远建不起来，用空值短缓存或布隆过滤器堵入口；击穿是热点 key 过期瞬间成千请求打穿库，用互斥锁只放一个去查或逻辑过期异步刷；雪崩是大片 key 同时过期或 Redis 宕机，TTL 加随机抖动摊开，再上哨兵集群加熔断限流兜底。

强一致的数据如余额库存不走缓存读路径，商品详情与排行接受毫秒窗口用缓存。删缓存本身可能失败，丢进消息队列重试，或订阅 binlog 自动删，要求更高用延迟双删。

异常 成因 解法
穿透 查无此数据，缓存建不起来 空值短缓存、布隆过滤器
击穿 热点 key 过期瞬间并发打库 互斥锁回填、逻辑过期
雪崩 大片 key 同过期或 Redis 宕机 TTL 加抖动、哨兵集群

6.3 限流、熔断与降级：系统的保命机制

🔹 流量超过系统容量时，与其让超额流量拖垮所有人，不如主动拒绝一部分，这叫限流。四种算法各有适用：固定窗口最简单但有窗口边界临界突刺；滑动窗口切成小格消除突刺；漏桶请求排队匀速流出，适合怕猛的下游；令牌桶匀速放令牌允许适度突发，是主流选择。限流还要看维度：全局、单机、用户级，用户级主要防刷防爬。

算法 特点 适用
固定窗口 每分钟数人头，有边界临界突刺 简单限流
滑动窗口 切小格消除突刺 平滑统计
漏桶 请求排队匀速流出 怕猛的下游
令牌桶 匀速发令牌允许突发 主流选择

🔹 熔断管的是下游挂了的情况。熔断器三态：闭合正常放行并统计失败率；打开直接拒绝走降级；半开放几个试探，成功恢复失败继续断，全程自动。降级保的是用户体验，返回兜底数据、简化流程或把写请求排进队列。熔断保护自己，降级保住体验，两者必须成对出现，跨服务调用务必设超时。

6.4 消息队列：把洪峰变成细水

🔹 同步下单串起扣库存、减优惠与发短信，8000 QPS 直接砸向数据库。改成异步：下单只预扣库存，扔一条消息立刻返回，消费者按 2000 QPS 平稳处理减优惠和发短信。洪峰 8000 落库只剩 2000，中间峰值被队列这个蓄水池吃掉，用户看到排队中几秒出订单。

🔹 异步还带来解耦，加一个发券需求只需加消费者，下单服务一行不改。代价是延迟、复杂度与幂等。消息必须重复消费也只干一次活，用订单号做唯一键，否则用户点几次就抢几次。

6.5 数据库层的四张牌

6.5.1 索引与防超卖

🔹 索引是基础。B+ 树把两百万行逐行比对变成约三到六次页访问

📌 考点：全表扫描秒级、索引毫秒级，差两三个数量级；慢查询日志每周清 top10。
（16KB 页约 3 层，主键查找约 3 次；二级索引需回表，最坏约 6 次，根/枝页多在缓冲池命中），全表扫描是秒级的同一条查询，改范围条件只要毫秒级，写法差一行性能差两三个数量级。上线卡点是扫描行数一大就该怀疑索引，慢查询日志每周清 top10。

🔹 防超卖是查库存、判足够、减库存三步有缝隙，并发请求插进缝隙就超卖。解法是把判断和扣减合并为原子动作。

📌 考点：防超卖用原子 UPDATE … WHERE cnt>0 或 Redis Lua 预扣，别用先查后改。
数据库里用 UPDATE stock SET cnt=cnt-1 WHERE id=? AND cnt>0，行锁保证一次只放行一个；或用 Redis 加 Lua 预扣，实战分层让请求先到 Redis 挡掉 99% 流量，预扣成功的少数再经消息队列落库。

🔹 分布式锁解决本地锁跨机器失效。synchronized 只锁一个 JVM，部署五台就是五个独立内存世界，锁要放到 Redis 或 ZooKeeper 这种大家都看得见的地方。Redisson 的 tryLock 带超时抢不到就快速失败，看门狗在业务跑超锁过期时间时自动续期。能用原子操作就别用锁，锁当兜底。

🔹 按《阿里巴巴 Java 开发手册》，单表行数超过 500 万行或容量超过 2GB 才推荐分库分表，按分片键哈希到 N 库 N 表，引入分布式 ID 和跨库聚合。分片键决定成败，订单按用户 ID 分则同用户订单总在一张表，查我的订单只碰一个分片。很多场景用归档（只留近一年热数据）就解决了，不必分库分表。最后做无状态水平扩容：把 session 外移 Redis、文件上对象存储、本地缓存只做可重建加速层，重启任意机器用户不掉线才叫无状态。

6.6 秒杀实战：三层漏斗

🔹 秒杀让三个最难条件同时出现。流量尖峰、热点行与绝对不能超卖。架构用三层漏斗接住。

📌 考点：秒杀三层漏斗——网关限流、Redis 原子预扣、消息队列落库；数据库只承受库存数量级请求。

第三层让进来的人公平抢。秒杀服务校验资格并用 Redis Lua 做原子预扣，单实例 Redis 简单命令官方基准约 18 万 QPS，但 Lua 脚本有额外开销（官方基准约 7 万/秒），预扣能否稳定十万级需按脚本与硬件实测，预扣失败返已抢完，成功的只剩库存数量级如 1000 笔扔进消息队列，订单服务慢慢落库，数据库从头到尾只建一千多个请求。

🔹 上线前用阶梯加压找拐点：并发从几十逐步加到几百时，QPS 停在两千多而 RT 猛涨到一百多毫秒，并发翻倍 QPS 不动就是容量拐点，限流阈值设在拐点略低的位置。估算值与实测值互证，才敢上线。

6.7 落地路线与常见坑

🔹 按阶段升级。阶段一止血，索引加缓存覆盖八成并发问题。阶段二防身，限流、熔断与异步做完系统就打不死。阶段三扩容，无状态、读写分离、归档与分库分表代价大，压测数据说了算才动。每阶段做完都做一次压测。

🔹 五个坑要避开。把会变的数据如库存缓存五分钟会导致超卖。无界队列和不设超时会内存溢出。消息队列不做幂等出现重复订单。压测环境和生产两张皮会得出错误结论。盲目加机器，慢 SQL 只会让烂查询跑在更多机器上。总原则是用便宜的再用贵的，先保命再提量，每步压测让数字说话。

6.8 常见错误清单

🔹 1. 把库存余额这类多变数据缓存几分钟，导致超卖，应走实时路径或只缓存静态信息。
2. 用无界队列且不设超时，请求越堆越多，最终内存溢出把服务拖死。
3. 消息队列不做幂等，用户重试一次就生成重复订单，应拿业务主键做唯一约束。
4. 限流只算算法不分层，全局单机用户级任一失守都没有下层兜底。
5. 缓存写路径用改而非删，并发写乱序把旧值写回，应删缓存并兜底重试。
6. 遇到慢 SQL 先加机器，烂查询只是跑在更多节点上，应先查索引。
7. 分布式锁用手搓 setnx，坑多且难续期，应用 Redisson 这类成熟实现。
8. 分库分表前不分片键想清楚，查询打满所有分片，拆分等于白做。
9. 压测只压到变慢就停，没找到崩塌点，限流阈值和容量规划都没有标尺。

6.9 小结

🔹 高并发的本质是漏斗。没有哪个数据库天生扛得住十万 QPS，但架构能让到达它的只有八百。遇到系统扛不住，第一反应是画漏斗，看问题出在层、哪层没挡住。组件会过时，这套漏斗方法不会。
