这篇从一次全站故障讲起，理清为什么要拆、怎么拆、拆完要补哪些治理能力，以及一条能落地的演进路线。

3.1 单体应用的得与失

🔹 想象一个把订单商品库存会员打成一个包的应用，大促前开发改了一行优惠券判断，要走全量回归，再灰度，最后审批，凌晨才上线。第二天优惠券抛空指针，所有模块共享同一 JVM 线程池，线程被占满，商品页打不开、下单挂掉，全站不可用几十分钟。根因和写错代码无关。所有代码属于同一个部署单元，没有只发优惠券的选项，这才是全站不可用的真正原因。

🔹 单体本身是好东西。一次打包一次部署，本地起个 main 方法就跑。调用是方法调用，不走网络无超时，一条堆栈从 controller 打到 mapper 秒级定位。一个 @Transactional 注解保证扣库存和扣余额要么都成要么都败。改类名 IDE 一键重命名全项目生效，重构成本最低。十人以内、流量平稳、产品处于验证期，单体就是最优解。

📌 考点：单体共享同一 JVM 线程池与部署单元，一处错全站不可用；能否单独重启、发版、扩容是判断要不要拆的标准。

3.2 微服务的定义与边界

🔹 微服务的判断标准只有一条：能不能单独重启、单独发版、单独扩容。它把一个大应用拆成一组微服务，每个独立开发部署运行，服务间用轻量协议调用。独立部署让改优惠券只发优惠券，十分钟内上线，回归只跑自己范围。独立部署让故障有隔离墙，优惠券崩了不影响商品页。按业务能力划分而非技术分层，订单库存账户各是一个服务。

🔹 拆的是运行时边界，不是代码目录。包分得再清仍在同一个 JVM、同一份数据库连接池，崩的还是整个进程，那叫模块化不是微服务。五个服务连同一个库、发版必须凑齐，那是分布式单体，把耦合原封不动留了五份还附赠网络不稳定，比单体更糟。

📌 考点：判断标准是能否单独重启、单独发版、单独扩容；模块化（同 JVM 同连接池）不是微服务，连同一库必须凑齐发版是分布式单体。

3.3 服务拆分的三条原则

🔹 服务拆分的三条原则：

  • 按业务能力拆而非技术分层：订单服务里装着 controller/service/DAO 全套，独立完成下单取消查询，而不是把 controller 拆成接口服务、service 拆成逻辑服务
  • 高内聚：经常一起改的代码放一块，回想最近三个需求都动哪些代码，它们该属于同一服务；每次改需求要跨三个服务发版就是边界画错了
  • 边界看数据归属：谁拥有这份数据谁就是主人，订单表归订单服务，别人改只能调接口

🔹 起步先拆三到五个天然独立的，别一上来拆二三十个。一个服务配两到八人小团队从头负责到底，这呼应康威定律：系统结构最终会长成组织的沟通结构。拆错了比不拆更贵，共享数据库必须一起发版的微服务就是分布式单体。

3.4 同步、异步与数据一致性

🔹 服务之间怎么说话？同步像打电话，下单调库存必须等返回，实时直观但对方慢你也慢、对方挂你也挂，必须配超时重试熔断。异步像发消息，下单成功发条订单已创建的消息就返回，通知积分报表各自消费，解耦且可削峰，结果最终一致，积分晚几秒到账能接受。判断口诀：这一步失败业务还能继续吗？库存没扣成订单不能继续就同步，短信晚发十秒无所谓就异步。

🔹 数据库拆开后 @Transactional 管不了两张表。三策略按推荐序：

  • 先质疑业务本身，能不能冻结后确认，各自本地事务
  • 其次用最终一致，发消息扣减、失败重试、不行反向补偿
  • 最后才用框架如 Seata 套全局事务

🔹 两条铁律：

  • 一个数据只有一个主人，不许幻想强一致
  • 网络会超时、消息会重复、服务会重启，方案必须假设它们发生并能自愈

📌 考点：强依赖用同步，可延迟的用异步；网络会超时、消息会重复、服务会重启，方案必须假设它们发生并能自愈。

维度 同步调用 异步消息
实时性 立即拿到结果 最终一致，有延迟
故障传播 对方挂你也挂 解耦，下游崩不影响主流程
适用 扣库存这类强依赖 发短信、加积分与统计

3.5 Spring Cloud 全家桶与版本

🔹 Spring Cloud 不是新框架，是一组解决前面六个麻烦的工具集，你的 Spring Boot 写法不变，多引几个 starter 加几行配置。三层版本联动：Spring Boot、Spring Cloud、Spring Cloud Alibaba，官方有版本对应表，配错常见 NoSuchMethodError、NoClassDefFoundError 等运行期错误，指向你没写过的类。新项目直接用 Spring Cloud Alibaba 套件：Nacos 管注册和配置，Sentinel 管熔断和限流，Seata 管分布式事务，中文资料多。Netflix 那套 Hystrix/Ribbon 已进入维护模式，Eureka 仍在维护，别再引入 Hystrix/Ribbon 背技术债。

🔹 刚起步的微服务项目通常只需注册中心和网关，链路、配置中心后面补，熔断事务等真出故障再引。技术不是越全越安全，多余能力本身也是负担。

📌 考点：Spring Cloud 全家桶里 Nacos 管注册与配置、Sentinel 管熔断限流、Seata 管分布式事务；Netflix 的 Hystrix/Ribbon 已进入维护模式。

下表列出组件与它们解决的麻烦。

组件 解决的麻烦
Nacos 地址会变、配置满天飞
Gateway 入口没人把守
OpenFeign 服务间调用写法繁琐
Sentinel 调用会失败、雪崩
Seata 跨服务数据不一致

3.6 注册中心与配置中心

🔹 地址会变是微服务的第一个麻烦。Nacos 工作机制：服务启动上报服务名加 IP 加端口；维护一份活着实例名单；靠心跳打卡维持存活，超时未打卡先标不健康、再摘掉，阈值由配置决定；调用方按服务名拉名单缓存在本地；调用时挑一台。服务重启期间调用方可能短暂找不到人，心跳还没超时名单没更新，调用代码必须容忍偶尔找不到加重试，这不是 bug 是机制属性。服务名要全局唯一稳定，是服务互认的唯一凭据。

🔹 配置中心还是 Nacos 第二个身份。二十个服务三套环境配置散在几十文件，改个库地址要改二十处重发二十次。配置放 Nacos 统一管，控制台改一条长轮询秒级通知服务动态刷新不重启。用 namespace 隔环境，group 隔业务线，data id 对应服务名。好处是可审计可回滚，谁改的何时改的一键回滚。Spring Boot 2.4+ 起默认禁用 bootstrap，Nacos 配置可用 spring.config.import 写在 application.yml；只有引入 spring-cloud-starter-bootstrap 后才用 bootstrap.yml。敏感信息仍要配合加密，Nacos 控制台谁登录都能看。

📌 考点：Nacos 靠心跳判活，超时未打卡先标不健康、再摘掉，阈值由配置决定；配置改一条长轮询秒级通知动态刷新。

3.7 网关、调用与熔断限流

🔹 网关是唯一入口，把鉴权限流日志跨域这些每个服务都要做的事集中做一次。一条路由等于一个断言（Predicate）加一组过滤器（Filter）加一个目标。Predicate 判断请求走不走这条路由，Filter 转发前验 token 记日志限流、响应后改头，还能把 user id 塞进请求头免去下游再解析。目标写 lb://order-service 按服务名去注册中心拿实例表再负载均衡，地址不写死。网关只做与业务无关的事，把判断优惠券能否用写进过滤器就危险了，它是门卫不是业务员。

🔹 服务间调用用 OpenFeign，声明接口加 @FeignClient 注解，方法签名照对方接口写，业务里注入后像调本地方法。Feign 启动生成动态代理，拼 HTTP、拿服务名查注册中心、负载均衡挑机器、解析响应。超时必须显式配置，默认超时对生产太宽，下游一卡线程全卡导致雪崩。雪崩是故障沿调用链放大。库存慢成五秒，订单每请求卡五秒，200 线程全卡死整个订单服务瘫。Sentinel 熔断器像保险丝，错误率超阈值进入打开状态直接拒绝快速失败释放线程，半开状态放小撮请求试探恢复。

📌 考点：网关只做鉴权限流等无关业务的事；Feign 必须显式配超时，否则下游卡住线程跟着卡引发雪崩。

3.8 链路追踪、消息与安全

🔹 一次下单穿过四五个服务，日志散在多台机器，用户投诉失败你总不能登四台机器按时间戳拼日志。给每个请求发个 trace id，进门生成、每经一服务跟着写进每条日志，查失败只搜这个 id，四台机器日志按顺序排好。trace 是一次完整调用链，span 是其中一环，trace id 靠 HTTP 头传递，框架自动做，但线程池里跑的异步代码 id 不自动跟过去要手动传，SkyWalking、OpenTelemetry Java agent 这类探针增强过的线池除外。存储展示用 Zipkin 轻量或 SkyWalking 带告警拓扑，日志聚合收进一处。

🔹 下单成功还要发短信加积分更统计，串在下单接口里下单变三秒还耦合，短信通道挂了下单跟着报错。放消息队列，订单服务发条消息立刻返回，消费者各自订阅。收益是解耦、削峰，达到最终一致。消息不免费。不能丢（生产者确认、MQ 持久化与消费者手动 ACK）、重复消费要幂等（数据库唯一键兜底）、顺序和积压要监控。安全上公网只进网关，认证服务签 JWT，网关验签解析把 user id 角色写进请求头转发下游，鉴权逻辑写一次，下游只管业务。JWT 前两段不加密谁都能看，手机号身份证别放 payload。

3.9 上线部署与演进路线

🔹 起步用单仓库多模块。shop-common 放 DTO 和工具，shop-api 放 Feign 接口定义，gateway 等各一模块。单仓库改公共代码一次提交全模块编译可见，拆五个仓库要改五次发五次。每个服务结构跟 Spring Boot 一样，只多一个放注册配置中心地址的 bootstrap.yml。四条约定：

  • 每服务只连自己库
  • common 只放 DTO 和工具别写业务规则
  • Feign 接口统一放 shop-api 防循环依赖
  • Spring 版本只在 pom 改一次

🔹 一次真实下单走九步：

  • 网关验 token 判权限限流记 trace id 路由
  • 订单服务建订单本地事务
  • Feign 调库存查注册中心负载均衡
  • 库存受 Sentinel 保护，熔断则快速失败
  • 调账户扣款
  • Seata 全局事务账户失败按 undo log 反向补偿
  • 成功发订单已创建消息返回
  • 下游各自消费幂等
  • 返回订单号，trace id 贯穿

🔹 中间件全用 docker compose 一条命令起，每服务一库从第一天遵守，启动先中间件再被依赖服务再订单最后网关。

🔹 Kubernetes 是运行平台，微服务是架构风格，两件事。三个演进阶段：

  • 一台机器多 jar 包靠手动
  • docker 容器化环境一致但不管调度自愈
  • K8S 接管自愈、滚动发布、弹性伸缩，和 Nacos 不冲突，一个管生死一个管地址

🔹 三五人四个服务没专职运维先用 docker compose 加脚本，K8S 出问题整集群没人兜底时复杂度大于收益。落地分三阶段：

  • 头三个月单体里按业务域划包边界禁跨域访问
  • 三到九月拆三五个核心服务建注册配置网关
  • 九个月后补链路熔断统一鉴权 CICD，最后才 K8S，治理能力跟着服务数量走

3.10 常见错误清单

⚠️ 为拆而拆切太细，一次下单跨好几个服务，排查一个 bug 开十几个窗口。
⚠️ 图省事让多服务共享数据库，得到比单体还难维护的分布式单体。
⚠️ 只拆服务不改组织，团队仍按技术分层，康威定律以故障形式讨回来。
⚠️ 没可观测性就上线，无 trace id 无告警，出问题靠用户投诉才发现。
⚠️ 一步到位上 K8S，服务和集群两头学，两头都没学明白。
⚠️ 网关里写业务逻辑，把判断优惠券能否用塞进过滤器，门卫变成业务员。
⚠️ Feign 不显式配超时，下游卡住线程跟着卡引发雪崩。
⚠️ 用 Seata 前不先问业务能否容忍不一致，热点高并发被全局锁排队。

3.11 小结

🔹 微服务用来治病，不是补品，项目没中单体那几道坎就继续写单体。拆的是进程和边界不是文件夹，能不能单独重启是判断标准。共享数据库的微服务是更贵的分布式单体。复杂度不会消失只会转移，把代码复杂度转成运维治理协作复杂度，必须按阶段走配得上团队规模。框架会更替，边界怎么画、代价怎么权衡永远是架构师自己的事。
