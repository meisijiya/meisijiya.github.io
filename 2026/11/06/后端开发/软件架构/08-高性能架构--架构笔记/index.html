高性能架构 — 缓存、异步与并行

高性能不是玄学，是算术。先测量，再定位，后优化，每一步都要留数字，因为快是用复杂度买来的。

每晚八点整点的秒杀，流量在五十九分五十九秒到八点整之间瞬间砸下来，之前一直平稳。一家生鲜电商预约人数到了四十二万，系统 QPS 从日常的二百爬到一万二。开抢那一刻下单接口响应时间从八十毫秒直接拉到八秒，移动端页面加载超过三秒就有五成三的访问被放弃。

8.1 八秒慢接口与死亡螺旋

🔹 事故当天值班同学紧急加十台应用服务器，响应时间不降反升，冲到十二秒。原因在瓶颈层不在应用层。数据库 CPU 已到百分之百，每台新实例都带着默认十个连接的连接池，排队连接从一百瞬间变三百，数据库更堵，并发更高，客户端超时重试更多，形成死亡螺旋。系统没宕机只是慢，但慢是另一种形式的宕机。

📌 考点：扩容只对有瓶颈的那一层有效；瓶颈在数据库却扩应用层会形成死亡螺旋。

这次事故留下一句结论。扩容只对有瓶颈的那一层有效。瓶颈在数据库，却去扩应用层，等于在堵车的路段又放一批车进去。十台机器本身没有做错什么，它们只是把更多的连接与线程砸向了已经瘫痪的数据库。问题从来不在加了多少机器，而在加到了哪一层。

8.2 四把尺子与两条定律

🔹 定性能目标要用 P99，而不是平均值。平均 RT 一百二十毫秒看似健康，P99 可能是八秒，意味着每百个请求里有一个转圈八秒。一万二千万请求按此比例就有十二万人次转圈，很可能多一条热搜。QPS 量的是接待能力不是速度，并发数是同时处理中的请求数，四者用利特尔法则串起：并发数等于 QPS 乘 RT。RT 一涨，同样 QPS 下并发必然暴涨，线程池和连接池随之填满，后来的请求排队，RT 更长，恶性循环。

木桶定律说总耗时由最慢那段决定。一条下单接口网关二毫秒、应用计算十五毫秒、渲染三毫秒，而 SQL 查询七千八百毫秒，把前三项全优化到零，总耗时还是七千八百毫秒出头。阿姆达尔定律回答优化一块板能快多少：占比大的才值得砍，占比小的砍出来没人感觉得到，且整体加速比有上限。

8.3 慢的四宗罪与四笔账

🔹 时间漏在哪有四类。网络往返每跨一次的延迟没有统一典型值，要分同可用区、跨可用区、跨区域，以云厂商区域延迟表或实测为准，串行调八个下游光路上就几十毫秒起步。计算与序列化是 CPU 做无用功，如大 JSON 反复序列化、循环里放本可外提的计算。锁与排队毫无价值，线程池排队、数据库行锁互等、同步块串行化，代码一行没跑时间却在流逝。IO 是最大头，内存纳秒级、磁盘毫秒级、跨网查库几十毫秒起步，慢 SQL、缺索引、循环查库的 N+1 全属此类。事故里 SQL 占七千八百毫秒，占九成七。

📌 考点：P99 而非平均值；并发数 = QPS × RT。

每一刀都有代价。复杂度账：加缓存要管失效，上异步要管补偿和幂等。一致性账：缓存里是上一刻的数据，异步是几秒前的结果，把绝对正确换成了最终正确。钱账：缓存集群、消息队列、更大内存都需采购。运维账：每个组件多一类故障模式、多一组监控指标。

8.4 性能四板斧

🔹 市面高性能组件几十个，底层只有四类动作。缓存把答案放在更近的地方，Redis、CDN、读写分离的读库本质同一件事。异步把不着急的事挪出主链路，Kafka、RabbitMQ、线程池队列都干这件事但消息模型不同：Kafka 是持久化日志、消费靠拉取按位点确认，RabbitMQ 是消息代理、推给消费者确认后删除，线程池队列仅在进程内。池化复用贵重资源，连接池、线程池、对象池本质同一件事。批量减少往返次数，批量插入、查询合并、下发本质同一件事。

板斧 原理 代价
缓存 用空间换时间，就近读 要管失效，一致性让步
异步 不着急的事往后放 最终一致，要幂等补偿
池化 复用连接与线程 配多大是学问
批量 减少网络往返 攒批要等，调参是学问

8.5 实战：八秒砍到九十毫秒

🔹 本机用 Docker 起 MySQL、Redis、RabbitMQ 三个容器，跑一个八秒慢接口。压测基线：QPS 六点二，P99 八点二秒，错误四千一百二十一，数据库 CPU 百分之百。接口慢在四宗罪集齐：三段 select 全表扫描无索引占五点八秒，循环查优惠券串行占一百二十毫秒，逐条 insert 无批量占部分，同步发短信加积分占部分。

第一斧缓存用 Caffeine 本地缓存，命中率九成二，数据库 QPS 从一万二掉到九百六十，P99 从八点二降到二点九秒。第二斧数据库本体抓慢日志头号通缉犯，用 explain 看 type 是 all、rows 近五百万、extra 有 filesort，建「商品 id 在前、创建时间在后」的联合索引，执行时间从一点八秒变十二毫秒，P99 降到一点一秒。第三斧异步把优惠券、短信、积分投进 MQ，主链路只留扣库存和下单，P99 降到二百四十毫秒。第四斧池化调参，按公式配连接数与线程数，P99 降到九十毫秒，全程零报错。四板斧砍完八秒变九十毫秒。压测环境要尽量干净，关掉 IDE 自动构建、别同时开着视频会议，本机压测最大的敌人是噪声。

降序索引能消掉 filesort 有前提：排序方向要与索引列一致，且前导列带等值条件，这条查询有 WHERE item_id = 1001 才用得上；没有等值条件的查询未必消得掉，上线前仍要 EXPLAIN 验证。

8.6 缓存一致性

🔹 缓存的翻车集中在三种异常。穿透是请求 key 在数据库也不存在，缓存形同虚设，解法缓存空值或布隆过滤器挡一道。击穿是热点 key 过期瞬间成千请求同查库，解法互斥重建或逻辑过期异步刷新。雪崩是一大批 key 同时失效或 Redis 宕机，解法过期加随机抖动、多级缓存、数据库限流兜底。

📌 考点：缓存一致性正确顺序是先更新数据库再删缓存；延迟双删扫净并发尾巴。

数据改了缓存怎么办，正确顺序是先更新数据库再删缓存，把脏数据生存窗口压到最小。再配延迟双删，删完后延迟一小段时间再删一次，扫净并发尾巴。删缓存而非更新缓存，因为并发写可能乱序互相覆盖，删除是幂等的。极致强一致的场景如账户余额扣减，不用缓存，用读库加锁，一致性是用响应时间买来的。

8.7 把优化变成团队的预算制度

🔹 一次性的优化救不了一个团队，要把打法变制度。第一件是 RT 预算表，把快变成像工程预算一样的东西：网关加鉴权十毫秒且本地缓存命中率大于九成九，应用计算加序列化三十毫秒，缓存读取命中率跌破九成五就告警，下游 RPC 合计五十毫秒。第二件是定位三板斧：链路追踪出嫌疑人，火焰图出嫌疑代码行，慢日志加 explain 出可执行修复动作。第三件是三阶段推进：止血先加索引上缓存调参，提速动架构做异步与多级缓存，体系把预算进需求模板、容量规划常态化、大促前全链路压测。

📌 考点：RT 预算表与定位三板斧把退化挡在用户感知之前。

常见错误清单

  • 瓶颈在数据库却去扩应用层，多加连接反而把库砸得更死。
  • 凭平均值判断性能，P99 八秒被平均 RT 掩盖，口碑悄悄崩掉。
  • 什么数据都塞缓存，连强一致的库存也塞，最后超卖比慢查询更贵。
  • 没有基线就动手优化，改完说不清到底有没有效果。
  • 一次动多个变量，效果好了查不清谁的功劳，差了查不清谁的锅。
  • 只测单接口压测，全链路一压测缓存击穿，把数据库打穿。
  • 只优化不设防，三个月后性能悄悄退化回原点。
  • 连接池无界或线程池用无界队列，请求堆积没有上限，内存早晚爆掉。

小结

高性能是算术不是运气。先用量化尺子找到瓶颈层，再用缓存、异步与池化、批量这四板斧按占比逐一砍，最后用 RT 预算和定位三板斧把退化挡在用户感知之前。快靠的是一套让退化无处藏身的制度，需要长期把尺子用下去。

指标 优化前 优化后
下单 P99 8.2 秒 90 毫秒
系统 QPS 6.2 820
数据库峰值 QPS 12000 900
数据库 CPU 100% 30%

同样的加十台机器，事故那天 RT 慢四秒，优化后 RT 再降三成，说明先砍瓶颈再扩容才有意义。
