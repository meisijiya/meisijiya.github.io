边缘计算给云补一条腿：该集中的数据继续集中，该就近处理的就近处理，只把必要结果送出去。

凌晨两点十分，郊区门店旁市政施工挖断了光缆。到四点整客服电话被打爆，三千多家门店的 POS 机集体转圈，收银员扫码屏幕却在转圈，顾客站柜台前尴尬等待，直到六点半才陆续恢复，前后瘫痪四小时，正好覆盖早高峰。

9.1 凌晨四点的四小时瘫痪

🔹 这套系统本是标准云中心架构：门店 POS 机每刷一笔卡，请求走专线跑到几百公里外的云机房，在云端数据库记账再返回支付成功。POS 机本质上只是带屏幕的浏览器，自己不记账，云不通就收不了钱，这是四小时瘫痪的技术根源。月底还有一张带宽账单：三千家店每家四路摄像头，共一万二千路视频流全量回传云端存储，专线费加云存储费加转码算力费一个月三四十万，其中九成以上视频没人看过一眼。

9.2 云中心的三道坎与边缘的定义

🔹 云中心没做错事，它有统一运维、弹性伸缩、数据强一致三大优点。但三条物理规律躲不开。带宽账单：一万二千路摄像头每路两兆码流全天回传，一路一天二十多 G，一天二百多 T，九成多是空镜头，却要为「什么也没发生」付几十万。延迟红线：POS 机刷卡走专线一个来回八十毫秒起步，客流识别要几百毫秒内提示店员迎客，回云一个来回早误了事。断网瘫痪：核心链路挂专线，专线一断门店从收银机退化成计算器。三道坎共同点是中间都隔着一条回云的路，带宽嫌它贵，延迟嫌它长，断网嫌它脆。

📌 考点：边缘三道坎是带宽、延迟、断网；三个关键词是下沉、就地、只送结果。

边缘计算的定义是把计算和存储从集中云机房下沉到靠近数据产生的网络边缘，让数据就近处理，只把必要结果送出去。三个关键词是下沉、就地、只送结果，少一个都不叫边缘。云仍是大脑负责统一管理、版本下发、模型训练与长期归档，只是学会了放权。

9.3 冷热路径：什么该下沉，什么回云

🔹 判断标准三个：数据在哪产生、响应要多快、断网能不能容忍。热路径留边缘：POS 机收银记账，数据店里产生、响应要秒级、断网必须能忍，本地数据库先落账；摄像头事件识别，原始视频海量，有价值的只是发生了什么；冷柜温度联动，本地告警规则直接触发；短周期数据缓存，七天内的监控录像本地存即可。

📌 考点：热路径留边缘、冷路径回云；Outbox 保证本地先成功。

路径 内容 位置
热路径 收银记账、事件识别，温度联动，短期缓存 边缘节点
冷路径 结构化事件上行、全国报表对账，模型训练，配置版本下发 云端

冷路径是热路径处理完的结果作为冷路径输入送回云端：结构化事件一句话加切片指针上行，全国报表对账回云端汇总，训练需大算力边缘只推理，配置和版本由云端统一下发。边缘省下的是带宽与延迟，多出来的是分布式运维这门新功课。

9.4 五层骨架与 K3S 减重版

🔹 端边云自下而上五层。L1 设备层即端，摄像头、POS 机、传感器在此产生数据，算力弱只做采集与最原始过滤。L2 边缘节点是主角，店里配一台盒子，跑 K3S、Spring Boot 容器，还有本地库与推理服务，是断网自制关键层，数据待七天滚动覆盖。L3 边缘网关做协议转换与汇聚，把蓝牙、Zigbee 等非 IP 协议统一成 IP 流量。L4 区域边缘是运营商或云厂商城市级机房，离用户典型几到几十毫秒，多数用户十毫秒内可达、尾部用户可达数十上百毫秒需按地区和运营商实测，放多门店共享能力。L5 云中心大机房，全局的数据库、报表，模型训练，版本仓库与统一管控，大脑地位不变。

K3S 是 Kubernetes 的减重版，名字直白：中间少了五个字母。它是不到一百兆的单二进制文件，一条命令装完；内存五百一十二兆就能跑，完整 Kubernetes 控制面起步就两 G；默认用 SQLite 代替 etcd，门店一台盒子不用选主。断网自制是本地自主，云断了照样调度容器、重启应用、读写本地库，恢复联网后增量数据按队列补传。学习成本近零，会 Kubernetes 就会 K3S，Spring Boot 打成镜像代码一行不改就能部署进去。

9.5 反向隧道与云在墙外管墙内

🔹 三千家店节点全躲在运营商 NAT 和门店防火墙后，云端在公网根本找不到它们。解决思路反过来：节点开机主动向云端发起一条长连接 WebSocket 或 gRPC 双向流，云端指令都从这条隧道下发，谁主动外联谁安全。隧道里有四类流量：心跳和指标每十秒报平安，指令下发改配置发版本，日志采样回传，K3S 控制面同步。隧道断了三件事：指数退避重连封顶五分钟，离线指令在云端排队重连后按序补投，通信专线断了切 4G 备用卡只保心跳与关键指令，控制面永远优先于数据面。

9.6 实战：断网也能收银的 Outbox

🔹 边缘应用第一戒律是本地先成功、云端后知晓，用户可见的成功绝不能依赖回云的路。POS 机返回支付成功只依赖店里盒子。pay 接口三行：DAO 把交易写本地库，outbox 表插一条待上报记录，return OK，三行包在同一本地事务里，落账与记下待上报要么都成要么都败。若落账成功却没记下待上报，这单永远到不了云端，对账就出鬼账。

📌 考点：本地先成功、云端后知晓；outbox 与业务写在同一事务。

outbox 是本地消息表方案，原封不动搬到边缘。发送器只发一次不放心，网络超时不等于失败，靠幂等键兜底；云端确认成功才删 outbox 记录，不确认就留着；乱序没关系，每条带 txnId，云端见过就丢弃。断网期间 outbox 越积越多不用慌，磁盘够大，恢复后按批次补传。视频账单从每月三十万变三千，思路是原始视频不出店门，出门的只有发生了什么。抽帧去噪在店门口丢掉空镜头，轻量模型在盒子跑事件识别，只传「几点几分什么人逗留」一句话，原视频留本地七天。

9.7 落地分仓与推进节奏

🔹 分仓是落地第一个决定，判定顺序固定两问加兜底。端上能做吗：延迟压到十毫秒内、数据绝不出口、逻辑简单且几年不变，如温度传感器本地阈值联动，就烧进固件。边上能做吗：断网可用、毫秒级响应、数据量大不值得回传或逻辑频繁迭代，如收银、视频事件识别，outbox 上报，本地缓存，就下沉容器走云端下发。剩下一切放云上：全局聚合的全国报表对账，需大算力的模型训练，长期合规归档，统一管控的版本与配置下发。

📌 考点：分仓判定顺序：端上能做吗 → 边上能做吗 → 剩下放云。

落地形态 适合 代价
自建 K3S 集群 有平台工程团队、节点量大、深度定制 运维面爆炸自己扛，换最高自由度
云厂商边缘服务 团队小、快速上线、接受托管 按台计费，节点越多越贵，形态受制于人
纯端测固件 逻辑极稳、点位海量、单点成本敏感 升级逐台刷机，迭代按月计

推进三阶段：单店试点一到两个月全链路跑通断网演练与对账闭环，看账单降多少；区域推广三到六个月五十到一百家店，验证下发灰度与硬件异构适配；规模化六个月后全量铺开谈容量规划与成本模型。五个坑都来自用云的思维做边缘。把云应用直接搬边导致内存超限整店瘫痪；拿门店本地时间排序对账，断电时钟漂移账永远对不平；下发不做灰度，坏配置三千店同时生效；日志全量回传把专线变日志专线；硬件采购即锁死，软件三年迁就硬件。

常见错误清单

  • 把云应用直接搬到边缘盒子，不设内存上限，JVM 一伸缩吃掉三 G 拖垮整店。只有 request 和 limit 都不设才是 BestEffort、节点压力下最先被驱逐，只设 request 不设 limit 属 Burstable。
  • 用门店本地时间排序对账，断电时钟漂移，账本乱成一团永远对不平。
  • 下发不灰度，一个坏配置三千店同时生效，收银全部停止。
  • 日志全量回传，把昂贵的专线变成日志专线，存储先爆。
  • 硬件采购即锁死，首批盒子定下三年换不动，软件永远迁就硬件。
  • 以为边缘节点是小号云，照搬云上玩法到无人值守、随时断电的盒子上。
  • 只传视频不传结果，原始流全量回传，带宽账单大到无法承受。
  • 断网期间指令在云端排队后重连补投却不做幂等，同一条指令到达两次。

小结

边缘计算先问数据为什么不能走远，再问要不要上边缘。本地先成功、云端后知晓这条不成立，断网就是事故；成立，断网只是延迟。省下的带宽钱会变成运维债退回来，所以要用反向隧道、冷热路径与 Outbox，还有双架构镜像和灰度下发，把这套机制咬合清楚再谈落地。
