高可用架构 — 冗余、隔离与故障自愈

07 高可用架构

高可用不是靠运气，靠的是冗余、自动切换与演练。本文从可用性数字讲到五层冗余，再到雪崩断路器与混沌演练。

7.1 先把可用性变成一个数字

🔹 可用性等于一年里系统真正能干活的时间比例。三个九 99.9% 一年允许停机几小时，是很多业务系统的常见目标。四个九 99.99% 一年只允许几十分钟故障，是支付与交易类系统的及格线。五个九 99.999% 一年停机约五分钟，代价高。

大促当天的五分钟故障，损失比平时零散的五分钟大得多。先定目标再谈架构，先把三个九坐稳，别一上来就追几个九。

🔹 单实例看着岁月静好：八核十六 G 跑应用，旁边一个数据库，日常七八百 QPS、RT 四十毫秒，监控全线绿。它有两个致命设定。任何一处故障用户立刻白屏，应用挂、库挂、断电都白屏，没有缓冲。所有修复必须停业务，发布、改配置与重启都要停机，业务越好越不敢动。整机可用性是应用乘数据库乘机器，任一失手全盘归零。问题在它没有第二套方案。

7.2 故障一定会来，且会链式传染

🔹 单实例压测有一条断崖曲线。起点八百 QPS、RT 四十毫秒很稳，流量爬到一万五变慢仍在服务，到一万八、两万时曲线断崖跳水，整台消失。前一毫秒还在服务上万个用户，后一毫秒一个也服务不了，这叫容量崩塌，特征是它非线性，是悬崖。

🔹 崩塌后最气人的是流量回落还瘫痪，堆积的请求把机器按在水底，除非重启爬不出来。根因是过载连锁。请求在连接池排队，每个请求等别的请求，占满线程，新请求包括健康检查都超时。

📌 考点：容量崩塌是非线性悬崖；过载连锁的根因是连接池排队占满线程，健康检查也超时。

7.2.1 四类故障

🔹 故障分四类。硬件如磁盘内存网卡整机，上云后机器仍会坏只是少。软件如 bug 与内存泄漏，阴险在不报错只变慢，一条慢 SQL 大促会拖死连接池。流量如大促热点与恶意刷量，不可预测。人祸如误操作错配置，行业占比高。单独每类不致命，串联才致命，而越往后越必然，没灰度没回滚几乎排着队来。

7.3 五层冗余与三种备胎力度

🔹 一个请求从用户手机到数据落盘穿过五层，任一层只活一份就会变成全栈死穴。接入层单点是一台 Nginx 或公网 IP，挂了后面应用再多也没用，冗余要多台加 DNS 多入口。应用层单点部署，解法是多实例加负载均衡，无状态是命门。缓存层单点 Redis 挂了全部请求砸向数据库，要哨兵或集群，并做缓存全灭演练保证库裸奔也能扛。数据库层优先级最高，单点主库造过无数事故，要主从复制加自动切换。机房层单点怕断电火灾光缆挖断，要同城双活或异地多活。

7.3.1 三种备胎力度

每一层至少活两份，但活两份之间差距很大。

力度 RTO RPO 适用
冷备 小时级 可能丢一段 内部系统、报表
热备 秒到分钟级 趋零 多数业务标配
多活 短、用户无感 秒级趋零 城市级灾难保险

选力度看 RTO（恢复要多久）与 RPO（最多丢多久数据），答案越严账单越贵，多数业务选热备。

7.4 故障检测与自动转移

🔹 一切切换的前提是先发现故障。健康检查每五秒发一次请求，正常返回 200，出问题超时或 500，连续 N 次失败才判定死亡，一次失败就摘除等于把喷嚏当病危。检查分被动式（进程在不在、端口通不通）和主动式（数据库连得上吗、依赖通吗、线程池有余量吗）。最容易踩的坑是只查进程不查依赖：数据库挂了应用进程活着、端口通，健康检查全过，假活的实例继续接流量，用户得到更彻底的白屏。健康检查必须覆盖核心依赖，依赖挂就承认自己也挂。多次失败才判死加自动摘除，两者配合才合格。

📌 考点：健康检查必须覆盖核心依赖；只查进程会导致假活实例继续接流量。

故障转移全程约三十秒，分五步：探测死亡并告警；摘除故障节点让新请求不再发给他；备胎顶上，从库提主库或请求路由到备胎实例；验证新主库健康后放开写流量；事后原节点修好以从库身份悄悄回归，择机演练回切。回切本身也要演练过，不能在生产首次练习。

7.5 雪崩四断路器：限流、熔断、降级、重试

🔹 限流是压测曲线的答案。与其被两万 QPS 打死，不如一次只接一万二，多的请稍后再试。令牌桶四行配置就够，发放周期一秒、每周期发八千令牌、请求最多等两百毫秒拿令牌，拿到正常处理，拿不到快速失败绝不让排队到死。配额用压测找崩塌点再留两成余量，分层在网关、服务与用户级设卡，任一层失误有下层兜底。

📌 考点：限流配额用压测找崩塌点再留两成余量；熔断打开后走降级。

断路器 管什么 动作
限流 入口流量过多 超额快速拒绝
熔断 下游挂了 失败率超阈值断开走降级
降级 用户体验 返回兜底、简化流程
重试 瞬时抖动 指数退避，带预算

7.5.1 熔断与降级

熔断管下游挂了的情况。推荐服务挂了，商品页每调一次等死三十秒超时，还傻等就是陪葬。熔断像电闸，烧了先打开。熔断器统计最近二十次调用，失败率超一半就打开，十秒后进半开放几个试探。打开后给用户什么靠降级：推荐挂返回热销榜，评价挂隐藏入口，残缺但能下单付款好过白屏。降级前先问功能挂了用户还能走完主流程吗，据此把依赖分主链路（下单库存支付，降不起）和边缘链路（推荐评价，放心降级）。熔断把等死三十秒变成拒绝一毫秒，雪崩链条从这儿剪断。

重试本是好东西，剂量不对变毒药。下单抖动十秒成功率掉八成，上游都配失败重试三次，到下游流量变三倍，把虚弱的下游压垮，十秒抖动放大成四十分钟瘫痪，叫重试风暴。原则是重试要幂等且值得，下单扣款必须带幂等键，业务报错如库存不足别重试。三件套是指数退避、退避加随机抖动打散，以及全链路重试占比超一成主动熔断。

7.6 舱壁隔离与混沌演练

🔹 舱壁隔离取自轮船密封隔间，一舱进水关闸船照航。系统把线程池按依赖切成独立小池，Tomcat 两百线程切三舱：下单一百二、推荐四十、评价四十。推荐挂只占满推荐舱四十线程，被关在自己船舱，下单一百二线程一寸没被占，购物车照常下单付款。对照雪崩链第三步线程池耗尽，灾难之所以传染是因为所有功能共享一个池。主链路给大池，边缘链路给小池，按降不起的程度分舱，分错舱代价翻倍。

📌 考点：舱壁隔离把线程池按依赖分仓，主链路大池、边缘链路小池。

没演练过的高可用是空中楼阁，要主动把系统搞挂验证自动切换真自动。三个入门演练：杀应用实例看 Nginx 能否自动摘除；给网卡加两秒延迟看熔断器是否一秒内打开切降级；把主库磁盘塞满看从库能否顶上。演练三要素是提前声明、一分钟能叫停、盯错误率与切换时间出结论。每次演练几乎必翻车，在演练时踩坑是排练，在大促踩是事故。

7.7 机房级冗余：双活与多活

🔹 前面的冗余都在同一机房，机房级灾难防不住。同城双活如上海浦东与外环两机房同时接流量，双向同步 binlog，专线延迟几毫秒无感，任挂流量换另一机房，RTO 分钟级 RPO 趋零。异地多活按城市分站点，按用户分片让同一行数据只有一个写点避免冲突，跨城异步复制复杂度高，双向写的数据冲突要专门仲裁。

双活核心难题是数据，两地同时写一行用谁的业务主流答案是按用户分片。不是每家公司都需要多活，先问 RTO、RPO 多低，机房级故障概率怎么估，多花的复杂度谁扛。多数业务做好同城双活够用，多活投入常是单活加主从的三到四倍，买的是城市级灾难保险。起步路径是先坐稳单机房五层，再做同城双活，最后有真实需求才碰异地多活。

7.8 选型与落地

🔹 选型先问挂了损失多少。停机每分钟损失一千以下的内部系统，单实例加每日备份加冷备够，别浪费钱。交易类每分钟损失几万，才值多付一个九到 99.99%。这叫预算思维，先定价再购物。再问哪一环最先挂，用五层检查法走一遍，应用层常被云平台兜底，真正脆弱在数据库和缓存击穿，资源有限先给最脆弱层加冗余。还要问谁在值班、演练过吗，切换脚本没人懂、演练从没跑过，这套高可用就是纸糊的。多数系统的答案都是主从热备加双实例加限流熔断再加季度演练，四样做到位基本达标。

部署形态三选：自建主从加演练适合有 DBA 与 SRE 的团队，完全可控但运维全自己弄；云托管适合中小团队，主从备份自动切换全托管，代价是费用溢价与厂商锁定；混合日常用托管自建一条逃生通道，灾难时验证自建真能接管，代价是两条体系都养。
落地分三阶段。阶段一消灭单点：应用双实例加 Nginx 自动摘除，数据库主从复制，每日备份异地存放。阶段二切断雪崩：限流、熔断、降级、重试预算与舱壁隔离逐个上线。阶段三演练常态化：混沌演练进排期，每月一次故障演习，大促前全链路压测。

7.9 常见错误清单

  1. 健康检查只查进程不查依赖，数据库挂了实例假活继续接流量，用户得到更彻底的白屏。
  2. 重试不设预算，每层乘三在长链路放大两百多倍，把十秒抖动变成四十分钟瘫痪。
  3. 切换脚本从未演练，真要切时发现还要人工改配置，应每次变更后必演练。
  4. 降级预案没有文案，降级生效用户却看到未定义字样，应把降级响应当产品需求验收。
  5. 备份跑了两年没验证，第一次恢复发现缺表，应每月挑一天做恢复演习。
  6. 把主链路依赖放进小舱壁，稍一抖动就拒绝，或把边缘链路放进大舱壁，挂了拖死全系统。
  7. 只做同机房冗余，遇断电光缆挖断这类机房级灾难整体失效，应按需上双活。
  8. 限流配额拍脑袋定，没用压测找崩塌点，系统该挡的没挡住。
  9. 多活一步到位，数据冲突与双向写仲裁都没解决，应先坐稳单机房五层再做双活。

7.10 小结

故障是必然的，无感是设计出来的。架构把故障概率做成用户无感知的手艺，靠的是冗余、自动切换与反复演练三件事。配置会过期，人员会流动，只有演练排期和值班制度能让这套高可用活到下一个季度。现在就用五层检查法给自己的系统画张图，把最脆弱的那层先加上备胎。
