1.1 Redis 是什么：内存中的工具箱

🔹 很多人把 Redis 当数据库看，它的真实定位是一把工具箱。应用服务器先问 Redis 拿数据，命中就一毫秒返回，没命中才去查 MySQL。慢的根因不在 SQL 写得多差，而在于同一份不怎么变的结果被反复计算了几百遍。把算好的结果放进 Redis，应用就不再反复打扰数据库。

🔹 把 Redis 名字拆开看就懂它的性格。Remote 表示它是独立进程，不是你程序里的包，会挂也要运维。Dictionary 表示给一个 key 还一个 value，没有表结构。Server 表示它长期运行，会满也会崩，所以才有后面的持久化与高可用。快来自三点：

  • 数据在内存
  • 省掉 SQL 的解析加锁流程
  • 单线程串行执行没有锁竞争

🔹 Redis 不替代 MySQL，它把重复查询、计数、排队这些活儿从数据库里剥离出来，让数据库专注保证数据正确。

1.2 数据类型与命令：五种结构怎么选

🔹 五种结构各有归属：

  • 单值用 string
  • 对象用 hash
  • 排队用 list
  • 去重用 set
  • 排名用 zset

🔹 把商品详情存成 hash，改库存只发一条 HSET product:1001 stock 99，比读出整个 JSON 再写回省事得多。zset 按分数排序，把订单号当元素、到期时间当分数，后台每秒扫一遍过期订单，就是天然的延迟队列。

🔹 还有三个省空间的结构：

  • bitmap 用一位记一个用户签到状态，100 万人只占 125KB
  • HyperLogLog 最多占 12KB（元素少时用稀疏编码更省），只估 UV 不存元素
  • GEO 把经纬度编码成分数，省掉自建空间索引

1.2.1 三个能直接跑的命令场景

  • 短信验证码用 SET code:phone 8674 EX 300，过期由 Redis 自己管，一行清理代码都不用写。
  • 阅读量用 INCR article:view:1001，一万并发同时加结果也不多不少。
  • 全局唯一单号用 INCR order:seq 做发号器，但重启会丢号，生产上用时间戳拼上 Redis 步长或雪花算法更稳。

1.3 过期与淘汰：内存满了怎么办

🔹 给 key 设过期有 EXPIRE key 300，TTL 查剩余秒数，返回 -1 永不过期、-2 已不存在。删除靠惰性（访问时才删）和定期随机采样配合，默认 hz 为 10，后台约每 100ms 跑一轮定期随机采样，对带 TTL 的键抽样删除，所以过期的 key 不一定立刻消失。

🔹 内存满用 maxmemory 限制，超了按策略淘汰。下表列出四种常见策略的取舍。

策略 淘汰范围 适用场景
noeviction 不淘汰，写命令报错 不允许丢数据的纯存储
allkeys-lru 所有 key 里最久未用 纯缓存，最省心
allkeys-lfu 所有 key 里访问最少 访问频率差异大
volatile-lru 仅设了过期的 key 缓存与队列混用

🔹 noeviction 是默认值，内存满直接对写入报错，缓存场景很危险。消息 list 没设 TTL，volatile-* 不会淘汰它，默认 noeviction 也保得住，只有 allkeys-* 才会把它当缓存淘汰掉。一批缓存的过期时间要加随机值，错开过期时刻，否则同一秒集体消失会打爆数据库。

📌 考点：删除 = 惰性（访问时才删）+ 定期随机采样（默认 hz 10，约每 100ms 一轮）；内存满按 maxmemory 策略淘汰，noeviction 是默认值，写命令直接报错。

1.4 缓存三大事故与一致性

🔹 缓存有三种经典事故。穿透查的是不存在的数据，缓存和数据库都没有，每次都打到库。击穿是一个热点 key 刚好失效，瞬间一堆请求穿透。雪崩是一大批 key 同时失效或 Redis 整体挂掉。

事故 关键点 解法
穿透 数据根本不存在 缓存空值、布隆过滤器与参数校验
击穿 单个热点 key 失效 互斥锁、热点 key 逻辑永不过期
雪崩 大批 key 同时失效 随机过期时间、多级缓存与限流降级

🔹 一致性用 Cache Aside（旁路缓存）：读先查缓存，没有查库并回填；写先更新数据库再删除缓存，删比更新安全，避免并发写把旧值留进缓存。删除失败就进消息队列重试或订阅 binlog 补偿，追求最终一致而非强一致。

📌 考点：穿透（数据不存在）、击穿（热点 key 失效）、雪崩（大批 key 同时失效）三者区别；一致性用 Cache Aside，写时先更新库再删缓存，追求最终一致。

1.5 分布式锁：从单机到集群

🔹 单机的 synchronized 管的是进程内，二十台机器各有各的锁等于没锁。锁要放在所有机器都看得见的地方，Redis 就是那个外部服务。用 SET key value NX EX 10 一条命令拿锁，NX 保证互斥、EX 保证崩溃后自动释放，严禁分两步 SET 再加 EXPIRE，中间崩了锁就永生。

🔹 解锁也不能直接 DELETE，要先比对身份。加锁时 value 放 UUID，解锁时确认是自己的才删，否则会误删别人的锁。比对加删除必须用 Lua 合成一步，避免中间被打断。业务可能比过期时间长，手写锁难解，生产上用 Redisson：看门狗每十秒续期，锁可重入，还自带读写锁和信号量。红锁（RedLock）安全性仍有争议，一般业务别碰。

📌 考点：加锁用 SET key value NX EX 一条命令完成，严禁分两步 SET 再 EXPIRE；解锁用 Lua 校验身份后再删，避免误删别人的锁。

1.6 Lua 脚本：把两步并为一步

🔹 先 GET 库存再 DECR 在高并发下会出错，两个请求都读到 1 都通过判断，超卖。根因是读和写之间有空隙。Redis 单线程，把逻辑写成 Lua 脚本一口气跑完，中间不处理别的命令，空隙消失，这就是原子性。

📌 考点：Redis 单线程，Lua 脚本整体执行、中间不插别的命令，因此保证原子性，消除读—写之间的空隙。

1.6.1 三条纪律

🔹 KEYS[1]、ARGV[1] 取参数而非拼字符串，防注入也帮 Cluster 判断槽位。脚本要短，执行期间阻塞全站。用 SCRIPT LOAD 避免每次传整段。Lua 不是事务，出错不回滚，要写成先判断后执行。一人一单和限流都靠 Lua 把判断加动作合成一步。

1.7 消息队列：用 Stream 削峰填谷

🔹 秒杀峰值可能到十万 QPS，普通 MySQL 实例扛数千量级 QPS，差二十多倍且只持续两秒。把立刻下单改成立刻登记，请求写进队列是内存操作毫秒完成，后端按数据库节奏匀速取，尖峰被削平填满低谷，这叫削峰填谷。

🔹 老办法用 list（LPUSH/BRPOP），但消息弹出即消失，消费者崩了任务永久丢失。发布订阅完全不落地，断线即丢，不能当任务队列。Redis 5.0 的 Stream 是专业方案。消息带自增 id，读完不删可以重放，XTRIM 保留最近千条防内存涨爆。消费者组把多实例组成一组，消息进待确认列表，业务成功才 XACK。崩溃未确认的消息用 XCLAIM 转移重做，这叫至少一次投递，业务必须幂等。

1.8 持久化与高可用：挂了怎么办

🔹 持久化是为了重启后快速恢复，真数据永远在 MySQL，丢了能从库重建。三种落盘方式对比如下。

方式 优点 代价
RDB 文件小、恢复快 两次快照间宕机丢一段
AOF 丢得最少、可审计 文件大、重放慢
混合 既快又丢得少 配置略复杂

🔹 RDB 快照文件小恢复快，但两次快照间宕机丢一段。AOF 追加每条写命令，每秒刷盘最坏丢一秒，文件大恢复慢需重写。混合持久化开头写 RDB 再追加增量，是生产推荐。持久化救不了硬盘坏或机器炸，要靠主从复制把数据存在多台机器。

🔹 主从带来读写分离和副本，但复制异步，刚写就读可能读不到，一致性敏感场景要强制读主。主挂了从节点不会自动上位，交给哨兵。哨兵每秒 PING，单个哨兵觉得挂是主观下线，达到配置的 quorum 票数（默认 2）才确认客观下线；启动主从切换才需要多数派哨兵授权，挑数据最新的从节点上位并通知客户端新地址。哨兵至少三个且奇数。容量超单机用 Cluster：16384 个槽分给多台，客户端对 key 做 CRC16 取模定位节点，跨节点事务和 Lua 要避开或用哈希标签。

📌 考点：主从复制异步，一致性敏感场景要强制读主；哨兵需达到 quorum 票数才确认客观下线；Cluster 把 16384 个槽按 CRC16 取模分给多台。

1.9 常见错误清单

⚠️ 给 key 设过期时分开执行 SET 和 EXPIRE，中间崩溃锁或缓存变成永生。
⚠️ 解锁直接 DELETE，没比对身份，把别人刚拿到的锁删了。
⚠️ 用 list 当队列存消息却配 allkeys-lru，消息被当缓存淘汰丢失。
⚠️ 一批缓存设相同过期时间，整点集体失效触发雪崩。
⚠️ 写缓存用更新而非删除，并发下旧值残留到下次过期。
⚠️ Lua 脚本写长循环或复杂逻辑，阻塞单线程拖垮全站。
⚠️ 把跨节点多 key 事务和 Lua 用在 Cluster 上，数据落在不同槽报错。
⚠️ 主从异步延迟下强读从节点，拿到还没同步的新数据。

1.10 小结

🔹 Redis 不只是快。它的价值在于替数据库扛住那些本不该它扛的事。缓存扛住重复查询，锁协调多机互斥，Stream 负责削峰，Lua 收束并发空隙。把这几件事拆开看，Redis 的岗位就清楚了。MySQL 始终是最终数据来源，这是底线。理解它在系统里这六个岗位，比背命令更重要。
