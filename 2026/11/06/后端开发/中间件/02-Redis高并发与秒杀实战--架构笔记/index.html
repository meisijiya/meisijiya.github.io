秒杀场景里 Redis 不是用来替代数据库的，它是在数据库前面加的一道闸门，把绝大多数请求拦在真正的数据源之外。

秒杀一开始是平静的。监控大盘上 CPU 正常，内存平稳，各项指标都和往常一样。可到了开抢那一秒，下单接口的响应时间从八十毫秒直接拉到八秒。这八秒足以让六成用户在移动端白屏时转身离开。

2.1 为什么秒杀必须加一道闸门

🔹 电商系统在秒杀开场那一瞬间的流量，往往是平时的上百倍。如果这股请求直接砸到 MySQL，结果不会只是变慢，数据库会直接拒绝服务。原因很直接：数据库的连接数一旦被打满，响应会越来越慢，最后干脆拒绝服务。用户看到的是页面一直转圈，随后报错。

🔹 更麻烦的是，数据库是全站公用的。它一旦趴下，商品列表打不开，订单查不了，个人中心转圈，连登录都进不去。中间加一层 Redis，正是为了挡住绝大多数请求，别让秒杀把整个系统拖下水。

📌 考点：秒杀开场流量是平时的上百倍，请求直接砸 MySQL 会连接数打满、拒绝服务，所以必须加 Redis 闸门。

2.2 Redis 是什么

🔹 Redis 全称是 Remote Dictionary Server，意思是远程字典服务。远程说明它不在你的程序里，而是跑在另一台机器上的独立进程，程序通过网络去连它。字典说明它存数据的方式就是查字典：给一个键，立刻还一个值。服务器说明它是一个独立进程，要启动、要占内存，也可能挂掉。

🔹 把它装进系统后，原来的链路从「用户 → 程序 → MySQL」变成「用户 → 程序 → Redis → MySQL」。多出来的这一层，相当于在程序旁边多了一台跑得飞快但容量不大的小仓库。程序先去小仓库问有没有能直接用的数据，没有再去 MySQL 捞，顺手把结果写回 Redis，下次就快了。

🔹 Redis 能担当这道闸门，靠的是三个天生的优势：

  • 所有命令串行执行，天然不会相互打架
  • 数据全部在内存，读写是微秒级
  • 每个键都能设过期时间，到点自动清理

🔹 它管热数据，数据库管真数据，分工就此明确。命令串行执行还有一个好处，多个客户端同时来改同一个数字时不会出现互相覆盖，这正是后续并发方案的底座。

📌 考点：Redis 单线程串行执行命令，天然无锁竞争，多个客户端改同一数字也不会互相覆盖。

2.3 五种基础结构

🔹 Redis 提供五种基础结构，每种适合放什么数据，比背命令更关键。

结构 形状 秒杀场景用法
String 一个键一个值 库存计数、验证码、登录令牌
Hash 一个键一组字段 商品详情、购物车
List 一列可双向进出的队伍 订单排队、简单消息队列
Set 不重复的无序名单 已购用户去重
ZSet 带分数的自动排行榜 延迟队列、限流窗口

🔹 String 用得最多，八成以上的场景都是它。Hash 存商品详情很合适，一个商品有标题、价格与库存，凑成一条 hash 取用方便，改价格只动一个字段，比整体存取省流量也更安全。Set 是防一个人抢十次的锁，谁已购写多少遍都只有一条。ZSet 把时间戳当分数就能做延迟队列，订单十五分钟未支付自动取消就是这么实现的，但要靠后台消费者轮询 ZRANGEBYSCORE 取出到期成员去投递，Redis 本身不会自动触发。

2.4 分布式锁

🔹 超卖的根源只有一句话：读和写之间被别人插了一脚。最朴素的写法先 get 查库存再 set 扣减，两步之间留有空隙，两个请求同时进来都读到库存为一，扣完还是一，超卖就此发生。

🔹 Redis 给的答案是一条命令 SET key value NX EX。NX 表示键不存在才设置，实现了互斥，只有第一个请求能成功，第二个请求键已存在直接失败。EX 表示自动过期，防止持有锁的进程崩溃或忘了释放，锁会自动到期，不会把整条业务线卡死。

📌 考点：加锁用 SET key value NX EX 一条命令完成；NX 互斥、EX 自动过期防崩溃卡死。

🔹 解锁必须用 Lua 脚本，先判断这把锁是不是自己的再删。因为锁可能已超时自动释放，别人已经拿了锁，你直接删就会误删别人的锁。生产环境更推荐用 Redisson，它解决了可重入，并在未显式设定 leaseTime 时通过看门狗（默认锁超时 30 秒）自动续期。手写锁最容易错的地方，就是业务还没跑完锁就过期了。

2.5 Lua 脚本与乐观锁

🔹 Lua 脚本是防超卖的终极答案。脚本在 Redis 里整体执行，中间不会插入任何别的命令。我们查库存、扣库存、记录用户这三步永远不会被打断。

🔹 脚本先检查用户是否在已购集合中，在就返回重复下单；再 get 库存，小于等于零返回售罄；最后 decrease 扣库存并把用户加进集合，返回成功。一个脚本把超卖、少卖、重复下单三个问题一起解决。

🔹 Lua 脚本的代价是会阻塞 Redis，因为脚本原子执行期间别的命令都得排队，所以脚本要短要快，不能带大循环，几万行的遍历就是生产事故。

🔹 乐观锁的思路是不锁门，谁想进谁进，出来时核对期间有没有人动过，动过这次就不算。具体用 watch 监视、multi 开事务、exec 提交，exec 返回 none 说明期间被改过，本次失败，自己决定重试还是放弃。stream 则解决别挤爆的问题：扣减成功只是抢到名额，真正的下单请求扔进队列，后台慢慢消费落库，数据库承受的压力被拉平。

📌 考点：Lua 脚本原子执行杜绝读—写空隙，一个脚本解决超卖、少卖、重复下单；乐观锁用 watch/multi/exec，exec 返回 none 即本次失败。

2.6 六种高并发优化策略

🔹 回答「结合 Redis 列举高并发优化策略」，至少能答三组，按请求从上游到下游排：

手段 解决的问题
网关限流 挡住刷单脚本与恶意流量
热点数据预加载 挡掉九成读请求
库存预扣减（原子操作） 防超卖
分布式锁 同一商品互斥修改
消息队列削峰 拉平瞬时洪峰
数据库条件更新 最后兜底，不扣成负数

🔹 整条链路可以这样理解：请求先到网关做限流，再到 Redis 缓存，商品详情和库存多数在此返回；第三站 Redis 原子扣减，扣不动直接返回售罄；第四站消息队列，扣减成功的请求扔进去；第五站后台消费者慢慢写订单、扣数据库；最后一站 MySQL，用 WHERE number > 0 做兜底，就算前面全出问题也不会扣成负数。

2.7 缓存三坑

🔹 缓存穿透是查一个根本不存在的数据，缓存永远不命中，每次都打穿数据库。有人拿不存在的商品 id 疯狂刷，成本低却能打穿数据库。解法两招：缓存空值并设短过期，再加布隆过滤器拦一道；布隆过滤器有假阳性，仍会有少量不存在的 key 漏到数据库，所以空值缓存这层不能省。

🔹 缓存击穿是某个热点键刚好过期，那一瞬间几万个请求同时冲向数据库。它和穿透不同，穿透是查不存在的数据，击穿是数据存在但热点键过期了。

🔹 缓存雪崩是一大批键在同一秒过期，或者整个 Redis 挂掉。根因常是大家统一设了三十分钟过期，到点集体过期。解法给过期时间加随机值打散，再配本地缓存兜底或哨兵集群。

📌 考点：穿透（数据不存在）、击穿（热点 key 过期）、雪崩（大批 key 同时过期或 Redis 挂）三者区别；雪崩用随机过期时间 + 多级缓存兜底。

2.8 对账兜底

🔹 Redis 只做预扣，数据库才是真正的数据源。扣减和落库不一致时，一律以数据库为准做对账回补。Redis 崩了，账对不上，没关系，MySQL 里的账是真的，我们拿数据库去修 Redis，而不是反过来。缓存可以丢，账不能错。记住，Redis 不解决并发，它只是把并发挡在数据库前面。

常见错误清单

⚠️ 把「先 get 再 set」当成原子扣减，忘了两步之间有空隙，埋下超卖隐患。
⚠️ 用普通删除解锁，锁过期以后误删别人持有的锁，导致并发失控。
⚠️ Lua 脚本里写大循环遍历海量键，阻塞 Redis 拖垮整站。
⚠️ 把强一致的库存余额也放心放进缓存，缓存与库不一致引发超卖。
⚠️ 所有键设统一过期时间，到点集体失效，触发缓存雪崩。
⚠️ 不看命中率，命中率跌破阈值仍不告警，数据库压力悄悄爬升。
⚠️ 把 Redis 当成数据库替代，忘了它断电会丢、容量小、只能按键查。
⚠️ 扣减成功就以为下单完成，跳过消息队列落库，洪峰直接打爆数据库。

小结

🔹 Redis 在秒杀里扮演的是闸门，不是仓库。它把绝大多数请求挡在数据库之前，用原子操作、分布式锁、Lua 脚本堵住超卖与重复下单，再用消息队列把瞬时洪峰削平。真正兜底的永远是 WHERE number > 0 这行条件更新，以及以数据库为准的对账回补。
