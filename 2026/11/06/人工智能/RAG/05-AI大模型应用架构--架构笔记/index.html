AI 大模型应用架构 — RAG 与 Agent 的工程落地

05 AI 大模型应用架构

📌 本篇速览

  • 大模型是 next-token 预测，像和准是两回事
  • 四层架构：接入、编排、模型、数据
  • RAG 先查资料再回答，治幻觉的根本办法
  • Agent 自主跑流程与工程护栏
  • 上线前的评估、版本与数据治理

把模型接上业务不是终点。本文按接入、编排、模型、数据四层骨架，讲清 RAG 与 Agent 落地的工程护栏。

5.1 大模型是怎么说话的

🔹 大模型只做一件事。它根据前面出现的文字，猜下一个词最可能是什么。

📌 考点：大模型是 next-token 预测，像和准是两回事，幻觉是续写方式的必然产物。
它不确定事实，只是在做一道大规模填空题。屏幕上的字是一个一个往外蹦的，底层逻辑没有变。

它读过的文本越多，措辞和格式就越像样。法律文书的腔调、Java 代码的命名与异常处理，它都能模仿得很像。这里要分清两点：模仿能力强不代表结论可靠。像和准是两回事。

5.2 它擅长什么，又一定会在哪里出错

5.2.1 四类能放心的活

🔹 可以放心交给模型的四类活：整理口语成正式通知，把长文档压成三句话；从通话记录里挑出客户名与保单号；按 JSON 或表格输出；判断工单是投诉还是咨询，判断客户情绪急不急。这些任务没有唯一标准答案，做错也不致命。

5.2.2 四条必错的短板

🔹 它必定会错的短板有四条。第一，不知道你的私有信息，公司规章、报价与客户资料一概没有。第二，算术不可靠，合同从某月某日到某月某日算几个月，它是猜一个看起来合理的数。第三，知识停在训练完成那天，之后发生的事它不知道，却会一本正经地讲。第四，不懂时不会说不知道，而是编一条，这叫幻觉。幻觉是续写式工作方式的必然产物，与偶发 bug 无关。

5.3 钱和速度：token 与上下文窗口

🔹 模型按 token 计费。中文大约一个字算 0.6 到 1.1 个 token（不同 tokenizer 版本略有差异，o200k 约 0.73、cl100k 约 1.0–1.1），一页 A4 文档大约 800 到 1200 个 token。进出都收费，一来一回都是钱。

一次对话能同时看见的 token 总量叫上下文窗口，超了 API 默认返回 400 错误（context_length_exceeded），不会自动截断，需调用方自行处理或摘要。聊天到后面忘了前面不是记性差，是容量有限。
模型生成每个新 token 时，有 KV cache 只需计算当前 token 的 K/V 并与缓存的历史 K/V 做注意力（成本随长度线性增长），不会重算前面全部内容；无缓存时才会重算，上下文从 1000 加到 10000，等待时间会明显变长。

由此推出三条设计约束。能先筛选再喂的，别整本塞进提示词。小模型便宜就别动最贵的模型。重复问题问一百遍要算一百遍，能缓存结果就缓存。

5.4 一个能上线的 AI 应用由四层拼成

🔹 直接把前端请求发给模型接口，缺了中间两层，上线必然出问题。标准做法是四层。

📌 考点：四层架构——接入（鉴权/限流/审计）、编排（模板/路由）、模型（公有或私有）、数据（向量/文档/业务）。

层 角色 职责
接入层 守门口 鉴权、限流、审计，所有请求唯一入口
编排层 调度台 提示词模板、模型路由、多步编排、输出约束
模型层 后厨 调用公有接口或自有机房跑开源模型
数据层 库房 向量库存意思、文档库存原文、业务库存事实

接入层把鉴权、限流与日志这类每个功能都要做的事集中做一次，业务代码保持干净。编排层决定这次走哪条路、用哪个模型、按什么模板答。模型层通常不只用一家，因为成本、数据敏感度与响应速度三者互相冲突，一个模型兼顾不了。数据层是模型的外挂记忆：向量库存语义坐标用于找资料，文档库存原文用于给出处，业务库走查询接口取准确数字。

🔹 实验室测二十道题能答得漂亮，上线后真实用户带错别字，一句话问三件事，准确率立刻掉。中间差的那六十分，要由四层架构补上。

5.5 RAG：先查资料再回答

🔹 RAG 三个字母是检索、增强与生成。人话就是先查资料，再让模型写答案。

📌 考点：RAG 不改模型，递资料给它；治幻觉的根本办法是要求逐条给出出处。
整个过程不改动模型本身，只是递三页资料给它。

5.5.1 为什么先做 RAG

🔹 做 RAG 有三个理由。答案来自资料，不靠印象，可以要求逐条给出出处，这是治幻觉的根本办法。私有规章、产品条款与历史工单不可能拿去训练，放进资料库随时查，文档一改第二天答案就跟着变。比起微调要准备训练数据、占用算力（用托管微调服务也无需自租 GPU，周期从数小时到数周不等），RAG 几天就能上线，效果不达标时更容易排查是资料没找对还是没答好。

向量是理解 RAG 的关键。嵌入模型把一段话变成一串数字，意思相近的文本坐标就相近，检索本质是找最近的几个邻居。长文档通常需要切块，具体粒度需按效果调优（常见如 500-1000 token 或按工具默认，而非固定 300-500 字），否则一段向量要代表几百页内容，意思会被平均掉。

建库是离线准备：收集文档、清洗解析、切块、向量化、连同原文与出处标签入库。问答是用户等待的旅程，分六步：用户提问、问题改写、检索召回粗选若干条（常见 top10-50，按效果调优）、重排精选 3 到 5 条、拼提示词（问题加资料加规则）、生成并校验附出处。模型其实只干了最后一步，前面全是普通程序，哪格出问题就查哪格。

检索问题 典型现象 改法
答得笼统像念通用稿 检索段落和问题无关 优化切块、加重排
明明有规定却说查不到 召回条数太少 提高召回、按类型分检后合并
张冠李戴 缺元数据过滤 给文档打产品、地区与版本标签先过滤
金额日期算错 让模型干了精确计算 改走数据库查询或计算工具

效果不好时按这个顺序查：先看召回的段落对不对，再调切块和召回条数，然后加混合检索（向量管意思、关键词管编号型号字面），最后才改提示词换模型。企业知识库项目多数问题出在前两步，不是模型不够好。

5.6 Agent：从会答到会办事

🔹 RAG 让模型先查再答，Agent 让它自己跑流程。你给目标，它自己拆步骤、调工具、拿结果、决定下一步。步骤不是提前定死的，是边走边看。

5.6.1 四个零件

🔹 四个零件构成 Agent。规划器把大目标拆成小步骤

📌 考点：Agent 执行权限始终在程序手里；模型只输出调用意图与参数。
，且步骤可随中间结果调整。工具是它动手的唯一途径，查订单、算价格与发通知都走明确写好的接口，模型只能选不能造。记忆分短期（本轮上下文）和长期（用户偏好、历史记录），没有记忆每轮都像第一次见面。反思让它在拿到工具结果后自检成败、有无矛盾，失败带错误信息重试而非原样重来。

模型永远不直接碰数据库。程序先给一份工具清单，模型只看清单输出调用意图和参数，真正的查询由程序执行。执行权限始终在程序手里。

工具红线三条。清单要收窄，能查不能写，退款、改状态等写操作默认不开放给模型自主调用，必须转人工确认。权限校验在程序里做：这人有无权限看这条数据、该实例能否调此工具、参数是否在合法范围。参数校验和幂等不能少，模型重试很常见，没有幂等会同一笔业务办两次。

放开自主性后最先出事的是停不下来。给每次任务设硬上限：最多 8 步、最多调工具 5 次、总耗时不超 30 秒、token 不超额定值，到顶强制结束并交出已完成部分。同工具连续失败两次就停，别让它无限换姿势重试。高风险的对外发送、改客户资料与涉及金额的动作直接挂起等人工点头，系统还要有一键中断。

能不能上生产，回答四个问题：最多跑几步、最多花多少 token、出错怎么停、哪一步必须有人点头。四问都能答上来才放。

5.7 上线前的工程护栏

🔹 先 RAG 后微调。不要一上来就微调，RAG 成本低、见效快、改动可控，等 RAG 做到极致确认是模型能力不够，再谈微调。

🔹 把数据当产品管，不是一次性导入就完事。清洗、切块与向量化之外，增量更新机制最容易被忽略。新政策新条款要能当天进库当天生效，过期文档要下架，没人维护的知识库几个月后就开始答错话。

🔹 提示词要做版本管理。它直接决定模型的行为边界，改一句话准确率可能上升也可能让它突然开始编。把提示词写成带占位符的模板文件和代码一起提交，谁改的、何时改的、为何改都有记录。新版本先给 10% 的量跑，盯住准确率、拒答率与投诉数，有问题立刻回滚。

🔹 评估要形成持续机制。自动检测每单都过四道：格式校验、引用校验、敏感合规过滤及异常指标标记，不合格转人工或拒答。人工抽检按原因归类而非逐条改，改一处能解决一片。数据安全是合规底线。输入脱敏、敏感数据只走私有模型不出内网、按角色控制谁能问到哪级资料、问答与工具调用全量留痕。发现错误走标准路径：归类、用审计日志定位完整链路、一次只改一个变量、用整套测试集回归。

5.8 常见错误清单

🔹 1. 把模型接口直接写进业务代码，换供应商要改十处，应统一收在接入层和编排层。
2. 以为上大模型就等于上系统，缺了编排与数据层，幻觉和超范围调用都无人兜底。
3. 长文档不切块或硬切，500 页变成一整串向量，语义被平均，检索必然跑偏。
4. 只做向量检索不做重排和混合检索，专业编号、型号与人名这类字面项几乎无感。
5. 把金额、日期与时效这类精确计算丢给模型，应改走数据库查询或计算工具。
6. 给 Agent 开放过多写操作工具，退款、发短信默认转人工才是保命做法。
7. 不限制 Agent 步数与 token 预算，失败无限重试，账单烧光却没解决问题。
8. 提示词散落在后台文本框随手改，出错无法定位最近改了什么，应进代码库带版本。
9. 评估只靠感觉，没有固定测试集，改完看着变好其实某个场景悄悄变差。

5.9 小结

🔹 大模型给出的是聪明的概率，工程化给出的是可控的确定性。架构不追求让模型永不犯错，它要做的是让错误可发现、可兜住、可修正。先把资料给到它、规矩立住它、权限卡住它，每一条回答都有人能查，AI 项目的成功率才高得起来。
