04 云原生架构及应用

📌 本篇速览

  • 交付、伸缩、治理做成标准件，告别手工发布
  • 容器化、微服务化、持续交付、可观测性四件事
  • 五条设计原则与 Kubernetes 七个对象
  • 数据一致性三解法与弹性伸缩的延迟真相
  • 韧性六手段与三种发布策略

云原生让软件从设计第一天起就为云环境而生，把交付、伸缩与治理都做成标准件。

🔹 一座系统凌晨上线，三个人花了一整夜只为了换三行代码。走到第24步发现一台生产服务器的配置文件漏改了，只能全部回滚从头再来。问题不在有人偷懒，而在把软件当成了手工艺品，每一次上线都要靠人手工雕一遍。

4.1 从一次凌晨发布事故说起

🔹 那次事故里全是没有人在偷懒的熟练工，可流程本身会重复出错。根源是「软件当手工艺品雕」：上线要走二十七步，停服务、做备份，替换文件，改配置，重启验证，全靠人一步一步执行。这引出了云原生要解决的第一个命题，也就是如何让交付不再依赖手工。

4.2 云原生到底在管哪四件事

🔹 把云的本质想清楚，它相当于把机房交给别人管。传统自建机房要提前买够用三四年的机器，扩容要走采购流程，以周为单位，机器不忙时还在空转。租云则是网页点几下机器到手，扩容改个数字，用多少付多少。

🔹 但上云不等于云原生。把原封不动的应用搬到云服务器，只是换了住的地方。云原生是软件生下来就为云而造，它管四件事：怎么装、怎么拆，怎么发，怎么看。怎么装是容器化，把应用和环境打包成集装箱，搬到哪都能原样跑。怎么拆是微服务化，把臃肿应用拆成小服务独立部署。怎么发是持续交付，用流水线代替手工上传。日志、指标、链路都留痕，才谈得上可观测性。

📌 考点：云原生管四件事——怎么装（容器化）、怎么拆（微服务化）、怎么发（持续交付）、怎么看（可观测性）。

🔹 传统方式与云原生方式在七个维度上拉开差距：

维度 传统方式 云原生方式
交付单位 几十兆的发包 自带环境的容器镜像
运行环境 人工逐台配装 JDK 镜像内全部自带
部署方式 手工多步，易出错 流水线自动，业务不中断
扩容方式 采购机器，按周计 自动扩缩容，按秒计
故障处理 人工登录查日志 监控告警加自动重启
发布节奏 一月一次，如临大敌 一天多次，随时回滚
系统结构 单体，牵一发而动全身 微服务，各管各的

4.3 五条设计原则

🔹 云原生的骨架有五条，每一条都在防一类事故，可用十五个字记：拆得开、伸得缩，看得见，扛得住，少动手。自动化这一条强调先标准化再自动化，流程本身不确定，机器就学不会，人只能继续手工救火。

🔹 服务化要在代码规模超出小团队协作范围时拆分，按业务边界和生命周期切，拆完面向接口编程、功能高内聚、公共模块复用。弹性让容量跟着业务走，设定规则由 Kubernetes 自动完成扩缩容。可观测让内部状态可被外部看到，指标告诉你哪里不对，日志告诉你错在哪一行，链路告诉你卡在哪一环。
|—|—|—|
| 服务化 | 改一处要全量回归 | 微服务、领域驱动、API 网关 |
| 弹性 | 大促撑不住、平时空转 | Kubernetes、自动扩缩容、负载均衡 |
| 可观测 | 出事只能靠猜 | ELK、Prometheus、SkyWalking |
| 韧性 | 依赖一抖全线崩 | 熔断、限流、降级 |
| 自动化 | 手工发布易错熬通宵 | CI/CD、蓝绿、灰度 |

4.4 连锁零售中台改造

🔹 一个连锁零售企业的订单履约中台改造，目标支撑三年业务涨四倍，大促不人工扩容，全年可用性不低于 99.99%。改造前核心单体有八十万行代码，十二个模块挤在一个工程，任何改动要跑三小时全量回归，四个小组共用一条流水线。

🔹 改造按五条原则落地。服务化把单体按业务域拆成订单、库存与支付、会员四个服务，需求交付周期从四周变一周。弹性按 CPU 超阈值触发自动扩容，月账单从四十二万降到二十六万。可观测接入链路追踪后，平均故障定位时间从两小时压到八分钟。韧性用熔断、限流、多可用区容灾，可用性从 99.9% 提升到 99.99%。自动化把发布从四十分钟手工缩到六分钟全自动。

🔹 一个微服务系统可切成五层。入口层是浏览器、App 与小程序，还有开放 API，只认一个域名。网关层是请求唯一入口，做路由、鉴权，限流，熔断与灰度。业务层是订单、库存与支付、用户各管一摊。支撑层是注册发现、配置中心、链路追踪。数据层原则上一个服务管自己的库，不直接连别人的表，这是微服务拆得干不干净的分水岭。

🔹 Kubernetes 里要记住七个对象。Pod 是共享网络和存储的最小家。Deployment 管无状态服务，要几份补几份。StatefulSet 管有身份的服务，如 MySQL、Kafka，重启后数据不丢，前提是用 volumeClaimTemplates 挂了持久卷，持久化由持久卷保证、不是 StatefulSet 对象本身。Service 给随时会变的 Pod 配一个固定入口。Ingress 是集群对外的大门与前台，但它只是路由规则，要跑起 Ingress Controller（如 ingress-nginx）才真正生效。ConfigMap 把配置从镜像里抽出来单独管理。HPA 按 CPU、内存、QPS 自动扩缩容，CPU、内存由 metrics-server 提供，QPS 这类自定义指标还要另装 prometheus-adapter 暴露 custom.metrics.k8s.io。

🔹 注意 Utilization 按实际用量除以 request 计算，目标 Pod 的容器必须设 cpu request，否则 HPA 算不出平均利用率。

📌 考点：HPA 需 metrics-server 提供 CPU/内存指标；自定义指标（如 QPS）需 prometheus-adapter。

4.6 数据一致性与弹性伸缩的真相

🔹 把一件事拆到三个服务后，它不再是一个事务。一次下单可能动订单库、库存库、用户库，订单写完库存没扣时服务挂了，数据就不一致。三种解法：两阶段提交全程锁资源，性能差，仅银行内部转账这类强一致场景用；可靠消息把写库和发消息绑在同一本地事务，最终一致，最常用；补偿事务哪步失败反向补偿已完成的步骤。两条铁律是幂等和对账，每天定时比对两边数据兜底。

📌 考点：服务拆分后不再是单事务，三解法：两阶段提交/可靠消息/补偿事务；铁律是幂等与对账。

🔹 弹性伸缩不是一键变快，它有延迟。缩容默认有 300 秒稳定窗口，要连续低于阈值一段时间才触发、防止抖动，扩容默认没有稳定窗口、到阈值立即触发；调度器找机器拉镜像要十几秒到几分钟；启动应用含 JVM 预热往往更久；健康检查通过才挂负载均衡。所以真实项目里弹性是三件事一块做。提前按日历扩、日常水位控在五成左右、缩容比扩容慢。

4.7 韧性六手段与发布策略

🔹 韧性是别人家的服务一定会挂、会慢，我们能控制的只有自己怎么反应。六手段：超时设且比上游更短，逐层递减；重试只做幂等操作，配退避与次数上限；熔断在下游持续失败时切断，有关闭、打开、半开三态；限流不能只设总闸，接口和用户得分开设；降级保核心功能，提前备兜底数据；隔离是前面五手段的前提，从第一天就做。顺序不能乱。先限流，设超时，有限度重试，再熔断，按预案降级，从第一天就要隔离。

📌 考点：韧性六手段顺序——先限流、设超时、有限重试、再熔断、按预案降级、从第一天隔离。

🔹 发布有三种打法。滚动发布一批一批换，最省资源，新旧版本会同时跑。蓝绿发布两套环境一切换，回滚最快，代价是资源翻倍。灰度金丝雀先放百分之一到五的用户看指标，正常再放量，是现在主流选择。共同前提是数据库变更必须向后兼容，先加字段、再改代码、最后删旧字段。

🔹 常见错误清单：

🔹 以为上云就是云原生，把原程序原封不动搬上云服务器，只换了住的地方。

  • 服务拆得越细越好，结果改一下仍要全体协调，退化成分布式单体。
  • 把治理逻辑写进业务代码，语言被绑死，SDK 升级要所有服务重发。
  • 自动扩容前不提前扩，洪峰瞬间新实例还在路上，老实例已经倒了。
  • 数据库变更不与代码兼容，先删旧字段，发布即事故。
  • 镜像用不可信源且不扫漏洞，容器用 root，口令写进代码仓库。
  • 可观测只配监控不设追踪，遇到没见过的问题无法一步步追问下去。
  • 限流只设一个总闸，不从接口和用户维度分别设，保护不到位。

🔹 云原生用十五个字作尺子：拆得开、伸得缩，看得见，扛得住，少动手。它把交付、伸缩、治理做成标准件，让团队从手工雕软件走向流水线，也让系统从「怕出事」走向「出了事也能原地爬起来」。
