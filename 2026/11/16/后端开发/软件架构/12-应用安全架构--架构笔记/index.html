12 应用安全架构

📌 本篇速览

  • 常见错误清单（12.6）

这门课不讲操作系统加固，也不讲网络设备安全，只讲你每天在写的那套后端服务、那些接口和那些数据。读完你能看懂一份安全风险清单，在代码评审里问出关键问题，也能把六条上线检查项挨个做完。

12.1 引言与本课定位

🔹 先划范围。视频讲的「应用系统安全」是后端服务、接口、数据这一层的安全，不包括操作系统加固、网络设备配置、WAF 产品的选型对比。课程给后端、产品、项目同学看，目标是三件务实的事：看懂风险，写出不埋雷的代码，评审的时候能问出关键问题。

🔹 课程分四段路。第一段认识安全，弄清谁在攻击你、要守住什么、为什么要最小权限、为什么一道防线不够。第二段讲输入端的漏洞，包括 SQL 注入、XSS、CSRF 和密码怎么存。第三段讲身份与传输，包括认证授权、越权、Session 与 JWT、HTTPS。第四段把所有武器拼成一套纵深防御体系，再补上监控告警与出事之后的应急流程。

🔹 开场用的三份事故报告来自一个虚构的网约车平台「飞驰出行」，三份报告对应三个入口。

事故 发生的事 被打开的入口
报告一 黑产撞库盗号 黑客拿别处泄露的 800 万条账号密码，对登录接口每秒几万次地试，一夜撞开 8000 个账号，随后代叫高端车盗刷 登录口
报告二 薅光新客券 有人写脚本自动注册账号领券、下 2 公里起步价单、注销账号，循环往复，一夜 13 万个新用户，补贴被烧掉 200 万 营销口
报告三 行程数据裸奔 内部排查用的查询接口忘了加登录校验就上线，任何人拼个网址就能看到乘客手机号和常用地址 数据口

🔹 三份报告的共同点值得单独拎出来讲：攻击者从头到尾没有攻破服务器，他只需要找到一扇没锁的门。报告一的登录接口本身没有漏洞，密码校验也是对的，密码还是用户自己设的那个，问题在于没有区分人和机器。报告三的接口更简单，一个「忘了加校验」就全裸奔。所以安全的做法是把每扇门都锁上，而且不止用一道锁。

📌 考点：攻击的入口不是「服务器的强度」，是「业务入口的疏漏」。报告一属于可用性之外的另一类问题——认证本身正确，但缺少防自动化手段。

12.2 认识安全：敌人、目标与纵深防御

12.2.1 谁在攻击你

🔹 视频把攻击者分成四类，重点是知道每类人用什么招、用什么招就得配什么防。

攻击者 特征 常用手法 防御重点
脚本小子 技术低但数量极大，下载现成扫描工具照着教程试 低危漏洞批量扫描、弱口令、已知框架 CVE 基本功：输入校验、参数化、依赖升级
黑产团伙 以赚钱为目的，有分工：有人写程序，有人出设备，有人销赃 撞库、薅券、DDOS、拖库 业务漏洞：验证码、限流、风控、账号锁定
竞争对手 动作温和，持续收集 爬价格、抓名单、拖数据库 数据外流：脱敏、权限、水印、审计
国家级 APT 有组织长期渗透，盯基础设施 长期潜伏、供应链、0day 靠更高层面的合规与响应，普通项目基本碰不到

🔹 黑产里有个词叫「肉鸡」，指被黑客远程控制的别人电脑。黑产手里可能握有几万台，一台换一个 IP 来打你，封都封不过来。视频给的排序是：对脚本小子靠基本功，对黑产靠业务漏洞，对对手方靠防数据外流，这三条基本能覆盖普通项目遭遇的大多数攻击。国家级 APT 这一类在普通公司层面遇不到，遇到了也要靠公司层面以上的力量应对，本课不展开。

12.2.2 要守住什么：CIA 三要素

🔹 安全行业有个共识框架叫 CIA 三要素，定义了安全要守住的三样东西。

要素 含义 网约车平台的例子 主要手段
保密性 Confidentiality 该看的人才能看 乘客手机号、行程位置只有本人和授权运营能看 加密、脱敏、权限控制
完整性 Integrity 数据没有被偷偷改 35 元的订单不能半路被改成 0.01 元 签名、校验、幂等
可用性 Availability 该用的时候能用得上 晚高峰打不开 App，业务就归零 限流、扩容、高可用

🔹 把三份报告对号入座：盗号是保密性失守，薅券是完整性被绕过，DDoS 打在晚高峰是可用性归零。后面讲的每一个防御动作，归根结底都在守护这三个字母。

12.2.3 第一条原则：最小权限

🔹 达成目标的第一条原则简单到像废话：只给完成工作所需的最小权限。视频的比喻是发钥匙——保洁阿姨只需要卫生间的钥匙，不需要办公室保险柜的密码。

🔹 最常见的违反方式是数据库账号。配置里写 username=root 的项目不少，root 是超级管理员，能建表、删表、删库。开发时省事，装完数据库默认就是它，不用建账号不用授权。但这份省事可能在应用被打穿那天变成大雷：攻击者拿到数据库连接，等于拿到整个库的生杀大权，脱库删库都很方便。

🔹 正确做法是专门建应用账号。给网约车平台建一个 ride_app 账号，只授权三张业务表的增删改查。那么同样的注入打进来，能碰到的只有三张表，损失从整库蒸发缩到部分数据。这条原则的适用面很广：服务器上不要用管理员账号跑应用，离职同事的账号要及时回收，云服务器只开用得到的端口。每发一把钥匙都问一句：他真的需要吗。

12.2.4 一道防线不够：纵深防御

🔹 就算权限全设对了，一道防线也够吗？不够。视频用两座城堡作比。第一座只有单面墙，一圈城墙一个城门，墙内的金库粮仓一览无余，城门被撞开一处就全线失守。第二座是同心城堡，外墙、中墙、内墙一层套一层，金库还自己上着锁，外墙破了只算进了下一层。

🔹 很多系统的安全就是第一座：登录这一道墙，墙内所有接口都不设防。报告三就是这么出的事。即便上了 WAF，WAF 也只是挡在服务器前面的过滤程序，按规则识别并拦截恶意请求，遇到规则没覆盖的新手法被绕过去，后面就是一马平川。

🔹 换到攻击者视角看成本就明白了：一层防线绕一次就行，四层防线要连续绕四次，而且全程不能被发现。永远会有新的攻击手段，所以「让攻破不可能」做不到，能做到的是「让攻破贵到不划算」，没有性价比攻击者就放弃了。

🔹 这个思想有个正式名字，叫纵深防御。视频给的定义是：不依赖任何单一防线，在攻击者必经之路上部署多道相互独立的防御，任何一道被绕过，下一道继续拦截。评估一个系统的安全性，就问一句：攻破它要连续穿过几道互不相干的防线。

层 放什么 视频给的比喻 挡什么
第 1 道 边界 DDoS 清洗、防火墙、IP 风控 城堡外墙 大批量的恶意流量军团
第 2 道 网关 限流、接口签名校验、WAF 规则 门口的卫兵 伪装进来的攻击请求
第 3 道 应用 登录认证、权限检查、输入校验、业务风控 墙内每道直廊 越权与业务逻辑漏洞
第 4 道 数据 最小权限账号、敏感字段加密、脱敏存储 金库最后一把锁 库被拖走后的损失

🔹 纵深有代价。每加一层，开发维护多一摊事，排查问题多一环。所以要按数据价值配层数：查路线的公开接口配两道就够，支付、账户、身份证号这类秘密等级高的才四道全上。

12.3 输入之恶：注入、XSS、CSRF 与密码存储

12.3.1 铁律与四个输入面

🔹 应用层漏洞最多的地方是输入，视频给的铁律是：永远不要相信任何输入。程序有一张嘴，外面进来的数据都从这张嘴进来，进来的可能是捣乱的指令。

输入面 典型例子 为什么不能默认可信
表单与 URL 参数 搜索框、登录框 最常见也最危险，直接进业务逻辑
请求头与 Cookie User-Agent、Referer、自定义头 浏览器发的附加信息全都能伪造
上传的文件 文件名、类型、内容 三者全都能伪造
第三方回调 支付通知、短信回调 同样不能默认可信，要验签

🔹 不信任不等于拒绝输入，正确的做法是让每处输入过三道关卡。第一关看格式对不对，手机号只允许 11 位数字，不对直接拒绝。第二关看内容危不危险，把可能危险的字符替换成无害写法，这个动作叫转译。第三关最关键，拿输入去干活的姿势安全吗，拿用户输入查数据库用什么姿势，姿势不对前两关全过也没用。

12.3.2 SQL 注入

🔹 SQL 注入是后端最该刻进 DNA 的一条。拼接这种写法当年很多教材就是这么教的，因为语句怎么写代码就怎么写，拿到用户输入的手机号直接拼进 select * from user where phone = '...'。直到攻击者发现，你的代码其实是在替他写 SQL。

🔹 最简单的攻击是在密码框输入一个单引号加 or 1=1，拼进去之后条件变成 pwd = '' or 1=1，一真为真，整个等式恒成立，不需要正确密码就能登录。

🔹 完整攻击分三步。第一步探门：在输入框提交一个单引号，正常系统把它当普通字符什么都不发生，有拼接的系统会被破坏语法并报错，报错本身就是「这里有拼接」的信号。第二步脱库：SQL 里有 UNION 语法，作用是把两次查询的结果拼在一起返回，攻击者注入一段 UNION 查询，让数据库在返回正常结果的同时把整张用户表也查出来一起送走，几百万条数据就这么被打包带走。第三步留后门：如果应用连数据库用的恰好是 root，攻击者还能注入建账号语句，给自己创建管理员账号，以后随时走正门，漏洞修了后门也还在。

🔹 根治办法是参数化查询，也叫预编译：SQL 骨架先写好，用问号占位，用户输入只作为值传进去。输入永远是数据，成不了指令，这个保证由数据库驱动层提供。格式校验、最小权限可以再叠加，但参数化才是根本，其余都是保险手段。要留个尾巴：表名、列名、排序方向这类结构没法参数化，只能映射到固定白名单；存储过程内部自己拼的 SQL 也不在参数化的保护范围内。

⚠️ 拼接过一次的项目要全量排查，不要只改出事的那处。排查手段有三：代码搜索字符串拼接到 SQL 的写法，全量开关 SQL 日志抽查实际执行的语句，做一次带引号的输入验证报错是否出现。

12.3.3 XSS：打在浏览器上的攻击

🔹 SQL 注入打的是数据库，XSS 打的是用户的浏览器。攻击者把一段恶意代码注入到你的页面里，在其他用户浏览时偷偷执行。

🔹 场景很具体：网约车平台的司机评价栏，有人提交了一段 JavaScript 代码。这段代码干的事只有一件，把当前浏览者的登录凭证发到黑产服务器。服务端没做处理，原样存原样发。司机打开这条评价，浏览器静默执行了这段代码，凭证被偷走，黑产冒充司机进账号接单，还能改收款账户。司机全程什么都没点，但这些都发生了。

🔹 防御有三层。第一层输出转义，页面要显示用户输入时，把 < 这类特殊字符替换成无害写法，浏览器只当文字显示不当代码执行。用 Thymeleaf 这类模板引擎时默认就是转义过的，最危险的是手工拼 HTML 字符串。第二层富文本白名单，评论区要支持加粗和图片，不能一刀切全转义，而是列一张允许清单，只放行这些标签，清单以外的一律删掉，用 OWASP Java HTML Sanitizer 这类现成工具，不要自己造轮子。第三层给 Cookie 加 HttpOnly 标记，浏览器里任何脚本都读不到它，XSS 就算得手，偷到的也是空的。

12.3.4 CSRF：不写一行代码的攻击

🔹 SQL 注入和 XSS 都是攻击者主动写代码，CSRF 更阴险，他一行代码都不写，借你的手。

🔹 四步过程。你登录了网约车平台，浏览器里存着自动登录的 Cookie，浏览器每次访问都会自动带上。你顺手点开邮件里的一个链接，是钓鱼网站。钓鱼页面里藏着一行看不见的代码，让浏览器去请求你的支付接口，收款人设成攻击者，金额 500 块。浏览器发请求时自动带上了你的 Cookie，服务器一看登录状态有效、请求合法，直接扣款。全程你没碰过支付页面，钱却少了。

🔹 服务器为什么没拦住？因为请求确实带着合法的 Cookie，它以为是你本人。破绽在于请求不是从这个平台的页面发出的。所以防御思路是让服务器能区分请求来自自家页面还是别家伪造的页面，用两招。

🔹 第一招是 CSRF Token：平台页面每次生成一个随机令牌塞进表单，提交时校验。跳到钓鱼站点的浏览器跨域拿不到这个令牌，伪造请求一验证就露馅。第二招是 SameSite 标记：给 Cookie 声明跨站请求不要自动带上，第四步就根本成功不了。

📌 考点：Spring Security 默认就开启了 CSRF 防护（CsrfFilter 在默认过滤器链里），不是配置一行才生效。视频里说的「一行配置开启」指的是需要自定义规则时的写法，纯 HTML 表单用默认策略反而更省事。

12.3.5 密码怎么存：四级演进

🔹 密码存储有四级，前三级都很危险，而且有些项目现在还在用。

级别 做法 问题
第 1 级 明文 数据库 pwd 列直接存密码 拖库一次，800 万条密码明文到手，还附赠一批用户素材
第 2 级 MD5 存 32 位指纹 攻击者提前把常见密码的指纹算成对照表（彩虹表），查表即还原
第 3 级 MD5 + 加盐 每个用户配随机盐再算 彩虹表失效了，但 MD5 设计目标就是快，显卡每秒几十亿次，能直接暴力猜
第 4 级 bcrypt 自动加盐 + 故意慢 同一密码每次指纹不同；单次校验耗时随 CPU 与 work factor 变化，业界常见量级是几十到一百多毫秒

🔹 视频给出的落地方式就是两行，注册时用 encoder.encode(密码) 存指纹，登录时用 encoder.matches(密码, 存的指纹) 校验，前面的加盐和慢速判断都由库包管。

🔹 存进数据库的指纹应该长成 $2a$ 开头的样子，这是 bcrypt 的标志，看到明文或者裸 MD5 就说明没改对。回到报告一，8000 个账号的密码如果当初都是这么存的，泄露出去的也只是指纹，黑产拿着指纹登录不了任何地方。

12.3.6 挡住机器：三层闸门

🔹 密码存好了，登录口还得设置去挡机器。回到报告一，黑产拿 800 万条密码对登录接口每秒几万次地试，接口本身没漏洞，密码验证也是对的，问题在于没有区分人和机器。视频给了三层闸门，下表阈值是示例值，实际要按自身业务量与风控成本实测校准。

层 做法 效果
第 1 层 验证码 登录失败 3 次后弹出 机器过不了这一关，撞库速度从每秒上万次掉到人工打码的成本价；策略是失败才出，正常用户无感
第 2 层 限流 同账号每分钟最多 5 次密码尝试，同 IP 每分钟最多 60 次登录请求，超了返回「稍后再试」 闸门只认速率，不管你是人是机器，用 Redis 计数器一小时能写完
第 3 层 账号锁定与核查 失败 10 次锁 30 分钟；异地登录、新设备登录要短信二次验证 密码被撞对了还有最后一道门兜底

🔹 报告二同理：领优惠券的接口加每设备限领一次、图形验证码、异常注册检测，脚本就薅不动了。视频把风控的本质总结成一句话：要让机器伪装成人的成本，高过装人能赚到的钱。

12.4 身份与传输：越权、Session、JWT 与 HTTPS

12.4.1 越权：应用安全第一大漏洞

🔹 第三章换个角度，问两个问题：接口怎么知道你是谁，怎么证明在路上没被偷听。先说第一个，认证和授权都是解决「证明你是谁」的问题。

🔹 越权指用合法的身份干超出权限的事情，分两种。

类型 定义 例子
水平越权 同级别用户互看数据 张三登录后看到自己的行程，URL 里 tripId=1024，改成 1025 就看到了李四的行程
垂直越权 低权限的人碰高权限的功能 普通乘客账号在地址栏拼管理后台的封禁司机接口，直接把司机封了

🔹 服务器只检查了「登录了吗」，没检查「这条数据是你的吗」「你的角色够吗」。报告三那个裸奔接口是极端的水平越权，连登录都不用查。

🔹 视频说越权是应用安全里数量第一的漏洞，给了三个理由。门槛最低，不需要任何黑客技术，改个数字谁都会。工具测不出，它藏在业务逻辑里，只有代码评审和手工测试才能发现。行业公认，OWASP 十大风险榜单里的访问控制失效常年排第一。

📌 考点：OWASP Top 10:2025 榜单里 A01 仍是 Broken Access Control（访问控制失效），官方描述写的是它「维持着第一名的位置」。2025 版把 XSS 并进了 A05 Injection。

🔹 修复口诀是「数据要认主」：每个查数据改数据的接口都要问一句，这条数据的归属人和当前登录人是同一个吗，不是就直接拒绝。管理接口再多问一句，他的角色够吗。验证只要五分钟：登录张三后改 id 查李四必须被拒，普通账号调管理接口也必须被拒。这两条要写进上线清单。

12.4.2 Session：服务器怎么记住你

🔹 登录之后服务器怎么记住你，靠 Session。提交账号密码，服务器验证通过后做三件事：生成一个随机的会话 ID，把 ID 连同用户和过期时间存进自己的存储；把 ID 塞进 Cookie 发给你；之后你每次请求都自动带上 ID，服务器查表发现是这个用户就放行。

🔹 视频用健身房手牌作比：前台登记你的信息并发一块手牌，之后刷卡进门，前台按牌号查登记簿，身份信息只存在前台，牌丢了挂失就行。

🔹 分布式时代的麻烦在于服务从一台变成十台：这次登录落在 A 机器，Session 也在 A 机器，下一个请求落到 B 机器，B 上没有这个登录态。两种解法：要么把 Session 集中存到 Redis，要么换思路用 JWT。

🔹 这里有个小坑叫会话固定攻击：登录成功后必须换发新的会话 ID，不能沿用登录前那个，否则攻击者可以先拿到一个会话 ID，等受害者登录后拿同一个 ID 冒充。Spring Security 默认就做这件事（Servlet 3.1+ 容器走 changeSessionId），用 Spring Session 存 Redis 也一样生效；自己手写登录逻辑、不走 Spring Security 认证链的就得当心。

12.4.3 JWT：把身份写成一张票

🔹 JWT 全称 JSON Web Token，思路是不把身份存在服务器上，直接写在一张防伪票据上。常见的是 JWS 形态：三段用点号分隔，头部、载荷、签名。RFC 7519 里 JWT 也允许 JWE 加密形态，那是五段，工程上做身份票据用的都是 JWS。载荷那一段是 Base64URL，也就是 URL 安全的变体，去掉了末尾补位符，解开就是一份 JSON 明文，含 user id、过期时间等，这些谁都能看，但谁也改不了，改任何一个字第三段签名就对不上，服务器直接拒绝。签名由服务器的密钥生成：若用 HMAC 这类共享密钥（HS256），能验签的一方也能签发；要保证只有签发方能造，就得用非对称私钥签名（RS256、ES256）。

🔹 还是手环的比喻：演唱会入场发你一个防伪手环，上面印着你是 VIP 区、3 日有效，任何一台闸机扫一眼防伪标志就能放行，不用打电话问客服。这就是无状态，十台服务器谁都能验票，前面集中存储 Session 的麻烦消失了。

🔹 JWT 有三个坑，面试和实战都爱问。

坑 说明 应对
不能主动作废 手环发出去，有效期内就是有效的，账号被盗了也拦不住 有效期缩短到 15 分钟级别，配刷新令牌，别发几天的长期票据
载荷是明文 Base64 不是加密，谁都能解开看 别把手机号、密码这类东西塞进载荷
退出登录是假的 客户端删了票据，这张票本身还能用到过期 要真踢下线就配黑名单

🔹 选型按业务来：传统 Web 单体用 Session 就够，简单省心；微服务、多端 App、跨域场景用 JWT 可以少一次集中查询；要立刻踢下线的能力，就用 Session 或 JWT 加 Redis 黑名单。

12.4.4 HTTPS：路上不被偷看

🔹 身份的问题解决了，但票据会在网络上跑，会被偷看，这就要上 HTTPS。视频把 HTTP 比作明信片：发登录请求，账号密码都是明文，经过路由器、运营商、机房任何一环被监听，密码直接泄露，咖啡馆的钓鱼 WiFi 多半就是干这个的。

🔹 HTTPS 要干两件事。一是加密，保证在路上被偷了也看不懂。二是验身份，确认对面真的是你要访问的那个服务器，而不是中间人冒充的。

🔹 握手四步走。第一步浏览器说，我要连接了。第二步服务器回一个钥匙加证书，证书相当于服务器的身份证，由权威的证书机构 CA 盖章担保，浏览器出厂时内置了这些机构的名单，所以能识别真假。第三步浏览器验完证书，用钥匙加密一个属于双方的暗号发过去。第四步全程用这个暗号做对称加密通信。

🔹 精髓一句话：用慢的非对称加密安全地商量暗号，用快的对称加密去跑业务，既安全又不牺牲速度。

🔹 对开发者来说其实只需要做一件事：全站启用 HTTPS。Let’s Encrypt 免费提供证书，有效期 90 天，到期必须自动续期，配合 certbot 申请后，Nginx 加几行指定证书路径的配置就能开启加密，技术门槛很低。两个细节要注意。一是 Cookie 加 Secure 标记，数据必须且只能通过 HTTPS 发送。二是 HTTP 全部 301 跳 HTTPS，不要留半个明文入口——用户先用 HTTP 连上哪怕只停留半秒再跳，这半秒传输的数据依然没加密，攻击者可以在这一瞬间把人劫持走。

⚠️ 2026 年了，任何明文 HTTP 都可以看作裸奔。

12.4.5 接口签名：防篡改与防重放

🔹 HTTPS 挡住了路上偷看，但还有两个它管不着：篡改和重放。

🔹 篡改是指订单本来 35 元，攻击者用抓包工具把参数改成 0.01 元再发出去。要注意这条消息是他自己发的，改完自己加密，HTTPS 拦不住。重放是把领券这种请求原样再发一万次，每次都是合法请求。

🔹 抓包工具就是能截获并查看手机与服务器之间来回数据的软件，程序员调试用它，攻击者也用它。HTTPS 之后它看到的是密文，但攻击者可以修改自己的客户端，让发出去的数据被改动后提交。

🔹 对策三件套。签名：把参数排序拼接，加上只有客户端和服务器知道的密钥，算出一个指纹一并上传，服务器用同样的算法重算对比，改一个参数指纹就全错，而密钥在服务端，攻击者算不出新指纹。时间戳：请求带当前时间，超过 5 分钟直接拒绝，等你想重放时包已经过期，像超市的限时券。nonce 一次性随机数：服务器记着见过的随机数，再出现就拒绝，同一个请求只能用一次。支付、领券这类涉及资产损失的接口值得加 nonce。

🔹 适用范围要说清楚。网页端的密钥藏不住，JS 里都能扒出来，所以签名主要是防篡改。App 端的密钥同样能被逆向提取，所以别指望密钥不可见，真正锁死重放的是服务端记录已用过的 nonce，nonce 一次性，签名只负责防篡改。开放给第三方的 API 签名是标配，微信、支付宝的支付回调都是这么验证的。

12.4.6 脱敏：展示时留一手

🔹 脱敏一句话：数据库里存全量，页面上按需遮掩。不是删数据，是不同人看到不同的精度。

数据 本人 司机 客服 运营报表
手机号 138****5678 138****5678 可解密核对 不出现，只存聚合值
家庭住址 完整 只到小区名 完整，但要录屏审计 按热力图聚合
身份证号 按业务需要 不展示 只看后四位核对 不展示

🔹 还有一个重灾区是日志。页面脱敏了，日志却把完整手机号和 token 全打出来，问题一样严重。日志权限要收紧，留存要久，还会被采集平台汇总，所以要给日志框架配脱敏转换器，上线前拿手机号正则 grep 一遍，确认这类内容已经不存在了。

12.5 纵深防御：四层全景与上线清单

12.5.1 四层拼起来

🔹 前面三章的内容，每一条都挂在四层全景图的某一层上。

层 组件 覆盖前面哪几章
边界 DDoS 清洗、防火墙、IP 风控 挡大批量恶意流量，属云厂商默认能力，选型时开启即可
网关 WAF 规则、限流、接口签名校验 报文级拦截，像门口的卫兵挨个盘查
应用 认证授权、输入校验、业务风控 开发者的主战场，输入之恶与身份两章都在这一层
数据 最小权限账号、字段加密、脱敏存储 库被拖走时拿到的也是密文和掩码

🔹 回看三份报告：盗号被第三层的验证码、限流和 bcrypt 拦住，薅券被第三层的业务风控拦住，裸奔接口被授权检查拦住。前面还有边界和网关两层缓冲，后面还有数据一层兜底。这就是城堡隐喻在工程上的对应物。

12.5.2 网关三件套的能力边界

🔹 网关三件套都是现成组件、配置就能用，但要知道各自的能力边界。

组件 像什么 能挡什么 挡不住什么
WAF 地铁安检机 内置成百上千条攻击特征，以 OWASP Core Rule Set 为例，包含 SQL 注入的引号套路、XSS 的 script 标签、路径穿越的 ../ 等专项规则文件 变形攻击、新漏洞、业务逻辑漏洞，所以它是缓冲不是答案
限流 景区闸机 单 IP 每秒 100 次、单用户每分钟 30 次；NGINX 的 limit_req 默认返回 503，要 429 语义得加 limit_req_status 429；挡撞库、薅券、爬虫 换了 IP 或换了设备的分布式慢速攻击
IP 风控 黑名单 接入威胁情报库识别已知代理、肉机、扫描器；同 IP 一小时注册 2000 个账号就加黑 黑产租得起很多机器时，所以风控不能只看 IP，还要配设备指纹和行为序列

🔹 限流算法记住两个就够：令牌桶是匀速发牌，允许小的突发；漏桶是匀速放行，超出的排队或拒绝。两者都比固定窗口科学，固定窗口在边界处会漏掉一倍的流量。NGINX 的 limit_req 用的就是漏桶，几行配置就能配出来。

12.5.3 应用层上线检查清单

🔹 网关三件套再强也只是外线，真正的清单还是应该在开发者手上。视频给了六条，每条都带几分钟能做完的验证方法。

# 检查项 验证方法
1 SQL 全部参数化，无一例外 代码搜索字符串拼接的查询，开 SQL 日志抽查
2 密码 bcrypt 存储；登录失败 3 次出验证码，10 次锁定 查数据库 pwd 字段应以 $2a$ 开头；手动试错验证策略生效
3 每个接口都答得出「是否认证」「是否授权」 不带 token 调一次必须被拒；拿张三的 token 查李四的数据必须被拒
4 输出默认转义、富文本白名单、Cookie 的 HttpOnly / Secure / SameSite 三标记 在评论区输入带 script 标签的内容，看是否原样执行；查响应头的 Set-Cookie
5 CSRF Token 开启；支付领券类接口有签名加时间戳再加 nonce 抓包重放同一个支付请求，第二次必须失败
6 敏感数据分级脱敏，日志里 grep 不到手机号和 token 按分级表抽查页面；日志平台用正则搜手机号

🔹 每条几分钟就能验完，都是顺手能做到的事，但漏一条就可能让系统出大问题。

12.5.4 数据层：最残酷的假设

🔹 数据层的假设最残酷：前三层全被攻破，攻击者拿到了数据库连接，执行了整库导出。这一层要保证这一刻他拿到的尽可能都是没用的东西，落到三件事。

🔹 第一件存储加密。身份证、银行卡这类拖走就造成资产损失的字段，落库前用 AES 加密，密钥放独立的 KMS 密钥管理服务里，拖走的是密文，没有密钥就是一串乱码。手机号既要加密又要能查，就额外存一列可检索的派生值，比如加盐 HMAC 的完整值做精确匹配，或者前 3 位加后 4 位的组合列做片段匹配。掩码形态只用于展示，不能拿去查库。

🔹 第二件权限矩阵。应用账号只碰业务表，数据分析账号只读副本并且看的是加脱敏的视图，DBA 不该有直接看明文身份的通道，要看就得走审批、走解密接口、留审计。

🔹 第三件备份。勒索软件的底气就是你没有备份，所以按 321 原则来：三份副本、两种介质、一份异地。而且必须真的演练过恢复，没恢复过或者恢复不了的备份等于没有。

12.5.5 监控与告警

🔹 没有系统能保证永远不被攻破，公开披露的大规模安全事件里不乏行业头部公司。区别在于被攻破后 10 分钟发现，还是 10 个月之后上了新闻，发现早晚直接决定损失是一次攻击还是一场灾难。

🔹 要盯住五个信号。登录失败率突然升高，可能是撞库。单个 IP 或单设备高频请求，可能是扫描或爬虫。异常时段大量数据导出，可能在拖库。造成资产损失的接口成功率骤降，可能是攻击已经成功。

🔹 告警有三个原则。发到运维值班群，而不是靠人盯屏幕。每条告警必须可以行动，收到就知道要干什么，否则只是噪音。每条要写清楚看哪里、找谁、按哪个手册。安全日志要单独留存六个月以上，按 180 天设保守值就能满足这条下限。

📌 考点：《网络安全法》要求采取监测、记录网络运行状态和网络安全事件的技术措施，并按规定留存相关网络日志不少于六个月。这条规定在 2016 年原法里是第二十一条，经 2025 年 10 月 28 日全国人大常委会修正（2026 年 1 月 1 日起施行）后条号顺延为第二十三条，引用时按现行版本写。

12.5.6 出事之后：应急五步走

🔹 真被攻破了怎么办，视频给了五步，应该直接写进运维手册。

步骤 动作 要点
1 止血 封 IP、下线受影响的接口、强制重置涉及账号 不要先急着查原因，先关水龙头
2 取证 保留攻击时段的日志快照 不要一重启就把证据冲毁了
3 定位 从告警倒查入口，看是哪个接口、什么漏洞
4 修复验证 补漏洞、回归、复盘还有没有别的口子
5 通报复盘 评估影响面，决定要不要通知用户改密码，写事故报告 把教训沉淀成清单上的新条目

🔹 第 5 步最后那句是安全体系的自我生长：每次事故都要给清单加一条新规则。

12.6 常见错误清单

⚠️ 数据库连接用 root，注入一次就拿到整库权限。应建应用账号，只授权业务表。

⚠️ SQL 语句用字符串拼接。哪怕前端做了校验、做了转义，绕过前端太容易，只有参数化是根治。

⚠️ 密码存 MD5 或 MD5 加盐。MD5 太快，显卡每秒几十亿次。改用带 work factor 的慢哈希：OWASP 现行首选 Argon2id，其次 scrypt，bcrypt 只作遗留系统的可接受选项。

⚠️ 登录失败没有验证码、无限流。密码再对，没有区分人和机器，一夜被撞开几千个账号。

⚠️ 评论区直接拼 HTML 渲染用户输入。用模板引擎默认转义，富文本走白名单工具，Cookie 加 HttpOnly。

⚠️ 只在登录这一道墙上设防，墙内接口全裸奔。报告三就是活例子，内部排查接口上线前忘了加校验。

⚠️ 查数据不校验归属。改个 id 就能看别人的行程，这是水平越权，OWASP 榜单第一类。

⚠️ Session 登录成功后不换 ID，或者 JWT 有效期一给几天。JWT 不能主动作废，长期票据等于长期后门。

⚠️ 站点留了 HTTP 入口。301 跳 HTTPS 之前那半秒是明文窗口。

⚠️ 只靠 HTTPS 就以为安全了。HTTPS 挡不住客户端自己的篡改和重放，敏感接口要签名加时间戳加 nonce。

⚠️ 页面脱敏了，日志却打印完整手机号和 token。日志同样是泄露面。

⚠️ 上 WAF 就当安全了。WAF 是缓冲不是答案，变形攻击和业务逻辑漏洞照样绕过去。

⚠️ 有备份但从没演练过恢复。恢复不了的备份等于没有，按 321 原则并且定期演练。

⚠️ 安全告警发到没人看的群。告警不能行动就只是噪音，发现早晚直接决定损失大小。

12.7 小结

🔹 这门课的结论是一句话：安全要靠让攻击者的每一步都付出代价来实现。

🔹 带走的具体东西有三样。一份 OWASP 十大风险的视角，知道注入、XSS、越权分别是什么、怎么防。一个思想叫纵深防御，四道墙配起来，每道被绕过下一道继续拦。三把输入的刀加两个身份方案，SQL 注入靠参数化、XSS 靠转义加白名单加 HttpOnly、CSRF 靠 Token 加 SameSite，身份侧 Session 与 JWT 各有适用场景和各自的坑。

🔹 落地的东西有两份。一张四层全景图，边界、网关、应用、数据，按数据价值配层数。一份六条规则的检查清单，SQL 参数化、密码 bcrypt、接口认人认角色、输出转义与 Cookie 三标记、CSRF 与签名 nonce、敏感数据分级脱敏，每条都带几分钟能做完的验证方法。

🔹 安全没有一劳永逸，是一个持续过程，每天自查才能越做越好。真正的判据是「攻破它要连续穿过几道互不相干的防线」。
