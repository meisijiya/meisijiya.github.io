简历上的项目描述一行就写完了，面试官会照着这一行往下切四五层。技术栈谁都背得下来，难答的是「你这么做的理由」和「你怎么证明它对」。这份合集按简历原句拆开，每一组都能对回简历里的某一句话，再补一层大概率会跟上的追问。

这一版按定稿的三版简历（软件测试、Java 后端、Python 后端）重写。数字分两类：实测数字写出来并交代怎么测的，设计值和经验值一律写成边界，不当成果报。

一、追问的四层

层 面试官在验什么 典型问法
一 你到底做没做过 这个项目解决什么问题，链路怎么走
二 你当时有几个选择 为什么用这个方案，别的不行吗
三 你有没有验证 怎么证明它真的work，怎么知道没测漏
四 你踩过什么坑 出过什么问题，怎么定位，改了什么

大部分回答停在一层，把技术栈念一遍。二层的答案是取舍，三层的答案是判据，四层的答案是事故。项目追问的分数集中在后两层。

一个通用句式，先说判断，再说动作，最后交边界。判断让人知道你懂原理，动作证明你动过手，边界说明你没夸大。

问题 1：固定长度切块把一句话劈成两半

简历原句：检索效果不靠感觉判断：自建固定问题集，按命中与召回口径横向比较切块与混合召回方案，用结果决定策略

会这么问：知识库的文档怎么进去，切块怎么切？

回答：起初按固定字数切，检索回来的是半句话，模型补全时就开始自己往下写。后来按语义边界切，标题、段落、列表项各算边界，超长的段落再按句子切，相邻块留一点重叠，避免答案正好落在切口上。块大小按文档类型分开设，教程类段落长、FAQ 类短，混用一套长度两种都吃亏。切哪种不靠感觉，靠固定问题集比：同一批问题在两套切法下各跑一遍，看命中率和正确答案的排位，差的那套就换掉。

再追一层：重叠会不会让同一段内容被召回两次？会。所以召回后按块 id 去重，拼接时按原文顺序排，乱序塞进去模型容易把因果读反。

边界：重叠量是经验值，换文档类型要重调。表格和图注没有专门处理，这类内容现在切得比较糙。固定问题集是我自己攒的，题目覆盖不到的类型，切块策略在那类上等于没验证。

问题 2：只靠向量检索，关键字查询全丢

简历原句：做查询重写、语义分块与 BM25 + 向量混合检索，用固定问题集按命中与召回口径比较

会这么问：用户搜一个具体的函数名或错误码，能搜到吗？

回答：纯向量检索对精确词不敏感。函数名、错误码、配置项这类字面匹配的查询，向量相似度反而把结果排到后面。我加了一路 BM25，两路各出候选后合并排序。比较用的是自建固定问题集，看正确的段落能不能被召回、召回后排第几。

再追一层：两路分数不在一个量纲上，怎么合并？两条路都有人用：把两路分数各自归一化再加权求和，或者直接用排名融合。我选了排名融合，因为 BM25 的分数和余弦相似度没有可比性，归一化本身也要按语料调参。融合之后还能再用重排模型过一遍，那属于可选的第二阶段，不做也能上线。

边界：语料规模小，融合权重是按经验定的，没做大规模调参。这套策略在更大的语料上未必还成立。查询重写目前只覆盖口语化问法，改写错了会把正确召回带偏，这条的失败样本我没统计。

问题 3：单测通过了，但把实现改坏它也不报错

简历原句：逐条判断断言能否抓住一次真实改动，抓不住的退回重写，固化成单测生成提示词模板

会这么问：AI 生成的单测，你怎么知道它有效？

回答：用例全绿不代表能发现问题。我的判据是改坏一条实现，对应用例必须转红。做法是先让 AI 按模板生成用例，人只判断断言有没有指向具体行为。然后改坏一处实现，把空值判断删掉、把边界条件从小于等于改成小于，跑一遍。用例还是绿的就说明断言是空的，退回重写。几轮之后，这套要求固化进了提示词模板。

再追一层：变异改哪里？改分支条件、改返回值的边界、删掉错误处理，这三类最容易被空洞断言漏掉。

边界：覆盖率只说明代码执行到了，不说明断言抓得住。变异跑全量成本高，实际只抽关键路径，抽样本身有遗漏风险。这条只在踏浪 AI 中心那个项目里用过，VidDigest 的验证是另一套手段（见第四章问题 8）。

问题 4：代码评审意见太大太笼统

简历原句：把项目规范整理成固定检查清单（空值、边界、错误吞没、共享状态并发）写进结构化 CR 提示词，再由人按误报条目反向收窄清单

会这么问：你怎么审别人的代码，会提什么意见？

回答：笼统的意见对提交的人没用。我把项目里反复出现的问题整理成固定清单，分四类：空值没判、边界没处理、异常被吞掉、共享状态有数据竞争。清单先写进结构化的 CR 提示词，再让评审的人按清单逐条过，同时把 AI 辅助生成与 CR 接进 CI 链路，让它成为流程里的一步而不是额外动作。清单的好处是可复用，坏处是会误报，所以定期回收误报条目，反向把清单收窄。

再追一层：为什么只留四类？四类对应的是真实事故。空值和边界直接崩，吞异常让问题查不到，数据竞争最难复现。

边界：这是人的检查清单，不是静态检查工具。清单收窄靠人工回收误报，前几版的误报不少。清单只覆盖我进过的项目，换一个技术栈这四类要重定。

问题 5：多轮对话把上文丢了

简历原句：另做分层会话记忆（摘要 + 向量召回）

会这么问：用户追问「那第二种方案呢」，系统还知道在说什么吗？

回答：早期只把最近几轮原样塞进上下文，长了超长度，超了就丢最早的内容，追问直接断。后来分两层：短期窗口留最近几轮的原文，超出窗口的部分压成摘要。长期记忆单独存用户确认过的事实，比如技术栈偏好、项目背景，用向量召回取回。取回时先按当前问题检索长期记忆，再拼短期窗口。

再追一层：摘要会不会把关键限定条件磨掉？会，所以摘要只压事实，不压判断。判断类的内容进长期记忆，不进摘要。

边界：摘要由模型生成，本身也可能丢东西，所以关键事实存原文不存摘要。这套没有做跨用户隔离。

问题 6：答案里出现文档没写的内容

简历原句（技能行）：了解幻觉的事实性、忠实性与逻辑性三类，能设计准确性与鲁棒性用例

会这么问：模型胡说怎么办？

回答：分两层堵。检索层保证片段真的相关，生成层把模型约束在片段内，提示词里只允许用给定材料，答案带引用编号，材料里找不到就回答不知道。跑一段时间后发现，编造多发生在召回为空还硬答的时候，所以空召回直接返回兜底话术。这条对应简历里写的三类：事实性是内容对不对，忠实性是有没有超出给的材料，逻辑性是前后推论站不站得住。

再追一层：怎么发现它在编？拿固定问题集跑，每题的答案逐条回原文核对，有依据的标通过，无依据的记一条。这份记录同时也是改提示词的依据。

边界：这套只能降低无依据回答的比例，做不到消除。兜底话术本身也是降级，不是解决。简历里这条写的是「了解」级，我做的是准确性与鲁棒性用例设计，没有做过完整的模型评测体系。

问题 7：上游模型限流，整条链路跟着堵

简历未单独写，属上游依赖的必问项

会这么问：上游返回 429 你怎么处理？

回答：三件事。一是读响应头里的等待时间做指数退避，加随机抖动，避免所有请求同一时刻重试。二是超过重试上限就降级，摘要任务排队稍后重跑，对话任务直接告诉用户稍后再试，不把请求挂在服务端等。三是入口也做限流，防止自己的并发把上游配额一次打光。

再追一层：等待时间那个头必须遵守吗？不是强制的，服务端可以不返回，值也只是建议。所以退避逻辑不能只依赖它，自己的上限要单独定。

边界：入口限流是保护自己，不解决上游配额本身。没有上限和抖动的重试，会把一次限流放大成雪崩。这条在简历里没有对应项目句，我讲的是做法，不是某个项目的线上事故。

四、VidDigest：端云分离、契约与额度回滚

项目简介一句话：端侧在用户自己的机器上解析视频（取字幕、生成总结与思维导图），联网后把结果贡献给社区；云端只做社群、账号与模型出口，端侧数据不上云。

链路一行：端侧取字幕 → 端侧调模型生成 → 端侧出结果 → 联网后上传可贡献产出 → 云端入社区 → 社区可搜索、可追问（SSE 流式）

节点 在哪 关键约束
取字幕、生成总结与思维导图 端侧（桌面壳 + 本地 FastAPI + SQLite） 登录态、cookie、自带密钥只留本机
贡献上传 端侧发起 只有官方模板与官方参数集的产出可上传
社群、账号、额度、管理后台 云端（FastAPI + PostgreSQL） 云端永不持有用户 cookie
模型出口 云端 平台模型按额度计，自带密钥走端侧

问题 1：端侧数据不上云，那隐私边界守在哪

简历原句：端侧本地解析视频（取字幕、下载、生成总结与思维导图），联网后把结果贡献给社区；云端只做社群、账号与模型出口，端侧数据不上云

会这么问：这个项目能给别人用吗？数据会不会泄露？

回答：先说清楚现在的形态：端侧离线可用，云端可以自部署，不是对外公开服务。隐私边界写在三处。第一，登录态、cookie 和自带密钥只留在本机——云端永远不持有用户的 cookie，用户用自己的模型凭据时调用在端侧发生。第二，社区只展示 AI 产出，字幕原文不直出；云端为了支持社区追问保留一份字幕缓存，存活期 30 天（apps/cloud-api/src/viddigest_cloud_api/media.py 里 MEDIA_TTL_DAYS_DEFAULT = 30），到期由定时清理任务删掉，缓存是缓存不是档案。第三，只有用官方模板和官方参数集生成的产出才允许上传，自定义提示词或自定义参数的产出只留本地。

再追一层：桌面壳这边呢？壳用 PySide6 + QWebEngine，登录态放在 Qt 自己的浏览器 profile 里，那属于壳的浏览器状态，应用代码不把它复制进本地数据库、日志或任何上云请求。壳还做单实例（用本地 socket 抢锁，第二个实例把已有窗口拉到前台）、托盘常驻，以及本地后端子进程的看门狗——后端进程死了换成可读的错误面板，不留白屏。

边界：这个形态的代价是数据不集中，云端做不了跨用户的全量分析。对外开放还受平台风控与登录态限制，那是我没解决的前置问题。字幕缓存过期后不保证可恢复，失败时回落用户端重传。

问题 2：接口契约怎么保证前后端不漂移

简历原句：接口按 OpenAPI 契约走，云端 26 条、端侧 16 条路径导出后生成前端类型，门禁重新导出时 git diff 必须为空，契约漂移就提交不上去

会这么问：你们接口怎么管的，前后端怎么保证字段一致？

回答：契约是单一来源，两端不许手抄字段。云端和端侧各自的 FastAPI 都能导出 OpenAPI，导出的文件放在 packages/contracts/ 下，前端类型由这份文件生成。门禁里重新跑一次导出和生成，然后 git diff --exit-code -- packages/contracts，只要有差异就提交不上去。路径条数是可以数的：云端 26 条、端侧 16 条，命令是数导出文件里的 paths 键，条数与操作数不是一回事——云端 26 条路径展开是 29 个操作。

再追一层：为什么用生成类型而不是手写接口定义？手写两边就会漂，漂了要到联调才发现。生成之后类型不对就是编译不过，CI 直接红。契约文件本身也是代码，改它要跟改实现同一个提交，不然门禁里的 diff 一定非空。

边界：契约保证的是形状一致，不保证行为一致——同一个字段名下返回什么值，还得靠用例断言。这条也是我敢说「契约漂移就提交不上去」的原因：漂移检测在门禁里是必跑的一段，不是靠自觉。

问题 3：额度扣了但模型没给结果，怎么算

简历原句：模型出口断连或没有完成信号时回滚额度并丢弃半成品，解析与对话额度独立按日重置，避免「扣了额度没结果」

会这么问：你说先扣额度再调模型，那模型挂了钱不就白扣了？

回答：所以有回滚。额度是先扣后调：额度耗尽是 HTTP 错误（429 quota_exhausted），不是流里的事件，所以先扣完再调模型。调模型走 SSE 流式返回，只有收到完成信号才算成功；没有完成信号就当失败，回滚额度，半成品不落库——不然用户白扣额度，社区里还多一条空版本。客户端中途断连同样回滚。已发出完成信号的不再回滚，避免重复回滚造成状态错乱。解析额度和对话额度是两套独立的计数，各自按日重置，跨日自动清零。

再追一层：回滚挂在哪？挂在生成器被关闭这个时机上。但客户端断连时同步生成器可能永远不被关闭，只等垃圾回收，所以光靠这一个时机不够，还有一把定时兜底：预扣带一个超时计时器，超时未结算就按失败回滚，而且结算本身加了锁，只生效一次，防止回滚和成功结算撞在一起。

边界：额度默认值是解析 3 次、对话 10 次，这是配置项，管理员能按账号覆盖，所以报数字要说清是默认值不是硬上限。回滚只覆盖云端平台模型出口这条链路，端侧用自带密钥的调用不走额度。

问题 4：同一个视频存几份结果，怎么选一份展示

简历原句：同一视频每厂商最多保留 3 个结果版本，代表版本按模型强度序在查询时算出而不落库

会这么问：一个视频你存了几份？社区里展示哪一份？

回答：一个视频可以有多个结果版本，一行代表一次解析的产出，带上谁产的：厂商、模型、官方模板与模板版本。唯一键是（视频、厂商、模型、模板、模板版本）。同一视频同一厂商最多留 3 个，超限淘汰模型强度序最低的那个，同强度淘汰最旧的。社区页展示的代表版本不落库，查询时按模型强度序排序取首。

再追一层：强度序是谁定的？人工维护的一列（model_catalog.strength_rank），未知模型取最低序，永远排不过已知模型。写代码的人不写这列，所以强度序错了表现是差模型霸榜——这是这条设计的代价。

边界：3 这个数是配置项（VIDDIGEST_VERSIONS_PER_VENDOR），不是硬编码的策略常量。代表版本在查询时算，读路径多一次排序。这个取舍的前提是规模小（决策文档写的是日活百以内、视频万级以内），规模上去、模型数量上去，要重新评估淘汰口径。

问题 5：流式返回怎么断言，断连算什么

简历原句（额度回滚那一句，流式部分是仓库事实）：模型出口断连或没有完成信号时回滚额度并丢弃半成品

会这么问：流式输出怎么测？断流算成功还是失败？

回答：按事件逐条读、逐条断，不等全部返回再整体比对，否则超时和截断两种情况都测不出来。事件形状是固定的：增量是 delta，成功是 done，失败是 error，done 是唯一成功信号；格式统一成 event: <名字> 加一行 data: 的 JSON，官方模型出口与社区追问复用同一套，断言可以共用一份形状表。以官方模型出口那条为例，用例里我拆了几种断法：正常流程断言事件顺序是 delta…→done；模型流没有完成信号，要断成错误事件并回滚额度；客户端断连要断成额度回滚且一条结果都不落库；已经发过完成信号之后再断连，额度不能再回滚——这一条专门防重复回滚把额度搞乱。

再追一层：真实部署链路中间还有一层反向代理，缓冲会改变观感。SSE 这类流式响应在反代后面要显式关掉响应缓冲，否则前端看到的是「卡住不动，最后一次性刷出来」。我知道这个坑，但仓库里的部署是 Compose 加单机，我没有在真实生产环境验证过代理配置，所以这条我讲成部署注意事项，不当成我踩过的线上事故。

边界：断言的是事件序列与额度结果，不断言模型内容质量——内容质量要靠固定问题集回原文核对，那属于 AI 侧的事。

问题 6：限流、并发、额度，三道闸门别混

简历原句（未单独写，属云端接口的必问项）：限流、并发、额度三道闸门

会这么问：你接口有限流吗？QPS 多少？

回答：先分清三件事，超限给的错误码不一样。额度是「一天能做几次」，耗尽回 429 quota_exhausted。频次限流是固定窗口计数，超了回 429 rate_limited 并带 Retry-After：注册和登录按来源 IP 限，贡献上传按账号限。并发是另一道闸门，官方模型出口和社区追问按账号并发 1，抢不到锁直接回 429 concurrency_limited，和频次限流的文案不一样，因为客户端要做的事不一样——限流要等，撞并发要先结束手上那个任务。

再追一层：为什么按账号限流不按 IP？云端请求都带鉴权，按 IP 分桶在 NAT 后面会误伤一整栋楼的人。

边界：限流是进程内内存实现，单机部署够用，进程重启就清零；也没有做过多实例下的全局限流。这条对应 Vapor 优选里 AOP 加自定义注解的滑动窗口限流（那是另一套实现，见第五章问题 5）。至于 QPS，本机回环的数字换个环境就变，我不报具体值，只报口径：线程数不等于并发数，看 P95 而不是平均值，错误率要和延迟一起看。

问题 7：管理后台改了权限，旧令牌还能用吗

简历原句：管理后台覆盖账号、额度、停用、邀请码与举报处理；管理员权限每次鉴权回查，不可逆操作只追加审计记录

会这么问：后台这么敏感，权限怎么管，操作怎么追溯？

回答：权限不写进令牌，每次鉴权都回查数据库——令牌里只放账号标识，是不是管理员查库里的当前状态。所以管理员被降级或账号被停用，旧令牌立刻失效，不用等令牌过期。后台的不可逆操作（建号删号、发码作废码、停用账号、删社区条目、改标签）都留一行审计记录：谁、什么时候、对什么、做了什么。这条记录只追加，不修改也不删除。

再追一层：为什么审计只追加？只追加就改不了，事后有人动过记录本身能看出来。代价是审计表只涨，清理策略要另外定。

边界：停用账号是把账号置为不可登录，不删数据，可以撤销。举报处理只记判定（resolved 或 dismissed），删不删条目是另一个动作。审计记录里的操作者是邮箱快照，账号被删后仍能回答「谁干的」。

问题 8：断言全是「状态码 200」就等于没测

简历原句：验证资产：224 条 pytest 用例（云端 167 / 端侧 50 / 桌面壳 7）与 17 条前端单测；门禁串起 lint、契约漂移、前端构建、pytest、前端单测与端云两套 Playwright E2E

会这么问：接口用例怎么写的？有多少条？

回答：分两档。单接口按契约逐字段断言，字段名、类型、必填项、错误码都要对；业务流程按场景断言，比如重复上传返回既有结果而不是新建一条、额度耗尽给的是 quota_exhausted 而不是 500。数据层每个用例起独立临时库，迁移有单独的升级回归（升降级往返都断言一遍）。写完还要用变异脚本改坏实现，确认对应用例真的转红。

再追一层：这些数字是怎么来的？是收集出来的，不是估的：跑 uv run pytest --collect-only -q，得到 224 条用例，按应用分是云端 167、端侧 50、桌面壳 7；前端单测跑 npm run test:unit -w @viddigest/terminal-ui，5 个文件 17 条。门禁七步：ruff lint 与格式检查、契约漂移、前端构建、pytest、前端单测、端侧离线路径 E2E 与云端真实 API E2E，全绿才提交。

边界：这 224 条只说明覆盖面，不说明断言强度——覆盖率高也可能全是空断言。所以还配了变异脚本改坏实现看用例转不转红。另外用例条数会随开发涨，报数字要说清是哪一次统计、哪个提交，比如本文这组数字取自仓库的 0b05f29；同一仓库更新之后条数就变了。

问题 9：模型出口断了，额度为什么没还回来

简历原句：模型出口断连或没有完成信号时回滚额度并丢弃半成品

会这么问：你前面说回滚挂在断连上，那断连没触发呢？

回答：这是我写断连用例时发现的坑，不是线上事故——项目还在自部署阶段，没有真实用户，所以我说的是开发期定位到的。最初的实现只有一条回滚路径：生成器被关闭时回滚额度。但客户端断连之后，那个同步生成器不一定马上被关闭，可能一直等到垃圾回收才释放，额度就卡在「扣了没还」的状态，用户当天白少一次额度。同一批用例还暴露了第二个问题：模型流没有发出完成信号时，旧实现照样往下走，把半成品当成功落库，等于社区里多一条空版本、额度还白扣了。

再追一层：怎么定位的？先看额度计数和实际产出对不上：额度扣了、结果表里没有对应版本，说明不是回滚金额写错，而是回滚根本没被触发。再往里看，断连场景下生成器没被及时关闭，所以挂在它身上的那条路径没跑。

再追一层：怎么改的？预扣额度时同时起一个超时计时器（默认 600 秒），超时未结算就按失败回滚；结算本身加锁，保证「成功结算」和「超时回滚」只有一次生效。这样三条路：正常断连走关闭钩子回滚，钩子没来走定时兜底，没有完成信号直接判失败、结果不落库。

边界：定时兜底的代价是断连之后额度最多被占住 600 秒才还，不是立刻还。这是个明确的取舍，不是零成本的修复。

五、Vapor 优选：秒杀原子性与缓存一致性

项目简介一句话：商品信息查询加秒杀优惠券功能，技术栈 SpringBoot + MySQL + Redis + Lua + Kafka + Caffeine + MyBatisPlus。链路从活动校验、资格与库存校验、原子扣减、订单落库，到异步通知与超时回补。

问题 1：并发下超卖

简历原句：用 Redis + Lua 把库存校验与一人一单资格审查压成一次原子执行

会这么问：秒杀怎么防超卖？

回答：数据库层加「库存大于零」的条件更新，看影响行数判断是否扣成功，这一层兜底。库存热点交给 Redis，把资格校验和库存扣减压到一次原子执行里，脚本内部先判资格、再判库存、最后扣减，返回不同的码区分失败原因。两层一起用，Redis 挡流量，数据库保正确。

再追一层：脚本报错会回滚吗？不会。脚本执行期间不被打断，但执行到一半报错，前面已执行的命令不会退回。所以要把全部校验做完再动数据，别一边改一边判。集群部署时脚本涉及的 key 还要落在同一个槽。

边界：能说出脚本里的判断顺序和返回码含义，这句话才算讲透。集群下多 key 必须同槽，否则直接报错。

问题 2：同一用户重复提交生成多单

简历原句：杜绝超卖与重复下单，并用重复提交与超时重试验证幂等

会这么问：用户连点两次会怎样？超时重试呢？

回答：两层。业务层让每次下单带一个请求号，服务端用「用户 + 优惠券 + 请求号」的唯一索引挡住重复写入。资格判断里把同一用户同一活动的重复请求直接拒绝。重复提交和超时重试走同一套，重试不该产生第二单。验证方式就是简历上写的那两条路径：重复提交、超时重试，各自断言只生成一单。

再追一层：超时重试和服务端已经成功怎么区分？客户端重试沿用同一个请求号，服务端查到已有记录就返回原结果，不新建。

边界：锁管的是同时，幂等管的是重复，两者不能互替。重试必须沿用原请求号，换号就等于新订单。这条跟 VidDigest 的写入幂等是同一个思路（唯一约束 + 查重后幂等写入），但那套不需要分布式锁，因为规模小、没有并发竞争点。

问题 3：为什么中间要加 Kafka

简历原句：用 Kafka 把库存物理扣减与订单持久化解耦，单量突增时核心链路不拖垮下游

会这么问：落库这一步为什么不用同步写？

回答：库存扣减和订单持久化不是一回事。扣减在 Redis 里是内存操作，毫秒级；落库要走 MySQL 索引、事务、刷盘，慢得多，突发流量时同步落库会把核心链路堵住。用 Kafka 把两件事解耦：扣减成功就发消息，消费者异步落库，核心链路的耗时和流量脱钩。

再追一层：消息重复怎么办？队列的投递语义一般是至少一次，重复是常态。消费端用业务唯一键做幂等表，处理前先插唯一记录，插入失败说明已经处理过，直接确认消费。幂等表和业务表在同一库就放一个事务里，跨库就靠状态机加对账。

边界：队列只保证至少一次，重复必然出现，幂等只能压在消费端。Kafka 解耦换来的是最终一致：扣了库存那一刻订单还没落库，中间有一个短暂窗口能看到「有库存没订单」。

问题 4：缓存和数据库不一致

简历原句：按「先更新数据库 + 后删除缓存」改造，配合消息队列异步重试补偿与 TTL 兜底保证最终一致

会这么问：改完库存，缓存怎么处理？

回答：先写数据库再删缓存，不更新缓存。更新缓存的问题在于并发写会把旧值盖回去，删掉让下次读回源更安全。删缓存失败的话，靠消息队列补偿再删一次，兜底是给缓存设过期时间，即使一直没删，最终也会回源。极端情况下还会用延迟再删一次，覆盖「读请求在写之前取了旧值、又在删除之后写回缓存」这个窗口。

再追一层：延迟删能不能彻底解决？不能，只能缩小窗口，所以还得有 TTL 和最终一致的对账。更彻底的做法是让缓存在删除后拒绝旧值回写，实现复杂度高，我没做。

边界：给的是最终一致，不是强一致。延迟删只缩小窗口，不关闭窗口。穿透、击穿、雪崩这三类是另一条线：穿透用空值短缓存或布隆过滤器挡，击穿用互斥重建，雪崩给过期时间加随机抖动；布隆过滤器有假阳性，只能挡请求不能判定存在。这条在简历里没有对应句，我讲的是通用做法。

问题 5：限流怎么实现，为什么用 AOP

简历原句：用 AOP + 自定义注解做滑动窗口限流，拦截恶意刷券与爬虫请求

会这么问：限流怎么做的？

回答：滑动窗口限流的逻辑写在一个切面里，切面拦带自定义注解的方法，注解上写阈值和窗口。窗口内按 key 计数，超了就拒。为什么用 AOP 加注解：限流的点是分散的（发券、领券、查询），每个手写一遍判断容易漏，注解标一次、切面统一处理，新接口加上注解就自动受保护。

再追一层：滑动窗口和固定窗口差在哪？固定窗口在窗口边界会放行两倍流量，滑动窗口按更细的时间片计数，边界不会翻倍。代价是计数维护更贵，内存占用更高。

边界：这套限流是单机内存计数，多实例部署时每个实例各算各的，不是全局限流。VidDigest 那边也是同类问题，决策文档里写清楚了：规模上去需要多实例与可靠队列时，这条要推翻。

问题 6：订单支付和超时关单撞在一起

简历原句：订单支付与超时关单用 CAS 乐观锁避免状态冲突

会这么问：用户正在付钱，超时任务同时把订单关了，怎么办？

回答：两个动作都改同一条订单的状态，所以用 CAS 乐观锁：更新语句带上「当前状态等于我读到的状态」这个条件，影响行数为 0 就说明状态被别人改过，这次更新不生效。支付和关单各带各的期望状态，谁先改成功另一个就更新不到。

再追一层：CAS 失败了怎么办？重读当前状态再判断：状态已经是已支付，关单就该放弃；状态已经是已关闭，支付就该走退款或提示。乐观锁适合冲突少、改一行字段的场合，冲突频繁就要换悲观锁或串行化。

边界：CAS 只保护这一次更新，不保护整条业务链。跨多步的操作还得靠状态机约束能走的下一步，不能只靠锁。

六、事故怎么讲：一个真实坑，别讲成线上事故

被问「讲一个你遇到的问题」时，不要从项目背景讲起，直接给坑。而且要分清是开发期定位到的，还是线上暴露的——项目还在自部署阶段、没有真实用户，把开发期的问题说成线上事故，面试官一追问细节就会露。

VidDigest 那条可以这么讲：

有个问题是额度扣了但结果没出来。我先怀疑是回滚的金额算错了，查了额度表和结果表发现对不上——额度扣了、结果表里没有对应版本，说明不是算错，是回滚根本没触发。再往里看，断连场景下那个同步生成器没被及时关闭，回滚是挂在它身上的，它没关闭，那条路径就没跑。改法是预扣额度时同时起一个超时计时器，超时未结算就按失败回滚，结算加锁保证只生效一次。代价是断连之后额度最多被占住 600 秒才还，不是一秒就还。这是我写断连用例时定位到的，项目还在自部署阶段，没有真实用户流量。

Vapor 优选那条可以这么讲：

缓存一致性最难复现的是「写库成功、删缓存失败」，所以我把它固定成一条复现路径，每次改这套逻辑都按这条路验一遍能不能自愈。修复分两层：删失败靠消息队列异步重试补偿，兜底给缓存设过期时间，即使一直没删也能回源。边界是最终一致，不是强一致——延迟删只缩小窗口，不关闭窗口。

结构固定成四句：什么现象、我一开始怎么想、真正原因是什么、改了什么。这套讲法对任何项目都成立，因为面试官听的是定位过程。

收尾交一句技术边界：

这部分我只做到能跑通和自己验证，没做过多实例和真实流量，所以我只说它做了什么，不说它扛住了多少。

七、数字怎么报：实测值和设计值分开

面试官追数字有两层意思，一层是确认结论可复核，一层是看你知不知道数字怎么算。分清两类数字，比背一堆数字有用。

数字 类型 怎么来的 面试怎么说
云端 26 条 / 端侧 16 条接口路径 实测 数 packages/contracts/openapi.json 与 openapi-terminal.json 里的 paths 键；展开的操作数是 29 / 19 「26 条路径、29 个操作，条数和操作数不是一个数」
224 条 pytest 用例（云端 167 / 端侧 50 / 桌面壳 7） 实测 uv run pytest --collect-only -q，224 条 「条数是收集出来的，不是估的；取自 0b05f29 这个提交」
17 条前端单测 实测 npm run test:unit -w @viddigest/terminal-ui，5 个文件 17 条 「只统计条数，没统计覆盖率」
门禁七步 实测 check.sh 里的段：ruff、契约漂移、前端构建、pytest、前端单测、端云两套 Playwright E2E 「漂移检测是必跑的一段」
字幕缓存 30 天 设计值 media.py 的 MEDIA_TTL_DAYS_DEFAULT = 30，可配置 「30 天是默认配置项，不是硬编码策略」
每厂商 3 个结果版本 设计值 ranking.py 的 VIDDIGEST_VERSIONS_PER_VENDOR，默认 3 「3 是配置项，前提是当前规模」
额度默认解析 3 次 / 对话 10 次 设计值 quota.py 的默认值，管理员能按账号覆盖 「默认值，账号可覆盖，不当成硬上限」
模型强度序 设计值 人工维护的一列，未知模型取最低序 「人工维护，写错会让差模型霸榜」
并发 1、60s 窗口 设计值 契约文档里定的口径 「单机内存计数，多实例不成立」
吞吐与延迟 不报 本机回环、空接口，换台机器就变 「线程数不等于并发，看 P95 和错误率」
覆盖率 不报 没跑 「覆盖率不证明断言有效，变异才证明」
用户量、日活 不报 没有真实流量 「端侧离线可用，云端可自部署，不是对外公开服务」
召回提升百分比 不报 固定问题集是自建评测器，没有可比基线 「只说方法：固定问题集、两路召回、按命中排位比较」

真要报实测数字，前面加一句适用范围（哪个提交、哪个环境），后面加一句口径（条数还是操作数）。这两句不加分，但准确。

八、背诵前的自检

检查项 通过标准
链路 每个项目能一句话说完入口到出口，不超过三十秒
取舍 每个项目能说出一个被放弃的方案和放弃的原因
验证 每个项目能说出一个判据，不是「测过了」
事故 每个项目能说出一次真实失败，含定位过程
边界 每个项目能说出一件自己没做的事
原句 简历每一行描述，都能对应到一个能展开的问题
数字 每个要报的数字，能说出统计命令或文件位置

七项全过，项目追问这一关基本就稳了。第二项和第五项过的人最少，因为这两项都要承认点什么。

九、判据和动作名的区别

技术面试里同一个问题，答动作名和答判据是两回事。

问「怎么验证」，答「用 AI 生成用例」是动作名，答「改坏一条实现看用例转不转红」是判据。问「接口怎么管」，答「用了 OpenAPI」是动作名，答「导出后生成前端类型，门禁里重新导出 diff 必须为空」是判据。问「额度怎么保证不白扣」，答「有回滚逻辑」是动作名，答「挂在生成器关闭上，再加一个超时兜底，结算加锁只生效一次」是判据。问「别人写的测试流程怎么确认可用」，答「要重新沟通」是动作名，答「固定问题集跑一遍，看命中率和误报率」是判据。

判据有个共同点，都能被第三个人复现。测试岗买的就是这个能力，动作谁都会做。

这份合集里每一组的「再追一层」，写的都是判据。
