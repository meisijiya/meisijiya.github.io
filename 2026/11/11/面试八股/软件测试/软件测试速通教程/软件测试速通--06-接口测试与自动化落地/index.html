一、接口是什么：一次请求的完整链路

一句话白话：接口就是程序与程序之间传数据的入口，你按约定发一份请求，它按约定回一份响应。

以一次「登录」为例，数据走完整条链路：

链路上每一环，测试能测什么：

环节 这一环在干什么 接口测试在这里抓什么
客户端 组请求：方法、URL、Header、Body 参数传错、漏传、类型错
网关 转发 + 限流 + 鉴权 未带 token、token 过期、被限流
后端服务 业务校验与处理 业务规则没生效、状态没流转
数据库 落库与查询 数据没写进去、查出来是脏数据
响应 回状态码 + 业务码 + 数据 状态码与业务码不一致、字段缺失

接口测试的主要目标是服务器：模拟客户端发请求，校验服务器回发的响应是否符合预期。它的价值在于绕开前端直接打后端，所以能发现页面操作发现不了的问题，比如参数校验缺失、越权、业务规则漏洞。

二、HTTP 速查表

HTTP 是基于请求与响应模式的应用层协议，特征是：客户端/服务器模式、简单快速、灵活、无状态。无状态意味着服务器默认不记得你是谁，所以登录态要靠 Cookie / Session / Token 带回来。

HTTP/1.1 起默认持久连接（keep-alive），一次连接可承载多个请求；HTTP/1.0 默认关闭，HTTP/2 在 TCP 连接上做多路复用。

请求方法（语义）

方法 语义 请求体 幂等 例子
GET 查询 通常没有（语义上未定义） 是 查员工列表、查详情
POST 新增 有 否 登录、新增员工、提交订单
PUT 修改 有 是 修改员工信息
DELETE 删除 通常没有（允许但语义未定义） 是 删除员工

不要把「GET 不能有 body」当协议约束（RFC 9110）：GET 带 body 在协议上允许，只是语义未定义，很多服务端与网关会忽略或直接拒绝。HTTP 方法幂等 ≠ 业务幂等，支付下单要靠业务幂等键。

状态码（记住分类即可）

分类 含义 常见值
2xx 成功 200 请求成功
3xx 重定向 301 永久重定向、302 临时重定向、304 资源未修改（可用缓存）
4xx 客户端错误 400 请求错误、401 未提供凭据或凭据无效（要重新认证）、403 身份已识别但无权限（再认证通常无效）、404 未找到、405 方法不允许
5xx 服务器错误 500 服务器内部错误、502 网关错误、504 网关超时

请求头与鉴权头

头部 作用 示例
Content-Type 描述请求体的数据类型 application/json、application/x-www-form-urlencoded
User-Agent 描述请求发送端的浏览器/客户端类型 postman-runtime/1.0
Authorization 鉴权凭证 Bearer your_token
Cookie 客户端携带的状态信息 sessionId=xxx

报文结构记两行就够：请求 = 请求行（方法 URL 协议版本）+ 请求头（k:v）+ 空行 + 请求体；响应 = 状态行 + 响应头 + 空行 + 响应体。

三、接口用例十要素

一张接口用例表，最少要有这十列。前六列是「这条用例是什么」，后四列是「怎么发、发什么、该回什么」。

要素 说明 示例
编号 唯一标识，便于回归与统计 API-LOGIN-001
用例名称 一句话说清测什么 正确账号密码登录成功
模块 归属哪个业务模块 登录模块
优先级 P0 主干 / P1 逆向 / P2 边界 P0
预置条件 执行前环境/数据要满足什么 账号已注册且未锁定
请求方法 GET / POST / PUT / DELETE POST
URL 接口路径 /api/sys/login
请求头 Content-Type、Authorization 等 Content-Type: application/json
请求体 参数名、类型、必填、示例值 {"mobile":"your_account","password":"your_password"}
预期结果 状态码 + 业务码 + 关键字段 200，code=10000，data 为 token

接口文档怎么读

拿到接口文档，按五步走，不要从第一行开始逐字读：

  1. 先看系统路径与域名，确认这套文档对应哪个环境。
  2. 找接口 Path 与 Method，判断这条接口干什么用。
  3. 看 Headers，确认要不要鉴权、请求体是什么格式。
  4. 看请求参数：名字、类型、是否必填、示例值。
  5. 最后看返回结构与错误码表，这决定断言怎么写。

参数设计：正向与反向

参数类用例的口径（正向三条 + 反向四条）：

类型 口径 示例
正向·必选 所有必选参数都包含 mobile + password
正向·组合 必选 + 任意一个或多个可选参数 登录 + 记住我
正向·全部 必选 + 所有可选参数 全字段提交
反向·多参 多出一个或多个参数 body 里多一个 abc 字段
反向·少参 缺少一个或多个必选参数 只有 password
反向·无参 一个参数都没有 body 为空
反向·错参 参数名写错 用 abc 代替 mobile

四类必测项

类别 测什么 例子
参数校验类 空值、格式、长度、类型、必填 手机号为空、密码 1 位、密码 100 位、含特殊字符
业务规则类 业务约束是否生效 连续错 5 次锁定、余额不足不能下单、库存为 0 不能买
异常类 异常返回与错误码 401 未提供凭据或凭据无效、403 身份已识别但无权限、系统繁忙 code=99999
安全类 越权与注入 改请求里的用户 ID 看能否拿到别人数据；SQL 注入串

正向用例覆盖「该成功的成功」，反向用例覆盖「该拒绝的拒绝、该报错的报错」。只测正向等于没测接口。

四、断言三层：状态码、业务码、业务字段

只断言「状态码 200」等于没测——业务失败时很多接口照样返回 200。断言要三层递进：

层 断什么 为什么必须
第一层 状态码（200 / 401 / 403） 请求有没有被正确受理
第二层 业务码（code=10000 / 20001 / 99999） 业务有没有真正成功
第三层 业务字段（data 的类型、值、条数） 数据对不对、有没有多返回少返回

七、落地验收标准

一套接口自动化「能交付」的最低标准，六条都要满足：

# 标准 怎么验证
1 可重跑 任何人 clone 下来，改一行 base_url，pytest 一把过
2 断言三层 每个用例都有状态码 + 业务码 + 业务字段断言
3 数据与脚本分离 加用例只改数据文件，不改测试代码
4 失败可定位 失败信息里能看到：哪个用例、哪一层断言、实际值与预期值
5 数据自清理 造的测试数据能删掉或用例自带 teardown，不污染环境
6 有报告 能出 HTML/Allure 报告，或 CI 里能拿到 pass/fail 汇总

自检清单（交付前过一遍）：

  • 登录 token 有没有写死在用例里？（应该走 fixture）
  • 反向用例有没有覆盖「该拒绝的拒绝」？
  • 造的数据有没有清理动作？
  • 换一台机器还能跑吗？
  • 失败时能不能一眼看出是哪一层断言挂了？

失败后怎么定位

脚本红了不等于接口有 bug。按固定顺序查，不要临时想：

  1. 看断言消息：先确认挂在第几一层（状态码 / 业务码 / 业务字段）。
  2. 打响应体：resp.text 是属性，直接取值，用 print(resp.text) 打出来，看服务端到底回了什么。
  3. 对请求参数：确认是参数错还是环境错（比如 base_url 指向别的环境）。
  4. 对服务端日志：按接口路径和请求标识在服务端日志里找对应那次调用。
  5. 看服务端资源与依赖：CPU、内存、数据库连接池、慢查询、第三方依赖是否异常。

这个顺序的价值是可复现：换了人、隔了几天，照着这五步仍能定位。

八、接口测试常发现的缺陷类型

按出现频率排，五条最典型：

# 缺陷类型 现象 怎么发现
1 参数校验缺失 必填参数不传也能成功；手机号不校验格式 反向用例：少参/无参/错参/格式错
2 越权 改请求里的用户 ID，能拿到别人的数据 安全类用例：换 ID、换 token、去掉 token
3 业务规则没生效 余额不足仍能下单；库存为 0 仍能扣 业务规则类用例 + 查库比对
4 状态码与业务码不一致 业务失败仍返回 200；成功却返回 500 三层断言里的第一层与第二层对比
5 数据不一致 接口说成功，库里没落库；或落库字段错 接口断言 + 数据库查询比对

面试被问「接口测试一般能发现什么问题」，按这五条讲，再补一句「接口测试绕开前端，所以前端藏了按钮但后端没鉴权的漏洞，只有接口层能测出来」。

🗣️ 面试怎么说

  1. 接口就是程序间传数据的入口，接口测试模拟客户端发请求、校验服务器响应，目标是服务器。
  2. 一次请求的链路是客户端 → 网关 → 后端服务 → 数据库 → 响应，测试要能说清每一环可能出什么问题。
  3. 用例设计我会先列十要素，再按正向三条（必选/组合/全部）加反向四条（多参/少参/无参/错参）。
  4. 断言至少三层：状态码、业务码、业务字段。只断言 200 等于没测，因为业务失败也常返回 200。
  5. 关联就是前置接口提取 token 存 fixture，后续接口 Header 带 Authorization: Bearer {token}。
  6. 参数化用 JSON 而不是 CSV，因为 JSON 支持 bool、多参少参和嵌套结构。
  7. 交付标准是六条：可重跑、断言三层、数据分离、失败可定位、数据自清理、有报告。
  8. 接口测试最常发现的是参数校验缺失、越权、业务规则没生效、状态码与业务码不一致、数据不一致。

✅ 自测 5 题

  1. 只断言状态码 200 有什么问题？ 业务失败时接口常返回 200，必须再断言业务码和业务字段。
  2. token 怎么在 pytest 多个用例间传递？ 用 scope="session" 的 fixture 提取一次，后续用例引用同一个 fixture。
  3. CSV 参数化有什么限制？ 读进来全是字符串、不支持 bool、不支持多参/少参/无参/错参和复杂类型。
  4. 接口用例十要素是哪十列？ 编号、名称、模块、优先级、预置条件、方法、URL、请求头、请求体、预期结果。
  5. 什么样的接口自动化算能交付？ 可重跑、断言三层、数据与脚本分离、失败可定位、数据自清理、有报告。
