一、六个方向的 JD 拆解

从 2026 年 11 月 10 日抓到的 15 个在招岗位里归纳出六个方向（岗位样本与 URL 见 📚 来源）。

方向 核心要求 门槛 加分 对应本教程哪几篇

选方向的两条建议：

  1. 按词频看，自动化测试/自动化脚本在 15 个岗位里出现 11 次，Python 出现 9 次，接口测试与 SQL 各 6 次，测试用例设计与测试理论 8 次。所以自动化 + 接口是覆盖面最广的主线，AI 测试是增量。
  2. AI 测试方向对实习生的新增要求集中在三处：评测集构建（4 个岗位提到）、Agent 测试与智能体（4 个）、幻觉与效果评价打分（3 个）。这三样恰好是本教程 08 篇的内容，可以直接作为作品集。

二、面经高频 20 问

每题给「问法 → 30 秒答案骨架 → 加分补一句」。骨架是三到四步的顺序，不是逐字稿。

组一：项目与动机（5 问）

1. 为什么选测试不选开发？
骨架：承认自己做过开发 → 说强项是挑毛病、盯边界 → 开发背景对测试是加分（能读源码和日志定位）→ 一句动机收尾。
加分：我不只测自己的东西，验证自己写的代码更难，因为要先把「什么算失败」定义出来。

2. 讲一个你的项目，说清你学到了什么。
骨架：项目一句话定位 → 我负责的测试动作 → 遇到的具体问题 → 我的解法 → 结论。
加分：不要说「学到了很多」，要给一个具体的技术判断，比如「我做完才明白用例通过不等于能发现问题」。

3. 测试开发和产品开发有什么区别？
骨架：开发交付功能并对需求负责 → 测试交付质量信号（用例、自动化、门禁、缺陷报告）→ 对问题能不能被提前发现负责 → 两者在需求阶段就开始协作。
加分：不要把测试说成执行角色，也不要贬低开发。

4. 你现在做到什么程度了？
骨架：分三层讲，链路跑通、单人可用、对外服务，明确说现在到哪一层 → 为什么停在这层（依赖、风控、登录态） → 下一步要补什么。
加分：区分「部署过」和「当前对外可用」，这句能救场。

5. 你怎么用 AI 做测试？
骨架：分三段讲，生成阶段给业务上下文和边界清单 → 验收阶段只看能不能跑通、断言是否指向具体字段、异常分支是否覆盖 → 沉淀阶段把跑通的进回归集。
加分：一句收尾，AI 出候选，人做判定和兜底。

组二：测试设计与流程（5 问）

6. 黑盒测试有哪几种方法，分别什么时候用？
骨架：先按输入形态分，表单类用等价类加边界值；多条件用判定表或因果图；多参数组合用正交；有状态用状态迁移；有流程用场景法 → 最后错误推测补漏。
加分：每种方法配一句适用场景，不要只背名字。

7. 测一个登录页你会怎么设计？
骨架：先澄清需求（账号类型、验证码、第三方登录）→ 分层：功能、兼容、接口、安全、性能 → P0 主干加安全、P1 隐藏入口、P2 兼容与文案 → 最后才落到输入框。
加分：隐藏入口别漏，账号切换、忘记密码、注册入口、第三方登录、登录态保持。

8. 一个 bug 从发现到关闭怎么走？
骨架：复现 → 提单（步骤、预期、实际、日志）→ 指派 → 修复 → 验证 → 关闭或打回。
加分：补一句「开发说这不是 bug 是设计如此」时怎么办：回需求文档拿证据，拉产品确认并记录，对方坚持且产品认可就标为已知限制并保留意见，不吵也不默默放过。

9. 冒烟测试是什么？回归测试测什么？
骨架：冒烟是提测前跑主干，通不过直接打回，不浪费后面用例执行 → 回归测三样：改了的地方、影响面、固定回归集，自动化跑固定集。
加分：回归范围要说明依据，「因为它和登录态耦合」比「都跑一遍」专业。

10. 时间不够，用例跑不完怎么办？
骨架：三轴排优先级，核心链路、本次改动影响面、历史缺陷高发模块 → 先冒烟再 P0 主流程 → 回归用影响面抽样加接口自动化全集 → 把没跑的写进报告风险说明。
加分：主动给决策人信息，不自己闷着扛。

组三：接口与工具（5 问）

11. 接口测试和功能测试有什么区别？
骨架：功能测试从界面点，接口测试直接对服务发请求 → 更早发现问题 → 能覆盖界面点不到的异常入参 → 不依赖前端做得好不好。
加分：单接口用例设计五方向：参数校验、鉴权（无 token、过期、别人的 token）、状态码与提示一致、业务正常流、重复提交与超时。

12. 断言只断状态码够吗？
骨架：不够 → 三层断言：状态码、业务码、业务数据 → 原因：只断 200 的用例，改坏任何业务逻辑都不会红。
加分：三条断言里业务数据那条最值钱，因为返回码能骗人。

13. token 怎么传给下一个接口？
骨架：登录接口的返回 token 用脚本存进环境变量 → 后续请求在 Header 里引用 → 换环境换一套变量 → 变量优先级是局部 > 数据文件 > 环境 > 集合 > 全局。
加分：说清集合变量和环境变量的区别，面试官会点头。

14. 接口报 500 你怎么定位？
骨架：固定顺序，服务端日志找异常栈 → 查进程与端口是否活着 → 看 CPU、内存、磁盘、连接数 → 查数据库慢查询与连接池 → 查第三方依赖是否变慢。
加分：Linux 四层（看日志、查服务端口、看资源、改权限）能直接背下来。

15. 抓包抓什么？改包有什么用？
骨架：抓请求头响应头、入参返回体、状态码、耗时 → 改包是验证服务端有没有做校验 → 顺带做弱网与中断场景。
加分：HTTPS 抓不到的原因（证书没信任、SSL Pinning）能答出来。

组四：AI 与前沿（3 问）

16. AI 测试和传统测试有什么不同？
骨架：输出概率性 → 评价主观化 → 需持续监控漂移 → 断言从对错变成准确、有用、无害、一致四个维度的评价。
加分：AI 生成代码后新增的测试对象是输出的稳定性、安全性和一致性。

17. AI 生成的用例靠谱吗？
骨架：铺量靠谱，业务场景不靠谱 → 必须人工评审补隐藏入口 → 我用固定格式的评审表逐条判覆盖、可执行、期望可判定。
加分：给判据，把「显示正常」这种不可期望改成能断的具体字段。

18. 大模型幻觉怎么测？
骨架：分事实性、忠实性、逻辑性三类 → 判定四问：事实能不能验证、有没有完全遵循指令、推理自不自洽、有没有引用不存在的来源 → 检出来靠事实核查、一致性检查和对抗性测试三法。
加分：主动补一句「AI 测试出的是候选和线索，最终判定还是要有依据可核对」。

组五：数据库与基础（2 问）

19. 怎么保证用例覆盖得全？
骨架：需求 → 测试点 → 用例三级映射逐条对勾 → 用例评审补漏 → 高风险模块补探索性测试 → 覆盖说的是需求覆盖，不是用例条数。
加分：给一句「每条需求至少能指到一条用例，每条用例能指回一条需求」。

20. 数据造不出来怎么办？
骨架：先用界面造 → 界面造不出的用 SQL 插 → 边界值、重复数据、时间序列、脏数据在库里造 → 造完要能清掉（TRUNCATE 或独立测试库）。
加分：依赖连不上就失败，不跳过，跳过等于把门禁变成永远绿。

三、六个场景题

每个给可背骨架。先澄清、再分层、最后给结论，这是统一套路。

1. 登录功能怎么测

骨架六步：

  1. 澄清：账号类型是手机号、邮箱还是账号 ID，有没有验证码和第三方登录。
  2. 拆输入项：账号、密码、验证码、记住我。
  3. 拆账号状态：未注册、已注册、已锁定、第三方账号。
  4. 串场景：注册 → 登录 → 切换账号 → 忘记密码 → 重置后用新密码登录。
  5. 打异常：空值、长度边界、连续输错锁定、验证码过期。
  6. 查安全：密码是否明文传输、验证码能否绕过、越权看他人信息、SQL 注入与 XSS。

一句话结论：功能用等价类加边界值铺输入，接口层查鉴权与错误码，安全层查越权与注入，兼容与文案放最后。

2. 搜索功能怎么测

骨架六步：

  1. 先确认排序规则、过滤条件、匹配度口径。
  2. 合法关键词查结果相关性与排序是否符合规则。
  3. 边界输入：空串、超长串、含 &、%、# 的特殊串。
  4. 零结果时的空态提示与错误词处理。
  5. 切换筛选条件后结果是否被正确收窄。
  6. 压测高并发搜索下的响应时间与资源占用。

一句话结论：搜索的根在查询条件与排序规则，先把这两条确认下来，再铺输入和筛选组合。

3. 支付模块怎么测

骨架六步：

  1. 正向：多种支付方式各成功一次，订单置为已支付。
  2. 负向：余额不足、卡号错误、用户中途取消。
  3. 状态机只往前走：待支付、支付中、已支付、已关闭不可跳变。
  4. 金额用整数最小单位或 Decimal，不用浮点。
  5. 同一订单重复提交只生成一笔支付。
  6. 回调验签，重复回调只迁移一次状态。

一句话结论：钱只能退不能撤，支付成功后的取消是退款流程；幂等要用订单条数核对，不能只看返回码。

4. 库存或权限怎么测

库存骨架：

  1. 理清库存增减的触发条件与业务流程。
  2. 下单成功扣减、取消订单回补、支付失败不扣。
  3. 库存为 0 和库存到上限时的提示与拦截。
  4. 并发下单压测，验不出超卖、库存不为负。
  5. 直接查库比对库存数与流水是否一致。
  6. 乐观锁或悲观锁冲突时只允许一条成功。

权限骨架：

  1. 建角色矩阵：管理员、运营、普通用户、未登录。
  2. 逐角色验菜单、按钮、接口的可见与可用。
  3. 改请求里的用户 ID，验能否拿到别人的数据。
  4. 用过期或伪造 token 调受保护接口。
  5. 前端藏了按钮但后端没鉴权的接口直接调。
  6. 查日志与数据落库，确认拒绝路径也留痕。

一句话结论：越权的本质是后端没鉴权，前端隐藏只是遮挡，验证要绕到接口层。

5. 无法复现的 bug 怎么处理

骨架六步：

  1. 记录环境、步骤、出现频率、日志与账号，保留现场。
  2. 比对测试环境与生产环境的配置差异。
  3. 主动加日志与埋点，扩大信息面。
  4. 用自动化高频跑关键路径，提高复现概率。
  5. 在高负载或回退版本上尝试复现。
  6. 复现不了先挂观察中，定期回顾并用灰度收集案例。

一句话结论：复现不了不等于不存在，先做取证与差异比对，再谈概率；结论写「未复现，原因待定」而不是「没问题」。

6. 需求变更或时间不够怎么办

需求变更骨架：

  1. 拉开发和产品一起评估变更对功能、用例、数据、环境的影响。
  2. 改用例清单：新增、修改、废弃分别列清。
  3. 调整测试计划与排期，把新增工作量写明。
  4. 变更过程用版本控制留痕，可追溯原因。
  5. 变更后按影响面做回归，确认没破坏老功能。
  6. 同步更新需求文档、用例与测试报告。

时间不够骨架：

  1. 和产品、开发一起做风险分析，定出必须测的 P0 链路。
  2. 划出高风险区域：改动大、历史缺陷多的模块优先测。
  3. 用已有自动化跑回归，人力压在主流程与异常分支。
  4. 每个新版本先跑冒烟，挡掉会卡住后续测试的严重问题。
  5. 边缘功能与兼容性往后放，并把砍掉的范围写进风险说明。
  6. 争取并行人力或分批上线。

一句话结论：变更和赶工都不是砍测试的理由，是换测法，改测范围与优先级，并且把取舍公开写下来。

四、自我介绍模板

4.1 结构表

二 工具 每工具一句「我做过什么」：Postman 断言与关联与数据驱动、Charles 抓包改包弱网、pytest 参数化与 fixture、JMeter 线程组与聚合报告 约 20 秒

收尾 选测试的动机，一句话 约 7 秒

4.2 通用模板（约 320 字，示例项目占位）

面试官您好，我叫 meisijiya，计算机科学与技术专业在校生，投软件测试实习生。我的测试能力分三块。第一块是基础：需求评审到用例设计我按流程走，等价类、边界值、判定表、场景法都会用，写用例先拿思维导图把测试点铺开再补前置条件、步骤和预期结果。第二块是工具：接口用 Postman 做断言、环境变量、请求关联和 CSV 数据驱动，用 Collection Runner 跑回归。抓包用 Charles，改包和弱网都试过。自动化是 Python 加 pytest，用参数化和 fixture 造数清数。性能能搭 JMeter 线程组看聚合报告。第三块是落地：我独立做过一个示例项目（此处替换为你自己的项目名与场景），按接口契约把测试点铺下来，pytest 一条命令跑全量回归；写完断言我还会改坏一处实现，看对应用例会不会转红，用例通过不等于能发现问题。团队经历让我熟悉版本按评审、提测、回归、复盘推进。AI 这块我在用结构化提示词先生成测试点，再人工收口补场景。我选测试是因为我更擅长把风险提前挖出来。

使用说明：方括号里的项目描述要换成你真做过的，数字按基线口径报，被追问时说「数字随版本走，我报的是基线那一版」。没有团队经历就把第四段换成课程项目。全文约 320 字，正常语速约 60 秒。

五、笔试速通

5.1 pytest 装饰器 10 题

# 问题 答案 为什么
1 scope 有哪些取值 function、class、module、package、session scope 越大执行次数越少，但状态共享风险越高；session 级不干净会互相污染（来源：pytest 官方文档，https://docs.pytest.org/en/stable/how-to/fixtures.html ，一手）
2 autouse=True 干什么 自动应用于同作用域内所有测试，无需显式请求 适合放清场、环境检查这类每次都要做的动作；注意它对同作用域全部用例生效，成本要算进去（pytest 官方文档，同上一手）
3 parametrize 怎么叠多个参数 可以堆叠多个装饰器，也可以传参数列表；ids 自定义用例名，indirect=True 把参数传给 fixture 叠多个装饰器时组合是笛卡尔积，参数组多了用例数会暴涨，要控制规模（同上一手）
4 skip 与 skipif 的差别 skip 无条件跳过；skipif 满足条件才跳过 条件式跳过要写清原因，否则报告里一堆 skip 看不出是环境问题还是漏测（pytest 官方文档，同上一手）
5 xfail 是什么语义 预期会失败的用例，仍然执行；失败记 XFAIL、通过记 XPASS，strict=True 时 XPASS 判为失败 用于「已知缺陷尚未修」，能把已知问题纳入回归而不阻塞；不写 strict 容易掩盖修复（pytest 官方文档，同上一手）
6 自定义 mark 怎么用 @pytest.mark.smoke 这类自定义标记要在 pytest.ini 注册，否则有 warning 注册后可以用 -m smoke 只跑冒烟集，这也是分层的常用做法（pytest 官方文档，同上一手）
7 conftest.py 的作用域 放在某目录的 conftest.py 里的 fixture 对该目录及子目录所有测试模块可见；同名 fixture 优先级是类 > 模块 > conftest 放公共造数与清数能避免每个文件重复；覆盖顺序要记清，否则调试时找不到用的是哪个（pytest 官方文档，同上一手）
8 fixture 里 yield 代替 return yield 前是 setup，yield 后是 teardown，测试结束后自动执行清理 比 return 多一步清理，适合「造数 + 清数」；fixture 之间可以互相请求形成依赖链，循环依赖会报错（pytest 官方文档，同上一手）
9 怎么重写断言 直接用 Python 的 assert 表达式，失败时 pytest 会给出断言改写后的详情（左右值对比） 不要用 try/except 自己包 assert，否则断言会被吞掉，pytest 也就收集不到失败信息（pytest 官方文档，同上一手）
10 -k 与 -m 的区别 -k 按测试名或类名关键字过滤（表达式），-m 按 marker 过滤 -k smoke 选名字含 smoke 的用例，-m smoke 选打了 smoke 标记的用例；两个可以叠加使用（同上一手）

补充两句常被追问的：monkeypatch 用来临时改对象属性、环境变量或 sys.path，测试结束自动还原；tmp_path 给一个临时目录，测完自动清理，适合写临时文件。

5.2 SQL 6 题

假设表结构：user(id, name, dept_id, salary, status, create_time)、orders(id, user_id, amount, create_time)。

# 题型 SQL
1 单表条件 SELECT id, name FROM user WHERE dept_id = 3 AND status = 1; —— 多条件用 AND 连接，注意 status 这类可能为 NULL 的字段
2 聚合与分组 SELECT dept_id, AVG(salary) AS avg_salary FROM user GROUP BY dept_id; —— 分组后过滤要用 HAVING，不是 WHERE
3 关联 SELECT u.name, o.amount FROM user u JOIN orders o ON o.user_id = u.id WHERE o.amount > 100; —— INNER JOIN 取交集，要保留没订单的用户用 LEFT JOIN
4 子查询 SELECT name FROM user WHERE salary > (SELECT AVG(salary) FROM user); —— 标量子查询只算一次；若写成相关子查询则逐行执行；MySQL 8.0 会把 IN/EXISTS 转成 semijoin，大列表时两者差别不大，按执行计划判断而非默认 EXISTS 更优
5 去重 SELECT DISTINCT dept_id FROM user; —— 查重复记录用 GROUP BY col HAVING COUNT(*) > 1
6 按更新时间排序取最新 SELECT * FROM user ORDER BY create_time DESC LIMIT 1; —— 每个用户取最新一条订单用窗口函数 ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY create_time DESC) = 1

SQL 笔试的常见题型还包括：NULL 处理（WHERE col IS NULL，不是 = NULL，COUNT(col) 不计 NULL 而 COUNT(*) 计）、EXISTS 与 IN 的区别（EXISTS 找到即停）、事务 ACID 与隔离级别。题型来源：QAJobFit，https://qajobfit.com/resources/sql-interview-questions-for-testers （二手）。

题 2：快速排序（一行分治）

平均 O(n log n)，最坏 O(n²)（有序数组且取末尾元素为基准）。不稳定。

题 3：内置 sorted 与稳定性

sorted 与 list.sort 都是稳定排序：相等元素保持原有相对顺序。多级排序用 key 返回元组，元组按位比较。稳定性的实际意义是「先按次要字段排，再按主要字段排」时不会打乱已有的相等元素顺序，测试里做报表排序经常依赖这一点。

六、诚实边界

6.1 不能说的话

不能说 为什么 换成
编造的缺陷数、用例数、通过率、提效百分比 一追问参数就露 报基线口径，并说明数字随版本走
把课程示例数据当成自己项目成绩 课件里的通过率、修复率是课程示例口径 明确写「课程示例口径」，自己的报告用实际跑出来的数
说「精通」某个没深用的工具 面试官会往下追细节 「能用它完成某件事」，并说清边界
说「AI 全自动生成测试并跑完」 现在不存在这种能力，说了就是不诚实 AI 出候选，我做判定和兜底
把别人的团队项目说成公司项目 归属错误 明确是团队项目，我负责质量部分
说「我用过某框架」但没跑过 追问细节会断 说「我没直接用过，但做过相邻的 X」

6.2 不会时怎么答

句式 用在哪
「这个我没直接用过，但我做过类似的 X，如果是我会先查文档，再……」 被问没碰过的工具或框架
「这块我没接触过，直说不硬编例子」 完全没做过的领域
「不会的题我先讲思路，再讲我确定的部分」 完全不会的概念题
「数字随版本走，我报的是基线那一版」 被追问数量口径
「课程实战规模，能跑通集合与回归，不报没记录的数字」 项目数字无法自证时

三条原则：先给思路再给细节。不会就说不会并给相邻经验。细节记不清时改说「排查到哪一层、下一步怎么查」，不要停在「有点忘记了」。

🗣️ 面试怎么说

  1. 我的主线是接口加自动化，因为 15 个岗位里有 11 个提到自动化脚本。AI 测试是我的增量方向，我准备了评测集、幻觉三类判定和提示注入用例三块。
  2. 面试高频题我准备了二十个骨架，每个都是三到四步：先澄清需求，再分层铺点，最后给结论和优先级。
  3. 场景题我统一用「澄清需求 → 功能/接口/安全/兼容/性能分层 → 结论」三段。场景题集中在登录、搜索、支付、库存与权限、缺陷复现、需求变更这六类，我按『澄清→分层→结论』三段答，这六类我背得最熟。
  4. 自我介绍我按七段讲，控制在六十秒，数字按基线口径报，被追问就说数字随版本走。
  5. 笔试三块我会手写：pytest 装饰器、SQL 六类查询、冒泡与快排加 sorted 的稳定性。
  6. 我不会把课程示例数字当成自己的成绩，也不会编提效百分比。不会的题我会先讲思路再讲确定的部分。
