一、七类测试岗位分型

判断：实习面试里「测试岗」不是一个大类，招聘启事原话决定你要补什么；先按七类归位，再对着启事圈词。

方向 核心职责 必备技能 启事原话摘录 样本薪资（口径见备注）
功能测试 按需求设计并执行用例，提缺陷 测试理论、用例设计、SQL、沟通 「协助功能/回归测试，梳理业务流程与需求，编写基础用例」 样本不足，未列出（样本中纯功能/第三方测评岗未公布日薪）
接口自动化 写接口用例与自动化脚本，做回归 Python、pytest、Postman、断言 「用 Python 开发自动化脚本，完成 UI 自动化、简易接口自动化」 180–250 元/天（实习日薪）
测试开发 做测试工具、框架与平台 Java 或 Python、数据结构、操作系统、数据库 「自动化测试工具开发维护，提升测试效率；监控设计与部署」（#2） 15–25K·14 薪（#6 招银网络科技）
性能测试 压测、找瓶颈、给优化建议 JMeter、指标口径、Linux、监控 「识别系统性能瓶颈与安全风险」 样本不足，未列出
安全测试 找漏洞、做渗透与加固 Web 安全、OWASP、工具链 「安全评估、兼容性测试等专项」 样本不足，未列出
测试平台/工具 搭平台、造工具、推落地 前后端、CI/CD、工程能力 「测试工具的设计、选型、引入与推广应用」（#5 薪资面议） 15–25K·14 薪（#6）
AI 测试 评测集、智能体测试、AI 辅助提效 评测集构建、Prompt、Agent 测试 「评测集构建、Agent 测试、指标体系（准确率/幻觉率/一致性）为新要求」（#10/#12 腾讯，薪资未公布） 150–400 元/天（实习日薪，#3、#4）

样本出处：2026 年 11 月抽样的 15 个岗位样本表，覆盖纯功能/第三方测评、测试开发、接口/自动化、性能/专项、金融/银行、AI/大模型、游戏七类方向。招聘页面可能已变化或下架，数字只当量级参考，实际以启事与城市为准。

薪资为同一批 15 个样本岗位的标价区间，仅作量级参考。

三个专项岗位的技能补一句

性能测试的「指标口径」看六个数：TPS/QPS（每秒处理的事务/查询数）、吞吐量（单位时间处理的请求数）、响应时间（看 P90/P95）、错误率（失败请求占比）、并发用户数（同一时刻在发请求的人数）、资源利用率（CPU/内存/磁盘/网络）。下面这组达标线是常用经验值（示例），不是行业标准：响应时间 500ms、错误率 <1%、CPU 长期 >80% 就要查。达标线优先按需求或 SLA 的约定；没有约定时，报口径就报「本项目约定的值」并说明这是经验值，别把它说成标准。

安全测试的「OWASP」是 Web 安全领域的权威社区，它的 Top 10 列十类最常见 Web 风险。2025 版的十类是：访问控制失效、安全配置错误、软件供应链失效、密码学失效、注入、不安全设计、认证失效、软件或数据完整性失效、安全日志与告警失效、异常处理不当（https://top10.owasp.org/2025/en/）。注入这一类把 SQL 注入、跨站脚本 XSS 都收了进去，2021 版里单列的 XSS、失效的身份认证、敏感数据泄露、XML 外部实体、组件漏洞这几种，在 2025 版分别并进了注入、认证失效、密码学失效、软件供应链失效。渗透测试是模拟攻击者找漏洞（信息收集 → 扫漏洞 → 拿权限 → 出报告），加固是按报告补校验、改配置、修代码。常用工具链：Burp Suite、OWASP ZAP、Nmap、SQLmap、Metasploit。

测试平台的「CI/CD」是一条自动流水线：提交代码 → 代码扫描 → 构建 → 单元测试 → 部署测试环境 → 接口/自动化回归 → 上线 → 线上监控。测试门禁嵌在「构建」和「自动化回归」两处，不过就不准往下走——这就是测试在 CI/CD 里的位置。

拆一份招聘启事的四步

拿到任何一条测试岗启事，按这四步拆，不要通读：

  1. 圈硬门槛。学历、毕业时间、专业、实习时长、必须会的语言与工具，这些是筛简历的条件，缺一条就可能被刷。
  2. 圈职责动词。启事里出现的动词决定岗位类型：写「编写用例、提交缺陷」是功能测试；出现「开发、维护、框架、平台」是测试开发；出现「评测集、指标体系」是 AI 测试。
  3. 圈加分项。加分项决定面试聊什么，简历里能对上就写进项目经历。
  4. 核对门槛统计。样本里本科及以上占 14/15，实习 3 个月及以上占多数，Python 出现 9/15。达不到硬门槛的岗位先别投，把时间留给能投的。

统计口径：基于同一批 15 个岗位启事摘录，同一岗位同一词计 1 次，同一份启事里重复出现也只记 1 次。开发转测的人，Python 是最高频硬门槛，先补它。AI 方向的专项词频在同一批样本里单独统计（AI 类岗位数远少于 15，故不并入上表）：评测集构建 4 次、Agent 测试 4 次、幻觉与效果评价 3 次、提示词 2 次。

薪资怎么看

样本里的薪资分成三档：按天结算的 120–400 元/天，固定薪资的一万五到两万五乘十四薪，还有未公布的。谈薪之前先看清计价方式：按天和按月不是一套逻辑。按天报价 × 22 个工作日可粗估到手月薪（22 天是常见的估算约定，示例值，实际按出勤天数与发薪月数算），且日薪通常不含社保公积金；月薪按月计，14 薪＝全年发 14 个月工资（即 12 个月月薪 + 2 个月年终奖，折月均约为月薪 × 1.17，这是按 12 个月摊薄的算术结果），合同上要看是「14 薪写死」还是「12 薪 + 年终奖看绩效」。样本里唯一写死月薪的是招银网络科技 15–25K·14 薪，银行与第三方测评多为面议或未公布。未公布的样本集中在腾讯三个社招岗，实习岗位反过来，多数直接写日薪。谈薪时先报自己期望的月等价值，对方给日薪再折算对比。

各方向启事里反复出现的动词

动词 出现在哪类岗位 说明你要产出什么
编写、梳理、执行 功能测试 用例、执行记录
开发、维护、框架 测试开发 脚本、框架、平台
评测、标注、打分 AI 测试 评测集、评分卡
压测、调优、监控 性能测试 压测报告、优化建议

动词是判断岗位类型的信号。启事里全是「开发」是测试开发，全是「评测」是 AI 测试，只写「编写用例」是功能测试。

投递前的三道检查

检查 怎么看 不通过就别投
硬门槛 学历、专业、毕业时间、实习时长 缺一条直接被筛

一个岗位投递前花五分钟做这三道检查，比投出去石沉大海划算。

七类岗位怎么选

你的现状 首选方向 理由
刚学测试，没有项目 功能测试 门槛最低，用例设计和沟通就能上手
会 Java 或 Python，写过脚本 接口自动化 启事里自动化词频最高，产出可量化
代码能力强，喜欢做工具 测试开发 样本里多为大厂，门槛是编程与数据结构
喜欢和系统性能打交道 性能测试 样本少，竞争相对小，但要能讲清指标口径

想进大厂工程团队 测试平台 要求前后端与 CI 能力，进阶方向

岗位名只是标签。同一个方向投十家，不如挑五家不同方向各投一家，先把覆盖面打开。

二、团队分工矩阵

判断：测试不是「开发写完再上场」，需求评审阶段就要介入；矩阵能让你说清每个阶段和谁对接、交付什么。

角色 需求阶段 开发阶段 提测与执行 上线
产品 写需求、定验收 答疑问 参与验收 确认上线
开发 评审技术方案 写代码、做单元测试 修缺陷 发布与回滚
测试 评审需求、查漏补缺 写用例、准备数据 执行用例、提缺陷、回归 验收、出报告
运维 评估资源 搭环境 保障环境 监控与扩容
用户代表 提需求 不参与 参与验收 使用与反馈

每格展开成「测什么、和谁对接、交付什么」：

阶段 测什么 和谁对接 交付什么
需求评审 需求描述是否清楚、验收口径是否明确 产品、开发 疑问清单、评审结论
计划 测什么不测什么、风险在哪 项目、开发 测试计划
设计 每个功能的测试点、用例 开发（规则） 用例、测试点树

| 提测 | 版本能不能跑通 | 开发 | 冒烟结论、是否接单 |
| 执行 | 用例结果、缺陷跟踪 | 开发 | 执行记录、缺陷单 |
| 验收 | 需求覆盖情况、遗留风险 | 产品、用户代表 | 验收结论 |
| 上线 | 上线结论、线上监控 | 开发、运维 | 测试报告 |

测试在需求评审阶段做三件事：熟悉核心业务、从不同角度查漏补缺、让各方对需求理解一致。评审由产品、开发、测试三方参与，正常情况下测试人员全部参与需求阅读。

三个角色边界的常见误解，面试容易被追问：

  • 测试不负责写代码。单元测试由开发做，测试从集成和系统层接手。
  • 测试不等开发写完。越早介入，缺陷发现越早，修复代价越低。
  • 测试不是提需求的。产品定需求、验收标准，测试提的是疑问和建议，不是替产品做决定。

面试被问「测试在项目里做什么」，用这张矩阵回答，比背「测试保证质量」具体得多。

三、60 条术语白话表

判断：术语表按七个组背，每组先记中文与英文对照，再记一句白话；面试里先给中文，追问再给英文。

测试类型组（12 条）

中文 英文 一句白话
软件测试 Software Testing 用技术手段运行软件，验证是否满足需求
功能测试 Functional Testing 验证程序功能是否满足需求
接口测试 API Testing 通过接口向被测对象提交请求并校验响应
性能测试 Performance Testing 判断被测对象的性能效率：响应时间、吞吐量、资源占用等
自动化测试 Automated Testing 用代码或工具代替人工验证
单元测试 Unit Testing 测试级别之一：验证可隔离测试的最小代码单元，一般由开发做
集成测试 Integration Testing 验证模块拼起来后能否协同工作，是测试阶段
系统测试 System Testing 对整个系统做端到端验证，覆盖功能与非功能
验收测试 Acceptance Testing 测试级别之一：判定是否接受这个系统，由用户或用户代表执行
黑盒测试 Black-box Testing 基于规格说明的测试：不依赖内部结构，只按需求与接口契约判定
白盒测试 White-box Testing 通过源代码测试源代码
灰盒测试 grey-box testing 黑盒与白盒的组合，需要掌握部分内部实现

设计方法组（8 条）

中文 英文 一句白话
等价类划分 Equivalence Partitioning 把输入按条件分有效与无效类
边界值分析 Boundary Value Analysis 测边界范围的数据
判定表 Decision Table 表格枚举条件组合与动作
因果图 Cause-Effect Graph 图形化输入条件与输出结果关系
正交试验法 Orthogonal Array Testing 从全组合中选代表性少量组合
状态迁移测试 State Transition Testing 基于状态及迁移设计用例
场景法 Scenario Testing 按用户使用流程设计用例
错误推测法 Error Guessing 凭经验推测易错点

设计方法组的定义口径来自 ISTQB 术语表（一手）：等价类划分、边界值分析、判定表、状态迁移见 CTFL v4.0.1 第 4.2 节，错误推测见第 4.4 节经验型技术；因果图、正交试验法、场景法取 ISTQB 术语表与维基百科（二手）口径。本篇按中英对照给出每条的白话定义，背这组就够了。

流程文档组（12 条）

中文 英文 一句白话
测试用例 Test Case 基于测试条件生成的一组前置条件、输入、操作、预期结果与后置条件
测试计划 Test Plan 描述测试目标、手段与进度安排（怎么达成、怎么协调）的文档
测试报告 Test Report 测试过程与结果的总结文档
缺陷 Bug / Defect 软件中不满足需求的地方
冒烟测试 Smoke Testing 对被测对象做一次短测试，获得「可以进入正式测试」的足够信心
回归测试 Regression Testing 变更相关的测试：确认改动没有在未改动的区域引入或暴露缺陷
需求评审 Requirement Review 产品开发和测试一起对需求
提测 Build Submission 开发把版本交给测试
准入标准 Entry Criteria 什么条件才能开始测
准出标准 Exit Criteria 什么条件才能结束测
测试环境 Test Environment 跑被测系统的环境
预发布环境 Staging Environment 上线前共用环境

本组里「预发布环境」不在 ISTQB 术语表内，属业界通用叫法；「准入标准、准出标准」在 CTFL 里有对应概念，但各团队的叫法与粒度不同，面试按团队口径讲。

缺陷组（6 条）

中文 英文 一句白话
缺陷严重级 Severity 缺陷对系统的影响程度

本组里「不可复现缺陷」「缺陷趋势」不是 ISTQB 术语表条目，属业界通用叫法或团队与工具的字段，面试按团队口径讲。

关联 Correlation 把前一个接口结果传给后一个
参数化 Parameterization 同一逻辑跑多组数据
接口文档 API Documentation 描述接口参数与响应的说明

性能组（7 条）

中文 英文 一句白话
并发用户数 Concurrent Users 同一时刻向服务器发请求的用户数
吞吐量 Throughput 单位时间处理的请求数
TPS Transactions Per Second 每秒事务数
QPS Queries Per Second 每秒查询数
响应时间 Response Time 从发请求到收到结果的时间
错误率 Error Rate 失败请求占总请求的比例
资源利用率 Resource Utilization CPU 内存磁盘网络的使用比例

AI 组（7 条）

中文 英文 一句白话
提示注入 Prompt Injection 输入里藏指令覆盖系统预设
幻觉 Hallucination 模型生成看似合理但错误的信息
事实性幻觉 Factual Hallucination 事实错误或虚构
忠实性幻觉 Faithfulness Hallucination 回答超出给定上下文、无依据地补充或编造引用
逻辑性幻觉 Logical Hallucination 推理结论自相矛盾
检索增强生成 RAG 先检索知识库再让模型回答
评测集 Evaluation Dataset 问题与预期答案的数据集

AI 组的三个幻觉分类与 RAG 分层测试本篇讲完。RAG 分层测试按流水线分层测，每层只测该层自己：

层级 测什么
检索层 召回准不准：查的问题能不能把相关文档捞回来，看召回率与相关性排序
生成层 答案对不对：只基于检索到的内容答，不编造，看事实准确率与幻觉率
整体层 端到端效果：从提问到最终回答的满意度、一致性，看多轮与边界场景

三层的失败点不同：检索层漏了，生成再对也答不出；生成层编了，检索再准也出幻觉。面试按这个顺序答，比只说「测 RAG」具体。
另有一类叫指令遵循（instruction following）：没按输入的格式、范围、角色等约束回答，表现为漏项、答非所问、越界。它不是幻觉，和忠实性幻觉要分开说。

背词表的用法：一个词说三遍——中文说一遍，英文说一遍，白话说一遍。一天 20 个词，三天能过完 60 个，之后按面试高频挑着背。面试里术语答不完整没关系，说得出英文和白话，对方就知道你真用过。

四、转测选岗建议

判断：开发转测有三个现成优势，也有三个必须补的短板；选岗顺序建议接口自动化 → 测试开发 → AI 测试。

三个优势：

  1. 懂代码：能读源码、看日志、定位问题，不用等人解释实现。
  2. 能写脚本：Python 与 pytest 上手快，接口自动化能立刻产出。
  3. 懂排查：知道系统怎么跑，出问题有固定顺序，不会临时乱试。

三个短板：

  1. 业务视角：容易只盯实现，漏掉用户路径和隐性需求。
  2. 用例设计：会把「验证代码」当「验证需求」，用例写成代码走查。
  3. 沟通：习惯和代码打交道，需求疑问和缺陷描述讲不清。

选岗顺序的理由：接口自动化离开发最近，入职后能立刻产出价值；测试开发需要框架与工程能力，适合作为中期目标；AI 测试是新方向，评测集与智能体测试的词频在涨。

三个短板怎么补，各有一个具体动作：

短板 补法 一周的最小动作
业务视角 拿一个真实需求，把用户路径画一遍 画登录到下单的流程图，标出每步的分支
用例设计 照上文设计方法组的八种方法各写一遍 一个需求用三种方法各写 5 条用例
沟通 练把技术问题写成缺陷单 写 5 条缺陷单，含步骤、预期、实际

面试被问「为什么选测试不选开发」，只讲强项和开发背景的用处，别贬低任何一方。被问「测试和开发的区别」，用产出物回答：开发交付功能并对需求负责，测试交付质量信号——用例、自动化、门禁、缺陷报告——对问题能不能被提前发现负责。

五、岗位与术语速查

判断：面试前 10 分钟只看这一页，左栏定岗位，右栏定术语。

岗位方向 硬门槛词 术语锚点
功能测试 用例设计、SQL、沟通 等价类、边界值、场景法
接口自动化 Python、pytest、Postman 状态码、业务码、断言三层
测试开发 Java/Python、数据结构、CI 参数化、接口文档、状态码
性能测试 JMeter、Linux、监控 并发用户数、TPS、响应时间
安全测试 OWASP、Web 安全、渗透流程 注入、XSS、越权、加密失效
测试平台 前后端、CI/CD 测试计划、准入标准
AI 测试 评测集、Prompt、Agent 幻觉、RAG、评测集

术语锚点补两句。断言三层指接口断言的三个层次：第一层状态码，HTTP 返回码是 200 才算请求通了；第二层业务码，业务码表示这次业务操作成功还是失败；第三层字段值与结构，响应里的字段值、字段齐全与否是否符合预期。三层都过才算一条接口用例通过。AI 安全测试的评测对象是模型与 AI 系统本身，区别于普通安全测试测的是软件系统。常见风险类型：提示注入（输入里藏指令绕过约束）、幻觉（编造事实与引用）、数据泄露（把训练数据或隐私输出出去）、越权与不当内容（绕过安全策略的输出）、工具调用风险（Agent 误调或被操控接口）。普通安全测试按 OWASP 查代码与配置漏洞，AI 安全测试按风险类型查模型输出与行为，两者工具与判据不同。

🗣️ 面试怎么说

  • Python 是最高频的编程语言（9/15），自动化相关词更高频（11 个岗位），我用它写过 pytest 脚本和 Postman 集合。
  • 测试在需求评审阶段就介入，我在评审里做三件事：熟悉业务、查漏补缺、统一理解。
  • 缺陷严重级看影响程度，优先级看修复顺序，两者不是一回事。
  • 我背术语按七组背：类型、设计方法、流程文档、缺陷、接口、性能、AI。
  • 开发转测我的优势是懂代码和排查，短板是业务视角，我在用用例设计补这块。
