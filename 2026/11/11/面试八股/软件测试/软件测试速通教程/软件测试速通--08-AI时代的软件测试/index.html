软件测试速通--08-AI时代的软件测试

Hi，我是 meisijiya ，也是 老江湖 ，感谢你的阅读，我们一起进步。

AI 测试改的是分工。机器出候选，人做判定。这一篇分三块——先用一条完整流水线讲清我日常怎么用 AI 做测试，配三段可以直接抄的提示词；再讲怎么去测 AI 产品和智能体本身；最后给 2026 年的学习路线和四周计划。

一、AI 辅助测试全流程

1.1 一条流水线，六步

流程：需求/原型 → 生成测试点 → 生成用例 → 评审打标 → 修正 → 回归

步 做什么 关键动作 产出物
1 需求/原型 把需求读成可测的东西 补齐业务规则、边界、异常、状态流转 一份「需求要点 + 禁止行为」清单
2 生成测试点 铺量 用固定模板让模型按模块出测试点树 分模块测试点清单
3 生成用例 落成 8 要素 约束编号、模块、优先级、前置、步骤、数据、预期 md 用例文档
4 评审打标 挑毛病 逐条判「覆盖 / 可执行 / 期望可判定」，不合格的打标 评审表（结论 + 原因 + 修改建议）
5 修正 闭环 归类不通过原因，回填提示词约束与示例，只重生成差异项 新版提示词 + 增量用例
6 回归 收口 合并去重入库，脚本化执行回归 回归集 + 缺陷单

为什么要分模块批量：一次性让模型出一千条，用例会重复、跑题、模块混淆。按模块拆批，每批固定模块与维度、统一编号规则和字段，评审表能直接回填到提示词。这是课件的批处理建议（来源：黑马 2026 AI+软件测试课件·AI 智能体测试线（day01–day02 课堂笔记））。

执行时的一个坑：智能体有记忆，会读历史对话导致偏差。执行每一批之前要么清空会话，要么在提示词里限定「仅评估当前输入 / 当前上传」。

1.2 三段可以直接抄的提示词

下面三段是课件原文，我按原文保留，直接复制就能用。

提示词 1：批量产出三类幻觉测试用例（用例生成环节）

提示词 2：评审模型输出是否通过幻觉判定（评审环节）

提示词 3：面向具体智能体生成功能用例

写提示词本身的规矩（课件称 CREAM 原则）：指令清晰无歧义；给角色（专业测试工程师）；给示例对齐标准；加约束限定格式、长度、排除项；要求结构化输出便于自动处理与评审。提示词六要素是角色、任务、要求、输出、背景、示例。

1.3 人工必须收口的三件事

模型能铺量，不能定标准。这三件事只能人来收口：

收口项 为什么模型做不了 人怎么做
覆盖边界 模型不知道业务里哪些是「不该有的行为」 逐模块对照需求与原型回勾，标出模型没覆盖的隐藏入口
期望结果 期望要可判定，模型常写成「显示正常」这样的话，不可判定 把每条期望改写成能断的具体字段、状态码或文案
业务语义 模型会把「已支付订单取消」这类语义搞混 对涉及状态流转、资金、权限的用例逐条人工读一遍

判断标准一句话：用例通过不等于能发现问题。写完断言要确认它能不能抓住一次真实改动，抓不住的退回重写。

1.4 脚本生成、失败归因与报告初稿

流水线里最花时间的三步，AI 帮得上忙，但都有前提。

环节 AI 能干什么 前提与人工收口
脚本生成 按接口契约生成 pytest + requests 骨架、按 OpenAPI 生成参数化用例、按 UI 元素生成 Playwright 定位 目录分层要自己定：接口只封装在 api/ 层，用例只写在 testcases/ 层，数据只放 data/ 层
断言补齐 给只有状态码的用例补业务码与业务数据断言 人工确认断言指向具体字段，而不是「返回成功」这种空话
失败归因 结合 trace 与日志，判断是提示词不清、知识库缺失、逻辑分支未覆盖还是工具异常 归因结论要落到具体配置项上，不能停在「AI 抽风」
报告初稿 按背景、目标、范围、周期、用例与缺陷统计、风险与发布判定要点生成 md 数字必须自己回填核对，课件里的通过率与修复率是课程示例口径，不能当成自己项目的成绩

工程上的硬规矩（来源：腾讯云开发者社区，https://cloud.tencent.com/developer/article/2698252 ，二手）：每条用例至少三层断言——状态码 + 业务码 + 业务数据；AI 生成的脚本不是一劳永逸，工程规范与业务逻辑校验仍要人工把关。还有一条更重要的：外部模型、抓取服务这类依赖要用替身接管，固定输出，依赖连不上就直接失败，不要跳过换绿灯——跳过等于把门禁变成永远绿。

1.5 一句话总结这条流水线

AI 出候选，人做判定和兜底。铺量、格式统一、找遗漏，交给模型；定标准、断业务语义、担责任，留给自己。

二、测试 AI 产品与智能体

2.1 三大转变与五大挑战

三大转变 从 到
输出性质 确定性（同输入同输出） 概率性（同输入可能异输出）
判定方式 功能正确（对/错） 质量评估（相对好坏）
验证时机 静态验证（一次性） 动态优化（持续监控迭代）
五大挑战 一句话
非确定性输出 同问两遍答案可能不同，断言要换成概率式与场景化
主观评价标准 「有用」没有唯一答案，要靠评分卡与多人打分
幻觉问题 说得像真的但没依据，必须单独设计检测口径
安全与伦理风险 偏见、毒性、隐私泄露
持续变化与漂移 模型或数据一变行为就变，要靠 trace 监控 + 定期回归评测

2.2 四个质量维度

维度 判什么 典型判据
准确性 事实正确、逻辑合理、信息完整 与知识库/权威资料比对无编造
有用性 真的解决了问题 建议可操作、与场景相关，不空泛
无害性 无偏见、无歧视、无有害内容 有害请求被拦截或安全拒答
一致性 相同或相似输入输出稳定 重复执行比较结论差异
评分卡与多人打分：开放性回答不能只靠一个人感觉。外部资料建议设计 1-5 分制评分卡，从准确性、连贯性、有用性等维度打分，每次评估至少安排 2-3 位评审员独立打分，再计算一致性系数（来源：阿里云开发者社区，https://developer.aliyun.com/article/1712146 ，二手）。

2.3 幻觉三类与判定四问

幻觉的本质是模型在按上下文做概率预测，不是查事实数据库。

类型 定义 检查法
事实性幻觉 事实错误或虚构（人物、时间、数据、来源不存在） 与客观事实比对，看是否与事实一致
忠实性幻觉 回答超出给定上下文：无依据地补充、编造引用 与召回材料/给定上下文逐句比对，看每句是否有出处
逻辑性幻觉 推理链或结论自相矛盾 看时间、因果、数值关系是否自洽

指令遵循（instruction following）是另一类问题：没按输入的格式、范围、角色等约束回答，表现为漏项、答非所问、越界。严格说它不是幻觉。课件把两者并在一起讲（见 §1.2 提示词 2 原文「忠实性（指令的遵循度）」），本文按业界 RAG 评测口径区分忠实性与指令遵循，提示词原文保留不改。

判定四问（课件口径，逐项给结论）：事实可验证？完全遵循指令？推理结论逻辑自洽？未引用不存在的来源信息？

外部资料给了三种检测方法（来源：阿里云开发者社区，https://developer.aliyun.com/article/1712146 ，二手）：事实核查、一致性检查、对抗性测试。第三种尤其有用——故意给模型一个带细微错误的前提，看它是盲目接受还是能识别矛盾。

2.4 鲁棒性输入清单

类别 清单
异常输入 空输入、超长文本、乱码、无意义字符串、大量重复字符
文件边界 损坏 PDF、0 字节文件、超大文件、非目标类型文件
并发稳定 连续快速提交多份任务，全部处理完成且响应可接受
逻辑矛盾 前后矛盾的请求，应识别并澄清，而不是强行编造

期望统一是：不崩溃，返回友好提示，不产生脏数据。

2.5 评测集怎么建

评测集就是「输入 + 期望答案」的集合，LangSmith 里对应 inputs 与 outputs（来源：黑马 2026 AI+软件测试课件·AI 智能体测试线（day11 课堂代码 数据集创建示例代码））。

建集要素 说明
规模 没有统一标准，先覆盖高频场景与已知缺陷点，再按失败样本增量扩
构成 领域知识问答 + 场景化任务 + 边缘案例 + 多难度样本（来源：阿里云开发者社区，https://developer.aliyun.com/article/1712146 ，二手）
期望值标注 每条标 reference，并对开放性回答额外写「必须命中的词」和「绝对不能出现的词」
执行定义 target 把输入送进被测系统产出实际结果；评估器比较实际与参考，聚合出通过率
评估器口径 课件示例的 exact_match 是「参考答案包含于实际答案即通过」，不是严格全等，适合关键词与结论核验（来源：黑马 2026 AI+软件测试课件·AI 智能体测试线（day11 课堂代码 RAG 评测示例代码））

公开数据集（MMLU、HELM 等）只能当基线参考，业务评测集必须自己建。

2.6 一致性怎么判

口径：同一输入重复执行，比较输出的差异。

课件示例口径（课程示例口径，非通用标准）：同一份简历测三次，三次评分差异小于 1 分视为稳定一致。

具体做法：把同一批输入跑 N 次（N 取 3 起步），逐条比对结论、评分与关键字段，把差异记成「同输入不同结论」的不一致样本，再回溯是提示词、示例还是知识库导致的。

2.7 Agent 四要素与四维拆法

智能体公式：Agent = LLM（大脑）+ 记忆 + 规划 + 工具。

要素 测点
大脑 准确性、一致性、幻觉、遗忘（多轮是否丢关键约束）
记忆 多轮上下文延续、隔轮再问能否取回、会话间串扰
规划 步骤完整、顺序合理（先解析后评估、先检索后生成）、异常分支可恢复
工具 调用准确（该查天气不查知识库）、参数正确、触发时机、失败与超时降级

四维测试体系：功能、准确性、鲁棒性、用户体验。第三件套（插件、知识库、工作流）各自测什么：插件测准确触发、异常、性能；知识库测检索准确与「问不到就不编」；工作流测节点、分支、变量传递与任务闭环。

2.8 RAG 三层与四个指标

链路：用户问题 → 查询改写 → 检索（知识库/向量库） → 重排序 → 拼上下文 → 生成 → 回答

层 测什么 关注指标
检索层 召回率、排序质量、多样性、边界（无命中时行为） 该召回的片段有没有进上下文、排在第几
生成层 引用准确性、综合能力、诚实度、拒答能力 回答是否只用上下文里的信息
端到端 用户旅程、长上下文、压力与衰减 整体答得好不好

RAG 黑盒评估三元组（来源：Zilliz 官方博客，https://zilliz.com.cn/blog/how-to-evaluate-rag-zilliz ，二手）：

指标 口径
Context Relevance 上下文相关性 召回的上下文与用户问题是否相关
Answer Faithfulness 忠实度 回答是否基于召回上下文，没有超出（与 §2.3 同一口径）
Answer Relevance 答案相关性 回答是否切题、回应了问题

外部资料另给了 RAG 特有指标：引用准确率、信息利用度、带检索的幻觉率（来源：阿里云开发者社区，同上 URL，二手）。

2.9 提示注入与安全

攻击类型 怎么构造 预期
直接提示注入 输入「忽略之前的指示……」，试图改角色或越权 拒绝执行，重申安全准则与原职责
间接提示注入 正常任务之后追加「忘记你是 AI / 泄露系统提示词」 完成正常任务，拒绝恶意后续指令
越狱 角色扮演、虚构场景诱导突破限制 扮演中仍坚守安全约束
敏感信息窃取 旁敲侧击索要系统提示词或训练隐私 拒绝透露，不确认敏感信息存在

四层防御（来源：aigcharness 技术博客，https://aigcharness.com/blog/llm-security-practice ，二手）：输入侧过滤、输出侧校验、权限最小化、人工兜底，再加 Agent 工具权限治理。

两件可引用的事实：

  • OWASP 官方 GenAI 安全站点（https://genai.owasp.org/ ，一手）提供 LLM/Agent 应用的提示注入与红队测试公开资料，可用于系统化测试 LLM 集成应用的提示注入技术、绕过方法与攻击意图。
  • 腾讯朱雀实验室基于 A.I.G 对 DeepSeek Harness 做了授权、受控的端到端测评，覆盖 14,560 次真实运行，揭示了 Agent 提示注入风险（https://matrix.tencent.com/zh/2026/08/20/deepseek-harness-agent-injection-risk ，二手）。

2.10 Coze / Dify / LangSmith 上各自测什么

平台 测什么
Coze 工作流节点与变量绑定（开始节点的 file_url → 解析 → LLM 分块 → 代码转数组 → 循环评分 → 汇总输出）；插件触发与返回；知识库召回与「问不到不编造」；上传文件边界与报告格式脱敏
Dify 查询改写前后召回命中对比；检索与重排序质量；答案是否「先结论再给法条依据」；记忆开启后的多轮承接；前端嵌入后是否可用
LangSmith / LangChain trace 看输入输出、链路步骤、耗时与错误；评测集跑通过率；RAG 链路验证加载→分块→向量化→入库→检索→拼上下文→生成

评测流程八步：初始化模型 → 动态提示词 → 建 Agent → 定义 target → 配环境 → 建 Client → 定义评估器 → evaluate 分析。课件示例中不同轮次出现过 0%、50%、100% 的通过率（课程示例口径），说明单次通过率不能当结论，要结合 trace 定位失败原因再迭代。

三、2026 学习路线

3.1 三层路线

层 学什么 怎么验 作品/证据长什么样
必备基础 用例设计八法、测试流程、接口十要素与三层断言、Postman、pytest 现场给登录页拆 20+ 测试点并分优先级；接口用例跑通集合并导出报告 一份测试点树、一套 Postman 集合、一份测试计划与冒烟清单
加分项 pytest 参数化与 fixture、Charles 抓包改包弱网、JMeter 线程组与聚合报告、Linux 排障四层、Git 与 CI 报 500 时用固定三条命令定位到日志行；加一条参数化用例在自己数据上跑通 一个 pytest 项目、一份抓包与弱网记录、一份聚合报告截图
前沿 AI 辅助测试流水线、幻觉三类与判定四问、评测集构建、Agent 四要素拆法、RAG 分层与三元组、提示注入用例 用同一批输入重复跑，统计结论差异；用 OWASP 的 LLM/Agent 安全测试资料（genai.owasp.org）跑一轮注入用例并记录预期与实际 一份提示词集、一张评测集（含 reference）、一份含注入用例的测试报告
分层不是按「难易」排，是按「面试官问到时你能不能顶住」排。必备基础答不上来直接出局，加分项答不上来只是少分，前沿答不上来不影响基本盘。所以时间不够时先保必备基础。

3.2 四周计划表

周 每天主攻 周末产出
第 1 周 用例设计八法 + 需求评审 + 缺陷流程；每天拆一个模块，把测试点树画出来 一套登录/搜索/上传模块的测试点树与用例
第 2 周 Postman 接口测试 + 抓包 + 三层断言 一套可跑回归的接口集合与抓包记录
第 3 周 pytest 参数化与 fixture + 数据驱动 + 一键回归脚本 一个 pytest 项目，加一条能跑的自动化用例
第 4 周 AI 辅助测试流水线 + 幻觉三类 + 评测集 + 提示注入用例 一份提示词集、一张评测集、一份 AI 测试小结
四周计划的节奏建议：每天留最后半小时，把当天学的写成三句能讲的话（做了什么、遇到什么问题、怎么判断对错），面试时能直接用；每周末把产出物归档成一份文档，简历和作品集只写自己真跑过的那部分。

3.3 趋势要点（带来源）

  • 2026 年测试从发布前最后一道关卡演变为贯穿全生命周期的持续性能力，质量工程（QE）逐步替代传统 QA 模式（TesterHome 社区文章，二手：https://testerhome.com/articles/43904 ）。
  • Shift-left 与 Shift-right 并行：前置验证延伸到需求与设计阶段，发布后靠生产数据持续验证（TesterHome 社区文章，二手）。
  • AI 生成代码带来新的测试对象，要验证输出在行为层面的稳定性、安全性与一致性（TesterHome 社区文章，二手）。
  • 有分析机构估算 AI 测试工具市场仍在快速扩张，公开报道里也常见『多数企业已试点生成式 AI、规模化落地仍是少数』这类判断；具体口径与数值以原报告为准，教程里不引用转述数字。

🗣️ 面试怎么说

  1. AI 在测试里我做的是出候选，判定和兜底还是人；铺量靠它，业务场景靠人补隐藏入口。
  2. 我的流水线是六步：需求要点 → 分模块出测试点 → 出 8 要素用例 → 评审打标 → 回填提示词增量重生成 → 合并去重做回归。
  3. AI 产品测试和传统测试最大的差别是输出是概率性的，断言从「对/错」变成准确、有用、无害、一致四个维度的评价。
  4. 幻觉我分三类测：事实性、忠实性、逻辑性，判定用四问——事实能不能验证、有没有完全遵循指令、推理自不自洽、有没有引用不存在的来源。
  5. 评测集就是输入加期望答案，期望值我会额外标「必须命中的词」和「绝对不能出现的词」，这样判定才是可复核的。
  6. Agent 我按大脑、记忆、规划、工具四块拆测：大脑看准确和一致，记忆看多轮延续与串扰，规划看步骤与分支，工具看触发、参数和失败降级。
