一、性能指标口径表

性能测试关注两件事：时间（响应快不快）和资源（服务器消耗多少）。所有指标都从这两件事派生。

指标 定义 计算 / 判断口径
响应时间 从客户端发起请求到收到结果的总时间 = 服务器处理时间 + 网络传输时间；看平均值更要看 P90/P95
并发用户数 某一时刻同时向服务器发送请求的用户数 同一时刻在发请求的用户数，不等于在线用户数
吞吐量 单位时间内服务器处理的请求数量 统计窗口内请求总数 ÷ 窗口秒数
TPS Transactions Per Second，每秒事务数 一个事务可以包含多个请求；统计窗口内完成的事务数 ÷ 窗口秒数
QPS Queries Per Second，每秒查询数 偏「一次查询请求」的速率；单请求接口场景下 QPS ≈ TPS
错误率 负载情况下失败业务的概率 失败请求数 ÷ 总请求数 × 100%
资源利用率 系统资源占用比例 常见 CPU、内存、磁盘 IO、网络 IO、连接数
点击数 页面元素请求总数量 一次页面点击可能触发多个元素请求，是请求数不是一次点击

TPS 和 QPS 的区别（高频追问）：TPS 统计的是「事务」，一个事务可能包含多个请求；QPS 统计的是「查询/请求」次数。一个下单事务里含查库存、锁库存、创建订单三个请求，那么 TPS=1 时 QPS 可能是 3。单接口压测场景里两者数值接近，但不能互相替代口径。

二、五类性能测试

类型 目的 时长 关注点
基准测试 单用户跑一遍，记录各项指标作为基线 短（几分钟） 建立对照基线，后续版本与它比
负载测试 逐步加压，找到满足需求前提下的最大负载 一般 1–2 小时（课件口径，非行业标准） 资源消耗随负载的变化曲线
压力测试 高负载下看容错与可恢复能力 短到中 极限在哪、崩了能不能自动恢复
稳定性测试 正常业务负载下长时间运行，看能否稳定 1 天 – 7 天（课件口径，非行业标准） 内存泄漏、连接池耗尽、日志膨胀
并发测试 极短时间内发大量请求，看资源争抢 极短（秒级） 秒杀、抢红包这类瞬时争抢场景

负载 vs 并发：负载测的是「高负载下的资源消耗」，并发测的是「瞬时争抢与并发处理」。一个看长，一个看快。

三、JMeter 元件执行顺序与作用域

JMeter 的元件按「配置 → 前置 → 定时 → 取样 → 后置 → 断言 → 监听」的顺序执行。记这张表：

顺序 元件 作用 压测时要不要开
1 配置元件（Config Element） 提供默认/公共配置，如 HTTP 请求默认值、CSV、变量 要
2 前置处理器（Pre Processors） 取样器执行前预处理请求 按需
3 定时器（Timer） 控制取样器执行前的等待/节奏（思考时间） 要
4 取样器（Sampler） 向服务器发请求的核心元件 要
5 后置处理器（Post Processors） 取样后处理响应，如提取 token 按需
6 断言（Assertions） 校验响应是否符合预期 要
7 监听器（Listener） 收集与展示结果 压测时只留聚合报告

同一作用域内，同类元件按从上到下顺序执行；不同类元件按上表顺序执行。

作用域规则（存量弱项，面试常问）

情况 作用范围
取样器 是核心元件，本身没有作用域
逻辑控制器 只对其子节点中的取样器和逻辑控制器起作用
元件的父节点是取样器 该元件只对其父节点（这一个取样器）起作用
元件的父节点不是取样器 作用于该父节点下的所有后代取样器

一句话记法：挂在取样器下 = 只管它一个；挂在别的节点下 = 管所有后代。

线程组三种

线程组 执行时机 用途
setUp Thread Group 所有脚本之前 预测试操作：登录取 token、准备数据
Thread Group 主体 执行测试用例，可 1 个或多个（并行/串行）
tearDown Thread Group 所有脚本之后 测试后操作：清理数据

四、线程组三个关键参数怎么填

参数 含义 填法建议
线程数（Number of Threads） 虚拟用户数，越多负载越大 按并发估算结果填，先小后大
Ramp-Up（秒） 在多少秒内启动完所有线程 别设 0，模拟用户陆续进场
循环次数（Loop Count） 线程组内元素遍历一遍的次数（每个线程各循环一遍） 可勾选 Infinite，配合调度器用

并发怎么估算（面试必问口径）

三个常用口径，按场景选：

举例（示例数字，仅用于说明算法）：某系统日活 10 万，早高峰 1 小时集中 40% 流量，则峰值 QPS ≈ 100000 × 40% ÷ 3600 ≈ 11；若平均响应时间 0.2 秒，则并发用户数 ≈ 11 × 0.2 ≈ 2~3。关键是报出你的估算依据，而不是直接报一个数字。

Ramp-Up 与循环次数的配合：

  • Ramp-Up 起步取「线程数」秒（即每秒启动一个线程）再按需上调；要做长思考时间场景用定时器补间隔；
  • 要压「瞬时并发」就把 Ramp-Up 设小（但别为 0，避免压测机自己先崩）；
  • 要压「持续负载」就配调度器 Duration，循环次数勾 Infinite。

参数化方式怎么选

方式 数据来源 适用 注意
用户定义的变量（UDV） 脚本内定义 全局固定值，如域名、路径前缀 用 ${name} 引用
用户参数（User Parameters） 脚本内按线程分配 每个虚拟用户不同值 适合模拟不同账号
CSV Data Set Config 外部 CSV 文件 大量批量外部数据 用相对路径、编码选 UTF-8
函数助手 运行时生成 动态唯一值 ${__Random(1,100,)}、${__counter(TRUE,my)}、${__time(yyyy-MM-dd,,)}

五、一个完整场景的设计步骤

八步，照着做就能出一个场景：

  1. 定目标：这次压什么？最大并发、目标响应时间、错误率上限，先写下来。
  2. 选场景：挑核心业务链路，例如「登录 → 查列表 → 查详情」，别一上来压全系统。
  3. 定业务比例：多个接口按真实流量比例分配，例如查列表 70%、查详情 30%。
  4. 建脚本：建线程组 → 加 HTTP 请求（协议/域名/方法/路径/参数）→ 加断言。
  5. 参数化：账号、商品 ID 从 CSV 读；动态值用函数助手 __Random、__counter、__time。
  6. 加关联：登录提取 token，后续请求用 ${token} 带上。
  7. 加思考时间：定时器补上用户操作间隔，别让请求连成一条直线。
  8. 执行与监控：先 GUI 调试单线程，再非 GUI 模式压：

-n 非 GUI、-t 指定脚本、-l 存结果、-e -o 生成 HTML 报告。压测时不要开着「查看结果树」，它很吃内存。

六、聚合报告怎么读

聚合报告（Aggregate Report）是性能结果的核心统计表，每一行是一个取样器。

列 含义 什么值算异常
Label 取样器名称 —
#Samples 样本数（请求数） 数量过少，结论不可信
Average 平均响应时间（ms） 超出目标响应时间
Median 中位数响应时间（ms） 与平均值差距过大，说明有长尾
90% Line / 95% Line / 99% Line 百分位响应时间（ms） 尾延迟超标，用户体感差
Min / Max 最小 / 最大响应时间 Max 特别大说明有抖动
Error % 错误率 明显高于预期（如 > 1%）
Throughput 吞吐量（请求/秒·分·时，JMeter 自动选单位使显示值 ≥ 1.0） 加负载不再上涨，说明到瓶颈
Received / Sent KB/sec 每秒收发数据量 网络带宽接近上限

读报告的顺序：先看错误率 → 再看 P90/P95 → 再看吞吐量是否随负载上涨 → 最后看资源利用率。 吞吐量上不去 + CPU 打满，瓶颈在应用；吞吐量上不去 + CPU 空闲，瓶颈可能在数据库或网络。

持续时间断言（Duration Assertion）用来做性能判定：设置最大允许响应时间（ms），超过即失败。比如设 500ms，压测里凡是超过这个值的请求都算失败——示例阈值，实际按需求定。

瓶颈定位：四层往下查

流程：

调优方向对应四层：应用与数据库改慢 SQL 和索引、减少多余查询、合理用缓存；中间件调连接池与线程池；架构层横向扩容、负载均衡、限流降级。

监控维度固定四项：服务器 CPU、内存、磁盘 IO、网络 IO，外加连接数。压测时必须同步采监控数据，只看客户端报告无法定位瓶颈。

单机压不出更高压力时，再上分布式：控制机（JMeter client / Controller）发起并汇总，负载机（JMeter server / Engine）执行脚本；注意远程模式下负载不均分，线程总数 = 线程数 × 服务器台数，数据文件不随脚本分发，需自行同步到各机。控制机的 jmeter.properties 配 remote_hosts 列出负载机地址，负载机跑 jmeter-server 等调度；各机 JDK 与 JMeter 版本、脚本、依赖文件保持一致。

七、8 个高频问答

# 问题 一句话答案
1 TPS 和 QPS 有什么区别？ TPS 统计事务（一个事务可含多个请求），QPS 统计请求次数。
2 并发用户数怎么定？ 用在线用户数 × 并发率，或峰值 QPS（= 峰值请求数 ÷ 峰值持续时间(秒)）× 平均响应时间(秒)，报出估算依据。
3 响应时间不达标怎么办？ 先看资源与慢查询定位瓶颈，再从 SQL 索引、缓存、连接池、扩容逐层优化。
4 Think Time 有什么作用？ 模拟用户操作间隔，让压力更接近真实，避免请求连成直线。
5 压力测试和负载测试怎么分？ 负载找最大可承受负载，压力看极限与恢复能力。
6 内存泄漏和内存溢出怎么分？ 泄漏是不用了不释放、缓慢增长；溢出是一次申请超上限、直接报错。
7 吞吐量和负载是什么关系？ 负载增加吞吐量先涨后平，平了就是到瓶颈。
8 压测环境怎么选？ 尽量接近生产：同配置、同网络、同数据量，否则结论只能标「示例」。

八、性能测试的诚实边界

本机跑出来的数字，不能当生产结论。写结论时守住三条：

  1. 只报口径与环境：写清「多少线程、Ramp-Up 多少秒、压了多久、什么机器配置、什么网络环境」，再给数字。
  2. 不吹 QPS：本机回环地址的压测结果没有参考价值，只能用来验证口径和脚本正确性。要报就报「本课程示例环境，仅验证脚本链路」。
  3. 小样本不下结论：样本数太少、只压了几分钟，就写「本次仅验证场景可跑通，不构成容量结论」。

对照一下错误答法：「JMeter 100 线程」——数字是编的，追问 Ramp-Up、思考时间、P95、瓶颈在哪就会露馅。诚实说法是：本机跑过，报真实参数，交代本机回环、无参考价值，只用来验证口径。

🗣️ 面试怎么说

  1. 性能指标我按口径讲：响应时间是服务器处理加网络传输，并发用户数是同一时刻在发请求的用户数。
  2. TPS 是每秒事务数、QPS 是每秒查询数；一个事务可能含多个请求，所以两者不能互相替代。
  3. 五类测试：基准建基线、负载找最大负载、压力看极限与恢复、稳定性看长时运行、并发看瞬时争抢。
  4. JMeter 元件执行顺序是配置 → 前置 → 定时 → 取样 → 后置 → 断言 → 监听，同类元件从上到下。
  5. 作用域记一句：挂在取样器下只管它一个，挂在别的节点下管所有后代。
  6. 线程数按并发估算填，Ramp-Up 别设 0，持续负载配调度器 Duration。
  7. 聚合报告先看错误率，再看 P90/P95，再看吞吐量是否随负载上涨，最后看资源。
  8. 本机压测结论只报口径与环境，不吹 QPS，样本不足就写「不构成容量结论」。

✅ 自测 5 题

  1. TPS 和 QPS 有什么区别？ TPS 统计事务，QPS 统计请求次数，一个事务可含多个请求。
  2. JMeter 元件的执行顺序？ 配置 → 前置处理器 → 定时器 → 取样器 → 后置处理器 → 断言 → 监听器。
  3. 并发用户数怎么估算？ 在线用户数 × 并发率，或峰值 QPS × 平均响应时间(秒)（峰值 QPS = 峰值请求数 ÷ 峰值持续时间(秒)），报出依据。
  4. 聚合报告先看哪一列？ 先看 Error %，再看 90% Line / 95% Line，再看 Throughput。
  5. 本机压测结论怎么写才诚实？ 只报口径与环境，说明本机回环无参考价值，样本不足不构成容量结论。
