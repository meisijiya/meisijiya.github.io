一、微服务全景：架构演进、核心组件与链路追踪

1. 分布式和微服务有什么区别？

🗣️ 回答重点

  • 分布式是干活的方式，微服务是组织的架构，这两个词描述的维度完全不同。
  • 分布式把任务分散到多台机器一起干活，节点目标一致，只为更快、更容错、更可扩展，比如 HDFS、TiDB。
  • 微服务是一种架构风格，把大服务拆成可独立部署、松耦合的小服务单元，比如电商拆成商品、用户、订单、库存服务，每个还能用不同技术栈。
  • 微服务通常跑在分布式系统上，但分布式不等于微服务：把单体复制 10 份加 Nginx 是分布式单体，业务逻辑没拆，不算微服务。
  • 反过来所有微服务都堆在一台机器上，虽然不常见，但它仍是微服务，只是不属于分布式。

📈 拔高

  • 分布式系统的核心挑战：网络不可靠（CAP 里互联网多取 AP，金融取 CP）、时钟不同步（Lamport 时钟、向量时钟，Spanner 用原子钟加 GPS）、故障检测（Raft、Paxos 在部分故障下仍达成一致）。
  • 微服务从单体到 SOA 再到微服务演化，Netflix 开源 Eureka、Zuul、Hystrix 后 Spring Cloud 整合才真正火起来。
  • 微服务带来新问题，服务发现、分布式事务（TCC、SAGA、Seata）、链路追踪（Zipkin、Jaeger、SkyWalking）这些原来一个进程内就搞定的事，都得单独设计方案，运维翻倍需要 K8s、Prometheus、ELK。
  • 不是所有项目都适合微服务，团队超 20 人、代码超 50 万行、迭代频繁、耦合严重才值得拆，小团队上微服务纯属自找麻烦。

2. 你是怎么理解微服务的？

🗣️ 回答重点

  • 微服务是把大型应用拆成一堆小服务的架构风格，每个服务只干一件事，独立开发、独立部署、独立扩容。
  • 拿电商举例，单体下订单库存支付用户全揉一个代码库；拆成微服务后支付升级只动支付服务，其他不受影响。
  • 服务间通过 HTTP 或 RPC 通信，订单成功后调库存服务扣减、再调支付服务扣款；每个服务可选不同技术栈。
  • 代价：服务拆多了运维复杂度上升，服务发现、负载均衡、熔断、链路追踪、分布式事务等问题全冒出来。
  • Martin Fowler：把微服务看作单体应用演进的终点，不是起点；团队少、业务未验证时别上微服务。

📈 拔高

  • 单体痛点：代码库膨胀编译启动慢、多人改同一库冲突多、单模块 bug 拖垮全局、扩容必须整体多部署。
  • 微服务拆分原则高内聚低耦合，一个服务只负责一个业务领域；拆太细信号：改动总要一起发布、调用链过长。
  • 数据一致性：尽量避免强一致，用最终一致性；TCC 三阶段、RocketMQ 事务消息、Seata AT 模式。
  • 微服务技术栈：通信 HTTP REST/gRPC/Dubbo；注册发现 Nacos/Consul/Eureka；配置 Nacos Config/Apollo；网关 Gateway/Kong；熔断 Sentinel/Resilience4j；事务 Seata；追踪 SkyWalking/Zipkin/Jaeger。
  • HTTP REST 跨语言友好调试方便但性能差；RPC 性能好，对外用 HTTP，内部高频用 RPC，gRPC 折中。

3. 单体应用、SOA、微服务架构有什么区别？

🗣️ 回答重点

  • 三种架构代表软件从集中到分布、从粗粒度到细粒度的演进。
  • 单体应用：所有功能打包成一个整体部署，一个进程跑所有业务，开发简单部署方便，但改一行要重新发布整个应用，单模块故障拖垮全局。
  • SOA：按业务域拆成多个服务，通过 ESB 企业服务总线通信，强调复用和标准化协议，但 ESB 成单点瓶颈、配置复杂。
  • 微服务：SOA 进化版，去中心化，服务间直接通信不需 ESB，拆分更细，每个服务独立开发部署扩容，团队自治程度更高。

📈 拔高

  • ESB 负责路由、协议转换、消息格式转换、服务编排；所有流量过 ESB 易成性能瓶颈，配置麻烦。
  • 微服务去中心化好处：无单点瓶颈、服务自治、技术栈自由；但分布式事务难、跨服务延迟高、运维复杂。
  • 数据库：单体共享库；SOA 可共享可独立；微服务 Database per Service，每服务独立库，跨服务查询需调服务内存拼。
  • 迁移用绞杀者模式：新功能微服务写，老功能逐步迁移，先拆边界清晰变更频繁的模块，每拆一个稳定一段时间再拆下一个。
  • 云原生趋势：服务网格 Istio/Linkerd 把熔断限流追踪下沉基础设施；Serverless 按调用付费。

4. Spring Cloud 的优缺点有哪些？

🗣️ 回答重点

  • 优势：开箱即用，服务注册、负载均衡、熔断、网关、配置中心、链路追踪全有现成组件，和 Spring Boot 无缝集成，中小团队两周能搭出微服务架构。
  • 缺点：组件多、版本迭代快，Eureka 停更换 Nacos、Hystrix 停更换 Resilience4j、Zuul 不维护换 Gateway，每隔一两年要折腾升级。
  • 另一缺点：HTTP + JSON 调用性能比不过 RPC 框架，高并发场景可能成瓶颈，但大多数业务场景可接受，热点接口可换 gRPC 或 Dubbo。
  • 组件演进：第一代 Eureka/Ribbon/Hystrix/Zuul/Config；Netflix 停更后第二代用 Gateway、Resilience4j、Nacos、LoadBalancer，现在主流 Spring Cloud Alibaba。

📈 拔高

  • Spring Cloud 与 Dubbo 本质区别在通信协议：HTTP vs TCP 长连接 + 自定义协议，Dubbo 性能更强。
  • 对外 API 走 HTTP 网关，内部高频调用走 Dubbo，Dubbo 3.x 支持注册到 Nacos 被 Spring Cloud 服务发现。
  • Eureka 只能做服务发现，Nacos 可同时做服务发现和配置中心，且 AP/CP 可切换，社区更活跃。
  • Resilience4j 比 Hystrix 更轻量，函数式设计、模块可单独使用、配置更友好、性能更好。
  • 真遇性能瓶颈可针对热点接口换 gRPC/Dubbo，Spring Cloud 和 Dubbo 混用没问题。

5. Spring Boot 和 Spring Cloud 之间的区别？

🗣️ 回答重点

  • Spring Boot 简化单个 Spring 应用开发，约定大于配置，几行代码跑起 Web 服务，解决开发效率问题。
  • Spring Cloud 把分布式系统常见问题的解法封装好，包括服务发现、负载均衡、熔断降级、配置中心这些微服务必备能力。
  • Spring Cloud 建立在 Spring Boot 之上，每个微服务本身是 Spring Boot 应用，Spring Cloud 加一层分布式能力，没法单独用 Spring Cloud。
  • 不用 Spring Cloud 只用 Spring Boot 也能做微服务，但得自己集成 Nacos/Consul、Nginx、Sentinel、Apollo 等，集成和排查都费劲。

📈 拔高

  • Spring Boot 自动配置核心是 @EnableAutoConfiguration：2.7 之前的版本扫描 classpath 下 META-INF/spring.factories，2.7 起改用 imports 文件注册，按 @Conditional 条件注解决定是否生效。
  • Spring Cloud 组件按需引入：服务发现 Eureka/Nacos，负载均衡 Ribbon/LoadBalancer，熔断 Hystrix/Resilience4j，网关 Zuul/Gateway，配置 Config/Nacos，追踪 Sleuth/Zipkin。
  • Spring Cloud 和 Dubbo 能混用，对外 API 走 Gateway，内部高频调用走 Dubbo，Dubbo 3.x 支持 Nacos 服务发现。
  • 小规模系统可能只需要 Nacos 做服务发现 + Gateway 做网关就够了。

6. SpringCloud 有哪些核心组件？

🗣️ 回答重点

  • Spring Cloud 核心组件围绕微服务的几类问题展开，包括服务注册发现、负载均衡、配置中心、服务调用、熔断限流、网关、消息驱动、链路追踪、监控与管理。
  • 注册发现有 Eureka、Consul、Nacos；负载均衡 Ribbon 已停更，现在是 Spring Cloud LoadBalancer。
  • 服务调用 Feign 停更，改 OpenFeign 声明式 HTTP 客户端；熔断限流 Hystrix 停更，用 Resilience4j 或 Sentinel。
  • 网关 Zuul 停更，用 Spring Cloud Gateway；配置中心可用 Spring Cloud Config、Apollo、Nacos。
  • 很多组件已经停更，公司现在多用 Spring Cloud Alibaba 那套：Nacos 管注册加配置、Sentinel 熔断限流、Gateway 网关、OpenFeign 做调用。

📈 拔高

  • 消息驱动是 Spring Cloud Stream，整合 Kafka、RabbitMQ；链路追踪 Spring Cloud Sleuth 整合 Zipkin、Jaeger；监控用 Spring Boot Admin 和 Spring Cloud Bus。
  • 用真实调用链记最牢：请求进 Gateway 做认证，Sentinel 限流，LoadBalancer 选实例，OpenFeign 调服务，配置变化 Bus 广播刷新，Sleuth 加 Zipkin 打 trace。
  • Spring Cloud 是规范和抽象，Netflix 那套（Eureka、Ribbon、Hystrix、Zuul）从 2018 起陆续停更，Alibaba 用 Nacos、Sentinel、Seata，社区更活跃。
  • Sentinel 用信号量和滑动窗口隔离，不需要额外线程池，资源占用小；Hystrix 用线程池隔离，切换有开销，线程池多了浪费。

7. Spring Cloud 由什么组成？

🗣️ 回答重点

  • Spring Cloud 本质是一套微服务工具集，基于 Spring Boot 之上，把分布式系统里最常见的问题都封装成开箱即用的组件。
  • 核心围绕四大块展开：服务注册与发现、负载均衡与远程调用、服务容错、服务治理。
  • 注册发现这块 Eureka 最经典，每个服务启动向 Eureka Server 注册地址，调用方去查有哪些实例；Consul 也能干这活，还顺带带配置管理和健康检查。
  • 负载均衡早期用 Ribbon 按轮询、随机等策略挑实例，现在由 Spring Cloud LoadBalancer 接手，Feign 更上一层，用注解定义接口就能发 HTTP 调用，底层自动整合这套负载均衡。
  • 容错靠 Hystrix 做断路器，下游挂了或响应太慢就熔断走降级返回兜底数据，防止一个服务拖垮整条链路。
  • 治理这块 Spring Cloud Config 做配置中心，网关现在用 Spring Cloud Gateway 统一路由鉴权限流，Sleuth 配合 Zipkin 靠 traceId 串起整条链路。

📈 拔高

  • 早期组件多来自 Netflix OSS（Eureka、Ribbon、Hystrix、Zuul），2018 年起陆续进入维护模式，新项目建议直接上 Spring Cloud Alibaba。
  • Spring Cloud Alibaba 核心是 Nacos 做注册加配置中心、Sentinel 做流控熔断降级、Seata 做分布式事务，阿里内部几十万台机器在跑，稳定性经过双十一验证。
  • Gateway 基于 WebFlux 和 Netty 异步非阻塞，吞吐量约为 Zuul 1.x 的 1.5 到 2 倍；Zuul 1.x 基于 Servlet 同步阻塞，并发高时线程池容易打满。
  • 一次典型调用是请求先到 Gateway 按路由转发，服务 A 问 Nacos 要服务 B 的实例，LoadBalancer 挑一个发 HTTP 调用，超时由 Sentinel 熔断，链路靠 Sleuth 的 traceId 串到 Zipkin 查看。

8. 为什么需要在微服务中使用链路追踪？Spring Cloud 可以选择哪些微服务链路追踪方案？

🗣️ 回答重点

  • 微服务系统一次请求可能跨越十几个服务，服务之间日志没关联，排查问题像噩梦，链路追踪能可视化追踪调用链快速定位问题。
  • 核心思想：统一 TraceId 串联整个调用链，每个服务内部用 SpanId 标志服务内调用，追踪信息经 HTTP Header 传递。
  • 常用方案：Spring Cloud Sleuth + Zipkin（经典组合，Sleuth 生成 TraceId/SpanId，Zipkin 收集展示）。
  • Jaeger：CNCF 托管，适合大规模系统；SkyWalking：Apache APM 平台，零侵入 Java Agent 接入，支持监控告警拓扑；OpenTelemetry：云原生推荐标准，跨平台跨语言。
  • Spring Boot 3.x 起推荐 Micrometer Tracing 替代 Sleuth，引入 micrometer-tracing-bridge-brave 即可对接 Zipkin。

📈 拔高

  • Span 有父子关系，一个 Trace 包含多个 Span 形成调用链树；Sleuth 默认用 X-B3-TraceId、X-B3-SpanId 头部传递。
  • 消息队列场景需把 TraceId 塞到消息属性/消息体，Sleuth 对 Kafka、RabbitMQ 有自动支持，自研队列需自行实现。
  • 生产环境需采样，常见固定比例、限速、自适应采样；Sleuth 默认 10%，调试可设 1.0，上线调低。
  • 开启链路追踪约增加 1-3ms 延迟，QPS 高的系统吞吐量下降 2-5%，主要开销在异步数据上报。
  • SkyWalking 用 Java Agent 零侵入，老项目改造成本低；小团队 Spring 全家桶用 Sleuth+Zipkin 够用。

9. 你们的服务是怎么做日志收集的？

🗣️ 回答重点

  • 我们用的是 ELK 那套方案：Logstash（或 Filebeat）从微服务集群采集日志，处理完发送到 Elasticsearch，ES 负责存储和检索，Kibana 负责可视化分析。
  • 三个组件各司其职：Elasticsearch 是分布式搜索引擎，专门存储和索引日志数据，支持全文检索和聚合查询；Logstash 是日志采集和预处理工具，能从文件、消息队列、网络等渠道抓日志并做过滤、格式转换；Kibana 是可视化前端，提供图表和仪表盘。
  • 日志收集流程：各微服务通过日志框架输出日志到文件或标准输出，采集组件从各服务器采集日志，经过过滤和格式化处理后发送到 Elasticsearch 存储，Kibana 连接 ES 提供可视化查询和分析界面。

📈 拔高

  • 微服务下一个请求可能经过 10 多个服务、每个服务又有多个实例，日志散落在几十台机器上；集中式日志收集把所有服务的日志汇聚到一处，一条 traceId 能串起整个调用链的日志，排查问题效率提升几十倍。
  • 高并发场景下，采集组件和 ES 之间一般会加一层 Kafka 做缓冲，削峰填谷，避免日志洪峰打垮 ES 集群。
  • 主流技术栈对比：ELK 功能全、搜索能力强但 Logstash 重；EFK 云原生友好、性能好，Kubernetes 日志收集基本都用 Fluentd 或 Fluent Bit；PLG 存储成本低 5-10 倍，搜索能力弱，适合日志量大但搜索需求简单的场景。
  • 采集组件选型：Filebeat 轻量（Go 写，单机 10-20MB 内存），只采集和传输；Logstash 功能最强但 JVM 应用、单机至少 1-2GB；Fluentd 插件生态丰富，Fluent Bit 是其轻量版（C 写）。
  • 生产优化：对 DEBUG 日志做采样（只采集 10%），热数据放 SSD 保留 7 天、冷数据归档保留 30-90 天，按天或按服务建索引、单分片控制在 30-50GB，采集组件和 ES 之间加 Kafka 缓冲。

10. 说一下你对于 DDD 的了解？

🗣️ 回答重点

  • DDD（领域驱动设计）是一套应对复杂业务系统的软件设计方法论，核心思想是先想清楚业务（领域），再写代码（技术），让代码结构和业务逻辑保持高度一致。
  • 回答 DDD 一定要分两个层面：战略设计（宏观）解决业务边界问题，核心是限界上下文（Bounded Context）和统一语言（Ubiquitous Language）；战术设计（微观）解决代码怎么写，核心是聚合（Aggregate）、实体（Entity）、值对象（Value Object）。
  • DDD 提倡充血模型，把业务逻辑写在对象内部，而不是只写 Get/Set 的贫血对象把逻辑全堆在 Service 层。
  • DDD 不是银弹：业务简单（如简单 CRUD）用 MVC 就够了，强行上 DDD 是过度设计；DDD 适合业务逻辑极其复杂、长期迭代的大型系统。

📈 拔高

  • 限界上下文与微服务：一个限界上下文通常对应一个微服务，有自己独立的数据库和领域模型；电商的”用户”在不同上下文含义不同（用户中心关注注册信息/密码/实名认证，订单系统只关心用户 ID/收货地址，营销系统关注用户等级/消费偏好），每个上下文维护自己需要的用户信息，通过防腐层转换，不共享数据库。
  • 贫血 vs 充血：贫血模型 POJO 只有 get/set，业务逻辑全在 Service 层，对象只是数据载体、业务逻辑分散、维护难；充血模型对象自己管理行为，如修改订单价格 changePrice 方法里可包含”价格不能为负数”、”记录改价日志”等业务逻辑内聚。
  • 实体看 ID（有唯一标识，属性全变还是它，如人），值对象看属性（无 ID，属性一样就是同一个东西，不可变，如颜色 RGB 都是 (255,0,0) 就是红色）；地址（省市区街道）通常为值对象。
  • 聚合根像家长：聚合里有很多对象（订单、订单明细、收货地址），外部对象想访问订单明细必须通过订单（家长）操作，目的是保证数据一致性。
  • DDD 四层架构：用户接口层（Controller、DTO）、应用层（ApplicationService）、领域层（Entity、ValueObject、DomainService、Repository 接口）、基础设施层（Repository 实现、MQ、缓存）；领域层只依赖自己，Repository 接口定义在领域层、实现在基础设施层，即依赖倒置，领域层可脱离 Spring、MyBatis 独立测试。
  • CQRS 把读写分离，命令模型负责写、查询模型负责读；事件溯源不存最终状态而存所有变化事件，回放事件还原任意时刻状态，天然支持审计和回溯（银行流水、Git 版本控制）。
  • DDD 构建模块：实体、值对象、聚合（聚合根）、领域服务（无状态、业务逻辑无法归属于实体/值对象时）、工厂（创建复杂对象和聚合）、仓储（封装对聚合根的持久化操作）。
  • 常见坑：聚合设计过大导致每次操作加载一大堆数据、性能差，原则是聚合尽量小、聚合之间用 ID 引用而非对象引用；团队习惯了 MVC，写着写着又把逻辑堆到 Service 层，需持续 Code Review 纠正。
  • DDD 与微服务不是强绑定：DDD 是设计方法论、微服务是部署架构，单体应用一样可以用 DDD 组织代码，限界上下文可以只是代码模块；微服务拆分边界可参考限界上下文但非强绑定。

二、分布式事务：Seata 的模式、原理与回滚

11. 什么情况下需要使用分布式事务，有哪些方案？

🗣️ 回答重点

  • 跨多个数据库或跨不同服务时就要上分布式事务，因为本地事务只能管一个库的原子性，订单和库存不在一个库就保证不了要么全成功要么全回滚。
  • 分布式事务本质是由多段本地事务跨设备拼起来的，中间还要经历复杂网络，所以比本地事务复杂得多。
  • 方案分两大类：强一致性追求严格 ACID 但性能可能差，最终一致性允许中间状态不一致但最终会收敛，性能更好，适合高并发。
  • 强一致经典是 2PC/XA，有个协调者先问大家准备好了没，统一提交或回滚，但同步阻塞、协调者单点故障风险高。
  • 柔性方案像 TCC 把事务拆成 Try 预留、Confirm 提交、Cancel 回滚三步，性能好、锁粒度小，但侵入业务、开发量大。
  • 最终一致可以靠本地消息表或事务消息（如 RocketMQ 半消息），异步高吞吐，但得处理消息幂等和顺序。

📈 拔高

  • 2PC 的协调者叫 Transaction Manager，参与者是数据库这种资源管理器，准备阶段除了提交啥都干了，所以资源被锁住；协调者挂了全员卡死，且网络分区会导致部分提交的数据不一致。
  • 3PC 在 2PC 基础上加了 CanCommit 预询问阶段，参与者也引入超时能自动提交或回滚，但多一次通讯开销，实际几乎找不到落地实现。
  • Seata 的 AT 模式其实是自动化的 2PC，不用手写三个方法，它代理数据源自动记录 Undo Log，事务失败就按日志把数据改回去。
  • 事务消息靠半消息机制保证原子性：先发半消息对消费者不可见，本地事务提交后消息才可见，broker 长时间没收到提交会反查生产者。

12. 什么是分布式事务的防悬挂，空回滚?

🗣️ 回答重点

  • 空回滚和防悬挂是 TCC 分布式事务必须处理的两个异常，不处理好就会数据不一致；TCC 拆成 Try 预留资源、Confirm 提交、Cancel 回滚三步。
  • 空回滚是 Try 因网络没到达，协调者超时以为失败发起 Cancel，Cancel 先到了但 Try 从没执行过，回滚了个寂寞。
  • 悬挂是空回滚的后遗症：Cancel 先执行完，迟到的 Try 后来才到并成功，预留的资源再也没人释放，因为 Cancel 不会再执行、Confirm 也不会来。
  • 防悬挂就是要阻止这种迟到的 Try 执行，不让它再冻结资源。

📈 拔高

  • 正确解法核心是一张事务记录表追踪每笔分支状态：Cancel 先查记录，没有说明是空回滚，插一条 ROLLBACKED 状态直接返回成功；Try 执行前也查，发现已有 ROLLBACKED 就拒绝，把悬挂挡住。
  • Seata 用 tcc_fence_log 表维护三态异常，1.5 之后给 @TwoPhaseBusinessAction 加 useTCCFence = true 就自动处理：
  • AT 模式更省事：框架执行业务 SQL 前申请全局锁，Cancel 先执行会释放锁并删 undo_log，迟到 Try 发现 undo_log 没了就拒绝；但它只支持关系型数据库且表要有主键。
  • 空回滚必须留痕而不能直接返回成功，否则后面的 Try 查不到记录会照常执行，资源就永远挂着；另外 Cancel 比 Confirm 更重要，它失败会导致资源一直锁着。

13. 什么是 Seata？

🗣️ 回答重点

  • Seata 是阿里开源的分布式事务解决方案，专门解决微服务场景下跨服务、跨数据库的数据一致性问题。
  • 分布式事务的难点：一个业务操作可能涉及多个服务、多个数据库，每个服务本地事务能保证 ACID，但整体业务的原子性没人管；比如下单扣库存，订单服务写成功了、库存服务挂了，数据就乱了。
  • Seata 有三个核心角色：TC 事务协调者（独立部署的服务端，维护全局事务和分支事务状态，协调提交或回滚，像总指挥）；TM 事务管理者（嵌入业务应用，负责开启全局事务、提交或回滚，加了 @GlobalTransactional 注解的方法，TM 在方法开始时向 TC 注册全局事务）；RM 资源管理器（嵌入业务应用，管理分支事务，向 TC 注册分支、报告状态、执行 TC 下发的提交或回滚指令，每个参与分布式事务的数据源都有一个 RM）。
  • 整个流程：TM 开启全局事务，业务代码调用各个微服务，每个服务的 RM 注册分支事务并执行本地 SQL，所有分支执行完毕后，TM 通知 TC 全局提交或回滚，TC 再通知各个 RM 执行相应操作。

📈 拔高

  • Seata 提供 4 种事务模式：AT（自动生成回滚 SQL，侵入性低只需注解，性能高，适用大多数场景）、TCC（业务代码实现 try/confirm/cancel，侵入性高，性能最高，适用高并发强一致性）、Saga（正向服务 + 补偿服务，侵入性中，性能高，适用长事务跨公司）、XA（数据库原生 XA 协议，侵入性低，性能低，适用传统数据库迁移）。
  • AT 模式工作原理（两阶段提交变种，关键是 undo_log）：一阶段业务 SQL 执行前，RM 解析 SQL 拿到表名、主键、修改前后的数据镜像存到 undo_log 表，然后执行业务 SQL，本地事务直接提交（不像 XA 一直持有锁）；二阶段提交时 TC 通知各 RM 删除 undo_log（异步）；二阶段回滚时 TC 通知各 RM 回滚，RM 根据 undo_log 数据镜像生成反向 SQL（UPDATE 还原旧值、INSERT 变 DELETE、DELETE 变 INSERT）。
  • 全局锁与写隔离：执行业务 SQL 前 RM 向 TC 申请全局锁（粒度”表名 + 主键”），另一个全局事务想修改同一条数据必须等锁释放；本地事务不受全局锁影响，所以 Seata 默认只能保证写隔离，读隔离需用 @GlobalLock + SELECT FOR UPDATE。
  • AT 回滚脏写校验：回滚前校验当前数据和 undo_log 里的 afterImage 是否一致，不一致说明被其他事务改过，回滚失败需人工介入；因此参与分布式事务的数据不能被本地事务绕过去改，要么都走全局事务，要么用 @GlobalLock 注解。
  • TCC 空回滚与悬挂：空回滚是 Try 没执行 Cancel 先到，Cancel 要识别直接返回成功；悬挂是 Cancel 执行完了 Try 才到，Try 不能再执行。解决办法是加一张事务控制表记录每个分支状态，Seata 的 TCC 模式内置该机制，用 BusinessActionContext 传递状态。
  • TC 挂了：进行中的全局事务会超时，TM 等不到响应抛异常；TC 恢复后从存储加载未完成事务继续处理。
  • Seata 与 Spring @Transactional：不冲突，是包含关系；@GlobalTransactional 管全局事务，@Transactional 管本地事务；加了 @GlobalTransactional 的方法里各服务方法仍需加 @Transactional 管本地事务，本地事务是全局事务的一个分支。

14. Seata 支持哪些模式的分布式事务？

🗣️ 回答重点

  • Seata 支持四种事务模式：AT、TCC、Saga、XA。
  • AT 模式，通过代理数据源自动管理事务：Seata 在业务 SQL 执行前后自动记录数据快照到 undo_log 表，提交时直接提交本地事务，回滚时用快照生成反向 SQL 还原数据。业务侵入最小，加个 @GlobalTransactional 注解就行。
  • TCC 模式，是两阶段提交的业务层实现：把一个操作拆成 Try 预留资源、Confirm 确认提交、Cancel 回滚释放三步，每一步都要业务代码自己实现。侵入性大，但性能最好，适合高并发场景。
  • Saga 模式，是长事务解决方案：把全局事务拆成多个有序的小事务，每个事务配一个补偿操作。某个事务失败了，按相反顺序依次执行补偿操作回滚之前的变更。适合流程长、参与方多的业务。
  • XA 模式，基于数据库原生的 XA 协议：一阶段执行 SQL 后 XA prepare，资源一直锁着，等 TC 统一下发 commit 或 rollback。强一致性，但性能最差，适合对一致性要求极高的场景。

📈 拔高

  • 模式对比：AT 侵入性低、性能高、最终一致性、适用大部分业务；TCC 侵入性高、性能最高、最终一致性、适用高并发交易；Saga 侵入性中、性能高、最终一致性、适用长事务跨系统；XA 侵入性低、性能低、强一致性、适用传统迁移强一致。
  • AT 模式：Seata 在内部做了对数据库操作的代理层，使用 Seata 自带的数据源代理 DataSourceProxy，在这层代理中加入插入回滚 undo_log 日志、检查全局锁等逻辑；全局事务由 TM（管理生命周期、标识开始和结束）、TC（管理全局事务状态和分支提交/回滚）、RM（管理本地事务资源和数据回滚、执行具体数据库操作、向 TC 注册分支事务）三部分协同完成。
  • AT 写隔离：一阶段本地事务提交前需先拿到全局锁，拿不到不能提交本地事务；拿全局锁的尝试被限制在一定范围内，超出范围放弃并回滚本地事务释放本地锁。整个过程全局锁在事务结束前一直被持有，所以不会发生脏写。
  • TCC：侵入式的分布式事务解决方案，业务系统自行实现 Try/Confirm/Cancel 三个操作；空回滚与悬挂问题通过事务控制表记录分支状态解决，Seata 的 TCC 模式内置该机制，用 BusinessActionContext 传递状态。
  • Saga：基于状态机引擎实现，通过状态图定义服务调用流程并生成 json 状态语言定义文件，节点可配置补偿节点；异常时状态引擎反向执行已成功节点对应的补偿节点回滚。
  • XA：利用事务资源对 XA 协议的支持管理分支事务；编程模型与 AT 完全一致，切换只需改数据源代理（DataSourceProxy → DataSourceProxyXA）。
  • AT 与 XA 本质区别：锁的持有时间，XA 一阶段 prepare 后数据库行锁一直持有直到二阶段 commit/rollback，AT 一阶段本地事务就提交、数据库锁释放，只持有 Seata 全局锁；所以 AT 并发性能好很多，但只能最终一致性，XA 是强一致性。
  • 生产选型：大部分业务用 AT；核心交易链路（支付、转账）对性能要求极高的用 TCC；需要强一致性又不想改代码（老系统迁移）用 XA；跨系统、长流程用 Saga。

15. 了解 Seata 的实现原理吗？

🗣️ 回答重点

  • Seata 靠 TC、TM、RM 三大组件协调全局事务：TC 管事务生命周期，TM 定义事务边界，RM 管本地资源和分支事务。
  • 业务方法上加 @GlobalTransactional 注解，TM 就向 TC 创建全局事务，TC 返回一个 XID。
  • 业务执行时 RM 向 TC 注册分支事务，同时记录数据快照生成回滚日志，本地事务先提交。
  • 业务结束后 TM 向 TC 发全局提交或回滚请求，TC 通知各 RM 执行，最后记录状态并释放全局锁。
  • Seata 有 AT、TCC、SAGA、XA 四种模式，AT 最具代表性，靠 undo_log 自动回滚。

📈 拔高

  • AT 模式在本地事务提交前用 undo_log 记数据快照实现原子回滚；TCC 拆成 Try、Confirm、Cancel 三步由开发者手写；SAGA 是长事务模式，每个小事务配补偿操作；XA 基于两阶段提交协议保证强一致但性能较低。
  • 全局锁是行级的，粒度细到表名加主键值，TC 用一张内存表维护锁，拿不到锁默认重试 30 次、每次间隔 10ms，高并发下锁竞争比较激烈。
  • 分支注册信息包括 XID、资源 ID、分支事务类型和数据锁定信息，TC 记录后把注册成功结果返回给 RM。
  • TC 支持集群部署和数据持久化，状态写进 MySQL，重启后能恢复；生产环境一般部署 3 个以上 TC 节点，用 Nacos 或 ZooKeeper 做服务发现和主备切换。
  • 事务结束后 Seata 会清理 undo_log 表数据，内置定时清理任务默认每隔 86400 秒清理一次超过 7 天的日志。

16. Seata 的事务回滚是怎么实现的？

🗣️ 回答重点

  • Seata 有四种事务模式，回滚策略完全不一样：AT 靠 undo_log，TCC 靠 Cancel，SAGA 靠补偿操作，XA 靠 ROLLBACK 指令。
  • AT 模式下每次 INSERT、UPDATE、DELETE 之前，RM 都会把操作前的快照存进 undo_log，这步在本地事务提交前完成。
  • 只要有一个分支失败或者 TM 发起全局回滚，TC 就通知所有相关 RM，RM 从 undo_log 读原始状态把数据还原。
  • TCC 的回滚就是调业务自己写的 Cancel 方法，撤销 Try 阶段预留的资源，通常是 Try 的逆操作。
  • SAGA 按相反顺序调用已完成子事务的补偿方法；XA 第一阶段准备好后不提交，TC 决定回滚就通知各 RM 执行 ROLLBACK。

📈 拔高

  • undo_log 里存 beforeImage 和 afterImage 两份快照，回滚前先拿当前数据跟 afterImage 比对，一致才用 beforeImage 还原，不一致就是脏写，Seata 抛异常告警、需要人工介入。
  • 回滚 SQL 按操作生成：UPDATE 生成把字段还原成 beforeImage 的 UPDATE，INSERT 生成 DELETE 删掉新行，DELETE 生成 INSERT 插回去。
  • undo_log 表核心字段有 branch_id、xid、log_status、rollback_info，rollback_info 用 JSON 存 tableName、beforeImage、afterImage，里面含完整行数据和主键值。
  • TCC 有两个经典坑：空回滚要在 Try 里记执行记录、Cancel 先查；悬挂要在 Cancel 里记回滚记录、Try 先查，防 Cancel 先于 Try 执行后资源永远预留着。
  • XA 第一阶段 prepare 后数据库连接和本地事务要一直持有，连接池容易耗尽；MySQL 5.7 之前 XA 实现有 bug，重启后未提交的 XA 事务会丢失。

三、配置中心：Spring Cloud Config 与 Nacos

17. 什么是配置中心？有哪些常见的配置中心？

🗣️ 回答重点

  • 配置中心把散落在各个服务里的配置文件统一收拢到一个地方管理，支持动态下发和热更新。
  • 没有它时改个数据库连接串或超时时间，得挨个服务改配置再重启，几十个服务能折腾一下午。
  • 有了它，在控制台改完配置点一下发布，几秒内所有服务自动拉到最新配置，压根不用重启，对线上太关键了。
  • 核心流程是后台改配置、存储并记录版本、实例通过长连接或长轮询监听、变更时推送或返回新配置、实例热加载无需重启。
  • 常见的配置中心有 Spring Cloud Config、Apollo、Nacos、Consul、Etcd、Zookeeper 这几个。

📈 拔高

  • Spring Cloud Config 配置存在 Git 仓库，版本管理天然支持，但没有原生推送能力，需要配合 Spring Cloud Bus 才能实现动态刷新。
  • Apollo 是携程开源，功能最全，支持灰度发布、权限管理、配置审计，国内用得很多，但部署复杂、依赖 MySQL 数据库。
  • Nacos 是阿里开源，注册中心和配置中心二合一，轻量好用，2.x 版本支持 gRPC 长连接推送，是目前国内微服务最主流的选择。
  • Consul 跟 K8s 生态整合好、基于 KV 键值对；Etcd 基于 gRPC 的 Watch 机制存 K8s 元数据；Zookeeper 用 Watcher 机制但本不是为配置中心设计，功能简陋。
  • 动态更新靠两种机制：长连接是毫秒级（Etcd、Nacos 2.x 用 gRPC Stream），长轮询是客户端发请求被服务端 hold 住（Apollo、Nacos 1.x、Consul，最差等一个超时周期）。

18. 你知道 Nacos 配置中心的实现原理吗？

🗣️ 回答重点

  • Nacos 配置中心原理可以从配置存储、推送机制、本地缓存三个核心部分来讲。
  • 客户端启动和 Nacos Server 建立 gRPC 长连接，注册监听器订阅指定的 Data ID，Server 从 MySQL 读配置返回，客户端缓存到本地内存和磁盘。
  • 运维在控制台改配置写入 MySQL，Server 检测到变更就通过 gRPC 长连接推给所有订阅客户端，客户端更新缓存并触发应用的配置刷新回调。
  • 配置按 Namespace、Group、Data ID 三级组织：Namespace 隔离环境，Group 区分业务模块，Data ID 就是具体的配置文件标识。
  • 客户端会把配置存一份到本地磁盘，默认路径是 ~/nacos/config，Server 挂了照样读本地缓存运行，恢复后自动重连同步。

📈 拔高

  • 1.x 用 HTTP 长轮询，客户端每 30 秒发一个请求，Server hold 住，有变更立即返回，最差要等 30 秒才感知，轮询对 Server 连接压力大。
  • 2.x 改成 gRPC 长连接，基于 HTTP/2，配置一改 Server 直接推过来延迟毫秒级，且多路复用让注册中心和配置中心的通信共用一个连接。
  • 配置数据本身存在 MySQL，所有节点共用一个库，不需要通过 Raft 同步配置内容；Raft 只同步集群元数据（哪个客户端连到哪个节点、各节点健康状态），节点可无状态横向扩展。
  • 客户端监听靠 gRPC 双向流，Server 维护订阅关系表，变更时按关系找到客户端通过 Stream 推送，客户端拉新配置后回调 Listener 的 receiveConfigInfo；热更新可用 @RefreshScope 或 @ConfigurationProperties。

19. Spring Cloud Config 是什么？

🗣️ 回答重点

  • Spring Cloud Config 是一套分布式配置中心解决方案，分为 Config Server 和 Config Client 两部分。
  • Config Server 是集中式的配置服务器，所有微服务的配置文件都往这里存，底层默认用 Git 管理配置内容，配置的版本控制天然就有。
  • Config Client 跑在每个微服务里，负责从 Config Server 拉取配置；服务启动时根据应用名和环境标识请求对应配置，拿到后加载到 Spring Environment 里用。
  • 整体流程是：Git 仓库存储各环境配置文件，Config Server 连接 Git 并暴露 HTTP 接口，Client 启动时带上 application name 和 profile 请求，Server 从 Git 拉取对应配置返回，Client 加载到 Spring Environment。

📈 拔高

  • 配置中心的动机：微服务下几十上百个服务各有配置文件，配置散落本地时改个数据库连接串要跑到几十个服务里挨个改、重新打包部署，运维成本极高；配置中心把配置从代码里剥离出来集中管理。

四、服务注册与发现：Eureka、Consul、Nacos、Zookeeper

20. 为什么需要服务注册发现？

🗣️ 回答重点

  • 分布式系统里服务数量多、变化快，服务 IP 天天在变，靠人工维护调用关系根本搞不定。
  • 服务注册与发现用注册中心自动管理：服务启动主动注册自身信息，消费者直接问注册中心拿地址列表。
  • 流程：提供者注册 → 注册中心存储元数据 → 消费者订阅 → 注册中心推送列表 → 消费者负载均衡选实例调用。
  • 服务上下线时注册中心主动推送通知，消费者本地缓存自动更新，扩容缩容都不用改配置，实现真正的弹性伸缩。
  • 主流注册中心有 Nacos、Eureka、Consul、Zookeeper，Nacos 国内最主流，能同时做注册中心和配置中心。

📈 拔高

  • Eureka 的老 2.x 预览分支在 2018 年 10 月就宣告停止，2022 年 12 月 Netflix 又发布了新的 2.x 系列，Eureka 1.x 仍在维护发版，新项目一般改用 Nacos 或 Consul；Nacos 默认 AP 模式，Zookeeper 是 CP 模式。
  • 健康检查：心跳检测（如每 5 秒一次，连续 3 次未收到剔除）或主动探测（如 Consul 访问 /health）；Nacos 支持临时实例（心跳）与持久实例（主动探测）。
  • 注册中心挂了服务仍可调用，因为消费者本地缓存服务列表，新服务上线/扩缩容时才感知不到变化。
  • AP 优先可用性、网络分区时数据可能不一致但发现可用；CP 优先一致性、网络分区时可能拒绝服务；注册中心场景多选 AP。
  • 实例规模达几万时注册中心会成瓶颈，可通过分集群、服务端缓存、调大心跳间隔、本地缓存兜底来缓解。

21. Spring Cloud 有哪些注册中心？

🗣️ 回答重点

  • Spring Cloud 常用注册中心有 5 个：Eureka、Consul、Zookeeper、Nacos、Etcd，按 CAP 分 AP 和 CP 两类。
  • Eureka 是 Netflix 开源的 AP 模式，有自我保护机制，Spring Cloud 原生支持集成最简单，但新项目基本不推荐。
  • Consul 是 HashiCorp 出的 CP 模式，走 Raft 协议，自带 KV 存储、健康检查和多数据中心。
  • Zookeeper 也是 CP，用 ZAB 协议，Kafka、Dubbo 早期拿它当注册中心，但太重了、本质不是为服务发现设计的。
  • Nacos 是阿里开源的，AP 和 CP 可切换、默认 AP，服务发现加配置中心一个组件干两件事，国内用得非常多。
  • Etcd 是 CoreOS 开发的 CP 模式 KV 存储，也走 Raft，Kubernetes 就拿它当底层存储。

📈 拔高

  • CAP 里网络分区是现实所以 P 必选：CP 宁可拒绝服务也保证数据一致，AP 宁可返回旧数据也保证可用；注册中心短暂不一致顶多流量打到刚下线节点重试一次，所以很多团队倾向 AP。
  • 选型场景：多机房用 Consul 的原生多数据中心最省心；Spring Cloud Alibaba 或 Dubbo 直接选 Nacos；跑在 K8s 上先用原生 Service 机制。
  • Spring Cloud 2020 版本之后官方推荐 Spring Cloud LoadBalancer 加任意注册中心的组合，Eureka 1.x 只剩 bug fix，Netflix 已取消 2.0 开源计划。
  • Nacos 2.x 通信协议从 HTTP 长轮询改成 gRPC，性能提升明显，服务数量上万建议直接上 2.x；临时实例走 AP，持久化实例走 CP。
  • Zookeeper 的 session 机制让注册和心跳强绑定、watcher 一次触发就失效、选主期间集群不可用，Dubbo 3.x 默认已推荐 Nacos。

22. 什么是 Eureka?

🗣️ 回答重点

  • Eureka 是 Netflix 开源的服务注册与发现组件，属于 Spring Cloud Netflix 套件，名字来自古希腊语”我找到了”。
  • 架构分两部分：Eureka Server 是注册中心维护服务实例注册表，Eureka Client 集成在各微服务里，启动注册、运行期发心跳、停止注销。
  • 流程是提供者把 IP、端口、服务名注册到 Server，消费者拉取服务列表缓存到本地，默认每 30 秒拉一次增量更新。
  • 提供者每 30 秒发一次心跳，Server 连续 90 秒没收到就把实例踢掉；消费者再配合 Spring Cloud LoadBalancer 做客户端负载均衡。
  • 用起来很简单：Server 端加 @EnableEurekaServer，Client 端加 @EnableEurekaClient 或者 @EnableDiscoveryClient。

📈 拔高

  • 服务注册本质上是个 RESTful 请求，Eureka Client 启动时往 Server 发一个 POST 请求，元数据里的核心字段长这样：

集群搭建思路是让每个 Server 互相注册，客户端配多个地址，挂了自动切下一个：

  • Eureka 选 CAP 里的 AP，牺牲强一致性换高可用，设计理念是注册中心挂了比返回过期数据更可怕；Client 有本地缓存，Server 全挂已启动的服务还能继续调用。
  • Server 端有多级缓存，ReadOnly 缓存加 ReadWrite 缓存，客户端拉取优先读 ReadOnly，30 秒才同步一次，所以注册信息更新有延迟。
  • 多个 Eureka Server 之间是 Peer to Peer 对等关系，没有主从，数据通过异步复制同步；自我保护按每分钟实际心跳与期望心跳的比例算，低于 85% 就触发，之后不再剔除实例、控制台红警，稳定内网可考虑 eureka.server.enable-self-preservation=false 关掉。
  • Netflix 2018 年取消 Eureka 2.0 开源计划，Spring Cloud 2020.0 起 Netflix 组件进维护模式，Ribbon、Hystrix、Zuul 分别被 Spring Cloud LoadBalancer、Resilience4j、Spring Cloud Gateway 替代。

23. Eureka 的实现原理说一下？

🗣️ 回答重点

  • Eureka 的原理可以拆成三个核心机制：服务注册发现、心跳续约、服务剔除。
  • 实例启动后 Eureka Client 向 Server 发 POST 请求，把服务名、IP、端口、健康检查地址这些元数据存进内存里的注册表 registry。
  • Client 每 30 秒发一次 PUT 心跳，Server 更新 Lease 的 lastUpdateTimestamp；连续 90 秒没收到就标过期，后台任务每 60 秒扫一次删掉。
  • 客户端启动时全量拉取，之后每 30 秒增量拉取只拿变化部分，增量失败会自动降级为全量拉取。
  • Nacos、Consul 也是注册、心跳、剔除这一套，差别在细节实现和 CAP 选型。

📈 拔高

  • 注册表是两层 ConcurrentHashMap：服务名 → 实例 ID → Lease，按服务名查实例 O(1)；Lease 封装 holder、evictionTimestamp、registrationTimestamp、lastUpdateTimestamp 和默认 90 秒的 duration。
  • Server 有三级缓存，客户端读 readOnlyCacheMap，它 30 秒才从 readWriteCacheMap 同步一次，新实例最坏 30 秒才被感知；把配置里的 use-read-only-response-cache 设成 false 可以关掉它换实时性。
  • 自我保护的期望心跳数 = 实例总数 × (60 / 心跳间隔) × 续约阈值，100 个实例就是 100 × 2 × 0.85 = 170 次/分钟，低于它就触发，剔除定时任务停跑、控制台红警告、新注册查询照常。
  • 集群是 Peer to Peer 对等架构，注册经 PeerEurekaNodes 异步复制到其他节点，请求带 isReplication=true 防循环同步；增量拉取靠 recentlyChangedQueue 队列存最近 3 分钟变更，合并后比对 hashcode 不一致就全量拉取。
  • 注册表纯内存，重启靠集群同步和客户端心跳重新注册；主动注销发 DELETE 请求，kill -9 只能等剔除任务，消费者本地缓存 30 秒刷新，所以服务间调用必须有重试机制。

24. Spring Cloud 如何实现服务注册？

🗣️ 回答重点

  • Spring Cloud 自己不具备注册能力，只定义了一套服务注册规范，真正干活的是底层的注册中心客户端 SDK。
  • 项目启动时它监听 Web 服务器启动事件，再把当前服务的名称、IP、端口这些信息推送到注册中心服务端。
  • 以 Nacos 为例，引入 spring-cloud-starter-alibaba-nacos-discovery 依赖后服务就能自动注册。
  • 配置文件指定 nacos discovery 的 server-addr，比如 192.168.1.100:8848，启动后服务就自动注册，开发者无需写一行注册代码。
  • 整个流程分三步：Spring Boot 启动发 WebServerInitializedEvent，AbstractAutoServiceRegistration 监听到后调 ServiceRegistry 的 register 方法，注册中心客户端把实例信息推上去。

📈 拔高

  • 注册规范就是三个接口：Registration 封装实例数据（Nacos 实现是 NacosRegistration），ServiceRegistry 负责 register，AutoServiceRegistration 监听启动事件触发注册。
  • 切换注册中心成本极低，Eureka、Zookeeper、Consul、Nacos 都有对应实现类，只换依赖改配置，业务代码一行不用动。
  • 要等 Web 服务器完全就绪才注册，避免服务没准备好就被调用；生产环境还能结合健康检查，只有状态健康才对外提供服务。
  • 不想让某服务自动注册就加 spring.cloud.nacos.discovery.register-enabled=false，服务仍可从注册中心拉取其他实例列表，典型场景是网关。
  • 正常关闭时 Spring Cloud 会调 ServiceRegistry.deregister 主动注销；Nacos 临时实例 15 秒没心跳标记不健康、30 秒没心跳自动剔除。

25. Consul 是什么？

🗣️ 回答重点

  • Consul 是 HashiCorp 用 Go 语言开发的一款开源服务注册中心，同时也能当配置中心用。
  • 它提供服务注册与发现、健康检查、KV 存储、多数据中心支持，还有 DNS 和 HTTP API 接口，自带一个可视化控制台。
  • 明显优势是 Raft 协议保证数据一致性、健康检查机制完善、原生支持跨数据中心 WAN 集群、提供跨平台图形化界面。
  • 部署架构分两层：每个服务节点部署一个 Client Agent 收集本地服务信息并转发给 Server，Server 节点组成集群选 Leader 保证一致。
  • 同一数据中心内用 LAN Gossip 协议同步状态，跨数据中心用 WAN Gossip 协议通信。

📈 拔高

  • 服务实例启动把服务名、IP、端口推给 Consul Server，其他服务可用 HTTP API 查 /v1/catalog/service/{service_name}，也可用 DNS 查 {service_name}.service.consul。
  • 健康检查支持 HTTP、TCP、Script、TTL 等方式，实例被标记为不健康就立刻从列表摘除，调用方拿不到它，全程自动无需人工介入。
  • 内置分布式 KV 存储可放配置、分布式锁、元数据，支持 Watch 机制；但单纯做配置中心时 Nacos、Apollo 功能更强大，KV 更适合存轻量元数据。
  • Consul 原生支持多数据中心，集群间走 WAN Gossip，比如查 {service_name}.service.shanghai.consul 就能跨机房发现，特别适合异地多活。
  • 1.2 版本加入 Connect 服务网格，在每个服务旁起 Sidecar 代理做自动 mTLS 加密和基于 Intention 的访问控制，比 Istio 轻量且不依赖 Kubernetes。

26. Eureka、Zookeeper、Nacos、Consul 的区别？

🗣️ 回答重点

  • 这四个组件在一致性模型、核心功能、使用场景上都有明显差异。
  • 一致性模型上 Eureka 是 AP，Zookeeper 和 Consul 是 CP，Nacos 既支持 AP 也支持 CP。
  • Eureka 专注注册发现，是 Spring Cloud Netflix 生态核心；Zookeeper 本质是分布式协调器，注册发现只是顺带能力。
  • Nacos 把注册中心和配置中心合二为一；Consul 除注册发现外还提供健康检查、KV 存储、多数据中心，功能最全面。
  • 健康检查上 Eureka 靠客户端心跳，Zookeeper 用临时节点，Nacos 支持心跳加服务端探测，Consul 支持 HTTP、TCP、gRPC、Script、TTL 五种。

📈 拔高

  • Eureka 选可用性，网络分区时各节点独立工作，还有自我保护机制：大量心跳丢失也不立刻剔除，宁可返回过期数据也不返回空。
  • Nacos 临时实例走 Distro 协议的 AP 模型、服务挂了自动剔除；永久实例走 Raft 的 CP 模型、需手动删除，多数场景用临时实例。
  • 性能上 Eureka 不建议单集群超 5000 实例；Zookeeper 写走 Leader 是瓶颈、节点建议 3 到 7 个；Nacos 2.0 换 gRPC 长连接支持百万级；Consul 杀手锏是多数据中心。
  • 选型上 Java 团队选 Nacos，大数据生态 Kafka、HBase 用 Zookeeper，跨机房或云原生用 Consul；Eureka 因 Netflix 停止维护新项目不推荐。
  • 客户端都缓存服务列表到本地，注册中心挂了只要本地有缓存服务仍能互相调用，只是感知不到上下线变化，所以至少部署 3 个节点保证高可用。

27. Nacos 中的 Namespace 是什么？

🗣️ 回答重点

  • Namespace 是 Nacos 提供的虚拟隔离区域，用来把服务和配置做逻辑分组。
  • 不同 Namespace 之间完全隔离，一个 Namespace 里的服务或配置压根影响不到另一个。
  • 最典型的用法是环境隔离，开发、测试、生产三套环境分别建 dev、test、prod，开发改配置不会搞挂生产。
  • 多租户系统里给每个租户分独立 Namespace，能保证租户之间数据完全隔离；一个 Nacos 实例跑多个项目也能用它隔开防冲突。
  • Nacos 用 Namespace、Group、Data ID 三层结构管配置和服务，Namespace 是最顶层的隔离单位。

📈 拔高

  • 配置时填的是 Namespace 的 ID 不是名称，控制台创建时会自动生成 UUID 作 ID，填名称不生效。
  • 默认有个 public Namespace，不显式指定参数就注册到 public 下，多个项目混在一起极易出问题，正式项目都该显式指定。
  • 跨 Namespace 调用不走服务发现，只能硬编码 IP 或域名，正常不建议跨调，真要调可走网关统一入口。

五、服务调用：负载均衡、Feign 与 RPC

28. 为什么需要负载均衡？

🗣️ 回答重点

  • 核心目的是把请求流量分摊到多台服务器上，让系统扛住更大并发，同时避免单台挂掉导致整个服务不可用。
  • 像双十一订单服务几十万 QPS 打进来，单台撑死也就几千，得靠负载均衡把流量打散到几百台机器。
  • 某台服务器宕机后，负载均衡器会自动把流量切到其他健康机器，用户根本感知不到。
  • 没有负载均衡时所有请求都打同一台，压力山大且一宕机全部用户受影响；有它之后每台只承担部分流量。
  • 纵向扩展是换更牛的机器，硬件性能提升有天花板、越往上成本越离谱；横向扩展是加普通机器，理论上没有上限，机器便宜、随时能加，但用户的请求怎么知道发给哪台机器，这正是负载均衡要解决的核心问题。

📈 拔高

  • 单机到瓶颈有两条路：纵向换更牛的机器（硬件有天花板、越往上越贵），横向加普通机器（廉价、随时加、理论无上限）。
  • 它带来的好处是高可用、高性能、弹性伸缩、资源利用率高，让每台机器都发挥作用而不是有的忙死有的闲着。
  • 没有它会单点故障、性能瓶颈，而且 DNS 改解析不支持健康检查，机器挂了照样往上打流量，扩展困难。

29. 负载均衡的实现方式有哪些？

🗣️ 回答重点

  • 主要有三种：软件负载均衡、硬件负载均衡、DNS 负载均衡。
  • 软件是在普通服务器上装负载均衡软件，像 Nginx、HAProxy、LVS，成本低又灵活，绝大多数公司都在用。
  • 硬件是买专用设备，比如 F5、A10，性能猛但价格贵，一台几十万起步，一般只有大厂核心业务才舍得上。
  • DNS 是通过 DNS 解析把同一个域名解析成不同的 IP，主要做地理级别的就近访问，北京用户访问北京机房、上海用户访问上海机房。
  • 层级上 DNS 在最外层做地理分流，硬件在机房入口承接单机房流量，软件在最内层把流量分到具体服务器实例。

📈 拔高

  • 软件负载均衡按 OSI 模型分四层和七层：四层只看 IP 和端口转发效率高，七层能解析 HTTP 头、URL 做精细路由。
  • LVS 只做四层，Nginx 和 HAProxy 四七层都能干，生产常见搭配是 LVS 前置四层转发、Nginx 后置七层路由。
  • DNS 负载均衡好处是简单省事、用户就近延迟低，坏处是缓存时间长、机房出问题切换慢，而且不知道后端是否健康。

30. 负载均衡算法有哪些？

🗣️ 回答重点

  • 轮询：按顺序把请求依次分给后端服务器，适合处理能力相当的场景，但性能差异大时分到一样多显然不合理。
  • 加权轮询：在轮询基础上给每台设权重，权重越高被选中概率越大，Nginx 的 upstream 默认就支持 weight 配置。
  • 随机：像掷骰子一样等概率随机挑一台，缺点是不考虑服务器性能差异。
  • 加权随机：随机的升级版，根据权重调整被选中的概率，减少高性能服务器的闲置。
  • 最少连接：选择当前连接数最少的服务器处理请求，适合请求处理时间差异大的场景。
  • 哈希：根据客户端 IP 或 URL 算哈希值，把同一特征的请求路由到同一台，Redis Cluster 和 Nginx 的 ip_hash 都这样。

📈 拔高

  • 普通哈希增删节点会让大量请求重路由，缓存失效率能到 75% 直接打爆数据库，一致性哈希把节点映射到 0 到 2^32 的环、顺时针找节点解决。
  • 一致性哈希有虚拟节点概念，把一台物理机映射成多个虚拟节点分散到环上，让数据分布更均匀，Dubbo 默认 160 个。
  • 服务端负载均衡把均衡器布在服务端前面（Nginx、LVS、F5），客户端无感知但可能成单点；客户端负载均衡把逻辑放客户端（Ribbon、LoadBalancer），无代理损耗但逻辑复杂。

31. HTTP 与 RPC 之间的区别？

🗣️ 回答重点

  • HTTP 是应用层协议，定义网络通信的数据格式和交互方式；RPC 是远程调用的编程范式，强调让调用远程服务像调用本地方法一样简单。
  • 很多 RPC 框架底层用 HTTP 传输：gRPC 底层走 HTTP/2，Dubbo 3.0 也支持 Triple 协议，底层同样基于 HTTP/2。
  • HTTP 面向资源，用 URL 标识资源，用 GET/POST/PUT/DELETE 操作资源，数据格式一般是 JSON 或 XML，人眼可读，RESTful API 就是典型 HTTP 风格。
  • RPC 面向方法调用，客户端拿到代理对象直接调方法名传参数，跟调本地方法没区别；数据格式通常是二进制的 Protobuf 或 Hessian，序列化效率高但人眼看不懂。
  • 对外暴露给第三方的接口用 HTTP，通用性好不挑语言不挑框架；内部微服务之间通信用 RPC，调用体验好、性能高，调用方不受控制就用 HTTP，都是自己的服务就用 RPC。
  • HTTP 接口每次调用要手动拼 URL、设 Header、处理返回值，写起来啰嗦；RPC 框架封装了连接池、序列化、负载均衡、超时重试这些脏活累活。

📈 拔高

  • IDL 是接口定义语言，如 Protocol Buffers 的 .proto 文件、Thrift IDL、OpenAPI 等。
  • HTTP/1.1 存在队头阻塞，单连接只能串行处理请求，高并发场景下需要建立大量连接，10 万 QPS 场景下开销很可观。
  • gRPC 基于 HTTP/2，支持双向流、多路复用，用 Protobuf 序列化，传输效率很高；K8s 内部组件通信、Istio 数据面都用 gRPC，跨多语言首选。
  • Dubbo 国内 Java 微服务常用，跟 Spring 深度集成，注册中心支持 Nacos、Zookeeper，3.0 推出 Triple 协议兼容 gRPC 可跨语言；Thrift 跨语言支持 20 多种，大数据组件内部通信多用。
  • Protobuf 比 JSON 快在两点：体积小（字段编号而非字段名，同样数据比 JSON 小 3 到 10 倍），解析快（按偏移量读字段而非字符串匹配）；代价是可读性差，调试看不懂。
  • Spring Cloud OpenFeign 底层走 HTTP/1.1、JSON 序列化，Spring 生态开发体验好；Dubbo 性能更好、服务治理能力强但学习曲线陡，两者可混用。

  • 传统方式用 HttpClient 或 RestTemplate 调接口，得自己组装 URL、拼参数、处理响应，代码又臭又长。用 HttpClient 调一个接口就得写这么多：

  • 调用流程：应用代码调接口方法 → 动态代理拦截 → 解析注解构建 HTTP 请求 → 通过负载均衡选择服务实例 → 发送请求接收响应 → 反序列化响应体返回结果。
  • Feign 跟 Spring Cloud 生态深度集成，配合 Nacos、Eureka 做服务发现，配合 Spring Cloud LoadBalancer 做负载均衡，配合 Sentinel 或 Hystrix 做熔断降级。

33. Feign 是如何实现负载均衡的？

🗣️ 回答重点

  • Feign 本身只是个 HTTP 客户端，不具备负载均衡能力，它的负载均衡是靠底层集成的负载均衡组件来实现的。
  • Spring Cloud 体系下早期用 Netflix 的 Ribbon，它在 2020 版之后停止维护并被移除，官方推出 Spring Cloud LoadBalancer 替代，现在新项目基本都用 LoadBalancer。
  • 整个调用流程：Feign 发起请求时先把请求交给负载均衡组件 → 组件从注册中心拉取目标服务的实例列表 → 根据策略选出一个实例把真实地址返回给 Feign → Feign 再用该地址发起真正的 HTTP 请求。
  • 代码层面只要引入了 spring-cloud-starter-loadbalancer 依赖，Feign 就会自动集成负载均衡能力，不需要额外配置，@FeignClient(name = "user-service") 调用时底层会自动从注册中心获取 user-service 的所有实例并选一个调用。

📈 拔高

  • Ribbon 通过 ServerList 接口获取实例，注册中心实现该接口即可，Nacos 的实现类是 NacosServerList，Eureka 是 DiscoveryEnabledNIWSServerList；Spring Cloud LoadBalancer 换成 ServiceInstanceListSupplier，思路一样。
  • Ribbon 内置策略：RoundRobinRule 轮询、RandomRule 随机、WeightedResponseTimeRule 权重响应时间、BestAvailableRule 最少并发、AvailabilityFilteringRule 可用过滤、ZoneAvoidanceRule 区域优先；LoadBalancer 默认只提供轮询和随机，复杂策略需自己实现 ReactorServiceInstanceLoadBalancer。
  • Ribbon 被弃用有几个原因，2018 年进入维护模式 Netflix 不再开发；代码结构老旧与响应式编程模型不兼容；Spring Cloud 想减少对 Netflix 组件依赖。
  • 缓存与更新：负载均衡组件本地缓存实例列表定期刷新，Ribbon 默认 30 秒（ribbon.ServerListRefreshInterval），LoadBalancer 默认 35 秒（spring.cloud.loadbalancer.cache.ttl）；实例刚下线时客户端可能仍发请求导致失败，配合重试或缩短刷新间隔。
  • 重试：Feign 原生有 Retryer 机制，但 Spring Cloud OpenFeign 默认禁用重试，可配置开启或配合 Spring Retry、Resilience4j；重试配合负载均衡每次可选不同实例，Ribbon 时代用 MaxAutoRetries 和 MaxAutoRetriesNextServer 控制同实例与换实例重试次数。
  • 指定实例不走负载均衡的方式：直接用 IP 调用、Nacos 元数据路由给实例打标签并在代码指定标签、自定义负载均衡策略做过滤，灰度发布、蓝绿部署常用。
  • LoadBalancer 基于响应式编程模型，WebFlux 场景性能更好，Servlet 场景下两者差别不大；Nacos 支持推送模式，实例变化时主动通知客户端，实时性更好。

35. Feign 和 OpenFeign 的区别？

🗣️ 回答重点

  • 两者都是简化服务之间 HTTP 调用的工具，Feign 是 Netflix 开源的声明式 REST 客户端，OpenFeign 是 Spring Cloud 在 Feign 基础上的封装。
  • Feign 的目标是让微服务调用像调本地方法：建一个接口，用注解声明方法和路径，它自动发 HTTP 请求、收响应并转成方法返回值。
  • OpenFeign 整合了 Spring Cloud 特性，靠 Spring Boot 自动配置，用 @FeignClient 和 @EnableFeignClients 就能创建客户端。
  • OpenFeign 支持 @GetMapping、@PostMapping 这些熟悉的 Spring MVC 注解，不用学 Feign 原生的 @RequestLine。
  • OpenFeign 能和服务发现组件集成实现客户端负载均衡，还能简单配置接入 Hystrix 做熔断，提高容错性。

📈 拔高

  • 原始 Feign 能脱离 Spring Cloud 体系用：接口加 @RequestLine("GET /order/{orderId}")，再手动 Feign.builder().target(OrderApiClient.class, "http://localhost:8088") 创建对象。
  • Feign 底层是 JDK 动态代理：构建时解析方法上的注解和参数，调用时把入参组装成 HTTP 请求发出，再按响应内容类型转换成返回值。
  • 核心组件可通过 Feign.builder() 替换：Contract 负责解析注解，Spring Cloud 自己实现了 Contract 才能识别 Spring MVC 注解；Encoder/Decoder 做序列化和反序列化，默认只支持 String 和字节数组，Spring 补齐了任意类型。
  • Client 是真正发 HTTP 请求的组件，默认用 JDK 的 HttpURLConnection，基于负载均衡的实现用来整合 Ribbon；RequestInterceptor 在发请求前拦截修改，比如加鉴权 token。
  • Spring Cloud 重写了很多组件：Retryer 没用默认最大重试 5 次的实现，Spring Cloud 下默认不重试；Hystrix 和 Sentinel 都实现了自己的 InvocationHandler，在 HTTP 调用前后做限流降级。

36. Feign 和 Dubbo 的区别？

🗣️ 回答重点

  • Feign 是声明式的 HTTP 客户端，通过接口注解发起 HTTP/REST 请求，底层走 HTTP 协议。
  • Dubbo 是阿里开源的 RPC 框架，默认用自定义的 Dubbo 协议做二进制序列化通信，性能比 HTTP 高不少。
  • 通信层面 Feign 报文是文本格式，跨语言友好但体积大、解析慢；Dubbo 报文是二进制，体积小、解析快，但跨语言需要额外适配。
  • 场景上 Feign 更适合对外开放 API 和异构系统调用，Spring Cloud 体系里服务间调用基本都用它；Dubbo 更适合内部高并发、低延迟的调用。
  • 用法上 Feign 定义接口加 @FeignClient 注解就行，Dubbo 定义服务接口后用 @DubboReference 注入远程服务代理。

📈 拔高

  • 核心差异一表看完：定位上 Feign 是 HTTP 客户端、Dubbo 是 RPC 框架；协议上 HTTP/HTTPS 对 Dubbo 协议、Triple、HTTP 等；序列化上 JSON 为主对 Hessian2、Protobuf 等二进制；服务治理上 Feign 依赖 Spring Cloud 组件、Dubbo 自带完整治理；性能中等对高；跨语言天然支持对需要协议适配。
  • 两条路线之争：HTTP/REST 简单通用，Spring Cloud 走这条，Feign 由 Netflix 最早开源、后来 Spring Cloud 团队接手改名 OpenFeign；RPC 换取性能，Dubbo 协议基于 TCP 长连接 + 二进制序列化，报文体积能小 50% 以上。
  • Dubbo 3.0 引入 Triple 协议，兼容 gRPC、基于 HTTP/2，Java 写的 Dubbo 服务能被 Go、Python、Node.js 直接调用，不用再搞协议转换网关。
  • 性能差异的底层原因在于序列化，一个对象序列化成 JSON 可能几百字节、Hessian2 只要几十字节，Dubbo 一个 TCP 长连接能跑几万个请求，实测同样业务逻辑 Dubbo 的 QPS 能比 Feign 高 2-3 倍。
  • 治理能力上 Dubbo 的注册发现、负载均衡、熔断降级、流量管控、链路追踪开箱即用；Feign 要靠生态补齐，负载均衡用 Spring Cloud LoadBalancer、熔断用 Resilience4j 或 Sentinel、链路追踪用 Sleuth + Zipkin，灵活但集成成本高。

六、稳定性：熔断、降级、限流与服务雪崩

37. 什么是熔断器？为什么需要熔断器？

🗣️ 回答重点

  • 熔断器是微服务架构中用来防止服务雪崩的保护机制，思路跟家里电路的保险丝一样：电流过大就自动断开，保护整个电路不被烧毁。
  • 微服务之间的调用是链式的，下游服务挂了或响应特别慢时，请求会堆在上游线程池里，最终整条链路全崩；熔断器在下游出问题时快速切断调用链，让请求直接失败返回，不拖垮整个系统。
  • 熔断器有三个状态：关闭状态正常放行所有请求，打开状态拒绝所有请求直接返回失败，半开状态放行少量请求试探，成功则关闭熔断器，失败则继续打开。
  • 光设超时解决不了根本问题，高并发下线程池照样被打满；熔断器的核心价值在于快速失败，连等待都不等，立刻返回失败腾出线程资源。
  • 限流是入口处的保护，防止流量太大把自己搞死；熔断是出口处的保护，防止下游故障把自己拖死；降级是功能层面的取舍，非核心功能可以暂时牺牲。

📈 拔高

  • 状态转换逻辑：关闭 -> 打开为失败率超过阈值，比如 10 秒内 50% 请求失败；打开 -> 半开为熔断一段时间后自动进入，比如 5 秒后；半开 -> 关闭为试探请求成功；半开 -> 打开为试探请求失败。
  • 触发策略有三种：慢调用比例，统计时间窗口内的慢调用比例超过阈值就熔断，比如响应时间超过 1 秒算慢调用、比例超过 50% 就熔断；异常比例，异常请求比例超过阈值就熔断，比如 10 秒内 50% 请求抛异常就熔断；异常数，异常请求绝对数量超过阈值就熔断，比如 1 分钟内 100 个请求失败就熔断。
  • 熔断 vs 降级 vs 限流：熔断触发时机是下游服务故障、目的防止故障扩散、典型场景订单服务调库存服务库存挂了就熔断；降级触发时机是系统压力过大或服务不可用、目的保核心功能、典型场景双十一关闭商品评价功能保下单链路；限流触发时机是请求量超过系统承载能力、目的保护自身不被打垮、典型场景接口 QPS 限制 1000 超过直接拒绝。
  • 主流框架对比：Hystrix Netflix 已停止维护，早期微服务标配，基于线程池隔离，资源消耗大；Sentinel 阿里开源活跃维护，轻量级，基于滑动窗口统计，支持集群流控；Resilience4j 活跃维护，专为 Java 8 设计，函数式风格，轻量级。现在新项目基本不用 Hystrix，国内用 Sentinel 的多，国外用 Resilience4j 的多，Spring Cloud 官方也推荐用 Resilience4j 替代 Hystrix。
  • Sentinel 用滑动窗口统计请求成功率，默认把 1 秒分成 2 个 500ms 的小窗口，每个小窗口独立统计请求数和失败数，统计更平滑，避免固定窗口清零导致熔断触发不了。
  • Sentinel degrade 配置示例：resource 为 getOrder，grade 为 1，count 为 0.5，timeWindow 为 10，minRequestAmount 为 5，statIntervalMs 为 1000，slowRatioThreshold 为 0.5。
  • 半开状态放行请求数：Hystrix 默认放 1 个，Sentinel 默认放 1 个，Resilience4j 默认 10 个，可通过 permittedNumberOfCallsInHalfOpenState 配置；minRequestAmount 是触发熔断的最小请求数阈值，不是半开状态放行的请求数。
  • 线程池隔离与信号量隔离：线程池隔离给每个下游服务分配独立线程池，调用在独立线程池里执行，调用方主线程不被阻塞，隔离性好但资源消耗大；信号量隔离用计数器限制并发数，调用还在主线程里执行，轻量但隔离性差。Hystrix 默认线程池隔离，Sentinel 默认信号量隔离，高并发场景下信号量隔离性能更好。
  • 熔断规则需持久化，Sentinel 支持把规则持久化到 Nacos、Apollo、ZooKeeper 等配置中心，应用启动时拉取规则，还可以通过控制台动态推送规则；单机统计数据一般不持久化，重启后重新统计。
  • 熔断触发时走降级逻辑返回兜底数据，比如商品详情接口熔断了返回缓存里的旧数据或简化版商品信息；Sentinel 用 @SentinelResource 注解的 fallback 属性指定降级方法，Resilience4j 用 @CircuitBreaker 注解的 fallbackMethod 属性。

38. 什么是 Hystrix？

🗣️ 回答重点

  • Hystrix 是 Netflix 开源的一个熔断器框架，在微服务架构里用来防止服务雪崩，核心思路是通过隔离、熔断、降级，让下游服务出问题时不至于把整个系统拖垮。
  • Hystrix 干了三件事：熔断，下游服务连续失败达到阈值后直接断开调用不再傻等；降级，调用失败或熔断触发时返回兜底数据；隔离，给每个下游服务分配独立线程池，互不影响。
  • Hystrix 在 2018 年已经进入维护模式，Netflix 不再开发新功能；现在新项目一般用 Sentinel 或者 Resilience4j 替代。

📈 拔高

  • 熔断示例：10 秒内有超过 50% 的请求失败，Hystrix 触发熔断，后续请求直接返回降级结果，等过一段时间再试探下游是否恢复。
  • 降级示例：推荐服务挂了，返回热门商品列表兜底。
  • 隔离示例：A 服务响应慢不会占用 B 服务的线程资源。
  • 代码示例：@HystrixCommand(fallbackMethod = “getOrderFallback”, commandProperties = {@HystrixProperty(name = “circuitBreaker.requestVolumeThreshold”, value = “10”), @HystrixProperty(name = “circuitBreaker.errorThresholdPercentage”, value = “50”), @HystrixProperty(name = “circuitBreaker.sleepWindowInMilliseconds”, value = “5000”)})，方法 getOrder 调用 http://order-service/order/{id}，降级方法 getOrderFallback 返回 new Order(id, “服务暂时不可用”)。配置意思是 10 个请求里有 50% 失败就熔断，熔断 5 秒后进入半开状态试探。
  • 执行流程：请求进来先检查熔断器状态；熔断器打开直接走降级；关闭则检查线程池/信号量是否有余量；没余量走降级；有余量执行实际调用；调用成功返回结果并统计成功；调用失败/超时走降级并统计失败；失败率超过阈值熔断器打开。
  • Hystrix 熔断器三种状态：Closed 关闭状态所有请求正常发往目标服务；Open 打开状态阻断所有请求直接返回降级结果；Half-Open 半开状态部分请求试探，成功率达到阈值则关闭恢复正常，失败则继续打开。
  • 关键配置项：circuitBreaker.requestVolumeThreshold 熔断器生效最小请求数，默认 20，统计窗口内请求数不到 20 即使失败率 100% 也不会熔断；circuitBreaker.errorThresholdPercentage 失败率阈值，默认 50%；circuitBreaker.sleepWindowInMilliseconds 休眠时间，默认 5000ms，休眠结束后进入半开状态。
  • 线程池隔离：每个 HystrixCommand 可配置独立线程池，A 服务响应慢占满自己的线程池不影响 B 服务。配置示例 groupKey OrderGroup、commandKey GetOrder、threadPoolKey OrderThreadPool，threadPoolProperties coreSize 10、maxQueueSize 100、queueSizeRejectionThreshold 50。coreSize 核心线程数默认 10 决定最大并发数；maxQueueSize 队列大小默认 -1 表示用 SynchronousQueue 不排队，设成正数用 LinkedBlockingQueue；queueSizeRejectionThreshold 队列拒绝阈值，队列里请求数超过该值开始拒绝新请求，可动态修改，maxQueueSize 不能。线程池隔离代价是每个请求都要切换线程有性能损耗，对本身就很快的调用如访问本地缓存用信号量隔离更合适，配置 execution.isolation.strategy 为 SEMAPHORE、execution.isolation.semaphore.maxConcurrentRequests 为 100。
  • Hystrix Dashboard 监控：实时查看每个 HystrixCommand 的请求成功/失败/超时数、熔断器状态、线程池使用情况、P99/P95 延迟。需先暴露监控端点 /hystrix.stream，集群环境用 Turbine 聚合多个实例监控数据；Hystrix 里包一段普通调用就行，比如：

然后启动 Hystrix Dashboard 应用，输入 http://your-service:port/hystrix.stream 就能看到实时监控数据。

  • 框架对比：Hystrix 已停止开发、线程池/信号量隔离、滑动窗口、不支持限流、Hystrix Dashboard、不支持规则持久化、线程池开销大；Sentinel 阿里活跃维护、信号量隔离、滑动窗口、支持功能丰富限流、Sentinel Dashboard、支持多种数据源持久化、轻量性能好；Resilience4j 社区活跃维护、信号量/线程池隔离、基于环形缓冲区、支持限流、无内置控制台需集成、需自行实现持久化、轻量性能好。国内用 Sentinel 有阿里背书控制台强大规则可动态推送；国外或不想依赖阿里生态用 Resilience4j，Spring Cloud 官方推荐。老项目 Hystrix 迁移到 Sentinel 可用 sentinel-annotation-aspectj 依赖，注解改一下即可，熔断规则需重新配置。
  • 线程池满了时：maxQueueSize 为 -1 用 SynchronousQueue 不排队，线程池满直接拒绝走降级；设成正数用 LinkedBlockingQueue 会排队，但 queueSizeRejectionThreshold 超过也会拒绝；一般不建议设太大队列。
  • Hystrix 超时与 Ribbon 超时：两个独立但要协调好，Hystrix 超时是整体超时包括排队等待、网络传输、服务处理全部时间，Ribbon 超时是单次 HTTP 请求超时；一般建议 Hystrix 超时大于 Ribbon 超时乘以重试次数。
  • Netflix 不维护 Hystrix 有几个原因，架构理念变了，转向自适应并发限制和无状态重试，觉得基于阈值配置的熔断方式太死板需要人工调参，内部用 concurrency-limits；线程池隔离性能开销大高并发场景不太划算；但设计思想仍有价值，Sentinel、Resilience4j 都借鉴了。
  • 异步调用：用 HystrixObservableCommand 或返回 Future；execute 同步，queue 返回 Future 可异步获取；HystrixObservableCommand 支持响应式编程返回 Observable；异步场景注意 RequestContext 在子线程里拿不到，需 HystrixRequestContext 初始化后才能访问。

39. 什么是服务雪崩？

🗣️ 回答重点

  • 服务雪崩就是微服务架构里一个服务挂了，把依赖它的其他服务也拖下水，像多米诺骨牌一样一个接一个倒，最后整个系统大面积瘫痪。
  • 典型场景：服务 A 调用服务 B，服务 B 调用服务 C；服务 C 响应超时，服务 B 线程池被等待中的请求占满，接着服务 A 调用服务 B 也开始超时，整条链路全崩。
  • 雪崩的根本原因有两个：调用链太长，微服务拆得越细依赖越复杂，底层服务出问题影响面沿调用链向上扩散；重试机制帮倒忙，下游快挂了还疯狂重试等于火上浇油，流量瞬间翻倍把服务彻底打死。

📈 拔高

  • 防范手段核心思路是快速失败、及时止损，别让故障扩散出去。
  • 熔断器思路跟家里的保险丝一样，电流太大就自动断开保护整个电路；Hystrix、Resilience4j、Sentinel 都提供熔断能力；工作原理统计一段时间内的请求失败率，比如 10 秒内失败率超过 50% 就跳闸，后续请求直接返回失败不再真正调用下游服务，过一段时间放几个请求试探，成功了就恢复正常调用。
  • Resilience4j 熔断器配置示例：CircuitBreakerConfig.custom().failureRateThreshold(50).waitDurationInOpenState(Duration.ofSeconds(30)).slidingWindowSize(10).build()，失败率阈值 50%，熔断后等待 30 秒，统计窗口大小 10。
  • 服务降级是服务出问题的时候给用户一个兜底方案，比如商品详情页推荐服务挂了就展示默认热销榜单，库存服务挂了就显示”库存查询中”让用户稍后再试；降级方案要提前设计好，核心交易链路一般不能降级，边缘功能完全可以。
  • 限流控制流量入口防止流量太大把服务压垮，常用算法有令牌桶和漏桶，比如限制每秒最多处理 1000 个请求超出直接拒绝；漏桶匀速处理请求能削峰填谷但没法应对突发流量，令牌桶匀速放令牌请求拿令牌拿不到就拒绝，桶里能攒一定数量令牌所以能应对短时间突发流量，实际用令牌桶更多。
  • 隔离把不同的调用方或接口隔离开，用独立的线程池或者信号量，一个接口出问题不会把其他接口资源耗光，比如订单服务调用库存、支付、物流三个下游分别用三个线程池，库存服务再慢也不影响支付。
  • 实际案例：某电商大促期间库存服务因数据库慢查询响应从 50ms 涨到 5 秒，订单服务 200 个线程很快占满，新下单请求全部排队，网关层开始超时，整个交易链路瘫痪 20 分钟损失上千万；事后复盘如果库存服务有熔断在响应变慢时直接熔断返回降级结果，订单服务就不会被拖死，至少能保证用户下单成功，库存扣减走异步补偿。
  • 熔断器三种状态转换：正常关闭状态请求正常通过；失败率达到阈值如 50% 切换到打开状态所有请求直接失败不再调用下游；打开状态持续一段时间后进入半开状态放几个请求试探，试探成功切回关闭，失败继续保持打开。
  • 线程池隔离与信号量隔离：线程池隔离用独立线程池处理请求调用方线程提交任务后返回不被阻塞，隔离彻底但线程切换有开销配置麻烦；信号量隔离用计数器控制并发数调用方线程直接执行只是限制同时进行的请求数量，开销小但隔离没那么彻底下游慢的话调用方线程还是被占着；一般来说调用外部服务用线程池隔离更安全，内部服务调用用信号量就够了。

40. 什么是服务降级？

🗣️ 回答重点

  • 服务降级就是系统扛不住的时候，主动砍掉一些非核心功能，保住最重要的业务；说白了就是丢卒保车，宁可让用户看不到推荐商品，也不能让他下不了单。
  • 拿电商场景举例，用户访问商品详情页正常流程要调用商品服务、库存服务、推荐服务、评价服务；推荐服务挂了如果没有降级策略整个页面可能都打不开，有了降级就返回默认热销榜单，其他功能照常用，用户感知不到有问题。
  • 降级的触发时机主要有三种：服务调用超时或失败，比如支付服务响应超过 3 秒直接返回”支付繁忙，请稍后重试”；系统负载过高，CPU 打到 90%、内存快爆了主动把推荐、评价关掉把资源留给下单和支付；下游服务不可用，库存服务挂了直接返回上次缓存的库存数据或显示”库存查询中”。

📈 拔高

  • Fallback 降级回调是最常用方式，给每个远程调用配一个 fallback 方法调用失败就执行 fallback 返回兜底数据；Resilience4j 示例：@CircuitBreaker(name = “inventoryService”, fallbackMethod = “getInventoryFallback”) 的 getInventory 调用 inventoryClient.getInventory，降级方法 getInventoryFallback 返回 cacheService.getCachedInventory(productId)。
  • 缓存兜底：查询类接口可以用缓存做降级，服务挂了返回上次查到的数据，商品详情、用户信息这种不经常变的数据特别适合。
  • 限流降级：流量太大的时候直接拒绝部分请求，秒杀场景只放 1 万个请求进来多出来的直接返回”活动太火爆，请稍后再试”。
  • 开关降级：通过配置中心动态关闭特定功能。
  • 主流降级框架对比：Hystrix 停止维护 Netflix 出品功能完善但较重适用老项目维护；Resilience4j 活跃轻量级函数式风格支持响应式适用 Spring Boot 2.x+ 新项目；Sentinel 活跃阿里出品功能丰富有控制台适用 Spring Cloud Alibaba 生态。Hystrix 2018 年进入维护模式官方推荐迁移到 Resilience4j，国内用 Sentinel 多主要是跟 Spring Cloud Alibaba 配合得好且有可视化控制台。
  • 设计原则：哪些功能可以降级，核心交易链路不能降级推荐评价积分这些边缘功能可以；降级后返回什么，缓存数据、默认数据还是友好提示要根据业务场景决定，库存可以返回缓存但余额查询不能返回缓存；降级开关放配置中心如 Nacos、Apollo，大促前提前把非核心功能关掉不用改代码重启。
  • 实际场景：双 11 大促期间电商提前把商品评价、问大家、买家秀降级成静态页面或直接隐藏，把算力集中在下单支付库存扣减，流量高峰过去再恢复；金融系统某个银行渠道不可用直接降级到其他渠道或提示用户换支付方式。
  • 降级和熔断区别：熔断是被动触发检测到下游服务故障率超过阈值自动断开调用，降级是主动策略可以提前配置或手动触发；熔断触发后一般执行降级逻辑，所以经常配合使用；熔断解决怎么发现故障并快速止损，降级解决止损后给用户返回什么。
  • 判断功能能否降级：业务影响，核心交易链路不能降级影响收入的功能谨慎纯体验优化类可大胆降级；数据一致性要求，余额库存涉及资金或核心数据返回错误数据比不返回更危险宁可报错也不能返回脏数据。
  • 降级后返回缓存数据缓存过期处理：多级缓存策略本地缓存过期还有 Redis Redis 也没有返回默认值或友好提示；或缓存永不过期后台定时刷新服务恢复后再更新；具体看业务对数据时效性的容忍度。
  • Sentinel 流控规则：支持 QPS 流控、线程数流控、关联流控、链路流控；QPS 流控每秒请求数超过阈值就限流；线程数流控并发线程数超过阈值就限流；关联流控 A 接口流量大时限制 B 接口；链路流控针对某个入口来源限流；实际用最多 QPS 流控配合预热模式让系统慢慢承接流量避免冷启动被打崩。

41. 什么是服务熔断？

🗣️ 回答重点

  • 服务熔断就是下游服务扛不住的时候，调用方主动切断请求，不再去调用它，跟家里的保险丝一个道理，电流太大就自动断开，保护整个电路不被烧掉。
  • 熔断器检测到某个服务在 10 秒内失败率超过 50%，就会跳闸，后续所有请求直接返回失败，不再真正调用那个服务；过 30 秒后放几个请求去试探一下，成功了就恢复正常调用，失败就继续熔断。
  • 熔断和降级经常一起出现但职责不同：熔断解决怎么快速发现故障并止损，降级解决止损后给用户返回什么；熔断触发后一般执行降级逻辑给用户兜底响应。

📈 拔高

  • 熔断器三种状态：Closed 关闭状态正常情况下熔断器关闭请求正常通过同时统计成功和失败次数；Open 打开状态失败率超过阈值熔断器跳闸进入打开状态所有请求直接失败不再调用下游服务；Half-Open 半开状态打开状态持续一段时间后进入半开状态放几个请求试探，试探成功切回关闭状态失败继续保持打开。
  • 熔断触发条件看三个指标：失败率，比如 10 秒内请求 100 次失败 60 次失败率 60% 超过阈值 50% 触发熔断；慢调用比例，请求虽然成功但响应时间超过 3 秒算慢调用比例超过阈值也会触发熔断因为慢调用会占用线程资源；异常数，某些场景下直接按异常次数触发比如 1 分钟内异常 5 次就熔断。
  • 主流熔断框架：Hystrix 停止维护滑动窗口配置较复杂适用老项目维护；Resilience4j 活跃滑动窗口/计数窗口配置简单适用 Spring Boot 2.x+ 新项目；Sentinel 活跃滑动窗口配置简单适用 Spring Cloud Alibaba 生态。Hystrix 2018 年停止更新官方推荐迁移到 Resilience4j，Resilience4j 更轻量基于 Java 8 函数式编程跟 Spring Boot 配合得很好。
  • Resilience4j 熔断配置示例：CircuitBreakerConfig.custom().failureRateThreshold(50).slowCallRateThreshold(80).slowCallDurationThreshold(Duration.ofSeconds(3)).waitDurationInOpenState(Duration.ofSeconds(30)).permittedNumberOfCallsInHalfOpenState(3).slidingWindowType(SlidingWindowType.COUNT_BASED).slidingWindowSize(10).build()。Sentinel 在国内用得比较多有可视化控制台可实时看到每个接口的 QPS、响应时间、熔断状态运维方便。
  • 熔断参数调优：阈值设太低正常波动就触发熔断用户动不动看到报错；阈值设太高真出故障熔断器迟迟不跳闸故障扩散开了才反应。失败率阈值 50% 是合理起点核心链路可以设低一点比如 30%；统计窗口不要太小至少 10 次请求以上再判断避免单次失败就触发；熔断等待时间 30 秒到 60 秒比较合适；半开状态试探请求数设 3 到 5 个。
  • 熔断和重试配合：重试应对偶发失败熔断应对持续故障；如果下游已挂还疯狂重试等于火上浇油；正确做法先重试再熔断，单次请求失败可重试 2 到 3 次但重试失败也算失败率统计的一部分，失败率超过阈值触发熔断后不再重试直接返回降级结果。
  • 熔断器统计窗口两种：基于时间的滑动窗口统计最近 N 秒内的请求情况如最近 10 秒失败率；基于计数的滑动窗口统计最近 N 次请求情况如最近 100 次请求失败率。时间窗口对流量变化更敏感低流量场景样本不够准确；计数窗口样本数固定但对时间不敏感可能很久以前的请求还在统计范围内；高流量用时间窗口低流量用计数窗口。
  • 熔断状态下请求直接失败不会影响用户体验，关键是熔断后要有降级逻辑兜底给用户合理响应，比如推荐服务熔断返回默认热销榜单库存服务熔断提示”库存查询中，请稍后”；熔断价值在于快速失败避免用户等 30 秒才看到超时报错现在 100 毫秒就能返回降级结果体验其实更好。
  • 半开状态试探请求失败处理取决于框架配置：Resilience4j 可配置半开状态允许请求数和成功阈值比如放 5 个请求成功 3 个以上就关闭熔断器否则继续打开；Sentinel 默认放一个请求试探成功就关闭失败就继续打开。
  • 线上怎么知道哪些服务触发了熔断：接入监控，Sentinel 自带控制台能实时看到每个接口的熔断状态和触发次数；Resilience4j 可通过 Actuator 暴露熔断器指标接入 Prometheus + Grafana；配好告警熔断器状态从关闭变成打开就发告警通知让运维第一时间知道有服务出问题。

42. 什么是服务限流？

🗣️ 回答重点

  • 服务限流是一种流量控制策略，通过限制每秒请求数量、请求频率、并发数这些指标，保护服务的处理能力，防止流量过大把系统压垮。
  • 限流和熔断、降级并称服务保护三大手段，核心思路都是限制进入系统的请求数量来实现保护。
  • 阈值可以按预估吞吐量来定，比如订单服务单实例能抗 2000 QPS，就把限流阈值设成 1800 QPS，超出的请求直接拒绝或排队等待。
  • 处理流程是请求先过限流器判断有没有超阈值，没超就放行正常处理，超了就触发限流策略：直接拒绝返回错误码、进等待队列排队，或者触发降级返回兜底数据。
  • 常见的实现算法有固定窗口、滑动窗口、漏桶、令牌桶，Guava 的 RateLimiter 就是令牌桶实现。

📈 拔高

  • 固定窗口在边界处可能双倍流量：第 1 秒最后 500ms 来 100 个请求、第 2 秒前 500ms 又来 100 个，实际 1 秒处理了 200 个；滑动窗口把大窗口切成小窗口统计最近总和，比如 1 秒切成 10 个 100ms，Sentinel 默认就是滑动窗口。
  • 漏桶匀速出桶，适合对下游有严格速率要求的场景，比如调第三方短信接口限制每秒最多 10 次；令牌桶按固定速率放令牌，桶里攒了令牌就能应对一波突发，桶满了新生成的令牌直接丢弃。
  • 单机限流用 Guava RateLimiter 最轻量，几行代码就能用，但只能控单实例；分布式限流靠 Redis + Lua 脚本，一个脚本里原子完成「读计数、判断超限、计数加一」，不会有并发问题。
  • 电商秒杀可以在网关层用令牌桶限流，每秒只放 5000 个请求进来，超出的返回活动火爆提示；防爬虫可以按 IP 用滑动窗口统计，超阈值的请求直接返回 429 状态码。

43. Sentinel 是怎么实现限流的？

🗣️ 回答重点

  • Sentinel 限流的核心思路是四步：定义资源、配置规则、流量统计、限流判断。
  • 先明确限流对象，在 Sentinel 里一个接口、一个方法甚至一段代码都可以定义成资源。
  • 再给资源配置限流规则，比如 QPS 不能超过 100、并发线程数不能超过 10。
  • 请求进来后 Sentinel 实时统计当前资源的 QPS 和并发数，跟阈值对比，超了就触发限流。
  • 代码层面用 @SentinelResource 注解就能定义资源，配上 blockHandler 处理限流后的逻辑。

📈 拔高

  • 执行流程走 Slot Chain 责任链，槽位依次执行：NodeSelectorSlot 构建调用树，ClusterBuilderSlot 创建统计节点，StatisticSlot 实时统计 QPS 和线程数，最后 FlowSlot 拿统计数据和规则对比，超阈值就抛 FlowException。
  • StatisticSlot 用 LeapArray 数据结构做滑动窗口，底层是环形数组，默认 1 秒切成 2 个 500ms 的窗口，按当前时间戳定位窗口累加计数，窗口过期复用槽位 reset 就行，不用频繁创建销毁对象。
  • 限流模式有直接拒绝、排队等待和预热：排队等待类似漏桶，可设最大等待 500ms（CONTROL_BEHAVIOR_RATE_LIMITER）；预热用于冷启动，令牌生成速率用冷却因子 3、预热时长 10 秒，阈值在 10 秒内从 1/3 爬升到设定值。
  • 规则默认存在内存里，重启就没了，生产要推送到 Nacos、Apollo 这些配置中心，监听变更自动刷新到规则管理器，控制台改完规则所有节点实时生效，不用重启。

44. Sentinel 与 Hystrix 的区别是什么？

🗣️ 回答重点

  • 最核心的区别是设计理念不同：Hystrix 以服务保护为切入点，Sentinel 以流量控制为切入点。
  • Hystrix 的核心是线程隔离，每次服务调用放独立线程池执行，一个服务挂了不拖垮整体，代价是线程池有开销，高并发下线程切换成本不低。
  • Sentinel 的核心是流量控制，用滑动窗口实时统计 QPS、并发数，靠信号量机制控制并发，不依赖线程池隔离，性能开销更小。
  • 功能上 Hystrix 主做熔断和降级，监控失败率和响应时间；Sentinel 限流、熔断、降级、热点参数限流、系统自适应保护都支持，还有可视化控制台实时调整规则。
  • 现实因素是 Hystrix 2018 年就停止维护了，Netflix 官方推荐迁移到 Resilience4j；Sentinel 持续更新，社区活跃，新项目基本都选 Sentinel。

📈 拔高

  • 熔断策略不同：Hystrix 是关闭、打开、半开三态，10 秒内请求数超过 20 个且失败率超过 50% 就打开，开 5 秒后半开放一个请求试探；Sentinel 支持慢调用比例、异常比例、异常数三种策略，慢调用比例能在服务变慢但还没挂时提前保护。
  • 隔离上 Hystrix 默认线程池隔离，每个依赖服务配独立线程池，比如每个池子 10 个线程，也有信号量隔离但不支持超时控制；Sentinel 默认信号量隔离，用 AtomicInteger 记录并发数，缺点是没法做超时中断，要靠调用方配置超时或慢调用熔断兜底。
  • 限流能力上 Hystrix 只能靠线程池大小和信号量间接限流，想做精细 QPS 限流得自己写代码；Sentinel 支持直接拒绝、排队等待、预热模式，还支持热点参数限流，比如同一个接口，普通用户限流 100 QPS，高等级用户限流 1000 QPS，按参数值区分对待。
  • 迁移时注解要换，@HystrixCommand 换成 @SentinelResource；blockHandler 处理限流熔断的 BlockException，要带 BlockException 参数，fallback 处理业务异常；线程池隔离在 Sentinel 没有直接替代，超时中断得在调用方自己设。

45. Sentinel 是怎么实现集群限流的？

🗣️ 回答重点

  • 核心思路是选一个节点当令牌服务器，所有实例请求资源前都去它申请令牌，拿到令牌才放行，拿不到就限流。
  • 集群分两种角色：Token Server 集中发放令牌、内部维护全局计数器，每秒最多发 1000 个令牌就意味着整个集群 QPS 上限 1000；Token Client 就是各业务实例，申请不到就走限流逻辑。
  • 具体流程是业务请求打到某个实例，实例作为 Client 通过 Netty 发一个 TCP 请求给 Token Server，计数器没超阈值就发令牌并加一，超了就返回拒绝，Client 拿到结果决定放行还是降级。
  • 这是为了解决单机限流的问题。10 个实例各限 100 QPS，流量分布不均时可能 3 个实例扛了 80% 流量先被限，其余 7 个还闲着；集群限流按全局视角判断，整体没超 1000 QPS 就都放行。

📈 拔高

  • Token Server 两种部署模式：嵌入式直接从业务集群选一个实例兼任，不用单独部署但压力大时容易成瓶颈；独立部署单独起进程不跑业务，生产推荐这种方式，一般 2-3 个节点做主备。
  • 通信细节是 Token Client 和 Token Server 走 Netty 长连接、Sentinel 自定义二进制协议，一次令牌申请约 0.5ms；申请失败 Client 可降级到单机限流，避免 Token Server 挂掉导致全被拒绝，也可配置快速失败。
  • 高可用要靠外部组件：Sentinel 本身没有内置选举算法，需要 Nacos、ZooKeeper 动态切换 Token Server 地址实现主备，注意不能让 Client 同时连不同节点，否则全局计数不一致。
  • Token Server 内部用滑动窗口算法，默认窗口 1 秒分多个小窗口统计；除 QPS 模式外还支持并发线程数模式，统计处理中的请求数，适合下游响应时间波动大的场景。

七、网关、服务网格与发布策略

46. 什么是服务网格？

🗣️ 回答重点

  • 服务网格是一层专门处理服务间通信的基础设施，核心思路是在每个服务旁边部署一个代理进程，路由、限流、熔断、监控这些脏活累活都由代理负责，业务代码压根不用管。
  • 具体就是 Sidecar 模式：业务服务和代理进程跑在同一个 Pod 里，业务发出的请求先到本地代理，代理再转发给目标服务的代理，最后才到目标服务。
  • 整个过程对业务代码完全透明，开发者只管写业务逻辑，服务发现、负载均衡、TLS 加密这些都由代理搞定。
  • Istio、Linkerd 是目前最主流的服务网格方案，数据平面一般用 Envoy 做代理。

📈 拔高

  • 演进过程是通信和业务先耦合在一起，后来抽成 Dubbo、gRPC 这类公共 RPC 组件但仍要引入 SDK，服务网格更进一步把通信逻辑连 SDK 都剥离，用独立进程做代理，被称为微服务 3.0 版本。
  • 架构分两层：控制平面是大脑，负责下发配置、管理策略，Istio 原来的 Pilot、Citadel、Galley 三个组件在 1.5 版本后合并成一个 istiod 进程；数据平面是一堆 Sidecar 代理，Istio 默认用 Envoy，执行路由、限流、熔断、加密。
  • 代价是每次服务调用多两跳代理，P99 延迟增加 2-5ms；每个 Pod 多跑一个代理进程，Istio 一个 Sidecar 大概占 50-100MB 内存，100 个服务就是 5-10GB 额外开销，Linkerd 用 Rust 写、内存只有 Istio 的十分之一左右。
  • 不是所有场景都适合上服务网格：服务数量 10 个以内，用 Spring Cloud 那套 SDK 方案反而更简单；上百个服务、跨多语言、需要统一流量治理的场景才体现价值，因为能力下沉到代理层后，任何语言的服务流量经过代理都享受统一治理。

47. 什么是灰度发布、金丝雀部署以及蓝绿部署？

🗣️ 回答重点

  • 这三种都是为了让新版本上线更安全的发布策略，核心思路就是避免一次性全量切换带来的风险。
  • 蓝绿部署最简单直接：线上同时跑两套环境，蓝色是当前生产版本，绿色是新版本，验证完把流量一把切到绿色，出问题秒切回蓝色当备份。
  • 金丝雀部署先放一小撮流量到新版本试水，比如 5% 请求打到新版本，观察没问题再逐步放大比例直到全量；名字来自矿工用金丝雀探有毒气体。
  • 灰度发布和金丝雀很像，区别在分流维度：金丝雀一般按比例随机分，灰度发布按用户属性分，比如先内部员工、再北京用户、最后全量。

📈 拔高

  • 蓝绿部署优点是切换快、回滚快（基本秒级），缺点是资源占用翻倍、两套环境成本高；涉及数据库 schema 变更时两个版本可能没法共用一个库。
  • 金丝雀不需要完整双环境，只在现有集群加几个新版本实例，K8s 里用两个 Deployment 配合 Istio 的 VirtualService 配流量权重（v1 90、v2 10）即可。
  • 灰度发布可在网关层做路由判断，读请求里的用户信息匹配灰度规则后决定转发哪个版本；按用户 ID 分流可用 userId % 100 < 10 保证同一用户天然打到同一版本。
  • 数据库变更最头疼，一般用两阶段发布向前兼容：先加字段但不依赖、发布新版本让它开始写、等旧版本全下线再依赖新字段，可配合 Flyway、Liquibase 做版本管理。

48. 什么是微服务网关？为什么需要服务网关？

🗣️ 回答重点

  • 微服务网关就是整个系统的统一入口，所有外部请求都得先经过它，再由它转发到后端各个微服务，就像小区门卫室先登记验证身份再指路。
  • 统一入口管理：没网关的话 10 个服务就是 10 个地址，客户端配置复杂、地址一变全得改；有网关客户端只认一个地址，路由分发交给网关。
  • 横切关注点集中处理：鉴权、限流、日志、监控这些公共逻辑放网关统一处理，一处修改全局生效，不用改 10 个服务。
  • 协议转换和适配：外部用 HTTPS，内部服务之间可能用 gRPC 或私有协议，网关做协议泛化，对外暴露标准 REST 接口，对内用高性能二进制协议。

📈 拔高

  • 没网关时服务一多（20、50 个）问题就暴露：跨域每个服务单独配 CORS、鉴权逻辑散落各处风格不统一、服务地址一变前端得跟着发版。
  • 网关核心能力包括路由转发、负载均衡、安全鉴权（统一校验 Token/签名/IP 白名单）、限流熔断、协议转换（HTTP 转 Dubbo 或 gRPC）。
  • 限流在网关层做比各服务做高效：整个系统每秒最多 1 万请求，超了直接返回 429 状态码压根不打到后端；常用令牌桶和漏桶，Gateway 内置 RequestRateLimiter 用 Redis 做分布式限流。
  • 网关本身也可能成单点，生产一般部署多个实例前面挂 LVS 或 Nginx，架构是 DNS -> LVS/Nginx -> Gateway 集群 -> 微服务集群，4 核 8G 跑 Gateway 单实例约扛 2 万 QPS。

49. Spring Cloud 可以选择哪些 API 网关？

🗣️ 回答重点

  • Spring Cloud Gateway 是官方主推方案，底层基于 WebFlux 和 Netty 走非阻塞响应式路线，和 Nacos、Sentinel、OpenFeign 配合得很好，Java 技术栈首选。
  • Kong 基于 Nginx 和 OpenResty 的高性能网关，单机轻松跑到 10 万+ QPS，插件生态丰富，缺点是 Lua 语言门槛高，Java 开发者二次开发不太顺手。
  • Apache APISIX 也是 Nginx + Lua 路线，性能和 Kong 一个级别但更云原生，支持 Java、Go、Python 多语言插件，配置通过 etcd 热更新不用重启。
  • Zuul 是 Spring Cloud Netflix 早期默认网关，1.x 是同步阻塞模型性能瓶颈明显，整体进入维护模式，Spring 官方从 2020 年起不再推荐，新项目直接上 Gateway。
  • Envoy 底层用 C++，二次开发难度较大，是 CNCF 云原生基金会的毕业项目，比较适合服务网格场景和多语言架构部署。

📈 拔高

  • 选型路径：纯 Java 技术栈选 Gateway；追求极致性能或多语言架构选 Kong 或 APISIX；服务网格场景考虑 Envoy。
  • 网关是微服务架构的咽喉要道，选错轻则性能跟不上、重则单点故障拖垮系统；某电商用 Zuul 1.x 大促扛不住（线程池 200、每请求 100ms 理论上限 2000 QPS），换成 Gateway 吞吐直接翻 10 倍。
  • 性能对比：各网关吞吐量强依赖测试环境，不同基准能差 10 倍以上，量级上 Kong/APISIX 明显高于 Gateway，Gateway 又高于 Zuul 1.x；Gateway 支持配置热更新、学习成本低、社区活跃，Zuul 1.x 已停止维护。
  • 从 Zuul 迁移分三步：先梳理现有路由配置和过滤器（ZuulFilter 对应 GatewayFilter），再并行部署新老网关先切 10% 流量观察，最后全量切换后下掉老 Zuul。

50. 什么是 Spring Cloud Zuul？

🗣️ 回答重点

  • Zuul 是 Netflix 开源的 API 网关，Spring Cloud 把它集成进来作为早期默认的网关方案。
  • 核心能力就是请求路由和过滤，所有进入微服务的流量先过 Zuul，由它决定转发到哪个服务，转发前后可做鉴权、限流、日志等横切逻辑。
  • Zuul 的核心是过滤器机制，所有功能都通过过滤器实现，过滤器分 pre、route、post、error 四种类型。
  • 请求进来先走 pre 过滤器链，再走 route 过滤器转发到后端服务，拿到响应走 post 过滤器链返回客户端，任何环节出错都跳到 error 过滤器处理。
  • 重要背景：Zuul 1.x 在 2017 年 11 月之后就没再更新，2019 年 1 月 Spring Cloud Greenwich 已把它列为被 Zuul 2 取代，Spring Cloud 2020 版起移除了相关模块，Spring 官方现在主推 Spring Cloud Gateway；新项目不建议再上 Zuul，老项目建议迁移到 Gateway。

📈 拔高

  • 四类过滤器分工：pre 在路由前做鉴权/参数校验/流量染色，route 用 HttpClient 或 Ribbon 转发，post 加响应头/记日志/统计耗时，error 做异常处理和错误响应。route 里直接指定后端地址就写成这样：
  • Zuul 1.x 底层就是一个 Servlet，一请求占一个线程，等后端响应时线程阻塞；Tomcat 配 200 线程、每请求 100ms 理论极限就是 2000 QPS，再多只能排队超时。
  • Zuul 2.x 用 Netty 重写网络层，IO 线程发完请求就处理别的连接，性能约 2 万 QPS，但 Spring Cloud 没官方集成、用着得自己折腾，Netflix 对开源投入也越来越少。
  • 迁移到 Gateway 涉及路由和过滤器两部分：Zuul 路由用 serviceId，Gateway 用 lb:// + predicates；过滤器 ZuulFilter 对应 GatewayFilterFactory，逻辑能复用但 API 得重写。

51. 什么是 Spring Cloud Gateway？

🗣️ 回答重点

  • Spring Cloud Gateway 是 Spring Cloud 官方推出的 API 网关，用来替代已经进入维护状态的 Zuul 1.x。
  • 它基于 Spring 5、Spring Boot 2 和 Project Reactor 构建，底层用 Netty 做通信，走异步非阻塞路线，高并发场景比 Zuul 那套同步阻塞模型扛得住多。
  • 在微服务架构里 Gateway 就是所有外部流量的统一入口，主要干三件事：路由转发、请求过滤、负载均衡。
  • 路由转发按预配置规则把请求分发到各微服务，客户端不用关心服务部署在哪；请求过滤借鉴 Zuul 思想但改成异步非阻塞；负载均衡配合 Spring Cloud LoadBalancer 或 Ribbon 分摊流量。

📈 拔高

  • 三个核心概念：Route 路由（含唯一 ID、目标 URI、一组 Predicate、一组 Filter），Predicate 断言判断请求匹配（内置十几种断言工厂，多断言是与关系），Filter 分 GatewayFilter 和 GlobalFilter，按 Order 值排序执行。
  • 替代 Zuul 的根本原因在于模型差异，Zuul 1.x 基于 Servlet 同步阻塞，一请求占一线程，流量大线程池易打满；Gateway 基于 Reactor 响应式，一线程处理多请求，基准实测吞吐约为 Zuul 1.x 的 1.5 倍，且内存更低。
  • 常见踩坑：WebFlux 和 Spring MVC 不能混用（别引 spring-boot-starter-web，得用 starter-webflux）；易漏超时配置；网关层做跨域后后端别再配否则重复 CORS 头。
  • 限流用内置 RequestRateLimiter 过滤器，底层 Redis 实现令牌桶，配 redis-rate-limiter.replenishRate 和 burstCapacity，拿不到令牌返回 429，用 Redis 支持集群分布式限流。

52. 你项目里为什么选择 Gateway 作为网关？

🗣️ 回答重点

  • 选 Spring Cloud Gateway 主要就三点：Zuul 1.x 凉了、性能更好、Spring 生态集成顺滑。
  • Zuul 1.x 在 2018 年就进入维护状态，Netflix 的 Eureka、Hystrix、Ribbon 都陆续停更，继续用风险太大。
  • Gateway 是 Spring 官方亲儿子，一直积极迭代、社区活跃，长期来看比 Zuul 稳得多。
  • Gateway 基于 WebFlux 和 Netty，走异步非阻塞模型，我们高峰接近 5000 QPS，线程从几百个降到几十个。
  • 项目用 Spring Cloud Alibaba 那套，Nacos 做注册中心、Sentinel 做熔断限流，Gateway 开箱即用不用写适配代码。

📈 拔高

  • Zuul 1.x 是 Servlet 阻塞模型，一个请求占一个线程；Gateway 用 Netty EventLoop 不阻塞等 IO，默认 worker 线程数是 CPU 核心两倍。
  • 迁移踩坑：Filter 写法变了，Zuul 用 filterType 区分 pre/route/post，Gateway 统一 chain.filter()，post 逻辑得用 then() 回调处理。
  • WebFlux 两个坑：响应体只能读一次，想打印日志得用 ServerHttpResponseDecorator 包一层缓存；大文件上传默认会内存溢出，得调大 spring.codec.max-in-memory-size 或用流式处理。
  • 动态路由：路由配置存在 Nacos 里，改了不用重启网关，监听 Nacos 变更事件发 RefreshRoutesEvent 重新加载路由表，几秒生效。
  • 限流做两层：Gateway 内置 RequestRateLimiter 基于 Redis 令牌桶做全局 QPS 限流，再接 Sentinel 针对具体路由做细粒度控制，超阈值返回 429 和友好提示。

53. 说说什么是 API 网关？它有什么作用？

🗣️ 回答重点

  • API 网关是微服务架构里的统一入口，所有外部请求先打到网关，再由网关转发到具体的后端服务。
  • 它不只是个路由器，还干认证鉴权、限流熔断、日志监控、协议转换、请求聚合这些活。
  • 简化客户端调用：客户端只认网关一个地址，不用记后端几十个服务都部署在哪儿。
  • 增强安全性：统一做 JWT、OAuth2 这些认证逻辑写一遍就够，后端服务的真实地址藏在网关后面外面看不到。
  • 流量管控：限流、熔断、降级在网关这层做最合适，流量突增先挡住保护后端服务不被打崩。

📈 拔高

  • 微服务拆成几十上百个服务后，客户端直连会代码爆炸、公网往返多延迟差、协议不统一、重构受限。
  • 网关把内网多个服务的响应合并成一个返回，协议转换也放网关做，客户端只用 HTTP 就行。
  • 主流方案里 Gateway 是 Java + Netty，Kong 和 APISIX 是 Nginx + Lua 性能极高，Zuul 1.x 已停止维护。
  • 生产部署最前面是 Nginx 或云厂商负载均衡做 SSL 卸载，后面至少 2 个网关实例保证高可用。

54. Dubbo 和 Spring Cloud Gateway 有什么区别？

🗣️ 回答重点

  • 这两个东西压根不是一个层面的，放在一起比其实不太合适。
  • Dubbo 是高性能 RPC 框架，解决服务与服务之间怎么互相调用，提供注册发现、负载均衡、容错重试。
  • Spring Cloud Gateway 是 API 网关，解决外部流量怎么进来的问题，按路由规则转发给后端各个微服务。
  • Gateway 干的活是统一鉴权、限流熔断、协议转换、日志监控这些脏活累活。
  • 关系是：App 或浏览器发请求先到 Gateway 做鉴权限流，再转给订单服务，订单服务内部调库存、用户服务走 Dubbo。

📈 拔高

  • Dubbo 像专注 RPC 通信的尖刀，Spring Cloud 是微服务的全家桶，实际常混用而不是二选一。
  • 不少公司对外接口走 Gateway 做入口管控，内部服务间走 Dubbo 追求性能和治理，注册中心统一用 Nacos。
  • 请求链路是 Nginx 四层负载 → Gateway 七层路由鉴权 → 转内部 HTTP 到 BFF → BFF 用 Dubbo 调领域服务。
  • Dubbo 用二进制协议和长连接省掉 HTTP 握手和 JSON 解析，且权重调整、灰度发布等治理能力比 Spring Cloud 原生强。

55. 什么是令牌桶算法？工作原理是什么？使用它有哪些优点和注意事项？

🗣️ 回答重点

  • 令牌桶算法是一种经典的流量控制算法，系统以固定速率往桶里放令牌，请求进来先拿到令牌才能被处理，拿不到就等着或拒绝。
  • 令牌按固定速率生成，比如配置成每秒 100 个，那就是每 10ms 生成一个。
  • 桶有容量上限，比如最多存 200 个，满了之后新生成的令牌直接扔掉。
  • 请求进来先从桶里拿令牌，有令牌就放行，没令牌就阻塞等待或者直接拒绝。
  • 因为桶能攒令牌，所以允许一定程度的突发流量，攒够 200 个令牌瞬间来 200 个请求也能全部处理。

📈 拔高

  • 优点很明显：能平滑控制流量，又能应对突发，桶容量就是容忍的突发量，令牌速率就是稳态吞吐量，两个参数一调就适配各种场景。
  • 注意事项主要有：桶容量别设太大否则突发扛不住；分布式场景单机限流没用，得用 Redis 做集中式令牌桶；预热问题，Guava 默认首次使用会预支约 1 秒令牌把桶填满，冷启动可能放过大量请求。
  • 和漏桶区别：漏桶恒定速率流出没法应对突发，令牌桶提前攒令牌，桶有余量时突发照样能处理。
  • 常见坑：时间精度要用纳秒计时；分布式限流各节点时钟不同步得用 Redis 服务端时间；tryAcquire 的超时是愿意等多久而非最多等多久。

面试前 10 分钟速查

微服务全景

  • 单体、SOA、微服务的差别：单体把所有模块打进一个进程，SOA 走企业级总线做系统间整合，微服务按业务边界拆成独立部署、独立数据的小服务，粒度更细、治理更靠自治。
  • 微服务不等于分布式：分布式是部署形态，微服务是拆分与治理方式；一个微服务系统必然是分布式的，但分布式系统不一定拆成微服务。
  • Spring Cloud 的定位：它是 Spring Boot 之上的一整套微服务解决方案，核心组件覆盖服务注册发现、配置中心、网关、熔断限流、链路追踪。
  • Spring Boot 与 Spring Cloud 的关系：Boot 解决单个应用的配置与部署，Cloud 解决多个应用之间的协作；做微服务是 Boot 打底、Cloud 加持。
  • 优缺点：优点是独立部署伸缩、故障隔离、技术栈自由；缺点是分布式带来网络延迟、链路变长、数据一致性更难保证、运维与排查复杂度上升。
  • 链路追踪：一次请求跨多个服务后日志就散了，靠 TraceId 把整条链路串起来；Spring Cloud 里可选 Sleuth 与 Zipkin、SkyWalking 这类方案。
  • 日志收集：微服务日志分散在各机器上，主流做法是统一采集到日志中心（ELK、Filebeat 之类）再检索，把打印的 TraceId 作为索引字段。
  • DDD：把业务复杂度放进领域模型，先划分限界上下文再映射到服务边界，聚合根保证一致性，不追求表结构跟数据库一一对应。

分布式事务

  • 什么时候需要：跨服务、跨库的一个业务操作必须原子成功或原子失败时，数据库本地事务就管不了了。
  • 常见方案：两阶段提交、TCC、可靠消息最终一致、Seata、还有 MQ 事务消息。
  • Seata 是什么：阿里开源的分布式事务框架，提供 AT、TCC、SAGA、XA 四种模式。
  • 各模式怎么选：AT 无侵入不改业务代码但只适合简单库表；TCC 要自己写三个方法、性能最好；SAGA 适合长流程、可补偿；XA 强一致但要 XA 数据源、锁资源时间长。
  • AT 原理：一阶段把业务数据和回滚日志一起提交，二阶段发现异常就按回滚日志反向补偿。
  • 空回滚与防悬挂：全局事务先到了但分支还没注册，就先回滚，分支注册后收到的是一阶段已回滚的通知，这就是空回滚；反过来分支先到、全局事务后到，分支执行完却没人通知就悬挂了，Seata 用 undo_log 里的状态位来识别这两种情况。
  • 回滚怎么做：靠 undo_log 记录一阶段的镜像与前后镜像，出问题按镜像还原，再通知 TC 结束全局事务。

配置中心

  • 配置中心是什么：把配置从代码和打包产物里抽出来，运行时统一管理，改配置不用重新发版；常见的有 Spring Cloud Config、Nacos、Apollo。
  • Spring Cloud Config：服务端把配置按仓库（Git 或后端存储）暴露成 REST 接口，客户端启动或刷新时拉取；支持按 {application}-{profile}.yml 组织，也支持仓库加密。
  • Nacos 配置中心原理：客户端启动时把 dataId、group、tenant 报给服务端建立长连接监听，服务端感知配置变更后推给客户端，客户端再拉取并触发 refresh 事件。
  • 为什么用配置中心：多环境多实例时配置一致性问题最突出，配置中心提供统一管理、动态推送、版本回滚与灰度发布能力。

服务注册与发现

  • 为什么需要注册发现：服务实例地址会动态变化，写死 IP 一扩容一缩容就得改代码，服务发现让调用方按服务名找实例。
  • 注册中心有哪些：Eureka、Zookeeper、Nacos、Consul，Spring Cloud 里对应 Spring Cloud Netflix、Zookeeper、Nacos Discovery、Consul Discovery 这几套实现。
  • Eureka 是什么：Netflix 开源的注册中心，Server 维护注册表，Client 启动注册、周期心跳续约、停止时注销。
  • Eureka 原理：注册本质是 POST 请求写内存注册表（ConcurrentHashMap 两层），心跳是 PUT 请求每 30 秒一次，超过 90 秒没续约标记过期；客户端拉全量加 30 秒增量缓存在本地。
  • Eureka 的坑：AP 架构、只保可用不保一致、单机内存存注册表、历史版本有 Eureka 1.x 的 bug，Spring Cloud 2020.0 起 Netflix 组件进维护模式。
  • Consul 是什么：HashiCorp 出品，注册中心加 KV 存储加多数据中心，服务实例靠 agent 主动上报并支持健康检查。
  • 四者怎么选：Zookeeper 强一致但写性能一般、要自己搭；Eureka 只做注册发现且已被弱化；Nacos 功能最全，注册加配置加推送，国内用得最多；Consul 多数据中心和 KV 是强项；跑在 K8s 上直接用 Service 就行。
  • Nacos 的 Namespace：租户级隔离，同一套 Nacos 给不同环境或不同团队用，靠 namespaceId 隔开，配置和注册实例都按这个维度分。

服务调用

  • 为什么需要负载均衡：把请求分摊到多台机器，既扛并发又避免单点故障；纵向扩展有天花板，横向加机器才撑得住大促流量。
  • 负载均衡怎么实现：四层（IP 层，改包，性能高）和七层（应用层，能按域名、路径、Header 路由）；硬件的用 F5/A10，软件的用 LVS、Nginx、HAProxy，云上用云厂商的 LB。
  • 常见算法：轮询、加权轮询、源地址哈希、最少连接、加权最少连接、随机。
  • HTTP 与 RPC 的差别：RPC 是跨进程调用方式的统称，HTTP 也是一种远程调用协议但更通用、可跨语言；RPC 走自定义二进制协议性能更高，HTTP 通用、调试方便、可被浏览器直接调用。
  • Feign 是什么：声明式 HTTP 客户端，定义接口加注解就行，底层生成动态代理把方法调用翻译成 HTTP 请求。
  • Feign 怎么负载均衡：配合 Ribbon 或 Spring Cloud LoadBalancer，服务名从注册中心拿实例列表，再按策略挑一个发请求。
  • Feign 第一次调用慢：负载均衡组件默认懒加载，第一次调用才初始化（拉实例、建连接池、加载策略），几百毫秒到几秒都正常；可以开饥饿加载或启动后预热一次。
  • Feign 与 OpenFeign：原生 Feign 只认自己的注解、依赖 feign-core；Spring Cloud OpenFeign 整合 Spring 生态、支持 Spring MVC 注解，老的 spring-cloud-starter-feign 已移除。
  • Feign 与 Dubbo：Feign 是声明式 HTTP 调用、和 Spring Cloud 生态一套；Dubbo 是 RPC 框架、有自己的服务治理与序列化协议，性能与治理能力更强，但和 Spring 体系融合成本高。

稳定性

  • 服务雪崩：一个下游服务慢或挂掉，把上游的线程池占满，一层层往上传染，最后整条链路全瘫，这就是雪崩。
  • 熔断器干什么：下游出问题时快速切断调用链，请求直接失败返回，连等待都不等，把线程资源腾出来；三个状态是关闭、打开、半开。
  • 熔断触发条件：慢调用比例、异常比例、异常数三种策略，Sentinel 用滑动窗口统计，比固定窗口平滑。
  • 降级：系统压力过大或服务不可用时保核心链路、牺牲非核心功能，比如大促时关掉商品评价保下单。
  • 限流：入口处保护自己，请求量超过承载能力就限制，比如接口 QPS 限制 1000 超出直接拒绝。
  • 限流的算法：令牌桶最常用，固定速率往桶里放令牌、请求先取令牌，桶有容量所以能容忍突发；漏桶恒定速率出流，应对不了突发。
  • 分布式限流：单机令牌桶在集群里没用，得靠 Redis 做集中式令牌桶并用服务端时间，避免各节点时钟不同步。
  • Hystrix：Netflix 出的熔断隔离框架，线程池隔离为核心，已停止维护，新项目基本不用。
  • Sentinel 与 Hystrix 的差别：Hystrix 靠线程池和信号量间接限流、只支持少量熔断策略；Sentinel 滑动窗口统计、限流/熔断/热点参数/系统自适应都有，还自带控制台、规则可持久化到 Nacos、Apollo，官方也推荐用 Resilience4j 替代 Hystrix。
  • 服务网格：在每个服务旁边放 Sidecar 代理，路由、限流、熔断、监控都在代理层完成，业务代码无感；主流方案 Istio、Linkerd，代价是多两跳延迟与额外内存。

网关、服务网格与发布策略

  • 为什么需要网关：统一入口，把鉴权、限流、路由、协议转换、日志这些横切能力收在一处，业务服务只管业务。
  • API 网关的作用：对外暴露统一 API，对内按服务名路由转发，顺手做认证鉴权、限流熔断、灰度发布、访问日志。
  • 常用网关：Spring Cloud Gateway、Zuul、Nginx、Kong、APISIX。
  • Zuul：Netflix 的网关，核心是过滤器机制，分 pre、route、post、error 四类；1.x 是 Servlet 阻塞模型、线程吃紧，2.x 用 Netty 重写但官方集成缺失，已被 Gateway 取代。
  • Gateway：基于 Netty 与 WebFlux 的响应式网关，路由用 lb:// 加 predicates，配 GatewayFilterFactory 做自定义过滤，性能与扩展性都强于 Zuul。
  • 选 Gateway 的理由：底层非阻塞 IO 扛得住高并发，路由规则可编程扩展，和 Nacos、Sentinel 这些组件集成顺畅，官方还在持续维护。
  • Dubbo 与 Gateway 的差别：Dubbo 是服务间 RPC 治理框架，Gateway 是南北向的外部流量入口，两者定位不同，常常并存。
  • 灰度发布：按比例或规则把一部分流量导到新版本，验证没问题再放量。
  • 金丝雀部署：先放少量流量给新版本观察指标，出问题立刻回滚。
  • 蓝绿部署：两套环境一套跑老版本一套跑新版本，切换时整体切流量，回滚也快，但资源成本翻倍。
