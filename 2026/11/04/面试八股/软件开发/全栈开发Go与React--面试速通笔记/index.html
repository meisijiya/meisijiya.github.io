一、业务认知

1.1 TikTok 广告生态与代理层级

代理层级（是什么/为什么/本岗用得上）

  • 是什么：广告主投广告要经过「代理商」开户与充值；代理商分一级（直接对接 TikTok）和二级（对接一级，覆盖更多市场）。
  • 为什么：代理商帮广告主处理开户、充值、授信、对账，TikTok 只对接代理商结算。
  • 在本岗哪里用得上：海客是巴西一级代理 + 多市场二级代理（D2、P6），平台要管理多个层级的账户与资金。
角色 作用 本岗对应
广告主 最终投广告、付钱的人 客户管理模块
一级代理商 直接对接 TikTok（如海客·巴西） 开户/结算主体
二级代理商 对接一级，覆盖日本/东南亚等 多市场二级
TikTok 平台 实际消耗广告费、返还返点 外部数据源

一句话话术：「海客是巴西一级代理，又做多市场二级代理，平台要同时管两类层级的账户、充值、消耗和返点。」

  • 第一问：一级和二级代理商平台有什么不同？
  • 答：一级直接对接 TikTok 结算，二级对接一级，平台要支持两种开户与对账路径。
  • 第二问：代理商的毛利来自哪？
  • 答：主要来自平台返点，按消耗或阶梯比例返还，这是 D3 返点结算模块的核心。
  • 第三问：多市场币种怎么处理？
  • 答：多币种汇率折算，金额保留 6 位小数（D3），折算时点要存快照，见五章。

术语 统一叫法 三行解释（是什么/为什么/本岗）
广告账户 广告账户 开户：广告主在平台开的一个投放账号；为什么：投放前必须有账户；本岗 D2 开户模块
钱包 钱包 预付充值、用来扣消耗的账户；为什么：先充钱才能投；本岗 D3
消耗 消耗 广告跑起来实际花掉的钱；为什么：平台对广告主的真实扣款；本岗 D2/D3
授信 授信 账期赊账额度，先消耗后付款；为什么：给大客户赊账周转；本岗 D2/D3

1.3 广告主完整资金链路（闭环图，≤12 节点）

一句话话术：「一条线就是开户→充值→授信→消耗→记账→对账→返点，返点再回充钱包，形成闭环。」

广告主开户 → 钱包充值 → 授信/账期 → 广告消耗 → TikTok 平台计费 → 内部流水记账 → 消耗对账 → 返点结算 → 回充钱包（闭环）

节点 钱怎么动、账怎么记
广告主开户 开立客户账户/钱包；账：客户主数据与账户状态记录
钱包充值 真实资金入账到钱包余额；账：充值流水（金额、渠道、时间）
授信/账期 授予广告消耗额度/账期；账：授信额度与到期日记录
广告消耗 广告投放扣减钱包/授信；账：消耗明细与扣费记录
TikTok 平台计费 平台侧计费确认实际消耗；账：平台账单/计费明细
内部流水记账 把平台消耗写入内部账本；账：内部流水（金额、币种、汇率时点）
消耗对账 核对平台数字与内部账本；账：对账差异记录（长款/短款/待核实）
返点结算 按比例/阶梯算返点并生成结算单；账：返点结算单
返点回充 返点回充到钱包/结算给代理商，形成闭环；账：返点入账流水
  • 第一问：对账对的是什么？
  • 答：对 TikTok 平台那边的消耗数字，和咱们内部账本记的数字，是不是一致。
  • 第二问：不一致怎么办？
  • 答：差异分长款（咱多记）、短款（咱少记）、待核实（数据延迟/汇率时点不同），见五章对账差异处理。
  • 第三问：返点怎么进来？
  • 答：按消耗或阶梯比例算返点，生成返点结算单，回充到钱包或结算给代理商。

1.4 钱与账的关系

  • 钱：真实资金流（钱包余额、授信额度、实际消耗），在银行/支付/TikTok 侧。
  • 账：记录（流水、账单、结算单），存在咱们 PostgreSQL 里。
  • 关系：账必须和钱对得上；对账就是核对「账上记的」和「实际发生的」一致。

一句话话术：「钱是真实发生的资金，账是咱们记下来的记录，对账就是让账和钱两边数一样。」

  • 第一问：账和钱对不上会怎样？
  • 答：要么多扣了客户钱（客诉），要么少记了收入（公司亏），所以 D3 必须能追溯每笔。
  • 第二问：账本存在哪？
  • 答：本岗用 PostgreSQL（R4），金额用 NUMERIC 精确存，绝不用 float（见四章）。

1.5 为什么金额要 6 位小数、为什么权限留痕重要

问法 一句话答 追问
为什么 6 位小数 多币种汇率折算会放大小数误差，6 位保证折算精度（D3） 那舍入怎么处理
单笔舍入 vs 总额舍入 两种舍入会产生尾差，必须固定一种并文档化（D3） 用什么类型存
为什么权限留痕重要 财务/运营/商务/客户数据范围不同，改钱必须可追溯（D5、R6） 怎么防越权

一句话话术：「钱系统里权限和留痕不能省，谁在什么时候改了哪笔钱，必须查得到，越权改账要从服务端拦。」

  • 第一问：权限为什么不能只靠前端？
  • 答：前端校验能被绕过，服务端必须按角色+数据范围再校验一次（D5、R6）。
  • 第二问：留痕记什么？
  • 答：操作人、时间、改了哪个字段、前后值，敏感操作还要二次确认（见五章 RBAC）。
  • 第三问：6 位小数是内部还是展示？
  • 答：6 位是内部精度，展示按币种 minor units 格式化（如日元 0 位、美元 2 位）。

  • 第一问：扣款顺序怎么定？
  • 答：通常先扣钱包余额，不够再走授信额度；具体顺序以公司财务规则为准（见五章钱包与授信）。
  • 第二问：消耗流水从哪来？
  • 答：TikTok 平台把消耗数据拉回内部，作为外部数据源，再和内部账对账（D4 外部接口联调）。
  • 第三问：返点结算周期？
  • 答：常见 T+1/T+7，按周期根据实际消耗确认金额（见五章返点计算）。

1.9 一个广告主的一天（业务串联）

一句话话术：「把一天拆开看，每个动作要么动钱、要么记账，平台就是把这些动作串成闭环并让账钱对平。」

时段 动作 钱怎么动 账怎么记 模块
早上 充值 1 万到钱包 真实资金进钱包 写充值流水 钱包充值（D3）
上午 投广告消耗 2000 扣钱包余额 写消耗流水 消耗（D2/D3）
中午 财务对账 不动钱 标记对账一致/差异 对账（D3）
下午 平台算返点 5% 返点回充或结算 写返点结算单 返点（D3）

  • 第一问：授信什么时候动？

  • 第三问：这和我写代码有什么关系？
  • 答：每个动作背后是一个接口（充值/消耗/对账/返点）和一张表，二章前端展示、三章 Go 写接口。

2.1 一次请求到页面出现

是什么：浏览器输入 URL 到看到内容，中间走 DNS→TCP→HTTP→解析→渲染。
为什么：理解这一步才能回答「白屏/首屏慢」在哪。
本岗哪里用得上：D1 页面加载/错误/权限状态都在这条链路上。

阶段 谁在做 产物
HTML 浏览器解析成 DOM 树 页面骨架
CSS 计算样式、布局（盒子位置） 视觉结构
JS 执行脚本，改 DOM 动态内容
React 把组件渲染成 DOM 交互界面
Next 决定 SSR/SSG/CSR 在哪渲染 首屏 HTML
  • 第一问：白屏一般是哪慢？
  • 答：要么 JS 包太大没下载完，要么接口阻塞首屏数据（SSR 时服务端卡住）。
  • 第二问：错误状态怎么展示？
  • 答：React 用 ErrorBoundary，接口失败走 loading/error UI（D1 明确要求）。
  • 第三问：权限状态怎么控制显示？
  • 答：服务端校验后下发数据范围，前端只渲染有权限的部分，但校验必须在服务端（D5）。

一句话话术：「用户输入 URL，浏览器拿回 HTML 建 DOM，CSS 算样式，JS/React 把组件填上，Next 决定这部分在服务端还是浏览器算。」

2.1.1 浏览器渲染五步

步骤 做什么 卡在哪会慢
1 DNS 域名解析成 IP 首屏多域名未预解析
2 TCP/TLS 建连、握手 未开 HTTP/2、证书重协商
3 请求/响应 拿 HTML 后端 SSR 慢、接口阻塞
4 解析/布局 建 DOM、算样式 JS 阻塞解析
5 绘制 像素上屏 大量重排重绘

一句话话术：「白屏多半是 HTML 没回来或 JS 没下完；数据驱动页面还要等接口，SSR 能省一次客户端请求。」

  • 第一问：JS 放 head 会怎样？
  • 答：默认阻塞解析，加 defer/async 或放 body 末尾，React 通常由打包器处理。
  • 第二问：SSR 省了什么？
  • 答：省掉客户端再发一次数据请求，首屏 HTML 已带数据（见 2.5 三态）。

2.1.2 重排、重绘与合成

概念 触发 代价
重排（reflow） 改尺寸/位置/结构 最高，要重新算布局
重绘（repaint） 改颜色/背景 中，不算布局
合成（composite） 改 transform/opacity 最低，GPU 层位移

一句话话术：「改布局比重绘贵，改 transform/opacity 最便宜走合成层；动画用 transform 别用 top/left。」

  • 第一问：React 怎么避免无谓重排？
  • 答：state 下沉到最小组件、用 useMemo/useCallback 减少重渲染、列表用 key 复用节点。
  • 第二问：开发者工具怎么看？
  • 答：Performance 面板录一段，看长任务和时间线，定位卡在哪一步。

是什么：TS 是带类型的 JS 超集，编译回 JS 跑。

2.3.1 闭包与模块

闭包（是什么/为什么/本岗）

  • 是什么：函数捕获了定义时外层作用域的变量，即使外层执行完，变量仍可被访问。
  • 为什么：它让函数带上「记忆」，但也会造成 useState 闭包陷阱（拿到旧值）。
  • 本岗哪里用得上：R2，事件回调、定时器里最容易踩。

模块（是什么/为什么/本岗）

  • 是什么：ES Module 用 import/export 拆分文件，export default 默认导出、具名导出多个。
  • 为什么：避免全局变量污染，依赖关系显式。
  • 本岗哪里用得上：R2，组件、hook、api 调用都按模块组织。
问法 一句话答 追问
闭包陷阱怎么破 用函数式更新 setX(prev=>...) 或把依赖放进依赖数组 useEffect 漏依赖会怎样
default 和具名导出 default 一个、具名多个，import 对应写法不同 循环依赖呢

2.3.2 Promise 链与 async

  • 第一问：await 后面一定要 try/catch 吗？
  • 答：不包会抛到上层，组件里常在调用处统一 catch，或用错误边界兜 UI。
  • 第二问：多个请求怎么并发？
  • 答：Promise.all([a,b]) 并行等全部完成；有一个失败整体失败，用 allSettled 要逐个看状态。

2.3.3 模块组织例子

  • 第一问：为什么拆分 api / hooks / 页面？
  • 答：请求逻辑可复用、可单测，页面只渲染，职责清晰。
  • 第二问：类型怎么共享？
  • 答：User 类型在 api 层定义，hooks 和页面 import 复用，改一处全链路报错（tRPC 更进一步自动同步）。

2.4 React 核心

是什么：React 用函数组件返回 JSX 描述 UI，靠 state 驱动重渲染。
为什么：组件化让后台页面可复用、可维护。
本岗哪里用得上：D1 表格/表单/弹窗全用 React 组件。

概念 一句话 与 Vue3 对照
组件 返回 JSX 的函数 像 Vue 的 SFC
props 父传给子的只读数据 像 Vue props
state 组件自己的可变数据 像 Vue ref/reactive
JSX 像 HTML 的语法写 UI Vue 用模板
Hooks useState/useEffect 等 Vue 用组合式 API
列表 key 帮 React 识别每项 Vue 也要 :key
受控表单 value+onChange 绑 state Vue v-model
Hook 作用 易错点
useState 局部状态 更新是异步批处理的
useEffect 副作用（请求/订阅） 依赖写错拿旧值
useMemo 缓存计算结果 不是为性能乱用
useCallback 缓存函数引用 依赖变就失效
useRef 存可变引用，不触发重渲染 改 .current 不重渲染
  • 第一问：为什么用 key？
  • 答：让 React 在列表增删时正确复用/重建节点，避免状态错乱。
  • 第二问：useEffect 依赖写错会怎样？
  • 答：依赖少了会拿到旧值，依赖多了会重复执行，StrictMode 双调用能暴露这类 bug。
  • 第三问：Context 解决什么？
  • 答：跨多层传数据不用一层层 props，但值变了所有消费者重渲染，配合细粒度状态库更好。

一句话话术：「React 组件是函数，state 变了就重渲染，useEffect 管副作用，key 帮 React 认出列表每一项；和 Vue 比，Vue 靠响应式自动追踪，React 靠状态驱动。」

2.4.1 状态提升、渲染与重渲染、StrictMode

概念 一句话 与 Vue3 对照
状态提升 子组件共享状态提到最近公共父组件，用 props 下发 Vue 用 emit 上抛或用 store
渲染与重渲染 state/props 变就重渲染该组件及子树 Vue 靠响应式精准更新
Context 跨层传值，避免逐层 props Vue 用 provide/inject
StrictMode 开发期双调用挂载/卸载，暴露副作用 bug Vue 无完全对应
  • 第一问：React 重渲染会拖慢吗？
  • 答：会，所以 useMemo/useCallback 缓存、Context 拆细、状态下沉到最小范围。
  • 第二问：StrictMode 双调用线上也双调用吗？
  • 答：只在开发环境，用来逼你写幂等的副作用（effect 能安全跑两遍）。
  • 第三问：状态提升和 Context 怎么选？
  • 答：少量共享用提升+props，跨多层用 Context，但 Context 值变全体消费者重渲染。

2.4.2 受控表单完整例子

一句话话术：「受控表单把输入绑到 state，每次输入走 onChange 更新，提交时直接读 state，校验和联动都方便。」

  • 第一问：为什么用不可变更新？
  • 答：React 靠引用变化判断要不要重渲染，直接改对象旧引用不触发更新。
  • 第二问：非受控什么时候用？
  • 答：简单一次性表单用 ref 取值，少一次渲染，但实时校验不便。

2.4.3 React 与 Vue3 全面对照

维度 React Vue3 本岗注意
组件 函数返回 JSX SFC <template> 你 Vue 经验直接迁移
状态 useState/useReducer ref/reactive React 靠重渲染
副作用 useEffect watch/watchEffect 依赖数组 vs 依赖函数
事件 onClick={fn} @click=”fn” 命名风格不同
双向绑定 受控 value+onChange v-model 受控即手动版 v-model
状态管理 Jotai/Redux Pinia VidDigest 用过 Pinia，近亲
路由 Next 文件路由 vue-router 概念一致

一句话话术：「我 Vue+TS 写过（VidDigest），React 的 useState 对应 Vue 的 ref，useEffect 对应 watch，组件化思维完全通用。」

  • 第一问：Vue 的 v-model 在 React 怎么写？
  • 答：React 没有内置双向绑定，用受控组件 value+onChange 手动实现，等价 v-model。
  • 第二问：Pinia 和 Jotai 区别？
  • 答：Pinia 是集中 store，Jotai 是原子粒度，订阅更细、无样板（见 2.6）。

2.4.4 useMemo/useCallback 实战

一句话话术：「useMemo 缓存昂贵计算，useCallback 缓存函数引用，避免每次渲染重算或子组件白重渲染。」

  • 第一问：什么时候不用 useMemo？
  • 答：计算很便宜时加了反而更慢，只有确实重或依赖频繁变才用。
  • 第二问：依赖写错会怎样？
  • 答：拿到过期值，和 useEffect 一样要靠 lint 规则兜底。

2.6.1 三者分工表

库 管什么状态 典型场景 不放什么

3.4.5 GMP 调度一句话

是什么：Go 调度器三件套——G（goroutine 协程）、M（机器 OS 线程）、P（处理器，逻辑 CPU 上下文）。
为什么：把海量 goroutine 映射到少量线程，靠 work-stealing 均衡，所以十万协程也不卡。
本岗哪里用得上：D2 异步任务、worker 高并发，理解调度能定位卡顿/泄漏。

字母 含义 类比 Java
G goroutine 协程 Thread 对象
M OS 线程 内核线程
P 处理器（上下文） 线程池的 slot
  • 第一问：goroutine 比线程便宜在哪？
  • 答：初始栈几 KB（线程 MB 级），创建/切换由 Go runtime 管，不进内核。
  • 第二问：work-stealing 是什么？
  • 答：某个 P 空闲时从别的 P 偷一半 G 来跑，避免忙的忙死、闲的闲死。

是什么：net/http 是标准库；chi 是轻量路由，兼容 net/http。
为什么：chi 路由分组/中间件简单，本岗用 chi v5（小版本以 go.mod 为准）（JD 技术栈）。
本岗哪里用得上：R3/P1，D2 后端接口。

问法 一句话答 追问
chi vs gin chi 纯 net/http 无锁定，gin 自带 ctx 中间件怎么写（r.Use / r.With）
URLParam 从路径 {id} 取值 正则约束（{id:[0-9]+}）
优雅关机 监听 SIGTERM 调 Shutdown worker 怎么停（停消费+等完成）

一句话话术：「chi 用 NewRouter+r.Get 注册路由，URLParam 取路径参数，Logger/Recoverer/Timeout 是中间件，优雅关机靠 Shutdown 接 SIGTERM。」

3.5.1 中间件清单

中间件 作用 来自

middleware.RequestID 每请求生成 ID 串起日志 chi/middleware

一句话话术：「chi 中间件是洋葱模型，Logger/Recoverer/Timeout 官方就有，鉴权自己写个读取 token 注 context 的。」

3.5.2 一个最小 chi 服务

一句话话术：「一个最小 chi 服务就是 NewRouter 加中间件，再 Route 分组挂 handler，超时/日志/恢复官方中间件直接 Use。」

  • 第一问：handler 签名为什么是 func(w,req)？
  • 答：chi 兼容标准 http.HandlerFunc，所以任何 net/http 处理函数都能直接用。
  • 第二问：分组路由好处？
  • 答：公共前缀和中间件就近挂，权限中间件可只对 /api 组加。

3.5.3 自定义鉴权中间件

一句话话术：「鉴权写成中间件，解析 token 后把 user 注进 context，下游 handler 直接取，不重复解析。」

  • 第一问：鉴权放哪层？
  • 答：放路由中间件或 BFF 聚合层（二章 2.8），但 Go 服务也要再校验一次（D5 服务端校验）。
  • 第二问：未登录返回什么？
  • 答：返回 401，并走统一错误映射（3.3.2），不泄露细节。

3.5.4 路由参数校验实战

  • 第一问：正则约束放哪？
  • 答：路由定义写 /users/{id:[0-9]+}，不匹配直接 404，不用手写校验。
  • 第二问：参数校验放 handler 还是 service？
  • 答：格式校验 handler 做，业务规则（如余额够不够）放 service。

3.5.5 中间件洋葱模型

请求方向 经过 响应方向
进 Logger → Recoverer → Auth → Handler 出：反向穿透

一句话话术：「中间件像洋葱，请求一层层进、响应一层层出；越先 Use 越在外层，单路由用 With 就近加。」

  • 第一问：Recoverer 放哪？
  • 答：放靠前，能兜住后面所有 handler 的 panic，避免进程崩。
  • 第二问：Auth 为什么可只挂部分路由？
  • 答：公开接口（如登录）不能拦，用 r.With(Auth) 只给需要登录的路由套。

3.6 后端分层

是什么：handler→service→repository→db 按职责切。
为什么：业务逻辑和数据库解耦，便于测试和替换。
本岗哪里用得上：R3 后端分层、D2。

层 职责 原则
handler 解析/响应，不做业务 薄
service 规则/事务/编排 接口在本层定义
repository SQL/GORM 访问 返回 domain 对象
  • 第一问：为什么 repository 用接口？
  • 答：便于 mock 测试与替换存储。
  • 第二问：接口放哪一侧？
  • 答：Go 惯例放在消费侧（service 定义，repository 实现），编译期检查实现。
  • 第三问：DTO 和 domain 为什么分离？
  • 答：避免把内部字段泄露给前端，边界处做转换。

一句话话术：「handler 只接请求调 service，service 写业务和事务，repository 管数据；依赖方向单向，接口在 service 侧定义方便 mock。」

3.6.1 DTO 与 domain 边界

是什么：DTO 是对外传输结构，domain 是纯业务结构，两者分开转换。
为什么：不把内部字段（如密码哈希、内部状态）泄露给前端。
本岗哪里用得上：R3、D2，接口出入参都要 DTO。

  • 第一问：为什么不直接返回 domain？
  • 答：避免内部字段泄露，金额格式（6 位/2 位）在转换处统一（D3）。
  • 第二问：转换放哪层？
  • 答：handler 或专门的 mapper，service 只认 domain。

3.6.2 接口定义与 fake 测试

  • 第一问：为什么 service 依赖接口不是结构体？
  • 答：编译期要求实现，测试注入 fake，替换存储零成本。
  • 第二问：fake 怎么写？
  • 答：手写一个内存 map 实现 AccountRepo，断言 service 行为，跑 -race 查竞争（3.8）。

3.6.3 完整目录约定

  • 第一问：handler 能直接调 repository 吗？
  • 答：不推荐，越过 service 会把业务逻辑漏进边界层，事务也难管。
  • 第二问：middleware 放哪？
  • 答：可放 internal/middleware，handler 或 router 装配，全局 Use 或单路由 With。

3.7 GORM 与事务

是什么：GORM 是 Go 的 ORM，把表映射成 struct。
为什么：少写 SQL，事务 API 简单。
本岗哪里用得上：P4、D2 客户/账户/钱包模块。

问法 一句话答 追问
防 N+1 Preload/Joins 预加载关联 AutoMigrate 能上生产吗（不推荐，用 Atlas）
事务 db.Transaction 包一层，返回 error 回滚 事务里能调 HTTP 吗（尽量不，会长事务）

一句话话术：「GORM 用 struct tag 映射列，Preload 防 N+1，db.Transaction 包业务自动提交/回滚；生产 schema 用 Atlas 管，不靠 AutoMigrate。」

3.7.1 GORM 钩子、软删除与 Atlas 边界

概念 一句话 本岗注意
BeforeCreate/AfterUpdate 创建/更新前后自动跑 别在里面做重 IO
软删除 DeletedAt 删了只是打标记 查询默认过滤已删
AutoMigrate 按 struct 建表 谨慎上生产
Atlas schema 版本化管理 生产用 atlas migrate，不靠 AutoMigrate（四章）

一句话话术：「GORM 钩子做自动字段填充，软删除靠 DeletedAt；生产 schema 走 Atlas 版本迁移，AutoMigrate 只适合本地开发。」

  • 第一问：AutoMigrate 为什么不能上生产？
  • 答：GORM AutoMigrate 会创建表/补列/补索引，不会主动删除未使用的列；风险在于无版本化、不可回滚、难审计，以及类型变更与锁表影响，生产用 Atlas 受控迁移（P4、四章）。
  • 第二问：N+1 除了 Preload 还有啥？
  • 答：Joins 预加载或手写单条聚合 SQL。

3.7.2 一个最小 GORM 用例

  • 第一问：余额为什么用 int64 分？
  • 答：金钱不用 float，用整数最小单位（分）或 NUMERIC(20,6)，避免精度丢失（见四章/五章）。
  • 第二问：ErrRecordNotFound 怎么来的？
  • 答：db.First 查不到返回 gorm.ErrRecordNotFound，用 errors.Is 判断再转 404。

3.7.3 事务实战：扣款并写流水

一句话话术：「扣款和写流水放进一个 Transaction，任一步出错整体回滚，保证账钱一致；返回非 nil 触发回滚。」

  • 第一问：事务里能调外部 HTTP 吗？
  • 答：尽量不，会拉长事务、锁资源、可能不一致；用 Saga/异步补偿。
  • 第二问：余额更新用表达式为什么安全？
  • 答：gorm.Expr("balance - ?") 在数据库侧原子算，避免先读后写竟态（见四章并发更新）。

4.2 索引

索引类型/技巧 用法 何时用
B-tree（默认） CREATE INDEX ON t(col) 等值/范围/排序
复合索引 (a,b) 查询条件含 a 且 b，遵循最左前缀
覆盖索引 INCLUDE (c) 只读 c，实现 Index-Only Scan
部分索引 WHERE status='pending' 只索引热点子集，减体积
表达式索引 ON t (lower(email)) 查询条件对列做函数
GIN jsonb/数组/全文 半结构化查询

最左前缀：复合索引 (a,b) 能加速 a、a+b，不能加速单独 b。覆盖索引 INCLUDE 把非键列塞进叶子，避免回表。

EXPLAIN (ANALYZE, BUFFERS) 读法：看 Seq Scan（全表扫描，索引没用上）vs Index Scan/Index Only Scan；actual time 是真实耗时；rows 估算与实际差距大说明统计信息过期。

何时不建：写多读少的小表；低区分度列（如性别）；已有索引覆盖的前缀；函数查询没建表达式索引。过度索引拖慢写入与 VACUUM。

失败案例 1：对 WHERE lower(email)=? 建了普通索引 (email)，查询仍 Seq Scan——因为对列做了函数，索引键不匹配，应建表达式索引 ON t(lower(email))。

失败案例 2：复合索引 (user_id, created_at)，查询只按 created_at 过滤，索引完全没用上——违反最左前缀，应把高频单独过滤列放前或另建索引。

问法 一句话答 追问
索引失效常见原因 对列做函数/类型转换、隐式转换、前缀 %LIKE、OR 条件 你怎么定位
覆盖索引是什么 把查询需要的列放进 INCLUDE，避免回表 和普通复合索引区别

4.3 事务与隔离级别

ACID：原子性（全成全败）、一致性（约束不破）、隔离性（并发互不干扰）、持久性（提交后不丢）。

隔离级别 PG 行为 防住的现象
Read Uncommitted PG 实现为 Read Committed —
Read Committed（默认） 每条语句新快照 脏读
Repeatable Read 事务开始时快照 不可重复读；PG 的 RR 还防幻读（快照）
Serializable SSI（可串行化快照隔离） 写偏斜（write skew）

幻读在 PG：Read Committed 下可能看到新插入行；RR 快照下看不到，但并发写会触发序列化失败（40001）需重试。

锁：行级 SELECT ... FOR UPDATE（写锁）/FOR SHARE（读锁）；表级 LOCK TABLE；咨询锁 pg_advisory_xact_lock。死锁 PG 自动检测并回滚一方，应用按 40P01 重试。

长事务危害：阻塞 VACUUM、表膨胀、持锁久；用 statement_timeout 和 idle_in_transaction_session_timeout 兜底。事务内不调外部 HTTP（见 3.7）。

追问链：第一问「幻读在 PG 怎么表现？」→ 答：Read Committed 下新插入行可见；RR 快照下不可见但并发写会序列化失败。第二问「死锁怎么处理？」→ 答：PG 回滚一方，应用捕获 40P01 重试。第三问「长事务为什么危险？」→ 答：阻塞 VACUUM 膨胀表，设超时。

  • 参考解法代码块（Go，≤20 行，简洁可写）
  • 易错点：死锁（忘记发信号）、通道关闭时机、协作次数不一致。

题3：slice 去重（保留顺序）

  • 考察点：map 用作去重、切片操作
  • 题目：用 Go 实现 slice 去重，保留首次出现顺序。
  • 参考解法代码块（Go，≤20 行）
  • 易错点：用 bool 也可但 struct{} 更省内存；未保留顺序的做法不可取。

题4：并发安全计数（sync.Mutex）

  • 考察点：竞态、sync.Mutex、go run -race 意识
  • 题目：用 10 个 goroutine 各加 1000 次，实现并发安全计数。
  • 参考解法代码块（Go，≤20 行）
  • 易错点：忘记加锁导致竞态；也可用 sync/atomic（思路类似），面试讲清二者区别即可。

题5：简单 HTTP handler（net/http）

  • 考察点：HTTP 基础、JSON 编码
  • 题目：用 net/http 写一个 /ping 接口，返回 JSON {"msg":"pong"}。
  • 参考解法代码块（Go，≤20 行）
  • 易错点：忘记设置 Content-Type；错误处理（示例简化但需知道要处理错误）。

题1：防抖（debounce）

  • 考察点：闭包、setTimeout、this 处理（思路）
  • 题目：手写 debounce，n 毫秒内只执行最后一次。
  • 参考解法代码块（TS，≤20 行）
  • 易错点：this 丢失、timer 类型、清除时机。

题2：深拷贝（简化版）

  • 考察点：递归、类型判断、循环引用可简要提及
  • 题目：实现简易 deepClone（处理对象/数组/基础类型）。
  • 参考解法代码块（TS，≤20 行）
  • 易错点：Date/RegExp 等特殊对象可简要说明（面试板上先写最小可用版）；循环引用需意识到（可提思路不强求全实现）。

题3：数组扁平化（flat 简易）

  • 考察点：递归、Array.isArray
  • 题目：实现 flatten，处理一层或递归扁平化（讲思路即可）。
  • 参考解法代码块（TS，≤20 行）
  • 易错点：深度控制、尾递归不可强求。

题4：手写 Promise.all（简化）

  • 考察点：Promise、数组遍历、计数、顺序
  • 题目：手写简易 PromiseAll，全部成功才 resolve，任意 reject 则 reject。
  • 参考解法代码块（TS，≤20 行）
  • 易错点：结果顺序需按索引存入；空数组要处理；要用 Promise.resolve 统一处理非 Promise 值。

题5：类型收窄（类型守卫）

  • 考察点：联合类型、类型收窄、泛型思路
  • 题目：用类型守卫处理联合类型，避免运行时错误。
  • 参考解法代码块（TS，≤15 行）
  • 易错点：用 in/typeof 做类型守卫；联合类型要配合可辨识字段（discriminated union）。

题1：按客户聚合消耗

  • 考察点：GROUP BY、SUM、ORDER BY
  • 题目：有 orders(customer_id, amount, created_at)，统计每个客户总消耗并按总额降序。
  • 参考解法（SQL，≤10 行）
  • 易错点：GROUP BY 包含非聚合列；金额类型用 NUMERIC 时聚合无精度丢失（注意岗位金额场景用 NUMERIC）。

题2：找出两表对账差异（NOT EXISTS / FULL JOIN）

  • 考察点：对账思路、差异查找
  • 题目：bill_internal(order_id, amount) 和 bill_external(order_id, amount)，找出仅一边存在或金额不一致的订单（简化版）。
  • 参考解法（SQL，≤10 行，PostgreSQL 风格）
  • 易错点：金额用 NUMERIC 比较要注意类型；NULL 处理用 COALESCE/IS NULL。

题3：联合索引命中与 EXPLAIN 思路

  • 考察点：最左前缀、覆盖索引、EXPLAIN ANALYZE
  • 题目：表 consumptions(account_id, date, amount)，建联合索引 (account_id, date)，分析以下查询能否命中索引并说明思路。
  • 参考解法思路（白板）：
    • 查询1：满足最左前缀 (account_id, date)，大概率命中索引（走索引查找或索引扫描）。
    • 查询2：跳过最左列 account_id，只用 date，不满足最左前缀，通常走全表扫描（除非有其他索引）。
  • 验证手段：用 EXPLAIN (ANALYZE, BUFFERS) 查看 Index Scan 还是 Seq Scan、rows 预估、实际耗时。
  • 易错点：SELECT * 可能导致回表（需覆盖索引才会 Index Only Scan）；函数套用索引列（如 DATE(date)=...）可能导致索引失效。

九、明天进门清单

本章解决什么面试问题：把前面内容压成明天能直接用的清单（自我介绍、反问、英文速读、时间线、核对）。

9.1 30 秒自我介绍逐字稿（第一人称，可背）

按简历事实来讲，短板要”承认+补课”，不夸大。

逐字稿：

“我叫梁杰豪，是广东海洋大学计算机科学与技术 2027 届本科生。我做过 Vapor 优选，用 Redis+Lua 做过资格校验和库存扣减的原子处理；做过 VidDigest，用 pytest 和变异验证去提升接口测试有效性，还做过权限回查和限流断言；在踏浪 AI 中心我做过 CR 清单和检索优化这类工程化实践。

Go 和 React 我目前还在补，Java 后端基础能帮我对照学习，chi + GORM + PostgreSQL 的 CRUD 正在跑通，目标是面试前跑通，React Hooks 也在补。对这家做 TikTok 广告运营平台的全栈实习生岗位很感兴趣，想从小功能开始学着处理业务里对金额准确性和数据权限的要求。”

节奏提示：开头报姓名和学校用正常语速；三个”做过”之间各停半秒，让面试官跟上；讲到”还在补”时放慢、坦然不遮掩；最后一句”想从小功能开始…”放慢收尾，说完停一下，再把话头交给面试官。

控制在 25-30 秒。讲项目时用”做过…”概括方法论即可，不强行报未给出的数字。

9.2 反问清单 6 条（针对”预发布→上线”阶段）

序号 反问问题 目的（想了解什么）
1 “团队现在平台处于预发布还是正式上线前的哪一步？最关键的待办是什么？” 判断节奏（联调/验收/上线），了解真实优先级。
2 “如果我入职，第一个会让我做的小功能大概是什么？是前端页面还是后端接口？” 明确带教预期，便于提前想思路但不臆测实现。
3 “日常联调时，前后端是怎么对齐接口的？用 OpenAPI、tRPC 还是直接约定文档？” 对应岗位技术栈（OpenAPI、tRPC、BFF），了解实际用法。
4 “上线前会怎么做预发布验证？有没有回归清单或者回滚预案？” 对应 D6，体现对”测试与上线”的关注。
5 “带教前 3 个月大概怎么安排？我需要重点先补 Go 还是先熟悉业务流程？” 主动表达学习意愿，获取针对性建议。
6 “转正的关注点主要是哪个方面？比如功能交付、代码质量、还是对业务（金额/权限）的意识？” 获取转正预期，后续用行动去靠近。

9.3 英文技术文档速读四步法（以 TikTok Marketing API 文档为例）

岗位要求”能读英文技术文档”（P6）。用四步法速读，不求全懂，求能问对问题。

步骤 操作 要点
第1步：找 endpoint 看 Overview/Endpoints，先锁定要用的接口路径和方法（GET/POST）。 别从头逐字读，先找”Create/Report”这类关键词对应的 endpoint。
第2步：看鉴权 找 Authentication/Authorization，确认是 access token、OAuth 还是其他方式。 注意 token 获取方式、有效期、是否需要刷新。
第3步：看必填参数 看 Request/Parameters，先列出 required，再看可选。 用笔记列 required 清单，能用最少信息拼出一次请求。
第4步：看错误码与限流 找 Errors/Rate limit/Quota，关注常用错误码、重试建议、限流规则。 尤其关注 429（可能配 Retry-After，没带时按退避策略处理）、权限相关错误码和是否有限流。

实战话术（面试提到文档阅读时用）：

“我会先找 endpoint 和鉴权，再列出必填参数，最后重点看错误码和限流，边读边用最小请求去验证，不求一次全懂。”

9.4 时间线表：今晚 / 明早 / 面试中 / 入职后 7 天

时间段 重点 建议动作
今晚 巩固框架 把第七章项目映射过一遍（用 STAR 精简版讲一遍），把第八章 Go/TS 各挑 1-2 题白板练习，背熟 30 秒自我介绍。
明早 查漏补空 用第九章清单自查：简历、项目要点、两个能讲清的项目细节（用简历原表述）、笔记本/纸笔。按四步法过一遍 TikTok Marketing API 文档结构（只看目录和鉴权页）。
面试中 实战节奏 先用 30 秒自我介绍；项目深挖用 STAR 精简版+7.6 追问链；短板用 7.5 三件套（承认+可迁移+补课证据）；不会的题先讲思路再讲已知部分；遇到业务题用”对账/权限”意识去回答（服务端校验、可追溯）。
入职后 7 天 熟悉节奏 第 1-2 天：熟悉业务流程（开户→钱包→消耗→对账→返点）和权限角色；第 3-4 天：跟着带教跑小功能，搞懂接口对齐方式（OpenAPI/tRPC/BFF）；第 5-7 天：补齐 Go 最小实战（chi 路由+中间件+错误处理）和 Next.js Pages Router 最小页面，先学会看日志和定位问题。

9.5 进门核对清单（checkbox）

材料准备

  • 简历：打印或电子版，和 materials-resume.md 一致（项目表述用原样要点）

  • 自我介绍：30 秒逐字稿背熟（含三个项目各一句 + 短板认知 + 为什么来这岗）

  • 短板话术：Go/React/对账权限三件套各能用一句话说出
  • 反问：选 2-3 条反问提前想好顺序

当天细节
