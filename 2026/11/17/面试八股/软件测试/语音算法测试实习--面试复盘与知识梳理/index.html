0.3 三个答崩点与根因

答崩点一，ASR：把「用 ASR」当成「测 ASR」。 我停在应用层，思路是「有字幕就不走 ASR，没有就走云端 ASR」。这是使用者视角。测试视角要回答的是另一串问题。输入是一段音频，输出是一段文本，怎么判这段文本对不对。骨架是四步，先定参考文本（人工听写转写），再定归一化规则（大小写、标点、数字与时间的读法统一），然后算字错率或词错率，最后按噪声、口音、语种分片看哪片最差。这一串我一个字没说出来。

答崩点二，语种：答的是自己项目的语种，不是岗位的语种。 我说中文英文，理由是视频字幕里有英文。这是把「我的场景」套到「他们的场景」。他们做跨境，测的是中英日德意法西七种语种，还要管语种切换和每种语种的模型效果。面试前应该先问清楚语种范围，或者至少答「中文和英文为主，如果涉及跨境多语种，我会按语种分片统计」。

答崩点三，Python：答「基本语法能看懂」。 这句话在「Python 脚本开发」写进 JD 的前提下是负分。正确答法是往做过的靠：pytest 用例集写过，参数化与 fixture 用过，能写脚本读文件、批量跑、算指标、导出 CSV，板端串口脚本在实训里跑过。承认「正在从 Java 往 Python 转」没问题，但不能把会读代码说成会写脚本。

0.4 面试官免费给的行业信息

这一段是整场面试的收获，比我答出来的部分值钱，因为它是他从内部视角讲的。

他说的原话要点 翻译成知识
唤醒词测试是独立一块 指标是唤醒率加误唤醒控制
指令准确率不测，指令归 NLP那块 团队按算法域分工，语音测试不背 NLP 的锅
声纹要判是不是本人：本人一定能进，不是本人也能进就不行 声纹测误接受与误拒识，双向指标
ASR 转写出来后要做归一化，大小写、数字、时间统一，不然算准确率会判错 归一化是 ASR 评测的前置步骤，不是可选项
TTS 要算音频的准确率，涉及语种比较多 TTS 侧要管多语种，指标含主观听感

项目还在早期阶段，节奏比较紧 早期团队，进来要能自己开路

0.5 对结果的判断

正面信号有三个。面试官愿意花时间把业务讲一遍，通常是想让候选人愿意来；岗位是补人，用人节奏急；结尾的评价是偏正面的。风险信号有两个，他当面点出我在语音这块没有涉猎，另外 Python 那段的回答也偏弱。

综合看，这次面试大概率是「流程往前走但技术面要补」的阶段。下一轮如果还有，考察点大概率就是语音评测的基本功。

一、岗位真相与公司画像

1.1 「你了解我们公司什么」怎么答

这类问题考三件事：知道它卖什么、知道它现在靠什么增长、知道你的经历跟哪条线对得上。答法三层，每层两句。

先认这类公司的通用画像，面试前用年报或官网核一遍，别背别人的稿。

维度 通常是这个样子 面试前怎么核
品类结构 充电、办公外设、影音、存储四条线，充电是现金牛，存储是新增量 年报的品类收入与占比表
增长来源 出海为主，线上销售占比高，常年依赖跨境电商渠道 年报的分地区收入与销售模式
技术动向 端侧 AI：设备本地跑识别与检索，云端只做增值；语音、视觉、存储各自有算法团队 年报研发项目披露，别把在研说成已量产
岗位落点 算法测试按算法域分组，语音与语义理解、图像各归各 面试里直接确认

三层答法，六十秒左右，别背年报。

这是一家做消费电子出海的品牌，产品线覆盖充电、办公、影音和存储，海外收入占大头，线上渠道为主。

我注意到它近两年在往端侧 AI 走，存储线在做本地的图片与文件检索，耳机那边有拾音与降噪算法。所以技术岗的活不是测网页，是测跑在设备上的算法准不准、稳不稳。

我自己做过的是把输出拆成口径再量化，AI 问答拆成准确性、召回和事实性，用固定问题集回归。这套做法换到语音的唤醒、识别、合成上，数据结构不同，方法是一套。

追问预案。

追问 回答要点
你看的哪份材料 最近一期年报的品类与研发章节，加上官网产品页
为什么说端侧是趋势 端侧省带宽、隐私不出去、断网可用；代价是模型要压缩，指标会掉
你觉得这类公司最大的质量风险 说产品线跨度大：充电是硬件安全，存储是数据可靠性，耳机是音频体验，三类质量标准完全不同，测试体系得按线分开管。这是判断，不是内部消息
这个岗位具体测哪块 反问确认语音、语义理解、图像的边界，别默认自己全包

不要说的话：不编内部组织架构、团队人数、缺陷平台，也不打探薪资与编制细节。这三样说错一句，整段可信度归零。

1.2 四块业务的边界

块 测什么 主指标 典型失败
唤醒词 有没有听到那句唤醒词 唤醒率、误唤醒率、漏唤醒率 电视背景音误唤醒、安静环境漏唤醒
声纹 是不是本人 误接受率、误拒识率、阈值 别人能开锁、本人开不了
ASR 语音转文本对不对 字错率、词错率、首字延迟 数字与专名错、噪声下掉字
TTS 文本转语音好不好 主观 MOS、发音正确率、多语种一致性 读错多音字、语种口音怪、韵律平

一句话区分，面试时能直接说：唤醒和声纹是「有没有听到、是不是本人」，ASR 是「听到的内容转对没有」，TTS 是「说出来的话像不像」。这四个问题的判定方式完全不同，指标也就完全不同。

1.3 他们不测什么

指令理解不在语音这一段的范围内，图像算法另有方向。语音测试工程师的边界在声学与识别这一侧，不在语义理解那一侧。回答问题时先分清自己在讲哪一块，这是这类团队做事的方式。

1.4 端侧带来的额外约束

他们测的是端侧。端侧意味着模型要压到能塞进设备，量化前后指标会变；意味着断网要能用，唤醒要在本地完成；意味着要盯首字延迟与功耗，不能只看准不准。

二、语音算法测试的知识点

这一章是本次面试答崩的地方，按面试官讲的四块业务写：唤醒、声纹、ASR、TTS。每块给「测什么、指标怎么算、数据怎么造、面试怎么答」。

2.1 唤醒词：唤醒率与误唤醒

唤醒是二分类任务，答案在两个错误率上。

指标 口径 说明
正确接受率（唤醒率） 说了唤醒词被唤醒的比例，接近召回率 漏掉的那部分就是 FRR，漏唤醒率
错误接受率（误唤醒率） 没唤醒词却被唤醒的比例 越小越好，和唤醒率此消彼长
误唤醒次数 常见报告单位是 FA/h，即每小时误唤醒几次 直接报百分比没有可比性
唤醒延迟 从说出唤醒词到设备响应的时间 端侧体验指标

误唤醒的折算方法：在总时长 T 小时的负样本音频上跑检测器，统计误唤醒次数 k，报 k/T 次/小时，同时给出 T、k、音频类型和触发计数规则。样本量也要交代，稀有事件可以按泊松计数近似，k 等于 0 时单侧 95% 上界约 3/T 次/小时，也就是说想声称「10 小时一次误唤醒」而不报错，得跑够 30 小时左右的负样本。

测试集分两半。正样本含唤醒词，按说话人、距离、口音、噪声与信道分片。负样本不含唤醒词，用来做误唤醒统计，常见来源是电视与媒体播放、日常对话、环境声，以及和唤醒词近似的短语这类难负样本。厂商的公开测试报告会给过具体条件下的例子，比如音乐 55 dBA 跑 12 小时误唤醒 1 次，这类数字只能当示例，不能当标准。

面试怎么答：

唤醒这块我会看两个数：正确接受率，也就是说了唤醒词被唤醒的比例；以及误唤醒率，这个我们一般不用百分比报，用每小时误唤醒几次，因为负样本时长不同百分比没法比。测试集正负分开，正样本按说话人、距离、口音分片，负样本主要是电视背景音、日常对话和近似音，用来逼出误唤醒。报的时候把负样本总时长和误触发次数一起给出，别人才知道这个数怎么来的。

2.2 声纹：是不是本人

声纹测的是「本人能不能进、别人能不能进」，所以两个方向的错误都要看。

概念 说明
说话人验证 1 比 1，判断是不是所声称的那个人
说话人辨识 1 比 N，判断这个人是谁
开集与闭集 闭集假设待测的人都注册过；开集要处理未注册的人，得多测一层拒识
错误接受率 FAR 把非本人当成本人放行的比例
错误拒绝率 FRR 把本人拒绝掉的比例
等错误率 EER FAR 与 FRR 相等时的那个错误率，由阈值扫描得到，衡量整体性能

阈值一动，FAR 与 FRR 就此消彼长，所以声纹测试一定要连着工作点报：在固定 FAR 下的 FRR，或者在固定阈值下的两个数。只报一个 FAR 没有意义。

多语种场景要额外覆盖口音、信道、设备和人群多样性，训练与测试条件不匹配会明显掉点；开集场景要单独测未知说话人的拒识。

面试怎么答：

声纹我理解是验证加辨识两种任务分开看。我这边更关心误接受和误拒识这两个方向，因为业务上两个都要卡：本人一定要能进去，别人进来就不行。阈值是取舍，所以不能只报一个数，要报工作点，比如在误接受率多少的前提下误拒识是多少。多语种还要把口音和信道拆开看。

2.3 ASR：转写对不对

这是本次面试彻底答崩的一块，也是他们团队最核心的日常，所以放在最前面写。

指标口径。

指标 口径 说明
WER 词错率 (替换 + 插入 + 删除) / 参考词数，词级对齐 语音识别的事实标准，分母是参考词数，所以可以大于 100%
CER 字错率 同上，改在字符级 中文与日文没有天然的词边界，词级切分不稳定，实测多用 CER；若项目约定分词口径，也可报 WER
RTF 实时率 处理耗时 / 音频时长，小于 1 表示快于实时 端侧能不能跑得动
首字延迟 从开始说话或开始送音频到输出第一个可用字 流式体验，各家起止点定义不同
端点检测延迟 系统判定用户说完到给出最终结果之间的等待 太长用户觉得迟钝，太短容易截断
时间戳偏移 字幕起止时间与参考的绝对差，毫秒级 字幕场景单独看

WER 与 CER 都属编辑距离类指标。词级会把一个字的错判成整词错，字符级只算那一个字符，所以同一段错误在词级口径下更严重。这条差别要主动说，显得你知道中文为什么用 CER。

归一化：他们面试时提示的那一步。 转写出来之后要先归一化再算指标，目的是消掉与语义无关的书写差异，否则大小写、标点、数字与时间的写法不一致会让本来正确的字被算成错。

开源实现可以直接参考 Whisper 自带的归一化器：BasicTextNormalizer 做语言无关的基础归一化，转小写、去括号内容、按 Unicode 类别去符号与标点、压缩空白；EnglishTextNormalizer 额外把拼写数字、序数、金额、年代等统一成阿拉伯数字写法，就是为了让「twenty」和「20」不被算成错误。中文场景的归一化没有统一公开标准，常见做法是把口语数字读法与阿拉伯数字统一、再统一标点与空白，各家按自己的数据集约定。

工程上用现成的归一化器加业务规则，别自己从头写；但规则本身必须知道，出问题时你要能判断是模型错了还是归一化把对的判错了。还有一条纪律：比较不同版本的字错率时必须声明用的哪套归一化规则，因为归一化策略会显著改变结果，换一套规则再比就等于没比。

主观与客观。 主观平均意见分（MOS）的框架出自 ITU-T P.800，P.808 给的是众包方式做主观评测的方法，适合大规模听测，语音输出设备另有 P.85。客观侧常用三个：PESQ 是侵入式指标，要拿参考语音做对比，输出感知质量的预测分，注意它对应的 ITU-T P.862 系列已过时并于 2024 年 1 月删除，现在要引用应写 P.863 系列；STOI 预测可懂度，反映降噪增强对听清的影响；MCD 是梅尔倒谱失真，比较两段语音在频谱包络层面的差异，常用于合成语音。

多语种与语码转换。 可用的公开资源：中文普通话基准 AISHELL-1（400 说话人、安静室内录制，论文口径超过 170 小时）；会议场景的 AISHELL-4（211 场会议、120 小时、每场 4 到 8 人、8 通道阵列，含重叠语音与标注）；VoxCeleb 是说话人识别与验证基准，不是转写准确率基准，别用错；中英混说的语料有 SEAME（新加坡与马来西亚场景的中英码转换）和 ASCEND（香港采集的中英多轮自发对话，约 10.6 小时）。语码转换场景的常见做法是在混语语料上算整体错误率或分语种错误率，并单独看语言切换点附近的错误。

流式的三个延迟要分清。 首字延迟、端点检测延迟、最终结果延迟是三件事。论文里有结论说，模型大小与实时率这类算法侧指标，和设备上观测到的用户感知延迟未必强相关，端点检测行为的影响更大。这条讲出来很显专业。

字幕场景。 SRT 用 HH:MM:SS,mmm --> HH:MM:SS,mmm 的时间行，VTT 用点分隔毫秒并带 WEBVTT 头。字幕质量同时取决于文本、分段换行与时间对齐。测法是逐条字幕比开始与结束时间的绝对误差，报均值与分位数；更完整的做法用 SubER 这类把文本、分块与时间一起算的指标。注意毫秒级可接受阈值没有行业统一标准，属产品与规范约定。

测试集要素。 安静与噪声按信噪比分层、远场近场与混响、口音方言、说话人多样性与重叠语音、含数字与专有名词、不同信道与设备。CHiME 系列挑战赛代表的是远场、多通道、噪声与混响、日常多说话人这类困难场景，评测就往这个方向分片。

面试怎么答：

ASR 我会先定参考文本，人工听写转写为准，然后定归一化规则，把大小写、标点、数字和时间的写法统一，再算字错率；中文没有词边界，我会用字错率而不是词错率。评测集会按信噪比、口音、远近场、说话人和内容类型分片，报告要给每一片的结果和跟上一版的对比，不只给一个总数。端侧还要看首字延迟、端点检测延迟和实时率，归一化规则在报告里必须写清楚，否则两个版本的数字没法比。

2.4 TTS：说出来像不像

TTS 测两条线，主观与客观。

主观侧的主观平均意见分（MOS）是 ITU-T P.800 给语音传输质量定的主观评定方法，TTS 评测常借鉴它；语音输出设备的主观评估方法另有 ITU-T P.85。实际做的时候常拆成几个分项打：自然度、说话人相似度、可懂度与发音准确度。分项名称和打分细则没有全球统一口径，按项目定。

客观侧看这些点：

检查项 怎么测
发音错误 错读、漏读、增读，统计错误句占比
多音字 按上下文选音是否正确
专有名词 人名、地名、缩写的读法
韵律与停顿 停顿位置与时长、语速是否稳定
跨语种 每种语言的发音与韵律、文本规范化是否正确
跨音色 同一段文本下音色是否稳定、有没有音色漂移

面试官的原话是「TTS 要算音频的准确率，涉及语种比较多，中英日德意法西」。所以多语种一致性是这家的重点，答题时要主动说这一点，显得你知道他们的痛点：七种语种要各自有评测集与听测样本，跨语种切换和专有名词读法是常见坑。

面试怎么答：

TTS 我会分主观和客观。主观用 MOS 打分，通常拆成自然度、相似度、发音准确度几个分项，请人按 1 到 5 打；客观看发音错误、多音字和专有名词读对没有、韵律停顿。这家公司做跨境，语种多，所以每种语言要有自己的评测集和听测样本，还要专门测语种切换和夹杂。面试里聊到覆盖好几种语种，我会先问现在每种语种是分别建模还是共用一个模型。

2.5 端侧语音：唤醒与 ASR 分开测

端侧语音的典型架构是本地小模型常驻做唤醒，命中之后再启动或上传到更大的识别与对话系统，兼顾功耗、隐私和识别能力。两块模型各测各的：

模型 测什么
唤醒模型 漏唤醒率、误唤醒率（FA/h）、唤醒延迟、常驻功耗与内存、不同噪声与距离下的表现、打断场景
ASR 模型 字错率或词错率、句准确率、首字延迟、实时率 RTF、内存与功耗、领域词与热词效果

量化与裁剪后的对比方法是：在同一测试集、同一前后处理与阈值策略下，跟基线模型比。唤醒看固定误唤醒水平下漏唤醒率的变化，ASR 看字错率与时延、内存、功耗的变化，另外要把 badcase 回归一遍。允许掉多少没有统一标准，属项目约定。

三、语音数据集与回归集怎么造

语音评测一半的活在数据上，面试问「需要哪些数据做统计」，答的就是这一章。

3.1 切片维度

维度 切片举例 为什么要切
语种 中英日德意法西 每种语言模型能力不同，混在一起平均没有意义
信噪比 安静、30 dB、20 dB、10 dB 噪声是识别掉点的主因
说话人 性别、年龄段、口音、儿童音 声学模型对不同人群表现不同
距离与信道 近讲、远场、免提、电话信道 拾音与信道影响很大
语速与音量 慢、快、轻声、大声 端点检测与声学模型都敏感
场景 安静房间、车内、地铁、餐厅 真实用户场景分布
负样本 静音、纯噪声、背景人声、媒体播放 专门看误识别与误唤醒
专有内容 人名地名、品牌词、数字、日期时间 热词与后处理最容易错的地方

3.2 回归集怎么维护

原则 做法
与训练分离 评测集不进训练与调参，按说话人与会话切分，避免泄漏
版本冻结 固定文件清单与校验和、转写规范、归一化规则版本；生产分布变了就建新版本，与旧版并行对比后再替换
标注质量 参考转写错一个字会直接污染字错率，转写规范要统一并复核
按切片统计 报告给每一片的结果，不只给总分
badcase 沉淀 典型 badcase 打标后纳入回归集，记模型版本与期望结果，防修复回退

3.3 参考文本从哪来

两种做法。人工听写转写最准，成本也最高，适合小而精的核心集。用现成数据集的官方标注当参考快，但要先确认标注规范跟自己的归一化规则一致。这件事面试答得出来很加分，因为它体现你懂「参考文本本身是误差来源」。

四、语音链路的 badcase 归因

识别错了别急着提给算法，先分层定位，链条从前往后是：

层 归因方向 典型现象
前端采集与降噪 拾音失真、削波、底噪、降噪过度把人声削掉 录音本身就难听
端点检测 VAD 切错句、吞字、把呼吸当成语音 句首句尾丢字
声学模型 发音与信道失配、噪声下掉字 安静环境对、嘈杂环境崩
语言模型与解码 上下文纠正过度、专名被改写 生僻词被换成常见词
词典与热词 品牌词、人名不在词表 专名识别不出来
文本后处理 数字与日期读法、标点、大小写 文本看着对，数字错

每条 badcase 要给：音频文件、参考文本、识别文本、模型与设备版本、期望与实际、以及它属于上面哪一层。归因错了修复方向就错。

对语音链路，音频回放加分阶段中间结果是最有效的定位手段：同一段音频反复听，看波形与频谱，再对比 VAD 切分结果与最终文本。

五、评测脚本：岗位要的 Python 到底写什么

面试里那句「Python 熟不熟」，问的就是能不能写评测脚本。语音评测的脚本大致是这四段，把每段写到能讲，Python 这关就过了。

5.1 第一段：批量跑，把音频或文本灌进模型

要点：一个模型服务一个进程，脚本只负责发请求、收结果、记时间；超时必设；每次调用打一行结构化日志，后面统计才有原料。

5.2 第二段：归一化，算 CER 与 WER

这是本次面试答不出来的核心，写成能默出来的一段。

归一化要统一的几项，按面试官说的顺序讲：大小写、标点、数字、时间与日期的读法、单位和符号。数字和时间最容易出错，「3」是「三」还是「叁」、「2024 年」读成「二零二四年」还是「两千零二十四年」，两边不一致就会平白多出一堆错误。

工程上通常用现成的归一化器再补业务规则，不要自己从头写一套；但归一化规则本身必须知道，因为出问题时你要判断是模型错了还是归一化把对的判错了。

5.3 第三段：统计与报告

报告要能回答三件事：总体是多少、哪一片最差、跟上一版比是涨还是掉。只给一个总体 CER 的报告，等于没做评测。

5.4 第四段：端侧与设备侧的脚本

这四段合起来就是语音评测工程师的日常：批量跑、算指标、按切片统计、出报告。四段都能默出来，Python 这关不会被卡。

5.5 面试时的答法

Python 我写测试脚本写得比较久。VidDigest 里用 pytest 维护接口用例集，做过参数化、fixture 造数清数和一键回归。语音评测这块我理解是四步：批量把音频喂给模型拿回结果，用参考文本算字错率，按语种和噪声切片统计，最后导出 CSV 出报告。归一化是其中最容易出问题的一步，大小写、标点、数字和时间的写法不统一，正确的字也会被算错。我板端这边也写过串口抓日志和统计的脚本。

7.2 三层讲法

第一层，一句话定位。

在学校跟粤嵌做的 20 天实训项目，做了一台跑在 RK3568 开发板上的语音问答终端：对着板子说话，它把语音转成文字，交给本地 Ollama 部署的 DeepSeek 推理，再把答案用 TTS 播出来，屏幕用 Framebuffer 显示，触摸屏切功能，另外通过 TCP 从 Web 平台拉科普文本。

第二层，我干了什么（说三条）。

板端音频链路：ALSA 录音、按固定时长切片、上传识别、拿回文本。显示与交互：Framebuffer 画字、输入子系统读触摸坐标做翻页。端侧大模型：Ollama 装到板子上跑 DeepSeek，用提示词约束回答范围，再接 Ekho-TTS 播报。

第三层，测试我怎么看这件事。

课程里以开发为主，测试是我自己按链路补的。我把这条链路拆成五段：采集、传输、识别、推理、播报，每段定一个能判定的标准。采集看录音时长和采样率对不对。传输看半包和断连。识别和推理看输出内容对不对、耗时多少。播报看文本和语音是否一致。整链路再补三个场景：打断、连续问、断网重连。

7.3 七条追问链

追问 答什么 落到哪句结论
跑在板子上的程序你怎么测 两条腿：能搬到主机上跑的（纯逻辑、协议解析）交叉编译后在主机或用 QEMU 用户态模式跑，用 gcov 与 lcov 出覆盖率；必须上板的（音频、触摸、显示）用 gdbserver 远程调试加串口日志 能上板的不硬搬到主机，主机的测不了硬件时序
语音这条链路的「准」怎么算 识别段用字错率或词错率，拿人工转写当参考答案；问答段用固定问题集判事实性与相关性；端到端用任务成功率 别用一个「准确率」盖住五个阶段
偶现问题怎么复现 固定三样东西：固件与模型版本、输入（用音频文件而不是真人说话）、环境（网络与电源）；再抓串口日志带时间戳 输入要可重放，真人说话不算可重放输入
板子录音没声音怎么排查 先看 /proc/asound/cards 有没有声卡，arecord -l 列设备，再用 arecord 试录一段，检查采样率与声道是否与播放端一致，最后看 mixer 音量 从设备枚举往上一层层排，不猜
TCP 通信怎么测异常 造半包、造超长包、拔网线、对端直接关连接；看程序是阻塞、重连还是崩 粘包靠定长或长度前缀，测试要专门打这两种边界
推理慢怎么定位 分段计时：录音时长、上传耗时、识别耗时、推理耗时、合成耗时，再在板端看 CPU 与内存占用 慢在哪里要先量出来，不要直接换模型；Ollama 在这类板子上是 CPU 量化推理，不是 NPU 加速，内存也卡得很紧
你测过 OTA 吗 说实话没做过端到端的 OTA，但能说出测试点：断网中断、断电中断、降级安装、跨版本升级、升级后配置与数据是否保留 没做过就说没做过，给测试点证明你懂怎么测

7.4 能拿出来的东西

口头讲结构是虚的，能跑的东西才实。三样小到当天能做完，做完就是可演示的证据；再配一张板上跑起来的截图或两分钟录屏，统计脚本导出的 CSV 留在手里。

一是用 Python 批量打本地大模型，算成功率与耗时，脚本见第五章。二是录音回环自检：arecord -d 3 -f cd -t wav /tmp/a.wav 录三秒，aplay /tmp/a.wav 放出来，再用 soxi 或 Python 读 wav 头核对采样率、声道与时长。三是串口日志统计：pyserial 接板子串口，跑十分钟，把含 error、fail、timeout 的行抓出来计数。

八、Linux 与 MySQL 速查

这场面试问了 Linux 命令与 MySQL 命令，答得上来，但别只答到 ls 与 select。

8.1 Linux：面试官问过的那些

用途 命令 一句话说明
看进程 ps -aux、ps -ef、top -p <pid> 找进程、看占用
看日志 tail -n 200 app.log、tail -f app.log 实时跟、grep -n "error" app.log 过滤 板端排错主力
看文件 ls -l、cat /proc/cpuinfo、cat /proc/meminfo、cat /sys/class/thermal/thermal_zone0/temp 板端看硬件状态

一句加分话：板端出问题我会先看 dmesg | tail 有没有驱动或内存错误，再看 ss 里服务有没有起来，最后看应用日志，三步能把问题分到驱动、服务、应用三层。

8.2 MySQL：够用的一层

用途 写法
查 SELECT id, name FROM user WHERE status = 1 ORDER BY created_at DESC LIMIT 10;
增 INSERT INTO user (name, status) VALUES ('a', 1);
改 UPDATE user SET status = 0 WHERE id = 5;
删 DELETE FROM user WHERE id = 5;
分组 SELECT status, COUNT(*) FROM user GROUP BY status;
分组后过滤 SELECT status, COUNT(*) c FROM user GROUP BY status HAVING c > 10;
关联 SELECT u.name, o.id FROM user u JOIN orders o ON o.user_id = u.id;
建索引 CREATE INDEX idx_user_status ON user(status);

两处容易答错的语义：WHERE 在 GROUP BY 之前过滤行，HAVING 在 GROUP BY 之后过滤聚合结果；COUNT(*) 统计行数，含空值与重复行，需要去重用 COUNT(DISTINCT 列)。

九、测试基础与用例设计

通用理论另有一篇《软件测试速通》讲得更细，这里只留跟语音端侧相关的部分。

9.1 一条流程线

阶段 通用做法 语音端侧的具体动作
需求评审 抓可测性，确认验收口径 问清指标是什么、在哪个数据集上算、允许掉多少
测试计划 范围、策略、资源、进度、风险、准出 补一条环境矩阵：机型乘固件版本乘模型版本乘语种
用例设计 等价类、边界值、场景法、判定表、错误推测 算法侧另加数据集切片（噪声、口音、语种、距离）
提测执行 冒烟先过，再跑全量与回归 冒烟等于设备能连上、能唤醒、能出一句结果
缺陷跟踪 现象、复现、预期与实际、影响面 多三样：固件版本、模型版本、原始音频

方法 一句话 语音端侧用例

9.3 一条语音用例该写什么

标题（做什么、在什么条件下）、前置条件（设备型号、固件版本、语种、噪声条件）、音频文件路径、步骤、预期结果（可判断，最好带数值）、优先级、备注。

语音用例额外两栏：音频文件与期望文本、需要的人工介入（要人对着麦克风说话）。这两栏决定它能不能进自动化。

10.3 测试报告的结构

范围（测了什么、没测什么）、环境矩阵（机型乘固件乘模型乘语种）、执行统计（总数、通过、失败、阻塞、跳过、通过率）、缺陷统计（新增、修复、遗留，按严重程度分）、指标变化（本版与上版对比）、风险评估与结论。

结论句要写「达到发布条件」或「不建议发布，原因是什么」，不要写「测试基本通过」。

10.4 协作里最容易被问的一件事

「你怎么保证测试不漏」。答三段：需求到用例有映射表，覆盖了什么写在报告里；没覆盖的列成风险，让产品签字；回归按影响面选，不按心情选。

十二、二面前要做的五件事

12.1 做一个 ASR 评测的最小闭环

不追求规模，能在面试前跑通一遍就行。找 20 段公开中文语音素材，人工写好参考文本，用任意 ASR 识别，套上归一化，算出字错率，按噪声与口音分两片统计，导出 CSV。两天足够。

这个闭环能回答三个面试官常问的问题，怎么定参考文本、怎么归一化、怎么按片统计。能说清比能做好更重要。

12.2 把唤醒与拒识的测试集方法讲清楚

不用真做数据集，把方法讲明白就够了：正样本是有唤醒词的音频，按距离、音量、口音分片；负样本是电视背景音、日常对话、相似音词，用来测误唤醒；误唤醒率通常折算成「每多少小时误触发几次」来报，因为绝对次数没有可比性。

12.3 把 Python 从「能看懂」写成「能写」

按第五章那四段各写一遍，写到能默。pytest 那部分已经在 VidDigest 里写过，重点补的是归一化与指标计算这两段。

12.4 简历上补一条语音评测

下个版本简历建议在踏浪 AI 中心那段的措辞上靠拢，把「AI 输出评估」的维度改成可迁移的表述，例如「按准确性、召回、事实性分维度设计评测口径，用固定问题集做版本回归」。如果这轮拿到语音相关的实习机会，再把评测脚本与语种切片的经验写进去。简历改动等你确认后再动。
