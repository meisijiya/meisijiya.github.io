软件测试实习笔试速通（第一轮）--基础概念、用例设计、排序与输出题

作者: 老江湖
日期: 十一月 9, 2026  21:30:00
分类: 面试八股 软件测试

Hi，我是 meisijiya ，也是 老江湖 ，感谢你的阅读，我们一起进步。

实习岗笔试不会为难人，考的是”这些词你认不认识、给个界面会不会设计用例、排序能不能手写出八九不离十”。基础薄弱也能靠七天补出来，因为范围就那么几块，题型也固定。

先说清楚笔试和面试的分工。笔试筛的是记忆与手写，面试问的是判断与表达。所以这份笔记只准备笔试：概念要能默写，用例要能当场列，排序要能手写，输出题要能一眼看穿。

零、笔试大概长这样

题型 分值占比 常见问法 拿分难度
单选 / 多选 20%–30% 定义辨析、生命周期、哪一步该做什么 低，背了就有
判断 10% “边界值只需要测边界”这类绝对化表述 低，先怀疑绝对词
填空 10% 补全流程、补全 SQL、补全命令 中，靠熟练
简答 15% 什么是软件测试、测试和调试的区别、怎么保证质量 中，背模板
用例设计 20% 给个登录框 / 输入框 / 优惠券，列测试点 中高，是最能拉分的一题
代码题 15%–20% 排序、查找、字符串处理、Python 输出题 中，取决于手写熟练度
SQL / Linux 10% 写一条查询、说出命令作用 低，背几条就够

时间一般 60–90 分钟。策略是先把概念题和判断题扫完（十分钟内），用例设计留 20 分钟，代码题留 25 分钟，剩下时间回头检查。

一、测试基础：十个必背概念

每个概念记两样东西，”一句话定义”和”一个反例”。反例比定义好记，笔试判断、面试追问都用得上。

概念 一句话定义 容易记错的地方
软件测试 用人工或自动手段运行或评价软件，检验它是否满足规定需求 目的是尽早发现问题；”证明软件没问题”这个想法本身就不成立
测试用例 描述输入、操作、预期结果的一组说明，用来判定某功能是否正常 缺”预期结果”的用例是无效用例
需求评审 在开发之前检查需求是否有歧义、遗漏、不可测 它是测试介入最早的一步
冒烟测试 提测后先跑主干功能，通不过就打回 目的在判断”能不能测”，不在找细碎缺陷
回归测试 修改之后重跑原有用例，确认没改坏其他功能 回归不等于全部重跑，覆盖改动影响面即可
验收测试 由用户或客户按需求验收，判断能不能交付 α 在开发场地由用户测，β 在用户现场测
缺陷（Bug） 软件不符合需求，或用户认为不可接受 需求没写清但用户不满意，也算缺陷
缺陷生命周期 新建 → 指派 → 修复 → 验证 → 关闭（不通过则重新打开） “关闭”之后仍可能被重新打开
严重程度 / 优先级 前者看对系统的影响，后者看修复的先后 影响小但必须先修的，优先级高、严重度低
测试覆盖率 被测试覆盖到的部分占总体的比例 功能覆盖率看需求，代码覆盖率看语句/分支

补充三个常考的关系题：

  1. 测试与调试的区别：测试由测试人员发起，目的是发现问题，有计划和用例；调试由开发发起，目的是定位并修好问题，无固定步骤。
  2. 为什么不能穷尽测试：输入空间与执行路径是无限的，时间与成本有限，所以按风险排优先级，选择测什么、测到什么程度。
  3. 测试能保证质量吗：测试只能发现缺陷、提供质量信息，质量是设计和生产出来的。这句话在简答题里能直接拿到分。

二、测试分类：别只背名字，按”维度”记

维度 分类 记忆抓手
是否看代码 黑盒、白盒、灰盒 黑盒看输入输出，白盒看代码逻辑，灰盒看接口与部分实现
是否运行程序 静态测试、动态测试 静态靠评审与走查，不跑程序
测试阶段 单元、集成、系统、验收 从小到大：函数 → 接口之间 → 整系统 → 用户手上
测试目的 功能、性能、兼容、安全、易用、可靠性 功能问”对不对”，性能问”快不快”，兼容问”换环境坏不坏”
是否手工 手工测试、自动化测试 自动化适合稳定、重复的回归

流程按 V 模型背最省力：需求分析 → 概要设计 → 详细设计 → 编码，右边对应验收测试 → 系统测试 → 集成测试 → 单元测试。W 模型把”测试与开发同步开始”讲得更清楚，需求阶段就写系统测试计划。

实际工作里的顺序：需求评审 → 测试计划 → 用例设计与评审 → 开发提测跑冒烟 → 执行用例 → 提缺陷 → 回归 → 上线前回归与冒烟清单 → 复盘补用例。

三、用例设计：四件套 + 两道例题

3.1 四个方法，各记一句

方法 什么时候用 一句话例子
等价类划分 输入取值多，不必逐个测 年龄 1–120 分成”小于 1””1–120””大于 120”三堆
边界值 有区间或长度限制，错都在边界上 输入 1–100 就测 0、1、100、101
判定表 多个条件组合决定一个结果 优惠券能否使用：满减门槛 × 会员等级 × 有效期
场景法 走完一整条业务链路 注册 → 登录 → 下单 → 支付 → 退款
错误推测 凭经验补漏 断网提交、连点两次、提交中杀进程

3.2 例题一：登录框怎么设计用例（笔试最爱）

按四类铺，别只盯输入框：

  1. 输入校验：账号空、密码空、全空格、长度边界（7/8/20/21）、特殊字符、中文、超长粘贴、SQL 注入串 ' or 1=1、XSS 串 <script>。
  2. 业务规则：账号不存在、密码错误、账号锁定、密码错误 5 次后锁定、验证码错误与过期、密码明文与密文切换。
  3. 交互与状态：按钮在未填时是否禁用、连点是否只发一次请求、回车能否提交、登录后回调原页面、token 过期回登录页、多端登录互踢。
  4. 界面与兼容：提示文案是否明确、Tab 顺序、密码可见性图标、分辨率缩放不错位、主流浏览器表现一致。

写答案按这个格式走：编号、用例标题、前置条件、步骤、预期结果。哪怕列十条，也要把预期结果写全，这是评分点。

3.3 例题二：输入框类通用模板

凡是”给一个输入框”的题，套这五步：空值、格式非法、长度边界、特殊字符、业务语义。业务语义因场景不同，比如金额要测 0、负数、两位小数、超上限；手机号要测 10 位、11 位、12 位、带空格、带横线、+86 前缀。

四、缺陷与覆盖率：两道必考细节

4.1 缺陷报告六要素

标题（一句话说清现象）、复现步骤、预期结果、实际结果、环境与版本、附件（日志与截图）。加分项是补”复现概率”和”影响面”。

严重程度分四级：致命（系统崩溃、数据丢失）、严重（主功能不可用）、一般（次要功能异常）、轻微（文案与样式）。优先级分高中低，看修复排期。

4.2 覆盖率怎么算

  • 语句覆盖率：执行过的语句占总语句的比例。
  • 分支（判定）覆盖率：每个判断的真假两支都走过。
  • 路径覆盖率：所有可能路径都走到，代价最高，实际很少要求。

自测一个小例子：if (a > 0) { x = 1; } else { x = 2; }。只跑 a=1 时执行到 x = 1，语句覆盖 1/2，即 50%；要语句覆盖 100% 必须 a>0 与 a<=0 各跑一次。分支覆盖 100% 同样要求两支都走，所以分支覆盖 100% 一定带来语句覆盖 100%，反过来不成立（跑过所有语句不等于走遍所有分支）。

五、算法：只要五个排序 + 一个查找

笔试不会要求最优解，要求的是”能写出能跑的代码，说得清复杂度”。

5.1 复杂度与稳定性速记

算法 平均时间 最坏时间 空间 稳定 记忆点
冒泡 O(n²) O(n²) O(1) 稳定 相邻比较交换，一趟冒一个最大值
选择 O(n²) O(n²) O(1) 不稳定 每轮选最小放到前面，交换会打乱相等元素
插入 O(n²) O(n²) O(1) 稳定 像摸牌，把当前牌插到合适位置
快速 O(n log n) O(n²) O(log n) 不稳定 选基准分区递归，最坏出现在已有序
归并 O(n log n) O(n log n) O(n) 稳定 分成两半排好再合并，代价是要额外空间
二分查找 O(log n) O(log n) O(1) — 前提是数组有序

口诀：冒泡插入逐位排，选择每轮挑最小，快排分区看基准，归并分治要空间。 稳定性记两个例外就够：选择、快排不稳定，其余三种稳定。

5.2 冒泡（手写要能一次过）

拿 [3,1,2] 走一遍：第一趟 3 与 1 换，3 与 2 换，得 [1,2,3]；第二趟无交换，swapped 为假直接退出。笔试常让人写”带优化的冒泡”，就是这句 swapped。

5.3 快排

这个写法好记但费空间，答题时补一句”原地分区版本用双指针，空间从 O(n) 降到 O(log n)”就够专业了。

5.4 二分查找（注意边界）

三处最容易写错：lo <= hi 写成 <（漏掉最后一个元素）、mid + 1 写成 mid（死循环）、数组未排序就用二分（前提不成立）。

5.5 字符串与数组常考题

反转字符串、判断回文、统计字符出现次数、两数之和、去重保序、斐波那契（递推比递归好，递归会重复计算）。每题能手写十行以内就够。

六、SQL 与 Linux：各背八条

6.1 SQL

常考细节：WHERE 在分组前过滤，HAVING 在分组后过滤；COUNT(*) 含空行，COUNT(col) 不计 NULL；LEFT JOIN 保留左表全部行，INNER JOIN 只留匹配行。

6.3 网络与 HTTP

TCP 三次握手：SYN → SYN+ACK → ACK，目的是双方确认收发能力并同步序列号。四次挥手多一步是因为 TCP 全双工，两个方向要分别关闭。

状态码常考：200 成功、301 永久重定向、302 临时重定向、304 命中缓存、400 参数错、401 未认证、403 无权限、404 找不到、405 方法不允许、500 服务端异常、502 网关收到无效响应、504 网关超时。

GET 与 POST 的差别：语义不同（取资源 vs 提交数据）、参数位置不同（URL vs 请求体）、幂等性不同（GET 幂等）、缓存行为不同。

七、Python 输出题：八个坑，全部实测过

笔试里的 Python 题多半问”输出是什么”，考的是边界认知。下面每条都在本机跑过。

代码 输出 为什么
def f(a, b=[]): b.append(a); return b 调 f(1)、f(2) [1] 然后 [1, 2] 默认参数只求值一次，两次调用共用一个列表
[1,2] == [1,2] 与 [1,2] is [1,2] True、False == 比值，is 比内存地址，两个字面量是两个对象
a = int("257"); b = int("257"); a is b False 小整数只有 -5 到 256 被缓存，257 每次新建
m = [[0]*2]*2; m[0][0] = 1 [[1,0],[1,0]] 外层乘号复制的是引用，两行指向同一个列表
[1,2].append(3) None append 原地修改，返回 None，写成 x = a.append() 就丢了列表
[lambda: i for i in range(3)][0]() 2 lambda 晚绑定，调用时才取 i，循环结束时 i 是 2
7//2、-7//2、-7%3 3、-4、2 向下取整，取模符号跟除数走
round(2.5)、round(3.5) 2、4 银行家舍入，恰好一半时取偶数

再补两个：0.1 + 0.2 == 0.3 是 False（浮点误差，比较要写 abs(a-b) < 1e-9）；sorted 是稳定排序，相同键的先后顺序保持原序。

八、五道简答模板（照抄能拿多半分）

  1. 什么是软件测试：用人工或自动化手段运行或评价软件，检验是否满足需求，目的是尽早发现缺陷，为质量提供依据。
  2. 测试与调试的区别：发起人不同、目的不同、是否有计划与用例不同、结论不同（测试找问题，调试解决问题）。
  3. 如何保证测试质量：需求评审提前介入、用例评审与覆盖率检查、环境与数据可控、缺陷闭环跟踪、回归与上线前冒烟、复盘补用例。
  4. 怎么设计一个好的用例：能复现、有明确预期结果、步骤简洁、不依赖其他用例、覆盖一个测试点、可自动化。
  5. 发现缺陷后怎么处理：确认能复现 → 缩小范围（接口还是界面、必现还是偶现）→ 提缺陷单（步骤、预期、实际、日志）→ 跟踪修复 → 按影响面回归 → 关闭或打回。

九、易混清单：笔试选择题高频二十对

A B 分清的关键
验证（Verification） 确认（Validation） 前者问”做得对不对”，后者问”做的是不是用户要的”
错误（Error） 缺陷（Defect） 错误是人犯的，缺陷是代码里的，故障是运行表现
缺陷严重程度 缺陷优先级 影响大小 vs 修复先后
冒烟测试 回归测试 能不能测 vs 改完有没有改坏
α 测试 β 测试 开发场地用户测 vs 用户现场测
静态测试 动态测试 不跑程序 vs 跑程序
黑盒 白盒 看输入输出 vs 看代码逻辑
语句覆盖 分支覆盖 执行过 vs 两支都走过
等价类 边界值 分堆取代表 vs 专挑边界点
功能测试 性能测试 对不对 vs 快不快、稳不稳
负载测试 压力测试 逐步加压找拐点 vs 超负荷看会不会崩
单元测试 集成测试 单个函数 vs 模块之间
系统测试 验收测试 测试团队 vs 用户或客户
缺陷密度 缺陷收敛 每千行代码缺陷数 vs 后期新增缺陷变少
测试计划 测试方案 做什么、谁做、何时做 vs 具体怎么测
缺陷验证 缺陷回归 修的那处对不对 vs 有没有连带影响
阻塞缺陷 一般缺陷 无法继续测 vs 不影响继续测
需求覆盖率 代码覆盖率 需求条目被用例覆盖 vs 代码被用例执行
预置条件 测试步骤 开始前的状态 vs 操作的顺序
缺陷打回 缺陷关闭 验证不通过退回开发 vs 验证通过收尾

十一、答题技巧

  • 判断题先怀疑绝对词：”只需要””一定””全部”多半是错的。
  • 简答题按”定义 + 目的 + 做法”三段写，哪怕不会也把关键词写上去，按点给分。
  • 用例设计题先写一句”我会从功能、边界、异常、兼容四类设计”，再列用例，阅卷人一眼能看到结构。
  • 代码题写不出来时，把思路用注释写清（”此处二分查找左边界”），有时候能拿到步骤分。
  • 时间不够就先做用例设计和简答，这两块分值密度最高。

十二、这份笔记的边界

概念与算法部分属于通用知识，随时可查可核；Python 输出题的八个结论都在本机跑过。用例设计的两道例题是模板，换业务要换语义。真正上考场前，把第五节五个排序在纸上各写一遍，比看十遍强。
