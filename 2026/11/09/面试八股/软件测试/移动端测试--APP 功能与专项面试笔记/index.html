移动端测试--APP 功能与专项面试笔记

一、平台差异：APP 与 Web、Android 与 iOS

1. APP 测试和 Web 测试的区别是什么？APP 测试需要特别注意哪些测试点？

🗣️ 回答重点

  • 两者区别主要看四个维度：测试环境、网络环境、用户接口、资源管理。
  • 环境上，APP 要覆盖不同品牌型号设备与不同操作系统版本，Web 主要覆盖不同浏览器的兼容性。
  • 网络上，APP 要看 2G、3G、4G、Wi-Fi 下的表现，Web 更关注不同带宽下的页面加载速度。
  • 交互上，APP 要重点验证触摸、滑动等手势以及与摄像头、GPS 等设备能力的整合，Web 关注鼠标点击、键盘操作。
  • 资源上，移动设备的内存、CPU、存储有限，APP 测试必须重视资源消耗，Web 较少考虑。
  • APP 专项测试点包括兼容性、性能、网络、电池使用、安全性、用户体验六类。

📈 拔高

  • 兼容性测试要求在尽可能多的真实设备上跑，因为屏幕大小、分辨率、硬件性能、系统版本都不同。
  • 性能测试重点看启动速度、运行速度、内存使用、CPU 占用，移动设备性能弱于 PC。
  • 网络测试要模拟弱网、断网重连等异常场景下的应用表现。
  • 安全性测试针对移动应用常涉隐私数据，需严格验证数据传输加密与存储安全。
  • 自动化可用 Appium 做移动端、Selenium 做 Web 自动化；用户行为分析可用 Firebase Analytics、Mixpanel；此外还有本地化测试与 Accessibility Testing（无障碍测试）这类专项关注点。

2. 移动端测试中，Android 和 iOS 测试的区别是什么？

🗣️ 回答重点

  • Android 走开源路线，厂商自由定制，设备类型、分辨率、系统版本都很杂，兼容性组合是测试重点；iOS 由苹果集中管控，设备与系统版本相对单一，测试复杂度低，但要跟进每次新版本发布带来的系统变化。
  • 分发渠道不同：Android 除 Google Play 外还有华为应用市场、Samsung Galaxy Store、F-Droid 等第三方商店，各有发布规范；iOS 主渠道是 App Store，需严格遵循苹果审核规范，欧盟另有替代市场与网页分发路径。
  • 工具链不同：Android 用 Android Studio，UI 自动化用 Espresso 加 AndroidX Test、Robolectric 只跑 JVM 单元测试，可借 Android Studio Managed Devices 或设备云在真实设备上跑；iOS 用 Xcode，UI 自动化用 XCUITest，Beta 分发用 TestFlight。
  • UI 规范不同：Android 侧按当前版本的 Material 规范校验组件、动画、样式；iOS 侧按 Apple 的 Human Interface Guidelines 校验，强调简洁与功能集成。
  • 权限模型不同：Android 从 6.0（Marshmallow）起引入运行时动态权限，粒度较细；iOS 同样运行时弹窗授权，但额外要求 ATT 跟踪授权与隐私清单声明，敏感信息的管控更严。

📈 拔高

  • Android 的兼容性测试本质是「厂商定制 + 系统版本 + 分辨率」的组合爆炸，成本主要花在机型矩阵取舍，而不是用例数量；选型要按 targetSdkVersion 分层，优先覆盖主流厂商与高占比分辨率。
  • iOS 的风险点集中在版本迭代：系统版本少不代表风险低，新版本带来的系统行为变化需要专项回归。
  • 多应用商店场景要额外验证下载渠道、更新链路与商店各自的审核规则是否影响发版节奏。
  • 真机覆盖靠设备云，TestFlight 解决的是 Beta 分发与发布流程衔接，两者不是一回事；Firebase Test Lab 已标记弃用，官方建议迁移到 Google Cloud 的 Developer Device Platform。
  • 权限测试不只测 6.0 前后：还要覆盖 Android 11 未使用权限自动重置、Android 13/14 媒体权限模型细分，以及 iOS 未授权时的拦截提示与降级路径。

二、测试内容与流程：APP 怎么测

3. APP 测试的内容主要包括哪些？如何开展？

🗣️ 回答重点

  • APP 测试内容主要包括功能测试、性能测试、兼容性测试、安全性测试和用户体验测试。
  • 开展这些测试时，一般遵循测试计划、需求分析、用例设计、测试执行和测试报告的过程。
  • 功能测试是最基础的测试类型，主要检查 APP 功能是否符合需求文档描述，需覆盖登录、注册、支付、消息通知等所有功能模块。
  • 性能测试关注 APP 在不同负载下的表现，如响应时间、CPU 使用率、内存占用；JMeter、LoadRunner 这类工具测的是后端接口负载，设备端指标还要看启动耗时、帧率、耗电与网络消耗，靠真机或模拟器采集。
  • 兼容性测试需确保 APP 在各种不同的设备和操作系统版本上都能正常运行。

📈 拔高

  • 性能测试可进一步分为压力测试、负载测试和稳定性测试。
  • 安全性测试包括漏洞扫描、权限验证、数据加密等，Burp Suite 可做接口与代理层的安全测试；移动端还要按 OWASP MASVS 对齐、查 SSL pinning 与本地明文存储等维度。
  • 用户体验测试关注界面设计、交互流程、易用性，可通过可用性测试和用户反馈进行。
  • 测试计划阶段需明确测试目标、确定测试范围和优先级，并规划资源和时间。
  • 需求分析阶段需详细阅读需求文档，确定关键功能点和性能指标并制定对应测试用例；用例设计阶段要编写包含前置条件、测试步骤、预期结果的详细用例；测试执行阶段按计划和用例执行并记录现象；测试报告阶段收集整理结果，生成报告并给出修复建议或反馈。

4. APP 测试具体是怎么做的？要经过哪些流程？

🗣️ 回答重点

  • APP 测试是一项系统工作，确保开发出来的应用程序能够正常运行，并符合用户的需求和预期。
  • 具体流程通常包括需求分析、测试计划、测试设计、测试执行、缺陷跟踪和测试总结几大步骤。
  • 需求分析阶段明确 APP 的功能需求和非功能需求，确保测试覆盖所有必须测试的功能点和性能指标。
  • 测试计划制定测试策略、测试环境配置、测试工具选择与测试进度安排；测试设计基于需求文档和测试计划设计测试用例，覆盖主要功能路径、边界情况与使用场景。
  • 测试执行按设计好的用例在真实或模拟环境中测试 APP 并记录结果，结合手动测试与自动化测试手段；缺陷跟踪记录并跟踪缺陷，与开发团队沟通确认并做回归测试确保修复。
  • 测试总结撰写测试报告，评价测试效果，为将来的测试工作积累经验。

📈 拔高

  • 需求分析阶段通常与产品经理、开发团队充分沟通，了解具体功能点和用户场景，这一步很大程度上决定测试的深度和广度；工具包括 JIRA、Confluence 等需求管理工具。
  • 测试计划需包含测试目标、策略、资源分配，可能估算测试时间和人力成本；工具如 TestRail、Zephyr 可帮助梳理测试计划。
  • 测试设计用例尽量详尽，覆盖功能测试、UI 测试、性能测试、安全测试等；工具如 JIRA、TestLink 可管理测试用例。
  • 手动测试适合复杂场景或无法自动化测试；自动化测试通过脚本做重复性高、结构化测试，原生 APP 用 Appium，Robot Framework 属通用框架需配 AppiumLibrary，Selenium 只能驱动浏览器、原生 APP 用不上。
  • 缺陷记录需注意准确性与完整性，包含重现步骤、环境信息、期望结果；工具如 JIRA、Bugzilla、Redmine 可高效管理跟踪 Bug。
  • 测试总结包括测试覆盖率、发现的问题及其状态、测试结果统计等；工具如 Excel、JIRA、TestRail。

三、故障定位：ANR、崩溃与日志

5. 测试 APP 时出现 ANR（应用无响应），可能是什么原因导致？

🗣️ 回答重点

  • 主线程阻塞：Android 的 UI 操作都在主线程，主线程执行网络请求、大量数据处理等耗时操作就会触发 ANR，输入事件派发超时默认 5 秒。
  • 死锁：多个线程争抢资源形成死锁，线程无法继续执行，主线程停滞，于是出现 ANR。
  • I/O 耗时过长：在主线程读大文件、访问数据库等耗时 I/O，同样阻塞主线程引发 ANR。
  • 后台线程池饱和：BroadcastReceiver 的 goAsync 后台任务池被长任务占满，会导致后台 ANR。
  • GC 频繁是主线程阻塞的放大因素，表现为掉帧卡顿，官方成因清单里并不把它单列为一类 ANR。

📈 拔高

  • 预防手段一是异步处理：网络请求、文件读写、数据库查询都放到异步线程，可用 HandlerThread、ThreadPoolExecutor 或 Kotlin 协程；AsyncTask 已在 API level 30 废弃，面试别再当首选。
  • 主线程里用 Handler 和 Looper 处理轻量级延时或定时任务，回调仍在主线程执行，重活必须切到工作线程。
  • 内存上减少大对象的频繁创建与销毁，降低 GC 压力以减少掉帧；同时严格划分主线程与工作线程职责，把避免死锁与资源占用变成习惯。
  • 布局也会拖慢渲染：问题在视图层级过深、嵌套多，与写在 XML 还是代码里无关，可用 Merge 标签、ConstraintLayout 扁平化层级、减少重绘来优化。
  • 排查工具：StrictMode 检测主线程上的磁盘与网络访问并告警，Android Studio Profiler 与 Perfetto System Trace 做性能分析，Layout Inspector 查看运行时视图层次。

6. 移动端测试中，APP 出现崩溃（闪退）的原因有哪些？

🗣️ 回答重点

  • 程序运行时遇到未捕获的异常，比如空指针异常、数组越界异常，没有被捕获处理，这是崩溃统计里的第一大类。
  • 内存泄漏：移动设备内存有限，未释放的内存逐渐耗尽，先表现为 OOM 与卡顿，被系统 LMK 杀进程，iOS 侧则是 jetsam 终止。
  • 网络不稳定或请求超时后应用处理不当，更常见的是触发 ANR 或超时异常，而不是直接崩溃。
  • 设备兼容性问题：设备种类繁多，硬件性能、操作系统版本、分辨率差异都可能让应用不兼容而崩溃。
  • 过度使用 CPU、GPU 等资源会让设备温度过高，系统会限流甚至热关停，不必然直接崩溃。
  • 第三方库或依赖版本不兼容，以及后台任务出错，也都会引发应用非正常退出；注意 iOS 后台任务超时只是被系统取消挂起，不会崩溃。

📈 拔高

  • 对应的处理思路一一对应：内存管理上及时释放不再使用的内存，可借助 Android Studio Memory Profiler 与堆快照定位；异常处理上给可能出错的代码块加处理，但别无差别捕获通用异常与 Error，OOM 这类不该吞掉。
  • 网络侧要实现稳定的网络请求管理，覆盖超时、失败和重试机制，保证弱网下应用仍能平稳运行。
  • 兼容性靠尽可能多的真实设备和操作系统版本上的测试来保证，可用自动化测试工具扩展覆盖面。
  • 依赖侧用依赖管理工具固定稳定的第三方库版本，新版本先测兼容性再更新；资源侧用性能监控工具观测 CPU、GPU、内存使用情况。
  • 后台任务要合理调度，避免高频率或高耗时任务，持久化后台任务首选 WorkManager，JobScheduler 是面向系统任务的平台 API，两者不是平级推荐；并保证任务失败时的错误处理逻辑完整。

7. 移动端测试中，查看 logcat 日志时如何将内容保存到本地？

🗣️ 回答重点

  • 用 Android 官方提供的 adb 工具捕获 logcat 并保存到本地文件。
  • 先确保设备 USB 连接电脑并启用 USB 调试模式。
  • 在终端或命令提示符输入 adb logcat -v time > path/to/your/filename.txt，靠 Shell 重定向把日志写到主机上的指定文件。
  • 例如 adb logcat -v time > D:/logs/logcat_output.txt，日志保存在 logcat_output.txt 中。
  • logcat 输出可能很大，可用过滤器和日志优先级优化，如 adb logcat ActivityManager:I MyApp:D *:S 只显示匹配的 Info/Debug 级别日志。

📈 拔高

  • logcat 是 Android 系统命令行工具，输出系统消息、应用日志及崩溃、调试、性能数据。
  • adb（Android Debug Bridge）通用命令行工具，可与模拟器或连接设备通信，支持安装 APK、运行 Shell 命令等。
  • 常用参数：-v time 显示时间戳，格式是 MM-DD HH:MM:SS.mmm，取的是设备时间；-s 是把默认过滤设为静默，要配合 tag:priority 写，如 adb logcat -s MyTag:D；-f 把日志直接写进设备文件，如 adb logcat -f /sdcard/my_log_file.log，再定期上传或 adb pull 复制下来。
  • 定期自动保存可用脚本定时操作，例如 Bash 脚本循环执行 adb logcat -v time -d > "logcat_$(date +%Y%m%d_%H%M%S).txt"，每小时保存一次；-d 是转储后退出。

四、兼容与专项：兼容、交互、Push、H5 与小程序

8. Android 的兼容性测试需要考虑哪些内容？

🗣️ 回答重点

  • 设备碎片化：测试不同品牌、型号、分辨率、屏幕尺寸的设备。
  • 操作系统版本：测试不同的 Android OS 版本，涵盖常见的主流版本。
  • 应用性能：保证应用在各个设备上的流畅度和性能稳定。
  • 硬件特性：不同设备可能有不同的硬件特性，如摄像头、传感器等，需要确保应用能正常使用这些硬件。
  • 网络环境：测试应用在不同网络环境下的表现，包括 Wi-Fi、4G、5G、弱网与网络切换。
  • 国际化和本地化：考虑多语言、多地区的适配，确保用户体验一致。

📈 拔高

  • 设备碎片化下无法覆盖所有设备，通常选择市场占有率较高的设备，并可借助设备云服务（如 AWS Device Farm，或 Android Studio Managed Devices）在不同设备上自动化执行测试；Firebase Test Lab 已标记弃用、将于 2027-09-30 全面关停，官方建议迁移到 Google Cloud 的 Developer Device Platform。
  • 不同 Android 版本会有不同的 API 和特性，优先测试最新版本以及市场占有率较高的旧版本；Google 官方的 Android 版本分布图是不定期快照，判断自家用户分布优先看 Play Console 的 Reach and devices。
  • 性能测试包括启动时间、内存使用、CPU 使用、响应时间等方面，可用 Android Studio Profiler 分析，基准测试用 Jetpack 的 Macrobenchmark（启动耗时、帧渲染）与 Microbenchmark（代码耗时、分配）。
  • 硬件特性测试需确保摄像头、GPS、指纹识别、NFC 等功能在各种设备上正常工作，例如摄像头需在不同像素、前置后置场景中验证。
  • 网络测试不仅涵盖不同网络类型，还包括良好和差的网络条件、网络切换等场景，模拟器可用 -netspeed 与 -netdelay 做限速与延迟模拟。
  • 国际化需考虑语言字符集、右到左排版、时区、日期格式和货币符号等，确保在测试中加以验证。

9. APP 兼容性测试是怎么做的？

🗣️ 回答重点

  • 目标是确保应用在各类设备、操作系统和网络环境中都能稳定运行。
  • 先选取市场上有代表性的安卓与 iOS 设备及不同系统版本，再分别做安装卸载测试、核心功能测试、UI/UX 显示测试。
  • 还要模拟弱网、丢包、高延迟、4G/5G 切换与断网重连等环境，检查性能指标（启动时间、内存、CPU）和安全漏洞。

📈 拔高

  • 自动化工具提升效率：Appium 是主流，Robot Framework 属通用关键字驱动框架、做移动端要配 AppiumLibrary；Calabash 已停止维护，别再当推荐工具。
  • 预算不足时用云测试服务：AWS Device Farm 提供真实设备与远程操作，按设备分钟计费、成本要按用量估；Firebase Test Lab 已标记弃用、将于 2027-09-30 全面关停，官方建议迁移到 Google Cloud 的 Developer Device Platform。
  • 跨平台框架（React Native、Flutter）一套代码多平台运行，真实风险集中在原生模块、插件与平台差异，不是「一律问题更多」，测试时要重点盯这三处。
  • 内部测试仍可能漏问题，用户反馈、崩溃日志、评论、反馈表单可及时发现并解决问题；Android vitals 的崩溃率与 ANR 率就是线上监控口径。
  • 兼容通过率要有基线：机型市占率与 OS 版本覆盖率取自自家 Play Console 的 Reach and devices 数据，再对崩溃率、ANR 率设门槛，否则「覆盖了多少」说不清。

10. 如何测试 APP 的交互性？

🗣️ 回答重点

  • 先做功能性测试，确保所有按钮、链接和交互元素都能正常工作。
  • 再做用户体验测试，通过实际操作检测应用的易用性和用户友好度。
  • 检查响应时间，确保每个交互操作的响应在可接受范围内。
  • 做兼容性测试，看应用在不同设备和操作系统上的表现。
  • 做可访问性测试，确保特殊需求用户也有良好的交互体验。

📈 拔高

  • 自动化用 Appium 模拟用户操作，它本身就是 WebDriver 的扩展，Android 侧走 UiAutomator2、iOS 侧走 XCUITest；Selenium 只能驱动浏览器，原生 APP 用不上，只有 WebView 部分才切到 web 上下文。
  • 交互测试要覆盖异常与中断：断网弱网、后台切前台、来电打断、权限弹窗、屏幕旋转、进程被杀后的状态恢复；还要测手势滑动长按双击拖拽与误触容错。
  • 做 A/B 测试，对比不同设计版本的用户交互效果。
  • 做 Usability Testing，邀请真实用户操作并观察反馈，捕捉自动化工具发现不了的细节；它是小样本定性研究，不能替代自动化回归。
  • 集成 GA4 或 Firebase Analytics 监控用户行为、定位交互问题，前提是事先设计好事件与漏斗埋点；性能卡顿另用 Firebase Performance Monitoring 或 Perfetto 采集。
  • 做压力测试，模拟大量用户同时交互，验证高并发下的稳定性和响应时间；后端压测不代表设备端手感，客户端侧还要看启动耗时、内存与耗电。

11. 如何测试 APP 的安装、卸载和更新功能？

🗣️ 回答重点

  • 安装测试先看正常安装：在不同设备与操作系统版本、Wi-Fi/4G/5G 网络环境下安装，确认过程顺利。
  • 空间不足时安装：设备存储接近满载时尝试安装，Android 侧会报 INSTALL_FAILED_INSUFFICIENT_STORAGE，要确认提示与失败后的状态清理。
  • 卸载测试：正常卸载确保应用私有数据被清除；强制关闭后再卸载要确认不崩溃、不留无效数据；多次重复卸载/安装循环验证稳定性。
  • 更新测试：旧版本更新到新版本确认数据不丢失、过程顺利；断网恢复更新要能继续；降级安装 Android 侧要 adb install -d 或先卸载，iOS 走 App Store 无法降级，只能通过 TestFlight 重装。

📈 拔高

  • 重新安装要确认无残留数据或冲突，但注意 Auto Backup 与 iCloud 备份会在重装时把数据还原回来，「卸载即清干净」要按私有数据、外部存储、云端备份三类分开说；不同版本安装要确保版本兼容，版本号回退会触发 INSTALL_FAILED_VERSION_DOWNGRADE。
  • 渠道包不是「无差异」：商店包与内部 APK 常因签名不同直接装不上（INSTALL_FAILED_UPDATE_INCOMPATIBLE），要专门覆盖渠道包的签名与包名一致性校验，并预期失败场景。
  • 自动化：Appium 支持 Android 和 iOS 多平台并可集成到 CI/CD，多台设备同时测安装/卸载/更新靠 mobile: installApp、mobile: removeApp 这类 execute method 实现；iOS 端还依赖 macOS、Xcode 与签名授权。
  • 性能监控：安装/卸载/更新过程中监控 CPU、内存与网络收发，掌握 APP 对设备资源的影响；Android Studio Profiler 与 iOS Instruments 可捕捉详细性能数据。
  • 日志分析：收集分析系统与应用日志，Android 用 adb logcat，iOS 用 Console.app；iOS 10 以后走 Unified Logging，崩溃日志另看 .ips 文件。
  • 用户数据保护：更新过程中区分本地沙箱数据、账号云端数据与系统级备份恢复三类，App 无权保证第三方数据不丢；回滚在 Android 靠 adb install -r 加签名密钥管理，iOS 要靠 TestFlight 或自建 MDM。
  • 跨平台兼容性：确保 iOS 和 Android 各版本兼容，提供一致体验；可用 BrowserStack 等云测试服务覆盖多种设备与 OS 版本。

12. 移动端测试中，Push 消息如何测试？

🗣️ 回答重点

  • 测试 Push 消息主要包括：确保推送服务配置正确、触发推送消息、验证消息接收、交互测试、边界条件与异常情况测试。
  • 先确认应用在开发者控制台（Firebase Cloud Messaging、Apple Push Notification Service）中已生成并配置推送凭据、已整合推送 SDK 且设置正确；FCM 服务端现在用服务账号加 OAuth2 的 HTTP v1，APNs 推荐用 .p8 token 式鉴权。
  • 通过服务器端脚本或工具、第三方推送平台控制台手动发送、或测试环境中编写专用测试代码来触发消息。
  • 确保用户在前台和后台状态下都能接收并展示推送消息，前台检查处理行为，后台检查通知中心显示；iOS 上用户从多任务界面强杀应用后系统不再投递，用例要区分前台、后台、已强杀三态。
  • 测试用户点击通知后打开应用、定向到特定页面或功能等交互，确认体验符合预期。
  • 测试异常场景：网络条件不好时的接收情况、离开通知栏后能否在应用内找到消息、更新或重新安装后能否正确接收。

📈 拔高

  • 权限是必查项：iOS 需用户在系统里授权通知，Android 13+ 需授予 POST_NOTIFICATIONS 运行时权限，否则通知不展示。
  • token 机制要说清：重装或系统还原后 APNs 与 FCM 的 token 都会变，应用要重新注册取 token 并上报服务端，旧 token 会被判失效。
  • 消息留存要应用自己做：推送本身不保证留存，要写入本地或服务端并提供消息中心，否则清掉通知后消息就丢了。
  • A/B 测试：正式推送前改变消息文本、图标、声音等属性，了解哪种消息更能吸引用户；Firebase 消息实验的变体主要改文案，图标声音属实验级统一设置。
  • 信息安全：APNs 走 HTTP/2 加 TLS、FCM 走 HTTPS，但通知正文在锁屏与通知栏是可读的，敏感数据要放进 data 载荷由应用鉴权后拉取，而不是直接写进标题正文。
  • 性能分析：关注推送频率对响应速度的影响以及大量推送导致的电池消耗增加，平台侧有明确的配额与节流阈值。
  • 用户反馈机制：记录用户点击推送后的行为数据帮助优化推送策略，这依赖事先设计好事件与漏斗埋点。

13. 如何测试移动端 H5 界面？

🗣️ 回答重点

  • 功能测试：确保页面所有功能如按钮、输入框、导航等能够正确运行。
  • 兼容性测试：不同设备、浏览器、操作系统上的展现效果是否一致。
  • 性能测试：页面加载速度和操作流畅度是否满足要求。
  • 用户体验测试：界面是否美观、操作是否便捷。

📈 拔高

  • 网络环境：在 4G、5G、Wi-Fi、弱网与断网下测页面加载速度和功能完整性，断网重连的恢复能力取决于有没有做 Service Worker 与 Cache API，DevTools 的 Offline 只是模拟断网、不会自动让页面具备离线能力。
  • 设备分辨率和屏幕尺寸：确保在各种分辨率和屏幕尺寸的设备上，界面布局和内容不会出现错位、遮挡等情况；DevTools 设备模式只改 viewport、DPR、UA 与触摸事件，真实 GPU 合成与滚动惯性、以及 Safari 的渲染差异只能靠真机验证。
  • 触屏交互：滑动、长按、缩放这些操作是否流畅、有无误触，多点触控响应是否正确；现代移动端推荐 Pointer Events，页面级捏合缩放靠 viewport meta 与 touch-action 控制，这两项不测容易漏缺陷。
  • 系统权限和通知：相机、地理位置这些权限 API 只在 secure context（HTTPS 或 localhost）下可用；iOS 上 Web 只能触发系统权限弹窗、不能自行调起系统设置页，拒绝后也没有再次主动申请的接口。
  • 缓存和存储：本地存储如 Web Storage、IndexedDB 要验数据能否在重启页面后恢复，但 sessionStorage 随会话结束就销毁，还要考虑配额与驱逐；内容更新能否即时反映取决于响应头 Cache-Control 与 Service Worker 缓存策略。
  • 安全性测试：前端侧重点是 XSS 防范与敏感数据保护，页面要走 HTTPS 并有加密措施；CSRF 防护必须由服务端实现（SameSite Cookie、CSRF token、校验 Origin），前端只能配合，不能算前端测试项。
  • 测试工具：Chrome DevTools 的设备模式可模拟不同设备并做 CPU 与网络节流，BrowserStack、Sauce Labs 等平台能覆盖真实浏览器与设备。

14. 如何测试微信小程序？

🗣️ 回答重点

  • 测试微信小程序要从功能测试、性能测试、兼容性测试、安全性测试几个维度入手。
  • 功能测试确保每个模块按预期工作，例如注册登录、页面跳转、信息提交。
  • 性能测试检测响应速度、加载时间、内存占用。
  • 兼容性测试覆盖不同品牌、不同分辨率手机及不同微信版本。
  • 安全性测试包括数据传输安全、用户隐私安全等方面的检测。

📈 拔高

  • 功能测试分三层：单元测试用 Jest 或 Karma（miniprogram-simulate 是自定义组件的单元测试工具集，不是集成测试框架），端到端用官方 miniprogram-automator，手工测试在真机上做。
  • 性能测试看官方性能面板的启动耗时、下载耗时、页面切换耗时与首次/再次渲染耗时；内存泄漏靠开发者工具的堆快照排查，不是「实时监控」；网络请求在 Network 面板看响应时间与数据量。
  • 兼容性测试覆盖苹果、三星、小米等主流品牌、不同屏幕分辨率与不同系统（iOS/Android/HarmonyOS），基础库版本用开发者工具切换验证，机型兼容性走云测质检。
  • 安全性测试检查 HTTPS 传输与域名白名单、用户隐私授权与范围；小程序端没有传统 DOM 注入面，重点在越权访问、敏感信息明文存储与本地缓存泄露，SQL 注入属于服务端接口的风险。

五、落地手段：ADB、启动过程与元素定位

15. ADB 是什么？

🗣️ 回答重点

  • ADB 即 Android Debug Bridge，是一种命令行工具，让用户能直接和 Android 设备通信，主要用于开发和测试阶段，提供安装应用、调试程序、复制文件等功能。
  • 它支持 USB 和无线网络两种连接方式，通过 adb devices 可以查看当前连接的所有设备。
  • USB 连接时需要在设备上打开“开发者选项”里的“USB 调试”并接受电脑的 RSA 密钥授权；Android 11 起主推“无线调试”，用 adb pair 加 adb connect 配对连接。

📈 拔高

  • 基本功能包括 adb install/adb uninstall 安装卸载 APK、adb push/adb pull 传输文件、adb shell 进入设备命令行、adb logcat 实时查看系统和应用日志。
  • 高级用法包括强制停止运行中的应用（adb shell am force-stop）、用 adb shell pm grant/revoke 调整应用权限，以及配合 scrcpy 这类工具实现手机屏幕的投屏与远程控制。
  • 两个别踩的坑：adb backup 从 Android 12 起被限制、targetSdk 31 以上基本备份不了；普通 adb shell 没有 root 权限，改不了系统目录的文件权限，分区存储后写 /sdcard 也受限。

16. ADB 的作用是什么？

🗣️ 回答重点

  • ADB 全称 Android Debug Bridge，是与 Android 设备通信和调试的命令行工具，从电脑直接交互执行调试和管理操作。
  • 主要作用包括应用安装、卸载、调试，PC 与设备间文件传输，命令执行，设备管理，实时日志查看。
  • 应用相关操作：安装 APK、调试应用、卸载不需要的应用。
  • 文件传输支持需要特定数据文件的测试场景；命令执行可用于查看系统日志、改变系统设置、运行脚本；设备管理可查看连接设备、重启设备、访问恢复模式。
  • 日志实时查看对调试应用问题很重要。

📈 拔高

  • 模拟用户输入：通过 ADB 模拟触摸、按键等操作（swipes、taps），常结合 adb shell input 命令，利于自动化测试。
  • 远程调试：Android 11 起官方主推「无线调试」，用 adb pair 加 adb connect 走 TLS 加密、无需先接 USB；adb tcpip 5555 是旧方案，明文 TCP 且设备重启后就失效。
  • 备份恢复：adb backup 从 Android 12 起被限制，targetSdk 31 及以上的应用基本备份不了，官方已弃用并预告可能移除，面试别把它当常规手段；备份测试数据要靠专门的备份方案或 root 设备。
  • 脚本化操作：结合 ADB 与 Shell 脚本实现自动化任务，减少手动操作时间和维护成本。
  • 权限管理：通过 adb shell pm grant 和 adb shell pm revoke 控制应用权限，便于检查应用权限管理逻辑；注意普通 adb shell 没有 root 权限时改不了系统目录的权限。

17. 移动端测试中，当点击 APP 图标启动程序时，将会发生哪些过程？

🗣️ 回答重点

  • 操作系统察觉点击事件，即用户与图标的交互。
  • 启动与该图标对应的应用程序进程，操作系统为新的应用程序分配资源，并创建独立的进程空间。
  • 加载应用程序的组件，如 Activity（在 Android 中）或 ViewController（在 iOS 中）。
  • 执行应用程序的初始代码，包括设置用户界面、初始化变量、读取配置等等。
  • 展示应用程序的首屏界面给用户。

📈 拔高

  • Android 侧启动目标是 AndroidManifest.xml 里声明了 MAIN 加 LAUNCHER intent-filter 的 Activity；iOS 侧经 main() 与 UIApplicationMain 创建 UIApplication 与 AppDelegate，再走 scene(_:willConnectTo:options:) 完成 UI 装配。
  • 冷启动顺序是 Application.onCreate 到启动主线程、创建宿主 Activity、初始化 UI、首帧绘制，onCreate 的耗时影响最大；启动阶段只做首屏必需的轻量初始化，联网请求与大数据量处理要异步延后，这是官方明确要求的优化方向。
  • 启动分三种：冷启动是进程从零创建，温启动是进程还在但 Activity 需要重建，热启动是进程与 Activity 都在、只回到前台。闪屏只在冷启动和温启动出现。
  • 启动耗时的可测口径：Android 看 TTID（首帧）与 TTFD（完全可交互，用 reportFullyDrawn 标记），iOS 用 MetricKit 的 TimeToFirstDrawMetric。
  • 未处理异常会导致崩溃，定位渠道是 logcat tombstone 与 Play vitals 的崩溃率、iOS 的 Xcode Organizer 与 MetricKit，并且要跟 ANR 分开看。

18. 常用的 ADB 命令有哪些？

🗣️ 回答重点

  • 常用 ADB 命令包括：adb devices 列出连接设备、adb install 安装 APK、adb uninstall 卸载应用、adb logcat 查看日志、adb shell 进入设备终端、adb push/pull 在本地与设备间传输文件、adb reboot 重启设备、adb shell am start -n / 启动指定 Activity、adb shell pm list packages 列出已安装包。
  • 先列出设备确认连接正常，再按场景选用安装、日志或 shell 命令。
  • 文件传输用 adb push 与 adb pull ，方向与路径参数位置要区分清楚。

📈 拔高

  • adb devices 加 -l 会额外列出设备的 qualifiers（product、model、device、transport_id），序列号不加 -l 也默认显示。
  • adb logcat 用过滤器按级别看，如 adb logcat *:E 只显示错误；想只看某个应用，得用 adb logcat –pid=$(adb shell pidof -s )，直接 adb logcat | grep <package_name> 基本无效，因为默认输出的是 PID 而不是包名。
  • adb shell 环境中可运行 ls、ps、top 等 Linux 命令，排查设备问题相当实用；但 adbd 以非特权 shell 用户运行，chmod、chown 动应用私有目录会 Permission denied。
  • adb install 可加 -r 覆盖安装、-g 授予 manifest 里声明的运行时权限；adb uninstall 可加 -k 保留用户数据和缓存目录。
  • adb push/pull 对大型文件或文件夹操作时可加速开发和测试过程，比如把应用数据库拉到本地分析；注意 Android 7.0 起的分区存储保护，应用私有目录要 debuggable 包用 run-as 才有权限。
  • 移动端测试最常用的一组是 adb shell input（tap、swipe、text、keyevent），另有 adb shell am force-stop 强停应用、adb shell dumpsys 查系统状态。
  • adb reboot 有更多重启模式：adb reboot recovery 重启到恢复模式，adb reboot bootloader 重启到引导加载程序，方便深度调试与修复。

19. 移动端测试中，定位方式有哪几种？一般如何选择？

🗣️ 回答重点

  • 常见定位方式有 ID、Class、XPath、CSS Selector、Name、Tag Name、Link Text 七种。
  • 优先选 ID 定位，因为 ID 唯一，定位速度快、准确度高。
  • 没有 ID 且结构简单时，可考虑 Name 或 Class 定位。
  • 对复杂元素结构，用 XPath 或 CSS Selector 更灵活，但要关注性能开销。
  • 定位超链接时，可使用 Link Text 定位。

📈 拔高

  • 稳定性上，ID、Name 相对稳定，XPath、CSS Selector 更易受页面结构变化影响。
  • 可维护性上，多人协作项目应选简单明了的定位方式。
  • 性能上，XPath 和 CSS Selector 执行速度可能慢于 ID、Name，性能要求高的项目应避免频繁使用复杂 XPath 和 CSS Selector。
  • 调试时，ID 和 Name 易于在开发者工具中查找，XPath 和 CSS Selector 需编写和调整表达式，消耗更多调试时间。
  • 移动端要补 Appium 特有的定位策略：accessibility id、-android uiautomator、-ios predicate string、-image、-custom，只答 Web 那七种在移动端面试里不完整。
  • 工具方面，浏览器开发者工具可检查元素属性并生成 XPath、CSS Selector；Appium 和 Selenium 支持多种定位方式并提供 API；Chrome 的 XPath Helper 插件可生成和验证 XPath 表达式。

面试前 10 分钟速查

平台差异

  • APP 与 Web 差在四处：测试环境、网络环境、用户接口、资源管理。APP 要覆盖机型与系统版本，Web 主要覆盖浏览器；APP 要看 2G/3G/4G/Wi-Fi，Web 看不同带宽下的加载速度；APP 侧重触摸滑动与摄像头、GPS，Web 侧重鼠标键盘；移动设备资源有限，APP 必须盯资源消耗。
  • APP 专项六类：兼容性、性能、网络、电池使用、安全性、用户体验。兼容性尽量在多台真实设备上跑，性能重点是启动速度、运行速度、内存使用、CPU 占用。
  • Android 与 iOS 的差别在四点：Android 厂商自由定制、机型与分辨率杂，兼容性组合是重点；iOS 由苹果集中管控，版本单一但要跟每次系统更新的行为变化。分发上 Android 除 Google Play 还有华为应用市场、Samsung Galaxy Store、F-Droid，iOS 主渠道是 App Store，欧盟另有替代市场与网页分发。
  • 工具链不同：Android 用 Android Studio，UI 自动化用 Espresso 加 AndroidX Test、Robolectric 只跑 JVM 单元测试，可借 Managed Devices 或设备云跑真机；iOS 用 Xcode，UI 自动化用 XCUITest，Beta 分发用 TestFlight。
  • UI 规范与权限模型不同：Android 按当前版本的 Material 规范校验组件动画样式，iOS 按 Apple 的 Human Interface Guidelines 校验；Android 从 6.0 起引入运行时动态权限，iOS 同样运行时弹窗，但额外要求 ATT 授权与隐私清单。
  • Android 兼容的成本在机型矩阵取舍：按 targetSdkVersion 分层、优先覆盖主流厂商与高占比分辨率；iOS 风险集中在版本迭代，新系统版本要做专项回归。

测试内容与流程

  • 五类内容：功能、性能、兼容性、安全性、用户体验。功能测试覆盖登录、注册、支付、消息通知等所有模块；性能测试看响应时间、CPU 使用率、内存占用，工具如 JMeter、LoadRunner；安全性测试做漏洞扫描、权限验证、数据加密，工具如 Burp Suite。
  • 开展流程：测试计划 → 需求分析 → 用例设计 → 测试执行 → 测试报告。
  • 性能测试再分三类：压力测试、负载测试、稳定性测试。
  • APP 测试六步：需求分析、测试计划、测试设计、测试执行、缺陷跟踪、测试总结。需求分析要覆盖功能与非功能需求；测试计划定策略、环境、工具、进度；缺陷跟踪要记录、沟通确认并回归验证。

故障定位

  • ANR 五个成因：主线程阻塞（网络请求、大量数据处理）、死锁、GC 频繁、I/O 耗时过长（主线程读大文件、访问数据库）、线程池耗尽。
  • ANR 预防：网络请求、文件读写、数据库查询都放异步线程，可用 HandlerThread、ThreadPoolExecutor 或协程，AsyncTask 已在 API 30 废弃；主线程用 Handler 和 Looper 只处理轻量延时；减少大对象频繁创建销毁以降低 GC 压力；严格划分主线程与工作线程职责。
  • ANR 排查工具：StrictMode 检测主线程上的磁盘与网络访问并告警，Android Studio Profiler 与 Perfetto System Trace 做性能分析，Layout Inspector 查看运行时视图层次。
  • 崩溃五个成因：内存泄漏、未捕获异常（空指针、数组越界）、网络服务依赖不稳定或超时处理不当、设备兼容性差异、过度使用 CPU/GPU 导致设备过热；第三方库版本不兼容与后台任务出错也会引发非正常退出。
  • 崩溃处理对应：内存上及时释放不再使用的内存并用内存分析工具定位，代码块加异常处理并用 try-catch 和错误日志，网络侧实现超时、失败、重试机制。
  • logcat 存本地：设备 USB 连接并启用 USB 调试，终端执行 adb logcat -v time > path/to/your/filename.txt；日志量大时用过滤器和优先级，如 adb logcat ActivityManager:I MyApp:D *:S。

兼容与专项

  • Android 兼容六项：设备碎片化（品牌、型号、分辨率、屏幕尺寸）、操作系统版本、应用性能（流畅度与稳定性）、硬件特性（摄像头、传感器）、网络环境（Wi-Fi、2G、3G、4G、5G）、国际化与本地化。
  • 覆盖策略：优先测最新版本和市场占有率高的旧版本，官方分布图是不定期快照，判断自家用户分布看 Play Console 的 Reach and devices；覆盖不全时用设备云，如 AWS Device Farm 或 Managed Devices，Firebase Test Lab 已弃用、2027-09-30 关停。
  • APP 兼容四步：选有代表性的安卓与 iOS 设备及不同系统版本，再做安装卸载测试、核心功能测试、UI/UX 显示测试，然后模拟弱网、丢包、高延迟、4G/5G 切换与断网重连看性能指标与安全漏洞。
  • 兼容工具：自动化用 Appium，Robot Framework 属通用框架需配 AppiumLibrary，Calabash 已停止维护；预算不足用云测试服务 AWS Device Farm。跨平台框架 React Native、Flutter 的真实风险集中在原生模块、插件与平台差异。
  • Push 测五步：确认推送服务配置正确（证书/令牌、SDK 集成）→ 触发推送（服务器脚本、第三方平台控制台或测试代码）→ 验证前台后台都能收到 → 点击交互与定向跳转 → 异常场景（弱网接收、离开通知栏能否在应用内找到、更新或重装后能否继续接收）。正式推送前可做 A/B 测试比较文案、图标、声音的效果，并关注传输加密。
  • 交互性六项：功能性（按钮、链接、交互元素正常）、用户体验、响应时间、兼容性、可访问性、压力测试；原生 APP 用 Appium 模拟操作，Selenium 只能驱动浏览器；用 Usability Testing 邀请真实用户捕捉自动化发现不了的细节，可集成 GA4 或 Firebase Analytics 监控用户行为。
  • 安装卸载更新：安装要在不同设备与系统版本、Wi-Fi/4G/5G 下验正常安装，也验存储接近满载时的安装；卸载验数据彻底清除与强制关闭后卸载不崩；更新验旧版升新版数据不丢、断网恢复、逆向降级无异常。性能监控用 Android Profiler 或 iOS Instruments，日志用 adb logcat 或 Console.app。
  • H5 测五类：功能、兼容性、性能、用户体验、网络环境；另查设备分辨率与屏幕尺寸下布局不错位遮挡、触屏滑动长按缩放与多点触控、系统权限请求、缓存与本地存储（Web Storage、IndexedDB）恢复、前端安全（XSS 与 HTTPS，CSRF 防护由服务端实现）。工具用 Chrome DevTools 设备模式、BrowserStack、Sauce Labs。
  • 小程序四维度：功能（注册登录、页面跳转、信息提交）、性能（响应速度、加载时间、内存占用）、兼容性（不同品牌、分辨率、系统与微信版本）、安全性（传输安全、隐私）。功能测试分单元测试（Jest 或 Karma）、端到端（miniprogram-automator）、手工测试（真机）；miniprogram-simulate 是组件级单元测试工具集。

落地手段

  • ADB 是什么：Android Debug Bridge，命令行工具，直接与 Android 设备通信，用于开发和测试阶段，提供安装应用、调试程序、复制文件等功能。
  • ADB 两种连接：USB 连接需在设备上打开「开发者选项」里的「USB 调试」并接受 RSA 密钥授权；Android 11 起主推「无线调试」，用 adb pair 加 adb connect 走 TLS 加密连接。adb devices 查看当前连接的设备。
  • ADB 六类作用：应用安装卸载调试、PC 与设备间文件传输、命令执行、设备管理、实时日志查看、模拟用户输入（adb shell input 的 swipes、taps）；还能备份恢复（adb backup/adb restore）与远程调试。
  • 常用命令：adb devices 列设备（加 -l 看型号和序列号）、adb install <apk_path>（-r 覆盖安装、-g 授予所有运行时权限）、adb uninstall <package_name>（-k 保留数据和缓存）、adb logcat 看日志、adb shell 进设备终端、adb push/adb pull 传文件、adb reboot 重启、adb shell am start -n <package_name>/<activity_name> 启动 Activity、adb shell pm list packages 列已装包。
  • shell 里能用 Linux 命令：ls、ps、top、chmod、chown 等，排查设备问题实用。
  • logcat 过滤：按包名过滤 adb logcat | grep <package_name>，按级别 adb logcat *:E 只看错误。
  • APP 启动五步：操作系统察觉点击事件 → 启动应用进程并分配资源与独立进程空间 → 加载组件（Android 按 AndroidManifest.xml 启动主 Activity，iOS 调用 AppDelegate 中的方法如 application:didFinishLaunchingWithOptions:）→ 执行初始代码（加载界面布局、联网请求与读取本地配置、注册监听器）→ 绘制首屏，可能先展示闪屏或启动动画。
  • 冷启动与热启动：冷启动从零创建进程与加载资源，热启动进程仍在只需恢复运行状态。启动耗时直接影响体验，要做性能分析优化耗时环节。
  • 定位七种：ID、Class、XPath、CSS Selector、Name、Tag Name、Link Text。优先 ID（唯一、速度快、准确度高），没 ID 且结构简单用 Name 或 Class，复杂结构用 XPath 或 CSS Selector（更灵活但有性能开销），超链接用 Link Text。稳定性上 ID、Name 相对稳，XPath、CSS Selector 易受页面结构变化影响。
  • 定位的三个权衡：性能上 XPath 和 CSS Selector 执行慢于 ID、Name，高性能要求的项目别频繁用复杂表达式；可维护性上多人协作项目应选简单明了的定位方式；结构上 ID、Name 稳定，XPath、CSS Selector 易变。
