全栈开发实习面试复盘（11-05）--支付退款与高并发场景题

Hi，我是 meisijiya ，也是 老江湖 ，感谢你的阅读，我们一起进步。

岗位是跨境广告代运营公司的全栈开发实习生，业务是广告代运营加支付结算。技术面全程围着支付退回、高并发、消息队列转，没有问 Go 语法。这次失分不在语言，在三块：支付概念空白、场景题没答到点上、压测口径没底。

零、三处硬伤

现场问题 我的答法 失分点 改法
支付平台与支付方式了解多少 “Redis 加 Luna 的一个时间命名” ①Lua 说成 Luna；②Redis+Lua 是扣减与限流的实现手段，不是支付概念 背第二节的支付五接口与状态机
已支付订单被取消退款怎么办 “消息队列异步落盘、延时落盘” 方向对了一半（异步 + 最终一致），但没戳中最关键的一句：钱已经出去了，不能撤销，只能退款 用第一节的四时序答法
高并发怎么做的 单机部署、说了一个 JMeter 线程数 没有真实数据支撑，一问 Ramp-up、思考时间、P95、瓶颈在哪就露 用 bench.py 真跑一次，拿本机真数据

第三条最危险。技术面的人天天看压测报告，临时凑的数字撑不过两个追问。诚实说”没做过严谨压测”不会扣分，硬凑数字会被直接看穿。

一、”支付成功又取消退款”的标准答法

先给结论句（这句必须有）

支付一旦成功，资金已经到商户或平台账户，不存在”撤销支付”，只能走退款。所以这个场景不是取消订单，是生成退款单，把已收的钱退回去。真正要解决的是两件事：退款请求不能重复执行，退款结果必须和渠道对得上。

我当时答的”异步、延时”讲的是手段，缺的是这层判断。

四种时序，分别答

时序 现场状态 正确做法 不这么做会怎样
A. 订单未支付 超时未付款，用户点取消 关闭订单。关单前先查单 用户其实刚付款成功、回调还没到，直接关单 → 钱收了单没了
B. 回调未到 用户说付了，系统还没收到通知 主动调渠道查询接口，查到已支付就按已支付处理 直接退款 → 退了一笔系统以为没付过的钱
C. 已支付 状态已置”已支付” 生成退款单 → 调渠道退款接口 → 等异步回调 → 置”已退款” 同步改状态 → 渠道退款失败，本地状态和资金对不上
D. 退款失败/超时 渠道返回失败或没回调 按退款单号重试（幂等）＋ T+1 对账兜底 单边账，用户投诉才被发现

一致性四件套（面试官想听的骨架）

  1. 状态机：待支付 → 已支付 → 退款中 → 已退款；失败回滚到已支付。状态只能往前走，不允许跳变。所有写操作带状态前置条件（WHERE status='已支付'）。
  2. 本地消息表（outbox）：改订单状态、插退款单、写待发消息，同一个本地事务提交。再由投递器把 outbox 的消息发到 MQ。这样不会出现”数据库改了但消息没发”。
  3. 幂等：两次幂等键——下单用 out_trade_no，退款用 out_refund_no，都建唯一索引。同一单号重复请求，第二次直接返回第一次的结果。渠道回调也可能重复推送，所以回调处理也要判状态。
  4. 对账：每天 T+1 下载渠道对账单，和本地流水逐笔比。差异分三类——本地有渠道无（长款）、渠道有本地无（短款）、金额不一致。差异单进人工或自动补偿任务。

45 秒现场版（背这段）

支付成功之后不存在撤销，只能退款。我会先看订单处于哪个状态：
如果还没支付，关单前一定先查一次渠道，防止钱到了单被关了；
如果已经支付，就生成退款单，用商户退款单号做幂等键，调渠道退款接口，退款是异步的，等回调再改状态；
退款失败就按单号重试，同时靠每日对账兜住单边账。
状态迁移我写成状态机，改库和发消息用本地消息表放在同一个事务里，避免状态改了消息没发出去。

已经在本地跑通的最小实现

二、支付基础：面试前 30 分钟能补上的概念

概念 一句话 常被追问
支付方式 网关支付（银行卡）、第三方钱包、余额、代扣、聚合支付 代扣和主动支付的区别：无需用户每次确认，靠签约
三方角色 商户（我方）、渠道（微信/支付宝/银行）、清算机构 资金流和信息流是两条线
五类接口 下单、支付、查询、退款、回调通知 每个都要幂等＋签名
幂等键 out_trade_no 下单，out_refund_no 退款 重复请求返回首次结果，不是报错
回调验签 用渠道公钥验签，再判状态做幂等 回调可能重复、可能乱序
退款 异步：渠道受理 ≠ 到账；原路退回；支持部分退款 受理后要等结果通知或主动查
对账 T+1 下载对账单，逐笔比对，差异单分类处理 长款/短款/金额不符
结算 平台按 T+N 结算给商家，可含分账与佣金 结算单与订单不是一对一
多币种 币种最小单位不同（日元无小数），汇率要留快照 金额用整数最小单位或 Decimal，禁止 double
状态机 待支付/已支付/退款中/已退款/已关闭 状态不可跳变，写操作带前置校验

面试答题时的关键取舍：能说出”金额不能用浮点”和”退款是异步的”这两点，比背十个支付方式管用，因为这两条是踩过坑的人才会强调的。

三、高并发：不要临时凑数字

为什么不要凑

技术面的追问链是固定的：线程数多少 → Ramp-up 多久 → 有没有思考时间 → P95 多少 → 瓶颈在应用还是数据库 → 怎么确认的。”100 线程”答完，第二个问题就会卡住。

三档诚实答案

真实情况 怎么说
完全没压过 “我没做过容量压测。我知道压测要看 P95 和错误率，不看平均 RT，也知道线程数不等于并发数。如果给我一个接口，我今天能跑出第一版数据。”
跑过小规模 “我在本机压过一个接口，20 线程 400 次请求，QPS 大约 80，P95 20 毫秒出头。这是本机回环，没有参考价值，主要用来验证脚本和指标口径。”
跑过链路 讲清楚压测目标、瓶颈定位顺序、优化前后对比

我当时处在第一档和第二档之间——花 20 分钟就能升到第二档，见下。

真跑一次（bench.py，纯标准库，无需 JMeter）

实测输出（对本地测试服务，一次运行的样例）：

QPS 基本固定，由线程数与 ramp-up 决定；延迟随本机服务与机器负载波动，P50 在 2–16ms、P95 在 23–24ms 之间都出现过。所以这套数字只能证明脚本可用与口径正确，不能当性能结论。

拿到真实数字后，面试直接说这个数字，并主动交代”本机回环、单机、没有参考价值，我用它验证口径”。

Windows 坑：urllib/requests 默认读系统代理，压本地服务会被代理截成 400。脚本里已经用 ProxyHandler({}) 绕开，requests 则要传 trust_env=False。

压测口径（面试能立刻显得懂行）

口径 说明
线程数 ≠ 并发数 线程按 Ramp-up 逐步启动，没有思考时间时并发才逼近线程数
思考时间 模拟真实用户停顿，否则并发被高估
看 P95/P99，不看平均 平均值被长尾掩盖，SLA 一般按 P95 承诺
错误率必须一起看 高 QPS 伴随超时，等于没压
压测环境 生产数据量、同等机器规格，否则数字没意义

瓶颈定位顺序

应用（线程池/GC/日志）→ 连接池 → 数据库（慢查询、锁、连接数）→ 缓存（命中率、大 key）→ 网络与带宽 → 下游依赖。

秒杀/高峰期四板斧

限流（网关或令牌桶）、缓存（热点数据前置）、异步（下单落 MQ 削峰）、降级（非核心功能关掉）。这岗 JD 写”节假日高峰期”——这一点是送分题，主动提一句预案，比等他问更好。

四、Vapor 项目怎么讲给高并发岗

不要说”这是个学习项目、单机部署”。同一个项目，换成链路语言讲，含金量完全不同：

秒杀这条链路我拆成四层。
接入层先做限流，超出的流量直接拒绝，不打到后端；
应用层把资格校验和库存扣减压进一次 Redis + Lua 原子执行，避免”查完还有货、扣的时候没了”的超卖；
异步层把下单落库放进消息队列削峰，接口先返回受理成功；
数据层按”先更库后删缓存”改造，删缓存失败用消息补偿加 TTL 兜底。
幂等靠请求唯一标识加唯一索引，超时重试只会生成一单。

每一句后面都能接”不做会怎样”：不限流 → 打穿数据库；不原子 → 超卖；不削峰 → 峰值写库雪崩；不补偿 → 缓存脏数据。

单机部署不是缺点，讲清楚边界就行：”单机能跑通链路，多实例要处理的是分布式锁和库存分片，这部分我只做过设计和验证，没有在集群上跑过。”

五、HR 面：商用化、落地、获客、业务了解

三问框架

任何”这个项目怎么商用”都用这三问接：谁付钱 → 为什么付 → 怎么获客。答不上第三问就诚实说没想过商业化。

VidDigest 的商用答法（诚实版）

这个项目目前的定位是技术验证，没有商用。如果要商用，三件事必须先解决：一是内容版权，抓取他人视频做摘要涉及授权；二是成本，模型调用按次计费，免费用户会直接把成本拉爆，需要配额和付费分层；三是获客，工具类产品靠搜索和社区扩散，我的方案是先做垂直场景，比如只服务某类内容创作者。

我没有做过真正的商业化，所以这块只能给思路，不能给结果。

主动说”没做过”比硬编一套增长方案更稳，HR 面考的是判断力不是业绩。

对方这块业务怎么接话

岗位描述写的是跨境广告代运营，做店铺管理、广告开户、账号管理、佣金与广告费结算、多币种对账与权限校验。可以这样接：

我理解你们是帮商家在海外短视频平台开店和投广告，收入来自服务费或佣金分成。所以系统里钱有两个方向：一边是商家充值投广告，另一边是平台结算回来再分给商家。这两边都要对账，多币种还要处理汇率和币种精度。我没做过跨境电商，但支付这块的通用问题——幂等、状态机、对账——我能对上。

不要硬说”我研究过海外广告后台”，JD 里”了解跨境广告/跨境电商”是加分项，不是必需。

六、为什么这次笔记没派上用场

判断是对的：语言基础题属于笔试，项目追问和场景题属于面试，两套东西。前面那份 Go/React 速通笔记回答了”Go 的 map 是不是并发安全”，但没回答”退款怎么办”。

旧路线 新路线
语言语法、框架 API 项目的每个技术选择”为什么这么选、不做会怎样”
知识点罗列 场景题：给一个业务现象，讲判定和处理顺序
单点正确 一致性、幂等、对账这类跨模块问题
背结论 能说出被追问三层的细节

写新笔记的自检标准只有一条：**这篇里的每一节，能不能直接回答”面试官问我项目里的某某，我怎么答”**。答不上就不该写。
