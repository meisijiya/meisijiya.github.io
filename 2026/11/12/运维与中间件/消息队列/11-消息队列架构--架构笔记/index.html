这篇从一个转圈 3.2 秒的叫车接口讲起，把消息队列的角色、代价、Redis Streams 写法和选型口径一次讲完。

11.1 引言：一个转圈 3.2 秒的叫车接口

🔹 视频开场给了一个事故。网约车平台「飞驰出行」，乘客点「叫车」后 App 白转了 3.2 秒，才跳到「正在为你派单」页面。深究底层，这 3.2 秒是五步串出来的：

步骤 耗时
校验乘客定位 120ms
写行程单 180ms
派单给司机 900ms
记行程积分 800ms
更新乘客画像 1200ms

🔹 慢不在等司机。早晚高峰运力紧张，等一会儿用户能接受。慢在接口。点了按钮页面没反应，用户不知道发生了什么。普通时段都这样，晚高峰五步叠加可能涨到十来秒，甚至报错。

🔹 两个细节值得注意。积分和画像排在主链路上，可积分晚 10 分钟到账、画像晚一小时更新，用户当下感知不大。五步又是串联的，任何一步抛异常，整个叫车就回滚。晚高峰网络抖一下、某个服务发个版，超时率就飙升，用户投诉的是「用 App 叫不到车」。

🔹 根源在于这个接口把用户当下没在等的事情干完了才返回。一个跟叫车成败无关的服务挂了，凭什么拖累整个叫车。要解决它，就要用到今天的主角——消息队列。

11.2 认识消息队列：是什么、为什么能治病、代价是什么

11.2.1 五步串成一条链，三宗罪

🔹 叫车接口从上到下五步：校验定位、写行程单、派单、记积分、更新画像，合计 3.2 秒。前三步是用户真的在等叫车时要等的，后两步晚一点用户也能接受。这五件事重要性有差别，现在却排成一队同生共死。排成一队就有三宗罪：

  • 慢：串行调用下总耗时是加法，每一步加起来就是用户等待的时长。没有任何一步慢得离谱，加起来却明显慢了。
  • 脆：可用性是乘法。五步每步都能达到 99% 可用，乘起来是 95% 可用。积分服务抖一下，前面的活儿全白干，整个叫车失败。
  • 崩：晚高峰每秒可能来上万个请求，接口里的调用全怼到数据库上。多出来的请求只能排队，压垮连接池和 CPU。同步系统没有缓冲的概念，流量什么形状，压力就什么形状。

🔹 三宗罪的病根，是所有事不管多急多慢、靠不靠谱，都挤在同一个管道里，必须同一时刻按顺序干完。病根不在某一步慢，在排队这个结构本身。结构的问题改配置解决不了，要换的是结构。

11.2.2 快递柜比喻：四个角色

🔹 把消息队列想成小区里的快递柜，四个画面就能对上：

  • 生产者 Producer：快递员把包裹放进格子，关上柜门就去送下一单，不等收件人拆、不等签收。对应代码里叫车服务不直接调积分服务，而是把「行程已创建」写成一条消息塞进柜子，塞完就返回，乘客很快看到「派单中」。
  • Broker：柜子自己负责暂存，有电源有锁，24 小时都在。它是独立运行、先把消息存下来的中转程序。关键在「独立」两个字，寄件人和取件人从不见面，放下就走、有空来取，谁也不等谁。
  • 消费者 Consumer：取件人有空来取，下班顺路取件，六点下班还是加班到十点都行。定义是订阅并且处理消息的那一方。积分服务抖动或宕机，柜子里的消息原封不动等着，叫车本身一点不受影响。
  • 重试与死信：取件人拆开发现商品是坏的，退回去重发一次，这叫重试。重发几次都不行，就有一个坏件专柜，消息进死信，等人工处理。

🔹 设计原则只有一条：消息永远不会凭空消失。四个画面合起来就能下定义——消息队列是一个独立运行的中转程序，发送方把消息塞进去就返回，接收方按照自己的节奏取出来去处理。

11.2.3 核心模型：topic、点对点、发布订阅、推拉

🔹 柜子的内部结构就是消息队列的核心模型。生产者把「行程已创建」打包成一条消息交给柜子就返回。柜子不是一整片格子混着放，它是有分栏的：行程事件一栏、支付事件一栏、用户事件一栏，每一栏只放一类消息。这个分类栏在行业黑话里叫主题，也就是 topic。分栏是为了让积分服务只收行程事件，混着放它得一条条挑出支付消息扔掉，白费功夫。

概念 视频里的定义
主题 topic 柜子的分类栏，每栏只放一类消息
点对点 一件包裹只能一个人取走
发布订阅 行程事件这一栏，积分、画像、推荐各拿一份复印件
推 快递员把包裹送到你本人手上、送到家里
拉 你去快递柜里取，按自己的消化能力来，不会被撑死
消费者组 同一栏的件分给组内几台机器各处理一部分

🔹 业务消息基本都是发布订阅模式，一次发布多方各自订阅。消费者自己拉，按自己的消化能力来，不会被撑死，主流也是拉模式。扩容有两条路：换更强的机器是纵向扩容，多加几台普通机器是横向扩容。

🔹 对常见产品，界面五花八门，骨架都是这张图。主题在不同产品里叫法不同：Kafka 叫 topic，Redis 可以记成 stream。

11.2.4 位点与消费者组

🔹 柜子怎么记住每个取件人取到哪了？给每个取件人发一张取件进度卡，上面记着「你已经取到第三件了」，取一件确认一件，卡片上的数字往后挪一格。重启或断电恢复后照着卡片继续取，取过的不会重来，没取的也不会漏掉。这张进度卡在消息队列术语里叫位点，英文 offset，是后面不丢失、不重复的第一根支柱。

🔹 画像服务一台机器处理不过来怎么办？纵向扩容很可能很快到天花板，那就多来三台普通机器，把行程事件栏里的件分着取，这叫横向扩容。一条消息只给一台机器处理，三台就是三倍速度，坏一台也只是停了三分之一。这几台机器组成一个消费者组，共享同一张进度卡。画像组和积分组是两张不同的卡，画像取完了积分才取一半，互不拖累。这就是发布订阅，一条消息，每组各拿一份。

📌 考点：位点 offset 是取件进度卡，保证取过的不会重来、没取的不会漏掉；消费者组共享同一张进度卡，组内一条消息只给一台机器，不同组各收一份。

11.2.5 代价与「什么时候不要用」

🔹 消息队列不是免费引进来就能用的，四个代价要摆上台面：

  • 一致性变慢：同步时积分画像当场做完，叫车才算成功；异步后叫车先成功，积分可能晚几分钟才到。中间有一段数据暂时不一致的窗口。业务能容忍就没关系，不能容忍还得放回同步。
  • 会重复：队列的保命设计是宁可重复、不可丢失，同一封信息可能推送两遍。收件方必须认得出「这单我已经处理过了」，这个能力叫幂等。
  • 可能积压：消费者慢了或挂了，柜子里的件越堆越多，必须有人盯着堆积量配告警。
  • 多一摊运维：原来只管数据库，现在要多一套部署、监控和扩容的集群。

🔹 什么时候不要用，也有三条标准：用户要立刻拿到结果的操作不要用，查余额、支付确认异步了会影响使用；只有一个系统在用的话，没必要自己跟自己解耦；流量平稳的小系统，一天只有几千单，没有流量洪峰，也没必要削峰填谷。

🔹 用消息队列，付出的是及时一致性和简单性，换回的是主链路飞快、故障隔离、洪峰缓冲。这笔账在不同系统上算的结果不一样。消息队列的使用应该是一个架构决策，不是每个系统默认的操作。

11.2.6 一条消息的一生：五站

🔹 一条消息从生产到被处理完，一共经历五站。每一站都要问两个问题：可能出什么事，保障机制是什么。

站 风险 保障机制
发送 网络抖动，消息没进柜子 发送确认：柜子收到后回一个消息编号，拿到才算放进去，没拿到再发一次
存储 硬盘坏了 刷盘加备份，主柜坏了备用柜子顶上，两个柜子互为副本
投递 消费者刚拿到就掉线 没有确认就一直算没送出去，消息在柜子挂着，回头再次投递
处理 代码抛异常，处理到一半失败 自动重投机制
签收 处理完了要回一句「这条我处理完了」 回完这句，进度卡才往前挪

🔹 签收之前，消息都不算处理完。处理之后、签收之前这段时间万一崩了，队列以为你做完了，这单就可能永远丢在半路。宁可迈一步去签收，也不能让它丢掉。

🔹 排查故障有口诀：消息丢了，查第一站、第二站；消息卡住不动，查第四站；消息重复了，看第五站。

11.2.7 自动重投与死信

🔹 消费者处理失败，队列要走四步：

  1. 消费失败：画像服务处理一条消息要调推荐引擎，推荐超时，代码抛异常，这条没处理完也没签收。
  2. 自动重投：队列没收到「处理完了」的确认，就把消息再交出去一次，失败了再试，全程自动。值得重试是因为很多故障是暂时的，数据库正在重启、网络抖动一下，过十秒再试一次就好。但重试不能无限去重试。
  3. 死信：重试了三次都失败，说明多半是代码有 bug 或数据本身有问题，再试一万次也没用。把这条消息挪进专门的死信专区单独存放，不再挡路，配上告警，有人之后来查询，修好后重新投递。
  4. 人工闭环：值班运维看死信，定位原因是 bug 就修完重投，是脏数据就登记结案。每条坏件都有下落、有闭环。

🔹 中间有一把尺子叫投递计数：队列给每条消息记被送过几次。一次可能是抖动，三次失败就可能是真的坏了，这个次数是区分暂时故障和真正坏件的分界线。

🔹 重试有副作用。上次可能已经干了一半，积分已经加过一次，再投一次就再加一次。

11.3 消息队列实战：Redis Streams 四段代码

🔹 视频讲这四段代码时，给的是方法名和对应的 Redis 原生命令，代码本身在画面上。下面按它讲的调用顺序还原，参数与签名对着 Spring Data Redis 的 StreamOperations 写，实际项目照抄前还是要跑一遍。

11.3.1 为什么拿 Redis 练手

🔹 队列软件有很多，这里用 Redis 练手有三个原因：项目里很可能已经有 Redis 在跑缓存，不用再装一套新的东西；Redis 的命令就几个，一个下午就能上手，概念和理念却跟很多消息队列产品完全相通，在这里学会了去哪儿都能很快上手；中小系统的消息量，Redis 的消息队列就扛得住。

🔹 对应关系要记住：前面说的主题，在 Redis 里叫流 stream，一条流就是一个主题。改造判断依据也只有一条：这一步的结果，用户当下要不要看到。校验定位、写行程单、派单给司机留在主链路；积分和画像搬到消息队列。

11.3.2 第一段：生产者发消息

🔹 代码头三行是校验定位、写行程单、派单给司机。中间两行注释是原来调积分、调画像的同步调用，都注释掉。删掉的位置换成一行 redis.opsForStream().add。

🔹 这个方法底层对应 Redis 命令 XADD。X 是 Redis 消息队列这套命令的统一前缀，ADD 是追加。其他方法 XREAD、XGROUP、XACK 也都是 X 前缀加动作。add 方法干三件事：把消息追加到流末尾；自动生成消息 id，格式是毫秒时间戳加序号，同一毫秒内自增，先来的编号小，天然按先后排好；返回这个 id，生产者拿到它就知道消息真正进入流里了。

🔹 消息设计有取舍。消息里只放线索，不能放全部内容。积分要算里程、画像要算行为明细，可以拿着 trip id 回查数据库。消息是事件通知，不是数据搬家，把数据放进消息体，消息会越滚越大，柜子就变成数据库了。

🔹 生产者这三步加 add 这一行，一共花 1.2 秒，对比前面 3.2 秒的总耗时少了很多。这里埋一个伏笔：如果 add 方法失败了，行程建了、事件却没进流，怎么办？后面有三道防线回应。

11.3.3 第二段：消费者组读、干活、划账

🔹 以画像服务为例，方法整个是一个死循环，分三步走：读、干活、划账。

🔹 这一长串 Java 调用对应原生命令 XREADGROUP。三个关键参数：profile-group 是组名，视频说 Redis 看到新组名就会自动建组，官方文档反着：组不存在时 XREADGROUP 直接报 NOGROUP，得先 XGROUP CREATE trip-created profile-group $ MKSTREAM 建组，组内的 worker 名字才是第一次读时自动创建的；worker-1 是组内身份，一条消息只会给组内一个工人，有两个 worker 就是两倍速度；lastConsumed 是从组上次读到的地方继续读，新消息在等着，读过了就不再来。

🔹 acknowledge 对应原生命令 XACK，ACK 是 acknowledge 的缩写，意味着确认和签收机制。告诉 Redis 这条已经处理完了，挂账单上划掉，位点前移一格。要注意精确传消息 id，Redis 不会记得你刚处理的是哪条，它只认编号。

🔹 位点保证消息不漏，没读过的下次还会读到。挂账单保证消息不丢失，在 Redis 里叫 PEL，也就是待确认列表。干了活儿没有划账的消息都挂在上面，还能再领出来处理。进程在干完活但还没划账之间崩溃，重启后这条会被再次投递。

11.3.4 幂等：SETNX 加唯一索引

🔹 幂等要防的就是这份重复。前面重试了两次，第三次已经成功，位点还没来得及提交，柜子又投递第四次，画像服务就重复计算。消费者自己要会确认「我是不是已经干过了」。

🔹 这一行代码就是 SET NX 加过期时间。键不存在就写入，已存在就什么也不做；不存在写入后返回 true，什么也不做就返回 false。查询和写入一步完成，中间没有缝隙。Redis 单线程处理命令，两个请求同时到也必然一前一后，不存在「查到没有但都写入了」的情况。

🔹 键的设计比代码重要。业务动作加单号，这里是 done:trip: 加行程 id。同一个行程的积分和画像是两个键，互不干扰；不同的行程天然就是不同的键。想清楚什么时候算重复，再动手。

🔹 判断主逻辑：first 是 false 就代表已经处理过，直接 return 跳过正事，但照样走到最后的 XACK 划账，不然它永远待在待确认表里被反复重投。first 是 true 就是第一遍收到，用 pointService.add 处理。Redis 能挡掉可能 90% 以上的重复，还设置 24 小时过期让键不会无限堆积。Redis 也宕机的话，还有数据库的唯一索引兜底，核心业务把这两层都上了，通知类业务只上一层就够。这样就保证了至少送达一次和只生效一次。

11.3.5 第四段：死信清扫定时任务

🔹 坏件最后去哪？进坏件专柜。每分钟跑一次的定时任务，分五步：

🔹 第一步 XPENDING 查出 profile-group 在 trip-created 流上超时未划账的消息，一次最多十条，这些是领了件但没签收的。第二步用投递计数判断坏没坏，大于等于三说明有三个清扫周期还挂着，不是暂时故障。这一步是整个任务里唯一的策略，通过次数定多少，重试的耐心和坏件的滞留时间要有平衡。第三步 XCLAIM 领回，把消息所有权从原工人转到清扫人 sweeper 名下。为什么要先领回？待确认表里的消息不一定读得出来，得让它先成为你的，才能转去投递。第四步把消息内容通过 add 进入 trip-dead 死信流，原流上通过 XACK 划账，从待确认表清除，PEL 就不会无限堆积。第五步告警推给值班运维群，运维看消息体和日志定位原因，修好后把消息通过 add 回到源流再走一遍，脏数据就登记结案。每条坏件都有下落、有闭环。

11.3.6 削峰填谷与对账

🔹 削峰总结就两句：上游照单全收，下游匀速消化。早晚高峰每秒可能上万个叫车请求，改造前峰值流量直冲数据库，不扩容就会崩溃。改造后通过 add 方法每秒 1 万个照单全收，Redis 追加写这个量级毫无压力；消费者每秒以 2000 的速度匀速消化。10 分钟洪峰达到几十万条，排队花 50 分钟到一个小时清理完，积分和画像最晚半个小时或一个小时更新，系统不会崩溃。

🔹 这几个数按公式算并不闭合：几十万条除以每秒 2000 只有几分钟到十几分钟。视频给的是课堂上的量级，真正定容量要拿自己压测出来的洪峰量除以消化速度，别照抄。

🔹 两个要注意的点：上游也要限流，网关要限制单机 QPS，别让洪峰先打垮叫车服务本身；容量要提前算，洪峰量除以消化速度等于积压时长，超过业务容忍度就要提前加消费者，或者在组内加 worker。

🔹 对账结果：接口耗时从 3.2 秒变成 1.2 秒，砍掉的全是用户不想等的，留下的全是真的在等的。积分服务宕机一小时，改造前叫车事件全挂，改造后叫车不受影响，恢复后还能追着消费补齐。晚高峰上万 QPS，改造前直冲数据库，改造后排队匀速处理。新增下游，改造前要改叫车服务代码发版，改造后它自己去订阅，上游零改动。可靠性上，改造前一步失败全部回滚，改造后有自动重试加死信兜底。异步的代价是积分和画像从当场完成变成晚一段时间完成，用户当下叫车时影响不大。快只是副产品，挂了也不怕才是主菜。

11.4 可靠性：不丢失、不重复、不乱序

11.4.1 不丢失：三道防线

🔹 第一道防线在发送端。XADD 网络超时，消息根本没放到柜子。要确认回执加失败重发：add 方法返回值是消息 id，拿到 id 才算真的进流，没拿到就捕获异常重发一次。寄件人要看到柜门真关上才走。

🔹 第二道防线在存储端 broker。消息进了柜子，Redis 掉电宕机怎么办？Redis 有 AOF 持久化加主从复制。写操作先记到 AOF 日志再应答，主从结构下主库再复制一份，主库挂了从库顶上。代价是如果设置 appendfsync everysec 每秒刷一次盘，极端掉电最多丢最后一秒的数据。这是 Redis 队列和专职消息队列拉开差距的地方。专职队列能配到一条不丢，代价是吞吐和复杂度，前提是 Kafka 那边 acks=all 配上 min.insync.replicas 且副本活着，RocketMQ 那边要同步刷盘加同步复制，默认配置下并不保证。

🔹 第三道防线在消费端。业务处理到一半断电，划账没发出去，怎么办？处理完才划账，用 XACK，没划账的消息挂在待确认表，重启后重新读出来处理。划账之前消息都不算处理完。

🔹 三道防线配齐，Redis 消息队列在极端情况下最多丢最后刷盘的那一秒。要考虑资产损失级别的业务就不用 Redis 队列，用专职消息队列；通知、积分这类丢一条也能接受的业务，用 Redis 刚刚好。不丢的代价是可能重复，所以还要幂等机制保证不重复。

11.4.2 不重复：幂等三板斧

板斧 做法 适用
第一板斧：Redis 查重 setIfAbsent 那几行代码，拦住大多数重复 通知类、可接受偶发重复
第二板斧：数据库唯一索引 积分流水表给行程 id 加唯一约束，第二条重复插入直接报错，捕获后跳过 扣钱这类没状态但怕出事的
第三板斧：状态机 带着条件的更新，全靠数据库行锁和 SQL 语句 订单、行程这类本身有状态流转的

🔹 第一板斧是 Redis 查重，前面讲过的 setIfAbsent 代码能拦住大多数重复。第二板斧是数据库唯一索引，积分流水表给行程 id 加唯一约束，第二条重复消息插入直接报错，捕获后跳过，Redis 挂了也拦得住。第三板斧是状态机，说白是带着条件的更新，不依赖 Redis，也不依赖额外的唯一索引，全靠数据库自带的行锁和 SQL 语句实现。

🔹 平时更新状态可能写 UPDATE orders SET status = '已发货' WHERE id = 123，重复消息来两次就执行两次。状态机写法加一个前置条件 AND status = '已支付'。第一次来时数据库状态是已支付，满足条件，更新成功；第二次重复消息来时状态已是已发货，WHERE 条件不满足，数据库直接忽略，影响行数为零，天然跳过。它稳定、零成本，适用场景是业务对象本身有状态流转，比如订单的已支付、已发货。

🔹 三板斧怎么配合：业务有状态，比如订单、行程，优先用第三板斧，低价且能实现防重复；没有状态但怕出事，比如扣钱，用第一板斧加第二板斧双重保险；只是发个通知，无所谓重复不重复，只用第一板斧，Redis 轻量挡一下就行。

11.4.3 不乱序

🔹 好消息是 Redis 一条流天然有序，消息 id 是时间戳加序号，先 ADD 的永远排在前面。专职队列像 Kafka 可能为了吞吐把一个主题拆成很多分区并行做，并行才是乱序的来源，那套要拿 offset 去分区，属于产品范畴，讲专门的 Kafka 时再讲。

🔹 Redis 真正的坑在消费端。组内多个 worker 并行取就可能乱序。worker-1 拿到接单，worker-2 拿到行程结束，谁先干完不一定。要严格顺序就是一组一个工人，单线程消费，一条处理完才取下一条。顺序和吞吐之间二选一，这是物理规律。

🔹 什么时候需要顺序？消息之间有前后依赖才需要，比如行程状态流转要先接单后结束，账户流水要先加后减。两条推送类消息谁先到谁后到，用户根本不关心，没必要为顺序牺牲并行度。

11.5 生产与选型：三大产品与 Redis 队列的边界

11.5.1 三大消息队列产品

产品 定位 吞吐 代价/边界
Kafka 数据管道，顺序写磁盘、成批搬运 单集群每秒上万到上百万条（视频口径） 生来搬日志，回执、重试、死信要自己搭积木
RocketMQ 业务消息专家，事务消息、延迟消息、消息轨迹 10 万级别（视频口径） 不如 Kafka 极致，可靠性开箱即用
RabbitMQ 灵活路由，规则最丰富，管理界面友好 上万级别（视频口径） 超大规模场景不适合

🔹 Kafka 可以理解为一个数据管道。LinkedIn 当年每天都有上亿条用户行为日志要搬运，用传统消息队列可能直接趴下。用 Kafka 的思路是别把消息当一封信，要当成一股水流，顺序写磁盘、成批搬运，就能快到飞起来，单个集群每秒能处理上万上百万条。代价是它生来就是搬日志的，不太关心这一条有没有被处理完，业务消息要的回执、重试、死信都得自己在上面搭积木。日志采集、数据管道用 Kafka，因为它就是干这个的。

🔹 RocketMQ 像是一个业务消息专家。阿里双 11 交易链路，订单、支付、库存这些场景要的全都有：事务消息，下单和扣库存要么都成要么都不成；延迟消息，30 分钟没有支付就自动关闭订单；消息轨迹，这条消息谁发的谁消费全要记着。RocketMQ 是 Java 写的，Java 团队看源码毫无障碍。吞吐 10 万级别，不如 Kafka 极致，但业务消息要的可靠性在 RocketMQ 这里开箱即用。

🔹 RabbitMQ 是灵活路由，也是比较老的产品。路由规则最丰富，一条消息可以按规则同时投给多个队列，复杂分发逻辑一行配置，管理界面友好，入门简单，中小系统常选它。吞吐上万级别，超大规模场景不适合。

11.5.2 Redis 队列的边界与判断线

🔹 Redis 队列的边界有三条：

  • 消息全在内存：堆积几百万条内存就紧张。专职消息队列像 Kafka 写硬盘，堆一年也不怕。
  • 持久化有秒级窗口：AOF 配 everysec，极端掉电丢最后一秒。可能造成资产损失级别的业务不能接受。
  • 高可用要自己搭：Redis 侧的哨兵能做故障转移，不用人工介入，但复制是异步的，主节点挂了仍可能丢掉已确认的写入。专职消息队列自带集群，切换和副本管理都在产品里。

🔹 什么时候 Redis 队列刚刚好？每天几万条到几十万条，公司本来也有 Redis，丢几条也能接受，比如中小系统的通知、积分、画像，省下一整套中间件的部署、监控和值班。判断线就一句话：消息丢了会赔钱、造成很大损失吗？会就用专职 MQ，不会 Redis 就够用。

🔹 最后画等号：今天学的三个角色、消费者组、位点、划账、幂等、死信，到 Kafka 或 RocketMQ 里一个词都不用换。Redis 的 XADD 在 Kafka 里换成 send，XACK 换成 offset commit。概念是通用的，产品只是实现。先学原理再学产品。

11.6 常见错误清单

⚠️ 把用户当下不需要的结果留在主链路，接口被积分、画像拖成 3.2 秒。
⚠️ 以为上了消息队列就自动可靠，不配生产者确认、持久化和手动划账。
⚠️ 消息体塞全量数据，越滚越大，把消息队列用成数据库。
⚠️ 消费者不做幂等，重试导致积分加两次、画像更新两遍。
⚠️ 重试无限进行，没有投递计数和死信兜底，坏件永远挡路。
⚠️ 消费者组多 worker 并行消费有前后依赖的消息，接单和结束乱序。
⚠️ 只看快慢上队列，不评估一致性窗口、积压告警和运维成本。
⚠️ 资产损失级别业务用 Redis 队列，everysec 极端掉电丢最后一秒。

11.7 小结

🔹 消息队列不解决并发，它把必须现在做完的事变成可以之后慢慢做的事。三宗罪（慢、脆、崩）的病根是排队结构本身，换结构才有异步、解耦、削峰。代价是及时一致性和简单性，换来主链路飞快、故障隔离、洪峰缓冲。

🔹 Redis Streams 四段代码把这套结构落到了地上：生产者 XADD 发事件、消费者组 XREADGROUP 读并 XACK 划账、setIfAbsent 幂等、定时任务把投递三次失败的消息投进死信流。三道防线保证不丢失，幂等三板斧保证不重复，单流天然有序。

🔹 选型就一条判断线：消息丢了会赔钱吗。会就换 Kafka、RocketMQ 这类专职队列，不会 Redis 就够用。概念是通用的，产品只是实现，先学原理再学产品。
