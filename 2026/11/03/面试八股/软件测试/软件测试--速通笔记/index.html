一、测试理论：用一条线讲完整个流程

1.1 测试是什么

软件测试是用受控的手段运行或评估软件，验证它是否满足需求、发现缺陷，并为发布决策提供质量信息。

三个关键词分别对应三个追问。发现缺陷是手段，评估质量是过程，支撑发布决策是目的。Dijkstra 那句话要记住：测试能证明缺陷存在，不能证明缺陷不存在。这句话能救你很多场”你能保证没有 bug 吗”。

1.2 生命周期与测试的位置

阶段 测试在做什么 产出
需求分析 参加需求评审，查可测性、歧义、验收标准是否可验证 需求问题清单、测试点
设计 评审接口契约、数据库设计、异常分支 接口测试点、可测性意见
编码 单元测试、代码评审 单测、缺陷
测试 集成、系统、回归、性能、安全 用例、缺陷单、测试报告
部署 冒烟、灰度验证、上线检查单 上线结论
维护 线上问题复现、热修回归 复盘、回归用例补充
退役 数据迁移校验、下线验证 迁移核对结果

这张表的价值在于：它把”测试只在最后阶段”这个错误印象掰正了。测试左移就是把活动往需求、设计阶段挪；测试右移是把质量保障延伸到上线后的监控、灰度、线上巡检。

1.3 四个模型，一句话一个

模型 核心特征 什么时候用
瀑布 阶段串行，文档驱动 需求稳定、合规要求强
V 模型 每个开发阶段对应一层测试：需求↔验收、概要设计↔系统、详细设计↔集成、编码↔单元 需要明确验证与确认对应关系
W 模型 双 V，开发与测试并行，测试从需求就开始 想强调早期介入
敏捷 短迭代、持续测试、自动化回归 需求变化快、要快速交付

被追问”V 和 W 的区别”，答：V 模型里测试仍然是开发完成之后的对应验证，W 模型把测试活动提前到需求与设计阶段同步进行，两个 V 并行。

1.4 测试分类（按四个维度切）

维度 分类
按阶段 单元、集成、系统、验收
按是否运行 静态（评审、代码扫描）、动态
按关注点 功能、性能、安全、兼容、易用、可靠性
按是否看内部实现 黑盒、白盒、灰盒

另外三个高频词必须能区分：冒烟测试验证主流程能不能跑通，决定这个版本值不值得测；回归测试验证改动没有破坏原有功能，范围由影响面决定；探索性测试不预设脚本，靠经验和风险点现场发散，用来补用例覆盖不到的地方。

1.5 测试计划六要素

目标与范围（含不测什么）、测试策略（方法、类型、环境、工具、数据）、资源与分工、进度与里程碑、风险与应对、准入准出与交付物。

范围里写清”不测范围”是加分项，说明你知道边界在哪里。风险那一栏要具体，比如”第三方模型接口不稳定，可能阻塞主流程验证”，配一条应对”预置假实现与降级开关”。

1.6 准入与准出

准入（提测标准）：需求与接口文档已更新、版本可部署、冒烟通过、测试环境与数据就绪。

准出（发布标准）：用例执行完成、P0/P1 缺陷关闭或已评估、回归通过、遗留缺陷有风险说明和责任人确认、测试报告输出。

各公司口径不同，答题时说”常见口径是……具体看团队规范”，比背死标准更稳。

1.7 缺陷管理

生命周期：新建 → 指派 → 确认（打开）→ 修复 → 待验证 → 关闭；旁支是拒绝（重复 / 非缺陷 / 无法复现）、延期、重开。

严重程度看影响，优先级看修复紧迫性，这两个不是一回事。分级参考：

级别 判定
S1 致命 崩溃、数据丢失、资金错误、安全漏洞、主流程完全阻断
S2 严重 主功能不可用且无绕行方案
S3 一般 功能异常但有绕行方案
S4 轻微 文案、样式、提示不准确

优先级 P0 立即修、P1 本版本修、P2 下版本、P3 有空再说。举一个能加分的例子：官网首页错别字是 S4，但对外可见，优先级给 P1；后台导出偶发失败是 S2，内部低频使用，优先级可以先 P3。

Bug 报告要素：标题写”条件 + 现象”、环境（版本、设备、账号、数据）、前置条件、复现步骤、预期结果与实际结果、证据（截图、日志、请求与响应）、影响面、复现率。

判断标准的落点只有一句：让开发不用自己复现就能定位。

偶现问题：记录发生时间与请求 id，把抓包和日志按时间对齐，统计复现率，给出可能的触发条件（并发、特定数据、缓存过期），必要时加日志或埋点再复现一轮。

1.8 四道刁钻题的答法

Q：时间不够，用例跑不完怎么办。
按三个轴排优先级：核心业务链路、本次改动的影响面、历史缺陷高发模块。先跑冒烟保证版本可测，再跑 P0 主流程，回归用”影响面抽样 + 接口自动化全集”兜底。把没跑的部分和风险写进报告，让决策人知道边界。

Q：开发说这不是 bug，是设计如此。
回到需求文档和验收标准，拿证据说话：需求原文、竞品行为、对用户的实际影响。拉产品一起确认，结论记录下来。对方坚持且产品认可，就在报告里标注为已知限制并保留意见。不吵，也不默默放过。

Q：你怎么保证覆盖率。
需求 → 测试点 → 用例三级映射，逐条对勾；用例评审补漏；风险高的模块补探索性测试。覆盖率说的是需求覆盖，不是用例条数。

Q：测到什么时候算结束。
看准出标准，加上缺陷收敛趋势：新增缺陷数在下降、P0/P1 清零、回归通过。最后由风险接受方签字。

1.9 自动化测试：先想清楚投在哪

分层是老生常谈，但答对不难、答细才加分：单元多、接口居中、UI 最少。理由是执行速度、稳定性与维护成本依次变差，越往上越容易因界面改动而红。

层 适合 不适合
单元 纯函数、边界与分支、核心算法 依赖大量外部状态
接口 鉴权、参数校验、业务链路、幂等 一次性验证、需求天天变
UI 主流程冒烟、跨系统端到端 频繁改版的页面、探索性测试

落地流程五步：选高频回归场景 → 分层设计 → 数据与断言分离 → 报告与失败归因 → 进 CI 形成门禁。维护阶段只看两个指标：通过率与失败归因分布，红了一片先分清是环境、数据还是真缺陷。

自动化解决的是重复回归，不替代人做判断。探索性测试、体验判断、新功能首轮验证，仍然靠人。

二、用例设计：给个功能就能拆

2.1 七种方法，一句话一种

方法 一句话 典型场景
等价类 把输入分成”处理逻辑相同”的类，每类取一个 输入框、参数校验
边界值 在等价类的边界上取 min-1、min、max、max+1 长度、金额、数量
判定表 条件组合与动作一一列全 多条件优惠、权限矩阵
因果图 从原因（输入）推结果（输出） 复杂组合逻辑
正交试验 多因素多水平时用少量组合覆盖 兼容性、配置组合
场景法 按用户操作路径串起来 下单、支付、注册登录
错误推测 凭经验猜哪里会错 异常、并发、重复提交

再加一个状态迁移法，适合订单状态、审批流这类有明确状态机的功能。

2.2 用例要素

编号、模块、标题、优先级、前置条件、测试数据、操作步骤、预期结果、实际结果、备注。

面试时被问”用例要素”，答完要素补一句：预期结果要可判定，写”提示密码错误”而不是”提示友好”。

2.3 万能四维拆解法

拿到任何功能，按这四层往下拆，基本不会漏：

  1. 功能正向：正常输入走通，结果正确。
  2. 数据边界：空、超长、特殊字符、类型不符、极值、重复。
  3. 异常与权限：未登录、越权、重复提交、超时、服务不可用、并发。
  4. 非功能：性能（时延上限）、安全（注入、敏感信息）、兼容（浏览器/设备）、弱网。

2.4 演练一：登录

维度 用例
正向 正确账号密码登录成功，跳转正确，token 有效
数据 空账号、空密码、超长输入、前后空格、大小写、手机号/邮箱格式、特殊字符、SQL 注入串、XSS 脚本
异常 密码错误提示不泄露账号是否存在、连续错误 5 次锁定、验证码过期/错误、重复点击登录、多端并发登录
权限与安全 明文传输检查（HTTPS）、暴力破解限流、会话固定、退出后 token 失效
非功能 登录响应时间、弱网表现、不同浏览器与分辨率

2.5 演练二：秒杀下单（对应你 Vapor 项目）

  • 库存：正常扣减、库存为 0、并发抢最后一件（超卖）、扣减后取消订单回补。
  • 幂等：同一用户重复提交、网络超时重试，只生成一单。
  • 时间边界：开始前一秒、开始瞬间、结束瞬间、活动已结束。
  • 优惠：优惠券叠加规则、过期券、超限使用、金额计算精度。
  • 一致性：缓存与数据库不一致、支付超时自动取消、消息补偿是否生效。
  • 非功能：限流、降级、热点 key、数据库连接池打满。

2.6 演练三：SSE 流式问答（对应你 VidDigest 项目）

  • 首帧时延、整段完成时延。
  • 分帧契约：event、data、结束标记是否按约定出现，字段能否逐字段断言。
  • 异常：模型超时、空返回、中途断开、客户端重连、并发会话互相污染。
  • 内容：长文本是否截断、特殊字符与换行是否破坏分帧、上下文记忆是否跨轮保留。

这三道演练覆盖了功能、业务链路、流式接口三类，面试现场给别的题，套四维往下拆即可。

2.7 一招吃遍天：三问、四维、五层

不管题目是登录、导出报表、优惠券、AI 摘要还是硬件配对，六十秒内能开口的模板只有这一套。

三问定位：输入从哪里来、状态存在哪里、失败长什么样。

四维展开：正向、数据、异常与权限、非功能。

五层断言：状态、结构、字段、副作用、性能。

套四个完全不同的功能，看同一套模板怎么变：

功能 输入 状态 失败长什么样 特有考点
登录 账号密码验证码 会话、错误计数 提示错误但不泄露账号是否存在 暴力破解限流、token 失效
文件上传 文件、类型、大小 存储、任务记录 超限、格式错、传输中断 断点续传、病毒扫描、并发同名
导出报表 筛选条件、时间范围 异步任务、文件生成 超时、空数据、超大导出 任务幂等、下载链接有效期
AI 摘要 视频链接或文本 解析任务、流式会话 解析失败、模型超时、空返回 分帧契约、降级、成本上限

同同一套模板也能回答”你会怎么测这个功能”之外的问题。面试官问”怎么保证质量”，你答四维覆盖加五层断言；问”用例怎么评审”，你答按这四维查漏；问”缺陷为什么漏了”，你答哪一维没覆盖。一个框架反复用，比背十道题更像有方法。

2.8 用例写作的两条硬要求

预期结果必须可判定：写”返回 401 且 body 中 code=1001”，不写”提示未授权”。

一条用例只验证一个判断点：把”登录成功且跳转正确且 token 有效”拆成三条，失败时才知道坏在哪。

三、接口测试：JD 的第二条，也是最容易拿分的一条

3.1 为什么先做接口

接口测试直接对数据交互做验证，能绕开界面，在 UI 还没做完时就开始；定位快，失败点明确；天然适合自动化，进 CI 后每次提交都能回归。

和 UI 测试的分工：接口测逻辑与契约，UI 测交互与呈现。缺陷里绝大多数逻辑问题在接口层就能抓到。

3.2 HTTP 报文

请求由三部分组成：请求行（方法、路径、协议版本）、请求头（Content-Type、Authorization、Cookie、自定义头）、请求体（JSON、表单、文件）。

响应由状态行、响应头、响应体组成。Content-Type: application/json; charset=utf-8 这类头信息，测试时要能看懂。

3.3 方法与语义

方法 语义 幂等 常见用途
GET 查询 是 列表、详情
POST 新建 / 提交 否 创建订单、登录
PUT 整体更新 是 覆盖式修改
PATCH 局部更新 通常不保证 改单个字段
DELETE 删除 是 删除资源

GET 与 POST 的区别从四个角度答：语义（查询 vs 提交）、参数位置（URL vs Body）、幂等与可缓存、长度与安全性（GET 参数会进日志和浏览器历史）。

3.4 状态码

码 含义 测试时关注
200 / 201 / 204 成功 / 已创建 / 无内容 201 是否带 Location，204 是否真无 body
301 / 302 / 307 / 308 永久 / 临时重定向 307/308 是否保留方法与 body
304 协商缓存命中 与 ETag、Last-Modified 配合
400 参数错误 错误信息是否具体、是否泄露内部细节
401 / 403 未认证 / 无权限 越权用例主要看这两个
404 / 405 不存在 / 方法不允许 路由与网关配置
409 冲突 重复创建、乐观锁版本冲突
415 / 422 媒体类型不支持 / 语义校验失败 校验层是否生效
429 限流 校验是否给出重试提示（规范不强制 Retry-After，但实现限流时通常会给）
500 / 502 / 503 / 504 服务端错误 / 网关错误 / 不可用 / 超时 先看日志再看网关

3.5 RESTful 与业务码

RESTful 的要点：URL 用名词表示资源（/orders/123）、用方法表达动作、用状态码表达结果、版本放路径（/v1）、分页用查询参数。

真实项目里常见”HTTP 200 + body 里的 code 表示业务错误”。测的时候两层都要断言：HTTP 状态码对，业务码和 message 也要对。

3.6 单接口用例的十个要素

  1. 功能是否正确返回。
  2. URL 与方法是否正确。
  3. 鉴权：无 token、过期 token、他人 token。
  4. 必填参数缺失。
  5. 参数类型错误。
  6. 边界值：长度、数值范围、分页上下限。
  7. 枚举与非法值。
  8. 异常路径：依赖服务不可用、超时、数据库异常。
  9. 幂等与重复提交。
  10. 敏感信息与越权：返回是否包含他人数据、错误信息是否泄露堆栈。

参数矩阵按”正常 / 缺省 / 为空 / 类型错 / 超长 / 特殊字符 / 越界 / 多余字段 / 重复提交 / 并发”十种造，能覆盖绝大多数接口。

3.7 断言分层

一层层往下断，越往下越能抓到真问题。

  1. HTTP 状态码。
  2. 响应结构（字段是否存在、类型是否对）。
  3. 关键业务字段的值（订单号、金额、状态）。
  4. 业务副作用（数据库是否有记录、消息是否投递、库存是否变化）。
  5. 性能约束（响应时间不超过阈值）。

只断状态码是最常见的空洞断言，面试时主动说”我会断到业务字段和数据库副作用”，直接区别于背题的人。

3.8 Postman 要点

  • 环境变量 {{baseUrl}}、{{token}}，切环境不改请求。
  • Tests 脚本断言：pm.response.to.have.status(200)、pm.expect(pm.response.json().data.id).to.be.a('number')。
  • Pre-request 脚本登录拿 token 并 pm.environment.set，后续请求自动带上，这就是接口关联。
  • Collection Runner 配 CSV / JSON 做数据驱动。
  • newman run collection.json -e env.json -r html 生成报告，能进 CI。

3.9 JMeter 与性能口径

  • 线程数是虚拟用户数，不等于同一时刻的真实并发；有思考时间、Ramp-up、连接复用时差别更大。
  • Throughput（常当 TPS 用）= 单位时间内完成的样本数，样本是请求还是事务，取决于采样器与事务控制器。
  • 响应时间看平均、90%、99% 分位，另看错误率。
  • 并发上升时响应时间先涨，TPS 到瓶颈后会掉，这个拐点就是容量上限。
  • 压不上去时按顺序排查：压力是否够（线程数、客户端网络）→ 应用（线程池、锁、慢 SQL）→ 中间件 → 数据库 → 机器资源。

校招层面知道这套口径就够，不必声称做过完整压测。

3.10 接口常见缺陷

参数校验缺失（负数金额、超大数量）、越权（水平越权看他人订单、垂直越权调管理接口）、返回码与业务码不一致、分页边界（page=0、size 超大）、时间与时区、字符集乱码、重复提交产生脏数据、限流缺失、错误响应里带堆栈。

限流这块可以结合你项目里的做法讲：并发打公开接口，断言返回 429 且带 Retry-After，窗口结束后请求恢复。

5.3 踏浪 AI 中心（占追问的三成）

追问一：你说 AI 生成的单测”测试通过但改坏实现也不报错”，怎么发现的。
我把生成的用例逐条读，判断每条断言能不能抓住一次真实改动。抓不住的典型是只断 is not None、只断状态码、只断长度。这类用例在实现被改坏时仍然是绿的，等于没测。发现后我退回重写，并把判断标准固化成提示词模板，让生成侧先按标准自查。

追问二：那你怎么验证重写后的用例真的有效。
用变异的方式反证：故意改坏实现里的一条不变量，比如把边界判断的 > 改成 >=，把空值分支删掉，然后跑用例，看对应用例是否转红。只有”只破坏一条不变量”的变异才算有效实验，一次改多处，红了也说明不了是哪条断言抓到的。

追问三：代码评审清单里的四条是怎么定的。
从误报里反推。评审意见笼统，开发不知道改哪，我就把项目里真实出现过的问题归类：空值、边界、错误被吞掉、共享状态的数据竞争。每条写成可判定的问句，比如”这个变量在并发下会被几个请求同时写”。跑一轮之后按误报反向收窄，删掉那些看起来像问题但不影响行为的条目，清单从宽变准。

追问四：多轮对话记忆怎么测。

5.4 VidDigest（占三成）

第一轮：你在这个项目里怎么测的。
三层。数据层用 pytest 分库建用例，每个用例一个独立临时库，跑完销毁，避免互相污染；升级路径单独一条用例，模拟老库缺列的情况验证迁移脚本；接口层对 SSE 帧按契约逐字段断言，不只看有没有返回。

第二轮：SSE 这种流式接口怎么断。
先断响应头 text/event-stream，再把流按空行切成帧，逐帧解析 event 与 data 字段，断言首帧内容、中间帧顺序、结束标记。异常路径单独造：模型超时、空返回、连接中断，验证前端或调用方拿到的是约定的错误帧而不是挂住。

第三轮：外部模型不稳定，测试怎么稳定。
把模型调用抽成可替换接缝，测试注入假实现，固定输出。这样用例只验证我方解析、降级与错误处理，不受模型随机性影响。降级路径逐个覆盖：哨兵切分、超时、空返回。

**被追问”假实现会不会掩盖问题”**：会，所以假实现只用在契约层，另外保留一组真实调用的小样本冒烟，两者分开跑。

安全那块：敏感内容扫描覆盖全部提交历史，不只当前工作区；管理员权限改成每次请求回查，避免会话里缓存旧权限；公开接口的并发上限用 429 与 Retry-After 断言。

5.5 Vapor 优选（占两成，压成一页）

秒杀不超卖怎么测。 并发打同一商品，线程数大于库存数，最后断言：成功订单数等于库存、数据库库存不为负、Redis 与数据库最终一致。

重复下单怎么测。 同一用户并发提交同一请求，加超时重试场景，断言只生成一单。实现是 Redis 加 Lua 把资格校验和库存扣减压成一次原子执行，测试就围绕这个不变量设计。

缓存不一致怎么测。 把复现路径固定成”写库成功、删缓存失败”，用消息队列补偿加 TTL 兜底，断言在补偿生效后读到的数据与库一致。

**如果问”你测出过什么 bug”**：讲自己造出来的那条路径比编一个故事可信，说”我把删缓存那一步打断，验证补偿是否生效”，然后说结论。

6.3 单测生成：怎么证明一条用例真有用（踏浪）

项目里的问题原话是”测试通过、但改坏实现也不报错”。落到具体，空洞断言有五种长相：

空洞长相 例子
只断非空 assert result is not None
只断状态码 assert resp.status_code == 200
断实现细节 assert mock.call_count == 2
依赖执行顺序 用例 B 依赖用例 A 造的数据
数据不隔离 共用一个库，跑第二遍就红

判断一条用例有没有效，看四条：断言绑定可观察行为（返回值或副作用）、至少有一条边界和一条异常、不依赖内部实现、能独立重复跑。

变异验证是把它变成可证明的动作：

三种变异，三种结论。

变异 用例反应 结论
>= 改成 > 100 转红 有效变异，用例抓住了边界
- 10 改成 - 9 100、101 转红，99 仍绿 有效，说明覆盖不齐
return total 改成 return total + 0 全绿 等价变异，不算失败

有效变异要让至少一条用例转红，等价变异应保持绿，一次只改一条不变量。 这三句话能直接回答”你怎么保证测试有效”。

提示词模板写成五段，产出才可检查：角色与目标、输入（代码 + 现有用例）、约束（必须覆盖边界与异常、不许只断 mock 调用）、自检清单（逐条回答断言能否抓住一次改动）、输出格式（文件 + 说明）。

6.4 代码评审清单：把”意见笼统”变成”可判定”（踏浪）

四条规则，每条都要能答是或否：

条目 判据 常见误报 收窄办法
空值 入参、返回值、数据库读回是否可能为 None，为 None 时行为是什么 框架已保证非空 加前置条件”仅业务层”
边界 > 与 >=、空集合、单元素、超长输入 常量枚举不可能越界 只对用户输入路径报
错误吞没 except 里是否只打日志、是否返回默认值掩盖失败 故意降级的兜底 要求标注降级理由
共享状态 类属性、全局缓存、单例是否被并发写 只读配置 排除不可变对象

误报处理是这套方法的核心动作。跑 20 条真实 diff，统计每条规则的命中里有多少是真问题，把误报归类（测试代码、生成代码、框架约定），删规则或加前置条件。清单从宽变准，比从准变宽难得多，所以先严后放。

拼装 超长被截断，关键段丢了 塞长文档 + 关键段放末尾 关键段是否仍在上下文里
生成 材料里没有也照答 问知识库没有的问题 是否拒答或标注不确定
引用 引用段落与结论不符 抽查引用定位 引用原文能否支持结论

指标口径要说清分母，这里最容易混：

指标 定义 回答的问题
Hit@k（常被误叫 Recall@k） top-k 里至少命中一篇期望文档的问题数 / 问题总数 有多少问题至少找到一篇对的
Recall@k（标准 IR） 前 k 个结果命中的相关文档数 / 该问题的相关文档总数，再对问题取平均 相关文档找全了多少
MRR 每个问题首个相关结果排名倒数的平均，没命中记 0 平均翻到第几名才首次命中
拒答准确率 正确拒答数 / 应拒答数 不知道时会不会硬答

多数 RAG 场景实际用的是 Hit@k，面试时把名字说对，比多背三个公式更能证明你读过原文。还要说明：期望文档不唯一时用 Recall@k，只有一个标准答案时用 MRR。

6.6 多轮记忆的测试（踏浪）

实现是短期摘要加长期事实两层，测四类场景：

场景 造法 断言
隔轮再问 问 A，插两轮别的，再问 A 回答与首轮一致，且引用到之前信息
指代消解 上一轮说”这个视频”，下一轮问”它多长” 指代对象正确
更正覆盖 用户说”不是 A，是 B” 后续回答只出现 B
跨会话隔离 换一个会话问同样问题 不携带上一个会话的事实

第一条就是简历里写的”同一问题隔轮再问”，把它讲成回归场景而不是功能演示，层次立刻不一样。

6.7 Agent 工具调用的测试（JD 原话）

链条是：识别意图 → 选工具 → 填参数 → 执行 → 观察结果 → 再决策。测点按链条排：

测点 断言
工具选择 该调检索调了检索，不该调的不调
参数 必填齐全、类型正确、越界被拒
失败处理 超时/5xx/429 时重试且幂等，不重复下单
权限 越权工具调用被拒，且留审计记录
终止条件 有最大轮次，不会无限循环
可观测 轨迹日志能回放每一步输入输出

做法是假工具记录调用序列，断言序列与参数；真实链路再录一份响应做回放。Agent 的问题多数出在编排，不在模型，所以断言要落在调用链上。

6.8 稳定性、时延、成本

  • 同一问题跑 5 次，看回答一致性；温度调高会放大差异，评测要在固定参数下做。
  • 时延分首帧与整段，报 P95 不报平均。
  • 超时要有人为阈值和降级路径，不能挂住连接。
  • 并发下看排队与限流，429 之后的重试要有退避，否则重试风暴比原故障更糟。
  • 每次请求的 token 上限要有约束，长上下文功能最容易在这里失控。

6.10 术语速查（进门前扫一遍）

术语 一句话 常见追问
token 模型处理的最小单位，约等于字或词片段 中文一个 token 大概几个字（不固定，别报死数）
embedding 把文本映射成向量，语义近的向量距离近 怎么算相似度（余弦）
向量检索 用向量近邻找相关文档 和关键字检索怎么配合（混合召回）
rerank 召回后用小模型重排，提升前几名质量 为什么两段式（召回要快，排序要准）
上下文窗口 单次请求能容纳的 token 总量，输入、历史、输出共享 超了怎么办（截断、摘要、分段）
temperature 采样随机性，越低越接近贪心 0 是不是完全确定（不是）
top_p 核采样阈值，从累积概率前 p 的候选里采 和 temperature 怎么配（一般只调一个）
few-shot 在提示里给几个示例 和微调区别（不改权重）
CoT 让模型先写推理步骤再给结论 什么时候没用（简单任务反而变慢）
function calling 模型按 schema 输出工具调用 参数错了怎么发现（schema 校验 + 断言）
MCP 模型与外部工具/数据源的标准化协议 和普通 API 区别（统一描述与调用方式）
RAG 先检索再生成，把材料塞进上下文 和微调怎么选（知识常变选 RAG）
越狱 绕过安全策略的提示技巧 和提示注入区别（目标不同：一个破限制，一个改指令）
幻觉 生成看似合理但不真实或没依据的内容 怎么量化（抽样分档，不追求单一数字）

6.11 评测方法：三层，各有各的偏差

层 做法 优点 局限
规则断言 契约、字段、状态码、耗时、拒答 确定、可进 CI 只能测形式
人工 rubric 固定评分表，双人标注 能判事实与逻辑 贵、慢、有主观性
模型裁判（LLM-as-judge） 让强模型按 rubric 打分或成对比较 便宜、可规模化 有已知偏差

模型裁判的三类偏差要能报出来：位置偏差（偏好第一个）、冗长偏差（偏好长答案）、自我偏好（偏好同族模型输出）。缓解办法：成对比较时随机交换顺序并看一致性、控制长度、用多个不同家族的评委、在目标领域用小规模人工标注校准。

模型裁判适合排序，不适合给绝对分。评估报告里把规则断言、人工分、模型分分三列写，比合成一个总分可信。

6.12 幻觉分类与 RAGAS 四指标

幻觉按与源材料的关系分两类：内在幻觉指回答与给定材料直接矛盾；外在幻觉指材料里推不出、属于额外新增的信息。工程上常按事实性（与世界事实不符）、忠实性（与材料不符）、逻辑性（自相矛盾）来分档，这三类是便于落地的划分，答的时候说清”我按这三档标注”，比说”学术上分三类”稳。

RAG 评测常用 RAGAS 的四个指标，前两个评生成，后两个评检索：

指标 口径 注意
faithfulness 回答拆成若干陈述，能被检索上下文支持的比例 衡量对上下文的事实一致性
answer relevancy 由回答反生成问题，与原问题的相似度 只看相关性，不判事实对错
context precision 相关块是否排在无关块之前 是排序质量，不是数量
context recall 参考要点被检索上下文覆盖的比例 依赖参考答案或参考上下文

6.13 采样参数与上下文窗口

  • temperature 越低越接近贪心解码，但 0 不保证逐字一致（并行、硬件、服务端实现都会带来差异），所以回归用例不能断言模型原文。
  • top_p 是核采样阈值，和 temperature 叠加影响分布，实践中一般只调一个。
  • 上下文窗口是输入、历史、输出共享的 token 池，超限会截断或直接报错，长文档功能必须专门测截断点。
  • 评测要固定参数并记录模型版本，否则两次结果不可比。

6.14 九十秒讲法

我负责的是 AI 研发效能和知识库问答。测试上我分三层。第一层是契约层，接口、SSE 分帧、字段、降级都是确定性断言，用 pytest 跑。第二层是检索层，我用一套固定问题集，每个问题三种问法，看命中率和前三条命中，切块和混合召回都是拿这套集子对比出来的。第三层是生成层，忠实性和事实性没法自动判，只能定 rubric 抽样人工评，所以报告里我把自动指标和人工评分分开写。另外我做过变异验证，把实现改坏一条不变量，确认对应用例真的会转红，避免用例绿着但抓不到问题。

7.7 Selenium（了解一下，能说清就算过）

八种定位，按稳定性排序用：

定位 写法 什么时候用
id By.ID 唯一且稳定，首选
name By.NAME 表单元素
class name By.CLASS_NAME 只能单个类名，不能复合，容易变
tag name By.TAG_NAME 批量取元素
link text By.LINK_TEXT 完整链接文案
partial link text By.PARTIAL_LINK_TEXT 文案长且会变
CSS selector By.CSS_SELECTOR 层级稳定、速度好
XPath By.XPATH 需要按文本或父子关系定位

CSS 与 XPath 的分工：CSS 简短、快，按属性与层级；XPath 能按文本、能向上找祖先，适合文案定位。动态 id 用相对 XPath（//button[contains(@class,'submit')]），别用绝对路径。

三类等待：

类型 作用范围 说明
强制等待 当前行 sleep，只在调试用
隐式等待 全局查找元素 找不到时轮询，一次设置长期有效
显式等待 指定条件 WebDriverWait 等可见、可点击、元素存在

动态页面一律用显式等待，等条件而不是等时间。PO 模式把元素定位与操作封在页面类里，用例只写业务动作，页面改版时只改一处。

Flaky 四处查：等待策略、定位是否依赖随机 id、用例数据是否互相污染、并发执行是否抢同一账号。

教程：Selenium 官方 Documentation。

主题 必答点
HTTP 版本 1.1 长连接与管道化；2.0 多路复用、头部压缩、二进制分帧；3.0 换 QUIC 走 UDP，解决 TCP 层队头阻塞
HTTPS TLS 握手协商密钥，证书链校验身份，解决窃听、篡改、冒充

Redis 快 纯内存、单线程处理命令避免锁竞争、IO 多路复用、数据结构针对场景优化

8.4 网络分层与 TCP/UDP

层次 OSI 七层 TCP/IP 四层 这一层有什么
应用 应用、表示、会话 应用层 HTTP、DNS、SSH、WebSocket
传输 传输 传输层 TCP、UDP
网络 网络 网络层 IP、ICMP、路由
链路 数据链路、物理 网络接口层 以太网、Wi-Fi、ARP

面试常问”输入 URL 之后发生了什么”，按这条链路说：DNS 解析 → TCP 握手 → TLS 握手（HTTPS）→ 发请求 → 网关转发 → 应用处理 → 响应 → 渲染 → 加载子资源。

TCP 与 UDP 的差别，落到使用场景：

TCP UDP
连接 面向连接 无连接
可靠性 确认、重传、排序 不保证送达与顺序
开销 握手、拥塞控制 头部小、时延低
场景 HTTP/1.1、HTTP/2、数据库连接 DNS 查询、音视频、游戏、HTTP/3（QUIC），前提是能容忍丢包或自行补可靠性

DNS 默认走 UDP 53，响应过大改用 TCP；HTTP/3 把可靠性做进 QUIC，不再依赖 TCP。

8.5 内存管理与文件系统

问题 一句话
虚拟内存 每个进程看到独立地址空间，靠页表映射到物理内存
缺页中断 访问的页不在内存，触发换入
页面置换 内存满时选一页换出，LRU 是常问的一种
栈与堆 栈放调用与局部变量，堆放动态分配，栈溢出与内存泄漏是两类问题
文件系统 inode 记录除文件名外的元数据，目录项负责名字到 inode 的映射
软链与硬链 软链是独立文件，内容为目标路径，源删了断链；硬链是同一 inode 的多个目录项，删一个名字只减计数
权限 rwx 分属主、组、其他，755 与 644 是最常见的两档

排查内存问题用 free -h 看整体、top 看进程、ps 看 RSS；OOM 先确认是泄漏还是流量涨。

8.6 MySQL 三范式与优化

范式 要求 违反的样子
1NF 每个字段都是原子值，且不允许重复组 一个字段存逗号分隔的多个值
2NF 在 1NF 上，非主属性完全依赖每个候选键，不能只依赖联合键的一部分 联合键里，某字段只由其中一个键决定
3NF 在 2NF 上，不存在非主属性对候选键的传递依赖 订单表里存了用户手机号，而手机号由用户 id 决定

严格表述里用的是候选键而不是主键：主键只是选定的一个候选键，约束作用于全部候选键。

实际项目会故意反范式：冗余字段换查询性能，代价是写入时同步。答这个题的正确姿势是先说范式，再说”什么时候故意不遵守”。

优化顺序：先看执行计划 EXPLAIN，再查索引是否命中，最后才考虑改 SQL 或加缓存。索引失效的常见原因在 8.1 那张表里。

8.7 Web 安全：四个老面孔

漏洞 原理 测法 防御
SQL 注入 参数被拼进 SQL，改变了语义 输入 ' or '1'='1、1' --、时间盲注 参数化查询、最小权限
XSS 注入的脚本在别人浏览器执行 评论/昵称里写 <script>、<img onerror> 按上下文输出编码、安全 API、富文本白名单，CSP 作纵深
CSRF 借用户已登录的 Cookie 发请求 构造第三方页面自动提交表单 同步令牌或双提交 Cookie、Fetch Metadata，SameSite 辅助
越权 改 id 访问别人的数据 换 id、换角色调接口 每次请求校验归属与角色

XSS 按老分类分三种：存储型（存进数据库，所有访问者中招）、反射型（藏在链接参数里）、DOM 型（前端脚本把不可信输入写进页面）。OWASP 现在更倾向按 Server XSS 与 Client XSS 归并，DOM 型属于 Client 侧。测法不同，防御核心是上下文输出编码与安全 API，CSP 属于纵深防御，不是主力。CSRF 里 Referer 校验容易被剥离，只能当补充。

安全测试的答题结构：先列风险面（输入、鉴权、文件、日志），再给一条具体验证手法，最后说清期望行为。别只报漏洞名。
