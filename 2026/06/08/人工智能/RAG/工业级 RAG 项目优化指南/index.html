工业级 RAG 项目优化指南

核心观点：简历中 RAG 项目应有的闭环

一个能打动面试官的 RAG 项目简历应当包含：

  1. 问题描述：在 RAG 过程中遇到了什么场景问题
  2. 解决方案：采用了什么优化策略
  3. 具体技术细节：实现了什么、达到了什么指标

反例：只写”用 RAG 技术，基于 LangChain 或 LangChain 实现一个什么智能体”

正例：发现切块时会导致上下文不连贯，步骤 A 和 B 经常被拆分分别召回，采用父子索引的优化策略——子块只作为检索索引，父块作为真实召回的文本，最终使召回率提升了多少。

RAG 系统的四大核心模块

工业级 RAG 可分为四个主要部分：

模块 主要优化方向
入库阶段 知识工程优化、语义切分、Tag 打标、冲突治理
Query 改写 主体改写、子查询拆分、同义改写、模型微调
检索层面 多路召回（向量+BM25+GraphRAG+标签检索）
排序层面 Cross Encoder 重排序、业务标签加权

一、入库阶段优化（知识工程）

1.1 知识的来源与入库流程

关键点：并不是所有问题都会被 RAG 检索入库，而是会做二次校验，保证知识飞轮的基础质量。

1.2 切块（Chunking）优化

传统做法：通过标题拆分 + 递归切分，暴力忽略语义

升级策略：

  • 通过 LLM 进行语义切分
  • 过长片段 → 拆分
  • 过短片段 → 合并
  • 保证文档结构完整，避免碎片化或冗长

最佳实践：保证每个 Chunk 是一个独立的语义单元

1.3 Tag 标签打标

Tag 打标是很多 RAG 系统忽略但很重要的环节。Tag 有三个作用：

  1. 识别枪口：标记需要审核的内容
  2. 定向召回：基于用户画像/业务类型，从对应枪口召回知识
  3. 重排序加权：在 Rank 阶段根据标签做加权计算

示例：用户问业务相关问题 → 专门从业务枪口中做召回 → 极大优化准确率

1.4 冲突治理

冲突治理是知识问答错误的重要来源。常见问题：

  • 知识时效性：政策变更、活动规则变化导致 RAG 失效
  • 旧文档冲突：过期文档仍在被召回
  • 粗置停用：错误文档仍在使用

企业落地做法：

  • 在向量知识处理后做二次检查
  • 定期（如每天一次）清理过期知识和冲突知识
  • 更新错误文档

准确率的影响因素：

  • 幻觉
  • 粗置停用
  • 冲突支持
  • 过期支持
  • 无效 URL

二、Query 改写优化

2.1 为什么需要 Query 改写

用户提问 vs 知识库标题的差异：

  • 用户问题更抽象、口语化
  • 多意图、带上下文
  • 可能使用代词（”它”指代上文某个实体）

直接用原文检索会导致检索失败。

2.2 三种改写策略

策略 作用 示例
主体改写 规范表达、补全语义 “它的含义是什么” → 补全为 “RAG 的含义是什么”
子查询拆分 一个问题拆成多个子问题 “空号和卡顿有关系吗” → 拆分为 “什么是空号”、”卡顿的原因有哪些”
同义改写 扩展召回范围 “怎么” → “如何”、”怎样”、”做法是”

2.3 Agentic RAG 中的应用

在 Agentic RAG 系统中，这三种策略是可选的，把选择能力交给模型：

  • 模型自主判断是否需要主改写
  • 是否需要子查询拆分
  • 是否需要同义改写
  • 如果召回的 Chunk 回答不全面，会做多次检索

代价：牺牲一些实时性，但能极大保证正确知识的命中率。

2.4 模型微调

Query 改写模块通常用小模型执行：

  • 训练数据固定：明确的 query → 对应的 chunk / 子问题
  • 可采用弱化微调（成本低）
  • 或 RLHF（强化学习训练）
  • 可极大提高小模型的改写率

关于模型微调的具体方法，UP 主表示会出单独视频讲解。

三、检索层面优化（多路召回）

3.1 多路召回架构

3.2 四种检索方式对比

检索方式 解决的问题 适用场景
向量检索 语义相似性 大部分通用场景
BM25 专有名词、关键词精确匹配 术语密集型问答
GraphRAG 多跳关系、实体关联 需要关系推理的场景
标签检索 业务字段过滤 有明确用户画像/业务分类的场景

3.3 GraphRAG 补充说明

GraphRAG 通过图结构捕获实体之间的关系：

  • 召回 A，但答案与连接 A 的 B 相关
  • 通过图的关联关系把 B 也召回

GraphRAG 原理和社区发现的具体做法，UP 主表示会出单独视频讲解。

3.4 多路融合与截断

  • 从四路得到 Chunk 后去重合并
  • 根据各路对应分数做加权融合
  • 截断：保证上下文窗口不爆炸，取前面 N 个 Chunk

四、排序层面优化（Rank）

4.1 Cross Encoder 原理

  • 把 Q 和候选 Chunk 拼接
  • 通过自注意力计算（dedup / encoder 部分）
  • 输出多维向量，映射到 0~1 分数
  • 分数表示 Query 和 Chunk 的语义相关程度

4.2 业务标签加权

真实业务仅靠语义分数是不够的，还需要手动控制分数：

  • 医疗问答场景：特定 tag 的分数更高
  • 不想频繁召回的内容：降低其分数
  • 类似推荐系统的手动调权

融合方式：将业务标签加权融合到最终的 Rank 计算中。

五、可信生成与评测

5.1 为什么需要可信验证

如果不做验证，可能出现：

  • 错误答案
  • 知识冲突
  • 过期信息

5.2 知识飞轮闭环

可信验证的作用：

  • 知识生产后的质量检查
  • 语义切分保证数据处理质量
  • 原数据增强提升召回准确度
  • 冲突治理保证知识时效性

六、过程评测

6.1 分阶段评测（不是只看最终结果）

RAG 拆解为 10 个阶段，每个阶段单独评测：

阶段 评测指标
Query 改写 改写准确度
混合检索 召回率
可信验证 能否识别错误/冲突
全流程 端到端效果

6.2 反馈回流机制

  • 召回率过低 → 调整各路检索参数或标签权重
  • 持续迭代优化

七、线上反馈与 Agentic RAG

7.1 线上反馈渠道

反馈类型 说明
用户反馈 点赞/踩、评分
后台监控 捕捉 Bad Case
内部反馈 用户直接反馈
AI 巡检 自动检测知识冲突

7.2 分诊 Agent

RAG 系统中引入分诊 Agent，负责对反馈做分流分类：

  • 知识缺失：该知识不在库中
  • 回答错误：知识存在但回答错误
  • 数据错误：底层数据有问题

分类后交给运营检测是否真实存在问题，作为下次回归测试的 Bad Case 评测集。

7.3 Agentic RAG 的优势

  • 基于更智能的 Agent 做 RAG
  • 更可控，可做强化学习训练约束生成
  • 越用越好的系统

总结：工业级 RAG 项目优化方法论

核心闭环

简历中应展示的内容

  1. 入库阶段：知识来源、语义切分策略、Tag 打标、冲突治理
  2. Query 改写：三种改写策略、模型微调
  3. 多路召回：向量 + BM25 + GraphRAG + 标签检索
  4. 重排序：Cross Encoder + 业务标签加权
  5. 评测闭环：分阶段评测 + 线上反馈回流

最低要求

一个真实的 RAG 项目应至少包含评测的闭环，而不是：

  • 只在项目中写”基于 RAG 实现什么知识库”
  • 用了一个 RAG 就声称”会做 RAG”

面试官判断你是否真实落地，靠的就是这个闭环：你最后达到了什么效果、为什么用这个技术、解决了什么问题。
