零、为什么用消息队列？（和 Redis Pub/Sub 对比）🎯

MQ（Message Queue，消息队列） 是分布式系统的”快递柜”，生产者（Producer）投递消息，消费者（Consumer）按需取件，双方无需直接认识。

0.1 MQ 三大核心价值

价值 一句话解释 生活类比 Redis 类比
解耦 系统间不直接依赖，通过 MQ 间接通信 快递柜：卖家只管放，买家只管取 远超 Redis Pub/Sub（后者没持久化）
异步 主流程快速返回，非核心逻辑后台慢慢跑 饭馆点完菜就能刷手机，菜好了叫号 Redis List 做异步队列太简陋
削峰 突发流量进 MQ 排队，后端按能力消费 水库蓄洪，天晴放水 Redis Streams 简单实现，远不如 MQ 专业

重点：你用过 Redis，那 Redis 也能做消息队列？能，但很弱。下面我们用一整节专门对比 RabbitMQ 和 Redis Pub/Sub。

0.2 Redis Pub/Sub vs RabbitMQ（⭐ 重点）

这是写给有 Redis 基础但没用过 MQ 的同学最重要的一节。

维度 Redis Pub/Sub RabbitMQ 谁赢
消息持久化 ❌ 不持久化，订阅者离线就丢消息 ✅ 队列持久化，消费者掉线消息还在 RabbitMQ
消息堆积能力 ❌ 发布者发得太快，订阅者跟不上 = 丢 ✅ 队列堆积百万级不影响 RabbitMQ

延迟消息 ❌ 原生不支持 ✅ TTL + 死信队列天然支持 RabbitMQ

消息顺序 ❌ 不保证 ✅ 单队列内 FIFO RabbitMQ
集群模式 ✅ Redis Cluster ✅ 普通集群 / 镜像集群 / Quorum 平手

一、RabbitMQ 是什么？🏢

RabbitMQ = 开源的 消息代理（Message Broker），实现了 AMQP（高级消息队列协议） 标准，用 Erlang 语言编写。

简单说：它就是消息的”中转站”，负责把消息从生产者可靠地送到消费者手里。

1.1 诞生背景

维度 说明
作者 英国 LShift 公司 + CohesiveFT，2007 年发布
创始人 Alexis Richardson、Matthias Radestock
语言 Erlang（爱立信为电信交换机开发的语言，天生支持高并发、分布式、容错）
协议 实现 AMQP 0-9-1 标准（Advanced Message Queuing Protocol）
开源协议 双协议：核心用 GPLv2，客户端库用 Apache 2.0
公司归属 2010 年被 VMware 收购 → 2013 年并入 Pivotal → 2019 年被 Broadcom 收购
社区 RabbitMQ 团队加入 VMware Tanzu，后被 Broadcom 收购后继续维护

重点：Erlang 是一门为电信级可靠性而生的语言，9 个 9 的可用性（一年只允许 31 毫秒故障），天生适合做消息中间件。

1.2 一句话总结 RabbitMQ 是什么

RabbitMQ = 用 Erlang 写的、实现了 AMQP 协议的、可靠的消息代理软件。

对比一下你熟悉的 Redis：

  • Redis = 用 C 写的、实现了 RESP 协议的、内存数据结构服务器
  • RabbitMQ = 用 Erlang 写的、实现了 AMQP 协议的、消息代理服务器

四、AMQP 协议详解 📜

AMQP（Advanced Message Queuing Protocol，高级消息队列协议） 是一个应用层的开放标准消息中间件协议，2006 年由 John O’Hara 在摩根大通提出。

4.1 AMQP 是什么？

维度 说明
全称 Advanced Message Queuing Protocol（高级消息队列协议）
目标 让不同语言、不同平台的消息中间件能互联互通
地位 消息中间件界的 HTTP（类比理解）
当前版本 AMQP 0-9-1（RabbitMQ 实现的主流版本） + AMQP 1.0（协议不同，不兼容）
标准化 OASIS 标准、ISO 标准

4.2 为什么 AMQP 重要？

类比 HTTP：HTTP 协议让所有浏览器和服务器互联，AMQP 协议让所有消息队列互联。

4.3 AMQP 0-9-1 协议分层

4.4 AMQP vs 其他消息协议

协议 全称 定位 代表实现 特点
AMQP Advanced Message Queuing Protocol 企业级消息中间件标准 RabbitMQ、ActiveMQ Artemis 功能最丰富、协议最重
MQTT Message Queuing Telemetry Transport 物联网（IoT）协议 Mosquitto、EMQX 极轻量、跑在嵌入式、低带宽
STOMP Simple/Streaming Text Oriented Messaging Protocol 简单文本协议 ActiveMQ 像 HTTP，简单但功能弱
JMS Java Message Service Java EE 标准 API ActiveMQ、JBossMQ 不是协议，是 Java API 规范

重点区别：

  • AMQP 是协议（跨语言、跨平台）✅
  • JMS 是 Java API（只面向 Java）❌
  • MQTT 适合 IoT（带宽极低）
  • STOMP 适合简单场景

4.5 AMQP 0-9-1 vs AMQP 1.0

维度 AMQP 0-9-1 AMQP 1.0
RabbitMQ 支持 ✅ 完整支持 ⚠️ 通过插件支持（不完整）
互操作性 仅 RabbitMQ 完整实现 跨中间件兼容（如 ActiveMQ Artemis）
复杂度 复杂 简洁
现状 事实标准 未来方向

面试回答：AMQP 0-9-1 是 RabbitMQ 实现的事实标准，AMQP 1.0 是个新规范，RabbitMQ 仍以 0-9-1 为主。

5.3 关键概念详解

① Broker

  • 定义：RabbitMQ 服务器节点，负责接收、存储、转发消息

② Connection & Channel（⭐ 重要）

这是面试常考点：为什么用 Channel 而不是直接用 Connection？

维度 Connection Channel
本质 TCP 连接 TCP 连接上的逻辑通道

③ VHost（Virtual Host）

维度 说明

④ Exchange、Queue、Binding（⭐⭐⭐ 最核心）

面试必考：完整描述一条消息的生命周期。

三者的关系：

对象 作用 由谁声明 是否可重复
Exchange 接收消息并路由 Producer 或 Consumer 任意一方 同名同类型会报错
Queue 存储消息 Producer 或 Consumer 任意一方 同名同名参数必须一致，否则报错
Binding Exchange → Queue 的路由规则 通常 Consumer 声明 可重复

最佳实践：消息的声明方（Publisher）负责声明 Exchange 和 Queue 及 Binding，避免消费者先启动时报”队列不存在”。

6.2 模式一：Hello World 🌍

入门第一课：生产者发一条，消费者收一条。

默认交换机（""）自动绑定到所有队列，routing-key 就是队列名。

6.3 模式二：Work Queues（工作队列）👷

多个消费者竞争消费同一个队列中的消息，一条消息只会被一个消费者处理。

关键概念 说明
轮询分发（默认） RabbitMQ 不管消费者处理快慢，平均分消息
公平分发 设置 prefetchCount=1，能者多劳，慢的少分
消息 ACK 处理完才能删，否则重投

6.4 模式三：Pub/Sub（发布订阅）📢

消息被广播给所有绑定到该交换机的队列。

关键点：fanout 类型的 Exchange 忽略 routing-key，所有绑定的队列都会收到一份。

6.5 模式四：Routing（路由）🛣️

精确匹配 routing-key，符合的队列才收到消息。

绑定示例：

Queue Binding Key 收到 routing-key
Q1（错误日志） error error ✅
Q2（所有日志） info、error、warning info、error、warning ✅

一个队列可以绑定多个 routing-key，一个 Exchange 可以绑定多个队列。

模式匹配 routing-key，比 Direct 更灵活。

* 匹配一个单词 user.* 匹配 user.login，不匹配 user.login.success
# 匹配零个或多个单词 user.# 匹配 user.login、user.login.success

6.7 模式六：RPC（远程过程调用）🔁

二十、Top 20 面试题详解 🎤

面试突击必看！每题答案控制在 3-5 行，可背诵。

送分题（初级）

① RabbitMQ 是什么？和 Kafka 的区别？

RabbitMQ 是用 Erlang 写的、实现了 AMQP 协议的消息代理，主打业务消息（订单、事务）。Kafka 是用 Scala/Java 写的分布式日志系统，主打高吞吐日志。RabbitMQ 适合万级 TPS、复杂路由、延迟队列；Kafka 适合百万 TPS、日志、可回溯。

② 什么是 AMQP？

AMQP（Advanced Message Queuing Protocol） 是应用层的开放标准消息协议，跨语言、跨平台。RabbitMQ 实现的是 0-9-1 版本（事实标准），让不同语言客户端能与同一消息中间件通信。

③ 消息队列三大作用？

解耦（系统间不直接依赖）、异步（主流程快速返回）、削峰（突发流量排队）。

④ RabbitMQ 核心组件？

Broker（服务器）、Connection（TCP 连接）、Channel（逻辑通道，复用 TCP）、Exchange（交换机路由）、Queue（队列存储）、Binding（绑定规则）、Routing-Key（路由键）、Producer/Consumer（生产/消费方）、VHost（虚拟主机，多租户隔离）。

⑤ 4 种 Exchange 类型？

direct（精确匹配 routing-key）、fanout（广播，忽略 routing-key）、topic（模式匹配 * 和 #）、headers（匹配消息头，少用）。

⑥ 6 种工作模式？

Hello World（1:1）、Work Queues（多消费者竞争）、Pub/Sub（fanout 广播）、Routing（direct 精确路由）、Topics（topic 模式匹配）、RPC（远程调用）。前 5 个最常用。

进阶题（中级）

⑦ 如何保证消息不丢失？（⭐⭐⭐ 必考）

三层都要做：

  1. 生产者：开启 Publisher Confirm + Return 回调，本地消息表兜底
  2. Broker：Exchange/Queue/Message 三重持久化
  3. 消费者：手动 ACK，处理完才确认，失败 NACK 进死信

⑧ 如何保证消息不重复消费？（幂等性）

Redis SETNX + 数据库唯一约束双重去重。消费者先 SETNX messageId 抢占，成功后再处理业务。数据库兜底，防止 Redis 故障导致漏判。

⑨ 如何保证消息顺序？

单队列 + 单消费者（prefetch=1），并且关闭重投（requeue=false）。多分区（Quorum / 镜像）天然有序。

⑩ 死信队列是什么？什么时候用？

DLX（Dead Letter Exchange） 是处理无法正常消费消息的机制。三种触发：消息被 NACK（requeue=false）、TTL 过期、队列满。典型应用：订单超时未支付自动取消（TTL + DLX）。

⑪ 如何实现延迟队列？

方案 1：TTL + DLX（业务队列 + 死信队列）。方案 2：rabbitmq-delayed-message-exchange 插件（更简单）。RocketMQ 内置 18 个延迟级别，更优雅。

⑫ RabbitMQ 怎么实现高可用？

Quorum Queue（4.x 默认，基于 Raft 强一致）。3 节点集群，挂在任 1 个节点仍能服务。老版本用镜像集群（已废弃）。

⑬ Channel 和 Connection 的区别？

Connection = TCP 长连接（昂贵）。Channel = Connection 上的逻辑通道（轻量）。1 个应用 1 个 Connection，1 个线程 1 个 Channel，避免每条消息都建 TCP。

⑭ 轮询分发 vs 公平分发？

轮询（默认）：平均分消息，不管消费者快慢。公平分发：basicQos(1) + 手动 ACK，能者多劳，先 ACK 的先拿下一条。

⑮ 持久化怎么做的？

Exchange durable=true、Queue durable=true、Message deliveryMode=2。三者缺一不可，否则重启可能丢。

高级题（高级）

⑯ RabbitMQ vs Kafka 怎么选？

业务消息、订单、事务 → RabbitMQ（复杂路由、延迟、ACK）。日志、大数据、百万 TPS → Kafka（高吞吐、Offset 回溯、分区）。阿里系电商强事务 → RocketMQ。

⑰ RabbitMQ 怎么实现分布式事务？

本地消息表 + 定时任务补偿。业务和消息表同一事务写入，发送 MQ 后异步标记已发送。定时任务扫描未发送消息重试。RocketMQ 事务消息（半消息机制）原生支持，更优雅。

⑱ RabbitMQ 怎么保证消息可靠性 100% 不丢？

不可能 100% 不丢，但可以趋近于 100%：① 同步刷盘 + 镜像（Broker 层）；② 至少 3 副本（Raft 协议）；③ 同步双写（生产者等所有副本确认）；④ 消费者手动 ACK + 失败重试。生产环境一般达到 99.99% 即可。

⑲ 消息积压了怎么办？

临时措施：① 紧急扩容消费者（concurrency=10-20）；② 临时关闭非关键功能；③ 跳过历史消息。长期方案：① 优化消费业务；② 异步化 + 批处理；③ 业务分级限流；④ 监控告警。

⑳ 集群脑裂怎么解决？

Raft 协议保证：Quorum Queue 通过 Raft 选举 Leader，只有多数派（≥ N/2+1）才能选主，少数派自动成为 Follower。网络分区恢复后，旧 Leader 自动降级。
