02. 微服务架构演进与核心概念

2.1 架构演进史 🏛️

架构 特点 适用场景
单体架构 所有功能打成一个 WAR/JAR 包，共享一个数据库 小型项目、毕业设计
垂直拆分 按业务拆分成多个应用，每个应用独立部署 中小型项目
SOA 架构 面向服务的架构，ESB 企业服务总线 大型企业内部系统
微服务架构 小而专一的独立服务，去中心化治理 互联网公司、大型复杂业务

2.2 什么是微服务？🌟

微服务架构（Microservices Architecture）是一种将单一应用程序开发为一组 小型服务 的方法，每个服务运行在 自己的进程 中，服务之间通过 轻量级通信机制（如 HTTP RESTful API）进行交互。

9 大核心特征（Martin Fowler 定义）：

  1. 服务组件化：以服务为单位，而非库
  2. 围绕业务能力组织：每个服务对应一个业务能力
  3. 产品而非项目：团队负责整个产品生命周期
  4. 智能端点 dumb pipes：业务逻辑在服务内，通信机制简单
  5. 去中心化治理：每个服务可选最适合的技术栈
  6. 去中心化数据管理：每个服务管自己的数据库
  7. 基础设施自动化：CI/CD、自动化部署
  8. 容错设计：服务可能失败，系统需容错
  9. 演进式设计：系统随业务演进

2.3 单体 vs 微服务：架构图对比

2.4 微服务架构的优缺点 ⚖️

✅ 优点：

  • 独立开发部署，快速迭代
  • 技术栈灵活（每个服务可选最适合的语言/框架）
  • 按需扩展，节约成本
  • 故障隔离，系统整体可用性高

❌ 挑战：

  • 分布式系统复杂性（网络延迟、分区容错）
  • 运维复杂度高（服务数量多、监控困难）
  • 测试复杂度高（集成测试、端到端测试）
  • 数据管理困难（数据一致性、分布式事务）
  • 网络延迟影响性能

4.5 面试要点 🎯

Q：服务注册和发现的流程是什么？

服务启动时向注册中心（Nacos）注册，保存 IP/端口/健康状态。消费者调用时从注册中心拉取服务列表（带本地缓存），通过负载均衡选择实例。服务定期发心跳（5s），超时未发则被剔除（15s 不健康，30s 移除）。

Q：为什么选择 Nacos 而不是 Eureka？

Nacos 支持 AP/CP 切换、内置配置中心、控制台完善、阿里持续维护。Eureka 已停更，Spring Cloud 2020.0.x 之后默认不再集成。

05. 客户端负载均衡：Spring Cloud LoadBalancer

5.1 什么是负载均衡？⚖️

将用户的请求 均匀分配 到多个服务实例上，避免单点压力过大。

两种类型：

  • 服务端负载均衡：Nginx、F5（请求先到负载均衡器，再转发）
  • 客户端负载均衡：LoadBalancer、Ribbon（客户端从注册中心拉取列表，自己选择实例）

5.2 LoadBalancer 内置策略 🎯

⚠️ Ribbon 已停维，Spring Cloud LoadBalancer 是官方推荐替代品。

策略类 策略名称 说明
RoundRobinLoadBalancer 轮询策略 默认，按顺序轮流
RandomLoadBalancer 随机策略 随机选择
RetryLoadBalancer 重试策略 失败后在限定时间内重试
WeightedResponseTimeLoadBalancer 加权响应时间 响应快的实例获得更多请求

06. 声明式服务调用：OpenFeign

6.1 什么是 OpenFeign？📝

OpenFeign 是 Spring 官方的 声明式 HTTP 客户端。你只需要写一个 接口 + 注解，它就能自动帮你发 HTTP 请求。让远程调用像调用本地方法一样简单！

OpenFeign vs RestTemplate：

可读性 高 低

熔断降级 配合 Sentinel 一行配置 需手写

6.3 面试要点 🎯

Q：Feign 是怎么实现远程调用的？

Feign 基于 JDK 动态代理 + 拦截器机制。调用接口方法时，代理会构造 HTTP 请求模板，通过 LoadBalancer 找到目标实例，发起 HTTP 调用，最后反序列化响应。

Q：Feign 如何传递请求头（鉴权信息）？

实现 RequestInterceptor 拦截器，从 RequestContextHolder 中获取当前请求的 Token，加入 Feign 请求头。

7.6 面试要点 🎯

Q：什么是服务雪崩？如何解决？

雪崩：一个服务故障引发级联失败，最终整个系统崩溃。解决方案：熔断（快速失败）、降级（返回兜底）、限流（控制流量）、隔离（线程池/信号量）。

Q：Sentinel 和 Hystrix 的区别？

Sentinel 功能更丰富（限流、热点、系统保护），规则配置可视化（Dashboard），阿里持续维护。Hystrix 已停维。

08. API 网关：Spring Cloud Gateway

8.1 什么是 API 网关？🚪

**API 网关 = 整个微服务系统的”大门”**，所有外部请求都要经过它。

核心作用：

  • 🚏 统一入口：客户端只记一个地址
  • 🛣️ 路由转发：/api/user/** → user-service
  • 🔐 安全认证：统一鉴权
  • 📊 限流熔断：在网关层保护所有服务
  • 📝 日志监控：所有请求日志统一收集

Gateway vs Zuul：

维度 Spring Cloud Gateway ✅ Zuul ❌
底层 WebFlux（响应式、非阻塞） Servlet（阻塞）
性能 高 一般
WebSocket ✅ 支持 ❌ 不支持
维护 Spring 官方 已停维

8.2 Gateway 三大核心概念 💡

概念 作用 示例

Predicate 断言，匹配条件 Path=/api/user/**、Method=GET

Q：网关的作用是什么？为什么需要网关？

统一入口、路由转发、负载均衡、鉴权、限流、日志。没有网关，客户端要记所有服务地址，且安全/限流要在每个服务重复实现。

Q：Gateway 的 Predicate 怎么工作？

Predicate 是断言函数，匹配 HTTP 请求的各种属性（路径、方法、Header、时间等）。匹配上则进入该路由的过滤器链。

09. 配置中心：Nacos Config

9.1 为什么需要配置中心？⚙️

传统方式的痛点：

  • 配置文件散落在各服务，改一个配置要重启 N 个服务
  • 多环境（dev/test/prod）配置管理混乱
  • 配置更新无法实时生效
  • 敏感信息（数据库密码）裸写在文件里

配置中心能干啥？

  • ✅ 集中管理：所有配置在 Nacos 控制台统一管理
  • ✅ 动态刷新：改完配置秒级生效，不用重启
  • ✅ 版本管理：每次修改有历史，可回滚
  • ✅ 多环境隔离：用 Namespace 隔离 dev/test/prod

10. 分布式事务：Seata

10.1 什么是分布式事务？💰

单体事务：@Transactional 搞定（一个数据库）
分布式事务：多个服务、多个数据库，必须保证数据一致

经典场景：电商下单

如果订单创建成功，但库存扣减失败 → 数据不一致 💥

10.2 CAP 与 BASE 理论 📐

CAP 定理（分布式系统的”不可能三角”）：

  • Consistency（一致性）
  • Availability（可用性）
  • Partition Tolerance（分区容错性）

P 必须满足，所以只能 CP 或 AP 二选一。

BASE 理论（CAP 的妥协方案，互联网公司主流选择）：

  • Basically Available（基本可用）
  • Soft State（软状态）
  • Eventually Consistent（最终一致性）

10.3 分布式事务解决方案对比 🔄

方案 一致性 性能 复杂度 适用场景
2PC / XA 强一致 差 中 传统金融
TCC 最终一致 好 高 资金、库存（手动实现）
AT 模式（Seata） 最终一致 好 低 通用业务（自动回滚）
Saga 最终一致 好 中 长流程业务
本地消息表 最终一致 中 中 异步场景
事务消息（RocketMQ） 最终一致 好 中 跨服务异步

💡 学习建议：初学者重点掌握 Seata AT 模式（自动回滚，最简单）。

10.4 Seata 四大核心组件 🧩

角色 英文 职责
TC Transaction Coordinator 事务协调者（Seata Server）
TM Transaction Manager 事务管理器（标注 @GlobalTransactional 的服务）
RM Resource Manager 资源管理器（每个微服务）
XID Transaction ID 全局唯一事务 ID

10.5 Seata AT 模式原理 ⚙️

核心思想：在每个分支事务执行前后做 快照，失败时根据快照回滚。

10.7 面试要点 🎯

Q：Seata AT 模式如何保证一致性？

在每个 RM 执行业务 SQL 前生成 前置镜像（before image），执行后生成 后置镜像（after image）。如果全局回滚，TC 通知 RM 用 before image 反向 SQL 回滚。

Q：为什么不用 2PC？性能问题？

2PC 同步阻塞、锁资源时间长、性能差，不适合高并发互联网场景。AT 模式是异步的，写本地事务即可，性能接近普通事务。

RocketMQ vs RabbitMQ vs Kafka：

特性 RocketMQ RabbitMQ Kafka

14. 实习 / 校招高频面试题（50 题）

💡 面试策略：实习 / 校招问 58 题，初级岗位以基础题（125）为主，资深岗会涉及原理题（26~50）。

🌱 基础概念篇（1~15）

Q1：什么是微服务？和单体应用有什么区别？

微服务是将单一应用拆分为一组小型、独立的服务，每个服务运行在自己的进程中，通过轻量级协议（HTTP/RPC）通信。

区别：

  • 单体：所有功能打一个包，部署简单但耦合严重
  • 微服务：独立部署、技术栈灵活、故障隔离，但运维复杂

Q2：微服务有哪些优缺点？

优点：独立迭代、技术异构、按需扩容、故障隔离
缺点：分布式事务、网络延迟、运维成本、测试复杂

Q3：什么时候该用微服务？

✅ 业务复杂（>5 个核心模块）、团队 > 20 人、需快速迭代、高可用要求
❌ 小项目（<3 人）、原型验证、QPS < 1000

Q4：Spring Cloud 是什么？和 Spring Boot 什么关系？

Spring Cloud 是微服务治理工具集（服务发现/网关/配置），基于 Spring Boot。

  • Spring Boot：构建单个微服务
  • Spring Cloud：协调多个微服务

Q5：微服务核心组件有哪些？

服务注册发现（Nacos）、配置中心（Nacos）、API 网关（Gateway）、服务调用（OpenFeign）、熔断限流（Sentinel）、分布式事务（Seata）、链路追踪（Zipkin/SkyWalking）

Q6：Spring Cloud 版本号怎么选？和 Spring Boot 怎么对应？

看官方版本对应表（如 2023.0.x → Boot 3.2.x）。用 <spring-cloud-dependencies> 统一管理版本。

Q7：什么是 CAP 定理？

分布式系统最多同时满足：

  • Consistency（一致性）：所有节点同一时间看到相同数据
  • Availability（可用性）：每个请求都能收到响应
  • Partition Tolerance（分区容错）：网络分区时仍能工作

P 必须满足，所以是 CP 或 AP 二选一。

Q8：什么是 BASE 理论？

互联网公司对 CAP 的妥协：

  • Basic Available（基本可用）
  • Soft State（软状态，允许中间态）
  • Eventually Consistent（最终一致）

Q9：服务注册中心的作用？

解决”服务之间如何找到彼此”的问题。服务启动时注册自己，调用方从注册中心拉取服务列表（带缓存 + 心跳刷新）。

Q10：CAP 中为什么 P 必须满足？

现代分布式系统中网络故障不可避免。如果 P 不满足，网络一断系统就崩。所以只能在 C 和 A 之间权衡。

Q11：Nacos 和 Eureka 有什么区别？

维度 Nacos ✅ Eureka ❌
一致性 AP+CP 可切换 仅 AP
配置中心 ✅ ❌
维护 活跃 停维

Q12：什么是服务雪崩？如何解决？

一个服务故障引发级联失败。
解决方案：熔断、降级、限流、隔离、幂等设计

Q13：什么是熔断？什么是降级？区别？

  • 熔断：下游故障时，自动切断调用，快速失败（保护下游）
  • 降级：服务异常时，返回兜底数据（保护用户体验）

熔断是”主动断开”，降级是”被动返回”。

Q14：什么是限流？常见限流算法？

限制请求速率，防止系统被打垮。
算法：计数器、滑动窗口、令牌桶、漏桶

Q15：什么是负载均衡？客户端 vs 服务端？

  • 服务端：Nginx、F5（统一入口转发）
  • 客户端：LoadBalancer（消费者自己选实例，少一跳）

🔧 组件原理篇（16~35）

Q16：Nacos 的服务注册流程？

  1. 服务启动向 Nacos Server 发送注册请求（含服务名、IP、端口）
  2. Server 写入注册表
  3. 客户端每 5s 发送心跳
  4. 15s 没心跳 → 标记不健康；30s 没心跳 → 剔除

Q17：Nacos 如何实现配置动态刷新？

客户端启动时拉取配置 + 启动长轮询任务（每 30s 拉一次）。Nacos Server 端用 ConcurrentHashMap 维护变更的 MD5，发现变更立即 push 给订阅的客户端。客户端收到后重新加载 @RefreshScope Bean。

Q18：Ribbon 停维后用什么？Spring Cloud LoadBalancer 怎么选实例？

用 Spring Cloud LoadBalancer（官方维护）。
选实例流程：本地缓存服务列表 → 按策略（轮询/随机）选一个 → 拼 URL → 发起请求

Q19：OpenFeign 的工作原理？

JDK 动态代理 + 拦截器。调用接口方法时，代理对象会：

  1. 解析方法注解（@GetMapping 等）构造 HTTP 请求
  2. 通过 LoadBalancer 选择服务实例
  3. 发起 HTTP 调用
  4. 反序列化响应结果

Q20：Feign 怎么传递请求头（如鉴权 Token）？

实现 RequestInterceptor，从 RequestContextHolder 获取当前请求的 Header，添加到 Feign 请求中。

Q21：Sentinel 和 Hystrix 的区别？

维度 Sentinel Hystrix
隔离 信号量/线程池 线程池
熔断 慢调用/异常比例/异常数 仅异常比例
限流 ✅ QPS/线程数/预热 仅 QPS
维护 阿里 停维

Q22：Sentinel 熔断器的状态机？

三状态：关闭 → 开启 → 半开 → 关闭

  • 关闭：正常调用，统计失败率
  • 开启：快速失败
  • 半开：放行少量请求试探

Q23：Sentinel 的限流规则有哪几种？

  1. QPS 限流：每秒请求数
  2. 并发线程数限流：占用线程数
  3. 预热模式：冷启动慢慢加流量
  4. 排队等待：匀速通过

Q24：Sentinel 热点参数限流是什么？

针对特定参数值限流。比如 getProduct(id=1) 限 100 QPS，但 getProduct(id=hot) 单独限 10 QPS（防止热点商品打爆服务）。

Q25：Spring Cloud Gateway 三大概念？

  • Route（路由）：一个转发规则
  • Predicate（断言）：匹配条件
  • Filter（过滤器）：修改请求/响应

Q26：Gateway 的请求流程？

客户端 → Gateway（断言匹配）→ 前置过滤器 → LoadBalancer 选实例 → 转发到目标服务 → 后置过滤器 → 响应

Q27：Gateway 和 Zuul 区别？

Gateway 基于 WebFlux（响应式、非阻塞），Zuul 基于 Servlet（阻塞）。Gateway 性能更高，支持 WebSocket。

Q28：Gateway 怎么实现限流？

内置 RequestRateLimiter 过滤器，基于 Redis + 令牌桶算法。也可集成 Sentinel。

Q29：Spring Cloud Config 的工作流程？

Config Server 从 Git 仓库拉配置 → 服务启动时从 Server 拉配置 → 通过 /actuator/refresh 手动刷新 → Spring Cloud Bus 自动广播刷新

Q30：Nacos Config 相比 Config 的优势？

  • 控制台友好（Web 操作）
  • 配置变更秒级推送（Config 依赖 Git 轮询）
  • 支持多环境命名空间
  • 配置版本管理和回滚

Q31：分布式事务的解决方案有哪些？

2PC/XA、TCC、AT（Seata）、Saga、本地消息表、事务消息（RocketMQ）

Q32：Seata 有几种事务模式？

四种：AT（自动）、TCC（手动）、Saga（长事务）、XA（强一致）

Q33：Seata AT 模式原理？

在业务 SQL 执行前后生成镜像（before/after image），失败时根据 before image 反向 SQL 回滚。对业务零侵入。

Q34：Seata 三大组件？

  • TC（Transaction Coordinator）：事务协调者
  • TM（Transaction Manager）：事务发起方（带 @GlobalTransactional）
  • RM（Resource Manager）：资源管理器（各微服务）

Q35：RocketMQ 事务消息流程？

  1. 生产者发送 Half 消息（对消费者不可见）
  2. 本地事务执行
  3. 根据本地事务结果，发送 Commit / Rollback
  4. Broker 收到 Commit 后，消费者可见

🎯 架构与设计篇（36~50）

Q36：如何设计微服务的边界？

DDD 领域驱动设计：按业务能力拆分（用户/订单/商品），单一职责，高内聚低耦合。

Q37：微服务之间如何保证数据一致性？

  • 强一致：TCC、AT 模式
  • 最终一致：Saga、本地消息表、事务消息
  • 互联网场景多用最终一致

Q38：什么是幂等性？为什么重要？

同一操作多次执行结果一致。
重要原因：网络重试可能导致重复请求（如支付），必须保证只扣一次款。
实现方案：唯一索引、Token 机制、状态机、乐观锁。

Q39：微服务下如何实现分布式 Session？

  • Token 替代 Session（JWT）
  • Session 集中存储（Redis）
  • Spring Session + Redis

Q40：什么是服务网格（Service Mesh）？

把服务间通信（服务发现、负载均衡、熔断）从应用层抽到独立的Sidecar 代理层（如 Istio + Envoy）。应用无感知，云原生时代的趋势。

Q41：Docker 和 K8s 在微服务中的作用？

  • Docker：容器化打包，每个服务一个镜像
  • K8s：容器编排，自动扩缩容、滚动升级、服务发现

配合使用 = 弹性微服务架构。

Q42：如何设计高可用的微服务架构？

  1. 冗余：服务多实例部署
  2. 隔离：线程池隔离、信号量隔离
  3. 熔断降级：防止雪崩
  4. 异步：MQ 解耦
  5. 限流：保护核心服务
  6. 监控告警：及时发现问题

Q43：什么是服务降级？降级策略有哪些？

服务不可用时返回兜底数据。
策略：返回默认值、返回缓存、调用备用服务、丢弃非核心功能

Q44：微服务如何做权限校验？

  • 网关层：JWT/OAuth2 统一鉴权
  • 服务层：Spring Security + RBAC
  • Token 传递：Feign 拦截器透传用户信息

Q45：什么是链路追踪？为什么需要？

追踪一个请求在多个服务间的完整调用路径。
作用：故障定位（哪个服务慢？）、性能分析（瓶颈在哪？）、服务依赖梳理。

Q46：SkyWalking 和 Zipkin 区别？

维度 SkyWalking Zipkin
接入方式 字节码增强（零侵入） 手动加依赖
性能 更好 一般
国产化 国产 Twitter

Q47：Feign 底层用的什么协议？

HTTP/HTTPS（基于 Ribbon/LoadBalancer 做负载均衡）。可改为 Apache HttpClient 或 OkHttp 提升性能。

Q48：OpenFeign 如何整合 Sentinel？

  1. 开启 feign.sentinel.enabled=true
  2. 在 @FeignClient 指定 fallback 类
  3. 远程调用失败自动走 fallback

Q49：为什么用 Nacos 做配置中心不用 Spring Cloud Config？

Q50：你做的微服务项目遇到的最大挑战是什么？怎么解决的？

答题模板（STAR 法则）：

  • Situation：项目背景（电商系统大促期间）
  • Task：你的任务（解决下单超时问题）
  • Action：采取的行动（用 Sentinel 限流 + 异步 MQ 解耦 + 缓存热点数据）
  • Result：成果（响应时间从 3s 降到 500ms，可用性 99.99%）

项目 1：基于 Spring Cloud Alibaba 的电商微服务系统

项目名称：ljh-mall（基于 mall-swarm 二次开发）

技术栈：

Spring Boot 3.2 / Spring Cloud 2023 / Spring Cloud Alibaba 2023 / Nacos 2.4 / Sentinel 1.8 / Seata 1.8 / MySQL 8.0 / Redis 7.0 / RabbitMQ / Elasticsearch / Docker

  3. 集成 Sentinel 实现商品查询的限流和熔断

  2. 提升响应速度：Redis 缓存 + 异步 MQ，订单接口 P99 从 800ms 降到 200ms

15.2 面试描述：STAR 法则 🎯

STAR 法则 是阿里、字节等大厂面试官最看重的回答框架。

字母 含义 关键词
S Situation 情境 项目背景、业务规模、面临挑战
T Task 任务 你的职责、目标、约束
A Action 行动 怎么做、技术选型、具体方案
R Result 结果 数据化成果、量化指标

范例问题：你做的微服务项目里最有成就感的事？

S：我们之前是个单体应用，代码 30 万行，每次发版要 2 小时，经常因为一个 bug 影响整个系统。

T：我负责把订单模块拆成独立的微服务，3 周内完成迁移，且不能影响线上。

A：

  1. 调研后选 Spring Cloud Alibaba 方案（Nacos + Sentinel + Seata）
  2. 先做双写迁移，新库旧库同步，灰度切流
  3. 引入 Sentinel 做熔断，防止老服务故障拖垮新服务
  4. 用 Seata 解决订单-库存-账户的分布式事务
  5. 完善监控（Prometheus + Grafana）

R：

  • 发版时间从 2 小时降到 15 分钟
  • 订单服务可用性从 99.9% 提升到 99.99%
  • 独立扩容，资源成本下降 30%

15.3 面试常见问题应对 💬

❓ 项目不真实怎么办？

方案：用开源项目二次开发（mall-swarm、mall、vhr 等）+ 加自己的功能模块

  • 加一个新服务（如评论服务）
  • 改一个组件（用 Sentinel 替换 Hystrix）
  • 优化一段代码（加缓存、改 SQL）

❓ 怎么解释技术选型？

模板：**”为什么 A 而不是 B”**

  1. 业务需求（高并发？强一致？）
  2. 团队熟悉度
  3. 社区活跃度 / 维护状态
  4. 性能 / 成本对比

❓ 怎么展示技术深度？

  • 不只说”用了 XX”，要讲”为什么用 XX“
  • 能讲清楚底层原理（如 Seata 的 undo_log 机制）
  • 能说踩过的坑（如 Nacos 集群脑裂、Seata AT 模式的脏写问题）
