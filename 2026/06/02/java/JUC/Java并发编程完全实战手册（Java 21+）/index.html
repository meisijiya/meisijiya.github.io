1.1 进程 vs 线程

核心区别

维度 进程 线程

为什么Java要用线程？

Java的并发模型是基于线程的——Thread类直接对应一个内核线程（1:1模型，Java 19之前）。Java 21+的虚拟线程打破了这一限制（M:N模型，详见第7章）。

1.3 Java内存模型（JMM）

为什么需要JMM？

问题：CPU有多级缓存（L1/L2/L3），多线程下：

  • 一个线程修改了共享变量，其他线程看不见（可见性）
  • 编译器/CPU会重排序优化，导致执行顺序与代码顺序不一致（有序性）
  • 即使同步，多个CPU的缓存不一致（原子性）

JMM = 一套规范，规定了线程如何与主内存、工作内存交互。

JMM 三大特性

特性 含义 解决方案
原子性 一个操作不可被中断 synchronized / Lock / CAS
可见性 一个线程修改后其他线程立即看到 volatile / synchronized / final
有序性 程序执行顺序与代码顺序一致 volatile / synchronized / happens-before

1.4 happens-before 8条规则

happens-before 是 JMM 的核心概念：如果 A happens-before B，则 A 的结果对 B 可见。

# 规则 说明 代码示例
1 程序顺序规则 同一线程，按代码顺序 int a = 1; int b = a; 后者可见前者
2 monitor锁规则 同一锁，unlock happens-before 后来的lock synchronized块串行
3 volatile规则 volatile写 happens-before 后来的读 状态标志位
4 线程启动规则 Thread.start() happens-before 该线程的每个动作 主线程设置 → 子线程可见
5 线程终止规则 线程的所有动作 happens-before 其他线程join()返回 子线程修改 → 主线程可见
6 线程中断规则 interrupt() happens-before 被中断线程检测到中断 略
7 对象终结规则 构造器 happens-before finalize() 略
8 传递性 A hb B, B hb C → A hb C 串联推理

平台线程的问题：

  1. 每个线程 ≈ 1MB 栈空间 + 内核调度开销
  2. 系统线程数有上限（Linux 默认 100万+，但实际几千就开始调度崩）
  3. 阻塞 = 浪费（线程挂起不做事但占资源）
  4. 高并发场景被迫用响应式编程（Reactor/RxJava），代码极其复杂

虚拟线程的解决思路

三种并发模型对比

模型 线程：OS线程 阻塞开销 代码复杂度 代表
平台线程 1:1 高（OS线程挂起） 低 Java 19 之前
异步回调 1:N（事件循环） 低 极高（回调地狱） Node.js、Reactor
虚拟线程 M:N（JVM调度） 低（让出即可） 低（写同步代码） Java 21+

💡 核心洞察：虚拟线程让你写同步阻塞代码，得到异步非阻塞性能。响应式编程的”复杂API”在 Java 21+ 多数场景都不需要了。

第12章：陷阱大全

12.1 Top 20 常见并发陷阱

# 陷阱 表现 解决方案
1 SimpleDateFormat 非线程安全 多线程下日期错乱 用 DateTimeFormatter 或 synchronized
2 Executors.newFixedThreadPool 队列无界 任务堆积 OOM 用 ThreadPoolExecutor 自定义有界队列
3 Executors.newCachedThreadPool 线程数无界 创建过多线程 OOM 同上
4 ThreadLocal 不清理 内存泄漏 用 try-finally 调 remove()
5 synchronized 用 String/Integer 作锁 字符串常量池导致锁串了 用 new Object()
6 volatile 用于复合操作 i++ 仍然非原子 用 AtomicInteger
7 锁内调用外部方法 死锁/超时 缩小锁范围
8 双重检查锁定用旧写法 实例可见性问题 用 volatile 或 Holder 模式
9 异步任务里抛异常没处理 异常”消失” CompletableFuture.exceptionally
10 锁对象本身变化（如集合） 锁失效 锁对象用 final 修饰
11 notify() 唤醒同类等待者 信号丢失 用 notifyAll() 或多个 Condition
12 wait() 在锁外调用 IllegalMonitorStateException 必须先获取锁
13 死锁未发现 应用卡死 jstack 检测；tryLock(timeout) 兜底
14 活锁（Livelock） 任务一直互相让步 加随机睡眠；指数退避
15 饥饿（Starvation） 某些线程一直得不到资源 用公平锁；调整调度策略
16 synchronized 包裹 Thread.sleep 虚拟线程 pinning 改 ReentrantLock；缩小锁范围
17 多个 @Async 用同一个线程池 互相影响 业务隔离用不同线程池
18 线程池未 shutdown 进程无法退出 实现 DisposableBean 或 @PreDestroy
19 CountDownLatch 计数 > 实际线程数 永远不释放 严格 1:1 配对
20 Future.get() 死等 任务卡死 用 get(timeout, unit)
