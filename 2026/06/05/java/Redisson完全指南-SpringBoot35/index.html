一、为什么需要 Redisson？

1.1 一个真实的痛点：秒杀库存超卖

假设你刚学完 Redis，写了下面这段”分布式锁”代码：

🚨 这段代码有 N 个致命缺陷：

  1. 业务执行时间 > 30 秒 → 锁自动过期 → 别人也抢到锁 → 超卖
  2. 客户端崩溃 → 锁永远不释放 → 死锁
  3. 锁过期后，另一个线程拿到锁，原线程 finally 里又 DEL → 误删别人的锁
  4. 没有可重入机制 → 同一个方法递归调用会死锁
  5. 等待锁的线程疯狂自旋 → CPU 拉满
  6. 主从架构下，主节点宕机锁丢失 → 双写问题

这就是为什么你需要一个工业级的分布式锁实现——而 Redisson 就是 Java 生态的事实标准。

二、Redisson 是什么？

2.1 官方定义

Redisson is the Java Client and Real-Time Data Platform for Valkey and Redis. Redisson greatly extends the capabilities of Valkey and Redis by providing additional services and data structures not natively available in either platform.
——Redisson 官方文档

翻译成大白话：

Redisson 是基于 Netty 的 Java Redis 客户端，提供了 60+ 个分布式对象和服务，其中 30+ 是 Redisson 独有（Valkey/Redis 原生没有）。

三、Redisson vs Jedis vs Lettuce

客户端 定位 线程安全 高并发 QPS 分布式对象 适用场景
Jedis 阻塞式同步客户端 ❌（需连接池） ~32K ❌ 简单脚本、工具
Lettuce Netty 异步响应式 ✅ ~46K ❌ 高并发 CRUD
Redisson 分布式服务框架 ✅ ~35K ✅ 60+ 分布式锁/限流/队列/集合

怎么选？

  • 简单 KV 缓存 → Lettuce（Spring Boot 默认）
  • 需要分布式能力 → Redisson
  • 老项目/特殊场景 → Jedis

实战建议：Spring Boot 项目中两者可以共存（Lettuce 跑 RedisTemplate，Redisson 跑分布式锁），但建议统一使用 Redisson 以减少依赖。

十二、面试宝典（20+ 高频题）

⭐ Q1：Redisson 是什么？和 Jedis、Lettuce 区别？

答：Redisson 是基于 Netty 的 Redis Java 客户端，提供 60+ 分布式对象和服务。Jedis/Lettuce 是”Redis 命令的封装”，Redisson 是”分布式对象的抽象“。

⭐ Q2：Redisson 分布式锁如何实现”可重入”？

答：用 Redis Hash 结构，field 是 UUID:threadId，value 是重入计数器。HINCRBY 实现原子自增/自减。

⭐ Q3：看门狗（WatchDog）是什么？默认多长时间？续期频率？

答：后台线程自动续期。默认 30s 过期，每 30s/3=10s 续期一次（续期间隔 = 过期时间的 1/3）。

⭐ Q4：lock()、tryLock()、tryLock(waitTime, leaseTime) 区别？

答：

API 阻塞 看门狗
lock() 永久阻塞 ✅
lock(10, s) 永久阻塞 ❌（指定了 leaseTime）
tryLock() 不阻塞 ✅
tryLock(3, -1, s) 最多等 3s ✅
tryLock(3, 10, s) 最多等 3s ❌

黄金组合：tryLock(waitTime, -1, unit)。

⭐ Q5：看门狗什么情况下会失效？

答：

  1. 指定了 leaseTime → 看门狗不启动
  2. GC 暂停 / 时钟跳跃 → 续期可能不及时
  3. 客户端进程崩溃 → 续期线程消失，30s 后锁自动过期（这是兜底机制）

⭐ Q6：主从架构下分布式锁有什么问题？RedLock 怎么解决？

答：主从异步复制可能导致”幽灵锁”（A 持锁后 Master 宕机，B 在新 Master 也加锁成功）。RedLock 需向 N（≥3）个独立 Master 申请锁，半数以上成功才算获取。但 Redisson 4.x 已弃用 RedLock，改用 RFencedLock。

⭐ Q7：可重入、阻塞、可重入公平锁的 API 区别？

答：

锁类型 API 备注
可重入非公平 getLock 默认，性能最佳
可重入公平 getFairLock FIFO 队列
不可重入（4.x） getNonReentrantLock 防递归误用
读写锁 getReadWriteLock 读共享、写独占
联锁 getMultiLock 多个资源一次性锁
红锁（已弃用） getRedLock 4.x deprecated
围栏锁（4.x） getFencedLock 抗 GC 失效
信号量 getSemaphore 限流/资源池
闭锁 getCountDownLatch 多任务协调

Q8：锁释放时其他线程拿到锁会怎样？

答：抛 IllegalMonitorStateException。应捕获该异常做幂等处理。

Q9：阻塞锁、非阻塞锁、可重入锁 API 区别？

答：阻塞 vs 非阻塞 = 是否无限等待。可重入 = 同一线程可多次加锁。三个维度可组合。

Q10：Redisson 锁比 SETNX 强在哪？

答：10 大能力：互斥、原子性、可重入、自动续期、阻塞唤醒、公平性、集群适配、读模式、写模式、释放校验。

Q11：Redisson 用什么网络框架？

答：Netty 4，基于 NIO 事件循环。

Q12：RRateLimiter 限流原理？

答：基于 Redis 滑动窗口（不是令牌桶）。{name}:permits 是 ZSet，存所有历史授权记录。

Q13：集群模式下锁的 key 如何路由？

答：用 CRC16(key) % 16384 计算 slot。MultiLock 必须用 Hash Tag（如 {order:userId}Lock）保证落到同一 slot。

Q14：如何与 Spring Boot 3.5+ 集成？

答：引入 redisson-spring-boot-starter，配置 spring.data.redis 自动注入 RedissonClient。或手动配置 Config + @Bean。

Q15：生产环境常见事故有哪些？

事故 原因 避免方法
死锁 finally 中 isHeldByCurrentThread() 抛异常，unlock 未执行 移除前置判断，直接 try-catch unlock
锁失效 指定 leaseTime 太短 不要指定 leaseTime
看门狗不工作 连接池耗尽 调整 connectionPoolSize
主从切换丢锁 异步复制 用 RFencedLock 或换 CP 系统

Q16：为什么 if (lock.isHeldByCurrentThread()) 是”画蛇添足”？

答：unlock 的 Lua 脚本已做越权保护。前置判断会额外执行 2 个 Redis 命令，网络抖动时可能抛异常导致 unlock 不执行，反而引发看门狗死锁。

Q17：性能调优关键参数？

答：connectionPoolSize: 64、connectionMinimumIdleSize: 16、timeout: 3000、retryAttempts: 3、threads: 32、nettyThreads: 64。

Q18：为什么用 destroyMethod = "shutdown"？

答：Redisson 内部有 Netty EventLoopGroup、连接池线程、HashedWheelTimer 线程等。Spring 关闭时需显式关闭，否则进程无法正常退出。

Q19：EXPIRATION_RENEWAL_MAP 是什么？

答：全局静态 Map，记录所有正在被看门狗续期的锁。unlock 时必须清理，否则会泄漏 TimerTask。

Q20：Redisson 4.x 的 RFencedLock 是什么？

答：通过 Fencing Token（递增版本号）解决 GC 暂停导致的”客户端自以为持锁但实际锁已过期”问题。每次 lock() 成功返回 token，写入资源时必须带 token，存储系统拒绝旧 token。

十三、生产最佳实践

✅ 必做（DO）

  1. 锁 key 命名空间化：业务:模块:资源ID，如 order:lock:1001
  2. tryLock 必传 waitTime：避免无限等待
  3. finally 中 unlock + 捕获 IllegalMonitorStateException
  4. 锁粒度尽量细：锁单个订单而非整个订单系统
  5. 监控锁等待时间和持有时间：用 Micrometer 上报 Prometheus
  6. 生产环境使用 destroyMethod = "shutdown"
  7. 统一使用 Redisson 客户端：避免与 RedisTemplate 混用

❌ 必避（DON’T）

  1. ❌ 在循环中重复创建 RLock 对象
  2. ❌ Redis password 留空字符串 ""（用 null）
  3. ❌ 同时引入 redisson-spring-boot-starter + 手动 RedissonConfig（冲突）
  4. ❌ 跨线程调用 unlock()（抛 IllegalMonitorStateException）
  5. ❌ 在事务方法上加分布式锁（事务回滚但锁已释放）
  6. ❌ 业务里加 Thread.sleep() 模拟业务
  7. ❌ lock.lock(10, SECONDS) 指定太短的 leaseTime

十四、常见问题排查

14.1 启动报错 Unable to connect to Redis

原因：自动配置默认连 localhost:6379，但你的 Redis 不在那里。

解决：使用手动配置或在 yml 中显式指定 spring.data.redis.host/port。

14.2 YAML 配置的引号问题

14.3 与 Spring Data Redis 冲突

解决：移除 spring-boot-starter-data-redis 依赖，或分开 Bean 名称避免连接池冲突。

14.4 Spring 容器关闭时进程不退出

原因：Redisson 的 Netty 线程未关闭。

解决：使用 @Bean(destroyMethod = "shutdown")。

14.5 看门狗不工作

排查步骤：

  1. 检查是否指定了 leaseTime（指定后看门狗不工作）
  2. 检查连接池是否耗尽
  3. 升级到 3.17+ 修复 NPE bug
  4. 检查 GC 日志，确认无长时间 STW

14.6 大量 IllegalMonitorStateException

原因：锁过期被别人拿走，原线程 unlock 时报错。

解决：

  • 升级到 3.36+
  • 业务耗时做好监控
  • finally 中 try-catch 异常

  10. ✅ 黄金组合：tryLock(waitTime, -1, unit)
