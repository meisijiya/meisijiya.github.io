1. Redisson 是什么 🤔

Redisson（Redis + isson）是架设在 Redis/Valkey 之上的 Java 驻内存数据网格（In-Memory Data Grid，IMDG），由俄罗斯开发者 Nikita Koksharov 主导，目前在 GitHub 上 ⭐ 24.4k+ Star（github.com/redisson/redisson）。

它能做什么：

能力 对应 Redisson 对象 底层 Redis 结构
通用 K/V RBucket String
分布式 Map RMap / RMapCache Hash
分布式 List RList List
分布式 Set RSet Set
分布式 Queue RQueue / RBlockingQueue List
分布式栈 RDeque List
分布式锁 RLock / RFairLock Hash + Lua
分布式原子数 RAtomicLong String + INCR
分布式发布订阅 RTopic / RReliableTopic Pub/Sub + Stream
分布式限流 RRateLimiter ZSet + Lua
分布式布隆过滤器 RBloomFilter Bitmap
分布式排行榜 RScoredSortedSet ZSet
分布式延迟队列 RDelayedQueue ZSet + List
分布式定时任务 RScheduledExecutorService ZSet
分布式集合分片 RClusteredMap 多 Key Hash
分布式远程服务 RRemoteService Pub/Sub
本地缓存 Map RLocalCachedMap Hash + Caffeine

一句话总结：Redisson = Redis 命令的”Java 分布式对象”封装层，让 Java 程序员用面向对象的方式操作 Redis，而不用关心底层的 Lua 脚本和并发问题。

分布式数据结构 ❌ 只有 K/V ❌ 只有 K/V ✅ 50+ 分布式对象
看门狗续期 ❌ ❌ ✅ 默认 30s 锁 + 10s 续期
Pub/Sub 唤醒 ❌ ❌ ✅ 锁释放时通过 Channel 唤醒等待线程

性能 同步阻塞 异步高性能 异步高性能（基于 Netty）

7. 看门狗（WatchDog）原理 ⏱️

看门狗是 Redisson 分布式锁的灵魂特性，解决了”锁过期 vs 业务执行时间”的经典难题。

7.1 问题来源

如果手动设置锁过期时间为 10 秒，但业务执行了 15 秒：

  • T=0s：加锁成功，TTL = 10s
  • T=10s：锁自动过期
  • T=10.001s：另一个线程加锁成功（双重执行）
  • T=15s：原业务执行完，调 unlock() 释放了别人的锁 ❌

7.2 Redisson 的解法

加锁成功后启动一个守护线程，每隔 lockWatchdogTimeout / 3 毫秒执行一段 Lua 脚本，把锁的 pexpire 重置为 lockWatchdogTimeout。

  • **默认 lockWatchdogTimeout = 30 秒**（Config.java#L81）
  • 续期间隔 = 30s / 3 = 10 秒

7.6 看门狗的危险边界

  • GC pause > 续期间隔（10s）：锁可能丢失，必须靠业务幂等兜底

8. RedLock 算法争议与 Redisson 官方态度 ⚔️

这是 Redisson 面试的”高级考点”，也是 2024 年后分布式系统领域的重要话题。

8.1 什么是 RedLock

2014 年，Redis 作者 Antirez 在《A proposal for more reliable locks using Redis》中提出 RedLock 算法，用 5 个完全独立的 Redis 实例 多数派加锁（N/2+1）来提高锁的可靠性。

五步法：

8.2 Martin Kleppmann 的批评（2016 年）

2016 年，分布式系统大神 Martin Kleppmann 发表《How to do distributed locking》，从时序假设角度批评 RedLock 的安全性。

核心论据：

维度 Antirez Kleppmann
进程暂停 GC 停顿可控 GC 暂停可达数十秒，远超 TTL
网络延迟 稳定内网 < 几 ms GitHub 实际发生过 90s 包延迟
时钟漂移 可控 任何”时序上界”假设都脆弱
fencing token 不必要 缺少单调递增 token，存储无法拒绝旧写

📌 Kleppmann 原文核心句：
*”the Redlock algorithm… does not have any facility for generating fencing tokens… if the algorithm were otherwise perfect, it would not be safe to use”*

8.3 Antirez 的反驳

Antirez 在《Is Redlock safe?》中承认应使用 monotonic clock，但坚持 RedLock 在合理假设下是安全的。

10. 布隆过滤器与限流器 🚦

10.1 布隆过滤器（防缓存穿透）

布隆过滤器原理：

  • 用 K 个哈希函数 把元素映射到位数组的 K 个位置，全部置 1
  • 查询时 K 个位置都是 1 → “可能存在“（有误判）
  • 任一位置 0 → “一定不存在“
  • ✅ 插入/查询 O(K)，空间极省
  • ❌ 不能删除（强行删除会破坏其他元素的哈希位）
  • ⚠️ 有误判率（可用 m = -n·lnp / (ln2)² 算位数组大小）

10.2 限流器（令牌桶）

令牌桶 vs 漏桶：

算法 原理 特点 适用场景
漏桶 任意速率进水，固定速率漏水 强制匀速，流量整形 保护下游（如 DB）
令牌桶 固定速率放令牌，拿令牌才能通过 允许突发流量（攒的令牌可一次性消耗） API 限流（Redisson 用这个）

⚠️ 大坑预警：高 QPS（10w+）下纯 RRateLimiter 会成为瓶颈，生产方案是”本地限流 + Redis 限流”双层。

15. 面试题精讲（10 道） 🎤

Q1：Redisson 是什么？和 Jedis、Lettuce 有什么区别？

答案：Redisson 是基于 Redis 的 Java 驻内存数据网格（IMDG），把 Redis 命令封装成 50+ 分布式 Java 对象。Jedis 是阻塞同步客户端，Lettuce 是 Netty 异步客户端，而 Redisson 是”高级 API 库”，解决”分布式场景下需要哪些数据结构和并发原语”的问题。

Q2：Redisson 的看门狗机制是什么？

答案：

  • 触发条件：leaseTime == -1（不传 leaseTime）
  • 默认 TTL：30 秒
  • 续期间隔：lockWatchdogTimeout / 3 = 10 秒
  • 实现：定时器执行 Lua 脚本 pexpire 刷新

Q3：Redisson 的分布式锁怎么实现可重入？

答案：用 Hash 结构 存锁，key = 锁名，field = "UUID:threadId"，value = 重入计数。加锁脚本用 hexists 判断重入，hincrby 自增计数。

Q4：什么是 RedLock？有什么问题？

答案：

  • RedLock：Antirez 提出的多 Redis 节点多数派加锁算法（5 节点加 3 个成功）
  • 问题：
    1. 缺乏 fencing token（Kleppmann 批评）
    2. 时序假设脆弱（GC pause、时钟漂移、网络延迟）
    3. Redisson 4.x 已标记 @Deprecated，推荐 RLock + RFencedLock

Q5：SETNX + Lua 脚本和 Redisson 锁的区别？

维度 SETNX + Lua Redisson RLock
可重入 ❌ 自己模拟 ✅
阻塞 + 唤醒 ❌ 自己写自旋 ✅ Pub/Sub
锁过期续期 ❌ ✅ 看门狗
集群兼容 ❌ ✅
公平/读写锁 ❌ ✅

Q6：RMap 和 Redis Hash 是什么关系？RMap 的本地缓存怎么实现？

答案：

  • RMap = Java 接口，底层 = Redis Hash
  • RMapCache = Hash + 单 key TTL
  • RLocalCachedMap = Hash + JVM 堆内 Caffeine，通过 Pub/Sub 失效多节点本地缓存

Q7：布隆过滤器的原理？Redisson 的布隆过滤器怎么用？

答案：

  • 原理：K 个哈希函数 → 位数组 K 个位置
  • 特点：插入/查询 O(K)，空间极省，不能删除，有误判率
  • Redisson 特别：用 128-bit Highway 哈希，误判率更低
  • 使用场景：防缓存穿透

Q8：限流器的令牌桶和漏桶原理？RRateLimiter 是哪种？

答案：

  • 令牌桶：固定速率放令牌，允许突发流量（攒的令牌可一次用完）
  • 漏桶：强制匀速（流量整形）
  • RRateLimiter = 令牌桶

Q9：分布式延迟队列怎么实现？有什么应用场景？

答案：

  • 底层：ZSet（存到期时间戳） + RBlockingQueue（到期后转移）
  • 应用：订单超时关闭、红包 24h 未领退回、定时提醒
  • 注意：Redis 崩溃数据丢失，金融场景用 RabbitMQ 延迟插件

Q10：看门狗的默认 30s 能不能改？

答案：

续期间隔 = 15s / 3 = 5 秒。

⚠️ 生产经验：调小会让续期频率变高（5w+ 锁时可能打爆 Redis），建议保持默认或适度调大。

附加高频题（精选 3 道）

Q11：分布式锁的锁过期了，业务还没执行完怎么办？

场景 解决方案
用 lock() 不传 leaseTime ✅ 看门狗自动续期
手动设了 leaseTime ❌ 必须改回不设
RedLock 5 节点 ⚠️ 业务执行前再”续租”
GC pause > 续期间隔 ⚠️ 必须靠业务幂等兜底
任何场景 ✅ 业务唯一索引、状态机、消息去重表

Q12：主从架构下锁丢失怎么办？

方案对比：

方案 原理 缺陷
WAIT 命令 强制 N 个从库同步 Redis 7+ 才稳定
RedLock 5 个独立 master 多数派 已被 Redisson 废弃
RFencedLock 单调递增 token 业务侧需改造
ZooKeeper ZAB 强一致 + zxid 性能差一个数量级
业务幂等 DB 唯一索引 真正兜底

Q13：Redisson 锁的”非可重入”和”可重入”区别？

  • 可重入（RedissonLock）：第二次进入 → hincrby 计数 +1，可递归调用
  • 非可重入（RedissonNonReentrantLock）：第二次进入 → Lua 抛错 IllegalMonitorStateException，防止代码意外重入

16. 版本演进与未来展望 🚀

本节以本文基线（Redisson 3.52.x + Spring Boot 3.5 + JDK 17）为锚，简要介绍 Redisson 的版本演进路线，帮助你判断何时升级、如何升级。

16.1 3.52.x 之前的重要版本（演进脉络）

时间 版本 关键节点
2024-05 3.27.2 Spring Boot 3.3 集成稳定版
2024-11 3.32.0 Spring Boot 3.4 集成
2025-05 3.45.0 Spring Boot 3.5 适配（本文基线起点）
2025-12 3.50.x 3.x 末期小版本，修复若干 Netty 兼容性问题
2026-03 3.52.x 当前推荐生产版本（3.x 最终稳定分支）

💡 演进规律：Redisson 3.x 走”小步快跑”路线，每 1-3 个月发一个版本，本文基线 3.52.x 是 3.x 末班车，生态最稳定。

16.2 未来版本展望（4.x）

⚠️ 4.x 已发布但生态仍在迁移，生产项目不建议立即跟进。

维度 3.52.x（本文基线） 4.x（未来）
JDK 最低要求 8+ 11+
Netty 版本 4.1.x 4.2+
Spring Boot 支持 3.3 ~ 3.6 4.0+（需要重新适配 spring-data-redis）
主体 API 50+ 分布式对象 相同，完全兼容 3.x 用法
破坏性变更 — 较少，主要是依赖升级和模块拆分
新增特性 — VectorSet（AI 向量）、TimeSeries（时序）、JSON Store、ReliableQueue
社区资料 ⭐⭐⭐⭐⭐ 丰富 ⭐⭐ 仍在积累

📌 关键结论：本文所有 API（RLock / RMap / RBucket / RBloomFilter / RRateLimiter / RScoredSortedSet / RDelayedQueue / RScheduledExecutorService / RFencedLock 等）在 3.52.x 和未来 4.x 中完全一致，今天学的代码到 4.x 仍能直接使用。

16.3 何时升级 4.x？

场景 建议
在用 3.52.x + Spring Boot 3.5 + JDK 17 ✅ 保持现状，无需升级
计划升级到 Spring Boot 4.0 再考虑 4.x
需要 VectorSet / TimeSeries（AI / 监控） 评估 4.x
新项目启动 仍推荐 3.52.x（生态最稳），除非有 4.x 专属需求

16.4 Community 版 vs PRO 版（与版本无关）

能力 Community PRO（付费）
基础数据结构（RMap / RLock / RQueue 等） ✅ ✅
看门狗、Pub/Sub、FencedLock ✅ ✅
Spring Cache 基础版 ✅ ✅
Spring Cache LocalCache（Caffeine 加速） ❌ ✅
Spring Cache 数据分片 ❌ ✅
RedissonClusteredMap（集群分片 Map） ❌ ✅
Valkey / Redis 企业版 ❌ ✅
商业技术支持 ❌ ✅

📌 90% 业务场景 Community 版完全够用，PRO 版主要解决”本地缓存+集群分片”的极致性能。

16.5 一句话总结

🎯 学 3.52.x 就对了——3.x 的 API 体系是 Redisson 10 年沉淀的精华，未来 4.x 也不会颠覆。本文所有代码示例（RLock / RMap / RBloomFilter / RFencedLock 等）在 3.52.x 直接可用，向 4.x 升级时零代码迁移成本。
