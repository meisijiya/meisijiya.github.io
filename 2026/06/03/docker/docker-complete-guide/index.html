🎬 第一章：为什么要学 Docker

1.1 真实场景：你为什么要学 Docker

讲个真实故事：我室友去年找 Java 后端实习，简历上写了”使用 Docker 部署个人项目”。二面面试官问：”你用 Docker 部署时，遇到 max virtual memory areas vm.max_map_count [65530] is too low 这个报错怎么解决的？”

他当场愣住，因为他项目里 Elasticsearch 那个坑是 ChatGPT 帮他修的，自己完全没搞懂原理。最后面试挂了。

这就是典型的”让 AI 部署但自己看不懂”的痛点。Docker 已经不是加分项，而是后端/运维/算法岗的入门券。

1.2 学完 Docker 你能搞定这些事

场景 学 Docker 前 学 Docker 后
部署开源项目 “我本地能跑，服务器上跑不起来，环境不一致 😭” docker-compose up -d 一键启动 ✅
找实习简历 “熟悉 Java 基础” “用 Docker Compose 部署过包含 MySQL/Redis/Nginx 的完整项目”
校招面试 答不出容器与虚拟机的区别 聊 namespace/cgroups/UnionFS，赢麻了
工作第一周 折腾环境三天 clone 仓库 → docker compose up → 完成环境搭建
毕设演示 “老师我能演示一下吗？需要先装一堆环境” “老师您看，浏览器输入 localhost 就行”

🧠 第二章：5 分钟搞懂 Docker 核心概念

2.1 一句话讲清 Docker

**Docker 就是一个”应用打包与运行的标准化工具”**——把你的代码、依赖、配置、运行环境一起打包成”镜像”，然后在任何机器上一键启动”容器”运行。

2.2 三个核心概念（用 Git 类比）

Docker 概念 类比 Git 作用 命令
镜像 Image 代码仓库（只读） 应用的”快照模板” docker images
容器 Container 代码运行实例 镜像运行起来的进程 docker ps
仓库 Registry GitHub 存放和分发镜像 Docker Hub / 阿里云

🎯 记忆口诀：镜像是死的，容器是活的，仓库是邮局。

2.3 一次完整的”代码 → 部署”流程

2.4 Docker vs 虚拟机（一图搞懂）

维度 虚拟机 VM Docker 容器
启动速度 30-60 秒 1-3 秒
体积 几 GB 几十 MB
性能损耗 5-10% <1%
隔离性 强（独立内核） 弱（共享内核）
资源占用 重 轻
本质 模拟整个硬件 隔离的进程

🎯 面试话术：容器本质是宿主机上的普通进程，被 namespace（命名空间）和 cgroups（控制组）”包裹”出隔离的”假象”。

症状：

排查步骤：

步骤 命令 说明
1 检查托盘鲸鱼图标 Docker Desktop 是否在运行
2 wsl -l -v 确认 WSL2 已安装
3 临时设置 socket export DOCKER_HOST=unix:///var/run/docker.sock
4 永久生效 echo 'export DOCKER_HOST=unix:///var/run/docker.sock' >> ~/.bashrc
5 重启 Docker Desktop Settings → Troubleshoot → Restart

踩坑 3️⃣：项目放在 /mnt/c 后构建/运行极慢

症状：docker build 或 npm install 在 /mnt/c/Users/... 路径下要等 10 分钟。

原因：WSL2 与 Windows 文件系统（NTFS）的跨文件系统 I/O 开销巨大。

/mnt/c/Users/...（Windows NTFS） ⭐ ❌

解决：

踩坑 5️⃣：WSL2 内存爆满，Docker 卡死

症状：开了 Docker 后 Windows 内存占用飙升到 90%+。

指令 作用 示例

8.5 Dockerfile 编写最佳实践

实践 原因 收益
使用 alpine 基础镜像 体积小（5-10MB） 拉取快、传输快

🎯 本章节专门为找实习准备。所有题目均来自 2024-2026 年大厂面试题库。

模块一：Dockerfile & 镜像优化（6题）

Q1. 什么是多阶段构建？为什么是最佳实践？

英文：What is a multi-stage build and why is it a best practice?

答案：
多阶段构建在单个 Dockerfile 中使用多个 FROM 指令，每阶段可选择性地复制产物到下一阶段。典型用法：第一阶段用完整构建环境（JDK/Node）编译，第二阶段仅将编译产物复制到 minimal 镜像（如 alpine/distroless）。优势：镜像体积减少 80%+、移除构建工具提升安全性、避免依赖泄漏。生产级 Node.js 镜像从 ~1.2GB 降至 ~150MB 是常见案例。

追问：多阶段构建中如何传递编译产物？COPY --from=0 的语法细节？

Q2. Docker 构建缓存如何工作？如何策略性地打破缓存？

英文：How does Docker build cache work, and how to strategically bust the cache?

答案：
Docker 逐条执行 Dockerfile 指令，每条指令检查是否有可复用缓存层。若指令及依赖文件未变，则复用。策略：将变化频率低的指令放前面（依赖安装），频率高的放后面（源码复制）。示例：先 COPY package*.json + RUN npm ci，再 COPY .。修改 package.json 才重建依赖层，源码变动不影响依赖缓存。

Q3. COPY 和 ADD 指令的区别？何时用哪个？

英文：Difference between COPY and ADD in Dockerfile?

答案：

  • COPY 是纯本地文件复制
  • ADD 多了两个特性：1) 可从远程 URL 复制文件；2) 自动解压 .tar.gz

最佳实践：优先用 COPY，除非确实需要 tar 自动解压。ADD 用于远程 URL 会增加镜像不可预测性。

Q4. 什么是 Distroless 镜像？安全收益是什么？

英文：What are distroless images and their security benefits?

答案：
Distroless 是 Google 提供的极简基础镜像，仅含应用及其运行时依赖，不含 shell、package manager 或其他 OS 工具。安全收益：极大缩小攻击面——即使攻击者拿到容器 shell，也无任何命令可用（如 curl/wget/ls）。典型镜像 gcr.io/distroless/static-debian12。

追问：Distroless 和 Alpine 的区别？如何选型？

Q5. 如何减少 Docker 镜像的层数？

答案：
每条 RUN/COPY/ADD 都产生新层。优化方式：用 && 合并相关命令。

Q6. ONBUILD 指令的使用场景？

答案：
ONBUILD 为镜像添加”触发指令”，在该镜像作为其他构建的基础镜像时执行。典型场景：创建通用基础镜像，自动复制源码而无需在每个子 Dockerfile 重复 COPY。

模块二：容器核心原理（6题）

Q7. Docker 如何利用 Linux namespace 和 cgroups 实现容器隔离？

答案：

  • Namespace（命名空间）：提供隔离的”虚拟化视图”——pid 隔离进程ID、net 隔离网络栈、mnt 隔离文件系统挂载点、user 隔离用户ID等
  • Cgroups（控制组）：限制资源使用——管理 CPU、内存、I/O 上限，防止单一容器耗尽宿主机资源

容器本质是宿主机上的普通进程，被多层隔离和资源限制”包裹”。

Q8. docker exec 和 docker attach 的区别？

答案：

  • docker attach：将终端 STDIO 连接到容器主进程（PID 1），类似”恢复”主进程。退出可能导致主进程停止，容器终止
  • docker exec：在已运行容器内新建进程，用于调试/检查，不影响主进程

Q9. Docker 镜像分层和 UnionFS 工作原理？

答案：
Docker 镜像由多层只读层堆叠组成，每条 Dockerfile 指令产生新层。创建容器时，Docker 在只读层堆栈上添加一层薄薄的可写层。UnionFS（如 OverlayFS）将多层合并为统一视图。写操作触发”写时复制”（Copy-on-Write）：修改下层文件时，先将该文件复制到可写层再修改。优势：容器创建极快，无需复制整个文件系统。

Q10. Docker daemon 的角色是什么？

答案：
Docker daemon 是持久运行的后台进程，管理所有 Docker 对象。它监听 Docker API 请求（来自 CLI 等客户端），负责构建、运行、分发容器。底层任务包括：创建网络、管理存储卷、与内核交互创建隔离容器环境。dockerd 启动时会启动 containerd 子进程。

Q11. Docker 镜像和容器的区别？

答案：

  • 镜像：只读、静止的模板，含应用及其所有依赖，是创建容器的蓝图，由多层只读层构成
  • 容器：镜像的可运行实例，是活着的进程，拥有自己的隔离文件系统、网络、进程空间。同一个镜像可运行多个容器

Q12. docker prune 命令的作用？

答案：
清理未使用的 Docker 资源。默认删除：所有已停止容器、不被任何容器使用的网络、悬空镜像（无 tag 且未被引用）。常用 flag：-a 删除所有未使用镜像，--volumes 删除未使用卷。用于回收磁盘空间。

模块三：网络（4题）

Q13. 解释 Docker 网络驱动：bridge/host/overlay 的区别？

答案：

  • bridge（默认）：创建私有内部网络，容器间可通过名字 DNS 通信。需用 -p 映射端口到宿主机
  • host：移除网络隔离，容器共享宿主机网络栈，容器内端口直接暴露在宿主机端口上
  • overlay：分布式网络，跨多台 Docker 主机通信，用于 Docker Swarm 多主机编排

Q14. 暴露端口（EXPOSE）和发布端口（-p）的区别？

答案：

  • EXPOSE（Dockerfile）：文档性元数据，仅声明容器监听端口，不实际开放或映射
  • -p（docker run）：实际创建防火墙规则，将宿主机端口映射到容器端口，使外部可访问

Q15. Docker 内嵌 DNS 在用户自定义网桥网络中的工作原理？

答案：
Docker 在网桥网络运行内嵌 DNS 服务器。容器按名字访问另一容器时（如 ping database），DNS 服务器拦截请求，在内部注册表中查找该名字，解析为正确的内部 IP。需注意：默认 bridge 网络不支持容器间 DNS 按名字解析，必须使用用户自定义网络。

Q16. 什么是 macvlan 网络？适用场景？

答案：
macvlan 允许为容器分配 MAC 地址，使其直接出现在物理网络上。容器从局域网 DHCP 服务器获取独立 IP。适用场景：遗留应用期望直接连接物理网络、监控工具需低层级网络流量嗅探。

模块四：存储与卷（4题）

Q17. Docker volumes vs bind mounts？如何选择？

答案：

  • Volumes：Docker 完全管理，存储在 /var/lib/docker/volumes/，与宿主机解耦。可移植、可通过 CLI 管理，是生产数据持久化的推荐方式
  • Bind Mounts：将宿主机文件/目录直接映射进容器，路径任意。适合：共享配置文件、本地开发源码热更新

Q18. 什么是 tmpfs mount？何时使用？

答案：
tmpfs 是存储在宿主机内存中的临时文件系统，不写入磁盘。容器停止时自动移除。适用场景：存储临时非持久状态、敏感数据（不希望落盘）、需要高性能但不必持久化的数据。

Q19. 什么是孤儿卷（orphaned volumes）？如何清理？

答案：
孤儿卷是已解除与任何容器关联的 Docker 卷。随着容器创建销毁累积，占用磁盘空间。可通过 docker volume prune 清理。

Q20. 数据库运行在 Docker 中需要注意什么？

答案：
数据库有大量顺序写入和 fsync 操作。OverlayFS 等存储驱动为每次写入增加写时复制和 fsync 开销，显著增加延迟。最佳实践：

  • 使用命名卷映射到高速存储路径
  • 或直接使用托管数据库服务（RDS/Cloud SQL）而非常驻容器
  • 始终设置 --memory 和 restart: unless-stopped

模块五：Docker Compose（3题）

Q21. depends_on 和 healthcheck 控制启动顺序的区别？

答案：
depends_on 仅控制启动顺序，不等待依赖”就绪”。可能 API 容器在 DB 还未接受连接时就启动，导致启动失败。healthcheck 更健壮：定义检查命令验证服务真实健康状态。

Q22. 多 Compose 文件间如何共享通用配置？

答案：
使用多文件合并。Compose 自动读取 docker-compose.override.yml 合并到主文件。典型模式：

  • docker-compose.yml：核心服务定义
  • docker-compose.override.yml：本地开发配置
  • docker-compose.prod.yml：生产环境配置

Q23. Docker Compose 中 .env 文件的作用？

答案：
.env 定义环境变量，Compose 自动读取并注入到 docker-compose.yml 中替换变量。用于管理环境相关配置（镜像 tag、外部端口等），避免硬编码。

模块六：安全（5题）

Q24. 什么是 rootless mode？解决什么安全问题？

答案：
Rootless mode 让 Docker daemon 和容器以非 root 用户运行。标准模式下 daemon 以 root 运行，容器逃逸攻击者可能获得宿主机 root 权限。Rootless 模式下逃逸只能获得运行 daemon 的非特权用户权限，极大限制破坏力。实现依赖 user namespace remapping。

Q25. 如何限制容器的 Linux capabilities？

答案：
Linux capabilities 将 root 权限拆分为细粒度权限。最佳实践：先丢弃所有，再用 --cap-add 仅添加必需权限。

Q26. 如何扫描 Docker 镜像中的已知漏洞？

答案：
常用工具：Trivy（开源、轻量）、Snyk（企业级）、Docker Scout（Docker 原生）。

建议：扫描时机 = 构建时 + 推送前 + 定时扫描运行中镜像。

Q27. Docker 中管理 secrets 的最佳实践？

答案：
禁止：将 secrets 放入 Dockerfile 或纯环境变量。推荐：

  • Docker Swarm：docker secret，加密存储
  • Kubernetes：K8s Secrets
  • 生产环境：集成 HashiCorp Vault / AWS Secrets Manager

Q28. Dockerfile 中 USER 指令的作用？为什么重要？

答案：
USER 设置运行镜像的用户（UID）。关键安全实践：创建非 root 用户并用 USER 切换。容器内以非 root 用户运行限制了应用被攻陷后的破坏范围。

模块七：运行时底层（6题）

Q29. Docker、containerd、runc 的关系？为什么 K8s 弃用 dockershim？

答案：

  • runc：OCI 参考实现，低级容器运行时，与内核交互创建/运行容器
  • containerd：高级运行时，管理容器生命周期、镜像传输、存储网络
  • Docker：完整生态封装，自身内部使用 containerd
  • dockershim：K8s 早期内置桥接，因 Docker 比 K8s 更早出现未实现 CRI，K8s 1.24+ 移除

Q30. CMD 和 ENTRYPOINT 的区别？最佳实践用法？

答案：

  • ENTRYPOINT：配置容器为可执行文件，不易被覆盖
  • CMD：为 ENTRYPOINT 提供默认参数，可被 docker run 参数覆盖

最佳实践：组合使用——ENTRYPOINT 指定可执行文件，CMD 提供默认参数

❓ 附录 B：常见问题 FAQ

Q1. 容器和镜像到底什么关系？

A：镜像是”死”的模板，容器是”活”的实例。一个镜像可以创建多个容器，容器删除不影响镜像。

Q2. 为什么 docker run 后容器立刻退出？

A：容器需要前台运行的进程。如果 CMD 指定的命令很快就执行完（如 echo hello），容器会立即退出。解决：加 -d 后台运行，或确保主进程是长驻的（如 nginx、node server.js）。
